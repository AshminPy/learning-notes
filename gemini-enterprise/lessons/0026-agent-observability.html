Agent Observability

Lesson 25's simulation happens before launch, against synthetic traffic you fully control. The moment a real agent is serving real users, you need the production equivalent: Agent Observability. Same underlying idea — a trace-level record you can inspect — but now for traffic you don't control and can't predict.

Mental model: a trace is a flight's black-box recorder; the Observability dashboards are the control tower's radar screen. When one flight has a problem, you pull that one flight's recorder — a single trace, a single session. When you want to know "is the whole fleet getting slower this week," you don't listen to a thousand individual recorders one at a time — you look at the tower's aggregate view. That predicts something concrete: a spike in overall p95 latency belongs in the Overview dashboard's aggregate metrics, but "why did this one user's refund request take 12 seconds" belongs in that single trace's span list — reaching for the wrong one wastes real debugging time.

Three signals: metrics, traces, logs

Per the platform's observability docs, agents emit telemetry in OpenTelemetry format to Google Cloud's observability storage — built-in platform components emit this automatically (Model Armor, for example, natively provides standardized telemetry for its own policy interceptions). The platform "relies heavily on the OpenTelemetry Semantic Conventions for generative AI systems to standardize how generative AI telemetry is captured, structured, and reported," which is what lets a multi-step workflow involving models, tools, and retrieval get described in one universal, vendor-agnostic format instead of a bespoke one per agent.

Six dashboards in the Observability tab

Selecting a specific agent from the Agent Registry opens an Observability tab with six targeted dashboards:

  • Overview — sessions, turns per session, invocations, token consumption (input/output), traffic volume, latency percentiles (p50/p95/p99), and error rates.
  • Evaluation — the Online Monitors from Lesson 24: response quality, safety, hallucination rate, and tool effectiveness, scored continuously on real traffic.
  • Models — per-foundation-model breakdown: p95 latency, call counts, errors, quota failures, token usage.
  • Tools — external tool latency, call frequency, error rates, and instances where no tool was invoked at all.
  • Usage — infrastructure metrics: container CPU/memory allocation and token consumption.
  • Logs — filterable raw logs with severity, timestamps, and execution summaries.

Traces: session, trace, and span views

A trace is "a factual, immutable record of the agent's behavior, including model inputs, responses, and tool calls." A trace is made of spans — individual operations like a foundation-model call, an API request, or a tool execution — each carrying its own inputs, outputs, latency, and status code. The Traces tab offers three levels: Session view (executions grouped by user session), Trace view (a single end-to-end request), and Span view (the granular list of operations inside it) — plus a separate Topology tab showing how agents depend on each other. None of this is automatic: it requires the Cloud Trace API, Cloud Logging API, and Telemetry API enabled on the project, the agent actually configured to send trace data, and IAM roles like Cloud Trace User and Logs Viewer to view it.

Try it

Q1. You want to know whether your agent's overall error rate has been creeping up over the past week across all users. Do you check a single trace, or the Overview dashboard?

The Overview dashboard — error rate over a week, across all users, is an aggregate metric. A single trace only tells you about one specific session, not the whole fleet's trend.

Before revealing: a user reports "the agent didn't use my calendar tool at all today." Which of the six dashboards would you check first, and what would you look at next to confirm it?

Reveal the approach

Start with the Tools dashboard's "no tool invoked" instances metric to see if this is a pattern, not just one user. Then confirm on that specific user by pulling their Session view for the day, drilling into the relevant Trace, and checking the Span view to see whether the model actually chose not to call the tool, or called it and it silently failed.

Common mistake: assuming observability is "free" the moment an agent is deployed. It isn't automatic without the prerequisite APIs enabled and the agent configured to emit telemetry — Cloud Trace API, Cloud Logging API, Telemetry API, plus the right IAM roles. A freshly deployed agent that hasn't had these enabled will serve real traffic while producing zero traces, which looks identical to "the platform is broken" and is actually "observability was never turned on."

A controlled failure

# Agent deployed and serving real users for the past hour.
# You open the Traces tab expecting to see today's sessions.

Predict first: the Traces tab shows nothing for the last hour, even though the agent is definitely handling live requests — is this a platform bug? Observe: check whether Cloud Trace API, Cloud Logging API, and Telemetry API are actually enabled on the project, and whether this specific agent's deployment is configured to send trace data — none of that is automatic. There's also no retroactive backfill: traffic served before telemetry was wired up produces no historical trace, no matter how long you wait after enabling the APIs afterward.

Production best practices

Production note: the six dashboards serve different roles differently — an on-call engineer watches Overview and Tools for anomalies and drills into a specific Trace to root-cause one incident; a quality or product owner watches the Evaluation dashboard's Online Monitors for drift; a platform team watches Usage for cost and capacity. Governance features you enabled earlier in this course show up here for free — Model Armor's policy interceptions (Lesson 20) emit their own standardized telemetry automatically, so a governance decision and its performance cost are visible in the same place, not two separate systems you have to cross-reference by hand.

Exam and interview notes

No certification currently exists for this platform (confirmed 2026-08-06) — this is real production-operations skill, not exam trivia.

Interview Q: "A user says an agent gave a wrong answer at 2:14pm yesterday. How do you find out what actually happened, without guessing?" A: Pull that specific session in the Traces tab — Session view to find the right session, Trace view for the exact request, Span view for the precise model inputs, outputs, and tool calls recorded at that timestamp. A trace is an immutable factual record, not a reconstruction pieced together from memory or aggregate logs.

Recap
  • Agent Observability captures three signals — metrics, traces, and logs — in standardized OpenTelemetry format.
  • The Observability tab has six dashboards: Overview, Evaluation, Models, Tools, Usage, and Logs, each answering a different aggregate question.
  • A trace is an immutable per-session/per-request record made of spans; Session, Trace, and Span views let you zoom from "which session" to "which exact operation."
  • Telemetry isn't automatic — it needs the Cloud Trace, Cloud Logging, and Telemetry APIs enabled and the agent configured to emit data, with no retroactive backfill for traffic served before that.

  • What has to be true before a deployed agent produces any traces at all?
