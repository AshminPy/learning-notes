Agents and Instructions

Lesson 4 got one agent running with four fields — model, name, description, instruction — and one closing question: which single field would you change to alter its behavior? You already guessed instruction. This lesson is why that guess was right, and what the other three fields are actually for.

Mental model: if the model (Lesson 2) is the employee's brain, the instruction is their job description and standing orders — the document that turns a generically-capable brain into someone doing one specific job, with one specific personality, inside one specific set of limits. That predicts something concrete: two agents built on the exact same model, with the exact same tools, can behave completely differently — one terse and refusing off-topic questions, one chatty and permissive — purely because their instruction text differs. Nothing about the model changed; only the standing orders did.

Where this fits

ADK Agent   (google.adk.agents.llm_agent.Agent)
 ├── name           required — unique id, avoid reserved words like "user"
 ├── model           required — the reasoning engine, e.g. gemini-flash-latest
 ├── instruction     ← you are here — the system prompt: goal, persona, constraints
 ├── description     optional but recommended — how OTHER agents route to this one (Lesson 8)
 └── tools[]                                    — what the agent can DO (Lesson 6)

Lesson 4 showed you all five fields at once without explaining four of them. This lesson slows down on name, model, instruction, and description; Lesson 6 does the same for tools.

Name: not just a label

An agent's name is "a unique string identifier crucial for internal operations, especially in multi-agent systems," per ADK's own guidance. The documentation is specific about two things: choose descriptive names (customer_support_router, not agent1), and avoid reserved names — user being the one explicitly called out, because conversational roles like "user" and "model" are already meaningful identifiers inside the framework's own turn-taking. Naming an agent something already reserved is exactly the kind of mistake that looks fine until a multi-agent system (Lesson 8) tries to route a task by name and collides with it.

Model: swappable, not fixed

The model field names the reasoning engine as a plain string, like "gemini-flash-latest". Lesson 2 already made the key point: the model is a component of the agent, not the agent itself — Lesson 13 (Phase D) covers how and why you'd swap it for a different one without touching instruction or tools at all.

Instruction: the actual system prompt

Per ADK's own guidance, the instruction communicates the agent's core goal and task, its personality or persona, behavioral constraints, when and why to use specific tools, and desired output formats. The documentation's own quality bar is "Clear and Specific" — vague instructions like "be helpful" give the model nothing to actually constrain its behavior against. Instructions also support dynamic state substitution using {var} syntax, so the same instruction template can inject session-specific values (Lesson 10 covers session state in full) without hand-writing a new instruction per conversation.

Description: for other agents, not for you

The description field is easy to mistake for documentation of your own. Its real audience is other LLM agents deciding whether to route a task to this one — a concise, accurate description is what makes automatic multi-agent routing (Lesson 8) actually work. An agent with a vague or missing description is invisible to that routing logic, even if its instruction is excellent.

Try it

Q1. You write an agent with a perfect instruction but leave its description blank, then plug it into a multi-agent system that routes tasks by description. What breaks?

Routing to that agent breaks or becomes unreliable — the router (Lesson 8) decides where to send a task based on description, not instruction. A great instruction the router never sees might as well not exist for routing purposes.

Now, before revealing: could you name an agent user and have ADK silently accept it with no problem?

Reveal the answer

No — ADK's own docs explicitly call out user as a reserved name to avoid, because it already means something specific in the framework's conversational turn-taking. This is exactly the kind of thing that only surfaces once a multi-agent setup tries to reference the name.

Common mistake: writing an instruction that only states the goal ("Answer questions about the weather") with no persona, constraints, or tool guidance. That's technically an instruction, but it leaves the model to improvise everything else — tone, refusal behavior, when to call a tool versus answer from memory. ADK's own "Clear and Specific" guidance exists precisely because an underspecified instruction produces inconsistent agent behavior across otherwise-identical runs.

A controlled failure

weak_agent = Agent(
    model='gemini-flash-latest',
    name='weather_agent',
    instruction="Answer questions about the weather.",
    tools=[get_current_time],   # a time tool, not a weather tool
)

Predict first: a user asks this agent for the current time in Tokyo. Does the instruction's narrow framing ("weather") stop the model from using the get_current_time tool it was actually given? Observe: not reliably — the model reasons over both its instruction and its available tools, and an instruction that doesn't explicitly scope tool usage leaves room for the model to call a tool that contradicts its own stated purpose. The fix isn't removing the tool; it's an instruction that states constraints explicitly ("only answer weather questions; if asked something else, say so") instead of leaving the boundary implicit.

Production best practices

Production note: teams that maintain many agents standardize their instruction structure the same way they'd standardize a code style guide — goal, persona, constraints, tool-usage guidance, output format, in that fixed order — so any engineer can read an unfamiliar agent's instruction and immediately know where to look for a given kind of rule. An instruction that's just a paragraph of prose is harder to audit and harder to diff in code review than one with that consistent internal structure.

Exam and interview notes

No certification currently exists for this platform (verified 2026-08-06) — this is real day-2 skill for anyone maintaining production agents, not exam trivia.

Interview Q: "Two agents share the same model and the same tools but behave completely differently in production. Where do you look first?" A: "The instruction field on each. Model and tools define capability; instruction defines behavior, persona, and constraints — identical capability with different instructions is the single most common reason for divergent behavior."

Recap
  • name must be unique and descriptive — avoid reserved words like user, especially once multi-agent routing is involved.
  • instruction is the real system prompt: goal, persona, constraints, and tool-usage guidance, ideally in that explicit order.
  • description is written for other agents to read, not for you — it's what makes automatic routing (Lesson 8) work.
  • An instruction that doesn't explicitly constrain tool usage doesn't reliably stop the model from using a tool anyway.

  • Who actually reads an agent's description — the end user, or something else?
  • Why is naming an agent user a real risk, not just a style nitpick?
  • How would you verify that an instruction's constraints actually hold, rather than just assuming they do?
