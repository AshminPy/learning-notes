Agent Identity

Every earlier lesson had an agent do something — call a tool, read from Memory Bank, run on Agent Runtime. None of them asked the question this lesson answers: when an agent calls a Google Cloud API or another agent, who is making that call, and how does the receiving side know the caller is really that agent and not something impersonating it? A service account key you could copy onto another machine doesn't answer that. Agent Identity is Google's answer, and it's the foundation the rest of Phase F (Agent Gateway, Model Armor, MCP hardening) is enforced on top of — none of those layers work without a trustworthy identity to check policy against first.

Mental model: a service account key is a spare house key anyone holding it can use, from anywhere, forever, until someone remembers to revoke it. Agent Identity is a passport that's biologically bound to one person — it can't be handed to someone else and used, it expires and gets reissued on its own schedule, and every border crossing gets logged against the actual passport holder, not "whoever had a key." That predicts something concrete: stealing the bytes of an agent's credential doesn't get an attacker anywhere on Agent Identity, because the credential is cryptographically bound to that one agent's certificate — a copied token without the matching private key is just useless data.

What Agent Identity actually is

Per Google Cloud's own docs, Agent Identity provides "a strongly attested, cryptographic identity for each agent that is based on the SPIFFE standard," letting agents "securely authenticate to MCP servers, cloud resources, endpoints, and other agents." Every agent gets a unique SPIFFE ID shaped like spiffe://TRUST_DOMAIN/resources/SERVICE/RESOURCE_PATH — for example, an Agent Runtime deployment gets an ID like spiffe://agents.global.org-123456789012.system.id.goog/resources/aiplatform/projects/9876543210/locations/us-central1/reasoningEngines/my-test-agent. When that identity shows up as a principal in an IAM policy, it's written as principal://TRUST_DOMAIN/resources/SERVICE/RESOURCE_PATH — the same identity, just in IAM's addressing format.

The cryptographic binding: why a stolen token is useless

Identity alone isn't the interesting part — SPIFFE just names the agent. The security actually comes from binding: "an X.509 certificate is auto-provisioned and managed on the agent," valid for 24 hours and automatically rotated by Google Cloud, and "access tokens generated for Google Cloud are cryptographically bound to the agent's unique X.509 certificates to prevent token theft." When agents talk across Agent Gateway, they add Demonstrating Proof of Possession (DPoP) on top of mTLS, creating what the docs call "double-bound credentials for end-to-end security." Why it's built this way: a plain bearer token (the kind most APIs use) is valid for whoever holds the bytes — copy it, use it from anywhere. A token bound to a specific certificate is only valid alongside the private key that certificate was issued with, and that key never leaves the agent's runtime. Stealing the token text alone gets an attacker nothing.

Not a service account with a new name

It would be easy to assume Agent Identity is just a service account rebranded for agents. It isn't, and the differences are the actual security story. Unlike service accounts, agent identities "are not shared by multiple workloads by default, can't be impersonated," and developers cannot "generate long-lived service account keys" for them. A service account key is designed to be portable — that's exactly the property Agent Identity removes. Every agent gets its own non-shared, non-impersonable identity, and every access it makes shows up in audit logs attributed to that specific agent's SPIFFE ID, not to a shared credential three different workloads happen to use.

Try it

Q1. An attacker copies the text of an agent's bound access token and pastes it into a request from their own laptop. Does the request succeed?

No. The token is cryptographically bound to the agent's specific X.509 certificate — using it from a machine that doesn't hold the matching private key fails verification, unlike a copied service-account key or a plain bearer token.

Now, before revealing: two different agents both need to call the same Google Cloud API. With Agent Identity's default model, do they end up sharing one identity to make that easier to manage, or does each keep its own?

Reveal the answer

Each keeps its own. Agent identities are not shared by multiple workloads by default and can't be impersonated — the whole design trades the convenience of one shared credential for per-agent isolation and clean audit attribution.

Common mistake: assuming Agent Identity is optional hardening you can skip for internal-only agents. Context-Aware Access — mTLS plus DPoP token binding — is the default Google-managed policy, not an opt-in extra. Treating identity as "something to add later" misreads the platform: it's already the baseline every agent runs under.

A controlled failure

# You try to grant an agent identity a legacy storage role
gcloud storage buckets add-iam-policy-binding gs://my-bucket \
  --member="principal://agents.global.org-123456789012.system.id.goog/resources/aiplatform/projects/9876543210/locations/us-central1/reasoningEngines/my-test-agent" \
  --role="roles/storage.legacyBucketReader"

Predict first: does this succeed, given the agent identity's principal string is correctly formed? Observe: it's rejected — Google Cloud's own docs state plainly that "you cannot grant agent identities legacy bucket roles (for example, storage.legacyBucketReader)." This isn't a syntax problem; legacy IAM roles predate the SPIFFE-based principal model and simply aren't compatible with it. The fix is using a current, fine-grained IAM role (for example roles/storage.objectViewer) instead of a legacy bucket role.

Production best practices

Production note: because agent identities can't be impersonated and can't mint long-lived keys, the usual "just grant broad access and narrow it later" habit from service-account IAM doesn't transfer cleanly — there's no equivalent of quietly sharing a key across a few workloads to save setup time. Google Cloud's Agent Identity docs describe a companion control, Principal Access Boundary (PAB), specifically for limiting which resources an identity can reach even within its granted roles — reach for that instead of over-provisioning one identity's role bindings out of convenience.

No certification currently exists for this platform (re-verified 2026-08-06) — this is real governance competence, not exam trivia.

Interview Q: "Why doesn't Gemini Enterprise Agent Platform just reuse IAM service accounts for agent-to-agent auth?" A: Service account keys are portable and impersonable by design — anyone holding the key can act as that identity from anywhere. Agent Identity binds a SPIFFE identity to a short-lived, auto-rotated X.509 certificate via mTLS and DPoP, so the credential is only usable alongside a private key that never leaves the agent's runtime — theft of the token text alone accomplishes nothing.

Recap
  • Agent Identity gives every agent a unique, strongly attested SPIFFE identity, built on the open SPIFFE standard.
  • An auto-provisioned, auto-rotated (24h) X.509 certificate cryptographically binds the agent's tokens — stealing the token text alone is useless without the matching private key.
  • Agent identities are not shared, not impersonable, and can't mint long-lived keys — the opposite design from a portable service-account key.
  • Agent Gateway (Lesson 19) is the layer that actually enforces policy using this identity as its trust anchor.
