Model Garden and Model Selection

Every agent you've built so far — through Agent Designer, Agent Studio, or raw ADK — has quietly assumed "a model" powers it, without ever asking which one or why. That's fine for a first working agent. It stops being fine the moment cost, latency, or a missing capability shows up in production. Model Garden is where that choice actually gets made: a centralized hub to "discover, test, and deploy a wide variety of first-party, partner, and open-source models."

Mental model: Model Garden is an app store for foundation models, not a single model with settings. You browse, filter by what you need, compare, and then reference one into your agent — the way you'd pick an app for a task rather than assume your phone only ever runs one. That predicts something concrete: "which model" is a per-agent, per-task decision on this platform, not a platform-wide default you set once and forget.

Three categories, one hub

Model Garden organizes models into three groups. First-party (Google) models: Gemini variants (Pro, Flash, Flash-Lite), plus specialized models like Veo (video), Lyria (music), Virtual Try-On, and Gemini Robotics ER 2. Partner models: third-party offerings such as Claude, Grok, Mistral AI, and Llama, available through managed partnerships. Open-source models: community models like DeepSeek, Gemma, Qwen, and embedding models, available either as Model-as-a-Service (MaaS) or for self-deployment. Google frames the curated set — over 200 models — as "best in class for their category," not a single recommended default.

Filtering: how you actually find one

With 200+ models, browsing isn't realistic — filtering is. Model Garden lets you filter by task (what the model should perform), collection (managed by Google, a partner, or you), provider, and feature — including whether a model supports function calling or structured output. That last filter matters more than it sounds: an agent built in Lessons 4-10 that relies on tool-calling only works with a model that actually implements function calling, and not every model in Model Garden does.

Why model choice isn't isolated

Model Garden connects to the rest of the platform, not just to agent-building: tuning (supervised fine-tuning, reinforcement learning, preference tuning), evaluation (Phase G, Lessons 23-24), and serving — Provisioned Throughput, PayGo, batch inference, and provisioned endpoints. Why it's built this way: picking a model is really picking a point on a cost/latency/capability curve, and that curve only makes sense alongside how you'll serve it — a model chosen for its accuracy but served on the wrong tier can still be a bad production decision.

Try it

Q1. Your agent needs to call external tools/functions reliably (Lesson 6's tool-calling pattern). Which Model Garden filter would you check first before picking a model?

The Features filter, specifically function-calling support. Not every model in the 200+ list implements it — checking this before wiring up tool-calling logic avoids building against a model that can't do it.

Now reason through it before revealing: you're building a high-volume ticket-triage agent (thousands of simple requests/day) and separately a legal-research agent (rare, high-stakes questions needing depth). Would you pick the same model and serving tier for both?

Reveal the reasoning

No. The high-volume, simple-task agent is a strong fit for a smaller/faster model (like Flash-Lite) on PayGo serving — cost scales with volume, and the task doesn't need maximum reasoning depth. The rare, high-stakes agent is a better fit for a larger, more capable model, possibly on Provisioned Throughput if its latency/availability needs are strict. Same platform, same Model Garden, two different points on the cost/capability curve.

Common mistake: defaulting to the largest, most capable Gemini variant for every agent "just to be safe." At production volume, that default is usually a cost and latency decision in disguise — most agent tasks don't need maximum reasoning capability, and Model Garden's filtering exists specifically so you can right-size the choice instead of over-provisioning by habit.

A controlled failure

Predict first: you pick an open-source model from Model Garden purely because it's the cheapest option, and wire it into an ADK agent that depends on the structured tool-calling pattern from Lesson 6. You didn't check the Features filter first. What happens?

Reality: the agent's tool-calling step fails or silently underperforms, because function calling is a documented, filterable capability — not every model in Model Garden's 200+ list implements it, especially in the open-source category. This isn't a platform bug; it's the exact gap the Features filter exists to close, and skipping it before wiring in a model is the mistake, not the model itself.

Production note: a real pattern: a helpdesk platform runs Gemini Flash-Lite on PayGo serving for roughly 95% of incoming tickets — routine triage, low latency requirement, cost matters at that volume. The remaining ~5% flagged as ambiguous escalate to a larger reasoning model on Provisioned Throughput, where accuracy matters more than per-call cost. Same agent, two models, chosen deliberately per task rather than one model for everything.

Recap
  • Model Garden is a centralized hub for 200+ first-party, partner, and open-source models — not a single default.
  • Filter by task, collection, provider, and feature (including function-calling support) before picking a model.
  • Model choice connects to tuning, evaluation, and serving (PayGo vs. Provisioned Throughput) — it's a cost/latency/capability decision, not just a capability one.
  • Production agents often use different models for different tasks within the same workflow, not one model for everything.

Confidence check — answer without looking back:

  • When would you deliberately choose a smaller/cheaper model over the most capable one?
  • How would you verify a chosen model actually supports the capability your agent depends on, before deploying?
