Model Armor

Agent Gateway (Lesson 19) answers "is this identity allowed to make this call?" — a question entirely about who and what, not about the actual words in the request. An identity can be perfectly authorized and still send a prompt engineered to hijack the model, or a response that leaks a customer's credit card number. Model Armor is the layer that inspects the actual content flowing through the gateway, not just the permission to send it — it's a different kind of check, running on the same path Lesson 19 already governs.

Mental model: if Agent Gateway is airport security checking your boarding pass, Model Armor is the baggage scanner running at the same checkpoint — a completely different check, on the same line, looking inside what's actually being carried rather than who's carrying it. A perfectly valid boarding pass doesn't get your bag waved through unscanned. That predicts something concrete: an agent with flawless Agent Identity credentials and full Agent Gateway authorization can still have its prompt or response blocked by Model Armor, because authorization and content safety are two independent gates, not one.

What it actually screens for

Per Google Cloud's Model Armor overview, it's "designed to enhance the security and safety of your AI applications" by "proactively screening LLM prompts and responses" across four concrete categories: prompt injection and jailbreak detection (configurable confidence levels), Responsible AI filters (hate speech, harassment, dangerous content, sexually explicit content, plus CSAM), sensitive data protection (PII, credit cards, SSNs, and cloud credentials — built on Google Cloud's Sensitive Data Protection service, adapted for unpredictable AI-generated text), and malicious URL detection in both prompts and responses.

How it's wired into Agent Gateway: the CONTENT_AUTHZ extension

This is the RESOURCES.md gap this lesson closes: Model Armor doesn't sit somewhere separate from Agent Gateway — it's plugged directly into the same Service Extensions mechanism Lesson 19 introduced for REQUEST_AUTHZ. A CONTENT_AUTHZ extension "streams body events to the extension for content sanitization, used to call Model Armor," and when content passes through Agent Gateway, "it invokes Model Armor to enforce your predefined security templates." Ingress and egress get configured with separate templates, exactly the same two-directions split as Lesson 19: ingress templates screen traffic between clients and agents, egress templates screen traffic between agents and external tools, MCP servers, or other agents.

Two enforcement modes, and a clear priority order

Every template is set to one of two modes: INSPECT_ONLY reports a violation without blocking the request; INSPECT_AND_BLOCK actually stops it, and a blocked response carries "blockReason": "MODEL_ARMOR" so the failure is unambiguous, not a generic error. Google Cloud's docs also specify a precedence order when multiple layers of protection exist: a request-level template (highest priority) overrides project-level floor settings, which override Gemini's own native safety filters (lowest priority) — so a project's floor setting is a baseline, not the final word, if a specific request explicitly names a stricter template.

Try it

Q1. An agent is fully authorized by Agent Gateway's REQUEST_AUTHZ policy to call a given tool, but its prompt contains a jailbreak attempt. Does the authorized status get the prompt through?

No. REQUEST_AUTHZ and CONTENT_AUTHZ are independent checks on the same gateway path — being authorized to make the call doesn't exempt the prompt's content from Model Armor's screening, and a jailbreak match can still block it.

Now, before revealing: a project has a floor setting requiring PII screening on all requests. One specific API call also names its own Model Armor template with a stricter policy. Which one actually applies to that call?

Reveal the answer

The request-level template. Templates take highest priority, then project-level floor settings, then Gemini's native safety filters last — a floor setting is only the fallback when nothing more specific is named.

Common mistake: setting a Model Armor template to INSPECT_ONLY during testing and forgetting to switch it to INSPECT_AND_BLOCK before production. INSPECT_ONLY still logs every violation, so the system looks like it's "working" in dashboards — but nothing is actually stopped, which only becomes obvious the first time a real violation reaches the model or the caller.

A controlled failure

# Model Armor template configured for a region where the request doesn't route
gcloud model-armor floorsettings update \
  --full-uri=projects/PROJECT_ID/locations/us-central1/floorSetting \
  --add-integrated-services=VERTEX_AI
# ...but a request gets routed to a different region entirely

Predict first: if Gemini Enterprise Agent Platform routes a request to a region where the specified Model Armor template doesn't exist, does the request fall back to running unscreened, or does it fail? Observe: per Google Cloud's own documented limitation, "if Gemini Enterprise Agent Platform routes a request to a region where the specified Model Armor template doesn't exist, the request fails" outright — it does not silently skip screening. The one case content does proceed unscreened is a genuine Model Armor service outage, and even then, in INSPECT_AND_BLOCK mode a configuration error still triggers reporting rather than passing silently. The practical fix is matching template regions to your Agent Gateway's actual deployment regions before relying on them.

Production best practices

Production note: Model Armor "operates as a stateless service, processing all prompts and model responses entirely in memory" and doesn't persist content unless Cloud Logging is explicitly enabled for it — worth knowing before assuming screened content is retained somewhere for later audit by default. If you need an audit trail of what was screened and why something was blocked, turn on the sanitization logs deliberately (Private Logs Viewer role required to read them) rather than assuming they exist.

Interview Q: "An agent has correct IAM permissions and passes Agent Gateway authorization, but a request still gets blocked. What's the likely cause?" A: Authorization (REQUEST_AUTHZ, checking who/what) and content screening (CONTENT_AUTHZ via Model Armor, checking the actual prompt/response) are independent gates on the same gateway path — a fully authorized identity can still be blocked if its content trips a prompt injection, jailbreak, sensitive-data, or Responsible AI filter, surfaced as blockReason: "MODEL_ARMOR".

Recap
  • Model Armor screens actual prompt/response content — prompt injection, jailbreak, malicious URLs, Responsible AI violations, sensitive data — independent of who's authorized to send it.
  • It plugs into Agent Gateway via a CONTENT_AUTHZ Service Extension, the content-inspection counterpart to Lesson 19's REQUEST_AUTHZ authorization extension, with separate templates for ingress and egress.
  • Two modes: INSPECT_ONLY logs without blocking; INSPECT_AND_BLOCK actually stops the request and returns blockReason: "MODEL_ARMOR".
  • Priority order is template > project floor setting > Gemini's native safety filters — and a routing mismatch to a region without the template fails the request rather than skipping screening silently.
