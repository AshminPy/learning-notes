Evaluation Datasets & Golden Answers

Lessons 1 through 22 covered building an agent, running it at scale, and locking it down with governance. None of that tells you whether the agent is actually any good — whether its answers are correct, its tool calls are safe, or a change you just shipped made things better or worse. That's what the Optimize pillar is for, and every technique in it starts from the same object: an evaluation dataset with a documented schema — not any random spreadsheet of questions.

Mental model: an evaluation dataset row is an exam question with an optional answer key. The prompt is the question; the response is what your agent answered; the reference field is the answer key a teacher already wrote — the "golden" answer. Some grading methods (overlap-based scoring like BLEU/ROUGE) need that answer key to work at all. Others — an LLM acting as a judge against a rubric — can grade an open-ended answer without ever seeing a reference. That predicts something concrete: pick a reference-based metric and leave reference blank, and that row simply can't be scored. That's not a bug — it's a structural requirement of that grading method, same as a strict answer-matching quiz can't grade an essay question with no answer key.

The Gen AI evaluation service

Per Google's own documentation, the platform's Gen AI evaluation service is what actually scores model and agent output — it isn't a separate agent-only tool bolted on later; it's the same evaluation engine both the model-evaluation docs and the Optimize pillar's agent-evaluation pages are built on. Calling client.evals.evaluate() or client.evals.create_evaluation_run() runs one or more metrics against a dataset you supply.

The dataset schema: what the service looks for

The evaluation service auto-detects a small set of documented field names in your dataset:

  • prompt (required) — the input given to the model or agent.
  • response (required) — the output being evaluated.
  • reference (optional) — the ground-truth "golden" answer to compare against. Often required in practice for computation-based metrics like bleu and rouge, which measure textual overlap against something already known to be correct.
  • conversation_history (optional) — prior turns, used for multi-turn evaluation.
  • reference_trajectory — required for agent trajectory metrics, with one documented exception (trajectory_single_tool_use doesn't need it): the expected sequence of tool calls, used to check whether the agent took the right steps, not just whether it produced the right final text.

A minimal row, following that schema:

{
  "prompt": "What is our return policy for electronics?",
  "response": "You can return electronics within 30 days with a receipt.",
  "reference": "Electronics can be returned within 30 days of purchase with proof of purchase.",
  "reference_trajectory": [
    {"tool_name": "search_policy_docs", "tool_input": {"category": "electronics"}}
  ]
}

Why it's built this way: separating reference (golden text answer) from reference_trajectory (golden sequence of tool calls) lets the service score two different questions independently — "did the agent say the right thing" and "did the agent do the right thing to get there." That distinction matters because an agent can call the wrong tool and still stumble into a correct-sounding answer; only a trajectory check catches that.

Why "golden" is optional, not universal

The platform ships 20+ pre-built metrics spanning quality, safety, grounding, and tool use, plus adaptive rubrics that tailor evaluation criteria per case rather than applying one fixed rubric to every row. Rubric-based, LLM-judge metrics are reference-free — they grade a response against stated criteria, not against a pre-written answer. That's deliberate: hand-writing a golden answer for every conceivable user question doesn't scale. Reference-based metrics stay valuable for the smaller set of cases where an exact or near-exact answer genuinely exists (policy text, pricing, compliance language) — Lesson 24 covers the AutoRaters that do the actual scoring.

Try it

Q1. You have a dataset with prompt and response filled in for every row, but no reference column at all. You run a rubric-based, LLM-judge metric. Does it fail?

No — a reference-free metric like a rubric/LLM-judge check scores the response directly against stated criteria, not against a golden answer, so it runs fine without reference. Only computation-based metrics like bleu/rouge, and trajectory metrics other than trajectory_single_tool_use, need reference fields filled in.

Now, before revealing: write your own dataset row (in the box) for evaluating whether an agent correctly cancels a subscription in exactly one tool call. Use the field names from this lesson.

Reveal a modeled answer

{
  "prompt": "Cancel my subscription, account ID 4471",
  "response": "Your subscription (account 4471) has been cancelled.",
  "reference_trajectory": [
    {"tool_name": "cancel_subscription", "tool_input": {"account_id": "4471"}}
  ]
}

Common mistake: treating reference as mandatory for every metric, then concluding "we can't evaluate anything without golden answers for every case." Most modern per-case rubric grading is deliberately designed to work without one — that's the entire point of reference-free metrics. Golden answers are worth writing for a small, high-stakes subset of cases, not the whole dataset.

A controlled failure

# Dataset row, deliberately missing "reference"
{"prompt": "Refund a $40 order for user 118", "response": "Refunded $40 to user 118."}

# Run a computation-based, reference-based metric against it
eval_result = client.evals.evaluate(
    dataset=my_dataset,
    metrics=["rouge"],
)

Predict first: can this row be scored? Observe: no — rouge measures textual overlap against something known-correct, and this row supplies nothing to compare against. This isn't the evaluation service being fragile; the metric is doing exactly what its name says (overlap against a reference) with no reference present. The fix isn't a workaround — it's either picking a reference-free metric for this open-ended case, or actually writing the golden answer.

Production best practices

Production note: teams don't hand-write golden answers for every conceivable user question — that doesn't scale past a handful of cases. The realistic pattern: write a small set of reference-based golden rows for your highest-stakes, most stable answers (policy text, pricing, compliance language) where an exact-or-near-exact match genuinely matters, and rely on rubric-based, reference-free metrics for the long tail of open-ended conversation. Lesson 24 covers where those long-tail test cases actually come from at scale.

Exam and interview notes

No certification currently exists for this platform (confirmed 2026-08-06) — this is real evaluation-engineering skill for shipping agents responsibly, not exam trivia.

Interview Q: "Why would an evaluation dataset need a reference_trajectory field separate from reference?" A: Because an agent can call the wrong tool and still produce a correct-sounding final answer — reference checks whether the text is right, reference_trajectory checks whether the agent's actual steps to get there were right, and those two things can disagree.

Recap
  • An evaluation dataset row auto-detects five documented fields: prompt and response (required), reference, conversation_history, and reference_trajectory (optional, but effectively required for specific metric types).
  • reference is the golden text answer; reference_trajectory is the golden sequence of tool calls — they check different things and can disagree.
  • Reference-based metrics (bleu, rouge, most trajectory metrics) need a golden answer to run at all; reference-free, rubric-based metrics don't.
  • Golden answers don't need to cover every case — write them for high-stakes, stable answers; let reference-free metrics cover the open-ended long tail.
