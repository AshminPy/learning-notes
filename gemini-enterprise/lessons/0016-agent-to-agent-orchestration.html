Agent-to-Agent Orchestration (A2A)

Lesson 7 connected an agent to tools and data via MCP. That's fine when the thing on the other end is a function — a database query, an API call, something stateless that runs and returns. It breaks down the moment the thing you actually want to reach is another whole agent: one with its own reasoning, its own multi-turn conversation, maybe owned by a different team or built on a different platform entirely. Wrapping that agent as a plain tool call would throw away everything that makes it an agent — its state, its ability to ask a clarifying question back. Agent2Agent (A2A) is the protocol built for exactly this: an "open communication protocol... that enables agents from different builders and platforms to discover each other, collaborate, and securely delegate tasks," without reducing either side to a stateless function.

Mental model: MCP (Lesson 7) is an agent reaching into a shared toolbox and picking up a wrench — the wrench doesn't think, it just does one job and hands it back. A2A is an agent picking up the phone and calling a colleague who happens to work at a different company. That colleague can ask a follow-up question, remember what was said earlier in the call, and say no. That predicts something concrete: if you find yourself wanting the called agent to negotiate, clarify, or hold state across multiple exchanges, MCP's tool model can't do that — you need A2A, because a tool call is a one-shot request, not a conversation.

The three pieces of an A2A agent

Building an A2A agent means defining three components. The AgentCard is a metadata document — literally "like a business card that other agents can use to discover what your agent can do" — listing named skills, each with an id, description, tags, and usage examples. The AgentExecutor holds the agent's actual task-handling logic: it implements execute() and cancel(), processing incoming requests asynchronously. The optional ADK LlmAgent is a normal ADK agent — instructions, a model, tools — that the executor wraps and runs. Combine all three into an A2aAgent and call set_up():

from a2a.types import AgentSkill
from vertexai.agent_engines.templates.a2a import create_agent_card, A2aAgent

skill = AgentSkill(
    id='get_exchange_rate',
    name='Get Currency Exchange Rate',
    description='Retrieves the exchange rate between two currencies on a given date.',
    tags=['Finance', 'Currency'],
)

agent_card = create_agent_card(
    agent_name='Currency Exchange Agent',
    description='An agent that provides currency exchange rates',
    skills=[skill],
)

a2a_agent = A2aAgent(
    agent_card=agent_card,
    agent_executor_builder=lambda: CurrencyAgentExecutorWithRunner(agent=my_llm_agent),
)
a2a_agent.set_up()

Once deployed to Agent Runtime, the agent becomes reachable through three HTTP endpoints: GET /v1/card for discovery, POST /v1/message:send to hand it a task, and GET /v1/tasks/{task_id} to check status. Notably, "Agent Runtime does not serve the public agent card" — a caller must retrieve it through an authenticated call instead, using an OAuth bearer token scoped to cloud-platform.

Try it

Q1. You wrap Agent B as a plain MCP tool instead of calling it via A2A. Mid-conversation, Agent B needs to ask the user a clarifying question before it can finish. Can it, through a tool call?

No. A tool call is a single stateless request-response — there's no channel for the tool to pause and ask something back. A2A is built for exactly this case: the called agent keeps its own reasoning and multi-turn ability, so it can hold state and ask a follow-up instead of being reduced to one function call.

Now trace a real flow before revealing: a Restaurant Agent on Cloud Run needs to book a table, so it delegates to a separately-deployed Reservation Agent on Agent Runtime via A2A. What are the three calls it makes, in order, and what does each one give it?

Reveal the sequence

1. GET /v1/card (authenticated) on the Reservation Agent — discovers its skills (create/check/cancel a reservation) without any integration hardcoded ahead of time. 2. POST /v1/message:send — hands over the booking request as a task; the Reservation Agent keeps its own multi-turn state (managed by its own session service) rather than being reduced to a function call. 3. GET /v1/tasks/{task_id} — polls for the result once the Reservation Agent has finished reasoning about it.

Common mistake: assuming an A2A agent's public agent card is reachable with a plain unauthenticated request, the way a public REST API doc page often is. It isn't — Agent Runtime explicitly does not serve the public card, so a caller must go through the authenticated retrieval path with real credentials from the start, not add auth only after a first "just try it" request fails.

A controlled failure

# Naive first attempt: fetch the agent card with no credentials at all
curl https://YOUR_AGENT_URL/v1/card

Predict first: does this return the agent's skills, the way hitting a public API docs page usually would? Observe: it doesn't — Agent Runtime "does not serve the public agent card" at all, by design. The fix isn't adding a header to an otherwise-working request; it's calling the authenticated retrieval path (handle_authenticated_agent_card()) with a real bearer token from the start, because there's no unauthenticated path to fall back to.

Production best practices

Production note: A2A calls run on real Google Cloud IAM — an OAuth bearer token scoped to cloud-platform, checked against the caller's actual project permissions. Don't hardcode long-lived credentials into one agent to call another; scope each agent's calling identity as narrowly as the task needs. This is exactly the gap Lesson 18 (Agent Identity, built on SPIFFE) and Lesson 19 (Agent Gateway) exist to close at scale — this lesson's raw bearer-token pattern is the mechanism those two lessons add real per-tool policy and audit logging on top of.

Exam and interview notes

No certification currently exists for this platform (re-verified 2026-08-06).

Interview Q: "How does A2A actually differ from wrapping one agent as another's tool?" A: A tool call is stateless and one-shot — the called system runs once and returns. A2A preserves the full called agent behind a discoverable, authenticated network interface (the AgentCard plus message/task endpoints), so it keeps its own reasoning and multi-turn state instead of being flattened into a single function call.

Recap
  • A2A is an open protocol for calling another full agent — not a tool call — preserving its state, reasoning, and multi-turn ability.
  • Three components build an A2A agent: the AgentCard (discovery metadata), the AgentExecutor (task logic), and an optional ADK LlmAgent.
  • Agent Runtime never serves the public agent card — every real caller must retrieve it through an authenticated request.
  • A2A calls run on Google Cloud IAM (OAuth bearer tokens) — the raw mechanism that Agent Identity (Lesson 18) and Agent Gateway (Lesson 19) later govern more tightly.
