MCP: Connecting Agents to Tools and Data

Lesson 6 covered three tool types, each tying an agent to one place: a function you wrote, an API spec someone else wrote, or a capability ADK ships. All three assume the tool speaks whatever protocol that specific integration expects. MCP is the answer to a different question: what if you want any agent to connect to any tool server, without custom glue code per pair? This lesson closes Phase B's tool coverage with the one tool type that's a standard, not a format.

Mental model: MCP is a power outlet standard, not a custom cable per device. Before a universal standard, every appliance needed its own plug shape and its own adapter; a standard socket means any compliant device works with any compliant outlet, made by anyone. MCP does the same for agents and tools: an ADK agent that speaks MCP can connect to a tool server built by a completely different team, in a completely different framework, with zero custom integration code — as long as both sides speak MCP. That predicts something concrete: a tool you build once, wrapped as an MCP server, becomes usable by ADK agents, Claude, or any other MCP-compliant client — not just the framework you happened to build it in.

What MCP actually is

The Model Context Protocol is, in its own description, "an open standard designed to standardize how Large Language Models (LLMs) like Gemini and Claude communicate with external applications, data sources, and tools." The key word is standardize — before MCP, connecting an agent to a new tool server meant writing integration code specific to that server's own API shape. MCP follows a client-server architecture, defining how "data (resources), interactive templates (prompts), and actionable functions (tools) are exposed by an MCP server and consumed by an MCP client" — one shared contract, regardless of who built either side.

ADK as an MCP client

An ADK agent can act as an MCP client, using tools an external MCP server exposes — mechanically, this is just another entry in the agent's tools list, pointed at a server instead of a function or a spec. This is the direction most agent builders reach for first: connecting an existing agent to tools and data that already live behind an MCP server someone else runs, without writing a custom integration for that server's specific API.

ADK as an MCP server

The relationship also runs in reverse: ADK can "build an MCP server that wraps ADK tools, making them accessible to any MCP client." This uses FastMCP, described as "a high-level and Pythonic" framework where "in most cases, decorating a function is all you need." Why it's built this way: a tool you write once for your own ADK agent doesn't have to be rewritten to be usable by a completely different framework — wrap it once as an MCP server, and any MCP-compliant client (including non-ADK ones) can call it, the same way any USB-C device works with any USB-C port.

The platform's own MCP surface

MCP isn't only an ADK-level concept here — Gemini Enterprise Agent Platform exposes its own MCP surface directly. Its reference documentation names an MCP reference for aiplatform.googleapis.com, and the platform separately documents its own remote MCP server your agents can connect to. Practically, this means an ADK agent's path to platform capabilities isn't limited to ADK-specific integrations — it can also reach the platform the same standardized way it reaches any other MCP server.

Try it

Q1. An ADK agent connects to a third-party tool server that was built entirely in a different framework, with no ADK-specific code on either side. What made that possible?

Both sides speak MCP — the standardized client-server protocol. Neither side needed to know anything ADK-specific about the other, because MCP is the shared contract, not either framework's own API shape.

Now, before revealing: a completely different AI framework (not ADK at all) wants to use a tool you already built and tested inside ADK. Do you rewrite the tool in that other framework?

Reveal the answer

No — wrap your existing ADK tool as an MCP server using FastMCP. Any MCP-compliant client, including that other framework, can then call it directly. This is ADK acting as an MCP server instead of a client — the reverse direction from Lesson 7's first example.

Common mistake: treating "MCP tool" as just another ADK-specific tool type, the same mental category as a function tool. Function, OpenAPI, and built-in tools (Lesson 6) are all ADK integrating with something on ADK's terms. MCP is the opposite direction — a vendor-neutral standard that exists independently of ADK entirely; ADK simply implements it on both the client and server side.

A controlled failure

An agent's tools list includes an MCP toolset pointed at a server that requires authenticated access, but no credentials were configured for that connection.

Predict first: does this fail inside your agent's own instruction-following logic, or somewhere else entirely? Observe: it fails at the MCP server boundary — the client-server handshake itself, before your agent's instruction or reasoning is even involved. The practical consequence: when an MCP-backed tool call fails, the first thing to check is the server's own auth requirements and your client's configured credentials, not your agent's prompt or tool-calling logic, which never got a chance to be the problem.

Production best practices

Production note: treat every MCP server your agents connect to as an external, unverified tool source — the same instinct you'd apply to any third-party API, and one Phase F's governance stack formalizes directly. MCP's own attack surface (prompt-injection through tool responses) is real enough that Lesson 21 covers dedicated hardening for it; this lesson's takeaway is narrower: know which MCP servers your agents actually connect to, and don't treat "it's just a tool call" as lower-risk than it is.

Exam and interview notes

No certification currently exists for this platform (verified 2026-08-06) — this is real day-2 integration skill, not exam trivia.

Interview Q: "Why would a platform team standardize on MCP instead of letting each team write custom tool integrations?" A: "Custom integrations are one-off and don't compose — every new tool-agent pair needs its own glue code. MCP is a shared standard: one MCP server built once is usable by any compliant client, and one client (like an ADK agent) can reach any compliant server, which is what makes tool integration scale across many teams instead of multiplying per pair."

Recap
  • MCP is an open, vendor-neutral standard for connecting LLMs/agents to external tools and data — not an ADK-specific tool type.
  • An ADK agent can be an MCP client (using someone else's server) or, via FastMCP, an MCP server (exposing its own tools to any client).
  • Gemini Enterprise Agent Platform exposes its own MCP surface, including a dedicated remote MCP server — agents can reach platform capabilities through the same standard protocol.
  • MCP failures happen at the client-server boundary, not inside your agent's own reasoning — check server auth and connection config first.
