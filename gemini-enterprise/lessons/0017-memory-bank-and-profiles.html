Memory Bank & Memory Profiles

Agent Runtime's Sessions (Lesson 15) hold a conversation's history — but only for that one conversation. The instant a user comes back tomorrow in a new session, an agent relying on Sessions alone has forgotten everything: their preferences, what they were working on, facts they already gave it. Memory Bank is the piece that fixes this: it generates "long-term memories based on conversations between the user and your agent" that "persist across multiple sessions, enabling your agent to adapt and personalize responses for context and continuity" — the difference between an agent that re-introduces itself every time and one that actually remembers the user.

Mental model: a Session is today's meeting notes — detailed, useful during the meeting, thrown away once it ends. Memory Bank is the running personnel file that survives every meeting you've ever had with that person. Memory Profiles are the standardized intake-form fields on that file (job title, plan tier — fast to read, always in the same place); natural-language memories are the free-text notes a colleague scribbled in the margins. That predicts something concrete: if you need an instant answer to "what's this user's plan tier?" at the very start of a new session, you want a profile field, not a search through paragraphs of notes.

How memories actually get generated

Nothing writes to Memory Bank automatically just because a conversation happened — generation has to be triggered. Three ways: GenerateMemories extracts facts "at a specified interval (such as the end of every session or the end of every turn)," running extraction (pulling out meaningful information) then consolidation (merging it with what's already stored). IngestEvents streams conversation events continuously and "automatically triggers memory generation based on batching rules you configure." CreateMemory writes a fact directly, for when you want the agent's code — not an LLM's judgment — deciding what gets remembered. Every memory lives inside an isolated scope (user identity plus agent name), so "for each scope, Memory Bank maintains an isolated collection of memories" — one user's memories are never visible under another's scope.

Retrieval has two modes with a real cost trade-off: simple retrieval pulls every memory in a scope; similarity search returns "only the most relevant memories to the current conversation." Dumping every memory into a prompt gets expensive and noisy fast at scale — similarity search is what keeps personalization affordable as memory volume grows.

Memory Profiles: the structured half

Profiles are "data structures with static schemas populated and updated using LLMs" — you define the schema once, as a Pydantic model with field descriptions, for example a technical_stack field ("comma-separated list of tools or languages used") or a job_status enum (unemployed, part_time, full_time, student). Each schema gets a unique ID when uploaded at Agent Platform instance creation. Generation runs the same two steps as natural-language memories — extraction, then consolidation, where the LLM either updates an existing field or populates a new one — but the output is always shaped exactly like your schema, never free text. Profiles and natural-language memories aren't either/or: they can coexist, and you can disable natural-language generation entirely if structured fields cover everything you need. The stated payoff is "initializing an interaction between an agent and user" instantly, without an expensive search running before the agent can even say hello.

Try it

Q1. A brand-new user sends their very first message to your agent. You immediately query Memory Bank for their profile before the agent replies. What comes back?

Nothing — an empty scope. Memory generation isn't synchronous with the conversation; it only runs when GenerateMemories fires (at its configured interval), IngestEvents' batching rule triggers, or CreateMemory is called explicitly. A query before any of those has happened simply finds nothing yet, which is expected, not a bug.

Now design one before revealing: you want a profile schema that captures a user's subscription tier (free/pro/enterprise) and preferred contact hour. Sketch the Pydantic-style fields, then check your reasoning against the pattern Memory Bank actually expects.

Reveal a working pattern

class UserProfile(BaseModel):
    subscription_tier: Literal["free", "pro", "enterprise"] = Field(
        description="The user's current subscription tier"
    )
    preferred_contact_hour: str = Field(
        description="Hour of day (24h, e.g. '14') the user prefers to be contacted"
    )

Match against the doc's own job_status example: an enum-style field for a bounded set of values, a plain string field with a clear description for something free-form. Each field gets extracted and consolidated the same way — the schema just tells the LLM exactly what shape to fill in.

Common mistake: assuming natural-language memories and Memory Profiles are an either/or choice you commit to once. They coexist by default — the real decision per field is which one fits: a bounded, frequently-read fact (plan tier, job status) belongs in a profile; a fuzzy one-off detail that doesn't fit any schema belongs in natural-language memory. Forcing everything into one or the other either loses detail or slows down every session-start read.

A controlled failure

# Session ends normally. GenerateMemories is configured to run "at the end of every session."
# You query the user's memories immediately after the session-end event fires.

Predict first: is the new memory guaranteed to be there the instant you query? Observe: not necessarily — generation is triggered by the event, but extraction and consolidation still have to run before anything is written. Treating memory generation as instantaneous, and querying immediately in the same request path, is the same class of mistake as the first quiz above: assuming memory exists before the trigger that creates it has actually finished.

Production best practices

Production note: default to similarity search, not simple retrieval, once a user has any real memory volume — injecting every memory into every prompt is both a cost problem (larger context, every call) and a quality one (irrelevant memories crowding out the ones that matter). Reserve Memory Profiles for the small set of fields your agent reads on nearly every turn (plan tier, role, locale); everything else is a better fit for natural-language memory plus similarity search. And because scopes are isolated by user and agent identity, memory isolation is also your first line of defense in a multi-tenant deployment — a bug that leaks scope keys between users is a data-exposure incident, not just a personalization bug.

Exam and interview notes

No certification currently exists for this platform (re-verified 2026-08-06).

Interview Q: "Why would a platform offer both free-text memories and structured Memory Profiles instead of just picking one?" A: Profiles give guaranteed-schema, low-latency reads at the very start of a session, with no search needed; natural-language memories cover the long tail of facts that don't fit any predefined field. Most production agents genuinely need both — one for speed on known fields, one for flexibility on everything else.

Recap
  • Sessions hold one conversation; Memory Bank persists facts across every future session, scoped by user and agent identity.
  • Memories are generated by GenerateMemories (interval-based), IngestEvents (streamed, batched), or CreateMemory (manual) — never automatically just because a conversation happened.
  • Memory Profiles are fixed-schema, LLM-populated structures for fast, predictable reads; natural-language memories are free text — the two coexist by design.
  • Similarity search (not simple retrieval) is the production default once memory volume grows, for both cost and relevance reasons.
