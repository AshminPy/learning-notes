The brief

Build an agent with exactly one real tool, deploy it to Agent Runtime with Agent Identity attached, query it once deployed, and confirm you can see the run afterward. That's the whole brief — small on purpose, so the point is the end-to-end path, not the agent's sophistication.

Build it — step by step, using verified commands

These are the exact steps and code from Google's own ADK quickstart, adapted to a one-tool agent. Prerequisites: a Google Cloud project with billing enabled, the Agent Platform and Cloud Storage APIs enabled, and roles/aiplatform.user plus roles/storage.admin granted to your identity.

pip install --upgrade --quiet "google-cloud-aiplatform[agent_engines,adk]>=1.112"
gcloud auth application-default login
import vertexai
client = vertexai.Client(project="PROJECT_ID", location="LOCATION")

Step 1 — write one real tool. Any function with a docstring works; the docstring is what the model reads to decide when to call it.

def get_exchange_rate(currency_from: str = "USD", currency_to: str = "EUR", currency_date: str = "latest"):
    """Retrieves the exchange rate between two currencies on a specified date."""
    import requests
    response = requests.get(
        f"https://api.frankfurter.app/{currency_date}",
        params={"from": currency_from, "to": currency_to},
    )
    return response.json()

Step 2 — build and test the agent locally, before touching deployment at all.

from google.adk.agents import Agent
from vertexai import agent_engines

agent = Agent(model="gemini-3.5-flash", name="capstone_agent", tools=[get_exchange_rate])
app = agent_engines.AdkApp(agent=agent)

async for event in app.async_stream_query(
    user_id="USER_ID", message="What is the exchange rate from US dollars to SEK today?"
):
    print(event)

Step 3 — deploy it, with governance attached in the same call. This is the line the whole capstone hinges on: identity isn't a step you do after deployment, it's an argument to the deploy call itself.

from vertexai import types

remote_agent = client.agent_engines.create(
    agent=app,
    config={
        "requirements": ["google-cloud-aiplatform[agent_engines,adk]"],
        "staging_bucket": "STAGING_BUCKET",
        "identity_type": types.IdentityType.AGENT_IDENTITY,
    },
)

Step 4 — verify against the remote agent, not your local one. Same query, different object — this is the check that proves the deployment actually happened, the same principle as proving a Docker image really reached a registry.

async for event in remote_agent.async_stream_query(
    user_id="USER_ID", message="What is the exchange rate from US dollars to SEK today?"
):
    print(event)

Try it

Q1. Before you run Step 3, predict: if you forget the identity_type line entirely, does deployment fail outright, or does it just deploy without Agent Identity attached?

It deploys without Agent Identity attached — the field is a configuration choice you make, not a required gate the SDK enforces. That's exactly why Lesson 27 called this out as something to attach deliberately, not something the platform forces on you.

Now actually run all four steps yourself, end to end, before revealing the cleanup command below.

Reveal cleanup

remote_agent.delete(force=True)

Run this once you've confirmed Step 4 worked — an idle deployed agent still exists as a resource until you delete it.

A controlled failure

# You query app (local) successfully, then assume remote_agent (deployed)
# will behave identically without actually querying it.

Predict first: if the local agent worked in Step 2, is querying the remote one in Step 4 just a formality? Observe: no — Step 2's local test uses in-memory sessions on your machine; Step 4 is a genuinely separate object (remote_agent, not app) running on infrastructure you don't control. A working local test proves your agent logic is sound; it proves nothing about whether the deployment itself succeeded, whether the staging bucket was reachable, or whether the deployed identity is configured correctly. Skipping Step 4 is exactly the "demo passed, never actually verified in production" mistake Lesson 28 named — just at capstone scale instead of team scale.

Production best practices

Production note: everything about this capstone that a real team would add before shipping: a second tool exercising error recovery (what happens when get_exchange_rate's API call fails?), an evaluation dataset per Phase G instead of one manual query, and a canary stage with real users before full production — all deliberately out of scope here so this capstone stays finishable in one sitting. Treat this build as the skeleton every one of those additions would attach to, not the finished product.

Recap
  • The capstone is small on purpose — one agent, one tool, through sandbox — because the point is the end-to-end path, not agent sophistication.
  • Governance attaches at deploy time (identity_type in the same call as the deploy itself), matching Lesson 27 exactly.
  • A working local test and a working deployed agent are different claims — always verify the remote object, never assume from the local one.
  • Everything left out on purpose (error-recovery tools, evaluation datasets, canary) is the real next step for turning this skeleton into an actual production agent.
