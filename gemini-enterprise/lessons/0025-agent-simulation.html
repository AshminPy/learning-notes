Agent Simulation

Lesson 24 assumed you already had eval cases and traces to score. This lesson is where a lot of those actually come from at scale: Agent Simulation runs your agent against a synthetic, LLM-played user instead of a real one, so you can stress-test multi-turn behavior — and even backend failures — before any real customer sees it.

Mental model: Agent Simulation is a flight simulator, not a real flight. A User Simulator plays the passenger — a synthetic user with a hidden "flight plan" (its own instructions the agent under test never sees) that drives a realistic, multi-turn conversation. Environment simulation plays bad weather — it intercepts specific tool calls and injects mocked errors (a fake HTTP 503, a latency spike) so you can see how the agent copes with a payment-API outage without ever touching a real payment API or waiting for a real outage. That predicts something concrete: you can validate "how does my agent behave when the refund tool times out" on day one, in CI, with zero real users and zero real outages — you don't have to wait for the failure to actually happen in production to test the response to it.

Notice the two steps here are the exact same two SDK calls Lesson 24 introduced for generating synthetic test cases — generate_conversation_scenarios() and run_inference(). Agent Simulation isn't a separate system; it's what those two calls actually do once a User Simulator is driving the conversation on the far side.

Two-step workflow: generate, then simulate

eval_dataset = client.evals.generate_conversation_scenarios(
    agent_info=travel_agent_info,
    config={
        "count": 5,
        "generation_instruction": "Generate scenarios where a user needs to change a flight after a missed connection",
    },
)

eval_dataset_with_traces = client.evals.run_inference(
    agent=travel_agent,
    src=eval_dataset,
    config={"user_simulator_config": {"max_turn": 5}},
)

Step 1 produces each scenario's starting prompt (the user's opening message) and a conversation plan — hidden instructions describing how the simulated user should behave and what they're trying to accomplish. Step 2 hands that plan to the User Simulator, which uses it to generate realistic follow-up replies for up to max_turn turns, driving the agent through a full multi-turn conversation and recording every step as a trace.

Environment simulation: injecting failure on purpose

Separately from simulating the user, environment simulation lets you intercept a specific tool call the agent makes and substitute mocked data or a simulated error — an HTTP 503, a latency spike — in place of the real backend response. This validates how the agent's logic actually handles a degraded dependency (does it retry, apologize, escalate, or silently fail?) without ever touching the real production backend, and without waiting for a real outage to find out.

What comes out: traces, scored the same way

Both paths — a normal multi-turn User Simulator run and an environment-simulation run with an injected failure — produce the same kind of output: traces, the immutable record of model inputs, responses, and tool calls introduced in Lesson 24. Those traces feed directly into the exact same client.evals.evaluate() call from Lesson 24 — simulation is a way of generating traces at scale and on demand, not a separate scoring system.

Try it

Q1. A User Simulator has a "conversation plan" the agent under test never sees. What is that plan actually for?

It's the hidden script driving the simulated user's realistic follow-up replies across multiple turns. The agent only ever sees ordinary user messages — never the plan itself — which is exactly what makes the conversation a fair test of the agent's actual behavior.

Common mistake: treating simulation and real-user testing as interchangeable. Simulation is for stress-testing conversational logic and failure handling cheaply, repeatably, and at scale — a User Simulator follows a written plan, so it won't surprise you in the genuinely unpredictable ways a real customer can. Simulation reduces how often real users find your bugs first; it doesn't eliminate the need to occasionally validate against real behavior.

A controlled failure

# Skips scenario generation entirely, jumps straight to inference
eval_dataset_with_traces = client.evals.run_inference(
    agent=travel_agent,
    src=some_other_dataset,
    config={"user_simulator_config": {"max_turn": 5}},
)

Predict first: what happens if src was never produced by generate_conversation_scenarios() — say, a plain list of prompts with no conversation plan attached? Observe: the User Simulator has no hidden plan to work from for any of these rows. The documented workflow is two strictly ordered steps — generate scenarios, then simulate sessions — not two independent options you can call in either order. Skipping step 1 leaves step 2 with nothing to simulate a realistic multi-turn conversation against, even though it will still attempt to run.

Production best practices

Production note: the value of simulation is volume and repeatability — stress-testing an agent against many synthetic interactions before it ever touches live customers. The realistic pattern is running simulation as a CI gate on every agent-instruction or tool-definition change, not just once before a big launch — a change that looks safe in isolation can shift how the agent behaves across an entire conversation plan, and simulation is what catches that before a real user does.

Recap
  • Agent Simulation runs the agent against a User Simulator — a synthetic user following a hidden conversation plan the agent never sees.
  • The workflow is two ordered SDK calls: generate_conversation_scenarios(), then run_inference() with a user_simulator_config — the same calls Lesson 24 used for synthetic test generation.
  • Environment simulation separately intercepts specific tool calls to inject mocked errors, testing resilience without touching real backends.
  • Both paths produce traces, scored by the exact same AutoRaters and evaluate() call from Lesson 24.
