Agent Runtime: Where Agents Actually Execute

Lessons 4 through 14 built an agent's logic: ADK agents and tools, Agent Designer or Agent Studio, a chosen model, grounding via RAG. Every one of those ran in your terminal, a notebook, or a builder's own preview pane — reachable by nobody but you. Agent Runtime is the piece that turns "an agent that works on my machine" into "an agent that's live": a managed place for it to actually run, be called, and stay up. It's the foundation the next two lessons — agent-to-agent orchestration and Memory Bank — both sit directly on top of.

If you've touched Vertex AI before this platform existed, you may already know this component under a different name. State it plainly: Agent Runtime is the current name for what Vertex AI called Agent Engine. Nothing about the underlying service changed identity — the rebrand from Vertex AI to Gemini Enterprise Agent Platform (announced at Google Cloud Next '26) renamed the product, not the thing it does. If a deploy-state, a teammate, or an older tutorial says "Agent Engine," they mean this lesson's Agent Runtime.

Mental model: Agent Runtime is a serviced apartment, not an empty plot of land. Cloud Run and GKE (Lesson 27) hand you land and utilities — you still frame the building yourself. Agent Runtime hands you a furnished unit built specifically for agents: it already knows how to hold a session open, wire up tracing, and enforce your IAM policy before you've written a line of infrastructure code. That predicts something concrete: the same ADK agent that takes real infrastructure work to run well on GKE can go live on Agent Runtime with a fraction of that setup — but you also give up the freedom to rewire the building's plumbing yourself.

The name changed, the resource didn't

Per Google's own Agent Runtime documentation: "Because the name of Agent Runtime changed over time, the name of the resource in the API reference is ReasoningEngine" — kept exactly so that code, deploy-states, and tutorials written under the older name keep working without modification. That single fact explains a lot of confusion learners hit going through real production repos: the product is called Agent Runtime, Vertex AI called it Agent Engine, and the API resource type underneath both names has stayed ReasoningEngine the whole time. Seeing any of these three words in a colleague's code is not a sign of a different or legacy product — it's the same service at a different point in its naming history.

What Agent Runtime actually manages

Agent Runtime is described as "a fully-managed, opinionated runtime that you can use to deploy, operate, and scale agentic applications." Concretely, it takes over: end-to-end deployment and scaling, container image customization via build-time install scripts, VPC-SC compliance and IAM-based authentication, and calling models and function-calling tools on the agent's behalf. Deploying to it is a five-step flow: set up your environment, develop the agent, deploy to the managed runtime, query it via API requests, then manage it post-deployment.

Framework support comes in three tiers, and which one your agent falls into changes how much of that management you actually get: full integration (the Agent Development Kit — first-class support built directly around it), SDK integration (LangChain, LangGraph, AG2, LlamaIndex — supported, but layered on top rather than native), and custom templates (CrewAI or a fully custom framework — the most manual wiring). An agent built purely with ADK gets the deepest tooling; an agent ported from another framework still runs, but with more of the plumbing left to you.

Try it

Q1. Your team's deploy-state file for an existing production agent says it runs on "Agent Engine." Is that a different, older product than Agent Runtime?

No. Agent Engine was Vertex AI's name for the exact same managed execution service that Gemini Enterprise Agent Platform now calls Agent Runtime. The rebrand changed the product's name, not its identity — the underlying API resource type has stayed ReasoningEngine across both names.

Now reason it through: your Lesson 4-9 agent is built purely with ADK's LlmAgent and tool-calling — no LangChain, no custom container. Which support tier does it fall into, and what does that concretely buy you versus porting in a CrewAI agent instead?

Reveal the answer

Full integration — the top tier, reserved for ADK. That buys first-class deployment tooling and support built directly around your agent's structure. A CrewAI agent falls into the "custom templates" tier: it still runs on Agent Runtime, but with more manual wiring left to you, since the platform's native tooling wasn't built around that framework's internals.

Common mistake: treating Agent Runtime as "Cloud Run, but for agents" — generic compute you can reconfigure freely. It's deliberately opinionated: sessions, memory hooks, and tracing are already wired in specifically for agentic workloads. Forcing a non-agent workload onto it, or expecting to freely restructure its container the way you would on GKE, fights the exact trade-off the mental model above describes — you gained a furnished unit by giving up control of its plumbing.

Seeing an old identifier in a very current API response is the naming bridge in action, not evidence you're in the wrong place.

Production best practices

Production note: the framework-tier decision is a long-term maintenance cost, not a one-time convenience pick. Teams building new agents get the most from Agent Runtime by staying ADK-native to land in the full-integration tier; reserve the SDK-integration or custom-template tiers for agents that already carry serious sunk cost in another framework (an existing LangGraph pipeline, for example), because day-2 operations — tracing, IAM wiring, observability — is documented as strongest for the natively-supported tier.

Recap
  • Agent Runtime is a fully-managed, opinionated execution environment for agentic applications — deploy, operate, and scale without building the infrastructure yourself.
  • Vertex AI called this exact service Agent Engine; the rebrand to Gemini Enterprise Agent Platform renamed the product, not the underlying service, which is why the API resource type has stayed ReasoningEngine across both names.
  • Framework support is tiered: full integration (ADK), SDK integration (LangChain/LangGraph/AG2/LlamaIndex), or custom templates (CrewAI/other) — the tier your agent lands in changes how much tooling you get for free.
  • Agent Runtime is deliberately opinionated, not general-purpose compute — that's the whole trade-off versus Cloud Run/GKE (Lesson 27).
