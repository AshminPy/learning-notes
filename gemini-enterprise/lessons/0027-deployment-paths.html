Deployment Paths: Cloud Run, GKE, Agent Runtime & Agent Engine Deployments

Every earlier phase of this course — building with ADK, governing with Agent Identity, evaluating with AutoRaters — quietly assumes the agent already runs somewhere. It doesn't, until you make one decision: which of three real deployment paths it runs on. Get this wrong and you either over-pay for infrastructure control you don't need, or hit a hard platform limit mid-build that a five-minute read here would have caught.

There's also a naming trap specific to this platform. If you've touched Vertex AI before — or read Ashmin's own SRE agent deploy-state notes — you've seen the term Agent Engine. That name didn't disappear; it's the former Vertex AI name for exactly what this platform now calls Agent Runtime. Same product, renamed. This lesson names that bridge explicitly, because the old name still surfaces in the SDK and the API itself.

Mental model: the three deployment paths are three ways to open a restaurant. Agent Runtime is renting a stall in a food court — the court handles power, cleaning, and foot traffic; you just cook. Cloud Run is renting your own shopfront — you sign your own lease (a container) and set your own hours, but the building's plumbing (serverless infrastructure) is still the landlord's problem. GKE is buying the whole building — total control over the kitchen and staffing, but you're also the one fixing the boiler at 2am. That predicts something concrete: if the food court doesn't serve your cuisine — today, that means non-Python agents — no amount of wanting a stall there helps. You need your own shopfront or building instead.

Deployment isn't the last step of the course by accident — every governance and evaluation concept from Phases F and G attaches to an agent after it's running somewhere. This lesson is the fork in the road that decides how much of that plumbing Google manages for you versus how much you manage yourself.

Agent Runtime — and the Agent Engine name you'll still see everywhere

Per Google's own Agent Runtime documentation: "Agent Runtime is a fully-managed, opinionated runtime that you can use to deploy, operate, and scale agentic applications," and it "abstracts away the underlying infrastructure, which lets you focus on agent logic instead of operations." That's the whole pitch — no servers, no cluster, no container registry required if you don't want one.

The naming bridge is stated directly in the docs, not something you have to infer: "Because the name of Agent Runtime changed over time, the name of the resource in the API reference is ReasoningEngine to maintain backwards compatibility." In practice this means the Python SDK module you actually import is still called agent_engines, and the managed resource it creates is still a ReasoningEngine under the hood — even though every current doc page, UI label, and this course call the product Agent Runtime. If you inherited code, runbooks, or deploy-state notes that say "Agent Engine," they're describing this exact thing, not something older or different.

Five ways to get an agent onto Agent Runtime

The deployment docs describe five distinct methods, all going through the same SDK call, client.agent_engines.create(...):

MethodBest for
Agent objectInteractive development (e.g. a Colab notebook) — deploys an in-memory agent object directly
Source filesCI/CD pipelines and Infrastructure-as-Code tools like Terraform — fully declarative, no Cloud Storage upload required
DockerfileCustom build steps, while still deploying to the managed runtime
Container image (Artifact Registry)Deploying a pre-built image you already produced elsewhere
Developer Connect (Git repo)Projects already managed in a Git repository — Google's own recommendation for that case

The actual deploy call, from Google's ADK quickstart, looks like this once you have a local agent (app) built and tested:

from vertexai import types

remote_agent = client.agent_engines.create(
    agent=app,
    config={
        "requirements": ["google-cloud-aiplatform[agent_engines,adk]"],
        "staging_bucket": "STAGING_BUCKET",
        "identity_type": types.IdentityType.AGENT_IDENTITY,
    }
)

Why it's built this way: notice identity_type: AGENT_IDENTITY sits right in the deploy call, not as a separate governance step bolted on afterward. This platform treats identity as a deploy-time property of the agent, which is exactly why Phase F's governance lessons assume deployment already happened — identity gets attached at the same moment the agent starts running, not later.

Cloud Run and GKE — the self-managed paths

Cloud Run sits in the middle: you build and own the container, but the underlying compute is still serverless — no cluster to patch. It's the right move the moment your agent needs a language Agent Runtime doesn't support, or a runtime dependency the managed path can't accommodate.

GKE gives full infrastructure control, and it comes with its own agent-specific tooling: Agent Sandbox, an open-source, Kubernetes-native execution environment built specifically for running untrusted agent code and tool calls safely. Per Google's own numbers (published May 20, 2026): Agent Sandbox natively supports gVisor kernel isolation and allocates 300 sandboxes per second, per cluster, with sub-second latency — "90% of allocations completing in 200 milliseconds." Running on Google's Axion N4A processors, it delivers "up to 30% better price-performance" than comparable hyperscaler offerings. That's the trade you're buying with GKE's extra operational burden: isolation and density at a scale the other two paths don't expose as a tunable knob.

Try it

Q1. You wrote your agent in TypeScript using ADK's TypeScript SDK. Can you deploy it straight to Agent Runtime today the same way you would a Python agent?

No. Agent Runtime deployment only supports Python today, even though ADK itself ships in five languages (Python, TypeScript, Go, Java, Kotlin). A TypeScript agent needs Cloud Run or GKE instead.

Now, before revealing: write out the deploy-time line from memory that attaches Agent Identity to an agent at the moment it's created on Agent Runtime.

Reveal the answer

"identity_type": types.IdentityType.AGENT_IDENTITY — passed inside the config dict of client.agent_engines.create(...). Identity is a property of the deploy call itself, not a separate step.

Common mistake: assuming "Agent Engine" in older docs, blog posts, or a teammate's code refers to a different or deprecated product. It doesn't — it's the exact same Agent Runtime this lesson covers, and the API resource name (ReasoningEngine) and SDK module (agent_engines) still use it internally, by design, for backward compatibility.

A controlled failure

# You have a working ADK agent written in TypeScript, tested locally.
# You try to deploy it the same way the Python quickstart shows:
remote_agent = client.agent_engines.create(agent=typescript_app, config={...})

Predict first: does this deploy successfully to Agent Runtime, just in a different language? Observe: it doesn't — Google's own deployment documentation states plainly that "Agent Runtime deployment only supports Python." The managed path has a hard language boundary that the framework itself doesn't share. The fix isn't a different SDK call — it's a different deployment target: package the TypeScript agent as a container and deploy it to Cloud Run (fastest path to serverless) or GKE (if you also need Agent Sandbox's isolation).

Production best practices

Agent RuntimePython agent, want fastest path to production with built-in identity/sessions/observabilityNon-Python agent, or you need custom network topologyLeast ops burden, least infrastructure control
Cloud RunAny language, want serverless ops without a clusterNeed GPU scheduling or dense multi-tenant isolationMiddle ground on both control and burden
GKENeed full infra control, or Agent Sandbox's isolation/density at scaleSmall team without existing Kubernetes operations capacityMost control, most operational burden

Production note: default to Agent Runtime unless you have a specific, named reason not to — a non-Python framework, a compliance requirement for custom network isolation, or a workload dense enough that Agent Sandbox's per-cluster sandbox rate genuinely matters. Teams that reach for GKE "just in case" before hitting one of those reasons are usually trading real operational cost for control they never exercise.

Recap
  • "Agent Engine" is the former Vertex AI name for Agent Runtime — same product; the API resource (ReasoningEngine) and SDK module (agent_engines) kept the old name for backward compatibility.
  • Agent Runtime is fully managed but Python-only today; Cloud Run and GKE accept any language, at increasing levels of operational control and burden.
  • Agent Identity attaches at deploy time (identity_type in the create call), not as a separate governance step afterward.
  • GKE's Agent Sandbox adds gVisor-isolated execution at 300 sandboxes/second/cluster — a density option the other two paths don't expose.
