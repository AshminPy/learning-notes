Context Management: Sessions, Memory & Artifacts

Every pattern in Lessons 8 and 9 quietly leaned on something this lesson finally names. A SequentialAgent's output_key handoff, a graph node's data flow between steps — both need somewhere to live between one step and the next. That "somewhere" isn't one thing in ADK; it's three, each with a different scope and a different lifetime, and confusing them is exactly what causes an agent to "forget" something a developer assumed it would remember.

Mental model: Session and its State are a whiteboard in today's meeting room — great for referencing what was said five minutes ago, wiped when the room resets unless someone specifically photographs it to a durable backend. Memory is the company wiki — searchable, built up from past meetings' minutes, still there next month. Artifacts are the shared drive folder — you don't scrawl a whole PDF's bytes on the whiteboard, you drop the file in the folder, and the folder keeps every version you've ever saved, not just the latest one. That predicts something concrete: a state key you write mid-conversation vanishes the moment an in-memory backend restarts, but something explicitly ingested into Memory survives that same restart, and a re-saved artifact never destroys the version that came before it.

Session and State: the current conversation, nothing more

Per ADK's docs, a Session represents "a single, ongoing interaction between a user and your agent system" — the chronological record of events within one conversation thread. State (session.state) is "data stored within a specific Session, used to manage information relevant only to the current, active conversation thread." State keys carry semantic prefixes that change their scope: plain keys and temp: are invocation/session-scoped, user: persists across a user's sessions (with a durable backend), and app: is application-wide. A SessionService — InMemorySessionService, DatabaseSessionService, or VertexAiSessionService — owns creating, updating, and deleting these sessions; the docs are blunt that the in-memory option is "designed specifically for local testing and fast development" and that everything in it "is lost when your application restarts."

Artifacts: versioned files, not text in a state key

Artifacts handle "named, versioned binary data" — files, images, audio, generated reports — that don't belong crammed into a text state value. Saving one is a single call: context.save_artifact(filename, artifact) returns an incrementing version number, and every prior version stays retrievable with context.load_artifact(filename, version=N) — the latest loads by default if you omit the version. context.list_artifacts() lists what's available. Filenames default to session scope; prefixing with user: (e.g. "user:settings.json") makes an artifact persist across that user's sessions instead. InMemoryArtifactService is the local, ephemeral option; GcsArtifactService persists to Google Cloud Storage for anything meant to survive a restart or redeploy.

Memory: searchable knowledge that outlives one conversation

Memory is the one layer explicitly designed to cross session boundaries. Per the docs, Memory "might span multiple past sessions or include external data sources" — a MemoryService ingests information, often from completed sessions, into a long-term store, and exposes it back to a running agent through context.search_memory(query). This is the mechanism that lets an agent recall something a user mentioned last week without that fact ever having been kept alive in this week's session state.

Try it

Q1. Your agent calls context.save_artifact("report.pdf", ...) twice, with two different sets of bytes. Does the second call overwrite the first, or does the first version stay retrievable?

The first version stays retrievable. save_artifact returns an incrementing version number rather than overwriting — you can load_artifact with a specific version number, or omit it to get the latest.

Now, before revealing: your agent writes a plain (unprefixed) state key mid-conversation. Does that value automatically show up in a brand-new conversation with the same user next week?

Reveal the answer

No. Plain session state is scoped to the current conversation thread only — it doesn't carry into a new session on its own. Anything meant to persist across sessions needs a user: (or app:) prefixed key on a durable backend, or has to be ingested into Memory explicitly.

Common mistake: shipping InMemorySessionService or InMemoryArtifactService to production because it worked fine in local testing. Both are documented as built specifically for local development — every session, state value, and artifact they hold is gone the moment the application restarts, which in production means gone on every redeploy.

A controlled failure

# A PNG's raw bytes are saved with the wrong declared type:
context.save_artifact(
    filename="chart.pdf",
    artifact=types.Part.from_bytes(data=png_bytes, mime_type="application/pdf")
)

Predict first: does save_artifact reject this because the bytes don't actually match a PDF? Observe: no — it saves successfully. Nothing in the artifact service validates that the declared mime_type matches the actual bytes; it stores whatever you tell it to store. The failure shows up later, downstream, when some other tool calls load_artifact and tries to interpret those bytes as a PDF and gets garbage or an outright parse error — which is exactly why the docs stress providing an accurate mime_type up front, not as a formality but as the only thing standing between this save and a confusing failure two steps later.

Production best practices

Production note: the backend choice per layer is a real decision, not boilerplate — DatabaseSessionService or VertexAiSessionService for session state, GcsArtifactService for artifacts, both once anything needs to survive past a local dev loop. State-key prefixes are the other lever worth planning deliberately: a design that quietly expects a plain state key to "just be there" next session is a design that will pass local testing and then quietly lose data in production the first time the service restarts.

Interview Q: "What's the actual difference between Session state and Memory in ADK, beyond one being 'short-term' and one being 'long-term'?" A: Session state is scoped to the current conversation thread and is only ever read/written directly by the running agent; Memory is a separately managed, searchable store — usually built from completed sessions or external sources — that an agent queries explicitly via search_memory. Expecting a plain state key to behave like Memory is the actual bug, not a naming confusion: nothing moves data from one to the other automatically.

Recap
  • Session/State covers only the current conversation thread; it's gone on restart unless backed by a durable SessionService.
  • Artifacts are versioned binary files — save_artifact never overwrites, it increments a version number you can still retrieve later.
  • Memory is the one layer explicitly built to cross session boundaries, queried via search_memory, usually filled from completed sessions or external sources.
  • InMemory* services are for local development only — every real deployment needs a durable backend per layer (Database/VertexAI for sessions, GCS for artifacts).
