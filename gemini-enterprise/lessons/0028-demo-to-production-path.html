The Full Demo-to-Production Path

Lesson 27 answered where an agent runs. This lesson answers a harder question: what actually has to happen, in what order, between "it demoed well in front of the team" and "it's trustworthy in front of real users"? Skip this and every phase of this course stays a pile of separate tools — ADK here, Model Armor there — instead of one repeatable path you can run again on the next agent.

Mental model: think of it like onboarding a new hire, not flipping a switch. A new hire doesn't go from interview straight to unsupervised production work — there's a supervised trial period first, with a small caseload and someone watching closely, before they get full responsibility. Skipping that trial doesn't make the hire more ready; it just moves the moment you discover a problem from "caught in supervision" to "discovered by a customer." That's exactly what skipping a staged rollout does to an agent.

Every phase before this lesson taught one box in that diagram in isolation. This lesson's only job is the arrows — the order, and why reordering any of them creates a specific, predictable failure.

The five stages, in Google's own words

Google's own guide to production-ready agents (published February 25, 2026) lays out a staged progression, not a single "deploy" event:

  • Build — architecture design, tool integration via MCP or A2A, context engineering, memory systems. This course's Phases B and C.
  • Evaluate — not just unit tests on individual components, but trajectory analysis: examining the full decision sequence an agent took, not only its final answer. The guide specifically calls out assessing "tool selection quality, reasoning quality, error recovery, and clarifying question generation" — all things a single happy-path demo run never exercises.
  • Govern — a security framework that keeps the agent "operating within intended boundaries," authentication and permissions controlling tool access, and real-time logging tracing every decision and action.
  • Deploy — session management, persistent memory, tool authentication, and a staged rollout rather than one release.
  • Observe — real-time logging and performance tracking, continuously, to catch problems "before expansion" to more users.

Deploy isn't one step — it's three

The same guide breaks "Deploy" itself into three stages, each with a distinct purpose:

StagePurpose
SandboxInternal testing in an isolated environment — validate core functionality and decision-making before anyone outside the team sees it
CanaryLimited rollout to real users — "catch issues before broader deployment" while monitoring behavior "in production-like conditions"
ProductionFull rollout to all users, with ongoing monitoring and logging carried forward, not switched off

Why it's built this way: canary exists specifically to shrink the blast radius of whatever Evaluate didn't catch. A golden dataset can't cover every real-world input; canary is the stage that trades a small, controlled dose of real-world exposure for the chance to catch a failure mode before it reaches everyone at once.

Now, before revealing: put these five words in the correct order from Google's own path — Observe, Build, Deploy, Govern, Evaluate.

Reveal the answer

Build → Evaluate → Govern → Deploy → Observe. Govern sits before Deploy, not after — security boundaries and permissions are checked into the agent before it ever reaches even the sandbox stage of deployment.

Common mistake: treating "the demo worked in front of stakeholders" as equivalent to "evaluated." A demo is a handful of happy-path runs performed by the person who built the agent — it exercises none of trajectory analysis's actual targets (tool selection under pressure, error recovery, clarifying questions on ambiguous input). A good demo and a passed evaluation are unrelated facts about the same agent.

A controlled failure

A team's agent passes every sandbox test. Under deadline pressure, they skip canary and push straight to 100% of production users.

Predict first: does skipping canary just save time, with no real downside if sandbox testing was thorough? Observe: per Google's own framing, canary's entire purpose is to "catch issues before broader deployment" under "production-like conditions" that sandbox — by definition internal-only — can't fully replicate (real user phrasing, real network conditions, real concurrent load). Skipping canary doesn't remove those failure modes; it just moves the first time you encounter one from "a small, monitored group" to "every user, at once." The fix isn't more sandbox testing — sandbox and canary test different things by design. The fix is running canary, even under deadline pressure, at a duration short enough to fit the deadline rather than skipped entirely.

Production best practices

Production note: a realistic team applying this path for an internal support agent: two weeks in sandbox against a golden dataset and internal dogfooding, one week in canary at 5% of real ticket volume with an engineer watching Agent Observability dashboards daily, then a graduated production rollout (25% → 100% over a few days) rather than a single cutover. The stages don't need to be long — they need to exist and be watched, not skipped under time pressure.

Exam and interview notes

No certification currently exists for this platform (re-checked at this lesson's write time, 2026-08-06) — this is the operational judgment a senior engineer is actually hired for.

Interview Q: "Walk me through how you'd take an agent from a working prototype to production on this platform." A: "Build it with ADK, then evaluate with trajectory-level testing — not just final-answer checks. Govern it before deploying: identity, permissions, and logging attached at deploy time, not bolted on after. Deploy through sandbox, then canary at limited real traffic, then full production. Observe continuously afterward, and feed what Observability finds back into the next Evaluate cycle."

Recap
  • The real path is five stages, in order: Build → Evaluate → Govern → Deploy → Observe, with Observe feeding back into the next iteration.
  • Evaluate means trajectory analysis (tool selection, reasoning, error recovery) — a demo tests none of that.
  • Deploy is itself three stages: sandbox (internal), canary (limited real users), production (full rollout) — not one release event.
  • Govern happens before Deploy, not after — identity, permissions, and logging are checked in before the agent runs anywhere real.
