Tools: Function Tools, OpenAPI, Built-ins

Lesson 2 defined a tool as "a single instrument on the desk — does exactly one thing, hands control straight back." Lesson 5 showed the tools field sitting on every Agent, without saying where those entries actually come from. There are three real answers — write one yourself, generate one from an API spec you didn't write, or use one ADK already ships — and each has a different failure mode when done carelessly.

Mental model: think of the three tool types as three ways to staff one desk. A function tool is training a new employee yourself — you write exactly what they do. An OpenAPI tool is hiring a vendor whose job is already fully specified in a contract (the OpenAPI spec) — you don't write their job description, you just point at the contract and ADK reads it. A built-in tool is someone already on staff, hired before you got there. That predicts something concrete: the amount of code you write is inversely proportional to how standardized the capability already is — a fully custom capability needs a hand-written function; a capability some other team already exposed via a documented API needs zero hand-written schema at all.

Where this fits

Function tools: your function, auto-wrapped

Per ADK's own docs, when you assign a plain function to an agent's tools list, "the framework automatically wraps it as a FunctionTool." The framework inspects your function's name, docstring, parameters, type hints, and defaults to generate the schema the model actually reasons over — you never hand-write that schema yourself. Two rules matter: required parameters need a type hint with no default value; optional ones need either a default value or a typing.Optional[SomeType] annotation. And the docstring isn't documentation for humans — per ADK's docs, "a well-written and comprehensive docstring is crucial for the LLM to understand how to use the tool effectively," because that docstring is what the model reads to decide when and how to call it.

def get_weather(city: str, unit: str):
    """Retrieves the weather for a city in the specified unit.

    Args:
        city (str): The city name.
        unit (str): The temperature unit, either 'Celsius' or 'Fahrenheit'.
    """

Return values matter too: ADK's guidance is to return a dictionary with a status key ("success", "error", "pending") so the model can reason about outcomes consistently across every tool. If a function returns something that isn't a dictionary, ADK wraps it automatically as {"result": value} — convenient, but it means you lose the ability to signal partial failure unless you return a dict yourself.

OpenAPI tools: generated, not written

When a capability already exists as a documented REST API, OpenAPIToolset generates the tools for you. Per ADK's docs, it "internally parses the spec, resolving any internal references ($ref) to understand the complete API structure," then creates one RestApiTool per operation — its name is "derived from the operationId in the spec (converted to snake_case, max 60 chars)," falling back to the HTTP method and path if operationId is missing. Parameters, request bodies, and authentication are all handled the same automatic way — global auth (API keys, OAuth) is "automatically applied to all generated RestApiTool instances."

from google.adk.tools.openapi_tool.openapi_spec_parser.openapi_toolset import OpenAPIToolset

toolset = OpenAPIToolset(spec_str=openapi_spec_json, spec_str_type="json")
api_agent = Agent(name="api_agent", model="gemini-flash-latest", tools=[toolset])

Why it's built this way: the moment an API's spec changes (a new field, a renamed operation), regenerating from the spec keeps the agent's tools in sync automatically — a hand-written function tool wrapping the same API would need a manual edit every time the underlying API does.

Built-in tools: already on staff

ADK ships "ready-to-use tools provided by the framework for common tasks" — Google Search, code execution, and Retrieval-Augmented Generation among them. These need no schema work at all; you add them to tools the same way as anything else, and the framework already knows their contract. They exist for the capabilities so common across agents that reimplementing them per project would be pure duplication.

Try it

Q1. You write a function tool with a complete docstring, but forget a type hint on a required parameter. What actually breaks?

The schema ADK generates for the model — type hints are what tell the framework the parameter's expected type. Without one, the tool's schema is incomplete or wrong, even though the docstring itself is fine; the two serve different, non-substitutable purposes.

Now, before revealing: a function tool returns a plain integer instead of a dictionary. What does the calling agent actually receive?

Reveal the answer

{"result": <that integer>} — ADK auto-wraps any non-dictionary return value under a result key. Convenient, but it means you can't signal a partial failure or extra context unless you return a real dictionary with your own keys, including status.

Common mistake: writing a function tool with a thin or missing docstring because "the code is self-explanatory." The model never sees your code — only the name, docstring, and parameter schema. A tool that's obvious to you reading the source is invisible in intent to the model deciding whether to call it, which shows up as an agent that has the right tool but never uses it correctly.

Predict first: does this function still get wrapped as a working tool, mechanically? Observe: yes — ADK still inspects the signature and wraps it as a FunctionTool with no error. The failure isn't mechanical, it's behavioral: with no docstring, the model has no description of what the tool does, what ticker means, or when to call it, so in practice the agent calls it rarely or incorrectly. This is a silent failure mode — nothing crashes, the agent just quietly underuses a tool it technically has.

Production best practices

Production note: at scale, teams prefer OpenAPI tools over hand-written function tools whenever a real API spec already exists — regenerating a toolset from an updated spec is a one-line change; keeping a hand-written wrapper in sync with someone else's API is an ongoing maintenance cost every time that API changes. Reserve function tools for logic that genuinely doesn't correspond to an existing API — internal business rules, local computation, anything with no spec to generate from.

Interview Q: "Your team needs an agent to call an internal REST API that already has OpenAPI documentation. Do you hand-write a function tool for each endpoint?" Recap
  • Function tools auto-wrap a plain function into a FunctionTool — type hints define the schema, the docstring defines intent for the model.
  • OpenAPI tools generate a RestApiTool per operation directly from an existing spec — no hand-written schema, and they stay in sync when the spec updates.
  • Built-in tools (Google Search, code execution, RAG) need no schema work at all.
  • A missing docstring doesn't break a function tool mechanically — it breaks it behaviorally, since the model can't tell when to use it.
