Part 1 — Platform vocabulary cheat sheet

A. Foundations

  • Gemini Enterprise Agent Platform is "the evolution of Vertex AI" — a rename and expansion, not a competing product (announced Google Cloud Next '26, April 22, 2026).
  • Four pillars organize everything: Build, Scale, Govern, Optimize.
  • Gemini Enterprise (the app: Agent Designer, Inbox, Projects, Canvas, Agent Gallery) is a different thing from the Agent Platform (the developer layer underneath it) — the app is where agents surface once built.

B. Building with ADK

  • Agent Development Kit ships in five languages: Python, TypeScript, Go, Java, Kotlin.
  • Tools: function tools, OpenAPI specs, and MCP (Model Context Protocol) tools.
  • Multi-agent orchestration: sequential, parallel, and looped execution; ADK 2.0 adds graph-based orchestration for deterministic logic combined with AI reasoning.
  • Context is structured data, not raw concatenation — sessions, memory, and artifacts are managed and filtered automatically.

C. No-Code Building

  • Agent Designer builds agents from natural language, including schedule- or trigger-based agents invoked by another business application.
  • Agent Studio / raw ADK is the code-first alternative for cases Agent Designer's natural-language flow doesn't fit.

D. Models

  • Model Garden is where model selection happens across the platform's supported models.
  • RAG grounds agent responses in enterprise data instead of relying on model knowledge alone.

E. Running & Scaling

  • Agent Runtime is the managed execution layer — formerly named Agent Engine under Vertex AI; the API resource is still ReasoningEngine and the SDK module is still agent_engines (Lesson 27).
  • A2A (agent-to-agent) protocol handles orchestration between separate agents.
  • Memory Bank and Memory Profiles carry context across sessions, not just within one.

F. Governance & Security

  • Agent Identity — a SPIFFE-based cryptographic identity per agent, using auto-renewed X.509 certificates over mTLS; attached at deploy time via identity_type (Lesson 27).
  • Agent Gateway — the networking layer securing client-to-agent and agent-to-anywhere traffic.
  • Model Armor — an optional layer extending Agent Gateway with runtime protection against prompt injection and sensitive data leakage.

G. Optimize

  • Agent and model evaluation runs on one engine with 20+ pre-built metrics (trajectory quality, final response quality, hallucination, grounding, safety) plus custom code-based or LLM-as-a-judge metrics — generally available as of this course's writing.
  • Agent Simulation stress-tests agents against scenarios before deployment; Agent Observability gives real-time visibility afterward.

H. Demo to Production (this phase)

  • Three deployment paths: Agent Runtime (managed, Python-only today), Cloud Run (self-managed container, any language), GKE (full control, Agent Sandbox's gVisor isolation at 300 sandboxes/sec/cluster).
  • The real path to production is five stages — Build → Evaluate → Govern → Deploy → Observe — with Deploy itself split into sandbox, canary, and production.

Top 4 traps

  1. "Agent Engine" and "Agent Runtime" are the same product, not two different ones — the old name persists in the SDK and API by design (Lesson 27).
  2. Agent Runtime deployment is Python-only today, even though ADK itself is multi-language — a non-Python agent needs Cloud Run or GKE (Lesson 27).
  3. "The demo worked" and "it's evaluated" are unrelated claims — evaluation means trajectory-level testing (tool selection, error recovery), which a happy-path demo never exercises (Lesson 28).
  4. Skipping canary doesn't remove a failure mode sandbox testing missed — it just moves the first time you hit it from a small monitored group to every user at once (Lesson 28).

Part 2 — Practical assessment (timed)

Three tasks covering this phase's real judgment calls. Time yourself — targets below are a competent-pace guide, not a hard limit. Attempt fully before revealing the hidden answer.

Task 1 — Choosing a deployment path · target 3 min
A teammate has an ADK agent written in Go that needs to go to production this week. They ask whether Agent Runtime is the fastest option. What do you tell them, and what do you recommend instead?

Agent Runtime deployment only supports Python today, regardless of which language ADK itself supports — so it isn't an option here at all, not just a slower one. Recommend Cloud Run: it accepts any language, stays serverless (no cluster to stand up under a one-week deadline), and is the middle ground between Agent Runtime's convenience and GKE's full control. GKE is overkill unless they specifically need Agent Sandbox's isolation.

Task 2 — Spotting a skipped stage · target 4 min
A team says: "We ran the agent against our golden evaluation dataset, it passed, then we deployed straight to 100% of production." Name the specific stage they skipped and the concrete risk it leaves unaddressed.

They skipped canary. A golden dataset — however thorough — can't cover every real-world input, phrasing, or concurrent-load condition; canary's specific job is catching exactly those gaps against a small slice of real traffic before the whole user base hits them at once. Passing evaluation and skipping canary means the first real-world failure mode surfaces at full volume, not in a monitored, limited blast radius.

Task 3 — The naming bridge · target 2 min
You find a two-year-old internal doc that says: "Deploy new agents to Agent Engine, staging bucket required." Is this doc describing a deprecated product, and what (if anything) needs to change before following it today?

Not deprecated — "Agent Engine" is the former Vertex AI name for what's now called Agent Runtime; the staging-bucket requirement and the underlying deploy mechanism are the same thing under a new name. What needs to change is terminology in docs and onboarding material (so new hires searching current docs can find it), not the underlying deployment approach itself.
