Agent Development Kit (ADK) Overview

Lesson 2 gave you the vocabulary — agent, tool, model — and Lesson 3 was this course's one detour up to the no-code app floor. Both lessons promised the same thing: Phase B is where you actually build with that vocabulary, not just define it. The gap between "an agent is a model plus tools plus instructions" and a running, debuggable, deployable piece of software is exactly what a framework fills. That framework is the Agent Development Kit — everything from here through Lesson 10 is a detail sitting inside it.

Mental model: ADK is a workbench with power tools, not a pile of raw parts. You could wire an agent by hand — call a model API directly, parse its output, decide which function to run yourself — the same way you could build furniture with no power tools at all. ADK is the framework that already built the saw, the clamps, and the measuring jig: define an agent's name, model, instruction, and tools, and ADK handles the reasoning loop, the tool-calling protocol, and (later, Phase E) how it actually runs at scale. That predicts something concrete: the same agent definition you write today can move from your laptop to Cloud Run, GKE, or Agent Runtime later (Phase E, Lesson 15) without rewriting its logic — because ADK deliberately separates "what the agent does" from "where it runs."

What ADK actually is

Per its own documentation, ADK is "the open-source agent development framework that lets you build, debug, and deploy reliable AI agents at enterprise scale." Two words there matter more than they look: open-source means you install it as a library, not sign up for a hosted service, and enterprise scale is a deliberate contrast with toy demo frameworks — the same code path is meant to carry you from a first prototype to production. ADK ships in five languages — Python, TypeScript, Go, Java, and Kotlin — each with its own repository and install method. This course's code examples use Python for consistency, exactly as Lesson 2 flagged; the concepts hold across all five.

Installing ADK and running your first agent

The install is one command: pip install google-adk (Python 3.10+ and a virtual environment recommended). From there, adk create my_agent scaffolds a project with agent.py, .env, and __init__.py. The whole shape of an agent lives in one object:

from google.adk.agents.llm_agent import Agent

def get_current_time(city: str) -> dict:
    """Returns the current time in a specified city."""
    return {"status": "success", "city": city, "time": "10:30 AM"}

root_agent = Agent(
    model='gemini-flash-latest',
    name='root_agent',
    description="Tells the current time in a specified city.",
    instruction="You are a helpful assistant that tells the current time in cities.",
    tools=[get_current_time],
)

Notice this is Lesson 2's definition made literal: a model string, an instruction, and a list of tools — nothing else is required to have a real, callable agent. Set GOOGLE_API_KEY in .env, then run it with adk run my_agent from the terminal, or adk web --port 8000 for a browser UI at localhost:8000 — the same agent definition, two different ways to talk to it.

Q1. What's the exact pip command that installs ADK, and what Python version does it require at minimum?

Now, before revealing: looking at the root_agent code above, which single field would you change to make this same agent answer in French instead of English — without touching its tools or model?

Reveal the answer

instruction. It's the only field that shapes behavior/personality/language — the model and tools stay exactly the same, which is the whole point of separating instruction from the reasoning engine underneath it (Lesson 5 goes deep on this).

Common mistake: treating ADK and Agent Runtime as the same thing because both show up in the same sentence about "building and deploying agents." ADK is the framework you write code against, installed locally as a library. Agent Runtime (Phase E, Lesson 15) is one of several places that code can actually execute in production. Building with ADK doesn't mean anything is deployed yet — that's always a separate, later step.

A controlled failure

adk create my_agent
# ...edit agent.py to match the example above, but skip the .env step...
adk run my_agent

Predict first: does the agent's code have a defect if this fails, or is something else missing? Observe: without a valid GOOGLE_API_KEY configured in .env, adk run and adk web have no way to authenticate to the model backend your agent's model field names — the failure happens at the authentication boundary, before your instruction or tools are ever reached. The fix is setting the key and rerunning, not debugging agent.py — a distinction worth keeping straight once your agents get more complex and a real bug could be hiding behind a misleading first guess.

Production best practices

Production note: ADK's own framing is that the exact same agent code should carry you from prototype to production — per its docs, deploying to Google Cloud via Agent Runtime, Cloud Run, or GKE gains "managed infrastructure, built-in authentication, Cloud Trace observability, and enterprise-grade security" without code changes. Practically: don't special-case your agent's logic for "the demo version" versus "the real version." If you find yourself doing that, the difference belongs in deployment configuration (Phase E), not in the agent definition itself.

Interview Q: "When would you reach for raw ADK instead of Agent Studio?" A: "When the agent needs advanced customization, complex control-flow logic, or integration with existing systems beyond what a low-code canvas can express — Agent Studio (Lesson 12) even exports to real ADK code for exactly this handoff, so it's a graduation path, not a wall."

Recap
  • ADK is an open-source framework, installed as a library (pip install google-adk), not a hosted service — the same code carries a prototype through to production.
  • An agent's whole shape is name, model, instruction, and tools — everything else is orchestration and infrastructure sitting on top of that.
  • ADK ships in five languages; this course uses Python for consistency.
  • Building with ADK and deploying it are separate steps — ADK is the framework, Agent Runtime/Cloud Run/GKE (Phase E) are where it runs.
