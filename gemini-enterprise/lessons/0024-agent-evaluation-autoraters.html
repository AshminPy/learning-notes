Agent Evaluation: AutoRaters, Online Evaluation & Synthetic Test Scenarios

Lesson 23 gave you the schema an evaluation dataset needs. This lesson is what actually happens once you run one against a real agent: automated raters that score whole conversations instead of single replies, a way to keep scoring the agent after it's already live, and a way to generate the test cases in the first place instead of hand-authoring every one.

Mental model: an AutoRater is a grading TA who reads the entire transcript before scoring, not just the last line. A last-message-only check can only ever judge the final reply. A multi-turn AutoRater reads every turn, so it can catch an agent that answers turn 1 perfectly and then quietly contradicts itself by turn 4. That predicts something concrete: a metric named multi_turn_task_success can fail a conversation that a single-turn grader would happily pass, because the two are looking at completely different amounts of evidence.

This five-phase workflow — define, infer, trace, score, analyze — is the platform's own structure for agent evaluation. Lesson 23's dataset schema is what step 1 produces; steps 3 and 4 are where this lesson's AutoRaters actually do their work.

AutoRaters: scoring the whole conversation

Per the platform's agent-evaluation docs, evaluation supports both prebuilt and custom raters, and specifically multi-turn evaluation using autoraters that analyze conversations across multiple steps — not just the final response. Metrics split the same way Lesson 23's dataset fields did: some are reference-based (they need an expected answer — Lesson 23's reference or reference_trajectory), others are reference-free (they evaluate the trace on its own merits, no golden answer required). A metric like multi_turn_task_success judges whether the agent actually accomplished the user's goal across the full conversation, not whether any single reply looked good in isolation.

Synthetic test scenarios: where test cases come from

Hand-writing every test conversation doesn't scale. The SDK generates them instead:

eval_dataset = client.evals.generate_conversation_scenarios(
    agent_info=support_agent_info,
    config={
        "count": 20,
        "generation_instruction": "Generate scenarios where a user asks for a refund",
    },
)

Each generated scenario has a starting prompt and a conversation plan, produced from your agent's own instructions and tool definitions — you describe the shape of the scenarios you want ("a user asks for a refund"), and the count, and the generator produces that many distinct starting points instead of you writing 20 refund conversations by hand.

Running the evaluation

Install with pip install google-cloud-aiplatform[adk,evaluation]. The core loop chains three SDK calls:

results = client.evals.run_inference(agent=support_agent, src=eval_dataset)

eval_result = client.evals.evaluate(
    dataset=results,
    metrics=["multi_turn_task_success"],
)

The same workflow exists in the console: Agent Platform > Agents > Deployments, select your agent's Dashboard tab, open the Evaluation subsection, click New Evaluation, define test cases and select metrics, then Run Evaluation. Both paths run the same underlying five-phase evaluation.

Online evaluation: scoring the agent after launch

Evaluation doesn't stop once an agent ships. Online Monitors continuously grade live production traffic as it arrives, surfacing scores over time in built-in dashboards and supporting drift alerts. Per Google's own GA announcement (2026-07-31): "Agent quality must be measured during development against the cases you wrote, and after launch against the tasks the agent actually performed." That's two distinct measurements, not one replacing the other — pre-launch evaluation checks the cases you anticipated; online evaluation checks the real traffic you didn't.

Try it

Q1. Your agent answers turn 1 of a 5-turn conversation correctly, then contradicts itself on turn 4. Would a single-turn, last-message-only metric reliably catch this?

No — a single-turn check most likely only sees the final message. A multi-turn AutoRater analyzing the full transcript (like multi_turn_task_success) is what's built to catch a contradiction that only appears partway through a conversation.

Before revealing: write the one line of config you'd add to generate_conversation_scenarios() to specifically stress-test refund requests for an order ID that doesn't exist.

Reveal a modeled answer

config={
    "count": 15,
    "generation_instruction": "Generate scenarios where a user requests a refund for an order ID that doesn't exist",

Common mistake: assuming online evaluation replaces pre-launch evaluation because "the monitors will catch problems anyway." Google's own framing is explicit that quality gets measured twice, for different reasons — during development against cases you wrote, and after launch against what actually happened. Skipping pre-launch evaluation because online monitors exist means real users become your first test cases.

Predict first: can a trajectory metric needing reference_trajectory (Lesson 23) run cleanly against a dataset that only came from synthetic scenario generation? Observe: not without an extra step — a synthetic scenario gives you a trace of what the agent did, but not a golden reference_trajectory of what it should have done, unless you separately author or derive one. That's exactly why multi_turn_task_success — reference-free, judging the trace on its own merits — is the metric reached for on synthetic data, while trajectory-exact-match style metrics need hand-labeled or otherwise-sourced golden trajectories. Same reference-based vs. reference-free split from Lesson 23, now applied to a full multi-turn run.

Production best practices

Production note: the platform ships 20+ pre-built metrics covering quality, safety, grounding, and tool use, plus adaptive rubrics that tailor criteria per case rather than one fixed rubric for every row. The realistic pattern: run offline evaluation in CI on every prompt or tool-definition change (the development-time check), and leave Online Monitors watching production continuously for drift (the after-launch check) — treating either one alone as sufficient is how regressions ship unnoticed.

Exam and interview notes

No certification currently exists for this platform (confirmed 2026-08-06) — this is real agent-quality engineering, not exam trivia.

Interview Q: "Why would you generate synthetic test scenarios instead of just hand-writing test cases for an agent?" A: Hand-written cases only cover what you thought to write, and don't scale past a handful of examples. Generating scenarios from the agent's own instructions and tools produces many distinct, realistic conversation starts at once, covering edge cases (like a nonexistent order ID) a human author is likely to miss.

  • Agent evaluation is a five-phase workflow: define eval cases, run inferences, generate traces, compute metrics (AutoRaters), analyze & optimize.
  • Multi-turn AutoRaters score the whole conversation, catching failures a last-message-only check would miss.
  • generate_conversation_scenarios() produces synthetic test cases from your agent's own instructions and tools instead of hand-authored ones.
  • Online evaluation (Online Monitors) continuously grades live production traffic — a second, different measurement from pre-launch evaluation, not a replacement for it.
