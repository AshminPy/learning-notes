Core Vocabulary: Agents, Tools, Models

Lesson 1 mapped where the platform sits relative to Vertex AI. Before you read a single ADK code sample in Phase B, you need three words used precisely: agent, tool, and model. This course uses them exactly as the Agent Development Kit's own docs do — and mixing them up is the single most common beginner confusion in agent frameworks generally, not just this one.

Mental model: an agent is a small, autonomous employee. A model is that employee's brain — the reasoning engine (Gemini) doing the actual thinking. A tool is a single instrument on their desk — a stapler, a phone — that does exactly one thing when picked up and hands control straight back. That predicts something concrete: a tool should never need its own multi-step reasoning loop. The moment something needs to decide, plan, or call other things on its own judgment, it has stopped being a tool and become a sub-agent — exactly the multi-agent pattern Lesson 8 covers.

Phase B spends seven lessons building on exactly these three words. Get the boundary between "agent" and "tool" wrong here, and Lesson 8's multi-agent systems and Lesson 9's graph orchestration will both feel like they're reinventing vocabulary instead of composing it.

Agent: model + tools + instructions

Per the Agent Development Kit's own framing, an agent combines a language model with tools and instructions to accomplish tasks autonomously. The autonomy is the key word — an agent doesn't just answer a single prompt, it decides which tools to call, in what order, based on the instructions it was given and what the model reasons through at each step.

Tool: one callable capability

A tool is a capability an agent can invoke — a single, discrete action, not a reasoning process of its own. ADK's own examples name concrete ones like google_search and GoogleSearchTool: an agent calls the tool, the tool does exactly one thing (run a search), and control returns to the agent with a result. Tools are what let an agent interact with external systems and data beyond pure language generation — without them, an agent could only talk, never act.

Model: the reasoning engine underneath

The model is the underlying generative AI engine powering an agent — ADK's documentation names examples like gemini-flash-latest. It handles the reasoning and decision-making inside an agent, but it is a swappable component, not the agent itself: the same agent instructions and tools can often run against a different model, which is exactly what Phase D's Model Garden lesson (Lesson 13) is about. ADK itself is available in Python, TypeScript, Go, Java, and Kotlin — the vocabulary in this lesson holds across all five, even though this course's code examples in Phase B use one language for consistency.

Try it

Q1. An agent calls google_search mid-conversation to look something up. Is google_search itself an agent or a tool?

A tool. It's a single callable capability the agent invokes for one discrete action — it doesn't reason, plan, or decide anything on its own, which is what would make it an agent instead.

Now, before revealing: predict this one using only the definitions above — no lookup needed. If you gave that same search function its own multi-step planning loop and let it decide on its own judgment when to call other functions, would ADK still call it a "tool"?

Reveal the answer

No. At that point it has its own reasoning and autonomy — the exact definition of an agent, not a tool. This is precisely the sub-agent pattern Lesson 8's multi-agent systems formalizes.

Common mistake: calling the model "the agent." Gemini and "the agent" are not the same thing — the model is the swappable reasoning engine inside an agent, while the agent is the combination of that model with its tools and instructions. Confusing the two makes Lesson 13's model-selection content look like it's changing "the agent" when it's really only swapping one component inside it.

A controlled failure

Using only the definitions above — not a lookup — predict: you want an agent to remember something a user told it three turns ago the next time a tool gets called. Does that memory live inside the tool, or somewhere else?

Predict first, then check your reasoning against the definitions in this lesson. Observe: a tool is a stateless, single-purpose capability — it doesn't hold memory between invocations. State and conversation history belong to the agent (its session), and at platform scale, to Memory Bank and Memory Profiles, which Lesson 17 covers directly. Building a "tool" that secretly tracks state across calls is a design smell — it means what you actually built is an under-specified sub-agent wearing a tool's name.

Production note: when you design your own tools in Phase B, keep each one doing exactly one thing — the way GoogleSearchTool does exactly one search. A "tool" that internally branches into five different behaviors depending on its input is usually an unbuilt sub-agent in disguise; split it out the moment you notice that pattern, using the same agent/tool boundary this lesson defines.

Recap
  • An agent combines a model, tools, and instructions to act autonomously — the autonomy is what separates it from a tool.

  • The model is the swappable reasoning engine inside an agent — not the agent itself.
