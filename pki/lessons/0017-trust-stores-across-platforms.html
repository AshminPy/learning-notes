Trust Stores Across Windows, Linux, macOS, Java, and Browsers

What you will learn

Why there is no single "the trust store" on a modern machine — how many independent trust stores actually exist on a typical laptop, exactly which ones Windows, Linux, macOS, Java, and each major browser read from, and the real, documented mechanism each one uses to decide which root CAs to ship and update. You'll also learn why adding a private root CA to the OS store doesn't automatically make every application on that machine trust it.

Why this matters

"I added the CA to the trust store and it still doesn't work" is one of the most common real support tickets in PKI, and the honest answer is almost always "which trust store?" A single Windows laptop can carry five or more independent root stores at once — the OS store, Firefox's own store, Chrome's own store (as of Chrome 105+), the JRE's cacerts, and possibly a container image's own ca-certificates bundle — each populated and updated by a completely different mechanism, governed by a different root program's policy. Deploying a private CA without knowing this leads to "it works in Chrome but not curl," "it works in the browser but not the Java service," or an internal CA rollout that silently misses every non-Windows machine.

Simple explanation

Think of a "trust store" as a curated guest list a piece of software checks before it lets a certificate's signer into the room. Windows keeps its own guest list. macOS keeps its own. Each Linux distro's package manager keeps one. Java keeps a completely separate one bundled inside the JRE. And critically, Firefox and — since 2022/2023 — Chrome and Edge increasingly bring their own guest list rather than reading the building's list at the front door. Adding a name to one list does not add it to the others. That's the whole lesson: trust is not one shared, OS-wide fact — it's a set of independently maintained lists, each with its own update mechanism and its own root program deciding who gets on it.

How it works

Windows — the OS-level Trusted Root store

Windows ships and updates its root store per the Microsoft Trusted Root Certificate Program. CAs apply for inclusion through CCADB, undergo annual audits (WebTrust or ETSI), and once enrolled are subject to strict technical requirements: root certificates must be self-signed X.509 v3, valid 8–25 years, with Key Usage marked critical and keyCertSign/cRLSign set, and the CA must give Microsoft 120 days' notice before transferring ownership of an enrolled root. Locally, roots live in the Trusted Root Certification Authorities certificate store, manageable via certmgr.msc (current user) / certlm.msc (local machine), certutil, or Group Policy for enterprise-added private CAs.

Linux — no OS store, a distro-family convention instead

There is no single "Linux trust store" — each distro family ships a ca-certificates package that assembles one from files on disk, and the two major families use different tooling:

  • Debian/Ubuntu family: certificates go in /usr/local/share/ca-certificates/ (locally added, implicitly trusted, must have a .crt extension) or are selected via /etc/ca-certificates.conf from /usr/share/ca-certificates/. Running update-ca-certificates regenerates the single bundle applications actually read: /etc/ssl/certs/ca-certificates.crt.
  • RHEL/Fedora family: certificates go in /etc/pki/ca-trust/source/anchors/, and update-ca-trust extract regenerates /etc/pki/tls/certs/ca-bundle.crt (and PEM/legacy formats alongside it).

Any tool that links against OpenSSL/GnuTLS on that distro reads the regenerated bundle — but only after the update command has been run. A certificate simply copied into the source directory and never followed by update-ca-certificates/update-ca-trust is not yet trusted by anything.

macOS — Keychain

Apple runs its own root program (the Apple Root Certificate Program), with CA inclusion requests submitted through CCADB and reviewed at Apple's sole discretion, audited annually against WebTrust or ETSI criteria per certificate type (TLS, EV TLS, S/MIME, client auth). Locally, roots live in Keychain Access — the System Roots keychain holds Apple's shipped root program, while an administrator-added private CA typically goes into the System keychain with its trust setting explicitly configured (manageable via the security command-line tool, e.g. security add-trusted-cert). Apple's program is what Safari and Mail (and, per Apple's iOS/iPadOS App Store policy, other apps that must use Apple's verifier) ultimately consult.

Java — its own store, isolated from all of the above

The JRE/JDK ships a completely separate truststore, cacerts, at $JAVA_HOME/lib/security/cacerts. Since JDK 18, it's a password-less PKCS#12 keystore (OpenJDK migrated it off the older JKS format specifically because JKS's "protection" was just the same well-known changeit password on every install, which protected nothing); on JDK 17 and earlier you'll still find it as classic JKS, password changeit. Either way it has nothing to do with the OS store — a Java application will not trust a certificate just because Windows or the distro's ca-certificates bundle trusts it. changeit still works as the password on newer JDKs too (PKCS#12 accepts it for backward compatibility even though nothing is actually password-protected anymore) — Oracle's own documentation still recommends changing it and locking down file permissions on installation, for any environment where you add sensitive material to the store. Managed entirely with keytool:

# list everything currently trusted
keytool -list -cacerts

# add your private/internal CA
keytool -importcert -alias my-internal-ca -file internal-ca.crt -cacerts

# remove a CA you no longer trust
keytool -delete -alias some-old-ca -cacerts

Browsers — increasingly their own thing, not the OS's

This is where the biggest, most current source of confusion sits, and it has changed materially in the last few years:

  • Firefox has never used the OS store by default. It ships and maintains its own independent, NSS-based root store under the Mozilla Root Store Policy (current version 3.1, effective July 1, 2026) — a separate CCADB-driven inclusion/audit process from Microsoft's or Apple's. An OS-added private CA is not automatically trusted by Firefox; an administrator has to explicitly enable "Enterprise Roots" support (the security.enterprise_roots.enabled preference, or the ImportEnterpriseRoots enterprise policy) — supported on Windows and macOS only, not Linux — before Firefox will import roots from the OS's Trusted Root store.
  • Chrome has moved the same direction. Under the Chrome Root Program (current policy version 1.8, effective February 5, 2026), Chrome ships and enforces its own Chrome Root Store, built from CCADB data and Chrome's own audit/CT-logging requirements, and this is enabled by default on Windows, macOS, ChromeOS, Linux, and Android — Chrome no longer defers to the OS's default public-trust decision on those platforms. The one documented exception is iOS: Apple's App Store policy requires Chrome for iOS to use Apple's own certificate verifier and root store instead.
  • Microsoft Edge followed the same pattern starting at Edge 112 (2023): on Windows and macOS, Edge ships its own built-in certificate trust list and verifier, sourced from the Microsoft Trusted Root Certificate Program's CTL but decoupled from the OS's live verification path — while still also querying and trusting locally-installed (user/enterprise-added) roots from the OS store. As of the current Microsoft documentation, Linux and Android rollout for this same change is still "to be determined"; iOS/iPadOS continue to use Apple's store per Apple's App Store policy.

The practical upshot: on the same Windows laptop, curl (OpenSSL against the Windows store), Edge (its own built-in CTL, sourced from Microsoft's program but not the same live check path), and Firefox (its own independent NSS store) can each reach a different trust verdict about the same certificate — not because any of them is broken, but because each one, by design, is consulting a different list.

One laptop, several independent trust stores:

  read by: curl/OpenSSL apps, legacy IE, most Win32 software
  Edge also reads locally-added roots from here (built-in CTL for its own defaults)

  independent of the OS store unless "Enterprise Roots" is explicitly enabled

  own store on Windows/macOS/ChromeOS/Linux/Android; Apple's store on iOS only

  verifier since Edge 112 (Win/macOS); still trusts locally-added OS roots

macOS Keychain              <- Apple Root Certificate Program
  System Roots keychain (Apple's own) + System keychain (admin-added)

$JAVA_HOME/lib/security/cacerts   <- JRE's own JKS store, fully isolated
  keytool -list/-importcert/-delete -cacerts

/etc/ssl/certs/ca-certificates.crt (Debian/Ubuntu)
/etc/pki/tls/certs/ca-bundle.crt   (RHEL/Fedora)
  <- assembled from local files by update-ca-certificates / update-ca-trust

Adding a private root to ONE of these adds it to exactly that one.

Important terminology

  • Root store / trust store — the set of root CA certificates a given piece of software treats as trust anchors when validating a chain.
  • Root program — the governance process (Mozilla, Apple, Microsoft, Chrome/Google) that decides which CAs get included in a specific trust store, and under what audit/compliance obligations.
  • CCADB (Common CA Database) — the shared database multiple root programs (Mozilla, Apple, Microsoft, Chrome) use for CA inclusion requests, audit evidence, and disclosure — one submission point feeding several independent decisions.
  • Enterprise Roots (Firefox) — the explicit opt-in (security.enterprise_roots.enabled / ImportEnterpriseRoots policy) that makes Firefox import roots from the Windows or macOS OS store; off unless configured.
  • cacerts — the JRE/JDK's own truststore file, isolated from the OS and from every browser's store.

Real-world example

A team stands up a private internal CA, pushes the root certificate to every domain-joined Windows machine via Group Policy, and calls the rollout done. Reports trickle in over the next week: curl-based health checks and the internal admin tool (a Win32 app reading the OS store) work fine. Firefox users get "Warning: Potential Security Risk Ahead" on the same internal site, because Firefox never reads the OS store by default. A Java-based internal service making outbound calls to another internal service throws PKIX path building failed, because nobody imported the root into that JRE's cacerts. Nothing about the CA or the certificate is broken — the rollout only reached one of the five trust stores actually in use on that fleet.

Hands-on lab

Track B. Generate a private root CA, then observe how it is trusted (or not) by different local stores on your own machine:

# Generate a throwaway private root CA
openssl req -x509 -newkey rsa:2048 -keyout lab-root.key -out lab-root.crt \
  -days 30 -nodes -subj "/CN=Lab Private Root CA"

# Confirm it is NOT yet trusted anywhere
openssl verify lab-root.crt   # expect: self-signed certificate error, that's expected

# Import into the Java cacerts store only, and prove it's isolated
sudo keytool -importcert -alias lab-root -file lab-root.crt -cacerts -storepass changeit -noprompt
keytool -list -cacerts -storepass changeit | grep -i lab-root

# On Linux: import at the OS level instead, and confirm cacerts is unaffected
sudo cp lab-root.crt /usr/local/share/ca-certificates/lab-root.crt   # Debian/Ubuntu
sudo update-ca-certificates
grep -c "Lab Private Root CA" /etc/ssl/certs/ca-certificates.crt     # present at OS level
keytool -list -cacerts -storepass changeit | grep -ic lab-root       # still separate

# Clean up afterward
sudo keytool -delete -alias lab-root -cacerts -storepass changeit
sudo rm /usr/local/share/ca-certificates/lab-root.crt && sudo update-ca-certificates --fresh

Expected result: importing into cacerts makes the root visible only to keytool -list -cacerts, not to the OS-level bundle, and vice versa for the OS-level import — direct, hands-on proof that these are genuinely separate stores, not one shared list.

What can go wrong

The most common mistake is assuming "I added it to the trust store" means all of them. A close second: forgetting that adding a certificate file to a Linux ca-certificates source directory does nothing until update-ca-certificates/update-ca-trust actually regenerates the bundle applications read. A third, increasingly common one since Chrome 105+/Edge 112: assuming a certificate trusted by Windows is automatically trusted by every browser on that machine — Chrome and (on Windows/macOS) Edge now ship their own default trust decisions, independent of the OS store's default public-CA list, even though both still honor locally/enterprise-added roots from it.

Troubleshooting

When one application trusts a certificate and another on the same machine doesn't, the fix is never "reinstall the certificate" — it's identifying which trust store each application actually reads. For a Java service throwing PKIX path building failed: unable to find valid certification path, check cacerts specifically, not the OS store. For "works in curl, fails in Firefox," check whether Enterprise Roots is enabled — Firefox's independent store is very often the actual cause, not a broken certificate. For "worked before a Chrome/Edge update, fails now," check whether the browser recently moved to its own built-in root store on that platform (Chrome 105+, Edge 112+) — a certificate chaining to a root that's in the OS's Trusted Root store but not in that browser's own root list will now fail there specifically.

Security considerations

Every additional independent trust store is an additional place a rogue or compromised root can be planted without triggering the same detection every other store would apply — a root pushed only into an OS's Trusted Root store via a compromised management tool would not need to also fool Mozilla's or Chrome's own root program, since those browsers may not even consult it. Treat each trust store as its own attack surface with its own audit trail: know exactly which roots are present in each one on your managed fleet, and why. Never disable a browser's own root-verification path (e.g. via a "trust everything" flag) to work around a distribution gap — fix the distribution instead.

Production best practices

When rolling out a private/internal CA, explicitly enumerate every trust store in your actual fleet — OS store (Windows GPO / macOS profile / Linux config-management module), each JRE's cacerts (via configuration management, not manual keytool on each host), and Firefox's Enterprise Roots policy if Firefox is in use — and automate distribution to all of them, not just the OS store. For Chrome/Edge on platforms where they now use their own default store, remember that locally/enterprise-added roots are still honored by both, so a private CA rollout through proper OS/enterprise channels keeps working; it's only public-CA-trust decisions that moved out of the OS's hands. Re-verify trust-store rollout after any major browser version bump — Chrome 105 and Edge 112 both silently changed which store was authoritative by default, and a rollout built against the old assumption can quietly stop covering a fleet.

Exam and interview notes

Interview Q: "I added our internal CA to Windows' trust store, but it's not trusted in Firefox. Why?" A: "Firefox ships and maintains its own independent, NSS-based root store under the Mozilla Root Store Policy — it doesn't read the Windows OS store by default. You need to either add the CA to Firefox's own store directly, or enable Enterprise Roots support so Firefox imports OS-trusted roots — that policy only works on Windows and macOS, not Linux."

Interview Q: "Does Chrome use the operating system's certificate store?" A: "Not for its default trust decisions anymore. Since Chrome 105+ (per the current Chrome Root Program policy), Chrome ships its own Chrome Root Store on Windows, macOS, ChromeOS, Linux, and Android — the one platform exception is iOS, where Apple's App Store policy forces Chrome to use Apple's own root store and verifier instead. Locally-added enterprise roots are still honored across these platforms."

Recap
  • There is no single OS-wide trust store — Windows, each Linux distro family, macOS, Java, and increasingly each browser all maintain independent lists under different root programs.
  • Firefox has always used its own NSS-based store by default (Mozilla Root Store Policy); enabling Enterprise Roots to inherit OS-trusted CAs works on Windows/macOS only, not Linux.
  • Chrome (105+) and Edge (112+, Windows/macOS) now ship their own default root stores rather than fully deferring to the OS — both still honor locally/enterprise-added roots from the OS store; iOS is the one platform where Apple's store/verifier is used instead.
  • Java's cacerts is completely isolated from the OS and every browser — it must be managed separately with keytool.
  • On Linux, copying a certificate into a source directory does nothing until update-ca-certificates (Debian/Ubuntu) or update-ca-trust extract (RHEL/Fedora) regenerates the actual bundle.
