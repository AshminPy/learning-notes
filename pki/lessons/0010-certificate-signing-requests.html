Certificate Signing Requests (CSRs): What's Inside, What's Not

What you will learn

The exact structure of a Certificate Signing Request (CSR) per its governing standard, PKCS#10 (RFC 2986) — what fields it contains, what it deliberately omits, and why. You'll generate and inspect real CSRs with OpenSSL, including the SAN-request pattern every modern CA expects, and learn what a CA is and isn't obligated to honor from what you send it.

Why this matters

Every certificate you'll ever obtain — public or private, TLS server, client auth, code-signing — starts as a CSR. Engineers who've never read the actual structure tend to assume a CSR is "basically a certificate" and get confused when a CA changes or drops fields they requested, or when a CSR built with CN-only (no SAN) gets rejected outright by modern browsers per RFC 9525 (Lesson 16 covers chain validation in depth; the SAN requirement is introduced here because it's a CSR-time decision). Knowing precisely what's in a CSR — and what only the CA adds later — removes an entire category of "why doesn't my cert have X" confusion.

Simple explanation

A CSR is a formal request, not a certificate. It says: "here is my public key, here is who I claim to be, and here is proof — a signature made with the matching private key — that I actually hold that key." It has no expiry date, no serial number, no issuer, and no CA signature, because none of those exist yet — they're the CA's job to add when (and if) it approves the request. Think of it as filling out a form and notarizing your own signature on it; the notary (the CA) still has to review it, decide what to actually issue, and sign the real document.

How it works

The CertificationRequestInfo structure

Per RFC 2986 (PKCS#10), a CSR's core data — CertificationRequestInfo — has exactly four fields:

  • version — a fixed value (0), present only for future-format compatibility.
  • subject — the distinguished name (DN) of the entity requesting the certificate (e.g. CN=example.com).
  • subjectPKInfo — the public key being certified, plus the algorithm it uses (RSA, ECDSA, etc.).
  • attributes — an optional set of additional claims about the subject — in practice, this is where requested X.509v3 extensions live, most importantly the Subject Alternative Name (SAN) list, via the extensionRequest attribute.

That whole structure is then signed once, by the requester's own private key, and wrapped with the signature algorithm and signature value to form the complete CertificationRequest. That self-signature is the "proof of possession" — it proves whoever built this CSR controls the private key matching the public key inside it. It is not a trust signal to anyone else; it proves key possession, nothing about identity.

What's explicitly not in a CSR

RFC 2986 is direct about this: a certification request "does not include issuer name, serial number, or validity period." Compare that to an issued X.509 v3 certificate's tbsCertificate (RFC 5280), which has all of those plus a CA-assigned signatureAlgorithm and signatureValue that a CSR never has:

Attributes are requests, not guarantees

This is the detail engineers most often get wrong: everything in the attributes field — SANs, key usage, extended key usage, anything else — is a request. A CA (or, in AD CS, a certificate template — Lesson 51) is free to ignore, override, or reject any of it. If your CSR requests DNS:app.internal.local and DNS:app.external.com but the template or CA policy only permits internal names, the issued certificate simply won't have the external SAN — with no error, unless the CA is configured to reject the whole request instead.

Important terminology

  • Distinguished Name (DN) — the structured identity string (CN, O, OU, C, etc.) identifying the subject.
  • subjectPKInfo / subjectPublicKeyInfo — the public key plus its algorithm identifier; the same structure name is used in both the CSR and the final certificate because it's carried through unchanged.
  • Proof of possession — the CSR's self-signature, proving the requester holds the matching private key. Not an identity or trust claim.
  • extensionRequest attribute — the specific PKCS#10 attribute used to carry requested X.509v3 extensions (SAN, key usage, EKU) inside a CSR.
  • PKCS#10 — the format standard for CSRs, defined in RFC 2986; distinct from PKCS#7 and PKCS#12 (Lessons 8-9), which are certificate/key container formats, not requests.

Real-world example

An engineer generates a CSR with only CN=app.example.com and no SAN, because that used to be enough. The CA issues the certificate exactly as requested — no SAN, CN only. The certificate installs fine. Every browser then rejects the connection with a name-mismatch error, because RFC 9525 (superseding RFC 6125, November 2023) requires SAN-based identity checking — CommonName-based hostname matching is no longer valid per spec, and current browsers enforce that. The CSR wasn't technically wrong; it just requested something no longer sufficient. The fix is always to request SAN explicitly (including the primary hostname as a SAN entry, not just the CN) — never rely on CN alone.

Hands-on lab

Track B. Generate a private key and a CSR requesting a SAN, then inspect and self-verify it:

# Generate a private key
openssl genrsa -out app.key 2048

# Generate a CSR requesting a SAN via -addext (no config file needed)
openssl req -new -key app.key -out app.csr \
  -subj "/CN=app.example.com" \
  -addext "subjectAltName=DNS:app.example.com,DNS:www.app.example.com"

# Inspect the CSR: confirm subject, public key, and requested extensions
openssl req -in app.csr -text -noout

# Verify the CSR's self-signature (proof of possession)
openssl req -in app.csr -verify -noout

Expected result: the -text -noout output shows a "Requested Extensions" section listing your SAN entries under attributes, and no issuer, serial number, or validity fields anywhere in the output — because a CSR has none. -verify should report the signature verifies OK, confirming the CSR was actually signed by the private key whose public half it carries.

What can go wrong

The most common real-world CSR mistake is exactly the one in the example above: no SAN, or a SAN list that doesn't include every hostname the certificate needs to serve — CN alone is not sufficient under current standards. A second: generating the CSR against a weak or wrong-algorithm key (Lesson 5) that doesn't meet the issuing CA's minimum requirements, discovered only at submission time. A third: assuming a requested extension will definitely appear in the issued certificate — as covered above, attributes are requests the CA (or template) can silently drop.

Troubleshooting

If openssl req -in file.csr -verify -noout reports a signature failure, the file is either corrupted or was tampered with after signing — regenerate it from the original key rather than trying to repair it. If a CA rejects a CSR outright, check the requested key algorithm and size first — most issuance failures at this stage are minimum-key-size or algorithm policy violations, not something wrong with the DN or SAN syntax. If an issued certificate is missing a SAN entry you're certain you requested, re-run -text -noout on your original CSR to confirm it was actually present in the request — a surprising number of "the CA dropped my SAN" reports turn out to be a CSR that never requested it correctly in the first place.

Security considerations

The private key never leaves the machine generating the CSR — only the public key travels inside it, which is the entire point of the CSR model. Never accept a CSR-and-key pair generated somewhere else and sent to you together; a private key that has already traveled over any channel should be considered potentially exposed. Because a CSR's attributes are just a request, never rely on a CSR alone as an access-control or policy boundary — the CA/template enforcement is what actually matters, and it must be configured correctly independent of what any given CSR asks for.

Production best practices

Always generate the key and CSR together, on the target system (or via automation that does the same), and always request SAN explicitly — never CN-only — including every hostname the certificate must serve. Standardize CSR generation through a script or automation tool (Stage L) so the subject format, key algorithm, and SAN list are consistent across the organization instead of hand-typed each time. Verify every CSR with -text -noout before submitting it, to catch a missing SAN or wrong DN before it becomes a support ticket after issuance.

Exam and interview notes

Interview Q: "What's the difference between a CSR and a certificate?" A: "A CSR is an unsigned-by-the-CA request: a public key, a claimed identity, and requested extensions, self-signed only to prove key possession. It has no issuer, serial number, or validity period. A certificate is what the CA produces after review — it adds its own issuer name, a serial number, a validity period, and its own signature, which is what actually creates trust."

Interview Q: "If you submit a CSR requesting five SAN entries, are you guaranteed to get a certificate with all five?" A: "No — SAN is carried as a requested attribute (extensionRequest) in the CSR. The CA or certificate template decides what to actually honor; it can drop or reject entries without that being a bug in the CSR itself."

Recap
  • A CSR (PKCS#10 / RFC 2986) contains only version, subject, subjectPKInfo, and requested attributes — self-signed once to prove key possession, nothing more.
  • Issuer, serial number, validity period, and the CA's own signature do not exist in a CSR — the CA adds all of them when it issues the actual certificate.
  • Requested extensions (like SAN) are attributes, not guarantees — a CA or template can drop or override them.
  • Always request SAN explicitly, including the primary hostname — CN-only identity checking is no longer valid per RFC 9525.
