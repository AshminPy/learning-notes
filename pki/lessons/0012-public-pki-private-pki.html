Public PKI vs Private PKI

What you will learn

The real, structural difference between public PKI (certificates trusted automatically by strangers' browsers and operating systems) and private PKI (certificates you trust only because you chose to install the root yourself) — who governs each, what rules apply to each, what each can and can't be used for, and why picking the wrong one for a given hostname is a common, entirely avoidable production mistake.

Why this matters

By Lesson 11 you know the components (CA, RA, repository, HSM) that make up any PKI. This lesson is about the decision every engineer eventually has to make: does this certificate need to be trusted by anyone on the internet, or only by systems I control? Getting this wrong in either direction causes real incidents — requesting a public certificate for a purely internal hostname that a public CA is contractually forbidden to issue, or exposing an internal-only trust boundary to third parties by mistake. Stage 13 covers the specific DNS-trust failure mode this creates; this lesson is the architectural decision that sits underneath it.

Simple explanation

Public PKI is trust you borrow. Every operating system and browser ships with a pre-installed list of root certificates from CAs that have passed independent scrutiny (audits, disclosure, technical requirements) — when your certificate chains up to one of those roots, every stranger's device already trusts it, with zero setup on their end. Private PKI is trust you build. You run your own CA, and it's trusted only by the specific machines where you've deliberately installed your root certificate — nobody outside your organization trusts it, and nobody outside your organization is supposed to.

How it works

Public PKI: governed, audited, narrow in what it can certify

A "Publicly-Trusted Certificate" has a precise, current definition from the CA/Browser Forum's TLS Baseline Requirements (v2.2.9, effective 2026-08-06): "A Certificate that is trusted by virtue of the fact that its corresponding Root Certificate is distributed as a trust anchor in widely-available application software." Getting a root into that "widely-available application software" list means passing a specific root program's requirements — Mozilla's, Chrome's, Apple's, Microsoft's — each independently. Mozilla's Root Store Policy (v3.1, effective 2026-07-01) requires, among other things, annual WebTrust- or ETSI-standard audits covering the CA "from key generation until the certificate is no longer trusted," a published CP/CPS following the RFC 3647 structure, and disclosure of every intermediate certificate into the CCADB within seven days of creation. In exchange for that scrutiny, a publicly-trusted certificate is instantly trusted by essentially every browser and OS on the internet.

That trust comes with a hard boundary, but it's narrower than people often assume: public CAs are contractually forbidden from certifying names or addresses that aren't globally, publicly resolvable and independently verifiable — not from certifying IP addresses altogether. The CA/Browser Forum deprecated issuing certificates for reserved IP addresses and internal server names starting 2015-11-01, and by 2016-10-01 all such certificates still in circulation were revoked or blocked by browser software — server.internal and 10.0.0.5 (a reserved, RFC 1918 private address) simply cannot get a publicly-trusted certificate, by design, permanently. What's actually banned is reserved IP addresses (RFC 1918 ranges like 10.0.0.0/8 and 192.168.0.0/16, plus other IANA-reserved blocks) and internal names — not real public IP addresses. The Baseline Requirements let a public CA issue a certificate containing a validated public IPv4 or IPv6 address as an iPAddress Subject Alternative Name, after performing one of the BR's IP Address Validation methods (Section 3.2.2.5) — an uncommon issuance path in practice, but a permitted one.

Private PKI: self-governed, no external audit requirement, no scope limit

A private (or "internal" / "enterprise") CA is not distributed in any root program's trust list — nothing outside your organization trusts it automatically. Nothing in the CA/Browser Forum's Baseline Requirements even applies to it: their scope is explicitly limited to Publicly-Trusted Certificates, meaning enterprises "operate their own Public Key Infrastructure for internal purposes only, where the Root CA Certificate is not distributed by any Application Software Supplier" are outside its rules entirely. That means no mandatory external audit, no CCADB disclosure, no CT logging requirement, no restriction on internal names, and no imposed validity-period ceiling — a private CA can issue a 10-year certificate for db-primary.corp.internal if that's what the organization's own policy allows. Microsoft's Active Directory Certificate Services (AD CS, Stage K) is the canonical example: a Windows Server role built specifically to run this kind of internal-only CA, distributing trust via Group Policy/Active Directory rather than a public root program (Microsoft Learn, updated 2026-05-12).

The trade-off in one line

Public PKI trades governance and scope restrictions for automatic, universal trust. Private PKI trades automatic trust (you must distribute your root yourself, to every relying device) for full control over scope, validity periods, and internal naming — with zero external body checking whether you're doing it safely, which means the safety has to come from you.

Important terminology

  • Root program — a browser/OS vendor's (Mozilla, Chrome, Apple, Microsoft) formal process and policy for deciding which CA roots it will trust by default.
  • Publicly-Trusted Certificate — a certificate whose root is distributed as a trust anchor in widely-available application software (CA/Browser Forum definition).
  • Internal name — a hostname that isn't a publicly-registered, resolvable domain (e.g. server.local, app.corp) — permanently ineligible for a publicly-trusted certificate.
  • Enterprise CA / internal CA — a privately-operated CA, trusted only by machines where its root has been deliberately installed; not subject to CA/Browser Forum rules.
  • CCADB (Common CA Database) — the shared disclosure database public CAs must publish into; private CAs have no equivalent obligation.
  • Trust anchor — a root certificate a relying party has decided, by whatever mechanism, to trust as a starting point for chain validation (Stage D).

Real-world example

A typical mid-size company runs both at once, deliberately. Its public-facing website (www.example.com) gets a certificate from a public CA (DigiCert, Let's Encrypt, Sectigo, etc.) — it must, because customer browsers need automatic trust with zero setup. Its internal service mesh, domain controllers, and employee laptop authentication run on an AD CS-based internal CA (Stage K) whose root was pushed to every domain-joined machine via Group Policy — because those names (dc01.corp.internal, internal service hostnames) could never get a public certificate anyway, and because the company wants full control over validity periods and template-based issuance policy (Lesson 51) that no public CA would offer. Neither PKI is "better" — they solve different trust problems for different audiences.

Hands-on lab

Track B. Build a minimal private root CA, then compare its self-signed root to a real public leaf certificate's issuer chain — the structural difference is visible immediately:

# Create a private root CA key and a self-signed root certificate
openssl genrsa -out private-root.key 4096
openssl req -x509 -new -key private-root.key -sha256 -days 3650 \
  -subj "/CN=Example Corp Internal Root CA/O=Example Corp" \
  -out private-root.crt

# Inspect it: notice it is self-issued (Issuer == Subject) and NOT
# chained to anything -- nobody trusts this until you tell them to
openssl x509 -in private-root.crt -noout -issuer -subject

# Compare against a real public certificate's issuer chain
openssl s_client -connect www.google.com:443 -servername www.google.com \
  /dev/null | openssl x509 -noout -issuer -subject

Expected result: your private root shows an identical issuer and subject (it signed itself, and nothing outside a trust store you personally configure will ever trust it). The public certificate shows a different issuer than subject — signed by a CA whose root already sits in your OS/browser trust store, which is why your terminal accepted the connection without you doing anything.

What can go wrong

The most common mistake in this decision is requesting (or expecting to request) a publicly-trusted certificate for an internal-only name — it will always fail, permanently, by design, since the 2016 deprecation; there is no appeal or exception path for a reserved IP or internal server name under the current Baseline Requirements. The opposite mistake also happens: standing up a private CA for something that's actually public-facing, forcing every external user to manually install a root certificate they have no reason to trust — a broken experience that public PKI exists specifically to avoid. A third, subtler mistake: assuming a private CA is automatically "safer" because it's internal — nothing in the CA/Browser Forum's rules or a root program's audit applies to it, so a private CA with a weak or unaudited key-management practice (Lesson 11) can be a larger, less-scrutinized risk than a public one.

Troubleshooting

If a browser or client reports "unknown CA" / "self-signed certificate" for an internal service, the near-universal cause is that the private root certificate was never installed into that specific device's trust store — this is a per-device, deliberate action (via GPO, MDM, or manual install), not something that happens automatically the way it does for public CAs. If a request for a certificate covering an internal hostname or private IP gets rejected by a public CA, that's not a bug or a misconfiguration on either side — it's the 2016 internal-names deprecation working as intended; the fix is either to use a real public subdomain instead, or to switch that hostname to a private CA.

Security considerations

Because nothing external audits a private CA by default, the burden of doing what a root program would otherwise enforce — HSM-backed keys, a documented key ceremony, access control, monitored issuance — falls entirely on the operating organization (Lesson 11). Never assume "internal only" means "lower stakes": a compromised internal root CA can issue trusted-looking certificates for every internal service an attacker wants to impersonate, and because there's no CT log requirement for private PKI, that misuse may never surface the way a public CA's misissuance eventually would via Certificate Transparency monitoring (Stage G). Distribute a private root only through a controlled mechanism (GPO, MDM, imaging) — never by asking users to manually accept or install it themselves, which trains people to click through exactly the kind of warning that's supposed to stop a real attack.

Production best practices

Default to public PKI for anything a third party (customer, partner, the general internet) needs to trust without setup. Default to private PKI for internal-only names, service-to-service/mTLS traffic (Stage F), and any case where you need validity periods, naming, or template control a public CA won't offer. Never try to work around the internal-names restriction by requesting a public certificate for a name you plan to only resolve internally — use a private CA, or use a real subdomain of a domain you control if you specifically need public-CA-style automation (e.g. ACME, Stage L) for an internal service. Apply the same key-security rigor (HSM, ceremony, least privilege) to a private root as you would expect from a public one, precisely because nobody is external­ly checking that you did.

Exam and interview notes

Interview Q: "Can you get a publicly-trusted certificate for an internal hostname like db01.corp.local?" A: "No — the CA/Browser Forum deprecated issuing certificates for internal server names and reserved IP addresses, effective 2015-11-01, with all such certificates revoked or blocked by 2016-10-01. It's permanent and has no exception path. Use a private/internal CA for that hostname instead."

Interview Q: "Why would a company run its own internal CA instead of just using a public one everywhere?" A: "Three reasons: internal hostnames can't get public certificates at all; a private CA gives full control over validity periods and issuance policy via templates, which public CAs don't offer; and it avoids exposing internal naming/service topology to the public Certificate Transparency logs that public CAs are required to publish into."

Recap
  • Public PKI = trust you borrow — a root already installed in everyone's browser/OS, in exchange for external audits (WebTrust/ETSI), CCADB disclosure, and a hard restriction against internal names and reserved/private IP addresses (real public domain names and validated public IPs are both fair game).
  • Private PKI = trust you build — no external audit or scope restriction, but nothing trusts your root until you deliberately install it on every relying device.
  • Internal server names and reserved IP addresses have been permanently ineligible for publicly-trusted certificates since the CA/Browser Forum's 2015-11-01/2016-10-01 deprecation — there's no exception path.
  • A private CA carries the same security responsibilities (HSM, key ceremony, access control) as a public one — just without anyone external checking that you met them.
