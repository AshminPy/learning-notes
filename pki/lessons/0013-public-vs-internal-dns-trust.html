Why google.com Works Instantly but internal.company.local Doesn't

What you will learn

Why "it doesn't work" for an internal hostname is almost always two separate failures bundled into one complaint — a DNS resolution failure and a certificate trust failure — and why they have completely different causes and fixes. You'll learn why public names like google.com resolve and get trusted certificates instantly everywhere, why internal names like internal.company.local can never get a publicly-trusted certificate at all (a hard policy rule, not a technical gap), and why the .local suffix specifically carries an extra trap most engineers don't know about.

Why this matters

This is the single most common "PKI 101" confusion in real support tickets: someone sees a browser error on an internal site and assumes it's the same kind of problem as a public site not loading. It isn't. DNS resolution (can the name be looked up at all) and certificate trust (is the certificate presented at that address signed by something the client trusts) are two independent systems. Internal names typically fail the first because they live in a private DNS zone, and they can never pass the second with a publicly-trusted certificate because of an explicit CA/Browser Forum rule — which is exactly why every organization running internal services needs a private CA (Lesson 12) and a plan to distribute its trust into every device that needs it.

Simple explanation

Think of it as two separate doors a connection has to pass through. Door 1 (DNS): can your computer even find the address for this name? Door 2 (trust): does your computer trust the certificate presented at that address? google.com passes both doors instantly and everywhere — it's in the public DNS system anyone can query, and its certificate chains up to a root CA that's already baked into your OS and browser. internal.company.local usually fails door 1 outright (it's not in public DNS, only in your company's private DNS), and even if it somehow passed door 1, it would still fail door 2 with a publicly-trusted certificate — because public CAs are contractually forbidden from ever issuing one for a name like that.

How it works

Door 1 — DNS resolution

google.com resolves through the public DNS hierarchy: any resolver anywhere in the world can walk from the root servers to the .com TLD servers to Google's authoritative name servers and get an answer, with no special configuration. internal.company.local typically lives in a private/split-horizon DNS zone — often Active Directory-integrated DNS — that only answers queries from devices whose resolver is pointed at the company's internal DNS servers (on the corporate network, over VPN, or via a configured internal resolver). Outside that path, the name simply doesn't exist as far as DNS is concerned: NXDOMAIN, not a certificate error.

Door 2 — certificate trust, and why .local can never pass it

google.com's certificate is issued by a CA that's a member of every major root program (Chrome, Mozilla, Apple, Microsoft), and those roots ship pre-installed in every OS and browser trust store — zero extra configuration needed for trust to work. internal.company.local can never get that same treatment with a publicly-trusted certificate, because the CA/Browser Forum's Baseline Requirements explicitly prohibit publicly-trusted CAs from issuing certificates containing "Internal Server Names" or "Reserved IP Addresses" — names and addresses that aren't publicly resolvable and can't be domain-validated, and which different organizations could claim to own internally at the same time. This has been a hard issuance prohibition since November 11, 2015, with any certificates that already existed required to be revoked by October 1, 2016. It is a policy rule enforced by every public root program, not a technical limitation you can work around by asking a CA nicely or waiting.

The .local suffix specifically has a second, independent problem: RFC 6762 (Multicast DNS) reserves the entire .local domain as a link-local special-use name — resolved via multicast (mDNS, the protocol behind Bonjour/Avahi), not ordinary unicast DNS, and meaningful only on the local network segment where the query originated. That means a name like internal.company.local can collide with mDNS resolution behavior on some devices, producing intermittent or confusing results that have nothing to do with your company's actual DNS zone — on top of the certificate-trust problem, which would exist even if you'd picked a suffix with no mDNS conflict at all.

Important terminology

  • Public DNS hierarchy — the globally queryable root → TLD → authoritative name server chain that resolves names like google.com from anywhere.
  • Split-horizon / private DNS zone — a DNS zone (often Active Directory-integrated) that only answers queries from resolvers configured to reach it, typically inside the corporate network or VPN.
  • Internal Server Name / Reserved IP Address — CA/Browser Forum terms for names and addresses that aren't publicly resolvable or assignable; publicly-trusted CAs are banned from issuing certificates for either.
  • Root program — the audited process (Chrome, Mozilla, Apple, Microsoft) by which a CA's root certificate gets pre-installed as trusted in an OS or browser.
  • mDNS (Multicast DNS) — RFC 6762's link-local name resolution protocol that reserves the entire .local domain, independent of ordinary unicast DNS.
  • Trust-store distribution — the act of pushing a private CA's root certificate into devices' trust stores (GPO, MDM, configuration management) so their certificates become trusted — this never happens automatically the way public root programs do it.

Real-world example

An engineer stands up internal.company.local and tries to request a certificate from a public CA for it. The request is refused outright — not because of a paperwork issue, but because CA/Browser Forum policy makes it impossible: the name can't be publicly domain-validated and is explicitly banned from public certificates. The team instead deploys a private CA (Lesson 12) and pushes its root certificate to every corporate-managed laptop via Group Policy. A new hire's personal, unmanaged laptop later connects to the same site over VPN — DNS resolves fine, the page loads, but the browser shows an untrusted-certificate warning, because that laptop never received the internal root CA. Same site, same certificate, two different outcomes — because trust-store distribution, not DNS, is the variable that changed.

Hands-on lab

Track B. Compare a public name's instant DNS + trust against a private name where you control (and initially don't have) trust:

# 1. Public DNS resolves instantly, no config
dig +short google.com

# 2. A name like internal.company.local won't resolve at all
#    unless your resolver is pointed at a private DNS zone
dig +short internal.company.local

# 3. Inspect google.com's real certificate chain (works with zero setup)
openssl s_client -connect google.com:443 -showcerts </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer -subject

# 4. Build a tiny private CA + leaf cert for a name that could NEVER be public
openssl req -x509 -newkey rsa:2048 -keyout ca.key -out ca.crt -days 3650 \
  -subj "/CN=Company Internal Root CA" -noenc

openssl req -newkey rsa:2048 -keyout internal.key -out internal.csr \
  -subj "/CN=internal.company.local" -noenc \
  -addext "subjectAltName=DNS:internal.company.local"

openssl x509 -req -in internal.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out internal.crt -days 365 -copy_extensions copy

# 5. Verify WITHOUT trusting the private CA (simulates a fresh, undistributed laptop)
openssl verify internal.crt

# 6. Verify again, explicitly trusting the private CA (simulates GPO/MDM distribution)
openssl verify -CAfile ca.crt internal.crt

Expected result: step 2 returns nothing (or your shell's resolver error) unless you have a private zone configured, while step 1 always returns an IP. Step 5 fails with something like error 20 at 0 depth lookup: unable to get local issuer certificate — exactly what a browser shows a device that never got the internal root. Step 6 reports internal.crt: OK — nothing about the certificate changed between steps 5 and 6, only whether the verifier was told to trust the issuing CA. That's the whole lesson in two command outputs.

What can go wrong

Assuming a private suffix like .local, .internal, or .corp will eventually get a publicly-trusted certificate if you just ask the right CA — it won't; it's a hard policy prohibition enforced by every root program, not a technical limitation with a workaround. Using .local specifically for an internal DNS zone and being surprised when resolution behaves inconsistently across devices — that inconsistency is RFC 6762's mDNS reservation colliding with your intended unicast DNS zone. Treating "DNS resolves" and "certificate is trusted" as the same signal — a site can resolve perfectly and still show a trust error, or (less commonly) fail to resolve while a cached/pinned trust decision elsewhere makes it look like a "certificate problem."

Troubleshooting

When someone reports "internal.company.local doesn't work," isolate which door failed before touching anything. Run dig/nslookup for the name from the affected machine: if it's NXDOMAIN, the problem is DNS resolver configuration (is the device pointed at internal DNS, connected to VPN/corporate network) — not a certificate issue at all. If the name resolves but the browser shows a trust/certificate warning, the problem is almost always that this specific device's trust store never received the internal CA's root certificate — check the GPO/MDM/config-management distribution status for that device, not the certificate itself (which is likely fine).

Security considerations

Never try to route around the public-CA prohibition by reusing a publicly-trusted certificate issued for a legitimate public name (e.g. mail.company.com) on an internal name it wasn't issued for — beyond the obvious SAN mismatch, every publicly-trusted certificate is logged in Certificate Transparency logs, which would expose your internal naming and network structure publicly. Protect a private CA's root key with the same rigor as any root CA (offline storage, Stage O key security) — anyone who can get a device onto the internal trust-distribution path can have that device trust certificates impersonating any internal name the CA is willing to sign.

Production best practices

Run a real private CA (Lesson 12) for internal names, with trust distribution automated — Group Policy for domain-joined Windows devices, MDM profiles for managed endpoints, configuration management (Ansible/Chef/Puppet) for servers — rather than manually installing root certificates machine by machine. Avoid the .local suffix for any DNS zone you intend to resolve over ordinary unicast DNS; prefer a suffix like .corp or a subdomain of a domain you actually own and don't publicly delegate (e.g. internal.example.com) to sidestep the RFC 6762 mDNS collision entirely. Document exactly which device populations receive the internal root distribution, so an "untrusted certificate" warning on an unmanaged or offboarded device is recognized as expected security behavior, not treated as a bug to fix.

Exam and interview notes

Interview Q: "Why can't I just get a public CA to issue a certificate for my internal server name?" A: "CA/Browser Forum Baseline Requirements have banned publicly-trusted CAs from issuing certificates for Internal Server Names or Reserved IP Addresses since November 11, 2015 — any that existed had to be revoked by October 1, 2016. It's a hard policy rule enforced across every root program, because those names can't be publicly domain-validated and could be claimed internally by more than one organization."

Interview Q: "A colleague says DNS resolution and certificate trust are basically the same problem. Are they right?" A: "No — they're two independent systems. DNS resolution answers 'can this name be looked up at all'; certificate trust answers 'do I trust the signer of the certificate presented at that address.' A name can resolve perfectly and still fail trust, or fail to resolve while trust would have been fine — diagnosing which one actually failed determines whether the fix is a DNS/resolver change or a trust-store distribution gap."

Recap
  • "Doesn't work" for an internal name is usually two separate failures: DNS resolution and certificate trust — diagnose which one before touching anything.
  • Public names resolve via the public DNS hierarchy and get certificates from CAs whose roots are pre-installed in every trust store — zero extra config.
  • Internal names typically live in a private/split-horizon DNS zone, and can never get a publicly-trusted certificate — CA/Browser Forum has banned issuance for Internal Server Names since 2015-11-11, a hard policy rule.
  • The .local suffix adds a second, independent trap: RFC 6762 reserves it for multicast DNS (mDNS), which can collide with your intended unicast DNS zone.
  • Private names need a private CA (Lesson 12) plus deliberate trust-store distribution (GPO/MDM/config management) to every device that must trust them.
