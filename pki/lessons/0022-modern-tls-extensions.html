Modern TLS Extensions: Encrypted Client Hello and Certificate Compression

What you will learn

Why cleartext SNI (Lesson 21) is a real, current privacy leak, how Encrypted Client Hello (ECH — standardized as RFC 9849, published March 3, 2026) closes that leak using an outer/inner ClientHello split and Hybrid Public Key Encryption (HPKE), what ECH actually requires to work in practice (a published DNS HTTPS/SVCB record, DNS-over-HTTPS or DNS-over-TLS), and separately, how TLS certificate compression (RFC 8879) shrinks the certificate message using zlib/brotli/zstd to cut handshake bytes and round trips. You'll also get the honest, current deployment picture for both — including the real gaps, not just the standards.

Why this matters

Lesson 21 established that SNI is sent in cleartext by default — anyone observing network traffic (an ISP, a network operator, a state-level censor) can see exactly which hostname a client is connecting to, even over an otherwise fully-encrypted HTTPS connection. That's not a theoretical gap; it's the single biggest remaining metadata leak in modern TLS, and it's exactly why ECH exists. Certificate compression is a smaller, more mundane win — but on a large certificate chain (multiple intermediates, big SANs lists) it can meaningfully shrink handshake size and remove round trips, which matters at mobile-network scale. Both are stage-relevant because you'll be asked, in real production reviews, "do we support ECH?" and "is certificate compression worth enabling?" — and the honest answer to both, as of this lesson, is "yes, but check these specific prerequisites first."

Simple explanation

Think of a normal TLS handshake's ClientHello as a postcard: most of it (including the SNI hostname) is readable by anyone who intercepts it in transit, even though the actual conversation that follows is fully encrypted. ECH is putting that postcard in a sealed envelope — the truly sensitive fields (the real hostname you want, ALPN preferences, etc.) go inside an encrypted "inner" ClientHello, while a mostly-generic "outer" ClientHello (with a decoy/cover name) is what actually travels in cleartext. Only the server holding the matching private key can open the envelope and see the real request. Certificate compression is a much simpler idea: certificates and their chains are just data, and data compresses — so instead of sending the raw certificate bytes over the wire every handshake, compress them first (like zipping a file before emailing it) and decompress on arrival.

How it works

Encrypted Client Hello — the outer/inner split

RFC 9849 (published as a Proposed Standard on March 3, 2026, authored by E. Rescorla, K. Oku, N. Sullivan, and C. A. Wood) defines ECH as a mechanism for "encrypting a ClientHello message under a server public key." The handshake now involves two ClientHello structures in one flight:

  • ClientHelloOuter — sent in cleartext, contains a generic/cover server name (often the CDN or hosting provider's own shared name, not the site the user actually wants), and carries the encrypted payload.
  • ClientHelloInner — encrypted, contains the real values: actual SNI hostname, actual ALPN preferences, and everything else that would normally be sensitive.

The encryption uses HPKE (Hybrid Public Key Encryption): the client performs an HPKE SetupBaseS() operation using the server's ECH public key (published in DNS, see below) and a fixed info string, "tls ech" || 0x00 || ECHConfig; the server performs the matching SetupBaseR() to decrypt. If the server can decrypt and process the inner ClientHello, it proceeds using those real values; if it can't (e.g. it doesn't support ECH, or the config is stale), it falls back to treating the outer ClientHello as the real request — which is what lets ECH degrade gracefully instead of hard-failing against non-supporting middleboxes.

ECHConfig — how the client gets the server's public key

The client needs the server's HPKE public key before it can encrypt anything — this is published as an ECHConfig structure (bundled into an ECHConfigList if multiple configs are offered), containing the HPKE public key, a config identifier, the supported HPKE cipher suites, a maximum name length, and the "client-facing" server's DNS name (the one used for the outer ClientHello's cover name). This is distributed via DNS HTTPS/SVCB resource records — a separate, companion specification (RFC 9848, "Bootstrapping TLS Encrypted ClientHello with DNS Service Bindings") defines exactly how. This dependency is the single biggest practical constraint on ECH: the client has to fetch that DNS record over an encrypted DNS channel (DNS-over-HTTPS or DNS-over-TLS) for ECH to have any real privacy value — fetching the ECHConfig over plain, unencrypted DNS would leak the very thing ECH is trying to hide.

TLS Certificate Compression — the compress_certificate extension

RFC 8879 defines a ClientHello/CertificateRequest extension, compress_certificate(27), through which a peer advertises which decompression algorithms it can handle: zlib (algorithm 1, per RFC 1950), brotli (algorithm 2, per RFC 7932), and zstd (algorithm 3, per RFC 8478). If both sides support a common algorithm, the sender replaces the normal TLS 1.3 Certificate message with a CompressedCertificate message: an algorithm identifier, the declared uncompressed length (so the receiver can detect a mismatch and abort — this guards against decompression-bomb-style attacks), and the compressed payload itself. This mechanism is TLS 1.3-and-later only, specifically to avoid the middlebox-compatibility problems that plagued earlier TLS extensions when deployed against TLS 1.2 infrastructure.

Architecture / diagram

Without ECH (Lesson 21's cleartext SNI):
  ClientHello (cleartext) --- server_name: "secret-internal-app.company.com" ---> [observable on the wire]

With ECH (RFC 9849):
  Step 0 (prerequisite): client resolves target's HTTPS/SVCB DNS record
                          over DoH/DoT -> gets ECHConfig (server's HPKE public key)

  ClientHelloOuter (cleartext):
    server_name: "cover-name.cdn-provider.com"      <- generic, not the real target
    encrypted_client_hello extension: [HPKE-encrypted blob]

  ClientHelloInner (only visible after HPKE decryption by the server):
    server_name: "secret-internal-app.company.com"  <- the REAL request, hidden
    alpn: [...]

  Server: has the matching HPKE private key -> decrypts inner CH -> proceeds
          with the real request. An observer only ever sees the cover name.

Certificate compression (RFC 8879), TLS 1.3 only:
  Normal:     Certificate message  = [raw cert chain bytes, e.g. 4-8 KB]
  Compressed: CompressedCertificate = [algorithm][uncompressed_length][compressed bytes]
              -> fewer bytes on the wire, meaningful on high-latency/mobile links

Important terminology

  • ECH (Encrypted Client Hello) — RFC 9849; encrypts the sensitive fields of the ClientHello (real SNI, ALPN preferences) using HPKE, so only the intended server can read them.
  • ClientHelloOuter / ClientHelloInner — the cleartext cover request and the HPKE-encrypted real request that together make up an ECH-enabled handshake.
  • HPKE (Hybrid Public Key Encryption) — the public-key encryption framework ECH uses to encrypt the inner ClientHello under the server's published public key.
  • ECHConfig / ECHConfigList — the structure containing a server's HPKE public key and related metadata, published via DNS so clients can encrypt to it.
  • HTTPS/SVCB DNS records — the DNS record types (per RFC 9848) used to publish ECHConfig; require DoH/DoT to be fetched safely for ECH to actually hide anything.
  • compress_certificate extension (27) — the RFC 8879 extension through which peers negotiate certificate-message compression (zlib, brotli, or zstd), TLS 1.3+ only.

Real-world example

Cloudflare has enabled ECH for connections to origins across its network, and — because Cloudflare also operates the widely-used 1.1.1.1 DNS-over-HTTPS resolver — it controls both halves of the prerequisite chain (DoH resolution and ECH-capable TLS termination) for a very large share of the sites it fronts. On the client side, Firefox enabled ECH by default starting with Firefox 119 (October 2023) for users who have DNS-over-HTTPS active, Safari followed with default-on support in Safari 17/iOS 17.4/macOS 14.4 (also gated on DoH/DoT being active), and Chrome has ECH enabled by default as of 2026 with support gated on the same DNS-over-HTTPS prerequisite and gradual, server-support-dependent rollout. On the certificate compression side, Chrome has supported brotli-based certificate compression since Chrome 69, and Safari supports the zlib variant — meaning a meaningful share of real-world HTTPS handshakes to well-configured servers are already sending compressed certificate chains today, even though this extension gets far less attention than ECH.

Hands-on lab

Track B. Inspect whether a live site advertises ECH support via DNS, and check certificate-compression negotiation:

# Check for an HTTPS/SVCB DNS record advertising ECH support
# (look for an "ech=" parameter in the answer)
dig +short HTTPS cloudflare.com
dig +short HTTPS www.cloudflare.com

# Compare a domain that does NOT publish ECH -- most sites still won't
dig +short HTTPS example.com

# Confirm your OpenSSL build's certificate-compression capability
# (requires a build with RFC 8879 support; not all distro builds include it)
openssl version
openssl s_client -connect www.cloudflare.com:443 -tls1_3 &1 \
  | grep -i "compress"

# Inspect the raw Certificate vs CompressedCertificate message size difference
# conceptually, by comparing chain size to what a compressor achieves locally:
echo | openssl s_client -connect www.cloudflare.com:443 -showcerts 2>/dev/null \
  | awk '/BEGIN CERT/,/END CERT/{print > ("chain" ++n ".pem")}'
cat chain*.pem > full_chain.pem
wc -c full_chain.pem
gzip -9 -c full_chain.pem | wc -c
brotli -q 11 -c full_chain.pem 2>/dev/null | wc -c || echo "install brotli to compare"

Expected result: dig +short HTTPS against an ECH-supporting domain shows an ech=... parameter (a base64 ECHConfigList) in its answer; a typical domain without ECH shows no such parameter, or no HTTPS record at all. The gzip/brotli comparison shows real compression savings on the certificate chain bytes — directly demonstrating why RFC 8879 is worth enabling on servers presenting long chains.

What can go wrong

The most common real ECH failure mode isn't a bug — it's an unmet prerequisite: a client has ECH support in its browser, but the network's default DNS resolver doesn't support DoH/DoT, so the ECHConfig is either never fetched or fetched over plaintext DNS (which defeats the entire privacy purpose, since an observer of that DNS query sees the real domain anyway). A second gap, confirmed as of 2026: most sites still don't publish an HTTPS/SVCB record with an ECH configuration at all, so even a fully ECH-capable client silently falls back to cleartext SNI against the vast majority of the web — ECH's protection only applies to the specific origins that have actually published it. For certificate compression, the failure mode is usually silent non-negotiation: if either side lacks support (older OpenSSL builds, some enterprise TLS middleboxes/inspection proxies), the handshake proceeds completely normally with the uncompressed Certificate message — there's no error, just a missed optimization, which makes it easy to assume it's working when it never actually negotiated.

Troubleshooting

If ECH appears "enabled" in a browser but traffic captures still show a real (non-cover) SNI value in cleartext, check the DNS resolution path first — confirm DoH/DoT is actually active for that client and that the target domain's HTTPS/SVCB record actually carries an ech= parameter with dig +short HTTPS <domain>; if either is missing, ECH cannot activate for that connection regardless of browser support. If a corporate network-inspection proxy breaks connections to ECH-enabled sites, that's a known, real interaction — some TLS-inspecting middleboxes can't parse or don't expect the ECH extension structure; this is a legitimate reason some enterprise environments explicitly disable ECH via policy (e.g. Chrome's EncryptedClientHelloEnabled enterprise policy) rather than a sign anything is broken on the server side. For certificate compression, if you expect it but don't see a CompressedCertificate message in a capture, check both endpoints' actual library versions and build flags before assuming misconfiguration — many OpenSSL distribution builds and older TLS libraries simply never wired in RFC 8879 support, so the absence is capability, not configuration.

Security considerations

ECH is a genuine privacy improvement for the specific metadata it covers (SNI, ALPN, and other inner ClientHello fields), but don't oversell it in a design review: it does not hide the destination IP address, connection timing, or traffic volume/pattern — all still-usable traffic-analysis signals independent of ECH. It also introduces a real new dependency: your privacy protection is now only as strong as your DNS resolution path, so recommending ECH without also recommending DoH/DoT is an incomplete answer. For certificate compression, the built-in uncompressed_length check exists specifically to prevent decompression-bomb attacks (a tiny compressed blob expanding to an enormous, resource-exhausting output) — any implementation you build or evaluate should be verified to actually enforce that check and abort on mismatch, not just log it.

Production best practices

If you operate public-facing TLS endpoints and control both DNS and TLS termination (directly, or via a CDN like Cloudflare that already supports it), publishing an ECH-capable HTTPS/SVCB record is now a real, standards-track option worth adopting — not an experimental draft anymore, since RFC 9849's Proposed Standard status. Pair it with DoH/DoT guidance for clients, since one without the other provides no real protection. For certificate compression, enabling brotli or zstd support costs little and helps most on chains with multiple intermediates or large SAN lists — verify it's actually negotiating in production with a real packet capture, not just assumed from library version numbers. Don't treat either extension as a substitute for the fundamentals from earlier lessons (correct chain, correct SNI-to-certificate mapping, forward-secret cipher suites) — they're real but incremental improvements layered on top of a correctly configured TLS 1.3 baseline.

Exam and interview notes

Interview Q: "What problem does Encrypted Client Hello solve, and what does it NOT solve?" A: "It encrypts the sensitive fields of the ClientHello — most importantly the real SNI hostname — using HPKE, inside an inner ClientHello, while a generic outer ClientHello with a cover name travels in cleartext. It does not hide the destination IP address, connection timing, or traffic volume. It also depends entirely on the client fetching the server's ECHConfig via encrypted DNS (DoH/DoT); over plaintext DNS, the real domain leaks in the DNS query anyway."

Interview Q: "Is TLS certificate compression widely deployed today?" A: "Partially — Chrome has supported it (brotli) since Chrome 69, and Safari supports zlib. It's TLS 1.3-only by design, to avoid middlebox compatibility problems. It negotiates silently: if either side lacks support, the handshake just proceeds uncompressed with no error, so you have to verify negotiation with a real capture rather than assume it from stated library support."

Recap
  • Cleartext SNI (Lesson 21) leaks the real hostname a client is connecting to on every ordinary TLS handshake — a real, current metadata exposure.
  • ECH (RFC 9849, Proposed Standard, published March 3, 2026) fixes this by HPKE-encrypting the sensitive fields inside a ClientHelloInner, hidden behind a cleartext ClientHelloOuter carrying a generic cover name.
  • ECH needs the server's public key published via a DNS HTTPS/SVCB record (RFC 9848) and needs that record fetched over encrypted DNS (DoH/DoT) — without both, it provides no real protection.
  • Firefox 119+, Safari 17+/iOS 17.4+, and Chrome (2026) all support ECH by default when DoH is active; Cloudflare is the largest current server-side deployer, but most of the web still doesn't publish an ECH-capable DNS record.
  • Certificate compression (RFC 8879) is a separate, TLS 1.3-only extension that shrinks the Certificate message using zlib/brotli/zstd — supported by Chrome (brotli, since Chrome 69) and Safari (zlib), and negotiates silently with no error if either side lacks support.
