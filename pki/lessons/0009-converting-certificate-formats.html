Converting Between Certificate Formats

What you will learn

How to convert a certificate, private key, or certificate chain between PEM, DER, PKCS#7, and PKCS#12 using OpenSSL, plus PKCS#12-to-JKS conversion for Java targets with keytool. You'll also learn the specific failure modes each conversion direction produces, and why "just convert it" is sometimes the wrong instinct.

Why this matters

Lesson 8 taught you the four container formats exist because different platforms expect different ones — IIS and Windows generally want PKCS#12, Java wants JKS or PKCS#12, Apache/NGINX want PEM, and some legacy Windows import flows want PKCS#7. In real work, a CA almost never hands you the certificate in the exact format your target server needs. You will convert formats constantly — and get it wrong at least once by converting a certificate without realizing the private key didn't come along, or by picking the wrong -inform/-outform and getting a cryptic "unable to load certificate" error.

Simple explanation

Converting between certificate formats is not cryptography — nothing about the key material changes, and no new trust is created or destroyed. You are only repackaging the same bytes: PEM is DER wrapped in Base64 text with -----BEGIN/END----- markers; DER is the raw binary ASN.1 encoding; PKCS#7 is a binary envelope for bundling certificates and CRLs together (no private key, ever); PKCS#12 is an encrypted binary container that can bundle a certificate, its private key, and the chain, protected by a password. Conversion tools just unwrap one container and repack the same bytes into another.

How it works

PEM ↔ DER (openssl x509)

# PEM to DER
openssl x509 -in cert.pem -inform PEM -out cert.der -outform DER

# DER to PEM
openssl x509 -in cert.der -inform DER -out cert.pem -outform PEM

-inform tells OpenSSL what the input actually is; -outform tells it what to produce. Get -inform wrong and OpenSSL fails to parse the file — it does not silently guess correctly in every case.

PEM ↔ PKCS#7 (openssl crl2pkcs7 / openssl pkcs7)

# PKCS#7 (.p7b) to PEM, printing the certificates it contains
openssl pkcs7 -inform DER -in chain.p7b -outform PEM -out chain.pem -print_certs

# PEM to PKCS#7 — building a NEW PKCS#7 bundle from plain certificates
openssl crl2pkcs7 -nocrl -certfile chain.pem -out chain.p7b -outform DER

This corner of OpenSSL trips people up: openssl pkcs7 only reads and converts an existing PKCS#7 structure — its -in file has to already be PKCS#7. Feed it a plain PEM certificate chain and it fails immediately with "unable to load PKCS7 object", because a bare certificate isn't PKCS#7-shaped data. To build a brand-new PKCS#7 bundle out of ordinary PEM certificates, use openssl crl2pkcs7 instead — it takes one or more certificates (and optionally a CRL) and wraps them into a PKCS#7 "certificates only" structure; -nocrl just means "don't include a CRL." PKCS#7 never contains a private key, so this direction is always safe to hand to someone else or store less carefully than a PKCS#12 file. openssl pkcs7 only understands PKCS#7 v1.5 per RFC 2315 — it cannot parse the newer CMS (RFC 5652) format, which looks similar but is a different structure.

PEM ↔ PKCS#12 (openssl pkcs12)

# Bundle cert + key + chain into a PKCS#12 (.p12/.pfx)
openssl pkcs12 -export -in cert.pem -inkey key.pem -certfile chain.pem \
  -name "my-server-cert" -out bundle.p12

# Extract everything back out to PEM (cert + key together)
openssl pkcs12 -in bundle.p12 -out bundle.pem -noenc

# Extract only the certificate (no private key)
openssl pkcs12 -in bundle.p12 -clcerts -nokeys -out cert.pem

# Extract only the CA chain
openssl pkcs12 -in bundle.p12 -cacerts -nokeys -out chain.pem

PKCS#12 is the only one of these four formats that routinely carries a private key, which is why it's always password-protected — the export password is not optional decoration, it's the only thing standing between that file and full key compromise if it leaks.

PKCS#12 → JKS (keytool, for Java targets)

keytool -importkeystore \
  -srckeystore bundle.p12 -srcstoretype PKCS12 -srcstorepass changeit \
  -destkeystore bundle.jks -deststoretype JKS -deststorepass changeit

Modern practice (and modern Java itself, since JDK 9) treats PKCS#12 as the preferred keystore format even for Java — JKS is a legacy, Java-only format. You'll still meet older applications and deployment scripts that hard-require .jks, which is why this conversion path exists.

Architecture / diagram

            openssl x509 (-inform/-outform)
   PEM  <----------------------------------->  DER
    |                                            |
    | openssl crl2pkcs7 (build) /                | (DER is also PKCS#7's
    | openssl pkcs7 (read/convert)               |  and PKCS#12's wire encoding)
  PKCS#7 (.p7b)  --- certs/CRLs only, no key ----+
    |
    | openssl pkcs12 -export  (needs the private key too)
    v
  PKCS#12 (.p12/.pfx)  --- cert + key + chain, password-protected
    |
    | keytool -importkeystore
    v
  JKS (.jks)  --- legacy Java-only keystore

Important terminology

  • Encoding vs. container — PEM/DER is an encoding question (text vs. binary ASN.1); PKCS#7/PKCS#12 is a container/bundling question (what's packed together). It's possible to have DER-encoded PKCS#7 and PEM-encoded PKCS#7 — the two axes are independent.
  • -inform / -outform — OpenSSL flags telling the tool what format to read/write; get the input one wrong and parsing fails.
  • Friendly name — the human-readable label (-name) stored inside a PKCS#12 file, shown by import wizards.
  • Legacy provider — an OpenSSL 3.x+ module needed to read/write older PKCS#12 files that use RC2-40-CBC or 3DES-CBC encryption, common from old Windows/Java tooling; invoked with -legacy.
  • Proof of possession — not a conversion concept, but relevant context: converting a certificate's format never re-proves anything about the key; that only happens at CSR generation (Lesson 10).

Real-world example

A private CA issues a certificate as a PEM file plus a separate PEM chain. The target is an IIS server, which needs a single PKCS#12 file to import through its certificate wizard. The engineer runs openssl pkcs12 -export -in cert.pem -inkey key.pem -certfile chain.pem -out bundle.p12, sets a strong export password, transfers the .p12 file to the Windows box over an already-encrypted channel (not email), and deletes the local unencrypted PEM copy of the private key afterward. This exact PEM-to-PKCS#12 handoff is one of the most common real conversions a PKI engineer performs.

Hands-on lab

Track B. Generate a self-signed cert and key, then walk it through every conversion direction covered above:

# Set up a test cert + key (self-signed, for lab purposes only)
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem \
  -days 30 -noenc -subj "/CN=lab.local"

# PEM -> DER -> PEM round trip
openssl x509 -in cert.pem -outform DER -out cert.der
openssl x509 -in cert.der -inform DER -outform PEM -out cert-roundtrip.pem
diff cert.pem cert-roundtrip.pem && echo "PEM round-trip: identical"

# PEM -> PKCS#7 -> PEM (certs only, no key involved)
openssl crl2pkcs7 -nocrl -certfile cert.pem -out cert.p7b -outform DER
openssl pkcs7 -inform DER -in cert.p7b -outform PEM -out cert-from-p7b.pem -print_certs

# PEM cert+key -> PKCS#12 -> back out
openssl pkcs12 -export -in cert.pem -inkey key.pem -name "lab-cert" -out bundle.p12
openssl pkcs12 -in bundle.p12 -info -noout   # inspect what's inside, prompts for the export password
openssl pkcs12 -in bundle.p12 -clcerts -nokeys -out cert-from-p12.pem

Expected result: the PEM round-trip file is byte-identical to the original; the PKCS#7 file contains only the certificate (confirm with -print_certs, no key present); the PKCS#12 -info output lists both a certificate bag and a (encrypted) key bag, proving the key traveled with it — the one format here that actually carries key material.

What can go wrong

The most common mistake is converting only the certificate and assuming the private key came along — PEM and DER conversions of a certificate never touch the key at all, because a certificate file doesn't contain one. A second common mistake: exporting a PKCS#12 with no password (some tools allow an empty password) and then treating the file as safe to email — it isn't, since an unprotected .p12 is a plaintext private key with extra steps. A third: hitting old PKCS#12 files from legacy Windows Server or old Java tooling that use RC2-40-CBC, which recent OpenSSL 3.x+ builds refuse to read without the -legacy flag.

Troubleshooting

"unable to load certificate" from openssl x509 almost always means -inform doesn't match the actual file — a DER file was fed in without -inform DER, or vice versa; file cert.xyz at the shell (binary vs. ASCII text) is a fast way to tell them apart before guessing. "Mac verify error: invalid password?" from openssl pkcs12 means either the export password is wrong, or (on OpenSSL 3.x+) the file uses a legacy cipher and needs the -legacy flag before OpenSSL will even attempt to check the password. If a converted PKCS#12 imports on one server but silently shows "no private key" on another, re-run openssl pkcs12 -in bundle.p12 -info -noout and confirm a key bag is actually present — the export step may have been run without -inkey.

Security considerations

Any conversion path that produces an unencrypted PEM private key on disk (extracting from PKCS#12 with -noenc, for example) creates a window where that key sits in plaintext — delete it immediately after use, and never leave it in a shell history, temp directory, or backup. Treat PKCS#12 export passwords with the same care as the key itself; a weak or shared export password defeats the whole point of encrypting the container. Never transfer an unencrypted private key (PEM or otherwise) over email, chat, or an unencrypted channel — only ever move it inside an already-encrypted transport, and prefer generating the key directly on the target system via a CSR (Lesson 10) so it never has to travel at all.

Production best practices

Automate format conversion as part of your issuance/deployment pipeline rather than doing it by hand repeatedly — a script that always uses the same flags removes the "did I get -inform right this time" class of error. Keep the CA-issued PEM as your source of truth and treat every other format as a derived, regenerable artifact — never treat a converted PKCS#12 as the canonical copy. Always verify a converted file before deploying it (-text -noout for certs, -info -noout for PKCS#12) rather than assuming the conversion succeeded because the command exited 0.

Exam and interview notes

Interview Q: "You're given a PEM certificate and need to install it on an IIS server. What do you do?" A: "IIS needs PKCS#12. Export it with openssl pkcs12 -export -in cert.pem -inkey key.pem -certfile chain.pem -out bundle.p12, set a strong password, transfer it over an encrypted channel, and delete any unencrypted key copies afterward."

Interview Q: "What's the difference between PKCS#7 and PKCS#12?" A: "PKCS#7 bundles certificates (and CRLs) only — never a private key, so it's relatively low-risk to move around. PKCS#12 can bundle a certificate, its private key, and the chain in one encrypted, password-protected file — treat it like key material because it can contain key material."

Recap
  • Conversion never changes cryptographic content — it only repackages the same bytes into a different encoding (PEM/DER) or container (PKCS#7/PKCS#12).
  • Only PKCS#12 carries a private key among these four formats — treat any PKCS#12 file, and any unencrypted PEM key extracted from one, as key material requiring key-grade protection.
  • -inform/-outform mismatches are the single most common conversion error, producing "unable to load certificate" errors.
  • Old PKCS#12 files (RC2-40-CBC, 3DES-CBC) need the -legacy flag on modern OpenSSL 3.x+ builds to even open.
