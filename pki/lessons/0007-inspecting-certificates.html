Inspecting Certificates with OpenSSL and Windows Tools

What you will learn

The exact commands to read every field from Lesson 6 out of a real certificate file or a live server, on both OpenSSL (Linux/macOS/Windows) and native Windows tooling — plus how automated linters like zlint and certlint check a certificate against RFC 5280 and CA/Browser Forum requirements instead of you eyeballing the output by hand.

Why this matters

You cannot troubleshoot what you cannot read. Every incident in Stage Q ("date invalid," "hostname mismatch," "unable to get local issuer") starts with pulling up the actual certificate and reading its fields — not guessing from a browser error message. This is the single most-used skill in this entire course; you'll run these commands dozens of times per week in a real PKI role.

Simple explanation

There are three ways to look inside a certificate: read a file you already have (openssl x509, or Windows certutil), pull one live off a running server (openssl s_client), or run an automated linter against it (zlint/certlint) that checks hundreds of RFC 5280 and CA/Browser Forum rules for you in seconds. Learn all three — each solves a different problem.

How it works

OpenSSL: reading a certificate file

The core command is openssl x509. By default it reads and re-outputs PEM; the flags below change what it shows instead:

# Full human-readable dump
openssl x509 -in cert.pem -noout -text

# Just the parts you usually need
openssl x509 -in cert.pem -noout -subject -issuer -dates -serial

# SHA-256 fingerprint (used to compare a cert against a known-good copy)
openssl x509 -in cert.pem -noout -fingerprint -sha256

# If the file is DER (binary), not PEM
openssl x509 -in cert.der -inform DER -noout -text

-noout is the flag that trips people up first: without it, openssl x509 re-prints the PEM certificate itself after whatever else you asked for, which is almost never what you want when you're just inspecting.

OpenSSL: pulling a certificate straight off a live server

You don't need the file at all if the server is reachable — this is usually the fastest path during an incident:

# Connect, show the full handshake and cert chain, then exit immediately
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -text

# Just check the dates without a full dump
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -dates

-servername sets SNI — without it, some servers hosting multiple certificates will hand back the wrong one, which is a real, common false alarm during troubleshooting.

Windows: certutil and PowerShell

Track A. Windows ships its own certificate inspection tooling that doesn't require OpenSSL at all:

# Dump a certificate file's contents (equivalent to openssl x509 -text)
certutil -dump cert.cer

# Dump a PKCS#12/.pfx bundle's structure
certutil -dumpPFX bundle.pfx

# PowerShell equivalent for a quick look
Get-PfxCertificate -FilePath .\cert.cer | Format-List *

certutil also doubles as the primary command-line tool for interacting with AD CS itself (submitting requests, managing the CA database) — Stage K covers that side. For this lesson, -dump and -dumpPFX are the two you'll use most for pure inspection. The Windows GUI equivalent is the Certificates MMC snap-in (certmgr.msc for the current user store, certlm.msc for the local machine store) — double-click any certificate to see the same fields in a dialog.

Automated linting: zlint and certlint

Reading fields by hand doesn't scale, and it doesn't catch subtle CA/Browser Forum Baseline Requirements violations a human reviewer would miss. Two purpose-built linters exist for this:

  • zlint (Go, ZMap project) — checks a certificate against RFC 5280 and CA/Browser Forum rules, organized into "lint sources" you can include/exclude: 
    zlint mycert.pem
zlint -excludeSources=ETSI_ESI mycert.pem
zlint -list-lints-source
  • certlint (Ruby, maintained by Rob Stradling at Sectigo, originally written by Peter Bowen) — a similar RFC 5280 / BR conformance checker, invoked via ruby -I lib:ext bin/certlint cert.pem. Output is one line per finding, prefixed by severity: Bug, Information, Notice, Warning, Error, Fatal.

In practice, public CAs and CT-log monitoring pipelines run both together — zlint and certlint don't check exactly the same rule set, so agreement between them is stronger evidence of a compliant certificate than either alone.

Important terminology

  • SNI (Server Name Indication) — the hostname a TLS client sends during the handshake so a multi-certificate server returns the right one; set with -servername in openssl s_client.
  • Fingerprint — a hash (commonly SHA-256) of the DER-encoded certificate, used to verify two copies are byte-identical without comparing the whole file.
  • zlint / certlint — automated X.509 conformance linters checking a certificate against RFC 5280 and CA/Browser Forum Baseline Requirements.
  • MMC (Microsoft Management Console) — the Windows GUI framework hosting the Certificates snap-in (certmgr.msc / certlm.msc).

Real-world example

A user reports "the site's certificate looks wrong." Instead of trusting the browser's summary, pull the live certificate directly: echo | openssl s_client -connect thesite.com:443 -servername thesite.com 2>/dev/null | openssl x509 -noout -subject -issuer -dates. In one line you get the actual subject, the actual issuer, and the actual validity window — ground truth, not a paraphrase.

Hands-on lab

Track B. Practice all three inspection methods against a real, live certificate:

# 1. Pull a live cert and dump it fully
echo | openssl s_client -connect www.google.com:443 -servername www.google.com 2>/dev/null \
  | openssl x509 -noout -text > google-cert.txt

# 2. Extract just the fields you'd check first during an incident
openssl x509 -in google-cert.txt -noout -subject -issuer -dates 2>/dev/null || \
echo | openssl s_client -connect www.google.com:443 -servername www.google.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# 3. Save the cert as PEM and lint it (if zlint is installed)
echo | openssl s_client -connect www.google.com:443 -servername www.google.com 2>/dev/null \
  | openssl x509 -out google-cert.pem
zlint google-cert.pem 2>/dev/null | head -20 || echo "zlint not installed — see https://github.com/zmap/zlint"

Expected result: you can identify the certificate's real subject, issuer, and expiry date without opening a browser, and (if zlint is installed) see it pass the great majority of RFC 5280 / BR lint checks, since it's a certificate from a major public CA.

What can go wrong

Forgetting -servername on openssl s_client against a server using SNI-based virtual hosting is the single most common mistake here — you'll pull back a default/wrong certificate and misdiagnose a perfectly healthy certificate as broken. Always set -servername to match the hostname you're actually trying to reach.

Troubleshooting

If openssl x509 -in file -noout -text fails with an error about the input, the file is very likely DER, not PEM (or vice versa) — try again with -inform DER, or check the first line of the file: a genuine PEM file starts with -----BEGIN CERTIFICATE-----. Lesson 8 covers format identification and conversion in depth.

Security considerations

Every command in this lesson only ever reads public certificate data — none of them touch a private key, so there's no secret-handling risk in running them, including against production servers. That said, avoid running unfamiliar third-party inspection tools against certificates from systems you don't control without checking what they send elsewhere first.

Production best practices

Build the habit of pulling live certificates directly (openssl s_client) rather than trusting a browser's or monitoring tool's summary during an incident — summaries can be stale, cached, or simplified in ways that hide the actual field values you need. In CI/CD pipelines that issue certificates, run zlint or certlint automatically on every newly issued certificate before it's deployed; catching a Baseline Requirements violation before deployment is far cheaper than after a CA is caught issuing non-compliant certificates.

Exam and interview notes

Interview Q: "How would you check a certificate's expiry on a remote server without opening a browser?" A: "echo | openssl s_client -connect host:443 -servername host 2>/dev/null | openssl x509 -noout -dates — connects, retrieves the live certificate, and prints notBefore/notAfter directly."

Interview Q: "What's the difference between zlint and certlint?" A: "Both are RFC 5280 / CA-Browser Forum conformance linters, but different implementations with different rule sets — zlint is Go, from the ZMap project; certlint is Ruby, maintained by Sectigo. Public CAs commonly run both, since they don't check identically overlapping rules."

Recap
  • openssl x509 -in file -noout -text reads a certificate file; always include -noout or you'll get the PEM re-printed too.
  • openssl s_client -connect host:443 -servername host pulls a live certificate straight off a server — always set -servername to avoid getting the wrong certificate on SNI-based hosting.
  • Windows has its own native tools — certutil -dump / -dumpPFX, PowerShell's Get-PfxCertificate, and the Certificates MMC snap-in — no OpenSSL required.
  • zlint and certlint automate RFC 5280 / CA-Browser Forum compliance checking; public CAs commonly run both since their rule sets don't fully overlap.
