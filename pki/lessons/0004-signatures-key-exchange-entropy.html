Digital Signatures, Key Exchange, and Entropy

What you will learn

How to actually sign and verify data with OpenSSL, what "forward secrecy" means and why ECDHE key exchange provides it, and why the randomness used to generate a key matters as much as the algorithm itself — including a real, documented incident where weak randomness broke thousands of keys that were otherwise generated "correctly."

Why this matters

Lessons 2 and 3 explained signatures and key exchange conceptually. This lesson makes both hands-on and adds the piece that quietly underlies every key you've generated so far: where does the randomness actually come from, and what happens when there isn't enough of it? This question has caused real, large-scale security failures — not hypothetical ones.

Simple explanation

Signing is "prove I made this, unaltered." Key exchange is "let's agree on a secret, in public, that an eavesdropper watching us can't reconstruct." Entropy is the raw unpredictability that everything above secretly depends on — a key generated from a predictable source is like a padlock combination chosen by always picking a family birthday: the lock mechanism can be flawless, and the combination is still guessable.

How it works

Forward secrecy — why key exchange matters even when you already have certificates

You might reasonably ask: if Bob already has a certificate proving his identity via a public/private key pair, why does TLS also do a separate key-exchange step (Lesson 2's Diffie-Hellman/ECDHE) instead of just encrypting everything directly with that key pair? The answer is forward secrecy: if a connection uses ECDHE to generate a fresh, temporary (ephemeral — the "E" in ECDHE) shared secret for each session, then even if an attacker later steals the server's long-term private key, they cannot decrypt previously recorded traffic — each past session's key is already gone, never stored, and can't be recomputed from the long-term key alone. Without ephemeral key exchange, a single future key compromise would retroactively expose every past conversation that was ever recorded and stored by an attacker (a real strategy called harvest-now-decrypt-later, which Stage V's post-quantum lessons return to).

Entropy: the randomness your keys are built from

Every key generation command you ran in Lesson 3 pulled randomness from your operating system's cryptographically secure random number generator (on Linux, ultimately /dev/urandom, seeded from real hardware/environmental noise). If that pool of randomness is predictable — because a system just booted and hasn't gathered enough entropy yet, because a bug feeds it the same seed repeatedly, or because a virtual machine template gets cloned before generating its own fresh entropy — then keys "generated correctly" by a correct algorithm can still be guessable, or even identical across supposedly-independent machines.

Architecture / diagram

Diffie-Hellman / ECDHE key exchange (ephemeral, per-session)

  Alice generates a temporary  ─────────▶  public value A
  (ephemeral) key pair, session-only

                                 Bob generates a temporary
                    public value B  ◀───── (ephemeral) key pair, session-only

  Alice combines: (her ephemeral private key) + B  ──▶  shared secret
  Bob   combines: (his ephemeral private key)  + A  ──▶  SAME shared secret

  Eve saw only A and B (public) — cannot derive the shared secret.
  Session ends → ephemeral keys are discarded → secret is gone forever,
  even if Alice's and Bob's LONG-TERM certificate keys are stolen later.

Important terminology

  • Forward secrecy (also "perfect forward secrecy," PFS) — past sessions stay secure even if a long-term private key is later compromised.
  • Ephemeral key — a temporary key generated fresh for one session/purpose, then discarded — the "E" in ECDHE.
  • Entropy — a measure of true unpredictability available to seed random number generation.
  • CSPRNG — cryptographically secure pseudo-random number generator; the specific class of random source safe to use for key generation (never a general-purpose, non-cryptographic random function).
  • Harvest-now-decrypt-later — an attacker records encrypted traffic today, betting on breaking the encryption later (e.g. with future quantum computers) — Stage V covers this in depth.

Real-world example

In 2008, a change to Debian's OpenSSL package accidentally removed most of the sources feeding its random number generator, without anyone noticing for about two years. Every key generated on an affected Debian or Ubuntu system during that window came from a pool of only around 32,768 possible values instead of astronomically many — meaning an attacker could simply generate and check every possible key in that tiny space. Tens of thousands of real, deployed keys (SSH keys, TLS certificates) had to be identified and reissued. The algorithms (RSA, DSA) were never broken — the randomness feeding them was, which is exactly this lesson's point: algorithm strength and entropy quality are two separate requirements, and a failure in either one breaks the whole system.

Hands-on lab

Track B (no Windows needed). Sign a file and verify the signature, using the RSA key pair from Lesson 3:

# Sign a file with your private key
openssl dgst -sha256 -sign rsa-private.key -out message.sig message.txt

# Verify the signature with the matching public key
openssl dgst -sha256 -verify rsa-public.key -signature message.sig message.txt
# Expected output: Verified OK

# Now tamper with the file and re-verify
echo "extra line" >> message.txt
openssl dgst -sha256 -verify rsa-public.key -signature message.sig message.txt
# Expected output: Verification Failure

This is Lesson 2's signing/verification model made concrete: the signature is tied to the exact byte content of the file at signing time, not to the file's name or location.

What can go wrong

Verification silently fails (or is skipped entirely) when the wrong public key is used — for example, verifying against a different key pair than the one that actually signed the data. OpenSSL will report "Verification Failure" clearly, but application code that doesn't check the return value of a verification call, or that logs a failure without stopping processing, effectively accepts unsigned or forged data while believing it's protected.

Troubleshooting

If a verification that should succeed keeps failing, check in order: (1) is the exact same file/byte content being verified as what was signed — even trailing whitespace or line-ending differences (CRLF vs LF) will break it, (2) is the public key actually the match for the private key that signed it (Lesson 3's modulus check), (3) is the same hash algorithm being used on both ends (a SHA-256 signature won't verify against a SHA-1 hash of the same content).

Security considerations

Never generate long-term keys on a freshly-booted system, a container image baked before boot-time entropy gathering, or a cloned VM template without confirming fresh entropy — this is precisely the failure class the Debian incident represents, and cloud/container environments can reintroduce the same risk if images are cloned improperly. Modern Linux kernels (5.x+) block key-generation-relevant randomness calls until sufficient entropy is available specifically to prevent this class of bug, but older or embedded systems may not.

Production best practices

Prefer cipher suites and TLS configurations that mandate ephemeral (ECDHE) key exchange over static key exchange, specifically for the forward-secrecy property — Stage E's TLS lessons show how to verify which mode a given connection actually negotiated. For entropy, trust your operating system's CSPRNG rather than rolling custom randomness, and be cautious about key generation immediately after provisioning a new VM or container from a template.

Exam and interview notes

Interview Q: "What is forward secrecy, and why does it matter?" A: "Forward secrecy means that even if an attacker later steals a server's long-term private key, they can't decrypt past sessions they recorded earlier. It works because each session uses a fresh, ephemeral key exchange (ECDHE) that's discarded afterward and never derivable from the long-term key. Without it, one future key compromise retroactively exposes every past recorded session."

Interview Q: "Can a correctly-implemented algorithm still produce a breakable key?" A: "Yes — if the randomness used to generate it is weak or predictable. The 2008 Debian OpenSSL incident is the canonical example: correct algorithms, broken entropy, tens of thousands of guessable keys."

Source

Debian Security Advisory DSA-1571-1 (the 2008 OpenSSL predictable-randomness incident) and NIST SP 800-90A, "Recommendation for Random Number Generation Using Deterministic Random Bit Generators" — both confirmed current against live sources before writing.

Recap
  • Ephemeral (ECDHE) key exchange provides forward secrecy: past sessions stay safe even if a long-term key is stolen later.
  • Signing ties data to an exact byte-for-byte content — any change, even whitespace, breaks verification.
  • Entropy quality is a separate requirement from algorithm correctness — a correct algorithm fed weak randomness still produces breakable keys, as the 2008 Debian incident showed at real scale.
  • Never generate long-term keys on freshly-booted or freshly-cloned systems without confirming adequate entropy.
