What Is a Digital Certificate? Anatomy of an X.509 Certificate

What you will learn

What a digital certificate actually is (a signed statement, not a secret), the exact field-by-field structure of an X.509 v3 certificate as defined by RFC 5280, and which fields you'll actually use day-to-day versus which exist mostly for edge cases.

Why this matters

Every troubleshooting session, every openssl x509 -text dump, every "why did this certificate fail validation" incident comes down to reading these fields correctly. If you don't know that Subject Alternative Name, not the Subject Common Name, is what browsers actually check for hostname matching (Lesson 16 covers validation in full; RFC 9525 made this official in 2023), you will misdiagnose real outages. This lesson is the map you'll reference for the rest of the course.

Simple explanation

A digital certificate is a public statement, signed by someone else, that says "this public key belongs to this identity." It contains no secrets — a certificate is safe to hand to anyone, post publicly, or attach to every TLS handshake, because it only ever contains a public key plus metadata about who that key belongs to and who's vouching for that claim. The private key that matches it never appears in the certificate at all. X.509 is simply the standard, structured format almost every certificate on the internet uses to say all of this.

How it works

The two-part structure

A certificate has two conceptual halves: the part that got signed (TBSCertificate — "to be signed certificate"), and the signature itself, covering everything in that first part:

Certificate  ::=  SEQUENCE  {
    tbsCertificate       TBSCertificate,
    signatureAlgorithm   AlgorithmIdentifier,
    signatureValue       BIT STRING  }

This matters because it explains why tampering with a certificate is detectable: change one byte of tbsCertificate and the signatureValue no longer validates against it. That's the entire integrity guarantee.

Fields inside TBSCertificate (RFC 5280, Section 4.1.2)

  • version — almost always v3 (encoded as integer 2); v3 is required if any extensions are present, and virtually every certificate issued today uses extensions.
  • serialNumber — a positive integer, unique per issuing CA, up to 20 octets. This is what a CRL or OCSP responder uses to identify exactly which certificate is being revoked.
  • signature — the algorithm identifier the CA used to sign (e.g. sha256WithRSAEncryption, ecdsa-with-SHA256); must match the outer signatureAlgorithm.
  • issuer — the distinguished name (DN) of the CA that signed this certificate. Never empty.
  • validity — a notBefore / notAfter pair (UTCTime or GeneralizedTime). Everything about certificate lifetimes (Lesson 32-38, and the 200-day CA/Browser Forum maximum from Ballot SC-081v3) traces back to this one field.
  • subject — the DN of the entity the certificate identifies. Can be an empty sequence if subjectAltName is present and marked critical — a detail that surprises people reading raw ASN.1 for the first time.
  • subjectPublicKeyInfo — the actual payload: the algorithm identifier plus the subject's public key bits. This is the one thing every certificate exists to carry.
  • issuerUniqueID / subjectUniqueID — optional, v2/v3 only, explicitly "not recommended" by RFC 5280. You will almost never see these populated in practice.
  • extensions — v3 only, a sequence of typed, optionally-critical extensions. This is where almost all the interesting, modern behavior lives (next section).

The extensions that actually matter (RFC 5280, Section 4.2)

ExtensionRFC 5280 §What it controls
basicConstraints4.2.1.9Is this a CA certificate (CA:TRUE) allowed to sign other certificates, or an end-entity leaf?
keyUsage4.2.1.3What cryptographic operations the key may perform — digitalSignature, keyCertSign, cRLSign, keyEncipherment, etc.
extendedKeyUsage4.2.1.12Application-level purpose — serverAuth, clientAuth, codeSigning, timeStamping.
subjectAltName (SAN)4.2.1.6DNS names, IPs, emails, URIs the certificate is actually valid for. This is what hostname checking uses today — not the Subject CN (RFC 9525, 2023).
authorityKeyIdentifier4.2.1.1Identifies which of the issuing CA's keys signed this certificate — needed when a CA has rotated keys.
subjectKeyIdentifier4.2.1.2A hash identifying this certificate's own public key — used by the next certificate down the chain as its authorityKeyIdentifier.
CRL Distribution Points4.2.1.13URL(s) where a revocation list for this certificate can be fetched (Lesson 39).
Authority Information Access4.2.2.1URL(s) for the OCSP responder and/or the issuing CA's own certificate (Lesson 40).

Architecture / diagram

Certificate
├── tbsCertificate                     (this whole block gets signed)
│   ├── version               → v3
│   ├── serialNumber          → unique per CA
│   ├── signature             → alg CA used to sign
│   ├── issuer                → CA's distinguished name
│   ├── validity               → notBefore / notAfter
│   ├── subject                → entity's distinguished name
│   ├── subjectPublicKeyInfo  → the actual public key (the payload)
│   └── extensions[]
│         ├── basicConstraints        (CA or leaf?)
│         ├── keyUsage / extendedKeyUsage
│         ├── subjectAltName          (real hostname-matching field)
│         ├── authorityKeyIdentifier / subjectKeyIdentifier  (chain-linking)
│         ├── CRL Distribution Points
│         └── Authority Information Access (OCSP)
├── signatureAlgorithm                 (must match tbsCertificate.signature)
└── signatureValue                     (signature OVER tbsCertificate only)

Important terminology

  • DN (Distinguished Name) — a structured name like CN=example.com, O=Example Inc, C=US identifying the subject or issuer.
  • TBSCertificate — "to be signed certificate": everything the CA's signature actually covers.
  • Critical extension — an extension flagged such that a client must reject the certificate if it doesn't understand that extension, rather than silently ignore it.
  • SAN (Subject Alternative Name) — the extension holding the actual list of DNS names/IPs a certificate is valid for.
  • ASN.1 / DER — the abstract syntax notation and binary encoding rules a certificate is actually built from under the hood (Lesson 8 covers the file formats built on top of this).

Real-world example

When you visit a website and your browser shows a padlock, the certificate it just received in the TLS handshake is being read exactly like the diagram above: is subjectAltName a match for the hostname you typed? Is notAfter still in the future? Does basicConstraints on the CA certificate above it actually say CA:TRUE? Every one of those checks is reading one specific field from this structure — there is no separate "trust database" beyond the certificate's own signed fields plus the trust store (Lesson 17).

Hands-on lab

Track B. Generate a self-signed certificate and map every field back to what you just learned:

# Generate a throwaway key + self-signed cert in one step
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 \
  -keyout self.key -out self.pem -days 30 -noenc \
  -subj "/CN=lab.example.com" \
  -addext "subjectAltName=DNS:lab.example.com,DNS:www.lab.example.com"

# Dump every field, human-readable
openssl x509 -in self.pem -noout -text

Expected result: in the output, find and identify — the version (should read 3 (0x2)), the serial number, the validity dates, the Subject DN, the two hostnames under X509v3 Subject Alternative Name, and X509v3 Basic Constraints: CA:FALSE (this is a leaf certificate, not a CA). Confirm you can point to each one without re-reading this lesson.

What can go wrong

A common beginner mistake: assuming the Subject CN field is what browsers check for the hostname. Since RFC 9525 obsoleted RFC 6125 in November 2023, CN-based hostname matching is no longer valid per spec — clients must use subjectAltName only. A certificate with a correct CN but no matching SAN entry will fail hostname validation in every modern client, even though the CN "looks right" to a human reading it.

Troubleshooting

If a certificate is rejected with a hostname-mismatch error but the Subject line looks correct, the first command to run is openssl x509 -in cert.pem -noout -text | grep -A1 "Subject Alternative Name" — check the SAN list, not the Subject DN. This single check resolves a large share of "but the name is right!" tickets.

Security considerations

Because a certificate is entirely public (it contains no secret material), it is always safe to log, share, or attach to a bug report in full — never treat a .crt/.pem certificate file itself as sensitive. The private key is the only part that requires protection (Lesson 72), and it is never present inside a certificate's own structure.

Production best practices

When issuing certificates, always set basicConstraints correctly (CA:FALSE for leaf certificates — never leave this to a template default without checking), always populate subjectAltName with every hostname the certificate needs to serve, and never rely on Subject CN alone. These three checks catch the majority of real-world misissuance problems before they reach production.

Exam and interview notes

Interview Q: "What's the difference between the Subject CN and the SAN, and which one actually matters?" A: "SAN is what matters — per RFC 9525 (obsoleting RFC 6125 in 2023), CN-based hostname matching is no longer valid. CN is still often set for human readability and legacy compatibility, but a modern client validates the hostname against subjectAltName entries only."

Interview Q: "What does a certificate's signature actually cover?" A: "The entire TBSCertificate structure — version, serial number, issuer, validity, subject, public key, and all extensions. Change any one byte of that structure and the signature no longer validates."

Recap
  • A certificate is a public, signed statement binding a public key to an identity — it contains no secrets and is always safe to share.
  • The signature covers the entire TBSCertificate block: version, serial number, issuer, validity, subject, public key, and extensions.
  • Extensions carry the fields that actually matter day-to-day: basicConstraints (CA or leaf), keyUsage/EKU (allowed operations), and subjectAltName (real hostname matching, per RFC 9525).
  • Subject CN is not used for hostname validation by modern clients — only subjectAltName is, since RFC 9525 obsoleted RFC 6125 in 2023.
