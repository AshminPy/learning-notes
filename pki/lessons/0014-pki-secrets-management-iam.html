PKI vs Secrets Management vs IAM: Where the Boundaries Are

What you will learn

Clear, working definitions of three categories engineers constantly conflate — PKI, secrets management, and IAM — and exactly where their real boundaries are, backed by how AWS itself documents the split between its own services. You'll also learn the two places these categories legitimately overlap (a tool like HashiCorp Vault, and the shared KMS/HSM layer underneath both PKI and secrets management), so you can tell a genuine overlap from a wrong-tool mistake.

Why this matters

Picking the wrong tool for the wrong category causes real production pain: a TLS private key dropped into a generic secrets store as an opaque blob has no certificate-authority renewal lifecycle attached to it, so nothing reissues it before it expires — a silent outage waiting to happen (Lesson 37). An IAM role scoped correctly on paper doesn't substitute for actually validating a certificate chain in code that's supposed to be doing mTLS. Engineers who can't name the boundary between these three systems tend to reach for whichever one is already open in another tab, not the one that's actually correct for the job.

Simple explanation

Three different questions, three different systems. PKI answers: "prove who or what you are, using a key pair and a trusted third party's signature." Secrets management answers: "where do I safely store, retrieve, and rotate a piece of sensitive data so it's never hardcoded or leaked." IAM answers: "given a proven identity, what is it actually allowed to do, and how do I define and enforce that." An analogy: PKI is your passport — it proves who you are, issued by an authority, and it expires. Secrets management is a safe deposit box — it stores sensitive items securely and can rotate the combination. IAM is the building's access list — once your passport has been checked at the door, IAM decides which floors you can actually enter.

How it works

PKI

Everything covered in Lessons 1-13: asymmetric key pairs, certificate authorities, X.509 certificates, chains of trust, revocation. The defining property is proof of possession — a certificate's holder must cryptographically prove they hold the matching private key (a signature challenge), and the private key itself is never transmitted to prove that. Certificates have a built-in expiry and a chain of trust back to a root; that lifecycle (issue, renew, revoke) is PKI's core job, not a generic storage system's job.

Secrets management

Centralized, access-controlled storage for opaque, mostly symmetric secrets — database passwords, API keys, OAuth tokens — with encryption at rest, audit logging, and (ideally) automatic rotation. Tools: HashiCorp Vault's KV engine, AWS Secrets Manager, Azure Key Vault's "secrets" object type, GCP Secret Manager. These systems are designed around a bearer model: whoever retrieves the secret value can use it directly — there's no cryptographic challenge to prove you're allowed to hold it beyond the retrieval-time access check.

IAM

Identity and Access Management systems (AWS IAM, Azure Entra ID, GCP IAM, Okta) handle authentication (verifying who's making a request) and authorization (deciding what that verified identity may do) via identities, roles, and policies. Per AWS's own IAM documentation: "IAM provides the infrastructure necessary to control authentication and authorization for your AWS accounts." IAM is not itself a key-pair or certificate system — it governs permissions layered on top of however authentication actually happened.

Where the boundaries genuinely blur

Two places, and only two, where these categories legitimately overlap rather than one being misused for the other:

  • HashiCorp Vault's PKI secrets engine. Vault issues short-lived X.509 certificates dynamically, using Vault's own authentication and policy engine to decide who's allowed to request which certificate. This means Vault genuinely straddles both categories — it's a secrets-management platform that also functions as an intermediate CA for its PKI secrets engine specifically. It's not a substitute for a full CA hierarchy; it's a secrets-engine feature within a broader secrets-management tool.
  • Cloud KMS/HSM (AWS KMS, GCP Cloud KMS, Azure Key Vault "keys"). This sits underneath both PKI (protecting a CA's private key, Stage O) and secrets management (encrypting secrets at rest). It's an enabling layer both systems depend on, not a third boundary-defining category of its own.

Everything else is a wrong-tool problem, not a real overlap — and AWS's own documentation draws the line explicitly. AWS Secrets Manager's own "What is Secrets Manager" page tells you, in its own words, to use something else for anything that isn't a generic application secret: AWS credentials → IAM. Encryption keys → KMS. SSH keys → EC2 Instance Connect. Private keys and certificates → AWS Certificate Manager (PKI). AWS is telling you not to put a TLS private key in Secrets Manager — that's ACM's job.

Important terminology

  • Proof of possession — a PKI credential's holder proves they hold the private key via a cryptographic challenge, without ever transmitting the key itself.
  • Bearer credential — a secrets-management or IAM credential (API key, session token) that anyone holding the exact value can use directly, with no cryptographic challenge.
  • Secrets engine — a Vault term for a pluggable backend (KV, PKI, AWS, database) that determines what kind of secret Vault issues or stores for a given mount.
  • KMS/HSM — Key Management Service / Hardware Security Module — the enabling layer that protects cryptographic key material used by both PKI (CA keys) and secrets management (encryption-at-rest keys).
  • Authentication vs authorization — IAM's two core functions: verifying identity (authentication) versus deciding what a verified identity may do (authorization); PKI can supply the authentication step via certificates, but IAM still owns authorization.

Real-world example

A team stores their server's TLS private key and certificate as a base64-encoded blob in a generic secrets manager, reasoning "it's sensitive, so it belongs here." It works — until the certificate expires. Nothing in a generic secrets store knows a certificate has a notAfter date or how to talk to a CA to renew it; that's not what the tool is for. The service goes down. Meanwhile the same team's IAM roles were scoped correctly the entire time — the outage had nothing to do with permissions. The fix: move the certificate to ACM (or an internal CA with cert-manager/Vault PKI automation, Stage L/M), keep the secrets manager for the application's actual API keys and database credentials, and leave IAM scoped to who may retrieve or rotate which of those — three tools, three jobs, no more guessing which bucket a credential belongs in.

Hands-on lab

Track B. Demonstrate the practical difference between a proof-of-possession credential (PKI) and a bearer credential (the secrets-management/IAM model), locally, with no cloud account required:

# --- PKI side: possession must be proven cryptographically ---
openssl genrsa -out server.key 2048
openssl req -new -x509 -key server.key -out server.crt -days 365 -subj "/CN=demo.local"

# "Prove possession" the PKI way: sign a random challenge with the private key
echo "prove-you-have-the-key" > challenge.txt
openssl dgst -sha256 -sign server.key -out challenge.sig challenge.txt

# A verifier checks the signature using only the PUBLIC key from the certificate --
# server.key itself is never sent anywhere
openssl dgst -sha256 -verify <(openssl x509 -in server.crt -pubkey -noout) \
  -signature challenge.sig challenge.txt

# --- Bearer-secret side: possession = simply presenting the value ---
API_KEY="sk_live_demo_12345"
echo "Anyone holding this exact string can use it directly: $API_KEY"
echo "No cryptographic challenge is involved -- the value itself IS the credential."

Expected result: the openssl dgst -verify step reports Verified OK — proof that whoever ran it holds server.key, without that key ever leaving the machine or being transmitted. Compare that to the bearer-secret block: API_KEY's entire security rests on the string itself staying secret — if it's copied into a log line, a chat message, or a compromised process's memory, whoever has that copy is now fully authenticated as that credential, permanently, until it's rotated. That gap is exactly why PKI-based identity (mTLS, code signing) is structurally stronger against interception than bearer secrets.

What can go wrong

Treating a certificate's private key like any other secret — dumping it into a generic key/value store with no renewal automation attached — leads directly to expired-certificate outages, because nothing in that store understands a certificate's lifecycle. Using IAM role/policy checks as a stand-in for actual cryptographic machine identity — trusting "this call came from IAM role X" over a network path that has no other authentication — when mTLS with real certificate validation is what the design actually needs. Rotating what looks like "just a secret" without realizing it's a certificate's private key, then not reissuing the certificate to match — the deployed certificate's public key no longer corresponds to anything, and it silently stops validating.

Troubleshooting

If an outage traces back to "the secret expired," check first whether that "secret" is actually a certificate (does it have a notAfter date) versus a genuinely opaque credential (which doesn't expire on its own, only rotates on a schedule you set) — the fix path is completely different: CA reissuance versus a secrets-manager rotation job. If an integration fails with a signature-verification error but the same call succeeds when a raw value is checked instead, the calling code and the credential's actual model have been mismatched — confirm whether the system in question was built for proof-of-possession (PKI) or bearer (secrets/IAM) credentials before changing anything else.

Security considerations

Bearer secrets — API keys, database passwords, most long-lived IAM access keys — are compromised the instant they're copied or leaked, with no way to detect misuse until after-the-fact log analysis catches it. PKI's proof-of-possession model means the private key itself is never transmitted, so intercepting network traffic or reading a log doesn't hand an attacker the ability to authenticate as that identity — this is exactly why Zero Trust architectures (Lesson 103) increasingly favor short-lived certificates and mTLS for service-to-service auth over long-lived bearer API keys wherever it's practical to do so. Never let a correctly-scoped IAM policy substitute for actually validating a certificate chain in code that's supposed to perform mTLS — a misconfigured IAM policy and a badly validated certificate are different failure classes, and conflating them creates a real blind spot.

Production best practices

Use each system for exactly what it's built for: ACM, an internal CA, cert-manager, or Vault's PKI secrets engine for anything that's fundamentally a key pair with an expiry and a chain of trust; a secrets manager (Vault KV, Secrets Manager, Key Vault secrets, Secret Manager) for opaque credentials that need storage, rotation, and audit but no cryptographic chain-of-trust concept; IAM for defining and enforcing what an already-authenticated identity may do. Treat AWS's own documented split — IAM for account credentials, KMS for encryption keys, ACM for certificates, Secrets Manager for everything else — as a reference model that maps cleanly onto any cloud or on-prem stack, not an AWS-only quirk. When a tool genuinely spans categories, like Vault's PKI secrets engine, know which part of it you're using and why, instead of treating "Vault" as one undifferentiated bucket for anything sensitive.

Exam and interview notes

Interview Q: "Where's the actual line between PKI and secrets management?" A: "PKI is specifically about asymmetric key pairs, certificates, and chains of trust, with possession proven cryptographically. Secrets management is about safely storing, retrieving, and rotating opaque bearer credentials — passwords, API keys, tokens. AWS's own documentation makes the split explicit: its Secrets Manager guide tells you to use IAM for account credentials, KMS for encryption keys, and Certificate Manager for private keys and certificates — not Secrets Manager itself."

Interview Q: "How does IAM relate to PKI?" A: "IAM answers authorization — what can an already-authenticated identity do. PKI is one mechanism that can supply the authentication step underneath that, via certificates and mTLS. They're complementary layers, not the same layer — a correct IAM policy doesn't mean the authentication step it's relying on was actually done with proper certificate validation."

Recap
  • PKI proves identity cryptographically via key pairs and a CA signature; secrets management stores/rotates opaque bearer credentials; IAM decides what an already-authenticated identity may do.
  • AWS's own docs draw the line explicitly: IAM for account credentials, KMS for encryption keys, ACM for certificates, Secrets Manager for everything else — a model that generalizes beyond AWS.
  • Only two genuine overlaps exist: Vault's PKI secrets engine (a secrets tool that also acts as a CA) and cloud KMS/HSM (the shared key-protection layer under both PKI and secrets).
  • Proof-of-possession (PKI) credentials are structurally stronger than bearer (secrets/IAM) credentials — the private key is never transmitted to prove ownership.
  • Storing a certificate's private key in a generic secrets store, with no CA renewal lifecycle attached, is a common real cause of expiry outages.
