Cryptography Fundamentals: Encryption, Hashing, Signing, and Key Exchange

What you will learn

Four operations that get confused constantly — encryption, hashing, signing, and key exchange — solve four different problems, use different math, and are not interchangeable. You'll also meet symmetric vs. asymmetric encryption, the algorithms behind them (AES, RSA, ECC), and why a public/private key pair is the single idea the rest of this course is built on.

Why this matters

Lesson 1 ended with four problems: confidentiality, integrity, authentication, non-repudiation. This lesson gives you the actual tools that solve them — and if you mix up which tool solves which problem, every later lesson (CSRs, certificate fields, TLS handshakes, AD CS templates) will feel like memorized trivia instead of a coherent system. Get this one distinction right and the rest of the course clicks into place.

Simple explanation

Imagine four completely different physical actions: locking a box so only someone with the right key can open it (encryption), taking a fingerprint of a document so any change to it is detectable (hashing), signing a document with a seal only you could have made (digital signature), and agreeing on a secret handshake with someone in full view of a crowd without the crowd learning the handshake (key exchange). All four use "keys" and "math," which is exactly why people conflate them — but they answer different questions, and you can do any one without the others.

How it works

Symmetric vs. asymmetric encryption

Symmetric encryption uses one shared key for both locking and unlocking — fast, but both parties need the same secret key already, which brings back Lesson 1's problem (how do two strangers agree on a secret over an insecure channel?). AES is the standard symmetric algorithm in use today.

Asymmetric (public-key) encryption uses a mathematically linked pair of keys: whatever the public key locks, only the matching private key can unlock, and the private key is never shared. This solves the "strangers with no prior secret" problem — Alice can publish her public key anywhere, and anyone can encrypt a message to her that only she can decrypt. RSA and ECC (elliptic-curve cryptography) are the two dominant asymmetric families; Lesson 5 compares them directly.

In practice, TLS uses both: asymmetric crypto to solve the identity/key-exchange problem, then switches to fast symmetric encryption (AES) for the actual bulk data — you'll see this exact handoff in Stage E's TLS handshake lessons.

Hash functions

A hash function takes any input and produces a fixed-length fingerprint. Change one character of the input, and the fingerprint changes completely and unpredictably. Hashing is one-way — you can't reverse a hash back into its original input — and it uses no keys at all. Hashing alone proves a message wasn't altered; it proves nothing about who sent it. SHA-2 and SHA-3 are the current standard hash families (SHA-1 is broken and obsolete — never use it for anything security-relevant).

Digital signatures

A digital signature combines hashing with asymmetric encryption to solve authentication and integrity and non-repudiation at once: the sender hashes the message, then encrypts that hash with their private key. Anyone with the sender's public key can decrypt the signature back into the hash, independently hash the message themselves, and compare. If they match, three things are proven simultaneously: the message wasn't altered (integrity), it came from whoever holds that private key (authentication), and the sender can't credibly deny sending it (non-repudiation) — because only they hold that private key.

Key exchange

Key exchange solves a narrower, specific problem: how do two parties agree on a shared symmetric key, in full view of an eavesdropper, without ever transmitting that key itself? Diffie-Hellman (and its elliptic-curve variant, ECDH/ECDHE) solves this using math where each side can compute the same shared secret from public information, but an eavesdropper watching the exchange cannot. This is a distinct operation from encrypting a message or signing one — it produces a shared secret, not a locked message or a signature.

Architecture / diagram

ENCRYPTION (confidentiality)
  Alice's message ──[locked with Bob's PUBLIC key]──▶ only Bob's PRIVATE key opens it

HASHING (integrity only — no keys, no identity)
  Document ──[hash function]──▶ fixed-length fingerprint
  Change 1 byte ──[hash function]──▶ completely different fingerprint

SIGNING (integrity + authentication + non-repudiation)
  Alice: hash(message) ──[encrypt hash with Alice's PRIVATE key]──▶ signature
  Bob:   decrypt signature with Alice's PUBLIC key ──▶ compare to his own hash(message)
         match ──▶ proves Alice sent it, unaltered

KEY EXCHANGE (agreeing on a shared secret, in public)
  Alice: public info A ───────────────▶
                          ◀─────────── Bob: public info B
  Alice computes secret from (A, her private value, B)
  Bob   computes secret from (B, his private value, A)
  Both arrive at the SAME shared secret — Eve, watching A and B, cannot

Important terminology

  • Symmetric encryption — one shared key, both directions (e.g. AES).
  • Asymmetric encryption — a public/private key pair; what one locks, only the other unlocks (e.g. RSA, ECC).
  • Public key — safe to share with anyone.
  • Private key — never shared, ever (Stage O covers this in depth).
  • Hash function — one-way fingerprint, no keys involved (SHA-2, SHA-3).
  • Digital signature — a hash, encrypted with the signer's private key.
  • Key exchange — two parties deriving the same shared secret in public (Diffie-Hellman, ECDH/ECDHE).
  • Entropy — the unpredictability that makes a key hard to guess; keys generated from a weak or predictable random source are breakable regardless of algorithm strength.

Real-world example

A wax seal on an old letter is a physical digital-signature analogy: the sender presses a unique signet ring (their "private key") into wax. Anyone who has seen the seal before (knows the "public key" — what the seal looks like) can verify the letter came from that sender and wasn't reopened and altered. But the wax seal doesn't keep the letter's contents secret from anyone who intercepts it — that's a separate problem (encryption), solved by a different action (sealing the envelope itself, or writing in a cipher).

Hands-on lab

Compute a hash and observe the avalanche effect (no keys needed yet — key generation starts in Lesson 5):

# Hash a short string
echo -n "Alice pays Bob $100" | openssl dgst -sha256

# Change one character and hash again
echo -n "Alice pays Bob $900" | openssl dgst -sha256

Compare the two outputs. Expected result: completely different hashes, with no visible relationship to each other, despite the input differing by a single character. This is the property that makes hashing useful for detecting tampering — a forged message can't be quietly patched to also produce the original valid hash.

What can go wrong

The most common conceptual mistake: assuming a hash proves who sent something. It doesn't — hashing has no keys and no identity attached to it at all. A hash only proves a message matches a specific fingerprint; anyone (including an attacker) can compute the hash of anything, including a forged message. Only a signature (a hash encrypted with a private key) ties a message to an identity.

Troubleshooting

If two systems disagree on whether a signature is valid, the fault almost always traces to one of: the wrong public key being used to verify (mismatched key pair), the message being altered even slightly after signing (changes the hash, breaks the match), or a hash/signature algorithm mismatch between signer and verifier. Stage Q's Incident 7 ("certificate and private key do not match") is this same category of failure applied specifically to certificates.

Security considerations

Never reuse a symmetric key across unrelated purposes, and never treat a hash as a substitute for a signature when authentication matters — a checksum-only integrity check (common in older or poorly-designed systems) can be silently regenerated by an attacker who modifies both the message and its accompanying hash together. Only a signature, verified with a public key the verifier already trusts, resists this.

Production best practices

Use current, unbroken algorithms only: AES for symmetric encryption, RSA or ECC for asymmetric operations, SHA-2/SHA-3 for hashing, ECDHE for key exchange when forward secrecy matters (Stage E explains why). Never use SHA-1 or MD5 for anything security-relevant — both are cryptographically broken, a fact worth stating explicitly since older documentation and legacy systems still reference them as if current.

Exam and interview notes

Interview Q: "What's the difference between encryption, hashing, and signing?" A: "Encryption is reversible and provides confidentiality — you can decrypt it back to the original. Hashing is one-way and provides integrity only — no keys, no identity, just a fingerprint. Signing combines hashing with asymmetric encryption to prove integrity, authentication, and non-repudiation all at once, using the signer's private key. They solve three different problems and none of them substitutes for another."

Interview Q: "Why do we need key exchange if asymmetric encryption already lets two strangers communicate?" A: "Asymmetric encryption is computationally expensive for bulk data. Key exchange lets two parties agree on a fast symmetric key using asymmetric math, then switch to symmetric encryption for the actual traffic — this is exactly what happens in a TLS handshake."

Source

Recap
  • Encryption (reversible, confidentiality), hashing (one-way, integrity only, no keys), signing (hash + private-key encryption, proves identity), and key exchange (agreeing on a shared secret in public) are four distinct operations.
  • Symmetric encryption (AES) is fast but requires a pre-shared key; asymmetric encryption (RSA/ECC) solves that using a public/private key pair.
  • A digital signature proves integrity, authentication, and non-repudiation together — a plain hash proves none of those beyond "the content matches."
  • TLS uses asymmetric crypto to establish identity and a shared key, then symmetric crypto for the actual data — this pairing shows up throughout the rest of this course.
