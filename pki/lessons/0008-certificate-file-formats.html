Certificate File Formats: PEM, DER, PKCS#7, PKCS#12, JKS

What you will learn

The five formats you'll meet constantly in real PKI work — the difference between an encoding (PEM text vs. DER binary, which can wrap a certificate, a CSR, a private key, or a public key) and a container (PKCS#7, PKCS#12, JKS — bundles of several objects at once) — what each can and can't hold, how to tell them apart on sight, and which tool reads/writes each one.

Why this matters

"The file format is a container, not the certificate" trips up more beginners than almost anything else in PKI. A .pfx file containing a private key and a .p7b file containing zero private keys can both be handed to you as "the certificate" — confusing the two, or not knowing which one a given server expects, is one of the most common causes of a failed certificate installation (Stage J).

Simple explanation

Think of a certificate, a CSR, or a private key (the signed/unsigned X.509 and key structures from Lessons 6 and 10) as different kinds of letters, and PEM/DER as two ways to write any one of those letters down — typed out as readable text (PEM) or written in raw shorthand bytes (DER). PKCS#7, PKCS#12, and JKS are envelopes that can hold a whole stack of letters at once. Only some of those envelopes are built to safely carry the sender's own private letter (the private key) alongside the public ones — and, as you'll see below, "which format can technically contain a private key" and "which format is actually the letter itself, whichever one it is" turn out to be two different questions.

How it works

PEM — the readable, everywhere format

Base64-encoded text wrapped in -----BEGIN ...----- / -----END ...----- markers. Extensions vary (.pem, .crt, .cer, .key) but the content structure is identical — this is why extension alone is never reliable proof of what's inside; you always look at the actual header line.

-----BEGIN CERTIFICATE-----
MIIDXTCCAkWgAwIBAgIJAJC1...
-----END CERTIFICATE-----

PEM isn't one object type — it's a text wrapper that can hold a certificate, a CSR (Lesson 10), a private key, or a public key. The header line tells you which:

-----BEGIN CERTIFICATE-----          a certificate
-----BEGIN CERTIFICATE REQUEST-----  a CSR
-----BEGIN PRIVATE KEY-----          a PKCS#8 private key (RFC 5958) — today's default
-----BEGIN RSA PRIVATE KEY-----      a legacy PKCS#1 RSA-only private key
-----BEGIN ENCRYPTED PRIVATE KEY-----  a password-encrypted PKCS#8 private key
-----BEGIN PUBLIC KEY-----           a public key on its own

PEM is the default format OpenSSL reads and writes for all of these — certificates, CSRs, and keys alike — and it's the one you can safely paste into an email, a chat message, or a config file, since it's plain text — except when the header says PRIVATE KEY. A PEM private key is exactly as sensitive as the key itself, because it is the key, just Base64-encoded. This is also why the standard Apache and NGINX layout is two separate PEM files: server.crt (the certificate — safe to be public) and server.key (the private key — locked down to root-only file permissions). Same PEM encoding both times; the difference is entirely in which header is inside the file.

DER — the binary encoding underneath

DER (Distinguished Encoding Rules) is the raw binary ASN.1 encoding of any of the structures above — a certificate, a CSR, or a private/public key. A PEM file is, literally, DER bytes base64-encoded with header/footer lines added — there is no information difference between a PEM and its equivalent DER, only a text-vs-binary difference. That means a DER-encoded private key is just as real (and just as sensitive) as a PEM one — Windows tooling in particular sometimes hands you keys in DER rather than PEM. Windows tooling generally (IIS, certutil, the Windows cert store) commonly defaults to DER for certificates too, often with a .cer or .der extension — the same .cer extension PEM sometimes uses, which is exactly why you check content, not extension.

# Convert a certificate PEM to DER
openssl x509 -in cert.pem -outform DER -out cert.der

# Convert a certificate DER to PEM
openssl x509 -in cert.der -inform DER -outform PEM -out cert.pem

# The same conversion works for a private key, not just a certificate —
# and the DER output below is exactly as sensitive as key.pem was
openssl pkey -in key.pem -outform DER -out key.der

PKCS#7 (.p7b / .p7c) — a bundle of certificates, never a private key

PKCS#7 (per IETF RFC 2315, which is what OpenSSL's pkcs7 command implements) is a container for a chain of certificates — typically a leaf plus its intermediates — with no private key ever included. It's the format Windows and Java tooling commonly use to hand over "the certificate plus its chain" as one file, and it's Base64 (PEM-style) or binary (DER-style) just like a single certificate.

# View what certificates are inside a .p7b bundle
openssl pkcs7 -in bundle.p7b -inform DER -print_certs -noout

# Convert PEM p7b to individual PEM certs
openssl pkcs7 -in bundle.p7b -print_certs -out certs.pem

PKCS#12 (.pfx / .p12) — cert, chain, and key bundled and encrypted together

PKCS#12 is a password-protected binary container that bundles a certificate, its full chain, and the matching private key together into one file. It isn't the only format that can technically hold a private key (as you just saw, a plain PEM or DER file can too) — what makes PKCS#12 special is that it's purpose-built to carry the whole cert+chain+key combination as one password-encrypted unit, instead of as several loose files. It's what you hand to IIS, or export from one server to move a certificate+key pair to another, and it always deserves the same handling care as a raw private key file, because functionally it is one.

# Create a .p12 from a PEM cert + key
openssl pkcs12 -export -in cert.pem -inkey key.pem -out bundle.p12 -name "my-cert"

# Inspect a .p12's structure without exporting anything
openssl pkcs12 -in bundle.p12 -info -noout

# Extract everything back out to PEM
openssl pkcs12 -in bundle.p12 -out extracted.pem -noenc

JKS — the Java-specific keystore format

JKS (Java KeyStore) is Oracle's own proprietary keystore format, historically the default for Java/Tomcat deployments. Since JDK 9, PKCS#12 is Java's default keystore type, but JKS remains widely deployed in older and existing systems. A JKS (or PKCS#12) keystore file can hold two different kinds of entries: a private-key entry (a key plus its certificate chain) or a trusted-certificate entry (a certificate only, no key) — the file format alone doesn't tell you which one you've got; you have to look at the entry. JKS keystores (and PKCS#12 ones) are managed with Java's own keytool, not OpenSSL:

# List everything in a JKS keystore
keytool -list -keystore mykeystore.jks -storetype jks

# Import a CA certificate as a trusted entry
keytool -importcert -alias myCA -file ca-cert.cer \
  -keystore mykeystore.jks -storetype jks -trustcacerts

# List one entry in full detail
keytool -list -alias mykey -keystore mykeystore.jks -storetype jks -v

Important terminology

  • ASN.1 — the abstract data structure notation X.509 certificates are defined in; DER is one binary encoding of it.
  • Base64 — the text encoding PEM uses to represent binary DER bytes as printable characters.
  • Keystore — a container (PKCS#12 or JKS) that can hold private keys plus certificates together, always password-protected.
  • Truststore — a keystore used to hold only trusted CA certificates (no private keys) — often the same file format (JKS or PKCS#12) used for a different purpose.

Real-world example

A common real handoff: a public CA emails you a .p7b bundle containing your new leaf certificate plus the intermediate chain — no private key, because the CA never had your private key to begin with (you generated the CSR yourself, Lesson 10). You then combine that .p7b's certificates with your own private key — which has been sitting there the whole time as a plain PEM .key file, since that's what openssl req wrote out when you created the CSR — into a .pfx, because that's the format IIS needs for import. Understanding which format holds what makes this two-step handoff obvious instead of confusing.

Hands-on lab

Track B. Build a certificate, then move it through every format in this lesson:

# 1. Generate a cert + key (from Lesson 6's pattern)
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 \
  -keyout lab.key -out lab.pem -days 30 -noenc -subj "/CN=lab.example.com"

# Open lab.key in a text editor: it's PEM, same as lab.pem, just with a
# different header (BEGIN PRIVATE KEY instead of BEGIN CERTIFICATE) —
# same encoding, different object, very different sensitivity.

# 2. PEM -> DER and back
openssl x509 -in lab.pem -outform DER -out lab.der
openssl x509 -in lab.der -inform DER -outform PEM -out lab-roundtrip.pem
diff lab.pem lab-roundtrip.pem && echo "PEM round-trip: identical"

# 3. Bundle into PKCS#7 and view it
openssl crl2pkcs7 -nocrl -certfile lab.pem -out lab.p7b
openssl pkcs7 -in lab.p7b -print_certs -noout

# 4. Bundle cert+key into PKCS#12
openssl pkcs12 -export -in lab.pem -inkey lab.key -out lab.p12 -name "lab-cert" -passout pass:labpass123
openssl pkcs12 -in lab.p12 -info -noout -passin pass:labpass123

# 5. Import into a JKS keystore (requires a JDK's keytool)
keytool -importcert -alias lab -file lab.pem -keystore lab.jks -storetype jks \
  -storepass labpass123 -noprompt
keytool -list -keystore lab.jks -storetype jks -storepass labpass123

Expected result: the PEM round-trip is byte-identical; openssl pkcs7 -print_certs shows your certificate's subject; openssl pkcs12 -info shows both a certificate bag and a (shrouded, encrypted) key bag; keytool -list shows one trusted certificate entry with a SHA-256 fingerprint.

What can go wrong

Assuming a .cer file is always PEM (or always DER) is a common, real mistake — that extension is used for both encodings by different tools (Windows tends toward DER, many Linux/OpenSSL workflows toward PEM). Always check the file's actual header, or just try both -inform PEM and -inform DER, rather than guessing from the extension.

A second, easy-to-repeat mistake: assuming PEM or DER "can't" hold a private key because most of the PEM/DER files you handle day-to-day are certificates. They can — a PEM private key looks almost identical to a PEM certificate, just with a different header line, and it deserves exactly the same protection as a .pfx. The one structural rule in this lesson that always holds is narrower than "PEM/DER never have keys": PKCS#7 (.p7b) never carries a key. Every other format here can, depending on what's actually inside it.

Troubleshooting

If a tool rejects a certificate file with a parse or "unable to load" error, run file cert.cer or open it in a text editor first — if you see -----BEGIN CERTIFICATE-----, it's PEM; if it opens as unreadable binary, it's DER (or a PKCS#7/#12 container). Matching -inform/-outform to what's actually in the file resolves the large majority of "OpenSSL won't read my certificate" issues.

Security considerations

Treat any file with a -----BEGIN PRIVATE KEY----- or -----BEGIN RSA PRIVATE KEY----- header — PEM or its DER equivalent — exactly like a .pfx/.p12 file or a JKS keystore holding a private-key entry: all of them are the private key, just in different wrappers. In fact an unencrypted PEM/DER .key file is the least protected of the bunch, since it has no password of its own — file permissions are all that guard it, which is exactly why server.key on a Linux box should be root-only, mode 600. Never email a private key (or a .pfx/.p12) without an equally secure, separate channel for any password involved, and never commit one to source control (this applies even in a personal lab — build the habit now).

Production best practices

Standardize on PEM for anything text-based/version-controlled-adjacent (configs, automation) and PKCS#12 for anything that needs to move a private key between systems as one encrypted bundle — avoid JKS for new deployments where PKCS#12 is equally supported, since JDK 9+ already defaults to PKCS#12 and it isn't Java-proprietary. On Linux web servers, the standard layout is two separate PEM files — server.crt (certificate, world-readable) and server.key (private key, root-only) — which is exactly what Apache's SSLCertificateFile/SSLCertificateKeyFile and NGINX's ssl_certificate/ssl_certificate_key directives expect; don't reach for PKCS#12 there just because "that's the format with the key in it" — plain PEM already has the key, it's just not bundled or password-wrapped. Always verify a converted file with an inspection command (Lesson 7) immediately after conversion — never assume a format conversion succeeded silently.

Exam and interview notes

Interview Q: "Which of these formats can contain a private key?" A: "All of them except PKCS#7. PEM and DER are just encodings — either can hold a certificate, a CSR, a public key, or a private key, depending on which structure and header is actually inside that file. PKCS#12 and JKS are containers purpose-built to bundle a private key together with its certificate and chain, usually password-protected. Recap
  • PEM and DER are encodings, not object types — either one can hold a certificate, a CSR, a private key, or a public key; same data, text (Base64) vs. binary, no information difference between them.
  • PEM/DER private keys are normal and common — server.key next to server.crt is the standard Apache/NGINX layout. The only format in this lesson that structurally can never hold a private key is PKCS#7 (.p7b), which bundles a certificate chain only.
  • PKCS#12 (.pfx/.p12) bundles cert + full chain + private key together in one password-encrypted file — the standard way to move that whole combo between systems. JKS does the same for Java, holding either private-key entries or trusted-cert-only entries in one keystore.
  • JKS is Java's own proprietary keystore format, managed with keytool; PKCS#12 has been Java's default keystore type since JDK 9.
  • Never trust a file extension alone to identify format — check the actual header/content, since .cer is used ambiguously for both PEM and DER.
