Certificate File Formats: PEM, DER, PKCS#7, PKCS#12, JKS

What you will learn

The five container formats you'll meet constantly in real PKI work — what each one actually holds (public data only, or public plus private?), how to tell them apart on sight, and which tool reads/writes each one.

Why this matters

"The file format is a container, not the certificate" trips up more beginners than almost anything else in PKI. A .pfx file containing a private key and a .p7b file containing zero private keys can both be handed to you as "the certificate" — confusing the two, or not knowing which one a given server expects, is one of the most common causes of a failed certificate installation (Stage J).

Simple explanation

Think of the certificate itself (the signed X.509 structure from Lesson 6) as the letter, and these five formats as different kinds of envelopes: some hold just one letter as readable text, some hold it as raw bytes, some hold a whole stack of letters, and one specific envelope type is the only one ever allowed to also contain the matching private key.

How it works

PEM — the readable, everywhere format

Base64-encoded text wrapped in -----BEGIN ...----- / -----END ...----- markers. Extensions vary (.pem, .crt, .cer, .key) but the content structure is identical — this is why extension alone is never reliable proof of what's inside; you always look at the actual header line.

-----BEGIN CERTIFICATE-----
MIIDXTCCAkWgAwIBAgIJAJC1...
-----END CERTIFICATE-----

PEM is the default format OpenSSL reads and writes, and it's the one you can safely paste into an email, a chat message, or a config file, since it's plain text.

DER — the binary encoding underneath

DER (Distinguished Encoding Rules) is the raw binary ASN.1 encoding of a certificate. A PEM file is, literally, DER bytes base64-encoded with header/footer lines added — there is no information difference between a PEM and its equivalent DER, only a text-vs-binary difference. Windows tooling (IIS, certutil, the Windows cert store) commonly defaults to DER, often with a .cer or .der extension — the same .cer extension PEM sometimes uses, which is exactly why you check content, not extension.

# Convert PEM to DER
openssl x509 -in cert.pem -outform DER -out cert.der

# Convert DER to PEM
openssl x509 -in cert.der -inform DER -outform PEM -out cert.pem

PKCS#7 (.p7b / .p7c) — a bundle of certificates, never a private key

PKCS#7 (per IETF RFC 2315, which is what OpenSSL's pkcs7 command implements) is a container for a chain of certificates — typically a leaf plus its intermediates — with no private key ever included. It's the format Windows and Java tooling commonly use to hand over "the certificate plus its chain" as one file, and it's Base64 (PEM-style) or binary (DER-style) just like a single certificate.

# View what certificates are inside a .p7b bundle
openssl pkcs7 -in bundle.p7b -inform DER -print_certs -noout

# Convert PEM p7b to individual PEM certs
openssl pkcs7 -in bundle.p7b -print_certs -out certs.pem

PKCS#12 (.pfx / .p12) — the one format that can hold the private key

PKCS#12 is a password-protected binary container that can hold a certificate, its full chain, and the matching private key together — this is the only format in this lesson where that combination is normal and expected. It's what you hand to IIS, or export from one server to move a certificate+key pair to another, and it always deserves the same handling care as a raw private key file, because functionally it is one.

# Create a .p12 from a PEM cert + key
openssl pkcs12 -export -in cert.pem -inkey key.pem -out bundle.p12 -name "my-cert"

# Inspect a .p12's structure without exporting anything
openssl pkcs12 -in bundle.p12 -info -noout

# Extract everything back out to PEM
openssl pkcs12 -in bundle.p12 -out extracted.pem -noenc

JKS — the Java-specific keystore format

JKS (Java KeyStore) is Oracle's own proprietary keystore format, historically the default for Java/Tomcat deployments. Since JDK 9, PKCS#12 is Java's default keystore type, but JKS remains widely deployed in older and existing systems. JKS keystores (and PKCS#12 ones) are managed with Java's own keytool, not OpenSSL:

# List everything in a JKS keystore
keytool -list -keystore mykeystore.jks -storetype jks

# Import a CA certificate as a trusted entry
keytool -importcert -alias myCA -file ca-cert.cer \
  -keystore mykeystore.jks -storetype jks -trustcacerts

# List one entry in full detail
keytool -list -alias mykey -keystore mykeystore.jks -storetype jks -v

Architecture / diagram

Format        Holds private key?   Encoding         Typical tool
────────────────────────────────────────────────────────────────────
PEM           no                   text (base64)    openssl (default)
DER           no                   binary            openssl -inform/-outform DER
PKCS#7 (.p7b) no  (chain only)     text or binary    openssl pkcs7
PKCS#12 (.pfx/.p12)  YES           binary, encrypted openssl pkcs12
JKS (.jks)    optional (keystore)  binary, proprietary  keytool

Only PKCS#12 and JKS are ever expected to contain a private key.
PEM, DER, and PKCS#7 hold public certificate data only.

Important terminology

  • ASN.1 — the abstract data structure notation X.509 certificates are defined in; DER is one binary encoding of it.
  • Base64 — the text encoding PEM uses to represent binary DER bytes as printable characters.
  • Keystore — a container (PKCS#12 or JKS) that can hold private keys plus certificates together, always password-protected.
  • Truststore — a keystore used to hold only trusted CA certificates (no private keys) — often the same file format (JKS or PKCS#12) used for a different purpose.

Real-world example

A common real handoff: a public CA emails you a .p7b bundle containing your new leaf certificate plus the intermediate chain — no private key, because the CA never had your private key to begin with (you generated the CSR yourself, Lesson 10). You then combine that .p7b's certificates with your own private key (which you've had locally the whole time) into a .pfx, because that's the one format IIS needs for import. Understanding which format holds what makes this two-step handoff obvious instead of confusing.

Hands-on lab

Track B. Build a certificate, then move it through every format in this lesson:

# 1. Generate a cert + key (from Lesson 6's pattern)
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 \
  -keyout lab.key -out lab.pem -days 30 -noenc -subj "/CN=lab.example.com"

# 2. PEM -> DER and back
openssl x509 -in lab.pem -outform DER -out lab.der
openssl x509 -in lab.der -inform DER -outform PEM -out lab-roundtrip.pem
diff lab.pem lab-roundtrip.pem && echo "PEM round-trip: identical"

# 3. Bundle into PKCS#7 and view it
openssl crl2pkcs7 -nocrl -certfile lab.pem -out lab.p7b
openssl pkcs7 -in lab.p7b -print_certs -noout

# 4. Bundle cert+key into PKCS#12
openssl pkcs12 -export -in lab.pem -inkey lab.key -out lab.p12 -name "lab-cert" -passout pass:labpass123
openssl pkcs12 -in lab.p12 -info -noout -passin pass:labpass123

# 5. Import into a JKS keystore (requires a JDK's keytool)
keytool -importcert -alias lab -file lab.pem -keystore lab.jks -storetype jks \
  -storepass labpass123 -noprompt
keytool -list -keystore lab.jks -storetype jks -storepass labpass123

Expected result: the PEM round-trip is byte-identical; openssl pkcs7 -print_certs shows your certificate's subject; openssl pkcs12 -info shows both a certificate bag and a (shrouded, encrypted) key bag; keytool -list shows one trusted certificate entry with a SHA-256 fingerprint.

What can go wrong

Assuming a .cer file is always PEM (or always DER) is a common, real mistake — that extension is used for both encodings by different tools (Windows tends toward DER, many Linux/OpenSSL workflows toward PEM). Always check the file's actual header, or just try both -inform PEM and -inform DER, rather than guessing from the extension.

Troubleshooting

If a tool rejects a certificate file with a parse or "unable to load" error, run file cert.cer or open it in a text editor first — if you see -----BEGIN CERTIFICATE-----, it's PEM; if it opens as unreadable binary, it's DER (or a PKCS#7/#12 container). Matching -inform/-outform to what's actually in the file resolves the large majority of "OpenSSL won't read my certificate" issues.

Security considerations

Treat any .pfx/.p12 file, and any JKS keystore holding a private-key entry, with the same care as a raw private key — because functionally it is one, just password-wrapped. Never email a .pfx/.p12 file without an equally secure, separate channel for its password, and never commit one to source control (this applies even in a personal lab — build the habit now).

Production best practices

Standardize on PEM for anything text-based/version-controlled-adjacent (configs, automation) and PKCS#12 for anything that needs to move a private key between systems — avoid JKS for new deployments where PKCS#12 is equally supported, since JDK 9+ already defaults to PKCS#12 and it isn't Java-proprietary. Always verify a converted file with an inspection command (Lesson 7) immediately after conversion — never assume a format conversion succeeded silently.

Exam and interview notes

Interview Q: "What's the difference between PEM and DER?" A: "No information difference — DER is the binary ASN.1 encoding, PEM is that same binary data Base64-encoded as text with BEGIN/END header lines. Same certificate, two encodings."

Interview Q: "Which of these formats can contain a private key?" A: "PKCS#12 (.pfx/.p12) always can and usually does; JKS keystores can hold key entries too. PEM, DER, and PKCS#7 (.p7b) are certificate-only formats — a private key should never be found inside a .p7b."

Recap
  • PEM and DER are the same certificate data — text (Base64) vs. binary encoding — with no information difference between them.
  • PKCS#7 (.p7b) bundles a certificate chain but never a private key; PKCS#12 (.pfx/.p12) is the one format that normally carries cert + chain + private key together, password-protected.
  • JKS is Java's own proprietary keystore format, managed with keytool; PKCS#12 has been Java's default keystore type since JDK 9.
  • Never trust a file extension alone to identify format — check the actual header/content, since .cer is used ambiguously for both PEM and DER.
