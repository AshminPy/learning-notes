The TLS 1.3 Handshake, Step by Step

What you will learn

The exact message-by-message flow of a TLS 1.3 full handshake per RFC 8446 — ClientHello through Finished — what's encrypted and when, why TLS 1.3 needs only one round trip instead of TLS 1.2's two, what a HelloRetryRequest is and when it happens, and how 0-RTT resumption works and why it comes with a real security trade-off you need to know about before ever enabling it.

Why this matters

"TLS handshake failed" is one of the most common errors you'll troubleshoot in this field, and you cannot diagnose it by guessing — you have to know which specific message in the sequence failed to know what's actually wrong (protocol version mismatch, no common cipher, untrusted certificate, missing key share). This lesson gives you the exact sequence so that later, when Stage Q walks through real incidents like "unable to get local issuer certificate," you already know precisely where in this flow that failure occurs.

Simple explanation

A TLS 1.3 handshake is a negotiation with three jobs, done in one round trip: agree on cryptographic parameters, exchange enough key material for both sides to derive the same shared secret, and let the client verify the server is who it claims to be via its certificate. The single biggest change from TLS 1.2 is timing: the client sends its Diffie-Hellman key material in its very first message instead of waiting for the server to ask for it, so the server can compute the shared secret and start encrypting immediately — that one change is what collapses TLS 1.2's two round trips down to TLS 1.3's one.

How it works

The full 1-RTT handshake, per RFC 8446 Section 2

RFC 8446 groups the handshake into three phases. In the notation below, {} means "encrypted with handshake traffic keys" and * means "optional/situational" — both taken directly from the RFC's own Figure 1 notation:

Phase 1 — Key Exchange (ClientHello / ServerHello)

The client sends a ClientHello containing: the highest TLS version it supports (via the supported_versions extension — TLS 1.3 repurposed the old version field for backward-compatibility reasons and uses this extension as the real version negotiation mechanism), a list of cipher suites it supports, a key_share extension containing its (EC)DHE public key material for one or more supported groups, and signature_algorithms listing which signature schemes it can verify. This is the single biggest structural change from TLS 1.2: the client guesses which key-exchange group the server will pick and sends its key share speculatively, in the very first message, rather than waiting to be asked. The server picks a cipher suite and a matching group, sends back its own key_share in the ServerHello, and at that point both sides can independently compute the same shared secret — this is the moment that makes the rest of the handshake encryptable.

Phase 2 — Server Parameters ({EncryptedExtensions}, {CertificateRequest*})

Everything from this point forward in the handshake is encrypted using keys derived from that shared secret — this is the other headline change from TLS 1.2, where the certificate and everything after it traveled in plaintext. EncryptedExtensions carries any server extensions that aren't needed for cryptographic negotiation (like ALPN's negotiated protocol, covered in Lesson 21). If the server wants to authenticate the client too (mutual TLS, covered in Stage F), it sends an optional CertificateRequest here.

Phase 3 — Authentication ({Certificate*}, {CertificateVerify*}, {Finished})

The server sends its Certificate message (its X.509 certificate chain, Stage B), then a CertificateVerify message — a signature over the entire handshake transcript so far, made with the private key matching that certificate, proving the server actually holds the private key and isn't just replaying someone else's certificate. Then a Finished message, a MAC over the full transcript, proves the server's view of the handshake matches the client's and that nothing was tampered with in transit. If the client's certificate was requested, the client mirrors this with its own {Certificate}, {CertificateVerify}, and {Finished}. Once both Finished messages are sent and verified, the handshake is complete and both sides switch to application traffic keys — [Application Data] in the diagram — for the actual HTTP (or whatever protocol) traffic.

HelloRetryRequest — when the client's first guess is wrong

The client's speculative key_share in Phase 1 is a guess about which group the server prefers. If the server doesn't support any of the groups the client sent a key share for, it can't just fail the connection — instead it sends a HelloRetryRequest telling the client which group to use, the client sends a corrected ClientHello with a matching key_share, and the handshake continues. This costs one extra round trip on that specific connection (making it functionally similar to TLS 1.2's two round trips for that case only), but the handshake transcript is preserved, not restarted — RFC 8446 treats it as a continuation, not a fresh attempt.

0-RTT — resuming a previous connection with zero added latency

If the client has a previously negotiated Pre-Shared Key (PSK) from an earlier session with the same server (session resumption, unified under the PSK model in TLS 1.3 — this replaces TLS 1.2's separate session-ID and session-ticket mechanisms), it can send encrypted early data in its very first flight, before the server has responded at all:

Client                                              Server

ClientHello
+ early_data
+ key_share*
+ psk_key_exchange_modes
+ pre_shared_key
(Application Data*)              -------->
                                                        ServerHello
                                                 + pre_shared_key
                                                     + key_share*
                                             {EncryptedExtensions}
                                                + early_data*
                                                        {Finished}
                                  <--------
(EndOfEarlyData)
{Finished}                        -------->
[Application Data]               <------->      [Application Data]

  ()  = encrypted using the client's early traffic secret (0-RTT data)

This is genuinely zero added round trips for that early data — but it comes with a real, well-documented risk: because there's no live back-and-forth confirming freshness before that data is accepted, a captured 0-RTT ClientHello can be replayed by an attacker, and the server has no built-in way to tell a replay from the original request at the TLS layer. RFC 8446 is explicit that 0-RTT data does not have the same forward-secrecy and replay protection as the rest of the handshake, and it's why 0-RTT is generally recommended only for idempotent requests (safe to process more than once) — never for anything that changes state, like a payment or a password change.

Important terminology

  • ClientHello / ServerHello — the first message from each side, negotiating protocol version, cipher suite, and key-exchange group.
  • key_share — the extension carrying a side's ephemeral (EC)DHE public key material, sent speculatively by the client in TLS 1.3.
  • HelloRetryRequest — the server's message telling the client to resend ClientHello with a different key-exchange group, when the client's initial guess didn't match anything the server supports.
  • CertificateVerify — a signature over the handshake transcript proving the sender holds the private key matching the certificate it just presented.
  • Finished — a MAC over the full handshake transcript, confirming both sides agree on everything exchanged so far and detecting any tampering.
  • 0-RTT / early data — encrypted application data sent in the client's very first flight using a resumed PSK, with no replay protection at the TLS layer.
  • Forward secrecy — the property that a compromised long-term private key later cannot decrypt past sessions, guaranteed in TLS 1.3 because key exchange is always ephemeral (EC)DHE, never static RSA (Lesson 21 covers this in full).

Real-world example

Cloudflare's own account of shipping RFC 8446, published the day the RFC was finalized, frames the practical payoff plainly: TLS 1.2 needed "two additional round-trips between the browser and the server before encrypted data can be sent," and TLS 1.3's redesign — sending the (EC)DHE key share speculatively in the first message — lets the server "learn the shared secret and send encrypted data one round trip earlier." On a mobile connection with 100-200ms of round-trip latency, cutting one full round trip off every single new HTTPS connection is a measurable, user-visible difference at the scale of a service like Cloudflare's, not a theoretical improvement.

What can go wrong

A very common real failure is a client and server that simply don't share a common cipher suite or key-exchange group after a server-side hardening change (e.g. disabling older groups) — this surfaces as a generic "handshake failure" alert with no further detail from most clients, and the only way to actually diagnose it is to check what the client offered against what the server now accepts, usually with openssl s_client's verbose output or a packet capture. Another real one: a server that supports TLS 1.3 but is missing intermediate certificates in its chain will still complete the cryptographic handshake successfully (ServerHello through Finished all succeed) but the client will reject the connection at the certificate-verification step — this looks like a handshake problem but is actually a chain-of-trust problem (Stage D), a distinction worth keeping straight before you start troubleshooting the wrong layer.

Troubleshooting

When a TLS connection fails, identify exactly which phase failed before guessing at a fix: if the failure happens before any certificate is even presented, suspect protocol version or cipher/group mismatch (Phase 1). If the certificate is presented but rejected, the cryptographic handshake itself succeeded and the problem is trust-chain or hostname validation (Stage D/Lesson 16), not the TLS mechanics covered in this lesson. openssl s_client -connect host:443 -msg shows you the actual message sequence exchanged, which tells you precisely how far the handshake got before it stopped — always more reliable than a generic client error message alone.

Security considerations

Never enable 0-RTT for anything that isn't provably idempotent — RFC 8446 itself documents that early data has no replay protection at the TLS layer, meaning an attacker who captures a 0-RTT ClientHello can resend it and have the server process the same request again. If your application needs 0-RTT's latency benefit, replay protection has to be handled at the application layer (e.g. idempotency tokens), not assumed from TLS. Also confirm any server you operate genuinely completed the certificate/CertificateVerify authentication step and isn't just accepting whatever cryptographic handshake succeeds — a handshake that finishes without proper certificate validation on the client side provides confidentiality and integrity but no actual server authentication, which defeats a core purpose of TLS.

Production best practices

Prefer TLS 1.3 wherever both ends support it — one fewer round trip on every new connection is a real, compounding latency win at scale, not a marginal one. Keep TLS 1.2 available as a fallback only if you have a genuine legacy-client population that can't be upgraded (verify this with real traffic data, not assumption), and never re-enable TLS 1.0/1.1 (RFC 8996, Lesson 19) to chase compatibility — that trade isn't worth it in 2026. If you enable 0-RTT for performance, scope it explicitly to safe, idempotent endpoints only, and document that decision — don't let it become an implicit default across an entire service.

Exam and interview notes

Interview Q: "Why does TLS 1.3 need only one round trip while TLS 1.2 needs two?" A: "The client sends its (EC)DHE key share speculatively in the very first ClientHello, guessing which group the server will accept, instead of waiting for the server to ask for it. That lets the server compute the shared secret and start encrypting — including the certificate — one full round trip earlier than TLS 1.2, which negotiated the key-exchange method first and only exchanged key material afterward."

Interview Q: "What happens if the client's key_share guess is wrong?" A: "The server sends a HelloRetryRequest specifying the group it actually supports, the client resends ClientHello with a matching key_share, and the handshake continues using the preserved transcript — it costs one extra round trip on that connection only, it doesn't restart the handshake from scratch."

Interview Q: "What's the risk with TLS 1.3's 0-RTT mode?" A: "Early data sent in the client's first flight has no replay protection at the TLS layer — RFC 8446 documents this explicitly. An attacker who captures that first flight can resend it, and the server has no built-in way to distinguish it from the original. It should only be used for idempotent requests, with any replay protection handled at the application layer."

Recap
  • TLS 1.3's full handshake is one round trip: ClientHello (with a speculative key_share) → ServerHello + encrypted Certificate/CertificateVerify/Finished → client Finished → application data.
  • Everything after ServerHello is encrypted — the single biggest structural change from TLS 1.2, where the certificate traveled in plaintext.
  • A HelloRetryRequest happens when the client's guessed key-exchange group doesn't match what the server supports — it costs one extra round trip but preserves the transcript rather than restarting.
  • 0-RTT lets a resumed client send encrypted data in its very first flight with zero added round trips, but RFC 8446 is explicit that early data has no replay protection at the TLS layer — restrict it to idempotent requests only.
  • Diagnose handshake failures by phase: pre-certificate failures point to version/cipher/group mismatch; post-certificate rejections point to chain-of-trust or hostname validation, a different problem entirely.
