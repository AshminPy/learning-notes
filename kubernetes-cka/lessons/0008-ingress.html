Ingress → Service

A ClusterIP Service (Lesson 3) gives you a stable address, but only reachable inside the cluster's own network. Real users are outside it. Ingress is the last hop: a set of routing rules that gets traffic from the internet to the right Service based on hostname and path.

Mental model: Ingress is a building directory board in the lobby, not a receptionist. The board lists "Room 4B → Acme Corp," but the board itself doesn't walk anyone anywhere — someone (staff) has to actually read it and direct people. That predicts the exam's biggest Ingress trap: the board (the Ingress object) can be posted perfectly and still send nobody anywhere, if no one (an Ingress controller) is actually reading it.

The shape of an Ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  ingressClassName: nginx
  rules:
  - host: web.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-svc
            port:
              number: 80
  • host / path/pathType — what request this rule matches
  • backend.service — which Service (never a Pod directly) gets the traffic
  • ingressClassName — which controller should handle this Ingress

Why it's built this way: the Ingress API is deliberately just data — a routing spec, no implementation. That's what lets multiple different controllers (nginx, Traefik, a cloud load balancer) all implement the exact same object shape, so your YAML doesn't change if you switch controllers, only ingressClassName does.

Try it

Q1. You apply a correct Ingress. No traffic gets routed, no error anywhere. What's missing?

An Ingress controller. The Ingress object is only rules — a controller must be running to read them and configure a real proxy/load balancer.

Now write your own, by hand: an Ingress routing to a Service called web-svc on port 80, path /. Try before revealing.

Reveal the reference answer

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  ingressClassName: nginx
  rules:
  - host: web.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-svc
            port:
              number: 80

Common mistake: pointing an Ingress backend at Pods, or expecting it to load-balance on its own — it only ever points at a Service, and the Service still does the actual Pod selection from Lesson 3.

A controlled failure

Apply the Ingress above, even with no controller installed:

kubectl apply -f web-ingress.yaml
kubectl get ingress web-ingress

Predict first: will the ADDRESS column ever fill in without a controller? Observe: the object is created fine — kubectl get ingress shows it, no error — but ADDRESS stays empty forever. Same silent-failure shape as Lesson 3's empty endpoints: the object exists and looks harmless, the thing actually missing is invisible from the object itself.

Production best practices

Production note: real clusters standardize on one Ingress controller (commonly nginx or a cloud-managed one) cluster-wide, and TLS termination is configured on the Ingress itself (spec.tls) rather than in each backend app — centralizing certs at the edge instead of per-service.

Exam & interview notes

Directly scored under Services & Networking (20%).

Interview Q: "You apply an Ingress and it never gets an external address. What's your first check?" A: Whether an Ingress controller is actually installed and running — kubectl get pods -A looking for it — before assuming anything is wrong with the Ingress YAML itself.

Recap
  • Ingress routes outside traffic to Services by host/path — it never points at Pods directly, Lesson 3's Service still does that.
  • An Ingress does nothing without a separately-installed Ingress controller — the object applies cleanly either way.
  • ingressClassName picks which controller handles a given Ingress.

Confidence check — answer without looking back:

  • Why does the Ingress API stay separate from any specific controller's implementation?
  • When would you need more than one Ingress controller in a cluster?
  • What happens if you apply an Ingress with no matching controller installed?
  • How would you verify an Ingress is actually being served, not just accepted by the API server?
