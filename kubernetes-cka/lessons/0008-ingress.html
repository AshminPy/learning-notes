Ingress → Service

Why this matters

Every path so far in this course stops at the edge of the cluster. A Service gives your app a stable address, but nothing outside the cluster can reach a ClusterIP directly. Ingress is the piece that takes traffic from the internet — a browser hitting https://shop.example.com — and hands it to the right Service. Get it wrong and the failure mode is brutal: not a slow response, not a 500, but total silence. A perfectly correct Ingress YAML, applied to a cluster with no Ingress controller running, produces no error and routes zero traffic — the single most common "worked in my dev cluster, dead on arrival in prod" bug in real Kubernetes deployments, because tools like kind and Docker Desktop often ship a controller pre-installed and a bare self-managed or freshly-created cloud cluster does not.

Get the TLS side wrong and it's worse, because it fails quietly in the other direction: Ingress terminates HTTPS at the edge, not end-to-end. If you assume "TLS on the Ingress" means your traffic is encrypted all the way to the Pod, you've shipped plaintext across your internal network without realizing it — a real production risk in any environment that doesn't treat the pod network as fully trusted.

Mental model: an Ingress object is a routing table you hand to whichever controller is watching — it is not a router itself. Writing an Ingress is like filling out a request form and leaving it at an empty desk: the form only does something once a receptionist (the controller) is actually there to read it. This predicts something that trips people up constantly — the exact same Ingress YAML, byte-for-byte identical, can behave completely differently across clusters depending on which controller reads it. On a cluster running the GKE ingress controller, a rule provisions a real cloud load balancer. On a cluster running ingress-nginx, the identical rule configures an nginx reverse proxy instead. A pathType: ImplementationSpecific rule can even match differently on two controllers, because the Kubernetes spec explicitly leaves that path type's behavior up to whichever controller implements it. If "the same Ingress" ever behaves differently on two clusters, you didn't change the routing table — you changed who's reading it.

Core concepts

The shape of a rule

An Ingress is a list of rules. Each rule says: for this host and path, send traffic to this Service.

rules:
  - host: nginx.example.com
    http:
      paths:
        - path: /
          pathType: Prefix
          backend:
            service:
              name: nginx-service
              port:
                number: 80
  • host — the hostname this rule matches
  • path / pathType — the URL path, and how strictly it must match
  • backend.service — which Service, and which port, gets the traffic

Notice: an Ingress rule only ever points at a Service, never at Pods directly — the Service still does the work of finding healthy Pods by label selector, exactly as in Lessons 3 and 5.

Path matching: pathType and precedence

pathTypeMatching ruleExample
ExactMatches the URL path exactly, case-sensitive, including trailing-slash differences./api/v2 matches only /api/v2 — not /api/v2/ and not /api/v2/users.
PrefixMatches path element by element, split on /. Every element of the rule's path must be a full, exact match to the corresponding element of the request path — not a raw string prefix./order does not match /orders/5, because the element order is not the same string as the element orders.
ImplementationSpecificBehavior is defined by your Ingress controller, not the Kubernetes API — a controller can treat it as Prefix, Exact, or something stricter.The same rule can match different requests on nginx vs. GKE vs. Traefik.

Kubernetes gives you no explicit priority field for overlapping rules — precedence is entirely positional and length-based: the longest matching path wins; if two matching paths are equally long, the one listed first in spec.rules wins. This exact rule is what causes the incident in the Failure scenario below, so it's worth memorizing precisely, not approximately.

TLS termination

Add a tls block to secure a host over HTTPS. The Ingress API supports exactly one TLS port — 443 — and terminates TLS at the ingress point itself: traffic from the client to the controller is encrypted, but traffic from the controller onward to your Service and Pods is plain HTTP. If you list multiple hosts under tls, the controller multiplexes them over that same port 443 using the hostname carried in the TLS handshake's SNI extension — provided the controller supports SNI.

spec:
  tls:
  - hosts:
      - foo.bar.com
    secretName: testsecret-tls
  rules:
  - host: foo.bar.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: Service1
            port:
              number: 80

The Secret named in secretName must be type kubernetes.io/tls and contain exactly two keys: tls.crt (the certificate) and tls.key (the private key). The certificate must cover the host you listed, or clients see a certificate mismatch even though the Ingress itself applied cleanly.

Default backend

If a request doesn't match any rule's host and path, where does it go? An Ingress with no rules at all sends everything to a single spec.defaultBackend. If you do specify rules but a particular request matches none of them, the real behavior is more precise than people assume: if defaultBackend is set, unmatched requests go there; if it isn't set, what happens to unmatched requests is left entirely to your Ingress controller — commonly a generic 404 from the controller's own default backend, but that's a controller convention, not a Kubernetes API guarantee.

spec:
  defaultBackend:
    service:
      name: default-http-backend
      port:
        number: 80

IngressClass: which controller reads this Ingress

The trap: an Ingress is only routing rules. It does nothing by itself. The Kubernetes docs say this outright: "You must have an Ingress controller to satisfy an Ingress. Only creating an Ingress resource has no effect." Apply an Ingress with no controller installed, and nothing happens — no error, just silence.

spec.ingressClassName tells Kubernetes which controller should read a given Ingress. It names an IngressClass object:

apiVersion: networking.k8s.io/v1
kind: IngressClass
metadata:
  name: external-lb
spec:
  controller: example.com/ingress-controller

Each installed controller watches only for Ingresses whose ingressClassName matches one of "its" IngressClasses. Omit ingressClassName entirely and Kubernetes falls back to whichever IngressClass is marked default with the ingressclass.kubernetes.io/is-default-class: "true" annotation — if no class is marked default, an Ingress with no class named just sits there, unclaimed, by design. The older kubernetes.io/ingress.class annotation did this same job before ingressClassName existed; it's deprecated, but you'll still see it in older manifests.

One more fact worth knowing early: the Ingress API is frozen — "no further changes or updates" per the Kubernetes docs — and the project now recommends the newer Gateway API instead. Ingress isn't going away or being removed, but it's also not where new routing features will land. Lesson 21 covers Gateway API in full; the Decision guide below only previews when you'd reach for it.

Production example

Production note: real clusters standardize on exactly one Ingress controller and mark exactly one IngressClass as the cluster default, rather than letting every team pick per Ingress. A common shape: the platform team installs ingress-nginx once, cluster-wide, creates an IngressClass named nginx, and marks it default so application teams can omit ingressClassName entirely and their Ingress "just works" without anyone needing to know a controller is even involved. For TLS, most real clusters don't hand-manage tls.secretName Secrets manually — they run cert-manager, which watches Ingress objects (commonly via an annotation like cert-manager.io/cluster-issuer) and automatically requests, renews, and stores a valid certificate in the exact Secret your spec.tls already points at. This is a widely-used pattern, not an exam requirement — the CKA exam only expects you to know the raw Ingress, TLS, and IngressClass mechanics above.

Hands-on exercise

Objective

Prove to yourself that a typo in ingressClassName fails silently — no error, no warning, just an Ingress that never routes anything — then fix it.

Scenario

You've installed ingress-nginx (its IngressClass is named nginx) and want to expose an existing app. You write the Ingress from memory and fat-finger the class name.

Environment assumptions

A kind/minikube cluster with ingress-nginx installed and an IngressClass literally named nginx (confirm with kubectl get ingressclass before starting). No existing Ingress named demo-ingress.

Commands

kubectl create deployment demo --image=nginx:1.29
kubectl expose deployment demo --port=80 --name=demo-service

cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo-ingress
spec:
  ingressClassName: ngnix
  rules:
  - host: demo.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: demo-service
            port:
              number: 80
EOF

kubectl get ingress demo-ingress

Expected result

kubectl apply succeeds with no error or warning — the API server never checks that ingressClassName refers to a real IngressClass. kubectl get ingress demo-ingress shows the CLASS column as ngnix (the typo, printed as literal text) and the ADDRESS column stays empty, because no controller claims a class it doesn't recognize.

Verification

Fix the typo (ngnix → nginx), reapply the same manifest, and re-run kubectl get ingress demo-ingress. Within a few seconds the ADDRESS column should populate with the controller's external IP or hostname — that transition from empty to populated is the actual proof the controller picked it up, not just that the object exists.

Common failure

Assuming kubectl apply returning success means the Ingress is live. It only means the YAML was syntactically valid — it says nothing about whether any controller is actually watching it.

Troubleshooting

Run kubectl get ingressclass and compare its NAME column, character for character, against your Ingress's ingressClassName. Case and spelling both matter — there's no fuzzy matching.

Cleanup / rollback

kubectl delete ingress demo-ingress --ignore-not-found
kubectl delete service demo-service --ignore-not-found
kubectl delete deployment demo --ignore-not-found

Production lesson

The API server will happily accept a typo as if it were valid, forever, until someone notices traffic isn't flowing. Treat "kubectl apply succeeded" as proof the YAML parsed — never as proof an Ingress is actually doing what you intended.

Failure scenario

A realistic incident built on the exact precedence rule from Core concepts above.

  1. 14:02 Marketing reports the new promo landing page at https://shop.example.com/ shows the regular storefront homepage instead of the promo page they just launched.
  2. 14:04 On-call port-forwards straight to the Service — kubectl port-forward svc/promo-service 8080:80 — and curls it directly. The promo page loads fine; the Service and its Pods are healthy.
  3. 14:07 On-call runs kubectl get ingress shop-ingress -o yaml and finds the rules list has grown: a path: /checkout rule, then a path: / rule pointing at storefront-service (added months ago), then a second path: / rule pointing at promo-service — appended to the end of the list an hour ago, in the same change that shipped the promo page, instead of replacing anything.
  4. 14:10 Root cause identified: per the pathType precedence rule, when two paths match a request with equal specificity, the rule that appears first in spec.rules wins. The storefront-service "/" rule was written first, months ago, so it wins for every request to "/" — the new promo-service "/" rule can never fire, no matter where it sits in the list.
  5. 14:14 Fix applied: reordering does nothing here, since both rules are equally specific catch-alls. The real fix is to scope the promo page to its own path, /promo, pathType: Prefix — a longer, more specific match that correctly takes precedence over the storefront catch-all regardless of list order.
  6. 14:19 Verified: curl -H "Host: shop.example.com" http://<ingress-ip>/promo returns the promo page; curl -H "Host: shop.example.com" http://<ingress-ip>/ still returns the storefront homepage, unaffected.

Troubleshooting workflow

The general method, applied to "my Ingress isn't routing traffic":

  1. Confirm the symptom. Curl the exact host and path from outside the cluster and note the precise failure — connection refused, timeout, wrong content, or a 404/503 from the controller. Each points to a different layer.
  2. Define scope. kubectl get ingress -A — is this one rule on one Ingress, every rule on this Ingress, or every Ingress in the cluster? A cluster-wide failure points at the controller itself, not your YAML.
  3. Check recent changes. kubectl get ingress <name> -o yaml against the last-known-good version — was a rule added, reordered, or a class name edited?
  4. Confirm the controller is running. kubectl get pods -n <controller-namespace> (for example ingress-nginx). If it isn't Running, nothing downstream of this step matters.
  5. Confirm the IngressClass. kubectl get ingressclass and compare, character for character, against .spec.ingressClassName. If it's omitted, confirm a class is actually marked default.
  6. Inspect the Ingress's own state. kubectl describe ingress <name> — read the Events section and check .status.loadBalancer. An empty address usually means no controller ever claimed this Ingress.
  7. Check the backend Service and its endpoints. kubectl get endpoints <service-name>. An Ingress pointing at a Service with zero endpoints (bad selector, Pods not Ready) returns a 502/503 from the controller — that's a Service-layer problem, not an Ingress routing problem.
  8. Check DNS. Does the hostname in your rule actually resolve to the controller's external IP or hostname? Compare dig <host> against kubectl get svc -n <controller-namespace>'s EXTERNAL-IP. A stale DNS record is a very common "it was working yesterday" cause.
  9. Form and test one hypothesis at a time. For example: "the new rule's path is shadowed by an earlier, equally-specific one." Isolate Ingress-layer from Service-layer by testing the Service directly (port-forward or in-cluster curl), bypassing the Ingress entirely.
  10. Fix, verify from outside the cluster, then document. Confirm the real client path works, not just kubectl output — then record the root cause and add a review check (no duplicate catch-all paths, a lint rule for ingressClassName) so the same mistake doesn't recur.

Security note: TLS termination at the Ingress means the controller decrypts your HTTPS traffic and forwards it as plain HTTP to reach your Service and Pods — this is exactly how the API is documented to behave. That plaintext travels across your cluster's pod network. On most clusters that's an acceptable trust boundary, since the pod network is private — but in a regulated environment, a multi-tenant cluster, or any zero-trust network policy model, "TLS on the Ingress" is not the same claim as "encrypted end-to-end." If plaintext behind the edge is unacceptable, you need re-encryption to the backend or a service mesh — the core Ingress API has no built-in mechanism for that.

Reliability note: a single Ingress controller is the front door for every external request into the cluster. If you run one controller replica and it goes down — a crash, an OOM kill, a bad rollout — every Ingress-routed Service becomes unreachable from outside at once, even though every backend Pod stays perfectly healthy. This is a textbook single point of failure: run the controller with multiple replicas and a PodDisruptionBudget, and treat its health as a top-tier cluster SLO, not an implementation detail.

Common mistake: applying an Ingress and assuming it's live because kubectl didn't error. The API server accepts a syntactically valid Ingress even when no controller exists, or when ingressClassName points at a class nobody installed — check that the controller is running and that .status.loadBalancer actually populates, not just that kubectl apply succeeded.

Common mistake: mismatching pathType. Exact requires a byte-for-byte match and never matches sub-paths; Prefix matches whole path segments, not a raw string prefix (/order does not match /orders); ImplementationSpecific behavior is defined by whichever controller you run, not by the Kubernetes API — the same rule can behave differently on two clusters.

Common mistake: writing a second "catch-all" rule for the same host expecting the newest one to win. It won't — equally-specific paths are resolved purely by list order, first-defined wins, until someone notices and either reorders or rescopes them (see the Failure scenario above).

Decision guide

OptionUse whenAvoid whenTrade-off
IngressStandard HTTP(S) host/path routing to many Services behind one entrypoint; broad controller support; what the CKA exam testsYou need non-HTTP protocols, or a clean split between infra-owned entrypoints and app-owned routesThe API is frozen — "no further changes or updates" — controller-specific annotations plug gaps but aren't portable
Gateway API (Lesson 21)Same routing needs, plus a portable, actively-developed API with a real separation between infra-managed Gateways and app-managed RoutesYour controller doesn't support it yet, or Ingress's simpler single-object model already covers your caseMore objects to learn (GatewayClass / Gateway / HTTPRoute) — full detail deferred to Lesson 21

Default recommendation: use Ingress for HTTP(S) routing today — it's what's tested on the CKA exam and what nearly every controller supports — but expect new clusters to lean increasingly on Gateway API, since the Kubernetes project has explicitly frozen the Ingress API and recommends Gateway API for anything new.

Knowledge check

Q1. You apply a correctly-written Ingress to a fresh cluster. No traffic gets routed, and kubectl showed no error. What's missing?

An Ingress controller. The Ingress object is only routing rules — a controller has to be running to read them and configure a real proxy or load balancer to enforce them.

Q2. Which field names the IngressClass — and therefore the controller — that should handle a given Ingress?

spec.ingressClassName. If it's omitted, Kubernetes falls back to whichever IngressClass carries the ingressclass.kubernetes.io/is-default-class: "true" annotation.

Q3. One Ingress has two rules for the same host: path: /api (Prefix) and path: / (Prefix). A request arrives for /api/users. Which rule wins?

A. The longest matching path always wins first — list order only breaks ties between paths of equal length, and /api is longer than /.

Q4. You set pathType: Prefix with path: /order. A request arrives for /orders/5. Does this rule match?

C. Prefix matching is done element by element, split on / — the element order is not an exact match for the element orders, so the rule does not match at all.

Q5. In an Ingress tls block, what two keys must the referenced Secret contain?

tls.crt and tls.key — the certificate and private key. The Secret itself must be of type kubernetes.io/tls.

Production challenge

Objective

Diagnose and fix a real pathType precedence bug in a multi-rule Ingress, using only what this lesson covered — no extra hints.

Scenario

A teammate says: "I added a new rule so /api/v2/* hits the new api-v2-service backend, but every request under /api/v2/ still hits the old api-service." Here's the Ingress they applied:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
spec:
  ingressClassName: nginx
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
      - path: /api/v2
        pathType: Exact
        backend:
          service:
            name: api-v2-service
            port:
              number: 80

Environment assumptions

A kind/minikube cluster with ingress-nginx installed (IngressClass nginx already exists). Build two backends you can tell apart:

kubectl create deployment api-service --image=nginx:1.29
kubectl expose deployment api-service --port=80
kubectl create deployment api-v2-service --image=nginx:1.29
kubectl expose deployment api-v2-service --port=80
kubectl exec deploy/api-service -- sh -c 'echo API-V1 > /usr/share/nginx/html/index.html'
kubectl exec deploy/api-v2-service -- sh -c 'echo API-V2 > /usr/share/nginx/html/index.html'

Apply the Ingress above as api-ingress.

Commands

curl -H "Host: api.example.com" http://<ingress-ip>/api/v2/users
curl -H "Host: api.example.com" http://<ingress-ip>/api/v2
kubectl describe ingress api-ingress

Expected result

Both curls return API-V1 — never API-V2 — no matter what's under /api/v2, even though the second rule's backend is api-v2-service.

Verification

Change the second rule's pathType from Exact to Prefix, leaving everything else identical, reapply, and repeat both curls plus a third: /api/orders. /api/v2 and /api/v2/users should now both return API-V2, and /api/orders should still return API-V1. That three-way result is the real proof — the fix didn't break the original rule.

Common failure

Concluding the bug is "rule order" and swapping the two rules instead of fixing pathType. Reordering does nothing here — the longest matching path always wins regardless of position; order is only a tie-breaker between equally-specific matches. The real defect is that Exact never matches sub-paths, so /api/v2/users was never a candidate for the second rule at all — it fell through to the only rule that did match: /api.

Troubleshooting

If curl hangs or refuses to connect at all, that's a Lesson-8-basics problem (no controller, wrong IngressClass, wrong external IP) — work through the Troubleshooting workflow above first, not this pathType bug.

Cleanup / rollback

kubectl delete ingress api-ingress --ignore-not-found
kubectl delete deployment api-service api-v2-service --ignore-not-found
kubectl delete service api-service api-v2-service --ignore-not-found

Production lesson

Exact vs. Prefix looks like a one-word typo in code review, but it silently reroutes an entire class of requests to the wrong backend with no error anywhere — not from kubectl apply, not from the controller, not from the app. The only signal is behavioral: the new backend never receives traffic. Curl any new Ingress rule directly before trusting it, the same way you'd never merge code without running it.

Recap
  • An Ingress is a routing table for whichever controller reads it — it does nothing without one, and the same YAML can behave differently across controllers.
  • pathType: Exact (byte-for-byte), Prefix (matches full path segments, not raw substrings), ImplementationSpecific (controller decides).
  • Overlapping paths: the longest match wins; equal-length matches are resolved by list order, first-defined wins.
  • TLS terminates at the Ingress — traffic to your Service and Pods is plain HTTP after that point.
  • An unmatched request goes to spec.defaultBackend if set; otherwise, handling is entirely up to the controller.
  • ingressClassName picks the controller; a typo or missing class fails silently, with no API-level validation.
