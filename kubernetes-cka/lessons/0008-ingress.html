Kubernetes / CKA — Lesson 8 of 17

Ingress → Service

Lesson 5 gave a Deployment a stable ClusterIP Service. That Service is reachable from inside the cluster — other Pods can hit it by name — but it has no path in from outside. This lesson is about that last hop: how traffic from outside the cluster reaches the right Service.

Tied to your mission: Services & Networking is 20% of the exam, and the current CNCF curriculum (v1.35) lists both "know how to use Ingress controllers and Ingress resources" and "use the Gateway API to manage Ingress traffic" as separate competencies — so Ingress is still directly examinable even though your day job runs on Gateway API. More on that at the end.

The mental model — why Ingress exists on top of Service

Start from what a Service alone gives you, and where each type stops being enough:

  • ClusterIP (the default, and what you built in Lesson 5) — has an IP that only exists inside the cluster's network. Nothing outside the cluster can reach it at all, full stop.
  • LoadBalancer — provisions a real cloud load balancer (on GKE, an actual forwarding rule + external IP) dedicated to that one Service. It works, but every LoadBalancer Service is its own billable cloud resource. Ten HTTP services behind ten LoadBalancers is ten load balancers, most of them sitting mostly idle.

Ingress solves the LoadBalancer problem for HTTP(S) traffic specifically: one entry point, one external IP, one load balancer — and it routes incoming requests to many different Services behind it based on the hostname and path in the request. Instead of ten load balancers, you run one, and Ingress rules decide which Service each request goes to.

The single most important thing in this lesson: an Ingress resource is only a set of routing rules. It is not, itself, a running process, a proxy, or a load balancer. Kubernetes stores your Ingress object in etcd the same as any other object — but nothing reads it and acts on it unless something called an Ingress controller is also running in the cluster, watching Ingress objects and actually configuring a proxy or cloud load balancer to match. "I applied an Ingress and nothing happened" is almost always "there is no Ingress controller installed" — the resource did exactly what it's supposed to do, which is nothing by itself.

GKE Autopilot, which you run daily, ships a default Ingress controller (GKE's own, backed by Google Cloud Load Balancing) — which is likely why you've never hit this gap in production. On a bare kubeadm cluster (closer to what the exam gives you), there usually isn't one until you install it (e.g. ingress-nginx). That's the trap: the manifest can be perfect and still do nothing.

The shape of an Ingress

An Ingress is a list of rules. Each rule says: for this host, when the request path matches this path, send it to this backend Service.

  • rules[].host — the hostname to match (e.g. shop.example.com). Omit it and the rule matches any host.
  • rules[].http.paths[].path + pathType — the URL path to match, and how strictly (Exact, Prefix, or ImplementationSpecific).
  • rules[].http.paths[].backend.service.name and backend.service.port.number — which Service, and which of its ports, gets the traffic that matches.

Notice what's not in there: no Pod IPs, no Deployment name. An Ingress rule only ever points at a Service — the same indirection you already trust from Lesson 5. The Ingress hands off to the Service, and the Service does what it always does: match its selector against Pod labels.

ingressClassName — which controller handles this Ingress

A cluster can have more than one Ingress controller installed at once (e.g. ingress-nginx for internal traffic, GKE's controller for public traffic). spec.ingressClassName is how a given Ingress object says which controller is responsible for it — it names an IngressClass object, which in turn maps to a specific controller implementation. Leave it unset and the cluster falls back to whichever IngressClass is marked default (if any) — same "there has to be a default, or nothing happens" trap as StorageClass in Lesson 7.

Try it first — before reading on

Q1. You write and apply a correct Ingress manifest. Nothing happens — no traffic is routed. What is the most likely reason, and what actually needs to exist in the cluster for an Ingress resource to do anything at all?

An Ingress controller must be running in the cluster. The Ingress object is just a set of routing rules stored in etcd — it does nothing by itself. A controller has to be watching Ingress objects and configuring a real proxy/load balancer to match them. No controller = a perfectly valid Ingress that does nothing.

Q2. What field tells Kubernetes which Ingress controller should handle a given Ingress, and what does that field actually point at?

spec.ingressClassName — it names an IngressClass object, which in turn maps to a specific controller implementation. Without it (and without a default IngressClass configured), it's ambiguous which controller, if any, should pick up the Ingress.

Q3. Why would you reach for Ingress instead of just giving every Service a type: LoadBalancer?

Every LoadBalancer Service provisions its own dedicated cloud load balancer — expensive and wasteful when you have many HTTP services. Ingress gives you one entry point (one load balancer, in front of the Ingress controller) that routes to many Services behind it based on hostname/path.

Now build it — in your terminal, not here

Write an Ingress by hand, no copy-paste, that routes a hostname to the nginx-service Service from Lesson 5. Requirements only:

  • kind: Ingress, API group networking.k8s.io/v1
  • an ingressClassName (use nginx, or whatever controller your cluster actually has installed — check with kubectl get ingressclass)
  • one rule with a host of your choosing (e.g. nginx.example.com — it doesn't need to resolve anywhere real for this exercise)
  • under that host, one path rule: path /, pathType: Prefix
  • a backend pointing at nginx-service, port 80 — the same name and port you gave the Service in Lesson 5

Don't peek at the answer below until you've written something.

Reveal the reference answer

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: nginx.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx-service
                port:
                  number: 80

Check it field-by-field: does backend.service.name match the Service's metadata.name exactly? Does backend.service.port.number match a port the Service actually exposes? Those two links are where this breaks in practice — the Ingress side is almost never the bug, the reference to the Service is.

Ingress vs. Gateway API — what the exam actually tests

You already know Gateway API from GKE Autopilot at work — it's the newer, more expressive replacement for Ingress (separate GatewayClass/Gateway/HTTPRoute objects instead of one flat Ingress resource, with cleaner support for things like traffic splitting). Verified directly against the official CNCF CKA Curriculum v1.35 (the current exam version): the Services & Networking domain lists both "know how to use Ingress controllers and Ingress resources" and "use the Gateway API to manage Ingress traffic" as separate, explicit competencies. So the exam still tests this older Ingress API in its own right — it has not been dropped or folded into Gateway API coverage — even though your day job runs on the newer one. Gateway API itself is a later lesson.

Recap
  • ClusterIP isn't reachable from outside the cluster at all. LoadBalancer gives every Service its own cloud load balancer — works, but expensive at scale. Ingress is one entry point that routes by host/path to many Services behind it.
  • An Ingress resource is only routing rules. It does nothing without an Ingress controller running in the cluster to implement it — "I applied it and nothing happened" almost always means no controller.
  • rules[].host, rules[].http.paths[].path, and backend.service.name/port define the routing. An Ingress rule only ever points at a Service, never at Pods directly.
  • ingressClassName picks which controller (via its IngressClass) handles a given Ingress, when a cluster runs more than one.
  • Both classic Ingress and Gateway API are explicitly in the current (v1.35) CKA curriculum — this lesson covers the one still most likely to appear in manifest-writing form.
