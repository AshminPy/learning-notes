Pod with labels

A Pod already has a name. A label is different — it's extra key/value metadata you stick on top, like tier: frontend. A Pod can carry many labels at once.

Simple example: think of labels like sticky notes on a box. The box has one shipping name. But you can stick many notes on it too — "fragile", "blue-team", "v2" — and other people find boxes by reading notes, not names.

Labels in a manifest

apiVersion: v1
kind: Pod
metadata:
  name: my-nginx
  labels:
    app: my-nginx
    tier: frontend
spec:
  containers:
    - name: nginx
      image: nginx

Labels live under metadata.labels — nothing in spec changes.

Why labels matter

Other objects — Services, Deployments — never point at a Pod by name. They use a selector: a set of key/value pairs matched against labels, live. Any Pod whose labels match gets picked up. Wrong or missing labels means nothing matches, silently.

  • kubectl get pods --show-labels — show every label
  • kubectl get pods -l tier=frontend — filter by a label

Labels are for selecting — that's why they're small and restricted. Info you never select on (a git commit hash, a contact) belongs in an annotation instead.

Try it — before looking below

Q1. Under which top-level field of a Pod manifest do labels live?

metadata.labels — a map of key/value pairs.

Now write your own

Take the Lesson 1 Pod manifest and add labels to it — by hand. Write:

  • the same Pod: name my-nginx, container nginx running image nginx
  • two labels: app: my-nginx and tier: frontend

Apply it, then check with kubectl get pods --show-labels. Try it before you look below.
