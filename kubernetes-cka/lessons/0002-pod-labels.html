Pod with labels

A label is not a name. A Pod already has one name (metadata.name), and that's unique and fixed. Labels are extra key/value metadata you attach on top — arbitrary tags like tier: frontend or release: canary — and a Pod can carry many of them at once.

Tied to your mission: Lesson 3 introduces a Service. A Service never points at a Pod by name — it points at a label selector, and every Pod whose labels match gets traffic. If the labels are wrong or missing, the Service finds nothing, and nothing in the logs will tell you why unless you already understand this. This is the single most important concept to nail before that lesson.

The mental model

Labels exist so that other objects — Services, Deployments, ReplicaSets, NetworkPolicies — can find a group of Pods without hardcoding names. The object doing the finding carries a selector (a set of key/value pairs, or expressions like in / notin / exists), and Kubernetes matches it against every object's labels live, continuously. Add a label that matches, the Pod is in the group. Remove it, the Pod falls out — no restart needed.

Name identifies one object. Labels group many. Everything from Lesson 3 onward — Service, Deployment, NetworkPolicy — works by matching labels, never by matching names.

Syntax rules (this will bite you if you skip it)

A label key is [optional-prefix/]name. The name part: max 63 characters, must start and end with an alphanumeric, and can contain -, _, . in between. The optional prefix must be a DNS subdomain, max 253 characters, and the kubernetes.io/ and k8s.io/ prefixes are reserved for core Kubernetes components — don't use them on your own objects. A label value follows the same character rules and can be empty.

Reading labels with kubectl

  • kubectl get pods --show-labels — adds a column showing every label on each Pod (hidden by default)
  • kubectl get pods -l tier=frontend — filters to only Pods matching that label (equality-based)
  • kubectl get pods -l 'environment in (production,qa)' — filters using a set-based expression

Labels vs. annotations, briefly

Both are key/value metadata under metadata. The difference is purpose: labels are for selection — that's why their charset is restricted and small. Annotations are for anything else you want to attach to an object (build info, a git commit hash, a contact) — up to 256 KiB, no charset restriction, but selectors can't query them. If you ever catch yourself trying to "select" on something, it belongs in a label, not an annotation.

Try it first — before reading on

Q1. Under which top-level field of a Pod manifest do labels live?

metadata.labels — a map of key/value pairs nested inside metadata, alongside name

Q2. Why do labels matter for what comes next in this course (a Service pointing at a Pod)?

A Service never targets a Pod by name — it uses a label selector, and traffic goes to every Pod whose labels match. Wrong or missing labels mean the Service finds zero Pods, with no error to point you at why.

Q3. What's the key difference in purpose between a label and an annotation?

Labels are for identifying/selecting objects (small, restricted charset, queryable with selectors). Annotations are for arbitrary non-identifying metadata (large, unrestricted, not queryable).

Now build it — in your terminal, not here

Start from the Lesson 1 Pod manifest structure and add labels to it — by hand, no copy-paste. Give it:

  • the same shape as Lesson 1: a Pod named my-nginx, one container named nginx running the nginx image
  • a metadata.labels map with two entries: app: my-nginx and tier: frontend
  • nothing changes in spec — labels are a metadata-only addition

Once it's written, apply it and check it with kubectl get pods --show-labels, then try filtering it out with kubectl get pods -l tier=frontend and back in with -l tier=backend (should return nothing). Don't peek at the answer below first.

Reveal the reference answer

apiVersion: v1
kind: Pod
metadata:
  name: my-nginx
  labels:
    app: my-nginx
    tier: frontend
spec:
  containers:
    - name: nginx
      image: nginx
