Kubernetes / CKA — Lesson 2 of 24

Pod + Labels

Why this matters

Every object in Kubernetes that depends on another object — a Service routing to Pods, a ReplicaSet managing Pods, a NetworkPolicy deciding who can talk to whom — finds its target the same way: by matching labels, live, not by looking up a name. That's convenient right up until someone runs a bulk kubectl label command with a typo, or a script re-labels a Pod for an unrelated reason, and a production Pod silently drops out of a Service's routing or a ReplicaSet's management — with no error, no restart, and no obvious symptom pointing at "labels" as the cause. The exact same mechanism is also a real, documented debugging technique: pull a live Pod out from under its controller on purpose, without deleting it, just by changing what it's wearing.

Mental model: a Pod's name is like an employee's badge number — permanent, unique, and nobody in the building actually uses it in conversation. Labels are what people key off instead: "everyone with a blue lanyard," "anyone tagged Frontend." Swap someone's lanyard mid-shift and every rule keyed on lanyard color re-evaluates against them immediately — no one had to move them, re-badge them at the front desk, or restart their shift. Kubernetes objects work the same way: Services, ReplicaSets, and NetworkPolicies never look up a Pod by name — they continuously re-evaluate label selectors against whatever labels exist right now. This predicts something you may not expect yet: you can pull a live, healthy Pod out of a Service's traffic, or out of a Deployment's management entirely, using nothing but kubectl label — no delete, no apply, no downtime for the Pod itself.

Core concepts: label syntax

Labels live under metadata.labels — nothing in spec changes:

apiVersion: v1
kind: Pod
metadata:
  name: nginx
  labels:
    app: nginx
    tier: frontend
spec:
  containers:
  - name: nginx
    image: nginx:1.29
PartRule
Key — name segment63 characters or less; must start and end with an alphanumeric; dashes, underscores, dots allowed between
Key — optional prefixA DNS subdomain (253 characters max) followed by / — kubernetes.io/ and k8s.io/ are reserved for core components
Value63 characters or less, can be empty; if non-empty, must start and end with an alphanumeric, same allowed characters as a key's name segment

A Pod can carry any number of labels at once — app, tier, env, version, whatever your team selects on. There's no ordering and no hierarchy between them; every selector match is evaluated independently.

Core concepts: label selectors

A label selector is how another object says which Pods it means — "the core grouping primitive in Kubernetes," per the docs. Two selector styles exist, and which one an object supports depends on how old/new that object type is:

StyleOperatorsUsed by
Equality-based=, ==, !=Service and ReplicationController's spec.selector — a flat key/value map, implicitly AND'ed
Set-basedin, notin, exists (key only)Only matchLabels/matchExpressions on Deployment, ReplicaSet, DaemonSet, Job — matchLabels is equality-only, matchExpressions adds set-based

This is why Lesson 1 and Lesson 3's Service manifest wrote selector: { app: nginx } as a plain map, but every controller from here on will use spec.selector.matchLabels instead — Services never gained set-based selector support, controllers did. On the command line, both styles work through the same flag:

kubectl get pods -l tier=frontend
kubectl get pods -l tier!=frontend
kubectl get pods -l 'environment in (production, qa)'
kubectl get pods -l 'environment notin (dev)'
kubectl get pods -l partition
kubectl get pods --show-labels

Simple example: comma-separated conditions are always AND, never OR — kubectl get pods -l 'tier=frontend,env=prod' means both must be true. There's no built-in OR across different keys; if you need that, you query twice.

Production example

Production note: real fleets don't invent their own label vocabulary from scratch — Kubernetes documents a recommended shared set under the app.kubernetes.io/ prefix specifically so tools interoperate instead of each parsing their own convention: app.kubernetes.io/name (e.g. mysql), /instance (a unique instance name, e.g. mysql-abcxyz), /version, /component (e.g. database), /part-of (the higher-level application this belongs to, e.g. wordpress), and /managed-by (e.g. Helm). Helm, Prometheus, and most dashboards already assume these keys exist. A real Pod fleet typically carries this shared set plus a handful of org-specific keys with no prefix (private to your team) — team: payments, cost-center: 4471 — since unprefixed keys are explicitly reserved for that purpose and won't collide with the shared ones.

Hands-on exercise

Objective

Reproduce a real, documented Kubernetes technique: pull a live Pod out of a Deployment's management by relabeling it — no delete, no scale-down.

Scenario

You want to inspect one specific Pod without a ReplicaSet fighting you — as soon as you delete or drain it for debugging, the controller just replaces it. There's a cleaner way.

Environment assumptions

Any cluster you can kubectl into, no existing resource named web in the current namespace.

Commands

kubectl create deployment web --image=nginx:1.29 --replicas=3
kubectl get pods -l app=web
# pick one Pod name from the output, then:
kubectl label pod <pod-name> app=debug --overwrite
kubectl get pods -l app=web
kubectl get pods --show-labels

Expected result

Immediately after the relabel, kubectl get pods -l app=web shows only 2 Pods — the one you relabeled is gone from that view, still Running, still fully alive. A moment later, a brand-new fourth Pod appears with app=web, created by the ReplicaSet to bring its matched count back to 3. Your relabeled Pod keeps running, untouched, now unmanaged.

Verification

kubectl get pods --show-labels should show 4 Pods total: 3 with app=web (the original 2 plus 1 fresh replacement) and 1 with app=debug — same age as the others, no restarts, just no longer claimed by the ReplicaSet's selector.

Common failure

Expecting the relabeled Pod to disappear or restart. It doesn't — relabeling never touches the running container, it only changes what selectors see.

Troubleshooting

If the ReplicaSet doesn't create a replacement, check kubectl get rs -l app=web for its DESIRED/CURRENT counts — if CURRENT already reads 3 including your isolated Pod, the label change didn't take; re-run kubectl get pod <name> --show-labels to confirm app=debug actually landed.

Cleanup / rollback

kubectl delete deployment web
kubectl delete pod <pod-name> --ignore-not-found

Production lesson

This is a genuinely useful, documented isolation technique for live debugging — and the exact same mechanism, triggered by accident instead of on purpose, is how a mislabeled Pod quietly stops being managed in production.

Failure scenario

The accidental version of the exercise above, at fleet scale instead of one Pod.

  1. 11:04 A platform engineer runs a cleanup script meant to tag old Pods for removal: kubectl label pods -l env=staging lifecycle=stale --overwrite. The -l env=staging filter was supposed to be scoped tighter, to one team's namespace — it wasn't.
  2. 11:05 The script exits 0. No error, nothing in the terminal looks wrong.
  3. 11:09 Alerts start firing: three unrelated Deployments across two namespaces report Pods "missing" — their ReplicaSets show CURRENT below DESIRED momentarily, then climbing back up as new replacement Pods get created.
  4. 11:11 On-call checks kubectl get pods -A --show-labels and finds a growing number of Pods carrying lifecycle=stale that were never meant to be tagged — every one of them still Running, just orphaned from its ReplicaSet's selector the instant the label overwrite hit it.
  5. 11:14 Root cause identified: the label selector on the cleanup script (env=staging) matched Pods in namespaces that reused the same env: staging label for an unrelated purpose — the script's blast radius was defined by a label, not a namespace boundary.
  6. 11:17 Fix applied: remove the accidental lifecycle=stale label from the affected Pods so they're picked back up — but the ReplicaSets already created replacements, so the orphaned originals are deleted instead, to avoid running double capacity.
  7. 11:22 Verified: kubectl get pods -A -l lifecycle=stale returns empty; every affected Deployment's CURRENT matches DESIRED again.

Troubleshooting workflow

The general method, applied to "a controller has the wrong number of Pods, or a Pod isn't receiving traffic it should be":

  1. Confirm the symptom. kubectl get rs <name> or kubectl get deploy <name> — compare DESIRED against CURRENT/READY yourself, don't trust a dashboard's cached count.
  2. Define scope. One controller, or every controller sharing a label value? kubectl get pods -A --show-labels tells you whether this looks like one manifest change or one broad relabel operation.
  3. Check recent changes. kubectl get events --sort-by=.lastTimestamp -A plus your own shell/CI history — kubectl label and kubectl patch commands don't show up as "deploys," so check command history, not just Git.
  4. Inspect the right state. kubectl describe rs <name> to see its exact Selector; kubectl get pods --show-labels -l <that selector> and, separately, kubectl get pods -o wide without a filter, to spot Pods that exist but aren't matching anymore.
  5. Form a hypothesis. For example: "extra unmanaged Pods exist with the app's old labels, minus one key that changed."
  6. Test one variable. kubectl get pod <suspect> -o jsonpath='{.metadata.labels}' and diff it, field by field, against the controller's spec.template.metadata.labels.
  7. Apply the safest fix. Relabel the orphan back if no replacement was created yet; if a replacement already exists, delete the orphan instead of relabeling it back, to avoid running extra capacity nobody asked for.
  8. Verify recovery. DESIRED == CURRENT == READY on the controller, and no stray Pods left carrying the accidental label anywhere in the cluster (-A, not just one namespace).
  9. Document the root cause. Name the exact selector/label that caused the blast radius mismatch — "script used env=staging as its filter, which wasn't unique to the intended namespace" is specific; "a labeling mistake" is not.
  10. Prevent recurrence. Scope bulk-label operations by namespace (-n) in addition to a label selector, never a label selector alone across the whole cluster — and dry-run (--dry-run=client -o yaml) any bulk kubectl label before it runs for real.

Security note: labels aren't just a Service/Deployment concern — NetworkPolicy's podSelector and namespaceSelector (Lesson 10) also match on labels. Anyone with RBAC permission to patch/update Pods can change which NetworkPolicies apply to that Pod, without touching the NetworkPolicy object itself or needing any permission on it — label-write access to a Pod is effectively network-policy-write access to that Pod too, and it's easy to grant the former without realizing you've granted the latter.

Reliability note: in apps/v1, a Deployment's spec.selector is immutable once created — the API server rejects an attempted change with a "field is immutable" error, precisely to stop the kind of accidental mass-orphaning this lesson describes at the controller-definition level. That protection only covers the selector field itself; it does nothing to stop someone from relabeling the Pods it selects, which is the far more common way this failure actually happens.

Common mistake: writing a Deployment where spec.selector.matchLabels doesn't exactly match spec.template.metadata.labels. For Deployment/ReplicaSet, this isn't a silent empty-match like a Service — the object is rejected outright as invalid, because the template must satisfy the controller's own selector.

Common mistake: using a label for data nobody will ever select on — a full git commit SHA, a free-text description, a timestamp. It technically works up to 63 characters, but it bloats every selector index for no benefit. That's exactly what annotations exist for (see Decision guide below); labels are for querying, not storage.

Decision guide

OptionUse whenAvoid whenTrade-off
LabelAnything a Service, controller, NetworkPolicy, or kubectl -l needs to select onHigh-cardinality or unstructured data (full commit hash, free text)Strict 63-char value limit, indexed and matched on every selector evaluation
AnnotationMetadata tools/humans read but never select on — build info, config-as-JSON, tool directivesAnything a Service or controller needs to find objects byNot selectable at all — "in contrast, annotations are not used to identify and select objects," per the docs
Object nameThe one stable, unique identifier for direct lookup (kubectl get pod <name>)Grouping or querying across many objectsMust be unique per namespace; can't express "all of these" the way a label can

Default recommendation: if you'll ever type kubectl get X -l key=value or reference it in a selector, it's a label. If you'll only ever read it in kubectl describe or a UI, it's an annotation.

Knowledge check

Q1. Under which top-level field of a Pod manifest do labels live?

metadata.labels — a map of key/value pairs, separate from everything in spec.

Q2. You relabel a running Pod so it no longer matches its Deployment's selector. What happens to the Pod itself?

B. The Pod keeps running exactly as it was — relabeling never touches the container. The ReplicaSet just stops counting it and creates a replacement to restore its desired count.

Q3. Which selector style — equality-based or set-based — can a plain Service's spec.selector use?

Equality-based only. Set-based operators (in/notin/exists) are only available through matchLabels/matchExpressions on newer controllers (Deployment, ReplicaSet, DaemonSet, Job) — Services never gained that.

Certification mapping

Foundational — not separately weighted, but selectors are the mechanism every scored domain leans on: you cannot correctly write or debug Workloads & Scheduling (15%) or Services & Networking (20%) objects, and you cannot reason about Troubleshooting (30%)'s most common "silently found nothing" failure class, without knowing exactly how label selectors match.

Production challenge

Objective

Diagnose and fix a ReplicaSet running more Pods than its spec says it should — without being told which Pod is the orphan.

Scenario

A teammate was debugging a Pod in the checkout Deployment yesterday using the isolation technique from this lesson's exercise, then went home without cleaning up.

Environment assumptions

A kind/minikube cluster. Reproduce the leftover state yourself first:

kubectl create deployment checkout --image=nginx:1.29 --replicas=3
kubectl get pods -l app=checkout -o name | head -n1 | xargs -I{} kubectl label {} app=checkout-debug --overwrite

Commands

Diagnose using only the troubleshooting workflow above, then fix it:

kubectl get deploy checkout
kubectl get rs -l app=checkout
kubectl get pods --show-labels | grep checkout

Expected result

kubectl get deploy checkout shows 3/3 ready — it looks completely healthy. The extra, unmanaged Pod only shows up once you list Pods without filtering by the Deployment's own selector and read every row's labels.

Verification

Once you've found the Pod carrying app=checkout-debug, confirm it's genuinely orphaned (no matching ReplicaSet claims it) before deleting it:

kubectl get pod <orphan-name> -o jsonpath='{.metadata.ownerReferences}'
kubectl delete pod <orphan-name>

An orphaned Pod's ownerReferences still names the ReplicaSet that originally created it — but that ReplicaSet's own spec.selector no longer matches its current labels, which is what actually matters, not the historical owner reference.

Common failure

Deleting a Pod from the Deployment's normal 3 instead of the orphan, because kubectl get pods -l app=checkout only shows the managed ones and hides the very Pod you're looking for.

Troubleshooting

If nothing looks extra, double check you're not filtering by -l app=checkout anywhere in your inspection commands — that filter is exactly what makes the orphan invisible.

Cleanup / rollback

kubectl delete deployment checkout --ignore-not-found

Production lesson

An orphaned Pod left behind by a debugging session doesn't show up in any of the normal health checks — the Deployment reports healthy, the ReplicaSet reports the right count, and the orphan just sits there consuming node capacity (and, if it still has the old Service-matching labels underneath a different key, possibly still serving stale traffic) until someone thinks to list Pods without a label filter.

Recap
  • Labels live under metadata.labels; every dependent object (Service, ReplicaSet, NetworkPolicy) finds its targets by continuously matching a label selector, live — never by name.
  • Services/ReplicationControllers support equality-based selectors only (a flat map); Deployment/ReplicaSet/DaemonSet/Job support set-based too, via matchLabels/matchExpressions.
  • Relabeling a running Pod so it no longer matches its controller's selector doesn't touch the Pod — it just stops being counted, and the controller creates a replacement. This is a real, documented isolation technique, and a real accidental-outage cause.
  • A Deployment's spec.selector is immutable after creation and rejected if it doesn't match the Pod template's labels — but nothing stops the Pods themselves from being relabeled after the fact.
  • Labels are for selecting; annotations are for everything else — high-cardinality or unstructured metadata belongs in an annotation, not a label.
