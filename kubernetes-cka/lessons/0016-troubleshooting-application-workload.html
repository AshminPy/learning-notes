Troubleshooting: application & workload level

Lesson 15 was the node layer. This is the other half of Troubleshooting (still 30% of the exam): a Pod that's scheduled, on a healthy node, and still broken — every failure mode Lessons 1-12's controlled failures already produced, now approached as "diagnose this," not "here's what caused it."

Mental model: three tools, always in this order — describe (what happened), logs (what the app said), exec (go look yourself, last resort). That predicts the actual cost of skipping ahead: jumping straight to exec means manually re-discovering facts describe's Events section would have handed you in one command.

Where this fits

Pod broken, node is healthy (ruled out via Lesson 15)
   │
   ▼
kubectl describe pod    ← Events: scheduling, image pulls, probe failures, restarts
   │
   ▼
kubectl logs [--previous]   ← the app's own stdout/stderr
   │
   ▼
kubectl exec / debug        ← inside the container, last resort

The three moves

  1. kubectl describe pod <name> — always first. Events is a timeline.
  2. kubectl logs <pod> [-c <container>] [--previous] — the app's own output. --previous reads the last crashed instance; the current log may be empty if it just restarted.
  3. kubectl exec / kubectl debug — get inside. Check env vars, DNS, files, network reachability.

Failure signatures at a glance

SignatureLikely causeCheck
ImagePullBackOffWrong image/tag, missing registry authdescribe Events
CrashLoopBackOffStarts, then dies, repeatedlylogs --previous + exit code in describe
Pending foreverNever scheduleddescribe Events — no CPU/memory fits, unmatched selector
0/1 Ready, not crashingReadiness probe failing (Lesson 11)describe Events, up but no traffic
Service has no working PodsSelector/label mismatch (Lesson 2/3)kubectl get endpoints

Why this table works as a diagnostic tool: the same displayed status (ImagePullBackOff, for instance) can have unrelated root causes — a typo'd tag and a missing pull secret look identical in kubectl get pods, but describe Events shows the actual error text ("manifest not found" vs. "unauthorized"), which is why the status string alone is never the diagnosis.

Try it

Q1. A Pod shows CrashLoopBackOff. What two commands first, and why?

kubectl describe pod (restarts, exit code, last state) and kubectl logs --previous (the crashed container's own output — the current instance may not have logged anything yet).

Now, on a scratch namespace, break one thing on purpose (a bad image tag) and diagnose it using only the ladder above before revealing what you'd expect to see.

Reveal what to expect

kubectl get pods shows ImagePullBackOff. kubectl describe pod Events shows the exact pull error, naming the image and tag it tried. No log line exists yet — the container never started, so kubectl logs would return nothing useful here; that's expected, not a second bug.

A controlled failure

kubectl run bad-image --image=nginx:this-tag-does-not-exist
kubectl get pods bad-image
kubectl describe pod bad-image | grep -A3 Events:

Observe: ImagePullBackOff, and Events names the exact image/tag it failed to pull — the fix is obvious from Events alone, no logs needed, because the container never got far enough to produce any.

kubectl delete pod bad-image

Getting inside the container

kubectl exec -it <pod> -- sh only works if the image has a shell. Minimal/distroless images often don't — kubectl debug <pod> -it --image=busybox --target=<container> attaches a temporary debug container instead, without needing a shell in the production image.

Production best practices

Production note: distroless/minimal production images are a deliberate security choice (smaller attack surface) — kubectl debug exists specifically so that choice doesn't cost you your debugging ability.

Exam & interview notes

Directly scored under Troubleshooting (30%).

Interview Q: "Two Pods both show ImagePullBackOff. Are they necessarily the same problem?" A: No — the status string is identical either way; describe Events' actual error text (missing image vs. missing registry credentials) is what tells them apart.

Recap
  • Fixed order: describe pod (Events) → logs (--previous for a crash) → exec/debug last.
  • The same status string can have different causes — describe Events, not the status, tells you which.
  • Service routing nothing → check kubectl get endpoints first; usually a label mismatch (Lesson 2/3).
