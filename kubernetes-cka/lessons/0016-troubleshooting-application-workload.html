Kubernetes / CKA — Lesson 16 of 24

Troubleshooting: application & workload level

Why this matters

Lesson 15 was the cluster and node layer. This lesson is the other half of Troubleshooting — a Pod that's scheduled onto a perfectly healthy node, and is still broken. In a real incident, this is where most of the wasted time actually happens. Not because the fix is hard — most application-level fixes are one line — but because engineers misread the failure signature and chase the wrong root cause for twenty minutes before looking at the one piece of evidence that would have told them immediately. Two failures can show the exact same status string in kubectl get pods and have completely unrelated causes. If you don't have a disciplined way to tell them apart, you're not troubleshooting — you're guessing with extra steps.

Mental model: describe, logs, and exec aren't three ways to do the same thing — they answer three different questions, at three different layers, and each question only makes sense once you have the answer to the one before it. describe answers "what did Kubernetes try to do with this Pod" — scheduling, image pulls, probe results, restarts — all from the control plane's point of view, without ever touching the container. logs answers "what did the app itself say" — its own stdout/stderr, from inside the one container you asked about. exec answers "what's actually true right now, live, inside the running container" — files, env vars, live network state. Going out of order means answering a question you haven't earned the context for yet: jumping straight to exec when you haven't run describe means you're poking around inside a container without knowing whether it even finished starting, restarted five times in the last minute, or was never scheduled the way you assumed.

Core concepts

The fixed order, and why each step earns the next one:

  1. kubectl describe pod <name> — always first. The Events section is a chronological log of what the control plane and kubelet actually did: scheduling decisions, image pull attempts, probe failures, restarts. The Containers section's State and Last State fields tell you if a container is currently running, waiting, or terminated, and — critically — why it last stopped.
  2. kubectl logs <pod> [-c <container>] — the app's own stdout/stderr, once you know from describe which container to look at and whether it has restarted. Add --previous (or -p) to read the log of the last crashed instance — per the kubectl reference, this "print[s] the logs for the previous instance of the container in a pod if it exists." The current log can be completely empty if the container just restarted seconds ago and hasn't logged anything new yet.
  3. kubectl exec / kubectl debug — get inside the container and check something live: an env var's actual value, whether a file exists, whether DNS resolves, whether something is listening on the port you think it is. This is the most expensive step in time and in access, so it only runs once describe and logs have narrowed the question down to something you can't answer from outside the container.

The status string kubectl prints (CrashLoopBackOff, ImagePullBackOff, Pending) is a symptom, not a diagnosis — the same string can point at genuinely unrelated root causes. This table is the reference worth keeping open during any real incident:

Getting inside the container

kubectl exec -it <pod> -- sh drops you into a running container — same network namespace, same filesystem, same process view as the app. It only works if the container's image actually has a shell. Minimal and distroless images often don't. For those, kubectl debug <pod> -it --image=busybox --target=<container> attaches a separate, short-lived debug container that shares the target container's process namespace, without needing a shell inside the production image at all. Per the kubectl reference, --target is what makes this useful: it lets the debug container "target processes in this container name" — so you can inspect the real app's processes and network namespace from a fully-equipped busybox shell, even though the app's own image has none.

Production example

Production note: mature on-call teams don't relearn the ImagePullBackOff-vs-registry-auth distinction from scratch every incident — they keep a living "failure signature" runbook, structurally identical to the table above, and it's a required output of every incident review: if this incident's signature wasn't already in the runbook, the last step before closing the ticket is adding it. A team running a few hundred services will eventually see almost every way a Pod can fail, and the value compounds — a new on-call engineer at 3am isn't starting from zero, they're pattern-matching against forty prior incidents someone already wrote down. The single column that matters most in that runbook is "confirm with," not "likely cause" — a guess doesn't end an incident, a command that proves which cause it actually was does.

Hands-on exercise

Objective

Prove you can name the exact cause of an ImagePullBackOff from Events alone — before you touch logs or exec, because neither will help you here.

Scenario

A teammate bumps a Deployment's image tag as part of a routine release. The tag they typed doesn't exist in the registry — a one-character typo, 1.29.99 instead of 1.29. This is a far more common real-world cause of ImagePullBackOff than a wrong image name entirely.

Environment assumptions

Any cluster you can kubectl into (kind, minikube, or a real dev cluster), with outbound access to Docker Hub, and no existing Deployment named bad-tag-demo.

Commands

kubectl create deployment bad-tag-demo --image=nginx:1.29.99
kubectl get pods -l app=bad-tag-demo
kubectl describe pod -l app=bad-tag-demo

Expected result

kubectl get pods settles into STATUS: ImagePullBackOff after a brief ErrImagePull. describe pod's Events section shows the registry's own rejection — wording like "manifest for nginx:1.29.99 not found" or "manifest unknown" — followed by "Back-off pulling image."

Verification

The exact wording in Events is the proof, not the status string. ImagePullBackOff alone can't tell you whether the tag is wrong or the registry credentials are wrong — the Events text can, because a missing tag and a missing/invalid imagePullSecrets produce visibly different error text ("not found" vs. "unauthorized"/"forbidden").

Common failure

Assuming ImagePullBackOff automatically means a registry-auth problem and adding or rotating imagePullSecrets — this does nothing for a typo'd tag, and wastes a deploy cycle chasing the wrong layer.

Troubleshooting

If Events don't clearly show the tag issue, cross-check the tag manually against the registry's own listing, or run docker pull <image>:<tag> from a machine with registry access — if that fails identically outside the cluster, the problem is the tag/registry, not anything Kubernetes-specific.

Cleanup / rollback

kubectl delete deployment bad-tag-demo --ignore-not-found

Production lesson

ImagePullBackOff is one status string covering at least two unrelated root causes (bad tag, bad auth) that need two different fixes. A runbook entry that just says "fix ImagePullBackOff: check the image" isn't specific enough to save the next on-call engineer any time — it has to name which sub-cause and how it was confirmed.

Failure scenario

A realistic incident where every Pod-level signal says "healthy," and the problem is one layer deeper than kubectl get pods can show you.

  1. 10:41 Alert fires: the public API's error rate has spiked, mostly 502 Bad Gateway from the ingress. On-call runs kubectl get pods -l app=checkout-api — all 4 Pods show 1/1 Running, zero restarts. Nothing looks broken at the Pod level at all.
  2. 10:44 kubectl get endpoints checkout-api shows all 4 Pod IPs present on port 8080 — so this isn't a selector mismatch or a failing readiness probe removing Pods from the roster (Lesson 3). The Service genuinely believes these Pods are ready to take traffic.
  3. 10:48 On-call reads the Deployment's readinessProbe: httpGet against port: 9090, a lightweight internal metrics endpoint the app has always exposed and that starts answering almost immediately on boot. It has been passing this whole time — which is exactly the problem.
  4. 10:52 A config change two deploys ago moved the app's real HTTP listener from port 9090 to port 8080, to free 9090 for metrics-only traffic. Nobody updated the readinessProbe's port to match. The Service's own targetPort: 8080 was updated correctly — but the probe checking readiness was left pointed at 9090.
  5. 10:55 Root cause confirmed: kubectl exec into one Pod and curl localhost:8080 from inside the container — connection refused, nothing is listening there yet during the app's slow startup phase; curl localhost:9090 — responds instantly. The probe has been reporting "ready" based on a port that was never the real traffic port, so Pods go into the Service's endpoint list before their real listener on 8080 is actually up.
  6. 11:02 Fix applied: update readinessProbe.httpGet.port to 8080, matching the Service's real targetPort, and roll the Deployment.
  7. 11:07 Verified: new Pods take slightly longer to report 1/1 Ready — because the probe is now checking the port that actually matters — and the ingress 502 rate drops to zero.

Troubleshooting workflow

The general 10-step method, applied specifically to an application/workload symptom:

  1. Confirm the symptom. Run kubectl get pods yourself, right now — is it genuinely CrashLoopBackOff, or Pending, or reporting healthy while users see errors (as in the timeline above)? Don't diagnose from a dashboard that might be stale.
  2. Define scope. One Pod, every Pod in the Deployment, or every Pod in the namespace? kubectl get pods -o wide -l <selector> tells you if this is isolated to one replica or systemic to the rollout.
  3. Check recent changes. kubectl rollout history deployment/<name> and kubectl get events --sort-by=.lastTimestamp — did a deploy, image bump, or config/probe change just land?
  4. Inspect the right state — describe and logs. kubectl describe pod <name> for its Events and Last State; kubectl logs <name> [-c <container>] [--previous] for what the app itself said. Most application-level incidents are solved by these two commands alone — this is the step people skip past too fast.
  5. Form a hypothesis. Name it precisely: not "the Pod is broken" but "the readiness probe is checking the wrong port" or "the image tag doesn't exist in the registry."
  6. Test one variable — exec/debug. kubectl exec -it <pod> -- sh (or kubectl debug for a shell-less image) to confirm the one specific thing your hypothesis depends on — curl a port from inside the Pod, check an env var, resolve a DNS name. Don't use this step to browse around generally; you're here to test one thing.
  7. Apply the safest fix. The smallest change that addresses the confirmed cause — fix the probe's port, roll back the bad tag, raise the memory limit — not a broader rewrite of the manifest while you're in there.
  8. Verify recovery. Confirm against the real signal: for a Service-fronted app, that means kubectl get endpoints and an actual request through the Service, not just kubectl get pods looking green.
  9. Document the root cause. Write down the specific sub-cause, not the status string — "readinessProbe.port left at 9090 after the app's listener moved to 8080," not "502s, fixed."
  10. Prevent recurrence. Add a review check or CI gate that catches this class of drift next time — e.g. require the probe's port and the Service's targetPort to be reviewed together whenever either changes.

Security note: kubectl exec and kubectl debug are not neutral, risk-free commands — they're a live shell into a running production container, and Kubernetes treats that access as a distinct, security-sensitive permission. Getting a shell requires the create verb on the pods/exec subresource; attaching a kubectl debug ephemeral container requires permission on the separate pods/ephemeralcontainers subresource. Neither is granted automatically just because someone can read Pods or view logs — this is exactly the RBAC Role/RoleBinding model from Lesson 9, applied to the one verb that gives a human (or a compromised CI credential) a real shell inside your cluster. Treat pods/exec the way you'd treat SSH access to a production host: grant it narrowly, per namespace, and know who currently holds it.

Common mistake: jumping straight to kubectl exec out of habit, before running describe or logs. It feels productive — you're "in" the container — but you're now manually re-discovering facts describe would have handed you in one command (restart count, exit reason, recent events), and you've spent the most expensive, most access-sensitive tool first instead of last.

Common mistake: reading the current kubectl logs output after a crash, seeing nothing useful (or nothing at all), and concluding "no errors, must be something else." The current log belongs to the new container instance, which may have only been alive for a few seconds — the crash you're investigating happened in the previous instance. kubectl logs --previous is the only place that crash's own output still exists.

Default recommendation: exhaust describe and logs before exec, every time — they're cheaper, safer, and in most real incidents they're already enough. Reach for exec/debug only to test one specific, named hypothesis you couldn't confirm from outside the container.

Knowledge check

Q1. A Pod shows CrashLoopBackOff. What two commands first, and why?

kubectl describe pod (restarts, exit code, Last State) and kubectl logs --previous (the crashed container's own output — the current instance may not have logged anything yet).

Q2. A Deployment's Pods show 0/1 Ready but aren't restarting. What's happening?

A failing (or misconfigured) readiness probe (Lesson 11). The container is genuinely running — no crash — but Kubernetes won't send it traffic. Confirm with describe pod: repeated "Readiness probe failed" events, or — as in this lesson's timeline — a probe that's passing against the wrong port entirely.

Q3. You see ImagePullBackOff on a fresh Pod. Name two different root causes, and where you'd tell them apart.

Wrong image name/tag, or missing/wrong registry auth (no imagePullSecrets). Both look identical as a status string — kubectl describe pod Events shows the real error ("manifest not found" vs. "unauthorized"), which tells you which one it is.

Q4. kubectl describe pod shows Last State: Terminated, Reason: OOMKilled, Exit Code: 137. What should you check first?

A. OOMKilled specifically means the container exceeded its memory limit and the kernel killed it — a CPU limit produces throttling, not a kill (Lesson 11), and a selector or tag problem wouldn't show up as a Terminated reason on the container at all.

Production challenge

Objective

Diagnose a multi-container Pod where one container is healthy and the other is crashing, using only describe, logs -c, and get events — no exec, no guessing from the YAML alone.

Scenario

A Pod runs two containers: app (serving traffic normally) and log-shipper, a sidecar meant to tail the app's log file and forward it elsewhere. kubectl get pods shows 1/2 Ready and a climbing restart count.

Environment assumptions

Any cluster you can kubectl into. Create the Pod yourself first — the bug is deliberately built into this manifest, don't fix it before diagnosing it:

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: multi-container-demo
  labels:
    app: multi-container-demo
spec:
  containers:
  - name: app
    image: nginx:1.29
  - name: log-shipper
    image: busybox:1.36
    command: ["sh", "-c", "tail -f /var/log/app/access.log"]
EOF

Commands

kubectl get pod multi-container-demo
kubectl describe pod multi-container-demo
kubectl logs multi-container-demo -c log-shipper --previous
kubectl get events --field-selector involvedObject.name=multi-container-demo

Expected result

describe's Containers section shows app in State: Running, ready, zero restarts — and log-shipper in State: Waiting, Reason: CrashLoopBackOff, with a climbing restart count and Last State: Terminated, exit code 1. logs -c log-shipper --previous shows something like tail: can't open '/var/log/app/access.log': No such file or directory.

Verification

The exact log line is the proof: log-shipper expects a file at /var/log/app/access.log, but no volume is mounted into either container — app never writes there and log-shipper has nothing to tail. This is a wiring bug, not a crash in either container's own logic.

Common failure

kubectl exec-ing into app first, out of habit, because it's the container name people notice first — app is completely healthy here. The failing container is named explicitly in the READY count and in describe's Containers section; read that before you decide where to look.

Troubleshooting

If restarts aren't climbing yet when you check, give it 30–60 seconds — CrashLoopBackOff's exponential back-off means the interval between restart attempts grows over time, so the very first restart can look deceptively calm.

Cleanup / rollback

kubectl delete pod multi-container-demo --ignore-not-found

Production lesson

A sidecar pattern (log shipper, service mesh proxy, metrics exporter) fails independently of the main container it rides alongside — READY showing 1/2 instead of 0/2 is the tell that one container is fine and the other genuinely isn't. Diagnosing which one, and why, from describe and logs -c alone — without ever needing a shell — is the actual skill this whole lesson has been building toward.

Recap
  • Fixed order, every time: describe pod (Events, Last State) → logs (--previous after a crash) → exec/debug last — each answers a question the previous one earns.
  • Same status string, different root causes: ImagePullBackOff (bad tag vs. bad auth) and CrashLoopBackOff (app bug vs. OOMKilled) both need Events or describe's Last State to tell apart — the status string alone never does.
  • Init:CrashLoopBackOff means an init container is failing, not the main one — you need -c <init-container-name> to see any logs at all.
  • A Pod can look fully healthy (1/1 Ready, in the Service's endpoint list) while a probe checking the wrong port lets broken traffic through — describe's Events and the probe's own port config are what catch this, not kubectl get pods.
  • kubectl exec/kubectl debug require their own RBAC grant (pods/exec, pods/ephemeralcontainers) — treat that access like production SSH, not a default.
Stuck, or your cluster showed something different from "Expected result" above? Paste the exact kubectl describe pod Events or the exact log line back to your teacher — that's almost always more useful than describing the symptom in your own words.
