Kubernetes / CKA — Lesson 16 of 17

Troubleshooting: application & workload level

Lesson 15 was the cluster and node layer — the plane you rarely touch on GKE Autopilot because Google owns it. This lesson is the other half of Troubleshooting (still the exam's single largest domain, 30%): a Pod that's scheduled, on a healthy node, in a healthy cluster — and still broken. This is the layer you already live in every day. It's also the last content lesson — Lesson 17 is a final review and cheat sheet, not new material.

Tied to your mission: you already reach for kubectl describe and kubectl logs the moment a Deployment goes sideways in production — that instinct is correct and it's the whole exam domain. What the exam adds is speed and completeness under a clock: naming the failure signature on sight (ImagePullBackOff vs CrashLoopBackOff vs a stuck Pending) instead of reasoning it out from scratch, and reflexively reaching for --previous and get endpoints — the two flags that are easy to forget under pressure and that change what you find.

The mental model — a fixed order of moves

Almost every workload problem resolves through the same three tools, in the same order. Skipping straight to exec because it feels more "hands on" wastes time — describe and logs usually hand you the answer without going anywhere near a shell.

  1. kubectl describe pod <name> — always first. The Events section at the bottom is a chronological log of what the control plane and kubelet actually did to this Pod: scheduling decisions, image pulls, probe failures, container starts and restarts, and the reason string attached to each. For scheduling and image problems, this is usually the entire investigation.
  2. kubectl logs <pod> [-c <container>] — what the app itself said. Once a container has actually started, its own stdout/stderr is here. Add --previous (short: -p) to read the log of the last container instance before it died — this is the one flag people forget, and it's the difference between seeing the actual crash and seeing nothing, because a restarted container's current log is often empty or just starting up again.
  3. kubectl exec or kubectl debug — get inside, last resort. For when the first two don't explain it: check env vars, DNS resolution, file contents, or network reachability from inside the Pod's own network namespace.

Same shape as Lesson 15's node-level ladder (SSH → journalctl/crictl → live inspection), one layer up: describe (the "what happened" log) → logs (the app's own account) → exec (go look yourself). Same ladder, different altitude.

Try it first — before reading on

Q1. A Pod shows CrashLoopBackOff. What two commands do you run first, and why those two specifically?

kubectl describe pod (Events section — how many restarts, last state, exit code/reason) and kubectl logs --previous (the crashed container's own output, since the current instance may not have logged anything useful yet). describe tells you that and how it died; logs --previous tells you why, from the app's own mouth.

Q2. A Service isn't routing to any Pods. What single command confirms this, and what's the most likely root cause?

kubectl get endpoints <service> (or get endpointslices -l kubernetes.io/service-name=<service>) — if it shows <none> or is empty, the Service has no Pods to send traffic to. Most likely cause: spec.selector on the Service doesn't match the labels actually on the Pods (typo, or the Pods were relabeled) — ties back to Lesson 3/5, where the selector was the only thing wiring the two objects together in the first place.

Q3. A Deployment's Pods all show 0/1 Ready but the container is not restarting and not crashing. What's the mechanism, and which lesson does it tie back to?

A failing readiness probe (Lesson 11) — the container is genuinely running (so no crash, no restart) but Kubernetes doesn't consider it ready to receive traffic, so it's pulled out of Service endpoints while still alive. Confirm with describe pod — the Events section shows repeated "Readiness probe failed" entries with the actual HTTP status/exit code returned.

Q4. You see ImagePullBackOff on a fresh Pod. Name two distinct root causes it could be, and the one place you'd look to tell them apart.

Wrong image name/tag (typo, or a tag that was never pushed) vs. missing/incorrect registry authentication (private registry, no imagePullSecrets). Both surface as the same status; kubectl describe pod's Events section shows the actual error string from the kubelet (e.g. "manifest not found" vs. "unauthorized"/"pull access denied"), which tells you which one it is.

The failure signatures, at a glance

Not a fix-it list to memorize — a map from "what you see" to "what to check next." The actual cause is always confirmed via Events or logs, never guessed from the status string alone.

  • ImagePullBackOff / ErrImagePull — kubelet can't pull the image. Wrong name/tag, image never pushed, or missing/wrong registry auth (imagePullSecrets). Check: describe pod Events.
  • CrashLoopBackOff — container starts, then exits, repeatedly; Kubernetes backs off between restarts. Check: logs --previous for the app's own error, describe pod for the exit code and "Last State" block.
  • Pending forever — never made it past scheduling. Check: describe pod Events for the scheduler's own reason — insufficient CPU/memory across all nodes, no node matches a nodeSelector/affinity rule, or an unsatisfied taint/toleration.
  • 0/1 Ready, container otherwise fine — readiness probe failing (Lesson 11). Pod is up, just not accepting traffic.
  • Service has no working Pods behind it — usually a selector/label mismatch (Lesson 3/5). Confirmed via kubectl get endpoints, not by staring at the Service spec.

Getting inside the container

kubectl exec -it <pod> -- sh (or bash, if the image has it) drops you into a shell inside a running container — same network namespace, same filesystem, same view the app itself has. Good for checking env vars, DNS resolution, config file contents, or reaching another service directly with curl/wget.

It only works if the container image has a shell. Minimal and distroless images (increasingly common — smaller attack surface, faster pulls) often don't. For those, kubectl debug <pod> -it --image=busybox --target=<container> attaches a temporary ephemeral debug container to the running Pod, sharing its network namespace (and, with --target, its process namespace) — full debugging access without a shell ever having to exist in the production image.

Now try it yourself — break something on purpose

On a scratch cluster or namespace, create three separate Pods/Deployments, each broken a different way, without telling yourself in advance which is which:

  • one with an image tag that doesn't exist
  • one whose container command exits immediately (e.g. command: ["sh", "-c", "exit 1"])
  • one with a Service pointing at it, where you deliberately set the Service's selector to not match the Pod's labels

For each, use only the ladder above — describe, then logs (with --previous where relevant), then get endpoints for the Service case — to name the failure signature and root cause before fixing it. Don't look at what you built to "cheat" the diagnosis; treat it like you don't know.

Recap
  • Fixed order: describe pod (Events) → logs (add --previous for a crashed container) → exec/debug as the last resort
  • ImagePullBackOff/ErrImagePull = can't pull (name/tag/auth); CrashLoopBackOff = starts then dies (check exit code + previous logs)
  • Pending forever = scheduling failure, root cause is in Events; 0/1 Ready = readiness probe failing, not a crash (Lesson 11)
  • Service routing nothing = check kubectl get endpoints first, root cause is almost always a selector/label mismatch (Lesson 3/5)
  • kubectl exec needs a shell in the image; kubectl debug (ephemeral containers) works even when the image is shell-less/distroless
