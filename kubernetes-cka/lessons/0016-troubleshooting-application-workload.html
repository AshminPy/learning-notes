Troubleshooting: application & workload level

Lesson 15 was the node layer. This is the other half of Troubleshooting (still 30% of the exam): a Pod that's scheduled, on a healthy node — and still broken. Last content lesson; Lesson 17 is a cheat-sheet review.

Simple example: three tools, always in this order — describe (what happened), logs (what the app said), exec (go look yourself, last resort). Jumping straight to exec wastes time; the first two usually hand you the answer.

The three moves

  1. kubectl describe pod <name> — always first. The Events section is a timeline: scheduling, image pulls, probe failures, restarts.
  2. kubectl logs <pod> [-c <container>] — the app's own stdout/stderr. Add --previous to read the log of the last crashed instance — the current log may be empty if it just restarted.
  3. kubectl exec / kubectl debug — get inside the container. Check env vars, DNS, files, network reachability.

Failure signatures at a glance

  • ImagePullBackOff / ErrImagePull — wrong image name/tag, or missing registry auth. Check: describe Events.
  • CrashLoopBackOff — starts, then dies, repeatedly. Check: logs --previous plus exit code in describe.
  • Pending forever — never got scheduled. Check: describe Events for the scheduler's reason (no CPU/memory fits, unmatched nodeSelector, unsatisfied taint).
  • 0/1 Ready, not crashing — readiness probe failing (Lesson 11). Pod is up, just not getting traffic.
  • Service has no working Pods — check kubectl get endpoints. Usually a selector/label mismatch (Lesson 3/5).

Try it — before looking below

Q1. A Pod shows CrashLoopBackOff. What two commands first, and why?

kubectl describe pod (restarts, exit code, last state) and kubectl logs --previous (the crashed container's own output — the current instance may not have logged anything yet).

Q2. A Deployment's Pods show 0/1 Ready but aren't restarting. What's happening?

A failing readiness probe (Lesson 11). The container is genuinely running — no crash — but Kubernetes won't send it traffic. Confirm with describe pod: repeated "Readiness probe failed" events.

Q3. You see ImagePullBackOff on a fresh Pod. Name two different root causes, and where you'd tell them apart.

Wrong image name/tag, or missing/wrong registry auth (no imagePullSecrets). Both look identical as a status string — kubectl describe pod Events shows the real error ("manifest not found" vs. "unauthorized"), which tells you which one it is.

Getting inside the container

kubectl exec -it <pod> -- sh drops you into a running container — same network, same filesystem. Only works if the image has a shell. Minimal/distroless images often don't — use kubectl debug <pod> -it --image=busybox --target=<container> instead, which attaches a temporary debug container without needing a shell in the production image.

Now try it yourself

On a scratch namespace, break three things on purpose: a bad image tag, a container that exit 1s immediately, and a Service whose selector doesn't match its Pod's labels. For each, use only describe → logs --previous → get endpoints to name the failure before fixing it.

Source

kubernetes.io/docs/tasks/debug/debug-application/debug-pods and kubectl logs reference — exam-allowed pages.

Recap
  • Fixed order: describe pod (Events) → logs (--previous for a crash) → exec/debug last.
  • Same status can have different causes — describe Events (not the status string) tells you which.
  • Service routing nothing → check kubectl get endpoints first; usually a label mismatch.
