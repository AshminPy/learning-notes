Kubernetes / CKA — Lesson 23 of 24

Resource monitoring

Lessons 15 and 16 diagnosed Pods and nodes that were visibly broken — CrashLoopBackOff, Pending, failed probes. This lesson is for the case with no error at all: the cluster is technically healthy, but something is slow, and you need real numbers, not a guess.

Simple example: metrics-server is a light gauge, not a data logger. It asks every kubelet "what's your CPU/memory right now" and keeps the answer in memory for a short time — nothing is stored, nothing has history. For real dashboards and alerting over time, that's Prometheus's job, not this.

kubectl top

kubectl top nodes
kubectl top pods
kubectl top pods --containers          # per-container, not just per-Pod totals
kubectl top pods -n kube-system        # any namespace, same as kubectl get

This is only possible because metrics-server is running in the cluster, scraping each kubelet's Summary API and exposing it through the Kubernetes Metrics API. On a kubeadm cluster, unlike most managed platforms, it isn't installed by default — you have to add it.

When it doesn't work

If metrics-server isn't installed or isn't healthy, kubectl top fails outright — no numbers, an error about the metrics API being unavailable. This is also exactly why an HPA (Lesson 22) shows <unknown> instead of a percentage: same missing data source, two different symptoms.

A well-known kubeadm-specific gotcha: metrics-server's Pod can CrashLoop because it can't verify kubelets' self-signed certs. The (deliberately narrow, lab-only) fix is adding --kubelet-insecure-tls to its args — worth recognizing, not something you'd do in production without understanding the trade-off you're making.

Try it — before looking below

Q1. kubectl top pods returns an error instead of numbers, but every Pod is Running and Ready. What's actually wrong?

Nothing wrong with the Pods — metrics-server is missing or unhealthy. Check kubectl get pods -n kube-system | grep metrics-server (or wherever it's installed) and its logs, the same ladder as any other workload.

Q2. A user reports the app "feels slow" but there are no failed probes, no restarts, no events. What's your first command, and what would make you suspect a resource problem specifically?

kubectl top pods --containers for that app first. A container pinned near its CPU limit (Lesson 11) with no crashes or restarts is a classic silent slowdown — the Pod looks perfectly healthy in describe/get events because nothing failed, it's just starved.

Source

kubernetes-sigs.github.io/metrics-server and kubectl top reference — exam-allowed pages.

Recap
  • metrics-server gives point-in-time numbers only — no history, that's a separate tool's job.
  • Not installed by default on kubeadm clusters — kubectl top failing outright usually means this, not a Pod problem.
  • Same missing dependency explains both a failing kubectl top and an HPA stuck at <unknown>.
