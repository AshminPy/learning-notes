Kubernetes / CKA — Lesson 23 of 24

Resource monitoring

Why this matters

The hardest production incidents to catch are the ones with no error to grep for. Lessons 15 and 16 gave you a ladder for the case where something is visibly broken — a CrashLoopBackOff, a Pod stuck Pending, a failing probe with an Events line spelling out exactly why. This lesson is for the opposite case: every Pod is Running, every container is Ready, restart counts are all zero, and a user is still telling you the checkout page takes eight seconds to load. There is nothing to grep for, because nothing failed — the app is just slow, and "slow" doesn't show up in describe or logs unless you already know to look at resource usage. On a cluster with no full observability stack installed — most kubeadm clusters, and plenty of real production ones too — kubectl top and metrics-server are often the only tool available that can surface this entire class of problem at all.

Mental model: metrics-server is a gauge, not a data logger. Walk up to a gauge right now and it tells you the truth: this Pod is using 340Mi of memory, this node is at 78% CPU, this instant. But it keeps no needle marks from an hour ago — ask it "was this Pod slow at 2pm" and it has nothing to give you, because it was never built to remember. That's not a limitation to work around, it's the design: metrics-server exists to answer one question fast — what's happening right now, for the scheduler, the HPA, or you to react to — and a completely different tool, a real time-series store like Prometheus, exists to answer the other question — what happened over time, so you can alert on a trend or investigate after the fact. If you can predict that metrics-server can never answer a "when did this start" question, no matter how you phrase the kubectl command, you've internalized the model. If you catch yourself looking for a --since or a history flag on kubectl top, you haven't yet.

Core concepts

metrics-server is a single cluster-wide component — usually one or two Pods in kube-system — that does exactly one job: on a roughly 15-second interval, it asks every kubelet in the cluster for its current CPU and memory usage, over the kubelet's resource metrics endpoint. Underneath, those numbers come from cAdvisor, the container-metrics collector built into the kubelet (or an equivalent the container runtime exposes) — metrics-server itself doesn't measure anything; it collects and re-exposes what the kubelet already knows. It keeps only the newest reading for each Pod and node, in memory, and discards the previous one the moment a fresher one arrives. There is no database, no disk write, no query language — ask it for last hour's numbers and there is nothing to return, because nothing was ever kept.

Those numbers are exposed through the Kubernetes Metrics API (API group metrics.k8s.io), registered with the API server via the aggregation layer — the same mechanism that lets extension APIs sit alongside the built-in ones. Two consumers read from it: kubectl top, for a human to look at, and the HorizontalPodAutoscaler (Lesson 22), which polls it on its own reconcile loop to decide whether to scale. The Vertical Pod Autoscaler reads the same API for its resize recommendations, though VPA itself is outside this course's scope.

kubectl top pods -l app=checkout         # filter by label selector

Every flag above is real and documented, not improvised: --sort-by only accepts cpu or memory; -A/--all-namespaces ignores whatever namespace your current context is set to; and --containers is the one people forget, which matters the moment a Pod runs more than one container and you need to know which specific one is heavy, not just the Pod's total.

Getting a number out of any of this depends on a working chain: the kube-apiserver's aggregation layer must be enabled, metrics-server needs network access to every kubelet on port 10250, and it has to trust the kubelet's serving certificate. On a self-managed kubeadm cluster, that last link is the one that most often breaks — kubelets frequently serve a certificate metrics-server won't verify out of the box, and its Pod CrashLoops on a TLS error. The narrow, lab-only fix is adding --kubelet-insecure-tls to its container args, which skips that verification — worth recognizing on sight, not something to reach for in production without understanding you've just turned off a certificate check.

Simple example: this exact missing dependency explains two symptoms that look unrelated. kubectl top pods failing outright with a "metrics API not available" error, and an HPA (Lesson 22) stuck showing TARGETS <unknown>/50% forever, are the same problem wearing two different costumes — metrics-server is missing or unhealthy, full stop. Fix metrics-server and both symptoms disappear together, because both were only ever reading its output.

Production example

Production note: a real production cluster runs both metrics-server and a full Prometheus stack, not one instead of the other, because they answer different questions. A 60-node cluster's HPA needs a fast, cheap "what's CPU right now" answer every 15 seconds to decide whether to add a Pod — metrics-server, with its in-memory snapshot, is built for exactly that and nothing else. The same cluster's platform team also runs Prometheus scraping every Pod on a similar interval, but writing every sample to a time-series store with weeks of retention, feeding Grafana dashboards ("show checkout-api's CPU for the last 7 days") and Alertmanager rules ("page someone if memory stays above 90% of its limit for 10 minutes straight"). Neither tool can do the other's job: metrics-server has no alerting and no history to draw a dashboard from, and Prometheus is too heavy and too slow — by design, since it's built for depth, not speed — to be the 15-second data source an HPA polls directly. (An HPA can scale on Prometheus-sourced custom metrics, but only through an adapter bridging it back into the Metrics API shape the HPA expects — it never talks to Prometheus directly.) Ripping out metrics-server because "we already have Prometheus" is a real mistake teams make, and it silently breaks every HPA in the cluster the moment it happens.

Hands-on exercise

Objective

Find the single heaviest container running in your cluster right now, using nothing but kubectl top — no guessing, no opening an application to check.

Scenario

You've just joined on-call for a cluster you don't know well. Before anything breaks, you want a fast baseline of what's actually consuming CPU and memory.

Environment assumptions

Any cluster with metrics-server installed and healthy — confirm first with kubectl top nodes; if that errors, install metrics-server before continuing (on kind/minikube you'll likely need the lab-only --kubelet-insecure-tls flag from Core concepts above). At least a couple of namespaces with running Pods.

Commands

kubectl top nodes
kubectl top pods --containers -A
kubectl top pods --containers -A --sort-by=cpu
kubectl top pods --containers -A --sort-by=memory

Expected result

The first command shows every node's current usage against its allocatable capacity. The next three list every container in every namespace — unsorted, then ranked by CPU descending, then ranked by memory descending. Note the container at the very top of each sorted list; it may not be the same one both times.

Verification

Take the Pod name from the top of the CPU-sorted list and run kubectl describe pod <name> -n <namespace>. Compare the usage number kubectl top just showed you against that container's resources.limits.cpu in the describe output (Lesson 11) — is it nowhere close to its limit, or pinned right at it? That comparison is the actual point of the exercise, not the ranking by itself.

Common failure

Running kubectl top pods without --containers and concluding a multi-container Pod is "using 400m CPU total" without knowing which of its containers is responsible. The Pod-level total is real, but it hides the one number you usually need during an incident.

Troubleshooting

If any command returns an error about the metrics API being unavailable, metrics-server itself is the problem, not your workloads — check kubectl get apiservices | grep metrics for its registration status, and kubectl get pods -n kube-system | grep metrics-server for a CrashLoop, then its logs.

Cleanup / rollback

Nothing to clean up — every command here is read-only.

Production lesson

"Ranked by CPU, ranked by memory, cross-checked against the manifest's limit" is a three-command habit, not a research project. Building it now, before an incident, is the difference between a 30-second check and the 20-minute dead end in the next section.

Failure scenario

A realistic incident: the right troubleshooting ladder, run in the right order, still costs real time before the actual tool for this job gets used.

  1. 11:03 Symptom: support escalates a ticket — "the checkout page takes 8-10 seconds to load, it used to be under a second." No alert has fired; there's no dashboard for this cluster showing anything red.
  2. 11:05 On-call runs kubectl get pods -n checkout — every Pod is Running, 1/1 Ready, RESTARTS at 0 across the board. Nothing obviously wrong.
  3. 11:08 Following Lesson 16's ladder, checks kubectl describe pod checkout-api-7f9c8-x8z2 — the Events section is empty except for a routine image pull and scheduling event from three days ago. No probe failures, no OOMKilled entries, nothing recent.
  4. 11:12 Checks kubectl logs checkout-api-7f9c8-x8z2 — clean access logs, every response code is 200, requests are just taking longer than usual to complete. Nothing to grep for.
  5. 11:19 Widens the search: the payment gateway's own status page is green, and the NetworkPolicy (Lesson 10) governing the namespace hasn't changed in two weeks. Twenty minutes gone, still no lead.
  6. 11:24 Finally runs kubectl top pods --containers -n checkout: checkout-api's one container shows 248m/250m CPU — pinned right against its configured limit, and very likely has been there for a while, since CPU throttling causes no restart, no crash, and nothing for describe or logs to ever show.
  7. 11:27 Confirms against the manifest: kubectl describe pod's resources section shows limits: cpu: 250m, an exact match. The container isn't broken — the kernel is throttling it every cycle it tries to exceed that number (Lesson 11).
  8. 11:33 Fix applied: after checking the traffic dashboard shows a genuine, sustained rise in checkout volume this week (not a code regression or a leak), raises the Deployment's CPU limit to 500m and rolls it out.
  9. 11:38 Verified: kubectl top pods --containers -n checkout now shows 310m/500m, comfortably under the new limit. Page load time is back under a second, confirmed with the same user who filed the ticket.

Twenty-one minutes were spent doing the right thing — the describe/logs/events ladder from Lesson 16 is correct, and skipping it isn't the lesson here. The lesson is what comes after it finds nothing: reach for kubectl top next, not deeper into application code.

Troubleshooting workflow

The general method, sequenced specifically for "the app is slow and nothing is failing":

  1. Confirm the symptom precisely. "Feels slow" isn't testable — get a number (response time, from where, for which endpoint) and a comparison baseline before doing anything else.
  2. Define scope. One Pod, one Deployment, one node, or the whole cluster? kubectl get pods -o wide -A shows whether this is isolated to one workload or spread across a node — which would point at node-level pressure, not this one container.
  3. Check recent changes. kubectl rollout history deployment/<name> and kubectl get events --sort-by=.lastTimestamp — did a traffic pattern, a resource limit, or a deploy change recently?
  4. Run Lesson 16's ladder first. kubectl describe pod (Events) then kubectl logs. If either explains it — a probe failure, an error in the logs — stop here. Most slowness complaints do have a visible cause; don't skip straight to metrics out of habit.
  5. If that ladder comes up clean, reach for kubectl top. kubectl top pods --containers -n <namespace> for the specific workload. This is the tool for exactly the case where nothing failed but something is still wrong.
  6. Form a hypothesis matched to the number. Usage sitting at or above a container's configured limit (Lesson 11) points at CPU throttling or a looming OOMKill, not an application defect — that's a resourcing hypothesis, not a code hypothesis.
  7. Test one variable. Confirm the exact resources.limits value in the manifest against what kubectl top is showing — don't eyeball it, read both numbers side by side.
  8. Apply the safest fix. Raise the limit only after confirming the usage reflects legitimate load growth, not a leak or a regression from a recent deploy — check the traffic trend, not just the CPU number, before resizing anything.
  9. Verify recovery. Re-run kubectl top and confirm usage now sits comfortably under the new limit, and confirm the user-facing symptom actually improved — a lower CPU number alone doesn't prove the page got faster.
  10. Document and prevent recurrence. Record the exact limit that was too low and why traffic grew past it; consider whether an HPA (Lesson 22) would have absorbed this automatically, or whether a Prometheus alert on sustained near-limit usage would have caught it before a user did.

Security & reliability considerations

Security note: kubectl top only works end to end if the Metrics API (metrics.k8s.io) is registered and reachable, and reading it is governed by ordinary RBAC like any other API resource — a user needs get/list/watch on pods and nodes in the metrics.k8s.io API group. metrics-server's own manifests ship a system:aggregated-metrics-reader ClusterRole specifically for granting this to ordinary users; if kubectl top works for you but fails with a permissions error for a teammate on the same cluster, that binding — not metrics-server itself — is the first thing to check with kubectl auth can-i get pods.metrics.k8s.io.

Reliability note: treat this as an availability problem, not just a performance one. A container silently pinned at its CPU or memory limit produces zero alertable signal on its own — no failed probe, no restart, no error log — which means "slow with nothing visibly broken" is a real outage from the user's point of view that alerting built only around crashes and probe failures will never catch. kubectl top closes part of that gap reactively, during an incident; a Prometheus alert on sustained near-limit usage (see the decision guide below) is what closes it proactively, before a user notices.

Common mistakes

Common mistake: reaching for kubectl exec and deep application-level debugging — profilers, strace, adding log statements — before checking basic resource usage. If the container is simply throttled at its CPU limit, no amount of application-level investigation will find that; the answer is one kubectl top command away, and skipping it is how a 30-second check turns into an hour spent in the wrong layer.

Common mistake: assuming metrics-server can answer "was it slow an hour ago." It can't — there is no history anywhere in metrics-server, by design (see the Mental model above). Asking kubectl top for anything but the current instant won't fail loudly; it will just show you the current instant again, and mistaking that for historical data leads to wrong conclusions about when a problem actually started.

Decision guide

Default recommendation: run metrics-server on every cluster, always — it's small, it's what the HPA needs, and it's your fastest incident-response tool. Add Prometheus (or a managed equivalent) the moment you need history, dashboards, or alerting on trends rather than current state; the two aren't competing choices, they're complementary layers, and most real production clusters run both.

Knowledge check

Q1. kubectl top pods returns an error instead of numbers, but every Pod is Running and Ready. What's actually wrong?

Nothing wrong with the Pods — metrics-server is missing or unhealthy. Check kubectl get pods -n kube-system | grep metrics-server (or wherever it's installed) and its logs, the same ladder as any other workload.

Q2. You've run kubectl describe pod and kubectl logs and both are clean — no unusual events, no errors. What's your next command, and what result would confirm a resource problem specifically?

kubectl top pods --containers for that workload. A container sitting at or above its configured CPU or memory limit (Lesson 11), with no crashes or restarts, is the fingerprint of silent resource starvation — describe/logs looked clean because nothing actually failed, the container is just throttled or near its ceiling.

Q3. Which tool can tell you whether a Pod's memory usage was high three hours ago, before the current outage?

C. Only a tool that was already storing history before the outage can answer this — that's Prometheus's entire job. metrics-server (A) and kubectl top (B) only ever show the current instant, by design, never the past. kubectl describe (D) shows Events like scheduling and probe failures, never a resource-usage time series.

Production challenge

Objective

Decide what to check next when a container is near its memory limit but hasn't been OOMKilled yet — before it becomes a real incident — using only what Lessons 11 and 23 have covered.

Scenario

You run kubectl top pods --containers -n payments as a routine check and see worker at 480Mi / 512Mi memory — 94% of its configured limit. kubectl get pods -n payments shows it Running, 1/1 Ready, zero restarts. Nothing has failed. Yet.

Environment assumptions

A kind/minikube cluster with metrics-server installed. Build a comparable scenario yourself first — don't skip straight to the fix:

kubectl create namespace payments

cat <<EOF | kubectl apply -f - --namespace=payments
apiVersion: v1
kind: Pod
metadata:
  name: worker
spec:
  containers:
  - name: worker
    image: polinux/stress
    resources:
      requests:
        memory: "256Mi"
      limits:
        memory: "512Mi"
    command: ["stress"]
    args: ["--vm", "1", "--vm-bytes", "480M", "--vm-hang", "0"]
EOF

kubectl top pod worker -n payments --containers

Commands

Work through the decision yourself before reading further: is 480Mi/512Mi an emergency, a trend to watch, or nothing? What would change your answer? Then check your reasoning against this:

# Is this stable, or trending up? metrics-server has no history (this lesson's mental
# model) — repeated manual checks over a couple of minutes are the closest substitute:
kubectl top pod worker -n payments --containers
sleep 30 && kubectl top pod worker -n payments --containers

# What's the container's actual configured limit and QoS class? (Lesson 11)
kubectl describe pod worker -n payments | grep -A4 "Limits\|QoS"

Expected result

Usage holds steady around 480Mi across repeated checks in this synthetic example — in a real incident, a number that keeps climbing across repeated checks is the difference between "stable, worth a ticket" and "about to OOMKill, act now." describe confirms limits.memory: 512Mi and a Burstable QoS class (Lesson 11), since only a memory limit was set here, not a matching request.

Verification

Confirm your read is right by pushing it over the edge on purpose: edit --vm-bytes up to 600M and re-apply. kubectl get pod worker -n payments should flip to OOMKilled within seconds, with kubectl describe's Last State block showing Reason: OOMKilled, Exit Code: 137 — proving 480Mi/512Mi genuinely was one step from exactly what happens next.

Common failure

Treating "not yet OOMKilled" as "not a problem." A container sitting at 94% of its limit is a near-miss, not a clean bill of health — the only reason it hasn't been killed yet is that it hasn't crossed the line, and metrics-server gives you no way to know how close it's been cutting it historically.

Troubleshooting

If kubectl top shows no data immediately after creating the Pod, metrics-server's ~15-second collection interval hasn't caught up yet — wait and re-run rather than assuming something is broken.

Cleanup / rollback

kubectl delete namespace payments

Production lesson

The right response to "near its limit, not yet killed" isn't panic or dismissal — it's exactly the Lesson 11 question: is this container's limit sized for its real, legitimate usage, or is requests/limits due for a resize? Raising the limit blindly just moves the ceiling; understanding whether the usage is a leak, genuine load growth, or a limit that was always too tight is the actual decision, and metrics-server alone can't make it for you — it can only tell you where the line is right now.

Recap
  • metrics-server collects CPU/memory from every kubelet's resource metrics endpoint (cAdvisor-derived) roughly every 15 seconds, keeps only the latest snapshot in memory, and exposes it via the Kubernetes Metrics API (metrics.k8s.io) that kubectl top and the HPA both read.
  • It has no memory of anything before "right now" — "was it slow an hour ago" is a question only a real time-series store like Prometheus can answer, never metrics-server.
  • Not installed by default on kubeadm clusters; kubectl top failing outright, and an HPA stuck at <unknown>, are usually the same missing dependency, not two different bugs.
  • A container silently pinned at its CPU or memory limit (Lesson 11) produces zero restarts, zero failed probes, and zero events — it will not show up anywhere in Lesson 16's ladder. kubectl top pods --containers is what finds it.
  • Run metrics-server and Prometheus together on real clusters — they solve different problems (fast point-in-time vs. history/alerting), and dropping either one leaves a real gap.
Stuck, or got a different result than "Expected result" above? Paste the exact kubectl top output back to your teacher — the actual numbers, next to what the manifest says the limit is, are the most useful thing you can bring back from a real slow-app investigation.
