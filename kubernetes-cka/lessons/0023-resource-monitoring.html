Resource monitoring

Lessons 15-16 diagnosed Pods and nodes that were visibly broken — CrashLoopBackOff, Pending, failed probes. This lesson is for the case with no error at all: the cluster is technically healthy, but something is slow, and you need real numbers, not a guess.

Mental model: metrics-server is a light gauge, not a data logger — it asks every kubelet "what's your CPU/memory right now" and keeps the answer in memory briefly. Nothing is stored, nothing has history. That predicts why it's also Lesson 22's single dependency: an HPA's thermostat needs a live sensor reading, not a historical chart, which is exactly what this component is built to provide and nothing more.

Where this fits

kubelet (every node)
   │  Summary API
   ▼
metrics-server   ← you are here (point-in-time only, no history)
   │
   ├─→ kubectl top          (you, reading it directly)
   └─→ HorizontalPodAutoscaler (Lesson 22, reading it automatically)

kubectl top

kubectl top nodes
kubectl top pods --containers
kubectl top pods -n kube-system

This only works because metrics-server is running, scraping each kubelet's Summary API. On a kubeadm cluster, unlike most managed platforms, it isn't installed by default.

When it doesn't work

If metrics-server isn't installed or isn't healthy, kubectl top fails outright — no numbers, a metrics-API-unavailable error. Why the same fix underlies two different symptoms: Lesson 22's HPA and this lesson's kubectl top both depend on exactly one component; when it's missing, one shows <unknown> and the other errors outright, but the root cause and the fix are identical.

A kubeadm-specific gotcha: metrics-server's Pod can CrashLoop because it can't verify kubelets' self-signed certs — the narrow, lab-only fix is --kubelet-insecure-tls, worth recognizing, not something to use in production without understanding the trust you're giving up.

Try it

Q1. kubectl top pods returns an error, but every Pod is Running and Ready. What's actually wrong?

Nothing wrong with the Pods — metrics-server is missing or unhealthy. Check kubectl get pods -n kube-system | grep metrics-server and its logs, same ladder as Lesson 16.

Now, before revealing: a user reports the app "feels slow" — no failed probes, no restarts, no events. What's your first command, and what would point at a resource problem specifically?

Reveal the answer

kubectl top pods --containers for that app first. A container pinned near its CPU limit (Lesson 11) with no crashes is a classic silent slowdown — describe/events show nothing failed, because nothing did; it's just starved.

A controlled failure

kubectl top pods 2>&1 | head -3

Predict first: on a fresh kubeadm cluster with nothing extra installed, does this work out of the box? Observe: no — an error naming the metrics API as unavailable, on a completely healthy cluster with every Pod Running. This is the exact same silent-dependency shape as Lesson 8's Ingress and Lesson 22's HPA: the consuming object/command is fine, the thing underneath it is simply absent.

Production best practices

Production note: metrics-server gives point-in-time numbers only — for dashboards, alerting, and historical trends, that's Prometheus's job, a separate tool entirely, not a bigger version of this one.

Exam & interview notes

Interview Q: "An HPA shows <unknown> and kubectl top also fails. Are these two separate bugs?" A: No — almost certainly one root cause, metrics-server missing or unhealthy, surfacing as two different symptoms in two different consumers of the same data source.

Recap
  • metrics-server gives point-in-time numbers only — no history, that's a separate tool's job (Prometheus).
  • Not installed by default on kubeadm clusters — kubectl top failing outright usually means this, not a Pod problem.
  • The same missing dependency explains both a failing kubectl top and an HPA stuck at <unknown>.
