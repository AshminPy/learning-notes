etcd backup/restore, cluster upgrades, and TLS certificates

On a managed cluster, Google runs etcd backups, node upgrades, and cert rotation for you — invisible. On a self-managed kubeadm cluster (what the exam runs), these jobs land on you. They're graded on exact command syntax — wrong flags, command fails, no partial credit.

Simple picture: etcd is the cluster's only filing cabinet. Every object — Pods, Secrets, everything — is a piece of paper inside it. Lose the cabinet with no backup, and every record is gone, not just "some pods restart."

etcd backup — etcdctl snapshot save

Tool is etcdctl, with ETCDCTL_API=3 set. etcd's connections use mutual TLS, so the backup command needs to authenticate like any other client.

Try it yourself — before reading on

Without looking anything up: what flags does etcdctl snapshot save need against a real, TLS-secured etcd, and why does each exist?

Reveal the reference command

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=<trusted-ca-file> \
  --cert=<cert-file> \
  --key=<key-file> \
  snapshot save <backup-file-location>
  • --endpoints — which etcd member to talk to (default 127.0.0.1:2379, the local one).
  • --cacert — verifies it's really talking to etcd, not an impostor.
  • --cert / --key — proves the client is authorized. Mutual TLS: both sides check each other.

On kubeadm those three files are usually under /etc/kubernetes/pki/etcd/. If unsure, kubectl -n kube-system describe pod etcd-<node> shows the exact mounted paths.

Back it up on a routine, before you need it — not as a panic response.

etcd restore — the gotcha

Restore uses etcdutl (not etcdctl — snapshot restore there is deprecated).

Q1. Does restore overwrite the live, running data directory — or something else?

It creates a brand-new directory, never touches the running one. etcdutl --data-dir <new-dir> snapshot restore snapshot.db.

You then have to point etcd at the new directory and restart:

  • New path: edit the etcd static Pod manifest (/etc/kubernetes/manifests/etcd.yaml), change the etcd-data hostPath, then delete the etcd pod or restart kubelet to recreate it.
  • Same path: stop etcd and delete the old directory first — etcdutl refuses to restore into a directory that already has data.

Order matters: stop all API server instances → restore etcd → restart API servers. Also restart scheduler, controller-manager, kubelet after — they may hold stale state.

Cluster upgrades with kubeadm

  • No skipping minor versions. 1.35 → 1.37 means going through 1.36 first, even on one node.
  • Control plane first, workers last, one node at a time — never all at once, so the cluster keeps serving traffic.

Try it yourself — before reading on

From memory: what's the drain/uncordon pattern around each node, and why per-node rather than all-at-once?

Reveal the reference sequence

# --- first control-plane node ---
kubeadm upgrade plan
kubeadm upgrade apply v1.x.y
kubectl drain <node> --ignore-daemonsets
# upgrade kubelet + kubectl, then:
systemctl daemon-reload
systemctl restart kubelet
kubectl uncordon <node>

# --- each additional control-plane node ---
kubeadm upgrade node
kubectl drain <node> --ignore-daemonsets
# upgrade kubelet + kubectl, restart kubelet
kubectl uncordon <node>

# --- each worker node, one at a time ---
kubectl drain <node> --ignore-daemonsets
kubeadm upgrade node
# upgrade kubelet + kubectl, restart kubelet
kubectl uncordon <node>

drain evicts Pods so they get rescheduled elsewhere first — same rolling-upgrade idea as a Deployment, applied to nodes.

Version skew — the short version

  • kube-apiserver replicas: within 1 minor version of each other.
  • kubelet / kube-proxy: never newer than apiserver, up to 3 minors older.
  • controller-manager / scheduler / cloud-controller-manager: never newer than apiserver, ~1 minor older.
  • kubectl: within 1 minor version either side of apiserver.

apiserver goes first because everyone else's allowed range is defined relative to it.

TLS certificates

Control-plane components trust each other only via mutual TLS. kubeadm init generates the whole tree under /etc/kubernetes/pki — certs valid 1 year, CA certs 10 years. On a long-lived cluster, expiry is a real event.

Q. What command shows how much time is left before certs expire?

kubeadm certs check-expiration — lists every managed cert with expiry date and signing CA.

Fix: kubeadm certs renew <cert-name> or renew all. Re-signs with the existing CA. Doesn't hot-reload — restart the affected static Pods after (move the manifest out of /etc/kubernetes/manifests/ and back). kubelet.conf is separate — kubeadm sets up automatic rotation for it already.

Retrieval practice — no peeking

Q1. What's the general node order for a kubeadm upgrade?

First control-plane node (plan → apply) → additional control-plane nodes (upgrade node) → workers one at a time, each drained before and uncordoned after.

Q2. Why does an etcd backup need TLS flags at all?

--cacert verifies the real etcd server. --cert/--key prove the client is authorized. Without mutual TLS, anyone reaching the endpoint could read or corrupt cluster state.

Recap
  • etcd holds all cluster state — back it up routinely. Restore creates a new data directory, never overwrites the live one; you repoint etcd's manifest and restart.
  • Upgrades go control plane first, workers last, one node at a time, drain before / uncordon after. Never skip a minor version.
  • kubeadm certs check-expiration reports; renew all re-issues — then restart the affected static Pods.
