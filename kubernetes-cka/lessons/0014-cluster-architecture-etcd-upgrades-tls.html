etcd backup/restore, cluster upgrades, and TLS certificates

Lesson 13 named etcd "the database — lose it, lose the cluster's memory." On a managed cluster Google runs its backups, node upgrades, and cert rotation invisibly. On a self-managed kubeadm cluster — what the exam runs — these land on you, graded on exact command syntax with no partial credit.

Mental model: etcd is the cluster's only filing cabinet — every object, Pods, Secrets, everything, is a piece of paper inside it. Lose the cabinet with no backup and every record is gone at once, not "some pods restart." That predicts why restore is deliberately paranoid: it never overwrites the live cabinet, only ever builds a new one you then swap in.

etcd backup — etcdctl snapshot save

etcd's connections use mutual TLS, so backing it up needs to authenticate like any other client:

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=<trusted-ca-file> \
  --cert=<cert-file> \
  --key=<key-file> \
  snapshot save <backup-file-location>

--cacert verifies it's really etcd, not an impostor; --cert/--key prove the client is authorized — both sides check each other. On kubeadm those three files are usually under /etc/kubernetes/pki/etcd/.

Try it

Q1. Does restore overwrite the live, running data directory?

No. It creates a brand-new directory: etcdutl --data-dir <new-dir> snapshot restore snapshot.db. You then repoint etcd's static Pod manifest at the new directory.

Now, from memory: write the drain/uncordon pattern for a kubeadm upgrade, and why per-node rather than all-at-once. Try before revealing.

Reveal the reference sequence

# first control-plane node
kubeadm upgrade plan
kubeadm upgrade apply v1.x.y
kubectl drain <node> --ignore-daemonsets
# upgrade kubelet + kubectl, then:
systemctl daemon-reload && systemctl restart kubelet
kubectl uncordon <node>

# each additional control-plane node, then each worker, one at a time
kubeadm upgrade node
kubectl drain <node> --ignore-daemonsets
# upgrade kubelet + kubectl, restart kubelet
kubectl uncordon <node>

Common mistake: skipping a minor version (1.35 → 1.37 directly) — kubeadm requires going through 1.36 first, even for a single node.

A controlled failure

Prove restore doesn't touch the running directory, without risking real cluster data — inspect, don't execute, on a real cluster:

kubectl -n kube-system describe pod etcd-<node> | grep -A2 "Mounts:"

Predict first: if etcdutl snapshot restore is pointed at a brand-new directory, does the currently-running etcd notice or change at all mid-command? Observe: no — restore only ever writes files to disk; nothing happens to the live process until you edit the static Pod manifest to point at the new directory and it gets recreated. That's why the "gotcha" exists: forgetting that second step means the restore did nothing observable.

Production best practices

Production note: back up etcd on a routine schedule, not as a panic response — and restore order matters: stop all API server instances → restore etcd → restart API servers → restart scheduler/controller-manager/kubelet, since they may hold stale state from before the restore.

Version skew, briefly: apiserver upgrades first because everyone else's allowed range is relative to it — kubelet/kube-proxy up to 3 minors older, controller-manager/scheduler ~1 minor older, kubectl within 1 minor either side.

TLS certificates

Control-plane components trust each other only via mutual TLS. kubeadm init generates the whole tree under /etc/kubernetes/pki — certs valid 1 year, CA certs 10 years.

kubeadm certs check-expiration   # lists every managed cert, expiry, signing CA
kubeadm certs renew all          # re-signs with the existing CA — doesn't hot-reload,
                                  # restart the affected static Pods after

Exam & interview notes

Core to Cluster Architecture, Installation & Configuration (25%) — high-value, syntax-graded tasks.

Interview Q: "You need to restore etcd from a backup on a live cluster. What's the biggest risk if you get the order wrong?" A: Restoring into the live data directory instead of a fresh one, or restarting API servers before the restore completes — either corrupts state instead of replacing it cleanly. etcdutl refuses to restore into a directory that already has data specifically to prevent this.

Recap
  • etcd holds all cluster state — back it up routinely. Restore always creates a new directory, never overwrites the live one.
  • Upgrades go control plane first, workers last, one node at a time, drain before/uncordon after. Never skip a minor version.
  • kubeadm certs check-expiration reports; renew all re-issues — then restart the affected static Pods.
