etcd backup/restore, cluster upgrades, and TLS certificates

On GKE Autopilot, Google runs the control plane for you — etcd backups, node upgrades, certificate rotation, all invisible. That's exactly why this lesson matters: on a self-managed kubeadm cluster (which is what the CKA exam runs), these three jobs land on you. They're also some of the highest-value exam tasks, because they're graded on exact command syntax, not on understanding alone.

Tied to your mission: etcd backup/restore is one of the most likely tasks to appear on the exam verbatim. Get the flags wrong and the command fails outright — there's no partial credit for "close enough" syntax.

Why etcd is the one thing you can't get wrong

etcd is Kubernetes' backing store — every object (Pods, Secrets, ConfigMaps, RBAC bindings, everything) lives there as key-value data. The API server is stateless; it reads and writes through to etcd. Lose etcd's data with no backup, and you've lost the entire cluster's state — not just "some pods restart," but every object definition is gone. This is why etcd backup is treated as a first-class exam skill rather than a footnote.

etcd backup — etcdctl snapshot save

The tool is etcdctl, and you must set ETCDCTL_API=3 — older API versions have a different command set. Because etcd's client connections are secured with mutual TLS, a snapshot command against a real cluster needs to authenticate the same way any other etcd client would: a CA certificate to verify the server, and a client cert/key pair to prove who's asking.

Try it yourself — before reading on

Without looking anything up: what flags does etcdctl snapshot save need to talk to a real, TLS-secured etcd cluster, and why does each one exist? Write your attempt down — the endpoint, and the three TLS-related flags — before revealing the answer.

Reveal the reference command

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=<trusted-ca-file> \
  --cert=<cert-file> \
  --key=<key-file> \
  snapshot save <backup-file-location>

What each flag is for:

  • --endpoints — which etcd member to talk to (defaults to 127.0.0.1:2379, the local member — fine on a control-plane node where etcd runs as a static pod).
  • --cacert — the CA certificate, so etcdctl can verify it's really talking to etcd, not something else.
  • --cert / --key — the client's own certificate and key, so etcd can verify etcdctl is an authorized client. This is mutual TLS — both sides authenticate each other.

On a real kubeadm cluster, those three file paths are usually /etc/kubernetes/pki/etcd/ca.crt, /etc/kubernetes/pki/etcd/server.crt, and /etc/kubernetes/pki/etcd/server.key — but don't memorize the paths blindly. If you're ever unsure where they live, kubectl -n kube-system describe pod etcd-<node-name> shows the exact paths mounted into the etcd static pod.

Take the backup before you need it — as routine maintenance, not as a panic response. If etcd is already broken, it's too late to snapshot it.

etcd restore — the gotcha

Restore uses a different tool: etcdutl (the disk/data-file tool, not the network client — etcdctl snapshot restore still works but is deprecated since etcd 3.5 and is being removed in 3.6, so learn etcdutl).

Q1. When you run a restore, does it overwrite the live, running etcd data directory in place — or does it do something else? Think about it before revealing.

It creates a brand-new data directory — it never touches the running one in place. The command is etcdutl --data-dir <new-dir-location> snapshot restore snapshot.db, where <new-dir-location> is a fresh directory the command creates during restore.

That's the real trap: running snapshot restore does nothing to your live cluster by itself. You then have to point etcd at the new directory and restart it:

  • If you restore to a new path — edit the etcd static pod manifest (/etc/kubernetes/manifests/etcd.yaml), change volumes.hostPath.path for the etcd-data volume to the new directory, then either delete the etcd pod (kubectl -n kube-system delete pod <etcd-pod-name>) or restart the kubelet so the static pod gets recreated against the new data.
  • If you want to reuse the same path — you must delete the old directory and stop the etcd process first, since etcdutl won't restore into a directory that already has data.

Kubernetes' own docs are blunt about the blast radius here: if the API server is still running, don't attempt a restore. The correct order is stop all API server instances → restore state in etcd → restart the API servers. The project also recommends restarting kube-scheduler, kube-controller-manager, and kubelet afterward, since they may be holding onto stale state.

Cluster upgrades with kubeadm

Two hard rules shape every upgrade:

  • You cannot skip minor versions. Going from 1.35 to 1.37 means upgrading through 1.36 first — one minor version at a time, even on a single-node cluster. This is a Kubernetes API-deprecation policy, not a kubeadm limitation.
  • Control plane first, workers last, one node at a time. You never upgrade everything simultaneously — each worker gets drained, upgraded, and uncordoned individually so the cluster keeps serving traffic throughout.

The general order

  1. First control-plane node: upgrade the kubeadm package itself → kubeadm upgrade plan (dry-run, shows what's possible) → kubeadm upgrade apply v1.x.y (does the actual upgrade) → drain the node → upgrade kubelet/kubectl packages → restart kubelet → uncordon.
  2. Additional control-plane nodes (HA clusters): same package upgrade, but run kubeadm upgrade node instead of upgrade apply — that command already ran once against the cluster.
  3. Each worker node, one at a time: drain → upgrade the kubeadm package → kubeadm upgrade node (with --kubelet-version if going through the older node-config flow) → upgrade kubelet/kubectl packages → restart kubelet → uncordon.

From memory: what's the drain/uncordon pattern around each node in this sequence, and why does it matter that it's per-node rather than all-at-once? Write it down, then reveal.

Reveal the reference sequence

# --- first control-plane node ---
kubeadm upgrade plan
kubeadm upgrade apply v1.x.y
kubectl drain <node> --ignore-daemonsets
# upgrade kubelet + kubectl packages, then:
systemctl daemon-reload
systemctl restart kubelet
kubectl uncordon <node>

# --- each additional control-plane node ---
kubeadm upgrade node
kubectl drain <node> --ignore-daemonsets
# upgrade kubelet + kubectl, restart kubelet
kubectl uncordon <node>

# --- each worker node, one at a time ---
kubectl drain <node> --ignore-daemonsets
kubeadm upgrade node
# upgrade kubelet + kubectl, restart kubelet
kubectl uncordon <node>

kubectl drain evicts running Pods off the node so the upgrade/restart doesn't take workloads down with it — they get rescheduled elsewhere first. Doing this one node at a time (never all workers together) is what keeps the cluster serving traffic through the whole upgrade — the same rolling-upgrade idea you already know from Deployments, just applied to nodes instead of Pods.

Version skew — why you can't just upgrade whatever, whenever

Verified against the official version skew policy — this is the current rule set, and it's worth knowing at a "which direction is safe" level rather than memorizing every number:

  • kube-apiserver instances in an HA cluster: must be within 1 minor version of each other.
  • kubelet and kube-proxy: must not be newer than kube-apiserver, and may be up to 3 minor versions older.
  • kube-controller-manager, kube-scheduler, cloud-controller-manager: must not be newer than kube-apiserver, and should generally track within 1 minor version older.
  • kubectl: within 1 minor version older or newer than kube-apiserver.

This is why the upgrade order matters: kube-apiserver goes first because everything else's allowed version range is defined relative to it. Upgrade a kubelet past the apiserver's version and you've violated the policy in the wrong direction — kubelet is never allowed to be newer.

TLS certificates in a kubeadm cluster

Control-plane components don't trust each other by default — the API server, etcd, the scheduler, the controller-manager, and kubelet all authenticate to each other (and API server to etcd) using mutual TLS, the same pattern you just used for the etcd backup command. kubeadm init generates a whole tree of these certificates under /etc/kubernetes/pki. By default they're valid for 1 year (CA certs for 10 years) — which means on a long-lived self-managed cluster, expiry is a real operational event, not a theoretical one.

Q. What command tells you how much time is left before a kubeadm cluster's certificates expire?

kubeadm certs check-expiration — lists every managed certificate (apiserver, etcd-server, admin.conf, etc.) with its expiry date, residual time, and which CA signed it.

To fix an expiring (or already expired) certificate: kubeadm certs renew <cert-name>, or kubeadm certs renew all to renew everything at once. It re-signs using the existing CA under /etc/kubernetes/pki, reusing the current certificate's Common Name/SAN attributes. One easy-to-miss step: renewing doesn't hot-reload the running components — you have to restart the affected static pods afterward for the new certs to take effect (moving the pod's manifest out of /etc/kubernetes/manifests/ briefly and back is the usual trick, since static pods aren't managed through the API server and kubectl delete pod alone won't do it).

Note: kubelet.conf is handled separately — kubeadm sets kubelet up with automatic certificate rotation from the start, so it isn't part of the manual certs renew flow.

Retrieval practice — free recall, no peeking first

Q1. Does restoring an etcd snapshot overwrite the live, running data directory, or create a new one?

Creates a new one (via --data-dir). It never touches the running directory in place — you have to repoint etcd's static pod manifest at the new directory (or delete the old directory first if reusing the same path) and restart etcd for the restore to take effect.

Q2. What's the general node order for a kubeadm cluster upgrade?

First control-plane node (kubeadm upgrade plan/apply) → any additional control-plane nodes (kubeadm upgrade node) → worker nodes, one at a time, each drained before the upgrade and uncordoned after.

Q3. What command checks how soon a kubeadm cluster's certificates expire, and what's the difference between that and the renew command?

kubeadm certs check-expiration reports expiry dates only (read-only). kubeadm certs renew all (or a specific cert name) actually re-issues the certificates — after which the affected static pods need restarting to pick up the new certs.

Q4. Why does an etcd backup need TLS flags at all — what's each one protecting against?

--cacert lets etcdctl verify it's really talking to the real etcd server (not an impostor). --cert/--key let etcd verify etcdctl is an authorized client. Together that's mutual TLS — without it, anyone who can reach the endpoint could read or corrupt the entire cluster's state.
