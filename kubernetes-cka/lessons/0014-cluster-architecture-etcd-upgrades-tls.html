Kubernetes / CKA — Lesson 14 of 24

etcd backup/restore, cluster upgrades, and TLS certificates

Why this matters

Three separate ways a self-managed cluster dies, all covered in this one lesson. An etcd cluster with no tested restore process isn't backed up — it just has a file nobody has proven works, which is a company-ending risk the day disk failure or a bad kubectl delete on the wrong object takes etcd down for real. A kubeadm upgrade run out of order — workers before control plane, or a skipped minor version — can leave the whole control plane unable to talk to itself. And an expired certificate doesn't announce itself: it breaks trust between components silently, so what you see is kubectl hanging or a node going NotReady, not an error message that says "your cert expired." On a managed cluster (GKE Autopilot, EKS, AKS), the provider does all three jobs for you, invisibly. On the kubeadm cluster the CKA exam runs — and on plenty of real self-managed clusters — they land on you, and they're graded (or judged, in production) on exact execution, not partial credit.

Mental model: an etcd backup you've never restored from is a parachute you've never test-jumped. It looks fine folded in the bag. The only way to know it actually opens is to pull the cord — and by the time you genuinely need it, mid-outage, is the worst possible moment to discover it doesn't. This predicts something concrete: "we take nightly snapshots" is not a backup strategy on its own. A backup strategy is "we take nightly snapshots and we've restored one, on a disposable cluster, recently enough to trust the runbook still matches reality." If you can't say the second half, assume the first half is decoration.

Core concepts: etcd backup

etcd is the cluster's only real database — every object this course has covered (Pods, Secrets, RBAC bindings, all of it) is a key in etcd. The tool for talking to it directly is etcdctl, and on any real cluster its connections are TLS-secured, so the backup command has to authenticate like any other client.

Try it yourself — before reading on

Without looking anything up: what flags does etcdctl snapshot save need against a real, TLS-secured etcd, and why does each one exist?

Reveal the reference command

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=<trusted-ca-file> \
  --cert=<cert-file> \
  --key=<key-file> \
  snapshot save <backup-file-location>
  • --endpoints — which etcd member to talk to (default 127.0.0.1:2379, the local one).
  • --cacert — verifies you're really talking to etcd, not an impostor.
  • --cert / --key — proves the client is authorized to connect at all.

On a kubeadm cluster those three files are usually under /etc/kubernetes/pki/etcd/. If you're not sure, kubectl -n kube-system describe pod etcd-<node> shows the exact mounted paths the running etcd process is actually using — read them off the container, don't guess from memory.

Simple example: etcd doesn't just use TLS — it uses mutual TLS, meaning both sides authenticate, not only the server. kubeadm turns this on with --client-cert-auth=true (and --peer-client-cert-auth=true for member-to-member replication traffic), so etcd refuses any client that can't present a cert signed by its own CA. You can see the proof of this directly in kubeadm certs check-expiration's output: alongside etcd-server (the cert etcd presents to prove its identity), it separately tracks etcd-peer, etcd-healthcheck-client, and apiserver-etcd-client — certs that callers must present to etcd. One-way TLS would only ever need the first one.

Back it up on a routine schedule, before you need it — not as a panic response once something's already gone wrong.

Core concepts: etcd restore — the gotcha

Restore uses etcdutl, not etcdctl — etcdctl snapshot restore has been deprecated since etcd v3.5 and is slated for removal in v3.6, so this is a hard requirement now, not a style preference.

Q. Does restore overwrite the live, running data directory — or something else?

Something else: it creates a brand-new directory and never touches the running one. etcdutl --data-dir <new-dir> snapshot restore snapshot.db — the target directory is created by the restore itself, and etcdutl will refuse to run if that directory already has data in it.

Because of that, you then have to point etcd at the new directory and let it restart:

  • Restoring to a new path (the normal case): edit the etcd static Pod manifest (/etc/kubernetes/manifests/etcd.yaml), change the etcd-data hostPath to the new directory. The kubelet watches that file and recreates the Pod once it changes — same static-Pod mechanism from Lesson 13, just triggered by an edit instead of a fresh file.
  • Reusing the same path: stop etcd and delete the old directory first — etcdutl refuses to restore into a directory that already has data in it, by design, so a restore can never silently, partially overwrite a live store.

Order matters on a real restore: stop all kube-apiserver instances → restore etcd into its new directory → point etcd at it and let it come back up → restart the API servers. Restart scheduler, controller-manager, and kubelet afterward too — otherwise they can keep relying on state they cached from before the restore, instead of the restored data.

Core concepts: cluster upgrades with kubeadm

  • No skipping minor versions. "Skipping MINOR versions when upgrading is unsupported" is kubeadm's own wording — 1.35 → 1.37 means going through 1.36 first, on every node, even if you never intend to run a workload on 1.36 itself.
  • Control plane first, workers last, one node at a time — never all at once, so the cluster keeps serving traffic throughout.

Try it yourself — before reading on

From memory: what's the drain/uncordon pattern around each node, and why per-node instead of all-at-once?

Reveal the reference sequence

# --- first control-plane node ---
kubeadm upgrade plan
kubeadm upgrade apply v1.x.y
kubectl drain <node> --ignore-daemonsets
# upgrade kubelet + kubectl packages, then:
systemctl daemon-reload
systemctl restart kubelet
kubectl uncordon <node>

# --- each additional control-plane node ---
kubeadm upgrade node
kubectl drain <node> --ignore-daemonsets
# upgrade kubelet + kubectl packages, restart kubelet
kubectl uncordon <node>

# --- each worker node, one at a time ---
kubectl drain <node> --ignore-daemonsets
kubeadm upgrade node
# upgrade kubelet + kubectl packages, restart kubelet
kubectl uncordon <node>

drain evicts Pods so they get rescheduled onto still-healthy nodes first — the same rolling-upgrade idea you already know from a Deployment, applied here to nodes instead of Pods.

Version skew — the short version

  • kube-apiserver replicas: the newest and oldest must be within 1 minor version of each other.
  • kubelet / kube-proxy: never newer than kube-apiserver; may run up to 3 minor versions older.
  • kube-controller-manager / kube-scheduler / cloud-controller-manager: never newer than kube-apiserver; may be up to 1 minor version older.
  • kubectl: within 1 minor version either side of kube-apiserver — the one component allowed to be newer.

kube-apiserver goes first in the upgrade order because every other component's allowed range is defined relative to it, not the other way around.

Core concepts: TLS certificates

Every control-plane component trusts every other one only through mutual TLS. kubeadm init generates the entire certificate tree under /etc/kubernetes/pki on first bootstrap: leaf certs (apiserver, etcd, kubeconfig client certs, and so on) default to 365 days' validity, CA certs default to 3650 days (10 years). On a cluster you actually keep running for more than a year, expiry stops being theoretical.

Q. What command shows how much time is left before certs expire?

kubeadm certs check-expiration — lists every kubeadm-managed cert with its expiry date, residual time, and signing CA, plus a separate table for the CA certs themselves.

Fix: kubeadm certs renew <cert-name> for one cert, or kubeadm certs renew all for everything kubeadm manages. Renewal re-signs with the existing CA — it doesn't hot-reload into the running process, so you still have to restart the affected static Pods afterward (move the manifest out of /etc/kubernetes/manifests/, wait, then move it back so the kubelet recreates the container). kubelet.conf isn't in that list — kubeadm sets kubelet up for automatic certificate rotation separately, under /var/lib/kubelet/pki.

Simple example: you get more free cert renewal than you might expect. kubeadm upgrade apply (first control-plane node) and kubeadm upgrade node (every other node) both renew every certificate they manage on that node automatically, as part of the upgrade — --certificate-renewal=false is the flag if you ever need to opt out. That's a real side effect worth knowing on purpose: a cluster you upgrade on a normal cadence is quietly getting its certs refreshed for free along the way. A cluster that never gets upgraded gets neither benefit — no version updates, and no free renewal either.

Production example

Production note: no real platform team relies on someone remembering to type etcdctl snapshot save. The standard pattern is a scheduled job — a CronJob or a systemd timer running directly on each control-plane node, since it needs the etcd PKI files — that takes the snapshot and, in the same job, immediately ships the resulting file to object storage in a different account or region than the cluster itself. A snapshot sitting on the same disk as the cluster it backs up doesn't survive the failure modes that actually destroy clusters: disk failure, an accidental rm -rf, or the node itself being terminated. Retention is typically a rolling window (say, 7 daily plus 4 weekly), not "keep everything forever." Separately, mature teams wire kubeadm certs check-expiration into monitoring — a small script parsing the RESIDUAL TIME column into a metric, alerting at a fixed threshold like 30 days out — because kubeadm itself sets no warning threshold at all. The command just reports the number back to whoever remembers to ask; treating that as a standing alert instead of a manual habit is the actual production practice.

Hands-on exercise

This exercise goes deep on etcd backup — the failure scenario below covers TLS certs, and the troubleshooting workflow after that covers cluster upgrades, so each of the three topics gets one full worked example instead of three shallow ones.

Objective

Prove you can take a real, TLS-authenticated etcd snapshot against a live cluster — not just recite the four flags.

Scenario

Your team's runbook says "back up etcd before any risky change." You're about to find out whether you can actually execute that line yourself, without looking anything up.

Environment assumptions

Any kubeadm-created cluster — a real kubeadm cluster, or a kind cluster (kind bootstraps its control-plane node with kubeadm internally, so the same static Pod and PKI layout applies). You need kubectl access to the kube-system namespace. This exercise only takes a snapshot — it never touches the restore path — so there's nothing here that can damage a real cluster. Restore is destructive and belongs on a disposable cluster only; don't practice it here.

Commands

# find the etcd static pod's exact name (it's named etcd-<node>)
kubectl -n kube-system get pods -l component=etcd

# take the snapshot from inside the etcd pod itself — it already has
# etcdctl and the PKI files mounted, so there's nothing extra to install
kubectl -n kube-system exec etcd-<node-name> -- sh -c \
  "ETCDCTL_API=3 etcdctl \
   --endpoints=https://127.0.0.1:2379 \
   --cacert=/etc/kubernetes/pki/etcd/ca.crt \
   --cert=/etc/kubernetes/pki/etcd/server.crt \
   --key=/etc/kubernetes/pki/etcd/server.key \
   snapshot save /tmp/etcd-snapshot-$(date +%F).db"

# verify it actually exists and isn't suspiciously small
kubectl -n kube-system exec etcd-<node-name> -- ls -lh /tmp/etcd-snapshot-*.db

Expected result

snapshot save prints a line confirming the snapshot and its hash; the ls -lh shows a real file — typically several megabytes even on a near-empty lab cluster, because etcd stores its own schema and revision history, not just the handful of objects you've created.

Verification

A file that's a few hundred bytes, or missing entirely, is not a real snapshot — that usually means the command failed partway (wrong cert path, wrong endpoint) while still exiting without an obvious error. Check the command's own stdout/stderr, not just whether a file with the right name appeared.

Common failure

context deadline exceeded or connection refused almost always means a wrong --endpoints value or a mistyped cert path, not a broken etcd process.

Troubleshooting

If your cert paths aren't the defaults shown above, don't guess — run kubectl -n kube-system describe pod etcd-<node-name> and read the exact --cert-file, --key-file, and --trusted-ca-file arguments straight off the running container's command line.

Cleanup / rollback

kubectl -n kube-system exec etcd-<node-name> -- rm /tmp/etcd-snapshot-*.db — it's sitting in the container's own filesystem, not under /var/lib/etcd or /etc/kubernetes/pki, so there's nothing else to undo.

Production lesson

You just did half the job. A snapshot file you've never restored from is a hypothesis about a backup, not a backup — the only way to know it's actually usable is to run the restore, and that has to happen on a disposable cluster you're willing to break, never for the first time during a real outage. Schedule that as its own deliberate exercise, not this one.

Failure scenario: the reboot that exposed a year of neglect

This walkthrough goes deep on TLS certificates — a realistic incident built from a cluster nobody had touched since the day it was built.

  1. Day 0 A 3-node kubeadm cluster (1 control-plane, 2 workers) is built for a project. It ships successfully. Nobody upgrades it, renews anything on it, or sets up cert-expiration monitoring, ever again.
  2. Month 11 A routine OS patching window reboots all three nodes overnight — standard infrastructure maintenance, unrelated to Kubernetes itself.
  3. 09:14 On-call notices kubectl get nodes from their workstation hangs, then fails with a TLS error instead of returning node status.
  4. 09:18 SSHes into the control-plane node and tries kubectl get nodes locally — same failure: Unable to connect to the server: x509: certificate has expired or is not yet valid.
  5. 09:21 Checks kubelet: journalctl -u kubelet -n 50 shows repeated Failed to connect to apiserver and x509: certificate has expired errors, starting right at the reboot timestamp — not before.
  6. 09:25 Checks the containers directly with crictl ps — the apiserver, etcd, and controller-manager static Pod containers are all running. This isn't a crash; it's a trust failure between components that are otherwise fine on their own.
  7. 09:27 Runs kubeadm certs check-expiration. Several client/server certs — created 11 months ago against kubeadm's 365-day default — show 0 or negative residual time. The CA certs, on their 10-year default, are still fine.
  8. 09:30 Root cause: the certs expired quietly, on schedule, some weeks earlier. Nothing forced a fresh TLS handshake until the reboot restarted every process and made them reconnect from scratch — a common reason expired certs go unnoticed for a while is that long-lived connections established before expiry can keep working without renegotiating.
  9. 09:33 Fix applied: kubeadm certs renew all, then the affected static Pods are restarted by moving /etc/kubernetes/manifests out and back so the kubelet recreates them against the renewed certs.
  10. 09:41 Verified: kubeadm certs check-expiration shows a fresh ~365-day residual time across the board, kubectl get nodes succeeds, and kubelet logs are clean.

Troubleshooting workflow: a node won't come back healthy after a kubeadm upgrade

The general 10-step method, applied specifically to cluster upgrades — one node stuck after its turn in the upgrade sequence.

  1. Confirm the symptom. Run kubectl get nodes yourself. Is the node NotReady, stuck with SchedulingDisabled (never uncordoned), or Ready but on the wrong version? Each points somewhere different — don't diagnose from what the last upgrade looked like.
  2. Define scope. kubectl get nodes -o wide — is it only the node you just upgraded, or every node upgraded in this batch? A single bad node suggests a local mistake on that host; every node suggests a bad procedure or a bad package version.
  3. Check recent changes. Compare against your own upgrade runbook: did kubeadm upgrade node actually complete, did the kubelet/kubectl package upgrade run, did systemctl restart kubelet happen, was kubectl uncordon run afterward? Missing any one step produces a different symptom.
  4. Inspect the right state. kubectl get node <name> -o jsonpath='{.status.nodeInfo.kubeletVersion}' — does it show the version you just installed, or the old one? If it's still old, the package upgraded but the running process never restarted onto it.
  5. Check logs. journalctl -u kubelet -n 100 on the node itself — look for version-skew rejections, bad config left over from the package upgrade, or CNI plugin errors if the node's CNI wasn't upgraded alongside it.
  6. Form a hypothesis. For example: "the kubelet binary upgraded, but the service was never restarted, so it's still running the old process against a newer apiserver." Write it down before touching anything else.
  7. Test one variable. Confirm it directly — does the installed package version (dpkg -l kubelet or rpm -q kubelet) match the version reported in step 4? If they differ, that's confirmed, not assumed.
  8. Apply the safest fix. If it's a stale process, systemctl daemon-reload && systemctl restart kubelet — don't reinstall packages or touch other nodes while this one is still being diagnosed.
  9. Verify recovery. kubectl get node <name> back to Ready on the correct version with no SchedulingDisabled; kubectl get pods -o wide shows workloads actually scheduling onto it again, not just the node object looking healthy.
  10. Document and prevent recurrence. Add an explicit check to the runbook: assert the kubelet version matches the target immediately after the restart step, before running uncordon — never uncordon a node you haven't confirmed is actually upgraded.

Security note: etcd is where every cluster Secret actually lives — and by default it's exactly as unencrypted there as it is inside the API server: base64, not encryption (Lesson 6 covers why that distinction matters for who can read it). That means an etcd snapshot file isn't just a database backup, it's a complete, portable copy of every Secret in your cluster — API tokens, TLS private keys, database passwords — sitting in one file with no cryptographic protection unless you've separately configured EncryptionConfiguration on the API server. Treat every .db snapshot with the same handling rules as your most sensitive credential store: encrypt it the moment it leaves the node, restrict who can read the storage bucket it lands in, and never leave one sitting in a world-readable /tmp directory or attach it to a support ticket.

Common mistake: treating "we take etcd snapshots" as equivalent to "we have a backup." A snapshot nobody has ever restored from is untested — the first real restore attempt, done under incident pressure on a production cluster, is the worst possible time to discover a missing flag, a version mismatch, or a corrupted file.

Common mistake: skipping a minor version to save time on an upgrade — going straight from 1.35 to 1.37 on the theory that it's just two small bumps. kubeadm's own upgrade path does not support this; every control-plane node has to pass through 1.36 first, even if nothing is ever meant to run workloads on that intermediate version.

Common mistake: assuming certs are "someone else's problem" because kubeadm upgrade apply and kubeadm upgrade node renew every cert they manage by default. That's true — but only while you're actually upgrading. A cluster that goes a year without an upgrade also goes a year without that free renewal, which is exactly the trap the failure scenario above fell into.

Knowledge check

Q1. What's the general node order for a kubeadm upgrade?

First control-plane node (upgrade plan → upgrade apply) → additional control-plane nodes (upgrade node) → worker nodes one at a time, each drained before and uncordoned after.

Q2. Why does an etcd backup need TLS flags at all?

--cacert verifies you're talking to the real etcd, not an impostor. --cert/--key prove the client is authorized to connect. Without mutual TLS, anyone who could reach the endpoint could read or corrupt cluster state.

Q3. Why does etcdutl snapshot restore create a brand-new data directory instead of overwriting the one etcd is currently using?

So a restore can never partially overwrite a live, running store. Writing into a fresh directory means the old data is still intact and untouched until you deliberately repoint etcd at the new one — if anything goes wrong mid-restore, the original state hasn't been damaged.

Q4. Your kube-apiserver instances run v1.36. Per the version-skew policy, which kubelet version is NOT supported?

D. v1.32 — kubelet may be up to 3 minor versions older than the apiserver, so the oldest supported kubelet against a v1.36 apiserver is v1.33. v1.32 is 4 minors older, outside the supported range.

Q5. Which certificate is NOT covered by running kubeadm certs renew all?

C. The kubelet's client certificate under /var/lib/kubelet/pki is handled by kubeadm's separate automatic rotation mechanism, not by kubeadm certs renew — that command only touches the certs kubeadm itself manages under /etc/kubernetes/pki and the component kubeconfig files.

Production challenge

Objective

Read a real kubeadm certs check-expiration output and decide, on your own, what to renew and in what order — the way a senior engineer would hand this to you, with no further hand-holding.

Scenario

You inherited a 14-month-old kubeadm cluster with no cert-monitoring in place. Ahead of your team's quarterly DR test next week, you run a health check and get this:

CERTIFICATE                EXPIRES                  RESIDUAL TIME   CERTIFICATE AUTHORITY   EXTERNALLY MANAGED
admin.conf                 Oct 02, 2026 09:10 UTC   60d                                     no
apiserver                  Aug 12, 2026 09:10 UTC   9d              ca                      no
apiserver-etcd-client      Aug 12, 2026 09:10 UTC   9d              etcd-ca                 no
apiserver-kubelet-client   Aug 12, 2026 09:10 UTC   9d              ca                      no
controller-manager.conf    Oct 02, 2026 09:10 UTC   60d                                     no
etcd-healthcheck-client    Aug 12, 2026 09:10 UTC   9d              etcd-ca                 no
etcd-peer                  Aug 12, 2026 09:10 UTC   9d              etcd-ca                 no
etcd-server                Aug 12, 2026 09:10 UTC   9d              etcd-ca                 no
front-proxy-client         Aug 12, 2026 09:10 UTC   9d              front-proxy-ca          no
scheduler.conf              Oct 02, 2026 09:10 UTC   60d                                     no

CERTIFICATE AUTHORITY   EXPIRES                  RESIDUAL TIME   EXTERNALLY MANAGED
ca                      Jul 14, 2035 09:10 UTC   9y              no
etcd-ca                 Jul 14, 2035 09:10 UTC   9y              no
front-proxy-ca          Jul 14, 2035 09:10 UTC   9y              no

Environment assumptions

Today is August 3, 2026, per this output's own timestamps. You have root/sudo on every control-plane node and no maintenance window booked yet — decide whether this is "schedule it for next week" or "do it right now."

Commands

Work out your own answer first, then check it against this reference:

# the 9-day-residual certs are the ones actually at risk before the DR
# test — renew everything kubeadm manages in one pass rather than
# cherry-picking, since it's a single safe command and won't miss one:
kubeadm certs renew all

# then force every static pod that reads a renewed cert to pick it up —
# apiserver, controller-manager, scheduler, and etcd all qualify here:
mv /etc/kubernetes/manifests /etc/kubernetes/manifests.bak
sleep 20
mv /etc/kubernetes/manifests.bak /etc/kubernetes/manifests

# confirm it worked before declaring done:
kubeadm certs check-expiration
kubectl get nodes
kubectl get pods -n kube-system

Expected result

The reasoning matters more than the command here: the 9-day certs (apiserver, both etcd-signed client certs, etcd-peer, etcd-server, front-proxy-client, apiserver-kubelet-client) are the genuinely urgent ones — 9 days out with a DR test next week is too close for comfort. The admin.conf/controller-manager.conf/scheduler.conf kubeconfig certs at 60 days aren't on fire yet, but renewing everything in one renew all pass is simpler and safer than tracking two separate timelines by hand. The CA certs at 9 years need nothing at all.

Verification

Re-run kubeadm certs check-expiration after the restart — every managed cert should show a fresh ~365-day residual time, not just the ones that were about to expire.

Common failure

Renewing only the apiserver cert because it's the one you recognize, and leaving etcd-server/etcd-peer on their original 9-day clock — those failing independently a week later, mid-DR-test, is a worse outcome than doing the full renew all up front.

Troubleshooting

If kubectl get nodes still fails right after the manifest restart, give the kubelet's own file-check interval a few more seconds before assuming the renewal didn't take — moving manifests out and back only works once the kubelet actually notices the directory changed and re-reads it.

Cleanup / rollback

None needed if verification passes. Before touching a production cluster's certs for real, copy /etc/kubernetes/pki somewhere safe first (cp -r /etc/kubernetes/pki /etc/kubernetes/pki.bak-$(date +%F)) — kubeadm certs renew doesn't create that backup for you, and it's your fastest way back if a renewal goes wrong.

Production lesson

The senior-engineer move here isn't running renew all — anyone can look that command up. It's reading the RESIDUAL TIME column, deciding urgency yourself instead of waiting to be told, and acting before the DR test surfaces the gap as an outage instead of a scheduled maintenance window.

Recap
  • etcd holds all cluster state — including every Secret, in the same base64-not-encrypted form as everywhere else. Back it up routinely and treat the snapshot file itself as sensitive. A backup you've never restored from is untested, not proven.
  • Restore uses etcdutl (not etcdctl — deprecated for this) and always creates a new data directory; you repoint etcd's manifest at it and restart, never overwriting the live directory in place.
  • Upgrades go control plane first, workers last, one node at a time, drain before / uncordon after. Never skip a minor version. kubeadm upgrade apply/upgrade node also auto-renew managed certs — one more reason a cluster that never gets upgraded quietly accumulates risk.
  • kubeadm certs check-expiration reports; renew all re-issues — then restart the affected static Pods (move the manifest out of /etc/kubernetes/manifests and back) since renewal doesn't hot-reload.
