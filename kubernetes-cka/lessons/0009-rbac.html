RBAC — ServiceAccount, Role, RoleBinding

Every manifest so far has assumed permissions just work. They don't — something has to say who is allowed to do what. RBAC (Role-Based Access Control) is that layer: four object kinds that answer "who" (ServiceAccount, User, Group), "what's allowed" (Role), and "who gets it" (RoleBinding).

Tied to your mission: you already run this exact model daily, just under different names. A Kubernetes ServiceAccount is the direct equivalent of a GCP Service Account — a non-human identity a workload acts as, which is precisely what Workload Identity Federation binds together (GCP SA ↔ Kubernetes SA). A Role is a GCP IAM Role — a named bundle of permitted actions on specific resource types. A RoleBinding is an IAM binding — the thing that actually grants the role to a principal. Same three-part shape, same reasoning, different YAML.

The mental model

A ServiceAccount is an identity a Pod can act as — distinct from you, the human kubectl user. When a Pod's spec.serviceAccountName is set, every API call that Pod makes (via the mounted token) is authenticated as that ServiceAccount, not as you.

A Role is a namespaced list of permissions: which verbs (get, list, watch, create, update, patch, delete, …) are allowed on which resources (pods, configmaps, secrets, …). A Role by itself grants nothing — it's a definition sitting on a shelf, like an IAM role you defined but never attached to anyone.

A RoleBinding is what actually grants it — it links a Role to one or more subjects (a ServiceAccount, a User, or a Group). No binding, no access, no matter how the Role is written.

Role/RoleBinding are namespace-scoped — same shape as everything since Lesson 2. ClusterRole and ClusterRoleBinding are their cluster-scoped twins: same fields, no namespace on the object, and they can grant access across every namespace at once (or to genuinely cluster-scoped things like nodes). Once Role/RoleBinding click, ClusterRole/ClusterRoleBinding are the same pattern with the namespace boundary removed — the naming makes it obvious.

Try it first — before reading on

Q1. In your GCP IAM mental model, what is the Kubernetes equivalent of an IAM binding — the object that actually grants a role to a principal, as opposed to just defining what the role can do?

RoleBinding (or ClusterRoleBinding) — the Role/ClusterRole only defines permissions, the (Cluster)RoleBinding is what attaches it to a subject

Q2. A Pod is running as ServiceAccount ci-bot in namespace ci. What single kubectl command tells you whether it's allowed to delete pods in that namespace — without actually creating the Pod and watching it fail?

kubectl auth can-i delete pods --as=system:serviceaccount:ci:ci-bot -n ci — the --as flag impersonates the ServiceAccount using its full system:serviceaccount:<namespace>:<name> identity string; you need permission to impersonate to run it

Q3. What are the two fields inside a Role's rules entry, besides resources, that together define what's permitted?

apiGroups (which API group the resource belongs to — "" for the core group that pods lives in) and verbs (the allowed actions, e.g. get, list, watch)

Now build it — in your terminal, not here

Write three manifests by hand — no copy-paste. Together they should let a workload read Pods and nothing else:

  • a ServiceAccount, any name, in a namespace of your choice
  • a Role in the same namespace that allows get and list on pods only
  • a RoleBinding in the same namespace that connects your ServiceAccount to your Role

Apply all three, then before checking the answer below, run kubectl auth can-i get pods --as=system:serviceaccount:<namespace>:<your-sa-name> -n <namespace> yourself and confirm it says yes. Then try kubectl auth can-i delete pods --as=... the same way and confirm it says no — that's the "additive only, nothing implied" nature of RBAC proving itself.

Reveal the reference answer

apiVersion: v1
kind: ServiceAccount
metadata:
  name: pod-reader-sa
  namespace: default
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
  - kind: ServiceAccount
    name: pod-reader-sa
    namespace: default
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

Note the RoleBinding's roleRef — it points at the Role by name, and it's immutable: change your mind about which Role to bind, and you delete/recreate the RoleBinding rather than edit it in place. Also note apiGroups: [""] — that empty string is the "core" API group that pods, configmaps, and secrets live in; things like Deployments live under "apps" instead.

Recap
  • ServiceAccount = a non-human identity a Pod acts as (GCP IAM equivalent: Service Account)
  • Role = a namespaced bundle of allowed verbs on specific resources (GCP IAM equivalent: IAM Role)
  • RoleBinding = grants a Role to a subject — ServiceAccount, User, or Group (GCP IAM equivalent: IAM binding)
  • ClusterRole / ClusterRoleBinding = the same two objects, cluster-scoped instead of namespaced
  • RBAC is additive only — no deny rules; a missing grant means no access, full stop
  • kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<sa> is the exam-core command for testing/debugging permissions

Try solo: add watch to your Role's verbs and re-apply — no need to touch the RoleBinding. Then create a second Role that allows get/list on configmaps too, and bind it with a second RoleBinding to the same ServiceAccount. Confirm with can-i that permissions from both bindings now apply.
