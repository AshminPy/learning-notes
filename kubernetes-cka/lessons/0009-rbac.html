RBAC — ServiceAccount, Role, RoleBinding

Why this matters

Over-permissioned ServiceAccounts show up again and again in real Kubernetes security reviews as one of the most common findings — right alongside exposed dashboards and unpatched images. The reason it matters more than most misconfigurations: a Pod is compromised through the application running inside it (a dependency vulnerability, a deserialization bug, a leaked credential baked into an image) far more often than through Kubernetes itself. When that happens, the attacker doesn't get "into Kubernetes" in the abstract — they get exactly whatever identity that Pod's ServiceAccount carries, no more and no less. A compromised Pod running as default with no RBAC bound to it is a contained, boring incident. A compromised Pod whose ServiceAccount is bound to cluster-admin — because someone wired it up "temporarily" during a deploy pipeline setup and never came back to narrow it — is a full cluster compromise: every Secret, every ConfigMap, every workload, in every namespace, readable and writable by whoever now controls that one Pod. This lesson is about the exact objects that decide which of those two outcomes you get.

Mental model: RBAC is a whitelist with no ceiling and no override. Every permission check is one question — "is there an explicit rule, anywhere, that allows this?" — and nothing else. There's no deny list to add an exception to, no priority system between rules, and, this is the part that causes real incidents, no automatic expiry or built-in containment on anything you grant. If you bind a ServiceAccount to cluster-admin "just for now, I'll fix it later," Kubernetes enforces that grant identically on day one and day two hundred — nothing about the word "temporarily" is checked or enforced anywhere in the system. The only thing that ever narrows a grant is a human going back and editing or deleting the binding. Once you accept that, you can predict the failure mode before you see it: the most dangerous RBAC mistake usually isn't a missing grant — that breaks something loudly, immediately, and gets fixed the same day. It's an excess grant that works fine for months, silently, until the day something else goes wrong at the same time.

Core concepts

Four objects, in two pairs. A Role lists what's allowed:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: rbac-demo
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
ObjectScopeDefines
ServiceAccountNamespacedAn identity a Pod can act as, instead of a human user
RoleNamespacedAllowed verbs on resources, inside exactly one namespace
ClusterRoleCluster-wideAllowed verbs on resources — namespaced or cluster-scoped (Nodes, PersistentVolumes) — or non-resource URLs like /healthz
RoleBindingNamespacedGrants a Role or a ClusterRole to a subject, scoped to the RoleBinding's own namespace
ClusterRoleBindingCluster-wideGrants a ClusterRole to a subject, across every namespace in the cluster

The detail most people miss: a RoleBinding can reference a ClusterRole, not just a Role. This lets a platform team define one reusable rule set once, then apply it namespace-by-namespace without redefining it each time. What actually grants the access is still the RoleBinding, and the RoleBinding's own namespace is what bounds the grant — referencing a cluster-wide ClusterRole does not make the grant cluster-wide.

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-secrets
  namespace: payments
subjects:
  - kind: ServiceAccount
    name: reporting-sa
    namespace: payments
roleRef:
  kind: ClusterRole
  name: secret-reader
  apiGroup: rbac.authorization.k8s.io

This binding grants reporting-sa the rules in the cluster-scoped ClusterRole secret-reader — but only inside the payments namespace, because that's where the RoleBinding lives. A different ClusterRoleBinding to the same secret-reader ClusterRole would instead grant it everywhere, in every namespace, present and future.

How the decision actually gets made. Every API request goes through two separate checks: authentication (who are you?) and authorization (are you allowed to do this?). RBAC only answers the second question — by the time RBAC runs, your identity is already settled, either a User, a Group, or, for anything running inside the cluster, the exact string system:serviceaccount:<namespace>:<name>. The RBAC authorizer looks at every RoleBinding and ClusterRoleBinding in the cluster, keeps the ones naming your identity as a subject, follows each one's roleRef to its Role or ClusterRole, and unions every rule from all of them. If any single rule in that union matches the verb, resource, apiGroup, and (for namespaced resources) namespace of your request, it's allowed. If none do, it's denied — there is no separate deny rule to evaluate, because denial is just the absence of a matching allow.

kubectl auth can-i runs this exact check for you without ever attempting the action:

kubectl auth can-i <verb> <resource> --as=<identity> -n <namespace>

For a ServiceAccount, <identity> is the full system:serviceaccount:<namespace>:<name> string, not the ServiceAccount's short name. This is the single most useful command in this lesson: it tells you what RBAC will decide before you find out the hard way from a Forbidden error in a real workload.

ServiceAccounts and token mounting. Every namespace has a ServiceAccount named default whether you created one or not. Any Pod that doesn't set spec.serviceAccountName explicitly runs as that namespace's default ServiceAccount and inherits whatever RBAC is bound to it. Kubernetes mounts that ServiceAccount's credentials into the Pod automatically, via a projected volume at /var/run/secrets/kubernetes.io/serviceaccount/ (containing token, ca.crt, and namespace). Since Kubernetes v1.22 that token comes from the TokenRequest API rather than a static Secret — it has a bounded lifetime and is automatically invalidated roughly 60 seconds after the Pod's deletionTimestamp, not indefinitely valid the way old-style token Secrets were.

You control whether that mount happens at all with automountServiceAccountToken (a boolean, default true), settable on the ServiceAccount itself or on the Pod spec — if both are set, the Pod's value wins:

apiVersion: v1
kind: ServiceAccount
metadata:
  name: report-reader-sa
automountServiceAccountToken: false

Most workloads never call the Kubernetes API at all — a web server handling HTTP traffic has no reason to hold a token that can talk to the API server. For those, set automountServiceAccountToken: false and remove a credential that has no legitimate use but is still a hole to steal if the Pod is compromised.

Aggregated ClusterRoles. Instead of hand-maintaining one giant ClusterRole, you can label several smaller ClusterRoles and let the control plane combine their rules into an aggregate automatically:

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: monitoring-viewer
aggregationRule:
  clusterRoleSelectors:
    - matchLabels:
        rbac.example.com/aggregate-to-monitoring-viewer: "true"
rules: [] # filled in automatically — never edit this by hand
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: monitoring-viewer-pods
  labels:
    rbac.example.com/aggregate-to-monitoring-viewer: "true"
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]

The control plane continuously watches for any ClusterRole carrying the matching label and merges its rules into monitoring-viewer's empty rules: []. This is the same technique an operator's own CRD can use to plug a narrow, purpose-built ClusterRole into a broader one — without anyone hand-editing the broader role every time a new component ships.

Production example

Production note: a real 15-microservice namespace has 15 ServiceAccounts, one per Deployment, each with a Role scoped to exactly the resources that one service touches — not one shared default ServiceAccount for the whole namespace. The reason isn't tidiness: if checkout-api's Pod is compromised through a dependency vulnerability, the blast radius should be checkout-api's own permissions, not whatever the namespace's most-permissive workload happens to need. CI/CD ServiceAccounts get extra scrutiny in security reviews for exactly this reason: a deploy pipeline's ServiceAccount usually needs broad-looking verbs (create, update, patch, delete across several resource kinds) to actually do its job, which makes it look superficially similar to cluster-admin at a glance. A careful reviewer checks whether that breadth is scoped to only the namespaces the pipeline deploys to, or left cluster-wide "to be safe" — the second option is a standing privilege-escalation path, not a convenience.

Hands-on exercise

Objective

Prove, with kubectl auth can-i, that a Role grants exactly what you wrote — no more, no less — and nothing outside its own namespace.

Scenario

A monitoring script needs read-only access to Pods in one namespace. You'll build the ServiceAccount, Role, and RoleBinding by hand, then verify both the allowed and the denied paths.

Environment assumptions

Any cluster you can kubectl into (kind, minikube, or a real dev cluster); no existing namespace called rbac-demo.

Commands

kubectl create namespace rbac-demo
kubectl create serviceaccount pod-reader-sa -n rbac-demo
kubectl create role pod-reader --verb=get --verb=list --resource=pods -n rbac-demo
kubectl create rolebinding pod-reader-binding \
  --role=pod-reader --serviceaccount=rbac-demo:pod-reader-sa -n rbac-demo

kubectl auth can-i get pods --as=system:serviceaccount:rbac-demo:pod-reader-sa -n rbac-demo
kubectl auth can-i list pods --as=system:serviceaccount:rbac-demo:pod-reader-sa -n rbac-demo
kubectl auth can-i delete pods --as=system:serviceaccount:rbac-demo:pod-reader-sa -n rbac-demo
kubectl auth can-i get pods --as=system:serviceaccount:rbac-demo:pod-reader-sa -n default

Expected result

The first two checks return yes. The third returns no — delete was never granted. The fourth also returns no — the Role is namespaced to rbac-demo and grants nothing in default, even though it's the same ServiceAccount identity.

Verification

The exact yes/no pattern above is the proof. If the fourth check unexpectedly returns yes, something else in your cluster (a stray ClusterRoleBinding) is granting this identity access — that's worth investigating, not this lesson's behavior.

Common failure

Forgetting -n rbac-demo on the can-i check and testing against your current default namespace instead — this produces a false no that looks like a broken Role when the Role is actually fine.

Troubleshooting

If the first check returns no when you expected yes, run kubectl get rolebinding pod-reader-binding -n rbac-demo -o yaml and confirm subjects[0].name is exactly pod-reader-sa. A typo here applies with no validation error and produces silent, total zero access — nothing in the apply step warns you.

Cleanup / rollback

kubectl delete namespace rbac-demo

Production lesson

The identity string system:serviceaccount:<namespace>:<name> is exactly what appears in API server audit logs and in every Forbidden error message. Learn to read it now — in a real incident you'll be grepping for it under pressure, not looking it up.

Failure scenario

A realistic incident built directly from the mental model above — an excess grant with no expiry, sitting quietly until something else goes wrong.

  1. 2026-02-03 09:14 Setup: an engineer stands up the ci-deploy pipeline's ServiceAccount ci-deploy-sa in the ci namespace. The pipeline needs to create Deployments, Services, and ConfigMaps across several app namespaces. Under launch-week pressure, they bind it to the built-in cluster-admin ClusterRole via a ClusterRoleBinding instead of writing a scoped Role, with a comment: # TODO narrow this after launch.
  2. 2026-02-03 09:15 Launch ships on time. The TODO is never revisited — no ticket, no expiry, no calendar reminder attached to it.
  3. 2026-08-01 22:47 Symptom: a compromised dependency pulled in during a routine version-bump PR executes attacker code inside the CI pipeline's build step, with the ci-deploy-sa token mounted in that build Pod.
  4. 2026-08-01 22:52 Using that token, the attacker runs kubectl get secrets --all-namespaces. Because the binding is cluster-admin with no scoping, it succeeds against every namespace in the cluster, not just ci.
  5. 2026-08-02 06:03 Security tooling flags anomalous audit log volume: thousands of secrets get calls from a single ServiceAccount identity, across namespaces it has never touched before.
  6. 2026-08-02 06:20 On-call confirms with kubectl get clusterrolebindings -o json | jq: ci-deploy-sa has been bound to cluster-admin since February. Every Secret in the cluster — including production database credentials — must now be treated as compromised.
  7. 2026-08-02 07:00 Containment: the ClusterRoleBinding is deleted. Access is revoked immediately — RBAC is checked on every request, so there is no cached "already granted" state left to clean up. Every credential the ServiceAccount could read is rotated.
  8. 2026-08-02 11:00 Fix: ci-deploy-sa is rebound to a namespaced Role, defined only in the namespaces the pipeline actually deploys to, granting only the verbs (get, create, update, patch) and resources (deployments, services, configmaps) it uses.

Troubleshooting workflow

The general method, applied to "my workload is getting Forbidden errors":

  1. Confirm the symptom. Get the exact Forbidden error text from the client or kubectl logs — it already contains the identity, verb, resource, and namespace it was denied for. Don't paraphrase it from memory.
  2. Define scope. Is it one workload, or every workload sharing that ServiceAccount? kubectl get pods -n <ns> -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.serviceAccountName}{"\n"}{end}' shows who else carries the same identity.
  3. Check recent changes. kubectl get events -n <ns> --sort-by=.lastTimestamp, and check git history on the Role/RoleBinding manifests — was one edited, replaced, or deleted recently?
  4. Confirm identity, reproduce outside the app. kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<name> -n <ns> — use the exact verb, resource, and namespace from the error, not an approximation.
  5. Check Role vs. ClusterRole scope. Is the permission defined in a namespaced Role when the request is actually cluster-scoped, or vice versa? kubectl describe role <name> -n <ns> (or describe clusterrole) shows the rules Kubernetes actually stored, not what you think you applied.
  6. Check the RoleBinding's roleRef and subjects. kubectl get rolebinding <name> -n <ns> -o yaml — confirm roleRef.name matches an existing Role/ClusterRole exactly, and subjects[].kind/.name/.namespace match the calling identity exactly. A mismatch here applies with no error and produces total, silent zero access.
  7. Check namespace alignment. A Role and the RoleBinding that uses it must live in the same namespace, and that namespace must match the one the request is actually made against — the namespace the Pod runs in, not necessarily the namespace it's trying to act on.
  8. Form and test one hypothesis. For example: "this RoleBinding references a Role that was deleted in last week's cleanup." Confirm with kubectl get role <name> -n <ns> before changing anything.
  9. Apply the minimal fix, then re-verify. Add the missing rule or correct the binding, then re-run the exact can-i check from step 4 before touching the real workload.
  10. Document the root cause and prevent recurrence. Record which rule was missing and why. Consider whether an aggregated ClusterRole, or a policy check blocking wildcard verbs at admission time, would have caught this before it reached production.

Security note: default to least privilege — grant the specific verbs and resource names a workload actually uses, not verbs: ["*"] or resources: ["*"] "to make it work." A wildcard verb combined with a wildcard resource and a wildcard apiGroup is functionally equivalent to cluster-admin if bound broadly enough, and it is far more common than an actual cluster-admin binding because it looks like ordinary, forgettable YAML. Audit ClusterRoleBindings to cluster-admin on a schedule, not just after an incident: kubectl get clusterrolebindings -o json | jq -r '.items[] | select(.roleRef.name=="cluster-admin") | .metadata.name' lists every subject currently holding it — every one of those should have a documented reason to exist.

Security note: set automountServiceAccountToken: false on any ServiceAccount (or Pod) that never calls the Kubernetes API — most application workloads fall into this category. A mounted token an application never uses is pure downside: it adds nothing to the workload's function and gives an attacker who compromises that Pod one more credential to steal.

Common mistake: binding to the wrong subject kind or name — writing kind: User for what's actually a ServiceAccount, or a small typo in the ServiceAccount's name. The RoleBinding applies with no validation error, and the workload silently has zero access. The failure only surfaces later, as a Forbidden error in the running workload, often in production.

Common mistake: granting list/watch on Secrets cluster-wide "to make an operator work," instead of scoping to the one namespace and the specific Secret names it actually needs. This is one of the most common findings in real RBAC reviews, because it turns any compromise of that one identity into a full-cluster credential leak.

Common mistake: treating cluster-admin as a debugging shortcut — "just for now, I'll fix it later." Per the mental model above, there's no automatic expiry or containment on that grant, so "later" only happens if an audit or an incident forces it.

Decision guide

OptionUse whenAvoid whenTrade-off
Role + RoleBindingPermission only needs to apply within one namespace — the default case for app workloadsThe same permission must apply across many or all namespaces, or targets a cluster-scoped resource (Nodes, PersistentVolumes)Must be repeated in every namespace that needs it
ClusterRole + ClusterRoleBindingThe permission genuinely must apply cluster-wide — cluster admins, controllers watching every namespace, non-resource URLsOnly one or a few namespaces actually need itBroadest possible blast radius — grants access in every namespace, including ones created later
ClusterRole + RoleBinding (per namespace)You want one reusable, centrally-maintained rule set applied to several specific namespaces without redefining it each timeYou actually want the grant to auto-extend to future namespaces — it won't, each namespace needs its own RoleBindingLeast duplication of the three real options, but needs one RoleBinding per namespace, kept current as namespaces are added
ClusterRoleBinding as a shortcutAlmost never for a workload — reserve for the rare identity that must act everywhere, present and future, with no per-namespace maintenance"Just in case it needs another namespace later" — this is exactly the failure mode in the timeline aboveZero maintenance per new namespace, but zero containment if the credential is compromised

Default recommendation: start with a namespaced Role and RoleBinding for anything workload-facing. Only reach for a ClusterRole or ClusterRoleBinding when you can name the specific cluster-scoped resource or genuine cross-namespace requirement that forces it — never as a shortcut to avoid writing the same Role twice.

Knowledge check

Q1. What actually grants a Role to someone — as opposed to just defining what it allows?

A RoleBinding (or ClusterRoleBinding). The Role only defines permissions — the binding attaches it to a subject. No binding means no access, no matter what the Role allows.

Q2. What command checks whether ServiceAccount ci-bot in namespace ci can delete Pods — without actually testing it?

kubectl auth can-i delete pods --as=system:serviceaccount:ci:ci-bot -n ci

Q3. A ServiceAccount has automountServiceAccountToken: false. A Pod using that ServiceAccount sets automountServiceAccountToken: true directly. Which setting wins?

B. The Pod spec's value takes precedence over the ServiceAccount's setting — so this Pod's token would be mounted despite the ServiceAccount saying not to. (There's no rejection, and timing has nothing to do with it.)

Q4. A RoleBinding in namespace payments references a ClusterRole named secret-reader. Where does this actually grant read access to Secrets?

A. The RoleBinding's own namespace bounds the grant, even though the rules come from a cluster-scoped ClusterRole. (RoleBindings referencing ClusterRoles is a documented, supported pattern — not a rejection, and there's nothing kube-system-specific about it.)

Production challenge

Objective

Rewrite an inherited, over-permissioned Role down to the minimum a specific workload actually needs — then prove the rewrite with kubectl auth can-i, not by reading the YAML and assuming it's right.

Scenario

You inherit this Role, bound to a log-shipper ServiceAccount in namespace logging:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: log-shipper-role
  namespace: logging
rules:
  - apiGroups: ["*"]
    resources: ["*"]
    verbs: ["*"]

The log-shipper workload's actual, documented job: read Pod metadata and Pod logs in the logging namespace, to tag shipped log lines with Pod name and labels. It never creates, modifies, or deletes anything, and it never touches Secrets, ConfigMaps, or any resource outside logging.

Environment assumptions

A kind/minikube cluster. Create the namespace, ServiceAccount, Role, and RoleBinding above yourself first if they don't exist.

Commands

# 1. Confirm the current (dangerous) breadth of the inherited Role
kubectl auth can-i delete secrets --as=system:serviceaccount:logging:log-shipper -n logging
kubectl auth can-i delete pods --as=system:serviceaccount:logging:log-shipper -n logging

# 2. Rewrite the Role to only what log-shipper's documented job needs
kubectl apply -f - <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: log-shipper-role
  namespace: logging
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["pods/log"]
    verbs: ["get"]
EOF

# 3. Re-verify: the needed access still works, the dangerous access is gone
kubectl auth can-i get pods --as=system:serviceaccount:logging:log-shipper -n logging
kubectl auth can-i get pods/log --as=system:serviceaccount:logging:log-shipper -n logging
kubectl auth can-i delete secrets --as=system:serviceaccount:logging:log-shipper -n logging
kubectl auth can-i delete pods --as=system:serviceaccount:logging:log-shipper -n logging

Expected result

Step 1: both checks return yes — the wildcard Role hides its real breadth until you actually ask. Step 3: get pods and get pods/log return yes; delete secrets and delete pods return no.

Verification

All four step-3 checks together are the proof — confirming only the "yes" checks isn't enough, since a Role can be both correctly permissive and incorrectly permissive at the same time.

Common failure

Granting resources: ["pods"] but forgetting the separate pods/log subresource line — this grants Pod metadata access (so get pods succeeds) but not log content, so the workload's actual log-reading calls still fail with Forbidden even though the "obvious" permission is in place.

Troubleshooting

If delete secrets still returns yes after the rewrite, a second binding is probably still pointing at this ServiceAccount. kubectl get rolebindings,clusterrolebindings --all-namespaces -o json | jq '.items[] | select(.subjects[]?.name=="log-shipper")' finds every binding referencing this identity — RBAC unions all of them, so removing only one doesn't help if another survives.

Cleanup / rollback

kubectl delete namespace logging

Production lesson

Least privilege isn't a one-time YAML edit — it's a routine you repeat whenever a Role is inherited from someone else, because "it works" is not evidence that it's scoped correctly. A Role with ["*"] "works" for absolutely everything, which is exactly the problem it hides.

Recap
  • ServiceAccount = an identity a Pod acts as. Role/ClusterRole = allowed verbs on resources. RoleBinding/ClusterRoleBinding = what actually grants it — no binding, no access.
  • A RoleBinding can reference a ClusterRole; the RoleBinding's own namespace still bounds the grant. Only a ClusterRoleBinding grants cluster-wide.
  • RBAC is additive only — no deny rules, no automatic expiry, no built-in containment. A "temporary" cluster-admin binding is permanent until a human removes it.
  • Every namespace has a default ServiceAccount; unset serviceAccountName means a Pod inherits it. automountServiceAccountToken: false (Pod-level overrides ServiceAccount-level) removes an unused credential from workloads that never call the API server.
  • kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<name> -n <ns> is the fastest way to prove what RBAC actually allows, instead of reading YAML and guessing.
