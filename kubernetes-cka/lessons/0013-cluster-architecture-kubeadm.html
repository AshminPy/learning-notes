Cluster Architecture: kubeadm, static Pods, and the control plane

Why this matters

This is the first lesson in a new domain — Cluster Architecture, Installation & Configuration, 25% of the CKA exam — and the first time this course asks you to think about the machine that runs your objects, not just the objects themselves. Every lesson before this one quietly assumed kubectl and the API server were just... there. They aren't a law of nature — the apiserver is a process that something has to start, and that something can break it. When it does, kubectl breaks with it: kubectl is nothing more than an HTTP client for the apiserver, so no working apiserver means no working kubectl, full stop. On GKE Autopilot (or EKS, or AKS) you will likely never see this failure mode, because the provider owns and repairs the control plane before you're even paged. On a kubeadm cluster — the kind this exam tests, and the kind plenty of on-prem, edge, and homelab environments still run in production — that page is yours, and the only tools that still work when the apiserver itself is what's down are exactly the two this lesson teaches: static Pods and crictl.

Mental model: picture the control plane as a bank. etcd is the vault — the only place account balances (cluster state) actually live. Every other control-plane process — kube-apiserver, kube-scheduler, kube-controller-manager — is a teller: replaceable, holds no money of its own, and only ever reads or writes through the vault. Fire a teller mid-transaction (kill kube-scheduler while it's mid-decision) and the next teller picks up exactly where the vault says things stand — zero data lost, because the teller never held the money. This predicts something concrete: you can restart kube-apiserver, kube-scheduler, or kube-controller-manager at any moment, mid-operation, and the cluster's actual state won't lose a bit. Restart etcd carelessly — wipe its data directory, restore the wrong snapshot, run it split-brain with mismatched members — and there is no vault left to reconcile against, no matter how many tellers you have running.

Control plane, one line each

  • kube-apiserver — the front door. It's the only component with a client connection to etcd; every read and write from kubectl, every controller, and every kubelet goes through it first.
  • etcd — the database. A consistent, highly-available key-value store holding every object's state. It is the cluster's only durable memory — lose it with no backup, and there's nothing left to rebuild from.
  • kube-scheduler — watches for Pods that don't have a node assigned yet and picks one for them. It only decides — it never starts a container itself.
  • kube-controller-manager — runs the reconciliation loops: control loops that watch the cluster's shared state through the apiserver and drive it toward the desired state. Example: a Pod under a Deployment dies, its ReplicaSet controller notices and creates a replacement.
  • cloud-controller-manager — talks to the cloud provider's own API (load balancers, node tags, volumes). On GKE it still exists — Google just runs it for you instead of you running it yourself.

Node components, one line each

  • kubelet — runs on every node. Makes sure the containers described in the Pods assigned to that node are actually running, and reports status back up to the apiserver.
  • kube-proxy — maintains the network rules on each node (iptables/IPVS) that make Service traffic land on the right backend Pod.
  • Container runtime — containerd or CRI-O, the software that actually runs containers. The kubelet talks to it through the Container Runtime Interface (CRI), which is exactly why the runtime is swappable, and why crictl works the same way against either one.

How controllers actually know something changed: watch, not polling

When a Pod dies and its Deployment notices within roughly a second, that isn't kube-controller-manager checking kubectl get pods on a timer. Controllers and the kubelet find out about changes through the apiserver's watch mechanism: a client sends a normal HTTP GET request with a watch query parameter, the apiserver keeps that connection open, and it streams a change event down the same connection every time something relevant happens — instead of the client asking again and again. This is the API's own documented purpose for the mechanism: efficient detection of changes, as opposed to polling.

The full pattern controllers use is list-watch: do one normal list to get a starting snapshot of the objects they care about, plus a resourceVersion — a marker for "as of this point in etcd's history" — then open a watch starting from that resourceVersion and apply each incoming event to an in-memory copy. If the connection drops, the client re-watches from its last known resourceVersion, or falls back to a fresh list if too much time has passed for etcd to still have that history. This is also the missing piece behind the mental model above: kube-controller-manager and kube-scheduler hold no authoritative state of their own — their in-memory copy is just a cache rebuilt from a list-watch against the apiserver, which is exactly why killing and restarting either one loses nothing.

Don't confuse this with how the kubelet checks its own static Pod directory, covered next — that really is periodic filesystem scanning, not a watch, because there's no apiserver involved at that layer at all. The word "watch" gets used loosely for both in conversation; the mechanisms underneath are different.

kubeadm — bootstrapping a cluster

kubeadm init runs once, on the first control-plane node: it generates the cluster's TLS certificates, starts etcd and the control-plane components on that same node, and prints a kubeadm join command containing a bootstrap token. kubeadm join runs on every other machine — worker nodes use that bootstrap token to authenticate; additional control-plane nodes in an HA setup use a separate certificate-key value so they can pull down the shared cluster certificates too.

The chicken-and-egg problem: kubeadm init has to start etcd and kube-apiserver before a scheduler or API server exists to schedule anything onto a node. Static Pods are the way out of that loop — they need nothing but a kubelet and a file on disk.

Concretely, kubeadm init writes four manifest files into /etc/kubernetes/manifests/ on that node:

Manifest fileRuns
etcd.yamletcd (only for local/stacked etcd — an external etcd cluster won't have this file here)
kube-apiserver.yamlkube-apiserver
kube-controller-manager.yamlkube-controller-manager
kube-scheduler.yamlkube-scheduler

The "aha": these four files are the control plane, as far as the node is concerned. There's no Deployment, no ReplicaSet, and no scheduler decision behind any of them — that's exactly how the control plane manages to start itself before it exists.

Static Pods — kubelet running things on its own

A normal Pod's path: you kubectl apply it, the apiserver stores it in etcd, the scheduler picks a node, and that node's kubelet starts it. A static Pod skips almost all of that — it's a manifest file sitting on one specific node's disk, in a directory that node's kubelet checks directly (staticPodPath, default /etc/kubernetes/manifests; a URL-based variant, staticPodURL, exists too). No apiserver, no scheduler, no etcd write involved in creating it.

The kubelet processes every file in that directory that doesn't start with a dot — it doesn't filter by extension. Leave a backup copy named kube-apiserver.yaml.bak in the same directory and the kubelet will try to run that too, as its own separate Pod. Keep backups in a different directory entirely.

Because static Pods exist outside the apiserver's own records, the kubelet creates a read-only mirror Pod in the API purely so kubectl get pods has something to show you (named <pod>-<node>). The mirror Pod is cosmetic: kubectl can't edit it, and kubectl delete on it only removes the API-visible copy — the kubelet notices the manifest file is still on disk and recreates the mirror right away. To actually change or remove a static Pod, you edit or delete the file on the node itself.

Exam tip: a Pod name ending in a node's hostname inside kube-system (like kube-apiserver-controlplane) is your fastest clue that it's a static Pod's mirror, not something a Deployment created — a quick way to spot which node is acting as control-plane on an unfamiliar exam cluster.

crictl — one layer below kubectl

kubectl is only useful if the apiserver is reachable and healthy. If the apiserver's own static Pod is the broken thing, kubectl isn't a smaller or degraded tool at that point — it's a completely dead one, because every kubectl command is an HTTP request to the exact component that's down. crictl solves this by skipping the apiserver entirely and talking straight to the node's container runtime over its own socket — the same interface (CRI) the kubelet itself uses, so it works identically against containerd or CRI-O.

  • crictl ps / crictl ps -a — running (or all) containers on this node, at the runtime level.
  • crictl pods — the runtime's own view of Pods on this node.
  • crictl logs <container-id> — logs straight from the runtime, no apiserver in the path.
  • crictl exec / crictl inspect — run a command in, or inspect the low-level state of, a specific container.

Shortcut worth memorizing: kubectl operates at the API level, cluster-wide, and depends on the apiserver. crictl operates at the runtime level, one node only, and keeps working precisely when the apiserver is the thing that's down.

Production example

Production note: this is exactly why GKE Autopilot (and EKS, and AKS) exist. Google runs, patches, and upgrades your control plane — you never see a static Pod manifest, you can't crictl into a control-plane node because there isn't one you can reach, and a broken kube-apiserver.yaml edit simply isn't a failure mode you can cause, because you never get write access to that file. That's a genuinely good trade for most teams: no 3am page for etcd disk pressure, no coordinating a control-plane upgrade window, no certificate rotation to track. The cost is that this entire layer — everything in this lesson — becomes invisible to you, which is fine until the day you're handed a self-managed cluster (a vendor appliance, an edge deployment, a homelab, or exactly this exam) and none of your production instincts about "check the Pods, check the Deployment" apply, because the thing that's broken is one level below all of that.

Hands-on exercise

Objective

See the control plane's static Pods with your own eyes, and prove that every manifest file has exactly one matching mirror Pod — including one you create yourself, with no kubectl apply anywhere in the process.

Scenario

You want firsthand proof, not just this lesson's word, that the Pods you've been trusting kubectl get pods -n kube-system to show you are files on a disk, not objects a controller created.

Environment assumptions

A kubeadm-bootstrapped cluster. kind works — its control-plane node is a Docker container running a real kubelet, bootstrapped by real kubeadm, with the same manifest directory a bare-metal cluster has. This will not work on GKE Autopilot, EKS, or AKS — you have no node-level access to this layer there, which is the whole point of the production note above.

Commands

Save this as static-web.yaml first — same shape as any Pod manifest (Lesson 1), nothing new in the YAML itself:

apiVersion: v1
kind: Pod
metadata:
  name: static-web
spec:
  containers:
    - name: web
      image: nginx

# 1. Create a lab cluster (skip if you already have a kubeadm cluster to use)
kind create cluster --name arch-lab

# 2. List the static Pod manifests the control plane bootstrapped from
docker exec -it arch-lab-control-plane ls /etc/kubernetes/manifests/

# 3. Confirm each file has a matching, already-running mirror Pod
kubectl get pods -n kube-system -o wide

# 4. Copy your own manifest onto the node -- no kubectl involved
docker cp static-web.yaml arch-lab-control-plane:/etc/kubernetes/manifests/static-web.yaml

# 5. Watch it appear on its own
kubectl get pods -o wide --watch

Expected result

Step 2 lists four files: etcd.yaml, kube-apiserver.yaml, kube-controller-manager.yaml, kube-scheduler.yaml. Step 3 shows four matching Pods already Running in kube-system, named <component>-arch-lab-control-plane. Within roughly a minute of step 4, step 5 shows a new Pod, static-web-arch-lab-control-plane, appear on its own.

Verification

The count must match exactly: one manifest file, one mirror Pod, every time — including your new one. If the count is off, you've found a real discrepancy worth chasing, not this lesson's expected behavior.

Common failure

Writing static-web.yaml into your host machine's own /etc/kubernetes/manifests/ instead of the one inside the arch-lab-control-plane container. Nothing happens — the kubelet that matters is running inside that container, watching its own filesystem, not your laptop's.

Troubleshooting

If static-web never appears, exec into the node and run crictl ps -a to see whether a container attempt exists at all, then journalctl -u kubelet -n 30 --no-pager for the parse or validation error. This is the exact skill the Failure scenario and Production challenge below both depend on.

Cleanup / rollback

kind delete cluster --name arch-lab

Production lesson

Nothing above touched the API server to create a Pod. On a kubeadm cluster, "what's running in kube-system" is a statement about files on disk plus a kubelet loop, not about a Deployment or ReplicaSet — there usually isn't one at this layer.

Failure scenario

A realistic incident, built from the exact gap this lesson opened with: the apiserver is the thing that's broken, so kubectl can't help diagnose it.

  1. 02:14 Symptom: three separate health checks page on-call for "API unreachable." On the on-call's laptop, kubectl get nodes just hangs — no error, no response, eventually times out.
  2. 02:17 Check: on-call tries kubectl from a second machine on a different network, then from a terminal open directly on the control-plane node itself (single control-plane node, no HA). Same hang everywhere — rules out this laptop, its network, and its kubeconfig as the cause.
  3. 02:19 Check: on the control-plane node, crictl ps -a — talking straight to containerd, bypassing the apiserver entirely — shows no kube-apiserver container at all, not even a crashed one. etcd, scheduler, and controller-manager containers are all present and running.
  4. 02:22 Check: journalctl -u kubelet -n 50 shows repeated errors trying to load /etc/kubernetes/manifests/kube-apiserver.yaml — the kubelet can't even parse the file, so it never attempts to create the container in the first place.
  5. 02:24 Finding: cat /etc/kubernetes/manifests/kube-apiserver.yaml shows a change from 40 minutes earlier — a teammate hand-added an extra --audit-log-path flag for a compliance request and left the new line under-indented, so it fell outside the container's command: list. Invalid Pod spec, and no error surfaced anywhere near the edit, because saving a file has no admission check — it isn't kubectl apply.
  6. 02:27 Fix: restore the previous working copy of the file (kept in the team's config-management repo — the only reason a good copy existed), re-add the new flag with correct indentation, save.
  7. 02:29 Verify: crictl ps on the node shows a new kube-apiserver container, Running, within the kubelet's next scan. From the original laptop, kubectl get nodes returns immediately.
  8. 02:31 Root cause recorded: an un-reviewed, un-versioned hand-edit to a static Pod manifest on a production control-plane node, with no rollback path except a config-management copy that happened to exist.

Troubleshooting workflow

The general method, applied specifically to "the apiserver — or another control-plane component — seems down," where kubectl itself may not be a usable tool:

  1. Confirm the symptom. Try kubectl get nodes or kubectl version from at least two independent clients or networks. If every client hangs or times out the same way, this isn't a local kubeconfig, VPN, or single-laptop network problem.
  2. Define scope. One control-plane node, or several? On an HA cluster, check whether the other control-plane nodes still answer — if so, this is a single-node problem, not a full outage, and you have room to work carefully.
  3. Check recent changes. ls -la /etc/kubernetes/manifests/ on the affected node for a recent modification time, and check your config-management/git history for that path if manifests are tracked there. Static Pod edits leave no kubectl-visible audit trail — the filesystem timestamp is often the only clue.
  4. Inspect the right state — not kubectl. SSH or exec onto the affected control-plane node and run crictl ps -a. This talks straight to the container runtime and works whether or not the apiserver is alive.
  5. Pull logs at the layer that's actually broken. If the suspect container is missing entirely, check journalctl -u kubelet -n 50 — the kubelet logs why it couldn't create it. If the container exists but is crashing, crictl logs <container-id> shows its output directly, no apiserver required.
  6. Form a hypothesis. For example: "the kube-apiserver static Pod manifest has a YAML or flag error from a manual edit, so the kubelet can't start it at all."
  7. Test one variable. Read the live manifest file and diff it against a known-good copy (git, backup, or another control-plane node's copy on an HA cluster) before changing anything else.
  8. Apply the safest fix. Restore the known-good manifest content rather than guessing at the broken line — and don't touch etcd's data directory or any other component's manifest while you're still isolating the problem.
  9. Verify recovery. crictl ps shows the container Running and not restarting; only then confirm from a normal client that kubectl get nodes returns.
  10. Document root cause and prevent recurrence. "Un-reviewed hand-edit to a static Pod manifest" is the real root cause, not "API server was down" — the prevention is treating /etc/kubernetes/manifests/ as production code: version-controlled, reviewed, and never edited live without a rollback copy already in hand.

Security & reliability considerations

Security note: etcd being the cluster's only memory cuts both ways for security. Anyone who can reach etcd's client port and present a valid client certificate has the same effective access as full cluster-admin — direct etcd access reads and writes every object in the cluster, including every Secret, completely bypassing RBAC (RBAC is an apiserver-layer control; etcd has no concept of it). Kubernetes Secrets are stored in etcd only base64-encoded, not encrypted, unless you've explicitly turned on encryption at rest — base64 is an encoding, not a control. In practice: keep etcd on a private network segment reachable only by the control-plane nodes, require mutual TLS for every client, and never expose its port the casual way you might expose the apiserver's. Lesson 14 covers etcd backup and restore in depth — the short version here is that "only memory" also means "only copy" unless you're taking snapshots, so don't treat that as solved by this lesson.

Reliability note: treat every file under /etc/kubernetes/manifests/ as production code, because functionally it is — a saved edit takes effect with no review, no dry-run, and no diff shown to you, unlike every change you make through kubectl apply. Keep a version-controlled, known-good copy of each manifest off the node before you ever hand-edit one live.

Cost note: running your own control plane means you provision and pay for the control-plane nodes, their disks, and their operational time directly — and you're the one who gets paged to patch and upgrade them. A managed control plane (GKE Autopilot, EKS, AKS) folds that into the platform's pricing and operational responsibility instead; the trade-off is spelled out in the Decision guide below.

Common mistakes

Common mistake: reaching for kubectl first when the apiserver itself seems to be the thing that's down. kubectl is an HTTP client for the apiserver — if that's the broken component, every kubectl command will hang or error no matter how correctly you type it. Drop to crictl and the static Pod manifest files on the affected node instead.

Common mistake: assuming a static Pod edit needs kubectl apply to take effect. It doesn't — saving the file on disk is the deployment action, immediately, with no review step. This is exactly what makes hand-edited static Pod manifests so dangerous in production.

Common mistake: running kubectl delete pod on a static Pod's mirror Pod, expecting it to actually stop or remove the workload. It only deletes the read-only API-side copy; the kubelet sees the manifest file is still on disk and recreates the mirror Pod right away. To really remove a static Pod, delete or move the file on the node itself.

Knowledge check

Q1. Which component is the only one allowed to talk directly to etcd?

kube-apiserver. Everything else — scheduler, controllers, kubelets, kubectl — goes through it.

Q2. A Pod under a Deployment gets deleted by hand. Which component recreates it, and does the scheduler get involved again?

kube-controller-manager creates the replacement. Yes — the new Pod is unscheduled at first, so kube-scheduler assigns it a node like any other new Pod.

Q3. Does kube-controller-manager find out a Pod was deleted by polling the API server every few seconds, or some other way?

Neither guess — it watches. It opens a long-lived HTTP connection to the apiserver with a watch request and receives a stream of change events as they happen. Polling is what the kubelet's static Pod directory check does instead — a different mechanism, easy to conflate with this one.

Q4. You run kubectl delete pod on a static Pod's mirror Pod on a kubeadm control-plane node. What actually happens?

B. The mirror Pod is a read-only, API-visible copy of the real static Pod, which is defined by the file on disk — deleting the mirror doesn't touch the file, so the kubelet immediately notices the file is still present and recreates it. (A describes a bare Pod's behavior, not a static Pod's. C and D invent controllers that have no authority over static Pods — no scheduler or controller-manager involvement exists on this path.)

Production challenge

Objective

Given a hanging kubectl get nodes and no working kubectl access assumed, find and fix which control-plane component is broken using only crictl and the static Pod manifest files on the node.

Scenario

You're on-call. kubectl get nodes hangs from every client you try. This is a single-control-plane-node kubeadm (or kind) cluster — there's no second control-plane node to fail over to.

Environment assumptions

Reuse the arch-lab kind cluster from the hands-on exercise above, or any kubeadm cluster you can exec or SSH into as root. You need shell access to the control-plane node itself — that's realistic; a real 2am page gives you exactly that, not a working kubectl.

Commands

# Induce the failure yourself first, so you have something real to diagnose
docker exec -it arch-lab-control-plane cp /etc/kubernetes/manifests/kube-apiserver.yaml /root/kube-apiserver.yaml.bak
docker exec -it arch-lab-control-plane sed -i 's/^\(\s*\)- kube-apiserver/\1  - kube-apiserver/' /etc/kubernetes/manifests/kube-apiserver.yaml

# Now diagnose it as if kubectl were unusable -- crictl and files only
docker exec -it arch-lab-control-plane crictl ps -a
docker exec -it arch-lab-control-plane journalctl -u kubelet -n 30 --no-pager
docker exec -it arch-lab-control-plane cat /etc/kubernetes/manifests/kube-apiserver.yaml

Expected result

crictl ps -a shows no kube-apiserver container attempt at all (etcd, scheduler, and controller-manager still present and running). The kubelet log shows it failing to load or unmarshal the manifest. Reading the file back shows the broken indentation you introduced.

Verification

Restore the backup copy (cp /root/kube-apiserver.yaml.bak /etc/kubernetes/manifests/kube-apiserver.yaml inside the node), wait for the kubelet's next scan, then confirm crictl ps shows a new, Running kube-apiserver container — only then check that kubectl get nodes from your original client returns normally again.

Common failure

Spending the first 20 minutes checking firewalls, security groups, or VPN state because "hangs" feels like a network problem. A closed port usually refuses a connection quickly; a hang more often means something on the other end is alive but not answering — which is exactly what a kubelet stuck failing to start the apiserver looks like from outside.

Troubleshooting

If the sed command above doesn't reproduce a real break on your setup (YAML is forgiving about some whitespace), open the file in an editor instead and move the - kube-apiserver line under a different, wrong parent key. Any edit that makes the container spec unparsable will do — the diagnostic method is the point, not the exact typo.

Cleanup / rollback

kind delete cluster --name arch-lab

Production lesson

The entire diagnostic path above never once used kubectl. That's not a stylistic choice — it's the only path that exists when the apiserver is the broken component. A managed control plane never asks you to know this, until the day you're on a cluster where nobody does and something breaks anyway.

Recap
  • Control plane: apiserver (only front door to etcd), etcd (only durable state), scheduler (placement decisions only), controller-manager (reconciliation loops), cloud-controller-manager (cloud integration). Node: kubelet, kube-proxy, container runtime.
  • Controllers and the kubelet find out about API object changes via watch — a long-lived HTTP connection streaming events — not polling. The kubelet's own static Pod directory check, by contrast, really is periodic filesystem scanning — a different mechanism.
  • kubeadm init bootstraps the first control-plane node and generates four static Pod manifests (etcd.yaml, kube-apiserver.yaml, kube-controller-manager.yaml, kube-scheduler.yaml) in /etc/kubernetes/manifests/ — solving the chicken-and-egg problem of starting a control plane before one exists to schedule anything.
  • A static Pod's mirror Pod is read-only and cosmetic: kubectl delete on it does nothing lasting, and kubectl apply is never involved in changing one — editing the file on disk is the real deployment action.
  • crictl talks straight to the container runtime, bypassing the apiserver entirely — it's the tool that still works when the apiserver's own static Pod is the thing that's broken.
  • etcd is the cluster's only copy of its state and, by default, stores Secrets unencrypted (base64 only) — treat etcd network access as equivalent to cluster-admin, and take its backup seriously (Lesson 14).
