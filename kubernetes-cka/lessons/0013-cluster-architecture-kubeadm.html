Cluster Architecture: kubeadm, static Pods, and the control plane

New domain: Cluster Architecture, Installation & Configuration — 25% of the exam. Lessons 1-12 were about objects the API server manages. This lesson is about the machine that runs the API server itself — territory a managed cluster (GKE Autopilot, EKS) normally hides from you, which is exactly why it needs its own lesson.

Mental model: the control plane is a restaurant. The API server is the front counter — every order goes through it. etcd is the order ledger. The scheduler decides which table (node) an order goes to. Controllers are the manager, watching that what's on the floor still matches what was ordered. That predicts the one rule everything else in this lesson hangs on: nothing talks to the ledger except the front counter.

Control plane, one line each

  • kube-apiserver — the front door. Every read/write goes through it. Only it talks to etcd.
  • etcd — the database. Holds every object's state.
  • kube-scheduler — picks which node a new Pod runs on. Decides only, doesn't start anything.
  • kube-controller-manager — the reconciliation loops (Lesson 4's ReplicaSet controller lives here).
  • cloud-controller-manager — talks to the cloud provider (load balancers, node tags).

Node components, one line each

  • kubelet — runs on every node, the one component from Lesson 1 that watches Pods after creation.
  • kube-proxy — makes Service traffic (Lesson 3) actually reach the right Pod.
  • Container runtime — containerd or CRI-O, swappable via the CRI.

Try it

Q1. Which component is the only one allowed to talk directly to etcd?

kube-apiserver — scheduler, controllers, kubelets, kubectl all go through it, never etcd directly.

kubeadm and the bootstrap problem

kubeadm init runs once on the first control-plane node: generates TLS certs, starts etcd and the control plane there, prints a kubeadm join command for every other machine. Why it's built this way: there's a chicken-and-egg problem — init must start etcd and kube-apiserver before a scheduler or API server exists to schedule anything onto. Static Pods solve this.

A normal Pod: you kubectl apply, API server stores it, scheduler places it, kubelet starts it. A static Pod skips almost all of that — a manifest file sitting on one node's disk, in a folder that node's kubelet watches directly (default /etc/kubernetes/manifests). No API server, no scheduler involved.

The "aha": kube-apiserver, etcd, scheduler, and controller-manager on a kubeadm control-plane node are themselves usually static Pods — that's how the control plane starts itself before it exists to manage anything.

Because static Pods live outside the API server, kubelet creates a read-only mirror Pod so kubectl get pods can still show it (named <pod>-<node>). Deleting the mirror doesn't stop the real Pod — the file on disk is still the source of truth.

A controlled failure

On a kubeadm cluster (kind/minikube control-plane node), prove the mirror-Pod claim rather than trust it:

kubectl get pods -n kube-system | grep apiserver
kubectl delete pod kube-apiserver-<node-name> -n kube-system

Predict first: does deleting that Pod take down the API server? Observe: within seconds the exact same Pod reappears — you deleted the mirror, not the real thing, and the kubelet just re-mirrors the file that's still on disk. If this actually took the API server down, that's a strong signal it wasn't running as a static Pod on this cluster.

crictl — one layer below kubectl

kubectl needs the API server reachable. If the API server's own static Pod is broken, crictl talks straight to the container runtime instead — crictl ps (running containers, runtime level), crictl logs <id>. Shortcut: kubectl = API level, cluster-wide; crictl = runtime level, this node only, still works when the API server is down.

Production best practices

Production note: most teams never run kubeadm init themselves — managed control planes (GKE, EKS, AKS) hide this entirely. It's still core CKA material because self-managed clusters and on-call debugging of a broken control plane both require knowing what's actually running underneath.

Exam & interview notes

Core to Cluster Architecture, Installation & Configuration (25%) — one of the two largest domains.

Interview Q: "The API server is down and kubectl can't connect. How do you check container health on that node?" A: crictl ps/crictl logs directly on the node — they talk to the container runtime, not the API server, so they work even when kubectl can't.

Recap
  • kube-apiserver is the only front door to etcd — everything else watches the API server and reacts.
  • kubeadm init bootstraps the first control-plane node; kubeadm join adds every other node.
  • Static Pods (kubelet-watched manifest files, default /etc/kubernetes/manifests) are how the control plane bootstraps itself before an API server exists to schedule anything.
  • crictl debugs one layer below kubectl — works even when the API server is unreachable.

Confidence check — answer without looking back:

  • When would you reach for crictl instead of kubectl?
  • What happens if you delete a static Pod's mirror Pod via kubectl?
  • How would you verify whether a broken component is a static Pod or a normal one?
