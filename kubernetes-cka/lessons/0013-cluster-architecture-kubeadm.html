Cluster Architecture: kubeadm, static Pods, and the control plane

This lesson starts a new domain: Cluster Architecture, Installation & Configuration — 25% of the exam, second only to Troubleshooting (confirmed against the CNCF curriculum, see sources below). It's also a different kind of lesson for you specifically. Every lesson so far (Pod, Deployment, Service, PVC…) was about objects you already touch daily on GKE Autopilot. This one isn't. Autopilot is fully managed — Google runs the control plane, and you've never had a reason to see a static Pod, run kubeadm, or SSH into a node and poke at /etc/kubernetes/. Treat this as genuinely new territory, not a refresher.

Tied to your mission: the exam performance tasks in this domain expect you to reason about a cluster you can actually log into and inspect at the node level — something Autopilot deliberately hides from you in production.

The control plane, component by component

The control plane is a handful of separate processes. On a kubeadm cluster they usually run as Pods on the control-plane node(s) — you'll see why that's interesting further down.

  • kube-apiserver — the front door. Every read and write to the cluster — kubectl, the scheduler, every controller, every kubelet — goes through it as a REST API. It's also the only component that talks to etcd directly; nothing else is allowed to touch the database.
  • etcd — the cluster's database. A consistent, highly-available key-value store that holds every object's state: every Pod spec, every Secret, every ConfigMap, all of it. If etcd is gone, the cluster's memory is gone.
  • kube-scheduler — watches for Pods that exist but have no node assigned yet, and decides which node each one goes on (based on resource requests, affinity rules, taints/tolerations). It only decides — it doesn't start anything itself.
  • kube-controller-manager — runs the reconciliation loops. This is the part you've been relying on without naming it: when you create a Deployment with replicas: 3 and one Pod dies, it's a controller inside kube-controller-manager (the ReplicaSet controller) that notices the drift and creates a replacement. Node health, Jobs, ServiceAccounts — all reconciled the same way, by different controllers running in this one process.
  • cloud-controller-manager (optional) — the piece that talks to the cloud provider's API: provisioning a cloud load balancer for a LoadBalancer Service, tagging nodes, that kind of thing. On GKE this exists and runs, you just never manage it — Google does.

The node components

  • kubelet — the agent that runs on every node. It watches the API server for Pods assigned to its node, and tells the container runtime to actually start the containers. It's the one component that turns a scheduler's decision into a running process.
  • kube-proxy — runs on every node, implements Service networking. It's what makes a request to a Service's ClusterIP actually reach one of the backing Pods, usually via iptables or IPVS rules it maintains locally.
  • Container runtime — the actual software that runs containers (containerd, CRI-O). The kubelet talks to it through a standard interface called the CRI (Container Runtime Interface) — that's why Kubernetes doesn't care which runtime a node uses, as long as it speaks CRI.

One sentence to keep: kube-apiserver is the only front door, etcd is the only memory, and everything else is a loop watching the API server and reacting. Scheduler reacts to unscheduled Pods. Controllers react to drift from desired state. Kubelet reacts to Pods assigned to its node. Nothing talks to etcd except the API server.

Try it first — before reading on

Q1. Which component is the only one allowed to talk directly to etcd?

kube-apiserver. Every other component — scheduler, controllers, kubelets, kubectl — goes through the API server, never straight to etcd.

Q2. You create a Deployment with replicas: 3, then kubectl delete one Pod by hand. Which control plane component notices and creates a replacement — and does the scheduler get involved again?

kube-controller-manager (the ReplicaSet controller inside it) creates the replacement Pod object. Yes, the scheduler gets involved again — the new Pod starts unscheduled, same as any other new Pod, and kube-scheduler assigns it a node.

Q3. Once a Pod is assigned to a node, which node component actually calls the container runtime to start it?

kubelet — it watches the API server for Pods bound to its node, then talks to the container runtime (via the CRI) to actually start the containers.

How kubeadm bootstraps a cluster (conceptual, not a full walkthrough)

kubeadm is the standard tool for standing up a cluster from raw machines. You won't build a full cluster in this lesson — just know the shape of it, since "create and manage clusters using kubeadm" is a named line item in the exam curriculum.

  • kubeadm init — run once, on the first control-plane node. It generates the TLS certificates the components need to trust each other, starts etcd and the control plane components on that node, and prints a kubeadm join command (with a bootstrap token) for adding every other node.
  • kubeadm join — run on every other machine, whether it's a worker or an additional control-plane node. It uses the token from init to securely fetch the cluster's trust info and register that node's kubelet with the cluster.

Notice the chicken-and-egg problem this creates: kubeadm init has to get etcd and kube-apiserver running on that first node before there's a scheduler or an API server to schedule anything onto it. That's exactly what static Pods solve.

Static Pods — the kubelet running things on its own

Every Pod you've written so far follows the same path: you kubectl apply it, the API server stores it in etcd, kube-scheduler picks a node, and the kubelet on that node starts it. A static Pod skips almost all of that.

A static Pod is defined by a manifest file sitting directly on a node's filesystem, in a directory the kubelet on that node watches directly — by default /etc/kubernetes/manifests on kubeadm clusters (configurable via the kubelet's staticPodPath setting). The kubelet scans that directory itself, and for any manifest it finds, it starts the Pod straight through the container runtime — no API server, no scheduler, no etcd involved in the decision at all.

The "aha" for this lesson: this is exactly how kubeadm solves its own bootstrapping problem. kube-apiserver, etcd, kube-scheduler, and kube-controller-manager on a kubeadm control-plane node are themselves usually just static Pod manifest files sitting in /etc/kubernetes/manifests. The kubelet starts them directly, with no API server required to exist first — because one of the things it's starting is the API server.

Because a static Pod exists outside the API server's control, the kubelet does something to keep it visible: it creates a read-only mirror Pod object in the API server, so kubectl get pods shows it (named like <pod-name>-<node-name>). You can look at it, but you can't really manage it through kubectl — deleting the mirror Pod doesn't stop the real one; the kubelet just recreates the mirror, since the source of truth is still the file on disk, not the API server.

crictl — debugging one layer below kubectl

kubectl only works if the API server is reachable. That's a problem if the thing that's broken is the API server's static Pod — you'd have no way to see what's happening. crictl is the tool for that situation: a CLI that talks directly to the CRI-compatible container runtime (containerd, CRI-O) on the node, completely bypassing Kubernetes' own API. A couple of the commands you'd reach for:

  • crictl ps — list running containers on this node, at the runtime level (works even if kube-apiserver is down).
  • crictl logs <container-id> — get logs straight from the runtime, same idea as kubectl logs but one layer lower.

Mental shortcut: kubectl = API level, cluster-wide. crictl = runtime level, this node only, and it still works when the API server itself is the thing that's broken.

Now build it — write a static Pod manifest, by hand

A static Pod manifest has the exact same shape as any Pod manifest you already know how to write — apiVersion, kind: Pod, metadata.name, spec.containers. Nothing new in the YAML itself. What's different is entirely about placement, not content:

  • it's a plain file, not something you kubectl apply
  • it has to live in the directory the kubelet on that specific node is watching — default /etc/kubernetes/manifests on a kubeadm node
  • the kubelet picks it up on its own, usually within seconds of the file appearing

Write, on paper or in your editor, a static Pod manifest for a single container running the nginx image (reuse what you already know from Lesson 1 — nothing here needs a field you haven't written before). Then write down, in words, exactly where that file would need to go on the node for the kubelet to find it. Don't peek until you've done both.

Reveal the reference answer

apiVersion: v1
kind: Pod
metadata:
  name: static-web
spec:
  containers:
    - name: web
      image: nginx

Save that file as /etc/kubernetes/manifests/static-web.yaml on the node you want it to run on. The kubelet running there watches that directory, sees the new file, and starts the Pod directly — no kubectl apply involved. It'll still show up if you run kubectl get pods from a machine with cluster access, as a read-only mirror Pod named something like static-web-<node-name>.

Bring what you wrote back to your notes — check it against the answer field-by-field, then also check the two things that aren't fields at all: did you get the directory path right, and did you correctly say the API server/scheduler are not involved in creating it?

Retrieval practice — no peeking

Q5. Which control plane component actually stores the cluster's state — not just reads or writes it, but is the database itself?

etcd.

Q6. What makes a static Pod different from a normal Pod, in terms of who actually manages it?

A normal Pod is created through the API server, stored in etcd, and placed on a node by kube-scheduler. A static Pod is defined by a manifest file on a specific node's disk — the kubelet on that node manages it directly, with no API server or scheduler involved in the decision. The API server only sees a read-only mirror Pod.

Q7. What directory does the kubelet watch by default for static Pod manifests on a kubeadm cluster?

/etc/kubernetes/manifests (configurable via the kubelet's staticPodPath setting).

Q8. Why does it make sense that kube-apiserver and etcd themselves typically run as static Pods on a kubeadm control-plane node, instead of normal Pods?

Bootstrapping problem: a normal Pod needs the API server (to be created) and the scheduler (to be placed) to already exist. But the API server itself can't be scheduled by an API server that isn't running yet. Static Pods break that circle — the kubelet starts them straight from a local file, with no dependency on any control plane component already being up.

Recap
  • Control plane: kube-apiserver (front door), etcd (database), kube-scheduler (placement decision), kube-controller-manager (reconciliation loops), cloud-controller-manager (cloud integration).
  • Node: kubelet (starts containers via the runtime), kube-proxy (Service networking), container runtime (containerd/CRI-O, speaks CRI).
  • kubeadm init bootstraps the first control-plane node; kubeadm join adds every other node using a token from init.
  • Static Pods: manifest files the kubelet watches directly (default /etc/kubernetes/manifests), started with no API server or scheduler involved — which is how the control plane components bootstrap themselves.
  • crictl debugs at the container-runtime level, one layer below kubectl — it still works when the API server itself is down.
