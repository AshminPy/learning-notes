Cluster Architecture: kubeadm, static Pods, and the control plane

New domain: Cluster Architecture, Installation & Configuration — 25% of the exam. Earlier lessons were about objects. This one is about the machine that runs those objects — territory a managed cluster (like GKE Autopilot) normally hides from you.

Simple picture: think of the control plane like a restaurant. The API server is the front counter — every order goes through it. etcd is the order ledger. The scheduler decides which table (node) an order goes to. Controllers are the manager, watching that everything still matches what was ordered.

Control plane, one line each

  • kube-apiserver — the front door. Every read/write goes through it. Only it talks to etcd.
  • etcd — the database. Holds every object's state. Lose it, lose the cluster's memory.
  • kube-scheduler — picks which node a new Pod runs on. Decides only, doesn't start anything.
  • kube-controller-manager — the reconciliation loops. E.g. a Pod dies under a Deployment, its ReplicaSet controller notices and creates a replacement.
  • cloud-controller-manager — talks to the cloud provider (load balancers, node tags). On GKE it exists, Google just runs it for you.

Node components, one line each

  • kubelet — runs on every node. Watches for Pods assigned to it, tells the runtime to start them.
  • kube-proxy — makes Service traffic reach the right Pod (iptables/IPVS rules).
  • Container runtime — containerd or CRI-O. Kubelet talks to it via the CRI, so the runtime is swappable.

One sentence to keep: kube-apiserver is the only front door, etcd is the only memory, everything else is a loop watching the API server and reacting.

Try it — before looking below

Q1. Which component is the only one allowed to talk directly to etcd?

kube-apiserver. Everything else — scheduler, controllers, kubelets, kubectl — goes through it.

Q2. A Pod under a Deployment gets deleted by hand. Which component recreates it, and does the scheduler get involved again?

kube-controller-manager creates the replacement. Yes — the new Pod is unscheduled at first, so kube-scheduler assigns it a node like any other new Pod.

kubeadm — bootstrapping a cluster

kubeadm init runs once, on the first control-plane node: generates TLS certs, starts etcd + control plane there, prints a kubeadm join command with a token. kubeadm join runs on every other machine to register it with the cluster.

Chicken-and-egg problem: init must start etcd and kube-apiserver before a scheduler or API server exists to schedule anything. Static Pods solve this.

Static Pods — kubelet running things on its own

Normal Pod: you kubectl apply it, API server stores it, scheduler places it, kubelet starts it. A static Pod skips almost all of that — it's a manifest file sitting on one node's disk, in a folder that node's kubelet watches directly (default /etc/kubernetes/manifests). No API server, no scheduler involved.

The "aha": kube-apiserver, etcd, scheduler, and controller-manager on a kubeadm control-plane node are themselves usually static Pods — that's how the control plane starts itself before it exists.

Because static Pods live outside the API server, kubelet creates a read-only mirror Pod so kubectl get pods can still show it (named <pod>-<node>). Deleting the mirror doesn't stop the real Pod — the file on disk is still the source of truth.

crictl — one layer below kubectl

kubectl needs the API server reachable. If the API server's own static Pod is broken, that's a problem — so crictl talks straight to the container runtime instead.

  • crictl ps — running containers on this node, at the runtime level.
  • crictl logs <id> — logs straight from the runtime.

Shortcut: kubectl = API level, cluster-wide. crictl = runtime level, this node only, still works when the API server is down.

Now build it — write a static Pod manifest, by hand

Same shape as any Pod manifest (Lesson 1) — nothing new in the YAML. What's different is placement, not content. Write a single-container nginx static Pod, and write down where the file must go on the node. Don't peek until you've tried both.

Reveal the reference answer

apiVersion: v1
kind: Pod
metadata:
  name: static-web
spec:
  containers:
    - name: web
      image: nginx

Save as /etc/kubernetes/manifests/static-web.yaml on the target node. The kubelet there watches that directory and starts it directly — no kubectl apply. It still shows up via kubectl get pods as a read-only mirror Pod, named like static-web-<node-name>.

Recap
  • Control plane: apiserver (front door), etcd (database), scheduler (placement), controller-manager (reconciliation), cloud-controller-manager (cloud integration). Node: kubelet, kube-proxy, container runtime.
  • kubeadm init bootstraps the first control-plane node; kubeadm join adds every other node.
  • Static Pods are manifest files the kubelet watches directly (default /etc/kubernetes/manifests) — no API server or scheduler needed, which is how the control plane bootstraps itself. crictl debugs one layer below kubectl.
