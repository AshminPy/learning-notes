ConfigMap & Secret → Pod

So far every Pod you've written has hard-coded its config in the image or the manifest. ConfigMap and Secret pull that config out into its own object, so the same image can run in dev, staging, and prod without changing a line of application code. You already do this in production with External Secrets Operator syncing from Vault into a Kubernetes Secret — this lesson is the layer underneath that: what a Secret actually is once it lands in the cluster, and the two mechanical ways a Pod picks it up.

The mental model

ConfigMap and Secret are the same mechanism — a map of key-value pairs stored as a cluster object, consumed by a Pod. The only difference is intent and encoding:

  • ConfigMap — plain-text key-value data. Non-sensitive: flags, URLs, filenames, config files.
  • Secret — same object shape, but values are stored base64-encoded instead of plain text.

Exam trap and production gotcha, same fact: base64 is encoding, not encryption. It's trivially reversible (echo <value> | base64 -d) and a Kubernetes Secret is not encrypted at rest by default — it sits in etcd exactly as base64 text. Anyone with API access or etcd access can read it as plain text. The docs say this outright: "Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store (etcd)."

The actual encryption-at-rest mechanism is a separate cluster-level object called EncryptionConfiguration, applied to the API server so etcd stores Secret (and optionally ConfigMap) data encrypted with a provider like aescbc. It's off by default — an admin has to turn it on. This is CKA-scope knowledge (know it exists, know the field), not something you'll configure end-to-end in the exam.

You already know the real answer to "how do we manage secrets in production": External Secrets Operator + Vault, so the source of truth never lives in Git or in a plain Kubernetes Secret at all. That's out of scope here — this lesson stays on the CKA-tested mechanics: what a Secret is once it exists in the cluster, and how a Pod reads it.

Two ways to consume either one

Once a ConfigMap or Secret exists, a Pod can pull its data in two ways:

  • Environment variables — envFrom (all keys) or env[].valueFrom.configMapKeyRef / secretKeyRef (one key). Simple, but the values are read once, at container start. If the ConfigMap or Secret changes later, the running container never sees the new value — it needs a restart (a new Pod).
  • Mounted volume — volumes.configMap / volumes.secret plus a matching volumeMounts entry. Each key becomes a file in the mount directory. These files do update after the source object changes — but not instantly, and not automatically visible to your app.

Be precise about "updates live" for mounted volumes — it's not instant and not free. The kubelet only re-syncs on its periodic sync interval, and depending on configMapAndSecretChangeDetectionStrategy in the KubeletConfiguration, there's an added cache propagation delay (watch-based, TTL-based, or direct API reads). So the total lag is kubelet sync period + cache delay, not zero. And even once the file on disk changes, your application process has to notice — most apps read a config file once at startup and never re-read it unless you build a file-watcher. Volume mounts make live updates possible; they don't make them automatic for free.

Try it first — before reading on

Q1. Is a Kubernetes Secret encrypted at rest by default?

No. It's stored base64-encoded (not encrypted) in etcd by default. Encryption at rest requires an admin to configure EncryptionConfiguration on the API server.

Q2. Name the two ways to consume a ConfigMap (or Secret) into a Pod, and the key tradeoff between them.

Environment variables (envFrom / valueFrom.configMapKeyRef or secretKeyRef) — simple, but frozen at container start, needs a restart to pick up changes. Or a mounted volume (volumes.configMap / volumes.secret + volumeMounts) — files update after a delay (kubelet sync + cache propagation), but the app must watch the file to notice.

Q3. What's the difference between base64 encoding and encryption, and why does it matter for a Secret sitting in etcd?

Encoding is reversible with no key — anyone can base64 -d it. Encryption needs a key to reverse. A Secret's value is only base64-encoded by default, so anyone with etcd or API access reads it as plain text. Encryption at rest needs a separate, explicitly configured EncryptionConfiguration.

Now build it — in your terminal, not here

Write two manifests by hand, no copy-paste:

  • A ConfigMap with exactly one key (your choice of key name and value).
  • A Pod that consumes that key as an environment variable — not a volume mount — using valueFrom.configMapKeyRef.
  • Any base image is fine (e.g. busybox or nginx) — the point is the env var wiring, not the container itself.

Apply it, then check with kubectl exec <pod> -- env that the variable actually shows up. Don't peek below until you've written something.

Reveal the reference answer

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  greeting: "hello from configmap"
---
apiVersion: v1
kind: Pod
metadata:
  name: config-env-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sleep", "3600"]
      env:
        - name: GREETING
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: greeting
