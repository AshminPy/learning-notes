ConfigMap & Secret → Pod

If config is baked into a container image, you need a different image per environment — dev, staging, prod — which defeats the point of "build once, run anywhere." ConfigMap and Secret pull config out of the image entirely, so the same image runs unchanged everywhere and only what's injected around it changes.

Mental model: a ConfigMap is a sticky note anyone in the room can read. A Secret is the same note written in Morse code — it looks obscured, but Morse is public knowledge, so anyone who bothers to decode it reads it instantly. That predicts something important: a Secret's protection comes entirely from who's allowed to read the Secret object (RBAC, Lesson 9), not from the encoding itself.

Running container sees an env var, or a mounted file

Same mechanism, different intent

  • ConfigMap — plain-text key/value data. Non-sensitive: flags, URLs, config files.
  • Secret — same shape, values are base64-encoded, not encrypted. Reversible with no key (base64 -d), and not encrypted at rest in etcd unless an admin turns on a separate EncryptionConfiguration.

Why it's built this way: separating config from image is the same idea Lesson 1-4 already taught applied to data instead of compute — Pods are disposable and interchangeable, so anything environment-specific has to live outside the Pod's own definition, referenced by name at runtime instead of hardcoded.

Two ways a Pod reads it

  • Environment variable (valueFrom.configMapKeyRef/secretKeyRef) — simple, but read once at container start; a change needs a Pod restart.
  • Mounted volume — each key becomes a file, updates after a delay, but your app must watch the file to notice.

Try it

Q1. Is a Kubernetes Secret encrypted at rest by default?

No — base64-encoded, not encrypted, unless an admin configures EncryptionConfiguration.

Now write your own: a ConfigMap with one key, and a Pod that reads it as an environment variable, by hand. Try before revealing.

Reveal the reference answer

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  greeting: "hello from configmap"
---
apiVersion: v1
kind: Pod
metadata:
  name: config-env-demo
spec:
  containers:
  - name: app
    image: busybox
    command: ["sleep", "3600"]
    env:
    - name: GREETING
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: greeting

Common mistake: treating a Secret as "safe" the moment it's a Secret instead of a ConfigMap — without also locking down who can kubectl get secret it, the base64 wrapping stops almost nobody.

A controlled failure

Apply the ConfigMap above, note the Pod's env var, then change the ConfigMap:

kubectl patch configmap app-config -p '{"data":{"greeting":"updated value"}}'
kubectl exec config-env-demo -- env | grep GREETING

Predict first: does the running Pod's env var change? Observe: it still shows the old value — env vars are read once, at container start, not live. Restart to pick it up:

kubectl delete pod config-env-demo
kubectl apply -f config-env-demo.yaml
kubectl exec config-env-demo -- env | grep GREETING

Production best practices

Production note: anything genuinely sensitive (API keys, DB passwords) should go through RBAC-restricted Secrets (Lesson 9 — preview: RBAC controls who can read/write which objects) at minimum, and ideally an external secrets manager integration rather than raw Secret objects, precisely because base64 alone stops nobody with API/etcd read access.

Interview Q: "Is a Kubernetes Secret secure by default?" A: No — it's base64-encoded, trivially reversible, and not encrypted at rest unless EncryptionConfiguration is explicitly enabled. Real security comes from RBAC restricting Secret access, not the encoding.

Recap
  • ConfigMap and Secret share one mechanism — Secret values are base64-encoded, not encrypted.
  • Env-var injection is frozen at container start; mounted-volume injection updates later but needs the app to watch for it.
  • A Secret's real protection is RBAC on who can read it — not the base64 wrapping.
