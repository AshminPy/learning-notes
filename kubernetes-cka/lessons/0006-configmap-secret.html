Kubernetes / CKA — Lesson 6 of 24

ConfigMap & Secret → Pod

Why this matters

There is a specific, recurring incident hiding in this lesson: an engineer runs kubectl get secret db-creds -o yaml, sees a blob like cGFzc3dvcmQxMjM=, and reasons "that's encoded gibberish, it's protected." It is not. Base64 is an encoding, not encryption — no key, no secret, reversible by anyone with the string and thirty seconds. This exact assumption is why database passwords and API tokens have ended up committed to git repos, pasted into Slack "for debugging," and handed to contractors as "already secured" — because the data looked obfuscated. If you only take one fact from this lesson: a Kubernetes Secret is a permissions problem, not a cryptography problem, unless you explicitly turn on encryption at rest and control who can read the object.

Mental model: a Secret is a labeled envelope, not a locked safe. Writing "CONFIDENTIAL" on an envelope doesn't stop anyone who's handed the envelope from opening it — and base64 is exactly that label, not a lock. This model predicts two things you haven't necessarily tested yet: (1) anyone with RBAC permission to get the Secret object can decode it in one command, no exploit required; (2) anyone who can kubectl exec into a Pod that mounts the Secret can read the plaintext value directly off disk or out of the environment, because the kubelet decodes it for the container automatically. The only two things that actually function like a lock are (a) who is allowed to read the object or exec into the Pod — RBAC — and (b) whether the cluster admin has separately configured encryption at rest for etcd. Base64 does neither.

Core concepts

ConfigMap and Secret are the same underlying mechanism: an API object that stores key-value pairs, decoupled from any container image, that a Pod can consume as environment variables or as files. The only structural difference is that Secret's data field is defined as base64 strings and the object carries a type (Opaque by default; also kubernetes.io/tls, kubernetes.io/dockerconfigjson, kubernetes.io/service-account-token, and others for specific use cases). Nothing about that difference is cryptographic — it's a convention that says "handle this one with more care," enforced by your RBAC rules and your own team's process, not by the API server.

apiVersion: v1
kind: Secret
metadata:
  name: db-creds
type: Opaque
data:
  password: cGFzc3dvcmQxMjM=      # base64 of "password123" — NOT encrypted
stringData:
  username: app_user               # plain text — API server base64-encodes it for you on write

data vs. stringData: data requires you to base64-encode every value yourself before writing the manifest. stringData is a write-only convenience field — you give it plain text, and on write the API server merges it into data, base64-encoding it for you. stringData is never returned when you read the Secret back (kubectl get secret ... -o yaml only ever shows you data); if the same key exists in both fields, the stringData value wins. In practice: write manifests with stringData so you're not hand-encoding strings, but understand that what actually gets stored — and what a `get` returns — is always `data`, base64.

FieldWhat you writeWhat's stored / returned
dataBase64 strings you encode yourselfExactly what you wrote — same base64 string comes back on get
stringDataPlain textMerged into data as base64 on write; never appears on read — only data does

Encryption at rest is a separate, opt-in control. By default, both ConfigMaps and Secrets are stored in etcd exactly as the API server received them — a Secret's base64 string sits in etcd unencrypted. Turning on real encryption requires a cluster admin to configure an EncryptionConfiguration resource and pass it to the API server, which then encrypts Secret data before writing it to etcd (and decrypts it on read) using a provider such as aescbc or a KMS plugin. This is cluster-level admin configuration, not something a Secret manifest can request for itself — if you haven't explicitly verified this is configured on your cluster, assume it isn't.

Immutable ConfigMaps and Secrets (immutable: true, stable since v1.21): add this field to either object's spec, and the API server rejects any further change to its data/stringData — you can only delete and recreate it, never edit it in place, and this cannot be reverted back to mutable once set. This isn't primarily a security feature; it's a reliability and scale feature. At large scale (Kubernetes cites tens of thousands of unique Secret-to-Pod mounts), the kubelet keeping a live watch on every mutable Secret/ConfigMap it has mounted is real load on the API server — marking one immutable tells the kubelet it never needs to watch that object for changes, cutting that load significantly. The trade-off: a config change now means a new object name (commonly a content-hash suffix) and a new rollout, not an in-place edit.

Two ways a Pod reads it — and what that means for updates

  • Environment variable (valueFrom.configMapKeyRef / secretKeyRef, or envFrom) — read once, at container start. If the ConfigMap or Secret changes afterward, the running container's environment variable does not update — official Kubernetes guidance is explicit that this requires the Pod to be replaced (a rollout restart) to pick up the new value.
  • Mounted volume — each key becomes a file under the mount path. The kubelet does update these files automatically, but not instantly: the total delay is the kubelet's periodic sync interval plus its local cache propagation delay, so treat it as "eventually, typically within roughly a minute" rather than immediate. One documented exception: a container using a ConfigMap or Secret as a subPath volume mount will not receive updates at all — subPath snapshots the file at mount time.

Production example

Production note: almost no team you'd consider mature hand-authors a production Secret with real credentials in it. The typical pattern: a tool like the External Secrets Operator or the Vault Agent Injector runs in-cluster, holds the actual credential in Vault, AWS Secrets Manager, or GCP Secret Manager, and continuously syncs a copy into a native Kubernetes Secret object that Pods mount normally — so application code still just reads a file or env var, but no human ever typed the real password into a YAML file or a terminal. On top of that, a real platform team writes an RBAC Role scoped to get on specific named Secrets for the one ServiceAccount that needs them, and explicitly withholds list and watch on the secrets resource from every human role except cluster admins — because list access effectively means read access to every Secret's contents in that scope, not just their names.

Hands-on exercise

Objective

Prove, with your own hands, that base64 provides zero confidentiality — don't take the lesson's word for it.

Scenario

You're handed get access to a namespace and want to know exactly what that access exposes.

Environment assumptions

Any cluster you can kubectl into (kind, minikube, or a real dev cluster), no existing Secret named db-creds in the current namespace.

Commands

kubectl create secret generic db-creds --from-literal=password=password123
kubectl get secret db-creds -o yaml

# extract just the value and decode it
kubectl get secret db-creds -o jsonpath='{.data.password}' | base64 -d
echo

# now prove volume-mounted access works the same way, from inside a Pod
kubectl run secret-demo --image=busybox --restart=Never --overrides='
{
  "spec": {
    "containers": [{
      "name": "app",
      "image": "busybox",
      "command": ["sleep", "3600"],
      "volumeMounts": [{"name": "creds", "mountPath": "/etc/creds"}]
    }],
    "volumes": [{"name": "creds", "secret": {"secretName": "db-creds"}}]
  }
}'
kubectl exec secret-demo -- cat /etc/creds/password

Expected result

The -o yaml output shows password: cGFzc3dvcmQxMjM=. The base64 -d line prints password123 in plain text. The final exec/cat also prints password123 — the kubelet already decoded it onto disk; no decoding step was needed from inside the Pod at all.

Verification

You should see the exact plaintext password twice, from two independent paths (direct get + decode, and Pod exec + read). If either comes back empty or errors, check you're in the right namespace and that the Secret and Pod actually created successfully with kubectl get secret,pod.

Common failure

Assuming the exec/cat step would show base64 text like the YAML did. It won't — volume-mounted Secrets are decoded to plaintext files by the kubelet before the container ever sees them. This is normal, expected behavior, not a bug.

Troubleshooting

If kubectl create secret fails with "already exists," a previous run left it behind — kubectl delete secret db-creds --ignore-not-found first. If the exec returns "no such file or directory," check the volume's mountPath matches what you cat, and that the Pod reached Running (kubectl get pod secret-demo) before you exec'd into it.

Cleanup / rollback

kubectl delete pod secret-demo --ignore-not-found
kubectl delete secret db-creds --ignore-not-found

Production lesson

Anyone who can run either of the two command sequences above already has full plaintext access to that credential. That means your real access boundary is RBAC on the Secret object and on pods/exec in that namespace — not the base64 wrapper, which every legitimate consumer (and every attacker who reaches this far) can strip in one line.

Failure scenario

A realistic version of the exact assumption named in "Why this matters" — discovered the way most of these actually are: during an audit, not during the mistake itself.

  1. Day 1, 09:14 A developer is documenting a new integration and pastes a working Secret manifest into the team's infra repo as a "reference example," complete with a real base64-encoded API key from the staging environment. In their head: "it's base64, not plaintext — close enough to safe for a repo only the team can see."
  2. Day 1, 09:20 The commit passes review. Nobody flags the manifest, because at a glance it looks like every other Secret example — nobody manually decodes a base64 blob during a routine review.
  3. Week 6, 14:00 A quarterly security audit runs a secret-scanning tool across the org's git history, specifically checking known-format strings (this API key has a recognizable prefix). It flags the commit from six weeks earlier.
  4. Week 6, 14:10 The auditor decodes the flagged blob with base64 -d in under a minute and confirms it's a live, still-valid staging API key — exposed to everyone with read access to that repo (which, six weeks later, includes several new hires and a contractor) since the day it was committed.
  5. Week 6, 14:25 Incident opened. The key is rotated immediately at the provider; the staging Secret is recreated with the new value; the commit is confirmed to not exist in any public fork.
  6. Week 6, 15:30 Root cause recorded: "base64 was treated as sufficient obfuscation for a value that never should have left the cluster or a proper secrets manager in the first place." Fix: add pre-commit secret-scanning to the repo, and move staging credentials to the same External Secrets Operator sync path already used in production, so no human ever holds the raw value again.

Troubleshooting workflow

The general method, applied specifically to "a Pod isn't picking up an updated ConfigMap or Secret value":

  1. Confirm the symptom. Don't trust the app's behavior alone — check the actual value the running container sees: kubectl exec <pod> -- printenv MY_VAR for an env var, or kubectl exec <pod> -- cat /path/to/mounted/key for a volume mount.
  2. Define scope. Is it one Pod, every replica of the Deployment, or every consumer across namespaces? kubectl get pods -l app=myapp tells you if this is one stale replica or all of them.
  3. Check recent changes. kubectl get configmap <name> -o yaml or kubectl get secret <name> -o yaml and check metadata.resourceVersion and any timestamps in your CI/GitOps history — was it actually updated, and when, relative to when the Pod last started?
  4. Inspect the right state. kubectl get pod <name> -o yaml and look at whether the container consumes it via env/envFrom (frozen at start) or a volumeMounts entry — and if it's a volume mount, whether it uses subPath (which never updates).
  5. Form a hypothesis. Most common: "it's an env var, so the change can't show up until the Pod is replaced" — or "it's a subPath mount, so it will never pick up the change without a restart."
  6. Test one variable. Do a controlled kubectl rollout restart deployment/<name> and re-check the value with the same exec command from step 1, rather than guessing.
  7. Apply the safest fix. For an env var or subPath mount, the only fix is a new Pod — a rollout restart. For a genuine full-volume mount that still hasn't updated after a few minutes, check the kubelet's health on that node before assuming the Secret itself is wrong.
  8. Verify recovery. Re-run the exact command from step 1 against the new Pod and confirm the value matches what you expect — not just that the rollout completed.
  9. Document the root cause. "Consumed as env var / subPath mount; these never live-update" — write down which mechanism it was, so the next person doesn't re-diagnose the same thing.
  10. Prevent recurrence. If this config changes often, either switch to a full (non-subPath) volume mount so updates propagate automatically, or adopt a pattern that forces a rollout on every change — a content-hash suffix on the ConfigMap/Secret name (what Kustomize's configMapGenerator does) or a controller like Reloader that watches for changes and triggers a rollout for you.

Security note: this is the section that matters most in this lesson — treat it as the main content, not an afterthought.

RBAC on Secrets is your real access boundary. Per Kubernetes' own good-practices guidance, granting list access to Secrets "implicitly lets the subject fetch the contents of the Secrets" — a list response includes full object bodies, not just names. The recommendation: restrict watch and list on Secrets to the most privileged, system-level components only; for everyone else — humans especially — grant get access only, and only for the specific named Secrets a role genuinely needs, never a blanket resources: ["secrets"] rule with no resourceNames. One sharp edge: resourceNames doesn't cleanly restrict list/watch the way it restricts get — those verbs act on a collection, so scoping them to specific names depends on the client sending a matching field selector, which most tools (including plain kubectl get secrets) don't do by default. Practical rule: if a role only needs specific Secrets, give it get on those names and drop list/watch entirely, rather than assuming resourceNames makes a broad list grant safe.

Encryption at rest is opt-in, and most learning/dev clusters don't have it. Without a configured EncryptionConfiguration on the API server, Secret data sits in etcd exactly as base64 — anyone with direct etcd access (backups included) has the same plaintext access as anyone with API access. If you're responsible for a real cluster, verify this is enabled; don't assume it because "it's a Secret."

Prefer mounted volumes over environment variables for highly sensitive values. Kubernetes' own documentation flags environment variables as more prone to leaking than files, specifically because of crash dumps ending up in logs and because environment variables have no equivalent to file permissions in Linux — any process that can read another process's environment (for example via /proc/<pid>/environ, when permitted) gets the value in one step, and env vars are commonly echoed into application logs, error trackers, and debugging output by accident. A mounted file at least benefits from normal filesystem permissions and doesn't get accidentally dumped into a stack trace. Neither mechanism protects you from your own application logging the value on purpose — that's on your code, not Kubernetes.

Common mistake: treating base64 as "encoded enough" and pasting a Secret's data value somewhere it shouldn't go — a ticket, a Slack message, a git commit — because it doesn't look like a plaintext password.

Common mistake: writing an RBAC Role with verbs: ["get", "list", "watch"] on resources: ["secrets"] and no resourceNames, intending to grant access to "the two Secrets my app needs" — this grants read access to every Secret in that scope, because list doesn't check names at all.

Common mistake: updating a ConfigMap or Secret and assuming a running Deployment "should just pick it up," then spending an hour debugging the app before remembering the value is consumed as an environment variable — which is frozen at container start until the Pod is replaced.

Common mistake: marking a Secret immutable: true in a hurry, then trying to kubectl edit it during an incident and being confused when the API server rejects the change — immutability has no override; the only path is delete-and-recreate.

Decision guide

OptionUse whenAvoid whenTrade-off
Environment variableNon-sensitive config, or values your app only reads once at startup anywayHighly sensitive values (long-lived DB passwords, signing keys)Simplest to wire up; frozen at start; more exposure surface (logs, crash dumps, /proc)

Default recommendation: mounted volume plus restrictive RBAC (get-only, named resources) for anything sensitive in a learning or small-team cluster; graduate to an external secrets manager syncing into native Secrets as soon as you're running anything you'd call "production." Use environment variables only for values that are genuinely low-sensitivity or that your app only ever reads once at boot regardless.

Knowledge check

Q1. Is a Kubernetes Secret encrypted at rest by default?

No. It's base64-encoded, not encrypted, unless a cluster admin configures an EncryptionConfiguration for the API server.

Q2. An environment variable pulled from a ConfigMap or Secret — does it update if the source object changes later?

No. It's read once at container start. The Pod must be replaced (a rollout restart) to pick up the new value.

Q3. Which RBAC verb, when granted on secrets with no resourceNames, effectively grants read access to the contents of every Secret in that scope — not just their names?

B. list returns full object bodies for every matching Secret, so it implicitly grants read access to their contents. (get is scoped to one named object; create and patch are write operations, not read.)

Q4. You set immutable: true on a Secret, then need to change one value inside it. What's the correct way to do that?

C. Immutability cannot be reverted and the data can't be mutated in place — delete and recreate is the only path. (A and B are both blocked by the API server once immutable is set; D isn't possible — the flip from immutable to mutable is one-way.)

Production challenge

Objective

Audit a real-looking RBAC Role for over-permissioned Secret access, using only what this lesson covered, then fix it.

Scenario

A teammate wrote this Role so their app's ServiceAccount could read the two Secrets it needs (db-creds and api-key) in the payments namespace:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-secret-reader
  namespace: payments
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "list", "watch"]

Environment assumptions

A kind/minikube cluster where you can create Roles and Secrets. Set up the scenario yourself first:

kubectl create namespace payments
kubectl -n payments create secret generic db-creds --from-literal=password=db-pass-1
kubectl -n payments create secret generic api-key --from-literal=key=api-key-1
kubectl -n payments create secret generic billing-master-key --from-literal=key=super-sensitive
kubectl -n payments apply -f - <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-secret-reader
  namespace: payments
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "list", "watch"]
EOF

Commands

Identify the over-permission, then fix it: scope the Role to only the two named Secrets the app actually needs, using get only.

kubectl -n payments apply -f - <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-secret-reader
  namespace: payments
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get"]
  resourceNames: ["db-creds", "api-key"]
EOF

Expected result

The original Role let its ServiceAccount list the entire secrets collection in payments — including billing-master-key, which the app never should have been able to see. The fixed Role grants get on exactly db-creds and api-key, and nothing else.

Verification

Bind both versions of the Role to a test ServiceAccount with kubectl create rolebinding and use kubectl auth can-i to prove the difference:

kubectl -n payments create serviceaccount test-app
kubectl -n payments create rolebinding test-app-binding \
  --role=app-secret-reader --serviceaccount=payments:test-app

kubectl -n payments auth can-i get secret/billing-master-key --as=system:serviceaccount:payments:test-app
kubectl -n payments auth can-i list secrets --as=system:serviceaccount:payments:test-app

Against the original Role, both return yes. Against the fixed Role, both return no — only get on db-creds or api-key by exact name returns yes.

Common failure

"Fixing" this by removing only watch and leaving list in place. list alone is still enough to read every Secret's contents in the namespace — the fix has to remove list and add resourceNames, not just trim the verb list a little.

Troubleshooting

If auth can-i still returns yes after applying the fixed Role, check whether an old, broader RoleBinding or ClusterRoleBinding is also bound to the same ServiceAccount — RBAC is additive, so a second binding elsewhere can silently override the effect of tightening one Role.

Cleanup / rollback

kubectl delete namespace payments

Production lesson

Over-permissioned Secret access almost never looks malicious in a code review — it looks like someone reaching for the obvious, broad verb set instead of the two verbs and two names they actually needed. This is the single most common RBAC finding in real security audits of Kubernetes clusters, and it's caught with exactly the auth can-i check above, not by reading YAML and guessing.

Recap
  • ConfigMap and Secret are the same mechanism — a Secret's data is base64, not encrypted; base64 provides zero confidentiality on its own.
  • stringData is a write-only convenience field merged into data on write — reads always return data, base64.
  • Real encryption at rest needs an admin-configured EncryptionConfiguration on the API server — off by default.
  • immutable: true blocks any further edit permanently (delete-and-recreate only); it's mainly a scale/reliability feature, cutting kubelet watch load, not primarily a security control.
  • Env vars are frozen at container start; mounted volumes update automatically (except subPath) after a kubelet sync delay.
  • The real access boundary is RBAC: list on Secrets exposes full contents, not just names — restrict to get on named resources wherever possible, and prefer mounted volumes over env vars for highly sensitive values.
