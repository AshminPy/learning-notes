CoreDNS & Gateway API

Since Lesson 3, you've written Service names into other objects and they just resolved. That only works because CoreDNS is silently running in every cluster. And since Lesson 8, Ingress has been the only way in — Gateway API is the newer, more expressive alternative the curriculum now expects you to know.

Simple example: CoreDNS is the cluster's phone book — every Service gets an entry the moment it's created, no action needed from you. Gateway API is Ingress split into two jobs: infra teams manage where traffic enters (Gateway), app teams manage where it goes (HTTPRoute) — separate permissions, separate blast radius.

CoreDNS — the phone book

CoreDNS runs as a Deployment in kube-system, fronted by the kube-dns Service. Every Pod's /etc/resolv.conf points at that Service's ClusterIP by default (dnsPolicy: ClusterFirst) — that's the entire mechanism behind every Service name you've used so far resolving.

<service>.<namespace>.svc.cluster.local

Its config lives in a ConfigMap, not a file on disk — edit it live, no redeploy needed:

kubectl -n kube-system get configmap coredns -o yaml   # see the Corefile
kubectl -n kube-system get pods -l k8s-app=kube-dns     # is it even running
kubectl run -it --rm dnsutils --image=registry.k8s.io/e2e-test-images/jessie-dnsutils:1.3 -- nslookup kubernetes.default

If Service names stop resolving cluster-wide, check CoreDNS's own Pods first (Lesson 16's ladder: describe → logs) before assuming the app is broken.

Gateway API — Ingress, with role separation

Three kinds, three owners:

  • GatewayClass (cluster-scoped) — which load-balancer implementation exists (e.g. nginx, cilium). Managed by infra admins.
  • Gateway — one actual listener: an IP, a port, a protocol. References a GatewayClass. Also infra-owned.
  • HTTPRoute (namespace-scoped) — routing rules, attached to a Gateway via parentRefs. App teams own these in their own namespace, without needing access to the Gateway itself.
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-app
spec:
  parentRefs:
    - name: shared-gateway
  rules:
    - matches:
        - path: { type: PathPrefix, value: /my-app }
      backendRefs:
        - name: my-app-service
          port: 80

Unlike Ingress, none of this is built into core Kubernetes — it's a CRD group (Lesson 19) plus a controller that implements it. kubectl get gatewayclass,gateway,httproute -A shows what's installed.

Try it — before looking below

Q1. Every Pod in a namespace suddenly can't resolve any Service name — Pods themselves are Running and Ready. What do you check first?

CoreDNS's own Pods in kube-system — kubectl get pods -n kube-system -l k8s-app=kube-dns, then describe/logs. If the phone book is down, nothing in the cluster can look anything up, even though every individual app is healthy.

Q2. An app team asks for the ability to add new routing rules without ever touching load-balancer config. Ingress or Gateway API — which grants that split cleanly, and why?

Gateway API — HTTPRoute is namespace-scoped and owned by the app team, while Gateway/GatewayClass stay with infra. Ingress mixes both concerns in one object, so splitting permissions cleanly is harder.

Source

kubernetes.io/docs — DNS debugging and gateway-api.sigs.k8s.io — exam-allowed pages.

Recap
  • CoreDNS gives every Service a name automatically; if names stop resolving cluster-wide, check CoreDNS itself first.
  • Gateway API splits Ingress into GatewayClass/Gateway (infra) and HTTPRoute (app team) for cleaner permission boundaries.
  • Neither Gateway API kind is built in — it's CRDs plus a controller, same pattern as Lesson 19.
