CoreDNS & Gateway API

Since Lesson 3, you've written Service names into other objects and they just resolved. That only works because CoreDNS runs silently in every cluster. And since Lesson 8, Ingress has been the only way in — Gateway API is the newer, more expressive alternative the curriculum now expects.

Mental model: CoreDNS is the cluster's phone book — every Service gets an entry the moment it's created, no action needed. Gateway API is Ingress split into two jobs: infra teams manage where traffic enters (Gateway), app teams manage where it goes (HTTPRoute) — separate permissions, separate blast radius. That predicts why teams migrate to it: an app team can ship new routing rules without ever touching load-balancer config.

Where this fits

Every Service (Lesson 3)
   │  auto-registered as
   ▼
CoreDNS   (<service>.<namespace>.svc.cluster.local)

Gateway API (a CRD group, Lesson 19's pattern):
GatewayClass (infra)  →  Gateway (infra)  →  HTTPRoute (app team)  →  Service (Lesson 3)

CoreDNS — the phone book

CoreDNS runs as a Deployment in kube-system, fronted by the kube-dns Service. Every Pod's /etc/resolv.conf points at that Service's ClusterIP by default (dnsPolicy: ClusterFirst) — the entire mechanism behind every Service name resolving.

kubectl -n kube-system get pods -l k8s-app=kube-dns
kubectl run -it --rm dnsutils --image=registry.k8s.io/e2e-test-images/jessie-dnsutils:1.3 -- nslookup kubernetes.default

Why it's built this way: its config lives in a ConfigMap (Lesson 6's mechanism), not a file baked into an image — edit it live, no redeploy needed, the same "config outside the container" principle Lesson 6 taught, applied to a cluster-critical component.

Gateway API — Ingress, with role separation

  • GatewayClass (cluster-scoped) — which load-balancer implementation exists. Infra-owned.
  • Gateway — one listener: IP, port, protocol. References a GatewayClass. Also infra-owned.
  • HTTPRoute (namespace-scoped) — routing rules, attached via parentRefs. App teams own these.

Unlike Ingress, none of this is built into core Kubernetes — it's exactly Lesson 19's CRD-plus-controller pattern. kubectl get gatewayclass,gateway,httproute -A shows what's installed.

Try it

Q1. Every Pod in a namespace suddenly can't resolve any Service name — Pods themselves are Running and Ready. What do you check first?

CoreDNS's own Pods in kube-system. If the phone book is down, nothing in the cluster can look anything up, even though every individual app is healthy.

Now, before revealing: an app team wants to add routing rules without touching load-balancer config. Ingress or Gateway API?

Reveal the answer

Gateway API — HTTPRoute is namespace-scoped and app-owned, while Gateway/GatewayClass stay with infra. Ingress mixes both concerns in one object.

A controlled failure

kubectl run web --image=nginx:1.29 --labels=app=web
kubectl expose pod web --port=80 --name=web-svc
kubectl run tester --image=busybox --restart=Never -it --rm -- \
  nslookup web-svc.default.svc.cluster.local

Predict first: if you then scale CoreDNS to 0 replicas, does tester still reach web-svc by IP? By name? Observe (reason through it, or test on a scratch cluster): by IP, yes — routing (Lesson 3's kube-proxy mechanism) doesn't depend on DNS at all. By name, no — name resolution is entirely CoreDNS's job, a separate failure domain from Service routing itself.

Production best practices

Production note: run CoreDNS with at least 2 replicas and a PodDisruptionBudget — it's a single point of failure for name resolution cluster-wide despite looking like "just another Deployment."

Exam & interview notes

Directly scored under Services & Networking (20%).

Interview Q: "Traffic works by IP but not by Service DNS name. What's broken?" A: CoreDNS specifically, not routing — Service routing (Lesson 3) and DNS resolution (this lesson) are separate mechanisms that happen to both usually work, so this symptom isolates the problem to one of them precisely.

Recap
  • CoreDNS gives every Service a name automatically; if names stop resolving cluster-wide, check CoreDNS itself first.
  • Gateway API splits Ingress into GatewayClass/Gateway (infra) and HTTPRoute (app team) for cleaner permission boundaries.
  • Neither Gateway API kind is built in — it's CRDs plus a controller, Lesson 19's pattern again.

Confidence check — answer without looking back:

  • Why is DNS resolution a separate failure domain from Service routing?
  • When would Gateway API's role split actually matter to your organization?
  • What happens to already-open connections if CoreDNS goes down mid-session?
  • How would you verify whether a connectivity issue is DNS or routing, in one command?
