Kubernetes / CKA — Lesson 21 of 24

CoreDNS & Gateway API

Why this matters

This lesson covers two topics because they share a theme: both are infrastructure everyone depends on and almost nobody looks at until it breaks. Since Lesson 3, every Service name you've written into a manifest has resolved silently — that only happens because CoreDNS is running in every cluster, answering millions of lookups a day, invisibly. When CoreDNS breaks, it doesn't look like a normal outage: every individual Pod is Running, every node is Ready, every app's own health check can even pass — and yet nothing in the cluster can reach anything else by name. That mismatch between "everything I'd normally check looks fine" and "nothing works" is what makes a CoreDNS incident one of the most disorienting failures in Kubernetes.

Gateway API's stakes are different but just as real. Since Lesson 8, Ingress has been the only built-in way to expose HTTP traffic — and Ingress packs "where does traffic enter" and "where does it go" into one object. That's fine for one team. It's a real permission problem the moment two teams share a cluster: whoever can edit the Ingress can affect every route through it, so either everyone gets broad access (unsafe) or one team becomes a routing-change bottleneck for everyone else (slow). Gateway API exists specifically to remove that trade-off.

Mental model: CoreDNS is a phone book every caller in the building shares. If the phone book itself becomes unreachable, every call fails at once — not because any phone, wire, or person is broken, but because the one thing everyone depends on to look each other up is gone. That's why a CoreDNS outage is so disorienting: none of the places you'd normally look for a broken workload (Pod status, node health, app logs) show anything wrong, because the failure sits one layer beneath all of them.

Mental model: Gateway API is Ingress split into two jobs with two separate owners: infra teams manage where traffic enters (Gateway), app teams manage where it goes from there (HTTPRoute). This model makes a specific, testable prediction: if an app team ships a broken HTTPRoute — a typo'd backend name, a path rule that matches nothing — the blast radius stops at their own route. They cannot touch the shared listener, other teams' routes, or the Gateway object itself, because their permissions (assuming someone designed them correctly — see the Common mistakes section) only ever grant them an HTTPRoute in their own namespace, never write access to the Gateway. A single shared Ingress object can't make that promise — anyone with edit access to it can affect every route funnelled through it.

CoreDNS — how the phone book actually works

CoreDNS runs as a Deployment in kube-system, fronted by a Service traditionally named kube-dns (kept for backward compatibility even though it now points at CoreDNS, not the old kube-dns binary). Every Pod's /etc/resolv.conf points at that Service's ClusterIP by default (dnsPolicy: ClusterFirst) — that one fact is the entire mechanism behind every Service name you've used since Lesson 3 resolving:

search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.0.0.10
options ndots:5

The query path: your Pod asks the nameserver in its own resolv.conf (the kube-dns Service ClusterIP) → the Service load-balances that query to one of the CoreDNS replica Pods behind it → CoreDNS decides how to answer based on its Corefile — a chain of plugins, each handling one piece of the job, in order:

.:53 {
    errors
    health
    kubernetes cluster.local in-addr.arpa ip6.arpa {
      pods insecure
      upstream
      fallthrough in-addr.arpa ip6.arpa
    }
    prometheus :9153
    forward . /etc/resolv.conf
    cache 30
    loop
    reload
    loadbalance
}
PluginIts one job
errorsLog query errors to stdout
healthExpose CoreDNS's own health endpoint, used by its liveness probe
kubernetesAnswer cluster.local queries from the Kubernetes API's Service/Endpoint data — this is why CoreDNS needs watch on services, endpointslices, pods, and namespaces (see the Security section)
forwardSend anything outside cluster.local upstream, using the node's own /etc/resolv.conf as the address list
cacheCache answers (30s here) so repeat lookups don't re-hit kubernetes/forward every time
loopDetect and break accidental forwarding loops
reloadPoll the Corefile for edits and hot-reload — no Pod restart needed
loadbalanceRandomize returned record order for simple client-side load spreading

You don't need to memorize one exact plugin list — the chain varies slightly by install method (kubeadm, EKS, GKE all ship close-but-not-identical Corefiles). What matters for troubleshooting is knowing the chain exists and roughly what each stage does, so a symptom points you at a plugin instead of at guesswork.

The config lives in a ConfigMap, not a file baked into the image — you can edit it live:

kubectl -n kube-system get configmap coredns -o yaml   # read the Corefile
kubectl -n kube-system edit configmap coredns           # edit it live
kubectl -n kube-system get pods -l k8s-app=kube-dns      # is it even running

Simple example: "no redeploy needed" isn't hand-waving — it's the reload plugin. It polls the Corefile every 30 seconds (plus up to 15 seconds of random jitter, so many replicas don't all reload at the exact same instant) and applies changes automatically once the kubelet has synced the updated ConfigMap into the Pod's mounted volume. Edit the ConfigMap, wait roughly a minute, and the new config is live — no rollout, no restart.

Gateway API — the role-separation model, precisely

Three kinds, three owners, three scopes — this is the part worth knowing exactly, not approximately:

KindOwned byScopeJob
GatewayClassInfrastructure providerCluster-scopedWhich load-balancer implementation exists (e.g. nginx, cilium, a cloud LB controller)
GatewayCluster/platform operatorNamespace-scopedOne real listener: an IP, a port, a protocol. References a GatewayClass
HTTPRouteApplication developerNamespace-scopedRouting rules, attached to a Gateway via parentRefs — app teams own these in their own namespace, without needing write access to the Gateway itself
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-app
  namespace: team-a
spec:
  parentRefs:
    - name: shared-gateway
      namespace: platform
  rules:
    - matches:
        - path: { type: PathPrefix, value: /my-app }
      backendRefs:
        - name: my-app-service
          port: 80

Notice parentRefs points at a Gateway in a different namespace (platform) from the HTTPRoute itself (team-a). That cross-namespace attachment is exactly the non-obvious mechanic worth understanding precisely, because it's controlled by two separate permission boundaries that are easy to mix up:

Cross-namespace referenceControlled byConfigured byDefault if unset
HTTPRoute attaching to a Gateway in another namespaceallowedRoutes.namespaces on the Gateway's listenerThe Gateway owner (platform/cluster operator)Same — only Routes in the Gateway's own namespace may attach
HTTPRoute's backendRef pointing at a Service in another namespaceA ReferenceGrant objectThe owner of the target namespace (the Service's namespace)Not allowed at all until a ReferenceGrant exists there
Gateway's TLS certificateRefs pointing at a Secret in another namespaceA ReferenceGrant objectThe owner of the target namespace (the Secret's namespace)Not allowed at all until a ReferenceGrant exists there

allowedRoutes governs the Route-to-Gateway attachment edge — the Gateway owner opts in via Same, Selector (specific namespaces by label), or All. ReferenceGrant governs a completely different edge — a Route (or Gateway) reaching into another namespace to point at one of its objects — and it's a real, separate Gateway API resource (apiVersion: gateway.networking.k8s.io/v1, GA as of Gateway API v1.5), created inside the namespace being referenced into:

apiVersion: gateway.networking.k8s.io/v1
kind: ReferenceGrant
metadata:
  name: allow-team-a-route
  namespace: billing            # the target namespace — where the Service lives
spec:
  from:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      namespace: team-a          # the namespace allowed to reference in
  to:
    - kind: Service

None of Gateway API is built into core Kubernetes — it's a CRD group (Lesson 19) plus a controller that implements it. kubectl get gatewayclass,gateway,httproute -A shows what's installed and where.

Production example

Production note: real platform teams treat CoreDNS as tier-0 infrastructure, not "just another Deployment." That means dedicated alerting on CoreDNS Pod readiness and on the kube-dns Service's live endpoint count — not folded into generic app-down alerting, because a CoreDNS incident isn't an app incident, it's a cluster incident. It means resource requests/limits sized deliberately: an under-provisioned CoreDNS Pod that gets OOMKilled under query load takes down name resolution for every workload in the cluster at once, not just itself. And it usually means more replicas than a small default, plus a PodDisruptionBudget, so a routine node drain can't take out every CoreDNS Pod in the same maintenance window.

Production note: namespace-scoped HTTPRoute is the actual mechanism, not just the intent, behind a platform team safely self-serving routing to many app teams. A platform team stands up one shared Gateway, grants allowedRoutes to the namespaces that should attach, and from that point on, thirty app teams can ship their own routing changes through their normal CI/CD — each one scoped to an HTTPRoute in their own namespace — without ever filing a ticket against the platform team or getting write access to the shared listener. That's the entire value proposition in one sentence: routing changes become self-service without becoming a shared blast radius.

Hands-on exercise

This exercise covers CoreDNS — proving the mechanism above actually works on a real cluster instead of taking the lesson's word for it.

Objective

Confirm CoreDNS is actually answering queries correctly, and see a real Corefile with your own eyes instead of trusting the example above.

Scenario

You want proof — not just "no error appeared" — that name resolution is working today, before you ever need to troubleshoot it under pressure.

Environment assumptions

Any cluster you can kubectl into (kind, minikube, or a real dev cluster), with at least read access to kube-system. No existing Pod named dnsutils in the current namespace.

Commands

kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl run -it --rm dnsutils --image=registry.k8s.io/e2e-test-images/agnhost:2.39 --restart=Never -- nslookup kubernetes.default
kubectl get svc kubernetes -o jsonpath='{.spec.clusterIP}'
kubectl -n kube-system get configmap coredns -o yaml

Expected result

The first command shows one or more CoreDNS Pods Running. The nslookup returns a Server line (the kube-dns ClusterIP) and an Address line for kubernetes.default. The ConfigMap dump shows the Corefile text under data.Corefile, in the plugin-chain shape from this lesson.

Verification

Don't stop at "nslookup didn't error." Compare the address it returned for kubernetes.default against the third command's output — they must be identical. That match is the actual proof CoreDNS answered correctly; a lookup that merely "succeeded" with the wrong address would be a worse bug than an outright failure, because nothing would look broken.

Common failure

nslookup: can't resolve 'kubernetes.default' — this almost always means the CoreDNS Pods aren't Running/Ready, or the kube-dns Service has no live endpoints behind it. It is rarely the debug Pod's own fault.

Troubleshooting

If the ConfigMap read comes back Forbidden, that's namespace RBAC working as designed, not a bug in this exercise — most namespaced developer roles have no legitimate reason to read kube-system ConfigMaps. Ask a cluster-admin to run the command or share the output rather than widening your own RBAC just to finish this exercise.

Cleanup / rollback

--rm already deletes the debug Pod for you. Nothing else was created — the ConfigMap commands were read-only.

Production lesson

The cross-check against kubernetes.get svc's ClusterIP is the same discipline Lesson 1's exercise used with a Pod UID: "did what I expected actually happen" needs one more command that proves it, not a glance that looks right.

Failure scenario

This scenario covers Gateway API — a routing conflict between two app teams sharing one Gateway. (CoreDNS's troubleshooting method is covered in its own section next, since a full 10-step walkthrough for each topic would double-cover the same ground.)

  1. Mon 10:00 The checkout team creates HTTPRoute checkout-status in namespace checkout, an exact-path match on /status routing to checkout-service, attached to the shared edge-gateway in namespace platform. It works fine — nobody else is using that path yet.
  2. Thu 14:00 The search team ships HTTPRoute search-status in namespace search — also an exact-path match on /status, routing to search-service, also attached to edge-gateway. kubectl apply succeeds with no warning or error.
  3. Thu 14:05 Search's on-call curls the shared Gateway's /status path expecting search-service's response. They get checkout-service's response body instead.
  4. Thu 14:09 They check their own object: kubectl get httproute search-status -n search -o yaml shows status.parents[].conditions with both Accepted: True and ResolvedRefs: True. From search-status's own point of view, everything is healthy — there is no error anywhere on this object.
  5. Thu 14:14 They widen the search: list every HTTPRoute across all namespaces whose parentRefs names edge-gateway, and compare match rules. checkout-status has an identical exact-path match on /status, created four days earlier.
  6. Thu 14:18 Root cause identified: the two routes tie exactly on match specificity (both are an identical exact-path match on the same string). Per Gateway API's documented precedence rules, a tie is broken first by the oldest Route's creation timestamp, then by alphabetical order of {namespace}/{name}. checkout-status is older, so it wins every time — search-status is valid, accepted, and permanently starved of traffic on that path.
  7. Thu 14:24 Fix applied: the search team changes their match to a path that doesn't collide — /search/status instead of the shared /status — coordinating through the platform team, who own edge-gateway and can see every Route attached to it.
  8. Thu 14:30 Verified: a curl to the new path reaches search-service; checkout-status's original /status path is untouched.

Troubleshooting workflow

This is CoreDNS's troubleshooting method — the generic 10-step approach, applied specifically to "Service names aren't resolving cluster-wide":

  1. Confirm the symptom. Reproduce the exact failing lookup yourself from a fresh debug Pod — kubectl run -it --rm dnsutils --image=registry.k8s.io/e2e-test-images/agnhost:2.39 --restart=Never -- nslookup <the-name-that-failed>. Don't diagnose from a secondhand report of "DNS is down."
  2. Define scope. Test from Pods in more than one namespace. Also test an external name (nslookup google.com) alongside an internal one (nslookup kubernetes.default) — external-only failure points at the forward plugin/upstream resolver; internal-only failure points at the kubernetes plugin or the API server watch behind it.
  3. Check recent changes. kubectl get events -n kube-system --sort-by=.lastTimestamp — was the coredns ConfigMap edited, the Deployment scaled, or was there a node drain that took out CoreDNS Pods recently?
  4. Inspect the right state. kubectl get pods -n kube-system -l k8s-app=kube-dns (are any Pods actually Running/Ready?); kubectl get svc kube-dns -n kube-system and kubectl get endpointslice -l kubernetes.io/service-name=kube-dns -n kube-system (does the Service have live endpoints behind it at all?); kubectl logs -n kube-system -l k8s-app=kube-dns for plugin errors.
  5. Form a hypothesis. For example: "the kube-dns Service has zero endpoints because every CoreDNS Pod is failing its readiness probe."
  6. Test one variable. Query a CoreDNS Pod's IP directly instead of the kube-dns Service ClusterIP, to isolate "CoreDNS itself is broken" from "the Service routing to it is broken."
  7. Apply the safest fix. For a stuck rollout, kubectl rollout restart deployment coredns -n kube-system is safer than deleting Pods by hand. For a bad ConfigMap edit, revert the Corefile change rather than guessing a new one under pressure.
  8. Verify recovery. Repeat the exact nslookup from step 1, from more than one namespace, and confirm the endpoint list is non-empty again.
  9. Document the root cause. Write down the specific finding — "CoreDNS had 0/2 Ready Pods after a memory limit set too low caused repeated OOMKills" — not "DNS was flaky."
  10. Prevent recurrence. This is where the tier-0 framing pays off: alert specifically on CoreDNS Pod readiness and kube-dns endpoint count, and revisit CoreDNS's resource requests/limits so it isn't the most fragile thing in a cluster everything else silently depends on.

Security note: the two cross-namespace mechanisms from the Core concepts section are a real access-control boundary, not a formality — and conflating them is the actual security risk. allowedRoutes decides which namespaces' HTTPRoutes may attach to a shared Gateway at all (default: same namespace only). A separate ReferenceGrant, created by the owner of the target namespace, decides whether a Route (or a Gateway's TLS config) may reach into that namespace to reference a specific Service or Secret. Getting the first one right says nothing about the second — a Gateway that happily accepts Routes from every namespace (allowedRoutes: All) still can't let any of them read a Secret in another namespace without an explicit ReferenceGrant there.

Reliability note: CoreDNS is a textbook single point of failure — every Service-name lookup in the cluster funnels through however many replicas exist, so its reliability ceiling is the cluster's reliability ceiling for anything that resolves a name before connecting. The cache plugin (30s default here) buys you a short grace window during a CoreDNS blip for names queried recently, but it is not a substitute for redundancy — once the cache entries expire during an outage, every lookup fails at once, cluster-wide, regardless of how healthy every other workload is.

Common mistake: escalating on a specific app being "broken" — restarting it, checking its code, rolling back its last deploy — when the real fault is CoreDNS and every other Service lookup in the cluster is equally broken. If more than one unrelated app starts failing to reach its dependencies at the same moment, check CoreDNS before you check any of them individually.

Common mistake: assuming Gateway API's role separation is automatic. Installing the CRDs and creating a Gateway doesn't create any permission boundary by itself — someone still has to design which namespaces may attach Routes (allowedRoutes) and which cross-namespace backend references are trusted (ReferenceGrant). Skip that design work and Gateway API is just Ingress with more YAML and the same shared blast radius.

Common mistake: treating allowedRoutes and ReferenceGrant as the same permission. They guard two different edges of the same diagram — one controls whether a Route may attach to a Gateway at all, the other controls whether it may reference an object in another namespace once attached. Configuring one correctly tells you nothing about the other.

Decision guide

OptionUse whenAvoid whenTrade-off
IngressSingle-team cluster, simple host/path routing, existing tooling already targets itMultiple teams need to change routing independently and safelyOne object mixes infra and app concerns — anyone who can edit it can affect every route through it
Gateway APIMultiple app teams share a cluster/Gateway and need self-service routing without infra access; need typed protocol support (HTTP/gRPC/TLS) beyond Ingress's HTTP-shaped modelSingle small team with simple needs, where the extra CRDs and controller add complexity with no permission problem to solve yetMore moving parts (GatewayClass/Gateway/HTTPRoute/ReferenceGrant) and feature support varies by controller — not every implementation supports every Gateway API feature yet

Default recommendation: reach for Gateway API when a cluster is genuinely multi-tenant and the permission split is worth the extra objects. Keep Ingress for a single-team cluster where that split buys nothing yet — the CRD and controller overhead isn't free.

Knowledge check

Q1. Every Pod in a namespace suddenly can't resolve any Service name — the Pods themselves are Running and Ready. What do you check first?

CoreDNS's own Pods in kube-system — kubectl get pods -n kube-system -l k8s-app=kube-dns, then the kube-dns Service's endpoints. If the phone book is down, nothing in the cluster can look anything up, even though every individual app is healthy.

Q2. An app team asks for the ability to add new routing rules without ever touching load-balancer config. Ingress or Gateway API — which grants that split cleanly, and why?

Gateway API — HTTPRoute is namespace-scoped and owned by the app team, while Gateway/GatewayClass stay with infra. Ingress mixes both concerns in one object, so splitting permissions cleanly is harder.

Q3. In the default Corefile, which plugin sends queries CoreDNS can't answer from cluster.local out to an upstream resolver?

C. forward — it sends unresolved queries to the address in /etc/resolv.conf on the node. cache stores answers after the fact, loop detects forwarding loops, and reload watches for Corefile edits — none of them do the actual forwarding.

Q4. An HTTPRoute in namespace search needs its backendRef to point at a Service in namespace billing. What has to exist for that reference to be allowed?

A. The ReferenceGrant must live in the namespace being referenced into — billing — naming HTTPRoute in search as a trusted referrer. allowedRoutes controls whether a Route may attach to a Gateway at all, a different boundary entirely; a NetworkPolicy controls packet-level reachability, not Gateway API's own reference permissions.

Services & Networking — 20% of the CKA exam, per the official CNCF curriculum (this course's own objectives tracker places CoreDNS, Ingress, and Gateway API here). Production challenge

This challenge covers Gateway API — diagnosing a routing conflict with less hand-holding than the failure scenario above.

Objective

Diagnose a routing conflict between two app teams sharing one Gateway, using only the reasoning this lesson gave you — not a script to follow line by line.

Scenario

The platform team runs one Gateway named edge-gateway in namespace platform-ingress, configured to accept HTTPRoutes from any namespace labeled gateway-access: allowed. Two teams, billing and reporting, both attach routes to it. The reporting team reports: "our nightly export callback under /reports/export stopped receiving traffic sometime this week — no errors show up anywhere on our own route."

Environment assumptions

A kind/minikube cluster with a working Gateway API implementation installed (any GatewayClass backed by a real controller). You may not have cluster-wide read access to every namespace's HTTPRoutes by default — if not, that gap is itself part of what this challenge is testing.

Commands

# Start broad, then narrow to the shared Gateway
kubectl get httproute -A -o wide
kubectl get gateway edge-gateway -n platform-ingress -o yaml   # check status.listeners[].attachedRoutes
kubectl get httproute -n billing -o yaml
kubectl get httproute -n reporting -o yaml
# Compare every route whose parentRefs names edge-gateway: matches, and metadata.creationTimestamp

Expected result

You find a second HTTPRoute (in billing) with a match that ties or beats reporting's on specificity for the /reports/export path, and you can name which precedence rule explains the winner — match specificity, oldest creation timestamp, or alphabetical {namespace}/{name} — not just "these two routes look similar."

Verification

State the winning rule out loud (or in writing) before proposing a fix. "billing's route is older" or "billing's match is more specific" are different root causes with different correct fixes — confusing them means you might ship a fix that doesn't actually change the outcome.

Common failure

Assuming the Gateway controller itself is broken and asking the platform team to restart it. A precedence conflict produces zero errors anywhere — every object involved is healthy and Accepted: True — so there is nothing for a restart to fix.

Troubleshooting

If you can't list HTTPRoutes across namespaces yourself, that's the exact cross-namespace-visibility gap this lesson's mental model predicts. Ask the platform team — who own the shared Gateway and can see every attached Route — to run the cross-namespace comparison with you, rather than requesting broad read access across every namespace just to debug one incident.

Cleanup / rollback

If you built this scenario yourself to practice, delete the test HTTPRoutes and Gateway when done. If you're diagnosing a real shared Gateway, don't delete anything that isn't yours — propose the path change to the route's owning team instead.

Production lesson

A shared Gateway needs an owner who can see every Route attached to it, across every team. Without that cross-namespace view, "my route looks completely fine" (reporting) and "the cluster is broken" (also reporting, to whoever's on call) are both truthful statements from two different vantage points at once — and nobody without the wider view can reconcile them.

Recap
  • CoreDNS answers every Service name via the kube-dns Service plus a Corefile plugin chain (kubernetes, forward, cache, loop, reload, loadbalance, ...); it's a live-editable ConfigMap — the reload plugin picks up changes in about a minute, no redeploy.
  • Service names failing cluster-wide while every Pod looks healthy is CoreDNS's signature symptom — check its Pods/Service/endpoints before any individual app.
  • CoreDNS is a single point of failure for name resolution across the whole cluster — real platform teams treat it as tier-0 infra: dedicated alerting, deliberate resource limits, a PodDisruptionBudget.
  • Gateway API splits Ingress into GatewayClass (infra provider, cluster-scoped), Gateway (cluster operator), and HTTPRoute (app developer, namespace-scoped) — three owners instead of one shared object.
  • Two separate cross-namespace boundaries exist and are easy to conflate: allowedRoutes controls which namespaces' Routes may attach to a Gateway (default: same namespace only); ReferenceGrant controls which namespaces' backend objects a Route may reference.
  • When two HTTPRoutes tie on match specificity, Gateway API breaks the tie by oldest creation timestamp, then alphabetical {namespace}/{name} — both routes can show Accepted: True while one silently never receives traffic.
  • Default to Gateway API for genuinely multi-tenant clusters that need the permission split; Ingress is still fine for a single-team cluster where that split buys nothing yet.
