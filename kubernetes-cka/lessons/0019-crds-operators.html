CRDs & Operators

Pod, Deployment, Service — every kind so far is one Kubernetes ships with. A CustomResourceDefinition (CRD) lets someone add a brand-new kind to your cluster's API, as if it were built in — which is exactly how Lesson 21's Gateway API objects work.

Mental model: a CRD is a blank order form — it defines the fields a new object type accepts, nothing more. An Operator is the person who reads submitted forms and actually does the work. That predicts something concrete: install the CRD and create an object, and nothing happens yet — the form exists, but no one's reading the tray.

Where this fits

Kubernetes core (Pod, Deployment, Service — built in)
   │
   ▼
CRD  (teaches the API server a new kind, e.g. Certificate)
   │
   ▼
Operator  (a normal Pod, same reconcile loop as Lesson 4's ReplicaSet controller)
   │
   ▼
Watches the new kind, acts on it (e.g. writes a TLS cert into a Secret)

CRD — a new kind, defined

kubectl get crds                       # every custom kind installed
kubectl explain certificate.spec       # CRDs support explain, same as built-ins

Operator — the controller that acts on it

An Operator is ordinary code running as an ordinary Deployment, doing exactly what kube-controller-manager (Lesson 13) does for built-in objects: watch desired state, compare to actual state, reconcile the difference. Why it's built this way: this is the same reconcile-loop pattern from Lesson 4, deliberately reused rather than reinvented — CRDs and Operators just extend that one pattern to things Kubernetes didn't ship with, instead of the API needing a new mechanism per extension.

kubectl get pods -n cert-manager       # the Operator is just a Pod
kubectl logs -n cert-manager deploy/cert-manager   # troubleshoot it like any workload

Try it

Q1. You create a custom-kind object and nothing happens — no error, no result. What's the most likely reason?

The CRD is installed (the API server accepted the object), but no Operator is running to watch and act on it. Check kubectl get pods in the namespace the Operator should be in.

Now, before revealing: an Operator's Pod crashed an hour ago and just restarted. What happens to custom objects created during that hour?

Reveal the answer

Nothing is lost — they're stored in etcd like any other object (Lesson 14). Once the Operator's Pod is Running again, its reconcile loop picks up every object not yet matching desired state, same as a Deployment controller catching up after a restart.

Common mistake: assuming a CRD alone does something — installing it only teaches the API server a shape, it never grants behavior.

A controlled failure

kubectl get crds | wc -l
kubectl get pods -A | grep -iE "operator|controller" | wc -l

Predict first: should these two numbers be roughly equal? Observe: usually not — several CRDs can be installed by one Operator (one controller Pod watching multiple related kinds), so CRD count and running-Operator count are independent numbers, not a 1:1 pairing.

Production best practices

Production note: before installing a CRD-based tool, confirm its Operator has resource requests/limits and a PodDisruptionBudget like any other production workload — an Operator crashing doesn't lose data, but it does stop reconciling everything it manages until it's back.

Exam & interview notes

Ties into Cluster Architecture (25%) and the extension-interfaces pattern from Lesson 18.

Interview Q: "How is an Operator different from a built-in controller like the ReplicaSet controller?" A: Mechanically, it isn't — same watch/compare/reconcile loop, running as a normal Pod instead of inside kube-controller-manager. The only real difference is what kind it watches: a CRD instead of a built-in type.

Recap
  • A CRD only defines a new kind — it doesn't act on it.
  • An Operator is a normal Pod running Lesson 4's reconcile-loop pattern, extended to custom kinds.
  • Custom objects persist in etcd even if the Operator is down — it catches up once it's back.

Confidence check — answer without looking back:

  • Why does Kubernetes reuse the reconcile-loop pattern for Operators instead of inventing something new?
  • When would you need a CRD without an Operator at all? (Hint: think about pure data storage use cases.)
  • What happens to existing custom objects if their Operator is deleted entirely?
  • How would you verify whether a "kind not found" error means the CRD is missing vs. just not yet acted on?
