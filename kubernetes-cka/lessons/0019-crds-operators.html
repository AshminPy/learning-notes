Kubernetes / CKA — Lesson 19 of 24

CRDs & Operators

Why this matters

A CustomResourceDefinition lets anyone with cluster-admin rights add a brand-new API type to your cluster with a single kubectl apply — no review of Kubernetes' own code, no core binary touched. That convenience cuts both ways. Install a CRD together with its Operator from a source you haven't audited, and you've given that code a standing reconcile loop that runs forever, with whatever RBAC permissions its ServiceAccount happens to hold — often broad ones, because watching and fixing a custom resource cluster-wide usually needs cluster-wide read/write access. The same pattern also produces one of the most disorienting silent failures a newcomer hits in Kubernetes: you write a perfectly valid custom object, kubectl apply reports created, and then genuinely nothing happens — no error, no result, no log line anywhere. That's not a bug in your YAML. It's the expected behavior of a CRD with no Operator watching it, and this lesson exists so "nothing happened" stops being mysterious.

Mental model: a CRD is a blank order form — it defines exactly which fields a new object type accepts, and the API server will happily file away any form filled in correctly. An Operator is the person who actually reads submitted forms from the inbox and does something about them. Sharpen that: almost every other object on this course already has someone reading its inbox before you ever touch it — a Deployment's ReplicaSet controller, a Job's controller, a Service's endpoint controller, all run inside kube-controller-manager and start watching the moment your cluster boots, whether or not you ever create an object of that kind. A CRD ships with zero readers. The API server validates your object against its schema, stores it in etcd, and returns success — exactly like it would for a Pod or a Deployment — but unless you deployed an Operator yourself, that form sits in an inbox nobody is checking. Same-looking success message, completely different real-world outcome. That's the trap this mental model predicts: kubectl apply succeeding tells you nothing about whether anything is actually going to happen.

CRD — a new kind, defined

Installing a CRD teaches the API server a new kind — cert-manager, for example, installs a Certificate CRD (more on cert-manager below). The moment it's installed, you can create objects of that kind immediately: the API server validates them against the CRD's schema, stores them in etcd, and serves them back through kubectl get — exactly the same storage and retrieval behavior every built-in kind gets. Kubernetes' own docs are direct about the limit here: "on their own, custom resources let you store and retrieve structured data. When you combine a custom resource with a custom controller, custom resources provide a true declarative API." Storage and retrieval, on their own, is all a CRD buys you.

kubectl get crds                       # every custom kind installed in this cluster
kubectl explain certificate.spec       # CRDs support explain, same as built-in kinds

kubectl explain works against a CRD's schema the same way it works against a built-in kind's, because a CRD is required to publish a schema — kubectl reads field names, types, and descriptions straight from the API server, with no special-case code for custom kinds. From kubectl's point of view, a well-defined custom kind and a built-in kind look identical. The only difference is who's watching.

The status subresource — where the Operator writes back

Every object on this course follows the same split: spec is what you want, status is what's actually true. You've been writing spec since Lesson 1; you've mostly been reading, not writing, status — because for built-in kinds, the built-in controller is the only thing meant to write it. The same rule applies to custom resources, and it's the single most important convention an Operator has to respect. Kubernetes' own docs describe the pattern generally: "the Kubernetes declarative API enforces a separation of responsibilities. You declare the desired state of your resource. The Kubernetes controller keeps the current state of Kubernetes objects in sync with your declared desired state." Applied to a CRD: you write spec, the Operator reads it, does the real-world work, and writes the outcome — success, failure, or in-progress — back into status. A well-built Operator should never write to an object's own spec; if it did, it would be silently overriding what you asked for instead of reporting what actually happened.

This is also your primary diagnostic tool later in this lesson: a custom object's status.conditions field is where a well-built Operator tells you, in structured form, exactly what it thinks is wrong — before you ever need to read a single log line.

CRD versioning, briefly — know it exists

One more mechanism worth recognizing rather than mastering at this stage: a CRD can serve more than one API version at once (v1alpha1 and v1beta1, for example), so some clients can keep using the old version while others migrate to the new one. Exactly one served version must be marked the storage version — the shape actually persisted in etcd — and every other served version is converted to and from that shape on request. If the versions are structurally identical, Kubernetes' default None conversion strategy handles this for free, changing only the apiVersion field. If the schema genuinely changed between versions — a field renamed or restructured — you need a conversion webhook: a small HTTP service the API server calls to translate an object between versions. You won't write one of these for the exam, or probably for most of your career — just recognize "conversion webhook" as "the thing that translates between CRD versions when a simple field-rename in a manifest isn't enough."

Operator — the controller that acts on it

An Operator is ordinary code, running as an ordinary Deployment/Pod in your cluster, doing the exact same job kube-controller-manager does for built-in objects: watch for a desired state, compare it to actual state, reconcile the difference. Kubernetes' own docs put it plainly: "Operators are software extensions to Kubernetes that make use of custom resources to manage applications and their components. Operators follow Kubernetes principles, notably the control loop." Create a Certificate object — the cert-manager Operator notices, requests a certificate from whatever issuer you configured, and writes the result into a Secret. You never told it how; the CRD only described the shape of the request.

kubectl get pods -n cert-manager       # the Operator is just a Pod
kubectl logs -n cert-manager deploy/cert-manager   # troubleshoot it like any workload

This is the same reconcile-loop pattern from Lesson 4 — a Deployment's ReplicaSet controller keeps replica count matching spec, forever, without you asking it to check again. CRDs and Operators just extend that exact pattern to things Kubernetes didn't ship with. The only genuinely new risk is who wrote the loop: for a Deployment, it's Kubernetes' own reviewed code; for a custom kind, it's whoever built the Operator you installed.

Production example

Production note: the default answer to "we need Kubernetes to manage X for us" should be "is there already a well-audited CRD + Operator for X from a reputable project," not "let's write one." cert-manager is the canonical example: it's a CNCF Graduated project (accepted 2020, graduated September 2024) that installs a Certificate CRD plus a controller, and its own docs describe the job plainly — it "creates TLS certificates for workloads in your Kubernetes or OpenShift cluster and renews the certificates before they expire," storing "the private key and certificate...in a Kubernetes Secret which is mounted by an application Pod or used by an Ingress controller." Thousands of clusters run this exact Operator instead of every team hand-rolling a cron job that calls an ACME API and rotates a Secret. Hand-rolling that yourself means you own the reconcile loop, the retry/backoff logic, the RBAC surface, and every edge case in certificate renewal, forever. Reaching for cert-manager means you inherit a maintained, widely-reviewed implementation instead — at the cost of trusting its maintainers and its RBAC footprint, which is exactly the trade-off the Decision guide below makes explicit.

Hands-on exercise

Objective

Prove to yourself that a CRD is inspectable exactly like a built-in kind, and that its Operator is just another Pod you can check on.

Scenario

You want to see a real CRD's schema with kubectl explain before you ever trust a Certificate manifest you copy from a README.

Environment assumptions

Any cluster you can kubectl into (kind, minikube, or a real dev cluster) with outbound internet access to pull a public manifest and container images. No existing cert-manager namespace.

Commands

kubectl get crds
# a bare kind/minikube cluster commonly prints "No resources found" here — expected, not broken

kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.21.1/cert-manager.yaml
kubectl get crds | grep cert-manager.io
kubectl explain certificate.spec
kubectl get pods -n cert-manager --watch

Expected result

After the apply, get crds lists several *.cert-manager.io CRDs (certificates, issuers, clusterissuers, among others). kubectl explain certificate.spec prints a structured field list — secretName, issuerRef, dnsNames, duration, and more — the same explain output style you've used for every built-in kind since Lesson 1. Within a minute or two, --watch shows three Pods (cert-manager, cert-manager-cainjector, cert-manager-webhook) reach Running.

Verification

Stop the watch (Ctrl-C) once all three Pods read 1/1 Running. That's your Operator — a real workload, schedulable, restartable, and log-able like anything else in this course, not a mysterious control-plane feature.

Common failure

The webhook Pod takes noticeably longer than the other two to go Running (it waits on a certificate of its own being injected by cainjector) — don't assume the install failed if it's still 0/1 after 20-30 seconds; give it the full couple of minutes before troubleshooting further.

Troubleshooting

If kubectl explain certificate.spec errors that the server doesn't recognize the resource type, the CRDs haven't finished registering yet — re-run kubectl get crds | grep cert-manager.io first to confirm they exist, then retry.

Cleanup / rollback

Leave cert-manager installed — the Failure scenario, Troubleshooting workflow, and Production challenge below all assume it's still running.

Production lesson

kubectl explain succeeding only proves the CRD is installed and its schema is readable. It proves nothing about whether an Operator is running, or whether it will ever act on an object you create — that's a completely separate fact, and the next two sections are about exactly that gap.

Failure scenario

A realistic incident built from the exact gap above — except this time the CRD, the Operator, and every object created against it were all fine on day one. The failure shows up days later, somewhere else entirely.

  1. Mon 09:14 A platform engineer runs a routine "scale down idle workloads" cleanup script, targeting Deployments with near-zero recent CPU usage. cert-manager's own Deployment matches the filter — its work is bursty, only active during issuance/renewal — and gets scaled to 0 replicas along with several genuinely idle apps.
  2. Mon 09:15 kubectl get pods -n cert-manager would show zero Pods, but nobody runs it — the cleanup script's dashboard only reports "Deployments scaled down: 14," not which ones, and no alert exists for "an Operator's replica count dropped to zero."
  3. Mon–Fri Teams keep creating and updating Certificate objects as normal all week. Each one is accepted by the API server and stored in etcd, showing a stale status.conditions from its last real reconcile. Nothing updates it and nothing errors either, because nothing is reconciling at all.
  4. Fri 06:58 A production Ingress's TLS certificate crosses its actual expiry. Its scheduled renewal — which would normally fire well before this point — never happened, because no Operator has watched it for four days.
  5. Fri 07:02 Customers hit browser TLS warnings on the checkout domain; the error-rate alert fires almost immediately after.
  6. Fri 07:06 On-call runs kubectl get pods -n cert-manager as one of the first checks — No resources found. That single command finds the root cause in under a minute.
  7. Fri 07:08 Fix applied: kubectl scale deployment cert-manager -n cert-manager --replicas=1 (and the same for cainjector and webhook). The reconcile loop resumes immediately.
  8. Fri 07:11 cert-manager notices the expired certificate on its next reconcile pass and issues a new one automatically — nobody touches the Certificate object itself, because its spec was correct the entire time.
  9. Fri 07:15 Verified: the new certificate is live in the Secret, the Ingress serves it, browser warnings are gone.
  10. Fri 09:00 Postmortem action item: alert explicitly on "any Operator Deployment's ready replicas == 0," separate from application-level alerts — an Operator being down produces no application error until something it manages actually expires or drifts.

Troubleshooting workflow

The general method, applied specifically to "I created a custom object and nothing is happening":

  1. Confirm the symptom. Run kubectl get <kind> <name> -o yaml yourself — is status genuinely empty or stale, not just "I expected more by now"?
  2. Define scope. kubectl get <kind> --all-namespaces — is it one broken object, or is every object of this kind stalled at once? The second pattern points straight at the Operator itself.
  3. Check recent changes. kubectl get events -n <operator-namespace> --sort-by=.lastTimestamp — was the Operator's Deployment scaled, restarted, or the CRD just upgraded to a new served version?
  4. Confirm the primitives exist and are alive. kubectl get crd <plural>.<group> confirms the kind is really installed, not a typo accidentally matching a different CRD; kubectl get pods -n <operator-namespace> confirms the Operator's Pod is actually Running, not 0, Pending, or CrashLoopBackOff. If it isn't, stop here — fix the Operator, not your object.
  5. Read what the Operator already told you. kubectl describe <kind> <name> — its Status.Conditions and Events sections are where a well-built Operator reports its own diagnosis, before you ever need a log line.
  6. Check the Operator's own logs for errors reconciling YOUR specific object. kubectl logs -n <operator-namespace> deploy/<operator> | grep <object-name> — treat this as the secondary, noisier source. cert-manager's own troubleshooting docs say exactly this: don't reach for logs first, check conditions and events before them.
  7. Form a hypothesis. For example: "the Operator is healthy, but this object references an Issuer that doesn't exist," versus "the whole Operator has been down since Monday."
  8. Test one variable. Fix only the one field you suspect (a bad reference, say) and re-apply — don't also restart the Operator or recreate the object in the same step, or you won't know which change actually fixed it.
  9. Apply the safest fix and verify. Correct spec if the mistake is yours; scale or restart the Operator if it's down. Never hand-edit status — it's the Operator's field, and your edit is overwritten on the next reconcile anyway. Confirm status.conditions reports success afterward (cert-manager's Ready: True, for example).
  10. Document the root cause and prevent recurrence. Write down the actual cause ("Operator scaled to 0 by a cleanup script," not "cert-manager broke"), and add the missing signal — per the Failure scenario above, an alert on the Operator's own health, not just on the objects it manages.

Security note: an Operator's ServiceAccount usually needs broad permissions to do its job — cert-manager's controller, for example, needs to read and write Secrets across namespaces and watch Certificates and Issuers cluster-wide, which in practice means a ClusterRole, not a narrow namespaced Role. Lesson 9 covered why that matters: RBAC is additive-only, with no deny rules — a broad ClusterRoleBinding for an Operator's ServiceAccount is exactly the kind of grant that lesson told you to scrutinize, except this time the code exercising those permissions isn't something your own team wrote. Installing a CRD and its Operator is not a config change — it's extending your cluster's trusted codebase to include someone else's controller, running continuously, with standing permissions you granted once and, realistically, may never review again. Treat "which Operators are installed, and what can their ServiceAccounts touch" as a real line item on your cluster's security inventory, not a one-time install-day decision.

Reliability note: every custom object's future is coupled to one Operator's uptime — if it runs as a single replica with no PodDisruptionBudget, a single node drain or an accidental scale-to-zero (see the Failure scenario above) halts reconciliation for every object of that kind, cluster-wide, with no error surfaced anywhere until something it manages actually expires or drifts. Many production-grade Operators support running multiple replicas with leader election (the same mechanism kube-controller-manager itself uses) so only one instance actively reconciles while the others stand ready to take over. Check whether the Operator you're installing supports this instead of assuming a single Pod is an acceptable single point of failure.

Common mistake: assuming a custom object failed because of a typo in your YAML, when the real cause is that no Operator is installed or running at all. The API server validates your object against the CRD's schema and will happily accept a perfectly-typed object that nothing will ever act on — schema-valid and functionally-inert are two completely different properties, and kubectl apply succeeding tells you nothing about the second one.

Common mistake: checking only whether kubectl apply succeeded and never reading the object's own status field afterward. A healthy, Running Operator Pod doesn't mean it's succeeding at reconciling every object it manages — status.conditions is where it reports per-object failures (a bad reference, a quota limit, an expired credential), and skipping that check is how a broken Certificate sits silently failing for days, exactly like the Failure scenario above.

Knowledge check

Q1. You create a custom-kind object and nothing happens — no error, no result. What's the most likely reason?

The CRD is installed (so the API server accepted the object), but no Operator is running to watch and act on it. Check kubectl get pods in the namespace the Operator should be in.

Q2. An Operator's Pod crashed an hour ago and just restarted. What happens to custom objects created during that hour?

Nothing is lost — they're stored in etcd like any other object. Once the Operator's Pod is Running again, its reconcile loop picks up every object that doesn't yet match desired state, same as a Deployment controller catching up after a restart.

Q3. Where does a well-built Operator write the result of its last reconcile attempt for a custom object — success, failure, or in progress?

B. The declarative API pattern keeps spec (what you want) and status (what's actually true) as separate fields on the same object — an Operator should only ever write status.

Q4. A CRD adds a new v1beta1 version alongside its existing v1alpha1, and the schema is structurally identical between the two. What's needed to serve both?

B. A conversion webhook is only required when the schema genuinely changes between versions. If it doesn't, the default None strategy handles it for free.

Q5. Why does installing a CRD and its Operator effectively extend your cluster's trusted codebase, even though you didn't write any of that code yourself?

Because the Operator's ServiceAccount usually holds broad, often cluster-scoped RBAC permissions to do its job, and that code now runs continuously with those permissions. Lesson 9's RBAC rule — no grant means no access, but any grant is a standing capability — applies just as much to code you installed as to code your own team wrote.

Production challenge

Objective

Diagnose a custom object stuck in a failed state using only the signals a real Operator exposes — kubectl describe, and only if needed, its logs — in the same order a real on-call engineer would use.

Scenario

A teammate created a Certificate for a new internal tool, pointing at a ClusterIssuer name they misremembered. It's been sitting unissued for an hour and they've pinged you: "TLS isn't working, can you check?"

Environment assumptions

cert-manager already installed and Running (from the Hands-on exercise above). Create the broken state yourself first — this simulates the teammate's mistake:

kubectl create namespace demo-tls
cat <<'EOF' | kubectl apply -f -
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: demo-cert
  namespace: demo-tls
spec:
  secretName: demo-cert-tls
  dnsNames:
  - demo.example.com
  issuerRef:
    name: does-not-exist
    kind: ClusterIssuer
EOF

Commands

Diagnose it the way the Troubleshooting workflow above prescribes — state before logs:

kubectl get certificate demo-cert -n demo-tls
kubectl describe certificate demo-cert -n demo-tls
kubectl get clusterissuer does-not-exist    # confirm your hypothesis before "fixing" anything

# Only reach for logs if describe's Conditions/Events genuinely don't explain it:
kubectl logs -n cert-manager deploy/cert-manager | grep demo-cert

Expected result

kubectl get certificate shows a READY column of False, not blank — proof the Operator is reconciling this object, it just can't complete it. describe's Status.Conditions section shows a condition of Type: Ready, Status: False, with a Reason and Message naming the problem. cert-manager's own troubleshooting docs show this exact shape for a different failure (a missing Secret):

Status:
  Conditions:
    Message:  Issuing certificate as Secret does not exist
    Reason:   DoesNotExist
    Status:   False
    Type:     Ready

Your Reason/Message will name the missing ClusterIssuer instead — read what it actually says rather than assuming it matches this example verbatim; the exact wording depends on your cert-manager version and what's actually broken. kubectl get clusterissuer does-not-exist confirms the object genuinely doesn't exist, proving the hypothesis before you touch anything.

Verification

Fix it by creating the missing Issuer (a minimal self-signed one is enough to prove the reconcile loop — no real CA needed):

cat <<'EOF' | kubectl apply -f -
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: does-not-exist
spec:
  selfSigned: {}
EOF
kubectl get certificate demo-cert -n demo-tls --watch

READY should flip to True within roughly a minute, with no change made to the Certificate object itself — the fix was entirely on the Issuer side, exactly as describe told you.

Common failure

Staring at the Certificate object's YAML looking for a typo in dnsNames or secretName — there isn't one. The object's shape is completely valid; it references something that doesn't exist, and no amount of re-reading the YAML in isolation reveals that. Only the Operator's own reconcile output (status.conditions) can.

Troubleshooting

If describe shows no Conditions at all — not even a False one — that's a different problem than the one this exercise built: it means nothing has ever reconciled this object, which points back at "is the Operator even Running" (Hands-on exercise, step one), not at a bad reference.

Cleanup / rollback

kubectl delete certificate demo-cert -n demo-tls --ignore-not-found
kubectl delete clusterissuer does-not-exist --ignore-not-found
kubectl delete namespace demo-tls --ignore-not-found
# Optional full cleanup of the Hands-on exercise's install:
kubectl delete -f https://github.com/cert-manager/cert-manager/releases/download/v1.21.1/cert-manager.yaml

Production lesson

The habit that separates a fast diagnosis from a confused hour of YAML-staring is the same one from the Troubleshooting workflow: read status.conditions and Events before logs, and logs before guessing. cert-manager's own docs say this explicitly — don't reach for controller logs first, they're verbose; check conditions and events before them. That ordering generalizes to any CRD + Operator pair you'll ever troubleshoot, not just this one.

Recap
  • A CRD only teaches the API server a new kind and gives it storage/retrieval — it has zero real-world effect until an Operator is watching it.
  • An Operator is ordinary code (a Pod, usually a Deployment) running the same reconcile-loop pattern as built-in controllers, extended to a custom kind.
  • Operators write outcomes to status, never spec — spec is what you asked for, status is what actually happened. Check status.conditions before logs.
  • A CRD can serve multiple versions; a conversion webhook is only needed when the schema genuinely changes between them.
  • Installing a CRD + Operator extends your cluster's trusted codebase, usually with broad RBAC permissions on the Operator's ServiceAccount — treat it as a security decision, not just a feature install.
  • Default to a well-audited existing Operator (cert-manager, for TLS) over hand-rolling your own, unless nothing suitable exists.
