CRDs & Operators

Pod, Deployment, Service — every kind you've written so far is one Kubernetes ships with. A CustomResourceDefinition (CRD) lets someone add a brand new kind to your cluster's API, as if it were built in.

Simple example: a CRD is a blank order form — it defines the fields a new object type accepts, nothing more. An Operator is the person who reads submitted forms and actually does the work. Install the CRD and nothing happens; you need an Operator watching it to act.

CRD — a new kind, defined

Installing a CRD teaches the API server a new kind — e.g. cert-manager installs a Certificate CRD. You can create objects of that kind immediately, they just do nothing until something is watching them.

kubectl get crds                       # every custom kind installed in this cluster
kubectl explain certificate.spec       # CRDs support explain, same as built-in kinds

Operator — the controller that acts on it

An Operator is ordinary code, running as an ordinary Deployment/Pod in your cluster, doing the exact same thing kube-controller-manager does for built-in objects: watch for a desired state, compare to actual state, reconcile the difference. Create a Certificate object — the cert-manager Operator notices, requests a cert, and writes the result into a Secret. You never told it how; the CRD only described the shape of the request.

kubectl get pods -n cert-manager       # the Operator is just a Pod
kubectl logs -n cert-manager deploy/cert-manager   # troubleshoot it like any workload

This is the same reconcile-loop pattern from Lesson 4 (a Deployment's controller keeps replica count matching spec) — CRDs and Operators just let you extend that pattern to things Kubernetes didn't ship with.

Try it — before looking below

Q1. You create a custom-kind object and nothing happens — no error, no result. What's the most likely reason?

The CRD is installed (so the API server accepted the object), but no Operator is running to watch and act on it. Check kubectl get pods in the namespace the Operator should be in.

Q2. An Operator's Pod crashed an hour ago and just restarted. What happens to custom objects created during that hour?

Nothing is lost — they're stored in etcd like any other object. Once the Operator's Pod is Running again, its reconcile loop picks up every object that doesn't yet match desired state, same as a Deployment controller catching up after a restart.

Source

kubernetes.io/docs — Custom Resources and kubernetes.io/docs — Operator pattern — exam-allowed pages.

Recap
  • A CRD only defines a new kind — it doesn't act on it.
  • An Operator is a normal Pod running a reconcile loop, the same pattern as built-in controllers.
  • Custom objects persist in etcd even if the Operator is down — it catches up once it's back.
