Helm & Kustomize

Every object so far, you've written by hand. Real cluster components (an Ingress controller, cert-manager, Prometheus) ship as someone else's YAML — dozens or hundreds of files. Helm and Kustomize are the two tools the exam expects for installing and adapting that YAML without hand-editing every file.

Mental model: Helm packages and templates a whole app into one installable unit (a "chart") — an app-store install. Kustomize takes plain YAML you already have and layers small, targeted edits on top ("overlays") without touching the originals. That predicts when each fits: distributing a reusable package to other people needs Helm's structure; a single app that only differs by replica count between dev and prod doesn't need a templating language at all.

Where this fits

Someone else's YAML (a chart, or a base)
   │
   ▼
Helm: template + install as a tracked "release"
   OR
Kustomize: patch the base with small overlays, no templating
   │
   ▼
Ordinary Kubernetes objects — Deployments, Services, everything from Lessons 1-16

Helm — install and manage packaged apps

A chart is templated manifests plus a values.yaml of defaults. Installing one creates a release — a tracked, named instance in your cluster.

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm install my-ingress ingress-nginx/ingress-nginx
helm upgrade my-ingress ingress-nginx/ingress-nginx --set controller.replicaCount=2
helm rollback my-ingress 1
helm uninstall my-ingress

Why it's built this way: whatever Helm installs is still ordinary Kubernetes objects underneath (kubectl get all -l app.kubernetes.io/instance=my-ingress shows them) — Helm only changes how they got created, not what they are, so nothing about troubleshooting them changes.

Kustomize — patch YAML without templating

Built into kubectl since v1.14 — no install needed. A base (plain manifests) plus overlays (small patches) per environment:

# overlays/prod/kustomization.yaml
resources:
- ../../base
patches:
- target: { kind: Deployment, name: my-app }
  patch: |-
    - op: replace
      path: /spec/replicas
      value: 5

kubectl kustomize overlays/prod   # render only
kubectl apply -k overlays/prod    # render and apply

Try it

Q1. You need to deploy the same app to dev and prod, only the replica count differs. Kustomize or Helm — which fits with less setup?

Kustomize — one base, two small overlays, no templating language or chart authoring. Helm's structure earns its cost when distributing a reusable package to others.

Now, before revealing: a teammate ran helm install and three Pods are crashing. What commands do you run — do you need anything Helm-specific?

Reveal the answer

No — kubectl get pods, describe, logs, same as Lesson 16. Find them via kubectl get all -l app.kubernetes.io/instance=<release> if you don't know their names.

Common mistake: assuming a Helm-installed app needs Helm-specific troubleshooting — it doesn't, Helm's involvement ends the moment the objects are created.

A controlled failure

helm install demo ingress-nginx/ingress-nginx --set controller.replicaCount=999
kubectl get pods -l app.kubernetes.io/instance=demo

Predict first: does this fail cleanly, or create 999 Pods stuck Pending? Observe: Helm doesn't validate whether your cluster can actually run 999 replicas — it just renders and applies the YAML. The Pods get created and most sit Pending, no different from Lesson 4's scheduling constraints, because Helm's job ended at "apply," not "verify it's sane."

helm uninstall demo

Production best practices

Production note: pin exact chart versions in CI (helm install --version x.y.z) rather than always pulling latest — an upstream chart update can silently change defaults under you otherwise.

Exam & interview notes

Both tools are explicitly listed in the CKA curriculum under Cluster Architecture, Installation & Configuration (25%).

Interview Q: "When would you reach for Kustomize instead of Helm?" A: When you own the base YAML and only need small, environment-specific tweaks — no templating language, no chart-authoring overhead, built into kubectl already.

Recap
  • Helm = package + template + track as a "release." Kustomize = patch existing plain YAML, no templating.
  • kubectl apply -k <dir> is built into kubectl — no separate install.
  • Whatever either tool creates is ordinary Kubernetes objects — troubleshoot the same way, regardless of how they got created.

Confidence check — answer without looking back:

  • Why does neither tool require Helm/Kustomize-specific troubleshooting knowledge once objects exist?
  • When would Helm's extra structure actually pay off over Kustomize?
  • What happens if a Helm chart's values request more replicas than the cluster can schedule?
  • How would you verify which tool (or neither) created a given running object?
