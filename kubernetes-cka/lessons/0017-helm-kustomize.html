Helm & Kustomize

Every object so far, you've written by hand. In the real world, cluster components (an Ingress controller, cert-manager, Prometheus) ship as someone else's YAML — dozens or hundreds of files. Helm and Kustomize are the two tools the exam expects you to know for installing and adapting that YAML without hand-editing every file.

Simple example: Helm packages and templates a whole app into one installable unit (a "chart") — think an app store install. Kustomize takes plain YAML you already have and layers small, targeted edits on top ("overlays") without touching the original files. Different problem, both exam-tested, often used together.

Helm — install and manage packaged apps

A chart is a packaged set of templated manifests plus a values.yaml of defaults. Installing one creates a release — a tracked, named instance of that chart in your cluster.

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
helm install my-ingress ingress-nginx/ingress-nginx
  • helm upgrade my-ingress ingress-nginx/ingress-nginx --set controller.replicaCount=2 — change config, same release
  • helm rollback my-ingress 1 — back to a previous revision
  • helm uninstall my-ingress — remove everything the chart created
  • helm template ingress-nginx/ingress-nginx — render the manifests locally, without installing anything

Whatever Helm installs is still ordinary Kubernetes objects underneath — kubectl get all -l app.kubernetes.io/instance=my-ingress shows them. Troubleshoot a Helm-installed app exactly like any other: describe, logs, get events. Helm only changes how it got created.

Kustomize — patch YAML without templating

Kustomize has been built into kubectl since v1.14 — no install needed. It starts from a base (plain manifests) and applies overlays (small patches) for each environment.

# base/kustomization.yaml
resources:
  - deployment.yaml
  - service.yaml

# overlays/prod/kustomization.yaml
resources:
  - ../../base
patches:
  - target:
      kind: Deployment
      name: my-app
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 5
  • kubectl kustomize overlays/prod — render the final YAML, don't apply
  • kubectl apply -k overlays/prod — render and apply in one step

No templating language, no {{ }} — just your real YAML, plus patches. That's the whole pitch.

Try it — before looking below

Q1. You need to deploy the same app to dev and prod, only the replica count differs. Kustomize or Helm — which fits with less setup, and why?

Kustomize — one base, two small overlays, no templating language or chart authoring needed. Helm is worth the extra structure when you're distributing a reusable package to other people/teams, not for a single app with a one-line difference between environments.

Q2. A teammate ran helm install and now three Pods are crashing. What commands do you run — do you need to know anything Helm-specific to debug it?

No — kubectl get pods, kubectl describe pod, kubectl logs, same as always. Helm's involvement ended the moment the objects were created; find them with kubectl get all -l app.kubernetes.io/instance=<release> if you don't know their names.

Source

helm.sh/docs and kubectl.docs.kubernetes.io — Kustomize reference — exam-allowed pages.

Recap
  • Helm = package + template + track as a "release." Kustomize = patch existing plain YAML, no templating.
  • kubectl apply -k <dir> is built into kubectl — no separate install.
  • Whatever either tool creates is ordinary Kubernetes objects — troubleshoot the same way regardless of how they got created.
