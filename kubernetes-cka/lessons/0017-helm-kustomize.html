Helm & Kustomize

Why this matters

Every object you've written so far, you wrote by hand. In the real world, cluster components — an Ingress controller, cert-manager, the Prometheus stack — ship as someone else's YAML, dozens or hundreds of files, and your own team's app needs slightly different config in dev, staging, and prod. Helm and Kustomize are the two tools the exam (and real platform teams) use to install and adapt that YAML without hand-editing every file. The stakes are not theoretical: a single helm upgrade that changes one line in a shared chart's values.yaml doesn't touch one Pod — it can roll a broken config out to every environment that chart is used in, silently, because the whole point of a chart is that many teams reuse the same templates. And when that broken rollout is live at 2am, the on-call engineer who doesn't already know helm rollback <release> <revision> cold — not kubectl edit, not deleting and reapplying files by hand — burns real incident minutes rediscovering it from scratch, or worse, "fixes" it in a way the tool doesn't know about and quietly undoes later.

Mental model: Helm and Kustomize are two different translators that both compile down to the same target language — plain Kubernetes API objects. The API server has no spec.createdBy: helm field it checks before scheduling a Pod, evaluating a probe, or enforcing RBAC; the moment an object exists in etcd, whatever tool produced it is irrelevant to how the cluster treats it. This predicts something you can verify yourself: run kubectl get deployment <name> -o yaml against a Deployment created by helm install and one created by kubectl apply -k, and the spec block — replicas, template, containers, probes, resource limits — reads like ordinary Deployment YAML either way, with only a handful of tool-specific labels layered on top (Helm adds app.kubernetes.io/managed-by: Helm and helm.sh/chart; Kustomize adds none by default). It also predicts the trap this lesson's Common mistakes section covers below: since the cluster itself doesn't enforce which tool "owns" an object, a kubectl edit on a Helm-managed or Kustomize-managed resource is accepted immediately and unconditionally — the drift only surfaces the next time that tool tries to reconcile the object, not before.

Helm — install and manage packaged apps

A chart is a packaged, templated set of manifests plus a values.yaml of defaults — the reusable unit you helm install. Installing a chart creates a release: a named, tracked instance of that chart in a specific namespace. Every release keeps a full revision history — helm install, helm upgrade, and helm rollback each increment the release's revision counter by exactly 1, starting from revision 1 on install. That history is what makes rollback possible at all: it isn't "undo my last edit," it's "redeploy the manifests exactly as they were at revision N."

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
helm install my-ingress ingress-nginx/ingress-nginx
  • helm upgrade my-ingress ingress-nginx/ingress-nginx --set controller.replicaCount=2 — apply a config change to the same release; revision +1
  • helm history my-ingress — list every revision this release has ever had: number, timestamp, status, chart version, app version, and a one-line description
  • helm rollback my-ingress 1 — redeploy revision 1's manifests. This does not take the release back to "revision 1" — it creates a brand-new revision (say, revision 4) whose content matches revision 1. helm history afterward still lists every revision that ever happened, in order, never rewound.
  • helm uninstall my-ingress — delete every object the chart created; add --keep-history if you might want to inspect past revisions later without a live release
  • helm template ingress-nginx/ingress-nginx — render the manifests locally: no cluster contact, nothing installed, values normally looked up in-cluster are faked
  • helm get manifest my-ingress — fetch the exact YAML the currently-installed release actually applied, straight from Helm's own record

A real helm history looks like this — read the columns, not just the numbers:

REVISION  UPDATED                   STATUS      CHART        APP VERSION  DESCRIPTION
1         Mon Aug  3 09:12:01 2026  superseded  demo-0.1.0   1.16.0       Install complete
2         Mon Aug  3 09:14:33 2026  superseded  demo-0.1.0   1.16.0       Upgrade complete
3         Mon Aug  3 09:16:50 2026  deployed    demo-0.1.0   1.16.0       Rolled back to 1

Whatever Helm installs is still ordinary Kubernetes objects underneath — kubectl get all -l app.kubernetes.io/instance=my-ingress shows them, using the label every Helm-created object carries automatically. Troubleshoot a Helm-installed app exactly like any other: describe, logs, get events. Helm only changes how it got created — not how it behaves once it exists, and not how you debug it.

Kustomize — patch YAML without templating

Kustomize has been built into kubectl since v1.14 (2019) — no separate install. It starts from a base (plain manifests) and layers overlays (small, targeted patches) on top, one per environment — no templating language, no {{ }}, just your real YAML plus patches.

# base/kustomization.yaml
resources:
  - deployment.yaml
  - service.yaml

# overlays/prod/kustomization.yaml
resources:
  - ../../base
patches:
  - target:
      kind: Deployment
      name: my-app
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 5
  • kubectl kustomize overlays/prod — render the final YAML, don't apply
  • kubectl apply -k overlays/prod — render and apply in one step
  • kubectl diff -k overlays/prod — render, then diff the result against what's actually live in the cluster, without applying anything

Two generator fields solve a real problem from Lesson 6: a Pod that reads a ConfigMap as an environment variable freezes that value at container start and never picks it up again without a manual rollout. configMapGenerator (and its twin, secretGenerator) build the ConfigMap or Secret from literals or files and append a content hash to its generated name — change the content, the hash changes, the name changes. Kustomize then automatically rewrites every reference to that name across your manifests, so the Pod template itself changes on the next apply — which forces a real rollout with new Pods that read the new value. No separate restart step, no Reloader-style controller needed.

# base/kustomization.yaml
configMapGenerator:
  - name: app-config
    literals:
      - LOG_LEVEL=info
resources:
  - deployment.yaml

kubectl kustomize . on that base renders a ConfigMap named something like app-config-c888dfbhf8. Change LOG_LEVEL to debug and the suffix changes too — any Deployment in the same kustomization that references app-config gets rewritten to reference the new name automatically, which is exactly the "new object, new rollout" pattern Lesson 6 recommended hand-building with a content-hash suffix.

Production example

Production note: most platform teams standardize on one tool per boundary, not one tool for everything. A common real split: Helm for anything you install from someone else — ingress-nginx, cert-manager, the Prometheus stack — because those projects already ship and version their own charts, and you want their tested upgrade path, not one you invent yourself. Kustomize for internal apps across environments — the same 40-line Deployment for a team's own service, with three overlays (dev/staging/prod) that differ only in replica count, resource limits, and one environment variable — because there's no reusable "package" here to justify chart authoring and its versioning overhead for code your own team owns end to end. Mixing both without that boundary — wrapping your own single app in a Helm chart and patching the result with Kustomize, or hand-authoring chart templates for something that's really one Deployment with three tiny variants — is the pattern that produces the most confused on-call handoffs, because now two tools both believe they own the same object's reconciliation. Either way, the render step belongs in CI before apply ever runs: a pipeline stage that runs helm template or kubectl kustomize and reviews the rendered diff catches a bad values.yaml change or a broken JSON patch while it's still text on a pull request — not after it's already live.

Hands-on exercise

Objective

Prove to yourself — don't take the lesson's word for it — what a Helm "revision" actually is, and that helm rollback doesn't rewind the revision counter.

Scenario

You want to see revision history and rollback behave with your own eyes before you'd trust helm rollback in a real incident.

Environment assumptions

A kind/minikube cluster (or real dev cluster) with the Helm v3 CLI installed locally, and outbound internet access from the cluster's nodes to pull the nginx image. No existing release named demo-release in the current namespace.

Commands

helm create demo
helm install demo-release ./demo
kubectl get pods -l app.kubernetes.io/instance=demo-release

helm upgrade demo-release ./demo --set replicaCount=3
kubectl get pods -l app.kubernetes.io/instance=demo-release
helm history demo-release

helm rollback demo-release 1
kubectl get pods -l app.kubernetes.io/instance=demo-release
helm history demo-release

Expected result

After install: one Pod (the chart's default replicaCount: 1). After upgrade: three Pods, and helm history shows revisions 1 and 2. After rollback: one Pod again — but helm history now shows three revisions (1, 2, 3), with revision 3 described as "Rolled back to 1," not a return to "revision 1."

Verification

The Pod count after rollback (1) proves the rollback took effect. The revision count in helm history (3, not 1) proves rollback creates a new revision instead of rewinding the counter — a distinction that matters the moment you script anything, or communicate anything to a teammate, using a specific revision number.

Common failure

Assuming helm rollback demo-release 1 puts the release "back at revision 1" — then checking helm history afterward and being confused that the latest revision number is 3, not 1.

Troubleshooting

If helm install errors that the release already exists, a previous run wasn't cleaned up — run helm uninstall demo-release --ignore-not-found first. If kubectl get pods shows nothing after install, check kubectl get events for ImagePullBackOff — the default scaffold chart pulls nginx from Docker Hub, so this exercise needs real outbound network access from the cluster's nodes.

Cleanup / rollback

helm uninstall demo-release --ignore-not-found
rm -rf demo

Production lesson

helm rollback <release> <revision> is the command you need cold during an incident — it restores known-good manifests in seconds. Hand-editing the live Deployment instead (kubectl scale, kubectl edit) doesn't touch the chart's recorded state — the next helm upgrade, even an unrelated one, can silently undo your manual fix, because Helm reconciles toward what its own revision history says the object should look like, not toward whatever is currently running.

Failure scenario

A realistic incident built on a fact you can check yourself: the default chart scaffold's readinessProbe checks httpGet path / — change that path in a values override to something the app doesn't actually serve, and Lesson 11's readiness mechanics kick in exactly as documented: the Pod stays Running, it just stops receiving traffic.

  1. 14:02 Alert fires: the payments-api Deployment shows 0 of 3 Pods Ready. On-call runs kubectl get pods -l app.kubernetes.io/instance=payments-api — all three Pods are Running, zero restarts, but every one reads 0/1 in the READY column.
  2. 14:04 kubectl describe pod shows the Events section: Readiness probe failed: HTTP probe failed with statuscode: 404 against path /healthz.
  3. 14:06 On-call runs helm history payments-api — revision 14 deployed 22 minutes ago, description "Upgrade complete." helm get manifest payments-api shows the current readiness probe pointing at /healthz; the chart's default before this revision was plain /.
  4. 14:09 Root cause identified: the shared chart's new version added a /healthz default, and the values override enabling it went out before the application code that actually serves that route — next week's release, not this one.
  5. 14:11 Fix applied: helm rollback payments-api 13 — not a live kubectl patch on the probe, because a manual edit would drift from what Helm's own revision history says revision 14 should look like, and get silently reasserted the next time anyone runs a legitimate helm upgrade.
  6. 14:13 Verified: within one probe interval, all three Pods read 1/1 Ready; Service endpoints repopulate; traffic resumes.
  7. 14:30 Root cause recorded, fix scheduled: add a CI step that runs helm template on every chart-version bump and diffs the rendered probe config against the previous revision, so a mismatched probe path fails a pull request instead of reaching production.

Troubleshooting workflow

The general method, applied specifically to "a Helm release or Kustomize-applied app is broken":

  1. Confirm the symptom. kubectl get pods,deployment for the actual current state — Ready counts, restarts, age — not what you remember it looking like yesterday.
  2. Define scope. One Pod, the whole release, or every consumer of a shared chart or base? kubectl get pods -l app.kubernetes.io/instance=<release> (Helm) or by the app's own labels (Kustomize) tells you if this is isolated or systemic.
  3. Check recent changes. helm history <release> for timestamps and descriptions, or git log/git diff on the kustomization and its overlay — was this deployed recently, and by exactly what change?
  4. Inspect the right state. Compare rendered intent against live reality: helm get manifest <release> vs. kubectl get <kind> -o yaml, or kubectl diff -k <overlay> directly — this is the step that reveals drift, not just breakage.
  5. Form a hypothesis. For example: "the last upgrade changed the readiness probe path" or "someone hand-edited this object and it's drifted from the base."
  6. Test one variable. Diff exactly what changed — helm get manifest --revision N-1 against the current revision, or the specific overlay commit — rather than re-deploying blind and hoping.
  7. Apply the safest fix. helm rollback <release> <previous-revision>, or revert the kustomization change in git and kubectl apply -k again — not a live kubectl edit/patch, which the tool won't know about and may silently overwrite or conflict with on the next legitimate change.
  8. Verify recovery. Confirm probes pass and Service endpoints repopulate with kubectl get endpoints, not just that the rollback command exited 0.
  9. Document the root cause. Record exactly which revision or commit introduced the bad value, and which field — "readinessProbe.httpGet.path changed in chart v2.3.0's default values" — not just "rolled back and it's fine now."
  10. Prevent recurrence. Add a CI render-and-review step (helm template / kubectl kustomize) before merge, so the same class of mistake fails a pull request instead of reaching a live cluster.

Security note: Helm supports nine lifecycle hooks (pre-install, post-install, pre-delete, post-delete, pre-upgrade, post-upgrade, pre-rollback, post-rollback, test) that are just ordinary Kubernetes manifests — usually Jobs — marked with a special annotation. Helm's own docs don't carry an explicit warning about this, but it follows directly from what a hook is: a chart from a repository you don't control can ship a hook Job that runs an arbitrary container image, with whatever RBAC permissions the identity running helm install/helm upgrade has. Helm doesn't sandbox this in any way — installing a third-party chart is functionally the same trust decision as applying someone else's raw manifests to your cluster. Treat helm repo add the way you'd treat adding a new package registry: verify the source, and pin exact chart versions instead of always pulling the latest.

Reliability note: rollback capability is the real reliability payoff of tracking deployments through Helm's revision history or a Git-tracked Kustomize overlay at all — it gives you a known-good state to return to in seconds during an incident, instead of reconstructing "what did this look like before" from memory. That safety net only holds if nobody hand-edits the live objects in between: both tools reconcile toward what they think the object should look like based on their own recorded state, not toward whatever is actually running right now.

Common mistake: hand-editing (kubectl edit, patch, or scale) an object that a Helm release or a Kustomize base manages, to fix something quickly during an incident. It works immediately — the API server has no concept of "this object belongs to a tool" — but the fix is invisible to Helm's revision history or the kustomization's patches, and the next legitimate helm upgrade or kubectl apply -k can silently revert it without warning.

Common mistake: mixing Helm and Kustomize on the same object without a clear boundary — for example, using Kustomize to patch a Deployment that a Helm chart also manages. Now two tools both believe they own that object's reconciliation, and whichever one runs last silently wins, with no error telling you the other tool's intended state was dropped.

Decision guide

OptionUse whenAvoid whenTrade-off
HelmInstalling a reusable third-party package — ingress controllers, cert-manager, monitoring stacks — with someone else's tested release pathA single internal app with no real "package" boundary to justify chart authoringRollback and revision history built in; adds a templating layer and its own release state you now have to reason about
KustomizeYour own app across environments (dev/staging/prod) that differ only in small config valuesYou need someone else's already-versioned package — you'd be hand-maintaining patches against their upstream YAML foreverNo templating, keeps real YAML readable; no built-in rollback — you rely on Git history for that, not the tool itself
Plain kubectl apply -fAd hoc single-cluster objects, quick debugging resources, one-off exam scenariosMultiple environments, or anything that needs a repeatable audit trail of what changed and whenZero extra tooling to learn; every environment difference is hand-maintained as a separate file, with no revision history beyond kubectl's own last-applied-configuration annotation

Default recommendation: Helm for anything you didn't author yourself; Kustomize for your own app's environment differences; plain kubectl apply -f only for one-off objects or throwaway debugging — never as the only deployment method for something more than one environment depends on.

Knowledge check

Q1. You need to deploy the same app to dev and prod, only the replica count differs. Kustomize or Helm — which fits with less setup, and why?

Kustomize — one base, two small overlays, no templating language or chart authoring needed. Helm is worth the extra structure when you're distributing a reusable package to other people or teams, not for a single app with a one-line difference between environments.

Q2. A teammate ran helm install and now three Pods are crashing. What commands do you run — do you need to know anything Helm-specific to debug it?

No — kubectl get pods, kubectl describe pod, kubectl logs, same as always. Helm's involvement ended the moment the objects were created; find them with kubectl get all -l app.kubernetes.io/instance=<release> if you don't know their names.

Q3. You run helm rollback my-release 2. Afterward, helm history shows revision 5 as the latest, described "Rolled back to 2." Why isn't the latest revision number 2?

Because rollback doesn't rewind the counter — every install, upgrade, or rollback increments the revision number by 1. Revision 5's content matches revision 2, but it's still a brand-new entry in the history, not a return to entry 2.

Q4. A Deployment reads a value from a ConfigMap as an environment variable. You update the ConfigMap's data through Kustomize's configMapGenerator. What actually makes the running Pods pick up the new value?

B. The content-hash suffix Kustomize appends to the generated ConfigMap's name changes whenever its data changes, and every reference to that name is rewritten automatically — forcing a real Pod template change and a real rollout, which is the only thing that can update an env var (see Lesson 6). A, C, and D all describe live-update mechanisms that don't exist for environment variables.

Q5. Your team owns one internal service that needs slightly different replica counts in dev, staging, and prod, with no plan to share it as a package. Per this lesson's decision guide, what's the recommended default?

B. Kustomize's base-plus-overlay model fits exactly this shape — one shared base, small per-environment patches — without the chart-authoring and versioning overhead Helm exists for. A adds structure this app doesn't need; C throws away the shared base, so every future change is repeated three times by hand; D is the hand-editing mistake this lesson warns against, with no audit trail at all.

Production challenge

Objective

Diagnose drift between a Kustomize base/overlay and what's actually running in the cluster, without being told what changed — using only kubectl diff -k and the method above.

Scenario

A teammate says: "the prod overlay says 3 replicas, but I keep seeing 5 Pods, and nobody remembers changing the overlay."

Environment assumptions

A kind/minikube cluster with kubectl v1.14+ (kustomize support is built in). No existing Deployment named web in the current namespace. Build the drifted scenario yourself first, then diagnose it as if you didn't:

mkdir -p demo-kustomize/base demo-kustomize/overlays/prod

cat > demo-kustomize/base/deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
      - name: web
        image: nginx:1.29
EOF

cat > demo-kustomize/base/kustomization.yaml <<'EOF'
resources:
  - deployment.yaml
EOF

cat > demo-kustomize/overlays/prod/kustomization.yaml <<'EOF'
resources:
  - ../../base
EOF

kubectl apply -k demo-kustomize/overlays/prod

# Simulate the "nobody remembers" drift: someone hand-scaled it during an incident
kubectl scale deployment web --replicas=5

Commands

Diagnose it using only read/diff commands — no editing yet:

kubectl get deployment web
kubectl diff -k demo-kustomize/overlays/prod

Expected result

kubectl get deployment web shows 5/5 replicas. kubectl diff -k prints a diff on spec.replicas: live is 5, the overlay's rendered manifest says 3 — proof the live object has drifted from what's tracked in the kustomization, and by exactly how much.

Verification

Re-run kubectl apply -k demo-kustomize/overlays/prod and confirm kubectl get deployment web returns to 3/3. The diff you found is exactly what apply corrects — nothing more, nothing less.

Common failure

"Fixing" this by hand-scaling back to 3 (kubectl scale deployment web --replicas=3) instead of running kubectl apply -k. It happens to produce the same end state here, but it doesn't fix the actual problem — a base/overlay that reality no longer matches — and teaches nothing about why the drift happened in the first place.

Troubleshooting

If kubectl diff -k prints nothing, the drift was already reconciled by something else — a GitOps controller, a scheduled kubectl apply -k job — before you looked. Check kubectl get deployment web -o yaml for recent changes in metadata.managedFields, and ask whether anything automated re-applies this kustomization on a schedule.

Cleanup / rollback

kubectl delete -k demo-kustomize/overlays/prod --ignore-not-found
rm -rf demo-kustomize

Production lesson

kubectl diff -k is the single command that answers "did someone change this by hand?" without guessing — the Kustomize equivalent of comparing helm get manifest against live state. It belongs at the front of your troubleshooting workflow, before you touch anything, not as an afterthought once something's already broken.

Recap
  • Helm = package + template + track as a "release," with a revision history where install/upgrade/rollback each add 1 — rollback creates a new revision matching old content, it never rewinds the counter.
  • Kustomize = patch existing plain YAML, no templating; configMapGenerator/secretGenerator append a content-hash suffix so a config change forces a real rollout, solving Lesson 6's "env var frozen at start" problem.
  • kubectl apply -k/kubectl kustomize/kubectl diff -k are all built into kubectl since v1.14 — no separate install.
  • Whatever either tool creates is ordinary Kubernetes objects — troubleshoot the same way regardless of how they got created, using helm get manifest or kubectl diff -k to compare intended vs. live state.
  • Hand-editing a Helm- or Kustomize-managed live object is accepted instantly by the API server, but invisible to the tool's own state — the next legitimate upgrade/apply can silently revert it.
