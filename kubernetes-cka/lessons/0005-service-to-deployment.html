Kubernetes / CKA — Lesson 5 of 24

Service → Deployment

Why this matters

A Service in front of a Deployment "just working" through a rolling update looks automatic — you run one command to update the image, and users never notice a blip. That behavior isn't built into Deployments, and it isn't magic. It's the direct, mechanical result of two independent things lining up correctly: Pod labels matching a Service's selector, and each new Pod passing its readiness probe before it's added to that Service's traffic. Nothing in the Kubernetes API ties a Service to "the Deployment I created it for" — there is no such field. If you assume that link exists anyway, two real incidents stay invisible until they hit production: a Service can silently start routing to Pods from a completely unrelated Deployment that happens to share one label, and a Service can just as easily send live traffic to a half-started Pod if nobody bothered to define a readiness probe at all.

Mental model: a Service is a saved search, re-run continuously — not a fixed guest list. Picture a smart playlist labeled "workout" that auto-adds every song tagged workout=true, from any album, by any artist, forever, with zero regard for which app or person added the tag. A Service behaves the same way: it doesn't hold a list of "the Pods from my Deployment" — it re-evaluates spec.selector against every Pod's current labels, and any Pod that matches right now is in, and any Pod that stops matching (label changed, Pod deleted, Pod fails its readiness probe) is out, automatically. Test that against a case you haven't seen yet: if you create a second, totally unrelated Deployment tomorrow and one of its Pods happens to carry the exact label your Service selects on, the Service includes that Pod immediately. There's no field, no annotation, nothing that says "only Pods from Deployment X." That's exactly the failure mode this lesson's exercise reproduces.

Core concepts

Lesson 3 showed a Service matching a bare Pod's labels. Lesson 4 showed a Deployment's real Pod labels living inside spec.template.metadata.labels, not the Deployment's own metadata.labels or spec.selector.matchLabels. Put those two facts together and the mechanism is simple: a Service's spec.selector is compared against exactly one thing — the labels on whatever Pod objects currently exist in the namespace, wherever those Pods came from.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web        # <- a Service selector matches THIS, not anything above it
    spec:
      containers:
        - name: web
          image: nginx:1.29

Three separate label fields exist in this one manifest, and a Service only ever reads the third:

  • metadata.labels on the Deployment itself — cosmetic bookkeeping; a Service never reads this
  • spec.selector.matchLabels — how the Deployment finds its own Pods, via its ReplicaSet
  • spec.template.metadata.labels — the actual Pod labels, and the only one a Service selector can see

A Service is not a static list, and it doesn't need to be told when Pods change. Per the Kubernetes docs, "the controller for that Service continuously scans for Pods that match its selector, and then makes any necessary updates to the set of EndpointSlices for the Service." Every time a Pod is created, deleted, relabeled, or changes readiness state, that scan runs again — no caching, no manual refresh, and nothing anywhere that remembers which controller originally created a given Pod.

Readiness probes are the second half of the mechanism, and the part most people miss. A new Pod matching a Service's selector does not receive traffic the instant it starts Running — it has to pass its readiness probe first. The docs state the failure direction plainly: "If the readiness probe returns a failed state, the EndpointSlice controller removes the Pod's IP address from the EndpointSlices of all Services that match the Pod." The same mechanism runs in reverse on the way up — a Pod's IP is only added to a matching Service's EndpointSlices once its containers report Ready. And if you never define a readinessProbe at all, the kubelet just treats the container as an automatic success: the Pod is considered Ready — and gets traffic — the moment it's running, warmed up or not.

Put both mechanisms on the same timeline and this is what a rolling update actually looks like from the Service's point of view:

MomentOld ReplicaSet (v1)New ReplicaSet (v2)Service endpoints
Before rollout3 Pods, Readynone3× v1 IPs — 100% v1
Rollout starts (maxSurge)3 Pods, Ready1 Pod created, not yet Readystill 3× v1 IPs — the new Pod isn't in yet
New Pod passes readiness probe3 Pods, Ready1 Pod, Ready4 IPs — v1 and v2 both receiving traffic
Old Pod terminated (maxUnavailable)2 Pods, Ready1 Pod, Ready3 IPs — mix continues
Rollout complete0 Pods3 Pods, Ready3× v2 IPs — 100% v2

By default a Deployment's rolling update allows maxSurge: 25% and maxUnavailable: 25%, so old and new Pods genuinely both serve traffic for most of the rollout, not just for an instant — which version answers any single request during that window isn't something a Service selector controls at all.

Simple example: this is also why a Service can send traffic to a broken new version mid-rollout even when the deployer swears "only 1 replica out of 10 has updated so far." If that one Pod reports Ready — because its readiness probe only checks "is the process listening on the port," not "can it actually serve correct responses" — the Service sends it a real share of requests. A readiness probe that's too shallow is a bug that hides inside a rollout that otherwise looks perfectly healthy.

Production example

Production note: teams running canary or blue-green rollouts learn this the hard way exactly once, then adopt a rule permanently: every Deployment gets a shared label for "what this is" (app: checkout) and a separate, unique label for "which specific rollout this is" (track: stable or track: canary) — and every Service selector must include both. A payments team running checkout (12 replicas, track: stable) behind checkout-svc, then adding checkout-canary (2 replicas, track: canary) for a new payment-provider integration, keeps checkout-svc's selector as app: checkout, track: stable specifically so the canary Deployment's Pods — which also carry app: checkout by convention — never qualify. The unique track label isn't decoration; it's the only thing stopping the two Deployments from sharing a Service by accident. A separate, deliberately scoped Service (checkout-canary-svc, selector app: checkout, track: canary) is what the canary's own test traffic hits instead.

Hands-on exercise

Objective

Prove — don't take the lesson's word for it — that a Service will silently span two unrelated Deployments if their Pods share a label the Service selects on.

Scenario

You're standing in for two teams that both used app: web as a base label — team A's stable web Deployment, and team B's web-canary Deployment — behind a Service that was written before team B's Deployment existed.

Environment assumptions

Any cluster you can kubectl into (kind, minikube, or a real dev cluster), no existing resources named web, web-canary, or web-svc in the current namespace.

Commands

# 1. The "stable" Deployment — 3 replicas, its own valid, non-overlapping selector
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
      track: stable
  template:
    metadata:
      labels:
        app: web
        track: stable
    spec:
      containers:
        - name: web
          image: nginx:1.29
EOF

# 2. A Service written to select only the SHARED label — the mistake
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
EOF

# 3. A second, unrelated Deployment that also happens to carry app: web
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-canary
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
      track: canary
  template:
    metadata:
      labels:
        app: web
        track: canary
    spec:
      containers:
        - name: web
          image: httpd:2.4
EOF

# 4. Check who the Service actually targets
kubectl get endpoints web-svc
kubectl get pods -l app=web --show-labels

Expected result

kubectl get endpoints web-svc lists 5 IP addresses, not 3 — three from web and two from web-canary. --show-labels confirms all 5 Pods carry app=web, but only 3 also carry track=stable.

Verification

Run kubectl run debugger --image=curlimages/curl --restart=Never -it --rm -- sh -c 'for i in $(seq 1 10); do curl -s http://web-svc; echo ---; done' from inside the cluster. nginx and httpd ship visibly different default pages — across the 10 requests you'll see both show up, mixed together, which is the proof that one Service is quietly serving traffic for two different applications.

Common failure

Assuming the Service picked up web-canary's Pods because the canary Deployment did something wrong. It didn't — web-canary's own selector (app: web, track: canary) is perfectly valid and doesn't overlap with web's own selector (app: web, track: stable). The bug is entirely in web-svc's selector being narrower than it should be.

Troubleshooting

If get endpoints shows fewer than 5 IPs, check that both Deployments actually reached Running/Ready with kubectl get pods -l app=web -o wide — a slow image pull for httpd:2.4 is the most likely reason the canary Pods aren't in the list yet, not a selector problem.

Cleanup / rollback

kubectl delete deployment web web-canary
kubectl delete service web-svc

Production lesson

The fix is one field: change web-svc's selector to app: web, track: stable and re-apply, then re-run kubectl get endpoints web-svc — it drops back to exactly 3 IPs. The lesson isn't "remember to fix this Service" — it's that this bug is invisible in kubectl get deployments, kubectl get services, and even a casual kubectl describe service. The only place it's visible is kubectl get endpoints, which is why that command belongs in your troubleshooting muscle memory, not just your setup checklist.

Failure scenario

A realistic incident built on exactly the mechanism above — except this time nobody set up the bug on purpose.

  1. 09:14 The checkout team merges a Helm values change to deploy checkout-canary — a new payment-provider integration — at 2 replicas, meant to only receive traffic from an internal test tool.
  2. 09:16 The canary chart was copy-pasted from the stable chart months ago and was never updated to set a track label. Its Pods come up carrying only app: checkout — the same shared label the stable Pods carry.
  3. 09:17 checkout-svc — the production Service, selector app: checkout only, written before the track convention existed — picks up both canary Pods the moment they pass their readiness probes. No one touched checkout-svc; it just re-evaluated its selector, as it always does.
  4. 09:21 Support tickets start: a small percentage of checkout attempts fail against the new, untested payment provider. Error rate on the dashboard rises from 0.1% to 4% — consistent with roughly 2 bad Pods out of 50 total.
  5. 09:26 On-call runs kubectl get pods -l app=checkout -o wide and sees more Pods than the known stable replica count. kubectl get pods -l app=checkout --show-labels reveals two Pods with no track label at all.
  6. 09:29 Root cause confirmed: kubectl get endpoints checkout-svc lists both canary Pod IPs alongside the stable ones.
  7. 09:31 Immediate fix: scale checkout-canary to 0 replicas, stopping the bleeding without touching the production Service.
  8. 09:40 Permanent fix: add track: stable / track: canary labels to both Deployments' Pod templates, update checkout-svc's selector to require track: stable, and scale checkout-canary back up behind its own, separately scoped Service.
  9. 09:45 Verified: kubectl get endpoints checkout-svc shows exactly the stable replica count; error rate returns to 0.1%.

Troubleshooting workflow

The general method, applied specifically to "my Service is sending traffic to Pods I didn't expect":

  1. Confirm the symptom. Don't trust a hunch from error rates alone — run kubectl get endpoints <service> and count the IPs against the replica count you actually expect.
  2. Define scope. Is every request affected, or only some? A mixed-response symptom (some requests correct, some wrong) points at multiple backends behind one Service, not one broken Pod.
  3. Check recent changes. kubectl get deployments --sort-by=.metadata.creationTimestamp — was a new Deployment created recently in this namespace? New Deployments are the most common source of an unexpected label collision.
  4. Inspect the right state. kubectl describe service <service> for its exact selector, then kubectl get pods -l <that exact selector> --show-labels to see every Pod it matches and every label each one carries.
  5. Form a hypothesis. For example: "the Service selector is missing a label that would normally distinguish this Deployment's Pods from another one's."
  6. Test one variable. Compare the Service's selector field-by-field against the suspect Deployment's spec.template.metadata.labels — don't eyeball the YAML, diff the actual values (kubectl get svc <service> -o jsonpath='{.spec.selector}' against kubectl get deploy <deploy> -o jsonpath='{.spec.template.metadata.labels}').
  7. Apply the safest fix. Fix it at the Service — narrow spec.selector to include the missing distinguishing label. Don't "fix" it by relabeling the Pods you don't want matched: those Pods are owned by their own Deployment's ReplicaSet, and hand-editing their labels fights that controller instead of fixing the actual bug, which is in the Service.
  8. Verify recovery. Re-run kubectl get endpoints <service> and confirm the IP count now matches only the intended Deployment's replica count — not just that error rates went down, which could be coincidental.
  9. Document the root cause. "Service selector narrower than the intended Deployment's unique labels; a second Deployment's Pods qualified by accident" — record the exact selector and label values involved, not just "labels were wrong."
  10. Prevent recurrence. Adopt a standing convention: every Deployment gets a unique track/version label in addition to its shared app label, and every Service selector must include both.

Reliability note: a label collision like this is a pure availability/correctness risk, not a Kubernetes bug — the platform is doing exactly what its selector-matching model promises. The blast radius scales with how broad the shared label is: a Service selecting on one common label like app: web in a busy shared namespace can pick up Pods from any Deployment, ReplicaSet, StatefulSet, or even a bare debug Pod someone spun up, as long as the label matches. The more Deployments that share a namespace and a naming convention, the higher the odds two of them eventually collide on a label by accident — this is a namespace-hygiene problem that gets worse as a team or cluster grows, not a one-off typo you fix once and forget.

Security note: the security angle here is real but secondary to reliability. In a genuinely multi-tenant namespace (multiple teams or customers sharing one namespace, which is itself against best practice), a label collision doesn't just misroute HTTP traffic — NetworkPolicy objects also select Pods by label (Lesson 10), so the same kind of overlap can accidentally widen a policy's scope to cover Pods it was never meant to include, exposing one tenant's Pods to another's traffic. The mitigation is the same one namespace isolation and RBAC already push you toward: don't share namespaces across trust boundaries, and don't rely on labels alone as an access boundary within a shared one.

Common mistake: treating a Service as if it were "bound" to the Deployment you created it for. There is no such binding anywhere in the API — no owner reference, no name reference, nothing. A Service is a standing query against Pod labels, full stop. If you want it scoped to one Deployment, the selector has to say so explicitly, and stay unique to that Deployment forever, including every future Deployment anyone adds to the namespace.

Common mistake: confusing this with the separate, also-real, also-documented risk of two Deployments overlapping their own selector.matchLabels. Kubernetes' own docs warn: "Kubernetes doesn't stop you from overlapping, and if multiple controllers have overlapping selectors those controllers might conflict and behave unexpectedly" — but that's a Deployment/ReplicaSet-vs-Deployment/ReplicaSet fight over owning the same Pods. The scenario in this lesson is different, and arguably easier to cause by accident: the two Deployments in the exercise above have perfectly valid, non-overlapping selectors of their own. It's only the Service's selector that's too broad.

Decision guide

Labeling conventionUse whenAvoid whenTrade-off

Fully unique selector per Deployment, no shared label at allYou want the strongest possible isolation between adjacent but unrelated workloads in one namespaceYou actually want one Service to intentionally span multiple Deployments (gradual migration)Safest against accidents, but shifting traffic requires an explicit Service selector change — nothing blends automatically

Default recommendation: shared app label plus a unique track or version label, with every Service selector including both, from the very first Deployment — not added later once a second one shows up. Retrofitting this convention under incident pressure, as in the Failure scenario above, is strictly harder than starting with it.

Knowledge check

Q1. Does a Service care whether the Pods it selects came from a Deployment, a ReplicaSet, a StatefulSet, or were created bare?

No. A Service selector only matches Pod labels — there's no field anywhere in the Service spec that references who or what created a Pod.

Q2. During a rolling update, which Pods can a Service send traffic to?

Any Pod — old ReplicaSet or new — that currently matches the selector and reports Ready. Old and new Pods commonly serve traffic at the same time mid-rollout, not just for an instant.

Q3. A Service has selector: app: web. Deployment A's Pods carry app: web, track: stable. Deployment B's Pods carry app: web, track: canary. Which Pods receive traffic from the Service?

C. The Service's selector only requires app: web — extra labels like track don't exclude a Pod from matching. Both Deployments' Pods satisfy the selector, so both get traffic.

Q4. A new Pod is Running during a rollout but hasn't passed its readiness probe yet. What does the matching Service do with it?

C. The EndpointSlice controller only adds a Pod's IP once it reports Ready — a Running-but-not-Ready Pod gets zero traffic from the Service until then.

Certification mapping

Services & Networking (20%) of the CKA exam — this lesson is the connective tissue between that domain and Workloads & Scheduling (15%). Expect exam scenarios that hand you a Service and a Deployment and ask you to explain or fix why traffic isn't reaching the Pods you expect — the fix is almost always a label/selector mismatch, exactly like the exercise above.

Production challenge

Objective

Design and prove a safe canary labeling scheme from scratch — with less hand-holding than the exercise above.

Scenario

You're adding a canary rollout to an existing api Deployment (3 replicas, image: httpd:2.4) already served by a Service named api-svc. You need a second Deployment, api-canary (1 replica, image: nginx:1.29, so you can visibly tell them apart), that receives zero traffic from api-svc, plus a separate Service, api-canary-svc, that reaches only the canary Pod.

Environment assumptions

A kind/minikube cluster. No existing resources named api, api-svc, api-canary, or api-canary-svc.

Commands

Don't copy the exercise above verbatim — design your own label scheme first (shared app label plus a unique second label is the pattern this lesson recommends), then write:

  • Deployment api — 3 replicas, your chosen labels
  • Service api-svc — selector scoped so it matches only api's Pods
  • Deployment api-canary — 1 replica, sharing the base label but with a distinguishing value
  • Service api-canary-svc — selector scoped so it matches only api-canary's Pod

Expected result

kubectl get endpoints api-svc lists exactly 3 IPs, all from api. kubectl get endpoints api-canary-svc lists exactly 1 IP, from api-canary. Neither Service's endpoint list ever contains a Pod from the other Deployment.

Verification

Prove it, don't assume it: cross-check every IP in both endpoint lists against kubectl get pods -o wide --show-labels and confirm each IP belongs to the Deployment you intended. Then delete and re-create api-canary once — endpoints should update to the new Pod's IP automatically, with no manual Service edit.

Common failure

Making api-canary-svc's selector too loose (for example just the shared app label). It'll pass a casual glance because it does return traffic, but it'll also silently include api's stable Pods. The only way to catch this is checking the endpoint count, not just "did curl get a response."

Troubleshooting

If either Service's endpoint list is empty, compare its spec.selector against the target Deployment's spec.template.metadata.labels field-by-field — a single mismatched key or value (not just a missing one) silently produces zero matches, with no error from kubectl apply.

Cleanup / rollback

kubectl delete deployment api api-canary
kubectl delete service api-svc api-canary-svc

Production lesson

A canary setup isn't "safe" because the YAML looked right on a read-through — it's safe once you've read the actual kubectl get endpoints output for every Service involved and confirmed the IP-to-Pod mapping yourself. That's the same verification habit the Hands-on exercise built, applied here without a script telling you the exact labels to use.

Recap
  • A Service matches spec.selector against Pod labels only — it has no concept of Deployments, ReplicaSets, or ownership.
  • A Deployment's actual Pod labels live at spec.template.metadata.labels, not the Deployment's own metadata.labels or spec.selector.matchLabels.
  • A Pod only receives Service traffic once it reports Ready; a failed readiness probe removes it from every matching Service's endpoints, and a missing readiness probe means "Ready" the instant the container starts running.
  • Two Deployments with distinct, non-overlapping selectors of their own can still both feed the same Service by accident, if the Service's own selector is broader than either Deployment's.
  • Give every Deployment a shared app label plus a unique track/version label, and always select on both in every Service — the single cheapest guard against this failure mode.
