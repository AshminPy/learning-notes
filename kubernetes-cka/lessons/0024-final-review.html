Final Review — Cheat Sheet & Practical Assessment

This page is two distinct things — don't treat the first as a substitute for the second. Part 1 is a cheat sheet: no new material, no assessment, just the commands and traps from Lessons 1–23 in one place to skim. Part 2 is a timed, hands-on practical assessment covering all 5 CKA domains — reading Part 1 proves you can recall; finishing Part 2 proves you can actually do it, which is what the real exam tests.

Part 1 — kubectl command cheat sheet

Pods, labels & Deployments

  • kubectl get pods --show-labels — show labels on every Pod
  • kubectl get pods -l tier=frontend — filter Pods by label
  • kubectl label pod <name> <key>=<value> --overwrite — isolate a live Pod from its controller by relabeling it out of the selector, without deleting it
  • kubectl get deploy / kubectl get rs — see Deployments and the ReplicaSets they own
  • kubectl rollout status deployment/<name> — watch a rollout finish
  • kubectl rollout undo deployment/<name> — roll back to the previous ReplicaSet
  • kubectl rollout history deployment/<name> — list revisions

Services & networking

  • kubectl get endpoints <service> — confirm a Service actually found Pods (empty = selector mismatch or every backend failing readiness)
  • kubectl get ingressclass — which Ingress controller(s) exist in the cluster
  • kubectl get networkpolicy — list NetworkPolicies (existing ≠ enforced — CNI must implement it)

Config, storage & RBAC

  • kubectl exec <pod> -- env — confirm an env var from a ConfigMap/Secret landed
  • kubectl get storageclass — check what a PVC will dynamically provision against
  • kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<sa> — test RBAC permissions without triggering the real action

Workloads (Job/CronJob)

  • kubectl get jobs — completions vs. target
  • kubectl get cronjobs,jobs,pods — watch a CronJob spawn Jobs over time

Cluster & node troubleshooting

  • kubectl get nodes — cluster-wide node health, first look
  • kubectl describe node <name> — Conditions (Ready/MemoryPressure/DiskPressure/PIDPressure) + Events
  • kubectl get events --sort-by=.metadata.creationTimestamp -A — cheap, chronological, cluster-wide first look
  • systemctl status kubelet / journalctl -u kubelet -n 100 --no-pager — kubelet health, on the node itself
  • crictl ps -a — container state straight from the runtime, works even if the API server is down

Application & workload troubleshooting

  • kubectl describe pod <name> — always first; Events section explains scheduling/image/probe failures
  • kubectl logs <pod> --previous — the last crashed container's own output
  • kubectl exec -it <pod> -- sh — shell into a running container (needs a shell in the image)
  • kubectl debug <pod> -it --image=busybox --target=<container> — debug shell-less/distroless images

etcd, upgrades & certs

  • ETCDCTL_API=3 etcdctl --endpoints --cacert --cert --key snapshot save <file> — back up etcd
  • etcdutl --data-dir <new-dir> snapshot restore <file> — restore into a new directory, never in place
  • kubeadm upgrade plan / kubeadm upgrade apply v1.x.y / kubeadm upgrade node — upgrade control plane, then each node
  • kubectl drain <node> --ignore-daemonsets / kubectl uncordon <node> — safely take a node out and back in during upgrades
  • kubeadm certs check-expiration / kubeadm certs renew all — check and renew control-plane TLS certs

Helm, Kustomize & extension interfaces

  • helm install/upgrade/rollback/uninstall <release> <chart> — package install, tracked as a release
  • kubectl apply -k <dir> — Kustomize, built into kubectl, no install needed
  • crictl ps -a (CRI) / /etc/cni/net.d (CNI) / StorageClass provisioner (CSI) — the three plugin sockets

CRDs, operators & HA control plane

  • kubectl get crds — every custom kind installed; an Operator (a normal Pod) is what actually acts on them
  • kubeadm init --control-plane-endpoint <LB> --upload-certs — HA-ready first control-plane node
  • kubectl get lease -n kube-system kube-scheduler — who's the current elected leader

CoreDNS, Gateway API & autoscaling

  • kubectl -n kube-system get pods -l k8s-app=kube-dns — is the cluster's DNS itself healthy
  • kubectl get gatewayclass,gateway,httproute -A — Gateway API objects, if installed
  • kubectl get hpa — TARGETS showing <unknown> means metrics-server is missing, not an HPA bug
  • kubectl top nodes / kubectl top pods --containers — needs metrics-server, not installed by default on kubeadm

Interview quick-fire

  • Q: How does a Service find its Pods? A: It matches spec.selector against Pod labels, continuously, live — never by name. kubectl get endpoints <svc> proves it actually found any.
  • Q: What restarts a crashed container? A: A failed liveness probe, via the kubelet's restartPolicy — a failed readiness probe never restarts anything, it only pulls the Pod out of Service routing.
  • Q: Is a Kubernetes Secret encrypted? A: No — base64-encoded only. Plain text to anyone with etcd/API access unless EncryptionConfiguration is explicitly turned on.
  • Q: Does creating a NetworkPolicy automatically restrict traffic? A: No — it's a no-op unless the cluster's CNI implements NetworkPolicy enforcement.
  • Q: You relabel a running Pod out of its Deployment's selector — what happens? A: The Pod keeps running untouched; the ReplicaSet creates a replacement to restore its desired count. Real isolation technique, real accidental-outage cause.

Top 7 exam traps

  1. An Ingress or NetworkPolicy object does nothing by itself — it needs a controller (Ingress) or a CNI that implements it (NetworkPolicy), or it's silently a no-op. See Lesson 8 and Lesson 10.
  2. A fresh cluster is default-allow for Pod-to-Pod traffic — the opposite of a firewall's default-deny. See Lesson 10.
  3. A Deployment's spec.selector.matchLabels must exactly match spec.template.metadata.labels, or the Deployment is invalid. See Lesson 2 and Lesson 4.
  4. A Kubernetes Secret is base64-encoded, not encrypted — anyone with etcd/API access reads it as plain text unless EncryptionConfiguration is explicitly turned on. See Lesson 6.
  5. A failed readiness probe never restarts a container — it only pulls the Pod out of Service routing. Only a failed liveness probe restarts it. See Lesson 11.
  6. A PV's reclaimPolicy decides whether data survives its PVC's deletion — Delete (default) destroys it, Retain keeps it but needs manual cleanup. See Lesson 7.
  7. An HPA showing <unknown> in TARGETS, or kubectl top failing outright, both trace back to the same cause — metrics-server missing or unhealthy, not a bug in either feature. See Lesson 22 and Lesson 23.

Part 2 — Practical final assessment (timed)

One task per domain, in real exam style: a goal, not a recipe. Time yourself — the targets below are a competent-candidate pace, not a hard limit. Attempt each fully before revealing its hidden answer; a cheat sheet you can read is not the same skill as a task you can finish under time pressure.

Task 1 — Troubleshooting (30% domain) · target 7 min
A web Deployment (3 replicas, label app=web) is fronted by a Service named web-svc with selector: app=web. Traffic to it fails. Find and fix the root cause.

Setup:

kubectl create deployment web --image=nginx:1.29 --replicas=3
kubectl expose deployment web --name=web-svc --port=80
kubectl patch service web-svc -p '{"spec":{"selector":{"app":"webapp"}}}'

Success criteria: web-svc has 3 endpoints again.
Verification command: kubectl get endpoints web-svc

The kubectl patch above quietly changed the Service's selector to app=webapp, which matches nothing. Fix: kubectl patch service web-svc -p '{"spec":{"selector":{"app":"web"}}}', then confirm with the verification command. Doc: kubernetes.io/docs/concepts/services-networking/service.

Task 2 — Cluster Architecture, Installation & Configuration (25% domain) · target 10 min
Take a snapshot of etcd and prove it's a valid, restorable backup — without restoring it (never test-restore onto a live cluster's data directory).

Success criteria: a snapshot file exists and etcdutl confirms it's structurally valid.
Verification command: etcdutl snapshot status /tmp/etcd-backup.db -w table

ETCDCTL_API=3 etcdctl snapshot save /tmp/etcd-backup.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
etcdutl snapshot status /tmp/etcd-backup.db -w table
Exact cert paths vary by install method — kubeadm's defaults are shown. The status command reads the file directly and doesn't touch the live cluster, which is why it's the safe way to prove a backup is good. Doc: kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd.

Task 3 — Services & Networking (20% domain) · target 10 min
Restrict a backend Deployment (label app=backend) so only Pods labeled role=frontend can reach it on port 80 — everything else should be refused.

Success criteria: a Pod labeled role=frontend can curl backend on port 80; a Pod without that label cannot.
Verification command: run curl from both a labeled and an unlabeled test Pod and compare the result.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-allow-frontend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          role: frontend
    ports:
    - port: 80
This only takes effect if the cluster's CNI implements NetworkPolicy — Lesson 10's biggest trap. If both test Pods can still reach backend after applying this, check the CNI first before assuming the YAML is wrong. Doc: kubernetes.io/docs/concepts/services-networking/network-policies.

Task 4 — Workloads & Scheduling (15% domain) · target 6 min
Update the web Deployment's image to nginx:1.29, confirm the rollout completed, then roll it back to the previous image.

Success criteria: after rollback, the Deployment's Pods are running the original image again.
Verification command: kubectl get deployment web -o jsonpath='{.spec.template.spec.containers[0].image}'

kubectl set image deployment/web nginx=nginx:1.29
kubectl rollout status deployment/web
kubectl rollout undo deployment/web
kubectl rollout status deployment/web
rollout undo works because every image change created a new ReplicaSet revision — kubectl rollout history deployment/web lists them. Doc: kubernetes.io/docs/concepts/workloads/controllers/deployment.

Task 5 — Storage (10% domain) · target 8 min
Create a PVC, write a file to it from one Pod, delete that Pod, mount the same PVC from a second Pod, and prove the file survived.

Success criteria: the second Pod can read the exact file the first Pod wrote.
Verification command: kubectl exec pod-b -- cat /data/proof.txt

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: proof-pvc }
spec:
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 1Gi } }
EOF
kubectl run pod-a --image=busybox --restart=Never --overrides='{"spec":{"containers":[{"name":"pod-a","image":"busybox","command":["sh","-c","echo hello > /data/proof.txt && sleep 5"],"volumeMounts":[{"name":"v","mountPath":"/data"}]}],"volumes":[{"name":"v","persistentVolumeClaim":{"claimName":"proof-pvc"}}]}}'
sleep 6 && kubectl delete pod pod-a
kubectl run pod-b --image=busybox --restart=Never --overrides='{"spec":{"containers":[{"name":"pod-b","image":"busybox","command":["sleep","3600"],"volumeMounts":[{"name":"v","mountPath":"/data"}]}],"volumes":[{"name":"v","persistentVolumeClaim":{"claimName":"proof-pvc"}}]}}'
kubectl exec pod-b -- cat /data/proof.txt
The point being proven: a PVC's data outlives the specific Pod that wrote it — data is bound to the volume, not the Pod. Requires a StorageClass capable of dynamic provisioning (default on most managed clusters and kind/minikube). Doc: kubernetes.io/docs/concepts/storage/persistent-volumes.
