Final Review — Cheat Sheet

This is a reference page, not a new lesson — no new material, no quiz. It pulls together the commands, traps, and the one repeatable troubleshooting method from Lessons 1–23 into a single page to skim before the exam.

Universal troubleshooting method

Every lesson in this course applies the same 10-step method to its own topic. Memorize the method once, not 23 separate command lists:

  1. Confirm the symptom. Run the real command yourself — don't diagnose from a dashboard or from memory of what it looked like earlier.
  2. Define scope. One object, one node, one namespace, or cluster-wide? Scope tells you which layer to suspect first.
  3. Check recent changes. kubectl get events --sort-by=.lastTimestamp, plus deploy/CI history and shell history — label/patch commands don't show up as "deploys."
  4. Inspect the right state. kubectl describe/kubectl get -o yaml on the object closest to the symptom, not the whole cluster at once.
  5. Form a hypothesis. One sentence, specific enough to be provably wrong.
  6. Test one variable. Change or inspect exactly one thing before concluding anything — never two at once.
  7. Apply the safest fix. The smallest change that addresses the confirmed cause, not the first thing that might help.
  8. Verify recovery. Re-run the original failing check, not just a related one that looks better.
  9. Document the root cause. Name the exact field/value that was wrong — "misconfigured" isn't a root cause.
  10. Prevent recurrence. A review check, an alert, or a guardrail — something that outlives this one incident.

kubectl command cheat sheet

Pods, labels & Deployments

  • kubectl get pods --show-labels — show labels on every Pod
  • kubectl get pods -l tier=frontend / -l 'env in (prod,staging)' — equality- and set-based label filtering
  • kubectl label pod <name> <key>=<value> --overwrite — isolate a live Pod from its controller by relabeling it out of the selector's match, without deleting it
  • kubectl get deploy / kubectl get rs — see Deployments and the ReplicaSets they own
  • kubectl rollout status deployment/<name> — watch a rollout finish
  • kubectl rollout undo deployment/<name> — roll back to the previous ReplicaSet
  • kubectl rollout history deployment/<name> — list revisions

Services & networking

  • kubectl get endpoints <service> — confirm a Service actually found Pods (empty = selector mismatch or every backend failing readiness)
  • kubectl get ingressclass — which Ingress controller(s) exist in the cluster
  • kubectl get networkpolicy — list NetworkPolicies (existing ≠ enforced — CNI must implement it)

Config, storage & RBAC

  • kubectl exec <pod> -- env — confirm an env var from a ConfigMap/Secret landed
  • kubectl get storageclass — check what a PVC will dynamically provision against
  • kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<sa> — test RBAC permissions without triggering the real action

Workloads (Job/CronJob)

  • kubectl get jobs — completions vs. target
  • kubectl get cronjobs,jobs,pods — watch a CronJob spawn Jobs over time

Cluster & node troubleshooting

  • kubectl get nodes — cluster-wide node health, first look
  • kubectl describe node <name> — Conditions (Ready/MemoryPressure/DiskPressure/PIDPressure) + Events
  • kubectl get events --sort-by=.metadata.creationTimestamp -A — cheap, chronological, cluster-wide first look
  • systemctl status kubelet / journalctl -u kubelet -n 100 --no-pager — kubelet health, on the node itself
  • crictl ps -a — container state straight from the runtime, works even if the API server is down

Application & workload troubleshooting

  • kubectl describe pod <name> — always first; Events section explains scheduling/image/probe failures
  • kubectl logs <pod> --previous — the last crashed container's own output
  • kubectl exec -it <pod> -- sh — shell into a running container (needs a shell in the image)
  • kubectl debug <pod> -it --image=busybox --target=<container> — debug shell-less/distroless images

etcd, upgrades & certs

  • ETCDCTL_API=3 etcdctl --endpoints --cacert --cert --key snapshot save <file> — back up etcd
  • etcdutl --data-dir <new-dir> snapshot restore <file> — restore into a new directory, never in place
  • kubeadm upgrade plan / kubeadm upgrade apply v1.x.y / kubeadm upgrade node — upgrade control plane, then each node
  • kubectl drain <node> --ignore-daemonsets / kubectl uncordon <node> — safely take a node out and back in during upgrades
  • kubeadm certs check-expiration / kubeadm certs renew all — check and renew control-plane TLS certs

Helm, Kustomize & extension interfaces

  • helm install/upgrade/rollback/uninstall <release> <chart> — package install, tracked as a release
  • kubectl apply -k <dir> — Kustomize, built into kubectl, no install needed
  • crictl ps -a (CRI) / /etc/cni/net.d (CNI) / StorageClass provisioner (CSI) — the three plugin sockets

CRDs, operators & HA control plane

  • kubectl get crds — every custom kind installed; an Operator (a normal Pod) is what actually acts on them
  • kubeadm init --control-plane-endpoint <LB> --upload-certs — HA-ready first control-plane node
  • kubectl get lease -n kube-system kube-scheduler — who's the current elected leader

CoreDNS, Gateway API & autoscaling

  • kubectl -n kube-system get pods -l k8s-app=kube-dns — is the cluster's DNS itself healthy
  • kubectl get gatewayclass,gateway,httproute -A — Gateway API objects, if installed
  • kubectl get hpa — TARGETS showing <unknown> means metrics-server is missing, not an HPA bug
  • kubectl top nodes / kubectl top pods --containers — needs metrics-server, not installed by default on kubeadm

Top 9 exam traps

  1. An Ingress or NetworkPolicy object does nothing by itself — it needs a controller (Ingress) or a CNI that implements it (NetworkPolicy), or it's silently a no-op. See Lesson 8 and Lesson 10.
  2. A fresh cluster is default-allow for Pod-to-Pod traffic — the opposite of a firewall's default-deny. See Lesson 10.
  3. A Deployment's spec.selector.matchLabels must exactly match spec.template.metadata.labels, or the Deployment is invalid — and the selector itself is immutable after creation. See Lesson 2 and Lesson 4.
  4. Relabeling a running Pod so it no longer matches its controller's selector doesn't delete or restart it — the Pod keeps running, orphaned, while the controller creates a replacement to restore its desired count. Real technique for isolating a Pod on purpose; real accidental-outage cause when done by mistake (e.g. a too-broad bulk kubectl label). See Lesson 2.
  5. A Kubernetes Secret is base64-encoded, not encrypted — anyone with etcd/API access reads it as plain text unless EncryptionConfiguration is explicitly turned on. See Lesson 6.
  6. A failed readiness probe never restarts a container — it only pulls the Pod out of Service routing. Only a failed liveness probe restarts it. See Lesson 11.
  7. A PV's reclaimPolicy decides whether data survives its PVC's deletion — Delete (default) destroys it, Retain keeps it but needs manual cleanup. See Lesson 7.
  8. An HPA showing <unknown> in TARGETS, or kubectl top failing outright, both trace back to the same cause — metrics-server missing or unhealthy, not a bug in either feature. See Lesson 22 and Lesson 23.
  9. RBAC permission to patch/update a Pod's labels is effectively permission to change which NetworkPolicy selectors apply to it — without needing any permission on the NetworkPolicy object itself. See Lesson 2 and Lesson 9.

Recap
  • Troubleshooting is worth more than any other domain — practice the 10-step method above until it's automatic, not just the command ladders.
  • Most exam traps are "it applied with no error but does nothing" — controller/CNI missing, a label mismatch, or a Pod quietly orphaned from its selector.
  • When stuck, search kubernetes.io/docs directly — that's the one tool you get in the real exam.
