Deployment

Lesson 1 proved a bare Pod has no memory — delete it and nothing brings it back. That's fine for a debug session, unacceptable for a real service: a Node failure would mean permanently lost capacity. A Deployment is the controller layer Lesson 1 predicted would exist: it watches a Pod template and keeps the right number of copies running, always.

Mental model: a Deployment is a staffing agency with a standing order — "always keep 3 people on this shift." If one quits, the agency notices within seconds and sends a replacement, without anyone asking. You manage the standing order, never the individual worker. That predicts what happens when you edit the order (change the image): the agency phases in new workers and phases out old ones — a rolling update, not a mass firing.

What's inside a Deployment manifest

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.29
  • spec.replicas — how many Pod copies should exist
  • spec.selector.matchLabels — how the Deployment finds "which Pods are mine" (Lesson 2's mechanism again)
  • spec.template — a full Pod spec, embedded — this is the Lesson 1 Pod manifest, nested

Gotcha: spec.selector.matchLabels must exactly match spec.template.metadata.labels, or the object is rejected outright — and normally the selector is immutable after creation.

Why it's built this way: a Deployment never touches Pods directly — it creates and owns a ReplicaSet, which creates and watches the actual Pods. That extra layer is what makes rolling updates safe: updating the image creates a new ReplicaSet, scaled up gradually, while the old one scales down — if the new version is broken, the old ReplicaSet (and its Pods) are still right there to roll back to.

Q1. What two fields must match for a Deployment to be valid?

Common mistake: writing spec.selector.matchLabels and spec.template.metadata.labels with a small mismatch (extra key, different casing) — rejected outright as invalid, unlike a Service's silent empty match.

A controlled failure

See the rolling update / rollback mechanism the mental model predicted:

kubectl set image deployment/web web=nginx:1.30
kubectl rollout status deployment/web

Predict first: if nginx:1.30 doesn't exist (a typo), what happens to the rollout? Then try it with a deliberately bad tag, e.g. nginx:99-does-not-exist. Observe: kubectl rollout status hangs — new Pods sit in ImagePullBackOff, but your 3 original Pods are untouched and still serving traffic; a Deployment never kills old capacity before new capacity is ready. Fix it:

kubectl rollout undo deployment/web
kubectl rollout status deployment/web

Production best practices

Production note: real Deployments almost always set explicit resource requests/limits (Lesson 11) and a rolling-update strategy (maxUnavailable/maxSurge) rather than relying on defaults — the defaults are reasonable for a demo, not for a service where "briefly zero capacity" is an incident.

Exam & interview notes

Core to Workloads & Scheduling (15%), and a frequent live-troubleshooting target under Troubleshooting (30%).

Interview Q: "You roll out a bad image. What happens to traffic while you fix it?" A: Nothing, if it's caught before the rollout completes — a Deployment only replaces old Pods with new ones as new ones become Ready, so a broken new image just stalls the rollout, it doesn't take down the old, working Pods.

Recap
  • A Deployment = Pod template + desired replica count + a selector (Lesson 2's mechanism) that finds its own Pods.
  • It never touches Pods directly — it owns a ReplicaSet, which owns the Pods.
  • A rolling update creates a new ReplicaSet and scales it up while scaling the old one down — old capacity survives until new capacity is Ready.
