Deployment

Why this matters

A Deployment is the controller you'll use for nearly every stateless workload you ever run on Kubernetes — and it's also where a huge share of real rollout incidents start, because the entire mechanism hides behind one innocent-looking command: kubectl apply. Misunderstand the Deployment → ReplicaSet → Pod chain, and a routine image bump turns into an outage: you assume "change the image, it just works," ship a broken build, and by the time anyone notices, the healthy old Pods are already gone because nobody understood how fast the rollout would replace them. The other classic trap is trying to rename or re-label an app mid-migration — spec.selector is immutable the instant a Deployment is created, so a perfectly reasonable-looking kubectl apply with an updated selector doesn't quietly update anything, it gets flatly rejected by the API, often during a maintenance window with people watching. This lesson builds the mental model that prevents both.

Mental model: a Deployment is a policy document, not a hands-on manager. It states one thing — "I want N Pods matching this exact template" — and hands that policy entirely to a ReplicaSet, which is the object that actually creates and deletes Pods to match the count. The Deployment itself never touches a Pod directly: not to create it, not to fix it, and not to notice if you changed one by hand. That predicts something that surprises almost everyone the first time: kubectl edit pod on a Pod owned by a Deployment can succeed, and the change can even work — until that specific Pod is ever replaced (a crash, a node drain, a future rollout). At that point the ReplicaSet builds the replacement strictly from the template stored on the ReplicaSet object, not from your edit, and your fix silently disappears — often days later, when nobody remembers making it.

What's inside a Deployment manifest

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-nginx
  template:
    metadata:
      labels:
        app: my-nginx
    spec:
      containers:
        - name: nginx
          image: nginx

Three parts do the real work:

  • spec.replicas — how many Pod copies should exist
  • spec.selector.matchLabels — how the Deployment (and its ReplicaSet) finds "which Pods are mine"
  • spec.template — a full Pod spec, embedded (this is the same Pod manifest shape from Lesson 1)

spec.selector must match spec.template.metadata.labels exactly, or the Deployment is rejected by the API at creation time — not silently accepted and left broken. Kubernetes' own documentation is explicit about this: .spec.selector must match .spec.template.metadata.labels, or it will be rejected by the API.

The chain: Deployment → ReplicaSet → Pod

A Deployment doesn't create Pods. It creates and manages a ReplicaSet, and the ReplicaSet is the object that actually creates, watches, and deletes Pods to keep the count right. The Deployment controller tags every ReplicaSet it creates (or adopts) with a pod-template-hash label, generated from the Pod template's content — this is how the Deployment tells its own ReplicaSets apart from each other and makes sure a Deployment's child ReplicaSets never overlap.

This chain is also why not every change to a Deployment does the same thing. A rollout — a brand-new ReplicaSet, scaled up while the old one scales down — is triggered if and only if spec.template changes: a new image, a changed env var, a different label on the Pod template. Changing spec.replicas alone is just scaling; it resizes the existing ReplicaSet and never creates a new one. Confusing these two is a common source of "why didn't my rollout do anything" confusion — because nothing about the Pod template changed, nothing should have.

Rolling update mechanics

The default spec.strategy.type is RollingUpdate (you don't have to specify it). Two fields control exactly how aggressive that rolling update is, and both default to 25%:

  • maxUnavailable — the maximum number of Pods that can be unavailable during the update. If given as a percentage, the absolute number is calculated by rounding down.
  • maxSurge — the maximum number of Pods that can be created over the desired count. If given as a percentage, the absolute number is calculated by rounding up.

Neither can be zero if the other is also zero — Kubernetes refuses a strategy that could freeze the rollout entirely. The two numbers bound the rollout from opposite directions: maxUnavailable guarantees a floor on how much capacity you keep serving traffic; maxSurge caps how much extra capacity (and cluster resource) the rollout is allowed to consume while it's in flight. The old and new ReplicaSets scale in tandem inside those two bounds — the controller keeps nudging the new ReplicaSet up and the old one down, one small step at a time, never letting available Pods drop below the maxUnavailable floor or total Pods rise above the maxSurge ceiling.

Setting (defaults, 25%)RoundingWorked example — 10 desired replicas
maxUnavailableRounds down25% of 10 = 2.5 → 2 unavailable allowed, so at least 8 Pods stay available at all times
maxSurgeRounds up25% of 10 = 2.5 → 3 extra allowed, so at most 13 Pods (old + new) exist at once

A Deployment is only considered a complete rollout once every replica is updated to the latest version, every replica is available, and no old replicas are still running — that third condition is why kubectl get rs keeps showing the old ReplicaSet at 0/0/0 for a while: it isn't gone, it's parked at zero, retained (by default, the last 10 revisions, via spec.revisionHistoryLimit) specifically so a rollback has something to roll back to.

The alternative strategy, Recreate, is blunt by comparison: all existing Pods are killed before any new ones are created. No mixed-version window, no surge — but a real downtime gap between the last old Pod terminating and the first new Pod becoming ready.

Production example

Production note: spec.selector is immutable after a Deployment is created (in apps/v1) — this is the single most common "gotcha" in real Deployment renames or migrations. A team decides to rename a service from api-legacy to api-checkout as part of a cleanup, edits the selector's app label to match the new name, and runs kubectl apply -f deployment.yaml expecting a routine update. It gets flatly rejected instead — not because the new selector wouldn't match the template (they updated both), but because the API refuses to change spec.selector on an existing Deployment at all, full stop. The real migration path is to create a brand-new Deployment object with the new name and selector, let it run side-by-side with the old one as two independent ReplicaSet trees, point the Service's selector at the new labels once the new Deployment is healthy, then delete the old Deployment. You don't rename a Deployment in place — you migrate traffic between two of them.

Hands-on exercise

Objective

Prove to yourself that a rolling update replaces Pods by standing up a brand-new ReplicaSet, not by editing existing Pods — and watch the maxSurge/maxUnavailable defaults bound the rollout in real time.

Scenario

You maintain my-nginx at 3 replicas and need to ship nginx:1.27 with no downtime.

Environment assumptions

Any cluster you can kubectl into (kind, minikube, or a real dev cluster), no existing Deployment named my-nginx in the current namespace.

Commands

kubectl create deployment my-nginx --image=nginx:1.25 --replicas=3
kubectl rollout status deployment/my-nginx
kubectl get rs -l app=my-nginx

kubectl set image deployment/my-nginx nginx=nginx:1.27
kubectl rollout status deployment/my-nginx
kubectl get rs -l app=my-nginx
kubectl rollout history deployment/my-nginx

Expected result

The first rollout status reports deployment "my-nginx" successfully rolled out with one ReplicaSet at 3/3/3. After set image, get rs briefly shows two ReplicaSets — the old one counting down, the new one counting up — before settling on the new one at 3/3/3 and the old one at 0/0/0. The second rollout status also reports success.

Verification

kubectl get pods -l app=my-nginx -o jsonpath='{.items[*].spec.containers[0].image}' should print nginx:1.27 three times — confirming every live Pod came from the new ReplicaSet, not a patched old one.

Common failure

Mistaking the old ReplicaSet still showing up in kubectl get rs (at 0/0/0) for a leftover bug. It isn't — it's retained on purpose, up to spec.revisionHistoryLimit (default 10), exactly so kubectl rollout undo has something to roll back to.

Troubleshooting

If the second rollout status hangs instead of completing, run kubectl get pods -l app=my-nginx — if the new Pods show ImagePullBackOff, you mistyped the tag. Fix it with another kubectl set image pointing at a real tag; you don't need rollout undo for a same-generation typo, the rollout self-corrects toward the new template.

Cleanup / rollback

kubectl delete deployment my-nginx --ignore-not-found

Production lesson

The rolling update only advances as fast as new Pods become ready. If you never define a readiness probe, Kubernetes treats a Pod as ready the moment its container starts — which can mean live traffic reaches a Pod before your app has actually finished initializing. A future lesson covers probes; file this away as the reason they matter here.

Failure scenario

A realistic incident: a bad image reaches production, and on-call has to decide fast whether to debug forward or roll back.

  1. 14:02 PagerDuty fires: checkout-api error rate over 5%. On-call runs kubectl get pods -l app=checkout-api — 2 of 5 Pods are in CrashLoopBackOff, restart count climbing.
  2. 14:03 kubectl rollout status deployment/checkout-api reports Waiting for deployment "checkout-api" rollout to finish: 2 out of 5 new replicas have been updated... — it isn't progressing.
  3. 14:05 kubectl logs <crashing-pod> --previous shows the app panicking on startup: FATAL: environment variable DB_DSN is not set. The new image expects a config key nobody wired into the Deployment's env.
  4. 14:07 kubectl rollout history deployment/checkout-api confirms this is revision 14 — the image bump that shipped 10 minutes ago. Nothing else changed.
  5. 14:09 Decision: this needs a reviewed ConfigMap change, not a live hotfix. On-call runs kubectl rollout undo deployment/checkout-api rather than debugging forward under pressure.
  6. 14:10 kubectl rollout status deployment/checkout-api shows the old ReplicaSet scaling back up and the broken one scaling to zero.
  7. 14:12 Verified: all 5 Pods Running on the previous image; error rate back to baseline within 2 minutes of the undo.
  8. 14:20 Postmortem note logged: root cause was a missing env var in the new image's rollout, caught by unit tests but never exercised against the real ConfigMap. Action item: add a staging rollout gate before prod.

Troubleshooting workflow

The general method, applied to "my Deployment's rollout is stuck or degraded":

  1. Confirm the symptom. Run kubectl rollout status deployment/<name> yourself — is it genuinely stuck ("Waiting for deployment... to finish"), or did it already report success and the real problem is somewhere else?
  2. Define scope. Is only this Deployment degraded, or is every rollout in the namespace failing? A cluster-wide resource or quota problem looks very different from one bad image.
  3. Check recent changes. kubectl rollout history deployment/<name> plus your CI/CD log — what actually changed in this revision: image tag, env vars, resource requests, probe config?
  4. Inspect the right state. kubectl get rs -l <selector> for desired/current/ready per ReplicaSet; kubectl get pods -l <selector> for individual status; kubectl describe pod <new-pod> for its Events section; kubectl logs <pod> --previous if it has restarted.
  5. Form a hypothesis. For example: "the new image crashes on start because of a missing env var" versus "the new Pods are Pending because the surge Pods don't fit in the namespace's resource quota."
  6. Test one variable. The Events line in describe pod tells you which: CrashLoopBackOff plus a non-zero exit code points at the app itself; Pending plus FailedScheduling points at capacity or quota; ImagePullBackOff points at the image reference.
  7. Apply the safest fix. If the new revision is broken, kubectl rollout undo deployment/<name> is fast, safe, and reversible. Only forward-fix in place if the cause is trivial and already verified — don't debug live while users are affected.
  8. Verify recovery. kubectl rollout status reports success, kubectl get rs shows the healthy ReplicaSet back at full desired/ready count, and your real error-rate or latency dashboard — not just kubectl — confirms it.
  9. Document the root cause. Record the exact trigger ("revision 14 shipped without the DB_DSN env var"), referencing the revision number from rollout history, not a vague "bad deploy."
  10. Prevent recurrence. Add the missing config to a pre-deploy validation step, or gate production rollouts behind a canary/staging Deployment that would have caught this before it reached live replicas.

Reliability note: maxSurge and maxUnavailable are a real capacity trade-off, not just rollout-speed knobs. Push maxUnavailable up (say, 50% or 100%) and a rollout finishes faster, but you accept a bigger dip in serving capacity while it runs — tolerable for a batch worker, risky for a payment API at peak traffic. Push maxSurge up instead and the rollout keeps full capacity throughout, but temporarily doubles (or more) the CPU/memory actually requested from the cluster — if your namespace's ResourceQuota or the cluster's free capacity can't absorb that surge, the new Pods just sit Pending instead of rolling out at all. The 25%/25% default is a reasonable balance for most services; treat any change to these values as a capacity-planning decision, not a cosmetic one.

Security note: a Deployment's own attack surface is thin — the real exposure lives in spec.template (image, ServiceAccount, securityContext), already covered in Lesson 1. What's specific to Deployments: RBAC write access to deployments (update/patch) is functionally equivalent to code-execution capability in the cluster, because editing spec.template.spec.containers[].image or command lets you run any image you want, with whatever privileges that Pod's ServiceAccount and securityContext already grant. If you wouldn't hand someone kubectl exec into your production Pods, don't hand them edit access to the Deployment either — it reaches the same place, one kubectl apply later.

Common mistake: running kubectl edit pod (or patching a single Pod's image) on a Pod owned by a Deployment, expecting the fix to persist. It can even appear to work — a Pod's container image is one of the few fields you can edit on a live Pod — but the ReplicaSet's stored template was never touched. The next time that specific Pod is replaced for any reason, the replacement comes from the ReplicaSet's original template, and the fix is gone with no error or warning.

Common mistake: letting spec.selector.matchLabels and spec.template.metadata.labels drift while hand-editing YAML — even one extra label on either side is a mismatch. The API rejects the Deployment outright rather than silently misbehaving, which is the right failure mode, but it's confusing the first time you hit it because the error surfaces at apply time, with no earlier warning.

Common mistake: assuming you can rename an app by editing spec.selector on an existing Deployment. You can't — spec.selector is immutable after creation, full stop, and the apply is rejected outright. Teams still discover this mid-migration instead of planning for it up front (see the Production note above).

Decision guide

StrategyUse whenAvoid whenTrade-off
RollingUpdate (default)Stateless app where old and new versions can safely coexist (two versions of a REST API behind the same Service)Old and new versions must never coexist (breaking DB schema change, a singleton holding an exclusive lock or port)Rollout takes longer, briefly mixes versions, surge Pods add temporary resource cost
RecreateA hard version incompatibility makes mixed-version traffic unsafeAnything user-facing where downtime is unacceptableFull downtime window between the last old Pod terminating and the first new Pod becoming ready

Default recommendation: stay on RollingUpdate at its 25%/25% defaults unless you have a specific, named reason — usually a breaking schema or contract change — to accept a downtime window with Recreate.

Knowledge check

Q1. What two fields must match exactly for a Deployment manifest to be accepted by the API?

spec.selector.matchLabels must match spec.template.metadata.labels. A mismatch is rejected by the API at creation time.

Q2. A Deployment has 3 replicas and default RollingUpdate settings. What's the maximum number of Pods that can exist at once mid-rollout?

B. maxSurge defaults to 25%, rounded up: 25% of 3 is 0.75, which rounds up to 1 extra Pod — so 3 desired + 1 surge = 4 at most.

Q3. You change only spec.replicas on a running Deployment, from 3 to 5. What happens?

B. A rollout (new ReplicaSet) is triggered only when spec.template changes. Scaling spec.replicas alone just resizes the current ReplicaSet.

Production challenge

Objective

Diagnose and safely recover a genuinely broken rollout using only kubectl rollout/get/describe — form a hypothesis before you fix anything.

Scenario

A teammate updated checkout-api's image right before standup and pinged you that "something looks off." You didn't see the change go in.

Environment assumptions

A kind/minikube cluster. Build the broken state yourself first — this simulates the teammate's change:

kubectl create deployment checkout-api --image=nginx:1.25 --replicas=4
kubectl rollout status deployment/checkout-api
kubectl set image deployment/checkout-api nginx=nginx:1.25-does-not-exist

Commands

Now diagnose it the way you would in the incident above, then fix it:

# Diagnose
kubectl rollout status deployment/checkout-api --timeout=20s
kubectl get rs -l app=checkout-api
kubectl get pods -l app=checkout-api
kubectl describe pod <a-new-pod-name>    # read the Events section
kubectl rollout history deployment/checkout-api

# Fix
kubectl rollout undo deployment/checkout-api
kubectl rollout status deployment/checkout-api

Expected result

The --timeout=20s status command times out with an error instead of completing — that timeout is your signal, not a bug. describe pod shows an ImagePullBackOff/ErrImagePull event referencing the bad tag. After rollout undo, status reports successfully rolled out and all 4 Pods run nginx:1.25.

Verification

kubectl get pods -l app=checkout-api -o jsonpath='{.items[*].spec.containers[0].image}' — all four entries should read nginx:1.25, none the bad tag. Run it twice, a minute apart, to confirm it's stable and not still converging.

Common failure

Repeatedly re-running rollout status and waiting, hoping the image will somehow start pulling — it won't, the tag doesn't exist. Equally wrong: kubectl delete pod on the broken Pods — the ReplicaSet just creates identical replacements from the same broken template.

Troubleshooting

If rollout undo doesn't land on the revision you expect, run kubectl rollout history deployment/checkout-api first to see what's available, then target one explicitly with kubectl rollout undo deployment/checkout-api --to-revision=<N>.

Cleanup / rollback

kubectl delete deployment checkout-api --ignore-not-found

Production lesson

The habit that separates a calm rollback from a panicked one is checking kubectl describe pod's Events section before touching anything else — it tells you in one command whether you're looking at a bad image, a crashing app, or a scheduling/capacity problem, and each of those has a different correct fix.

Recap
  • A Deployment is a policy layer: it manages a ReplicaSet, which manages Pods — it never touches a Pod directly.
  • spec.selector.matchLabels must match spec.template.metadata.labels on creation, and spec.selector is immutable afterward — no in-place renames.
  • Only changes to spec.template trigger a new rollout (new ReplicaSet); changing spec.replicas alone just scales the existing one.
  • Default strategy is RollingUpdate with maxUnavailable=25% (rounds down) and maxSurge=25% (rounds up); Recreate kills every old Pod before creating new ones.
  • kubectl rollout undo deployment/<name> [--to-revision=N] is the fast, safe way out of a broken rollout — up to revisionHistoryLimit (default 10) old ReplicaSets are kept for exactly this.
