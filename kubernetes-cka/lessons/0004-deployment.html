Deployment

A bare Pod has no memory. Kill it — node reboot, OOM, `kubectl delete pod` — and it stays dead. Nothing notices, nothing recreates it. A Deployment is the object that fixes that: it wraps a Pod template with a controller that continuously checks "do I have the number of Pods I was told to have?" and reconciles reality toward that number. That's self-healing, and it's also what makes rolling updates and scaling possible — they're all just the same reconcile loop, aimed at a Pod template that changed.

Tied to your mission: almost every real workload you run in GKE Autopilot is a Deployment (or something built the same way — StatefulSet, DaemonSet). The CKA troubleshooting domain assumes you already know this shape cold, so a broken rollout question doesn't cost you time re-deriving it.

The mental model

Strip a Deployment down and it's three things bolted together:

  • spec.template — a full Pod spec, embedded (this is literally the Pod manifest you already know, minus apiVersion/kind, sitting one level deeper).
  • spec.replicas — how many copies of that Pod template should exist.
  • spec.selector — the label query the Deployment uses to find "which Pods are mine."

The single trickiest structural gotcha: spec.selector.matchLabels must match the labels in spec.template.metadata.labels. If they don't match, the Deployment is invalid — the controller has no way to tell which Pods it owns. Nothing else in Kubernetes requires an object to "match itself" like this; it trips up almost everyone coming from bare Pods.

The Deployment itself doesn't touch Pods directly. It creates and manages a ReplicaSet, and the ReplicaSet is the thing that actually creates and watches the Pods. When you update a Deployment's Pod template (say, a new image), it creates a new ReplicaSet and scales the old one down to zero while scaling the new one up — that's a rolling update. This is why kubectl get rs shows objects named like my-app-7d9f8c9b7 — the hash suffix is generated from the Pod template, so a new template means a new ReplicaSet.

Try it first — before reading on

Q1. What two fields must match for a Deployment to be valid?

spec.selector.matchLabels must match spec.template.metadata.labels

Q2. What object does a Deployment actually create to manage Pods — the thing you'd see if you ran kubectl get rs?

A ReplicaSet. The Deployment manages the ReplicaSet; the ReplicaSet manages the Pods.

Q3. A Pod inside a Deployment gets OOMKilled and dies. What actually notices and recreates it — the Deployment, or something else?

The ReplicaSet's controller loop notices the replica count dropped below spec.replicas and creates a new Pod. The Deployment isn't watching Pods directly — it delegates that to the ReplicaSet it owns.

Now build it — in your terminal, not here

Take the labeled Pod you wrote in Lesson 2 and turn it into a Deployment with 3 replicas. Write it by hand — no copy-paste. It needs:

  • apiVersion: apps/v1, kind: Deployment (note: different API group from Pod — Pod is v1, Deployment is apps/v1)
  • a Deployment name in metadata
  • spec.replicas: 3
  • spec.selector.matchLabels — pick a label key/value (e.g. the same one you used on your Lesson 2 Pod)
  • spec.template.metadata.labels — must be the exact same label key/value as the selector above
  • spec.template.spec.containers — the same container spec (name + image) you used in your Lesson 2 Pod

Once it's written, apply it and check the shape: kubectl get deploy, then kubectl get rs, then kubectl get pods --show-labels. Confirm you can trace Deployment → ReplicaSet → 3 Pods by label.

Reveal the reference answer

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-nginx
  template:
    metadata:
      labels:
        app: my-nginx
    spec:
      containers:
        - name: nginx
          image: nginx

Bring what you wrote back to your notes — check the selector against the template labels field-by-field, since that's the one thing that silently breaks if you get it wrong.

Now use the operational payoff

This is the part a bare Pod can never give you. With the Deployment applied, try:

  • kubectl rollout status deployment/my-nginx — watch a rollout reach steady state
  • change the image in your manifest (e.g. pin a tag), re-apply, and run kubectl rollout status again — watch the new ReplicaSet come up while the old one scales to zero
  • kubectl rollout undo deployment/my-nginx — roll back to the previous ReplicaSet's Pod template
  • kubectl rollout history deployment/my-nginx — see the revisions that undo can target

Read (or at least skim) the official docs — the exact pages you're allowed to search during the real exam: kubernetes.io/docs/concepts/workloads/controllers/deployment and kubectl rollout reference.

Recap
  • A Deployment = Pod template (spec.template) + desired count (spec.replicas) + a selector that finds its own Pods (spec.selector)
  • spec.selector.matchLabels must exactly match spec.template.metadata.labels, or the Deployment is invalid
  • A Deployment doesn't manage Pods directly — it creates and manages a ReplicaSet, which creates and watches the Pods
  • kubectl rollout status / rollout undo / rollout history are the operational payoff: safe rollout tracking and rollback, something a bare Pod can never give you
