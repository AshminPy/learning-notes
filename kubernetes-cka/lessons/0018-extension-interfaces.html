Extension interfaces: CNI, CSI, CRI

Kubernetes core doesn't run containers, doesn't wire up Pod networking, and doesn't talk to storage arrays. It defines three plugin interfaces and lets other software do that work. You've already used all three without naming them — this lesson names them, because the exam does.

Simple example: think of Kubernetes as a socket, not the appliance. CRI is the socket a container runtime plugs into. CNI is the socket a network plugin plugs into. CSI is the socket a storage driver plugs into. Swap the plugin, the socket doesn't change.

CRI — Container Runtime Interface

The kubelet doesn't run containers itself — it calls a CRI-compatible runtime (containerd, CRI-O) over a gRPC socket. crictl talks to that same socket directly, which is why it works even when the API server is unreachable (Lesson 15).

crictl ps -a          # containers, straight from the runtime
crictl images         # images pulled on this node
crictl logs <id>      # same idea as kubectl logs, one layer lower

CNI — Container Network Interface

A CNI plugin (Calico, Cilium, Flannel...) is what actually gives every Pod an IP and routes traffic between nodes. Kubernetes defines that a Pod gets an IP; the CNI plugin defines how. This is why a NetworkPolicy object can exist and do nothing (Lesson 10) — creating the object doesn't enforce it, only a CNI plugin that implements NetworkPolicy does.

ls /etc/cni/net.d/            # CNI plugin config, on the node
kubectl get pods -n kube-system -l k8s-app=calico-node   # example: Calico's own Pods

CSI — Container Storage Interface

You already met this in Lesson 7 without the name: a StorageClass's provisioner field (e.g. pd.csi.storage.gke.io) names a CSI driver. When a PVC requests dynamic storage, Kubernetes core hands the request to that driver — it's the driver, not Kubernetes, that actually creates the disk.

kubectl get storageclass                 # which provisioner (CSI driver) is default
kubectl get pods -n kube-system | grep csi   # the driver's own Pods, running in-cluster

Try it — before looking below

Q1. A Pod is stuck Pending, and describe shows no scheduling error — it's scheduled, but has no IP and never goes Running. Which interface's plugin would you check first?

CNI. Assigning the Pod an IP and wiring its network is the CNI plugin's job — check its Pods/DaemonSet in kube-system are Running on that node, and check /etc/cni/net.d has valid config.

Q2. A PVC stays Pending forever with no PV bound. What's the most likely missing piece, and which interface does it belong to?

The CSI driver named in the StorageClass's provisioner field either isn't installed or isn't running — check kubectl get pods -n kube-system for it. That's CSI, storage's plugin interface.

Source

kubernetes.io/docs/concepts/extend-kubernetes — exam-allowed page.

Recap
  • Kubernetes defines three plugin sockets, doesn't implement them: CRI (runtime), CNI (networking), CSI (storage).
  • crictl talks straight to CRI — works even if the API server is down.
  • A CNI plugin gives Pods IPs and enforces NetworkPolicy; a CSI driver actually creates the disk behind a StorageClass.
