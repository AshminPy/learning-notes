Extension interfaces: CNI, CSI, CRI

Kubernetes core doesn't run containers, doesn't wire up Pod networking, and doesn't talk to storage arrays. It defines three plugin interfaces and lets other software do that work. You've used all three since Lesson 1 without naming them — this lesson names them, because the exam does.

Mental model: Kubernetes is a socket, not the appliance. CRI is the socket a container runtime plugs into. CNI is the socket a network plugin plugs into. CSI is the socket a storage driver plugs into. That predicts a real debugging move: a symptom that "looks like a Kubernetes bug" is almost always one specific plugin's problem, once you know which socket it plugs into.

Where this fits

Kubernetes core (defines the interface, not the implementation)
   ├ CRI → containerd / CRI-O        (Lesson 13's crictl talks here directly)
   ├ CNI → Calico / Cilium / Flannel (Lesson 10's NetworkPolicy enforcement lives here)
   └ CSI → cloud disk drivers        (Lesson 7's StorageClass provisioner names this)

CRI — Container Runtime Interface

The kubelet doesn't run containers itself — it calls a CRI-compatible runtime over a gRPC socket. crictl talks to that same socket directly, which is why it works even when the API server is unreachable (Lesson 15).

CNI — Container Network Interface

A CNI plugin gives every Pod an IP and routes traffic between nodes. Kubernetes defines that a Pod gets an IP; the CNI plugin defines how. This is exactly why a NetworkPolicy object (Lesson 10) can exist and do nothing — creating the object doesn't enforce it, only a CNI plugin that implements NetworkPolicy does.

CSI — Container Storage Interface

You met this in Lesson 7 without the name: a StorageClass's provisioner field (e.g. pd.csi.storage.gke.io) names a CSI driver. When a PVC requests dynamic storage, Kubernetes core hands the request to that driver — the driver, not Kubernetes, actually creates the disk.

Try it

Q1. A Pod is stuck Pending, scheduled with no scheduling error, but never gets an IP and never goes Running. Which interface's plugin first?

CNI — check its Pods/DaemonSet are Running on that node, and /etc/cni/net.d has valid config.

Now, before revealing: a PVC stays Pending forever with no PV bound. Which interface, and what's the check?

Reveal the answer

CSI — the driver named in the StorageClass's provisioner field isn't installed or isn't running. Check kubectl get pods -n kube-system | grep csi.

A controlled failure

ls /etc/cni/net.d/
kubectl get pods -n kube-system -l k8s-app=calico-node 2>/dev/null || \
  kubectl get pods -n kube-system | grep -iE "cni|calico|flannel|cilium"

Predict first: if this directory were empty, would existing Pods lose their network mid-flight? Observe: no — CNI runs at Pod creation time to wire networking; a config change or CNI Pod crash after a Pod is already running doesn't retroactively unwire it. This is why "the CNI Pod just crashed" and "existing Pods lost network" are two separate claims, not one.

Production best practices

Production note: when choosing a CNI plugin, NetworkPolicy enforcement isn't universal — verify the specific plugin/mode supports it before relying on Lesson 10's policies in production; some CNI configurations provide networking without policy enforcement.

Exam & interview notes

Ties directly into Services & Networking (20%) and Storage (10%) troubleshooting.

Interview Q: "A cluster has zero NetworkPolicy enforcement despite policies being applied. What layer is responsible, and how do you confirm it?" A: The CNI plugin — NetworkPolicy is only data until a CNI that implements it reads and enforces it. Confirm by checking which CNI is installed and its documented NetworkPolicy support, not by re-reading the policy YAML.

Recap
  • Kubernetes defines three plugin sockets, doesn't implement them: CRI (runtime), CNI (networking), CSI (storage).
  • crictl talks straight to CRI — works even if the API server is down.
  • A CNI plugin gives Pods IPs and (if it supports it) enforces NetworkPolicy; a CSI driver actually creates the disk behind a StorageClass.

  • When would a "Kubernetes networking bug" actually be a CNI plugin bug instead?
  • What happens to a Pod's network if the CNI plugin crashes after the Pod is already running?
  • How would you verify which CSI driver is actually provisioning a given PVC's storage?
