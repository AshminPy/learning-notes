Kubernetes / CKA — Lesson 18 of 24

Extension interfaces: CNI, CSI, CRI

Why this matters

"My cluster is broken" is one of the most misleading sentences in this job. Very often the cluster — the API server, etcd, the scheduler, the kubelet — is completely fine, and the thing that's actually broken is a piece of third-party software running inside it: a network plugin, a storage driver, a container runtime. Kubernetes core deliberately doesn't run containers, doesn't wire up Pod networking, and doesn't talk to a storage array — it defines three plugin interfaces and lets other vendors' software do that work instead.

If you don't know where the boundary sits, you troubleshoot the wrong layer. People restart kube-apiserver, re-run kubeadm upgrade, or file a Kubernetes bug report — burning hours — when the real fix is a one-line log check on a plugin's own Pod, or a credential rotation on a storage driver that has nothing to do with Kubernetes itself. This lesson exists so you can answer, in under a minute, "is this Kubernetes, or is this the plugin?" — because that single question is exactly what the exam's Troubleshooting domain (30% of the CKA, the single largest domain) is built around.

Mental model: Kubernetes is a socket, not the appliance. CRI is the socket a container runtime plugs into. CNI is the socket a network plugin plugs into. CSI is the socket a storage driver plugs into. The socket's shape doesn't change based on which appliance is plugged in — and that predicts something concrete: because the plugin is a separate piece of software from Kubernetes itself, it has its own version number and its own release cycle. Upgrading your cluster from Kubernetes 1.33 to 1.34 does not force a CNI, CSI, or CRI upgrade in lockstep — Calico, for example, ships as its own "v3.x" line, tested against a specific range of Kubernetes versions, and an old Calico release can simply stop being supported on a newer Kubernetes release without either side changing on the same day. The socket analogy also predicts the failure mode: compatibility isn't automatic just because both sides are independently versioned — you still have to check the plugin's own compatibility matrix before either side upgrades, the same way you'd check a wall socket's voltage before plugging in an appliance bought in another country.

CRI — Container Runtime Interface

The kubelet never runs a container directly. It's a gRPC client to a CRI-compatible runtime — containerd or CRI-O — and that gRPC protocol, not any specific runtime binary, is what "CRI" actually names. Any runtime that speaks the CRI API (v1, required since Kubernetes 1.26) can sit behind the kubelet; Kubernetes doesn't care which one.

This is the one interface with no cluster Pod at all — clarify this precisely, because it trips people up. CRI isn't a Deployment, a DaemonSet, or anything you'll ever see in kubectl get pods. It's a service running directly on the node's operating system (a systemd unit, typically), underneath the kubelet, underneath Kubernetes as a whole. If a container runtime is unhealthy, no kubectl command reaches it — you have to look at the node itself.

crictl is the tool for that: it talks to the same CRI socket the kubelet does, which is why it keeps working even when the API server is unreachable (Lesson 15).

crictl ps -a          # containers, straight from the runtime, no API server involved
crictl images         # images already pulled on this node
crictl logs <id>      # same idea as kubectl logs, one layer lower
crictl pods           # the runtime's view of Pod sandboxes on this node

CNI — Container Network Interface

A CNI plugin (Calico, Cilium, Flannel...) is what actually gives every Pod an IP and routes traffic between nodes. Kubernetes defines that a Pod gets an IP; the plugin defines how.

Go one level deeper on what "CNI-compliant" means, because the exam and real production both assume you know this: CNI is not a Kubernetes-specific technology. It's a CNCF specification — a plugin contract for adding and removing network interfaces from a Linux network namespace — maintained independently of Kubernetes and consumed by several other platforms (Cloud Foundry and Apache Mesos both use it too). A "CNI-compliant plugin" just means it implements that generic add/remove contract; nothing about the contract itself is aware Kubernetes exists. Kubernetes requires a plugin compatible with CNI spec v0.4.0 or later, and recommends v1.0.0.

One more internals detail worth knowing precisely: since Kubernetes 1.24 removed dockershim, the kubelet no longer invokes CNI plugins itself — the container runtime does, as part of setting up a Pod sandbox. That's the one point where CRI and CNI actually touch, even though you should keep reasoning about them as two separate sockets for everything else. Plugin binaries live at /opt/cni/bin; config lives at /etc/cni/net.d by default.

This is also why a NetworkPolicy object can exist and do nothing (Lesson 10): the API server will happily store the object regardless of whether anything enforces it. Enforcement is a capability of the specific CNI plugin installed, not something Kubernetes core provides — and not every plugin has it (see the Common mistakes callout below for a concrete case).

Don't confuse this with kube-proxy. It runs as a DaemonSet in every cluster too, but it's a core Kubernetes networking component, not a CNI plugin — its job is Service virtual IPs (writing the iptables/IPVS/nftables rules that redirect ClusterIP traffic to real Pod IPs). Some CNI plugins, Cilium among them, can fully replace kube-proxy's job with their own eBPF dataplane — but that's an optional integration a specific plugin offers, not evidence that kube-proxy itself is part of CNI.

ls /etc/cni/net.d/                                  # CNI plugin config, on the node
kubectl get pods -A -o wide | grep -Ei 'calico|cilium|flannel|weave'   # example plugin Pods

CSI — Container Storage Interface

You already met this in Lesson 7 without the name: a StorageClass's provisioner field (for example pd.csi.storage.gke.io) names a CSI driver. When a PVC requests dynamic storage, Kubernetes core hands the request to that driver — the driver, not Kubernetes, actually creates the disk.

Same pattern as CNI: CSI is also a cross-platform standard, not a Kubernetes invention — it's defined as a standard for exposing block and file storage systems to containerized workloads across multiple container orchestration systems, Kubernetes being one of them. A real CSI driver typically ships as two separate deployments: a controller component (talks to the cloud provider's API to create/attach/detach the actual disk — this is the piece that usually needs cloud credentials) and a node plugin, usually a DaemonSet, that mounts and formats the volume on whichever node needs it. Both are ordinary Pods, visible with kubectl, running in kube-system or a driver-specific namespace depending on how it was installed.

kubectl get storageclass                      # which provisioner (CSI driver) is default
kubectl get csidrivers                        # CSI drivers registered with the cluster
kubectl get pods -A | grep -i csi             # the driver's own controller + node Pods

Production note: a platform team's choice of CNI plugin — Calico vs. Cilium vs. Flannel — is exactly the kind of decision you make once and live with for years, not something you casually swap later. It isn't just "which one is popular": Flannel by itself doesn't enforce NetworkPolicy at all (this is well-known enough that Calico ships an official "Canal" install path — Flannel for networking, Calico bolted on purely for policy enforcement); Cilium's eBPF dataplane and built-in WireGuard encryption are real capabilities Flannel doesn't have; Calico's BGP-based routing behaves differently at scale than Cilium's or Flannel's overlay approach. Migrating a live fleet from one CNI plugin to another later means re-networking every node — a genuinely painful, multi-week project with real outage risk, not a config change. The same logic applies to picking a CSI driver: the cloud-native driver (GCE PD, EBS, Azure Disk) vs. a third-party one (Portworx, OpenEBS) locks in your snapshot/backup tooling and IAM footprint for the life of the cluster.

Hands-on exercise

Objective

Prove to yourself which running Pods in your cluster are CNI, which are CSI, and confirm that CRI genuinely has no Pod at all.

Scenario

You've been told "check the CNI Pods" and "check the CSI Pods" in a runbook before, but you've never actually confirmed you can tell them apart from core Kubernetes components on a real cluster — or confirmed the CRI claim that it isn't a Pod.

Environment assumptions

Any cluster you can kubectl into (kind, minikube, or a real dev cluster) with a CNI plugin and a CSI driver installed. Namespace layout varies by install method — a manifest-based Calico install commonly lands in kube-system, but the Tigera operator install puts Calico's own Pods in a separate calico-system namespace, and modern Flannel installs use their own kube-flannel namespace. Don't assume kube-system is the only place to look.

Commands

kubectl get pods -A -o wide
kubectl get pods -A | grep -Ei 'calico|cilium|flannel|weave|antrea'
kubectl get pods -A | grep -i csi
kubectl get csidrivers
kubectl get pods -A | grep -i kube-proxy

Expected result

The first grep returns your cluster's CNI plugin Pods (a DaemonSet, one per node). The second returns CSI controller and node Pods. The third lists registered CSI drivers by name. The fourth returns kube-proxy — present, but not a CNI plugin, a separate core component. None of the four commands return anything for "CRI" or your container runtime by name, because it isn't a scheduled workload.

Verification

The absence in that last point is the proof, not a gap in the exercise. If you want to see CRI directly, you have to leave kubectl entirely and either SSH to a node and run crictl info, or check the container runtime's own service status (for example systemctl status containerd) — it lives one layer below anything the API server can see.

Common failure

Assuming kube-proxy is "part of CNI" because it's networking-related and also runs as a DaemonSet. It isn't — it's core Kubernetes, implementing Service virtual IPs, independent of whichever CNI plugin you've installed.

Troubleshooting

If the CNI/CSI greps return nothing in any namespace, check kubectl get pods -A unfiltered first — you may be grepping for the wrong plugin name, or the plugin genuinely isn't installed (some managed clusters, like a stock kind cluster, ship a minimal default you might not expect).

Cleanup / rollback

Nothing to clean up — every command here is read-only.

Production lesson

This exact five-command sequence is how you scope "is this Kubernetes or is this a plugin" in under two minutes on a cluster you've never seen before. Knowing it cold, without having to think about it mid-incident, is the actual skill this lesson is teaching.

Failure scenario

A realistic incident showing the specific pattern that makes CNI failures confusing: existing traffic keeps working while new Pods silently fail.

  1. 02:58 Worker node ip-10-0-4-17 reboots for a routine, automated OS security patch.
  2. 03:01 The node rejoins the cluster within three minutes — kubectl get nodes shows it Ready. The kubelet and containerd both came back cleanly.
  3. 03:03 The node's CNI plugin Pod, calico-node-x7k2p, restarts along with everything else on the node — but it doesn't come up clean. kubectl describe pod shows repeated readiness-probe failures; it settles into CrashLoopBackOff.
  4. 03:07 On-call notices something odd: three payment-api replicas that were already running on this node before the reboot show Running, healthy, serving traffic normally. A rollout five minutes later schedules a fourth replica onto the same node — it goes Running, but .status.podIP stays empty and nothing can reach it.
  5. 03:12 kubectl logs calico-node-x7k2p --previous -n calico-system shows it failing to reach its datastore fast enough during startup — a known class of startup-ordering issue after a quick reboot, not a scheduler or API server problem. Existing Pods keep working because their network namespace, veth pair, and routes were already programmed into the kernel before the crash — the CNI plugin's job for them is already done. New Pods fail because bringing up a brand-new Pod's networking requires the plugin's control process to be alive and reachable, and it isn't.
  6. 03:15 Fix applied: delete the crashing Pod so its DaemonSet replaces it — kubectl delete pod calico-node-x7k2p -n calico-system. The replacement starts after the node has had more time to settle, reaches the datastore, and passes its readiness probe.
  7. 03:18 Verified: the fourth replica is deleted and rescheduled; this time .status.podIP populates immediately and it goes healthy. The three original replicas were unaffected for the entire incident.

Troubleshooting workflow

The general 10-step method, applied specifically to "is this Kubernetes core or a CNI/CSI/CRI plugin":

  1. Confirm the symptom. Run the actual command yourself — kubectl get pod -o wide for a missing IP, kubectl get pvc for storage, kubectl describe pod for a stuck container. Don't diagnose from a Slack message describing what someone thinks happened.
  2. Define scope. kubectl get pods -A -o wide — is this one Pod, one node, or cluster-wide? A single-node symptom points hard at that node's plugin instance, not core Kubernetes, which is cluster-wide by nature.
  3. Identify which interface is implicated. Use the decision table below: no IP or cross-node traffic issue → CNI. PVC/PV/provisioning issue → CSI. Container stuck with a runtime-level error string (shim, sandbox, image pull at the runtime layer) → CRI. This step alone resolves most "which team owns this" questions.
  4. Check recent changes. kubectl get events --sort-by=.lastTimestamp — was the plugin just upgraded, did its DaemonSet just roll, was the node just rebooted or drained?
  5. Inspect the plugin's own state. kubectl get pods -n <plugin namespace> -o wide for its DaemonSet/Deployment, kubectl logs <pod> --previous if it restarted. For CRI there's no Pod to inspect — go to the node itself: crictl info, or the runtime's own service logs (journalctl -u containerd).
  6. Check the plugin's own docs and issue tracker before assuming Kubernetes is broken. Search the exact error string in the plugin's own GitHub repo — CNI/CSI/CRI projects all have public issue trackers, and this exact symptom has usually been reported before. In parallel, rule out a genuine core problem independently: journalctl -u kubelet on the node, and the kube-apiserver's own logs. If those are clean and only the plugin's Pod is unhealthy, it isn't a Kubernetes bug.
  7. Form a hypothesis. For example: "the CNI plugin's control process can't reach its datastore after a fast reboot — this is a plugin startup issue, not a scheduler bug."
  8. Test one variable. Schedule an equivalent test Pod on a different, healthy node. If it works there, you've isolated the failure to this node's plugin instance, not a cluster-wide Kubernetes misconfiguration.
  9. Apply the fix at the layer that owns it. Restart or roll back the plugin's own Pod, fix the CSI driver's cloud credentials, or restart the container runtime service on the node — never restart kube-apiserver or run a control-plane upgrade to fix a plugin-owned problem.
  10. Verify, document, and prevent recurrence. Confirm new Pods get IPs, PVCs bind, or containers start — then write down which of the three interfaces actually owned the root cause, so the next on-call doesn't spend an hour looking at Kubernetes core again for the same symptom.

Security note: installing a CNI plugin is a real trust decision, not a routine install. Most CNI plugins run as a privileged, host-network DaemonSet on every single node — Calico's own docs are explicit that calico-node needs the CAP_SYS_ADMIN capability and runs as a privileged container to get it. That means every node in your cluster is granting this third-party software root-equivalent access to its network stack. Vet the source, pin exact versions, and don't apply a random CNI manifest you found in a blog post. CSI drivers carry a different but equally serious trust requirement: their controller component frequently needs real cloud credentials to do its job — the GCE persistent disk CSI driver's controller, for example, depends on a GCP service account to call the Compute Engine API and typically needs a role like roles/compute.storageAdmin. That's a credential capable of creating, attaching, and deleting real cloud disks — scope it to exactly what the driver needs, never a project-owner-level account.

Reliability note: because every node depends on the same CNI or CSI plugin, a bad plugin upgrade has cluster-wide blast radius even though Kubernetes core is untouched. Treat a CNI/CSI/CRI upgrade with the same care as any other risky production change — canary it on a subset of nodes first, watch, then proceed — rather than as a routine "just apply the new manifest" afterthought.

Common mistake: filing a "Kubernetes bug" — or telling your team "Kubernetes is broken" — for what's actually a CNI or CSI plugin issue. This wastes hours going down the wrong path (core component logs, control-plane restarts) and, if you do report it, you've filed it in the wrong place: the fix has to come from the plugin's own project, not from Kubernetes.

Common mistake: assuming a fresh kind or minikube cluster gives you full NetworkPolicy enforcement to practice against. Kind's default CNI, kindnetd, is documented by the kind project itself as not enforcing default-deny NetworkPolicy — you can apply a policy, see it accepted, and still see traffic flow right through it. If you want to actually test NetworkPolicy behavior, install a policy-enforcing CNI (Calico, Cilium) via kind's disableDefaultCNI option first.

Common mistake: treating kube-proxy as a CNI component because it's networking-related and ships as a DaemonSet too. It's core Kubernetes — Service virtual IPs — independent of whichever CNI plugin is installed, even though some CNI plugins can optionally replace it.

Knowledge check

Q1. A Pod is stuck Pending, and describe shows no scheduling error — it's scheduled, but has no IP and never goes Running. Which interface's plugin would you check first?

CNI. Assigning the Pod an IP and wiring its network is the CNI plugin's job — check its Pods/DaemonSet are Running on that node, and check /etc/cni/net.d has valid config.

Q2. A PVC stays Pending forever with no PV bound. What's the most likely missing piece, and which interface does it belong to?

The CSI driver named in the StorageClass's provisioner field either isn't installed or isn't running — check kubectl get pods -A for it. That's CSI, storage's plugin interface.

Q3. A container is stuck in ContainerCreating, and the event text reads "failed to create containerd task: failed to create shim". Which interface should you check first?

C. The error string names containerd directly — that's the container runtime, CRI's job. There's no Pod for it; go to the node with crictl or check the runtime's own service logs.

Q4. You upgrade your cluster's control plane by one Kubernetes minor version. What does this imply about your installed CNI plugin?

C. CNI plugins are versioned and released independently of Kubernetes — Calico, for example, publishes its own tested range of compatible Kubernetes versions per release. Independent versioning means you check compatibility, you don't assume it.

But the skill it actually builds — correctly attributing a symptom to Kubernetes core vs. a plugin before you start fixing anything — is exactly what Troubleshooting (30%), the exam's single largest domain, tests. Expect this distinction to show up disguised as an ordinary-looking broken-Pod or broken-storage scenario, not as a question that names "CNI" or "CSI" directly.

Production challenge

Objective

Given only symptom descriptions — no logs yet — correctly attribute each incident to CNI, CSI, or CRI, and name the exact first command you'd run, before you're allowed to look anything up.

Scenario

Three tickets land in the same on-call shift:

Ticket A: "New Pods scheduled onto node worker-7 stay Pending or come up with no IP; Pods already running on that node are fine."
Ticket B: "The PVC for our new Postgres StatefulSet has been Pending for 20 minutes; no PV has bound."
Ticket C: "A Pod is stuck in ContainerCreating; the event reads: 'failed to create containerd task: failed to create shim: OCI runtime create failed'."

Environment assumptions

A real or kind/minikube cluster with a CNI plugin, a CSI driver, and containerd installed. You have kubectl access, and node access (SSH or a debug Pod) if a ticket turns out to need crictl.

Commands

Write down, for each ticket, the owning interface and the first command — then confirm with these:

# Ticket A — CNI
kubectl get pods -A -o wide --field-selector spec.nodeName=worker-7

# Ticket B — CSI
kubectl describe pvc <pvc-name>
kubectl get pods -A | grep -i csi

# Ticket C — CRI
crictl ps -a          # run on worker node hosting the Pod

Expected result

Ticket A → CNI (the error is about IP assignment on one node while others are fine — a plugin instance problem, not the scheduler). Ticket B → CSI (a provisioning failure belongs to the driver named in the StorageClass). Ticket C → CRI (the error string names containerd and an OCI runtime failure directly — that's the runtime, not Kubernetes objects at all).

Verification

kubectl describe pod on Ticket A's Pod should show it was scheduled successfully with no networking error at the API level — confirming this isn't a scheduler problem. kubectl describe pvc on Ticket B should show a provisioning-failure Event naming the CSI driver. Ticket C's event text already names the runtime — no further kubectl digging will explain it; only node-level runtime logs will.

Common failure

Treating Ticket C as "the Pod is broken" and spending time on kubectl describe pod, YAML, or RBAC. The error string is telling you exactly where to look — the container runtime — and no amount of API-level inspection fixes a node-level runtime problem.

Troubleshooting

If you're unsure which namespace a ticket's plugin Pods live in on this specific cluster, run kubectl get pods -A unfiltered and look for name patterns (calico/cilium/flannel for CNI, csi for CSI) instead of guessing kube-system — install method changes the namespace.

Cleanup / rollback

None — this is a read-only triage exercise.

Production lesson

This exact triage — three tickets, three different owning components, in one shift — is a normal on-call hour. The senior engineer on the team isn't the one who already knows the fix for all three; it's the one who routes each ticket to the right owner in under two minutes instead of debugging all three as "Kubernetes is down."

Recap
  • Kubernetes defines three plugin sockets and implements none of them: CRI (runtime), CNI (networking), CSI (storage). All three are open specs, not Kubernetes-specific technology — CNI and CSI are both used by other platforms too.
  • CRI has no Pod — it's a node-level service underneath the kubelet. crictl talks straight to it, working even when the API server is down.
  • Since Kubernetes 1.24, the container runtime — not the kubelet — is what invokes the CNI plugin. That's the one point CRI and CNI actually touch.
  • Plugins are versioned and released independently of Kubernetes — upgrading one doesn't force upgrading the other, but compatibility still has to be checked.
  • A crashed CNI plugin Pod stops new Pods from getting networking on that node, while already-running Pods keep working — their routes were already programmed before the crash.
  • CNI plugins typically run privileged, host-network DaemonSets on every node; CSI driver controllers often hold real cloud credentials. Both are real trust decisions, not routine installs.
  • "Kubernetes is broken" is very often actually "the plugin is broken" — check the plugin's own Pods, logs, and issue tracker before assuming a core Kubernetes bug.
