NetworkPolicy

Service (Lesson 3), Ingress (Lesson 8), and RBAC (Lesson 9) all control who can reach an address or call an API. None of them stop raw Pod-to-Pod traffic at the network layer — by default, everything can reach everything. NetworkPolicy is the layer that closes that.

Mental model: a NetworkPolicy is a firewall rule that only exists once you write one — the cluster ships with no firewall at all. That predicts something that surprises almost everyone the first time: a fresh cluster is default-allow, the exact opposite of a real firewall's default-deny. You don't need to open paths, you need to close them.

Where this fits

Cluster └ Node └ Pod └ Labels

NetworkPolicy
  podSelector: app=backend       (which Pods this rule applies to)
  ingress.from.podSelector: role=frontend
      │
      ▼
CNI plugin   (must implement NetworkPolicy, or this does nothing)
      │
      ▼
Actual packet allow/deny between Pods

The shape of a policy

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          role: frontend
  • podSelector — which Pods this policy applies to (empty {} = all Pods in the namespace) — Lesson 2's label-matching, applied to network rules instead of Service routing
  • policyTypes — Ingress, Egress, or both
  • ingress.from/egress.to — the allow-list: podSelector, namespaceSelector, or ipBlock

Why it's built this way: once any policy selects a Pod for a direction, that direction becomes deny-by-default except what's explicitly allowed — but only for Pods a policy actually selects. Pods no policy mentions stay fully open. This lets teams adopt NetworkPolicy incrementally, namespace by namespace, instead of an all-or-nothing cluster lockdown.

Put podSelector and namespaceSelector in the same list entry and they AND together; list them as separate entries and they OR. One indent level flips the meaning. Multiple policies on the same Pod are also additive (OR), never AND.

Try it

Q1. With zero NetworkPolicy objects anywhere in the cluster, what's the default Pod-to-Pod traffic behavior?

Fully open — every Pod reaches every other Pod, any port, any namespace.

Now write your own, by hand: a NetworkPolicy applying to app: backend, Ingress only, allowing traffic solely from role: frontend on port 80. Try before revealing.

Reveal the reference answer

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-allow-frontend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          role: frontend
    ports:
    - protocol: TCP
      port: 80

Common mistake: applying a NetworkPolicy on a cluster whose CNI doesn't enforce it — kubectl get networkpolicy shows it exists, traffic flows exactly as before, no error anywhere.

A controlled failure

kubectl run backend --image=nginx:1.29 --labels=app=backend
kubectl run tester --image=busybox --labels=role=other --restart=Never -it --rm -- \
  wget -qO- --timeout=3 backend

Predict first: before applying any policy, does tester reach backend? Observe: yes — default-allow. Apply the policy above (selecting app: backend, only from role: frontend), then re-run the same test. It should now time out — tester is labeled role: other, not frontend.

Production best practices

Production note: real clusters default-deny at the namespace level (an empty podSelector: {} policy with no ingress/egress rules) and then explicitly allow only the traffic that's actually needed — treating "open by default" as the exception to justify, not the baseline to accept.

Exam & interview notes

Directly scored under Services & Networking (20%).

Interview Q: "You apply a NetworkPolicy and traffic is still unrestricted. What do you check first?" A: Whether the cluster's CNI actually implements NetworkPolicy enforcement — the object applies successfully either way, with zero error, so this is easy to miss without knowing to check it.

Recap
  • Default with no NetworkPolicy: every Pod reaches every Pod — the opposite of a firewall's default-deny.
  • A NetworkPolicy does nothing unless the CNI implements it — no error either way.
  • podSelector (Lesson 2's mechanism) + policyTypes pick the Pods and direction; multiple policies are additive (OR), never AND.

Confidence check — answer without looking back:

  • Why does Kubernetes ship with no Pod-to-Pod firewall by default?
  • When would a NetworkPolicy targeting app: backend leave a different Pod completely unaffected?
  • What happens to traffic if a policy is applied but the CNI doesn't support it?
  • How would you verify a NetworkPolicy is actually being enforced, not just accepted by the API?
