Kubernetes / CKA — Lesson 10 of 24

NetworkPolicy

Why this matters

Every lesson before this one quietly assumed a Pod can only reach what it's supposed to reach. That assumption is false the moment your cluster exists. Kubernetes ships with zero network segmentation: with no NetworkPolicy objects anywhere, every Pod can open a connection to every other Pod, on any port, in any namespace — including namespaces it has no business talking to. In a multi-tenant cluster, where one team's workloads share nodes and a control plane with another team's, this isn't a theoretical gap. It's a breach-amplification vector: one compromised Pod — a vulnerable dependency, a leaked token, a malicious image — can pivot laterally straight into another tenant's database Pod, with nothing in its way but a boundary you assumed existed and never actually configured. NetworkPolicy is the object that turns "flat network, trust everyone" into "default-deny, trust only what's explicitly allowed" — and this lesson is about knowing exactly how it decides what's allowed, because a NetworkPolicy that looks right and does nothing is worse than no policy at all: it gives you the confidence of a boundary without the boundary.

Mental model: a NetworkPolicy is a firewall rule stapled to a Pod's label selector, not to an IP address or a network segment. A traditional firewall rule says "allow traffic to 10.2.3.4" — the rule is anchored to a location. A NetworkPolicy says "allow traffic to any Pod labeled role: db" — the rule is anchored to an identity that travels with whichever Pods currently match, wherever they get rescheduled. This predicts something a location-based mental model gets wrong: change a running Pod's labels — kubectl label pod db role- — and its effective firewall changes in that same instant, with no NetworkPolicy edit, no CNI reload, no restart. Relabeling a Pod out of a selector is functionally equivalent to unplugging its network cable for whatever traffic that policy was allowing; relabeling it back in re-plugs it. This is also why a security review of "what can reach this Pod" has to check kubectl get pods --show-labels alongside the NetworkPolicy YAML — the policy text alone never tells you the current answer, only the policy plus the current labels does.

Core concepts

Default behavior: two independent directions, both open

Kubernetes defines two separate kinds of isolation for a Pod — isolation for ingress and isolation for egress — and decides them completely independently. The official docs state it plainly: "By default, a pod is non-isolated for egress; all outbound connections are allowed... By default, a pod is non-isolated for ingress; all inbound connections are allowed." A Pod becomes isolated in a direction only once some NetworkPolicy both selects that Pod and lists that direction in policyTypes. Until then, nothing restricts it. This is why "no NetworkPolicy anywhere" is not a neutral starting point — it's the most permissive state the cluster can be in, and it stays that way until you write your first policy.

The shape of a policy

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: test-network-policy
  namespace: default
spec:
  podSelector:
    matchLabels:
      role: db
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - ipBlock:
        cidr: 172.17.0.0/16
        except:
        - 172.17.1.0/24
    - namespaceSelector:
        matchLabels:
          project: myproject
    - podSelector:
        matchLabels:
          role: frontend
    ports:
    - protocol: TCP
      port: 6379
  egress:
  - to:
    - ipBlock:
        cidr: 10.0.0.0/24
    ports:
    - protocol: TCP
      port: 5978

This is the official reference example, and it's worth reading exactly as the docs describe it: it isolates Pods labeled role: db for both ingress and egress. The ingress rule allows connections on TCP 6379 from any one of three separate sources — an IP range, Pods in a labeled namespace, or Pods labeled role: frontend in the policy's own namespace. The egress rule allows connections out to a CIDR block on TCP 5978. Four fields do all the work:

  • podSelector — which Pods this policy applies to (empty {} = every Pod in the namespace)
  • policyTypes — Ingress, Egress, or both — which direction(s) this policy governs
  • ingress[].from / egress[].to — the allow-list, built from podSelector, namespaceSelector, and/or ipBlock
  • ports — restrict the rule to specific protocols/ports; omit it and the rule matches all ports

AND vs. OR: one indent level changes everything

The single most common way to write a NetworkPolicy that doesn't do what you think is to get the nesting of namespaceSelector and podSelector wrong inside a from/to entry. The docs give this exact pair of examples. First, both selectors inside the same list entry:

ingress:
- from:
  - namespaceSelector:
      matchLabels:
        user: alice
    podSelector:
      matchLabels:
        role: client

This is AND: "a single from entry that specifies both namespaceSelector and podSelector selects particular Pods within particular namespaces" — only Pods labeled role: client that also live inside a namespace labeled user: alice. Now the same two selectors, but as two separate entries in the list:

ingress:
- from:
  - namespaceSelector:
      matchLabels:
        user: alice
  - podSelector:
      matchLabels:
        role: client

This is OR: "it contains two elements in the from array, and allows connections from Pods in the local Namespace with the label role=client, or from any Pod in any namespace with the label user=alice." Same two selectors, same two label values, and a completely different traffic surface — the second version admits any Pod from an alice namespace, including ones with no client label at all. The docs' own advice for when you're unsure: run kubectl describe networkpolicy <name> and read back how Kubernetes actually parsed it, rather than trusting your eyes on the YAML.

The default-deny-all pattern

An empty podSelector: {} selects every Pod in the namespace. Combine that with a policyTypes entry and no matching ingress/egress block, and you get a policy that isolates every Pod for that direction while allowing nothing — because an isolated direction only permits what's explicitly listed, and nothing is listed. These five patterns are lifted directly from the official docs, and they're the actual building blocks of a real segmentation rollout:

# Deny all ingress to every pod in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes:
  - Ingress
---
# Deny all egress from every pod in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
spec:
  podSelector: {}
  policyTypes:
  - Egress
---
# Deny all ingress AND all egress — the full default-deny baseline
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress

The mirror image — explicitly allow-all, useful for temporarily opening a namespace back up without deleting your deny policy — uses an empty rule entry ({}, not an empty list) inside ingress/egress:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-all-ingress
spec:
  podSelector: {}
  ingress:
  - {}
  policyTypes:
  - Ingress

Simple example: notice the difference between "no ingress key at all" (deny everything, because nothing is listed) and "ingress: [{}]" (allow everything, because the one rule listed has no restrictions). Deleting the ingress: line entirely and writing ingress: [] or ingress: [{}] look like small edits but produce opposite security postures — this is a real place to slow down and re-read your own YAML before applying it.

namespaceSelector, combined selectors, and targeting a namespace by name

Just like podSelector, an empty namespaceSelector: {} is not "no namespaces" — per the NetworkPolicy API reference, "this field follows standard label selector semantics; if present but empty, it selects all namespaces," including the policy's own namespace. And because NetworkPolicy has no field to name a namespace directly, the docs are explicit: "it is not possible to directly specify the name of the namespaces in a NetworkPolicy. You must use a namespaceSelector with matchLabels or matchExpressions to select the namespaces based on their labels." The workaround Kubernetes provides for this: every namespace automatically carries an immutable label, kubernetes.io/metadata.name, set to the namespace's own name — so namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: kube-system}} is how you target one specific namespace by name in practice.

One more detail that matters once you're troubleshooting a "why is this connection still blocked" case: a connection is only allowed if both sides agree. Per the docs, "for a connection from a source pod to a destination pod to be allowed, both the egress policy on the source pod and the ingress policy on the destination pod need to allow the connection. If either side does not allow the connection, it will not happen." An allow-rule on the receiving Pod's ingress does nothing if the sending Pod is itself egress-isolated and hasn't been granted a matching egress rule.

Production example

Production note: real multi-tenant clusters don't write NetworkPolicy ad hoc, one app at a time, as an afterthought. The pattern Kubernetes' own docs bake in as the "Default policies" recipe is the one that shows up repeatedly in hardened production clusters: apply a default-deny-all policy (the exact podSelector: {} / policyTypes: [Ingress, Egress] spec above) to every tenant namespace as a baseline the moment the namespace is created — often via GitOps or an admission policy that refuses to let a namespace exist without one — and only then add narrow, explicit allow rules for each real traffic path as it's discovered: ingress-controller namespace → frontend Pods, frontend → backend, backend → database, backend → the cluster's DNS Service in kube-system. Every first rollout of default-deny to an existing namespace breaks something quietly on day one — DNS is the single most common casualty, because a bare default-deny-egress blocks CoreDNS lookups along with everything else. That's a reason to stage the rollout (apply, watch error rates and CNI-level flow logs, then tighten) — not a reason to skip default-deny and stay wide open instead.

Hands-on exercise

Objective

Prove, by testing it yourself, that a default-deny policy blocks everything and a single explicit allow rule opens exactly one path — not "roughly the right traffic," exactly the path you named.

Scenario

You have a Pod labeled app=web. You want only Pods labeled app=client to reach it — nothing else, including a third Pod that has no relationship to either label.

Environment assumptions

This exercise requires a CNI that enforces NetworkPolicy — Calico, Cilium, Antrea, Kube-router, Romana, or Weave Net are the providers Kubernetes' own tutorial lists as supporting it. It will not work as described on an unmodified kind or minikube cluster: kind's default CNI (kindnetd) and minikube's default CNI are both minimal implementations built for basic pod-to-pod connectivity, and minikube's own docs state it directly — "a vanilla minikube installation (minikube start) does not support any NetworkPolicies, since the default CNI, Kindnet, does not support Network Policies, by design." To fix this on minikube, start (or restart) with minikube start --cni calico. On kind, set networking.disableDefaultCNI: true in the cluster config and install Calico yourself afterward. Verify enforcement before you trust any result from this exercise — see Troubleshooting below.

Commands

kubectl create namespace netpol-lab

# the target Pod
kubectl run web --image=nginx:1.29 --labels=app=web -n netpol-lab
kubectl wait --for=condition=Ready pod/web -n netpol-lab --timeout=60s
WEB_IP=$(kubectl get pod web -n netpol-lab -o jsonpath='{.status.podIP}')

# baseline: confirm the client can already reach it (default-allow-all, no policy yet)
kubectl run client --image=busybox --labels=app=client -n netpol-lab --restart=Never --rm -it -- \
  wget --spider --timeout=1 http://$WEB_IP

# apply a default-deny-ingress policy to the whole namespace
cat <<'EOF' | kubectl apply -n netpol-lab -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes:
  - Ingress
EOF

# same test again — expect a timeout now
kubectl run client --image=busybox --labels=app=client -n netpol-lab --restart=Never --rm -it -- \
  wget --spider --timeout=1 http://$WEB_IP

# add the one allow rule: only app=client may reach app=web
cat <<'EOF' | kubectl apply -n netpol-lab -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-allow-from-client
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: client
EOF

# app=client should now succeed again
kubectl run client --image=busybox --labels=app=client -n netpol-lab --restart=Never --rm -it -- \
  wget --spider --timeout=1 http://$WEB_IP

# a pod WITHOUT the app=client label should still be blocked
kubectl run stranger --image=busybox --labels=app=stranger -n netpol-lab --restart=Never --rm -it -- \
  wget --spider --timeout=1 http://$WEB_IP

Expected result

Baseline wget succeeds ("remote file exists"). After default-deny-ingress, the identical command times out. After adding web-allow-from-client, the client-labeled Pod succeeds again, but stranger still times out — proving the rule is scoped to the label, not to "whatever was blocked a minute ago."

Verification

Run kubectl describe networkpolicy -n netpol-lab and confirm both policies list the Pods/rules you expect. If stranger unexpectedly succeeds, re-check its labels with kubectl get pod stranger -n netpol-lab --show-labels — a stray label matching app=client would explain it instantly, per this lesson's mental model.

Common failure

Every step "succeeds" — including the one right after default-deny-ingress that should have timed out. This is the signature of a non-enforcing CNI, not a wrong policy: the object exists in the API, kubectl get networkpolicy shows it, and the CNI silently ignores it.

Troubleshooting

Confirm which CNI is running with kubectl get pods -n kube-system -o wide — look for calico-node, cilium, antrea-agent, or similar. Seeing only kindnet Pods (or nothing NetworkPolicy-related at all) confirms enforcement isn't happening, and no error anywhere will tell you that directly — the docs are explicit that "creating a NetworkPolicy resource without a controller that implements it will have no effect."

Cleanup / rollback

kubectl delete namespace netpol-lab

Production lesson

This exact gap — a policy that exists, looks correct, and enforces nothing — is why "I applied the NetworkPolicy" is not evidence of anything on its own. The only real evidence is a blocked connection you expected to be blocked, and an allowed one you expected to be allowed, tested on the actual CNI your workload will run on.

Failure scenario

A realistic version of the exact gap the exercise above just demonstrated — except this time nobody caught it before it shipped.

  1. Mon 10:14 A platform engineer writes a "least privilege" NetworkPolicy set for the billing namespace: default-deny-all plus explicit allows for the two paths the team knows about (frontend → billing-api, billing-api → billing-db). Tests it on their local kind cluster, default config, no CNI swapped.
  2. Mon 10:31 All local tests pass — every allowed call succeeds, every call they try to block also "succeeds," but nobody notices, because the local cluster's default CNI never enforces NetworkPolicy in the first place. Green checkmarks, false confidence.
  3. Mon 14:02 PR merges. The exact same manifests deploy to the staging cluster, which runs Calico and genuinely enforces every policy.
  4. Mon 14:06 Alerts fire: billing-api Pods are Running and healthy, but requests are failing with DNS resolution errors — could not resolve host: billing-db.billing.svc.cluster.local.
  5. Mon 14:11 On-call checks the applied policies: default-deny-all selects every Pod in the namespace for both Ingress and Egress. The two explicit allows only cover the app-to-app paths — nobody wrote an egress rule for DNS, because the local test cluster never made that dependency visible.
  6. Mon 14:15 Root cause confirmed: billing-api can't even ask CoreDNS what IP billing-db has, let alone connect to it. This has nothing to do with the billing-db allow rule being wrong — it's correct. The Pod never gets that far.
  7. Mon 14:19 Fix applied: add an explicit egress-allow rule from every Pod in the namespace to kube-system's DNS Service on UDP/TCP port 53, using a namespaceSelector matched on the kubernetes.io/metadata.name: kube-system label.
  8. Mon 14:23 Verified: DNS resolves, billing-api reaches billing-db, error rate returns to zero.

Troubleshooting workflow

The general method, applied specifically to "traffic that should be blocked isn't, or traffic that should be allowed is blocked":

  1. Confirm the symptom precisely. Which direction, which two Pods, which port? "It doesn't work" isn't a symptom — kubectl exec into the source Pod and reproduce the exact failing call.
  2. Confirm the CNI enforces NetworkPolicy at all. kubectl get pods -n kube-system -o wide — if you don't recognize a NetworkPolicy-capable CNI (Calico, Cilium, Antrea, Kube-router, Romana, Weave Net) running, stop here: nothing else in this list matters until enforcement is confirmed.
  3. Define scope. Does this affect one Pod, every Pod with a label, or the whole namespace? kubectl get networkpolicy -n <ns> lists every policy in play — more than one can apply to the same Pod.
  4. Check recent changes. kubectl get events -n <ns> --sort-by=.lastTimestamp and check policy history — was a policy just added, or did a Deployment rollout change the Pod's labels?
  5. Inspect the actual selectors. kubectl describe networkpolicy <name> -n <ns> shows how Kubernetes parsed podSelector/namespaceSelector nesting — don't trust your read of the YAML indentation, trust this output.
  6. Check the labels on both Pods. kubectl get pod <name> -n <ns> --show-labels on source and destination. A typo, a missing label, or a label a rollout silently changed is the single most common root cause.
  7. Check policyTypes covers the direction you care about. A policy with only an egress block still isolates for Ingress too if policyTypes was left unset — Kubernetes defaults Ingress to "on" whenever policyTypes is omitted, regardless of which rules you actually wrote.
  8. Form a hypothesis and test one variable. Temporarily add a broader, throwaway allow rule (or a matching label) to isolate whether the selector, the direction, or the port is the mismatch — change one thing, not three.
  9. Apply the safest fix and verify from both sides. Remember a connection needs the source's egress AND the destination's ingress to agree — fixing only one side and declaring victory is a common half-fix. Re-run the exact failing call, not just kubectl get networkpolicy.
  10. Document the root cause and prevent recurrence. Write down which selector/direction/label was wrong, and if the miss was something like the DNS-egress gap, add it to the default-deny-all template itself so the next namespace doesn't repeat it.

Security note: treat default-deny-all as the baseline posture for anything multi-tenant or handling sensitive data — not an optional hardening step you get to later. The asymmetry matters: a missing allow rule breaks something loudly (a failed connection, an alert, a ticket); a missing NetworkPolicy entirely fails silently and forever, because default-allow never produces an error for the traffic it's letting through that shouldn't be. The more dangerous trap is the one this whole lesson has been building toward: a NetworkPolicy applied to a cluster whose CNI doesn't enforce it produces exactly zero errors, zero warnings, and a kubectl get networkpolicy output that looks identical to a cluster where it's fully working. That's a false sense of security, not a partial one — worse than having no policy, because no policy at least doesn't claim to be protecting you. It's also worth knowing NetworkPolicy's real limits, straight from the docs' own "what you can't do" list: there's no explicit deny (only additive allow rules on top of an implicit deny), no built-in cluster-wide default policy across every namespace (each namespace needs its own, unless your CNI adds a proprietary cluster-scoped policy CRD), no way to target a Service by name, and no built-in logging of which connections were blocked or allowed. Plan your audit trail and your default posture around those gaps, not against a version of NetworkPolicy that doesn't exist.

Common mistake: assuming a NetworkPolicy is enforced simply because kubectl apply succeeded and kubectl get networkpolicy shows it. The API server accepts and stores NetworkPolicy objects regardless of whether anything downstream implements them — validation happens against the schema, not against your cluster's actual networking capability. Always confirm which CNI is running and that it's on the supported list before trusting a policy's effect, especially in a fresh kind/minikube cluster you didn't build yourself.

Common mistake: writing namespaceSelector and podSelector as two separate list entries when you meant AND. It's an easy typo — one extra - and two spaces of indentation is the entire difference between "Pods labeled role=client inside namespaces labeled user=alice" (AND, one entry) and "any Pod labeled role=client anywhere, or any Pod at all inside a user=alice namespace" (OR, two entries) — and the second one is dramatically wider than most people intend. Always confirm the parsed result with kubectl describe networkpolicy, not a visual scan of the YAML.

Common mistake: applying a bare default-deny-egress (or default-deny-all) to a namespace without a matching DNS-allow rule. Every Pod in that namespace instantly loses the ability to resolve any DNS name, including your own Services' — this is a documented, expected side effect, not a bug, and it's the single most common "why did rolling out default-deny break everything" incident.

Knowledge check

Q1. With no NetworkPolicy anywhere in the cluster, what's the default Pod-to-Pod traffic behavior?

Fully open in both directions — every Pod is "non-isolated" for ingress and egress independently, so every Pod can reach every other Pod, any port, any namespace, until some policy selects it for a direction.

Q2. Two NetworkPolicies both select the same Pod for Ingress, each allowing a different source. Do they AND or OR?

OR. Network policies are additive — the connections allowed are the union of what every applicable policy allows. Policies never narrow each other, and order of evaluation never matters.

Q3. You write a NetworkPolicy with only an egress rule block and no policyTypes field at all. What direction(s) does the Pod actually get isolated for?

C. If policyTypes is left unset, Kubernetes always sets Ingress, and additionally sets Egress because egress rules are present. The Pod ends up isolated for a direction you never intended to touch.

Q4. One from entry lists namespaceSelector: {user: alice} and podSelector: {role: client} together, in the same entry. Which traffic does this allow?

A. Selectors in the same from entry AND together — this allows only Pods matching both conditions at once. (B and C each drop one half of the requirement; D describes what two separate entries would allow instead.)

Q5. You apply a bare default-deny-all-egress policy to a namespace and add no other rules. What's the first thing that typically breaks, and why?

DNS resolution. Lookups against CoreDNS are outbound (egress) traffic like anything else, so a bare default-deny-egress blocks them along with everything else — Pods can no longer resolve any name, including their own cluster's Service names, until you add an explicit egress-allow rule to kube-system's DNS Service.

NetworkPolicy falls under Services & Networking (20% of the CKA exam) — one of the highest-weighted domains on the exam, alongside Services, Ingress, and CoreDNS/Gateway API. Production challenge

Objective

Design a default-deny-all-plus-explicit-allow NetworkPolicy set for a real three-tier application, without being handed the finished YAML.

Scenario

A namespace called shop runs three tiers: tier=frontend (receives traffic from an ingress controller running in a separate ingress-nginx namespace, and needs to reach tier=backend on port 8080), tier=backend (only ever reachable from tier=frontend, and needs to reach tier=database on port 5432), and tier=database (only ever reachable from tier=backend, and initiates no outbound connections of its own). All three tiers need DNS. Your job: write the policy set. Nobody but frontend should ever be able to reach backend, and nobody but backend should ever be able to reach database — not even frontend, directly.

Environment assumptions

A cluster with a NetworkPolicy-enforcing CNI (see the Hands-on exercise above for how to check/enable this). Set up the scenario yourself first:

kubectl create namespace shop
kubectl create namespace ingress-nginx
kubectl label namespace ingress-nginx kubernetes.io/metadata.name=ingress-nginx --overwrite

kubectl run frontend --image=nginx:1.29 --labels=tier=frontend -n shop
kubectl run backend --image=nginx:1.29 --labels=tier=backend -n shop
kubectl run database --image=nginx:1.29 --labels=tier=database -n shop
kubectl run ingress-sim --image=busybox --labels=tier=ingress -n ingress-nginx --restart=Never -- sleep 3600

Commands

Write and apply your own NetworkPolicy manifests in the shop namespace. At minimum you'll need: one default-deny-all baseline, one allowing ingress-nginx → frontend, one allowing frontend → backend on 8080, one allowing backend → database on 5432, and a DNS-egress allow for all three tiers to kube-system. Decide for yourself whether that's one policy per tier or something more consolidated — there's more than one correct shape.

Expected result

An HTTP call from ingress-sim to frontend succeeds. A call from frontend to backend succeeds. A call from backend to database succeeds. A direct call from frontend to database — skipping backend — must fail. A call from database to anything outbound (other than DNS) must fail, since it initiates nothing.

Verification

# exec into a shell in the relevant pod and test with wget --spider --timeout=1 against
# the target's pod IP or in-namespace DNS name for each of the five checks above

Run all five checks, not just the ones you expect to pass — the frontend-to-database call failing is just as important a proof point as backend-to-database succeeding.

Common failure

Getting the happy path working and stopping there. A policy set that lets frontend reach database directly "because it was easier" defeats the entire point of tiering the application in the first place — verify the negative cases, not just the positive ones.

Troubleshooting

If DNS lookups fail for any tier, you've hit the same gap as this lesson's Failure scenario — add the kube-system egress-allow rule. If frontend can unexpectedly reach database, check for an overly broad namespaceSelector: {} or a default-deny that only covers Ingress and not Egress on the source side — remember both sides of a connection have to agree.

Cleanup / rollback

kubectl delete namespace shop
kubectl delete namespace ingress-nginx

Production lesson

This is what "least privilege" actually looks like as YAML, not as a slogan: every hop in the request path gets exactly one explicit allow rule, nothing gets a shortcut, and DNS is planned for from the start instead of discovered as an outage.

Recap
  • Default with no NetworkPolicy: every Pod is non-isolated for both ingress and egress, independently — fully open, the opposite of a firewall's default-deny.
  • A NetworkPolicy does nothing unless the CNI implements it — kind's and minikube's default CNIs don't; Calico, Cilium, Antrea, Kube-router, Romana, and Weave Net do.
  • Empty podSelector: {} or namespaceSelector: {} means "all" (all Pods / all namespaces), not "none" — both follow standard label-selector semantics.
  • Selectors in the same from/to entry AND together; selectors as separate list entries OR together. Multiple policies on the same Pod are always additive (OR), never AND.
  • A connection needs both the source Pod's egress policy and the destination Pod's ingress policy to agree — fixing only one side doesn't fix a blocked path.
  • Default-deny-all (empty podSelector, no matching rules, both directions in policyTypes) is the recommended baseline for multi-tenant namespaces — but it blocks DNS too, so plan the DNS-allow rule from day one.
