NetworkPolicy

Everything so far — Service, Ingress, RBAC — controls who can call an API or reach a stable address. NetworkPolicy is different: it's the only object in this course that controls raw Pod-to-Pod network traffic, at the packet level, inside the cluster.

Tied to your mission: you already think in GCP VPC firewall rules — default deny, explicit allow. Kubernetes Pod networking starts from the opposite default, and that gap is exactly where CKA exam questions and real production incidents live.

The default nobody expects

With zero NetworkPolicy objects in a cluster, every Pod can talk to every other Pod, on any port, in any namespace — no restriction at all. The official docs call this "non-isolated": "By default, a pod is non-isolated for egress; all outbound connections are allowed. ... By default, a pod is non-isolated for ingress; all inbound connections are allowed."

This is the reverse of a GCP VPC. A VPC firewall is default-deny — you write rules to open a path. A fresh Kubernetes cluster is default-allow — every Pod is flat-open to every other Pod until you write a NetworkPolicy to close paths. Walking into the CKA exam still thinking "firewall = deny by default" will cost you marks.

The catch: your CNI has to enforce it

A NetworkPolicy is just an API object — it does nothing by itself. Enforcement is done by the cluster's network plugin (CNI), and the plugin has to specifically implement the NetworkPolicy API. The docs are blunt about this: "Creating a NetworkPolicy resource without a controller that implements it will have no effect."

This is the same trap as Ingress needing an Ingress controller. You kubectl apply the NetworkPolicy, it's accepted, kubectl get networkpolicy shows it — and traffic keeps flowing exactly as before, with no error anywhere, because the CNI silently ignores it. On the exam, and in production, this is a real gotcha to check first when a NetworkPolicy "isn't working."

Where you run daily — GKE Autopilot — this is handled for you: Autopilot defaults to GKE Dataplane V2 (Cilium-based), which enforces NetworkPolicy out of the box. GKE Standard does not enforce it until you explicitly enable the add-on. Don't assume every cluster you'll ever touch (including exam clusters) behaves like your Autopilot one.

The three fields that make up a policy

podSelector — which Pods this policy applies to, in the same namespace as the NetworkPolicy. Same label-matching mechanism as Service and Deployment. An empty podSelector: {} means "all Pods in this namespace."

policyTypes — a list containing Ingress, Egress, or both. This declares which traffic direction(s) the policy governs for the selected Pods. If you write an ingress block but forget policyTypes: [Ingress], Kubernetes infers it for you — but don't rely on inference, write it explicitly so the policy says what it means.

ingress.from / egress.to — the allow-list for that direction. Each entry can be one of three selector types:

  • podSelector — Pods in the same namespace as the policy, matched by label
  • namespaceSelector — all Pods in namespaces matched by label
  • ipBlock — a CIDR range (for traffic outside the cluster, e.g. an external database)

Combining podSelector and namespaceSelector in the same list entry ANDs them ("this label, in that namespace"). Listing them as separate entries ORs them ("this label, OR that namespace"). This is a common exam trap — one YAML indent level changes AND into OR.

Once a policy touches a Pod, that direction flips to deny

A Pod is "isolated" for a direction the moment any NetworkPolicy selects it with that direction in policyTypes. From that point on, only what the applicable policy or policies explicitly allow gets through in that direction — everything else is dropped.

Multiple NetworkPolicies on the same Pod are additive — a union (OR), never an AND. If Policy A allows ingress from role: frontend and Policy B allows ingress from role: monitoring, the Pod accepts traffic from either. You cannot use a second policy to narrow what a first policy already allowed. Also remember: a connection needs both sides to agree — the source Pod's egress policy AND the destination Pod's ingress policy must both allow it.

Try it first — before reading on

Q1. With no NetworkPolicy objects anywhere in the cluster, what is the default Pod-to-Pod traffic behavior?

Fully open — every Pod can send to and receive from every other Pod, any port, any namespace. Pods are "non-isolated" for both ingress and egress by default.

Q2. What has to be true about the CNI for a NetworkPolicy to actually do anything?

The cluster's network plugin must implement the NetworkPolicy API. If it doesn't, the object applies successfully with no error, but enforces nothing — traffic flows exactly as before.

Q3. Two NetworkPolicies both select the same Pod for Ingress, each allowing a different source. Do they combine with AND (must satisfy both) or OR (either is enough)?

OR — additive/union. The Pod accepts anything allowed by either policy. Policies never narrow each other.

Now build it — in your terminal, not here

Write a NetworkPolicy by hand — no copy-paste. It needs to:

  • apply to the Pods from your Lesson 4 Deployment (match them by the label their Pod template carries, e.g. app: nginx — not by the Deployment's name, NetworkPolicy only ever selects Pods)
  • govern Ingress only — leave Egress out of policyTypes
  • allow ingress only from Pods carrying one specific label of your choosing (e.g. role: frontend-client) — pick a label, then use a podSelector inside ingress.from to match it
  • optionally restrict it further to a single port (the port your nginx container actually listens on)

Apply it, then test both sides: run a throwaway Pod without the allowed label and confirm it can no longer reach your Deployment's Pods, then run one with the label and confirm it can. Don't peek at the answer below until you've written something.

Reveal the reference answer

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: nginx-allow-frontend
spec:
  podSelector:
    matchLabels:
      app: nginx
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              role: frontend-client
      ports:
        - protocol: TCP
          port: 80

This assumes your Lesson 4 Deployment's Pods carry the label app: nginx and listen on port 80. If yours differ, the podSelector and port must match what you actually wrote — same rule as every selector so far: exact match, no fallback.

Primary source

Read (or at least skim) the official docs on this — it's the exact page you're allowed to search during the real exam: kubernetes.io/docs/concepts/services-networking/network-policies.

Recap
  • Default with no NetworkPolicy: fully open, every Pod reaches every Pod — opposite of a GCP VPC firewall's default-deny
  • NetworkPolicy does nothing unless the CNI implements it — no controller, no enforcement, no error either
  • podSelector = which Pods the policy applies to; policyTypes = which direction(s) it governs
  • ingress.from / egress.to use podSelector, namespaceSelector, or ipBlock — same entry ANDs them, separate entries OR them
  • Once any policy selects a Pod for a direction, that direction becomes default-deny except what policies allow — and multiple policies are additive (OR), never AND

Try solo: add a second NetworkPolicy that allows ingress to the same Pods from a different label, and confirm both sources work at once (proving the additive/OR behavior yourself, not just from the answer above). Don't reopen this file to check — bring what you observed back to your notes instead.
