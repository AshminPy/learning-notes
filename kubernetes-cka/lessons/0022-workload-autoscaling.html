Workload autoscaling

Why this matters

An HPA that's silently stuck is one of the most dangerous failure modes in this entire course, because nothing about it looks broken. Pods are Running. No CrashLoopBackOff, no failed probes, no red text anywhere. The only thing wrong is a number that quietly stopped updating — and that number happens to be the one thing supposed to save you when real traffic shows up. If metrics-server dies quietly at 6am and nothing alerts on it directly, your HPA is technically still "running": its control loop still fires every 15 seconds, it's just working from the last data it ever received. Then a real spike hits at 2pm, replica count never moves, and by the time anyone realizes the problem is autoscaling and not the application, you've eaten an incident that a 10-second kubectl top pods would have caught immediately.

Mental model: an HPA is a thermostat, not a temperature sensor — sharpen that one step further. A thermostat with a broken sensor doesn't detect a freezing room; it just keeps trusting the last reading it ever got, forever, with total confidence. Two things follow directly from this, and both are testable, not just poetic: first, an HPA can never fix a problem the metrics pipeline itself has — if metrics-server is down, the HPA doesn't estimate or guess, it just stops making new decisions and holds whatever replica count already existed. Second, every HPA decision lags real load by design, even when metrics are perfectly healthy — it only re-checks every 15 seconds, and its scale-down logic deliberately looks backward over several minutes before it trusts that a drop is real (the "why" is below). The HPA is exactly as good as the data feeding it, and never faster than its own reconcile loop. If you remember one sentence from this lesson, remember that one.

Creating and reading an HPA

kubectl autoscale deployment my-app --cpu-percent=50 --min=1 --max=10

Or the manifest form, which is what the exam usually expects you to write:

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50

scaleTargetRef is the only part that points at your Deployment — everything else describes the target and the bounds. This only ever changes replica count (horizontal) — it never changes a single Pod's CPU/memory requests. Resizing an individual Pod's own resources is a different, separate feature (Vertical Pod Autoscaler), not covered in this lesson.

Reading it:

kubectl get hpa
NAME     REFERENCE          TARGETS   MINPODS   MAXPODS   REPLICAS
my-app   Deployment/my-app  35%/50%   1         10        2

If TARGETS shows <unknown>/50% instead of a real number, the HPA has nothing to read from. That's the single most common HPA failure, and it looks nothing like an error — no red text, no restart count, just a number that quietly refuses to update. There are two distinct root causes, and you should rule out both before assuming which one you have:

  • metrics-server is missing or unhealthy (Lesson 23) — the whole cluster's metrics pipeline is down. kubectl top pods will also fail, for the same underlying reason, in every namespace.
  • The target Pods have no CPU (or memory) resource request set (Lesson 11). A Utilization-type target is a percentage of the request — with nothing to divide by, the percentage is undefined, and the docs are explicit that the autoscaler "will not take any action for that metric" when this happens. metrics-server can be completely healthy and you'll still see <unknown>.

Same symptom, two different failure domains — one is a cluster-wide infrastructure problem, the other is a one-Deployment YAML mistake. kubectl top pods tells you which one you have: if it returns real numbers for other workloads, metrics-server is fine, and the problem is the missing request on this specific Deployment.

Scale-up vs. scale-down: deliberately asymmetric

Kubernetes does not treat growing and shrinking replica count the same way — and once you know the actual default numbers, "why is it scaling down so slowly" stops being a mystery. This is the implicit behavior block applied automatically even if you never write one yourself, verified against the current docs:

behavior:
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
    - type: Pods
      value: 4
      periodSeconds: 15
    selectPolicy: Max
  scaleDown:
    stabilizationWindowSeconds: 300
    policies:
    - type: Percent
      value: 100
      periodSeconds: 15
  • Scale-up has no stabilization window (0 seconds) — the controller acts on the very first metric reading that says "scale up." It can add up to 100% of current replicas or 4 Pods, whichever is larger, every 15 seconds (selectPolicy: Max always takes the more aggressive of the two policies). This is deliberately fast: the cost of scaling up a little too eagerly is a few extra Pods for a few minutes; the cost of scaling up too slowly is dropped requests.
  • Scale-down has a 300-second (5-minute) stabilization window — and it isn't a simple delay timer. The controller keeps every desired-replica-count recommendation computed over the last 5 minutes and scales down to the highest (most conservative) of them, not the most recent one. This "rolling maximum" is what actually stops flapping — without it, a metric that dips for 20 seconds and recovers would trigger a scale-down and then an almost-immediate scale-up right after, tearing down a Pod only to reschedule a near-identical one moments later.

The asymmetry is the design, not an oversight: Kubernetes would rather run a few extra Pods for five minutes than tear down capacity on a metric blip and get caught understaffed if load comes right back.

Two more verified defaults worth knowing: the controller re-evaluates every HPA on a fixed sync period — --horizontal-pod-autoscaler-sync-period, 15 seconds by default — so "reacts immediately" never means sub-second; and it applies a default tolerance of 0.1 (10%), meaning if the desired replica count is within 10% of the current one, it does nothing at all, to avoid churn on statistical noise.

Metric sources: what an HPA can actually watch

CPU utilization is the default everyone learns first, but the HPA API supports four distinct metric source types, each backed by a different API and a different piece of infrastructure:

Metric typeBacking APIWhat it measures
Resourcemetrics.k8s.io (metrics-server)Per-Pod CPU or memory — a Utilization percentage of the request, or a raw value
Podscustom.metrics.k8s.ioA custom per-Pod metric with a raw value, e.g. requests-per-second per Pod
Objectcustom.metrics.k8s.ioA single metric describing another object in the cluster, e.g. requests queued on an Ingress
Externalexternal.metrics.k8s.ioA single metric from outside the cluster entirely, e.g. queue depth on a managed message queue

Pods, Object, and External all require a metrics adapter you install and operate yourself (Prometheus Adapter and KEDA are the two you'll most often run into) — metrics-server alone only ever serves Resource metrics. "Just use custom metrics" is a real, documented HPA capability, but it's infrastructure you now own, not a checkbox — the decision guide below treats it that way.

Production example

Production note: a real team running a user-facing checkout-api Deployment does not ship the tutorial defaults. A realistic HPA for that service looks like: minReplicas: 3 (never 1 — see the reliability note below), maxReplicas: 40 deliberately kept below what the node pool could technically schedule, a 60% CPU target with headroom for burst traffic before new Pods finish starting, and behavior.scaleDown.stabilizationWindowSeconds raised from the 300-second default to 600 (10 minutes) — because this specific team had a real incident where a 3-4 minute internal batch job periodically paused outbound calls, tripping a scale-down that reversed itself minutes later. Tuning the stabilization window was a one-line change once they had the graph proving the pattern; nobody guessed the number, they measured it first.

Hands-on exercise

Objective

Watch replica count actually change in response to real CPU load — not just read about it — using Kubernetes' own official HPA example workload.

Scenario

Deploy a small Apache/PHP app that deliberately burns CPU per request, put an HPA in front of it, generate real load from inside the cluster, and watch kubectl get hpa -w react.

Environment assumptions

A cluster with metrics-server installed and healthy — confirm with kubectl top nodes before starting. If that command errors, fix that first (Lesson 23); otherwise this exercise "fails" for a reason that has nothing to do with the HPA itself, which is exactly the trap this lesson is about.

Commands

# 1. Deploy the official example app (sets requests.cpu: 200m, limits.cpu: 500m)
kubectl apply -f https://k8s.io/examples/application/php-apache.yaml

# 2. Create the HPA: scale 1-10 replicas, target 50% CPU
kubectl autoscale deployment php-apache --cpu-percent=50 --min=1 --max=10

# 3. In one terminal, watch it live
kubectl get hpa php-apache -w

# 4. In a second terminal, generate load
kubectl run -i --tty load-generator --rm --image=busybox:1.28 --restart=Never -- \
  /bin/sh -c "while sleep 0.01; do wget -q -O- http://php-apache; done"

Expected result

Within the first minute, TARGETS climbs well past 50%. Within 1-3 minutes, REPLICAS starts climbing from 1 toward higher numbers as the scale-up policy (100%, or +4 Pods, per 15 seconds — whichever is more) kicks in.

Verification

Stop the load generator (Ctrl+C — --rm deletes the Pod automatically) and keep watching. TARGETS drops back toward 0% quickly, but REPLICAS should hold near its peak for close to 5 minutes before it starts dropping — that pause is the 300-second scale-down stabilization window you just read about, not a stuck HPA.

Common failure

TARGETS stays at <unknown> the whole time. That's not this exercise being broken — it's Lesson 23's failure mode, live: either metrics-server isn't actually healthy despite the earlier check, or (less likely here, since the example manifest sets requests explicitly) a resource request is missing somewhere.

Troubleshooting

kubectl top pods — if this also fails, it's metrics-server, not the HPA. kubectl describe hpa php-apache — check the Conditions section for ScalingActive: False, which states the exact failure reason in plain text instead of leaving you to guess.

Cleanup / rollback

kubectl delete hpa php-apache
kubectl delete deployment php-apache
kubectl delete service php-apache

Production lesson

Doing this once, and actually watching the 5-minute pause on scale-down happen in real time, is what turns "the HPA seems slow" from a red flag into a calibrated expectation during a real incident.

Failure scenario

A realistic incident — the actual failure is hours old before anyone notices, because nothing ever alerted on it directly.

  1. 06:14 metrics-server's Pod is OOMKilled during a routine node patch cycle and comes back in CrashLoopBackOff — its memory limit was sized for a smaller cluster months ago and never revisited. No alert exists on metrics-server itself, only on application-level symptoms, so nobody notices.
  2. 14:02 A marketing push drives traffic to checkout-api to roughly 5x normal. Latency alerts fire.
  3. 14:05 On-call runs kubectl get pods — every checkout-api Pod is Running, zero restarts, no failed probes. Nothing here looks broken.
  4. 14:09 Assuming an application bug, on-call reads checkout-api logs and manually restarts two Pods. Latency doesn't improve — restarting healthy Pods that are simply overloaded never helps.
  5. 14:18 On-call finally checks kubectl get hpa: TARGETS reads <unknown>/70%, and REPLICAS has been stuck at 4 (the configured minimum) since before the spike even started.
  6. 14:20 kubectl top pods returns error: Metrics API not available — the first hard evidence this was never an application problem.
  7. 14:22 kubectl get pods -n kube-system | grep metrics-server shows CrashLoopBackOff, restart count in the hundreds, running since 06:14.
  8. 14:25 kubectl describe pod on the metrics-server Pod shows OOMKilled as the last termination reason. Its memory limit is raised and reapplied.
  9. 14:28 metrics-server comes up Running and stable. kubectl get hpa shows a real TARGETS percentage again within about a minute.
  10. 14:34 Replicas climb from 4 to 19 over the next few minutes; latency recovers.

Total time to the real root cause: 24 minutes, roughly 16 of which were spent investigating the application — because every one of the on-call's first checks (Pod status, restarts, logs) looked completely healthy. kubectl top pods would have surfaced the real problem in under 10 seconds, at 14:05, if it had been the first check instead of the fifth.

Troubleshooting workflow

The general 10-step method, applied specifically to "my HPA isn't scaling":

  1. Confirm the symptom. kubectl get hpa <name> — is TARGETS a real number that just hasn't crossed your threshold yet, or is it stuck at <unknown>? Those are two completely different problems; don't diagnose from a stale mental picture of what it showed an hour ago.
  2. Define scope. kubectl get hpa -A — is every HPA in the cluster showing <unknown> (cluster-wide: metrics-server), or just this one (Deployment-specific: missing resource requests, or a wrong scaleTargetRef)?
  3. Check recent changes. kubectl get events --sort-by=.lastTimestamp -A — was metrics-server recently restarted or OOMKilled? Was the target Deployment recently edited (renamed, requests removed, replaced)?
  4. Inspect the right state. Three checks, in order: kubectl top pods (does the metrics pipeline work at all, independent of any HPA object); kubectl describe hpa <name> (read the Conditions section — AbleToScale, ScalingActive, ScalingLimited — and the Events at the bottom, which name the exact failure); kubectl get deployment <name> to confirm scaleTargetRef actually names a Deployment that exists, with the right kind and apiVersion — a typo here silently points the HPA at nothing.
  5. Form a hypothesis. Narrow to one of: metrics-server down, missing resource requests, wrong scaleTargetRef, or — genuinely healthy — already pinned at maxReplicas/minReplicas.
  6. Test one variable. kubectl get hpa <name> -o yaml and read .status.conditions directly: ScalingLimited: True with reason TooManyReplicas means you're not stuck — you're correctly capped at maxReplicas, and the real question becomes "is the ceiling too low," not "why won't it scale."
  7. Apply the safest fix. Restart or resource-fix metrics-server if it's unhealthy; add the missing resources.requests if that's the cause; correct scaleTargetRef if it's a typo. Don't raise maxReplicas as a reflex before confirming the cluster's nodes can actually schedule that many more Pods.
  8. Verify recovery. kubectl get hpa <name> -w — confirm TARGETS shows a real, updating number and REPLICAS moves in the direction the metric predicts, not just that the object "looks" healthy in one snapshot.
  9. Document the root cause. Write down which of the four categories it actually was — "metrics-server OOMKilled at 06:14, no alert existed on it" is a useful sentence; "HPA was broken, now it's fixed" is not.
  10. Prevent recurrence. Alert directly on metrics-server health (Pod restarts, kubectl top success), not only on downstream symptoms like latency — and alert on ScalingLimited: True persisting for a sustained period as an early warning that maxReplicas is now too low for real traffic.

Security & reliability considerations

Production note: minReplicas: 1 is a genuine availability risk for anything user-facing, and it's easy to land there by accident — minReplicas defaults to 1 if you omit it entirely. One replica means a single node failure, a single rolling update, or a single crash takes the service fully down while a replacement gets scheduled. For anything user-facing, set minReplicas to at least 2, and ideally 3 spread across nodes, so the service survives routine disruption, not just quiet periods.

Cost note: maxReplicas is a required field with no default — Kubernetes forces you to pick a number, but not a sane one. An overly generous ceiling turns a runaway load event — a retry storm from a buggy downstream client, a cache stampede, a genuine volumetric spike — into a real bill event, not just a performance one, once the HPA is free to keep adding Pods. Treat maxReplicas as a capacity-planning number tied to what your node pool and your budget can actually absorb, not a round number picked to "leave headroom."

Security note: an HPA has no concept of "is this legitimate traffic" — it reacts to whatever the configured metric says, full stop. If an attacker (or a misbehaving internal client) can drive up the metric an HPA watches — request volume, CPU load, queue depth — they can indirectly drive your replica count and your cloud spend, independent of whether the load was ever real demand. This isn't a credentials-and-access-control issue; it's a reason maxReplicas and upstream rate limiting (Lesson 8's Ingress, or a dedicated rate limiter) matter together — the HPA alone can't tell a flash sale from an attack.

Common mistakes

Common mistake: leaving minReplicas at its default of 1 for a user-facing Deployment because nobody explicitly typed a number. At that point it isn't a deliberate choice, it's an accident — and it's the exact setup that turns a routine node drain into a full outage instead of a non-event.

Common mistake: setting maxReplicas generously "to be safe," without checking node capacity or cost, then discovering during a genuine traffic anomaly or a retry-storm bug that the HPA did exactly what it was told and scaled far past what anyone expected. maxReplicas protects you from under-scaling; nothing protects you from an unreasonable maxReplicas except setting a reasonable one.

Common mistake: writing a Utilization-type CPU or memory target on a Deployment with no resources.requests set (Lesson 11), then spending an hour debugging "why is metrics-server broken" — metrics-server was never the problem, the percentage the HPA needed was undefined from the start.

Decision guide

Metric typeUse whenAvoid whenTrade-off
CPU (Resource)Load is genuinely compute-bound — a typical stateless API or web frontendCPU stays flat under real load (I/O-bound or memory-bound workloads)Simplest option, needs only metrics-server — but a poor signal if CPU isn't your real bottleneck
Memory (Resource)Working-set size genuinely tracks load, e.g. per-request caching that grows with trafficMost other workloads — memory often doesn't fall back down after a spike, which breaks scale-down and risks OOMKill before the HPA reactsSame metrics-server dependency as CPU, but a far less reliable signal in both directions
Custom / external (Pods, Object, External)A real business signal exists — queue depth, requests-per-second, active connections — that predicts load better than CPU canYou don't already run a metrics adapter (e.g. Prometheus Adapter, KEDA) — this is real infrastructure to operate, not a config flagThe most accurate scaling signal available, at the cost of owning another moving part in production

Default recommendation: start with CPU for stateless HTTP/worker workloads — it needs nothing beyond metrics-server and covers most real cases. Move to a custom or external metric only once you can point at a specific, measured mismatch between CPU and actual load. Don't reach for memory as your primary signal unless you've verified memory usage tracks load and genuinely falls back down once load drops.

Knowledge check

Q1. You create an HPA and traffic spikes hard, but kubectl get hpa shows <unknown>/50% and replica count never moves. What's actually broken?

Nothing about the HPA object itself — it's waiting on metrics it never receives. Check kubectl top pods first: if it fails cluster-wide, metrics-server is missing or unhealthy; if it works fine elsewhere, the target Deployment is likely missing a CPU resource request.

Q2. Write an HPA manifest by hand for a Deployment called web, targeting 70% CPU, min 2 / max 6 replicas. Try it before revealing.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

Q3. By default, how long does the HPA controller wait before scaling down, once metrics indicate fewer replicas are needed?

C. The default scaleDown.stabilizationWindowSeconds is 300. Scale-up, by contrast, has a stabilization window of 0 — it reacts immediately. (15 seconds is the sync period, how often the controller checks at all, not how long it waits before acting. 600 seconds is a value some teams tune to deliberately, not the shipped default.)

Q4. Which of these is not one of the four real HPA metric source types?

D. The real four types are Resource, Pods, Object, and External. "Volume" isn't an HPA metric type at all — disk usage isn't something the HPA API watches.

Q5. If you omit minReplicas entirely from an HPA spec, what value does it default to?

B. minReplicas defaults to 1 if omitted — which is exactly why it's easy to accidentally ship a user-facing service with no redundancy at all. (0 is only reachable with an explicit alpha feature gate plus an Object/External metric; it's never the default.)

Production challenge

Objective

Diagnose a "the HPA is maxed out and we're still overloaded" incident using only what this lesson covered — decide what to check, and in what order, before touching any config.

Scenario

Your team's api-gateway Deployment has an HPA with minReplicas: 4, maxReplicas: 30. During a real incident, kubectl get hpa shows REPLICAS: 30 (fully maxed) and TARGETS: 145%/60% — CPU is still far above target, but the HPA cannot add a single Pod more. Latency is degraded and getting worse.

Environment assumptions

This is a diagnostic exercise, not a hands-on cluster task — reason through it the way you would a CKA scenario question, or a real page at 2am. Write down your own answer before reading further.

Commands

# Confirm the HPA really is capped by maxReplicas, not something else
kubectl get hpa api-gateway -o yaml   # check .status.conditions for ScalingLimited: True

# Confirm whether the cluster even has room for more Pods than 30
kubectl get nodes
kubectl describe nodes | grep -A5 "Allocated resources"
kubectl get pods -o wide | grep api-gateway | wc -l   # cross-check against REPLICAS

Expected result

ScalingLimited: True, reason TooManyReplicas — confirming the HPA is doing exactly what it's configured to do: refusing to exceed maxReplicas: 30 even though the metric says it needs more. That's not a bug. The real question is whether 30 was ever the right ceiling, and whether the nodes could even hold more Pods if you raised it.

Verification

Two independent findings decide the fix, not a guess: (1) is maxReplicas genuinely too conservative for this traffic level, and (2) does the node pool have allocatable CPU/memory left to schedule beyond 30 Pods at all. If the nodes are already near full allocation, raising maxReplicas alone changes nothing — the new Pods would just sit Pending.

Common failure

Reflexively bumping maxReplicas to some large number without checking node capacity first. If the cluster can't schedule the extra Pods, you've edited a number and fixed nothing — the incident continues, now with a confusing "Pods stuck Pending" symptom layered on top of the original one.

Troubleshooting

This is exactly where the Horizontal Pod Autoscaler and the separate Cluster Autoscaler intersect, and the boundary is worth being precise about: the HPA only ever changes a Deployment's replica count — it has no concept of nodes at all. If your cluster runs a Cluster Autoscaler, that's the component watching for Pods stuck Pending due to insufficient node resources, and it adds nodes in response — a genuinely separate control loop, reacting to a different signal (unschedulable Pods, not CPU/memory percentages) on a different timescale. Raising maxReplicas without a Cluster Autoscaler — or without spare headroom in a fixed node pool — just trades one bottleneck for a more confusing one.

Cleanup / rollback

Not applicable — this is a diagnostic exercise; no cluster changes were made.

Production lesson

"The HPA is maxed out" is never the end of an investigation by itself — it's a pointer to one of two follow-up questions: is the ceiling wrong, or is the cluster itself out of room. Confusing the two wastes exactly the kind of time Lessons 15 and 16's troubleshooting method exists to prevent.

Recap
  • An HPA only adjusts replica count — it reads metrics, it never produces them, and it never touches a single Pod's own CPU/memory requests.
  • TARGETS showing <unknown> has two distinct causes: metrics-server missing/unhealthy, or the target Pods have no resource request set for a Utilization-type metric. kubectl top pods tells you which.
  • Scale-up and scale-down are deliberately asymmetric: scale-up has a 0-second stabilization window and can add 100% of replicas or 4 Pods (whichever is more) every 15 seconds; scale-down waits 300 seconds and scales to the highest recommendation seen in that window, to prevent flapping.
  • HPA metrics come in four types — Resource, Pods, Object, External — but only Resource (CPU/memory via metrics-server) works with no extra infrastructure to run.
  • minReplicas defaults to 1 if you omit it — a real availability risk for anything user-facing. maxReplicas is required with no default; an unbounded one is a cost risk, not just a safety net.
  • An HPA maxed out at maxReplicas is working correctly, not broken — check node capacity and the separate Cluster Autoscaler before assuming you just need a bigger number.
