Highly-available control plane

Lesson 13 built a cluster with one control-plane node. If that node dies, existing Pods keep running (kubelets don't need the API server minute to minute), but nothing can be scheduled, healed, or modified until it's back. A highly-available (HA) control plane runs multiple control-plane nodes so no single machine is that critical.

Mental model: kube-apiserver is stateless — run three copies behind a load balancer and any of them answers any request identically. kube-scheduler and kube-controller-manager are the opposite: two copies deciding independently could schedule the same Pod twice, so exactly one is elected leader; the rest sit idle, watching. That predicts why losing the leader isn't an outage: a standby is already running, just waiting for the Lease.

Where this fits

Cluster
  └ control plane × 3 (not 1, per Lesson 13)
      ├ kube-apiserver × 3   — all ACTIVE simultaneously, behind a load balancer
      ├ kube-scheduler × 3   — 1 LEADER (Lease), 2 idle standbys
      └ kube-controller-manager × 3 — same pattern

Setting it up with kubeadm

kubeadm init --control-plane-endpoint "LB_DNS_NAME:6443" --upload-certs

--control-plane-endpoint points every node at the load balancer, not one specific node's IP — that's what makes the other control-plane nodes replaceable later. --upload-certs stores the cluster's certs in a Secret so the next control-plane node fetches them automatically. The command prints two kubeadm join variants: a plain one for workers, one with --control-plane --certificate-key <key> for adding another control-plane node.

etcd: stacked vs. external

kubeadm defaults to stacked etcd — each control-plane node runs its own etcd member locally. Simpler, and what the exam expects unless told otherwise. External etcd runs etcd as a separate cluster, used when etcd needs to scale or fail independently of the control plane.

Try it

Q1. Why does kube-apiserver not need leader election, but kube-scheduler does?

kube-apiserver is stateless — any number of copies can serve requests at once with no conflict. kube-scheduler makes decisions; two copies deciding independently could double-schedule a Pod, so only one may act at a time.

Now, before revealing: in a 3-control-plane-node cluster, the node holding the kube-scheduler Lease goes down. What happens to scheduling?

Reveal the answer

Briefly nothing new gets scheduled, then one of the two remaining kube-scheduler instances (already running, just idle) acquires the Lease and becomes leader. No manual action needed.

A controlled failure

kubectl get lease -n kube-system kube-scheduler -o jsonpath='{.spec.holderIdentity}'

Predict first: on a single-control-plane cluster (kind/minikube), does this Lease still exist? Observe: yes — leader election runs even with one instance, it just always wins uncontested. The mechanism doesn't know or care how many replicas exist; that's exactly why adding a second one later needs zero application-level changes.

Production best practices

Production note: production clusters run an odd number of control-plane nodes (3 or 5) — etcd's Raft consensus needs a majority to keep writing, and an odd count avoids a tie during a network split.

Exam & interview notes

Core to Cluster Architecture, Installation & Configuration (25%).

Interview Q: "Why run an odd number of control-plane nodes, not an even one?" A: etcd needs a strict majority to keep accepting writes; an even count (e.g. 4) can split into two equal halves during a network partition, with neither having a majority — an odd count always has a decisive majority side.

Recap
  • --control-plane-endpoint points at a load balancer, not one node — that's what makes control-plane nodes replaceable.
  • kubeadm defaults to stacked etcd (one member per control-plane node).
  • API servers are all active at once; scheduler and controller-manager elect one leader via a Lease object.
