Highly-available control plane

Why this matters

Lesson 13 built a cluster with exactly one control-plane node. That's the most common shape for a self-managed cluster outside of production, and it's also one of the most common real outage causes: the node running kube-apiserver reboots for a kernel patch, a disk fills up, someone runs kubectl drain against it by mistake — and for as long as it's down, nothing can be scheduled, healed, or changed, even though every existing Pod keeps running just fine (kubelets don't need the API server minute to minute). A highly-available (HA) control plane exists to remove that single point of failure by running multiple control-plane nodes behind a load balancer.

But HA isn't something you get automatically just by having three control-plane nodes. It's entirely possible to build a cluster that looks highly available — three API servers, three etcd members — while a single point of failure is still hiding in it. If --control-plane-endpoint (or any kubelet's server address, or any kubeconfig) is pointed at one specific control-plane node's IP instead of the load balancer's DNS name, every client in the cluster is quietly depending on that one machine. The mistake is invisible on day one — it works perfectly. It only surfaces the day that one node is rebooted, drained, or decommissioned, and by then it can take the whole cluster down at once, exactly like a single-node setup would.

Mental model: kube-apiserver is a bank with three teller windows, all reading and writing the same ledger (etcd) — walk up to any window and get the same answer, and the bank can close any one window for maintenance without the queue even noticing. kube-scheduler and kube-controller-manager are the opposite: three on-call engineers sharing one pager, under a strict rule that only whoever is currently holding the pager may act — the other two just watch. This model makes a specific, testable prediction: you can restart or replace any kube-apiserver instance whenever you like, with zero coordination and zero gap, because none of them is "more in charge" than another. But restarting the CURRENT scheduler or controller-manager leader does cause a real, bounded gap — not zero — while a standby notices the pager went quiet and picks it up. If your idea of "HA" says every component fails over instantly with no gap at all, that's true for the apiserver and false for the other two — and this lesson tells you how long that gap actually is, and how to check it yourself.

Setting it up with kubeadm

kubeadm init --control-plane-endpoint "LB_DNS_NAME:6443" --upload-certs

--control-plane-endpoint points every node at the load balancer, not at one specific control-plane node's IP — this is what makes the other control-plane nodes replaceable later. kubeadm's own docs are direct about this: the load balancer's real address must always match whatever you set here, or joins and certificate validation start failing in confusing ways. --upload-certs stores the cluster's certs in a Secret so the next control-plane node can fetch them automatically — but only for a limited window. kubeadm treats this as sensitive enough to delete the uploaded certs automatically after two hours as a safeguard, and if you need to add another control-plane node after that window, you re-run kubeadm init phase upload-certs to reload them.

The command prints two different kubeadm join commands:

  • A plain one, for worker nodes.
  • One with --control-plane --certificate-key <key>, for adding another control-plane node.

The load balancer itself isn't a Kubernetes object — it's infrastructure you provide. For a cloud environment, the docs recommend a TCP forwarding load balancer whose health check is a plain TCP probe against port 6443 (the apiserver's port), and specifically advise against pointing --control-plane-endpoint at a bare IP address in the cloud — use the load balancer's DNS name instead. Outside the cloud, a software load balancer (the documented pattern pairs keepalived with HAProxy) plays the same role. Either way, the load balancer's only job is: know about every healthy control-plane node, and stop sending traffic to one that stops answering on 6443.

etcd: stacked vs. external

kubeadm defaults to stacked etcd — each control-plane node runs its own etcd member locally, alongside its API server. Simpler to operate, and what the exam expects unless told otherwise. External etcd runs etcd as a separate cluster the API servers all connect to — more moving parts, used when etcd needs to scale or fail independently of the control plane. The docs describe the stacked topology's real risk plainly: losing one node in that setup costs you an etcd member and a control-plane instance at the same moment — a coupled failure, not two independent ones. The Decision guide further down formalizes when each is the right call.

Who's actually in charge right now

Every kube-apiserver is active simultaneously. kube-scheduler and kube-controller-manager use a Lease object to elect one leader each — check who's holding it:

kubectl get lease -n kube-system kube-scheduler -o jsonpath='{.spec.holderIdentity}'
kubectl get lease -n kube-system kube-controller-manager -o jsonpath='{.spec.holderIdentity}'

What actually happens during a handover is governed by three flags both components ship with, each with a documented default: --leader-elect-lease-duration (15s), --leader-elect-renew-deadline (10s), and --leader-elect-retry-period (2s). In plain terms: the current leader must successfully renew its Lease within 10 seconds of its last renewal, retrying every 2 seconds if a renewal attempt fails. A standby doesn't get pushed a signal that the leader is gone — it watches the Lease's renewTime, and once 15 seconds have passed since the last observed renewal, it's allowed to force-acquire the Lease and become the new leader. So the honest answer to "is scheduling actually paused during handover?" is: yes, briefly. New Pods that need a placement decision wait for a new leader to acquire the Lease — bounded by that ~15-second window on kubeadm's defaults, not instant and not indefinite. Pods that are already scheduled and running are completely unaffected; the gap only touches new scheduling decisions and new reconciliation actions.

The Lease object itself carries evidence of this history: .spec.leaseTransitions counts how many times leadership has changed hands, and .spec.renewTime / .spec.acquireTime tell you how fresh the current leadership claim is. You'll use these in the exercise below.

Production example

Production note: the load balancer in front of your control plane needs to sit outside the control plane's own failure domain, or you've just relocated the single point of failure instead of removing it. A team running self-managed kubeadm on three bare-metal nodes in one rack doesn't put HAProxy on one of those same three nodes with no redundancy of its own — that just moves the SPOF from "one control-plane node" to "one load-balancer VM." The two realistic patterns: in a cloud environment, use the provider's own managed load balancer (an AWS NLB, a GCP TCP load balancer) — it's already redundant across zones and isn't running on any machine you also count as a control-plane node; on bare metal, run the software load balancer on at least two dedicated nodes with a floating VIP between them, separate from the control-plane machines. Either way, the test is simple: if the load balancer has a single instance with no failover of its own, ask what happens to every kubelet and every kubectl config in the cluster the day that one VM dies. The answer should never be "the cluster loses its control plane" — that's the exact failure this whole lesson exists to prevent.

Hands-on exercise

Objective

Find out, on a real cluster, exactly which node is currently acting as leader for kube-scheduler and for kube-controller-manager — and reason about what happens if that node is taken out of service.

Scenario

Before you trust "one of the standbys just takes over" in an actual incident, look at the Lease objects yourself and know what a healthy one looks like.

Environment assumptions

Ideally a real multi-control-plane kubeadm cluster (3 control-plane nodes). Honest constraint: most learners won't have one handy — kind and minikube both default to a single control-plane node, and standing up 3 real (or 3 VM) control-plane nodes just for this exercise is a meaningful chunk of infrastructure. If you don't have one, treat this as a thought exercise against your single-node dev cluster instead — the commands are identical, you'll just always see the same holder, since there's only one candidate.

Commands

kubectl get lease -n kube-system kube-scheduler -o yaml
kubectl get lease -n kube-system kube-controller-manager -o yaml
kubectl get lease -n kube-system kube-scheduler -o jsonpath='{.spec.holderIdentity}{"\n"}'
kubectl get lease -n kube-system kube-controller-manager -o jsonpath='{.spec.holderIdentity}{"\n"}'

Expected result

Each -o yaml shows a spec.holderIdentity (a string like node-1_<random-id>), a recent renewTime (within the last few seconds), and a leaseTransitions count. On a healthy, stable cluster that's been running a while, leaseTransitions is usually small — it only increments on an actual handover.

Verification

Run the two jsonpath commands a few seconds apart. holderIdentity should stay identical between runs if nothing has failed over — that stability, not just a non-empty answer, is what proves the current leader is healthy and still renewing.

Common failure

Assuming a non-empty holderIdentity means "everything is fine." A stale renewTime (well over 15 seconds old) with an unchanged holderIdentity can also mean the leader is stuck and hasn't been forcibly replaced yet — non-empty isn't the same as healthy.

Troubleshooting

If either command 404s, you're not looking at a kubeadm-managed control plane with these components exposed the normal way (a managed cluster like GKE Autopilot hides this layer) — confirm with kubectl get pods -n kube-system | grep -E "scheduler|controller-manager" first.

Cleanup / rollback

Read-only exercise — nothing to clean up.

Production lesson

Now reason it through: if node-1 is the holder for both Leases and you run kubectl cordon node-1 && kubectl drain node-1 --ignore-daemonsets, its scheduler and controller-manager static Pods get evicted along with everything else on that node. Both Leases go stale within the ~15-second window from the Core concepts section above, and standbys on the other two nodes take over — not necessarily the same node for both. That's the exact behavior "HA" is buying you. If you only have one control-plane node, this same drain takes your whole control plane down — which is precisely why a production control plane is never just one node.

Failure scenario

A realistic incident, built from the exact mistake named in "Why this matters" — a "3-node HA cluster" with a hidden single point of failure.

  1. Day 1, 09:15 A platform engineer bootstraps a new 3-node control-plane cluster. In a hurry, they run kubeadm init --control-plane-endpoint "10.0.1.11:6443" --upload-certs — 10.0.1.11 is node-1's own IP, not a load balancer's DNS name, because the load balancer hadn't been provisioned yet and "we'll fix it later."
  2. Day 1, 09:40 The other two control-plane nodes join successfully with --control-plane --certificate-key. Every worker node's kubelet joins pointing at 10.0.1.11:6443 too, since that's the endpoint kubeadm printed. The cluster works. Nobody circles back to "fix it later."
  3. Month 4, 11:02 node-1 is scheduled for decommissioning as part of a routine hardware refresh — it's just one of three control-plane nodes, so this looks routine. It's cordoned, drained, and powered off.
  4. Month 4, 11:03 Every kubelet in the cluster — on every worker node, and on the two remaining control-plane nodes — loses contact with the API server at the same moment. kubectl from any workstation configured against 10.0.1.11:6443 times out too. node-2 and node-3's own kube-apiserver static Pods are still running and healthy; nothing is actually wrong with the control plane itself.
  5. Month 4, 11:07 On-call checks node-2 directly: crictl ps shows kube-apiserver running. curl -k https://127.0.0.1:6443/healthz from node-2 returns ok. The individual API servers were never the problem.
  6. Month 4, 11:12 Root cause identified: --control-plane-endpoint was set to node-1's IP at cluster creation, not a load balancer. Every client in the cluster — kubelets, other control-plane nodes, kubeconfig files — had that one IP baked into its config. Decommissioning node-1 removed the only address anything was actually configured to talk to.
  7. Month 4, 11:20 Immediate fix: power node-1 back on to restore service while a real fix is planned. There's no fast way to repoint every kubelet's server address and every dependent config cluster-wide.
  8. Month 4, 15:00 Real fix scheduled as planned, disruptive maintenance: stand up an actual load balancer, then migrate every node's configuration to point at it — effectively redoing the HA setup that should have existed from day one.

Troubleshooting workflow

The general method, applied to: "nothing new is being scheduled or reconciled, but Pods that were already running are fine."

  1. Confirm the symptom. Try something that requires the API server and a controller to actually act — kubectl create deployment probe --image=nginx:1.29 --replicas=1 — and watch whether it gets scheduled at all, versus sitting in Pending forever.
  2. Define scope. Is the API server reachable at all (kubectl get nodes works, full stop), or is it specifically scheduling/reconciling that's stuck while reads work fine? Check the apiserver first, since it's stateless and should always answer — if kubectl itself is timing out, this isn't a leader-election problem, it's a reachability or load-balancer problem (see the Failure scenario above).
  3. Check recent changes. kubectl get events -n kube-system --sort-by=.lastTimestamp — was a control-plane node just drained, rebooted, or upgraded? Cross-check against any recent maintenance window.
  4. Inspect the right state — the Lease holders specifically. This is the concept this lesson is built on: kubectl get lease -n kube-system kube-scheduler -o yaml and the same for kube-controller-manager. Look at holderIdentity (who claims to be leader) and renewTime (how fresh that claim is).
  5. Form a hypothesis. For example: "the node holding the kube-scheduler Lease was just drained, and no standby has taken over — which shouldn't be possible if the standbys are healthy."
  6. Test one variable. Check whether standby instances are actually running: kubectl get pods -n kube-system -o wide | grep kube-scheduler across all control-plane nodes. If only one kube-scheduler Pod exists cluster-wide, there's no standby to take over — that's a static-Pod-manifest problem, not a Lease problem.
  7. Apply the safest fix. If a standby exists but isn't renewing, check its logs (kubectl logs -n kube-system kube-scheduler-<node>) for connectivity errors to the API server — often the same root cause as the Failure scenario above (still pointed at a decommissioned endpoint). Don't manually delete the Lease as a first move; that forces an election but doesn't fix why the previous leader stalled.
  8. Verify recovery. Re-run the probe Deployment from step 1 and confirm it actually gets scheduled and reaches Running — a fresh holderIdentity alone isn't proof the underlying cause is fixed.
  9. Document the root cause. Write down exactly which component stalled, on which node, and why — "scheduler leader lost API server connectivity because it was still configured against a decommissioned node's IP" is a very different root cause from "scheduler crashed," and points to a different fix.
  10. Prevent recurrence. If the root cause traces back to a hardcoded node IP anywhere (a kubelet, a kubeconfig, a manifest), that's the Common mistakes section below — fix the endpoint, not just the symptom.

Security & reliability considerations

Reliability note: reliability is this entire lesson's subject, not a footnote, so state it plainly. In a 1-node control plane, losing that one node is a 100% outage of the cluster's ability to schedule, heal, or change anything. In a healthy 3-node stacked control plane, losing one node cleanly (not the endpoint-pointed-at-one-node mistake above) costs you exactly one API server instance out of three and, briefly, a Lease handover for whichever of the two elected components it happened to be leading — existing workloads and the remaining two-thirds of the control plane are unaffected. That's the actual, measurable blast-radius reduction HA buys you.

Security note: --upload-certs is security-adjacent, not just an operational convenience — it temporarily stores the cluster's CA and other sensitive certificates in a Secret in kube-system so a joining control-plane node can fetch them. kubeadm treats this as sensitive enough to auto-delete it after two hours, and expects you to explicitly reload it (kubeadm init phase upload-certs) if you need to add a control-plane node after that window — it's not a "run once, valid forever" credential drop. Re-uploading certs well before you actually need them, out of habit, just extends the window that cluster secrets sit in that Secret for no operational benefit.

Common mistakes

Common mistake: setting --control-plane-endpoint (or any kubelet/kubeconfig server address) to one specific control-plane node's IP instead of the load balancer's DNS name. It works perfectly on day one — that's exactly what makes it dangerous. The failure only shows up later, when that specific node is rebooted, drained, or decommissioned, and by then the person who set it up may not even be on the team anymore.

Common mistake: running an even number of control-plane nodes (2 or 4) instead of an odd number (3 or 5). kubeadm's docs give the reasoning directly: an odd count helps leader selection survive a machine or zone failure without a tie, and for an external etcd cluster, an odd member count is a documented requirement for optimal voting quorum. A 4-node control plane doesn't buy you anything a healthy 3-node one doesn't — it just adds a fourth machine that still only splits into a majority/minority the same way 3 does, at extra cost.

Common mistake: treating the load balancer in front of the control plane as an afterthought — a single, unmonitored VM with no failover of its own. See the Production example above: this doesn't add HA, it just moves the single point of failure one hop over.

Knowledge check

Q1. In a 3-control-plane-node cluster, the node currently holding the kube-scheduler Lease goes down. What happens to scheduling?

Briefly, nothing new gets scheduled. A standby doesn't get an instant signal — it waits until the Lease's renewTime is older than the lease duration (15s by default) before force-acquiring it. After that, one of the two remaining kube-scheduler instances (already running, just idle) becomes the new leader. No manual action needed — that's the point of running more than one.

Q2. Why does kube-apiserver not need leader election, but kube-scheduler does?

kube-apiserver is stateless — it just reads/writes etcd, so any number of copies can serve requests at once with no conflict. kube-scheduler makes decisions (which node gets this Pod) — two copies deciding independently could schedule the same Pod twice, so only one may act at a time.

Q3. Your cluster has 3 control-plane nodes. Which single kubeadm setting, if pointed at the wrong thing, can make one of those three a hidden single point of failure even though the other two exist?

--control-plane-endpoint. If it's set to one node's IP instead of a load balancer's DNS name, every kubelet and kubeconfig ends up depending on that one machine, no matter how many control-plane nodes actually exist.

Q4. Why does kubeadm's documentation recommend an odd number of control-plane nodes rather than an even number?

A. An odd number of control-plane nodes helps leader/quorum-style selection survive a machine or zone failure without a tie, and for external etcd, an odd member count is a documented requirement for optimal voting quorum. B, C, and D aren't documented behaviors — cost, snapshot speed, and connection handling aren't affected by node parity.

Production challenge

Objective

Given only a kubectl get lease observation, reason through whether it indicates a real problem — without being told the answer first.

Scenario

You're doing a routine health check on a 3-control-plane-node cluster. kubectl get lease -n kube-system shows that node-2 has held both the kube-scheduler and kube-controller-manager Leases continuously for the last 40 days — the cluster's entire uptime since its last full restart. leaseTransitions is 0 for both.

Environment assumptions

No cluster required for this one — it's a reasoning exercise. If you do have a long-running multi-control-plane cluster available, run the real commands below and compare against your own numbers.

Commands

kubectl get lease -n kube-system kube-scheduler -o yaml
kubectl get lease -n kube-system kube-controller-manager -o yaml
kubectl get pods -n kube-system -o wide | grep -E "kube-scheduler|kube-controller-manager"

Expected result

Work out your own answer before reading on: is one node holding both Leases for 40 days straight, with zero transitions, a problem by itself?

Verification

No — by itself, this is exactly what a healthy, stable cluster looks like. Nothing in the leader-election mechanism forces periodic handovers; a leader keeps the Lease for as long as it keeps successfully renewing it, which a healthy node-2 will do indefinitely. leaseTransitions: 0 means there has never been a failover, which is good news, not a warning sign — as long as the standby scheduler and controller-manager Pods on node-1 and node-3 are also confirmed Running and healthy (that's what the third command checks). The real risk isn't "one node has been leader too long" — it's "are the other two nodes' standbys actually capable of taking over if node-2 fails right now," which you can only confirm by checking they're running, not by looking at the Lease alone.

Common failure

Concluding "this looks unbalanced, let's force a failover to spread the load" by deleting the Lease or restarting node-2's components on a schedule. There's no load-balancing reason to rotate leadership — kube-scheduler and kube-controller-manager don't share work between leader and standbys the way a stateless service would; only one is ever doing anything. Forcing rotation adds a real, if brief, scheduling gap for zero benefit.

Troubleshooting

The one pattern that would be worth investigating: leaseTransitions climbing steadily — many handovers in a short time suggests the current leader keeps failing to renew before the 10-second renew deadline, which points to real instability (resource pressure, network flakiness to that node, or a crash-looping Pod) worth root-causing, not a cosmetic quirk.

Cleanup / rollback

Nothing to clean up — this challenge is observational.

Production lesson

Long, stable leadership on one node is the expected, healthy shape of leader election, not evidence against it. The habit to build is checking whether the standbys are healthy, not whether the current leader has "been in charge too long."

Recap
  • --control-plane-endpoint must point at a load balancer, never at one control-plane node's IP — that's the one setting that makes control-plane nodes actually replaceable, and getting it wrong silently defeats HA until the day that node disappears.
  • kube-apiserver is stateless and active on every instance at once; kube-scheduler and kube-controller-manager elect one leader each via a Lease, governed by documented 15s/10s/2s lease-duration/renew-deadline/retry-period defaults — a leader failing produces a real, bounded gap in new scheduling and reconciliation, not zero and not indefinite.
  • kubeadm defaults to stacked etcd (simpler, but couples an etcd member's failure to a control-plane instance's failure); external etcd trades roughly double the hosts for better failure isolation.
  • Use an odd number of control-plane nodes (3, not 2 or 4) — that's what the docs specify for clean leader selection and etcd quorum.
  • --upload-certs certs auto-delete after two hours as a safeguard — reload them with kubeadm init phase upload-certs if you need to add a control-plane node later.
