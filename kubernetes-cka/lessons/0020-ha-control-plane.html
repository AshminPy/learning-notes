Highly-available control plane

Lesson 13 built a cluster with one control-plane node. If that node dies, the cluster can't be changed — existing Pods keep running (kubelets don't need the API server minute to minute), but nothing can be scheduled, healed, or modified until it's back. A highly-available (HA) control plane runs multiple control-plane nodes so no single machine is that critical.

Simple example: kube-apiserver is stateless — run three copies behind a load balancer and any of them can answer any request, same answer either way. kube-scheduler and kube-controller-manager are the opposite — running two copies acting at once would double-schedule Pods, so exactly one is elected leader at a time; the rest sit idle, watching.

Setting it up with kubeadm

kubeadm init --control-plane-endpoint "LB_DNS_NAME:6443" --upload-certs

--control-plane-endpoint points every node at the load balancer, not at one specific control-plane node's IP — this is what makes the other control-plane nodes replaceable later. --upload-certs stores the cluster's certs in a Secret so the next control-plane node can fetch them automatically.

The command prints two different kubeadm join commands:

  • A plain one, for worker nodes.
  • One with --control-plane --certificate-key <key>, for adding another control-plane node.

etcd: stacked vs. external

kubeadm defaults to stacked etcd — each control-plane node runs its own etcd member locally, alongside its API server. Simpler to operate, and what the exam expects unless told otherwise. External etcd runs etcd as a separate cluster the API servers all connect to — more moving parts, used when etcd needs to scale or fail independently of the control plane.

Who's actually in charge right now

Every kube-apiserver is active simultaneously. kube-scheduler and kube-controller-manager use a Lease object to elect one leader each — check who's holding it:

kubectl get lease -n kube-system kube-scheduler -o jsonpath='{.spec.holderIdentity}'
kubectl get lease -n kube-system kube-controller-manager -o jsonpath='{.spec.holderIdentity}'

Try it — before looking below

Q1. In a 3-control-plane-node cluster, the node currently holding the kube-scheduler lease goes down. What happens to scheduling?

Briefly nothing new gets scheduled, then one of the two remaining kube-scheduler instances acquires the Lease (it was already running, just idle) and becomes the new leader. No manual action needed — that's the point of running more than one.

Q2. Why does kube-apiserver not need leader election, but kube-scheduler does?

kube-apiserver is stateless — it just reads/writes etcd, so any number of copies can serve requests at once with no conflict. kube-scheduler makes decisions (which node gets this Pod) — two copies deciding independently could schedule the same Pod twice, so only one may act at a time.

Recap
  • --control-plane-endpoint points at a load balancer, not one node — that's what makes control-plane nodes replaceable.
  • kubeadm defaults to stacked etcd (one member per control-plane node).
  • API servers are all active at once; scheduler and controller-manager elect one leader via a Lease object.
