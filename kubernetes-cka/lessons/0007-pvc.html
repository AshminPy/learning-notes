PersistentVolumeClaim → Pod

Everything so far (ConfigMap, Secret) has been about injecting small bits of config into a Pod. Storage is a different problem: a container's filesystem dies with the container, so anything that needs to survive a restart — a database's data directory, an uploaded file — needs a volume backed by real, persistent storage. Kubernetes splits this into three layers, and the exact plumbing between them is a classic exam trap.

Tied to your mission: storage binding issues (PVC stuck Pending, wrong access mode, wrong StorageClass) are a recurring Troubleshooting-domain scenario — the domain worth 30% of the exam.

The mental model — three layers

PersistentVolume (PV) — the actual storage resource (a disk, an NFS share, whatever the backend is). It is cluster-scoped, not namespaced. It exists independently of any Pod.

PersistentVolumeClaim (PVC) — a namespaced request for storage: "I need N GiB, with this access mode." The control plane binds it to a PV that satisfies the request.

Pod — mounts the PVC as a volume, never the PV directly.

This indirection is the single most important thing to understand in this lesson. A Pod's spec.volumes never points at a PV — it points at a PVC by name. The PVC is what's bound to the PV behind the scenes. Try to wire a Pod straight to a PV and there's no field for it; the normal path always goes Pod → PVC → PV. This trips people up in the exam because it feels like an unnecessary extra step — it isn't, it's what makes the Pod spec portable across clusters where the underlying storage differs.

Static vs. dynamic provisioning

Dynamic provisioning is the realistic default on GKE and most clouds: a PVC references a StorageClass, and if no existing PV matches, the cluster automatically creates one for you. You rarely hand-write a PV yourself. GKE ships a default StorageClass out of the box (provisioner pd.csi.storage.gke.io, backed by a Persistent Disk) — create a PVC with no storageClassName at all and it still gets provisioned against that default.

Static provisioning is the older, on-prem-style pattern: an administrator pre-creates PVs by hand, and a new PVC binds to whichever existing PV matches its size and access mode — no StorageClass involved.

Know both directions. The CKA exam environment may use static provisioning, a default StorageClass, or neither depending on how the cluster is set up — don't assume dynamic provisioning "just works" until you've confirmed a default StorageClass exists (kubectl get storageclass).

accessModes, briefly

  • ReadWriteOnce (RWO) — the volume can be mounted read-write by a single node at a time. Most block storage (e.g. cloud persistent disks) only supports this.
  • ReadOnlyMany (ROX) — many nodes can mount it read-only at once.
  • ReadWriteMany (RWX) — many nodes can mount it read-write at once. Needs a backend that supports shared access (e.g. NFS) — most cloud block storage doesn't.

(There's also ReadWriteOncePod, a stricter RWO that limits the mount to a single Pod rather than a single node — good to recognize if you see it, not the focus here.)

Try it first — before reading on

Q1. Does a Pod's spec.volumes reference a PV or a PVC?

A PVC — always. The Pod never mounts a PV directly; the PVC is what's bound to the PV behind the scenes.

Q2. What makes a PVC automatically get a matching PV without you creating one by hand?

Referencing a StorageClass (or letting the cluster's default StorageClass apply) — that triggers dynamic provisioning, which creates a new PV to satisfy the claim.

Q3. Which accessMode would you pick for a volume that needs to be mounted read-write by Pods on several different nodes at the same time?

ReadWriteMany (RWX) — and note most cloud block storage (e.g. GCP Persistent Disk) doesn't support it, only ReadWriteOnce.

Now build it — in your terminal, not here

Write two manifests by hand, no copy-paste:

1. A PersistentVolumeClaim that requests:

  • 1Gi of storage
  • ReadWriteOnce access mode
  • a storageClassName (use standard, or whatever your cluster's default StorageClass is called — check with kubectl get storageclass)

2. A Pod that:

  • mounts that PVC as a volume
  • mounts it into the container filesystem at some path (e.g. /usr/share/nginx/html if you use the nginx image)

Don't peek at the answer below until you've written something.

Reveal the reference answer

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard
  resources:
    requests:
      storage: 1Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: pvc-pod
spec:
  containers:
    - name: app
      image: nginx
      volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: my-pvc

Bring what you wrote back to your notes — check it field-by-field: does volumes[].persistentVolumeClaim.claimName match your PVC's metadata.name? Does volumeMounts[].name match volumes[].name? Those two links are where typos usually break this.

Recap
  • PV = actual storage, cluster-scoped. PVC = namespaced request for storage. Pod mounts the PVC, never the PV.
  • Dynamic provisioning (PVC + StorageClass, auto-creates the PV) is the realistic default on GKE/cloud. Static provisioning (hand-created PVs) is more common on-prem, and possibly in the exam lab.
  • accessModes: ReadWriteOnce (one node, read-write), ReadOnlyMany (many nodes, read-only), ReadWriteMany (many nodes, read-write — needs a backend that supports it).
