Kubernetes / CKA — Lesson 7 of 24

PersistentVolumeClaim → Pod

Why this matters

Every other lesson in this course lets you undo a mistake: redeploy a bad Deployment, re-apply a Service, restart a crashed Pod. Storage is different. If a PersistentVolume's reclaim policy is Delete — the default for dynamically-provisioned volumes — then deleting the PersistentVolumeClaim on top of it deletes the underlying disk too, immediately, with no confirmation prompt and no trash can to recover from. This is one of the only genuinely irreversible mistakes in the entire CKA curriculum: a kubectl delete pvc that looks like it's removing a small Kubernetes object is actually, silently, also asking the cloud provider to destroy real data. Get this lesson wrong in production and you don't get a second attempt.

Mental model: a PersistentVolumeClaim is a coat-check ticket, not the coat. You hand your coat to storage (the PersistentVolume) and get a ticket (the PVC) — the Pod just carries the ticket around. Drop the Pod and get a new one (delete and recreate the Pod), and the new Pod hands the same ticket to the same counter — the same coat comes back, because neither the ticket nor the coat ever changed. But tear up the ticket itself (delete the PVC), and what happens next depends entirely on the counter's house policy: some counters shred the coat the instant the ticket is torn up (Delete — the default), others hold the coat in a back room until a manager sorts it out (Retain). That's the prediction this mental model makes, and the one this lesson's exercise proves: Pod churn is safe, PVC deletion is the dangerous action, and the reclaim policy — not anything about the Pod — decides whether "dangerous" means "recoverable" or "gone."

Core concepts: the three-layer model

Kubernetes splits storage into three layers so the thing your Pod asks for (space) is decoupled from the thing that actually holds data (a specific disk):

  • PersistentVolume (PV) — the real storage: a cluster-scoped resource representing an actual disk, whether an admin hand-created it or a StorageClass provisioned it automatically. Not namespaced — a PV isn't "owned" by any one team's namespace.
  • PersistentVolumeClaim (PVC) — a namespaced request for storage: "I need this much space, with this access mode." The control plane binds it to a matching PV — one PVC to exactly one PV, one PV to at most one PVC at a time.
  • Pod — mounts the PVC in spec.volumes, never the PV directly. This indirection is what makes the mental model above true: the Pod's manifest never names a specific disk, so replacing the Pod never touches the disk.
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard
  resources:
    requests:
      storage: 1Gi

The Pod side of the contract:

apiVersion: v1
kind: Pod
metadata:
  name: pvc-pod
spec:
  containers:
    - name: app
      image: nginx:1.29
      volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: my-pvc

Notice the Pod's volumes block names a PVC (claimName: my-pvc) — never a PV name, never a disk ID. That's not a style choice; the Pod API doesn't have a field for mounting a PV directly.

Dynamic provisioning and where StorageClass fits

A StorageClass is the piece that turns "I need 1Gi of storage" into an actual disk, automatically. It names a provisioner — the plugin or CSI driver that talks to the real storage backend — plus the default reclaim policy and binding behavior every PVC using it will get:

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: pd.csi.storage.gke.io
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Retain
allowVolumeExpansion: true

Dynamic provisioning (the default on GKE/EKS/AKS) means a PVC just names a storageClassName and the StorageClass's provisioner creates a matching PV for it — no admin has to hand-create anything. Static provisioning is the older pattern: an admin creates PVs ahead of time, and a PVC binds to one of them by matching size and access mode, with no StorageClass involved at all.

One field changes when that automatic PV actually gets created: volumeBindingMode. Left unset, it defaults to Immediate — the PV is provisioned the moment the PVC is created, before any Pod exists to use it. Set to WaitForFirstConsumer, provisioning is delayed until a Pod that references the PVC is actually scheduled. This matters most on multi-zone clusters: with Immediate, the disk can end up provisioned in a zone the eventual Pod can't be scheduled into (because of node selectors, affinity, or just where capacity happens to be), leaving the Pod permanently unschedulable. WaitForFirstConsumer waits until the scheduler has already picked a node, then provisions storage in that node's zone — this is why it's the field to check first when a Pod is stuck Pending on a multi-zone cluster.

Reclaim policies: what happens when the claim goes away

A PV's persistentVolumeReclaimPolicy decides what happens to the underlying storage once its PVC is deleted:

Reclaim policyWhat happens to the PVWhat happens to the data
DeleteThe PV object is deletedDeleted along with it — this is the default a StorageClass gives dynamically-provisioned volumes if you don't set reclaimPolicy yourself
RetainThe PV stays, status moves to ReleasedUntouched; won't bind to a new PVC automatically — an admin must manually reclaim or delete it
RecycleN/ADeprecated by the Kubernetes docs — dynamic provisioning replaced it; don't use it in new manifests
kubectl get pv                                    # STATUS column: Bound / Released / Available
kubectl patch pv <name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'

Two details worth holding onto: the reclaim policy lives on the PV, not the PVC, and it can be changed on an existing, already-bound PV at any time with the patch above — you don't have to get it right only at creation time, but you do have to remember to check it.

Access modes

An accessModes entry on a PVC describes how many nodes and Pods can mount the volume, and whether they can write:

Access modeAbbreviationWhat it allows
ReadWriteOnceRWORead-write, mounted by one node at a time (any number of Pods co-located on that node can share it)
ReadOnlyManyROXRead-only, mounted by many nodes at once
ReadWriteManyRWXRead-write, mounted by many nodes at once — needs a backend like NFS; most cloud block storage doesn't support it
ReadWriteOncePodRWOPRead-write, restricted to exactly one Pod cluster-wide (not just one node) — CSI volumes only

Production example

Production note: production databases almost never run on the default Delete policy. The usual pattern is either Retain on the StorageClass (or patched onto the PV after the fact) so a mistaken PVC deletion leaves the disk recoverable, paired with an actual scheduled backup — cloud disk snapshots, or an in-cluster tool like Velero — since Retain alone only stops the disk from being destroyed, it doesn't back anything up. This connects directly to StatefulSets, covered in Lesson 12: a StatefulSet uses volumeClaimTemplates to create one PVC per replica automatically, and its persistentVolumeClaimRetentionPolicy field — beta since Kubernetes v1.27 — controls whether those PVCs are deleted when a replica is removed or the StatefulSet itself is deleted. Its default for both cases is Retain: a StatefulSet's storage survives Pod churn, scale-downs, and even StatefulSet deletion unless someone explicitly opts into Delete. The lesson to take from both mechanisms together: the controller managing your Pods doesn't decide your data's fate — the reclaim policy and retention policy do, and both default toward safety for exactly this reason.

Hands-on exercise

Objective

Prove that deleting and recreating a Pod does not touch the data behind its PVC — the exact claim the mental model above makes.

Scenario

Write a file into a PVC-backed Pod, delete the Pod (not the PVC), recreate it, and confirm the file survived.

Environment assumptions

Any cluster with a default StorageClass (kind, minikube, or a real dev cluster) — run kubectl get storageclass first and confirm one is marked (default). No existing my-pvc PVC or pvc-pod Pod in the current namespace.

Commands

cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
EOF

cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: pvc-pod
spec:
  containers:
    - name: app
      image: nginx:1.29
      volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: my-pvc
EOF

kubectl wait --for=condition=Ready pod/pvc-pod --timeout=60s
kubectl exec pvc-pod -- sh -c 'echo "hello from before the delete" > /usr/share/nginx/html/proof.txt'
kubectl delete pod pvc-pod

cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: pvc-pod
spec:
  containers:
    - name: app
      image: nginx:1.29
      volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: my-pvc
EOF

kubectl wait --for=condition=Ready pod/pvc-pod --timeout=60s
kubectl exec pvc-pod -- cat /usr/share/nginx/html/proof.txt

Expected result

The final command prints hello from before the delete — read back by the second Pod, which never existed when that file was written.

Verification

Don't just trust that it "looks like" a new Pod — check kubectl get pod pvc-pod -o jsonpath='{.metadata.uid}' before and after the delete; the UIDs should differ. Then check kubectl get pvc my-pvc -o jsonpath='{.metadata.uid}' — that UID should be identical throughout. Same claim, same disk, two different Pods.

Common failure

If the second Pod never reaches Ready, run kubectl describe pod pvc-pod first. On a single-node kind/minikube cluster this almost never happens, but on a multi-node cluster a PV tied to one zone can leave the new Pod stuck Pending if it's scheduled onto a node in a different zone — a preview of this lesson's troubleshooting section, not a bug in this exercise.

Troubleshooting

If the PVC itself hangs at Pending before you even get to the Pod, run kubectl get storageclass — no StorageClass marked (default) means you need to add storageClassName: <name> to the PVC explicitly rather than waiting for a default that doesn't exist.

Cleanup / rollback

kubectl delete pod pvc-pod --ignore-not-found
kubectl delete pvc my-pvc --ignore-not-found

Production lesson

This is the boring, reassuring half of the story — Pod churn (crashes, node drains, rollouts) is safe by design. The failure scenario next covers the half that isn't boring: what happens when someone deletes the PVC instead of the Pod.

Failure scenario

A realistic incident built entirely from the default this lesson keeps returning to: Delete.

  1. Mon 16:40 A platform engineer runs a "namespace cleanup" script ahead of decommissioning an old staging-billing environment: kubectl delete pvc -n staging-billing --all, to tidy up leftover claims before deleting the namespace itself.
  2. Mon 16:41 The wildcard also matches invoices-db-pvc — a PVC that, unlike everything else in that namespace, is quietly backing a real Postgres instance someone deployed there as a "temporary" fix months ago and never moved.
  3. Mon 16:41 kubectl delete pvc returns instantly. The bound PV's reclaim policy was the dynamic-provisioning default, Delete — the underlying cloud disk is destroyed as part of the same operation, not on a delay.
  4. Tue 09:15 Support tickets start: the billing dashboard shows no data for the last quarter. On-call checks the Postgres Pod — it's Running, healthy, zero restarts... and completely empty. Its StatefulSet noticed the PVC was gone and had a fresh, empty one provisioned in its place automatically.
  5. Tue 09:32 kubectl get pv shows no record of the old volume at all — not Released, not Failed, simply gone. kubectl get events -n staging-billing --sort-by=.lastTimestamp confirms the PVC delete event from Monday afternoon, 17 hours earlier.
  6. Tue 09:40 Root cause confirmed: the cleanup script's --all flag matched a PVC it had no business touching, and the default Delete reclaim policy left nothing to restore — no snapshot existed for this "temporary" database either.
  7. Tue 10:15 Recovery: restored from the last full database export, three weeks old. A quarter's worth of billing data between the export and the deletion is unrecoverable.

Nothing here required a bug, an attacker, or even a missing RBAC rule. A wildcard flag and a reclaim policy default did all of the damage.

Troubleshooting workflow

The general method, applied to "my Pod is stuck Pending and I suspect its PVC":

  1. Confirm the symptom. kubectl get pod <name> — is it genuinely Pending, and for how long? A few seconds of Pending during normal scheduling isn't this problem.
  2. Define scope. kubectl get pvc -n <namespace> — is the Pod's PVC itself Bound, or stuck Pending too? If the PVC is Pending, the Pod was never going to schedule — fix the PVC, not the Pod.
  3. Check recent changes. kubectl get events -n <namespace> --sort-by=.lastTimestamp — look for FailedScheduling on the Pod and a provisioning failure on the PVC.
  4. Inspect the right state. kubectl describe pvc <name> for its Events section, then kubectl get storageclass — does the storageClassName the PVC asks for actually exist on this cluster? A typo'd or missing StorageClass name is the single most common cause.
  5. Form a hypothesis. In rough order of likelihood: (a) no StorageClass matches the requested name, (b) a static PV exists but its accessModes or capacity don't satisfy the claim, (c) volumeBindingMode: WaitForFirstConsumer is working as designed and is simply waiting for a schedulable Pod, (d) a multi-zone cluster provisioned the disk in a zone the Pod can't be scheduled into.
  6. Test one variable. Read the scheduler's own reason string in kubectl describe pod <name>'s Events section — node(s) had volume node affinity conflict confirms a zone mismatch specifically; don't change anything until you've distinguished that from a plain "no PV available" message.
  7. Apply the safest fix. Correct the StorageClass name, or create the missing one. Don't delete and recreate the PVC to "reset" it — that risks the exact data-loss failure mode this lesson is built around if the PVC had already bound to something real.
  8. Verify recovery. Confirm kubectl get pvc <name> shows Bound, then that kubectl get pod <name> shows Running — check both, since a Pod can go Running against the wrong PVC if you edited the wrong field.
  9. Document the root cause. "PVC requested StorageClass X, which doesn't exist in this cluster" — specific enough that the next engineer doesn't re-diagnose from scratch.
  10. Prevent recurrence. Add a pre-deploy check (admission policy, CI lint, or a documented list) of valid StorageClass names per cluster, since this typo only ever shows up after the manifest is applied.

Security note: RBAC controls who can run kubectl delete pvc — the delete verb on the persistentvolumeclaims resource. In a shared cluster, treat that permission the way you'd treat access to a production database's drop privileges, not the way you'd treat "delete a Pod." One safety net already exists for free: Kubernetes attaches a kubernetes.io/pvc-protection finalizer to any PVC currently mounted by a running Pod, so kubectl delete pvc against an in-use claim doesn't actually delete it immediately — it hangs in Terminating until the last Pod using it is gone. That protects against deleting a PVC a Pod is actively using; it does nothing to protect an unused-but-still-important PVC, which is exactly what the failure scenario above hit.

Reliability note: reclaim policy is not a backup strategy — it's a last-resort brake. Retain only guarantees the disk isn't destroyed; it doesn't guarantee anyone remembers it exists, and a Released PV with no documentation is effectively lost to the next engineer anyway. For anything that matters, pair Retain with an actual, scheduled backup — cloud disk snapshots, or an in-cluster tool like Velero — so recovery doesn't depend on someone having picked the right reclaim policy months before the incident that tests it.

Common mistake: trusting the default Delete reclaim policy for anything you'd be upset to lose. It's the right default for scratch space and CI runners — disposable by design — and the wrong default for a database, precisely because nobody has to opt into it; dynamically-provisioned volumes start there automatically, with no warning.

Common mistake: assuming kubectl delete pod touches the data behind its PVC. It doesn't — the hands-on exercise above proves it — but the fear of it makes people avoid routine, harmless Pod restarts, while the opposite mistake (assuming everything storage-related is just as safe to delete) is what actually causes incidents.

Common mistake: setting storageClassName to a name that looks right but doesn't exist on this particular cluster. StorageClass names aren't standardized across providers, or even across clusters on the same provider — copying a manifest from one cluster to another is one of the most common ways a PVC ends up stuck Pending. Worth knowing before you try to "fix" it: storageClassName is immutable once a PVC is created, so the actual fix is usually deleting and recreating the PVC, not patching it.

Decision guide

Reclaim policy:

PolicyUse whenAvoid whenTrade-off
DeleteScratch space, CI/CD runners, dev/test environments, anything trivially recreatedDatabases, anything holding data you can't regenerate on demandZero cleanup effort; zero recovery if the PVC is ever deleted by mistake
RetainProduction databases, anything where losing data costs more than a manual cleanup stepHigh-churn ephemeral workloads — Released PVs pile up and need someone to actually clean themSurvives PVC deletion; needs a human or automation to reclaim the released PV afterward
RecycleNever — deprecatedAlwaysSuperseded by dynamic provisioning; don't use it in new manifests

Default recommendation: if you can't answer "what's our backup strategy for this volume?" in one sentence, treat it as important and set Retain — reversing that decision after a Delete has already run isn't possible.

Access mode:

ModeUse whenAvoid whenTrade-off
ReadWriteOnce (RWO)A single Pod, or several co-located on one node, need read-write — the common case, and what most cloud block storage supportsPods spread across multiple nodes all need write access to the same volumeWidest storage-backend support; ties the volume to one node at a time
ReadOnlyMany (ROX)Many Pods across many nodes need to read the same static data — shared config, reference datasetsAnything needs to write to itGood fan-out for reads; no write path exists at all
ReadWriteMany (RWX)Multiple Pods on multiple nodes must genuinely read and write the same files — a shared upload directoryA single writer would actually do — RWX backends cost more and run slower than block storageMost flexible of the four; also the least commonly supported by cheap default backends
ReadWriteOncePod (RWOP)You must guarantee exactly one Pod cluster-wide has it mounted, not just one node — e.g. preventing a bad rollout from double-mounting a volumeThe volume plugin isn't CSI, or the stricter single-Pod guarantee isn't neededStrongest safety guarantee of the four; CSI-only, so not universally available

Default recommendation: reach for ReadWriteOnce unless you have a specific, named reason for something else — it's what almost every stateful workload actually needs, and what almost every storage backend actually supports.

Knowledge check

Q1. Does a Pod's spec.volumes reference a PV or a PVC?

A PVC — always. The Pod API has no field for mounting a PV directly.

Q2. Which accessMode lets many nodes mount a volume read-write at the same time?

ReadWriteMany (RWX) — most cloud block storage only supports ReadWriteOnce, so this needs a backend like NFS.

Q3. A PVC holding a production database is accidentally deleted. Its PV's reclaim policy is Retain. Is the data gone?

No. The PV moves to Released, not deleted — the underlying disk and its data are untouched. An admin has to manually re-bind or clean it up; nothing happens automatically. If the policy had been Delete, the data would already be gone.

Q4. You create a StorageClass but leave reclaimPolicy unset. What reclaim policy do PVs it dynamically provisions get?

A. An omitted reclaimPolicy on a StorageClass defaults to Delete — the same default that makes this lesson's failure scenario possible. Setting it to Retain is an explicit, deliberate choice.

Q5. A StorageClass sets volumeBindingMode: WaitForFirstConsumer. When does the volume actually get provisioned?

B. Provisioning waits until the scheduler has picked a node for a Pod using the PVC — this avoids provisioning a disk in a zone the Pod can never be scheduled into. Immediate (the default when unset) provisions right away instead, with no awareness of the eventual Pod's placement.

Production challenge

Objective

Diagnose and fix a Pod stuck Pending because of a PVC/StorageClass mismatch, using only the troubleshooting method above — not this lesson's exercise as an answer key.

Scenario

A teammate's manifest requests a StorageClass named fast-ssd that doesn't exist on your cluster. Build the broken state yourself first, then diagnose it as if you'd inherited it cold.

Environment assumptions

A kind/minikube cluster with a default StorageClass (commonly named standard — check with kubectl get storageclass and substitute your actual default name in the fix step below).

Commands

# 1. Build the broken state
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: broken-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 1Gi
EOF

cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: broken-pod
spec:
  containers:
    - name: app
      image: nginx:1.29
      volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: broken-pvc
EOF

# 2. Diagnose — don't skip straight to a fix
kubectl get pod broken-pod
kubectl get pvc broken-pvc
kubectl get storageclass
kubectl describe pvc broken-pvc

Expected result

broken-pod stays Pending indefinitely; broken-pvc stays Pending too; kubectl get storageclass shows no fast-ssd entry; kubectl describe pvc's Events show a provisioning failure referencing the missing StorageClass.

Verification

Confirm the diagnosis before touching anything: the PVC being Pending, not just the Pod, is what proves this is a storage problem rather than an unrelated scheduling issue (taints, resource requests, and so on).

Common failure

Deleting and recreating the Pod, expecting that to help. It won't — the Pod was never the broken object, and this "fix" just repeats the same failure under a new Pod name.

Troubleshooting

If kubectl describe pvc's Events section looks empty, wait a few seconds and re-run it — provisioning-failure events aren't always instant. If it's still empty, confirm the cluster has a dynamic provisioner running at all; some bare-metal or kubeadm clusters have none by default, which is a cluster-level gap, not a manifest typo.

Cleanup / rollback

kubectl delete pod broken-pod --ignore-not-found
kubectl delete pvc broken-pvc --ignore-not-found

Note: storageClassName is immutable once a PVC exists, so the real fix is recreating the PVC with the correct name — not patching this one. Deleting it here is safe specifically because it never bound to a PV and therefore never held real data; that would not be true in production.

Production lesson

The fix, once diagnosed, is trivial. The actual skill this challenge tests is not jumping straight to "restart the Pod" before confirming which object is actually broken — and the same discipline, applied in reverse, is what would have stopped the failure scenario earlier in this lesson from ever reaching production data.

Recap
  • PV = real storage, cluster-scoped. PVC = namespaced request. Pod mounts the PVC, never the PV — this indirection is why Pod deletion never touches data.
  • Dynamic provisioning (PVC + StorageClass) auto-creates the PV; volumeBindingMode: WaitForFirstConsumer delays that until a Pod is scheduled, avoiding zone-mismatch Pending Pods.
  • reclaimPolicy: Delete (default — storage dies with the PVC), Retain (storage survives, needs manual cleanup), Recycle (deprecated).
  • accessModes: ReadWriteOnce (one node), ReadOnlyMany (many, read-only), ReadWriteMany (many, read-write), ReadWriteOncePod (exactly one Pod cluster-wide, CSI only).
  • Deleting the wrong PVC under the default Delete policy is one of the few genuinely irreversible mistakes in this course — treat kubectl delete pvc with the same caution as a production database's drop privileges.
