PersistentVolumeClaim → Pod

A container's filesystem dies with the container — and per Lesson 1, a Pod itself is disposable too. Anything that must survive a restart (a database's data, an upload store) needs storage that outlives both. Kubernetes splits this into three layers instead of letting a Pod just declare "give me a disk."

Mental model: a PersistentVolume (PV) is an actual storage locker; a PersistentVolumeClaim (PVC) is the request form — "I need a locker this size." A Pod never touches the locker directly, it only holds the claim form. That predicts something real: delete the Pod, the claim form (PVC) and the locker (PV) are untouched — storage outlives the Pod exactly the way it's supposed to.

The three layers, and why

  • PersistentVolume (PV) — the real storage. Cluster-scoped, not namespaced.
  • PersistentVolumeClaim (PVC) — a namespaced request for storage; the cluster binds it to a matching PV.
  • Pod — mounts the PVC, never the PV directly.

Why it's built this way: this separates "what storage exists" (an infra/admin concern — disk type, size, backend) from "what a Pod needs" (an app concern — just a mount path). A Pod manifest asking for a PVC stays identical whether it runs on AWS EBS, GCP PD, or bare-metal NFS — only the PV/StorageClass underneath changes, which is what makes the same manifest portable across clusters.

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: standard
  resources:
    requests:
      storage: 1Gi

Most managed clusters auto-create the PV for you — dynamic provisioning, triggered by storageClassName. The older pattern, static provisioning, is an admin hand-creating PVs ahead of time.

What happens when the PVC is deleted

A PV's persistentVolumeReclaimPolicy decides what happens to the underlying storage once its PVC is gone:

  • Delete — the PV and the real storage behind it are deleted too. Default for dynamically-provisioned volumes.
  • Retain — the PV is kept (status Released), data intact, but won't bind to a new PVC automatically — an admin has to manually reclaim it. Use this for anything you can't afford to lose to a mistaken kubectl delete pvc.

Try it

Q1. Does a Pod's spec.volumes reference a PV or a PVC?

A PVC — always. The Pod never mounts a PV directly.

Now write your own: a Pod that mounts the PVC above at /usr/share/nginx/html. Try before revealing.

Reveal the reference answer

apiVersion: v1
kind: Pod
metadata:
  name: pvc-pod
spec:
  containers:
  - name: app
    image: nginx:1.29
    volumeMounts:
    - name: data
      mountPath: /usr/share/nginx/html
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: my-pvc

Common mistake: assuming the default Delete reclaim policy is fine for production data — it means one mistaken kubectl delete pvc destroys the underlying disk too, with no recovery path.

A controlled failure

Set a PV to Retain, then delete its PVC — a mistake you want to survive, not just avoid:

kubectl patch pv <pv-name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
kubectl delete pvc my-pvc
kubectl get pv

Predict first: is the data gone? Observe: the PV's STATUS shows Released, not deleted — the underlying disk and its data are untouched, just unbound and waiting for an admin to manually re-bind or clean it up.

Production best practices

Production note: set Retain explicitly on any StorageClass or PV backing real data — never rely on the Delete default for anything you'd need to recover from. Snapshot/backup policy at the storage layer (Lesson 14's etcd backup is the control-plane equivalent) is a separate, additional safeguard, not a substitute for the right reclaim policy.

Exam & interview notes

Directly scored under Storage (10%) — the smallest domain by weight, but a reliable source of exam tasks.

Interview Q: "A PVC bound to production data gets accidentally deleted. What determines whether the data is recoverable?" A: The PV's reclaimPolicy — Retain means the PV survives as Released with data intact; Delete (the default for dynamic provisioning) destroys the underlying storage along with the PVC.

Recap
  • PV = real storage, cluster-scoped. PVC = namespaced request. Pod mounts the PVC, never the PV.
  • Dynamic provisioning (PVC + StorageClass) auto-creates the PV — the default on most managed clusters.
  • reclaimPolicy: Delete (default, storage goes with the PVC) vs. Retain (storage survives, needs manual cleanup).
