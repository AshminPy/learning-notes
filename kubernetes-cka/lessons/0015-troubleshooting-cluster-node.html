Kubernetes / CKA — Lesson 15 of 17

Troubleshooting — cluster & node level

This lesson opens the Troubleshooting domain — 30% of the CKA exam, the single largest domain by weight. Everything from here on is less "here's a new object kind" and more "here's a system that's broken, find out why, in order."

Tied to your mission: you troubleshoot production Kubernetes every day, but on GKE Autopilot the node and kubelet layer is Google's problem, not yours — you've never had to SSH into a node and read journalctl because that layer is managed away from you. The instinct you already have ("narrow the blast radius before you touch anything") is exactly right. What's missing is just the specific commands for the layer GKE normally hides: is the node itself healthy, is kubelet running, and — if things are bad enough that kubectl itself won't answer — is the container runtime even alive.

The mental model

Cluster/node troubleshooting is one discipline applied at shrinking scope: cluster-wide symptom → which node(s) → which component on that node → logs for that component. Skipping a step (jumping straight to reading kubelet logs before you've even confirmed which node is unhealthy) wastes exam minutes. Work the funnel in order.

Step 1 — cluster-wide: is a node NotReady?

kubectl get nodes

Confirm every node you expect is present and in Ready state. If one isn't, that's your scope — stop looking cluster-wide and focus on that node.

Step 2 — node-level: what does the node say is wrong?

kubectl describe node <node-name>

Read the Conditions block. A node reports four (sometimes five) conditions, each with a Status of True, False, or Unknown:

  • Ready — kubelet is healthy and posting status. False means kubelet said it's unhealthy; Unknown means the node controller hasn't heard from kubelet recently at all (heartbeat stopped)
  • MemoryPressure — node is low on available memory
  • DiskPressure — node is low on disk space
  • PIDPressure — node is running too many processes

The bottom of describe node output also has an Events section — often the fastest way to see why a condition flipped.

Step 3 — component-level: check kubelet on the node itself. A NotReady node is almost always a kubelet problem — kubelet is what posts the heartbeat that keeps a node Ready. Log in to the node and check:

systemctl status kubelet
journalctl -u kubelet -n 100 --no-pager

This tells you whether kubelet is running at all, and if not, why (crashed, cert expired, config error, can't reach the API server, disk full, and so on).

Step 4 — control-plane component health. Control-plane components (kube-apiserver, kube-scheduler, kube-controller-manager, etcd) run as static pods, as covered in Lesson 13 — kubelet on the control-plane node starts them straight from manifest files, with no API server involved in that decision. If one of those isn't running, and the reason kubectl itself won't answer is that the API server is the thing that's down, kubectl get pods can't help you — it depends on the very component you're diagnosing. Drop to the container-runtime level directly:

crictl ps -a

crictl talks to the container runtime (containerd/CRI-O) directly over the CRI socket, bypassing the API server entirely. It's the one tool that still works when kubectl doesn't.

kubectl get events --sort-by=.metadata.creationTimestamp is your first-look tool across the whole cluster, before you narrow to a node. Add -A for every namespace. Events are cheap, chronological, and often name the exact object and reason (FailedScheduling, NodeNotReady, Evicted, …) before you've read a single log line.

Try it first — before reading on

Q1. A node's Ready condition shows Unknown rather than False. What does Unknown specifically mean, as opposed to False?

False means kubelet is running and actively reported itself unhealthy. Unknown means the node controller hasn't heard a heartbeat from kubelet recently at all — kubelet may be crashed, the node may be unreachable, or the network path between node and API server is broken. Same visible symptom (NotReady), different next step: False points you at kubelet's own logs; Unknown points you at whether the node is reachable at all first.

Q2. Why can't you always rely on kubectl to diagnose a control-plane outage, and what do you drop down to instead?

kubectl talks to the API server — if the API server's static pod itself is down, kubectl has nothing to talk to, so kubectl get pods can't tell you the API server is broken. Drop to crictl ps -a on the control-plane node, which queries the container runtime directly and bypasses the API server entirely.

Worked scenario — a node shows NotReady

Before you look at the checklist below, think through it yourself: a teammate pings you that a Pod is stuck Pending and the node it should land on shows NotReady. What do you check, and in what order?

Reveal the diagnostic order

  1. kubectl get nodes — confirm scope: is it one node, or several? One node points at that node; several pointing at once often points at something shared (network, a control-plane component, a cloud-provider outage)
  2. kubectl describe node <node-name> — read the Conditions block: is it Ready=False (kubelet reported unhealthy) or Ready=Unknown (no heartbeat at all)? Also check MemoryPressure/DiskPressure/PIDPressure — any of those being True can itself cause Ready to flip
  3. kubectl get events --sort-by=.metadata.creationTimestamp -A — cluster-wide, chronological, look for anything near the time the node went NotReady (evictions, a cloud-provider event, other nodes affected)
  4. Log in to the node itself (SSH, or your cloud provider's serial console)
  5. systemctl status kubelet — is the kubelet process even running?
  6. journalctl -u kubelet -n 100 --no-pager — read the actual error: expired certificate, cannot reach the API server, disk full, cgroup driver mismatch, OOM-killed process, etc.
  7. If kubelet looks fine but pods (including control-plane static pods, if this is a control-plane node) aren't coming up as expected: crictl ps -a to see container state directly at the runtime level, independent of kubelet's own reporting
  8. Fix the root cause you found (restart kubelet, free disk space, renew the cert, correct the config) and re-run kubectl get nodes to confirm Ready returns

Try it yourself — build the recall habit

The exam rewards speed of diagnosis, not memorized fixes. For each symptom below, answer out loud or in the box: what's your first command, and why that one first? Then reveal and compare your reasoning, not just the command.

Scenario 1: kubectl get nodes shows one node as NotReady. What's your first command on that node, and why?

kubectl describe node <node-name> first — while still using kubectl, before logging into the node — to read the Conditions and Events and see whether the API server already knows the reason (DiskPressure, MemoryPressure) without you needing node access yet. Only after that do you SSH in and run systemctl status kubelet / journalctl -u kubelet, because NotReady is almost always a kubelet problem and those commands show you kubelet's own account of what's wrong.

Scenario 2: every kubectl command hangs and times out, cluster-wide, on a cluster where you manage your own control plane. What's your first move?

Don't keep retrying kubectl — it depends on the API server, and the API server is likely the thing that's down. SSH to a control-plane node and check kubelet there first (systemctl status kubelet, since kubelet is what starts the API server's static pod), then crictl ps -a to see directly whether the kube-apiserver container is even running, bypassing kubectl entirely.

Scenario 3: Pods across several unrelated namespaces started getting evicted at roughly the same time. What's your first command to find the common cause?

kubectl get events --sort-by=.metadata.creationTimestamp -A as a cluster-wide first look — evictions across unrelated namespaces usually share one root cause rather than being coincidence, and sorted events will often show the shared trigger (a node's DiskPressure or MemoryPressure flipping True) right before the evictions start. That points you at kubectl get nodes / kubectl describe node next, to confirm which node and which condition.

Recap
  • Work the funnel in order: cluster-wide symptom → which node(s) → which component → logs for that component
  • kubectl get nodes then kubectl describe node — read the Conditions: Ready, MemoryPressure, DiskPressure, PIDPressure
  • Ready=False (kubelet reported unhealthy) vs. Ready=Unknown (no heartbeat at all) are different next steps
  • NotReady is almost always a kubelet problem — check it on the node itself with systemctl status kubelet and journalctl -u kubelet
  • Control-plane components are static pods (Lesson 13) — if the API server itself is down, kubectl can't help you diagnose it; drop to crictl ps -a, which bypasses the API server
  • kubectl get events --sort-by=.metadata.creationTimestamp -A is your cheap, cluster-wide, chronological first look

Try solo: pick any Pod running in your GKE Autopilot cluster and run kubectl get events --sort-by=.metadata.creationTimestamp -n <its-namespace> for real. You won't get node/kubelet-level access on Autopilot — that's expected and is exactly the boundary this lesson is teaching you to recognize — but confirm you can read the event stream fluently and pick out what's signal vs. noise.
