Kubernetes / CKA — Lesson 15 of 24

Troubleshooting — cluster & node level

Why this matters

When a node goes bad at 3am, the gap between a 5-minute fix and a 45-minute outage almost never comes down to how much Kubernetes you know — it comes down to the order you checked things in. Engineers who can recite every kubectl flag from memory still burn 40 minutes SSHed into a node, grepping raw kubelet logs, before running the one command that would have named the problem in its very first line of output. This lesson is the method that Troubleshooting — 30% of the CKA exam, the single largest domain — is built around, and it's the same method real on-call runbooks are built around too: work from cluster-wide, down to node, down to component, down to logs. Never the other order. Never skip a layer because you're confident you already know the answer.

Mental model: troubleshoot a cluster like a funnel, not a dartboard. Start wide — is the whole cluster healthy? — then narrow: which node, then which condition on that node, then that component's own logs. The funnel only works if every layer runs in order. Jumping straight to journalctl -u kubelet on a hunch, without first running kubectl get events and kubectl describe node, is how experienced engineers still end up fixing a symptom instead of the root cause — you patch what you found first, watch the real problem resurface an hour later, and pay for the mistake twice. Under pressure, the instinct is to skip steps to feel faster. Resist it: the funnel is faster precisely because it stops you from guessing.

Core concepts

Run kubectl get nodes first, always — it's cheap and it tells you your scope: one node, several, or none. If a node isn't Ready, kubectl describe node <name> is your next stop, and its Conditions block is doing more work than most people realize. There are five conditions, not one:

ConditionWhat it means when trueWhat Kubernetes does automatically
Ready = Falsekubelet is running and posting status, but reports itself unhealthyNo new Pods scheduled here; existing Pods without a matching toleration are evicted after the default grace period
Ready = Unknownthe node controller hasn't received a heartbeat within node-monitor-grace-period (default 50 seconds)Kubernetes auto-adds a node.kubernetes.io/unreachable taint; Pods without a matching toleration are evicted after 5 minutes by default
DiskPressure = Truedisk capacity is lowA matching scheduling taint is added so new Pods stop landing here; the kubelet tries to reclaim space itself (e.g. deleting unused container images) before touching running Pods
MemoryPressure = Trueavailable node memory is lowSame pattern: scheduling taint first, then the kubelet proactively evicts Pods to reclaim memory if the pressure doesn't clear
PIDPressure = Truetoo many processes are running on the nodeSame pattern: scheduling taint first, then Pod eviction if pressure continues
NetworkUnavailable = Truethe node's network isn't correctly configuredNode isn't usable for Pod networking until this clears

The Ready row splits into two rows on purpose — False and Unknown mean genuinely different things, and they demand different next steps. False means the kubelet is alive and talking, just unhappy: go read its logs. Unknown means nobody has heard from the kubelet at all: check whether the node is even reachable before you assume anything about what's running on it.

The pressure conditions (DiskPressure, MemoryPressure, PIDPressure) come from the kubelet's own eviction manager watching a small set of signals — memory.available, nodefs.available, nodefs.inodesFree, imagefs.available, and pid.available among them — against configured thresholds. Cross a hard threshold and the kubelet terminates Pods immediately, with a 0-second grace period, no PodDisruptionBudget, no respecting terminationGracePeriodSeconds. Cross a soft threshold and it waits out a configurable grace period first. Either way, if the evicted Pod belongs to a Deployment, StatefulSet, or similar controller, the control plane immediately creates a replacement — this is the exact mechanic behind a mistake covered later in this lesson: restart or delete a Pod on a pressured node without checking node health first, and its replacement can land right back on the same overloaded node, or on a different node that's also running hot.

When kubectl itself can't help you

kubectl talks to the API server — that's the whole tool, end to end. If the API server's own static Pod is down, kubectl has nothing to talk to, no matter how correct your command is. Per the official troubleshooting guide, an unreachable API server means you're "unable to stop, update, or start new pods, services, replication controller," but "existing pods and services should continue to work normally unless they depend on the Kubernetes API" — the data plane doesn't stop just because the control plane went quiet. For that situation, drop to crictl ps -a on the affected node: it talks to the container runtime directly, with no API server in the loop at all, and it's the documented tool for exactly this case.

For logs: on a systemd-managed node, journalctl -u kubelet is your primary source for the kubelet itself (the docs note explicitly that on systemd-based systems you'll want journalctl over hunting for log files). Control-plane component logs depend on how the cluster was built — on a kubeadm cluster, the control plane runs as static Pods, so crictl logs or kubectl logs -n kube-system <pod> (when the API server itself is reachable) is your path; some distros still write to files like /var/log/kube-apiserver.log. When you don't yet know where to look, kubectl cluster-info dump pulls a wide, verbose snapshot of cluster and namespace state into one place — slow, but a reasonable last resort before you start SSHing around.

Production example

Production note: real on-call runbooks for "node alert fired" are, almost without exception, this exact funnel written down as a checklist: check the cluster health dashboard (cluster-wide) → check the node's status and conditions (node) → check the specific component implicated by the condition (kubelet, container runtime, disk) → read that component's logs. Teams that skip straight to "restart the Pod" or "reboot the node" without that first look at node Conditions have a specific, repeatable failure mode: if the real problem is DiskPressure or MemoryPressure, deleting a Pod doesn't fix anything — its replacement gets scheduled somewhere, and if capacity is tight, "somewhere" can be another node that's also under pressure, or the same node once the taint briefly clears. You haven't fixed the incident, you've spread it. This is precisely why serious runbooks put "check node Conditions and Events" as a mandatory early gate, not an optional step for when you're not busy.

Hands-on exercise

Objective

Practice separating a genuine signal from routine noise in a real event stream — the skill the funnel depends on at its very first step.

Scenario

Before you can use kubectl get events to diagnose anything real, you need to know what "normal" looks like, so an actual problem stands out instead of blending in.

Environment assumptions

Any cluster you can kubectl into — kind, minikube, or a real dev cluster. If you're on managed Kubernetes such as GKE Autopilot, you won't get node or kubelet SSH access — that's an intentional platform boundary the provider manages for you, not a gap in your setup, and it's fine for this exercise.

Commands

kubectl get events --sort-by=.metadata.creationTimestamp -A

Expected result

A chronological list mixing routine lifecycle events (Scheduled, Pulled, Created, Started — a healthy Pod coming up normally) with anything unusual, if something unusual has happened recently.

Verification

You've done this correctly if you can point to one event and say "that's noise — routine startup" and, ideally, one you'd flag as signal (Killing, Evicted, FailedScheduling, BackOff, anything with NodeNotReady or NodeHasDiskPressure in the reason). If your cluster is quiet, that's a valid result too — note what a fully-noise stream looks like so you recognize it later.

Common failure

Reading events top to bottom without sorting by timestamp first — without --sort-by, you can't tell what happened before what, and cause/effect gets scrambled.

Troubleshooting

If the command returns nothing at all, that's not a broken cluster — the default event retention window is short (roughly an hour), so events from anything that happened earlier have already rolled off.

Cleanup / rollback

None — this is a read-only command.

Production lesson

On a real on-call rotation, this exact command, sorted by time, is very often the fastest way to learn what happened — faster than opening a dashboard, faster than SSHing anywhere.

Failure scenario

A realistic incident showing what skipping the funnel actually costs, minute by minute.

  1. 03:14 PagerDuty fires: node worker-07 is NotReady. On-call, still half asleep, has seen "kubelet flaked out" alerts before and goes in with that assumption already formed.
  2. 03:16 On-call SSHes straight to worker-07 and runs systemctl restart kubelet — skipping kubectl get events and kubectl describe node entirely, because the hypothesis already feels obvious.
  3. 03:19 kubectl get nodes still shows NotReady. On-call restarts kubelet a second time, then a third, each time waiting a minute and checking again. No new evidence gathered between attempts — same action, repeated, expecting a different result.
  4. 03:24 Pods on worker-07 start showing Evicted — the default 5-minute eviction window since the node first went NotReady has elapsed. The blast radius just grew from "one node" to "every workload that was running on it."
  5. 03:27 A second engineer joins and starts at the top of the funnel instead of where on-call left off: kubectl get events --sort-by=.metadata.creationTimestamp -A. Near the top: Warning NodeHasDiskPressure worker-07, timestamped several minutes before the first NotReady alert.
  6. 03:29 kubectl describe node worker-07 confirms it: DiskPressure = True, Ready = False (not Unknown — the kubelet was alive and reporting the whole time, which is exactly why three kubelet restarts changed nothing).
  7. 03:32 On the node: df -h shows /var at 100%. A log-rotation cron job silently started failing two days ago; an unrelated app's container logs grew unbounded and filled the disk.
  8. 03:38 Fix applied: clear the runaway log files, restart the failed log-rotation job, confirm free space. No kubelet restart needed — it was never the problem.
  9. 03:44 DiskPressure clears, Ready flips back to True, the scheduler resumes placing Pods on worker-07. Total time: 30 minutes, most of it spent restarting a healthy component instead of reading the one event that named the real cause.

The funnel — get nodes → get events → describe node → then, and only then, the node itself — would have shown NodeHasDiskPressure before anyone touched kubelet at all. That's a 10-minute incident, not a 30-minute one, and zero Pods evicted along the way.

Troubleshooting workflow

The general 10-step method, mapped explicitly onto cluster and node problems:

  1. Confirm the symptom. kubectl get nodes — which node, what status, right now. Don't diagnose from a Slack message describing what someone else saw ten minutes ago.
  2. Define scope. One node or several? kubectl get nodes -o wide across the whole cluster. One node pointing to something node-local (disk, kubelet, hardware); several pointing to something shared (control plane, network, a cloud-provider outage).
  3. Check recent changes. Was a node drained for an upgrade recently? Did a DaemonSet or log-shipping agent just get updated? kubectl get events --sort-by=.metadata.creationTimestamp -A — cheap, chronological, and usually names the object and reason (NodeNotReady, NodeHasDiskPressure, Evicted) before you read a single log line.
  4. Inspect the right state. kubectl describe node <name> for its full Conditions block and its own Events section. Only after that: SSH to the node itself, systemctl status kubelet, then journalctl -u kubelet -n 100 --no-pager.
  5. Form a hypothesis. State it in one sentence you could defend to someone else: "Ready is False, not Unknown, so the kubelet is alive and reporting — the cause is whatever condition is True alongside it."
  6. Test one variable. If you suspect disk, check disk — df -h on the node, not a kubelet restart. Change one thing, or check one thing, before you decide the hypothesis is right or wrong.
  7. Apply the safest fix. Fix the actual resource constraint (free disk space, kill a runaway process, address memory pressure) rather than the kubelet — and don't delete or reschedule other Pods while you're still diagnosing, since that can push load onto a node that's already struggling.
  8. Verify recovery. Re-run kubectl get nodes and confirm Ready = True and every pressure condition back to False — not just that the alert stopped firing.
  9. Document the root cause. "Log rotation cron job failed silently two days prior; disk filled; kubelet correctly reported DiskPressure and Ready=False" — write down the real cause, not "restarted kubelet, it started working" (which, in this scenario, would be documenting a coincidence as a fix).
  10. Prevent recurrence. Alert on disk usage and on a failed log-rotation job directly, before it becomes a node-level Kubernetes symptom — the earlier you catch the real cause, the less it looks like a "Kubernetes problem" at all.

Security & reliability considerations

Security note: in a self-managed cluster, node/SSH access should be scoped to the platform or infra team only, through an audited path (bastion host, short-lived session, no standing SSH keys handed out broadly) — not given to every engineer who might want to debug a Pod. A node isn't just compute: it holds the kubelet's own credentials, every mounted ServiceAccount token for every Pod scheduled there, and often node-level cloud IAM credentials. Anyone with node access effectively has a path to everything running on that node, which is a much bigger blast radius than "SSH access" sounds like on its own.

Reliability note: node-pressure eviction is a self-protection mechanism, not a failure — the kubelet killing Pods to save itself is the system working as designed. But it's also a cascading-failure risk in an under-provisioned or unevenly-loaded cluster: evicted Pods get rescheduled, rescheduling adds load elsewhere, and if remaining capacity is already thin, you can watch pressure hop from node to node. This is a real argument for headroom in cluster capacity planning, not just for redundancy across zones.

Common mistake: treating Ready = Unknown the same as Ready = False. They point to different next steps — False means go read the kubelet's own logs; Unknown means check whether the node is even reachable before you assume anything about what's running on it. Debugging a heartbeat-loss problem as if it were an application-level kubelet failure wastes real time.

Common mistake: restarting a service, a Pod, or a whole node before running kubectl get events and kubectl describe node. A restart based on a hunch sometimes "fixes" things by accident (and teaches you the wrong lesson for next time), and sometimes actively makes things worse — as the failure scenario above shows, three kubelet restarts changed nothing because kubelet was never the problem.

Decision guide

SymptomStart hereWhy
One Pod misbehaving, cluster and node otherwise healthykubectl describe pod / kubectl logs (covered in Lesson 16)Scope is already narrow — jumping up to node or cluster checks first wastes time you don't need to spend
One node NotReady or showing a pressure condition, others finekubectl get nodes → kubectl describe node → kubectl get events -AThis is exactly the funnel this lesson teaches — node-scoped symptom, node-scoped diagnosis
Multiple nodes degraded, or the whole cluster feels "off"kubectl get events --sort-by=.metadata.creationTimestamp -A first, then compare nodes for a shared causeA shared symptom across many nodes is usually one shared cause (control plane, network, cloud outage), not N independent, unrelated kubelet failures
kubectl commands hang or time out entirelyCheck API server health on the control-plane node; fall back to crictl ps -a directly on affected nodeskubectl only works if the API server does — a dead API server needs a different toolset, not more kubectl retries

Default recommendation: whatever the symptom, start one level higher than you think you need to. Confirming "yes, this really is scoped to one Pod" or "yes, this really is scoped to one node" takes seconds and prevents the single most common troubleshooting mistake: solving the wrong-sized problem.

Knowledge check

Q1. Why can't kubectl always diagnose a control-plane outage?

kubectl talks to the API server. If the API server's own static Pod is down, kubectl has nothing to talk to. Use crictl ps -a on the node instead — it talks to the container runtime directly, bypassing the API server entirely.

Q2. What's your first command, cluster-wide, before you even pick a node?

kubectl get events --sort-by=.metadata.creationTimestamp -A — cheap, chronological, and it often names the object and reason (NodeNotReady, NodeHasDiskPressure, Evicted) before you've read a single log line.

Q3. A Pod is stuck Pending, and its node shows NotReady. Write your diagnostic order before revealing.

  1. kubectl get nodes — one node affected, or several? Several often means something shared (network, control plane, cloud outage).
  2. kubectl describe node <name> — Conditions block, plus its own Events section.
  3. kubectl get events --sort-by=.metadata.creationTimestamp -A — anything else around that timestamp, cluster-wide.
  4. SSH to the node. systemctl status kubelet — is it even running?
  5. journalctl -u kubelet -n 100 --no-pager — expired cert, can't reach the API server, disk full, and so on.
  6. If kubelet looks healthy but Pods still aren't coming up: crictl ps -a for runtime-level state.
  7. Fix the root cause, re-run kubectl get nodes, confirm Ready = True before declaring it resolved.

Q4. A node shows Ready = Unknown. What does that specifically tell you?

B. Unknown means the node controller hasn't heard from the node within node-monitor-grace-period (default 50 seconds) — it says nothing about whether the kubelet is healthy, unhealthy, or actually crashed, only that no heartbeat has arrived. (A describes Ready = False. C overstates what Unknown proves — the node might reconnect. D describes PIDPressure.)

Q5. A node's DiskPressure condition flips to True. What happens automatically, right away?

A. Kubernetes adds a matching scheduling taint the moment the condition goes True, so the scheduler stops placing new Pods there. Existing Pods aren't touched immediately — the kubelet first tries to reclaim space itself (e.g. removing unused images) and only evicts running Pods if the pressure doesn't clear. (B and D don't happen automatically at all; C skips the kubelet's own reclaim-first behavior.)

Production challenge

Objective

Work a multi-symptom incident to its one real root cause, using only the funnel — no live cluster required, this is a diagnostic-reasoning exercise using the output below, exactly like a real on-call handoff.

Scenario

You're paged with three things reported at once: several Pods stuck Pending, one node NotReady, and a vague mention of "disk pressure" in a teammate's handoff note. Here's what you pull:

$ kubectl get nodes
NAME       STATUS     ROLES    AGE   VERSION
node-a     Ready      <none>   40d   v1.30.2
node-b     NotReady   <none>   40d   v1.30.2
node-c     Ready      <none>   40d   v1.30.2

$ kubectl get pods -A | grep Pending
checkout    orders-7d9b6-abc12    0/1   Pending   0   3m
checkout    orders-7d9b6-def34    0/1   Pending   0   3m
billing     invoicer-99f-xz1      0/1   Pending   0   2m

$ kubectl get events --sort-by=.metadata.creationTimestamp -A | tail -6
... Warning  FreeDiskSpaceFailed    node/node-b            (combined) failed to garbage collect required amount of images
... Normal   NodeHasDiskPressure    node/node-b            Node node-b status is now: NodeHasDiskPressure
... Warning  FailedScheduling       pod/orders-7d9b6-abc12 0/3 nodes are available: 1 node(s) had untolerated taint {node.kubernetes.io/disk-pressure: }, 2 Insufficient cpu
... Warning  FailedScheduling       pod/orders-7d9b6-def34 0/3 nodes are available: 1 node(s) had untolerated taint {node.kubernetes.io/disk-pressure: }, 2 Insufficient cpu
... Warning  FailedScheduling       pod/invoicer-99f-xz1   0/3 nodes are available: 1 node(s) had untolerated taint {node.kubernetes.io/disk-pressure: }, 2 Insufficient cpu
... Normal   NodeNotReady           node/node-b            Node node-b status is now: NotReady

Commands

Before reading further: write down, in order, which commands you'd run next and what you expect each one to confirm.

Expected result

This is one root cause wearing three costumes, not three unrelated problems. node-b hit DiskPressure, got auto-tainted, and stopped accepting new Pods. That shrank the cluster's effective scheduling capacity from three nodes to two — and node-a/node-c don't have enough spare CPU between them to fit all three Pending Pods, hence Insufficient cpu stacked on top of the taint in every FailedScheduling message.

Verification

kubectl describe node node-b should show DiskPressure = True and Ready = False (posted by a live kubelet, not Unknown) with a reason referencing disk space. If you had node access, df -h on node-b would confirm which filesystem is full.

Common failure

Triaging the three Pending Pods as three separate application-team tickets — "why won't my Pod schedule" — instead of noticing they all started failing within the same one-minute window as node-b's disk event. Symptoms that start at the same moment across unrelated teams are a strong signal of one shared upstream cause.

Troubleshooting

If clearing node-b's disk fixes it today but it fills again in a week, look for the same pattern as this lesson's failure scenario: a silently-failed log rotation job or an unbounded container log, not a one-off fluke.

Cleanup / rollback

None — this is a reasoning exercise against provided output, not a change made to a live cluster.

Production lesson

Three tickets that land at the same time, from three different teams, almost always share one cause. Check for that before you split the incident into three separate investigations — you'll close it in a third of the time.

Recap
  • Funnel, in order, every time: cluster-wide symptom → which node → which condition/component → that component's own logs. Skipping a layer under pressure is how you fix a symptom instead of the root cause.
  • Five node Conditions, not one: Ready, DiskPressure, MemoryPressure, PIDPressure, NetworkUnavailable. Ready = False (kubelet alive, unhealthy) and Ready = Unknown (no heartbeat) need different next steps.
  • Pressure conditions auto-taint the node against new scheduling immediately, and can trigger the kubelet to evict running Pods if the pressure doesn't clear — restarting a Pod without checking node health can push the replacement onto another already-stressed node.
  • If the API server itself is down, kubectl can't help — use crictl ps -a directly against the container runtime instead.
  • Node/SSH access is a real security boundary, not just a convenience — it exposes every Pod's ServiceAccount token on that node, so scope it to the platform team, audited.
