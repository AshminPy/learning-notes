Troubleshooting — cluster & node level

This starts Troubleshooting — 30% of the exam, the biggest domain. Lessons 1-14 built objects; from here it's "something's broken, find out why," using exactly the components Lessons 1-14 already named.

Mental model: a funnel, not a guess. Start wide — is the whole cluster okay? — then narrow: which node, then which part of that node, then that part's own logs. That predicts the actual cost of skipping a step: jump straight to reading kubelet logs on a random node before checking kubectl get nodes, and you might spend twenty minutes debugging a perfectly healthy node while the real problem is somewhere else entirely.

Where this fits

Symptom: something's broken
   │
   ▼
kubectl get nodes            ← scope: all nodes, or one?
   │
   ▼
kubectl describe node        ← Conditions: Ready / MemoryPressure / DiskPressure / PIDPressure
   │
   ▼
systemctl status kubelet     ← is the node-level agent (Lesson 13) even running?
   │
   ▼
crictl ps -a                 ← bypass kubectl entirely if the API server itself is down

Step by step

  1. kubectl get nodes — any node not Ready? That's your scope.
  2. kubectl describe node <name> — read Conditions, each True/False/Unknown.
  3. SSH to the node: systemctl status kubelet, journalctl -u kubelet -n 100 --no-pager.
  4. If kubectl itself won't respond, drop to crictl ps -a — talks to the container runtime directly (Lesson 13), no API server needed.

Why it's built this way: Ready=False means kubelet is running and actively reporting unhealthy — the fix is in kubelet's own logs. Ready=Unknown means no heartbeat reached the API server at all — the node might be unreachable, not necessarily unhealthy. Same displayed problem, genuinely different next step, which is exactly why describe node comes before SSH-ing anywhere.

Try it

Q1. Why can't kubectl always diagnose a control-plane outage?

kubectl talks to the API server. If the API server's own static Pod (Lesson 13) is down, kubectl has nothing to talk to — use crictl ps -a on the control-plane node instead.

Now, before revealing: a Pod is stuck Pending, its node shows NotReady. Write your full diagnostic order.

Reveal the checklist

  1. kubectl get nodes — one node, or several? Several often means something shared (network, control plane, cloud outage).
  2. kubectl describe node <name> — Conditions + Events.
  3. kubectl get events --sort-by=.metadata.creationTimestamp -A — anything near that timestamp.
  4. SSH to the node. systemctl status kubelet — running at all?
  5. journalctl -u kubelet -n 100 --no-pager — expired cert, can't reach API server, disk full, etc.
  6. If kubelet looks fine but Pods aren't up: crictl ps -a.
  7. Fix root cause, re-run kubectl get nodes, confirm Ready.

A controlled failure

kubectl get events --sort-by=.metadata.creationTimestamp -A | tail -20

Predict first: will this be readable and specific, or vague? Observe: events usually name the exact object and reason (NodeNotReady, Evicted, FailedScheduling) — this single command is often the fastest signal in the whole funnel, cheaper than SSH-ing anywhere.

Production best practices

Production note: on managed Kubernetes (GKE Autopilot, EKS Fargate) you won't get node/kubelet SSH access at all — that's a deliberate platform boundary, not a gap in your knowledge. The funnel still applies down to describe node; the SSH/kubelet layer is the platform's job, not yours, on those clusters.

Exam & interview notes

Directly scored under Troubleshooting (30%) — the single largest domain.

Interview Q: "A node shows NotReady. What's the difference between investigating Ready=False vs. Ready=Unknown?" A: False means kubelet is alive and reporting a real problem — read its logs. Unknown means no heartbeat reached the API server — check node reachability/networking before assuming kubelet itself is broken.

Recap
  • Funnel: cluster-wide symptom → which node → which component → its logs. Skipping a step wastes time on the wrong layer.
  • describe node Conditions distinguish False (kubelet unhealthy) from Unknown (no heartbeat) — different next step.
  • If the API server itself is down, kubectl can't help — crictl ps -a bypasses it entirely.

Confidence check — answer without looking back:

  • Why start the funnel cluster-wide instead of jumping straight to one node's logs?
  • When would kubectl get events alone be enough to identify a root cause?
  • What happens differently between Ready=False and Ready=Unknown in terms of what you check next?
  • How would you verify a node is genuinely fixed, not just temporarily reporting Ready?
