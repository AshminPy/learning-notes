Troubleshooting — cluster & node level

This starts Troubleshooting — 30% of the exam, the biggest domain. From here on, less "new object," more "something's broken, find out why."

Simple example: think of it like a funnel. Start wide (is the whole cluster okay?), then narrow — which node, then which part of that node, then read that part's own logs. Skip a step and you waste time guessing.

Step by step

  1. kubectl get nodes — any node not Ready? That's your scope.
  2. kubectl describe node <name> — read Conditions: Ready, MemoryPressure, DiskPressure, PIDPressure. Each is True/False/Unknown.
  3. SSH to the node, check kubelet: systemctl status kubelet and journalctl -u kubelet -n 100 --no-pager.
  4. If kubectl itself won't respond, the API server may be down. Drop to crictl ps -a — it talks to the container runtime directly, no API server needed.

Ready=False means kubelet is running and says it's unhealthy. Ready=Unknown means no heartbeat at all — kubelet may be crashed or unreachable. Different next step: False → read kubelet's logs. Unknown → check if the node is reachable first.

Try it — before looking below

Q1. Why can't kubectl always diagnose a control-plane outage?

kubectl talks to the API server. If the API server's own static pod is down, kubectl has nothing to talk to. Use crictl ps -a on the control-plane node instead — it bypasses the API server.

Q2. What's your first command, cluster-wide, before you even pick a node?

kubectl get events --sort-by=.metadata.creationTimestamp -A — cheap, chronological, often names the object and reason (NodeNotReady, Evicted) before you read a single log.

Reveal the checklist

  1. kubectl get nodes — one node, or several? Several often means something shared (network, control plane, cloud outage).
  2. kubectl describe node <name> — Conditions + Events.
  3. kubectl get events --sort-by=.metadata.creationTimestamp -A — anything around that timestamp.
  4. SSH to the node. systemctl status kubelet — running at all?
  5. journalctl -u kubelet -n 100 --no-pager — expired cert, can't reach API server, disk full, etc.
  6. If kubelet looks fine but pods aren't up: crictl ps -a for runtime-level state.
  7. Fix root cause, re-run kubectl get nodes, confirm Ready.

Hands-on

Pick a Pod in your own cluster and run kubectl get events --sort-by=.metadata.creationTimestamp -n <its-namespace> for real. On managed Kubernetes (e.g. GKE Autopilot) you won't get node/kubelet SSH access — that's expected, it's a boundary the platform manages for you. Just confirm you can read the event stream and spot signal vs. noise.

Source

kubernetes.io/docs/tasks/debug/debug-cluster and kubernetes.io/docs/concepts/architecture/nodes — the exact pages allowed in the real exam.

Recap
  • Funnel: cluster-wide symptom → which node → which component → its logs.
  • kubectl describe node Conditions tell you False (kubelet unhealthy) vs. Unknown (no heartbeat) — different next step.
  • If the API server itself is down, kubectl can't help — use crictl ps -a instead.
