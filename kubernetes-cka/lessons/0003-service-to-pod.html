Service → Pod (ClusterIP)

Why this matters

A Service that silently finds nothing is one of the most common production incidents in Kubernetes, and one of the hardest to notice, because nothing about it looks broken. kubectl apply -f service.yaml succeeds. kubectl get svc shows a healthy-looking ClusterIP. The Pods behind it show Running, zero restarts. And yet every single request fails, because the one field that actually connects a Service to its Pods — spec.selector — doesn't match a label on a single Pod. If you don't understand exactly how a Service decides who its backends are, you'll spend the first ten minutes of that incident looking everywhere except the one place the bug actually lives.

Mental model: a Service is not a router you configure once — it's a live, continuously-recomputed roster. Think of a hospital's on-call board: the board itself doesn't treat anyone, it just lists whoever currently has their pager on and their badge scanned in. A nurse manager walks the floor every few seconds and rewrites that board the instant someone's status changes — clocks out, takes their badge off, steps out of pager range. Kubernetes works the same way: spec.selector is the rule ("anyone wearing this badge"), a control loop continuously re-scans Pods against that rule and keeps the roster (its EndpointSlices) current, and kube-proxy is the switchboard operator who actually routes the call using whatever the roster currently says. This predicts something you may not have seen yet: a Pod doesn't need to crash or get deleted to disappear from a Service. It just needs to stop answering its own health check — the roster updates itself within a second or two, with no kubectl command from you at all.

Core concepts: the Service manifest

The shape is the same four-part object you learned in Lesson 1, specialized for routing:

apiVersion: v1
kind: Service
metadata:
  name: my-nginx-svc
spec:
  type: ClusterIP
  selector:
    app: my-nginx
  ports:
    - name: http
      port: 80
      targetPort: 80
FieldWhat it controls
spec.typeClusterIP is the default — reachable only from inside the cluster's network
spec.selectorMust exactly match a Pod's metadata.labels (same namespace only), or the Service finds nothing
portThe port the Service itself listens on — what clients and other Services dial
targetPortThe port on the Pod traffic is actually forwarded to; defaults to the same value as port if you omit it
nodePortOnly meaningful on type: NodePort (or LoadBalancer) — a port opened on every Node's own IP, from the default range 30000–32767

A single Service can expose more than one port — for example, an application port and a separate metrics port on the same backend Pods. The moment spec.ports has more than one entry, every entry needs its own unique name, because that name is what lets targetPort reference a named container port instead of a bare number, and it's how DNS tells one Service port apart from another (more on that below).

Simple example: no selector match means no traffic, and the Service will not tell you. It's created successfully either way — an empty backend list is a valid, silent state, not an error.

How kube-proxy actually routes ClusterIP traffic

Two separate mechanisms make a Service work, and troubleshooting depends on knowing which one is failing. First, an endpoint control loop keeps the roster current: "the controller for that Service continuously scans for Pods that match its selector, and then makes any necessary updates to the set of EndpointSlices for the Service." That's the part that makes a Service a living roster instead of a list you fill in once. Second, kube-proxy — running on every node — watches the API server for changes to Services and EndpointSlices and keeps a set of local rules on that node in sync with them.

On Linux, the current default proxy mode is iptables. In this mode, kube-proxy "installs a series of iptables rules which redirect from the virtual IP address to more iptables rules, defined per Service. The per-Service rules link to further rules for each backend endpoint, and the per-endpoint rules redirect traffic (using destination NAT) to the backends," and "a backend is chosen (either based on session affinity or randomly) and packets are redirected to the backend without rewriting the client IP address." In plain terms: the ClusterIP isn't bound to any real network interface anywhere — it's virtual. Packets addressed to it get rewritten by the kernel's netfilter subsystem, on the node that sent them, before they ever reach the real Pod IP.

An IPVS mode also exists — "based on netfilter hook function that is similar to iptables mode, but uses a hash table as the underlying data structure and works in the kernel space," which scales better with very large numbers of Services because lookup is closer to constant-time instead of a linear iptables chain. Current Kubernetes docs now mark IPVS mode deprecated (as of v1.35), with a newer nftables mode also available. None of this changes what you write in YAML — it changes what's actually happening on the node when a ClusterIP won't route, which is exactly the layer you drop to once you've ruled out selector and port mismatches.

If you omit spec.selector entirely, Kubernetes assumes you're managing the backend list yourself and doesn't create EndpointSlices automatically — a deliberate pattern for pointing a Service at something outside the cluster, and a confusing one if it happens by accident.

Endpoints don't depend on labels alone, either. A Pod can match the selector perfectly and still be missing from the roster: "if the readiness probe returns a failed state, the EndpointSlice controller removes the Pod's IP address from the EndpointSlices of all Services that match the Pod." The Pod itself stays Running — nothing alarming shows up in kubectl get pods — but it stops receiving traffic the moment it fails its own health check, and it's added back automatically the moment it starts passing again.

By default (sessionAffinity: None), kube-proxy is free to pick a different backend Pod for every new connection. Setting sessionAffinity: ClientIP pins a given client IP to the same backend Pod for a configurable window (sessionAffinityConfig.clientIP.timeoutSeconds, three hours by default) — useful for a client that can't tolerate its session hopping between Pods mid-conversation, but it's not a substitute for making the app itself stateless, and it doesn't survive the backend Pod being replaced.

DNS: how Pods find a Service by name

Every Service also gets a stable DNS name, which is how Pods actually reach each other in practice — not by ClusterIP directly. For a normal Service this takes the form <service>.<namespace>.svc.<cluster-domain> (for example, my-nginx-svc.default.svc.cluster.local), and it "resolves to the cluster IP of the Service." The default cluster domain is cluster.local, configurable per-cluster via the kubelet's --cluster-domain flag and the cluster's own DNS server.

A headless Service (spec.clusterIP: None) gets the exact same DNS name format — but instead of resolving to one virtual IP, "unlike normal Services, this resolves to the set of IPs of all of the Pods selected by the Service." The client gets the raw Pod list back from DNS and picks one itself (or talks to all of them), which is exactly what you want when a client needs a specific backend instance rather than any interchangeable one — the pattern StatefulSets rely on for stable per-replica identity, covered later in this course.

Multi-port, named Services also get DNS SRV records, of the form _<port-name>._<protocol>.<service>.<namespace>.svc.<cluster-domain> — for a regular Service this resolves back to the Service's own port and name; for a headless Service it returns one answer per backing Pod, each with that Pod's own hostname. Most application code just uses the plain Service name and never touches an SRV record directly, but they're worth recognizing for the exam and for the occasional client library that does DNS-based discovery.

Production example

Production note: a real Service almost never selects a bare Pod, for the same reason Lesson 1 covered — Pods get replaced, and a Service you'd have to manually recreate every time a Pod disappears defeats the entire point of having a stable address. In practice a Service sits in front of a Deployment or StatefulSet, and the two are written and reviewed together, in the same pull request. A realistic example: checkout-api exposes two ports through one Service — port: 80 → targetPort: 8080 named http for application traffic, and port: 9100 → targetPort: 9100 named metrics for Prometheus to scrape — both under a single stable name, checkout-api.payments.svc.cluster.local, instead of standing up two separate Services (and two DNS names, and two sets of firewall/NetworkPolicy rules) for one application. This is exactly why the port-naming rule from Core concepts exists: targetPort: http and targetPort: metrics only work as names because the Pod's own containerPort entries are named the same way.

Hands-on exercise

Objective

See a broken selector fail silently, then fix it — don't just take the lesson's word for it, reproduce it yourself.

Scenario

You're wiring up a Service for a Pod, but mistype the selector's value — a one-character difference from the Pod's real label, exactly the kind of typo that survives a quick code review.

Environment assumptions

Any cluster you can kubectl into, no existing resources named web or web-svc in the current namespace.

Commands

kubectl run web --image=nginx:1.29 --labels=app=web
kubectl get pods --show-labels

Save this as web-svc.yaml — the selector doesn't match the Pod's label, on purpose:

apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: ClusterIP
  selector:
    app: webapp
  ports:
    - port: 80
      targetPort: 80

kubectl apply -f web-svc.yaml
kubectl get svc web-svc
kubectl get endpoints web-svc

Expected result

kubectl get svc web-svc shows a normal, healthy-looking ClusterIP — nothing about it looks wrong. kubectl get endpoints web-svc shows <none>. The apply succeeded, the Service exists, and it routes to nothing.

Verification

Fix the selector to match, re-apply, and confirm the endpoint appears:

# edit web-svc.yaml: change "app: webapp" to "app: web"
kubectl apply -f web-svc.yaml
kubectl get endpoints web-svc

You should now see one entry, <pod-ip>:80. If you still see <none>, run kubectl get pod web --show-labels and compare the exact key and value against spec.selector character by character.

Common failure

Assuming that no errors from kubectl apply means the Service is working. Applying a Service never validates that it actually matches anything — the API server only checks that the YAML is well-formed.

Troubleshooting

Selectors only match Pods in the same namespace as the Service. If you applied the Service into a different namespace than the Pod (for example, by adding -n to one command and not the other), you'll see the exact same empty-endpoints symptom for a completely different reason.

Cleanup / rollback

kubectl delete pod web --ignore-not-found
kubectl delete svc web-svc --ignore-not-found

Production lesson

Nothing in the normal "did my apply succeed" workflow catches this. kubectl get endpoints is the one command that actually proves a Service found its Pods — get in the habit of running it every time you create or change a Service, not only once something's already on fire.

Failure scenario

A realistic incident where the Service and its selector are both already correct — the exercise above wouldn't have caught this one.

  1. 09:14 Alert fires: the ingress controller reports a rising 502 rate for checkout-api. On-call checks kubectl get pods -l app=checkout-api — all 3 Pods Running, 0 restarts, READY 1/1.
  2. 09:16 kubectl get endpoints checkout-api shows 3 entries, all 3 Pod IPs, port 8080. That rules out a selector mismatch — the Service found exactly the Pods it should have.
  3. 09:19 kubectl describe pod on all three shows Ready: True and no probe failures in Events. That rules out a readiness problem too — every matched Pod is genuinely eligible for traffic.
  4. 09:23 On-call runs kubectl port-forward pod/checkout-api-7d9f4 8080:8080 and curls localhost:8080 directly — connection refused. The Pod itself is unreachable on 8080, independent of the Service entirely.
  5. 09:26 kubectl get pod checkout-api-7d9f4 -o jsonpath='{.spec.containers[0].ports}' shows containerPort: 8081. Last night's deploy changed the app's listen port via an environment variable, but the PR never touched the Service's targetPort, which still reads 8080.
  6. 09:29 Fix applied: kubectl edit svc checkout-api, change targetPort from 8080 to 8081.
  7. 09:31 Verified: kubectl get endpoints checkout-api now lists all 3 Pod IPs on port 8081; the ingress 502 rate drops to zero within a minute.

Troubleshooting workflow

The general 10-step method, applied specifically to "a Service isn't routing traffic to my Pods":

  1. Confirm the symptom. Actually test it — kubectl run debug --image=busybox --restart=Never -it --rm -- wget -qO- http://<service>.<namespace>.svc.cluster.local from inside the cluster. Don't diagnose from a dashboard alone; find out whether it's a timeout, a refusal, or wrong data coming back.
  2. Define scope. Is every client failing, or only some? (sessionAffinity: ClientIP can pin one unlucky client to one bad Pod while everyone else is fine.) Is it one Service, or every Service on this node — the latter points at kube-proxy or the node's network, not your manifest.
  3. Check recent changes. kubectl get events --sort-by=.lastTimestamp -n <namespace>, and diff the Service and Deployment manifests against the last deploy. A changed label, a changed container port, and a changed targetPort are the three most common causes, and none of them show up as an error anywhere.
  4. Inspect the right state. kubectl get endpoints <service> first — empty means selector mismatch, partial means some Pods aren't ready, full-but-still-failing means a port or app-level problem. Then kubectl describe svc <service> to see Selector, Port, and TargetPort side by side, and kubectl get pods --show-labels -l <selector> for the Pods' actual labels.
  5. Form a hypothesis. For example: "the Service and Pod both look healthy, so this is probably a targetPort mismatch, not a selector problem."
  6. Test one variable. kubectl port-forward pod/<name> <targetPort>:<targetPort> and connect straight to the Pod, bypassing the Service entirely — this tells you whether the fault is in the Service's config or in the Pod/app itself.
  7. Apply the safest fix. Change exactly the one field the evidence points to — selector, targetPort, or the probe — not several at once, so you know which change actually fixed it.
  8. Verify recovery. Re-check kubectl get endpoints shows the expected IPs and re-run the actual traffic test from step 1. A correct-looking endpoint list is not the same as working traffic.
  9. Document the root cause. Write down the exact field and value that was wrong ("targetPort: 8080, app now listens on 8081") — "the Service was misconfigured" isn't specific enough to prevent a repeat.
  10. Prevent recurrence. Require Service and Deployment port changes to ship in the same pull request, and alert on endpoint count dropping to zero for any Service on a critical path — don't rely on Pod-level restart counts alone, since this entire failure mode never restarts anything.

Security note: type: ClusterIP means "not reachable from outside the cluster's network" — it does not mean "access controlled." By default, any Pod in any namespace on the same cluster can resolve and connect to any ClusterIP Service, regardless of which team owns it. ClusterIP keeps the internet out; it does nothing to keep one workload from reaching another workload it has no business talking to. That's what NetworkPolicy is for (Lesson 10) — don't mistake "internal-only" for "isolated."

Reliability note: a Service with zero endpoints doesn't fail loudly. There's no crash, no non-zero exit code, no restart counter to watch — the Service object itself reports perfectly healthy the entire time every request against it is failing. Because "endpoint count" doesn't surface in the metrics teams usually watch first (Pod restarts, CPU, memory), it's worth an explicit alert on endpoint/EndpointSlice count reaching zero for any Service on a critical path, rather than assuming Pod-level health checks would have caught it.

Common mistake: mixing up port and targetPort. port is what clients dial; targetPort is what the container actually listens on. Get them backward — or change one without the other after an app's listen port changes — and you get a Service with a full, correct-looking endpoint list that still refuses every connection, because nothing on the Pod is listening where the Service is aiming.

Common mistake: a label typo in spec.selector that survives review because it's easy to eyeball two YAML files and miss one wrong character (app: my-nginx vs. app: nginx, or a leftover env: stage from a copy-pasted manifest). The match is exact-string and case-sensitive, with no partial credit — and it only checks Pods in the Service's own namespace, so a Service and its Pods living in different namespaces show the identical empty-endpoints symptom even with perfectly matching labels.

Decision guide

OptionUse whenAvoid whenTrade-off
ClusterIPInternal Pod-to-Pod or Service-to-Service traffic — most backend communicationTraffic must originate from outside the clusterNot reachable externally without an Ingress or gateway layered on top
NodePortQuick manual/external access for a demo or dev cluster, or infra that can only reach node IPsReal production external traffic, or when a proper load balancer is availableOpens a fixed port on every node, from a limited port range; not itself highly available
LoadBalancerCloud-hosted cluster, need a real externally routable, health-checked IPBare-metal without a cloud/MetalLB integration, or traffic already fronted by a shared IngressTypically provisions (and bills) one cloud load balancer per Service
Headless (clusterIP: None)Client needs each Pod's own identity — peer discovery, StatefulSet members addressing each other directlyYou just want ordinary, don't-care-which-backend load balancingNo built-in load balancing at all; the client has to handle the Pod list itself

Default recommendation: reach for ClusterIP unless you have a specific, stated reason to expose externally (LoadBalancer, or an Ingress in front of a ClusterIP) or need per-Pod identity (headless). Most Services in a real cluster are ClusterIP, and that should be your starting assumption too.

Knowledge check

Q1. You create a Service and see no errors. What command tells you whether it actually found any Pods?

kubectl get endpoints <service-name> — an empty result means the selector matched nothing.

Q2. A Service has port: 80 and targetPort: 9376. Which port does a client calling the Service actually connect to?

A. Clients always dial port — targetPort is only where kube-proxy forwards the traffic to on the Pod, invisible to the caller.

Q3. Which kube-proxy mode is the current default on Linux nodes for implementing ClusterIP routing?

A. iptables is the current Linux default. IPVS is now marked deprecated in the docs; nftables is a newer option; userspace mode is long obsolete.

Q4. A Service has clusterIP: None and a selector matching 3 Pods. What does its DNS name resolve to?

B. A headless Service's DNS name resolves to the set of every matching Pod's IP directly — there's no single virtual IP to hand back.

Directly scored under Services & Networking (20%) — one of the exam's two largest domains. Expect to write ClusterIP Service manifests from memory, use kubectl expose, and diagnose a broken endpoint live, under time pressure, using nothing but kubectl and the doc pages linked below.

Production challenge

Objective

Diagnose and fix a Service that has the right selector, a Pod that's genuinely Running, and still shows zero entries in its endpoints — using the troubleshooting workflow above, not this lesson's earlier exercise.

Scenario

A teammate fronts an nginx Pod with a readiness probe (a real production habit — never skip the probe once a Service depends on the Pod). Monitoring shows the target flapping "down" even though kubectl get pods says Running, 0 restarts.

Environment assumptions

A kind/minikube cluster, no existing resources named app-check.

Commands

Build the broken setup first. Save this as app-check.yaml — the probe path is wrong on purpose, a path stock nginx doesn't serve:

apiVersion: v1
kind: Pod
metadata:
  name: app-check
  labels:
    app: app-check
spec:
  containers:
  - name: app-check
    image: nginx:1.29
    ports:
    - containerPort: 80
    readinessProbe:
      httpGet:
        path: /healthz
        port: 80
      periodSeconds: 5

kubectl apply -f app-check.yaml
kubectl expose pod app-check --port=80 --target-port=80 --name=app-check-svc
# wait ~15s for a few probe cycles, then diagnose:
kubectl get pods app-check
kubectl get endpoints app-check-svc
kubectl describe pod app-check

Expected result

kubectl get pods shows app-check Running, READY 0/1. kubectl get endpoints app-check-svc shows <none> — the Pod is fully matched by the selector but absent from the endpoint list. kubectl describe pod shows a failing Readiness probe against /healthz in its Events (nginx returns 404, outside the probe's success range).

Verification

Pod fields like readinessProbe are immutable once a Pod is running — delete and recreate with the corrected path rather than trying to patch it in place:

# edit app-check.yaml: change path: /healthz to path: /
kubectl delete pod app-check
kubectl apply -f app-check.yaml
kubectl get endpoints app-check-svc --watch

Within a couple of probe cycles, app-check-svc's endpoint list should populate with the Pod's IP on port 80.

Common failure

Assuming the Service or its selector is broken and rewriting spec.selector or spec.ports — neither is the problem here. The Service configuration was correct the whole time; the Pod was voluntarily excluding itself by failing its own health check.

Troubleshooting

If the endpoint still doesn't appear after the fix, re-check kubectl describe pod app-check's Events for a different readiness failure (typo in the new path, wrong port number), and confirm you didn't leave the old, still-failing Pod running alongside a new one under the same selector.

Cleanup / rollback

kubectl delete pod app-check --ignore-not-found
kubectl delete service app-check-svc --ignore-not-found

Production lesson

This is the failure mode that a "just check if the Pod is Running" mental model misses entirely. Endpoints depend on two independent things being true — label match and readiness — and a real incident review has to check both before declaring the Service itself broken.

Recap
  • A Service is a continuously-recomputed roster, not a static pointer — a control loop re-scans Pods against spec.selector on an ongoing basis, and kube-proxy programs the node's kernel (iptables by default) to route ClusterIP traffic to whatever's currently on that roster.
  • port is what clients dial; targetPort is what the container listens on (defaults to port if omitted); nodePort only applies to NodePort/LoadBalancer types, from the 30000–32767 range by default.
  • A failed readiness probe removes a Pod's IP from the Service's endpoints automatically, even though the Pod stays Running — endpoints depend on label match and readiness, not labels alone.
  • kubectl get endpoints <service> is the one command that proves a Service actually found Pods — a clean kubectl apply proves nothing about that.
  • ClusterIP means "not reachable from outside the cluster," not "access controlled" — anything already inside the cluster can still reach it unless a NetworkPolicy says otherwise.
  • Default to ClusterIP unless you have a specific, stated reason to reach for NodePort, LoadBalancer, or a headless Service.
