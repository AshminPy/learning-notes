Service → Pod (ClusterIP)

In Lesson 2 you put labels on a Pod. That was the setup, not the point. The point is this: a Service is a stable address that finds a moving target — a set of Pods that come and go, get rescheduled, and change IP every time — purely by matching the labels you already wrote.

Tied to your mission: in production this is exactly how one workload finds another inside a cluster — no hardcoded Pod IPs, no per-Pod config. Get the selector-to-label link solid here and Ingress and NetworkPolicy (both label-driven) will click much faster later.

The mental model

A Service is not a proxy you install on each Pod, and it's not a load balancer you configure by pointing at IPs. It's an object with its own stable virtual IP and DNS name. Kubernetes constantly watches for Pods matching the Service's selector and keeps an internal list of "who currently qualifies" up to date. Traffic to the Service gets spread across whatever Pods are on that list right now.

ClusterIP is the default Service type — and the one you'll use most. It's reachable only from inside the cluster. That's the right scope for Pod-to-Pod traffic (frontend calling backend, app calling database) where nothing outside the cluster needs to see it.

The whole mechanism is one match: spec.selector on the Service has to equal the metadata.labels you put on the Pod. No selector match, no traffic — the Service exists but is silently empty. This is the payoff of Lesson 2.

Try it first — before reading on

Q1. Which field on a Service has to match which field on a Pod for the Service to find it?

the Service's spec.selector must match the Pod's metadata.labels (key and value, exact match)

Q2. You create a Service and it looks fine — no errors. What command tells you whether it actually found any Pods?

kubectl get endpoints <service-name> (or kubectl get ep) — if the list is empty, the selector didn't match any Pod's labels

Q3. What's the full DNS name a Pod would use to reach a Service called my-service in the default namespace?

my-service.default.svc.cluster.local — pattern is <service>.<namespace>.svc.cluster.local

Now build it — in your terminal, not here

Write a ClusterIP Service manifest by hand — no copy-paste. It needs to:

  • select the Pod you built in Lesson 2, using the exact labels you put on it (not the Pod's name — selector matches labels, never the name field)
  • be type ClusterIP (or omit type entirely — it's the default)
  • expose a port and forward it to the port your container listens on
  • have its own name, separate from the Pod's name

Apply it, then before checking the answer below, run kubectl get endpoints <your-service-name> yourself and confirm it lists your Pod's IP. If it's empty, that's real signal — go compare your selector against your Pod's actual labels before reading on.

Reveal the reference answer

apiVersion: v1
kind: Service
metadata:
  name: my-nginx-svc
spec:
  type: ClusterIP
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80

This assumes your Lesson 2 Pod carries the label app: nginx. If you used a different key or value, your selector must match whatever you actually wrote — there's no default or fallback, just an exact key/value match against the Pod's labels.

Primary source

Read (or at least skim) the official docs — the exact page you're allowed to search during the real exam: kubernetes.io/docs/concepts/services-networking/service. For the DNS naming rules specifically: kubernetes.io/docs/concepts/services-networking/dns-pod-service.

Recap
  • A Service = a stable virtual IP + DNS name that load-balances to whatever Pods currently match its selector — it doesn't sit "on" a Pod
  • spec.selector on the Service must exactly match metadata.labels on the Pod — that's the entire mechanism
  • ClusterIP is the default type: internal-only, for Pod-to-Pod traffic inside the cluster
  • kubectl get endpoints <service> is how you check a Service actually found Pods — an empty list means the selector didn't match
  • DNS name: <service>.<namespace>.svc.cluster.local
