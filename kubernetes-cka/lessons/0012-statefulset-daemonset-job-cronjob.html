Kubernetes / CKA — Lesson 12 of 17

StatefulSet, DaemonSet, Job, CronJob

This is the last lesson of the core manifest stack — after this, the mission moves to Cluster Architecture and then Troubleshooting. Everything so far has been one controller, Deployment, used every way it can be used. This lesson is different: four controllers, each solving one specific problem Deployment can't. The goal here is breadth, not depth — know what each one is for and the one field that defines it, well enough to reach for the right tool on exam day.

The pattern break: when Deployment isn't enough

A Deployment's Pods are interchangeable, disposable, and meant to stay running forever. Each of these four controllers breaks one of those assumptions on purpose.

StatefulSet — when replica identity matters

Kill a Deployment's Pod and a replacement comes up with a new, random name — nothing about "which one" ever mattered. StatefulSet exists for the opposite case: each replica keeps a stable identity across restarts and rescheduling.

  • Predictable Pod names: web-0, web-1, web-2 — the pattern is $(statefulset name)-$(ordinal), not a random suffix.
  • Each Pod gets a matching stable DNS name, but only because a headless Service (clusterIP: None) is pointed at it — StatefulSet doesn't create this Service for you, you have to write it.
  • Add volumeClaimTemplates and each replica also gets its own PersistentVolumeClaim that follows that specific Pod — web-0 gets its volume back after rescheduling, not whichever one happens to be free.

Reach for this when: replica identity is part of correctness — databases, anything with per-replica state (leader election, sharding).

You run GKE Autopilot with Crossplane provisioning CloudSQL outside the cluster — the database's identity and storage already live outside Kubernetes entirely. That's exactly why you've never needed a StatefulSet in production. This is genuinely new ground, not review.

DaemonSet — exactly one Pod per node

No replicas field at all. A DaemonSet's job: keep one matching Pod running on every node (or every node matching a nodeSelector/affinity rule), automatically, as nodes join or leave the cluster.

Reach for this when: you need a node-level agent, not an application replica — log collectors, monitoring agents (node-exporter), CNI/networking components. These exist once per node by definition, not "N copies somewhere."

Job — run to completion, not "keep it up"

A Deployment treats a dead Pod as a failure to fix. A Job inverts that: it runs Pod(s) until the task succeeds, then stops. It tracks completions, not uptime.

  • completions — how many successful Pod completions the Job needs before it's considered done.
  • parallelism — how many Pods can run at once while working toward that count.
  • backoffLimit — how many times a failed Pod is retried before the Job gives up and marks itself failed. Defaults to 6.

Reach for this when: the work has a defined end — a migration, a batch export, a one-off script.

CronJob — a Job on a schedule

A CronJob is a thin wrapper: it creates a new Job at each scheduled time, using standard cron syntax in .spec.schedule (e.g. 0 3 * * * = every day at 3 AM).

The field worth knowing cold: concurrencyPolicy — what happens if the previous run is still going when the next scheduled time hits:

  • Allow (default) — let them overlap, both run.
  • Forbid — skip the new run if the old one hasn't finished.
  • Replace — kill the old run, start the new one.

Reach for this when: a Job needs to repeat on a timer — backups, report generation, cleanup sweeps.

Try it first — before reading on

Q1. Which of the four gives each replica a stable, predictable name and its own storage that follows it across rescheduling?

StatefulSet — Pod names follow $(name)-$(ordinal) (e.g. web-0), and volumeClaimTemplates gives each ordinal its own PersistentVolumeClaim that follows it across rescheduling.

Q2. What field controls how many times a Job retries a failing Pod before giving up, and what does it default to?

backoffLimit. It defaults to 6 if not set.

Q3. A CronJob's previous run is still executing when the next scheduled time arrives. Name the three concurrencyPolicy values and what each one does.

Allow (default) — both runs execute concurrently. Forbid — the new run is skipped. Replace — the old run is killed and replaced by the new one.

Now build it — in your terminal, not here

Of the four, Job is the simplest to hand-write end to end — write one by hand, no copy-paste, that runs a single one-off task to completion. Requirements:

  • kind: Job, with a name.
  • A Pod template with one container — any image that exits on its own is fine (e.g. busybox running a short command).
  • restartPolicy set to a value a Job actually allows (a Job cannot use Always — check the docs for why, and what it can use instead).
  • An explicit backoffLimit — don't rely on the default, set it yourself so you know exactly what it does.

Apply it, then run kubectl get jobs and kubectl get pods — watch the Pod go from Running to Completed, and the Job show 1/1 under COMPLETIONS. Don't peek below until you've written something.

Reveal the reference answer

apiVersion: batch/v1
kind: Job
metadata:
  name: one-off-task
spec:
  backoffLimit: 2
  template:
    spec:
      containers:
        - name: task
          image: busybox
          command: ["echo", "job ran to completion"]
      restartPolicy: Never

Bring what you wrote back to your notes — check that you used restartPolicy: Never or OnFailure (not Always — a Job that never stops restarting can never be "complete"), and that your backoffLimit is a number you chose, not one you left out.

Recap
  • StatefulSet: stable per-replica name + DNS (via a headless Service) + storage that follows the replica. Use when replica identity matters.
  • DaemonSet: no replicas field — one Pod per matching node, automatically. Use for node-level agents.
  • Job: runs to completion, not forever. completions/parallelism define the target, backoffLimit (default 6) caps retries.
  • CronJob: a Job on a schedule. concurrencyPolicy (Allow/Forbid/Replace) decides what happens on overlap.

Try solo: turn your Job into a CronJob that runs the same task every minute (*/1 * * * *), with concurrencyPolicy: Forbid. Watch kubectl get cronjobs,jobs,pods over a few minutes and confirm a new Job only starts once the previous one has finished. Don't reopen this file to check — bring it to your notes instead.
