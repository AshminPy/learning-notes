Kubernetes / CKA — Lesson 12 of 24

StatefulSet, DaemonSet, Job, CronJob

Why this matters

The most expensive mistake in this lesson is running a database as a Deployment because a Deployment is what you already know. It looks fine in a demo — three replicas, all Running, a Service load-balancing across them. Then a node drains for a routine upgrade, or someone does a rolling restart to pick up a config change, and Kubernetes recreates the Pods in whatever order it feels like, each with a fresh name, a fresh PVC binding (or none at all if you didn't template one per replica), and no guarantee the old primary comes back before the replicas do. For a stateless API that's a non-event. For Postgres, Elasticsearch, Kafka, or anything that elects a leader or tracks per-node data, that's a quorum loss or a split-brain incident — and it happens precisely because a Deployment was never designed to answer the question "which replica is this, and does it matter." StatefulSet, DaemonSet, Job, and CronJob each exist because a Deployment's two core assumptions — Pods are interchangeable, and Pods run forever — are wrong for a specific class of workload. Knowing which one you're in front of, before you write the manifest, is the actual skill this lesson teaches.

Mental model: a Deployment answers "how many copies of this do I want running?" The other four controllers each override that question with a more specific one. StatefulSet asks: does each replica need its own name, and does order matter? — yes, so Pods get numbered (web-0, web-1...) and are created, scaled, and terminated one at a time, in order. DaemonSet asks: does every node need exactly one? — so there's no replicas field at all; the fleet size is however many nodes match. Job asks: does this run once and then stop? — success ends it, not a restart. CronJob asks: does this run once, but on a schedule? — it's a Job factory, not a long-running Pod. Test this model against a case you haven't seen: if someone asks "what happens if I scale a DaemonSet to replicas: 5," the answer falls out immediately — there's no such field, because the question a DaemonSet answers was never "how many," it was "which nodes."

Core concepts

StatefulSet — ordered identity, ordered lifecycle

A StatefulSet's Pods get predictable names — $(statefulset name)-$(ordinal), so a StatefulSet named web with three replicas produces web-0, web-1, web-2. That naming is only half the mechanism; the other half is ordering, controlled by .spec.podManagementPolicy:

  • OrderedReady — the default. The controller launches Pods in ascending order (0, 1, 2...), and waits for each Pod to be Running and Ready before launching the next one. Scaling down or deleting the set terminates Pods in reverse ordinal order (N, N-1, ..., 0), waiting for each to fully terminate before touching the next.
  • Parallel — launches and terminates all Pods at once, no ordering or readiness gating between them. You opt into this when replicas genuinely don't depend on each other's startup order.

Rolling updates follow the same ordering logic, controlled separately by .spec.updateStrategy: the default is RollingUpdate, and it updates Pods from highest ordinal to lowest — web-2 first, then web-1, then web-0 last. You can further restrict this with .spec.updateStrategy.rollingUpdate.partition: set it to 2 and only Pods with ordinal ≥ 2 get the new template on update; anything below the partition is left alone, and even if you delete one of those lower-ordinal Pods, it comes back running the old template. That's the mechanism behind a manual canary rollout on a StatefulSet — update one replica, watch it, then lower the partition to roll further.

None of this identity is useful without stable network addressing, which is why a StatefulSet requires you to create a headless Service yourself (clusterIP: None, referenced by .spec.serviceName) — the docs are explicit that "you are responsible for creating this Service," it is not generated for you. Combine the Service's domain ($(service name).$(namespace).svc.cluster.local) with a Pod's hostname ($(statefulset name)-$(ordinal)) and each replica gets its own resolvable, stable DNS name — for the docs' own example, web-0.nginx.default.svc.cluster.local always means the same replica, no matter how many times that Pod has been rescheduled.

Storage follows the same stability contract. volumeClaimTemplates creates one PersistentVolumeClaim per replica (named $(template name)-$(statefulset name)-$(ordinal), e.g. www-web-0), and that PVC is bound to that ordinal for the life of the StatefulSet — delete web-0 and its replacement mounts the same PVC, not a new empty one. Deleting or scaling down the StatefulSet does not delete these PVCs either; Kubernetes treats data safety as more important than automatic cleanup, so orphaned PVCs from old replicas are a real, verified cost/cleanup item, not a hypothetical.

DaemonSet — one Pod per matching node, no replica count

A DaemonSet has no replicas field. Instead it uses a node selector or affinity rule (or none, meaning "every node"), and the controller's job is to converge the cluster to exactly one matching Pod per matching node — add a node, it gets a Pod automatically; remove a node, its Pod goes with it.

Updates default to .spec.updateStrategy.type: RollingUpdate, throttled by maxUnavailable, which defaults to 1 — meaning by default only one node's DaemonSet Pod is down for update at any given moment, and the controller proceeds to the next node only after that one comes back. This matters directly for blast radius: a bad DaemonSet image doesn't hit every node simultaneously during a rollout — it's gated one node (or whatever percentage you set) at a time, same mechanism as a Deployment's rolling update, just node-scoped instead of replica-scoped.

The DaemonSet controller also automatically adds a specific, narrow set of tolerations to every DaemonSet Pod so it can run on nodes a normal Pod would be evicted from or excluded from: node.kubernetes.io/not-ready and node.kubernetes.io/unreachable (both NoExecute — so DaemonSet Pods aren't evicted when a node goes unhealthy), and node.kubernetes.io/unschedulable (NoSchedule). What it does not add automatically is a toleration for the control-plane taint (node-role.kubernetes.io/control-plane:NoSchedule). If you want a DaemonSet's Pods running on control-plane nodes too, you add that toleration to the Pod template yourself — the official example manifest even carries a comment saying exactly that: these tolerations are there to make the DaemonSet run on control-plane nodes, remove them if you don't want that.

Job — run to completion, not forever

A Job tracks successful completions, not liveness. Three fields do the real work: completions (how many successful Pod completions the Job needs before it's done), parallelism (how many Pods may run at once while working toward that count), and .spec.backoffLimit, which defaults to 6 — the number of retries allowed before the Job is marked failed. Job Pods must use a restartPolicy of Never or OnFailure; Always (the Pod default) is not allowed, because a Job pod that always restarts in place could never report a completion or a countable failure back to the Job controller.

.spec.activeDeadlineSeconds is a separate, independent ceiling: the duration, in seconds relative to the Job's start time, that it may stay continuously active before the system tries to terminate it — regardless of how many retries backoffLimit has left. A Job with a generous backoffLimit but no activeDeadlineSeconds can retry quietly for hours against a hung dependency; setting a deadline is how you put a hard wall-clock cap on that, independent of the retry count.

CronJob — a Job factory on a schedule

A CronJob creates a new Job object at each scheduled time from standard 5-field cron syntax in .spec.schedule (minute, hour, day-of-month, month, day-of-week — e.g. 0 3 * * * is daily at 3 AM; macros like @daily and @hourly are also accepted). .spec.concurrencyPolicy decides what happens if the previous run's Job is still active when the next scheduled time arrives:

  • Allow (default) — the CronJob allows concurrently running Jobs. Nothing stops a second, third, or fourth overlapping run from starting.
  • Forbid — the CronJob skips the new run if the previous one hasn't finished. When the previous run does finish, startingDeadlineSeconds is still honored and may still trigger a fresh run.
  • Replace — the still-running Job is replaced by a new one at the next scheduled time.

.spec.startingDeadlineSeconds is a separate safety valve: if a Job misses its scheduled start time by more than this many seconds (a control-plane outage, for example), the CronJob controller counts it as missed and skips that occurrence rather than trying to catch up. The docs are explicit that CronJob scheduling is only approximate — "in certain circumstances, a single CronJob can create multiple concurrent Jobs" even outside of a deliberate Allow policy — so treat exact once-per-schedule execution as a best effort, not a guarantee, and design the job itself to tolerate being run more than once.

Production example

Production note: a 3-node Postgres cluster (one primary, two streaming replicas) is a textbook StatefulSet: pg-0 is always the same identity, always the same PVC, and the team wires up pg-0 specifically as the primary via an init script that checks the Pod's own ordinal. The headless Service gives every replica a stable DNS name the replication config can reference directly, instead of chasing Pod IPs. The reason this has to be a StatefulSet and not a Deployment isn't storage alone — a Deployment can use one PVC per replica too, with enough care — it's the ordering guarantee. When the team rolls out a Postgres minor-version bump, RollingUpdate's default highest-to-lowest ordinal order means the replicas (pg-2, pg-1) get updated and verified healthy first, and the primary (pg-0) only goes last — so if the new image is bad, it's caught on a replica, not the primary, and quorum is never at risk mid-rollout. A Deployment's rolling update has no concept of "which one is the primary" to protect — that's the entire gap StatefulSet closes.

Hands-on exercise — StatefulSet

Objective

Prove that a StatefulSet Pod's replacement keeps the same name and reattaches to the same PVC — don't take the lesson's word for it.

Scenario

You're about to depend on "stable storage per replica" for a real workload. Confirm it actually behaves that way before you trust it in production.

Environment assumptions

Any cluster you can kubectl into (kind/minikube is fine) with a default StorageClass available, no existing objects named web or nginx in the current namespace.

Commands

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Service
metadata:
  name: nginx
  labels:
    app: nginx
spec:
  ports:
  - port: 80
    name: web
  clusterIP: None
  selector:
    app: nginx
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: "nginx"
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.29
        ports:
        - containerPort: 80
          name: web
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: www
    spec:
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 1Gi
EOF

kubectl get pods -l app=nginx -w
# Ctrl-C once you see web-0, web-1, web-2 all Running — note they came up in that order

kubectl get pvc -l app=nginx
kubectl get pod web-0 -o jsonpath='{.metadata.uid}{"\n"}'
echo "hello from web-0" > /tmp/marker.txt
kubectl cp /tmp/marker.txt web-0:/usr/share/nginx/html/marker.txt

kubectl delete pod web-0
kubectl get pods -l app=nginx -w
# Ctrl-C once web-0 is Running again

kubectl get pod web-0 -o jsonpath='{.metadata.uid}{"\n"}'
kubectl get pvc -l app=nginx
kubectl exec web-0 -- cat /usr/share/nginx/html/marker.txt

Expected result

Pod names came up in strict order — web-0 reaches Running before web-1 is created, web-1 before web-2. The PVC list shows three claims named www-web-0, www-web-1, www-web-2. After deleting web-0, the replacement Pod is named web-0 again — same name, but a different UID (it's a new Pod object) — and cat marker.txt still prints hello from web-0, proving the new Pod mounted the same PVC rather than a fresh empty one.

Verification

The UID change plus the surviving file is the actual proof — a same name with different UID confirms this is a genuinely new Pod object, not something that failed to terminate, and the surviving marker file confirms the PVC (not just the name) followed the ordinal.

Common failure

Watching only the Pod name and concluding "nothing happened" — the name staying web-0 is expected and not itself proof of anything; the UID change and the marker file are what actually demonstrate replacement-with-reattachment versus an in-place restart.

Troubleshooting

If the new web-0 Pod sticks in Pending instead of Running, check kubectl describe pod web-0 for a scheduling failure — a common cause in kind/minikube is the PVC being bound to a node-local volume from a node the scheduler didn't pick for the replacement Pod. That's a real, verified limitation of node-local default StorageClasses, not a StatefulSet bug.

Cleanup / rollback

kubectl delete statefulset web
kubectl delete pvc -l app=nginx
kubectl delete service nginx

Production lesson

This is the exact guarantee the Postgres example above depends on: replica identity and its storage survive Pod replacement. If you had run the same experiment against a Deployment with one shared PVC (ReadWriteOnce, no volumeClaimTemplates), a second replica couldn't even mount it — this exercise is why "just use a Deployment with a volume" doesn't scale past one replica for stateful workloads.

Failure scenario — CronJob

A realistic incident built directly from concurrencyPolicy: Allow being the default — nobody set it deliberately, it's just what happens when nobody thinks about it.

  1. 02:00 A CronJob named nightly-report fires on schedule (0 2 * * *), querying the reporting database and writing a summary table. It normally finishes in about 12 minutes. concurrencyPolicy was never set, so it's Allow.
  2. 02:00 Unnoticed change from last week: the reporting database grew 4x, and the query the Job runs now takes over an hour instead of 12 minutes. Nobody updated the CronJob when the data grew.
  3. 03:00 The next scheduled run fires. The 02:00 run is still active. Because concurrencyPolicy is Allow, a second Job starts anyway, running the same expensive query against the same database at the same time.
  4. 03:41 Database connection pool alerts start firing — both Jobs are holding long-running connections and competing for the same rows, and now application traffic is being starved of connections too. On-call is paged for "API returning 503s," not "CronJob."
  5. 04:00 A third overlapping run fires. Three concurrent copies of the same expensive query are now active. The database's CPU is pegged; the original nightly report still hasn't finished from any of the three runs.
  6. 04:12 On-call runs kubectl get jobs -l app=nightly-report and finds three Jobs, all still Active, all created by the same CronJob. The actual root cause surfaces: not a database problem, a scheduling-overlap problem.
  7. 04:15 Immediate fix: kubectl delete job on the two newer runs to free the connection pool, letting the original run finish.
  8. 04:30 Real fix applied: concurrencyPolicy: Forbid added to the CronJob spec, plus an activeDeadlineSeconds on the underlying Job template so a genuinely stuck run gets killed instead of accumulating forever.

The CronJob itself never failed — every individual run would have succeeded eventually. The outage was caused entirely by the schedule interval becoming shorter than the job's real runtime, and Allow not being a decision anyone made on purpose.

Troubleshooting workflow — Job

The general ten-step method, applied to "my Job's Pods keep failing and it's not retrying or succeeding the way I expected":

  1. Confirm the symptom. kubectl get job <name> — read the actual COMPLETIONS column (e.g. 0/1) rather than assuming from the Pod list alone; a Job can show several failed Pods while still technically retrying.
  2. Define scope. kubectl get pods -l job-name=<name> — is every attempt failing the same way, or did it succeed once and the Job still isn't marked complete (a sign of a completions misconfiguration, not a Pod failure)?
  3. Check recent changes. kubectl get events --field-selector involvedObject.name=<job-name> --sort-by=.lastTimestamp — did someone change the image, the command, or the resource requests right before this started failing?
  4. Inspect the right state. kubectl describe job <name> — read the Conditions section for a Reason like BackoffLimitExceeded, and cross-check .spec.backoffLimit against how many failed Pods you actually see; also confirm restartPolicy in the Pod template is Never or OnFailure — Always is invalid for a Job and will be rejected at creation, so if the Job exists at all this is usually already fine, but double check a copy-pasted template.
  5. Form a hypothesis. For example: "the container is exiting non-zero every time because of a bad argument, and it's about to hit backoffLimit (default 6) and stop retrying for good."
  6. Test one variable. kubectl logs -l job-name=<name> --previous --tail=50 on the most recent failed Pod — read the actual exit reason before changing anything. Don't edit the Job spec yet.
  7. Apply the safest fix. If backoffLimit is already exhausted, the Job is done retrying — delete it and re-create with the fix rather than editing a dead Job in place (most fields are immutable on an existing Job). If the real issue is a hung dependency, add or lower activeDeadlineSeconds so it fails fast next time instead of quietly retrying for hours.
  8. Verify recovery. kubectl get job <name> -w and confirm COMPLETIONS reaches the value you set, not just that a Pod reached Running.
  9. Document the root cause. Write down the actual Reason string from describe job (e.g. BackoffLimitExceeded) and the underlying cause (bad argument, missing secret, wrong image tag) — "it failed" isn't a root cause.
  10. Prevent recurrence. Set an explicit activeDeadlineSeconds and a deliberate backoffLimit on every Job template going forward instead of relying on the default 6 — a default that's fine for a flaky network call is far too many retries for a Job with a genuinely broken argument.

Security & reliability considerations

Reliability note — StatefulSet: the ordering guarantee (OrderedReady creation/termination, highest-to-lowest rolling updates) is itself the reliability feature, not a side effect. It's also a documented sharp edge: using RollingUpdate with the default OrderedReady Pod management policy can leave the StatefulSet in a broken state that needs manual repair if a Pod update fails mid-rollout and the controller can't safely proceed past it — know that this manual-intervention path exists before you hit it at 3 AM.

Reliability note — DaemonSet: the cluster-wide blast radius people worry about is real but not instant — the default maxUnavailable: 1 throttles a rolling update to one node at a time, so a bad image is normally caught after breaking one node's Pod, not all of them. That protection disappears if someone raises maxUnavailable to speed up a rollout, or if the DaemonSet is being created fresh (not updated) — a first-time rollout of a bad image goes to every matching node immediately, because there's no "previous good version" to roll from.

Reliability note — CronJob: overlap risk (the Failure scenario above) is the main one, but it's compounded by the docs' own caution that scheduling is approximate — "in certain circumstances, a single CronJob can create multiple concurrent Jobs" even without Allow being a deliberate choice. Design every CronJob's workload to be safe to run more than once (idempotent), not just fast — you can reduce overlap with Forbid, but you can't rely on the schedule to guarantee exactly-once execution.

Security note: DaemonSets are the most common legitimate reason to request hostNetwork, hostPath mounts, or a privileged security context in a cluster — log shippers and CNI/monitoring agents genuinely need node-level access. That's exactly why a DaemonSet's Pod spec deserves more RBAC and admission-policy scrutiny than an ordinary Deployment, not less: a compromised DaemonSet Pod potentially has a foothold on every node in the cluster at once, simply because that's what the controller is designed to guarantee.

Common mistake: defaulting to a Deployment for a workload that needs stable per-replica identity (a database, a message broker with per-broker state, anything doing leader election by Pod name) because Deployment is the first controller people learn. The failure doesn't show up in normal operation — it shows up the first time a Pod gets rescheduled, which is exactly the worst time to discover it.

Common mistake: writing a StatefulSet without its headless Service. The StatefulSet still creates Pods fine — web-0, web-1 come up — but per-Pod DNS resolution silently doesn't exist, and anything relying on web-0.<service>... for peer discovery fails at the exact moment you scale or fail over, not at deploy time.

Common mistake: shipping a Job with no activeDeadlineSeconds. A Job with a generous or default backoffLimit and a container that hangs (rather than exits non-zero) can sit "retrying" indefinitely against a dead dependency, consuming a node's resources and never surfacing as a clear failure in monitoring built around exit codes.

Common mistake: assuming a DaemonSet automatically runs on control-plane nodes. It doesn't — the automatic tolerations DaemonSet Pods get cover unhealthy/unreachable/unschedulable nodes, not the control-plane taint. If a node-level agent is missing from your control-plane nodes specifically, check the toleration list before assuming a scheduling bug.

Knowledge check

Q1. Which controller gives each replica a stable name and its own storage that follows it across rescheduling?

StatefulSet — names follow $(name)-$(ordinal), and volumeClaimTemplates gives each ordinal its own PVC that survives Pod replacement.

Q2. A CronJob's previous run is still going when the next scheduled time hits. Name the three concurrencyPolicy values and what each does.

Allow (default) — both run concurrently. Forbid — the new run is skipped. Replace — the old run is killed and the new one starts.

Q3. A StatefulSet's default podManagementPolicy is OrderedReady. In what order are Pods terminated when you scale down?

B. Highest ordinal first — termination runs in reverse order (N, N-1, ... 0), the mirror of the ascending creation order. (Option C describes Parallel mode, not the default OrderedReady.)

Q4. A Job's Pods keep exiting non-zero and kubectl describe job shows BackoffLimitExceeded. What does this tell you, and what field controls it?

The Job retried until it hit .spec.backoffLimit (default 6) and then stopped and marked itself failed — it isn't going to retry again on its own. Fix the underlying cause and re-create the Job rather than waiting for it.

Try it — write a Job by hand

Hands-on

Write a Job manifest by hand (no copy-paste) that runs one task to completion:

  • kind: Job, with a name
  • one container, any image that exits on its own (e.g. busybox with a short command)
  • restartPolicy set to a value Job allows (not Always)
  • an explicit backoffLimit

Apply it. Run kubectl get jobs and kubectl get pods — watch the Pod go Running → Completed, and the Job show 1/1 under COMPLETIONS.

Reveal the reference answer

apiVersion: batch/v1
kind: Job
metadata:
  name: one-off-task
spec:
  backoffLimit: 2
  template:
    spec:
      containers:
        - name: task
          image: busybox
          command: ["echo", "job ran to completion"]
      restartPolicy: Never

Production challenge — DaemonSet

Objective

Diagnose, don't just fix by guessing: a DaemonSet is missing a Pod on one specific node, and you need to find out why using the same method you'd use on a real cluster.

Scenario

A teammate reports: "our log-shipper DaemonSet shows Pods on every worker node, but not on the control-plane node — is that a bug?" You don't yet know if it's expected behavior or a real scheduling failure.

Environment assumptions

A kind/minikube cluster with at least one control-plane node and one worker node. Reproduce the setup first:

cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-shipper
spec:
  selector:
    matchLabels:
      app: log-shipper
  template:
    metadata:
      labels:
        app: log-shipper
    spec:
      containers:
      - name: shipper
        image: busybox
        command: ["sh", "-c", "sleep 3600"]
EOF

Commands

kubectl get pods -l app=log-shipper -o wide
kubectl get nodes
kubectl describe node <control-plane-node-name> | grep -A2 Taints
kubectl get daemonset log-shipper -o jsonpath='{.spec.template.spec.tolerations}'

Expected result

The Pod list shows one Pod per worker node but none on the control-plane node. describe node on the control-plane node shows a taint like node-role.kubernetes.io/control-plane:NoSchedule. The DaemonSet's toleration list is empty (or missing that specific key) — it only has whatever the controller adds automatically (not-ready, unreachable, unschedulable), none of which match the control-plane taint.

Verification

Add the matching toleration to the DaemonSet's Pod template and re-apply; a new Pod should appear on the control-plane node within seconds, confirming the taint/toleration mismatch — not a selector, resource, or image problem — was the root cause.

kubectl patch daemonset log-shipper --type='json' -p='[{"op":"add","path":"/spec/template/spec/tolerations","value":[{"key":"node-role.kubernetes.io/control-plane","operator":"Exists","effect":"NoSchedule"}]}]'
kubectl get pods -l app=log-shipper -o wide

Common failure

Assuming this is a bug in the DaemonSet controller, or that DaemonSets get a free pass onto every node including control-plane nodes by default. They don't — the automatic tolerations are narrowly scoped to node-health states, not role-based taints.

Troubleshooting

If adding the toleration still doesn't produce a Pod, check for a second blocker stacked on the same node — a nodeSelector/affinity rule that explicitly excludes control-plane nodes, or resource requests the control-plane node can't satisfy. A taint/toleration match is necessary but not sufficient if something else in the spec also excludes that node.

Cleanup / rollback

kubectl delete daemonset log-shipper

Production lesson

This exact scenario is why "our monitoring agent isn't running on the control plane" tickets exist — it's almost never a controller bug, it's a taint the DaemonSet's Pod template was never given a toleration for. Check describe node's Taints line and the DaemonSet's tolerations side by side before assuming anything more exotic is wrong.
