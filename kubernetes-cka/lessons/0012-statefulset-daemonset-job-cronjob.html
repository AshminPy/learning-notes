StatefulSet, DaemonSet, Job, CronJob

A Deployment (Lesson 4) assumes three things: Pods are interchangeable, exactly N should run, and they should run forever. Plenty of real workloads break one of those assumptions — a database cares which replica it is, a log agent needs exactly one per node, a migration needs to run once and stop. Four controllers exist because bolting all of that onto Deployment would make it worse at the one job it's actually good at.

Mental model: Deployment Pods are identical, interchangeable workers — any one can do the job. StatefulSet workers wear name tags. DaemonSet posts exactly one guard per building. Job and CronJob run an errand, then stop. Each breaks exactly one Deployment assumption, not all of them — that's why there are four separate controllers instead of one with more flags.

StatefulSet — stable identity

Kill a Deployment Pod, its replacement gets a random name. StatefulSet Pods keep a stable identity instead: predictable names (web-0, web-1, web-2), stable per-Pod DNS (needs a headless Service, clusterIP: None), and volumeClaimTemplates giving each replica its own storage that follows it back after rescheduling. Use for: databases, anything where "which replica" matters.

DaemonSet — one Pod per node

No replicas field — keeps one matching Pod on every node (or every node matching a selector), automatically. Use for: node-level agents — log collectors, monitoring agents, CNI components.

Job — run to completion

A Deployment treats a dead Pod as a failure to fix. A Job runs Pods until they succeed, then stops on purpose. completions — successes needed. parallelism — how many run at once. backoffLimit — retries before giving up (default 6). Use for: migrations, batch exports, one-off scripts.

CronJob — a Job on a schedule

Creates a new Job at each scheduled time (cron syntax, e.g. 0 3 * * * = daily 3 AM). concurrencyPolicy: Allow (default, both run), Forbid (skip new run), Replace (kill old, start new).

Try it

Q1. Which controller gives each replica a stable name and its own storage that follows it across rescheduling?

StatefulSet — names follow $(name)-$(ordinal), and volumeClaimTemplates gives each one its own storage.

Now write your own, by hand: a Job that runs one task to completion, with an explicit backoffLimit. Try before revealing.

Reveal the reference answer

apiVersion: batch/v1
kind: Job
metadata:
  name: one-off-task
spec:
  backoffLimit: 2
  template:
    spec:
      containers:
      - name: task
        image: busybox
        command: ["echo", "job ran to completion"]
      restartPolicy: Never

Common mistake: using a Deployment for a batch job because it's the first controller you learned — a Deployment expects its Pods to keep running, so a container that exits successfully just gets restarted forever, not recognized as "done."

A controlled failure

kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata: { name: always-fails }
spec:
  backoffLimit: 2
  template:
    spec:
      containers:
      - name: task
        image: busybox
        command: ["sh", "-c", "exit 1"]
      restartPolicy: Never
EOF
kubectl get pods -l job-name=always-fails --watch

Predict first: does this retry forever? Observe: exactly 3 Pods total (backoffLimit: 2 = 2 retries after the first attempt), then the Job stops trying — kubectl get job always-fails shows it Failed, not stuck retrying indefinitely.

kubectl delete job always-fails

Production best practices

Production note: set activeDeadlineSeconds on Jobs that touch external systems, so a hung (not failed) task doesn't run forever — backoffLimit only bounds failed attempts, not a single attempt that never exits.

Exam & interview notes

Core to Workloads & Scheduling (15%).

Interview Q: "You need to run a nightly database migration. Which controller, and why not a CronJob-less Job triggered manually?" A: CronJob — it's the only controller with a schedule; a plain Job still needs something else to create it at the right time, which is exactly what CronJob automates.

Recap
  • Each controller breaks exactly one Deployment assumption: StatefulSet (identity), DaemonSet (one per node), Job/CronJob (finite, not forever).
  • StatefulSet: stable name + DNS (via headless Service) + storage that follows the replica.
  • Job runs to completion (backoffLimit, default 6, bounds retries not runtime). CronJob is a Job on a schedule.

Confidence check — answer without looking back:

  • Why not just add a "keep identity" flag to Deployment instead of a separate StatefulSet?
  • When would a DaemonSet be the wrong choice even for a "run on every node" need?
  • What happens to a Job's Pods once backoffLimit is exceeded?
  • How would you verify a CronJob actually ran last night, not just that it's scheduled?
