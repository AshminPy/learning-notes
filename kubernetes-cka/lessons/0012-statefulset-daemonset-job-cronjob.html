Kubernetes / CKA — Lesson 12 of 24

StatefulSet, DaemonSet, Job, CronJob

Four controllers, each breaking one assumption a Deployment makes: that Pods are interchangeable, disposable, and meant to run forever.

Simple example: Deployment Pods are identical workers — any one can do the job. StatefulSet workers wear name tags. DaemonSet posts exactly one guard per building. Job and CronJob run an errand, then stop.

StatefulSet — stable identity

Kill a Deployment Pod, its replacement gets a random name. StatefulSet Pods keep a stable identity instead.

  • Predictable names: web-0, web-1, web-2 — pattern is $(name)-$(ordinal).
  • Stable DNS per Pod, but only if you also write a headless Service (clusterIP: None).
  • volumeClaimTemplates gives each replica its own storage that follows it — web-0 always gets its volume back.

Use for: databases, anything where "which replica" matters.

DaemonSet — one Pod per node

No replicas field. Keeps one matching Pod on every node (or every node matching a selector), automatically.

Use for: node-level agents — log collectors, monitoring agents, CNI components.

Job — run to completion

A Deployment treats a dead Pod as a failure. A Job runs Pods until they succeed, then stops.

  • completions — successful Pod completions needed.
  • parallelism — how many Pods run at once.
  • backoffLimit — retries before giving up. Defaults to 6.

Use for: migrations, batch exports, one-off scripts.

CronJob — a Job on a schedule

Creates a new Job at each scheduled time, using cron syntax in .spec.schedule (e.g. 0 3 * * * = daily at 3 AM).

concurrencyPolicy decides what happens if the previous run hasn't finished:

  • Allow (default) — both run.
  • Forbid — skip the new run.
  • Replace — kill the old run, start the new one.

Try it — before looking below

Q1. Which controller gives each replica a stable name and its own storage that follows it across rescheduling?

StatefulSet — names follow $(name)-$(ordinal), and volumeClaimTemplates gives each one its own storage.

Q2. A CronJob's previous run is still going when the next scheduled time hits. Name the three concurrencyPolicy values and what each does.

Allow (default) — both run. Forbid — new run skipped. Replace — old run killed, new one starts.

Now write your own

Write a Job by hand (no copy-paste) that runs one task to completion:

  • kind: Job, with a name
  • one container, any image that exits on its own (e.g. busybox with a short command)
  • restartPolicy set to a value Job allows (not Always)
  • an explicit backoffLimit

Apply it. Run kubectl get jobs and kubectl get pods — watch the Pod go Running → Completed, and the Job show 1/1.

Reveal the reference answer

apiVersion: batch/v1
kind: Job
metadata:
  name: one-off-task
spec:
  backoffLimit: 2
  template:
    spec:
      containers:
        - name: task
          image: busybox
          command: ["echo", "job ran to completion"]
      restartPolicy: Never

Recap
  • StatefulSet: stable name + DNS (via headless Service) + storage that follows the replica.
  • DaemonSet: no replicas — one Pod per matching node.
  • Job runs to completion (backoffLimit, default 6). CronJob is a Job on a schedule (concurrencyPolicy).
