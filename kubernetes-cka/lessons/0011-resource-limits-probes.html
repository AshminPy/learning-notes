Kubernetes / CKA — Lesson 11 of 24

Resource limits + probes

Why this matters

A missing memory limit is not a small oversight — it's an open invitation for one container to consume every byte of memory on a node, starving every other Pod scheduled there, Guaranteed or not, until the kernel starts killing things more or less at random. A missing or misconfigured readiness probe is just as costly in the opposite direction: Kubernetes will happily route real user traffic to a Pod the instant its container process starts, whether or not the app inside has actually finished loading its config, warmed its cache, or opened a database connection — and the first users to hit it get errors, not a graceful wait. Both failure modes look identical from the outside ("the app is broken") but have completely different root causes and completely different fixes, which is exactly why the CKA exam — and real on-call rotations — test them together.

Mental model: requests is a promise to the scheduler — "reserve this much space for me before you place me on a node." limits is a promise enforced by the kernel and the kubelet — "never let me use more than this, once I'm running." These are two separate guarantees, checked at two separate moments, by two separate enforcers. That single fact predicts something that looks like a contradiction the first time you see it: a Pod can be scheduled perfectly fine — its requests fit comfortably on the node — and then get OOMKilled ten minutes later, because its limit was exceeded. The scheduler only ever looks at requests. It never re-checks limits, and it has no idea your container is about to blow past its memory ceiling. If you remember nothing else from this lesson, remember that "scheduled successfully" and "will run forever without being killed" are two unrelated claims.

Requests vs. limits — two different guarantees, two different enforcers

requests is what the scheduler reads to pick a node — it never looks at limits when placing a Pod. limits is what the kubelet (and, underneath it, the Linux kernel via cgroups) enforces once the Pod is actually running.

resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "250m"
    memory: "256Mi"

The exam trap: exceeding the two limits does not do the same thing, and the difference is verified straight from the Kubernetes docs.

  • Memory limit exceeded → OOMKilled. Memory limits are enforced by the kernel via out-of-memory kills, and that enforcement is reactive, not immediate — the docs are explicit that "a container that over allocates memory may not be immediately killed," because the kill only happens once the kernel actually detects memory pressure. So a container can briefly spike over its memory limit and survive; it's not a hard, instant wall. When the kill does land, the container restarts according to the Pod's restartPolicy (Always by default).
  • CPU limit exceeded → throttled, never killed. CPU limits are enforced by the kernel restricting CPU time via cgroups — a genuinely hard limit, but one that just slows the container down. There is no CPU-limit equivalent of OOMKill. The container keeps running, forever, just capped.

Two more facts that matter and are easy to get backwards:

  • If you set limits but skip requests, Kubernetes copies your limit and uses it as the request — you end up with requests == limits whether you meant to or not.
  • If you set requests but skip limits entirely, nothing caps the container. As long as the node has spare capacity, "it's possible (and allowed) for a container to use more resource than its request" — all the way up to whatever the node has free. This is the single most dangerous combination in this lesson, because it looks safe (you set something) while leaving the door fully open.

QoS classes — what the kubelet decides for you

Kubernetes computes a Quality-of-Service class for every Pod automatically, from the requests/limits you set (you never set it directly), and that class decides eviction order when a node runs low on resources.

QoS classHow it's assignedEviction priority
GuaranteedEvery container in the Pod sets requests and limits for both CPU and memory, and for every container requests == limits on both.Last to be evicted — the kubelet only touches these if system daemons themselves are starved.
BurstableDoesn't qualify for Guaranteed, but at least one container has a CPU or memory request or limit set.Middle. Among Burstable Pods, the kubelet evicts the ones using more than they requested before the ones that aren't.
BestEffortNo container in the Pod sets any CPU or memory request or limit at all.First to be evicted, with no ceremony — Kubernetes made zero resource promises to this Pod, so it owes it nothing.

Simple example: a Pod with requests.memory: 256Mi and limits.memory: 512Mi, but no CPU request or limit at all, is Burstable — not Guaranteed and not BestEffort. QoS is computed across every container and every resource; setting one resource carefully doesn't buy you Guaranteed if you left another one unset or unequal.

The three probes

A probe is the kubelet asking a container a yes/no health question, on a repeating timer, using httpGet, tcpSocket, exec, or grpc. Unless you override them, probes default to checking every 10 seconds (periodSeconds: 10), waiting up to 1 second for a response (timeoutSeconds: 1), and acting after 3 consecutive failures (failureThreshold: 3).

  • livenessProbe — "is this container alive, or stuck?" Fails → kubelet kills and restarts the container, per restartPolicy. This is for genuine deadlocks — an app that's technically still running but will never recover on its own.
  • readinessProbe — "is this container ready for traffic right now?" Fails → the Pod is removed from every Service's endpoint list. No restart, no kill — the process keeps running, it just stops receiving new requests until it passes again.
  • startupProbe — "has this container finished its (possibly slow) startup?" While a startupProbe is configured and hasn't yet succeeded once, liveness and readiness probes are disabled entirely — the kubelet won't even run them. The moment the startup probe succeeds, it hands off and liveness/readiness take over for the rest of the container's life. This exists for one reason: to stop a slow-starting app (a JVM warming up, a legacy monolith loading a large cache) from being killed by an impatient liveness probe before it ever got a fair chance to start.

Most confused pair: readiness failing never restarts anything — it only pulls the Pod out of load balancing. Liveness failing is the one that kills the container. Mixing these two up in an incident is how "traffic loss, zero restarts" gets misdiagnosed as "the app crashed."

Putting requests/limits and a probe on the same container looks like this in practice:

containers:
  - name: nginx
    image: nginx:1.29
    resources:
      requests:
        cpu: "100m"
        memory: "128Mi"
      limits:
        cpu: "250m"
        memory: "256Mi"
    readinessProbe:
      httpGet:
        path: /
        port: 80
      initialDelaySeconds: 5
      periodSeconds: 10

Scheduling constraints: node affinity

Requests/limits constrain how much of a node's resources a Pod may use. Node affinity constrains which nodes it's even allowed to land on, by matching node labels via spec.affinity.nodeAffinity.

  • requiredDuringSchedulingIgnoredDuringExecution — a hard requirement. No matching node, no scheduling; the Pod stays Pending.
  • preferredDuringSchedulingIgnoredDuringExecution — a soft preference, with a weight. The scheduler tries to honor it, but will place the Pod elsewhere rather than leave it unscheduled.
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: disktype
              operator: In
              values: ["ssd"]

Both words end in "IgnoredDuringExecution" for a reason worth remembering: neither form re-evaluates once the Pod is already running. Relabel the node out from under a running Pod and nothing evicts it — affinity is a scheduling-time decision only.

Production note: real clusters don't leave requests/limits to individual engineers' discretion, because a single unbounded Pod has taken down shared multi-tenant nodes in real incidents — a memory-leaking service with no limit climbing for hours until the node itself hits pressure and the kubelet starts evicting unrelated, innocent workloads to make room. The standard defense is a namespace-scoped LimitRange object that sets a default request/limit for any container that omits one, plus a hard min/max any container must fall within — LimitRange rejects (HTTP 403) a Pod that violates it, the same admission-time "nothing gets created" behavior you'll see again below for Pod Security Admission. Some orgs go further with a policy engine (OPA Gatekeeper, Kyverno) that flat-out refuses to admit any Pod that omits resources.requests/resources.limits at all. Either way, the point is the same: don't rely on every engineer remembering to set this by hand.

Hands-on exercise — trigger and observe a real OOMKill

Objective

Stop taking "memory limit exceeded means OOMKilled" on faith — force it to happen and read the exact evidence the kubelet leaves behind.

Scenario

You're using the same deliberately-oversized-allocation pattern from the official Kubernetes memory-management tutorial: a container that requests 50Mi, is limited to 100Mi, and then tries to allocate 250Mi — well past its ceiling.

Environment assumptions

Any cluster you can kubectl into (kind, minikube, or a real dev cluster). No existing namespace called mem-example.

Commands

kubectl create namespace mem-example

cat <<EOF | kubectl apply -f - --namespace=mem-example
apiVersion: v1
kind: Pod
metadata:
  name: memory-demo-2
spec:
  containers:
  - name: memory-demo-2-ctr
    image: polinux/stress
    resources:
      requests:
        memory: "50Mi"
      limits:
        memory: "100Mi"
    command: ["stress"]
    args: ["--vm", "1", "--vm-bytes", "250M", "--vm-hang", "1"]
EOF

kubectl get pod memory-demo-2 --namespace=mem-example
kubectl describe pod memory-demo-2 --namespace=mem-example

Expected result

The first get call shows STATUS flip to OOMKilled with RESTARTS climbing, because the container immediately tries to hold 250Mi against a 100Mi limit. kubectl describe's "Last State" block shows Terminated, Reason: OOMKilled, and Exit Code: 137 — 137 is the kernel's SIGKILL signature (128 + signal 9), the same number you'll see in any OOMKill, in any container, on any platform.

Verification

Run kubectl get pod memory-demo-2 --namespace=mem-example -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}' — it should print exactly OOMKilled. Watch RESTARTS over 30–60 seconds; it should keep climbing as the kubelet restarts the container and it immediately re-triggers the same allocation and dies again.

Common failure

Expecting a graceful error message from the app. There isn't one — the kernel kills the process outright before the container gets a chance to log anything useful. This is exactly why "app just disappeared, no error in logs" is a strong OOMKill signal, not a mystery.

Troubleshooting

If the Pod shows Running instead of OOMKilled, check you didn't typo the --vm-bytes value below the limit — the allocation genuinely has to exceed limits.memory to trigger this. If kubectl describe shows no lastState at all, the container hasn't restarted yet; wait a few seconds and re-run.

Cleanup / rollback

kubectl delete namespace mem-example

Production lesson

Exit code 137 with no restart-triggering application log is the fingerprint of an OOMKill, not a crash bug in your code. The very first thing to check on any Pod stuck in a restart loop is kubectl describe pod's "Last State" section — it tells you in one line whether you're chasing a memory-limit problem or an actual application defect, and those two require completely different fixes.

Failure scenario

A realistic incident where nothing crashes, nothing restarts, and the rollout still fails — caused by the other probe.

  1. 09:41 A teammate ships a routine change to the checkout-api Deployment (5 replicas) and renames the health endpoint from /health to /healthz in the app code — but doesn't update the Deployment's readinessProbe.httpGet.path, which still points at /health.
  2. 09:42 CI runs kubectl rollout status deployment/checkout-api as its deploy gate. The command doesn't return — it just hangs, printing "Waiting for deployment... 2 out of 5 new replicas have been updated."
  3. 09:47 CI's step times out after five minutes and marks the deploy "failed," but the rolling update has already replaced 2 of the 5 old Pods with new ones. On-call is paged: "deploy failed, service partially degraded."
  4. 09:49 On-call runs kubectl get pods -l app=checkout-api — the 2 new Pods are Running with 0/1 READY, not CrashLoopBackOff and not Pending. No restarts on either one. The 3 old Pods are still up and still serving traffic, untouched.
  5. 09:52 kubectl describe pod <new-pod> shows an Events line repeating every 10 seconds: Readiness probe failed: HTTP probe failed with statuscode: 404. The container itself never restarted — this was never a liveness problem.
  6. 09:55 On-call checks the new image's actual routes and confirms the endpoint is now /healthz, not /health — the probe path is stale, not the app.
  7. 09:58 Fix applied: update readinessProbe.httpGet.path to /healthz in the Deployment manifest and re-apply. The rolling update, which had been stalled the whole time (the Deployment's rolling-update strategy won't scale down old Pods until enough new ones report Ready), resumes on its own.
  8. 10:01 All 5 new Pods reach 1/1 READY; the 3 old Pods are terminated by the rollout; kubectl rollout status returns successfully rolled out.

Notice what didn't happen anywhere in this timeline: no container crashed, no restart count went up, and "the deploy failed" was technically wrong — the rollout wasn't failing, it was correctly refusing to finish an unsafe rollout. That distinction is the entire lesson.

Troubleshooting workflow

The general method, applied specifically to "my Pod keeps restarting" and "my Pod isn't Ready" — two symptoms that get confused constantly, and need to be told apart in step 1, not step 10.

  1. Confirm the symptom. kubectl get pods — read the READY column (0/1 vs 1/1) and RESTARTS separately. Rising restarts = something is killing the container. 0/1 with restarts not rising = a readiness problem, not a crash.
  2. Define scope. One Pod, one Deployment's Pods, or every Pod on a node? kubectl get pods -o wide across the namespace tells you if this is app-specific or node-wide (which would point at node memory pressure, not this one probe/limit).
  3. Check recent changes. kubectl rollout history deployment/<name> and kubectl get events --sort-by=.lastTimestamp — did a probe path, a resource limit, or an image change in the last rollout?
  4. Inspect the right state. kubectl describe pod <name> — read both the "Last State" block (Terminated / OOMKilled / exit code — proves a kill happened and why) and the live Events feed (repeating "Readiness probe failed" or "Liveness probe failed" lines — proves which probe, and how often).
  5. Form a hypothesis, matched to the exact evidence. Reason: OOMKilled in Last State → memory-limit hypothesis. Restarting with Reason: Error and a liveness-probe-failed Event right before each restart → liveness hypothesis. 0/1, zero restarts, repeating readiness-failed Events → readiness hypothesis — the container itself is fine.
  6. Test one variable. For a suspected OOMKill: kubectl top pod <name> against its configured limit. For a suspected bad probe: run the exact same check manually — kubectl exec <name> -- curl -sf http://localhost:<port><path> — using the literal path/port from the manifest, not what you assume it should be.
  7. Apply the safest fix. OOMKill → raise the memory limit only after confirming the usage is legitimate, not a leak. Bad liveness probe → loosen timeoutSeconds/failureThreshold or add a startupProbe, don't just delete the probe. Bad readiness probe → fix the path/port to match the app, don't remove it — removing it means the Pod gets traffic immediately on container start, the exact problem readiness probes exist to prevent.
  8. Verify recovery. READY reaches 1/1, RESTARTS stops climbing, and — for the readiness case specifically — confirm the Pod is actually back in the Service's endpoint list: kubectl get endpoints <service>.
  9. Document the root cause. Name the exact mechanism: "readinessProbe path was stale after an app route rename" is useful; "probes were misconfigured" is not — the next person needs to know which probe and why.
  10. Prevent recurrence. Add a CI check that the probe path in the manifest actually exists in the built image, and treat probe-path changes as part of the same PR as the route rename that causes them — not an afterthought.

Security & reliability considerations

Two more mechanisms constrain whether a Pod is even allowed to exist, and treating resource limits purely as a performance knob misses their reliability role entirely.

Security note: Pod Security Admission is a built-in admission controller that checks every Pod against one of three Pod Security Standards, applied per-namespace via labels — no separate policy object, no RBAC bindings to get wrong (the problem that made its predecessor, PodSecurityPolicy, hard to operate; PSP was deprecated in 1.21 and fully removed in 1.25, with Pod Security Admission as its stable replacement since 1.25). The three standards, each stricter than the last: privileged (effectively unrestricted), baseline (blocks known privilege-escalation paths — privileged containers, host namespaces, host ports), and restricted (baseline plus a locked-down capability set, a mandatory non-root user, a required seccomp profile, and no privilege escalation at all). Three independent modes control what happens on a violation, and only one of them blocks anything: enforce rejects the Pod outright at admission time; audit allows it but records the violation in the audit log; warn allows it but returns a warning message to whoever ran kubectl apply. All three can be set simultaneously, each at its own level, each independently version-pinned:

apiVersion: v1
kind: Namespace
metadata:
  name: secure-ns
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
Exam trap: a Pod rejected by an enforce label never shows up in kubectl get pods at all — the create request itself is denied, full stop. If kubectl apply errors immediately with an admission message and nothing gets created, that's Pod Security Admission (or another admission controller, like a LimitRange), not a scheduling failure — a scheduling failure still creates the Pod object, just stuck in Pending.

Reliability note: resource limits are a security control too, in a specific and easy-to-forget sense — they're your defense against "noisy neighbor" incidents. On a shared node, one container with no memory limit doesn't just risk itself; it can push actual memory pressure onto every other Pod scheduled on that node, regardless of how carefully those teams sized their own limits, until the kubelet starts evicting BestEffort and Burstable Pods to relieve it. A resource limit isn't only about protecting the container that has one — it's about protecting everything else sharing that node from the one that doesn't.

Common mistakes

Common mistake: setting requests without ever setting limits, assuming a request is "close enough" to a cap. It isn't — with no limit, the container can consume memory or CPU all the way up to whatever the node has free. Worse, the Pod won't even qualify as Guaranteed (it needs matching requests and limits on every resource), so it lands in Burstable — meaning it's also higher up the eviction list than a Pod that took the two extra lines to set a limit.

Common mistake: tuning a livenessProbe to be "fast and strict" (short timeoutSeconds, low failureThreshold) without accounting for normal slowness — a JVM garbage-collection pause, a brief spike in request load. The app is genuinely healthy; it's just slow for two seconds. An overly aggressive liveness probe reads that as "dead," kills the container, and the restart itself adds cold-start latency right when the app was already under load — manufacturing a restart loop out of a health check, not an actual bug.

Decision guide

ProbeUse whenAvoid whenTrade-off
livenessProbeApp can enter a real stuck/deadlocked state only a restart fixesSlowness is normal and transient (GC pause, cold cache)Catches real hangs fast, but too strict causes restart loops on healthy apps
readinessProbeApp needs warm-up time or depends on another service before serving trafficAlmost never — nearly every real workload benefits from oneSafer rollouts, but a wrong path silently blocks all traffic with no crash to alert on
startupProbeStartup time is long and variable (legacy app, big in-memory cache load)Startup is fast and consistent alreadyOne more field to tune, but stops false liveness-kills during a slow boot
Sizing choiceUse whenAvoid whenTrade-off

Default recommendation: set both requests and limits on every production container, every time. Reach for Guaranteed (requests == limits) for stateful or business-critical workloads where eviction is unacceptable; reach for Burstable for bursty stateless services where efficient packing matters more than eviction safety. Never ship BestEffort to a shared cluster on purpose.

Knowledge check

Q1. A Pod's readiness probe starts failing. Does the container restart?

No. It's pulled from every Service's endpoint list. The container itself keeps running untouched.

Q2. A container hits its memory limit. A different container hits its CPU limit. What happens to each?

Memory: the kernel OOMKills it (exit code 137), then it restarts per restartPolicy. CPU: it's throttled by the kernel via cgroups — never killed, just slower.

Q3. kubectl apply on a Pod manifest fails instantly with an admission error, and kubectl get pods shows nothing was created. Is this a scheduling problem?

No — a scheduling failure still creates the Pod object, just stuck Pending. Nothing being created at all, with an immediate admission error, points to Pod Security Admission's enforce mode (or a LimitRange) rejecting the request outright.

Q4. A container sets requests.cpu: 200m, limits.cpu: 200m, requests.memory: 256Mi, limits.memory: 512Mi. What QoS class is this Pod?

B. Guaranteed requires requests == limits on every resource, not just one. CPU matches, but memory doesn't (256Mi vs 512Mi), so the Pod is Burstable overall.

Q5. Your app takes up to 4 minutes to finish loading a large in-memory cache before it can serve traffic reliably, but once loaded, it's snappy and stable. Which change fixes this without weakening ongoing health checks?

B. A startupProbe sized for the full warm-up window disables liveness and readiness only until it succeeds once — giving the slow boot room without permanently loosening the checks that matter for the rest of the container's life.

Q6. A namespace has pod-security.kubernetes.io/warn: restricted set, with no enforce label present at all. A Pod violating the restricted standard is submitted. What happens?

A. Only enforce blocks Pod creation. warn (like audit) still creates the Pod — it just surfaces a warning message to whoever ran kubectl apply.

Production challenge

Objective

Diagnose a Pod stuck 0/1 Not Ready with zero restarts, using only the troubleshooting method above — no shortcuts, no being told the answer up front.

Scenario

A teammate deploys an app and says "it's stuck, I think it's crashing." Your job is to find out whether that's even true before touching anything.

Environment assumptions

A kind/minikube cluster. Build the broken scenario yourself first — don't peek at the fix below before you've tried step 1 of the troubleshooting method on it:

cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: broken-readiness
spec:
  containers:
  - name: web
    image: nginx:1.29
    ports:
    - containerPort: 80
    readinessProbe:
      httpGet:
        path: /this-path-does-not-exist
        port: 80
      periodSeconds: 5
      failureThreshold: 2
EOF

Commands

Apply the troubleshooting workflow yourself: run kubectl get pod broken-readiness, note READY and RESTARTS, then kubectl describe pod broken-readiness and read the Events feed before forming a hypothesis. Only after that, fix the manifest and re-apply.

Expected result

Before the fix: READY 0/1, RESTARTS 0, and repeating Readiness probe failed: HTTP probe failed with statuscode: 404 Events. After correcting path to / and re-applying, READY reaches 1/1 within a couple of probe periods, with RESTARTS still at 0 the entire time.

Verification

kubectl get pod broken-readiness -o jsonpath='{.status.containerStatuses[0].restartCount}' should read 0 both before and after the fix — proving this was never a crash, only a routing problem in the probe itself.

Common failure

"Fixing" it by deleting the readinessProbe block instead of correcting the path. That makes the symptom disappear (the Pod immediately shows Ready) without proving anything about whether the app can actually serve real traffic — you've removed the safety check, not restored it.

Troubleshooting

If you still see RESTARTS climbing, you've built a different failure than intended — check whether you accidentally pointed a livenessProbe (not readinessProbe) at the bad path; that would explain restarts, and would mean you're now debugging this lesson's other failure mode instead.

Cleanup / rollback

kubectl delete pod broken-readiness --ignore-not-found

Production lesson

"It's stuck" and "it's crashing" are not the same claim, and confusing them wastes real incident time — the first thing kubectl get pods tells you is which one you're actually looking at, before you touch a single line of application code.

Recap
  • requests places the Pod (scheduler, checked once). limits caps it once running (kubelet/kernel, enforced continuously) — two separate guarantees, which is why a scheduled Pod can still be OOMKilled later.
  • Memory limit exceeded → kernel OOMKills reactively (exit code 137), then restarts per restartPolicy. CPU limit exceeded → throttled by cgroups, never killed.
  • QoS class is computed automatically: Guaranteed needs requests == limits on every resource in every container; Burstable is anything in between; BestEffort has no requests/limits at all. Eviction order under pressure: BestEffort first, Burstable next, Guaranteed last.
  • Liveness fails → restart. Readiness fails → removed from Service endpoints, no restart. startupProbe disables both until it succeeds once — for slow-starting apps.
  • Pod Security Admission's enforce mode rejects non-compliant Pods at creation (nothing gets created); audit and warn allow creation and only log or display a message. PSP is gone since 1.25 — this is the only supported replacement.
  • Node affinity constrains which nodes a Pod can land on at scheduling time only (...IgnoredDuringExecution) — required... is a hard rule, preferred... is a soft one.
