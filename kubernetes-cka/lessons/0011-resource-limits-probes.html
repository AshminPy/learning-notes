Resource limits + probes

A Deployment (Lesson 4) keeps N Pods running, but "running" isn't the same as "healthy" or "well-behaved." Two mechanisms fill that gap: resource requests/limits control how much CPU/memory a container may use, and probes tell Kubernetes whether a container is actually working.

Mental model: requests is what you tell the scheduler you need — like reserving a seat. limits is the hard ceiling you can't cross once seated. That predicts why they're enforced by different components at different times: requests only matters once, at scheduling; limits is enforced continuously by the kubelet for as long as the container runs.

Where this fits

Cluster └ Node └ Pod └ Labels
                          ├ Deployment          (Lesson 4 — keeps N Pods running)
                          └ resources / probes  ← you are here (defines "running well")

Requests vs. limits

resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "250m"
    memory: "256Mi"

Why exceeding each limit does something different: memory can't be reclaimed from a process without killing it, so the kernel OOMKills the container when it crosses its memory limit — it dies and restarts per restartPolicy. CPU time, on the other hand, can just be rationed — the kernel throttles a container that hits its CPU limit instead, no kill needed. Same enforcement layer, different underlying resource, different consequence.

The three probes

A probe is the kubelet asking a container a yes/no question, on a timer:

Probe fails
   │
   ▼
livenessProbe   → kubelet RESTARTS the container
readinessProbe  → Pod REMOVED from Service endpoints (Lesson 3) — no restart
startupProbe    → liveness/readiness disabled until this succeeds once

Common mistake: assuming a failing readiness probe restarts anything — it never does, it only stops new traffic (via Lesson 3's endpoint mechanism). Only liveness restarts.

Try it

Q1. A container hits its memory limit. A different container hits its CPU limit. What happens to each?

Memory: OOMKilled, then restarted. CPU: throttled, keeps running slower — never killed.

Now write your own: add requests, limits, and a readinessProbe to a Deployment's Pod template, by hand. Apply it, check with kubectl describe pod. Try before revealing.

Reveal the reference answer

          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "250m"
              memory: "256Mi"
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10

A controlled failure

kubectl run bad-probe --image=nginx:1.29 --overrides='{"spec":{"containers":[{"name":"bad-probe","image":"nginx:1.29","readinessProbe":{"httpGet":{"path":"/does-not-exist","port":80}}}]}}'
kubectl get pod bad-probe
kubectl expose pod bad-probe --port=80 --name=bad-probe-svc
kubectl get endpoints bad-probe-svc

Predict first: is bad-probe Running? Does it get an endpoint? Observe: it's Running, READY 0/1 — and bad-probe-svc has zero endpoints, same silent-failure shape Lesson 3 taught, caused this time by a probe instead of a label mismatch.

Pod admission and scheduling constraints

Requests/limits constrain resources. Two more mechanisms constrain where a Pod runs and whether it's allowed to exist at all:

  • Pod Security Admission — rejects (or warns about) Pods violating a security standard, enforced per-namespace via a label: pod-security.kubernetes.io/enforce: restricted. Standards: privileged, baseline, restricted (least permissive).
  • Node affinity — spec.affinity.nodeAffinity constrains which nodes a Pod can land on. requiredDuringSchedulingIgnoredDuringExecution is a hard requirement; preferredDuringSchedulingIgnoredDuringExecution is a soft preference.

Common mistake: confusing a Pod Security Admission rejection with a scheduling failure. A rejected Pod never gets created at all — kubectl apply errors immediately, nothing shows in kubectl get pods. A scheduling failure creates the Pod, just stuck Pending.

Production best practices

Production note: always set both requests and limits — no requests means the scheduler under-provisions the node; no limits means one runaway container can starve every other Pod on the node. Set restricted Pod Security Admission on every namespace that doesn't have a specific reason to need more.

Exam & interview notes

Core to Workloads & Scheduling (15%), and a frequent Troubleshooting (30%) scenario.

Interview Q: "A Pod is Running with zero restarts but receives no traffic. What's the likely cause?" A: A failing readiness probe — the container is alive (liveness is fine), just not passing its readiness check, so it's pulled from Service endpoints without ever restarting.

Recap
  • requests places the Pod (scheduler, once). limits caps it once running (kubelet, continuously).
  • Memory limit exceeded → OOMKilled + restart. CPU limit exceeded → throttled, no restart.
  • Liveness fails → restart. Readiness fails → removed from Service endpoints, no restart.
  • Pod Security Admission rejects non-compliant Pods at creation — nothing gets created, unlike a Pending scheduling failure.
