Kubernetes / CKA — Lesson 11 of 17

Resource limits + probes

Back in Lesson 5, a Service routed traffic to Pods with zero questions asked — as soon as a Pod matched the label selector, it got traffic, ready or not. That was foreshadowing. This lesson closes the gap: readiness is how a Pod tells a Service "don't send me traffic yet," without ever touching whether the container gets restarted. Restart and traffic-routing are two separate decisions in Kubernetes, made by two separate probes — and mixing them up is the single most common way people misread the exam.

Tied to your mission: GKE Autopilot forces every Pod you run to declare resources.requests — you've already worked around this in production without necessarily knowing why the scheduler cares, or what the matching limits field actually enforces underneath. This lesson gives you the mechanics behind a field you already touch daily.

The mental model — requests vs limits

Requests are what the kube-scheduler uses to place your Pod. It looks at each node's spare capacity and only places a Pod on a node that can cover the sum of its containers' requests. Requests are a promise to the scheduler, not a ceiling on the container.

Limits are enforced by the kubelet, on the node, after the Pod is already running. A limit is the hard ceiling: the container is not allowed to use more of that resource than the limit says — but "not allowed" plays out very differently depending on which resource it is.

The exam trap: exceeding a memory limit and exceeding a CPU limit do NOT produce the same outcome.

Memory is enforced by the kernel killing the process — OOMKilled. The container dies and (subject to restartPolicy) gets restarted from scratch. This is reactive: the kernel only kills once it detects memory pressure, so a container isn't necessarily killed the instant it crosses the line, but it can be killed at any point after.

CPU is enforced by throttling. A container that hits its CPU limit is not killed — it's just denied more CPU time until the next scheduling period. It keeps running, just slower. No restart, no crash, no event beyond degraded performance.

Same mechanism in your head ("a limit"), completely different consequence. Memory limit too low → crash loop. CPU limit too low → silent slowness that never shows up as a Pod restart.

The mental model — liveness, readiness, startup

A probe is the kubelet periodically asking a container a yes/no question. There are three, and each answers a different question:

  • livenessProbe — "is this container alive?" If it fails (enough times to cross the failure threshold), the kubelet kills and restarts the container.
  • readinessProbe — "is this container ready for traffic?" If it fails, the Pod is pulled out of every Service's list of endpoints. The container keeps running untouched — nothing restarts.
  • startupProbe — "has this container finished starting up yet?" While a startup probe hasn't yet succeeded, liveness and readiness probes are disabled. This exists for slow-starting apps: without it, a liveness probe with a short timeout can kill a container that was never actually broken, just still booting.

Once startupProbe succeeds (or if you didn't define one), livenessProbe and readinessProbe take over and run for the rest of the container's life.

ProbeQuestion it asksOn failure
livenessProbeIs this container alive?Restart the container
readinessProbeIs this container ready for traffic?Remove Pod from Service endpoints — no restart
startupProbeHas the container finished starting?Blocks liveness/readiness from running until this succeeds (or the Pod is killed if startup itself never succeeds in time)

The pair everyone confuses: a failed readiness probe never restarts a container — it only pulls the Pod out of Service routing. A failed liveness probe is the one that restarts. If you see "Pod still Running, 0 restarts, but no traffic reaching it" — that's readiness. If you see "Pod restart count climbing" — that's liveness.

Try it first — before reading on

Q1. A Pod's readiness probe starts failing. Does the container restart?

No. A failed readiness probe never restarts the container — it only removes the Pod from the Service's endpoint list. The container keeps running.

Q2. A container exceeds its memory limit, and separately, a container exceeds its CPU limit. What happens in each case?

Memory: the kernel OOMKills the container — it dies and gets restarted (subject to restartPolicy). CPU: the container is throttled, not killed — it keeps running, just denied extra CPU time.

Q3. What problem does startupProbe solve that livenessProbe alone can't?

A slow-starting app can look "dead" to a liveness probe with a normal timeout while it's still booting, causing the kubelet to kill it before it ever gets a chance to start. startupProbe holds off liveness (and readiness) checks until the app has actually finished starting.

Now build it — in your terminal, not here

Take the Deployment you wrote in Lesson 4 and edit its Pod template — no copy-paste. Add, to the container:

  • resources.requests — a CPU value (e.g. 100m) and a memory value (e.g. 128Mi)
  • resources.limits — a CPU value and a memory value, at or above your requests
  • readinessProbe — an HTTP GET probe against the container's port (nginx serves on port 80), with an initialDelaySeconds and a periodSeconds

Apply it, then run kubectl describe pod <pod-name> and check the Requests/Limits lines and the Readiness line under the container section. Watch kubectl get pods — a Pod isn't marked READY until its readiness probe passes at least once.

Reveal the reference answer

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-nginx
  template:
    metadata:
      labels:
        app: my-nginx
    spec:
      containers:
        - name: nginx
          image: nginx
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "250m"
              memory: "256Mi"
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10

Bring what you wrote back to your notes — check that limits is at or above requests for each resource (Kubernetes allows limits below requests to be set, but it's a self-defeating config: the Pod could be scheduled expecting headroom it can't actually use), and that the probe's port matches the port the container really listens on.

Recap
  • requests = what the scheduler uses to place the Pod. limits = the hard ceiling the kubelet enforces once it's running.
  • Exceed a memory limit → OOMKilled (container dies, restarts). Exceed a CPU limit → throttled (keeps running, just slower). Same word "limit," opposite failure mode.
  • livenessProbe fails → container restarts. readinessProbe fails → Pod pulled from Service endpoints, no restart. These are independent decisions.
  • startupProbe holds off liveness/readiness checks until a slow-starting container has actually finished starting.

Try solo: add a livenessProbe to the same Deployment (a different check than your readiness probe, e.g. a different path), deliberately point it at a path that returns an error, apply it, and watch kubectl get pods restart count climb. Then fix the path and confirm it stabilizes. Don't reopen this file to check — bring it to your notes instead.
