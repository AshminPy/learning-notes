Resource limits + probes

Two topics that always show up together: how much CPU/memory a container may use, and how Kubernetes checks if a container is healthy.

Simple example: requests are what you tell the scheduler you need — like reserving a seat. Limits are the hard ceiling you can't cross once seated. Requests get you placed. Limits cap you.

Requests vs limits

requests is what the scheduler uses to pick a node — a promise, not a cap. limits is what the kubelet enforces once the Pod is running — a hard ceiling.

resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "250m"
    memory: "256Mi"

The exam trap: exceeding the two limits does not do the same thing.

  • Memory limit exceeded → kernel OOMKills the container. It dies and restarts (per restartPolicy).
  • CPU limit exceeded → container is throttled, not killed. It keeps running, just slower.

The three probes

A probe is the kubelet asking a container a yes/no question, on a timer.

  • livenessProbe — "alive?" Fails → kubelet restarts the container.
  • readinessProbe — "ready for traffic?" Fails → Pod is removed from Service endpoints. No restart.
  • startupProbe — "finished starting?" While it hasn't succeeded, liveness and readiness are disabled. For slow-starting apps.

Most confused pair: readiness failing never restarts anything — it only stops traffic. Liveness failing is the one that restarts.

Pod admission and scheduling constraints

Requests/limits (above) constrain resources. Two more mechanisms constrain where a Pod runs and whether it's allowed to exist at all:

  • Pod Security Admission — a built-in admission controller that rejects (or just warns about) Pods violating a security standard, enforced per-namespace via a label: pod-security.kubernetes.io/enforce: restricted. The three standards are privileged, baseline, and restricted (least permissive). This replaced the older, now-removed PodSecurityPolicy.
  • Node affinity — spec.affinity.nodeAffinity constrains which nodes a Pod can land on, by matching node labels. requiredDuringSchedulingIgnoredDuringExecution is a hard requirement (won't schedule without a match); preferredDuringSchedulingIgnoredDuringExecution is a soft preference (schedules elsewhere if no match).
apiVersion: v1
kind: Namespace
metadata:
  name: secure-ns
  labels:
    pod-security.kubernetes.io/enforce: restricted
Exam trap: a Pod rejected by Pod Security Admission never shows up in kubectl get pods at all — the create request itself is denied. If kubectl apply errors immediately with an admission message and nothing gets created, that's this, not a scheduling failure (which would create the Pod in a Pending state instead).

Try it — before looking below

Q1. A Pod's readiness probe starts failing. Does the container restart?

No. It's pulled from the Service's endpoint list. The container keeps running.

Q2. A container hits its memory limit. A different container hits its CPU limit. What happens to each?

Memory: OOMKilled, then restarted. CPU: throttled, keeps running slower — never killed.

Q3. kubectl apply on a Pod manifest fails instantly with an admission error, and kubectl get pods shows nothing was created. Is this a scheduling problem?

No — a scheduling failure still creates the Pod object, just stuck Pending. Nothing being created at all, with an immediate admission error, points to Pod Security Admission (or another admission controller) rejecting the request outright.

Now write your own

Take a Deployment's Pod template (no copy-paste) and add to the container:

  • resources.requests — a CPU and memory value
  • resources.limits — a CPU and memory value, at or above your requests
  • readinessProbe — an HTTP GET on the container's port, with initialDelaySeconds and periodSeconds

Apply it. Run kubectl describe pod <name> and check the Requests/Limits and Readiness lines.

Reveal the reference answer

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-nginx
  template:
    metadata:
      labels:
        app: my-nginx
    spec:
      containers:
        - name: nginx
          image: nginx
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "250m"
              memory: "256Mi"
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10

Recap
  • requests places the Pod (scheduler). limits caps it once running (kubelet).
  • Memory limit exceeded → OOMKilled + restart. CPU limit exceeded → throttled, no restart.
  • Liveness fails → restart. Readiness fails → removed from Service, no restart. startupProbe delays both for slow-starting apps.
  • Pod Security Admission rejects non-compliant Pods at creation time (per-namespace label) — nothing gets created, unlike a scheduling failure which creates a Pending Pod.
  • Node affinity constrains which nodes a Pod can land on — required... is a hard rule, preferred... is a soft one.
