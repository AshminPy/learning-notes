The Pod

Every workload you'll ever run on Kubernetes — a web API, a batch job, a database — comes down to the same question: what actually runs my container, and what happens to it when something goes wrong? Skip this lesson and every later one (Deployment, Service, Job) feels like memorizing unrelated objects instead of variations on one idea.

A Pod is the smallest thing Kubernetes runs — one or more containers that share the same network address and the same fate: they start together, they stop together. Most Pods hold exactly one container.

Mental model: a Pod is a boarding pass, not the passenger. When a flight is cancelled, the airline doesn't repair your old boarding pass — it issues a new one, for a new flight, with a new seat. A "restarted" Pod works the same way: it's not fixed, it's replaced — a new object, usually with a new IP. That predicts something concrete: any system that assumes "this Pod will always have this IP" will break the first time it's replaced.

Where this fits

Cluster
  └ Node            (a machine — full mechanics in Lesson 13)
      └ Pod          ← you are here
          └ Container(s)

You already know roughly what a cluster and a node are from real-world use — this course fills in the manifest-level detail, starting at the bottom. Everything else in this course (Deployment, Service, Job) is a controller that creates and manages Pods on your behalf — none of them replace this layer, they all sit on top of it.

What's inside a Pod manifest

Every Kubernetes object — Pod, Deployment, Service, all of them — is written the same shape:

apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx:1.29
  • apiVersion — which version of the Kubernetes API this object uses
  • kind — what kind of object this is (here: Pod)
  • metadata — its name (and, from Lesson 2, its labels)
  • spec — what you actually want: run the nginx image, one container

Learn these four once — every object you write from here on reuses the same shape.

How it works, and why

you write YAML
   │
   ▼
API server        (accepts and stores the Pod object)
   │
   ▼
scheduler          (picks which Node it runs on)
   │
   ▼
kubelet (on that Node)   (actually creates the containers, watches them)

The kubelet is the part that matters most for this lesson: it's the only thing watching a bare Pod after creation. It applies restartPolicy, reports status back to the API server, and terminates containers gracefully on delete. No controller, no scheduler stays involved once the Pod exists.

Why it's built this way: Kubernetes assumes any single machine can fail at any time. If Pods were repaired in place, a dead Node would mean permanently dead workloads. Making Pods disposable — and pushing "keep N of these running" into a separate, optional controller layer (Deployment, Lesson 4) — is what makes self-healing possible at all. A bare Pod opts out of that layer entirely, which is exactly what this lesson's failure below demonstrates.

Try it

Q1. Which of the four top-level fields says what container to actually run?

spec — specifically spec.containers.

Now write your own, by hand, no copy-paste: a Pod named my-redis running the redis image. Try before revealing.

Reveal the reference answer

apiVersion: v1
kind: Pod
metadata:
  name: my-redis
spec:
  containers:
  - name: redis
    image: redis:7

Common mistake: writing bare Pods for real workloads because it's the first primitive you learn, then being surprised when a routine node drain takes the workload down permanently instead of rescheduling it.

A controlled failure

Prove the mental model above, don't just take it on faith:

kubectl run my-nginx --image=nginx:1.29
kubectl get pod my-nginx

Predict first: if you delete this Pod, will it come back? Then run:

kubectl delete pod my-nginx
kubectl get pod my-nginx

Observe: Error from server (NotFound) — nothing recreated it. That's the whole lesson, made concrete: no controller was watching, so nothing replaced it.

Production best practices

Production note: a bare Pod almost never survives real code review for a service. It shows up for two legitimate reasons only: quick interactive debugging (kubectl run debug --image=busybox -it --rm -- sh), and as the object a controller creates on your behalf. You'll still write raw Pod YAML constantly in this course and on the exam — it's the primitive every controller builds on.

Exam & interview notes

Foundational — not separately weighted on the CKA exam, but every scored domain sits on top of it.

Interview Q: "If a Node running a bare Pod crashes, what brings the Pod back?" A: Nothing. A bare Pod has no controller watching it — it stays gone until something (you, or a controller if one existed) creates it again. This is precisely why production workloads use a Deployment instead.

Recap
  • A Pod = one or more containers sharing network and storage; every object follows the same apiVersion/kind/metadata/spec shape.
  • Kubernetes never repairs a Pod — a "restarted" Pod is a new object, usually with a new IP.
  • Only the kubelet watches a bare Pod after creation — no self-healing without a controller layered on top.
  • Pods are deliberately disposable so that "keep N running" can be a separate, optional layer (Deployment) instead of built into every workload.

Confidence check — answer without looking back:

  • Why does Kubernetes make Pods disposable instead of repairable?
  • When is it actually fine to run a bare Pod?
  • What happens if the Node running your bare Pod is deleted?
  • How would you verify a Pod was replaced vs. never went away? (Hint: think about what changes and what doesn't.)
