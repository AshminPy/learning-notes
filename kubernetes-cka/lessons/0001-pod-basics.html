The Pod

Why this matters

The single most common mistake people make when they start running real workloads on Kubernetes is treating a Pod like a small VM — something you keep alive, patch, and expect back after a restart. It isn't. A Pod is disposable by design, and every workload controller you'll learn later (Deployment, StatefulSet, Job, DaemonSet) exists purely to manage the creation and replacement of Pods for you. If this lesson doesn't land, rolling updates, self-healing, and Services will all feel like unexplained magic instead of predictable consequences of one simple fact: Kubernetes never repairs a Pod — it replaces it.

Mental model: a Pod is a boarding pass, not the passenger. When a flight is cancelled, the airline doesn't fix your old boarding pass — it issues you a new one, for a new flight, with a new seat number. Kubernetes does the same thing: when a Pod dies, the replacement is "near-identical" (same image, same spec) but it is a brand-new object, with a new identity and — this is the part that causes real incidents — usually a new IP address. If any part of your system assumes "this Pod will always come back" or "this Pod will always have this IP," it will break the first time a node fails or you scale down and back up.

Core concepts

Every Kubernetes object — Pod, Deployment, Service, all of them — is written in the same four-part shape:

apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx:1.29
    ports:
    - containerPort: 80
  • apiVersion — which version of the Kubernetes API this object uses
  • kind — what kind of object this is (here: Pod)
  • metadata — its name and labels
  • spec — what you actually want (here: run the nginx image, one container)

Learn these four once — every object you write from here on reuses the same shape.

The official definition: a Pod "is a group of one or more containers, with shared storage and network resources, and a specification for how to run the containers." The containers in a Pod share a set of Linux namespaces and cgroups — the same isolation mechanisms that separate one container from another — which is why containers in the same Pod can talk to each other over localhost and see the same mounted volumes. Most Pods hold exactly one container; running more than one in a Pod is explicitly called out by the docs as "a relatively advanced use case," reserved for containers that are genuinely tightly coupled (a sidecar that ships logs, for example) — not a way to group unrelated apps.

Internally: you send this manifest to the API server, the scheduler picks a node for it, and the kubelet on that node is what actually creates the containers and keeps watching them locally — it's the kubelet's job to apply restartPolicy, report Pod status back to the API server, and terminate containers gracefully (30 seconds by default) when the Pod is deleted. Nothing above the kubelet — no controller, no scheduler — is watching a bare Pod after it's created; that's the detail this whole lesson hinges on.

Pod phaseWhat it means
PendingAccepted by the cluster, but at least one container isn't set up yet (includes time waiting to be scheduled or pulling images)
RunningBound to a node, all containers created, at least one still running or starting/restarting
SucceededAll containers terminated successfully and will not be restarted
FailedAll containers terminated and at least one failed (non-zero exit or killed by the system)
UnknownThe cluster lost contact with the node and can't determine the Pod's state

Simple example: CrashLoopBackOff is not one of these phases — it's a display string kubectl shows you in the Status column when a container keeps failing to start. The Pod's real phase underneath is usually still Running or Pending. Don't confuse the friendly status text with the actual API phase; if you're scripting against Pod state, read .status.phase, not the word kubectl prints.

Production example

Production note: you will almost never see a bare Pod manifest survive code review for a real service. A stateless API, a queue worker, a batch job — every one of them is defined as a Deployment, StatefulSet, or Job, and Kubernetes creates the underlying Pods for you. Bare Pods show up in production for exactly two legitimate reasons: quick interactive debugging (kubectl run debug --image=busybox -it --rm -- sh) and as the thing a controller creates on your behalf — you'll still write raw Pod YAML constantly on the CKA exam, because the exam tests whether you understand the primitive underneath the controllers.

Hands-on exercise

Objective

Prove to yourself — don't just take the lesson's word for it — that a bare Pod has no self-healing.

Scenario

You want to confirm what happens when a bare Pod is deleted, before you trust that claim in a real incident.

Environment assumptions

Any cluster you can kubectl into (kind, minikube, or a real dev cluster), no existing resource named my-nginx in the current namespace.

Commands

kubectl run my-nginx --image=nginx:1.29
kubectl get pod my-nginx -o wide
kubectl delete pod my-nginx
kubectl get pod my-nginx

Expected result

The first get shows my-nginx Running. After delete, the second get returns Error from server (NotFound) — nothing recreated it.

Verification

The NotFound error itself is the proof. If you instead see a Pod named my-nginx running with a different AGE, something else in your cluster (a controller, an admission webhook, a GitOps tool) recreated it — that's worth investigating, not this lesson's behavior.

Common failure

Expecting the Pod to come back the way a Deployment's Pod would. It won't — there is no controller watching a bare Pod.

Troubleshooting

If kubectl run errors about an already-existing resource, someone (or something) left a Pod with that name behind — kubectl delete pod my-nginx --ignore-not-found first, then retry.

Cleanup / rollback

Nothing to clean up — the Pod is already deleted by the exercise itself.

Production lesson

This exact gap — "no controller, no recreation" — is a real production incident category. A workload that looks fine today can have zero resilience to a node failure tomorrow, and the only way to see that from the manifest alone is to know it's a bare Pod, not a Deployment.

Failure scenario

A realistic incident, built from the fact you just proved above — except this time the Pod does come back, and that's what causes the outage.

  1. 14:02 Alert fires: the payment-worker Deployment's health check is failing. On-call opens kubectl get pods — the worker Pod is Running, healthy, no restarts.
  2. 14:03 App logs show connection refused to 10.244.1.15 — a downstream Pod IP that's hardcoded in a debug config file left over from an earlier troubleshooting session, instead of the proper Service name.
  3. 14:06 On-call checks that downstream Pod: it's Running too, but its IP is now 10.244.2.9. kubectl get events shows the node it used to live on was cordoned and drained 20 minutes earlier for a routine upgrade — its controller recreated it on a different node, with a new IP, exactly as designed.
  4. 14:09 Root cause identified: nothing is actually broken. The config file assumed a Pod IP was permanent. It never was.
  5. 14:12 Fix applied: point the config at the Service's stable ClusterIP / DNS name instead of the Pod IP, and restart payment-worker to pick up the change.
  6. 14:15 Verified: payment-worker connects successfully; health check passes.

Troubleshooting workflow

The general method, applied to "a Pod isn't doing what I expect":

  1. Confirm the symptom. Run kubectl get pods yourself — is it Pending, CrashLoopBackOff, or genuinely gone? Don't diagnose from memory of what it looked like yesterday.
  2. Define scope. Is it one Pod, every Pod on a node, or every Pod in the namespace? kubectl get pods -o wide --all-namespaces tells you if this is isolated or systemic.
  3. Check recent changes. kubectl get events --sort-by=.lastTimestamp — was this Pod deleted and recreated, evicted, or has it never successfully started?
  4. Inspect the right state. kubectl describe pod <name> for its Events section; kubectl logs <name> --previous if it has restarted, to see the logs from the crash, not the fresh container.
  5. Form a hypothesis. For example: "this isn't the same Pod I saw this morning — it was replaced."
  6. Test one variable. Compare kubectl get pod <name> -o jsonpath='{.metadata.uid}' against a UID you noted earlier, instead of assuming replacement vs. in-place restart.
  7. Apply the safest fix. If it's IP churn, fix the caller to use a Service/DNS name — don't hardcode Pod IPs, and don't delete more Pods while you're still diagnosing.
  8. Verify recovery. Confirm the dependent system can reach it again through the Service, not just that the Pod itself looks healthy.
  9. Document the root cause. "Hardcoded Pod IP; Pod identities are not stable" — write this down, don't just fix and move on.
  10. Prevent recurrence. Add a review check: no raw Pod IPs in application config, ever — only Service DNS names.

Security note: a bare Pod runs under the default ServiceAccount of its namespace unless you set spec.serviceAccountName explicitly — it inherits whatever RBAC permissions that ServiceAccount has. A debug Pod you spin up with a broad, convenient base image inherits that same blast radius. Use a minimal image and the least-privileged ServiceAccount available for anything you run interactively, not just for real workloads.

Reliability note: "no self-healing" isn't a footnote, it's the headline reliability property of a bare Pod. There is a real cost dimension too: an abandoned debug Pod nobody deletes sits consuming node CPU/memory allocation indefinitely, since nothing is watching it to clean it up either.

Common mistake: creating bare Pods for real workloads because it's the first primitive you learn, then being surprised weeks later when a routine node drain takes the workload down permanently instead of rescheduling it.

Common mistake: assuming "restart" means the same Pod comes back. It doesn't. restartPolicy only governs whether the kubelet restarts a failed container inside a Pod that still exists — it has nothing to do with what happens when the Pod itself is deleted or evicted.

Decision guide

OptionUse whenAvoid whenTrade-off
Bare PodQuick interactive debugging, one-off scratch workAnything that must survive a node failureNo self-healing, no rolling updates, no scaling
DeploymentStateless replicated app (web API, worker pool)App needs stable per-instance identity or storageSlight extra YAML for a real controller and rollout history
JobRun-to-completion task (migration, one-time batch)Anything meant to run indefinitelyWon't restart the workload once it succeeds — by design
DaemonSetExactly one Pod per (matching) node — log shipper, node exporterApp doesn't need to run on every nodeScales with your node count, not your traffic

Default recommendation: reach for a Deployment even for a single replica — it costs you nothing extra in complexity and buys self-healing for free. Use a bare Pod only when you explicitly want something disposable and unmanaged.

Knowledge check

Q1. If the Node running your bare Pod crashes, what recreates the Pod?

Nothing. A bare Pod has no controller watching it, so it stays gone until you (or something else) create it again.

Q2. Which restartPolicy value means Kubernetes never automatically restarts a failed container in the Pod?

B. Never — the container is left stopped. (Always is the Pod default; OnFailure restarts only on a non-zero exit code; "Default" isn't a real value — there's no config-driven fourth option.)

Production challenge

Objective

Fix a hardcoded-Pod-IP bug yourself, without being told the exact fix — using only what this lesson covered.

Scenario

Your teammate wrote a health-check script that runs from inside a debug Pod on the cluster. It curls a backend Pod's IP address directly and worked fine yesterday. Today it fails.

Environment assumptions

A kind/minikube cluster. Create the setup yourself first:

kubectl run backend --image=nginx:1.29 --labels=app=backend
kubectl expose pod backend --port=80 --name=backend-svc
kubectl run debugger --image=busybox --restart=Never -it --rm -- sh -c \
  "wget -qO- http://$(kubectl get pod backend -o jsonpath='{.status.podIP}')"

Commands

Force the exact failure from the scenario, then fix it:

# 1. Force an IP change, simulating the backend Pod being replaced
kubectl delete pod backend
kubectl run backend --image=nginx:1.29 --labels=app=backend

# 2. Re-run the ORIGINAL hardcoded-IP script above — it now fails or hits the wrong Pod

# 3. Fix it: use the Service name instead of a Pod IP
kubectl run debugger --image=busybox --restart=Never -it --rm -- sh -c \
  "wget -qO- http://backend-svc"

Expected result

Step 2 fails or silently succeeds against stale data if the old IP was reassigned; step 3 succeeds regardless of how many times backend has been replaced.

Verification

Repeat the delete-and-recreate cycle on backend a second time, then re-run only the Service-name version. It should keep working every time — that repeatability is the actual proof, not a single success.

Common failure

"Fixing" it by hardcoding the new IP instead of switching to the Service name — this doesn't fix the root cause, it just delays the next failure.

Troubleshooting

Service DNS names (like backend-svc) only resolve from inside the cluster's network — that's why the debug script runs as a Pod on the cluster, not from your laptop. If you try this from outside the cluster, name resolution will fail; that's expected, not a bug in this exercise.

Cleanup / rollback

kubectl delete pod backend --ignore-not-found
kubectl delete service backend-svc --ignore-not-found

Production lesson

"It worked yesterday" plus "nothing changed in my code" is exactly the signature of a Pod-identity bug. Lesson 3 covers Services in depth — this challenge is why they exist.

Recap
  • A Pod = one or more containers sharing network and storage; every object follows the same apiVersion/kind/metadata/spec shape.
  • Kubernetes never repairs a Pod — a "restarted" Pod is actually a new object with a new UID and usually a new IP.
  • restartPolicy (Always default, OnFailure, Never) only governs containers restarting inside a Pod that still exists — it has no effect on Pod-level replacement.
  • A bare Pod has no controller watching it — no self-healing, no rolling updates. Default to a Deployment instead.
  • CrashLoopBackOff is a kubectl status string, not a real Pod phase — the real values are Pending, Running, Succeeded, Failed, Unknown.
