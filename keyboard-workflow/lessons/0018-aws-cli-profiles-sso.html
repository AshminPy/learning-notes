AWS CLI: profiles, SSO, and checking who you actually are

Identity and secrets are sorted for Git and SSH. The same problem shows up again with cloud CLIs: one AWS CLI install, several AWS accounts — personal sandbox, work dev, work production — and running a command against the wrong one is exactly how real incidents start. Today: named profiles that keep the accounts apart, and the one habit that catches a mistake before it becomes an outage.

Simple example: imagine a terminal with two accounts open at once, but nothing on screen says which one is active. You run a deploy thinking you're in a sandbox account and you're actually in production. Named profiles turn "which account am I in" from a guess into something you check with one command before every risky action.

Two files, two jobs

The AWS CLI splits configuration across two files, and mixing up what goes where is a common early mistake:

FileHoldsSection header
~/.aws/configSettings: region, output format, SSO details[profile work]
~/.aws/credentialsSecret material: access key ID and secret key[work] — no "profile" prefix
# ~/.aws/config
[profile work]
region = us-east-1
output = json

[profile personal]
region = us-west-2
output = json

Select a profile with a flag or an environment variable — the flag wins if both are set:

aws s3 ls --profile work
export AWS_PROFILE=work
aws s3 ls

Prefer SSO login over long-lived static keys

Static keys in ~/.aws/credentials work, but they're long-lived secrets sitting in a plaintext file — if one leaks, it stays valid until someone notices and deactivates it. AWS's own recommended path is IAM Identity Center (SSO) instead, which issues short-lived, auto-expiring credentials:

aws configure sso
SSO session name: example-sso
SSO start URL: https://example-org.awsapps.com/start
SSO region: us-east-1
SSO registration scopes: sso:account:access

This writes a profile plus a linked sso-session block into ~/.aws/config — no long-lived secret ever touches ~/.aws/credentials:

[profile work]
sso_session = example-sso
sso_account_id = 111122223333
sso_role_name = ExampleRole
region = us-east-1
output = json

[sso-session example-sso]
sso_region = us-east-1
sso_start_url = https://example-org.awsapps.com/start
sso_registration_scopes = sso:account:access

Sign in and out explicitly:

aws sso login --profile work
aws sso logout

Credentials from a signed-in session auto-renew while the session is valid and simply expire when it isn't — nothing to manually rotate, nothing to leave lying around after you're done.

The one habit that catches a wrong-account mistake

aws sts get-caller-identity needs no special permissions and returns exactly who you're authenticated as — run it before anything that changes real infrastructure:

aws sts get-caller-identity --profile work
{
    "UserId": "AIDAEXAMPLE000000000",
    "Account": "111122223333",
    "Arn": "arn:aws:iam::111122223333:user/example-user"
}

If the Account field isn't the one you meant to be in, stop — you just avoided running a command against the wrong AWS account.

Common mistake: running a command with neither --profile nor AWS_PROFILE set silently falls back to [default] — which may not be the account you think it is. Get in the habit of checking with aws sts get-caller-identity whenever the cost of being wrong is real.

Security note: never commit ~/.aws/credentials, and never paste an aws_secret_access_key into a script, ticket, or chat message — treat a static key exactly like a password. Prefer SSO wherever your organization supports it. If a static key does leak, deactivate it immediately in the IAM console — don't wait for a scheduled rotation.

Try it

Create ~/.aws/config with two example profiles (work and personal) using fake account IDs and different regions, as shown above. Run export AWS_PROFILE=work then aws configure list to see which profile and region are active without needing real credentials. Switch to personal and confirm the output changes. If you have real IAM Identity Center access, follow up with aws configure sso and aws sts get-caller-identity for real.

Quiz

Q1. Where do aws_access_key_id and aws_secret_access_key belong?

A. Secret material lives in credentials; settings like region and output live in config.

Q2. What does aws configure sso set up that static keys don't?

A. Session credentials expire on their own — nothing long-lived is left sitting in a file.

Q3. Which command confirms which account and identity you're using right now?

A. It needs no special permissions and returns UserId, Account, and Arn for whoever is calling it.

Q4. With no --profile flag and no AWS_PROFILE set, which profile runs?

A. The AWS CLI always falls back to [default] when nothing else selects a profile.

Q5. What should you do if a static AWS access key leaks?

A. A leaked key stays usable by anyone who has it until it's deactivated — every hour of delay is real exposure.

Recap
  • ~/.aws/config holds settings ([profile name]); ~/.aws/credentials holds secrets ([name]).
  • Select a profile with --profile or AWS_PROFILE — no selector falls back to [default].
  • aws configure sso is the recommended path: short-lived credentials, nothing long-lived to leak.
  • Run aws sts get-caller-identity before anything that changes real infrastructure — always verify, never assume.

Try solo: next time you're about to run a command against a real AWS account, make aws sts get-caller-identity the very first thing you type, before the command that actually does something.

If a profile behaves differently than you expect, paste the output of aws configure list and aws sts get-caller-identity back to your teacher — together they show exactly which file supplied which setting.
