direnv: stop switching profiles by hand

You now have multiple AWS profiles, multiple gcloud configurations, and soon multiple kubeconfigs too. Manually remembering to switch all three every time you cd between a work project and a personal one is exactly how "I thought I was on staging" mistakes happen — not because anyone was careless, but because remembering three separate commands, every single time, doesn't scale. direnv fixes this by making the switch automatic and tied to the directory itself.

Simple example: today, moving from a personal project folder into a work one means manually running export AWS_PROFILE=work, gcloud config configurations activate work, and maybe export KUBECONFIG=~/.kube/work-config — three commands, every time, easy to forget one. direnv's fix: write those exports once, inside the project folder itself, and let cd do the switching from then on.

The .envrc file: environment that lives with the project

Install direnv and hook it into your shell:

brew install direnv

Add this line to ~/.zshrc, then restart your terminal or run source ~/.zshrc:

eval "$(direnv hook zsh)"

Now, inside a project directory, create a file named .envrc:

export AWS_PROFILE=work
export CLOUDSDK_ACTIVE_CONFIG_NAME=work
export KUBECONFIG=~/.kube/work-config

cd into that directory and direnv checks for the file on every prompt — but it won't load a file it hasn't seen before. You'll get a warning that the file isn't allowed yet. Approve it once:

direnv allow

From then on: cd into the directory and all three variables load automatically; cd back out and they unload automatically, with nothing left behind in your shell.

Why the allow step exists — and why not to route around it

An .envrc file is just shell code, and direnv would otherwise execute it automatically the instant you cd in — before you've opened the folder, read a README, or looked at a single file. If a malicious .envrc came bundled inside a cloned repo, that's arbitrary shell code running silently on nothing more than a directory change. The allow step forces a human decision the first time a file appears, and again any time its contents change — that's a deliberate safety feature, not friction to script around.

Common mistake: editing an already-allowed .envrc, adding a new line, and being confused when it doesn't take effect. direnv detects the file changed and re-blocks it until you run direnv allow again — that's the same protection working correctly, not a bug.

Security note: never disable or bypass the allow check to save a step — treat every unfamiliar .envrc the same way you'd treat an unfamiliar shell script: read it before you approve it, especially in a repo you didn't write yourself.

Try it

Install direnv and add the shell hook. Create a folder, e.g. ~/example-work-project, and inside it write an .envrc with the three example exports above. Run echo $AWS_PROFILE — nothing yet. cd into the folder, see the blocked warning, run direnv allow, then cd out and back in and run echo $AWS_PROFILE again to watch it appear and disappear on its own.

Quiz

Q1. What triggers direnv to load or unload variables?

A. direnv checks for an .envrc on every prompt, keyed to the current directory.

Q2. What must you do before direnv loads a brand-new .envrc?

A. Nothing else substitutes for the explicit allow step — that's the whole point of it.

Q3. Why does direnv require that explicit allow step at all?

A. An .envrc is arbitrary shell code — allow forces a human decision before it ever runs.

Q4. You edit an already-allowed .envrc and add a new line. What happens on the next cd in?

A. Any content change re-triggers the same allow check — expected behavior, not a glitch.

Q5. What real problem does this .envrc setup actually solve?

A. direnv doesn't replace the profiles from the last two lessons — it automates switching between them.

Recap
  • An .envrc file auto-loads on cd in and auto-unloads on cd out — no manual export or unset.
  • Install with brew install direnv, hook into ~/.zshrc with eval "$(direnv hook zsh)".
  • A new or changed .envrc is blocked until you run direnv allow — a deliberate safety check, not friction.
  • Use it to bundle AWS_PROFILE, CLOUDSDK_ACTIVE_CONFIG_NAME, and KUBECONFIG per project, replacing three manual switches with one cd.

Try solo: add a real .envrc to one project folder you actually use, using your own real profile and configuration names — not the placeholders from this lesson.

If a variable isn't appearing after cd-ing in, run direnv status and paste the output back to your teacher — it usually pinpoints whether the file is blocked, has a syntax error, or was never found in the first place.
