kubeconfig and fast context switching

The last lesson used direnv to make variables like AWS_PROFILE and KUBECONFIG change automatically per project folder. This lesson opens that KUBECONFIG file itself: what's actually inside it, how several of them merge into one, and how to jump between clusters fast without ever wondering which one you're pointed at. This lesson assumes you already know basic kubectl — if get pods and describe are new to you, the Kubernetes administration course covers that ground first.

Mental model: think of a kubeconfig file as a phone's contact list. Each saved contact — a context — is a shortcut to three things at once: an address (cluster), an ID badge to show at the door (user), and a default room to walk into (namespace). Picking a contact by name is faster and safer than typing the address, presenting your badge, and stating your floor separately, every single time.

Inside a kubeconfig file: clusters, users, contexts

A kubeconfig file has three lists and one pointer:

  • clusters — a server address plus the certificate needed to trust it
  • users — credentials: a client certificate, a token, or similar
  • contexts — a named pairing of one cluster, one user, and (optionally) a default namespace
  • current-context — which context kubectl uses when you don't say otherwise

Here's a minimal example with clearly made-up values — never paste real cluster addresses or credentials into a file you're just practicing with:

apiVersion: v1
kind: Config
current-context: sandbox

clusters:
- name: sandbox-cluster
  cluster:
    server: https://203.0.113.10:6443
    certificate-authority-data: DATA+OMITTED
- name: staging-cluster
  cluster:
    server: https://203.0.113.20:6443
    certificate-authority-data: DATA+OMITTED

users:
- name: sandbox-admin
  user:
    client-certificate-data: DATA+OMITTED
    client-key-data: DATA+OMITTED
- name: staging-viewer
  user:
    token: REDACTED

contexts:
- name: sandbox
  context:
    cluster: sandbox-cluster
    user: sandbox-admin
    namespace: default
- name: staging
  context:
    cluster: staging-cluster
    user: staging-viewer
    namespace: web-team

Two contexts, two clusters, two different users — and current-context: sandbox says which pairing is active right now. Switching contexts never edits your credentials; it just moves the pointer.

One file becomes many: KUBECONFIG and merging

With nothing set, kubectl reads ~/.kube/config alone. Set the KUBECONFIG environment variable to a colon-separated list of paths (macOS and Linux; semicolons on Windows) and kubectl merges all of them into one logical config, without you ever combining the files by hand:

export KUBECONFIG=$HOME/.kube/config-personal:$HOME/.kube/config-freelance
kubectl config get-contexts

That's genuinely useful once you have configs from more than one source — one file from a personal learning cluster, another handed to you by a client or employer. Instead of copy-pasting entries into a single file, list both paths and let kubectl merge them on the fly.

The merge has one hard rule, straight from kubectl config --help: "When a value is modified, it is modified in the file that defines the stanza. When a value is created, it is created in the first file that exists." In practice — if two files both define a context called prod, the first file in the list wins for that name; the second file's version of prod is ignored entirely, not merged field by field.

Security note: a kubeconfig file is a credential, not just settings — treat it like one. Don't commit it to a public repo, don't email it, and be careful merging in a file from a source you don't fully trust: a same-named context or cluster entry from an untrusted file can silently shadow one of yours if it happens to load first.

Want one portable file instead of juggling several? kubectl config view --flatten > ~/.kube/config-merged writes a single, self-contained file with everything resolved — handy for copying a working setup to another machine.

Switching fast: kubectl config vs kubectx/kubens

The built-in commands work everywhere and need no install:

CommandWhat it does
kubectl config get-contextsList every context; a * marks the active one
kubectl config current-contextPrint just the active context's name
kubectl config use-context <name>Switch the active context
kubectl config set-context --current --namespace=<ns>Change only the default namespace of the current context

That's correct but wordy for something you do dozens of times a day. kubectx and kubens are two small, actively maintained tools built exactly for this — last release March 2026, commits landing as recently as this month. Install both with brew install kubectx (it installs kubectx, kubens, and the kubectl ctx/kubectl ns plugin forms):

kubectx                # list contexts, current one highlighted
kubectx staging        # switch to the context named "staging"
kubectx -               # jump back to the previous context
kubens web-team         # switch namespace within the current context
kubens -                 # jump back to the previous namespace

Same outcome as the table above, in a fraction of the keystrokes — and kubectx - / kubens - have no built-in equivalent at all: they're a genuinely new capability, not just a shortcut.

The wrong-cluster guardrail

The single most expensive Kubernetes mistake is running a destructive command against the wrong cluster because you assumed you were still on sandbox. Two habits fix this:

  • Check before you act. Run kubectl config current-context (or kubectx -c) before any delete, apply, or rollout restart — make it reflexive, the way you'd glance at a street sign before crossing.
  • Make it visible everywhere, always. A context-aware shell prompt removes the need to remember to check at all. kube-ps1 (brew install kube-ps1, still active as of this year) prints the current context and namespace directly in your prompt, on every line. Lesson 23 wires this permanently into your .zshrc.

Try it

Save the example kubeconfig from this lesson to ~/.kube/config-practice (it points at fake servers, so nothing will actually connect). Run KUBECONFIG=~/.kube/config-practice kubectl config get-contexts to see both contexts listed. Then, with kubectx installed, run KUBECONFIG=~/.kube/config-practice kubectx staging followed by kubectx -c to confirm the switch, and kubectx - to jump back to sandbox.

Quiz

Q1. What three things does a single kubeconfig context bundle together?

A. A context is just a named pairing of cluster + user + (optionally) namespace — nothing more.

Q2. Two files on your KUBECONFIG path both define a context named "prod". What happens?

A. Per kubectl config --help, an existing value stays with the file that first defined it — the later file's version of "prod" is dropped, not blended in.

Q3. Which command changes only the default namespace, without switching clusters?

A. Only set-context accepts both --current and --namespace together to edit the active context in place — use-context, set-cluster, and get-contexts don't take that flag combination.

Q4. What does kubectx add that plain kubectl config commands don't have?

A. kubectx - and kubens - toggle back to the previous value — there's no built-in kubectl equivalent for that.

Q5. Before running a destructive command, what's the safest habit to build?

A. A quick kubectl config current-context (or a prompt that always shows it) catches the "wrong cluster" mistake before it becomes an incident.

Recap
  • A kubeconfig has clusters, users, and contexts — a context just names one cluster + one user + an optional namespace together.
  • KUBECONFIG takes a colon-separated list of files and merges them; for a name defined in more than one file, the first file wins, no field-by-field blending.
  • kubectl config get-contexts / use-context / set-context --current --namespace= work everywhere; kubectx/kubens (actively maintained, brew install kubectx) make the same moves in far fewer keystrokes.
  • Before anything destructive: check current-context, or better, keep it always visible with a prompt tool like kube-ps1.
