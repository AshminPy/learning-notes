gcloud CLI: configurations, and the login command that trips everyone up

Same multi-account problem as AWS, different cloud — and gcloud adds one extra wrinkle. There are two different "login" commands, and they authenticate two completely different things. Mixing them up is one of the most common GCP mistakes, including among people who've used gcloud for years. Today: named configurations to keep accounts apart, and the one distinction worth memorizing for good.

Mental model: gcloud auth login is you badging into the building — it lets you personally walk around and open doors. gcloud auth application-default login is issuing a badge to a robot that acts on your behalf while you're not there — your code, Terraform, a client library. They're separate badges for separate wearers. Badging in yourself doesn't badge in your robot too.

Named configurations: account, project, and region, bundled

A gcloud "configuration" bundles an account, a default project, and default region/zone settings under one name, so switching contexts is one command instead of several:

gcloud config configurations create work
gcloud config set account work@example.com
gcloud config set project example-work-project
gcloud config set compute/region us-central1
gcloud config set compute/zone us-central1-a

gcloud config configurations create personal
gcloud config set account personal@example.com
gcloud config set project example-personal-project

Switch between them, and check what's currently active:

gcloud config configurations activate personal
gcloud config configurations list
gcloud config list

gcloud config list prints the active configuration's actual settings — account, project, region — so you can confirm the switch actually took before running anything else.

auth login vs. application-default login

This is the distinction that matters most. gcloud auth login authorizes the gcloud CLI itself — the commands you type interactively, like gcloud compute instances list. It obtains your user credentials through a web-based flow and sets the active account for your current configuration.

gcloud auth application-default login is separate: it produces Application Default Credentials (ADC), the credentials read by client libraries and tools like Terraform's Google provider — not by the gcloud CLI's own commands. Google's own docs are explicit about this: "The gcloud CLI itself doesn't use ADC to access Google Cloud resources."

gcloud auth login
gcloud auth application-default login

Running one does not authenticate the other. If Terraform can't authenticate against GCP, the fix is almost always application-default login, not logging in again with plain auth login.

Verify before you run anything

Two commands, two different questions:

gcloud config list
gcloud auth list

gcloud config list shows which configuration is active and what it's set to. gcloud auth list shows every account gcloud has stored credentials for, and marks which one is currently active — useful when a configuration says one account but the credentials backing it have gone stale.

Common mistake: assuming gcloud auth login alone is enough for Terraform or a client library to work. Most tooling reads Application Default Credentials, not your interactive gcloud session — without application-default login, that tooling has nothing to authenticate with, even while gcloud itself works fine.

Security note: don't run gcloud auth application-default login casually on a shared or production server — any script or library on that machine picks up those credentials automatically, which widens the blast radius far past your own terminal session. Never commit an application_default_credentials.json file or a downloaded service account key to a repo, and never point GOOGLE_APPLICATION_CREDENTIALS at a key file sitting somewhere shared.

Try it

Create two named configurations, work and personal, with placeholder account and project values as shown above. Activate each in turn and run gcloud config list after every switch to confirm it changed. Then run gcloud auth list and compare it against gcloud config list — one tells you which configuration is active, the other tells you which accounts actually have valid credentials behind them.

Quiz

Q1. What does gcloud auth login authorize?

A. It's your own interactive session with the gcloud CLI — nothing more.

Q2. What does gcloud auth application-default login provide credentials for?

A. Per Google's own docs, the gcloud CLI itself doesn't use ADC — this command is for everything else that does.

Q3. Which command switches which named configuration is active?

A. Create makes a new one; activate switches which existing one is in use.

Q4. Which command shows the properties of the currently active configuration?

A. describe needs you to already know a configuration's name; list shows what's active right now.

Q5. Why avoid running application-default login casually on a shared server?

A. ADC is a shared, well-known location — anything running on that machine can read it, not just you.

Recap
  • A named configuration bundles account, project, and region — switch with configurations activate, verify with gcloud config list.
  • gcloud auth login authenticates the CLI itself; gcloud auth application-default login authenticates everything else (Terraform, client libraries).
  • The gcloud CLI does not use ADC for its own commands — that's Google's own stated distinction, not an implementation detail.
  • gcloud auth list shows every stored account and which one is active — check it alongside gcloud config list.

Try solo: the next time a Terraform run fails to authenticate against GCP, resist the urge to run gcloud auth login again — check gcloud auth application-default login first.

If a tool "can't find credentials" even though gcloud itself works fine, paste the exact error back to your teacher along with the output of gcloud auth list — nine times out of ten it's the ADC vs. CLI-login mixup this lesson covers.
