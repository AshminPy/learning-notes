Git with multiple GitHub accounts, without the accidents

SSH access, secured. Sessions, persistent. Now the identity problem: most SRE and platform engineers carry at least two GitHub accounts — work and personal — on the same laptop. Sooner or later, one gets used for the other: a personal side project pushed under a work email, or worse, a work repo cloned and committed to under a personal identity. Today you make that mistake structurally impossible instead of something you just try to remember.

Mental model: think of each GitHub account as a different ID badge. With only one badge on your keychain, you swipe into whichever door you're facing — sometimes the wrong one. Give each identity its own badge (SSH key) and its own door (a Host alias), and the mixup stops being a matter of memory. The wrong badge simply doesn't open the wrong door.

The problem: Git identity is directory-blind by default

Fresh install, one global ~/.gitconfig, one user.name/user.email, usually one SSH key. Clone a work repo, clone a personal repo — both get authored with the same identity, because nothing on your machine distinguishes them. Nothing stops git push from working with the wrong key either, as long as that key happens to be the one your SSH agent offers first.

The fix is two independent layers: SSH decides which key authenticates you to GitHub, and Git config decides which name and email get attached to a commit. Both need to be set up per account, not left as one shared default.

Step 1: one SSH key per account

ssh-keygen -t ed25519 -C "work@example.com" -f ~/.ssh/id_ed25519_work
ssh-keygen -t ed25519 -C "personal@example.com" -f ~/.ssh/id_ed25519_personal

Add each public key (the .pub file) to the matching GitHub account under Settings → SSH and GPG keys. Two accounts, two keys — never share one key across both.

Step 2: Host aliases in ~/.ssh/config

GitHub only recognizes github.com as a hostname, so you can't just add a second Host github.com block. Instead, invent an alias per account and point each one at the real host:

Host github.com-work
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_work
  IdentitiesOnly yes

Host github.com-personal
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_personal
  IdentitiesOnly yes

IdentitiesOnly yes stops SSH from trying other loaded keys first — without it, a busy agent holding several keys can authenticate with the wrong one before it ever reaches the IdentityFile you specified. Test each alias:

ssh -T git@github.com-work
ssh -T git@github.com-personal

Then clone using the alias host, not github.com directly:

git clone git@github.com-work:example-org/example-project.git
git clone git@github.com-personal:example-user/side-project.git

Step 3: point each directory tree at the right identity

SSH now picks the right key per clone. Git config needs the same split, keyed off where the repo lives on disk, using includeIf:

# ~/.gitconfig
[user]
  name = Personal Name
  email = personal@example.com

[includeIf "gitdir:~/work/"]
  path = ~/.gitconfig-work
# ~/.gitconfig-work
[user]
  name = Work Name
  email = work@example.com
[core]
  sshCommand = ssh -i ~/.ssh/id_ed25519_work

Any repo cloned under ~/work/ now picks up the work identity automatically — no per-repo git config user.email to remember. Everything else falls back to the personal identity in the top-level [user] block.

Verify before your first commit

Don't trust the setup — check it, every time you start work in a new clone:

cd ~/work/example-project
git config user.email
# expect: work@example.com

If it prints the wrong address, the gitdir pattern in includeIf doesn't match this directory — fix the path before you commit, not after.

Common mistake: cloning with a plain git clone git@github.com:org/repo.git inside your work folder still uses whatever key a bare Host github.com entry (or the agent's first offered key) resolves to — not necessarily the work key. Always clone through the account-specific alias, or set up a URL rewrite with git config --global url."git@github.com-work:example-org/".insteadOf "git@github.com:example-org/" so plain URLs get rewritten automatically for that org.

Security note: never reuse one SSH key across a work and a personal account — if the work account is ever offboarded or audited, a shared key makes revocation messy and can lock you out of the personal account too. Never commit a private key file, and never paste key material into a chat, ticket, or repo, even a private one.

Try it

Set this up end to end with two example accounts. Generate id_ed25519_work and id_ed25519_personal, add the two Host aliases to ~/.ssh/config, create ~/work/ and ~/.gitconfig-work with the includeIf block, then clone one test repo into each directory tree and run git config user.email in both before touching a single commit.

Quiz

Q1. What does IdentitiesOnly yes prevent?

A. Without it, a loaded agent key can authenticate before SSH ever reaches your named IdentityFile.

Q2. What does includeIf "gitdir:~/work/" do in ~/.gitconfig?

A. It's a conditional include — the settings in the referenced file only apply to matching directory trees.

Q3. Before your first commit, which command confirms the identity Git will use?

A. Run this inside the actual repo directory — it shows the value Git will attach to your next commit.

Q4. Why clone through github.com-work instead of plain github.com?

A. The alias is what routes the connection to the right key — plain github.com has no way to know which account you mean.

Q5. What real risk does this whole setup exist to prevent?

A. Everything here — keys, aliases, includeIf, the verify step — targets one failure mode: the wrong "you" making the commit.

Recap
  • One SSH key per account, added to a Host alias in ~/.ssh/config (never a bare github.com entry per account).
  • Clone through the alias host so SSH picks the right key automatically — git@github.com-work:..., not git@github.com:....
  • includeIf "gitdir:..." in ~/.gitconfig points a whole directory tree at a different [user] block.
  • Always run git config user.email before your first commit in a new clone — verify, don't assume.

Try solo: add a third identity (a client's account, say) using the same pattern — new key, new alias, new includeIf block — without looking back at this lesson.

If git config user.email ever prints the wrong address, paste your ~/.ssh/config and ~/.gitconfig back to your teacher — a mismatched gitdir pattern is the almost-always cause, and it's easy to spot with a second pair of eyes.
