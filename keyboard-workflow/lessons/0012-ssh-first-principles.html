Keyboard Workflow — Lesson 12 of 24

SSH from first principles

Lessons 12 through 15 build one skill: reaching remote machines safely, entirely from the keyboard. SSH is the protocol underneath all of it — an encrypted remote shell, not just "the command that gets you a prompt on another box." Today you build the foundation: a real key pair, an agent that remembers it for you, and the host-key check that keeps a stolen password from becoming a stolen fleet.

Mental model: a key pair is a lock and its one matching key. The public key is the lock — hand out copies freely, pin one to as many servers as you want. The private key is the only key that opens any of those locks. It never leaves your machine, never gets emailed, never gets pasted into a server.

What SSH actually does

SSH (Secure Shell) opens an encrypted channel between your machine and a remote one, then runs a shell — or a single command — on the far end through that channel. Two jobs happen every time you connect:

  • Encryption — everything you send and everything the server sends back is unreadable to anyone watching the network in between.
  • Authentication — the server proves who it is with its own host key, and you prove who you are with yours. A password can do this. A key pair does it better: nothing secret ever has to cross the network.

Generate a real key pair

ssh-keygen -t ed25519 -C "generic-example@example.com"

-t ed25519 picks the key type. Ed25519 is the modern default for a reason: it's a newer elliptic-curve algorithm that gives strong security from a small, fixed-size key — faster to generate, faster to verify, and simpler to get right than RSA, which needs at least 3072 bits today to be considered adequate. Unless something you're connecting to genuinely can't support it, Ed25519 is the right default. -C just sets a comment on the public key, so use it to label which key this is — never to store anything secret.

You'll be asked where to save the key (the default ~/.ssh/id_ed25519 is fine) and for a passphrase. Set one — an unencrypted private key file is one stolen laptop away from a stolen identity. This creates two files: id_ed25519 (private — this stays put) and id_ed25519.pub (public — this is the one you hand out).

Security note: the private key file never gets copied to a server, never gets pasted into a chat for "quick debugging," and never gets committed to a repo — not even a private one. Only the .pub file is ever meant to leave your machine.

ssh-agent and ssh-add: stop retyping your passphrase

A passphrase-protected key is safer at rest, but typing that passphrase on every single connection gets old fast. ssh-agent is a small background process that holds your decrypted key in memory for your session — unlock it once, and every connection after that just uses the agent.

ssh-add ~/.ssh/id_ed25519   # unlock once, agent remembers it
ssh-add -l                  # list what the agent currently holds

macOS starts an agent for you automatically at login, so you don't need to launch one by hand. ssh-add -l is your sanity check: if it reports no identities, the agent is empty and your next connection is about to ask for that passphrase again.

Host-key verification: known_hosts

The first time you connect to a new host, SSH shows you that host's fingerprint and asks you to confirm it. Accept it, and SSH stores that fingerprint in ~/.ssh/known_hosts. Every connection after that, SSH quietly checks the host's key against what's on file — and if it ever doesn't match, you get this:

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!

There are two real explanations. The boring one: the host was rebuilt, reimaged, or had its keys legitimately rotated. The dangerous one: something between you and that host is impersonating it — a machine-in-the-middle attack. The warning alone can't tell you which. That's the entire point of showing it to you instead of deciding for you.

Common mistake: running ssh-keygen -R hostname to clear the old entry and reconnect, on autopilot, every time this shows up. That command makes the warning go away — it does not tell you whether the change was legitimate. Confirm out of band first: ask whoever manages that host whether it was rebuilt or had keys rotated recently. Only then clear the old entry and reconnect.

Try it

Generate a real key pair with the command above (a throwaway comment is fine). Load it — ssh-add ~/.ssh/id_ed25519 — then confirm it's loaded with ssh-add -l. Now turn on Remote Login (System Settings → General → Sharing → Remote Login) and connect to your own Mac: ssh yourusername@localhost. Watch the first-connection fingerprint prompt happen for real, accept it, then check ~/.ssh/known_hosts for the new line it added.

Quiz

Q1. What does the private key in an SSH key pair do?

A. The private key never leaves your machine — only its matching public key is ever handed out.

Q2. Why is Ed25519 the recommended default key type today?

A. Ed25519 gives strong security from a small, fixed-size key — simpler and faster than RSA, which needs much larger keys to reach comparable strength.

Q3. What problem does ssh-agent solve?

A. The agent holds your decrypted key in memory so you unlock it once, not on every connection.

Q4. A host shows "REMOTE HOST IDENTIFICATION HAS CHANGED." What should you do first?

A. The warning can't tell you whether the cause is a legitimate rebuild or an attack — verify with whoever manages the host before clearing it.

Q5. Where does SSH store a host's fingerprint after you first accept it?

A. ~/.ssh/known_hosts is the local record SSH checks on every later connection to that host.

Recap
  • A key pair is a lock (public key, hand it out) and its one matching key (private key, never leaves your machine).
  • ssh-keygen -t ed25519 -C "..." generates a modern key pair; ssh-agent + ssh-add mean you only type the passphrase once per session.
  • ~/.ssh/known_hosts remembers every host's fingerprint — a mismatch triggers a warning that needs a real answer, not a reflex ssh-keygen -R.

Try solo: next time you SSH into something new, actually read the fingerprint prompt before typing "yes" — get in the habit of treating it as a real question, not a formality.
