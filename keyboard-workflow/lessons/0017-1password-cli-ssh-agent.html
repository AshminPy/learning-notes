1Password's SSH agent and the op CLI: one secrets story

Last lesson sorted out which identity commits as you. This one sorts out what backs that identity: SSH keys sitting as plaintext files, a separate gpg-agent for commit signing, and cloud credentials that too often get pasted into a terminal or a .env file "just for now." Juggling three separate secrets stories is itself a security risk — the more places a secret can leak from, the more places it eventually does. Today: one tool that replaces all three.

Mental model: a normal ssh-agent is like carrying your actual house key in your pocket — decrypted, physical, and lost the moment the pocket is. 1Password's SSH agent is a keycard system instead: your key material never leaves the vault, each request is approved or denied on the spot, and nothing you can lose was ever handed to you in the first place.

The problem with plaintext secrets

A classic ssh-agent holds decrypted keys in memory, but the private key itself still lives on disk as a file — copyable, backup-able, exfiltratable. Separately, cloud CLI secrets tend to end up pasted into .env files that get accidentally committed, or exported directly in a terminal command that lands permanently in ~/.zsh_history. Add a third tool for GPG commit signing and you're now maintaining three unrelated secret stores by hand.

1Password SSH agent: keys that never touch disk

1Password can store an SSH key's private material encrypted inside a vault and run a local agent process that answers SSH's authentication requests on your behalf — the key bytes never get written to a file on disk in plaintext. Setup, on macOS:

  1. Open 1Password's Settings, go to the Developer tab, and turn on the SSH agent.
  2. Add or generate an SSH key inside 1Password (item type "SSH Key"), or import an existing one.
  3. Point SSH at 1Password's agent socket in ~/.ssh/config:
Host *
  IdentityAgent "~/Library/Group Containers/2BUA8C4S2C.com.1password/t/agent.sock"

Confirm it's working:

ssh-add -l

This lists the keys 1Password is offering — without ever exposing the private key bytes to your shell. When you SSH or git push, 1Password prompts you (Touch ID or your unlock method) to approve the connection each time it's used.

op CLI: secrets into a command, not into a file

The same vault backs the op CLI, which injects a secret straight into a running process's environment — it's never written to disk and never typed into a command that lands in shell history:

export DB_PASSWORD="op://Example-Vault/example-item/password"
op run -- ./deploy.sh

op run scans for op:// references, resolves them only inside the subprocess's memory, and masks them in printed output by default. It also reads a whole file of references at once:

op run --env-file="./.env" -- terraform apply

where .env holds only pointers, never real values:

AWS_SECRET_ACCESS_KEY=op://Example-Vault/aws-example/secret

Common mistake: pasting a real secret value into a .env file "just to get it working," meaning to swap it for a reference later. The file gets committed the moment someone forgets it's in .gitignore. An op:// reference is safe to commit — it's a pointer, not a secret — so write it that way from the first line, not as a cleanup step.

The free alternative: macOS Keychain

If you don't want another app in the mix, macOS Keychain Access is a fair, honest option — built in, no cost, protected by your login password, and perfectly fine for simple per-app credential storage (Wi-Fi passwords, Safari logins). What it doesn't give you is an SSH agent socket you can point tooling at, a CLI secret-injection workflow like op run, or shared vaults for a team. For a single-user machine with modest needs, Keychain alone can be enough — 1Password earns its keep once you're managing SSH keys, signing keys, and cloud secrets together, across more than one identity.

Security note: never paste a real access key, password, or token into a shell command, a script, or a plaintext file — not even "temporarily." Never share a vault's master password or Secret Key with anyone, including a teammate who says they just need it once. If a secret ever does leak, rotate it immediately rather than hoping no one finds it.

Try it

In the 1Password app, enable the SSH agent (Settings → Developer), add the IdentityAgent line to ~/.ssh/config exactly as shown above, then run ssh-add -l and confirm 1Password lists a key. Next, create one throwaway item in a vault, set a reference like export TEST_VAR="op://Private/example-item/some-field" (using your own vault and item names), and run op run -- printenv TEST_VAR to see it resolve without ever appearing in your shell history.

Quiz

Q1. What's different about a key stored in 1Password's SSH agent?

A. A classic ssh-agent still reads key bytes from a plaintext file on disk; 1Password's never does.

Q2. What does the IdentityAgent line in ~/.ssh/config do?

A. It's how SSH is told to ask 1Password's agent process for keys instead of the OS default.

Q3. What does op run -- some-command avoid that a hardcoded secret doesn't?

A. The reference is resolved only inside the subprocess's memory, at runtime, and masked in output.

Q4. Which is a fair description of macOS Keychain next to 1Password's CLI workflow?

A. Keychain is genuinely useful for simple per-app storage; it just doesn't cover the SSH-agent and secret-injection workflow this lesson builds.

Q5. What should you never do with a real secret value, per this lesson?

Recap
  • 1Password's SSH agent keeps private key material in the vault — never written to disk in plaintext.
  • Point SSH at it with an IdentityAgent line in ~/.ssh/config; verify with ssh-add -l.
  • op run -- command injects secrets as environment variables for one subprocess only — never to disk, never to shell history.
  • macOS Keychain is a genuine free alternative for simple per-app credential storage — just without the SSH-agent and CLI-injection workflow.

Try solo: move one real SSH key you currently keep as a plaintext file into 1Password, delete the plaintext copy once the agent confirms it works, and confirm git push still succeeds.

If ssh-add -l shows nothing, or a git push still asks for a passphrase, paste the exact output back to your teacher — it's almost always the socket path in IdentityAgent or the agent toggle not being on.
