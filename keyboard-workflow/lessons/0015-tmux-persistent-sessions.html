tmux: persistent sessions

Here's the problem this lesson solves: you SSH into a remote host, start a long-running command, and then your laptop sleeps — or wifi drops, or you close the terminal by accident. Normally, that connection dying kills everything running inside it. The fix isn't a more stable network. It's running your work inside tmux on the remote host, so the SSH connection becomes disposable and the work isn't.

Mental model: sessions > windows > panes, like a browser. A session is the whole browser process — it keeps running even after you close the window. A window is a tab. A pane is a split view inside a tab. Detaching a session is like minimizing the browser, not quitting it.

Start a session, kill the connection, come back

tmux new -s work

This opens a new named session called work. Anything you run inside it now survives your SSH connection dying — start a long-running command, then detach on purpose to prove it:

Ctrl-b d

Ctrl-b is tmux's default prefix — press it, release it, then press the next key. d detaches: you're back at your normal shell, and the session keeps running in the background on the remote host, untouched. Close the SSH connection entirely if you want to prove the point. Then reconnect and:

tmux attach -t work

You're back exactly where you left off — same scrollback, same running commands. tmux ls lists every session currently alive on that host, in case you forget a name.

Windows and panes

KeysWhat it does
Ctrl-b cCreate a new window
Ctrl-b n / Ctrl-b pMove to the next / previous window
Ctrl-b %Split the current pane vertically (side by side)
Ctrl-b "Split the current pane horizontally (stacked)
Ctrl-b + arrow keyMove focus between panes

Windows are for separate tasks in the same session (logs in one, a shell in another). Panes are for watching more than one thing at once inside the same window — a log tail next to the shell you're actually typing in.

Security note: a detached session on a shared or multi-user host doesn't expire on its own. A forgotten, still-running root session left detached is a standing exposure — anyone who reaches that account inherits it, no login required. Kill sessions you're done with (tmux kill-session -t name) instead of just detaching and walking away. And never attach to a session someone else is actively also attached to right before typing a secret — you'd both be watching the same live screen.

A newer alternative: zellij

zellij is a newer terminal multiplexer solving the same core problem, with one real advantage for a beginner: it shows an on-screen bar of available keybindings as you use it, so you don't need a cheat sheet from day one. tmux's advantage is availability — it's been the standard for over a decade, and it's far more likely to already be installed on a remote production host you don't control. Learn tmux first, since it's what you'll actually find when you SSH somewhere; try zellij for your own local, interactive use if its discoverability appeals to you. Neither is definitively "better" — they solve the same problem differently.

Try it

On your own Mac: tmux new -s test, then run something long-lived like top. Detach with Ctrl-b d. Run tmux ls and confirm test is still listed as running. Reattach with tmux attach -t test, then split the window into two panes with Ctrl-b % and move between them with Ctrl-b + arrow keys.

Quiz

Q1. What actual problem does tmux solve?

A. Work inside tmux keeps running on the remote host even after the SSH connection carrying it dies.

Q2. What's the default keybinding to detach from a tmux session?

A. Prefix (Ctrl-b) then d — the session keeps running detached in the background.

Q3. In tmux's mental model, what sits directly inside a window?

A. Panes live inside windows, and windows live inside sessions — that's the full hierarchy.

Q4. Which command reattaches to a session named "work"?

A. tmux attach -t work reattaches to the existing session by name — new would create a fresh one instead.

Q5. How should zellij and tmux be weighed against each other, per current evidence?

A. Each has a genuine, different edge — zellij's on-screen keybinding hints vs. tmux's near-universal presence on remote hosts. Neither claim in B, C, or D holds up.

Recap
  • tmux keeps remote work alive across a dropped SSH connection — that's the entire reason to use it.
  • Sessions > windows > panes. tmux new -s name, Ctrl-b d to detach, tmux attach -t name to come back.
  • zellij is a real alternative with better discoverability; tmux wins on being already installed wherever you SSH.

Try solo: next real SSH session you start for a long-running task — a build, a sync, a deploy watch — start it inside tmux first, on principle, before you need it to save you.

Session not showing up when you reattach, or a keybinding not doing what this lesson describes? Paste what tmux -V reports — prefix and defaults occasionally differ between versions and distro configs.
