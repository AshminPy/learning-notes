SSH at scale: jump hosts, multiplexing, troubleshooting

One host, one key, one command — that's Lesson 12. Real SRE work is dozens of hosts, some reachable only through a bastion, connections you make over and over in the same session, and failures where "permission denied" tells you nothing on its own. This lesson covers the config file that replaces the long command, ProxyJump for hosts you can't reach directly, connection reuse for speed, and a repeatable way to actually debug a broken connection.

Mental model: ~/.ssh/config is a shell-alias file for connections. Instead of typing the full command with every flag, every time, you name the destination once and reuse the name.

Host blocks: aliases with real settings

Host myserver
    HostName 203.0.113.10
    User deploy
    Port 2222
    IdentityFile ~/.ssh/id_ed25519

Now ssh myserver does everything that long command used to. HostName is the real address; Host is just the name you type. You can also match a whole group at once, Host *.internal-example.net, to set something for every host in that pattern. Put the more specific blocks first — for any given setting, SSH uses the first value it finds, not the last, so specific overrides need to come before general ones.

ProxyJump: reaching a host you can't reach directly

The mental model: hop through one host that is reachable to get to another host that isn't directly reachable — a private-subnet target behind a public bastion, for example.

Host bastion
    HostName 203.0.113.1
    User jump-user
    IdentityFile ~/.ssh/id_ed25519

Host internal-app
    HostName 198.51.100.25
    User deploy
    IdentityFile ~/.ssh/id_ed25519
    ProxyJump bastion

ssh internal-app now hops through bastion automatically — one command, two hops. The inline equivalent, no config needed, is ssh -J jump-user@203.0.113.1 deploy@198.51.100.25. ProxyJump replaced the older ProxyCommand + nc trick — same result, no separate netcat binary required.

Multiplexing: reuse the connection

Your first connection to a host pays the full cost — TCP handshake plus the cryptographic negotiation. Every connection after that, to the same host, can ride the same already-open pipe instead of paying that cost again.

Host *
    ControlMaster auto
    ControlPath ~/.ssh/sockets/%r@%h-%p
    ControlPersist 600

Create the socket directory first: mkdir -p ~/.ssh/sockets. The first connection becomes the "master" and opens the control socket; every later connection to that same host — a second terminal tab, a quick scp — reuses it and connects almost instantly. ControlPersist 600 keeps that master connection alive for 10 minutes after the last client disconnects, so a burst of connections stays fast without holding the socket open forever.

Security note: a live control socket lets anyone who can read it ride your already-authenticated connection with no further login required. Keep the sockets directory private — chmod 700 ~/.ssh/sockets — and never point ControlPath at a location shared with other users, like a world-readable /tmp.

Troubleshooting: -v, and the #1 real cause of "permission denied"

ssh -v user@host (or -vvv for maximum detail) prints exactly what the client is doing — which keys it's offering, and why each one gets rejected. Read it in a real failure and the answer is usually right there.

The single most common real-world cause of Permission denied (publickey) isn't a wrong key — it's file permissions. SSH refuses to use a private key that's readable by anyone but you, and refuses to trust an ~/.ssh directory that's writable by anyone but you.

chmod 600 ~/.ssh/id_ed25519
chmod 700 ~/.ssh

Second check: is the right key even loaded? ssh-add -l lists what the agent currently holds — compare its fingerprint against the one ssh -v reports it tried to offer. If they don't match, that's the whole bug.

Try it

Write a ~/.ssh/config with the two-host chain above, using the example addresses as-is (they're reserved documentation ranges, not real hosts — swap in real ones when you have them). Then run ssh -v against any host you can already reach and read the "Offering public key" and "Authentications that can continue" lines it prints — that's the exact information you'd use to debug a real failure.

Quiz

Q1. What does a Host block in ~/.ssh/config let you do?

A. A Host block bundles HostName, User, Port, and IdentityFile under one short name you type instead.

Q2. What problem does ProxyJump solve?

A. ProxyJump hops through one reachable host to reach a second host that isn't directly reachable — a bastion pattern.

Q3. What does ControlPersist 600 do?

A. 600 is seconds — the master connection stays up for 10 minutes after the last client detaches, ready to be reused.

Q4. What is the most common real cause of "Permission denied (publickey)"?

A. SSH silently refuses a group- or world-readable private key — chmod 600 on the key and 700 on ~/.ssh is the usual fix.

Q5. You want to check the agent has the right key loaded before troubleshooting further. Which command shows that?

A. ssh-add -l is the one that reports what the agent is currently holding. B, C, and D are real, useful commands — just for different jobs.

Recap
  • ~/.ssh/config Host blocks turn a long command into a short alias — specific blocks should come before general wildcard ones.
  • ProxyJump hops through a bastion in one command; ControlMaster/ControlPath/ControlPersist reuse that connection so later hops are instant.
  • ssh -v/-vvv plus ssh-add -l is the real debugging loop — and file permissions (600/700) are the fix behind most "permission denied" surprises.

Try solo: take a real command you type often with several flags and turn it into a named Host block — measure how much shorter the daily version gets.

Stuck on a connection that still fails after checking permissions and the loaded key? Paste the full ssh -vvv output — the real cause is almost always visible in there.
