Dotfiles as code: bare repo vs. chezmoi

Three lessons in, you already have real config worth keeping: ~/.aerospace.toml (Lesson 1), a Karabiner Hyper key rule (Lesson 10), a Brewfile (Lesson 9). None of it is backed up, versioned, or restorable on a new Mac — it just lives in $HOME, one accidental deletion away from gone. This lesson turns that scattered config into something you can back up, diff, and restore with one command.

Mental model: treat your dotfiles like a production config, not a personal scribble. If you can't git log it, you can't tell what changed, when, or how to roll it back — the exact reason you wouldn't accept an unversioned config on a server.

Approach 1: the bare git repo

A normal git init creates a repo and a working tree in the same folder. You can't do that in $HOME — it would try to track your entire home directory, Downloads and all. A bare repo has no working tree of its own; you point it at $HOME separately, and an alias makes the whole thing feel like ordinary git:

git init --bare "$HOME/.dotfiles"
alias dotfiles='git --git-dir=$HOME/.dotfiles/ --work-tree=$HOME'
dotfiles config --local status.showUntrackedFiles no

That last line matters: without it, dotfiles status would list every untracked file in your entire home directory. With it, only files you've explicitly added ever show up.

Track your first real file and push it somewhere for backup:

dotfiles add ~/.aerospace.toml
dotfiles commit -m "Track AeroSpace config"
dotfiles remote add origin git@github.com:your-username/dotfiles.git
dotfiles push -u origin main

Add the alias line to your shell config so it survives a new terminal tab — Lesson 23 covers exactly where in that file it belongs.

Approach 2: chezmoi

chezmoi takes a different shape: it keeps a separate source copy of each dotfile (an ordinary git repo at ~/.local/share/chezmoi) and generates your real files from it — like a small build step for config. That extra layer is what buys you templating: one source file can produce different output per machine, so a hostname or a specific device name never has to be hardcoded twice.

brew install chezmoi
chezmoi init
chezmoi add ~/.aerospace.toml
chezmoi edit ~/.aerospace.toml
chezmoi diff
chezmoi apply -v

chezmoi edit opens the source copy, not the live file — chezmoi diff then shows exactly what would change, and apply writes it out for real. On a new Mac, restoring your whole setup is two commands:

chezmoi init https://github.com/your-username/dotfiles.git
chezmoi apply

Quiz

Q1. Why can't you just run a normal git init inside $HOME?

A. A normal init makes the current folder both repo and working tree — in $HOME that means everything becomes trackable at once.

Q2. What does --work-tree=$HOME tell git, in the bare-repo alias?

A. Work-tree is just "where the actual files are" — separate from --git-dir, which is where the repo's own data lives.

Q3. In chezmoi, what does chezmoi edit ~/.aerospace.toml actually edit?

A. chezmoi always edits its own source copy — apply is the separate step that writes those changes to the real file.

Q4. What does chezmoi's templating solve that a bare repo doesn't?

A. Templating is specifically for machine-to-machine differences — a bare repo has no equivalent built in.

Q5. Which is the better fit for one Mac, with no second Mac planned?

A. The bare repo's whole appeal is zero extra tooling — chezmoi's templating pays off once there's a second machine to diverge from.

Recap
  • Bare git repo: git init --bare $HOME/.dotfiles + a --git-dir/--work-tree alias — no extra tool, edits real files directly.
  • chezmoi: a source copy plus templating — one extra tool, but handles per-machine differences cleanly.
  • Either way: add, commit, and push your Brewfile (Lesson 9) and AeroSpace config (Lesson 1) so a wiped Mac is a restore, not a rebuild.

Try solo: once your first file is tracked, add your Karabiner Hyper key rule from Lesson 10 as the second one — that's two real, working configs now backed up and diffable.
