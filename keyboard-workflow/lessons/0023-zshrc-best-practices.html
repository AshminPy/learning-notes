.zshrc best practices: load order, speed, and plugins

Every lesson so far has told you to add a line to a dotfile — an alias here, an eval there, an environment variable somewhere else. By now your shell config is a pile of copy-pasted lines with no structure, and every new terminal tab takes a beat longer to open than it used to. This lesson gives you the mental model for where each line actually belongs, how to measure whether your shell is slow, and what to do about it if it is.

Mental model: zsh doesn't read one config file — it reads a sequence of them, and which ones run depends on two independent questions: is this shell a login shell, and is it interactive? Get the sequence wrong and you'll either duplicate work on every new tab, or set something up in a place a script running over SSH never sees.

The four files, and when each one runs

zsh's own manual defines the load order precisely. Four files matter for daily use (a fifth, .zlogout, runs on exit and is rarely used):

FileRuns forPut here
~/.zshenvEvery zsh process — interactive or not, login or notOnly PATH and environment variables a script or cron job might need
~/.zprofileLogin shells only (roughly: a fresh Terminal window, or a new SSH session)One-time login setup — rare, most people leave this empty
~/.zshrcInteractive shells only (any shell showing you a prompt)Aliases, prompt, plugins, functions, completions, keybindings — almost everything
~/.zloginLogin shells, after .zshrcRare — commands you want to run once per login, after the interactive setup is ready

The zsh manual is explicit about the first one: .zshenv "is sourced on all invocations of the shell," and because of that it warns "it is important that it be kept as small as possible." Every script, every cron job, every non-interactive SSH command that touches zsh pays the cost of whatever you put in .zshenv — so it should hold nothing but PATH exports and environment variables that genuinely need to exist everywhere.

Common mistake: putting aliases or a prompt theme in .zshenv "to be safe." Aliases are meaningless to a non-interactive script, and a slow prompt-theme init will now run on every single zsh invocation on your machine, not just the ones where you'd see the prompt. Aliases, functions, plugins, and prompt setup belong in .zshrc — the file that only loads for shells with a human watching.

Almost everything from Lessons 9-22 — aliases for eza/bat, the starship or direnv hook, completion setup, your kubectx shortcuts — belongs in .zshrc. Reserve .zshenv for the handful of variables that must survive into non-interactive contexts, most commonly a PATH addition for a tool you install outside Homebrew.

Measure before you optimize

Don't guess whether your shell is slow — measure it. Two ways, from simplest to most detailed:

# Rough total: how long does an interactive shell take to start and exit?
for i in {1..5}; do time zsh -i -c exit; done

Run it several times — the first run is skewed by disk cache being cold. Anything consistently under roughly 100-200ms is fine; if you're seeing numbers in the seconds, something in .zshrc is the cause.

To find out which line is slow, zsh ships a built-in profiler as a loadable module. Add this as the very first line of .zshrc:

zmodload zsh/zprof

And this as the very last line:

zprof

Open a new interactive shell and zprof prints a table of every function call made during startup, sorted by how much time it consumed. Plugin managers and tool initializers (starship init, direnv hook, a Kubernetes completion script) all register as functions here, so the table points straight at the worst offender instead of leaving you to guess. Remove or comment out both zprof lines once you're done — they're a diagnostic tool, not something to leave running permanently.

The most common real offender: eager tool initializers

If you've followed a tutorial for a language version manager — nvm, pyenv, rbenv, and similar tools all work the same way — it likely told you to add a line like this to .zshrc:

# the naive way — runs on every single new shell, whether you need it or not
eval "$(pyenv init -)"

That line does real work every time a shell starts: scanning directories, writing shims, checking versions — even in a tab where you'll never run python. Across dozens of tabs a day, that adds up to the slow-shell feeling. The fix is lazy loading: only pay the cost the first time you actually use the tool, by wrapping it in a shell function that replaces itself:

# lazy-load pyenv: a stub function stands in until you actually call pyenv
pyenv() {
  unset -f pyenv
  eval "$(command pyenv init -)"
  pyenv "$@"
}

The first call to pyenv in a shell removes this stub, runs the real initializer once, then re-invokes itself with your original arguments. Every later call in that same shell hits the real pyenv directly. A shell that never touches Python pays nothing at all. This pattern — a thin stub function that removes itself on first use — is worth learning once and reusing for every slow tool initializer, not just pyenv.

Production note: on a real team, the tools that get lazy-loaded change over time as your toolchain changes. Re-run the zprof measurement after adding any new eval-a-script line to .zshrc — don't assume last month's fast startup is still true after this month's additions.

Plugin managers: an honest comparison

A plugin manager handles installing, updating, and loading community zsh plugins (syntax highlighting, autosuggestions, extra completions). There is no single "best" one — the right choice depends on what you're optimizing for.

OptionOptimizes forTradeoff
Oh My ZshSimplicity and ecosystem — hundreds of bundled plugins and themes, huge community, easy to get startedLoads plugins eagerly by default; a large plugin list measurably slows every shell start unless you actively trim it
zinitRaw startup speed — "turbo mode" defers plugin loading until after the prompt appears, so the prompt shows up fast even with many plugins installedMore syntax to learn, smaller ecosystem of pre-packaged bundles than Oh My Zsh
antidoteStartup speed via a different mechanism — pre-compiles your plugin list into one static file, so nothing is parsed or fetched at shell-start timeRequires an explicit regeneration step (antidote bundle) whenever your plugin list changes

If you're new to zsh and want the biggest plugin catalog with the least setup thinking, Oh My Zsh is a reasonable default — just watch your zprof numbers as you add plugins. If startup speed matters more than catalog size — which it usually does once you're opening a dozen terminal tabs a day — zinit or antidote are the better fit. Don't switch plugin managers as a reflex the first time your shell feels slow; measure with zprof first, since a single slow eval line is a far more common cause than the plugin manager itself.

A fast default for the prompt

Whichever plugin manager you use, the prompt itself is a separate decision. Starship is a good default: a single cross-shell prompt binary, written in a compiled language rather than shell script, that reads your current directory's context (git branch, language runtime versions, cloud CLI profile) and renders it without the eval-heavy overhead older shell-script prompt frameworks carry. Setup is one line at the end of .zshrc, after any plugin manager:

eval "$(starship init zsh)"

Because it's a single native binary rather than a tree of sourced shell scripts, it's one of the few eval "$(...)" lines that's genuinely cheap to leave eager rather than lazy-loading — but confirm that with your own zprof output rather than taking this lesson's word for it.

Try it

Measure your own shell right now. Run for i in {1..5}; do time zsh -i -c exit; done and note the real time on each run. Then add zmodload zsh/zprof as the first line of ~/.zshrc and zprof as the last line, open a new terminal tab, and read the table it prints. Find the single slowest line in your own config — is it a plugin manager, a tool initializer, or something else? Remove the two zprof lines once you've seen the report.

Try it — before looking below

Q1. A script runs over cron with no interactive shell involved. Which zsh startup file(s) does it read?

A. .zshenv runs for every zsh invocation, interactive or not. .zshrc only runs for interactive shells, which a cron job is not.

Q2. Where should a Kubernetes-related alias like alias k=kubectl be defined?

A. An alias is meaningless to a non-interactive script, and it belongs in the file scoped to interactive shells.

Q3. What does the zsh manual say is the reason to keep .zshenv minimal?

A. Because it runs for every invocation, anything slow in it is a tax paid by every script and every shell, not just interactive ones.

Q4. What problem does lazy-loading a tool initializer (like pyenv init) actually solve?

A. A stub function defers the real eval "$(... init -)" until the tool's first actual use in that shell, so idle shells never pay for it.

Q5. What is the correct way to decide between Oh My Zsh, zinit, and antidote?

A. There's a genuine tradeoff — catalog size and ease of use versus raw startup speed — not a single universally correct pick.

Recap
  • .zshenv loads for every zsh process, always — keep it to just PATH/env vars. .zshrc loads only for interactive shells — that's where aliases, prompt, and plugins belong.
  • Measure before optimizing: time zsh -i -c exit for a rough total, zmodload zsh/zprof + trailing zprof for a per-line breakdown.
  • The most common slow-shell cause is an eagerly-evaluated tool initializer (nvm/pyenv/rbenv) — wrap it in a self-removing stub function so it only runs on first real use.
  • Plugin managers trade off differently: Oh My Zsh for ecosystem/simplicity, zinit/antidote for raw speed — no universal "best," measure your own startup.
  • Starship is a solid fast-by-default prompt: one binary, one eval "$(starship init zsh)" line.

Try solo: profile a coworker's or a public dotfiles repo's .zshrc (mentally or by reading it) and guess which line zprof would flag before you'd need to run it yourself.

Your own zprof output looks different from the examples here? Paste the table back to your teacher — the real bottleneck is almost always specific to what you've personally installed.
