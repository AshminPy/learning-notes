AeroSpace, from first principles

You already have a working AeroSpace config, copied from a video. This lesson isn't about new commands — it's about understanding why the commands you already have work the way they do, so you can extend them yourself instead of hunting for another tutorial. Everything below quotes your actual ~/.aerospace.toml.

The one idea that explains everything else

Most window managers (including stock macOS) treat windows as independent floating objects you drag around. AeroSpace doesn't. It's a tiling window manager: every window lives inside a tree, and the tree — not you — decides each window's exact position and size. Your job is to tell the tree how to arrange itself; you never drag a window by its edges.

Tree, top to bottom: Workspace (the root — like a virtual desktop) → Container (a box that holds either windows or more nested containers, and has an orientation) → Window (a leaf — it holds nothing else). A workspace can have many containers nested inside each other; most people's setups stay shallow (one or two levels).

Your config's two big decisions

Two lines in your config decide almost everything about how new windows appear:

default-root-container-layout = 'accordion'
default-root-container-orientation = 'horizontal'

Layout answers "when two windows share a container, how are they arranged?" There are two options:

  • tiles — the container splits into a grid. Two windows side by side (or stacked), each getting a visible slice. This is what most tiling WMs default to.
  • accordion — what you have. Only one window in the container is fully visible at a time; the rest collapse to a thin strip along the edge (like a stack of file folders, or browser tabs turned sideways). Your accordion-padding = 30 line controls how wide that collapsed strip is.

Orientation answers "which direction does a container split in?" — horizontal means new splits happen left/right. This interacts with layout: in accordion mode, orientation decides whether the collapsed-window strip sits on the side (horizontal) or top/bottom (vertical).

Try it — on your real desktop, right now

Open two windows in the same workspace. Press alt-slash (your config's layout tiles horizontal vertical toggle) and watch them switch from accordion-stacked to side-by-side tiles. Press it again to go back. This is the single fastest way to build intuition for what "layout" actually controls.

Focus and move: navigating the tree, not "next window"

Your config binds:

ctrl-alt-h = 'focus left'
ctrl-alt-j = 'focus down'
ctrl-alt-k = 'focus up'
ctrl-alt-l = 'focus right'

This isn't "cycle to the next window" (like Cmd-\` on stock macOS) — it's spatial. AeroSpace looks at the tree, figures out which window is physically to the left/right/up/down of the one you're on, and jumps there. ctrl-alt-shift-h/j/k/l does the same thing but moves the window itself in that direction instead of just moving focus — which can restructure the tree (e.g. pulling a window out of an accordion stack into a tiled split next to it).

Q1. In your config, what does ctrl-alt-shift-l do, based on the pattern above?

A. The shift modifier is what turns a focus-direction binding into a move-direction binding — same direction key, different verb. Your config uses this exact pattern for all four directions (see the "Move windows" section of your file).

Modes: a keybinding namespace switch

Your config has [mode.main.binding] and [mode.service.binding]. Think of a mode like Vim's normal/insert modes: it's a completely separate set of keybindings that only apply while that mode is active. You're in main mode almost all the time. Your service mode binding (usually triggered by a key you'd bind to mode service) gives you access to esc (reload config + return to main), r (flatten the tree + return to main), f (toggle the focused window floating/tiling), and backspace (close every window except the current one).

"Floating" is the escape hatch: a floating window ignores the tree entirely and behaves like a normal draggable macOS window. Some apps (system dialogs, small utility windows) work better floating — that's what your service-mode f binding is for.

Workspace-to-monitor: pinning, not just switching

Your config forces every workspace 1–10 onto a specific physical display:

[workspace-to-monitor-force-assignment]
"1" = "Built-in Retina Display"
"2" = "LG ULTRAGEAR+"
...

This means workspace 1 always lives on your laptop screen and workspace 2+ always lives on your external monitor — regardless of which one you're actively looking at. Combined with your on-window-detected rules (Chrome → workspace 1, Warp → workspace 4, etc.), the effect is: every app has a fixed home, every time, without you deciding where it goes.

Try it

Quit and relaunch one of the apps in your on-window-detected list (e.g. Warp). Watch which workspace it lands in — then check that against the rule in your config that names its app-id. This is how you'll debug or extend these rules later: find the app's bundle ID (Raycast can show you this — covered in Lesson 2) and add a matching [[on-window-detected]] block.

Quiz

Q2. What's the key difference between "tiles" and "accordion" layout?

A. Tiles gives every window in the container a visible slice simultaneously; accordion shows only the focused window fully, collapsing the rest to a thin strip. B/C/D describe things that aren't true of either layout.

Q3. Your config sets default-root-container-orientation = 'horizontal'. What does this control?

A. Orientation is purely about split direction (left/right vs top/bottom) — it has nothing to do with floating, monitor assignment, or animation.

Q4. What is "service mode" in your config, conceptually?

A. Modes are just alternate sets of keybindings, active only while you're "in" that mode — the same idea as Vim's normal vs insert mode, applied to window management instead of text editing.

Q5. If you move Warp to workspace 7 manually, then quit and relaunch it, where will it open per your config?

A. The on-window-detected rule for dev.warp.Warp forces it to workspace 4 every time a new window is detected — it doesn't remember where you last moved an existing instance to.

Q6. What does ctrl-alt-h (no shift) actually do?

A. No-shift bindings in your config are all "focus" (move your attention), while the shift versions are "move" (relocate the window). This pairing is consistent across all four directions.

Recap
  • Windows live in a tree: workspace → container → window. You arrange the tree; you don't drag windows.
  • Layout (tiles vs accordion) controls how windows in a container share space. Orientation controls split direction.
  • Focus moves your attention spatially; move (shift+) relocates the window, restructuring the tree.
  • Modes are alternate keybinding namespaces — like Vim modes, for windows.
  • workspace-to-monitor-force-assignment pins workspaces to physical displays; on-window-detected auto-routes apps to workspaces.
