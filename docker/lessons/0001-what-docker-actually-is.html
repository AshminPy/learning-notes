What Docker Actually Is

Without Docker, shipping an app means hoping the target machine has the exact right language runtime, libraries, and OS packages your app needs — the classic "works on my machine" problem. Docker solves this by packaging an app with everything it needs into one portable unit, and running it in an isolated slice of the host's Linux kernel. But "Docker" isn't one program — it's a chain of separate pieces handing work down to each other, and almost every confusing Docker error ("cannot connect to the Docker daemon", "permission denied") is really a question of which link in that chain broke.

This course assumes you already know how that isolation is actually built at the kernel level — namespaces (what a process can see) and cgroups (what it can use), covered fully in Linux Lesson 21 — Containers at the Linux Level. This lesson doesn't re-teach that; it teaches the Docker-specific tooling built on top of it.

Mental model: Docker Engine is a chain of remote controls, not one single tool. The docker CLI is the remote control in your hand. dockerd (the daemon) is the TV's own control board, listening for button presses. containerd is the tuner module the control board hands work to for each individual channel (container). runc is the physical switch that actually flips the picture on, using the kernel namespaces/cgroups mechanism from Linux Lesson 21. That predicts a real, unseen failure: press a button on the remote (run a docker command) while the TV is unplugged (the daemon isn't running), and you get silence — not because your remote is broken, but because nothing is listening on the other end.

How it works

The Docker client and daemon talk over a REST API, normally through a Unix socket on the same machine (though the client can also point at a remote daemon over the network). The daemon itself doesn't run containers directly — it delegates that to containerd, which by default uses runc as its low-level, OCI-compliant runtime to actually create the namespaced, cgroup-bounded process.

Why it's built this way: early Docker (pre-1.11) was one monolithic daemon. Splitting out containerd as its own component meant container processes could keep running even if the Docker daemon itself restarted or upgraded — and meant other tools could reuse the exact same runtime without needing Docker at all. That's exactly why Kubernetes nodes can run containerd directly as their CRI runtime (Kubernetes Lesson 18 — Extension interfaces: CNI, CSI, CRI) with no Docker daemon present.

Practical example: see the two halves for yourself

docker version

Run that now. The output splits into two clearly labeled sections: Client and Server (the "Server" section is the daemon, dockerd). Each has its own version number, API version, and OS/architecture line — because they really are two separate programs that happen to usually run on the same machine, exactly as the mental model above describes.

Q1. If the Client section prints fine but the Server section is missing or errors out, what does that tell you about your Docker installation?

The docker CLI binary itself is installed and working — but dockerd (the daemon) isn't running or isn't reachable. The remote control works; the TV isn't on.

Now, before revealing: run docker info as well. Which section of that output tells you which low-level runtime your daemon is actually using?

Reveal the answer

The Server section of docker info includes a Runtimes line (default runc) and a containerd version line — direct, on-screen proof of the containerd → runc handoff described above, not just a diagram.

Common mistake: treating "Docker" as one indivisible program. It's the CLI, the daemon, containerd, and runc — four separable pieces. Knowing which one a symptom belongs to is the actual debugging skill, not a trivia fact.

A controlled failure

# Quit Docker Desktop (or: sudo systemctl stop docker on Linux)
docker ps

Predict first: does the docker command itself disappear, or does it still run and just fail? Observe: the command still exists and runs — it prints Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?. That's the client half working perfectly and reporting, accurately, that nothing answered on the other end of the socket. Restart Docker Desktop (or sudo systemctl start docker) and rerun docker ps to confirm it's back.

Production best practices

Production note: on real Docker hosts and CI runners, most container problems that "look like a Docker bug" are actually one specific layer — check docker version's Server section first to confirm the daemon is even reachable before debugging further up the stack. And remember many production Kubernetes nodes run containerd directly with no Docker daemon at all (Kubernetes Lesson 18) — "no Docker installed" doesn't mean "no containers running."

Interview notes

Interview Q: "What's the actual difference between Docker and containerd?" A: containerd is one component Docker Engine uses internally to manage container lifecycle (create/start/stop); it's also a standalone project usable without Docker at all — for example as the CRI runtime a Kubernetes node talks to directly.

Recap
  • Docker Engine is a chain: the docker CLI talks to dockerd over a REST API; dockerd delegates to containerd; containerd uses runc to actually create the namespaced, cgroup-bounded process.
  • docker version shows this split directly — a Client section (the CLI) and a Server section (the daemon).
  • The daemon being unreachable is a different failure than the CLI being broken — the error message tells you which one it is.
