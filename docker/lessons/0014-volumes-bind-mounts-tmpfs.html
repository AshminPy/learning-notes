Volumes, Bind Mounts, and tmpfs

A container's writable layer disappears the moment the container is removed — that's deliberate (Lesson 3), but it means a database container with nowhere else to keep its data loses everything on docker rm. Docker gives you three different ways to give a container storage outside its own disposable layer, and picking the wrong one either loses data you needed or couples your app to a host path it shouldn't depend on.

Mental model: a volume is a storage unit you rent from Docker itself — Docker decides exactly where it physically lives, hands you a name to reference it, and the unit stays put even after you scrap the moving truck (the container). A bind mount is propping your container's door directly into one specific room of the host's own house — full, direct, two-way access to that exact host path, no abstraction. tmpfs is a whiteboard in that room — fast, memory-only, wiped clean the instant the room (container) closes. That predicts the actual behavior: delete a container using a named volume, and the data survives (the storage unit is still rented). Delete a container using a bind mount, and the host directory is obviously untouched — it was never the container's to own. Delete or even just restart a container using tmpfs, and the data is gone — it only ever existed in memory tied to that one running container.

How the three types work

Volumes are created explicitly (docker volume create) or implicitly the first time a container references a name that doesn't exist yet. Docker owns where they physically live and can hand that storage off to a volume driver for NFS, cloud block storage, or other backends — your container config never needs to know or care which. Bind mounts skip that abstraction entirely: whatever real file or directory you point at on the host is what the container sees, live, in both directions — edit it from the host, the container sees the change immediately, and vice versa. tmpfs mounts a portion of the host's RAM (backed by swap if needed) directly into the container's filesystem namespace — nothing ever touches disk, and the mount ceases to exist the moment the container stops.

Why it's built this way: containers are meant to be disposable and replaceable (the same idea behind Lesson 12's lifecycle model) — so persistent data can't safely live inside the container's own writable layer, it has to live somewhere the container's lifecycle doesn't control. Volumes exist so that "somewhere" doesn't require your app or your deploy scripts to know or trust an exact host filesystem path; bind mounts exist for the opposite, deliberate case — when you genuinely want that host coupling, like live-editing source code during local development.

Typo behaviorInvalid type/option errors outA missing ./ or leading slash silently creates a new named volume instead of a bind mount (see Common mistakes)

Docker's own documentation recommends --mount for anything beyond the simplest case, precisely because it's explicit and behaves the same way across all three mount types. Both syntaxes exist and produce identical results for the basic cases — this course uses --mount as the primary example, per the same "teach the production convention first" approach as Lesson 10's base-image pinning.

Practical example — named volume surviving container removal

docker volume create db-data
docker run -d --name pg --mount type=volume,src=db-data,dst=/var/lib/postgresql/data -e POSTGRES_PASSWORD=demo postgres:16
sleep 3
docker exec pg psql -U postgres -c "CREATE TABLE demo(id int);"
docker rm -f pg
docker run -d --name pg2 --mount type=volume,src=db-data,dst=/var/lib/postgresql/data -e POSTGRES_PASSWORD=demo postgres:16
sleep 3
docker exec pg2 psql -U postgres -c "\dt"

Active learning action — predict, then run: before running the last command, predict whether demo shows up in pg2's table list, given that pg (the container that created it) was removed entirely. Run the sequence and check. Then try the same experiment with a bind mount instead, to see the other side of the model:

mkdir -p ./html && echo "hello" > ./html/index.html
docker run -d --name web --mount type=bind,src="$(pwd)"/html,dst=/usr/share/nginx/html,readonly nginx:alpine
docker exec web cat /usr/share/nginx/html/index.html
echo "changed on host" > ./html/index.html
docker exec web cat /usr/share/nginx/html/index.html

Predict before the last line: does the container see the host-side edit without any restart? (It does — that's the "propped door," live in both directions, and exactly why the volume model deliberately avoids this coupling for anything you don't want tied to a host path.)

Try it

Q1. A container using a named volume for /data is removed with docker rm -f. Is the data in /data gone?

No. The volume exists independently of any container's lifecycle — removing the container only removes its writable layer and the reference to the volume. The data stays until something explicitly runs docker volume rm on it (and Docker will refuse that while any container still references it).

Now, before revealing: you run docker run -v test-typo:/data ..., intending to bind-mount a folder named test-typo in your current directory, but you forgot the $(pwd)/ prefix. What actually happens?

Reveal the answer

Docker doesn't error out. Because test-typo has no path separator, the CLI treats it as a named volume, not a host path — it silently creates (or reuses) a volume literally called test-typo, mounts that instead, and the container starts normally with empty, unrelated storage. Nothing in the container's output tells you this happened; you'd only notice by running docker volume ls and seeing an unexpected volume.

Common mistake: using -v with a bare name you meant as a relative host path (e.g. -v mydata:/data instead of -v $(pwd)/mydata:/data). Docker can't tell the difference between "a volume name" and "a relative path you forgot to prefix" — a bare name with no slash is always parsed as a volume name. --mount type=bind,src=... doesn't have this ambiguity, which is one more reason it's the recommended syntax.

A controlled failure

docker run -d --name tmptest --mount type=tmpfs,dst=/scratch alpine sh -c "echo secret > /scratch/note.txt; sleep 300"
docker exec tmptest cat /scratch/note.txt

Predict first: the file is written and readable right now — will it still be there after the container restarts? Observe: restart it and check:

docker restart tmptest
docker exec tmptest cat /scratch/note.txt

cat: can't open '/scratch/note.txt': No such file or directory — the tmpfs mount is recreated empty on every start, because it's backed by memory tied to that specific running container instance, not disk. Why this matters: tmpfs is the right choice specifically because it never persists (secrets, scratch space you don't want touching disk) — using it for anything you expect to survive a restart is the mistake, not the mount type itself.

Production best practices

Production note: use named volumes for anything stateful you actually need to keep — databases, message queue data — with a volume driver matched to your infrastructure (local disk is fine for a single host; an NFS or cloud-block driver for anything that needs to survive the host itself dying). Reserve bind mounts for deliberate host coupling: local dev source-code hot-reload, or mounting a config file/cert you manage outside the image. Docker doesn't back up volumes for you — treat "how do I back this up" as a real question before you put production data in one, not an afterthought.

Interview notes

Interview Q: "Why would you use a named volume instead of a bind mount for a database container?" A: A named volume decouples the data from any specific host path — Docker manages where it physically lives, it can be backed by a proper storage driver, and it survives container recreation cleanly. A bind mount ties you to one exact host directory structure, which is fragile across different hosts/environments and gives the container direct read/write access to a real filesystem path you may not want it touching.

Recap
  • Volumes are Docker-managed and outlive any single container — the right default for anything stateful you need to keep.
  • Bind mounts give direct, live, two-way access to one exact host path — correct only when you deliberately want that coupling.
  • tmpfs is memory-only and disappears on every stop/restart — correct only for data you explicitly don't want to persist.
  • --mount is the explicit, recommended syntax; -v's shorthand can silently turn a forgotten path prefix into an unrelated named volume.
