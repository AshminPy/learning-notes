Docker Networking

A container that can't talk to another container is nearly useless — a web app that can't reach its database, a worker that can't reach a queue. Docker solves this with virtual networks, but the driver you pick changes something fundamental: whether containers can even find each other by name, or only by an IP address that changes every time you recreate them.

Mental model: a Docker network is a hotel floor. The default bridge network is a floor with no directory service — you can dial a room's raw extension (IP address) but there's no concierge to look up "the room named db" for you. A user-defined bridge network is a floor with a concierge (Docker's embedded DNS server) who resolves any guest's name to their current room the instant they check in. That predicts the exact failure you'll see later: two containers on the default bridge can ping each other's IP just fine, but ping db fails — there's no concierge on that floor to ask.

The six built-in drivers

Every Docker network uses one driver. On Linux, the built-in drivers are:

  • bridge — the default. An isolated private network on the host, containers reach each other and the outside world through NAT. Most single-host setups use this.
  • host — no isolation at all: the container shares the host's network namespace directly. No port mapping needed (and none possible) — the container just uses the host's ports.
  • none — no networking except loopback. Total isolation.
  • overlay — connects multiple Docker daemons together (Swarm), so containers on different physical hosts can reach each other as if on one network.
  • macvlan — gives a container its own MAC address, so it appears as a physical device on the host's LAN.
  • ipvlan — similar goal to macvlan (container reachable directly on the physical network), different mechanism — containers share the host's MAC address instead of getting their own.

Default bridge vs. user-defined bridge

Every fresh Docker install already has a default bridge network, and any container started without --network lands on it silently. It works, but with one real limitation worth internalizing:

Default bridgeUser-defined bridge
Container-to-container by nameNot supported — no embedded DNS for itSupported via Docker's embedded DNS (127.0.0.11)
Container-to-container by IPWorksWorks
How you get on itAutomatic if you skip --networkExplicit: docker network create first
Isolation from other networksShared floor for everythingIts own floor, per app/stack

Why it's built this way: the default bridge predates Docker's embedded DNS server and was kept for backward compatibility rather than removed. Once multi-container apps became the normal case, Docker added user-defined networks with real name-based service discovery — so the fix isn't "the default bridge is broken," it's "always create your own network for anything with more than one container," which is also exactly what Docker Compose does for you automatically (Lesson 15).

Practical example — the production convention: your own network first

Create a user-defined bridge network before running anything, the way a real multi-container app is set up:

docker network create --driver bridge my-app-net
docker network ls
docker run -d --name db --network my-app-net postgres:16
docker run -it --rm --network my-app-net alpine ping -c 2 db
docker network inspect my-app-net

Active learning action — predict, then run: before you run the ping command above, predict whether it succeeds. Then run the whole sequence for real (postgres:16 needs no special setup for this — it'll start even without a password env var set, just to prove reachability; don't use it this way for anything real). Now run the same test against the default bridge instead, and compare:

docker run -d --name db2 postgres:16
docker run -it --rm alpine ping -c 2 db2

Predict again before running: does ping db2 succeed this time? Check docker network inspect bridge afterward and look for a DNS-related section — you'll find none, unlike my-app-net's inspect output.

Try it

Q1. Two containers are both running with no --network flag specified. Can they reach each other using ping their-container-name?

No. With no --network flag they both land on the default bridge network, which doesn't run Docker's embedded DNS for user containers — only IP-to-IP reachability works there. They'd need to be started on the same user-defined network (docker network create + --network my-app-net on both) for name resolution to work.

Now, before revealing: you run docker run --network host -p 8080:80 nginx. Does the -p 8080:80 flag do anything?

Reveal the answer

No — host networking mode shares the host's network namespace directly, so the container is already using the host's real ports with no isolation to map through. Docker ignores -p in this mode (nginx binds directly to the host's port 80, not 8080). This is a common source of "why didn't my port mapping work" confusion.

Common mistake: assuming the default bridge network supports container-name DNS because "it's just Docker networking." It's the one driver mode that doesn't — always create a user-defined network for anything with more than one container that needs to talk to another by name.

A controlled failure

docker run -d --name failtest-db postgres:16
docker run -it --rm --name failtest-app alpine ping -c 2 failtest-db

Predict first: both containers exist and are running — does the ping resolve? Observe: ping: bad address 'failtest-db' — DNS resolution fails immediately, even though both containers are healthy and running. Why: both landed on the default bridge (no --network was given), which has no embedded DNS entry for either container name. Fix: put them on a user-defined network instead and re-test:

docker network create failtest-net
docker run -d --name failtest-db2 --network failtest-net postgres:16
docker run -it --rm --network failtest-net alpine ping -c 2 failtest-db2

Production best practices

Production note: give every application/stack its own user-defined bridge network, never share the default bridge across unrelated apps — it keeps DNS resolution scoped correctly and stops unrelated containers from being reachable by name at all. Reserve host mode for the rare case of a network-appliance-style container that genuinely needs the host's raw network stack (e.g. some monitoring agents); using it for ordinary app containers throws away Docker's isolation for no real benefit. macvlan/ipvlan are specialist tools — only reach for them when a container genuinely needs to appear as its own device on the physical LAN (e.g. legacy network services expecting a real IP), not as a default choice.

Interview notes

Interview Q: "What's the practical difference between Docker's default bridge network and a user-defined bridge network?" A: Both are the same driver (bridge) and both give containers NAT'd outbound access, but only the user-defined one runs Docker's embedded DNS server, so containers can resolve each other by name. On the default bridge, containers can only reach each other by IP — which is why real multi-container setups always create their own network first (Compose does this automatically).

Recap
  • Six built-in drivers: bridge (default), host, none, overlay (Swarm), macvlan, ipvlan.
  • Only user-defined bridge networks run Docker's embedded DNS (127.0.0.11) — the default bridge only supports IP-to-IP reachability, not name resolution.
  • Real setups always create their own network first (docker network create) instead of relying on the default bridge — this is what Compose does automatically under the hood.
  • host mode shares the host's network namespace entirely — no isolation, and -p port mapping is ignored because there's nothing to map through.
