Image Registries

Every earlier lesson in this course ends with an image sitting on one machine. That's useless the moment a second machine — a teammate's laptop, a CI runner, a production node — needs to run the exact same thing. A registry is the piece that closes that gap: a server that stores images by name and hands them back to whoever asks, so "the image I built" and "the image that runs in production" can provably be the same bytes.

A registry is just a name-addressed store for images. You push an image to it under a name; anyone with the right access pulls that name back and gets an identical copy, layer for layer. Docker Hub is the default registry every plain docker pull nginx talks to, but it's one option among several — private registries (AWS ECR, Google Artifact Registry, GitHub Container Registry, or a self-hosted one) work the same way, just with different access rules and where they physically live.

Mental model: a registry is a shipping warehouse with labeled shelves, not a delivery truck. docker build makes the product; docker tag writes the shelf label (a name); docker push is the truck dropping it on that shelf; docker pull is anyone else's truck picking up whatever currently sits under that label. That predicts something concrete: relabeling a box (docker tag) never moves it anywhere — nothing leaves your machine until a push actually happens.

Image names: the four parts

Per Docker's own reference, every image name follows one structure: [HOST[:PORT]/]NAMESPACE/REPOSITORY[:TAG]. Each part answers one question:

  • HOST[:PORT] — which registry. Omit it and Docker defaults to docker.io (Docker Hub). A private registry needs its host written explicitly, e.g. localhost:5000/... or 123456789.dkr.ecr.us-east-1.amazonaws.com/....
  • NAMESPACE — your username or org on that registry. Docker Hub's official images (like plain nginx) live under the implicit namespace library.
  • REPOSITORY — the image's name within that namespace.
  • TAG — defaults to latest if you don't specify one (Lesson 19 covers why that default is a common source of production surprises).

nginx is really shorthand for docker.io/library/nginx:latest — nothing is hidden, it's just defaults filling in the parts you left out.

Public vs. private, and why push can fail

Docker Hub gives every account unlimited public repositories plus private repositories for restricted access. Pulling a public repo needs no authentication at all; pulling or pushing a private one requires docker login first. Push additionally enforces ownership: you can generally only push into a namespace you actually control (your username or an org you belong to) — this is why a beginner's first push often fails even after a successful login, covered as a controlled failure below.

Why it's built this way: because images are layered and content-addressed (Lesson 3), a registry doesn't need to understand what's inside an image — it just needs to store layers once and serve them by digest. That's why a push of an image sharing layers with something already on the registry reports Layer already exists instead of re-uploading — the registry is matching content, not blindly copying files.

Try it

Q1. You run docker tag hello-world myregistry.example.com/team/hello-world:v1 and nothing else. Has anything left your machine?

No. docker tag only creates a new local name pointing at an image you already have — purely local bookkeeping. Nothing reaches any registry until docker push actually runs.

Now do the full round trip yourself: run a local registry, tag a real image for it, push, then pull it back to prove the bytes really moved. Try it before revealing.

Reveal the sequence

# 1. Start a local registry (Docker's own official image, no account needed)
docker run -d -p 5000:5000 --restart always --name registry registry:3

# 2. Get a tiny public image, then tag it for your local registry
docker pull hello-world
docker tag hello-world localhost:5000/hello-world:v1

# 3. Push it — this is the step that actually uploads bytes
docker push localhost:5000/hello-world:v1

# 4. Prove the round trip: remove your local copy, pull it back from the registry
docker rmi hello-world localhost:5000/hello-world:v1
docker pull localhost:5000/hello-world:v1

If step 4 succeeds after removing every local copy first, you've proven the image genuinely lived on the registry, not just in your local cache.

Common mistake: assuming a successful docker login means any push will succeed. Login only proves who you are — it doesn't grant write access to every namespace. Pushing to a namespace you don't own (including the bare library/ namespace) is denied regardless of being logged in.

A controlled failure

# Build/tag an image WITHOUT a registry host prefix
docker pull hello-world
docker tag hello-world myapp:v1
docker push myapp:v1

Predict first: where does this push actually try to go, and what happens? Observe: with no host prefix, Docker defaults to docker.io — so this attempts to push to Docker Hub under a namespace matching your Docker Hub username (or fails outright if you're not logged in). It does not go to your local registry from the exercise above, even though that's what a beginner typically intends. The fix is the same lesson as the mental model: the shelf label has to name the actual warehouse. Restore intent with an explicit host:

docker tag hello-world localhost:5000/myapp:v1
docker push localhost:5000/myapp:v1

Production best practices

Production note: Docker Hub enforces pull rate limits — 100 pulls per 6 hours per IP for anonymous access, 200 per 6 hours for an authenticated free account, unlimited on paid tiers. An unauthenticated CI runner hammering Docker Hub is a common, confusing production failure ("pulls started randomly failing") that's actually just this limit. Authenticate CI pulls, or use a private registry (ECR/Artifact Registry/GHCR/self-hosted) close to where you deploy — most cloud registries also support short-lived, role-based credentials instead of a long-lived registry password baked into CI config.

Exam and interview notes

No single certification anchors this course (see MISSION.md) — this is real day-2 CI/CD skill, not exam trivia.

Interview Q: "Your CI pipeline's image pulls started failing intermittently with no code changes." A: Check whether pulls are unauthenticated against Docker Hub and hitting its per-IP rate limit — the fix is authenticating the pull or moving to a private/self-hosted registry, not debugging the pipeline logic.

Recap
  • A registry stores images by name; docker tag is purely local, docker push/docker pull are the only steps that actually move bytes.
  • An image name is [HOST[:PORT]/]NAMESPACE/REPOSITORY[:TAG] — omit HOST and it silently means Docker Hub, which is the single most common beginner push mistake.
  • Login proves identity, not write access — you can only push into a namespace you control.
  • Docker Hub rate-limits unauthenticated and free-tier pulls; production CI should authenticate or use a private registry.
