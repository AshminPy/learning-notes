Vault's Core Architecture

Lesson 2 had you write and read a secret without asking where it actually lives or how it stays protected. Every later lesson in this course — seal/unseal, storage backends, auth methods, policies — is a detail sitting on top of three architectural pieces this lesson introduces. Skip this, and later lessons feel like unrelated trivia instead of one coherent system.

Mental model: Vault is a safe-deposit box room, not a filing cabinet. The room itself (the barrier) is what actually encrypts and decrypts — nothing gets stored or retrieved except through it. The boxes (the storage backend) sit in a vendor's warehouse outside the room and are treated as untrusted — if someone steals a box, they get locked steel, not readable contents, because everything was already encrypted before it left the room. That predicts something concrete: compromising Vault's storage backend alone (a database breach, a stolen disk) doesn't hand over your secrets — the encryption happened before data ever reached storage.

The barrier: Vault's encryption layer

Per HashiCorp's own architecture docs: "Vault's encryption layer, referred to as the barrier, is responsible for encrypting and decrypting Vault data." Every single read or write to storage passes through the barrier — there is no path that reaches storage unencrypted.

The storage backend: deliberately untrusted

"Since the storage backend resides outside the barrier, it's considered untrusted so Vault will encrypt the data before it sends them to the storage backend." Why it's built this way: this separation means Vault's actual security model doesn't depend on trusting whatever holds the bytes — a cloud provider's object storage, a self-hosted Consul cluster — because none of them ever see plaintext. Lesson 6 covers the specific backend options (Integrated Storage/Raft is the current recommended default); this lesson's point is that the choice of backend never changes what an attacker gains from compromising it alone.

The core and the HTTP API

Every client — the CLI you used in Lesson 2, the web UI, or any SDK — talks to Vault exclusively through its HTTP API. "Requests may be processed from the HTTP API to the core once Vault is unsealed," and the core "manages the flow of requests through the system, enforces ACLs, and ensures audit logging is done." This is why policies (Lesson 17) and audit devices (Lesson 26) can be enforced consistently no matter which client is used — they're not client-side features, they're enforced once, centrally, in the core.

Try it

Q1. If an attacker steals a full copy of Vault's storage backend files, do they get readable secrets?

No — the storage backend only ever holds data the barrier already encrypted. Without the encryption key (protected by the seal, Lesson 4), stolen storage is unreadable ciphertext.

Now, before revealing: which single component in this lesson's diagram is the one every client — CLI, UI, or SDK — is required to go through, with no exceptions?

Reveal the answer

The HTTP API into the core. There's no client-side bypass — ACL enforcement and audit logging happen centrally in the core, which is exactly why they can't be skipped by using a different client.

Common mistake: assuming storage backend choice (Consul vs. cloud storage vs. Raft) is primarily a security decision — it isn't. Every option sits outside the barrier and receives only encrypted data either way; the real trade-offs (Lesson 6) are durability, operational complexity, and HA behavior, not confidentiality.

Production best practices

Production note: because the storage backend is explicitly untrusted by design, production teams don't need to over-invest in exotic storage-layer encryption or access controls beyond what the backend itself reasonably offers — the barrier is already doing the real protective work. Effort is better spent on unseal/auto-unseal hardening (Lesson 4) and network-level TLS, which protect the layers the barrier doesn't cover.

Exam & interview notes

Directly scored under Vault architecture fundamentals — one of the 9 real exam domains.

Interview Q: "Why does Vault treat its own storage backend as untrusted?" A: Because the barrier encrypts all data before it ever reaches storage — this means Vault's security doesn't depend on the storage layer's own access controls being perfect, and a storage-layer breach alone yields only ciphertext, not secrets.

Recap
  • The barrier is Vault's encryption layer — every read/write to storage passes through it, no exceptions.
