Installing & Running Vault

Lesson 1 explained why Vault exists. Before touching any real concept, you need a Vault server to actually run commands against — and HashiCorp ships a mode built exactly for that: a throwaway, zero-config server that starts unsealed and ready in one command.

Mental model: dev mode is a demo car, not a production vehicle — full working controls, zero safety certification, and it's towed away (data gone) the moment you turn the engine off. That predicts the one rule this lesson repeats from HashiCorp's own docs: never run it anywhere real traffic could reach it, because "insecure" here isn't a caveat, it's the literal design.

Starting a dev-mode server

vault server -dev

This single command auto-configures everything a real deployment normally needs a separate setup pass for:

  • Initialized and unsealed — ready to use immediately, no manual init step (Lesson 4 covers what "sealed" means and why real deployments don't skip it)
  • In-memory storage — all data encrypted in RAM, lost on restart
  • No TLS — listens on 127.0.0.1:8200 unencrypted
  • A KV v2 secrets engine already mounted at secret/

Why it's built this way: HashiCorp's own docs are direct about the trade-off: "Never, ever, ever run a 'dev' mode server in production. It is insecure and will lose data on every restart (since it stores data in-memory)." Every convenience above is a security or durability property a real deployment needs — dev mode trades all of them away specifically so you can learn the CLI and API without a multi-step setup first.

Your first commands

vault status

Reports whether the server is Initialized, Sealed, its Version, storage type, and HA status — the first command to run against any Vault server, dev or production, to confirm what you're actually talking to.

vault kv put -mount=secret creds passcode=my-long-passcode
vault kv get -mount=secret creds

The -mount flag names which KV engine instance to use — current HashiCorp guidance prefers this explicit flag over the older path-style syntax, specifically to avoid confusion with KV v2's internal /data/ path segment (the actual API path a policy or raw API call uses is different from what you type here).

Try it

Q1. Does dev mode need vault operator init or an unseal step before you can use it?

No — dev mode starts already initialized and unsealed. That's exactly what makes it dev-only; a real deployment doesn't get to skip that step (Lesson 4).

Now try it yourself: start a dev server, write a secret with a field of your choice, read it back, then run vault status and identify what Storage Type it reports. Try before revealing.

Reveal the sequence

vault server -dev
# in a second terminal, using the root token and VAULT_ADDR printed above:
vault kv put -mount=secret myapp username=admin
vault kv get -mount=secret myapp
vault status

Storage Type should read inmem — confirming the in-memory, non-durable storage the dev-mode warning refers to.

Common mistake: restarting a dev-mode server expecting the data to still be there — it won't. In-memory storage means every restart is a clean slate, which is exactly why dev mode is unsuitable for anything you'd be upset to lose.

A controlled failure

vault kv put -mount=secret temp value=hello
vault kv get -mount=secret temp
# stop the server (Ctrl-C), then start a fresh one:
vault server -dev
vault kv get -mount=secret temp

Predict first: does the second get find the secret? Observe: no — a fresh dev-mode invocation is a brand-new server with a brand-new in-memory store; nothing carries over, not even the same root token or unseal key.

Production best practices

Production note: the root token dev mode prints on startup has unrestricted access to everything — treat it exactly like you would in a real deployment (Lesson 10 covers why the real root token gets revoked after initial setup, not used day to day) even in a throwaway dev environment, so the habit is already correct before it matters for real.

Exam & interview notes

Foundational — sets up the hands-on environment every later domain's lessons use.

Interview Q: "A teammate wants to demo Vault quickly for a five-minute meeting. What's the fastest safe way?" A: vault server -dev — but explicitly flag it as demo-only, never point real application traffic or real secrets at it, and expect all data to vanish the moment it's stopped.

Recap
  • vault server -dev starts an already-initialized, unsealed, in-memory-storage server — convenient for learning, never for production.
  • vault status is the first command to run against any Vault server to confirm what you're talking to.
  • vault kv put/vault kv get -mount=secret ... is the current recommended CLI syntax for the KV v2 engine.
  • Dev-mode data doesn't survive a restart — every fresh invocation is a clean slate.
