HTTP/HTTPS Fundamentals

HTTP is the Application-layer protocol behind essentially every API call and webpage — a plain-text request/response exchange over the TCP connection Lesson 6 already covered. HTTPS is exactly the same protocol, wrapped in TLS encryption (Lesson 10) so the exchange can't be read or tampered with in transit.

Simple example: A request is a method (GET, POST, ...), a path (/users/42), and headers. A response is a status code (200, 404, ...), headers, and a body. curl -v shows both sides of this exchange in plain text, even over HTTPS — curl decrypts it for you to display.

Methods — what the request wants to do

MethodTypical use
GETRetrieve a resource, no side effects expected
POSTCreate something, or submit data that changes state
PUTReplace a resource entirely
PATCHPartially update a resource
DELETERemove a resource

Status code ranges — what the response means

RangeMeaning
2xxSuccess
3xxRedirect — go look somewhere else
4xxClient error — the request itself was wrong (404 not found, 401 unauthorized, 403 forbidden)
5xxServer error — the request was fine, the server failed to handle it

401 and 403 get confused constantly: 401 means "I don't know who you are" (missing or invalid credentials); 403 means "I know who you are, and you're not allowed." Fixing the wrong one wastes time — a 403 isn't solved by re-authenticating if the account genuinely lacks permission.

Headers carry the metadata

Headers are key-value pairs that carry information outside the actual body — content type, authentication tokens, caching instructions, and more. Content-Type: application/json tells the receiver how to parse the body; Authorization: Bearer <token> is how most APIs authenticate a request.

Try it — before looking below

Q1. An API call returns 403. Will sending a valid API key/token fix it?

Not necessarily — 403 means the server already recognizes who's asking and is deliberately denying the action. That's a permissions problem, not an authentication problem; a 401 is the one that specifically means the credentials themselves are the issue.

Now try it yourself

curl -v https://example.com 2>&1 | grep -E "^[<>]"
# > lines are the request being sent, < lines are the response coming back

Source

RFC 9110 — HTTP Semantics — the official IETF specification for HTTP methods and status codes.

Recap
  • HTTP is a plain-text request/response protocol over TCP; HTTPS is the same protocol wrapped in TLS.
  • Status codes group by first digit: 2xx success, 3xx redirect, 4xx client error, 5xx server error.
  • 401 = unknown identity (authentication); 403 = known identity, denied anyway (authorization) — different problems, different fixes.
curl -v showing you both the request and response headers is often faster for diagnosing an API issue than reading application logs first.
