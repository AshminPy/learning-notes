CDN Fundamentals

A CDN (Content Delivery Network) caches your content at edge locations physically close to users worldwide, so a request doesn't have to travel all the way to your origin server every time. The result is lower latency for users far from your origin, and less load hitting your origin directly.

Simple example: Without a CDN, a user in Tokyo requesting an image hosted in Virginia waits for that full round trip. With a CDN, that same image is cached at a Tokyo edge location after the first request — every subsequent request from nearby users is served locally, far faster.

Cache hit vs. cache miss

ResultWhat happenedSpeed
Cache hitThe edge location already had this content cachedFast — served locally, origin never contacted
Cache missThe edge location didn't have it (or it expired) — fetches from origin, then caches itSlower this one time, then cached for next time

Response headers usually reveal which happened — a header like X-Cache: HIT or CF-Cache-Status: HIT (naming varies by CDN provider) tells you directly whether a request was served from cache or went back to origin.

Cache control — you decide what's cacheable

The Cache-Control HTTP header (set by your origin server) tells the CDN how long content can be cached and whether it can be cached at all. Static assets (images, CSS, JS with a version in the filename) are usually cached aggressively; personalized or frequently-changing content (a logged-in user's dashboard) is usually marked non-cacheable, or cached for a very short time.

Caching an API response that includes user-specific or sensitive data is a real, serious mistake — the CDN might serve one user's cached personalized response to a completely different user. Cache-Control: private or no-store exists specifically to prevent this, and it's worth double-checking on any endpoint returning per-user data.

Cache invalidation

When origin content changes before the cached copy's TTL expires, you need to explicitly invalidate (purge) the stale cached version at the edge — otherwise users keep seeing the old content until it naturally expires. Every CDN provider offers a purge/invalidation API or console action for exactly this.

Try it — before looking below

Q1. You update an image on your origin server, but users still see the old version for a while afterward. Assuming the CDN is working correctly, what's happening?

The edge locations are still serving the previously cached version — it hasn't expired (per its Cache-Control TTL) yet, and no manual invalidation was triggered. This is expected CDN behavior, not a bug — the fix is either waiting out the TTL or explicitly invalidating the cached object.

Recap
  • A CDN caches content at edge locations close to users — a cache hit is fast and skips the origin entirely; a cache miss fetches from origin once, then caches it.
  • Cache-Control headers from the origin decide what's cacheable and for how long — user-specific data should generally be marked non-cacheable.
  • Content changed at origin before its cached TTL expires needs explicit invalidation, or users keep seeing the stale cached version.
"Users are seeing old content after a deploy" is almost always a caching (CDN or browser) question first, an application bug second — check cache headers before diving into application code.
