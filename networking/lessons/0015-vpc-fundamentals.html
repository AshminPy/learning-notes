VPC Fundamentals

A VPC (Virtual Private Cloud) is your own logically isolated slice of a cloud provider's network — your own private address space, your own routing, your own security boundary, running on shared physical infrastructure you never directly see. Everything from Lessons 2-14 (CIDR, routing, NAT, firewalls) applies inside a VPC; a VPC is where those concepts actually get configured in cloud work.

Simple example: Creating a VPC starts with exactly the CIDR block decision from Lesson 2 — pick a private range like 10.0.0.0/16, and every subnet you create afterward carves out a smaller piece of that same range.

What a VPC actually contains

ComponentRole
CIDR blockThe overall private address range for the whole VPC
SubnetsSmaller CIDR slices within the VPC — public or private (Lesson 16)
Route tablesWhere traffic goes, per subnet (Lesson 16)
Security groups / firewall rulesWhat traffic is allowed, per resource (Lesson 13)
Internet/NAT GatewaysHow (and whether) resources reach the public internet (Lesson 12)

A VPC is isolated by default — nothing in it is reachable from outside unless you explicitly add a gateway, and nothing in it can reach the outside internet unless you explicitly add an Internet or NAT Gateway. This "isolated unless connected" default is the same default-deny mental model from Lesson 13, applied at the network-boundary level instead of the per-resource level.

Multiple VPCs and isolation

Two VPCs, even with identical or overlapping CIDR ranges, are completely isolated from each other by default — nothing in one can reach anything in the other unless you deliberately connect them (VPC peering, a VPN, or a transit gateway). This is useful for separating environments (production vs. staging) with a hard boundary, not just a naming convention.

Picking the exact same CIDR range for every VPC "because it's simple" blocks future peering between them (Lesson 14) — two VPCs with overlapping ranges can't be directly peered without renumbering. Plan distinct, non-overlapping ranges across VPCs from the start, the same lesson as Lesson 2's private-range planning, just one level up.

Try it — before looking below

Q1. You create a brand-new VPC with no gateways attached yet. Can a resource inside it reach the public internet, or be reached from it?

Neither, by default — a VPC is fully isolated until you explicitly add an Internet Gateway (both directions, for public resources) or a NAT Gateway (outbound only). This is intentional, not a bug to fix.

Source

VPC implementation details are cloud-provider-specific — always check the current official documentation for your provider (AWS VPC, GCP VPC, or Azure Virtual Network docs) for exact limits and defaults, which change over time.

Recap
  • A VPC is your isolated private network slice in the cloud — everything from earlier lessons (CIDR, routing, NAT, firewalls) configures inside it.
  • A VPC is isolated by default: no inbound or outbound internet access without an explicitly added gateway.
  • Separate VPCs need distinct, non-overlapping CIDR ranges if they might ever need to be peered together later.
Every cloud networking concept in this course converges here — if a later lesson's terminology feels unfamiliar, it's almost certainly a VPC component described from a different angle.
