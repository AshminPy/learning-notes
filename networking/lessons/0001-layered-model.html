How Data Actually Moves: The Layered Model

Every network conversation — loading a webpage, an API call, an SSH session — is built from layers, each one only responsible for one job and trusting the layer below it to have done its own job correctly. You don't need to memorize all seven OSI layers to work effectively; you need four practical ones, because that's what real tools and error messages actually reference.

Simple example: When curl fails with "connection refused," that's a Transport-layer problem (nothing was listening on the port). When it fails with "could not resolve host," that's Application-layer, specifically DNS. Same tool, same command, but the fix is completely different depending on which layer failed.

The four layers that matter day to day

LayerJobExamples
ApplicationWhat the software actually wants to sayHTTP, DNS, SSH
TransportReliable delivery (or not) between two endpoints, addressed by portTCP, UDP
NetworkGetting a packet from one network to another, addressed by IPIP, routing
LinkGetting a frame across one physical/local segmentEthernet, Wi-Fi

This four-layer model (closer to the practical "TCP/IP model" than the academic 7-layer OSI model) is what you'll actually reason with when troubleshooting — each failure symptom points to roughly one layer, which is why "what layer is this" is often the fastest first diagnostic question.

Why the split matters

Each layer only cares about its own job and expects the layer below to already be solved. TCP (Transport) doesn't know or care whether it's running over Wi-Fi or Ethernet (Link) — that's exactly the point. This separation is what lets the same HTTP request (Application) work identically whether it travels over a home Wi-Fi network or a data center's fiber backbone.

Try it — before looking below

Q1. A colleague says "the network is down" because a website won't load in their browser. What's the first question that narrows down which layer actually failed?

"Does the exact same failure happen if you use the IP address directly instead of the domain name?" If using the raw IP works, the problem is DNS (Application layer). If it still fails, the problem is lower — Transport or Network.

Now try it yourself

curl -v https://example.com
# Watch the output stages: DNS resolution, then TCP connect, then TLS handshake,
# then the actual HTTP request — each stage is a different layer succeeding in order.

Source

RFC 1122 — Requirements for Internet Hosts — the official IETF reference defining the practical Internet (TCP/IP) layering model.

Recap
  • Four practical layers: Application (HTTP/DNS/SSH), Transport (TCP/UDP), Network (IP/routing), Link (Ethernet/Wi-Fi).
  • Each layer trusts the one below it to already work — that separation is a feature, not an abstraction for its own sake.
  • "What layer is this" is often the fastest first question when troubleshooting any network failure.
