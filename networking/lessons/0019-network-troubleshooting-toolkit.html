Networking for Cloud Engineers — Lesson 19 of 20

Network Troubleshooting Toolkit

This lesson connects the whole course into one diagnostic order. Rather than guessing, the layered model from Lesson 1 gives you a natural sequence: confirm DNS resolves, confirm you can reach the host at all, confirm the specific port responds, confirm the application-level response is correct. Each step rules out one entire category of cause.

Simple example: A failing API call could be broken DNS, an unreachable host, a closed port, a firewall block, or an application bug — five very different fixes. Working through the sequence below in order finds which one in under a minute, instead of guessing.

The narrowing sequence

StepCommandRules out
1. DNSdig hostnameWrong or missing DNS record (Lesson 7-8)
2. Basic reachabilityping hostnameHost completely unreachable at the network level
3. Path/routetraceroute hostname / mtr hostnameWhere along the path traffic actually stops
4. Port reachabilitycurl -v hostname:port / nc -zv hostname portNothing listening, or a firewall silently dropping that specific port
5. Application responsecurl -v, read status code and bodyThe network is fine — remaining issue is application-level

traceroute/mtr show every hop your packet passes through on the way to the destination, and where it stops responding — useful for narrowing "unreachable" down to a specific point in the path, rather than treating the whole route as one black box.

Cloud-specific tools worth knowing

Beyond the local commands above, cloud providers offer VPC flow logs — a record of every connection attempt through a network interface, including ones a security group blocked. This is often the fastest way to confirm "was this traffic even allowed to leave/enter" separately from "did the application respond correctly" — the two failure modes look identical from the client's side but have completely different fixes.

Testing connectivity from your own laptop and getting different results than a server-to-server test inside the cloud environment is common and expected — your laptop and the cloud resource are on entirely different networks, with different security group/firewall rules applying. Always test from the actual failing vantage point, not a convenient substitute.

Try it — before looking below

Q1. ping to a host succeeds, but a specific application port never responds — no error, just a hang. Where in the 5-step sequence does this land, and what's the likely cause?

Step 4 (port reachability) — basic network reachability is confirmed, but the port itself times out rather than being actively refused. That combination usually points to a firewall or security group silently dropping traffic to that specific port, rather than nothing listening (which would typically show "connection refused" instead).

Now try it yourself

dig example.com +short
ping -c 3 example.com
traceroute example.com          # or: mtr example.com, for a live continuous view
curl -v https://example.com 2>&1 | tail -20

Recap
  • Diagnose network failures in order: DNS, basic reachability, path, port, application — each step rules out one entire category.
  • traceroute/mtr narrow "unreachable" down to a specific hop instead of treating the path as a black box.
  • Always test from the actual failing vantage point — a laptop and a cloud resource sit on different networks with different rules.
This exact sequence — DNS, reachability, path, port, application — is the single most reusable skill in this entire course. Internalize the order, not just the commands.
