VPNs & Private Connectivity

A VPN creates an encrypted tunnel between two networks (or a device and a network) over the public internet, so traffic inside that tunnel behaves as if it's on a private, trusted network — even though it's physically traveling over the same internet as everything else.

Simple example: A site-to-site VPN connects your office network to a cloud VPC — a server in the office can reach a private-subnet database in the cloud directly by its private IP, with no public exposure of that database anywhere, because the whole path between them is encrypted and routed through the tunnel.

Two common shapes

TypeConnectsTypical use
Site-to-siteTwo entire networks (office ↔ cloud VPC)Persistent, always-on connectivity between fixed locations
Client/remote-accessA single device ↔ a networkAn individual engineer connecting to a private VPC from their laptop

Cloud private connectivity beyond VPN

Cloud providers also offer dedicated private connections (AWS Direct Connect, GCP Cloud Interconnect, Azure ExpressRoute — names vary by provider) that don't traverse the public internet at all, using a physical or provider-managed link instead. These trade the VPN's flexibility and low setup cost for more consistent latency and higher throughput — typically used when a VPN's variable internet-path performance isn't acceptable.

A VPN connects two networks — it doesn't automatically make routing or firewall rules on either side permissive. A common surprise: the tunnel comes up successfully (both ends report "connected"), but traffic still doesn't flow, because a route table on one side was never updated to send traffic for the other network through the tunnel. A working tunnel and working end-to-end connectivity are two separate things to verify.

VPC peering — a related but different concept

VPC peering connects two cloud VPCs directly to each other (often within the same provider), without an encrypted tunnel or gateway device — it's closer to routing two private networks together than to a VPN. Worth knowing as a distinct option: peering for VPC-to-VPC within the same cloud, VPN or dedicated connection for anything crossing into a different network entirely (like an on-premises office).

Try it — before looking below

Q1. A site-to-site VPN shows "connected" on both ends, but a server on one side still can't reach a server on the other. What's the most common overlooked cause?

The route table on one (or both) sides was never updated to actually send traffic for the remote network's CIDR range through the VPN tunnel — the tunnel itself being up doesn't automatically create the routing needed to use it.

Now try it yourself

ip route show | grep tun         # if a VPN tunnel interface exists locally, see its route
ip addr show | grep tun           # confirm a tunnel interface is actually present and up

Source

RFC 4301 — Security Architecture for the Internet Protocol (IPsec) — the official IETF specification underlying most site-to-site VPN implementations.

Recap
  • A VPN is an encrypted tunnel making two networks (or a device and a network) behave as private/trusted, over the public internet.
  • Site-to-site connects two whole networks persistently; client/remote-access connects one device on demand.
  • A tunnel being "connected" doesn't guarantee traffic flows — routing on both sides must also send the right traffic through it.
When a VPN "isn't working," check the tunnel status and the route table separately — they fail independently, and conflating them wastes time.
