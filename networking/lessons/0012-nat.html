NAT & Outbound Internet Access

Private IP addresses from Lesson 2 (10.x, 172.16-31.x, 192.168.x) aren't routable on the public internet — no internet router knows how to send a reply back to 10.0.1.5. NAT (Network Address Translation) is what makes outbound internet access work anyway: it rewrites a private source address to a public one on the way out, and rewrites the reply back on the way in.

Simple example: Your laptop on a home network has address 192.168.1.42. When you browse the web, your home router rewrites that to its own public IP before sending the request out — the website only ever sees the router's public address, never your laptop's private one.

How NAT keeps track of who gets which reply

A NAT device maintains a translation table mapping (private IP, private port) to (public IP, public port) for every active connection. When a reply comes back addressed to that public IP and port, the NAT device looks up the table and forwards it to the correct internal device — this is exactly why NAT works fine for outbound connections you initiate, but can't handle unsolicited inbound connections (there's no table entry yet to route them by).

NAT in the cloud — NAT Gateways

A private subnet's instances have no public IP at all — by design, for security. A NAT Gateway sits in a public subnet and does exactly the router job above: instances in the private subnet route their outbound internet traffic through it, get a shared public IP for that traffic, and can reach the internet for things like package updates — while remaining completely unreachable from the internet for inbound connections.

ComponentJob
Internet GatewayAttaches a VPC to the public internet — allows both directions if a resource has a public IP
NAT GatewayAllows outbound-only internet access for private-subnet resources with no public IP

A NAT Gateway is not a substitute for a firewall or security group — it controls address translation, not whether traffic is allowed. Resources behind a NAT Gateway can still reach anywhere outbound unless something else (security groups, network policies) restricts that traffic.

Try it — before looking below

Q1. An instance sits in a private subnet with no public IP, routed through a NAT Gateway. Can someone on the internet initiate a connection directly to that instance?

No — NAT only has a translation table entry for connections the private instance itself initiated outbound. There's no existing entry for an unsolicited inbound connection, so the NAT Gateway has nowhere to route it, and it's dropped.

Recap
  • NAT rewrites a private source address to a public one on the way out, tracked in a translation table so replies route back correctly.
  • NAT naturally allows outbound connections but blocks unsolicited inbound ones — there's no table entry to route them by.
  • In the cloud, an Internet Gateway allows both directions for public resources; a NAT Gateway allows outbound-only for private ones. Neither replaces a firewall — that's a separate control (Lesson 13).
"My private-subnet server can reach the internet but nothing can reach it" is NAT working exactly as designed, not a misconfiguration to fix.
