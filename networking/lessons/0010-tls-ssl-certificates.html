TLS/SSL & Certificates

TLS (the modern successor to the older, now-deprecated SSL — people still say "SSL" out of habit) does two jobs at once: it encrypts the connection so no one in between can read it, and it proves the server's identity so you know you're actually talking to who you think you are. A certificate is what makes the second part possible.

Simple example: When you visit an HTTPS site, its certificate is signed by a Certificate Authority (CA) your browser already trusts. The browser checks that signature — if it's valid and the domain matches, you get the padlock icon. If not, you get a warning page, because it can no longer vouch for who you're really connecting to.

The TLS handshake, high level

StepWhat happens
1. ClientHelloClient says what TLS versions/ciphers it supports
2. ServerHello + certificateServer picks a cipher, sends its certificate to prove identity
3. VerificationClient checks the certificate's signature against trusted CAs, and that the domain matches
4. Key exchangeBoth sides agree on a shared encryption key for the rest of the session

This whole exchange happens on top of the TCP handshake from Lesson 6, adding its own round trips before any actual HTTP request goes out — which is why the first connection to a new HTTPS host is slightly slower than a plain HTTP one.

What's actually in a certificate

  • Subject — the domain(s) it's valid for
  • Issuer — the CA that signed it
  • Validity period — a start and expiry date
  • Public key — used in the key exchange

An expired certificate is one of the most common, entirely preventable outages — the certificate was valid for months, then one day it simply wasn't. Monitoring certificate expiry dates (most CAs and cloud load balancers support auto-renewal) is a basic operational habit, not an edge case to handle reactively.

Try it — before looking below

Q1. A browser shows a certificate warning for a site that was working fine yesterday. What are the two most likely causes to check first?

The certificate expired (check the validity dates), or the certificate doesn't match the domain being visited (e.g., a recent DNS change points to a server with a certificate for a different name). Both are common, both are checkable in seconds with the right command.

Now try it yourself

echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -dates -subject -issuer
# Shows the certificate's validity dates, subject, and issuing CA directly

Source

RFC 8446 — The Transport Layer Security (TLS) Protocol Version 1.3 — the official IETF specification.

Recap
  • TLS both encrypts a connection and verifies the server's identity via a certificate signed by a trusted CA.
  • The TLS handshake adds round trips on top of the TCP handshake — expected, small first-connection overhead.
  • Expired or mismatched certificates are a common, entirely preventable outage — monitor expiry, don't wait for a user report.
openssl s_client against any host is the fastest way to see exactly what certificate a server is actually presenting — faster than trusting what a dashboard claims is configured.
