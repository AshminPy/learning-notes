TCP vs UDP

Both TCP and UDP sit at the Transport layer and both use ports to address a specific application — but they make opposite trade-offs. TCP guarantees delivery and order at the cost of setup time and overhead. UDP sends immediately with no guarantee, trading reliability for speed. Neither is "better" — they're built for different jobs.

Simple example: Loading a webpage uses TCP — every byte of that HTML must arrive, in order, or the page breaks. A live video call uses UDP — a dropped frame every so often is a minor glitch, but waiting for TCP to retransmit a lost packet would cause a much worse stutter than just moving on.

Why DNS mostly uses UDP

A DNS query and response is small and simple: ask a question, get an answer, done. TCP's handshake overhead would roughly double the time for a lookup that's this quick and low-stakes — if the response doesn't arrive, the resolver just asks again, which is cheaper than the guaranteed-delivery machinery TCP carries. (DNS does fall back to TCP for responses too large for a single UDP packet, but the common case is UDP.)

Ports — how both protocols find the right application

Both TCP and UDP use a 16-bit port number (0-65535) alongside the IP address to identify which specific application on a host should receive the data — this is exactly what ss -tulnp from Lesson 23 in the Linux course shows you. A TCP connection and a UDP "connection" on the same port number are entirely separate — port 53 TCP and port 53 UDP don't interfere with each other.

Try it — before looking below

Q1. A video call occasionally has a brief glitch but keeps moving forward in real time rather than pausing to "catch up." Which transport protocol is it almost certainly using, and why does that behavior make sense?

UDP — it doesn't retransmit lost packets or wait for them, so the call just continues with a small visible glitch instead of pausing to guarantee every frame arrives, which would make a live call feel worse, not better.

Now try it yourself

ss -tulnp | head          # -t = TCP, -u = UDP — see both listed side by side
nc -u -zv 8.8.8.8 53       # test a UDP port (DNS) is reachable

Source

RFC 9293 — Transmission Control Protocol (TCP) and RFC 768 — User Datagram Protocol (UDP) — the official IETF specifications.

Recap
  • TCP guarantees delivery and order at the cost of setup overhead; UDP sends immediately with no guarantee.
  • DNS defaults to UDP because a quick retry is cheaper than TCP's handshake for a small, low-stakes query.
  • Ports (0-65535) identify the specific application on both protocols — TCP and UDP on the same port number are independent of each other.
If a service "sometimes works" intermittently over a lossy connection, checking whether it's UDP-based (no automatic retry) is often the fastest explanation.
