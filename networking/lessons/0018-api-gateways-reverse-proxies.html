API Gateways & Reverse Proxies

A reverse proxy sits in front of one or more backend servers and forwards client requests to them, while the client only ever sees the proxy — the same basic shape as the L7 load balancer from Lesson 11, but the term "reverse proxy" is used more broadly for anything that also does extra work like caching, compression, or TLS termination. An API gateway is a reverse proxy purpose-built for APIs, adding API-specific concerns on top.

Simple example: Nginx running in front of an application server is a classic reverse proxy — clients connect to Nginx, Nginx forwards to the app, and the client never talks to the app server directly. An API gateway does the same forwarding, but also handles things like rate limiting per API key and request validation before the request ever reaches your backend code.

What an API gateway typically adds beyond basic proxying

FeatureWhy it matters
Authentication/authorizationValidate API keys or tokens once, centrally — backends don't each reimplement it
Rate limitingProtect backends from being overwhelmed by one client, deliberately or accidentally
Request/response transformationReshape a request before it reaches the backend, or a response before it reaches the client
Routing to multiple servicesOne public entry point fronting many backend services (a common microservices pattern)

TLS termination — where encryption actually ends

"TLS termination" means the proxy decrypts the incoming HTTPS connection and forwards the request to the backend as plain HTTP over the internal network. This is a deliberate, common design — it centralizes certificate management in one place instead of every backend server needing its own certificate — but it means traffic between the proxy and backend is unencrypted unless a separate internal TLS layer is added.

Assuming "the site uses HTTPS" means every hop of the request is encrypted is a common misunderstanding — after TLS termination at a reverse proxy or load balancer, the internal hop to the backend is frequently plain HTTP. For sensitive internal traffic, that internal hop may need its own TLS layer, not just the client-facing one.

Try it — before looking below

Q1. A user's browser connects over HTTPS to a load balancer, which then forwards to a backend server over plain HTTP inside the private network. Is any part of this request actually unencrypted?

Yes — the hop between the load balancer and the backend server is plain HTTP, unencrypted. The client-to-load-balancer hop is encrypted (that's the "HTTPS" the user sees), but TLS termination means encryption ends there unless a separate internal TLS layer is explicitly configured for the second hop.

Now try it yourself

curl -sI https://example.com | grep -i "server\|via\|x-forwarded"
# X-Forwarded-* headers, when present, are a strong signal a reverse proxy or
# load balancer is in front of the actual backend

Source

RFC 7239 — Forwarded HTTP Extension — the official IETF specification for how proxies communicate original client information to backends.

Recap
  • A reverse proxy forwards client requests to backend servers, hiding those backends from direct client access — an API gateway is a reverse proxy specialized for APIs (auth, rate limiting, transformation).
  • TLS termination decrypts at the proxy — the hop onward to the backend is commonly plain HTTP unless separately encrypted.
  • "The site uses HTTPS" describes the client-facing hop, not necessarily every internal hop behind it.
When investigating whether internal traffic is actually encrypted, don't assume from the public-facing HTTPS — check what protocol the proxy actually uses on its backend connection.
