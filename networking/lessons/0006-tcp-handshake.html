The TCP Handshake & Connection Lifecycle

Before a single byte of real data moves over TCP, both sides exchange three packets to agree the connection is open and synchronize where sequence numbering starts. This is the "three-way handshake," and it's why a fresh TCP connection always has a small delay before the actual request goes out — that delay is the handshake completing.

Simple example: curl -v against a slow-to-respond server shows this directly — a visible pause labeled "Connected" happens before "GET request sent," because the handshake had to finish first.

The three steps

StepWho sendsWhat it means
1. SYNClient → Server"I'd like to start a connection"
2. SYN-ACKServer → Client"Acknowledged, and I'd like to too"
3. ACKClient → Server"Acknowledged — connection is now open"

Only after all three packets complete does actual application data (the HTTP request, the SSH banner, whatever the connection is for) start flowing. This is why "connection refused" and "connection timed out" mean different things: refused means step 1 got an immediate rejection (nothing listening on that port); timed out means step 1 never got any reply at all (likely a firewall silently dropping it, or the host is unreachable).

Closing a connection

Closing is a similar four-step exchange (FIN/ACK from each side), because either side can finish sending independently — one direction can close while the other still has data in flight. A connection that's supposed to be closed but keeps showing up in ss output in a TIME_WAIT or CLOSE_WAIT state is normal cleanup behavior, not automatically a bug — though a large pile-up of either can indicate the application isn't closing connections properly.

"Connection refused" and "connection timed out" get treated as the same failure in casual conversation, but they point to different causes — refused means you reached the host and it actively said no; timed out means you likely never reached it at all. Diagnosing the wrong one wastes real time.

Try it — before looking below

Q1. You try to connect to a port and get an immediate "connection refused" versus a 30-second hang ending in "connection timed out." What's the practical difference in what you should check next?

Refused: the host is reachable but nothing is listening on that port — check if the service is running and bound correctly. Timed out: your packet likely never got a reply at all — check firewalls/security groups and basic network reachability first, the service question comes second.

Now try it yourself

ss -tan | grep -E "SYN|ESTAB|TIME_WAIT" | head   # see connections in different lifecycle states
curl -v https://example.com 2>&1 | grep -i connect  # watch the handshake complete in curl's own output

Source

RFC 9293 — Transmission Control Protocol (TCP) — the official IETF specification, Section 3.5 covers connection establishment.

Recap
  • TCP requires a three-way handshake (SYN, SYN-ACK, ACK) before any real data flows — this is the delay you see on a fresh connection.
  • "Connection refused" (actively rejected) and "connection timed out" (no reply at all) point to different root causes — treat them differently.
  • Closing is a separate four-step exchange; connections sitting in TIME_WAIT/CLOSE_WAIT briefly is normal, not automatically a bug.
When a network issue is intermittent, capturing the handshake itself with tcpdump (Linux course, Lesson 23) shows you exactly which step is failing — far faster than guessing.
