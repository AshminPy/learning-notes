DNS Troubleshooting

"It works on my machine but not yours" is one of the most common DNS symptoms — and it's usually not a broken record, it's two different resolvers holding two different cached answers. Knowing how to bypass the cache and query authoritatively directly is what separates a fast diagnosis from a confused half hour.

Simple example: dig example.com uses your system's configured resolver (which might have a stale cached answer). dig @8.8.8.8 example.com asks Google's public resolver directly, bypassing whatever your local resolver has cached — a quick way to check if the problem is your resolver's cache or the record itself.

The narrowing sequence

StepCommandTells you
1. Check the current answerdig example.comWhat your resolver currently returns
2. Check a different resolverdig @8.8.8.8 example.comWhether it's your local cache specifically
3. Check the authoritative source directlydig @<authoritative-ns> example.comThe real, current, ground-truth answer — no caching involved
4. Check the TTLdig example.com, read the number next to the recordHow long a cached wrong answer could realistically persist

Common DNS failure patterns

  • NXDOMAIN: the domain doesn't exist at all, from that resolver's perspective — check for a typo or confirm the domain is actually registered/delegated.
  • SERVFAIL: the resolver tried and got a failure partway through — often a misconfigured DNSSEC signature, or the authoritative server itself is down.
  • Different answers from different locations: often intentional (geo-based DNS/CDN routing, Lesson 17), not a bug — confirm whether the domain is expected to behave this way before assuming an error.

Flushing your local DNS cache fixes exactly one machine's stale-cache problem — it does nothing for anyone else's cached answer anywhere else on the internet. If the issue is reported across many users, the fix is waiting out the TTL (or reducing it before the next planned change), not flushing caches one machine at a time.

Try it — before looking below

Q1. dig example.com from your machine returns the old IP. dig @8.8.8.8 example.com returns the new, correct IP. What does that combination tell you?

The record itself is already correct at the authoritative level — your local/configured resolver is just serving a stale cached answer. Flushing your local cache (or waiting out the TTL) resolves it, not a DNS record problem.

Now try it yourself

dig example.com
dig @8.8.8.8 example.com
dig example.com NS +short          # find the authoritative nameservers
dig @<one-of-those-ns> example.com  # query authoritatively, no caching

Source

RFC 8499 — DNS Terminology — the official IETF reference defining recursive, authoritative, and related DNS terms precisely.

Recap
  • Narrow DNS issues in order: your resolver's cached answer → a different public resolver → the authoritative nameserver directly.
  • NXDOMAIN means the name doesn't exist from that resolver's view; SERVFAIL means the lookup itself broke partway through.
  • Flushing a local cache only fixes that one machine — a widely-reported stale answer needs the TTL to expire, not individual cache flushes.
When a DNS issue is reported by "some users, not others," suspect caching or geo-routing before suspecting a broken record — both produce that exact symptom.
