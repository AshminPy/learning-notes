Subnets, Route Tables & Gateways in the Cloud

A VPC's CIDR block (Lesson 15) is just the outer boundary — subnets carve it into smaller pieces, and what actually makes a subnet "public" or "private" isn't a special flag, it's simply which route table is attached to it and what that route table points to.

Simple example: A "public" subnet is public because its route table has a route sending 0.0.0.0/0 traffic to an Internet Gateway. A "private" subnet either has no such route, or routes 0.0.0.0/0 to a NAT Gateway instead — same subnet mechanics, different route table.

Building the picture

LayerExample
VPC CIDR10.0.0.0/16
Public subnet10.0.1.0/24 — route table sends 0.0.0.0/0 to Internet Gateway
Private subnet10.0.2.0/24 — route table sends 0.0.0.0/0 to NAT Gateway (or has no default route at all)

This is the exact same CIDR subnetting math from Lesson 2, and the exact same longest-prefix-match routing logic from Lesson 4 — cloud networking doesn't introduce new concepts here, it just gives you a UI/API for configuring the same primitives.

A typical layout

A common pattern spreads resources across multiple availability zones for resilience, with a public and private subnet pair in each: load balancers and NAT Gateways live in the public subnets; application servers and databases live in the private subnets, reachable only from inside the VPC (or through the load balancer). This shape directly implements the "public entry point, private everything else" security posture from Lessons 12-13.

Route tables are associated per-subnet, not automatically inherited VPC-wide — adding a new subnet and forgetting to associate the right route table is a common setup mistake that leaves it either unexpectedly public or unable to reach the internet at all, silently, with no error until someone tries to use it.

Try it — before looking below

Q1. A subnet has a route sending 0.0.0.0/0 to an Internet Gateway. Does that alone make every resource in the subnet reachable from the internet?

Not by itself — the resource also needs a public IP address, and security group rules (Lesson 13) must actually allow the inbound traffic. The route table controls the path; the public IP and security group control whether anything can actually use that path.

Exact subnet/route table/gateway behavior is cloud-provider-specific — always check current official documentation for your provider before implementing (AWS VPC, GCP VPC, or Azure Virtual Network docs).

Recap
  • "Public" and "private" subnets aren't a special property — they're defined entirely by which route table is attached and where its default route points.
  • This is the same CIDR and routing math from Lessons 2 and 4, just configured through a cloud provider's interface.
  • A route table alone doesn't make a resource reachable — it also needs a public IP and permissive security group rules.
When a new subnet "isn't working" as expected, checking its route table association first is usually faster than checking security groups — a missing or wrong association is a very common, very quiet failure.
