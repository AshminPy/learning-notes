DNS Fundamentals

DNS translates a domain name into the IP address a computer actually needs to connect. That translation isn't one lookup — it's a chain of servers, each responsible for one piece of the domain, queried in sequence from the most general to the most specific.

Simple example: Resolving www.example.com means asking a root server "who handles .com?", then asking that .com server "who handles example.com?", then asking example.com's own nameserver "what's the address for www?" Each step narrows down one label of the domain.

Common record types

RecordMaps
ADomain name → IPv4 address
AAAADomain name → IPv6 address
CNAMEDomain name → another domain name (an alias)
MXDomain → mail server, with a priority
TXTArbitrary text — commonly used for domain verification and email security (SPF/DKIM)
NSWhich nameservers are authoritative for this domain

Recursive vs. authoritative

Your laptop doesn't walk the whole chain itself — it asks a recursive resolver (often your ISP's, or a public one like 8.8.8.8) to do that walk on its behalf and just return the final answer. The nameserver that actually owns the final answer for a specific domain is called authoritative for that domain — it's the source of truth, not a cache of someone else's answer.

Caching and TTL

Every DNS record has a TTL (time to live) — how long a resolver is allowed to cache that answer before it must ask again. This is exactly why a DNS change (pointing a domain at a new server) doesn't take effect everywhere instantly: resolvers holding a cached answer keep using it until that TTL expires, even though the authoritative record already changed.

Before a planned DNS cutover, lower the TTL well in advance (hours or a day ahead, not minutes) — a record with a 24-hour TTL set 5 minutes before the change means some users see the old answer for up to 24 more hours after the change goes live.

Try it — before looking below

Q1. You updated a domain's A record an hour ago, but some users still reach the old server. The change was applied correctly on the authoritative nameserver. What's the most likely explanation?

Those users' resolvers are still serving a cached answer from before the change, and the record's TTL hasn't expired yet — this is expected DNS propagation behavior, not a broken change.

Now try it yourself

dig example.com A               # the A record, plus its TTL
dig example.com NS               # which nameservers are authoritative
dig +trace example.com           # watch the full resolution chain, root to authoritative

Source

RFC 1035 — Domain Names: Implementation and Specification — the official IETF DNS specification.

Recap
  • DNS resolution is a chain from root to authoritative nameserver — a recursive resolver walks that chain on your behalf.
  • A/AAAA map to IP addresses, CNAME aliases to another name, MX routes mail, TXT holds arbitrary verification text.
  • TTL controls caching — a low TTL set well before a planned change is what makes a DNS cutover fast and predictable.
dig +trace is worth running once deliberately, just to see the full root-to-authoritative chain happen in real time — it makes every later DNS lesson click faster.
