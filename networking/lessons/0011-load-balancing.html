Load Balancing Fundamentals

A load balancer sits in front of multiple backend servers and spreads incoming traffic across them — for capacity, and just as importantly, so a single failed server doesn't take the whole service down. The key distinction to understand first is which layer it operates at, because that decides what it can actually see and act on.

Simple example: An L4 (Transport-layer) load balancer sees only IP addresses and ports — it can't read the HTTP request inside. An L7 (Application-layer) load balancer terminates the connection and reads the actual HTTP request, so it can route /api/* to one backend and /static/* to another.

L4 vs L7

L4 (Transport)L7 (Application)
SeesIP + port onlyFull HTTP request — path, headers, cookies
Routing decisionsBy connection onlyBy path, header, hostname, cookie — much more flexible
Performance overheadLower — doesn't parse the requestHigher — has to actually read and understand HTTP
Typical useRaw TCP/UDP services, very high throughput needsWeb applications, APIs, anything needing path-based routing

Health checks — the part that actually prevents outages

A load balancer periodically checks each backend (an HTTP request to a health endpoint, or a simple TCP connect) and stops sending traffic to any backend that fails. This is the real value beyond just "spreading load" — a single crashed server gets automatically routed around within seconds, without anyone paging anyone.

A health check that only confirms the server process is running (not that it can actually serve real requests) gives false confidence — a backend can pass a trivial health check while its database connection is broken and every real request fails. Health checks should exercise the actual critical dependency, not just "is the port open."

Common algorithms

  • Round robin — each backend gets a turn in order, simplest option
  • Least connections — send to whichever backend currently has the fewest active connections, better when requests take variable time
  • IP hash / session affinity — the same client consistently reaches the same backend, useful when a backend holds session state locally

Try it — before looking below

Q1. You need to route /api/* requests to one set of servers and everything else to another set, based on the URL path. Does an L4 or L7 load balancer support this?

L7 — path-based routing requires reading the actual HTTP request, which an L4 load balancer never sees. L4 only knows IP and port, not the path inside the request.

Recap
  • L4 load balancers see only IP/port; L7 load balancers read the actual HTTP request, enabling path/header/cookie-based routing.
  • Health checks are the real value beyond load spreading — they automatically route around a failed backend.
  • A health check must exercise the actual critical dependency, not just confirm the process is alive, or it gives false confidence.
When one backend in a pool behaves strangely while others are fine, checking whether it's failing its own health check (and why) is usually faster than debugging application code first.
