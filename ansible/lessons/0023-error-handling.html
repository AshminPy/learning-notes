Error handling: block/rescue

You already know the default from Lesson 6: if a task fails on a host, Ansible stops running further tasks in that play for that host. Everything in this lesson is about working with that default — telling Ansible more precisely what counts as a failure, and building recovery logic — not fighting it by accident.

Mental model: the default "stop on failure" behavior is a safety net, the same reason a shell script with set -e stops instead of plowing ahead after an error. Don't casually turn it off. Everything below is a controlled, deliberate way to say "I know this can fail, and here's exactly what I want to happen when it does."

Why the default matters

Imagine a play that installs a package, then configures it, then restarts a service. If the install task fails and Ansible kept going anyway, the configure task might run against software that isn't there, and the restart might bounce a service into a broken state. Stopping immediately is what keeps a partial failure from turning into a worse mess. Treat "stop on failure" as correct behavior to design around, not a bug to route around.

ignore_errors — continue past a failure

Sometimes you genuinely want to keep going even if a task fails — for example, a cleanup task that might fail if the thing it's cleaning up never existed. ignore_errors: true does exactly that, confirmed against Ansible's own docs:

- name: Do not count this as a failure
  ansible.builtin.command: /bin/false
  ignore_errors: true

The task still shows as failed in the output and in the play recap's ignored count, but Ansible moves on to the next task instead of stopping.

Use sparingly. ignore_errors: true can mask real problems — a task quietly failing every single run, forever, with nobody noticing because the play always reports "success." It also only works when the task actually executes and returns a failed status; it cannot suppress an undefined variable, a connection failure, a missing package the module depends on, or a syntax error. If you reach for ignore_errors, ask first whether failed_when (next section) would let you define the real success condition instead — that's usually the better fix.

failed_when and changed_when — redefine what counts

Ansible's default idea of "failed" is a non-zero return code, and its default idea of "changed" is module-specific. Sometimes that default is wrong for what you're running — a command-line tool that returns exit code 1 for "no results found" isn't necessarily broken, it just didn't find anything. failed_when and changed_when let you say precisely what failure and change mean for a task, using a condition checked against the task's own result.

failed_when — override when a task counts as failed:

- name: Fail task when either condition is met
  ansible.builtin.command: /usr/bin/example-command
  register: command_result
  failed_when: command_result.rc != 0 or 'ERROR' in command_result.stdout

You can also list multiple conditions — as a list, they're joined with an implicit AND (all must be true to count as failed):

- name: Check if a file exists in temp and fail task if it does
  ansible.builtin.command: ls /tmp/this_should_not_be_here
  register: result
  failed_when:
    - result.rc == 0
    - '"No such" not in result.stderr'

changed_when — override when a task counts as changed (which affects handler triggering and your play recap's changed count):

- name: Report 'changed' when the return code is not equal to 2
  ansible.builtin.shell: /usr/bin/billybass --mode="take me to the river"
  register: bass_result
  changed_when: "bass_result.rc != 2"

- name: This will never report 'changed' status
  ansible.builtin.shell: wall 'beep'
  changed_when: False

Both directives need register: in almost every real use — you're checking the result of the task you just ran, so you need a name to check it by. This is the same register you've used before to capture task output; here it feeds directly into the condition.

block / rescue / always — group, catch, and clean up

Everything so far handles one task at a time. block groups several tasks together and adds recovery logic around the whole group — confirmed against Ansible's own docs, and structurally similar in spirit to try / except / finally if you've seen exception handling in any general-purpose programming language:

  • block: — the tasks you actually want to run, in order. If any task in the block fails, the rest of the block is skipped (same "stop on failure" rule as a normal play, just scoped to this group).
  • rescue: — runs only if a task in the block failed. This is your recovery logic — the "except" clause. If nothing in the block fails, rescue is skipped entirely.
  • always: — runs no matter what happened in block or rescue — success, failure, or recovered failure. This is your "finally" clause, the place for cleanup that must happen either way.

Here's the full example from Ansible's docs, showing all three together:

tasks:
  - name: Attempt and graceful roll back demo
    block:
      - name: Print a message
        ansible.builtin.debug:
          msg: 'I execute normally'

      - name: Force a failure
        ansible.builtin.command: /bin/false

      - name: Never print this
        ansible.builtin.debug:
          msg: 'I never execute, due to the above task failing, :-('
    rescue:
      - name: Print when errors
        ansible.builtin.debug:
          msg: 'I caught an error'

      - name: Force a failure in middle of recovery! >:-)
        ansible.builtin.command: /bin/false

      - name: Never print this
        ansible.builtin.debug:
          msg: 'I also never execute :-('
    always:
      - name: Always do this
        ansible.builtin.debug:
          msg: "This always executes"

Walk through what happens: Print a message runs fine, then Force a failure fails, so Never print this (still inside block) is skipped. Because the block failed, Ansible jumps to rescue: Print when errors runs, and — notice this — the rescue section can fail too, so if its own task fails, the rest of rescue is skipped the same way the block was. Either way, always runs at the end no matter what happened above it.

Inside a rescue: section, Ansible gives you two special variables so recovery logic can react to exactly what went wrong, without you needing your own register:

  • ansible_failed_task — the task that triggered the rescue (for example, ansible_failed_task.name gives you its name).
  • ansible_failed_result — the failed task's captured result, the same shape you'd get from register.

Best practice: reach for block/rescue/always when a failure needs a real response — rolling back a change, notifying someone, cleaning up a partial state. Reach for failed_when when the problem is that Ansible's definition of "failed" doesn't match reality for this specific command. Reach for ignore_errors last, and rarely — it's the bluntest tool of the three, with no logic attached to what happens next.

Try it — before looking below

Q1. A block has three tasks. Task 2 fails. Does task 3 in the block run? Does the rescue section run?

No, task 3 does not run — the block stops at the first failure, same as a normal play. Yes, rescue runs, because the block as a whole failed. That's the entire point of pairing block with rescue: catch the failure and decide what to do next, instead of the play just dying.

Q2. You have a task calling a command-line tool that returns exit code 1 when it finds "no results" — which isn't really an error for your use case. Should you reach for ignore_errors or failed_when?

failed_when. The task isn't really failing — Ansible's default definition of failure (non-zero exit code) just doesn't match your situation. Redefine what "failed" means for this task, for example failed_when: result.rc not in [0, 1]. ignore_errors would hide a real failure too — it can't tell the difference between "exit code 1 meaning no results" and "exit code 1 meaning something actually broke."

Now try it yourself

Write a playbook with one play targeting localhost. Inside it, build a block/rescue/always group:

  • in block:, a task that will fail — reuse the docs' own trick, ansible.builtin.command: /bin/false
  • in rescue:, an ansible.builtin.debug task that prints a message about the failure, using ansible_failed_task.name
  • in always:, an ansible.builtin.debug task that prints something like "cleanup running regardless"

Run it, then read the output top to bottom: confirm the block task shows failed, the rescue task ran and printed the failed task's name, and the always task ran too. Then check the PLAY RECAP — look for the rescued count from Lesson 6's recap line; this is exactly what it's counting.

Try writing the YAML yourself before checking the reference below.

Reveal the reference playbook

- name: Block rescue always practice
  hosts: localhost
  tasks:
    - name: Attempt something risky
      block:
        - name: Force a failure
          ansible.builtin.command: /bin/false

      rescue:
        - name: Report what failed
          ansible.builtin.debug:
            msg: "Recovered from failure in task: {{ ansible_failed_task.name }}"

      always:
        - name: Cleanup runs no matter what
          ansible.builtin.debug:
            msg: "cleanup running regardless"

Recap
  • Default behavior: a failed task stops the play for that host. That's a safety net — work with it deliberately, don't disable it casually.
  • ignore_errors: true continues past a failure but can mask real problems — use it rarely, and prefer failed_when when the real issue is Ansible's definition of "failed" not matching your case.
  • failed_when / changed_when let you define exactly what counts as failure or change for a task, checked against its registered result.
  • block: groups tasks; rescue: catches a failure in the block and runs recovery logic (with ansible_failed_task / ansible_failed_result available); always: runs regardless — similar in shape to try/except/finally.
