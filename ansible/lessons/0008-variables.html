Variables

Every playbook you've written so far has hardcoded values straight into the tasks — a literal path, a literal message. That's fine for one host, but it breaks down the moment you want the same playbook to do slightly different things in different places: a different directory on dev vs. prod, a different package version this release vs. last. Variables are how you pull those changing values out of the task and give them a name — one place to change, everywhere it's used updates.

Mental model: a task without variables is a sentence with the details baked in — "create /tmp/ansible-practice." A task with variables is a sentence with a blank to fill in — "create {{ directory_name }}" — and you decide what fills the blank, per run, without touching the task itself.

Defining a variable at the play level

The simplest place to define a variable is right in the play, with vars:, confirmed against Ansible's own docs:

- hosts: webservers
  vars:
    http_port: 80

vars: sits at the same indentation level as hosts: and tasks: — it's a property of the play, not of any one task. As the docs state directly: "When you define variables in a play, they are visible only to tasks executed in that play." Every task in that play can read http_port; tasks in a different play in the same file can't, unless you define it there too.

Referencing a variable — Jinja2's {{ }}

To use a variable's value inside a task, wrap its name in double curly braces:

ansible.builtin.template:
  src: foo.cfg.j2
  dest: '{{ remote_install_path }}/foo.cfg'

That {{ }} syntax isn't Ansible's own invention — it's Jinja2, a templating language Ansible uses throughout: for variable substitution here, and later (Lesson 13) for much more — conditionals, loops, filters, and full template files. For now, just remember the shape: {{ variable_name }} anywhere a value is expected, and Ansible substitutes the real value at run time.

Watch the quotes: when a value starts with {{ }}, YAML can misparse it unless you quote the whole string — that's why the example above wraps '{{ remote_install_path }}/foo.cfg' in single quotes. If your value is only the variable with nothing else around it, quoting is usually optional, but quoting whenever {{ }} starts the value is a safe habit that avoids YAML parsing surprises.

Variable naming rules

Variable names aren't completely free-form. Straight from the docs:

  • A variable name can only include letters, numbers, and underscores.
  • A variable name cannot begin with a number.
  • Variable names can begin with an underscore.
  • You can't use a Python keyword (like async, lambda) or an Ansible playbook keyword (like environment) as a variable name.

In practice, the rule that trips people up most: no dashes. directory-name is invalid — YAML and Jinja2 will both read the dash as a minus sign. Use an underscore: directory_name. No spaces and no dots either — stick to letters, numbers, and underscores, and start with a letter or underscore, and you'll never hit this.

Overriding a variable from the command line

A default in vars: is just that — a default. You can override it for a single run without editing the playbook, using --extra-vars or its short form -e:

$ ansible-playbook release.yml --extra-vars "version=1.23.45 other_variable=foo"

That's the simple key=value form — space-separated pairs, all quoted together as one string. For anything more structured (numbers, lists, nested values), the docs show a JSON form instead:

$ ansible-playbook arcade.yml --extra-vars '{"pacman":"mrs","ghosts":["inky","pinky","clyde","sue"]}'

You'll reach for the key=value form constantly — it's how you parameterize a playbook run without keeping a dozen near-duplicate playbook files around. Extra-vars set on the command line win over a play's vars: — that's the one precedence fact you need for now. There's a full precedence order across every source Ansible can pull a variable from, but that's Lesson 22's job, not this one.

Where else variables come from (previews)

vars: in a play and -e on the command line are the two you'll use starting today. Two more sources exist, and you'll meet them properly later in this course — just enough now so the names aren't a surprise:

  • Inventory variables — instead of a play's vars:, a variable can live next to the inventory itself, per-host in host_vars/ or per-group in group_vars/. That's how you'd give every host in a group the same variable without repeating it in every playbook. Full treatment in Lesson 21.
  • Role defaults — once you start packaging tasks into reusable roles (Lesson 16), each role ships its own fallback values in roles/x/defaults/main.yml. They're the lowest-priority source — easy to override, which is exactly the point of a "default."

All of these — play vars:, -e, inventory variables, role defaults, and a few more — feed into a single, well-defined precedence order when the same variable name is set in more than one place. Lesson 22 covers that order in full. For now, the two you're using today are enough to make playbooks reusable.

Try it — before looking below

Q1. You write vars: { dir-name: /tmp/app } in your play. What's wrong, and what would you write instead?

The dash in dir-name is not allowed — variable names can only contain letters, numbers, and underscores. Write dir_name: /tmp/app instead.

Q2. Your play sets vars: { app_env: staging }. You run ansible-playbook -i inventory playbook.yml -e "app_env=production". Which value does the task actually see: staging or production?

production. Extra-vars passed with -e on the command line win over a play's vars: — that's why -e is the tool for one-off overrides without editing the playbook file.

Now write your own

Go back to the Lesson 6 playbook — the one that creates /tmp/ansible-practice with ansible.builtin.file. Parameterize the directory name with a variable, give it a default, and prove you can override that default from the command line.

Edit playbook.yml:

- name: My first playbook
  hosts: localhost
  vars:
    practice_dir: /tmp/ansible-practice

  tasks:
    - name: Print a message
      ansible.builtin.debug:
        msg: "Hello from my first playbook"

    - name: Create a practice directory
      ansible.builtin.file:
        path: '{{ practice_dir }}'
        state: directory

Then:

  • run it with no extra flags: ansible-playbook -i inventory playbook.yml — confirm it still creates /tmp/ansible-practice, using the default from vars:
  • now override it: ansible-playbook -i inventory playbook.yml -e "practice_dir=/tmp/ansible-override"
  • confirm the second run created a different directory: ls -ld /tmp/ansible-override
  • confirm the first directory is untouched — the override only affects the run you passed it to, the playbook file itself didn't change

Recap
  • Define a variable at the play level with vars:; reference it anywhere with Jinja2's {{ variable_name }}.
  • Variable names: only letters, numbers, underscores; can't start with a number; no dashes, spaces, or dots.
  • Override any variable for one run with -e/--extra-vars "name=value" — it beats a play's vars: default.
  • Variables can also come from inventory (host_vars/group_vars, Lesson 21) and role defaults (Lesson 16) — the full precedence order across every source is Lesson 22.
