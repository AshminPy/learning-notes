group_vars & host_vars

Lesson 8 gave you vars: inside a play, and Lesson 20 gave you an inventory that can group hosts by environment or role. Put those two together and a problem shows up fast: if dev and prod need different values for the same variable, you either write two playbooks or stuff a pile of conditional vars: logic into one. Neither scales. group_vars and host_vars solve this a different way — variables that live next to your inventory, not inside your playbook, and get loaded automatically for the hosts they apply to.

Mental model: a play's vars: is a note taped to one specific recipe — it only means something while that recipe is open. group_vars/host_vars is a label taped to the ingredient itself — the host or group — so any playbook that touches that host or group automatically sees the right values, with nothing written in the playbook at all.

The directory convention

Confirmed against Ansible's own inventory guide: create two directories, group_vars/ and host_vars/, sitting alongside your inventory file (or alongside the playbook, if you're not using a separate inventory directory). Inside each, one file per group or per host, named after that group or host:

inventory/
  hosts.ini
  group_vars/
    webservers.yml
    dbservers.yml
  host_vars/
    web1.example.com.yml

If hosts.ini defines a host web1.example.com that belongs to the webservers group, Ansible automatically loads variables from group_vars/webservers.yml for every host in that group, and from host_vars/web1.example.com.yml for that one host specifically — no vars_files: line, no include_vars task, nothing referencing these files anywhere in your playbook. Ansible finds them itself, by matching the filename to a group name or host name from your inventory. Valid file extensions are .yml, .yaml, .json, or no extension at all; this course uses .yml throughout for consistency with everything else you've written.

The docs also allow a directory instead of a single file — group_vars/webservers/db_settings.yml and group_vars/webservers/cluster_settings.yml both get loaded, read in lexicographical order, for the same group. That's a Lesson-16-style organization trick for when one group's variables grow too large for one file — you won't need it yet, but recognize the pattern if you see it in someone else's repo.

The special file: group_vars/all.yml

One group name is reserved: all. A file at group_vars/all.yml applies to every host in your inventory, regardless of which other groups they belong to — it's the place for values that are truly global, like an organization-wide NTP server or a default SSH port. Anything more specific than "every single host" belongs in a named group's file instead, where it'll only apply to hosts that actually need it.

Why this beats inline vars: for this job

Nothing stops you from writing per-environment logic inside a play with conditionals, but it's the wrong tool. group_vars/host_vars keeps the data (what value does this environment need) separate from the logic (what should the playbook do) — the same playbook runs unmodified against dev or prod, and the file that changes when you add a new environment is a small variables file, not the playbook itself. It also means the variable definitions live in one predictable place instead of scattered across every play that happens to need them.

Practical example — a different app_port per environment

Say your inventory groups hosts by environment:

[dev]
dev1.example.com

[prod]
prod1.example.com
prod2.example.com

Give each group its own port with two small files:

# group_vars/dev.yml
app_port: 8080
# group_vars/prod.yml
app_port: 443

Now one playbook — no vars:, no conditionals, no per-environment copy — references {{ app_port }}:

- name: Configure the app
  hosts: all
  tasks:
    - name: Show the port this host will use
      ansible.builtin.debug:
        msg: "Listening on port {{ app_port }}"

Run it against dev and you'll see 8080; run the exact same file against prod and you'll see 443 — because Ansible resolved app_port from the group each targeted host actually belongs to, before the play even started. That's the payoff: one playbook, correct behavior everywhere, and the only thing that differs between environments lives in two three-line files.

Try it — before looking below

Q1. You have group_vars/webservers.yml setting app_port: 8080 and host_vars/web1.example.com.yml setting app_port: 9090. web1.example.com is in the webservers group. Which value does a playbook running against web1.example.com see?

9090. This is a preview of Lesson 22's full precedence order, but the mental model you can use right now: the more specific a variable's source is to one exact host, the more it wins. A host's own host_vars file is more specific than a group's group_vars file, so it takes priority.

Q2. You need a variable that should apply to literally every host in your inventory, no exceptions. Which file do you create?

group_vars/all.yml — the reserved group name all matches every host, regardless of what other groups they're in.

Now write your own

Build a small inventory with a webservers group, give that group a variable through group_vars, and prove a playbook picks it up with zero vars: block.

Create the folder layout:

mkdir -p group_vars

inventory:

[webservers]
localhost ansible_connection=local

group_vars/webservers.yml:

welcome_message: "Hello from the webservers group"

playbook.yml — notice there is no vars: block anywhere in this file:

- name: Prove group_vars loads automatically
  hosts: webservers
  tasks:
    - name: Print the group variable
      ansible.builtin.debug:
        msg: "{{ welcome_message }}"

Then:

  • run ansible-playbook -i inventory playbook.yml
  • confirm the TASK [Print the group variable] output shows your message — even though playbook.yml never mentions welcome_message being set
  • edit the value in group_vars/webservers.yml and run the playbook again — confirm the new value shows up, with the playbook file completely untouched

Try it yourself before checking the reference commands below.

Reveal the reference commands

mkdir -p group_vars
# create inventory, group_vars/webservers.yml, playbook.yml as shown above
ansible-playbook -i inventory playbook.yml
# edit group_vars/webservers.yml, change welcome_message, then:
ansible-playbook -i inventory playbook.yml

Recap
  • group_vars/<groupname>.yml and host_vars/<hostname>.yml, sitting alongside your inventory, are loaded automatically for matching hosts — no vars_files:, no include_vars, nothing referenced in the playbook.
  • group_vars/all.yml is the reserved file that applies to every host in the inventory.
  • This is the cleaner alternative to Lesson 8's inline vars: for anything environment- or host-specific — the same playbook behaves differently per group (e.g. app_port 8080 in dev, 443 in prod) with zero conditionals.
  • A host's own host_vars beats its group's group_vars when both set the same variable — the full precedence order across every source is Lesson 22.
