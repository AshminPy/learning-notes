Ansible Lint

Since Lesson 6 you've been checking your playbooks with ansible-playbook --syntax-check before running them. That command only answers one question: is this valid YAML that Ansible can parse into tasks? It says nothing about whether the playbook is good Ansible — whether it's actually idempotent, whether it uses syntax Ansible is about to remove, or whether you just committed a plaintext password to your repo. A playbook can pass --syntax-check cleanly and still be full of real problems. ansible-lint is the tool that catches those.

Mental model: Think of --syntax-check as a spell-checker — it confirms the words are real words. ansible-lint is closer to a style and correctness reviewer — it reads content that's already spelled correctly and flags patterns known to cause bugs, security exposure, or maintenance pain, based on rules the Ansible community has learned the hard way. It doesn't run your playbook against any host; it only reads the files.

What plain syntax-checking misses

Take this task. It's completely valid YAML, and ansible-playbook --syntax-check passes it without a single complaint:

- name: clean up an old config file
  command: rm -f /etc/myapp/old.conf

- name: make sure the app package is current
  ansible.builtin.package:
    name: myapp
    state: latest

- name: store the db password for later tasks
  set_fact:
    db_password: "S3cretPass!"

All three tasks are quietly broken in ways syntax-checking can't see:

  • The command task always reports changed: true, every single run, whether or not the file existed — that's not idempotent reporting (Lesson 7), and it will fire any handler notified by this task on every run, forever.
  • state: latest means every run can silently pull in a new package version — the opposite of the repeatable, predictable behaviour you want from a playbook.
  • db_password is now sitting in plaintext, and if this task's output is ever logged (a CI log, a verbose run someone pastes into a ticket), the secret leaks in plain text.

ansible-lint catches all three, by name: no-changed-when, package-latest, and no-log-password.

Installing it

Confirmed against ansible-lint's own docs — it installs alongside ansible-core automatically:

# Plain install
$ pip3 install ansible-lint

# Isolated install (recommended if you don't want it in your project's venv)
$ pipx install ansible-lint

# Fedora / RHEL
$ dnf install ansible-lint

Verify it landed correctly:

$ ansible-lint --version

Running it and reading the output

Point it at a playbook or a whole role/project directory:

$ ansible-lint site.yml

Each finding names the rule, the file and line, and a short explanation — for example, running it against the three tasks above would report something in this shape:

site.yml:2: no-changed-when Commands should not change things if nothing needs doing
site.yml:6: package-latest Package installs should not use latest
site.yml:10: no-log-password Password should not be logged

Each rule name is exactly what you'd search for in the rule docs or grep in your CI logs — that's deliberate, so a failure is always traceable back to a specific, documented rule.

The rule categories

Confirmed against ansible-lint's current rule reference — over 55 rules, grouped roughly like this:

CategoryExample rulesCatches
Idempotency / stateno-changed-when, package-latestTasks that misreport change, or drift on every run
Deprecationsdeprecated-module, deprecated-bare-varsSyntax and modules a future Ansible release will remove
Securityno-log-password, risky-file-permissionsSecrets that could leak into logs, files created world-writable
Best practicefqcn, literal-compare, command-instead-of-moduleStyle/maintainability issues — e.g. using command: git ... instead of the git module

Common mistake: treating ansible-playbook --syntax-check as "the linter." It isn't — it's a parser check. A playbook with terrible idempotency, deprecated modules, and a hardcoded secret can sail through --syntax-check with zero complaints. They're two different tools answering two different questions: "is this parseable?" vs. "is this good?"

Security note: no-log-password and similar rules exist because plaintext secrets in task output aren't hypothetical — CI logs get archived, verbose playbook runs get pasted into tickets and Slack, and neither of those is a secure place for a password to live. If a variable genuinely holds a secret, mark the task no_log: true and, per Lesson 26, keep the value itself in an Ansible Vault-encrypted file, not a plain set_fact.

Production note: ansible-lint is normally wired in at two points, not one: a pre-commit hook (so a violation never even gets committed locally) and a CI pipeline gate (so it's enforced centrally, even if someone skips the local hook). A minimal .pre-commit-config.yaml entry:

repos:
  - repo: https://github.com/ansible/ansible-lint
    rev: v25.1.0
    hooks:
      - id: ansible-lint

Try it — before looking below

Q1. You run ansible-playbook --syntax-check site.yml and it passes with no errors. Does that mean the playbook follows Ansible best practices?

No. --syntax-check only confirms the file is valid YAML that Ansible can parse into tasks — it says nothing about idempotency, deprecated syntax, or security issues like plaintext secrets. A playbook can pass syntax-check cleanly and still fail ansible-lint on multiple real problems.

Q2. A task uses command: rm -f /tmp/old_config with no changed_when set. What does ansible-lint flag here, and why does it matter?

The no-changed-when rule. command/shell tasks always report changed: true regardless of whether they actually changed anything, which breaks idempotent reporting and can trigger handlers unnecessarily on every run. Fix it with an explicit changed_when (often changed_when: false for a task that never meaningfully changes state).

Q3. Where should ansible-lint run so a violating playbook never reaches production? Name two real integration points.

A pre-commit hook (blocks the problem locally, before it's even committed) and a CI pipeline gate (enforces it centrally, so a skipped local hook doesn't let something through). Using both means a violation has to slip past two independent checks, not one.

Now write your own

In a practice folder, create site.yml with the three deliberately-broken tasks from earlier in this lesson (target hosts: localhost so you don't need any real inventory):

---
- hosts: localhost
  connection: local
  tasks:
    - name: clean up an old config file
      command: rm -f /tmp/old.conf

    - name: make sure the app package is current
      ansible.builtin.package:
        name: myapp
        state: latest

    - name: store the db password for later tasks
      set_fact:
        db_password: "S3cretPass!"

Then:

  • run ansible-playbook --syntax-check site.yml — confirm it passes clean
  • run ansible-lint site.yml — read every finding, and match each one back to the explanation earlier in this lesson
  • fix all three: add changed_when: false to the command task (it never actually changes anything meaningful here), change state: latest to a pinned state: present, and add no_log: true to the set_fact task
  • run ansible-lint site.yml again and confirm those three findings are gone

Try it yourself before checking the reference fix below.

Reveal the fixed playbook

---
- hosts: localhost
  connection: local
  tasks:
    - name: clean up an old config file
      command: rm -f /tmp/old.conf
      changed_when: false

    - name: make sure the app package is current
      ansible.builtin.package:
        name: myapp
        state: present

    - name: store the db password for later tasks
      set_fact:
        db_password: "S3cretPass!"
      no_log: true

Recap
  • ansible-playbook --syntax-check only confirms valid, parseable YAML — it catches nothing about idempotency, deprecated syntax, best practices, or security.
  • ansible-lint reads your playbooks/roles/collections and flags real problems by rule name: idempotency issues (no-changed-when), version drift (package-latest), deprecated syntax, security exposure (no-log-password, risky-file-permissions), and style/best-practice violations (fqcn, command-instead-of-module).
  • Install with pip3 install ansible-lint (or pipx); run with ansible-lint <path>.
  • Wire it in at two points: a pre-commit hook (catch it locally) and a CI gate (enforce it centrally) — not just one.
