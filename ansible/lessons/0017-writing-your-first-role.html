Writing your first role

Lesson 16 walked through the anatomy of a role — the fixed set of folders Ansible expects (tasks/, handlers/, templates/, defaults/, and the rest) and why that shape is what makes a role reusable across playbooks and projects. Anatomy on paper only gets you so far. This lesson builds a real one: a small role that renders a message into a file, using a default variable and a handler, exactly the pieces you already know from Lessons 8, 12, and 13–14 — just organized the role way instead of loose in one playbook file.

Mental model: a role is a playbook's tasks:, handlers:, and default vars: pulled out into their own folder with a fixed shape, so any playbook can pull the whole bundle in with one line instead of copy-pasting the tasks every time. You don't write less YAML the first time — you write it once and stop repeating it.

Scaffold the role with ansible-galaxy role init

Don't hand-create the role folders — ansible-galaxy ships a generator that builds the whole skeleton for you, confirmed against Ansible's own docs: "Use the init command to initialize the base structure of a new role, saving time on creating the various directories and main.yml files a role requires."

Roles live in a roles/ directory next to your playbook by default, so create that first, then run init from inside it:

$ mkdir roles
$ cd roles
$ ansible-galaxy role init greeting_file
$ cd ..

greeting_file is the role's name — letters, numbers, and underscores only, same rule as a variable name (Lesson 8). Avoid dashes in role names for the same reason you avoid them in variable names.

What ansible-galaxy just built for you

Confirmed against the docs, init creates this exact structure under roles/greeting_file/:

greeting_file/
    README.md
    defaults/
        main.yml
    files/
    handlers/
        main.yml
    meta/
        main.yml
    tasks/
        main.yml
    templates/
    tests/
        inventory
        test.yml
    vars/
        main.yml

You met most of these names already, just not as folders:

  • defaults/main.yml — default variables, the lowest-priority source in Ansible's variable precedence (Lesson 8 previewed this — full precedence order is Lesson 22). This is where a role's "fallback" values live.
  • tasks/main.yml — the task list, same shape as a playbook's tasks: section, just without the hosts: and tasks: wrapper — the file itself is the list.
  • handlers/main.yml — handlers, same notify:-by-name mechanism as Lesson 12, scoped to this role.
  • templates/ — an empty folder for Jinja2 .j2 files, the same templating you used in Lesson 13–14, now living next to the role that uses them instead of some arbitrary path.
  • vars/main.yml, meta/main.yml, files/, tests/ — higher-precedence variables, role metadata/dependencies, static files to copy, and a starter test playbook. You won't touch these today; leave them as generated.

Nothing forces you to fill in every folder. As the docs put it: "You must include at least one of these directories in each role. You can omit any directories the role does not use." For this lesson you'll fill in four: defaults/, templates/, tasks/, and handlers/.

Fill in defaults/main.yml — the variable with a fallback

Open roles/greeting_file/defaults/main.yml and replace its contents:

---
greeting_message: "Hello from your first Ansible role!"
greeting_dest: /tmp/ansible-greeting.txt

Two ordinary variables, defined exactly like Lesson 8's vars: — the only difference is where they live. Because they're in a role's defaults/, anyone calling this role gets a sensible message and destination for free, and can override either one without touching the role's files at all.

Fill in templates/greeting.txt.j2 — the Jinja2 template

Create roles/greeting_file/templates/greeting.txt.j2:

{{ greeting_message }}

Rendered by the greeting_file role.

Same {{ }} Jinja2 syntax from Lesson 8 and Lesson 13–14 — greeting_message resolves to whatever value wins for this run: the role's default, or an override, following the precedence rules you already know the shape of.

Fill in tasks/main.yml — render the template

Open roles/greeting_file/tasks/main.yml:

---
- name: Render the greeting file from the template
  ansible.builtin.template:
    src: greeting.txt.j2
    dest: "{{ greeting_dest }}"
  notify:
    - Report the greeting file changed

Notice src: greeting.txt.j2 has no path in front of it — inside a role, ansible.builtin.template automatically looks in that role's own templates/ folder. That's the payoff of the fixed folder shape: no path-juggling, the module already knows where to look.

Fill in handlers/main.yml — confirm on change

Open roles/greeting_file/handlers/main.yml:

---
- name: Report the greeting file changed
  ansible.builtin.debug:
    msg: "Greeting file at {{ greeting_dest }} was created or updated."

Same notify: / handler-name matching rule as Lesson 12: this only fires when the template task actually reports changed — first run, or a run where the message was overridden to something new. A run where nothing changed stays silent, same as always.

Call the role from a playbook

Everything above lives inside the role. To actually run it, write a normal playbook next to the roles/ folder — site.yml:

---
- name: Use the greeting_file role
  hosts: localhost
  roles:
    - greeting_file

That's the whole playbook. roles: is a play-level keyword, a sibling of hosts: and tasks: — confirmed against the docs' own example (hosts: webservers / roles: [common, webservers]). Listing greeting_file there pulls in its tasks/main.yml, makes its defaults/ available, and wires up its handlers/ — all in one line, and Ansible finds the role automatically because it's sitting in roles/ next to the playbook.

The task-level alternative — import_role and include_role: roles: runs the role's tasks before anything in that play's own tasks: section. If you need a role's tasks to run in the middle of, or after, other tasks in the same play, call it as a task instead:

tasks:
  - name: Import the greeting_file role
    ansible.builtin.import_role:
      name: greeting_file

Confirmed against the docs: "the behavior is the same as using the roles keyword" for import_role — it's a static, pre-processed alternative. ansible.builtin.include_role looks identical but is dynamic: "included roles run in the order they are defined" at the point Ansible reaches them during the run, rather than being resolved upfront. For a straightforward role at the top of a play — like this lesson's example — plain roles: is still the standard, most-used form; reach for import_role / include_role once you need that finer control over ordering.

Try it — before looking below

Q1. You call greeting_file with plain roles: and never set greeting_message anywhere else. What message ends up in the rendered file?

The default from roles/greeting_file/defaults/main.yml — "Hello from your first Ansible role!" Role defaults are the fallback that's always there if nothing overrides them.

Q2. You run the playbook a second time with no changes at all. Does the "Report the greeting file changed" handler run?

No. The template task reports ok because the file's content already matches — same idempotency rule as every earlier lesson — so it never notifies the handler, and the handler doesn't fire.

Now write your own

Build this exact role and playbook, in a fresh practice folder:

  • Create the folder, then roles/ inside it, then scaffold: cd roles && ansible-galaxy role init greeting_file && cd ..
  • Fill in defaults/main.yml, templates/greeting.txt.j2, tasks/main.yml, and handlers/main.yml exactly as shown above.
  • Reuse the localhost inventory file from earlier lessons in this project's root folder (next to roles/).
  • Write site.yml in that same root folder, calling the role with roles:.
  • Run ansible-playbook -i inventory site.yml — find the TASK [Render the greeting file from the template] section, expect changed on this first run.
  • Find the RUNNING HANDLER [greeting_file : Report the greeting file changed] section and confirm the debug message printed. (Notice the handler name in the banner is prefixed with the role name — that's Ansible telling you which role it came from.)
  • Confirm the file's contents: cat /tmp/ansible-greeting.txt
  • Run the exact same command again. Confirm the template task now shows ok, and the RUNNING HANDLER section is gone entirely.
  • Now override the default without editing any role file: ansible-playbook -i inventory site.yml -e "greeting_message='Overridden from the command line'"
  • Check the file again — confirm the new message is there, and confirm the handler fired this time, since the template's content genuinely changed.

Recap
  • Scaffold a role with ansible-galaxy role init role_name, run from inside a roles/ folder next to your playbook — it builds the full folder structure for you.
  • Fill in only the folders you need: defaults/main.yml for fallback variables, templates/ for Jinja2 files, tasks/main.yml for the task list, handlers/main.yml for notify targets — everything you already knew from Lessons 8, 12, and 13–14, just organized the role way.
  • Call a role with the play-level roles: keyword for the standard case; use ansible.builtin.import_role (static, same behavior as roles:) or ansible.builtin.include_role (dynamic, runs where it's placed) at the task level when you need a role's tasks to run somewhere other than "before everything else in the play."
