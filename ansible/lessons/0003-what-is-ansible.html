What is Ansible? Agentless, push, idempotent

You've got Ansible installed from Lesson 2. Before you run a single command, you need the mental model underneath it — what Ansible actually is, and what makes it different from the other tool people constantly confuse it with: Terraform. Three words do most of the work: agentless, push-based, and idempotent. This lesson unpacks each one.

Ansible, defined

Ansible is a configuration management and automation tool. Its own getting-started docs put it simply: "Ansible automates the management of remote systems and controls their desired state." In practice that means: installing packages, editing config files, starting and stopping services, creating users, applying security patches — the day-to-day work of keeping a fleet of already-running machines in the state you want, written as a repeatable script called a playbook instead of done by hand over SSH.

Agentless — no software to install on the target

Some configuration management tools (Puppet and Chef, for example) work by installing a permanent background program — an agent — on every machine they manage. That agent has to be installed, kept updated, and kept running on every single target host, forever.

Ansible doesn't do this. The official docs are direct about it: "Ansible is agentless, it can still communicate with devices without requiring an application or service to be installed on the managed node." Red Hat's own explainer describes the mechanics: "Ansible connects to managed nodes and pushes out small programs — called Ansible modules — to them," then "executes these modules (over SSH by default), and removes them when finished."

Mental model: Ansible doesn't move in — it visits. It connects over plain SSH (using credentials you already have), drops off a small program, runs it, cleans up after itself, and disconnects. Nothing is left behind, running, or waiting on the target machine. That's why a brand-new server with nothing installed but SSH access is already a fully manageable Ansible target.

Push-based — you trigger the run

Because there's no resident agent, there's also nothing on the target machine periodically checking in on its own. You — from your control node (your laptop, or a CI runner) — decide when a playbook runs, and Ansible pushes the changes out to every target in that run, right then.

Contrast that with a pull-based model: an agent installed on the managed machine wakes up on its own schedule, contacts a central server, and pulls down whatever configuration it should apply. Puppet and Chef are classic examples of this pattern — an agent on each node polls a master server at an interval and pulls its configuration down.

Push (Ansible)Pull (agent-based tools)
You run the command, right now, from the control nodeAn agent on the target wakes up on its own schedule
Nothing installed or running on the target between runsAn agent process runs permanently on every target
You control exactly when and to which hosts a change goes outDrift correction happens automatically, even if no one triggers it

Neither model is universally "better" — push gives you tight, deliberate control over timing; pull gives you continuous self-healing without anyone needing to remember to run anything. Ansible chose push, and that choice is why the SSH-only, agentless model works: someone has to initiate the connection, and with Ansible, that someone is you.

Idempotent by design (preview)

The third word — idempotent — means running the same playbook twice should land you in the same end state, not double-apply the same changes. The official docs describe it this way: "When the system is in the state your playbook describes, Ansible does not change anything, even if the playbook runs multiple times." Or, more precisely at the module level: "These modules are designed to be idempotent when possible, so that they only make changes to a system when necessary."

Quick preview, not the full picture: if a playbook says "nginx should be installed" and nginx is already installed, running that playbook again does nothing — Ansible checks first, sees the target state already matches, and skips the step. If you ran a raw bash script with apt install nginx twice, the second run would either error or waste time reinstalling. Idempotency is why it's safe to re-run playbooks constantly, and it gets a full dedicated lesson later (Lesson 7) once you've written your first playbook and can see it in action. For now, just hold onto the word.

Where Ansible fits next to Terraform

If you've taken this site's Terraform course, you've already met this split from the other side — Terraform's own Lesson 3 says it plainly: "Terraform provisions infrastructure; tools like Ansible configure what's already running." Here it is again, from Ansible's side of the fence:

  • Terraform provisions — it creates the VM, the network, the disk, the load balancer. Before Terraform runs, that infrastructure doesn't exist. After, it does.
  • Ansible configures — it takes a machine that already exists (whether Terraform created it, or it's been sitting in a data center for years) and installs packages, writes config files, and starts services on it.

Mental model, matching the Terraform course: Terraform builds the kitchen — the walls, the plumbing, the outlets. Ansible stocks the fridge and turns on the stove. You need the kitchen to exist before you can stock it, which is exactly why many real teams run both, in order — Terraform first to provision the servers, then Ansible to configure what's now running on them.

They are not competitors, even though newcomers often ask "should I use Terraform or Ansible?" as if it's one-or-the-other. The honest answer is usually "both, for different jobs." (This site's Terraform course covers the provisioning side in depth — see Terraform Lesson 3: What is Infrastructure as Code? if you want the mirror image of this lesson.)

Try it — before looking below

Q1. "Create a new EC2 instance in AWS with a specific instance type and security group." Is this a provisioning task or a configuration task?

Provisioning — the instance doesn't exist yet. This is Terraform's job, not Ansible's.

Q2. "Install nginx and start the service on a server that's already running." Provisioning or configuration?

Configuration — the server already exists; this is about changing software on it. This is Ansible's job.

Q3. True or false: to manage a server with Ansible, you must first install an Ansible agent on that server.

False — Ansible is agentless. It connects over SSH and pushes out modules that run and then remove themselves. Nothing persistent gets installed on the managed node.

Q4. You run the same playbook twice in a row against a server that's already correctly configured. What should happen the second time?

Nothing changes — Ansible checks the current state, sees it already matches the desired state, and skips the step. That's idempotency (full lesson coming in Lesson 7).

Recap
  • Ansible is a configuration management/automation tool — it manages already-running machines, written as playbooks.
  • Agentless: no software to pre-install on managed hosts; it connects over SSH, pushes a module, runs it, removes it.
  • Push-based: you trigger the run from your control node — contrast with pull-based tools where an agent on the target checks in on its own schedule.
  • Idempotent by design: running the same playbook twice shouldn't double-apply changes — a full lesson (Lesson 7) is coming on this.
  • Terraform provisions infrastructure (creates it); Ansible configures what's already running (installs, edits, starts services). Many teams use both, Terraform first.
If agentless/push/idempotent still feel like just words, that's fine — you'll feel push in action the moment you run your first playbook, and idempotency will click when you run that same playbook a second time and watch nothing happen.
