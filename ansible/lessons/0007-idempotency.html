Idempotency

Stop here for a second. Of the 36 lessons in this course, this is the single most important one. Not because the syntax is hard — there's barely any new syntax at all — but because idempotency is the idea that everything else in Ansible is built on top of. If this mental model doesn't click, every lesson after this one will feel like memorizing module options instead of understanding a system. If it does click, the rest of the course is just filling in details.

At the end of Lesson 6 you ran the same playbook twice and watched the changed count on the directory task drop to zero the second time. That wasn't a coincidence or a lucky module — that was idempotency, and this lesson is about exactly why it happened and why it matters.

The precise definition

Ansible's own glossary defines it plainly: an operation is idempotent if the result of performing it once is exactly the same as the result of performing it repeatedly, without any intervening actions.

Translated into playbook terms: run the same playbook against the same host twice, back to back, and you should get two things —

  • the host ends up in the same end state both times
  • the second run reports no changes at all

Notice what idempotency is not. It's not "the playbook doesn't error the second time." A command that silently does nothing useful on rerun but also doesn't crash is not what we mean. It's not "roughly the same state" either — it's the exact same state, verified every single run, by a module that actually checks before it acts.

Mental model: you already met this pattern if you've done the Terraform course on this site. Terraform describes desired infrastructure state and reconciles reality toward it — apply twice with no changes in between, and the second plan shows zero changes. Ansible does the same thing, one level down the stack, for configuration on a host: desired state described in YAML, reconciled by modules that check reality before acting. Different tool, same declarative idea: say what you want, not the steps to get there, and let the tool figure out whether it needs to do anything at all.

Why this matters in practice

Idempotency isn't a nice theoretical property — it's what makes a playbook safe to use in ways a plain shell script never is:

  • Safe to re-run anytime. Playbook run failed halfway through because of a network blip? Just run it again. You don't need to figure out which tasks already succeeded — the ones already done will report ok and change nothing, and only the ones still needed will actually act.
  • Safe to schedule. A cron job or CI pipeline can run the same playbook every night, or every few minutes, without slowly making a mess of the host. If nothing has drifted, nothing changes.
  • Safe to run against a host that already has some config applied. You don't need a "clean" host to point a playbook at. Idempotent tasks check current state first — a host that's already 80% configured the way you want just shows mostly ok with a few changed for the missing 20%.

Put together, this is why Ansible playbooks describe desired state rather than a sequence of one-time setup steps. You're not writing "install this, then edit that, then restart this service" as a script that only makes sense run once from a blank slate. You're writing "this package should be present, this file should look like this, this service should be running" — a description that's true or not true regardless of how many times you check it.

ok vs changed — now it means something

Lesson 6 introduced these two PLAY RECAP counters without explaining the "why." Now you have it:

  • ok — the task checked the host, found it already matched the desired state, and took no action.
  • changed — the task checked the host, found it did not match the desired state, and made a change to fix that.

This is idempotency made visible, task by task, every single run. A well-written, fully idempotent playbook run against an already-configured host should show changed=0 in the PLAY RECAP. If you expect a host to be untouched and you see a nonzero changed count, that's a signal worth investigating — either the host had drifted, or a task in your playbook isn't as idempotent as you assumed.

Best practice: treat an unexpected changed count the same way you'd treat an unexpected line in a Terraform plan — stop and read which task changed before you shrug it off. Idempotency is what lets you trust that number; don't throw that trust away by ignoring it.

The gotcha: command and shell are not automatically idempotent

Here's the part that catches almost everyone. Lesson 5 told you to prefer dedicated modules (package, service, file, and friends) over ansible.builtin.command or ansible.builtin.shell whenever one exists. This lesson is why.

Proper Ansible modules are idempotent by design. ansible.builtin.file with state: directory checks whether the directory already exists before creating it — that's built into the module's logic, you get it for free. ansible.builtin.package checks whether the package is already installed at the right version. ansible.builtin.service checks whether the service is already in the state you asked for. You didn't write any of that checking logic — the module author did, once, and every user of the module benefits.

command and shell have none of that. They just run whatever you told them to run, every single time, with no built-in awareness of "did I already do this?" Ansible's own documentation confirms this directly: the command module offers creates and removes parameters specifically because, without them, the module has no idea whether its job is already done — you have to tell it what file to check for.

Concretely: a task like this will fail the second time you run it, because mkdir itself errors if the directory already exists, and nothing about the shell module stops it from trying:

- name: Make a directory (NOT idempotent)
  ansible.builtin.shell: mkdir /tmp/foo

Compare that to the module version, which is idempotent with zero extra effort:

- name: Make a directory (idempotent)
  ansible.builtin.file:
    path: /tmp/foo
    state: directory

Same end goal, but only one of these is safe to run twice. This is the concrete reason Lesson 5's advice — "reach for a dedicated module before shell" — is a rule about idempotency, not just style. If you must use command or shell because no dedicated module exists for what you need, you're now responsible for the idempotency check yourself, usually with creates/removes, or a conditional based on checking current state first. Nobody hands you that for free the way ansible.builtin.file does.

Try it — before looking below

Q1. You run a playbook against a fresh host for the first time. Every task reports changed. You run the exact same playbook again immediately after, with nothing else touching the host in between. What should the PLAY RECAP show this time, if every task uses proper Ansible modules?

changed=0 for that host, with the same ok count as the total number of tasks. The host is already in the desired state from the first run, so every task checks, finds nothing to do, and reports ok instead of changed. If you see any nonzero changed on the second run, either something on the host drifted between runs, or a task isn't truly idempotent.

Q2. A teammate writes ansible.builtin.shell: mkdir /var/log/myapp in a playbook with no creates parameter. What happens the second time this playbook runs against a host that already has that directory?

The task fails — mkdir errors out because the directory already exists, and the shell module has no built-in awareness that the job was already done, so it just re-runs the raw command. This is exactly the gotcha this lesson covers: shell/command are not idempotent by default. The fix is either switch to ansible.builtin.file with state: directory (idempotent by design), or add creates: /var/log/myapp to the shell task so it skips when the directory already exists.

Now try it yourself

Reuse the playbook.yml from Lesson 6 — the one with the debug task and the file task creating /tmp/ansible-practice.

  • Run it: ansible-playbook -i inventory playbook.yml. Note the PLAY RECAP — on a fresh host, the directory task should show changed.
  • Run the exact same command again, immediately: ansible-playbook -i inventory playbook.yml. Check the PLAY RECAP again — the directory task should now be ok, and the line should read changed=0. That's idempotency, observed directly.
  • Now add a third task at the end of the tasks: list to see the contrast:
    - name: Make a directory the non-idempotent way
      ansible.builtin.shell: mkdir /tmp/ansible-shell-test
  • Run the playbook once — it succeeds, changed on that task.
  • Run it again, immediately — this task should now fail, because mkdir refuses to create a directory that already exists, and shell did nothing to check for you first.
  • Fix it by adding a guard: creates: /tmp/ansible-shell-test under the same shell: line. Run it a third time — it should now report ok instead of failing, because you gave Ansible a way to check whether the job was already done.
  • Clean up when you're done: rm -rf /tmp/ansible-practice /tmp/ansible-shell-test.

Recap
  • Idempotency: running the same playbook against the same host twice gives the same end state, and the second run reports no changes. This is the core idea the whole course builds on — the same declarative spirit as Terraform's desired-state model, applied to configuration instead of infrastructure.
  • In the PLAY RECAP: ok means the task checked and found nothing to do; changed means the task had to act to reach desired state. A fully idempotent playbook re-run should show changed=0.
  • Proper modules (package, service, file, ...) are idempotent by design. command/shell are NOT — they just re-run the raw command every time, and can even fail on rerun (like mkdir on an existing directory) unless you add a guard like creates:. This is exactly why Lesson 5 said to prefer dedicated modules over shell.
