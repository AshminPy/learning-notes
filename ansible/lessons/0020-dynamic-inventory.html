Dynamic inventory

Lesson 4 gave you the mental model for inventory: a list of hosts, hand-organized into groups, that you write and edit yourself. That works great for a handful of servers that don't change much. It falls apart the moment your infrastructure starts changing on its own — autoscaling groups, ephemeral cloud instances, containers that come and go by the hour. This lesson opens the "Inventory & Variables at Scale" phase of the course by showing you the fix: dynamic inventory, where Ansible asks a real source for the current list of hosts instead of you maintaining a file by hand.

Mental model: a static inventory is a photograph of your infrastructure at the moment you wrote the file. A dynamic inventory is a live camera feed — Ansible asks the actual source of truth (a cloud provider's API, a CMDB) "who exists right now?" every time it runs.

Why static inventory breaks down at scale

Picture a team running an autoscaling group of web servers on AWS. Traffic goes up at 9am, the group scales from 3 instances to 12; traffic drops overnight, it scales back down to 2. Every one of those scaling events creates or destroys a real EC2 instance with its own IP address. If your inventory is a static [webservers] block you edit by hand, you now have a full-time job: log in, find the new IPs, add them to the file, remove the ones that got terminated, commit, repeat — forever, and often faster than a human can keep up.

The official Ansible docs describe exactly this failure mode: "If your Ansible inventory fluctuates over time, with hosts spinning up and shutting down in response to business demands, the static inventory solutions described in How to build your inventory will not serve your needs." Static inventory isn't wrong — it's just built for infrastructure that mostly sits still. Autoscaling groups, spot instances, and Kubernetes-managed workloads don't sit still.

What dynamic inventory actually is

A dynamic inventory is a script or plugin that builds the inventory automatically by querying a real source at run time — a cloud provider's API (AWS, Azure, GCP), a CMDB, or any other system that already knows which hosts exist. Instead of you maintaining the list, Ansible asks the source directly, every time a playbook runs. Add a server in AWS and it appears in the next Ansible run with zero file edits; terminate one and it disappears the same way.

Two mechanisms exist to do this, and it matters which one you reach for:

  • Inventory scripts — the original approach: an executable program that outputs JSON in the shape Ansible expects. Still supported today for backward compatibility, but Ansible's own docs are direct about it: "We recommend plugins over scripts for dynamic inventory."
  • Inventory plugins — the modern approach, built into Ansible collections. They "take advantage of the most recent updates to the Ansible Core code," and most of the older cloud inventory scripts have been retired in favor of a plugin in the matching collection.

Mental model: think of an inventory plugin the same way you think of the collection modules from Lesson 19. A module is "one task, one API call, written in a standard shape Ansible understands." An inventory plugin is the same idea applied to the whole inventory: "one query to a real source, written in a standard shape Ansible understands," instead of a bespoke script every team reinvents.

Example: the aws_ec2 inventory plugin

The amazon.aws collection you met in Lesson 19 ships an inventory plugin called amazon.aws.aws_ec2. It queries the EC2 API directly and turns your running instances into an Ansible inventory — no manual IP-copying required. A few concrete facts about it, confirmed from the plugin's own documentation:

  • It needs AWS credentials to authenticate — access keys, a named profile, or an IAM instance role, the same credential options any AWS API caller uses.
  • You can scope it with regions (which AWS regions to query — if you leave this out, it queries every non-restricted region) and filters (an EC2-style filter dictionary, so you can pull back only instances with a certain tag, for example).
  • It can build Ansible groups automatically from EC2 tags and attributes using a keyed_groups setting — so instances tagged role: webserver can land in a webservers group without you writing that grouping logic yourself.

This is one example among many — Azure, GCP, and most major CMDBs have an equivalent collection-provided plugin. The shape is always the same: point the plugin at your source, give it credentials, and it produces the inventory.

The YAML inventory-plugin config file

You don't write a script to use an inventory plugin — you write a small YAML config file, the same way you'd configure any other tool. Ansible recognizes which plugin to use from the file's name, not its location: the config file for aws_ec2 must end in aws_ec2.yml or aws_ec2.yaml (for example, production.aws_ec2.yml). Inside, a required plugin: key names the plugin to use:

plugin: amazon.aws.aws_ec2
regions:
  - us-east-1
filters:
  tag:Environment: production

Read that top to bottom: plugin: tells Ansible "use the amazon.aws.aws_ec2 plugin to build this inventory." regions: limits the query to us-east-1 instead of scanning every AWS region. filters: narrows it further to instances tagged Environment: production. Point ansible-inventory or ansible-playbook at this file with -i, exactly like you'd point at a static inventory.ini — the difference is entirely inside the file, not in how you invoke Ansible.

Best practice: a dynamic inventory config file is source-controlled like everything else, but it never contains credentials directly — those come from environment variables, a credentials file, or an IAM role attached to the machine running Ansible. If you ever see an AWS access key hardcoded in an inventory YAML file, that's a finding, not a style choice.

Try it — before looking below

Q1. Your company's web servers autoscale up and down hourly based on traffic. Should you use static or dynamic inventory, and why?

Dynamic inventory. Hosts are being created and destroyed automatically by the autoscaling group, so a hand-maintained static file would be wrong within the hour — either missing new instances or still listing terminated ones. A dynamic inventory plugin (like amazon.aws.aws_ec2) queries the cloud provider at run time and always reflects what's actually running right now, with no manual editing.

Q2. What must the config file for the aws_ec2 inventory plugin be named, and what key inside it tells Ansible which plugin to use?

The filename must end with aws_ec2.yml or aws_ec2.yaml (e.g. production.aws_ec2.yml) — that's how Ansible recognizes it. Inside the file, the plugin: key names it: plugin: amazon.aws.aws_ec2.

Q3. Ansible still supports inventory scripts. Should you write a new one for a new project today?

No. Scripts still work for backward compatibility, but Ansible's own docs recommend plugins over scripts for dynamic inventory — and most cloud providers already ship a maintained plugin in their collection (like amazon.aws.aws_ec2), so you're rarely starting from scratch.

Hands-on: explore inventory plugins without any cloud credentials

A real aws_ec2 inventory needs real AWS credentials and real EC2 instances — this course can't assume you have either. What you can do right now is confirm the plugin exists, read its documentation, and watch Ansible recognize a plugin config file even without credentials to complete the query.

  1. List every inventory plugin available in your Ansible install — this needs no credentials at all: 
    ansible-doc -t inventory -l
    Look for entries under the amazon.aws namespace, such as amazon.aws.aws_ec2 (only shows up if you installed the collection in Lesson 19 — ansible-galaxy collection install amazon.aws if it's missing).
  2. Read the plugin's own documentation, the same way you'd read a module's docs: 
    ansible-doc -t inventory amazon.aws.aws_ec2
    Scan for the regions, filters, and keyed_groups options mentioned above — you're confirming the docs in this lesson against the plugin's real source of truth.
  3. Write a minimal config file named demo.aws_ec2.yml: 
    plugin: amazon.aws.aws_ec2
regions:
  - us-east-1
  4. Try to use it: 
    ansible-inventory -i demo.aws_ec2.yml --list
    Without valid AWS credentials this will fail — and that failure is the useful part. Read the error carefully: it should be an authentication error (Ansible recognized the file as an aws_ec2 config and tried to call the EC2 API), not a "no such plugin" or "couldn't parse this file" error. That distinction confirms the plugin auto-detection worked correctly off the filename alone, even though the query itself couldn't complete.

Why this matters: reading an error message carefully instead of just seeing "it failed" is a skill you'll use constantly with dynamic inventory. An auth error means the plumbing is right and you need real credentials. A "plugin not found" error means the collection isn't installed. A YAML parse error means the config file itself is wrong. Three different problems, three different fixes — the error text tells you which one you have.

Recap
  • Static inventory (Lesson 4) works when hosts barely change. It breaks down when infrastructure fluctuates — autoscaling groups, ephemeral cloud instances — because hand-editing a file can't keep up.
  • Dynamic inventory queries a real source (cloud API, CMDB) at run time to build the host list automatically — no manual edits, always current.
  • Two mechanisms: inventory scripts (older, still supported) and inventory plugins (modern, recommended — "plugins over scripts for dynamic inventory").
  • amazon.aws.aws_ec2, from the amazon.aws collection (Lesson 19), is one example — it queries EC2 directly, scoped with regions and filters.
  • Plugin config files are YAML, recognized by filename suffix (e.g. *.aws_ec2.yml), with a required plugin: key naming which plugin to use.
  • ansible-doc -t inventory -l lists installed inventory plugins; ansible-doc -t inventory <plugin> shows one plugin's options — both work with zero cloud credentials.
Don't have AWS/Azure/GCP access to try a real dynamic inventory against? That's completely normal at this stage — the hands-on above is designed so you can verify the plugin mechanics without any cloud account. When you do get access to a real cloud environment, come back to this lesson and run the full ansible-inventory --list against it for real; the config file shape doesn't change.
