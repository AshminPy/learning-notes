Ansible / Zero to Expert — Lesson 33 of 36

Performance & best practices

A playbook that takes 4 seconds against 1 host can take 20 minutes against 200 — and most of that time isn't "doing work," it's waiting: waiting for SSH connections, waiting for fact-gathering nobody needed, waiting because only 5 hosts run at once by default. This lesson covers the handful of real, commonly-cited levers that actually change that, each one confirmed against Ansible's own documentation rather than folklore.

Mental model: forks is the width of the pipe — how many hosts Ansible works on at the same moment. strategy is whether hosts have to stay in lockstep with each other or can run ahead once they're done. Widen the pipe, and/or stop making faster hosts wait for slower ones, and the same playbook finishes sooner — without changing a single task.

Forks: how many hosts run at once

Confirmed against Ansible's configuration reference: forks is the "Maximum number of forks Ansible will use to execute tasks on target hosts," and its default value is 5. Against an inventory of 5 hosts that's invisible. Against 100 hosts, only 5 run at a time by default — everyone else queues.

# ansible.cfg
[defaults]
forks = 30

# or per-run, no config file change needed
$ ansible-playbook site.yml --forks 30
# or
$ ANSIBLE_FORKS=30 ansible-playbook site.yml

Raise it to roughly the number of hosts you actually want running simultaneously, bounded by what your control node and network can sustain (see the production note below) — there's no universal "right" number, only "higher than the default of 5 once your inventory is bigger than 5."

Strategy: linear vs. free

Confirmed against Ansible's playbook strategies documentation. The default, linear, means "Ansible runs each task on all hosts affected by a play before starting the next task on any host" — every host finishes task 1 before anyone starts task 2. free instead "allows each host to run until the end of the play as fast as it can," with no waiting on slower hosts:

- hosts: all
  strategy: free
  tasks:
    - name: install packages
      ansible.builtin.package:
        name: "{{ item }}"
        state: present
      loop: "{{ required_packages }}"

free is the right call when hosts genuinely differ in speed (mixed instance sizes, some over a slower network link) and tasks don't depend on every host reaching the same point together. linear (the default) is right when a later task assumes every host already finished an earlier one — which is most playbooks, which is why it's the default.

Fact gathering: turn it off when you don't need it

Lesson 9 introduced facts; here's the performance side. Confirmed against Ansible's own docs: "By default, Ansible gathers facts at the beginning of each play" — every play, every host, even if not one task in that play references a single fact.

- hosts: webservers
  gather_facts: false   # skip it entirely if this play never uses ansible_facts[...]
  tasks:
    - name: ensure nginx is running
      ansible.builtin.service:
        name: nginx
        state: started

The documentation is explicit about why this matters at scale: "Disabling facts may particularly improve performance in push mode with very large numbers of systems." If a play only ever runs fixed, non-conditional tasks — no when: ansible_facts[...], no OS-family branching from Lesson 10 — gathering facts for it is pure overhead.

When you do need facts but re-run the same playbook often, fact caching is the other lever: "Fact caching can improve performance. If you manage thousands of hosts, you can configure fact caching to run nightly, and then manage configuration on a smaller set of servers periodically throughout the day" — gather once, reuse across many runs, instead of re-discovering the same facts every single time.

Pipelining: fewer SSH round-trips per task

Confirmed against Ansible's SSH connection plugin docs: pipelining "reduces the number of connection operations required to execute a module on the remote server, by executing many Ansible modules without actual file transfers." It's disabled by default because it can conflict with certain sudo/privilege-escalation configurations (specifically ones requiring a TTY) — but for most setups it's safe and a real speed win:

# ansible.cfg
[ssh_connection]
pipelining = true

Enable it once, test a real playbook run against it, and keep it on if nothing broke — that's the whole rollout.

The anti-pattern: reaching for shell/command instead of a real module

This connects straight back to Lesson 7's idempotency and Lesson 5's ad-hoc guidance: command/shell aren't idempotent on their own, and every run re-executes the raw command whether anything needs to change or not. That's not just a correctness problem — it's a performance one too, at scale: a proper module (package, service, file, copy, template) checks current state first and reports ok (does nothing) when nothing needs to change, while a shell task pays the full cost of re-running every time, on every host, every play.

Common mistake: reaching for ansible.builtin.shell: mkdir /opt/myapp because it's the first thing that comes to mind, instead of ansible.builtin.file: path=/opt/myapp state=directory. Both "work" the first time. The file module checks whether the directory already exists and reports ok if so; the shell version re-runs mkdir every single time and can even report a failure on a rerun if the directory already exists and the underlying command isn't written to tolerate that. Confirmed against Ansible's own command module docs, which point you toward dedicated modules directly: "For rebooting systems, use the ansible.builtin.reboot... module" rather than a raw command — the same logic applies to almost every "I'll just shell out for this" instinct.

Production note: real teams don't crank forks to 100 blindly — the control node's CPU/network and the target hosts' own SSH connection limits are real ceilings. A common pattern: start at the default, double it, measure the actual wall-clock time difference on a real run, and stop increasing once the gain flattens out. Combine with strategy: free only when hosts are genuinely heterogeneous in speed — for a uniform fleet, linear plus higher forks is usually simpler to reason about and just as fast.

Try it — before looking below

Q1. A playbook against 150 hosts is slow, and none of its tasks use ansible_facts or any conditional based on host facts. Name two independent config changes that would likely speed it up, and explain what each one actually does.

1) Raise forks above the default of 5, so more of the 150 hosts run each task simultaneously instead of queuing in batches of 5. 2) Set gather_facts: false on the play, since no task references any fact — this skips the automatic fact-gathering step Ansible otherwise runs at the start of every play, for every host, for no benefit here. (Enabling pipelining would be a third valid answer if privilege escalation isn't in play.)

Q2. Why is command: mkdir /opt/data a worse choice than ansible.builtin.file: path=/opt/data state=directory, even though both "create the directory" the first time you run them?

The file module is idempotent — it checks whether /opt/data already exists as a directory and reports ok (no action) if so, exactly like Lesson 7 covered. command: mkdir /opt/data just re-executes the raw mkdir every run, with no state check — on a rerun it can report a false "changed," or even fail outright if the underlying command errors on an existing directory, unless you add a manual guard like creates:. At scale, across every host and every run, that's real wasted work that a proper module simply skips.

Now write your own

You don't need real infrastructure to see fact-gathering overhead — it's measurable on localhost alone. And you can simulate multiple hosts for free using several inventory entries that all point back to your own machine:

# inventory-perf.ini — five "hosts," zero real infrastructure needed
[fleet]
node1 ansible_connection=local
node2 ansible_connection=local
node3 ansible_connection=local
node4 ansible_connection=local
node5 ansible_connection=local
  • write a tiny playbook, perf-test.yml, targeting fleet, with one harmless task (e.g. ansible.builtin.debug: msg="hello")
  • time a normal run: time ansible-playbook -i inventory-perf.ini perf-test.yml
  • time it again with facts turned off: add gather_facts: false to the play, rerun with time in front, and compare — you should see less time spent even on this tiny, five-fake-host example, because fact-gathering was skipped five times
  • try --forks 2 vs --forks 5 against the same fake fleet and watch the PLAY RECAP timing change as fewer hosts wait behind each other

Recap
  • forks (default 5) controls how many hosts run each task simultaneously — raise it for larger inventories, bounded by what your control node and network can sustain.
  • strategy: linear (default) keeps every host in lockstep task by task; strategy: free lets each host race to the end of the play independently — pick free only when hosts genuinely differ in speed and don't depend on each other.
  • gather_facts: false skips fact collection for plays that never use facts; fact caching avoids re-gathering the same facts on every run when you do need them.
  • pipelining = true cuts SSH round-trips per task — off by default because of some privilege-escalation setups, safe to enable and test in most environments.
  • The single biggest anti-pattern: reaching for shell/command where a proper module already exists — it's not just less idempotent (Lesson 7), it's slower at scale because it never gets to report "nothing to do."
