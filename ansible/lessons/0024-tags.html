Tags

Real playbooks grow. What starts as ten tasks in one file becomes a site.yml that includes a dozen roles — web servers, databases, monitoring, firewall rules, cron jobs — each with its own tasks. Running the whole thing every time you're iterating on one small piece is slow, and slow feedback loops kill momentum. Tags solve this: labels you attach to tasks, blocks, roles, or plays so you can run — or skip — just the part you care about.

Mental model: a tag is a label on a box, not a switch that changes what's inside the box. Tagging a task config doesn't alter what the task does — it just lets you tell ansible-playbook "only open the boxes labeled config this time" instead of opening every box in the playbook.

Adding tags

You can put tags: on a single task, a block of tasks, a role, or a whole play. Confirmed against Ansible's own docs — here's each level:

On a task:

tasks:
  - name: Install the servers
    ansible.builtin.yum:
      name: [httpd, memcached]
      state: present
    tags:
      - packages
      - webservers

On a block (every task inside inherits the tag):

- name: ntp tasks
  tags: ntp
  block:
    - name: Install ntp
      ansible.builtin.yum:
        name: ntp
        state: present

On a role:

roles:
  - role: webserver
    vars:
      port: 5000
    tags: [ web, foo ]

On a play (every task in the play inherits the tag):

- hosts: all
  tags: ntp
  tasks:
    - name: Install ntp
      ansible.builtin.yum:
        name: ntp
        state: present

A task can carry more than one tag — write them as a YAML list (tags: followed by dashed items) or inline (tags: [ web, foo ]), both are the same thing, just two ways to write a YAML list. Tag names are your choice — packages, config, slow, whatever groups make sense for how you'll want to run this playbook later.

Running a subset with --tags

Pass --tags to ansible-playbook and only tasks carrying one of the listed tags run (plus a couple of special cases covered below):

$ ansible-playbook example.yml --tags "configuration,packages"

That runs every task tagged configuration or packages — untagged tasks and tasks with other tags are skipped for this run. Two other useful values: --tags all runs everything (the default, minus anything tagged never), --tags tagged runs only tasks that have at least one tag, and --tags untagged runs only tasks with no tags at all.

Skipping a subset with --skip-tags

The opposite: run everything except the tagged tasks you name.

$ ansible-playbook example.yml --skip-tags "packages"

Useful when most of the playbook is what you want, and only one slow or risky part needs to sit out this run — say, a task tagged slow that rebuilds a large cache, and you're iterating on something else entirely.

You can combine both flags in one run:

$ ansible-playbook example.yml --tags "tag1,tag3" --skip-tags "tag4"

Why this matters at scale: without tags, "test my one change" means running the entire playbook — including the parts that already work and take five minutes to converge. With tags, it means running the three tasks you're actually touching, in three seconds. That's the difference between a tight feedback loop and dreading every test run.

The two reserved tag names

Two tag names have special meaning built into Ansible — don't use them as ordinary labels, and know what they do because you'll meet them in other people's playbooks.

always — a task or play tagged always runs on every invocation, regardless of what --tags you passed, unless you explicitly skip it with --skip-tags always (or skip it via another tag defined on that same task). Verified against current Ansible docs, quoting exactly: "If you assign the always tag to a task or play, Ansible will always run that task or play, unless you specifically skip it (--skip-tags always) or another tag defined on that task." Good fit for something like a fact-gathering or sanity-check task that every run needs, no matter which subset you asked for.

never — the opposite: a task or play tagged never is skipped by default, even by a plain ansible-playbook run with no --tags at all, and only runs if you specifically ask for it with --tags never (or another tag defined on that task). Quoting the docs exactly: "If you assign the never tag to a task or play, Ansible skips that task or play unless you specifically request it (--tags never) or another tag defined for that task." Good fit for a destructive or rarely-needed task — like a full data wipe — that you never want to fire by accident.

Try it — before looking below

Q1. A task has no tags: at all. You run ansible-playbook site.yml --tags "config". Does that task run?

No. When you pass --tags, only tasks matching one of the named tags run (plus anything tagged always). An untagged task doesn't match config, so it's skipped for this run — nothing about the task itself changed, only which tasks this particular invocation chose to touch.

Q2. A task is tagged never. You run ansible-playbook site.yml with no tag flags at all. Does it run?

No. never-tagged tasks are skipped by default, even on a plain run with no --tags flag. They only run if you explicitly ask with --tags never (or another tag on that same task). It's the safety switch for tasks you never want to fire unless someone deliberately opts in.

Now write your own

Reuse the playbook.yml from earlier lessons, or start a fresh one. Give it three tasks, tag two of them differently, and leave the third untagged:

- name: Tags practice
  hosts: localhost
  tasks:
    - name: Setup step
      ansible.builtin.debug:
        msg: "Running setup"
      tags:
        - setup

    - name: Config step
      ansible.builtin.debug:
        msg: "Running config"
      tags:
        - config

    - name: Untagged step
      ansible.builtin.debug:
        msg: "Running with no tag"

Then:

  • run the full playbook with no tag flags — confirm all three TASK banners appear in the output
  • run it again with --tags config — confirm only TASK [Config step] appears, and the other two are missing entirely from the output (not shown as skipped — they're not evaluated at all)
  • run it with --skip-tags config — confirm Setup step and Untagged step run, but Config step doesn't
  • run it with --tags untagged — confirm only Untagged step runs

Try it yourself before checking the reference commands below.

ansible-playbook -i inventory playbook.yml
ansible-playbook -i inventory playbook.yml --tags "config"
ansible-playbook -i inventory playbook.yml --skip-tags "config"
ansible-playbook -i inventory playbook.yml --tags "untagged"

Recap
  • tags: labels a task, block, role, or play. Run only tagged subsets with --tags, or run everything except them with --skip-tags — instead of running the whole playbook every time you're iterating on one piece.
  • This matters most at scale: a large playbook with dozens of roles is slow to run in full on every small change. Tags turn "test my change" from a five-minute full run into a three-second targeted one.
  • always runs every invocation unless explicitly skipped. never is skipped every invocation unless explicitly requested. Both are reserved names, not ordinary labels.
