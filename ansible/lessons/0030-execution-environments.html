Execution environments

"It works on my machine" is a real, common Ansible failure — not because the playbook logic is wrong, but because your laptop happens to have a particular Python version, particular collection versions installed at particular times, and dependencies nobody remembers installing. Your teammate's laptop, and the CI runner, don't have the exact same set. Execution environments exist to remove that variable entirely.

Mental model: An execution environment is a container image — the same idea as a Docker image for a web app — but purpose-built to run Ansible. It bundles a specific ansible-core version, a specific Python version and its dependencies, and specific Ansible collections, all pinned together in one image. Run your playbook inside that image, on any machine, and you get identical execution every time — no more "it works on my machine."

ansible-builder — building the image

Confirmed against ansible-builder's own docs: you describe the environment in a file, then build it into a container image using Podman or Docker.

A minimal execution-environment.yml:

---
version: 3
images:
  base_image:
    name: quay.io/ansible/ansible-runner:latest
dependencies:
  python:
    - requests
  galaxy:
    collections:
      - community.general

Build it:

# Generate the build context only, without building the image
$ ansible-builder create

# Generate the build context AND build the image
$ ansible-builder build -t my-execution-env:1.0

The result is a real container image — tag it, push it to a registry, and it's now a versioned, reusable artifact exactly like any other application image.

ansible-navigator — running content inside it

Confirmed against ansible-navigator's own docs: it's a command-line tool and text-based UI for running, reviewing, and troubleshooting Ansible content using an execution environment instead of your local Python/Ansible install.

# Run a playbook inside an execution environment
$ ansible-navigator run site.yml -m stdout

# Inspect what's actually bundled inside an execution environment image —
# Ansible/Python/collection versions, without guessing
$ ansible-navigator images

ansible-navigator images is the answer to "what version of collection X is really in this environment?" — instead of trusting your memory or a README, you inspect the image directly.

Common mistake: treating a running execution environment like a general-purpose container you SSH/exec into and patch by hand — installing one more Python package "just this once" because a task needs it right now. That silently recreates the exact problem execution environments exist to solve: the running container now differs from the image definition, and nobody else gets that fix. If a task needs something new, add it to execution-environment.yml and rebuild the image.

Production note: teams version execution environment images in a registry like any other container image (a real tag, e.g. my-org/network-ee:2.3.1), and reference that exact tag from CI pipelines and, later, from Automation Controller job templates (Lesson 31). "Which environment did this run use?" then always has an exact, reproducible answer — the image tag — instead of "whatever was on that person's laptop that day."

Try it — before looking below

Q1. Two teammates run the identical playbook — one succeeds, the other gets a module import error because a Python library is a slightly different version locally. What execution-environment-based fix prevents this entire class of bug, instead of asking both people to manually sync their local pip/collection versions?

Build one execution environment image with ansible-builder — pinning ansible-core, the Python dependencies, and the collections in execution-environment.yml — and have both people (and CI) run the playbook inside that same image via ansible-navigator instead of their own local install. Since everyone runs the identical image, "different local version" bugs can't occur.

Q2. What does ansible-navigator images let you check, and why does that matter once you're relying on execution environments instead of local installs?

It lets you inspect exactly what's inside a given execution environment image — the Ansible Core, Python, and collection versions actually bundled in it — so you can confirm what a playbook will really run against instead of guessing based on what happens to be installed locally.

Q3. Where do you declare the Python packages and Ansible collections that should be baked into an execution environment image, and what command builds the image from that declaration?

In the execution-environment.yml definition file, under dependencies.python (a Python requirements list) and dependencies.galaxy.collections (an Ansible collections list). Built into an actual image with ansible-builder build.

Recap
  • Execution environments solve "works on my machine": a container image bundling a pinned Ansible Core, Python, and collection set, run identically everywhere.
  • ansible-builder builds the image from an execution-environment.yml definition (python and galaxy.collections dependencies) using ansible-builder build.
  • ansible-navigator runs and inspects Ansible content against an execution environment — ansible-navigator run to execute, ansible-navigator images to see exactly what's bundled inside one.
  • Never hand-patch a running execution environment container — add the dependency to the definition file and rebuild, so the fix is reproducible for everyone.
