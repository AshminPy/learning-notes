Ansible Vault

Real playbooks eventually need real secrets — a database password, an API key, a TLS private key you're pushing to a host. Those values have to live somewhere in your project: a variable file, group_vars, a task. If you type them in as plain text and run git add, you've just written a secret into your repo's history forever — readable by anyone with clone access, and still there even if you delete the file in a later commit. That's not a hypothetical; it's one of the most common real-world security incidents in infrastructure code.

If you took the sibling Terraform course, this is the exact same problem you met in Terraform Lesson 24: Terraform's sensitive = true hides a value from CLI output but still writes it into terraform.tfstate in plaintext — a display filter, not encryption. Ansible has the same underlying risk (secrets sitting in plaintext files that want to be committed), but it ships a real answer to it: Ansible Vault, which actually encrypts the file on disk.

Mental model: Vault turns a file into a locked box. Anyone can see the box exists in your repo — file name, git history, the fact that it's there — but opening it (editing it, viewing it, or letting a playbook read the variables inside) requires the password. No password, no contents. That's a real security boundary, not a CLI filter.

What Vault actually encrypts

Ansible Vault can encrypt two different things, and the mental model for each is the same "locked box" idea, just at different sizes:

  • A whole file — a variables file, a whole playbook, any file Ansible would read. Once encrypted, the entire file's contents are ciphertext; nobody can read a line of it without the password.
  • A single value inline — one secret string embedded in an otherwise-plaintext, readable YAML file, using ansible-vault encrypt_string. Useful when the rest of the file has nothing sensitive in it and you don't want to lock the whole thing down.

The core commands

Confirmed against Ansible's own CLI reference and vault guide:

# Create a new file, encrypted from the start — opens your editor,
# encrypts on save
$ ansible-vault create secrets.yml

# Open an existing encrypted file, decrypted in your editor,
# re-encrypted automatically when you save and close
$ ansible-vault edit secrets.yml

# Encrypt a file that already exists (has plaintext secrets in it right now)
$ ansible-vault encrypt vars/prod.yml

# Decrypt a file back to plaintext on disk — use sparingly, re-encrypt when done
$ ansible-vault decrypt vars/prod.yml

# View the decrypted contents in a pager, without writing plaintext to disk
$ ansible-vault view secrets.yml

Every one of these prompts you for the vault password interactively unless you tell it where to get the password some other way (more on that below).

Encrypting a single value

encrypt_string is the tool for the "just this one secret" case — you get back a block you paste directly into an otherwise plaintext YAML file:

$ ansible-vault encrypt_string --vault-password-file a_password_file 'S3cretPass!' --name 'db_password'

That prints a YAML block starting with db_password: !vault | followed by the encrypted blob — copy that whole block into your vars.yml as-is. The rest of the file stays readable; only that one value is locked.

Running a playbook that uses vault-encrypted content

Ansible needs the password at run time to decrypt whatever it reads, so ansible-playbook needs to be told where to get it:

# Prompt for the password interactively
$ ansible-playbook --ask-vault-pass site.yml

# Read the password from a file
$ ansible-playbook --vault-password-file /path/to/vault-password-file site.yml

# Named vault IDs — supports multiple different passwords for
# different files in the same run
$ ansible-playbook --vault-id dev@prompt site.yml

Critical — the password file is a secret too: --vault-password-file is convenient (it's how CI systems like Jenkins supply the password without a human typing it), but that file contains the plaintext password that unlocks everything. Never commit the vault password file to git — that puts the key right next to the lock, and the whole exercise of encrypting the vault file was pointless. Keep the password file outside the repo entirely, or better, don't use a file on disk at all: pull the password from a secrets manager (Vault, AWS Secrets Manager) or your CI system's built-in secret store (a GitHub Actions secret, a GitLab CI variable) and feed it in at run time.

The best-practice pattern

Put the two pieces on opposite sides of the git boundary:

  • Commit the encrypted vault file to git. It's ciphertext — safe to store, review in a PR (as an unreadable blob), and version like any other file. This is the whole point: your secrets file lives in your repo history like everything else, without ever exposing the secret.
  • Keep the vault password itself completely out of git. No password in a .tfvars-style file, no password in a script committed to the repo, no password in a .env file that "just this once" gets committed. It lives in a secrets manager, a CI secret store, or — for solo/local work — a file outside the repo that's listed in your global gitignore, never the project's.

Add the plaintext files you'll be encrypting-and-deleting, and any local password file, to .gitignore before you start:

vault-password-file
*.decrypted

Q1. You run ansible-vault encrypt vars/prod.yml and commit the result. A teammate clones the repo and opens vars/prod.yml in a text editor, no Ansible involved. What do they see?

Ciphertext — an unreadable encrypted blob, not the YAML variables. Unlike Terraform's sensitive = true (which only hides a value from CLI output while the state file still holds it in plaintext), Vault genuinely encrypts the file's bytes. Without the vault password, the actual secret values are not recoverable from the file.

Q2. Your CI pipeline needs to run a vault-protected playbook unattended. Where should the vault password come from?

A CI secret store (GitHub Actions secrets, GitLab CI variables) or a dedicated secrets manager — supplied to --vault-password-file or --vault-id at run time, never a password file committed to the repo. Committing the password file defeats Vault entirely: anyone who can read the repo can now decrypt the "protected" file too.

Hands-on: encrypt, view, decrypt

In your practice folder, create a small plaintext variables file, secrets.yml:

db_user: admin
db_password: correct-horse-battery-staple

Then walk the round trip yourself:

  • encrypt it: ansible-vault encrypt secrets.yml — enter a password when prompted, confirm it
  • open the file in a plain text editor (not ansible-vault, just cat secrets.yml or your editor) — confirm it's unreadable ciphertext starting with $ANSIBLE_VAULT;1.1;AES256
  • view the decrypted contents without changing the file on disk: ansible-vault view secrets.yml — enter the same password, confirm your two variables print in plaintext
  • decrypt it back to plaintext on disk: ansible-vault decrypt secrets.yml — enter the password once more
  • confirm it's readable plaintext again: cat secrets.yml

Try it yourself before checking the reference commands below.

Reveal the reference commands

ansible-vault encrypt secrets.yml
cat secrets.yml
# unreadable ciphertext — confirm the $ANSIBLE_VAULT header line

ansible-vault view secrets.yml
# prompts for password, prints db_user / db_password in plaintext

ansible-vault decrypt secrets.yml
cat secrets.yml
# back to plain, readable YAML

Recap
  • The problem: playbooks and variable files often need real secrets, and committing them in plaintext to git is a security incident — the same underlying risk you met with Terraform state in Terraform Lesson 24, but Ansible Vault gives you a real fix, not just a display filter.
  • Vault encrypts a whole file (create, encrypt, edit, view, decrypt) or a single inline value (encrypt_string) — both require the vault password to read.
  • Run a vault-protected playbook with --ask-vault-pass (interactive prompt) or --vault-password-file / --vault-id (password from a file or script, for CI).
  • Never commit the vault password — file or otherwise — to git. That puts the key next to the lock. Supply it from a secrets manager or your CI's secret store instead.
  • Best-practice pattern: commit the encrypted vault file to git, keep the vault password completely out of git.
