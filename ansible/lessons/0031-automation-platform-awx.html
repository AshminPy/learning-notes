Automation controller and AWX

Every lesson so far has run from a terminal, on one machine, triggered by one person typing a command. That doesn't scale to a team: there's no shared record of who ran what, no control over which credentials people are allowed to use, and no way for a non-technical stakeholder to safely re-run yesterday's deployment without reading YAML. Automation controller — the exact term the EX374 exam itself uses — is Red Hat's answer: a supported product for running your existing playbooks under governance, as a service, instead of ad hoc from someone's laptop.

Mental model: think of the difference between running scripts from your own laptop versus running them from a real job scheduler with permissions. Nothing about the Ansible content changes — same playbooks, same roles, same collections. What changes is that every run is now logged centrally, gated by role-based access control, and launchable by someone who has never opened a terminal.

AWX vs. Automation controller — the upstream/downstream relationship

Confirmed directly against the AWX project's own GitHub README and Red Hat's official FAQ: this is a real, standard upstream/downstream open-source relationship, not two competing products.

AWXAutomation controller
What it isThe open-source, community upstream projectThe Red Hat Ansible Automation Platform component built from it
Official relationship"One of the upstream projects for Red Hat Ansible Automation Platform" (AWX's own README)"Produced by taking selected releases of AWX, hardening them for long-term supportability" (Red Hat's own description)
SupportCommunity-supported only — Red Hat provides no paid support for itFully supported by Red Hat, under an Ansible Automation Platform subscription
Release paceFast-moving, frequent releases, all new development happens here firstSlower, hardened, long-term-supportable releases
Production recommendationRed Hat's own FAQ: not recommended for productionThe supported choice for production use

AWX is genuinely free and self-hostable (for example via the AWX Operator on Kubernetes), which makes it the honest way to get real hands-on practice with these concepts without an Automation Platform subscription — the same way this course has used free local tools throughout rather than assuming paid infrastructure.

Core concepts

The same four building blocks exist in both AWX and Automation controller — confirmed against Red Hat's own Automation controller documentation:

ConceptWhat it is
ProjectA logical collection of playbooks — typically pointing at a git repository, so the controller always pulls the current, version-controlled source
InventoryThe target hosts — static, or dynamically sourced (Lesson 20), managed centrally instead of as a file on someone's laptop
CredentialSecurely stored authentication material — SSH keys, Vault passwords, cloud API keys — used to run jobs without exposing the actual secret value to whoever launches them
Job templateCombines a Project + Inventory + Credential(s) (+ execution environment, Lesson 30) into one named, reusable, launchable unit

Why teams actually move to this model

  • Role-based access control — grant someone permission to launch a specific job template, without ever granting them the underlying credential or repo access.
  • Centralized logging — every run, every host, every result, in one place — an actual audit trail instead of "ask whoever ran it last."
  • Scheduling — recurring automation runs without a person, or a fragile personal cron job, remembering to trigger it.
  • Delegation — someone who has never written a line of YAML can safely click "Launch" on a job template someone else built and tested.

Security note: credentials in the controller are stored encrypted and injected into the job at run time. A user can be granted "use" permission on a credential — enough to launch a job with it — without ever being able to view or extract the actual secret value. It's the same underlying idea as Ansible Vault (Lesson 26): the secret stays usable without ever being exposed to the person using it.

Production note: the natural progression this whole course has been building toward: a role gets written, lint-checked (Lesson 27) and Molecule-tested (Lesson 28) locally, packaged into a pinned execution environment (Lesson 30), then registered as a Project and wired into a Job Template in Automation controller. The same tested artifact then runs identically whether it's triggered by a person clicking Launch, a schedule, or a CI pipeline — not three different ad hoc processes.

Try it — before looking below

Q1. Your team currently has one person SSH into their laptop and run ansible-playbook by hand whenever a deployment is needed. Name two concrete problems this creates that moving to Automation controller job templates fixes.

Any two of: no audit trail of who ran what and when; no access control — anyone with laptop and repo access can run against production with full credentials; a single point of failure, since only that one person can trigger the deploy; credentials often end up stored locally and insecurely rather than centrally managed; nothing runs on a schedule unless a person remembers to do it manually.

Q2. In Automation controller, what four building blocks does a Job Template combine into one reusable, launchable unit?

A Project (the playbook source, typically a git repo), an Inventory (the target hosts), Credentials (the auth material needed to reach hosts and decrypt secrets), and typically an execution environment — combined so anyone with launch permission can run the exact same automation the same way, without touching any of the underlying pieces directly.

Q3. Is AWX something Red Hat provides paid support for? What's the practical implication if your production automation currently runs on AWX?

No. AWX is the fast-moving, community-supported upstream project — Red Hat provides no paid support for it, and its own FAQ doesn't recommend it for production. Automation controller is the hardened, Red Hat-supported downstream product built from selected AWX releases. Running production automation on AWX means you're relying entirely on community support, not a Red Hat support contract.

Now write your own

A real controller is a licensed product, not something to spin up casually for a practice exercise — so this is a concept-mapping exercise instead, using material you've already built across this course. Imagine you're registering the Vault-protected playbook from Lesson 26 in Automation controller. Write down, in your own words, what you'd configure for each of the four building blocks:

  • the Project — where would it point?
  • the Inventory — what hosts does it target?
  • the Credential(s) — what does the job need access to, and how many separate credentials might that be?
  • the Job template — what does it tie all three together into?

Try it yourself before checking a reasonable answer below.

Reveal a reasonable mapping

Project: the git repository holding the playbook and its Vault-encrypted variables file. Inventory: the target hosts the playbook manages (static list, or a dynamic source per Lesson 20). Credentials: at least two, kept separate — a machine credential (SSH key/password to reach the hosts) and a Vault credential (the password to decrypt secrets.yml) — the controller injects both at run time without ever showing either to the person launching the job. Job template: the named, launchable unit combining that Project + Inventory + both Credentials, so anyone with launch permission can run this exact automation without needing the SSH key, the Vault password, or even the repository access themselves.

Recap
  • AWX is the free, fast-moving, community-supported upstream project; Automation controller is Red Hat's hardened, fully-supported downstream product built from selected AWX releases — Red Hat does not recommend AWX itself for production.
  • Four core concepts, shared by both: Project (playbook source), Inventory (target hosts), Credential (secured auth material), Job template (combines all three into one launchable, reusable unit).
  • Credentials are usable without being exposed — the same "usable without being seen" idea as Ansible Vault (Lesson 26).
  • Teams move to this model for RBAC, centralized logging/audit, scheduling, and safe delegation to non-experts — not because the underlying playbooks change at all.
