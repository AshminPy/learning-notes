Roles: anatomy

Every playbook you've written so far has kept tasks, handlers, variables, and templates loose in one project folder. That's fine for a handful of tasks. But once you're managing nginx on one set of hosts, PostgreSQL on another, and a monitoring agent everywhere, loose files stop scaling — you end up copy-pasting the same tasks between playbooks, or scrolling through one giant file that mixes three unrelated jobs together. A role is Ansible's answer: a standardized, reusable directory structure that packages tasks, handlers, variables, templates, and files together around one responsibility — "install and configure nginx" — so that responsibility can be written once and reused anywhere.

Mental model: if you've seen the Terraform course in this series, a role is the same idea as a Terraform module — a self-contained, composable unit built around one job, with its own inputs and internals, that you can call from any project instead of rewriting. Terraform modules compose provisioning. Ansible roles compose configuration. Same instinct, different layer of the stack.

The standard directory layout

A role isn't a special file type — it's a folder with a specific, predictable set of subfolders that Ansible knows how to look inside automatically. Here's the layout, confirmed against Ansible's own documentation:

roles/
    common/
        tasks/
            main.yml
        handlers/
            main.yml
        templates/
            ntp.conf.j2
        files/
            bar.txt
            foo.sh
        vars/
            main.yml
        defaults/
            main.yml
        meta/
            main.yml

common here is just an example role name — you'll create roles named things like nginx or postgres. Ansible finds and loads a role's pieces by convention: it looks for a file called main.yml inside each subdirectory, and if that subdirectory or file doesn't exist, it just skips it. You don't declare which pieces a role has anywhere — the presence of the folder is the declaration.

Here's what each subdirectory is for, and how it maps to what you've already learned:

  • tasks/main.yml — the list of tasks the role runs, in order. This is exactly the tasks: list from Lesson 6's playbooks, just moved into its own file instead of sitting inline in the play.
  • handlers/main.yml — handlers the role provides, importable into the parent play for use by this role or others in the same play. Same handler mechanics as Lesson 12 (notify:, runs once at the end of the play) — just packaged with the role instead of declared loose.
  • templates/ — Jinja2 template files (they end in .j2, like the ntp.conf.j2 in the tree above) for use with the template module. This is the templating you built in Lessons 13–14, scoped to the role.
  • files/ — static files for use with the copy module, and scripts for use with the script module. Unlike templates, nothing here gets rendered through Jinja2 — what's in the file is exactly what lands on the host.
  • vars/main.yml and defaults/main.yml — both hold variables, same key: value syntax from Lesson 8, but with a deliberate difference covered below.
  • meta/main.yml — metadata about the role: role dependencies (other roles this one requires) and, optionally, Ansible Galaxy metadata if you plan to publish it.

Beyond these, the docs also list library/, module_utils/, and lookup_plugins/ — for shipping custom modules, module utilities, and plugins inside a role. You won't need those as a beginner; they exist for teams extending Ansible itself, not for configuring servers.

defaults/main.yml vs vars/main.yml — same syntax, opposite intent

Both files define variables for the role, and both use the same YAML you learned in Lesson 8. The difference is entirely about how easily the value can be overridden by whoever calls the role:

  • defaults/main.yml holds, in Ansible's own words, "very low precedence values for variables provided by the role." Put a value here when you expect callers to change it — a port number, a package version, a config flag. Defaults exist to be overridden.
  • vars/main.yml holds "high precedence variables provided by the role to the play." Put a value here when it's an internal detail the role depends on to function correctly, and you don't want a caller accidentally breaking the role by overriding it.

Mental model: think of defaults/ as the role's dials — knobs it hands you on purpose, expecting you to turn them. vars/ is the role's internal wiring — values it needs to work correctly, that it isn't offering up for casual tweaking. If you're not sure which one a value belongs in, ask: "would I expect someone reusing this role to want to change this?" Yes → defaults/. No → vars/.

This precedence difference is a small preview of a much bigger topic: Ansible has roughly twenty distinct precedence levels across defaults, vars, inventory variables, play variables, extra vars, and more. Lesson 22 covers the full precedence order in detail — for now, the one fact worth holding onto is: a role's own defaults are the lowest-precedence variable source in the whole system, deliberately, so that almost anything else can override them.

Try it — before looking below

Q1. You're building an nginx role. It needs a handler that restarts the nginx service, a Jinja2 template for nginx.conf, and a variable nginx_port that callers should be free to change to something other than 80. Which subdirectory does each of these three things belong in?

The restart handler goes in handlers/main.yml. The Jinja2 template goes in templates/ (as something like nginx.conf.j2). nginx_port goes in defaults/main.yml — not vars/ — precisely because you want callers to override it easily; that's what low-precedence defaults are for.

Q2. A role has a value in vars/main.yml that a teammate is trying to override by setting the same variable name at the play level. Based on what you've read here, would you expect that override to work easily, or fight against the role?

It fights against the role. vars/main.yml is high-precedence by design, so it's harder for outside values to win against it — that's the whole point of putting a value there instead of in defaults/. If a teammate keeps needing to override something in vars/, that's usually a sign the value belongs in defaults/ instead. The exact precedence order across every variable source is Lesson 22.

Recap
  • A role is a standardized folder structure that packages tasks, handlers, vars, templates, and files around one responsibility — the configuration-layer equivalent of a Terraform module.
  • Standard layout: roles/rolename/{tasks,handlers,vars,defaults,templates,files,meta}/main.yml. Ansible finds each piece by convention — missing subdirectories are just skipped.
  • defaults/main.yml is low-precedence, meant to be overridden by callers. vars/main.yml is high-precedence, meant to stay fixed. Same syntax, opposite intent — full precedence order comes in Lesson 22.
