Conditionals (when)

Lesson 9 gathered facts about a host — things like ansible_facts['os_family']. Facts are only useful if a task can act on them. Right now, every task in your playbooks runs unconditionally on every targeted host, whether it makes sense there or not. A task that installs a package with apt will fail outright on a RedHat host, because apt doesn't exist there. Conditionals fix that: a task can say "only run me if this is true."

Mental model: when is an if statement for a task. The task is still written in the playbook and still shown in the output, but Ansible evaluates the condition first — if it's false, the task is marked skipped and nothing runs. Nothing changed on the host, nothing failed, it simply didn't apply.

The when clause

Add when: to any task, at the same indentation level as name: and the module call. If the expression evaluates to true, the task runs as normal. If it's false, Ansible skips it and reports skipped in the output — you saw that status waiting in the PLAY RECAP counts back in Lesson 6.

- name: Print a message only on Debian-based hosts
  ansible.builtin.debug:
    msg: "This host is Debian-based"
  when: ansible_facts['os_family'] == "Debian"

Common beginner mistake — do NOT use {{ }} inside when. Everywhere else in a playbook (a msg:, a path:) you write {{ my_var }} to reference a variable. Inside when, don't — it's already a raw Jinja2 expression, so the variable name is used directly. Confirmed straight from Ansible's own docs: "The when clause is a raw Jinja2 expression without double curly braces," and "you do not need to use {{ }} to use variables inside conditionals, as these are already implied." Writing when: {{ ansible_facts['os_family'] }} == "Debian" is a syntax error, not just bad style — leave the braces off.

Combining conditions with and / or

Write a when condition exactly like a normal Jinja2/Python boolean expression — and, or, and parentheses all work:

when: (ansible_facts['distribution'] == "CentOS" and
       ansible_facts['distribution_major_version'] == "6") or
      (ansible_facts['distribution'] == "Debian" and
       ansible_facts['distribution_major_version'] == "7")

There's also a shorthand: give when a YAML list instead of one long expression, and Ansible ANDs every item together automatically. This is often easier to read than chaining several conditions with and:

when:
  - ansible_facts['distribution'] == "CentOS"
  - ansible_facts['distribution_major_version'] == "6"

Both forms above check the same thing. Reach for the list form when all conditions must hold (implicit AND); reach for explicit and / or when you need to mix the two or need real OR logic.

The practical case: one playbook, two OS families

This is exactly the problem Lesson 9's facts were building toward. ansible_facts['os_family'] tells you whether a host is Debian-based (Ubuntu, Debian) or RedHat-based (RHEL, Rocky, Fedora). Those two families use different package managers — apt and dnf — so a single "install a package" task can't cover both. With when, you don't need two playbooks; you write both tasks in the same play and let the condition pick the right one per host:

- name: Install web server on any OS family
  hosts: all
  become: true
  tasks:
    - name: Install on Debian-based hosts
      ansible.builtin.apt:
        name: nginx
        state: present
      when: ansible_facts['os_family'] == "Debian"

    - name: Install on RedHat-based hosts
      ansible.builtin.dnf:
        name: nginx
        state: present
      when: ansible_facts['os_family'] == "RedHat"

Run this against a mixed inventory and each host runs exactly one of the two tasks — the other shows skipped for that host. That's the whole point: one playbook, checked into git once, that correctly adapts itself to whatever it's pointed at. This pattern — a pair of OS-specific tasks guarded by ansible_facts['os_family'] — is one of the most common things you'll write in real Ansible code.

Checking a variable is defined

Not every variable is guaranteed to exist — an optional variable from -e, group_vars, or a role default might simply not be set for a given run. Referencing an undefined variable directly is an error, so guard it first with the is defined test:

when: my_var is defined

The opposite test also exists, for the times you specifically want to act only when something is missing:

when: my_var is undefined

is defined and is undefined are Jinja2 tests, not comparisons — no == needed. You'll combine this constantly with the AND-list form above: check a variable is defined first, then check its value, so the second condition never even gets evaluated against a missing variable.

Try it — before looking below

Q1. A play has one task with when: ansible_facts['os_family'] == "Debian", run against a RedHat host. What status does that task show in the output, and does the PLAY RECAP count it as failed?

It shows skipped, not failed. The condition being false is not an error — the task simply didn't apply to that host. The PLAY RECAP's skipped count goes up by one; failed stays at 0.

Q2. What's wrong with when: {{ my_var }} == "yes"?

The {{ }} shouldn't be there. when is already a raw Jinja2 expression, so variables are referenced by name directly: when: my_var == "yes". Adding {{ }} is a syntax error, not just a style slip.

Now write your own

Reuse the localhost inventory from Lesson 4. Create conditional.yml:

- name: Practice conditionals
  hosts: localhost
  tasks:
    - name: Show message only when enabled
      ansible.builtin.debug:
        msg: "The feature flag is on"
      when: enable_feature is defined and enable_feature == "yes"

Now run it twice — once where the condition is true, once where it isn't — using -e to pass the variable on the command line, the same flag you used to pass extra variables earlier in this course:

$ ansible-playbook -i inventory conditional.yml -e "enable_feature=yes"
$ ansible-playbook -i inventory conditional.yml
  • First run: check the TASK [Show message only when enabled] section — it should print the message and show ok.
  • Second run (no -e at all, so enable_feature is undefined): the same task should show skipped instead — that's exactly why the task checks is defined first, so it doesn't error on a missing variable.
  • Compare the skipped count in the PLAY RECAP between the two runs.

Try it yourself before checking the reference command below.

Reveal the reference commands

ansible-playbook -i inventory conditional.yml -e "enable_feature=yes"
# TASK shows "ok" and prints the message, skipped=0

ansible-playbook -i inventory conditional.yml
# TASK shows "skipped" — enable_feature was never set, so "is defined" is false, skipped=1

Recap
  • when: on a task runs it only if the condition is true — false means skipped, not failed.
  • No {{ }} inside when — it's already a raw Jinja2 expression, variables are referenced directly.
  • Combine conditions with and/or, or list several conditions to AND them implicitly.
  • The real-world pattern: pair an apt task (when: ansible_facts['os_family'] == "Debian") with a dnf task (when: ansible_facts['os_family'] == "RedHat") so one playbook adapts to whatever host it's run against.
  • Guard optional variables with when: my_var is defined before checking their value.
