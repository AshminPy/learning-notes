Ansible / Zero to Expert — Lesson 34 of 36 — CAPSTONE

Capstone project: configure a small fleet

This is the capstone — the longest lesson in the course, on purpose. It doesn't teach anything new. It combines a static inventory (Lesson 4), a real role with defaults/templates/handlers (Lessons 16–17), facts (Lesson 9), a vault-encrypted secret (Lesson 26), and a check-mode dry run before a real run (Lesson 29) into one working project: idempotently configuring a small "fleet" of 3 example web servers. Like every hands-on example in this course, it needs zero paid infrastructure — the primary path uses your own machine as all 3 "hosts" at once. If you already have 2-3 real Linux VMs or containers, a stretch step at the end shows exactly what changes to make it real.

What you're building

A role that, given a host, writes that host's own small "site" — an index.html with a per-host welcome message, and a separate, non-public app.conf holding a secret that came from Ansible Vault, never from a plaintext file. Run it against 3 hosts, and you get 3 independent, correctly-templated sites, a secret that never touched git in plaintext, and a second run that changes nothing — proof the whole thing is idempotent, not just "worked once."

Step 0 — project folder

mkdir -p capstone-fleet/roles
cd capstone-fleet
mkdir -p group_vars/web

The layout you're building toward:

capstone-fleet/
├── inventory.ini
├── site.yml
├── group_vars/
│   └── web/
│       ├── vars.yml        # plain — site_title etc.
│       └── secret.yml      # vault-encrypted — admin_api_key
└── roles/
    └── site_web/
        ├── defaults/main.yml
        ├── tasks/main.yml
        ├── handlers/main.yml
        └── templates/
            ├── index.html.j2
            └── app.conf.j2

Step 1 — the inventory

Three "hosts," zero real infrastructure required — every entry points back at your own machine, exactly like Lesson 33's fake-fleet trick, so ansible_connection=local is all each one needs:

# inventory.ini
[web]
web1 ansible_connection=local
web2 ansible_connection=local
web3 ansible_connection=local

If you'd rather point this at real documentation-range addresses for the sake of the exercise looking realistic, group them the same way and add real connection details later — the role itself doesn't change either way:

# inventory.ini — the "real fleet" shape, for reference
[web]
web1 ansible_host=192.0.2.10
web2 ansible_host=192.0.2.11
web3 ansible_host=192.0.2.12

Step 2 — scaffold the role

cd roles
ansible-galaxy role init site_web
cd ..

Fill in only what you need, exactly Lesson 17's pattern — defaults/main.yml for overridable fallbacks:

# roles/site_web/defaults/main.yml
web_root: "/tmp/ansible-capstone/{{ inventory_hostname }}"
site_title: "Capstone Demo"

Step 3 — the templates

The public page — deliberately holds nothing sensitive, just facts (Lesson 9) and the per-host inventory name:

<!-- roles/site_web/templates/index.html.j2 -->
<html>
<body>
  <h1>{{ site_title }}</h1>
  <p>Served from: {{ inventory_hostname }}</p>
  <p>Configured at: {{ ansible_date_time.iso8601 }}</p>
</body>
</html>

The app config — this one holds the secret, and is deliberately kept out of anything a browser would ever serve:

# roles/site_web/templates/app.conf.j2
# app.conf for {{ inventory_hostname }} — not web-served, mode 0600
admin_api_key = {{ admin_api_key }}

Step 4 — the vault-encrypted secret

Exactly Lesson 26's pattern: a plain variable file for anything non-sensitive, a whole separate file encrypted with Vault for the one thing that isn't:

# group_vars/web/vars.yml — plain, safe to read in a PR
site_title: "Capstone Demo — Web Fleet"
# create the encrypted file — opens your editor, encrypts on save
$ ansible-vault create group_vars/web/secret.yml

Type this inside the editor that opens, then save and close:

admin_api_key: "capstone-demo-key-do-not-reuse"

Confirm it's genuinely ciphertext on disk, the same check Lesson 26 walked through:

$ cat group_vars/web/secret.yml
$ANSIBLE_VAULT;1.1;AES256
663835...  # unreadable — exactly what you want to see

Step 5 — the tasks and handler

# roles/site_web/tasks/main.yml
---
- name: ensure web root exists
  ansible.builtin.file:
    path: "{{ web_root }}"
    state: directory
    mode: '0755'

- name: deploy the public index page
  ansible.builtin.template:
    src: index.html.j2
    dest: "{{ web_root }}/index.html"
    mode: '0644'
  notify: reload site

- name: deploy the app config (holds the vaulted secret)
  ansible.builtin.template:
    src: app.conf.j2
    dest: "{{ web_root }}/app.conf"
    mode: '0600'
  notify: reload site
# roles/site_web/handlers/main.yml
---
- name: reload site
  ansible.builtin.file:
    path: "{{ web_root }}/.reloaded"
    state: touch

The handler stands in for "restart the web service" from Lesson 12 — it only fires when a task above it actually reported changed, and only once per host per run, no matter how many of the two tasks changed.

Step 6 — the playbook

# site.yml
---
- hosts: web
  become: false
  roles:
    - site_web

Step 7 — dry run first

Lesson 29's rule, applied for real before anything touches disk: --check --diff shows you exactly what would be created, with nothing actually written:

$ ansible-playbook site.yml -i inventory.ini --check --diff --ask-vault-pass
# read every task's diff output — confirm index.html and app.conf
# would be created with the values you expect, for all 3 hosts

Try it — before looking below

Q1. You run the playbook for real, then immediately run the exact same command again with nothing else changed. What should the second PLAY RECAP show for every host, and what would it mean if it didn't?

Every host should show changed=0 — the file and template modules both check current state before writing anything, so a second run with identical inputs has nothing left to do (Lesson 7). If a host showed changed=1 or more on the second run with no inputs changed, that's a sign the templates or tasks aren't actually idempotent — for example a task that always reports changed regardless of real state, which is exactly the failure mode Lesson 7 warned about with raw shell/command tasks.

Q2. group_vars/web/secret.yml is safe to commit to git. The vault password used to create it is not. Why is that split safe, and what would break the whole design if you got it backwards?

secret.yml is genuinely encrypted ciphertext on disk — committing it exposes nothing without the vault password, exactly Lesson 26's model. The vault password is the one thing that actually unlocks it. If you committed the vault password (in a file, in the workflow, anywhere in git) instead of keeping it out entirely, you'd have put the key right next to the lock — anyone who can read the repo could decrypt admin_api_key, making the encryption pointless.

Step 8 — run it for real, then verify

$ ansible-playbook site.yml -i inventory.ini --ask-vault-pass

$ cat /tmp/ansible-capstone/web1/index.html
$ cat /tmp/ansible-capstone/web2/index.html
# confirm "Served from: web1" / "web2" differ — same template, per-host data

$ cat /tmp/ansible-capstone/web1/app.conf
# confirm admin_api_key is the plaintext value you typed in Step 4 —
# proof Ansible decrypted it correctly at run time

$ ls -l /tmp/ansible-capstone/web1/app.conf
# confirm mode is 0600 — not world-readable, unlike index.html's 0644

Then prove idempotency directly — re-run the exact same command:

$ ansible-playbook site.yml -i inventory.ini --ask-vault-pass
# PLAY RECAP: changed=0 for web1, web2, web3 — nothing left to do

Optional stretch: a real web server

If you have 2-3 real Linux VMs or Docker containers available, the same role becomes a real one with two additions: a task installing and starting an actual web server package (ansible.builtin.package, conditioned on ansible_facts['os_family'] the way Lesson 10 taught), and pointing web_root at that server's real document root instead of /tmp. The inventory, the vault file, the templates, and the handler pattern don't need to change at all — that's the whole benefit of having built this on roles and variables instead of one-off commands.

Commit it, minus the secret

Same discipline Lesson 26 established, now applied to a whole project:

# .gitignore
*.retry
/tmp/ansible-capstone/

Commit everything, including group_vars/web/secret.yml — it's ciphertext, that's the point. Never commit the vault password itself, in any form, anywhere in the repo.
