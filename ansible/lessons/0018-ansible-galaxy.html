Ansible Galaxy

Lesson 17 showed you how to package a task list into a reusable role. But you don't have to write every role yourself. Most of what you need — an Nginx setup, a Docker install, a firewall baseline — has already been written, tested, and shared by someone else. Ansible Galaxy is where that shared work lives.

Mental model: Galaxy is to roles what a package registry (npm, PyPI, the Terraform Registry) is to code — a public hub where the community publishes reusable units, and you pull one down instead of writing it from scratch. Same trust model too: anyone can publish, so you are still responsible for checking what you install before it runs in production.

What galaxy.ansible.com actually hosts

galaxy.ansible.com is the public hub for two kinds of shareable content:

  • Roles — the reusable task-list units from Lesson 17, published under a namespace.role_name format (for example geerlingguy.nginx, a well-known community role).
  • Collections — a bigger packaging format that bundles roles, modules, plugins, and playbooks together. Collections are Lesson 19's topic in full; for now, just know Galaxy hosts both, and the install pattern you're about to learn works for both.

Anyone can publish to Galaxy — individuals, vendors, and Red Hat itself all use it. That openness is exactly why the vetting habit later in this lesson matters.

Installing a single role

The command follows the same shape as the ad-hoc and playbook commands you already know:

$ ansible-galaxy role install namespace.role_name

For example, to install the popular Nginx role:

$ ansible-galaxy role install geerlingguy.nginx

By default this downloads into your configured roles path (often ~/.ansible/roles or a roles/ folder next to your playbook, depending on your config). Once it's there, you use it in a playbook exactly like the role you wrote by hand in Lesson 17:

- name: Configure web servers
  hosts: webservers
  roles:
    - geerlingguy.nginx

Pinning roles with requirements.yml

Installing one role by name is fine for trying something out. But a real project depends on several roles, and every teammate — plus your CI pipeline — needs to install the exact same set. That's what a requirements.yml file is for: one file that lists every role your project needs, with the version pinned.

roles:
  - name: geerlingguy.nginx
    version: "3.1.4"

  - name: geerlingguy.docker
    version: "7.4.4"

  - src: https://github.com/bennojoy/nginx
    version: "ee8aa41"

Install everything the file lists in one command:

$ ansible-galaxy install -r requirements.yml

Read the keys: name is the namespace.role_name to pull from Galaxy (or a custom download name), src can point at a Galaxy name or a raw git URL, and version pins a release tag, commit hash, or branch. If you skip version, Ansible installs whatever the latest release happens to be at the moment you run the command — and that moment is different for every teammate, every CI run, and every re-run six months from now.

Mental model — same discipline as Terraform module versioning: if you've taken the Terraform course, this is the exact same lesson wearing a different hat. An unpinned module source resolves to "whatever is latest today," which silently changes under you later. An unpinned Galaxy role does the same thing. The fix in both cases is identical: pin the version, commit the pin to git, and only bump it on purpose, after testing.

Vet a role before it touches production

Anyone can publish to Galaxy — that's the same openness the Terraform Registry has for community modules, and it comes with the same responsibility: check what you're pulling in before it runs on real infrastructure. Before you depend on a Galaxy role for anything that matters, check:

  • Maintenance activity — when was the last commit or release? A role untouched for years may not work against current Ansible versions or target OS releases.
  • Download counts — Galaxy shows this on each role's page. High usage doesn't guarantee quality, but near-zero usage means almost nobody has found its bugs for you yet.
  • Open issues — check the linked source repository (usually GitHub). A long list of unresolved bug reports is a signal to read the code yourself before trusting it.

This is the same checklist the Terraform course teaches for registry modules — because it's the same underlying risk: third-party code you didn't write, running with the permissions you gave it.

Try it — before looking below

Q1. Your team's playbook depends on a community role with no version pinned in requirements.yml. Six months later, a fresh ansible-galaxy install -r requirements.yml pulls a different version than what you tested. What's the fix?

Add a version: key under that role's entry in requirements.yml, pinned to the release tag (or commit hash) you actually tested against — then commit that file to git. From then on, everyone and every CI run installs the exact same version, and you only move to a newer one deliberately, after testing it. This is the same fix as an unpinned Terraform module source: unpinned third-party content is a moving target, and "it worked when I tested it" isn't true anymore once the version underneath you has silently changed.

Now try it yourself

In your practice project folder:

  • run ansible-galaxy role install geerlingguy.timezone (a small, low-risk role good for practice) and note where it installed
  • create a requirements.yml with that same role, pinned to a specific version: — check the role's Galaxy page for a real release tag to use
  • run ansible-galaxy install -r requirements.yml and confirm it installs that exact pinned version
  • open the role's page on galaxy.ansible.com and check its last-updated date and download count before you'd trust it further

Recap
  • Ansible Galaxy (galaxy.ansible.com) is the public hub for community and vendor roles and collections — collections are covered fully in Lesson 19.
  • Install one role with ansible-galaxy role install namespace.role_name; install a whole project's set from a requirements.yml with ansible-galaxy install -r requirements.yml.
  • Always pin version: in requirements.yml — unpinned third-party content is a moving target, the same discipline as pinning Terraform module versions.
  • Vet a role before production use: check maintenance activity, download counts, and open issues, same as vetting a Terraform Registry module.
