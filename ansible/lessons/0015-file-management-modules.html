File & directory management modules

You've already used ansible.builtin.file once — back in Lesson 6, to create a directory. And in Lesson 14 you used ansible.builtin.template to write a whole config file from scratch. But most of the time, managing files on a server isn't "create a directory" or "replace an entire file" — it's smaller than that: set the right permissions on something that already exists, tweak one line in a config file without touching the rest of it, or check whether a file is there before deciding what to do next. This lesson covers the three modules that do exactly that: file (properties of files/dirs/links), lineinfile (surgical single-line edits), and stat (check-before-you-act).

Mental model: template and copy (Lesson 14) own the whole file — every run, the destination becomes an exact copy of your source. file, lineinfile, and stat don't own the whole file — they make one narrow, targeted change (or just look) and leave everything else alone. Reach for the narrow tool when the change is narrow; reach for template/copy when you own the whole file's content.

file — properties of files, directories, and links

In Lesson 6 you only saw state: directory. The file module actually manages four different kinds of filesystem objects, all through the same state parameter:

  • state: directory — ensure a directory exists (creates it, and any missing parent directories, if it doesn't).
  • state: file — assert a file exists and manage its attributes; it does not create the file's content. If the file isn't already there, this fails — pair it with lineinfile's create: true or with copy/template to actually create content.
  • state: absent — remove the file, directory (recursively), or link, if it's there. Nothing happens if it's already gone — idempotent by design.
  • state: link — create a symbolic link. Needs src (what the link points to) and path (where the link itself lives).

Whatever the state, you can also set ownership and permissions on the same task with mode, owner, and group:

- name: Change file ownership, group and permissions
  ansible.builtin.file:
    path: /etc/foo.conf
    owner: foo
    group: foo
    mode: '0644'

Removing a file, and creating a symlink, confirmed against the official examples:

- name: Remove file (delete file)
  ansible.builtin.file:
    path: /etc/foo.txt
    state: absent

- name: Create a symbolic link
  ansible.builtin.file:
    src: /file/to/link/to
    dest: /path/to/symlink
    owner: foo
    group: foo
    state: link

Best practice — always quote mode. Write mode: '0644', not mode: 0644. Without quotes, YAML may parse the number differently than you expect (leading zeros are ambiguous across YAML parsers). A quoted string removes the ambiguity — Ansible's own docs use this style everywhere.

lineinfile — one correct line, nothing else touched

Sometimes you don't own a whole config file — it's mostly managed by hand, or by another tool, and you just need to guarantee one specific line is present and correct. Rewriting the whole file with template would be overkill and risky (you'd have to recreate every other line perfectly). lineinfile does one narrow thing: find a line matching a pattern, and make sure it says what you want.

- name: Ensure SELinux configuration
  ansible.builtin.lineinfile:
    path: /etc/selinux/config
    regexp: '^SELINUX='
    line: SELINUX=enforcing
    state: present
    backup: yes

Key parameters, confirmed against the official docs:

  • path — the file to modify (required).
  • line — the exact line you want present (required when state: present).
  • regexp — a pattern used to find the line to replace. This is the parameter that makes lineinfile idempotent — without it, Ansible has no way to recognize "this line is already there" versus "add a new one."
  • state — present (default) or absent to remove a matching line instead.
  • create — if true, creates the file when it doesn't exist yet (default false — Ansible will otherwise fail rather than silently create a file you didn't expect).
  • backup — if true, keeps a timestamped copy of the file before changing it.
  • insertafter / insertbefore — if regexp doesn't match anything, where to add the new line (a pattern to insert after/before, or the literal EOF/BOF for end/beginning of file).

Mental model — why regexp is the whole trick: lineinfile doesn't compare the line you're adding to what's in the file byte-for-byte. It runs regexp against every line in the file. If a line matches, that line gets replaced with line (and if it already equals line, nothing changes — ok, not changed). If nothing matches, your line gets inserted fresh. The docs are explicit about this: your regexp should match the line both before and after your change, or every run will look like a fresh insert instead of a clean idempotent update. Write the regexp to match the setting (e.g. ^SELINUX=), not the exact value — otherwise it can never find and fix a wrong value.

stat — look before you act

Sometimes a task should only run if something already exists — or doesn't. stat gathers information about a path (does it exist, is it a file or directory, what are its permissions) without changing anything. On its own it's not very useful; paired with register and the when conditional from Lesson 10, it becomes the standard "check first, act second" pattern:

- name: Get file statistics
  ansible.builtin.stat:
    path: /etc/myconfig.conf
  register: config_stat

- name: Process if file exists
  ansible.builtin.debug:
    msg: "File found and readable"
  when: config_stat.stat.exists and config_stat.stat.readable

Two things to notice in that pattern:

  • register: config_stat saves the module's result into a variable — same mechanism you'd use to capture output from any module, not specific to stat.
  • The useful data lives one level deeper, under .stat — so it's config_stat.stat.exists, not config_stat.exists. This trips people up the first time; the module's top-level result always has a stat key holding the actual dictionary of properties (exists, isdir, mode, size, and more).

Best practice — check for existence, don't assume. A task that unconditionally tries to read or copy a file that might not be there will fail the whole run for that host. Running stat first and gating the real task with when: some_stat.stat.exists turns a hard failure into a clean, predictable skip — visible as skipped in the recap, exactly like you saw in Lesson 6's PLAY RECAP walkthrough.

Try it — before looking below

Q1. You run lineinfile with line: "PORT=8080" but no regexp. The file already has a line PORT=8080. You run the playbook twice. What happens on the second run?

Without a regexp, lineinfile falls back to matching the exact line text itself to decide whether it's already present. If the file already contains a line that's byte-for-byte identical to line, the second run reports ok (no change) — it won't duplicate the line. But this only works cleanly when the value never needs to change; if you later need to update PORT=8080 to PORT=9090, matching on the exact old line would fail to find anything to replace, and you'd end up with two lines. That's why a regexp like '^PORT=' that matches the setting name, independent of its value, is the safer habit.

Q2. A task uses ansible.builtin.file with state: file on a path that doesn't exist yet. What happens?

The task fails. state: file asserts the file already exists and lets you manage its attributes (mode, owner, group) — it does not create content for you, unlike state: directory, which will create the directory. If the file needs to be created from scratch, use copy, template, or lineinfile with create: true instead.

Now write your own

Reuse the localhost inventory from Lesson 4. In the same folder, create a starting file to work with:

$ echo "APP_ENV=dev" > /tmp/app.conf

Then write file-management.yml:

- name: Practice file, lineinfile, and stat
  hosts: localhost
  tasks:
    - name: Lock down permissions on the config file
      ansible.builtin.file:
        path: /tmp/app.conf
        mode: '0640'

    - name: Ensure APP_ENV is set to prod
      ansible.builtin.lineinfile:
        path: /tmp/app.conf
        regexp: '^APP_ENV='
        line: APP_ENV=prod
        state: present

    - name: Check if a marker file already exists
      ansible.builtin.stat:
        path: /tmp/app-configured.marker
      register: marker

    - name: Create the marker (only if it wasn't already there)
      ansible.builtin.file:
        path: /tmp/app-configured.marker
        state: touch
      when: not marker.stat.exists

Then:

  • run ansible-playbook -i inventory file-management.yml
  • check the permissions: ls -l /tmp/app.conf — confirm it shows -rw-r----- (0640)
  • check the content: cat /tmp/app.conf — confirm it now reads APP_ENV=prod, not APP_ENV=dev
  • find the TASK [Create the marker...] section — it should show changed, since the marker didn't exist yet
  • run the exact same command a second time. Watch the last task: it should now show skipped, because marker.stat.exists is true the second time round

Recap
  • file manages properties of an existing filesystem object via state: directory (create it), file (assert it exists, manage attributes), absent (remove it), link (symlink) — plus mode/owner/group on any of them. Always quote mode, e.g. '0644'.
  • lineinfile surgically ensures one line is present/correct in a file that already exists, without touching the rest of it. Its idempotency depends on regexp matching the setting, not the exact value — match the key, not the value, so future changes stay idempotent.
  • stat inspects a path (existence, type, permissions) without changing anything. Pair it with register and Lesson 10's when to skip tasks based on a file's presence — the result lives under <var>.stat.<field>, e.g. marker.stat.exists.
