Jinja2 templating basics

Since Lesson 8 you've been writing {{ variable_name }} without asking where that syntax comes from. Time to answer that: it's Jinja2, a Python templating language Ansible uses under the hood. Every {{ }} substitution you've done so far is Jinja2 doing exactly one of its jobs — dropping a value into a string. Jinja2 can do a lot more than that: transform values on the way out, decide what text to include, and repeat a block of text for every item in a list. This lesson covers those three things, all still as plain text — no new Ansible module yet. Lesson 14 wires this into the template module to generate real config files.

Mental model: Jinja2 is a text-generation language. Feed it a template (text with {{ }} and {% %} markers) plus some variables, and it renders out plain text — no markers left, just the final result. Everything in this lesson is about controlling what that final text looks like: which value gets substituted (filters), whether a chunk of text appears at all ({% if %}), and how many times a chunk repeats ({% for %}).

Filters — transform a value with a pipe

A filter changes a value on its way into the output, using the pipe character | after the variable. Confirmed against Jinja2's own docs, the shape is:

{{ variable | filter_name }}
{{ variable | filter_name(argument) }}

Three filters you'll use constantly:

  • default — supply a fallback if the variable is undefined. Straight from Ansible's own docs: {{ some_variable | default(5) }} — if some_variable isn't defined, Ansible uses 5 instead of raising an "undefined variable" error and failing the whole run.
  • length — count items in a list (or characters in a string): {{ my_list | length }}.
  • upper (and its opposite, lower) — change case: {{ ansible_hostname | upper }} turns web01 into WEB01.

Filters chain left to right, same idea as piping commands in a shell: {{ my_list | length | default(0) }} feeds the result of length into default. And filters aren't an Ansible invention grafted on — the docs are explicit: "you can use all the standard filters and tests included in Jinja2," plus Ansible adds a handful of its own on top (you'll meet more of those later in the course). default, length, and upper/lower are all standard Jinja2, so they work anywhere Jinja2 runs, not just in Ansible.

Why default matters more than it looks: without it, referencing an undefined variable stops your playbook cold with an error. {{ retries | default(3) }} means "use retries if someone set it, otherwise assume 3" — the same idea as a function parameter with a default value. You'll reach for this constantly once you start writing reusable templates and roles.

{% if %} — conditional text, not a conditional task

Lesson 10 taught when: — a playbook keyword that decides whether a task runs at all. Jinja2's {% if %} looks similar but does something different: it decides whether a chunk of text appears in the rendered output. You're not inside a playbook's YAML structure anymore — you're inside a template, and {% if %} is Jinja2 deciding what to write to the file.

{% if ansible_facts['os_family'] == "Debian" %}
This is a Debian-based system.
{% else %}
This is not a Debian-based system.
{% endif %}

Render that with a Debian host's facts, and the output is just the line This is a Debian-based system. — the {% if %}, {% else %}, and {% endif %} markers themselves never appear in the result; Jinja2 consumes them while deciding which branch of plain text to keep.

{% for %} — repeating text, not repeating a task

Same relationship applies to loops. Lesson 11's loop: repeats a task once per item, with results you can see per item in the playbook run. Jinja2's {% for %} repeats a block of text once per item, inside a template — there's no task, no per-item "ok/changed" output, just more lines of rendered text.

{% for user in user_list %}
{{ user }}
{% endfor %}

Given user_list: [alice, bob, carol], this template renders three lines — alice, bob, carol — one per loop iteration, with the {% for %}/{% endfor %} markers gone from the output, exactly like {% if %}. Jinja2 also exposes a loop variable inside the block — loop.index (1-based position), loop.first, loop.last — useful for things like adding a comma after every line except the last. You won't need those yet; just know they exist for when a template gets fussier about formatting.

Mental model recap: when: and loop: are playbook keywords — they control which tasks execute and how many times. {% if %} and {% for %} are Jinja2 control structures — they control what text comes out of a template. Same-looking job (decide / repeat), completely different layer: one operates on tasks in a playbook run, the other operates on text inside a single file being rendered.

Q2. What's the actual difference between a playbook's when: keyword and a template's {% if %} block — they both look like "conditionals," so what changes?

when: decides whether a task runs during the playbook — you'd see it as skipped in the output. {% if %} lives inside a template file and decides whether a chunk of text appears in the rendered result — there's no task and no "skipped" status, the text is either in the generated file or it isn't.

Recap
  • Jinja2 is the templating engine behind every {{ }} you've written since Lesson 8 — it renders a template plus variables into plain text.
  • Filters transform a value with a pipe: {{ variable | default('fallback') }}, {{ list | length }}, {{ string | upper }}. They're standard Jinja2, not Ansible-only, and they chain left to right.
  • {% if %}/{% endif %} and {% for %}/{% endfor %} are Jinja2 control structures inside a template — they decide what text gets rendered, unlike the playbook keywords when: (Lesson 10) and loop: (Lesson 11), which decide whether/how many times a task runs.
  • Everything here is still plain Jinja2 text, not yet a real file on disk — Lesson 14's template module is what actually renders a .j2 file to a destination path.
