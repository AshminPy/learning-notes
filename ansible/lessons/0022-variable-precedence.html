Variable precedence deep dive

You now know five different places a variable can come from: a role's defaults/main.yml (Lesson 16), inventory group_vars/host_vars (Lesson 21), a play's vars: (Lesson 8), a role's vars/main.yml (Lesson 16), and -e/--extra-vars on the command line (Lesson 8). Each one made sense in isolation. The question this lesson answers: what happens when the same variable name is set in more than one of those places, to different values? Ansible doesn't error out or merge them — it picks exactly one, by a fixed, documented order. This lesson is that order, in full, verified against Ansible's own precedence table.

Mental model: think of it as a stack of sticky notes on a variable's name, one from each source that set it. Ansible doesn't look at every note — it looks at the note on top of the stack and uses that value, full stop. "Top of the stack" is decided by how specific and how "in-the-moment" the source is: a role's generic fallback goes to the bottom, a value you typed on the command line for this one run goes to the top.

The full precedence order — lowest to highest

This is Ansible's complete, official list, confirmed against the current docs. When the same variable is set in two or more of these, the one further down this list wins:

  1. Command-line values (for example -u my_user — these aren't playbook variables, just here for completeness)
  2. Role defaults (roles/x/defaults/main.yml) — Lesson 16
  3. Inventory file or script group vars
  4. Inventory group_vars/all
  5. Playbook group_vars/all
  6. Inventory group_vars/*
  7. Playbook group_vars/*
  8. Inventory file or script host vars
  9. Inventory host_vars/*
  10. Playbook host_vars/*
  11. Host facts and cached set_facts
  12. Play vars: — Lesson 8
  13. Play vars_prompt
  14. Play vars_files
  15. Role vars (roles/x/vars/main.yml) — Lesson 16
  16. Block vars (for tasks in that block only)
  17. Task vars (for that task only)
  18. include_vars
  19. Registered vars and set_facts
  20. Role (and include_role) params
  21. include params
  22. Extra vars (-e "user=my_user") — always wins, no exceptions

Twenty-two entries is a lot to hold in your head, and most Ansible work doesn't need all of it — some of these (block vars, include_vars, registered vars) belong to topics later in this course. What you need today is the shape of the list and where your five known sources land in it.

Your five sources, in order

Pulling just the sources you've actually used out of the full list above, lowest to highest:

  1. Role defaults (defaults/main.yml) — position 2, the floor
  2. Inventory group_vars / host_vars — positions 3–10, several tiers above role defaults
  3. Play vars: — position 12
  4. Role vars (vars/main.yml) — position 15
  5. Extra vars (-e) — position 22, the ceiling

So for these five, the win order is: -e beats role vars, role vars beats play vars:, play vars: beats inventory group_vars/host_vars, and inventory group_vars/host_vars beats role defaults. Role defaults lose to all four of the others, every time.

The trap hiding in plain sight: a role has both a defaults/ folder and a vars/ folder, and the names look almost interchangeable — "defaults" and "vars," both just variables for the role. They are not the same tier. defaults/main.yml sits at position 2 (rock bottom, meant to be overridden). vars/main.yml sits at position 15 — higher than a play's own vars: block. If you move a value from a role's defaults/ to its vars/ thinking it's a harmless rename, you've just made it much harder for anyone — including you — to override.

Practical takeaway: design for predictable overrides

You don't memorize this table to recite it — you use it to decide, on purpose, where a new variable should live. Two rules do most of the work:

  • -e on the command line always wins. That's exactly why it's the right tool for a one-off override — a single test run, a one-time hotfix value — without touching any file. It cannot be silently out-ranked by anything else in the list.
  • Role defaults/ always loses. That's not a limitation, it's the design. A role default is a sane fallback the role ships with so it works out of the box — and because it sits at the bottom, literally any other source (inventory vars, play vars, even another role) can override it without a fight.

The general design guidance that falls out of this: put a variable in the lowest-precedence place that still gets the job done. If a value genuinely never changes per-host or per-environment, a role default is enough. If it needs to differ per group of hosts, inventory group_vars is the right altitude — not a role's vars/ folder, which sits above play vars and is much harder to override later. Reaching for a higher tier than you need doesn't make the value "more official" — it just makes every future override an uphill fight against precedence, instead of the easy, expected kind.

Try it — before looking below

Q1. A variable greeting is set to three different values: "from role defaults" in roles/demo/defaults/main.yml, "from group_vars" in your inventory's group_vars/all.yml, and "from extra vars" passed with -e "greeting=from extra vars" on the command line. Which value does the task actually see?

"from extra vars." Extra-vars (-e) sit at the top of the precedence order and always win — no other source, including inventory group_vars, can outrank them. If you then removed the -e flag, group_vars/all.yml would win next: inventory group vars (position 4) outrank role defaults (position 2). Role defaults only win if nothing else sets the variable at all.

Q2. A role has greeting: "role default" in defaults/main.yml and also greeting: "role var" in vars/main.yml. No play vars:, no inventory vars, no -e. Which one wins, and why does it matter that they're in different folders?

"role var" wins. vars/main.yml (position 15) outranks defaults/main.yml (position 2) within the very same role. It matters because the two folders look similar but serve opposite purposes: defaults/ is meant to be easily overridden by the person using the role, while vars/ is meant to hold values the role author does not want casually overridden. Putting a value in the wrong one flips who's actually in control of it.

Now prove it yourself

Build the exact three-way scenario from Q1 and watch the precedence order play out for real.

Create a role with a default value:

$ mkdir -p roles/demo/defaults roles/demo/tasks
$ cat > roles/demo/defaults/main.yml <<'EOF'
greeting: "from role defaults"
EOF

$ cat > roles/demo/tasks/main.yml <<'EOF'
- name: Show the greeting
  ansible.builtin.debug:
    msg: "{{ greeting }}"
EOF

Create a minimal playbook that uses the role, and an inventory with a group_vars/all.yml override:

$ cat > site.yml <<'EOF'
- hosts: localhost
  roles:
    - demo
EOF

$ mkdir -p group_vars
$ cat > group_vars/all.yml <<'EOF'
greeting: "from group_vars"
EOF

Now run it three ways and watch greeting change:

# 1. no overrides: role default is the only source that set it... or is it?
$ ansible-playbook -i localhost, site.yml
# msg should show "from group_vars" — group_vars outranks role defaults

# 2. same run, now add -e
$ ansible-playbook -i localhost, site.yml -e "greeting=from extra vars"
# msg should show "from extra vars" — -e outranks everything

That first run is the one worth pausing on: even with zero flags, the role default already lost — to group_vars/all.yml, which was sitting there quietly. That's precedence working exactly as documented, not a bug. If you'd expected the role default to show up, this exercise is exactly why Lesson 22 exists.

Recap
  • Ansible resolves a variable set in multiple places using one fixed, documented precedence order — the higher source wins completely, nothing merges.
  • Of the five sources you know: role defaults (lowest) < inventory group_vars/host_vars < play vars: < role vars/main.yml < -e/extra-vars (highest).
  • -e always wins — use it for one-off overrides. Role defaults/ always loses — that's what makes it a safe, easy-to-override fallback.
  • Design rule: put a variable in the lowest-precedence place that still gets the job done, so future overrides stay predictable instead of fighting the precedence order.
