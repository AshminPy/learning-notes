copy vs template modules

Lesson 13 taught you Jinja2 — {{ }} for values, {% %} for logic, and how to render a .j2 file into something concrete. But rendering it in your head isn't the same as getting Ansible to render it onto a real host. You've actually already met both modules that do this: Lesson 6's example playbook used ansible.builtin.template to write an Apache config, and Lesson 12's handler demo used ansible.builtin.copy to write a plain file. This lesson makes the difference between them explicit, and gives you a rule for picking the right one every time.

Mental model: copy is a photocopier — whatever is on the page on the control node is exactly what lands on the managed host, byte for byte. template is a mail-merge — it takes a .j2 file, fills in the {{ }} blanks with real values for this specific host, and only then produces the page that gets copied over. Same delivery mechanism underneath, completely different question about whether the content changes per host.

copy: exact, no substitution

ansible.builtin.copy takes a file from the control node and places it on the managed host unchanged. If the source file contains the literal text {{ ansible_hostname }}, that literal text — braces and all — is what ends up on the remote host. Nothing in copy looks at Jinja2 syntax; it just moves bytes.

- name: Copy a static config file
  ansible.builtin.copy:
    src: files/motd.txt
    dest: /etc/motd
    owner: root
    group: root
    mode: '0644'

Confirmed against Ansible's own docs: copy's required parameter is dest (where the file goes), and src is the local path on the control node to copy from. You can also skip a source file entirely and hand it a string directly with content:, which is what Lesson 12's handler demo did to write a file inline without needing a separate file on disk.

template: render first, then copy

ansible.builtin.template takes a .j2 file, processes it through the Jinja2 engine — resolving every {{ }} variable and {% %} block from Lesson 13 using real values for the host it's running against — and only then writes the rendered result to the destination. The module name is honest about the order: template first, copy second.

- name: Template a config file per host
  ansible.builtin.template:
    src: templates/app.conf.j2
    dest: /etc/app.conf
    owner: root
    group: root
    mode: '0644'

Confirmed against Ansible's own docs: src is "path of a Jinja2 formatted template on the Ansible controller," and dest is "location to render the template to on the remote machine" — the word render there is doing real work, it's not just a copy. By convention, template source files end in .j2 so it's obvious at a glance that a file has substitutions in it, though Ansible itself doesn't require the extension.

The decision rule

One question settles it every time: does this file need to differ per host or per environment?

  • No — the content is identical everywhere. A license file, a static binary config, a README dropped onto every server. Use copy. There's nothing to render, so don't reach for a templating engine you don't need.
  • Yes — something in the file depends on the host, environment, or a variable. A config file where the port, hostname, environment name, or a list of upstream servers changes between dev/staging/prod, or between individual hosts. Use template, and pull in variables the way Lesson 8 (variables) and Lesson 9 (facts) taught you.

Best practice: if you ever catch yourself writing a separate near-identical static file per host or per environment just to work around copy not substituting values, that's a sign the file should be one .j2 template with template instead. One template plus variables beats five almost-identical copies you have to keep in sync by hand.

Both are idempotent — this ties back to Lesson 7

Neither module blindly overwrites the destination every run. Both check the destination's actual content first and only report changed — and only write — when it differs from what should be there. Ansible's own docs confirm this for both: copy "will only set the changed state if the destination content is being modified," and template works the same way, comparing the freshly rendered content against what's already on disk. Run either task twice with nothing else different, and the second run reports ok, not changed — exactly the idempotency rule from Lesson 7, applied to file content instead of a directory's existence.

Both notify a handler the same way — this ties back to Lesson 12

This is the classic pattern Lesson 12 already named: template (or copy) a config file, then notify a handler that restarts the service that reads it. The restart only fires when the config genuinely changed, because notify only queues a handler when the notifying task reports changed — and you now know exactly what makes these two modules report changed in the first place.

- name: Write nginx config from a template
  ansible.builtin.template:
    src: templates/nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    mode: '0644'
  notify:
    - Restart nginx

handlers:
  - name: Restart nginx
    ansible.builtin.service:
      name: nginx
      state: restarted

Swap template for copy in that task and the pattern is identical — the only thing that changed is whether the source file has {{ }} in it that needs resolving before it lands on the host.

Try it — before looking below

Q1. A source file on the control node contains the line Welcome to {{ ansible_hostname }}. You copy it to a host using ansible.builtin.copy. What does the destination file contain?

The literal text Welcome to {{ ansible_hostname }}, braces included. copy does not process Jinja2 at all — it moves the file exactly as it is. To get the hostname actually substituted in, the file needs to be a .j2 template rendered with ansible.builtin.template instead.

Q2. You run a playbook with a template task that has notify: Restart service. The rendered content turns out to be byte-for-byte identical to what's already on the host. Does the handler run?

No. template is idempotent — if the rendered content matches the destination exactly, the task reports ok, not changed. Since notify only queues a handler when its task reports changed, the handler never fires. Same rule as Lesson 12, now driven by content comparison instead of a simpler check.

Now write your own

Reuse the localhost inventory from earlier lessons. In the same folder, create a template source file called message.txt.j2:

Hello from {{ ansible_hostname }}!
This file was rendered by the template module.

Now create copy-vs-template.yml:

- name: copy vs template demo
  hosts: localhost

  tasks:
    - name: Render the message with template (substitutes the variable)
      ansible.builtin.template:
        src: message.txt.j2
        dest: /tmp/rendered-with-template.txt

    - name: Copy the same file with copy (does NOT substitute)
      ansible.builtin.copy:
        src: message.txt.j2
        dest: /tmp/copied-with-copy.txt

Then:

  • run ansible-playbook -i inventory copy-vs-template.yml
  • check both task statuses in the output — expect changed on both, since neither destination file exists yet
  • read the rendered file: cat /tmp/rendered-with-template.txt — it should show your real hostname, no braces
  • read the copied file: cat /tmp/copied-with-copy.txt — it should still show the literal {{ ansible_hostname }}, unresolved, because copy never touches Jinja2 syntax
  • run the exact same command a second time — both tasks should now report ok, confirming both modules are idempotent
  • clean up: rm -f /tmp/rendered-with-template.txt /tmp/copied-with-copy.txt

Recap
  • copy moves a file exactly as-is — no Jinja2 processing, even if the file happens to contain {{ }}. template renders a .j2 file's Jinja2 first, then writes the rendered result.
  • Decision rule: content identical everywhere → copy. Content needs to differ per host/environment → template.
  • Both are idempotent (Lesson 7) — they compare content before writing, so a second run with nothing changed reports ok. Both can notify a handler (Lesson 12) — the classic pattern is template/copy a config, notify a "restart service" handler.
