CI/CD for Ansible

Every playbook you've written so far, you've run yourself, from your own terminal. That's fine for learning. It's a real problem in production: "someone's laptop" is now the only thing standing between a typo and a broken fleet — no review, no lint, no staging check, no record of who ran what. A real team runs Ansible from a pipeline instead, the same way Lesson 27's ansible-lint and Lesson 29's check/diff mode exist to catch problems before a human types "yes."

Mental model: think of a pipeline as a series of gates, each one guarding the next. A change can't reach production until it's walked through every gate in order — lint, syntax, a dry run against a safe copy of production, then the real thing. Skipping a gate doesn't make the pipeline faster; it just moves the failure from "caught in 30 seconds by a robot" to "caught at 2am by a human."

The four gates

A realistic Ansible pipeline is a sequence, each stage depending on the previous one passing:

GateWhat it checksTool
1. LintStyle, known-bad patterns, deprecated syntax — before anything even runsansible-lint (Lesson 27)
2. Syntax checkThe YAML and playbook structure actually parsesansible-playbook --syntax-check
3. Dry run against stagingWhat would change, on a real (but safe) inventory, with nothing actually touchedansible-playbook --check --diff (Lesson 29)
4. ApplyThe real run — staging first, production only after that succeeds (often gated by a human approval)ansible-playbook

Notice the order: cheapest, fastest checks first. Lint takes seconds and needs no inventory at all. Syntax check takes seconds too. Only once both pass does the pipeline spend the time to actually connect to staging hosts. This is the same "fail fast, fail cheap" logic behind any CI pipeline — Terraform's plan-before-apply pipeline, if you took that course, is the exact same shape.

A real pipeline, in GitHub Actions

This mirrors what a small team would actually run. Each stage is a separate job; needs: makes each one wait for the last to succeed. GitHub's own official ansible/ansible-lint@main action runs the lint stage without you having to install anything yourself:

# .github/workflows/ansible-ci.yml
name: Ansible CI/CD

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  lint:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: ansible/ansible-lint@main

  syntax-check:
    needs: lint
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - run: pip install ansible-core
      - run: ansible-playbook site.yml -i inventories/staging.ini --syntax-check

  dry-run-staging:
    needs: syntax-check
    runs-on: ubuntu-24.04
    environment: staging
    steps:
      - uses: actions/checkout@v4
      - run: pip install ansible-core
      - name: Dry-run against staging — makes no changes
        env:
          VAULT_PASS: ${{ secrets.STAGING_VAULT_PASSWORD }}
        run: |
          echo "$VAULT_PASS" > /tmp/vault-pass
          ansible-playbook site.yml -i inventories/staging.ini \
            --check --diff --vault-password-file /tmp/vault-pass
          rm -f /tmp/vault-pass

  apply-staging:
    needs: dry-run-staging
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    environment: staging
    steps:
      - uses: actions/checkout@v4
      - run: pip install ansible-core
      - env:
          VAULT_PASS: ${{ secrets.STAGING_VAULT_PASSWORD }}
        run: |
          echo "$VAULT_PASS" > /tmp/vault-pass
          ansible-playbook site.yml -i inventories/staging.ini \
            --vault-password-file /tmp/vault-pass
          rm -f /tmp/vault-pass

  apply-production:
    needs: apply-staging
    runs-on: ubuntu-24.04
    environment: production   # protection rule: a human must approve this job
    steps:
      - uses: actions/checkout@v4
      - run: pip install ansible-core
      - env:
          VAULT_PASS: ${{ secrets.PRODUCTION_VAULT_PASSWORD }}
        run: |
          echo "$VAULT_PASS" > /tmp/vault-pass
          ansible-playbook site.yml -i inventories/production.ini \
            --vault-password-file /tmp/vault-pass
          rm -f /tmp/vault-pass

Two details carry the whole design: needs: chains the gates in order, and environment: production lets GitHub require a human reviewer to click approve before that one job runs — confirmed directly against GitHub's own Actions documentation: a job tied to a protected environment "must follow any protection rules for the environment before running," and an environment can require that "people or teams... must approve workflow jobs that use this environment." Staging applies automatically once the dry run is clean; production still gets a human in the loop.

Credentials and the vault password in CI

Lesson 26 already established the rule: commit the encrypted vault file, never the password. In CI, that means the vault password lives in the CI system's own secret store — a GitHub Actions secret (secrets.STAGING_VAULT_PASSWORD above), a GitLab CI protected variable, or an external secrets manager — never a file checked into the repo, and never hardcoded in the workflow YAML itself.

Common mistake: writing the vault password straight into the pipeline's --vault-password-file argument, or committing a vault-pass.txt "just to get CI working," meaning to remove it later. That "later" is exactly how vault passwords end up in git history permanently — the same mistake Lesson 26 covered, just moved into a YAML file instead of a vars file. Write the password to a temp file at run time, from a CI secret, and delete the temp file in the same step (as the workflow above does) — nothing sensitive should outlive the job that needed it.

Security note: a CI runner that can decrypt your vault and reach production is, functionally, a production credential holder. Scope its access the same way you'd scope a human's: separate secrets per environment (notice STAGING_VAULT_PASSWORD and PRODUCTION_VAULT_PASSWORD are different secrets above, not one reused everywhere), and restrict who can approve the production environment's protection rule. A pipeline that can silently touch production with no approval step isn't really safer than someone's laptop — it's the same risk, automated.

Why staging comes before production, always

A dry run (--check --diff) tells you what a playbook would do. It doesn't prove it actually works against real infrastructure — check mode has real limits (Lesson 29 covers why a task that depends on a previous task's registered result can't always be predicted in check mode). Running the real playbook against a staging inventory first — hosts that look like production but aren't — is how a team catches the failures check mode can't: a role that assumes a package repository staging doesn't have, a template that references a variable only defined in one environment's group_vars. Staging is disposable; production isn't.

Production note: real teams keep staging and production as separate inventory files (or separate dynamic inventory sources, Lesson 20) with the same group structure, so the exact same playbook and roles run against both — only group_vars/staging.yml vs group_vars/production.yml differ. If your "staging" playbook looks structurally different from your "production" playbook, staging isn't testing what production will actually do.

Try it — before looking below

Q1. Your pipeline has four stages: lint, syntax-check, dry-run-staging, apply-staging. A teammate suggests removing the lint stage "to make the pipeline faster." What's wrong with that reasoning?

Lint is the cheapest, fastest check in the whole pipeline — it runs in seconds with no inventory, no SSH connections, no real infrastructure involved. Removing it doesn't meaningfully speed up the pipeline; it just means a style/deprecation problem that lint would have caught in 5 seconds now gets caught later, by a slower and more expensive stage (or not caught at all until it breaks something in staging or production).

Q2. A CI job needs to run a vault-protected playbook against production, unattended. Where should the vault password actually live, and where should it never live?

It should live in the CI system's own secret store (a GitHub Actions secret, a GitLab CI protected variable, or an external secrets manager), injected into the job at run time. It should never live in a file committed to the repo, never be hardcoded in the workflow YAML, and ideally shouldn't even persist on disk on the runner past the step that needs it — write it to a temp file and delete the temp file in the same step, exactly like Lesson 26's rule about keeping the vault password completely out of git, extended to CI.

Now write your own

You don't need a real GitHub repo or real hosts to practice the structure — build the pipeline file itself and reason through what each stage would do:

  • create a folder cicd-practice/ with a tiny playbook site.yml targeting a fake staging inventory (use the RFC 5737 documentation range, e.g. 192.0.2.10, 192.0.2.11 as [staging] — you don't need these hosts to actually exist to write and syntax-check the pipeline)
  • write .github/workflows/ansible-ci.yml following the four-stage shape above, adjusted to your playbook's real filename and inventory path
  • run the first two gates locally, exactly as CI would: ansible-lint site.yml, then ansible-playbook site.yml -i inventories/staging.ini --syntax-check
  • fix anything either one flags — this is the same feedback loop CI gives you, just without waiting for a runner

Recap
  • Running Ansible from a pipeline instead of a laptop turns "hope it works" into a sequence of gates: lint (Lesson 27) → syntax-check → dry-run against staging (--check --diff, Lesson 29) → apply — cheapest checks first.
  • A realistic pipeline chains jobs with needs: and gates production behind a human approval — in GitHub Actions, an environment: with a required reviewer.
  • The vault password (Lesson 26) belongs in the CI system's own secret store, injected at run time — never committed, never hardcoded in the pipeline file.
  • Staging and production should run the exact same playbook and roles, differing only in inventory and group_vars — if they're structurally different, staging isn't really testing what production will do.
