Handlers & notify

Lesson 7 taught you idempotency: a task should only report changed when it actually changed something. Lesson 11 taught you loops. Now put idempotency to work — restarting a service every single run, whether or not its config actually changed, is wasteful and risky (an unnecessary restart can drop connections for no reason). A handler is how you say "only do this if something upstream actually changed."

Mental model: a handler is a task that sits off to the side, doing nothing, until a regular task notifys it — and even then, it only actually runs if that task reported changed. Think of it as a doorbell wired to a specific event: editing a config file rings the bell, and the bell triggers "restart the service." No edit, no ring, no restart.

The two pieces: handlers: and notify:

A handler is defined in its own handlers: section on the play, written exactly like a task — a name: and a module call:

handlers:
  - name: Restart apache
    ansible.builtin.service:
      name: httpd
      state: restarted

A regular task points at that handler by name using notify::

tasks:
  - name: Write the apache config file
    ansible.builtin.template:
      src: /srv/httpd.j2
      dest: /etc/httpd.conf
    notify:
      - Restart apache

The link between the two is the name string — notify: Restart apache has to match name: Restart apache under handlers: exactly, character for character. There's no ID, no reference syntax, just a matching name. notify: can take a single name or a YAML list of names if one task should trigger several handlers.

Here's the part that makes this idempotent instead of just "run it anyway": notify only actually fires the handler if the notifying task reports changed. If ansible.builtin.template looks at the file, sees it already matches, and reports ok, the handler is never triggered — not "triggered but skipped," genuinely never called. This is Lesson 7's idempotency rule, now driving a second task's behavior.

The detail that catches people out: handlers run at the end

Handlers do not run at the point in the task list where notify: appears. They run once, after all the regular tasks in that section of the play have finished. I confirmed the exact behavior against Ansible's own docs:

"Notifying the same handler multiple times will result in executing the handler only once regardless of how many tasks notify it."

So if three different tasks each edit a different config file and all three notify: Restart apache, Ansible does not restart Apache three times. It queues the notification, keeps running the rest of the tasks, and fires "Restart apache" once, deduplicated, after the last task in the play (or in pre_tasks / roles / tasks / post_tasks — each of those sections flushes its own handlers at its end). Handlers also run in the order they're defined under handlers:, not the order they were notified in.

Best practice — the classic pattern: edit a config file with ansible.builtin.template or ansible.builtin.copy, and notify a handler that restarts the matching service. The service only bounces when the config genuinely changed — never on a routine run where nothing was different. This is the standard, idiomatic way to wire config changes to service restarts in Ansible; you'll use this pattern constantly from here on.

One more edge case worth knowing now: if a task fails partway through a play, any handlers it already notified will not run, because Ansible stops that host's play on failure before reaching the end where handlers fire. You'll deal with error handling explicitly later in this course — for now, just know that a handler is not guaranteed to fire just because notify: was reached; the play has to reach its end successfully for that host.

Try it — before looking below

Q1. A play has three tasks. Tasks 1 and 2 both edit config files and both notify: Reload service. Task 3 does something unrelated and doesn't notify anything. How many times does "Reload service" run?

Once — assuming at least one of task 1 or task 2 reported changed. Even though two tasks notified it, Ansible deduplicates and fires the handler a single time, after task 3 finishes.

Q2. You run a playbook. The task that writes a config file reports ok (not changed) because the file already matched. The task has notify: Restart nginx. Does the handler run?

No. notify only queues the handler when the task reports changed. An ok result means nothing changed, so the handler is never triggered — this is exactly what stops nginx from restarting on every run where the config was already correct.

Now write your own

Reuse the localhost inventory from earlier lessons. Create handlers-demo.yml:

- name: Handlers and notify demo
  hosts: localhost

  tasks:
    - name: Write a demo file
      ansible.builtin.copy:
        content: "hello from the handlers lesson\n"
        dest: /tmp/ansible-handlers-demo.txt
      notify:
        - Say the file changed

  handlers:
    - name: Say the file changed
      ansible.builtin.debug:
        msg: "Handler fired — the file actually changed this run."

Then:

  • run ansible-playbook -i inventory handlers-demo.yml
  • check the TASK [Write a demo file] status — expect changed on this first run, since the file didn't exist yet
  • look for a RUNNING HANDLER [Say the file changed] section after the tasks, and confirm the debug message printed
  • run the exact same command a second time
  • check the copy task's status again — expect ok this time, since the content is identical
  • confirm the handler section does not appear at all on the second run — no notify, because nothing changed

Try it yourself before checking the reference command below.

Reveal the reference command

ansible-playbook -i inventory handlers-demo.yml
# first run: copy task = changed, handler fires and prints the debug message

ansible-playbook -i inventory handlers-demo.yml
# second run: copy task = ok, no RUNNING HANDLER section at all

Recap
  • A handler is a task defined under handlers: that only runs when a task notifys it by matching name — and only if that task reported changed.
  • Handlers run once, at the end of the play, no matter how many tasks notified them — deduplicated, and in the order they're defined, not the order they were notified.
  • The classic pattern: edit a config with template or copy, notify a "restart service" handler — the service only bounces when the config genuinely changed.
