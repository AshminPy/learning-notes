Loops

Without loops, installing three packages means writing three near-identical tasks — same module, same options, only the package name changes. That's noise: more lines to read, more places to make a typo, more work every time the list changes. Ansible's loop keyword lets you write the task once and hand it a list of items to repeat over.

Mental model: a loop is one task with a list attached. Ansible runs that single task once per item in the list, substituting {{ item }} with the current value each time — same module, same logic, different data. You write the "what" once; the list supplies the "how many times."

The loop keyword

Add a loop: list to any task, and reference the current value inside the task as item. Confirmed against Ansible's own docs, this is the canonical shape:

- name: Add several users
  ansible.builtin.user:
    name: "{{ item }}"
    state: present
    groups: "wheel"
  loop:
     - testuser1
     - testuser2

Ansible runs the ansible.builtin.user task twice — once with item set to testuser1, once with item set to testuser2. In the output you'll see two separate result lines for this one task, one per item, so you can tell at a glance which items changed and which were already ok.

loop vs the older with_items / with_*

If you read older playbooks or blog posts, you'll see with_items instead of loop — same idea, different keyword:

# older style — still works, but not what to write today
- name: Add several users
  ansible.builtin.user:
    name: "{{ item }}"
    state: present
  with_items:
    - testuser1
    - testuser2

Ansible's official guidance is direct about which one to reach for: loop was added as "a simpler way to do loops," and the docs recommend it for most use cases going forward. with_items and the rest of the with_* family (with_dict, with_nested, and so on) are not deprecated — they'll keep working — but they exist today mainly so older playbooks don't break. Ansible's own migration guidance says most with_* loops can be rewritten with loop.

Best practice: in every new task you write, reach for loop. Only recognize with_items when you meet it in existing code — you don't need to go rewrite working playbooks just to swap the keyword, but don't introduce new with_* loops either.

The classic use case: a list of packages

The most common loop in real playbooks is installing a set of packages in one task instead of one task per package:

- name: Install required packages
  ansible.builtin.apt:
    name: "{{ item }}"
    state: present
  loop:
    - git
    - curl
    - vim

Three packages, one task. Add a fourth package later and you add one line to the list — you don't add a whole new task. The same pattern applies to creating a list of files or directories with the ansible.builtin.file module, which you'll use yourself in the hands-on below.

Combining loop with when

Lesson 10 covered when: to skip a task based on a condition. Put a when: on a looping task and Ansible evaluates it separately for every item — it's not one decision for the whole list, it's one decision per item. Some items can run while others get skipped, in the same task, same run:

- name: Install packages, skipping one on Debian
  ansible.builtin.apt:
    name: "{{ item }}"
    state: present
  loop:
    - git
    - curl
    - some-redhat-only-tool
  when: item != "some-redhat-only-tool" or ansible_facts['os_family'] != "Debian"

Watch the output closely when you run something like this: you'll see a changed or ok result for each item that ran, and a skipped result for each item that didn't — all under the one task name, one line per item.

Try it — before looking below

Q1. A task loops over a list of 5 items using loop. How many times does the module in that task actually run?

Five times — once per item in the list. Each run substitutes {{ item }} with that item's value, and each gets its own result line in the output (ok / changed / skipped / failed), even though it's written as a single task.

Q2. You find a playbook written two years ago using with_items. Is it broken? Should you rewrite it before touching anything else in the file?

Not broken — with_items is not deprecated and still works. No need to rewrite it just to swap the keyword. The rule is forward-looking: write new tasks with loop, and only touch old with_items tasks if you're already editing that task for another reason.

Now write your own

Reuse the localhost inventory and playbook file from earlier lessons. Add a task that loops over a list of three directory names and creates all of them with the ansible.builtin.file module:

- name: Loops practice
  hosts: localhost
  tasks:
    - name: Create practice directories
      ansible.builtin.file:
        path: "/tmp/{{ item }}"
        state: directory
      loop:
        - ansible-loop-one
        - ansible-loop-two
        - ansible-loop-three

Then:

  • run ansible-playbook -i inventory playbook.yml
  • find TASK [Create practice directories] — count the result lines. You should see three, one per directory
  • confirm all three directories exist: ls -d /tmp/ansible-loop-*
  • run the playbook a second time and watch the changed count on that task — same idempotency lesson from Lesson 7, now applied to a loop

Recap
  • loop: attaches a list to a task; Ansible runs the task once per item, accessed inside the task as {{ item }}.
  • loop is the recommended keyword going forward. with_items and the rest of with_* still work and aren't deprecated, but are the older style — don't start new tasks with them.
  • Classic use case: one task looping over a list of packages or files/directories, instead of one task per item.
  • Combine loop with when: to skip specific items conditionally — the condition is checked separately for every item, not once for the whole list.
