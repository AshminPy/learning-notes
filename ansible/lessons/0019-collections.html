Collections

Lesson 18 mentioned collections in passing while installing roles from Galaxy. Time to open that box properly. Every module you've called since Lesson 6 — ansible.builtin.debug, ansible.builtin.file, ansible.builtin.copy, ansible.builtin.template — already lives inside one. You've been using a collection this whole course without knowing its name.

Mental model: a role (Lesson 16-17) is one reusable job — "configure Nginx," "set up a firewall baseline." A collection is a distribution package — like a library on PyPI or npm — that can bundle many roles, plus modules, plugins, and playbooks, all published and versioned together. A role is a recipe. A collection is the cookbook it ships in, and the cookbook can hold other things too.

What a collection actually contains

Confirmed against Ansible's own collections guide: a collection is Ansible's packaging format for distributing content. A single collection can bundle:

  • Modules — the building blocks tasks call, like copy or a cloud-provider API wrapper.
  • Plugins — connection types, filters, lookups, and other extension points.
  • Roles — yes, the Lesson 17 kind. A collection can bundle several finished roles.
  • Playbooks and docs — ready-to-use examples and reference material shipped alongside the code.

You've already met three real ones by name:

  • community.general — a broad grab-bag of community-maintained modules that don't have a more specific home.
  • ansible.posix — modules for POSIX-specific system tasks (things like file ACLs, mounts).
  • amazon.aws — AWS-specific modules and plugins, maintained by AWS/the community for provisioning and managing AWS resources.

The naming pattern: namespace.collection_name

Every collection is named namespace.collection_name — the same two-part shape as the namespace.role_name pattern from Lesson 18, just one level up. namespace identifies who publishes it (a vendor, an org, or ansible and community for content Ansible itself curates); collection_name identifies the package. amazon.aws reads as "the aws collection, published by the amazon namespace" — exactly like geerlingguy.nginx read as "the nginx role, published by geerlingguy."

FQCN — the name you've already been typing

A Fully Qualified Collection Name (FQCN) is namespace.collection_name.resource_name — the collection's full name plus a dot plus the specific module (or plugin) inside it. This is the piece that reframes everything from Lesson 6 onward: ansible.builtin.copy is not a special "built-in" keyword — it's an FQCN. ansible.builtin is a real collection (the one that ships with Ansible core itself, containing native modules like copy, file, template, and debug), and copy is a module inside it. Every example playbook in this course has been calling FQCNs since Lesson 6, you just hadn't been told the pattern had a name yet.

Best practice — always write the FQCN, never the short name. Ansible lets you write just copy: instead of ansible.builtin.copy: if nothing else on the system defines a module with that same short name. But the moment you install a second collection that also happens to ship a copy module, the short name becomes ambiguous — which one runs depends on collection search order, not on what you meant. Writing the full FQCN in every task removes that ambiguity permanently and makes the task self-documenting: anyone reading it knows exactly which collection's code is running, without checking your installed collections list first.

Installing a collection

Same tool as Lesson 18, different subcommand:

$ ansible-galaxy collection install namespace.collection_name

For example:

$ ansible-galaxy collection install community.general

Pin an exact version with a colon:

$ ansible-galaxy collection install community.general:==8.0.0

Pinning collections in requirements.yml

Confirmed against the current collections guide: it's the same file format from Lesson 18, extended. A requirements.yml can hold a top-level roles: list, a top-level collections: list, or both in one file:

---
roles:
  - name: geerlingguy.nginx
    version: "3.1.4"

collections:
  - name: community.general
    version: "8.0.0"

  - name: amazon.aws
    version: ">=7.0.0,<8.0.0"

Install everything the file lists — roles and collections together — with the same command from Lesson 18:

$ ansible-galaxy install -r requirements.yml

Or install only the collections half:

$ ansible-galaxy collection install -r requirements.yml

The version rule from Lesson 18 carries over exactly: pin it, commit the file to git, only bump on purpose after testing. An unpinned collection is the same silent moving target an unpinned role or an unpinned Terraform module source is.

Role vs collection — the distinction that matters

Role (Lesson 16-17)Collection (this lesson)
One specific automation job — e.g. "install and configure Nginx"A distributable package — can contain many roles, modules, and plugins
Named namespace.role_nameNamed namespace.collection_name
Used under a play's roles: keyIts modules are called via FQCN inside tasks; its roles (if any) are used like any role
Installed with ansible-galaxy role installInstalled with ansible-galaxy collection install

A collection can ship zero roles and just be a set of modules (like ansible.builtin). Or it can ship mostly roles (like geerlingguy.php_roles, seen in the official requirements.yml example). The two concepts aren't a hierarchy where one always contains the other — a collection is a packaging boundary, a role is a unit of automation logic. They're independent axes that happen to overlap often.

Try it — before looking below

Q1. What's the FQCN of the copy module you've been using since Lesson 6?

ansible.builtin.copy — ansible.builtin is the collection namespace.name that ships with Ansible core, and copy is the module inside it. Same pattern as ansible.builtin.file, ansible.builtin.template, and ansible.builtin.debug — every "built-in" module you've called in this course is really an FQCN pointing at the ansible.builtin collection.

Q2. Your project needs community.general for one module and geerlingguy.nginx for a full Nginx setup. Can one requirements.yml pin both, and what command installs everything in it?

Yes — put geerlingguy.nginx under a top-level roles: key and community.general under a top-level collections: key in the same requirements.yml file, each pinned with version:. Install both with one command: ansible-galaxy install -r requirements.yml.

Now try it yourself

In your practice project folder:

  • run ansible-galaxy collection install community.general and note where it installs
  • write a small playbook task using an FQCN from that collection instead of ansible.builtin — check the community.general docs on Galaxy for a module name to try
  • create (or extend) your requirements.yml from Lesson 18 to add a collections: section pinning community.general to a specific version
  • run ansible-galaxy install -r requirements.yml and confirm both your pinned role and your pinned collection install
  • go back to any task you wrote in earlier lessons using a short module name (like copy:) and rewrite it as the full FQCN (ansible.builtin.copy:) — get in the habit now

Recap
  • A collection (namespace.collection_name) is a distribution package that can bundle modules, plugins, roles, and playbooks together — bigger than a role, which is one specific automation job.
  • Every module you've used since Lesson 6 is an FQCN — ansible.builtin.copy, ansible.builtin.file, ansible.builtin.template all live in the ansible.builtin collection that ships with Ansible core.
  • Install a collection with ansible-galaxy collection install namespace.collection_name; pin it in the same requirements.yml from Lesson 18, which can hold both a roles: list and a collections: list.
  • Always write the full FQCN in tasks — it removes ambiguity if two installed collections ever ship a module with the same short name.
