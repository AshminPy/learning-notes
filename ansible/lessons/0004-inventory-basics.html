Inventory basics

Ansible has no agents. There's no daemon running on every server waiting for instructions. So how does Ansible know which machines to manage? You tell it — with a file called the inventory. This lesson is the mental model for that file: what it is, the two formats you can write it in, and how to organize hosts into groups so your playbooks can target "all my webservers" instead of listing every hostname by hand.

What an inventory actually is

An inventory is just a list of the hosts Ansible is allowed to manage, optionally organized into groups. That's the whole idea. It can be a plain text file, a YAML file, or even a script that generates the list dynamically (you'll meet dynamic inventory later in the course). For now, think of it as an address book: names (or IPs) of machines, sorted into folders by role.

Mental model: a playbook says what to do. The inventory says where to do it. Without an inventory, a playbook is just a recipe with no kitchen to cook in.

The default inventory format: INI-style

The classic Ansible inventory is a plain text file in INI style — one hostname or IP per line, with [groupname] headers in square brackets marking the start of a group. Straight from the official inventory guide:

mail.example.com

[webservers]
foo.example.com
bar.example.com

[dbservers]
one.example.com
two.example.com
three.example.com

Read that top to bottom: mail.example.com sits outside any group heading, so it isn't in a named group. Everything under [webservers] belongs to the webservers group; everything under [dbservers] belongs to dbservers. You can add per-host variables on the same line, separated by spaces — for example:

[atlanta]
host1 http_port=80 maxRequestsPerChild=808

That sets http_port and maxRequestsPerChild as variables available to host1 only, inside the atlanta group.

The modern alternative: YAML inventory

Ansible also accepts inventory written in YAML — the same format you'll use for playbooks, so many teams standardize on it for consistency. The INI example above, written as YAML, looks like this (from the official docs):

ungrouped:
  hosts:
    mail.example.com:
webservers:
  hosts:
    foo.example.com:
    bar.example.com:
dbservers:
  hosts:
    one.example.com:
    two.example.com:
    three.example.com:

Notice the structure: each group is a top-level key, with a hosts: block listing its members. Host variables nest under the host itself instead of trailing on the same line:

atlanta:
  hosts:
    host1:
      http_port: 80
      maxRequestsPerChild: 808

Both formats describe the exact same information. INI is quicker to hand-type for a handful of hosts; YAML reads better once you have nested groups and lots of variables. Pick one per project and stay consistent — don't mix them in the same inventory file.

The two groups Ansible always gives you

You never have to create these — Ansible makes them automatically the moment you have an inventory:

  • all — every host in the inventory, no matter what group (if any) they're in. Target it in a playbook with hosts: all to run against everything.
  • ungrouped — every host that isn't listed under any [groupname] heading. In the INI example above, mail.example.com lands here because it sits outside any bracketed group.

Official docs, word for word: "Even if you do not define any groups in your inventory, Ansible creates two default groups: all and ungrouped. The all group contains every host. The ungrouped group contains all hosts that do not belong to any other group."

You'll also run into localhost a lot — that's just the machine Ansible itself is running on (your laptop, or a control node in a pipeline). It's useful for tasks that don't touch a remote server at all, like generating a report or calling a local API. You'll set it up explicitly in the hands-on below.

Why grouping matters

Grouping isn't decoration — it's what makes playbooks reusable. Instead of a playbook listing 20 hostnames by hand, it says hosts: webservers, and every host you add to that group later is automatically included, no playbook edit required. Group hosts by role, so the group name tells you what the machines do:

[webservers]
web1.example.com
web2.example.com

[databases]
db1.example.com

Mental model: groups are how you decouple "what to configure" (the playbook) from "which machines" (the inventory). Add a new web server to production? You edit the inventory, not the playbook. That separation is a big part of why Ansible scales from 2 servers to 2,000 without the playbooks getting more complicated.

Try it — before looking below

Q1. In this INI inventory, which group does db1.example.com belong to besides all?

app1.example.com

[databases]
db1.example.com
databases — it sits under the [databases] heading. app1.example.com sits above any heading, so it lands in ungrouped instead.

Q2. A playbook has hosts: webservers. You add a new host under [webservers] in the inventory file. Do you need to change the playbook to include the new host?

No. The playbook targets the group, not individual hostnames. Any host added to the group is automatically in scope the next time the playbook runs.

Q3. What are the two groups Ansible creates automatically, even if your inventory file defines no groups at all?

all (every host) and ungrouped (every host not listed under a named group).

Hands-on: write and verify a local inventory

You don't need any real servers for this — you're going to point Ansible at your own machine using ansible_connection=local, which tells Ansible to run tasks directly instead of connecting over SSH.

  1. Create a file named inventory.ini with this content: 
    [local]
127.0.0.1 ansible_connection=local
  2. Verify Ansible reads it correctly: 
    ansible-inventory -i inventory.ini --list
    You should see JSON output with a local group containing 127.0.0.1, plus the automatic all and ungrouped groups.
  3. Confirm which hosts a pattern resolves to, without running anything: 
    ansible all -i inventory.ini --list-hosts
    This should print 127.0.0.1 as the one matching host.
  4. Optional — write the same inventory in YAML instead, as inventory.yml: 
    local:
  hosts:
    127.0.0.1:
      ansible_connection: local
    Run ansible-inventory -i inventory.yml --list and confirm you get the same result as the INI version.

Why this matters: ansible-inventory --list and --list-hosts don't touch any servers — they just show you what Ansible would target. Get in the habit of running one of these before every playbook run against real infrastructure. It's the cheapest way to catch "I'm about to run this against the wrong 40 servers" before it happens.

Recap
  • An inventory is the list of hosts Ansible manages — the "where," separate from the playbook's "what."
  • INI format: one host per line, [groupname] headers in brackets, host variables trail on the same line.
  • YAML format: groups are top-level keys with a hosts: block; the same information, more nesting-friendly.
  • all (every host) and ungrouped (hosts in no named group) are created automatically — you never define them yourself.
  • localhost / 127.0.0.1 with ansible_connection=local lets Ansible run tasks on the control machine itself, no SSH needed.
  • Group hosts by role ([webservers], [databases]) so playbooks target the group and stay correct as hosts are added or removed.
  • ansible-inventory -i <file> --list and ansible all -i <file> --list-hosts both show what Ansible would target, without running anything.
If the INI vs YAML choice feels arbitrary right now, that's fine — most real teams settle on one and never look back. What matters more is the group habit: always target a group in your playbooks, never a hardcoded hostname list. That single habit is what keeps playbooks working as infrastructure grows.
