Check mode and diff mode

A role can be lint-clean (Lesson 27) and pass every Molecule test (Lesson 28) against a disposable container, and still surprise you the first time it runs against a real, unfamiliar set of hosts — different existing files, different facts, a variable nobody overrode the way you assumed. Before a playbook makes real changes to production, Ansible gives you a rehearsal: --check shows what WOULD change without changing anything, and --diff shows exactly what the actual content difference would be.

Mental model: --check is a dry run — Ansible walks through every task, works out whether it WOULD report changed, and tells you, without touching the real system. --diff adds detail on top: for any task that changes file content, it prints an actual before/after diff, the same idea as git diff. If you took the Terraform course, this is the same discipline as Terraform Lesson 26, Plan review discipline — never make a real change without reviewing what would happen first.

Running check mode

Add --check to any ansible-playbook run:

$ ansible-playbook deploy.yml --check

Every task still executes its logic and reports what it would do — ok, changed, or failed — but nothing on the target host is actually modified.

Adding diff mode

Combine it with --diff to see the actual content that would change, not just a changed/unchanged flag:

$ ansible-playbook deploy.yml --check --diff

For a task using the template or copy module, this prints a real unified diff of old vs. new file content — the clearest possible preview of what a config change would actually do. --diff also works without --check, on a real run, to show you what changed as it happens.

The critical caveat: not every module supports check mode

Confirmed directly from Ansible's own docs: "Modules that support check mode report the changes they would have made. Modules that do not support check mode report nothing and do nothing." The second half of that sentence is the trap — an unsupported module doesn't run for real during --check, but it also doesn't tell you anything. It's simply skipped, silently, as far as your dry-run report is concerned.

command and shell are the two you'll hit constantly — they don't support check mode. A playbook full of shell tasks can report "0 changes" under --check and tell you almost nothing about what the real run will actually do.

Forcing a task's check-mode behaviour

The check_mode task keyword overrides the playbook-level setting for one specific task:

# Force this task to always run for real, even during --check —
# useful for a read-only diagnostic you want live output from
- name: report current disk usage
  ansible.builtin.command: df -h
  check_mode: false

# Force this task to always simulate, even on a real run
- name: destructive cleanup step
  ansible.builtin.command: rm -rf /var/cache/myapp
  check_mode: true

There's also a magic variable, ansible_check_mode, for conditionally changing behaviour inside a task based on whether the run is a dry run:

- name: skip a task entirely in check mode
  ansible.builtin.git:
    repo: https://example.com/repo.git
    dest: /opt/myapp
  when: not ansible_check_mode

Common mistake: seeing "0 changes" from ansible-playbook --check and assuming the real run will be identical. If any task uses command, shell, or another check-mode-unaware module, that task was skipped during the dry run, not verified — a clean --check result doesn't cover it at all. Check which modules your playbook actually uses before trusting a "no changes" dry run.

Production note: the real-world habit this lesson exists to teach: run --check --diff against production, actually read the diff output line by line, and only then run the playbook for real. Skipping the review step and just glancing at "looks fine" defeats the entire point — the value is in reading what would change, the same way you'd review a Terraform plan before apply.

Try it — before looking below

Q1. You run ansible-playbook deploy.yml --check against production and it reports zero changes. The playbook has one task using the shell module. Can you be fully confident the real run will also make zero changes?

No. The shell module doesn't support check mode, so during --check it isn't actually evaluated — it's skipped, not verified. "Zero changes" from the dry run tells you nothing about what that shell task would really do. You'd need to inspect that task separately, or test it carefully in a non-production environment.

Q2. What's the difference in what --check and --diff each show you, and why run them together?

--check simulates the run and reports which tasks WOULD report changed, without making real changes. --diff shows the actual before/after content for tasks that change file content (templates, copied files, in-place edits). Together, you get both which tasks would change and exactly what that change's content looks like — the fullest possible dry-run picture.

Q3. You have one read-only diagnostic task you want to actually execute even during a --check dry run, while every other task in the playbook stays fully simulated. What do you set on that one task?

check_mode: false on that specific task. It overrides the playbook-level --check setting so just that task runs for real, live, even inside a dry run — every other task in the playbook is still simulated normally.

Now write your own

In a practice folder, create a small playbook that mixes a check-mode-aware module with one that isn't:

---
- hosts: localhost
  connection: local
  tasks:
    - name: write a config file from a template
      ansible.builtin.copy:
        content: "setting = enabled\n"
        dest: /tmp/myapp.conf

    - name: touch a marker file via shell
      ansible.builtin.shell: touch /tmp/marker.txt

Then:

  • run it for real once: ansible-playbook site.yml — both tasks report changed
  • run it again with --check --diff: ansible-playbook site.yml --check --diff
  • look closely at each task's status — the copy task should report no change (the file already matches) and print no diff; the shell task's behaviour is the one to pay attention to
  • edit the content: value to a different string, then re-run with --check --diff and read the actual diff output for the copy task

Reveal what you should see

After the real run, a second --check --diff pass shows the copy task as unchanged (content already matches — no diff printed). The shell task shows as changed again on every --check run regardless — shell doesn't support check mode, so Ansible can't actually tell whether touch would do anything; it just reports its default "assume changed" behaviour. After editing the content and re-running with --check --diff, the copy task prints a real unified diff showing the old line removed and the new line added — exactly what would land on disk if you dropped --check.

Recap
  • --check is a dry run: tasks report what they would change, without changing anything for real.
  • --diff adds an actual before/after content diff for file-changing tasks — run it together with --check for the fullest preview.
  • Critical caveat: modules that don't support check mode (command, shell) are simply skipped during --check — a "0 changes" dry run doesn't cover them at all.
  • Override per task with check_mode: false (always run for real) or check_mode: true (always simulate); use the ansible_check_mode magic variable to branch logic conditionally.
  • Production habit: always --check --diff against production, actually read the output, then run for real.
