Facts

Back in Lesson 5 you ran ansible.builtin.setup ad-hoc and saw it dump a wall of data about a host. In Lesson 6 you saw TASK [Gathering Facts] run automatically before your own tasks, every single time. Now it's time to actually use what that step collects. A fact is a piece of information Ansible automatically discovers about a managed host at the start of a play — its operating system, IP addresses, memory, CPU count, hostname, and dozens more — without you asking for any of it by name.

Mental model: variables (Lesson 8) are things you decide and write down. Facts are things Ansible finds out by asking the host directly. Same mechanism for using them in a task — but the value comes from the host itself, not from your YAML.

Where facts come from

Facts are gathered by the ansible.builtin.setup module — the same module you ran by hand in Lesson 5. A play runs it automatically before your first task, which is exactly the TASK [Gathering Facts] banner you've been seeing since Lesson 6. Nothing new is happening here; you're now learning to read and use the data that step was quietly collecting the whole time.

gather_facts — on by default

Every play has a gather_facts keyword, and it defaults to true. You can set it explicitly:

- name: A play that needs facts
  hosts: webservers
  gather_facts: true
  tasks:
    - name: Show the OS family
      ansible.builtin.debug:
        var: ansible_facts['os_family']

Fact gathering isn't free — it's an extra round trip to every host before any of your tasks run, which adds up across large inventories. If a play's tasks never reference any facts, turn it off:

- name: A play that doesn't need facts
  hosts: webservers
  gather_facts: false
  tasks:
    - name: Just ping
      ansible.builtin.ping:

Best practice: leave gather_facts on unless you have a specific, measured reason to turn it off (large inventories, tight time budgets, a play that genuinely never touches OS-specific behavior). Don't disable it by default "for speed" before you've confirmed you need to — most real playbooks end up needing at least one fact eventually, and re-adding it later is easy to forget.

Referencing a fact

Ansible's current docs give two ways to reach the same data:

  • The ansible_facts dictionary (current, recommended): ansible_facts['os_family'], ansible_facts['distribution'], ansible_facts['memtotal_mb'].
  • The older top-level style: ansible_os_family, ansible_distribution, ansible_memtotal_mb — these exist because, by default, Ansible also injects facts as top-level variables with an ansible_ prefix. This can be turned off via the INJECT_FACTS_AS_VARS setting, which is one more reason to not depend on it.

Both work today. Prefer the ansible_facts['...'] dictionary form in anything you write from here on — it's explicit about where the value came from, and it doesn't rely on a setting someone could turn off in a different environment. Treat the bare ansible_os_family style as something you'll recognize in older playbooks, not something you write yourself.

Why facts matter — adapting instead of assuming

Here's the actual payoff. Without facts, a playbook that installs a package has to hardcode one OS's package manager:

# Hardcoded — only works on Debian/Ubuntu hosts
- name: Install nginx
  ansible.builtin.apt:
    name: nginx
    state: present

Point that same task at a Red Hat-family host (which uses dnf/yum, not apt) and it fails outright. Facts let a playbook check what it's actually talking to and adapt:

- name: Show what package manager this host needs
  ansible.builtin.debug:
    msg: "This host is {{ ansible_facts['os_family'] }}"

ansible_facts['os_family'] comes back as something like "Debian" or "RedHat" — a normalized grouping, not the exact distro name (that's ansible_facts['distribution'] instead, e.g. "Ubuntu" or "CentOS"). You now have a real value to make a decision with. You can't act on that decision yet — picking one task or another based on a fact's value is exactly what Lesson 10's conditionals (when:) are for. Facts are the "what do we know about this host" half of the picture; conditionals are the "so do this instead of that" half. This lesson gives you the data; the next lesson gives you the branching.

Try it — before looking below

Q1. A play targets ten hosts, a mix of Ubuntu and CentOS. One task hardcodes ansible.builtin.apt. What happens on the CentOS hosts?

The task fails on every CentOS host — apt doesn't exist there, CentOS uses dnf/yum. This is exactly the problem facts plus conditionals solve: check ansible_facts['os_family'] and branch to the right module per host, instead of assuming every host matches the one you tested on.

Q2. You disable gather_facts on a play to save time, but one of its tasks references ansible_facts['distribution']. What happens?

The fact was never collected for that play, so the task can't get a real value from it — expect an undefined-variable error (or, depending on how it's used, silently missing data). Facts are only available if something gathered them first: either gather_facts: true on the play, or an explicit ansible.builtin.setup task earlier in it.

Now try it yourself

Using the localhost inventory from Lesson 4, create facts.yml:

- name: Explore facts on localhost
  hosts: localhost
  gather_facts: true
  tasks:
    - name: Show OS family
      ansible.builtin.debug:
        var: ansible_facts['os_family']

    - name: Show distribution and version
      ansible.builtin.debug:
        msg: "{{ ansible_facts['distribution'] }} {{ ansible_facts['distribution_version'] }}"

    - name: Show total memory in MB
      ansible.builtin.debug:
        var: ansible_facts['memtotal_mb']

Then:

  • run ansible-playbook -i inventory facts.yml
  • find the TASK [Gathering Facts] banner and confirm it ran before your own tasks, same as every playbook since Lesson 6
  • read the output of each debug task — these are real values Ansible discovered about your own machine, not something you typed anywhere
  • compare ansible_facts['os_family'] against what you know your machine actually is

Try it yourself before checking the reference command below.

Reveal the reference command

ansible-playbook -i inventory facts.yml
# check the three debug tasks in the output — os_family, distribution + version, memtotal_mb

Recap
  • Facts are information Ansible discovers about each host automatically, via the ansible.builtin.setup module, run at the start of every play unless gather_facts: false.
  • Reference them as ansible_facts['os_family'] (current, recommended) — the older bare ansible_os_family style still works but depends on a setting (INJECT_FACTS_AS_VARS) that can be off.
  • Facts let a playbook know what it's actually running against (OS family, distro, memory) instead of assuming — the missing piece is acting on that knowledge, which is Lesson 10's conditionals (when:).
