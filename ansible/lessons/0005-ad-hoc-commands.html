Ad-hoc commands

Lesson 4 gave you an inventory — a list of hosts Ansible knows about. Now let's actually do something to them, without writing a single file. An ad-hoc command is a one-off Ansible task you run directly from the terminal: one line, one action, no playbook required. It's the fastest way to ask a fleet of machines a question or make a small change right now.

The shape of an ad-hoc command

Every ad-hoc command follows the same pattern:

$ ansible <pattern> -i <inventory> -m <module> -a "<module args>"
  • <pattern> — which hosts or group to target, from your inventory (all, localhost, a group name like webservers).
  • -i <inventory> — path to the inventory file to use. If you skip this, Ansible falls back to its configured default inventory location.
  • -m <module> — the module to run. A module is a small, self-contained unit of work Ansible ships with — "check connectivity," "run a command," "gather facts" are all modules. If you omit -m, Ansible defaults to the command module.
  • -a "<module args>" — the arguments for that module, usually key=value pairs (some modules also accept a JSON string here).

Mental model: a playbook is a written recipe you save and hand to someone else to cook from. An ad-hoc command is you walking into the kitchen and doing one thing yourself, right now, because you don't need a recipe for "check if the oven is on."

When ad-hoc is the right tool — and when it isn't

Ad-hoc commands are great for quick, one-time, single-step questions or fixes across many hosts at once:

  • "Is this file present on every web server?"
  • "Restart the nginx service on the whole webservers group, right now."
  • "What's the disk usage on all my hosts?"

Reach for a playbook instead — the subject of Lesson 6 — as soon as either of these is true:

  • You'll run it again. Anything you'll repeat belongs in a file you can save, version, and re-run identically, not retyped from memory or shell history.
  • It's more than one step. Ad-hoc commands do exactly one thing. "Install the package, then copy the config, then restart the service" is three dependent steps — that's a playbook's job, not three separate terminal commands you have to run in the right order by hand.

Think of ad-hoc commands as the disposable, throwaway end of Ansible, and playbooks as the durable, reusable end. You'll use both for as long as you use Ansible — they're not a beginner stage you graduate out of.

A few modules worth knowing now

ping — is this host reachable and ready?

$ ansible all -i inventory.ini -m ping

This is the module you reach for first on any new host or inventory, to sanity-check everything before you try anything real.

Common beginner confusion — this is not ICMP ping. The ping module does not send network ping packets. Per Ansible's own docs, it "is NOT ICMP ping, this is just a trivial test module" — it connects over SSH, confirms it can log in, and confirms Python is available and working on the remote host. A successful run returns "pong". If a host fails this, the problem is SSH access or a missing/broken Python interpreter — not network reachability in the ICMP sense.

command and shell — run a raw command

# command is the default module if you don't pass -m at all
$ ansible webservers -i inventory.ini -a "uptime"

# shell explicitly, for when you need shell features
$ ansible webservers -i inventory.ini -m shell -a "echo $TERM"

command runs a command directly, without going through a shell on the remote host — so pipes, redirects, and environment variable expansion (like |, >, or $HOME) don't work with it. shell runs the command through the remote host's shell, so all of that works — but it costs you the safety command gives you.

Best practice — prefer a dedicated module over shell when one exists. Purpose-built modules (for installing packages, managing services, copying files, and so on — Lesson 7 covers a working set of them) are usually idempotent: run one twice and the second run changes nothing, because the module checks the current state first and only acts if reality doesn't already match what you asked for. A raw shell command has no such awareness — ansible all -m shell -a "useradd bob" run twice will error the second time, because it has no idea "bob" already exists. Reach for command/shell when no dedicated module covers what you need; reach for the dedicated module first whenever one does.

setup — gather facts about a host

$ ansible all -i inventory.ini -m ansible.builtin.setup

This module collects detailed information about each host — OS, IP addresses, memory, disks, and dozens more "facts" — and returns it as data. It's the same fact-gathering that runs automatically at the start of every playbook, which is why playbooks can reference things like a host's OS family without you ever asking for it explicitly. Lesson 9 goes deep on facts and how to use them; for now, just know the module exists and what it's for.

Try it — before looking below

Q1. You need to check whether a config file exists on 40 servers, one time, right now. Do you write a playbook or run an ad-hoc command?

An ad-hoc command — it's a one-time, single-step check. No need for a file you'll save and re-run.

Q2. ansible webservers -m ping fails on one host. Does that mean the host is down on the network?

Not necessarily. The ping module isn't ICMP — it checks SSH login and Python availability. A failure here points to an SSH or Python problem on that host, not necessarily a network-down problem.

Now try it yourself

Using the inventory file you built in Lesson 4:

  • run ansible localhost -m ping
  • run ansible localhost -m command -a "uptime"
  • look closely at the output of each — it's JSON-ish key/value data, not plain text
$ ansible localhost -m ping
localhost | SUCCESS => {
    "ansible_facts": {
        "discovered_interpreter_python": "/usr/bin/python3"
    },
    "changed": false,
    "ping": "pong"
}

$ ansible localhost -m command -a "uptime"
localhost | CHANGED => {
    "changed": true,
    "cmd": [
        "uptime"
    ],
    "rc": 0,
    "stdout": "10:14  up 2 days,  3:41, 4 users, load averages: 1.42 1.58 1.61",
    "stdout_lines": [
        "10:14  up 2 days,  3:41, 4 users, load averages: 1.42 1.58 1.61"
    ],
    "stderr": "",
    "stderr_lines": []
}

Two things worth noticing in that output:

  • "changed": false for ping, but "changed": true for command. Ansible tracks, per task, whether it believes it altered anything on the host — ping never changes state, so it always reports false; command has no way to know if running uptime "changed" anything, so it defaults to reporting true any time it runs. This changed flag is central to how playbooks report their results — you'll see it constantly from Lesson 6 onward.
  • SUCCESS vs CHANGED at the start of the line is a quick visual status — Ansible colors and labels these differently in a real terminal so you can scan a long run at a glance.

Recap
  • An ad-hoc command is a one-off task run straight from the CLI: ansible <pattern> -i <inventory> -m <module> -a "<args>" — no playbook file needed.
  • Use ad-hoc for quick, one-time, single-step jobs. Reach for a playbook (Lesson 6) as soon as something repeats or needs more than one step.
  • ping checks SSH + Python, not network reachability — it's not ICMP. Prefer dedicated modules over shell/command when one exists, because dedicated modules are usually idempotent. setup gathers host facts (more in Lesson 9).
