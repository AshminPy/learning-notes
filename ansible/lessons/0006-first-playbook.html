Your first playbook

Lesson 5 ran one-off commands with ansible — quick, but nothing was saved. Real automation needs to be written down, repeatable, and reviewable in a pull request like any other code. That's a playbook: a YAML file that says exactly what you want done, so anyone (including future you) can read it, run it, and get the same result.

Mental model: an ad-hoc command is a sentence you say once. A playbook is a recipe you write down — so it can be handed to someone else, checked into git, reviewed before it runs, and repeated exactly the same way next time.

What a playbook actually is

A playbook is a YAML file containing a list of plays. Each play does two things: it picks a group of hosts to target, and it lists the tasks to run against them, in order, top to bottom. A task is one step — almost always one module call, like ansible.builtin.debug or ansible.builtin.file, the same modules you used ad-hoc in Lesson 5, just written down instead of typed on the command line.

Here's the official example structure, confirmed against Ansible's own docs:

- name: Update web servers
  hosts: webservers
  remote_user: root

  tasks:
  - name: Ensure apache is at the latest version
    ansible.builtin.yum:
      name: httpd
      state: latest

  - name: Write the apache config file
    ansible.builtin.template:
      src: /srv/httpd.j2
      dest: /etc/httpd.conf

Read the shape, not the specific modules yet:

  • The whole file is a YAML list of plays — that's why it starts with - name:. This example has one play; a playbook can have several, each targeting different hosts.
  • hosts: — which group from your inventory this play runs against. Could be a single host, a group name, or all.
  • tasks: — another YAML list, one entry per task. Each task needs a name: (a human-readable description shown in the output — always write one, it's how you read the run later) and exactly one module call underneath it.
  • Tasks run in order, top to bottom, within a play. No parallel surprises, no reordering.

Just enough YAML to not get stuck

You don't need a full YAML tutorial to write playbooks, but two rules will trip you up if nobody tells you upfront:

  • Indentation is structure, not decoration. YAML uses spaces (never tabs) to show what's nested inside what — a task's module call is indented under the task, which is indented under tasks:. Get the indentation wrong and either the file fails to parse, or worse, it parses into something you didn't mean.
  • Lists start with a dash and a space (- ). Both plays and tasks are YAML lists, so both start with -. A dash followed by name: at the same indentation level means "here's a new item in this list."

Pick any consistent number of spaces (two is the community convention, used in every official example) and stay consistent. An editor with YAML syntax highlighting will save you a lot of pain here — it's worth setting up before you go much further in this course.

Running a playbook

One command, always the same shape:

$ ansible-playbook -i inventory playbook.yml

-i inventory points at the inventory file — the same flag and the same file you used with ad-hoc ansible commands in Lesson 5. playbook.yml is the file you just wrote. Nothing here is optional: without -i, Ansible falls back to its default inventory location, which is almost never what you want while you're learning.

Reading the output

Run a playbook and you'll see three kinds of sections, always in this order:

PLAY [My first play] ****************************************************************************

TASK [Gathering Facts] **************************************************************************
ok: [192.0.2.50]

TASK [Ping my hosts] ****************************************************************************
ok: [192.0.2.50]

TASK [Print message] ****************************************************************************
ok: [192.0.2.50] => {
    "msg": "Hello world"
}

PLAY RECAP **************************************************************************************
192.0.2.50: ok=3    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
  • PLAY — one banner per play, named after its name:.
  • TASK — one banner per task, in the order you wrote them. Notice Gathering Facts runs automatically before your first task — Ansible collects information about each host before doing anything, you didn't write that task yourself.
  • PLAY RECAP — the summary, one line per host, with counts you'll read on every single run for the rest of your Ansible career:
    • ok — tasks that succeeded and needed no change (the host already matched what you asked for).
    • changed — tasks that succeeded and did change something on the host.
    • unreachable — Ansible couldn't connect to the host at all (network, SSH, wrong address).
    • failed — the task ran but reported an error.
    • skipped — the task's condition wasn't met, so it didn't run (you'll meet conditionals later in this course).

Best practice — always check the recap, not just "did it print red text": a run can show failed=0 and still not be what you wanted if changed is higher than you expected, or unreachable is non-zero for a host you thought was fine. Get in the habit of reading all five numbers, every run — the same discipline as reading a Terraform plan before typing yes.

Try it — before looking below

Q1. Your playbook has one play with three tasks. Task 2 fails on a host. Does Ansible still run task 3 on that host?

No — by default, Ansible stops running further tasks in that play for that host as soon as one task fails on it. Other hosts that didn't fail keep going. (Ansible has options to change this behavior with error handling, covered later in this course — the default is "stop for the host that broke.")

Q2. In the PLAY RECAP, a host shows ok=2 changed=0 unreachable=0 failed=0 skipped=0. What does changed=0 tell you?

Every task succeeded, but none of them had to actually change anything on the host — the host was already in the desired state for all 2 tasks. This is a preview of idempotency, the exact topic of the next lesson: running the same playbook twice should show changed=0 the second time.

Now write your own

Reuse the localhost inventory file from Lesson 4 (the one pointing at localhost with a local connection, no SSH needed). In the same folder, create playbook.yml:

- name: My first playbook
  hosts: localhost
  tasks:
    - name: Print a message
      ansible.builtin.debug:
        msg: "Hello from my first playbook"

    - name: Create a practice directory
      ansible.builtin.file:
        path: /tmp/ansible-practice
        state: directory

Then:

  • run ansible-playbook -i inventory playbook.yml
  • find the TASK [Print a message] section and confirm your message printed
  • find the TASK [Create a practice directory] section — check its status. Was it ok or changed?
  • read the PLAY RECAP line and check all five counts against what you expected
  • confirm the directory exists: ls -ld /tmp/ansible-practice
  • run the exact same command a second time. Watch what happens to the changed count on the directory task — hold onto that observation, it's the whole subject of Lesson 7.

Try it yourself before checking the reference command below.

Reveal the reference command

ansible-playbook -i inventory playbook.yml
ls -ld /tmp/ansible-practice
ansible-playbook -i inventory playbook.yml
