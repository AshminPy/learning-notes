Molecule testing

ansible-lint (Lesson 27) reads your role's code and flags patterns known to cause problems — but it never actually runs anything. It can't tell you whether your role converges without errors against a real target, and it can't tell you whether it's genuinely idempotent (Lesson 7's central concept: running it twice should report changes on the first run and zero changes on the second). Right now, verifying that means manually spinning up a host, running your role twice, and eyeballing the output. Molecule automates exactly that, in a disposable test environment, with one command.

Mental model: Molecule is a test harness built specifically for Ansible roles. It spins up a disposable instance (a container, by default), runs your role against it, runs it a second time and checks that nothing changed, optionally checks specific facts about the result, then tears the instance down — all repeatable, all scriptable in CI, no host of yours ever touched.

Why "it worked once" isn't enough

A role can converge successfully — every task reports ok or changed, no errors — and still be broken in the way Lesson 7 warned about: if you ran it a second time, would anything report changed again when it shouldn't? Molecule checks both things, not just the first:

  • Converge — does the role apply cleanly against a fresh instance, with no task failures?
  • Idempotence — run it again immediately. Does the second run report zero changes?

Installing it

Confirmed against Molecule's own docs — Molecule ships a "delegated" driver by default, but the common real-world setup adds a container driver plugin:

# Base install
$ python3 -m pip install --user molecule

# Add the podman driver plugin (or swap podman for docker)
$ python3 -m pip install --user "molecule-plugins[podman]"

You'll also need the container engine itself (Podman or Docker) installed and running — Molecule drives it, it doesn't replace it.

Scenario anatomy

Inside a role, molecule init scenario creates a molecule/default/ directory — a scenario is a complete, named test configuration for that role:

my_role/
  tasks/
    main.yml
  molecule/
    default/
      molecule.yml     # driver, platforms (what instance(s) to spin up), verifier config
      converge.yml      # the playbook that applies your role to the test instance
      verify.yml        # assertions run after converge, to check the result

A minimal molecule.yml:

driver:
  name: podman
platforms:
  - name: instance
    image: docker.io/library/rockylinux:9
provisioner:
  name: ansible

A minimal converge.yml — this is the playbook Molecule actually runs against the test instance:

- name: Converge
  hosts: all
  tasks:
    - name: run the role under test
      ansible.builtin.include_role:
        name: my_role

A minimal verify.yml — assertions checked after convergence:

- name: Verify
  hosts: all
  tasks:
    - name: confirm the config file exists
      ansible.builtin.stat:
        path: /etc/myapp/myapp.conf
      register: config_file

    - name: assert it's actually there
      ansible.builtin.assert:
        that:
          - config_file.stat.exists

The full test sequence

Confirmed against Molecule's workflow reference — molecule test runs every one of these steps in order:

StepWhat it does
dependencyInstalls the role's own dependencies (e.g. from a requirements.yml)
createProvisions the test instance(s) defined in molecule.yml
prepareAny setup the instance needs before the role runs (rarely used)
convergeRuns converge.yml — applies your role to the instance
idempotenceRe-runs converge.yml and fails the whole test if the second run reports any changes
side_effectOptional — simulate a failure or external event, if your scenario defines one
verifyRuns verify.yml — your assertions about the end result
destroyTears down the test instance(s)

The idempotence step is the one that directly enforces Lesson 7's rule: it isn't satisfied by the role merely running without errors — it fails the test outright if anything reports changed on that second run.

The core commands

CommandDoes
molecule testThe full sequence above, start to finish, always ending in destroy
molecule convergeJust create + converge — leaves the instance running so you can keep iterating
molecule verifyJust runs verify.yml against the already-running instance
molecule loginOpens a shell inside the running test instance, for debugging
molecule destroyTears the instance down when you're done

Common mistake: running molecule test in a tight edit-run-edit loop while actively developing a role. Every molecule test destroys and recreates the instance from scratch — slow, and wasteful when you're just iterating on one task. Use molecule converge repeatedly while you work (it reuses the running instance), then run the full molecule test once at the end to confirm idempotence and verification both pass.

Production note: CI runs molecule test on every change to a role — the full sequence, including idempotence and destroy, is exactly what you want enforced automatically on every PR. Locally, engineers live in the faster converge / login / verify loop and only run the full test before pushing.

Try it — before looking below

Q1. You add a task to a role using ansible.builtin.command: touch /etc/myapp.conf with no idempotency handling. What would Molecule's idempotence step report, and why?

It would fail. The idempotence step re-runs converge.yml and requires zero changes on that second run — a bare command/touch task always reports changed: true regardless of prior state, so the second run isn't "zero changes," and Molecule fails the test even though the role itself ran without errors.

Q2. While actively iterating on a role's tasks, why would you run molecule converge repeatedly instead of molecule test each time?

molecule test runs the entire sequence — create, converge, idempotence, verify, destroy — every time, which recreates the test instance from scratch and is slow for a tight edit loop. molecule converge just re-applies the role to the already-running instance, so you iterate fast; you run the full molecule test once at the end to confirm idempotence and verification both actually pass.

Q3. What are the three files in a default Molecule scenario, and what does each one do?

molecule.yml (the scenario's config — driver and platforms/instances to create), converge.yml (the playbook Molecule runs to apply your role to the test instance), and verify.yml (assertions checked after convergence, to confirm the role actually did what it should).

Now write your own

In a practice folder, create a tiny role and give it a Molecule scenario:

$ mkdir -p my_role/tasks
$ cat > my_role/tasks/main.yml <<'EOF'
- name: create a marker file
  ansible.builtin.file:
    path: /tmp/molecule_marker.txt
    state: touch
    mode: '0644'
EOF

Then, from inside my_role/:

  • run molecule init scenario (or hand-create the molecule/default/ files shown above, pointing converge.yml at my_role)
  • run molecule test — watch it move through create, converge, idempotence, verify, destroy
  • confirm the idempotence step passes — the file module is idempotent by design, so a second run of this task should report no change
  • now break idempotence on purpose: change the task to ansible.builtin.command: touch /tmp/molecule_marker.txt and run molecule test again
  • read the failure — the idempotence step should now fail, because command reports changed every run

Try it yourself before checking the expected result below.

Reveal what you should see

With the file module: all steps pass, including idempotence — the second converge reports zero changes. After switching to ansible.builtin.command: touch ...: converge still succeeds, but the idempotence step fails, because the second run of a bare command task reports changed again. This is Molecule directly enforcing Lesson 7's idempotency rule — not just "did it run," but "does running it again change nothing."

Recap
  • ansible-lint reads code; Molecule actually runs your role against a disposable instance and checks the result — including whether it's truly idempotent, the thing Lesson 7 says matters most.
  • A scenario is molecule.yml (config), converge.yml (applies the role), verify.yml (assertions).
  • molecule test runs the full sequence — create, converge, idempotence (re-run, expect zero changes), verify, destroy.
  • Iterate locally with molecule converge (fast, reuses the instance); run the full molecule test before pushing, and always in CI.
