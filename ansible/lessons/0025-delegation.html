Delegation

Every task you've written so far runs on every host in the play's target group — that's the default, and it's usually what you want. But sometimes one specific task needs to run somewhere else entirely. Think about updating a web server that sits behind a load balancer: before you touch the server, you need to pull it out of the load balancer's pool — and that step has to happen on the load balancer, not on the server being updated. Delegation is how you tell one task "run on a different host than the rest of this play."

Mental model: a play's hosts: line sets the default audience for every task in it — like addressing an email to a whole team. delegate_to is a sticky note on one specific task that says "actually, send just this one to someone else instead." The rest of the play still goes to the team; only that one task's destination changed.

delegate_to: sending one task to a different host

Confirmed against Ansible's own docs — here's the load balancer example, the canonical case for delegation:

- hosts: webservers
  serial: 5

  tasks:
    - name: Take out of load balancer pool
      ansible.builtin.command: /usr/bin/take_out_of_pool {{ inventory_hostname }}
      delegate_to: 127.0.0.1

    - name: Actual steps would go here
      ansible.builtin.yum:
        name: acme-web-stack
        state: latest

    - name: Add back to load balancer pool
      ansible.builtin.command: /usr/bin/add_back_to_pool {{ inventory_hostname }}
      delegate_to: 127.0.0.1

The play targets webservers, so without delegate_to, all three tasks would run on each web server in turn. But the first and third tasks have delegate_to: 127.0.0.1 — so instead of running on the web server currently being processed, they run on the control node (in this real-world version, 127.0.0.1 would usually be the load balancer's address, or you'd delegate to a host named in your inventory, like delegate_to: loadbalancer). {{ inventory_hostname }} still refers to the web server the play is currently working on — delegation changes where the task executes, not which host's name and variables it's reasoning about. That's the whole trick: "run this command, about this host, but execute it over there."

delegate_to: localhost — the everyday pattern

The most common delegation you'll actually write day to day isn't the load balancer dance — it's delegating a task to the control node itself, so a remote-targeted play can still do one local thing, like write a log entry, send a notification, or drop a file on the machine running Ansible.

- hosts: webservers
  tasks:
    - name: Update the application
      ansible.builtin.yum:
        name: acme-web-stack
        state: latest

    - name: Record that this host was updated
      ansible.builtin.lineinfile:
        path: /tmp/update-log.txt
        line: "{{ inventory_hostname }} updated at {{ ansible_date_time.iso8601 }}"
        create: true
      delegate_to: localhost

localhost here means the control node — the machine running ansible-playbook — regardless of which remote host the play is currently targeting. Without delegate_to: localhost, that lineinfile task would try to write /tmp/update-log.txt on each remote web server instead of on your own machine. The docs also show a shorthand for this specific case, local_action, which delegates to 127.0.0.1 automatically:

tasks:
  - name: Take out of load balancer pool
    local_action: ansible.builtin.command
    args:
      cmd: /usr/bin/take_out_of_pool {{ inventory_hostname }}

local_action and delegate_to: localhost do the same thing for this case — delegate_to is the more general form (it works for any host, not just the control node), so it's the one you'll see and reach for most often.

run_once: true — once for the play, not once per host

Delegation answers "which host runs this task." A related but different question is "how many times should this task run at all." By default, a task runs once per host in the target group — five hosts means the task runs five times. Sometimes that's wrong: a task like "send one Slack notification that the deploy started" should fire exactly once for the whole play, not once per host (which would spam five identical messages). run_once: true fixes that — the task runs a single time, on the first host in the play, and is skipped everywhere else.

- name: "handle concurrency with a loop on the hosts with `run_once: true`"
  lineinfile: ""
  run_once: true
  loop: '{{ ansible_play_hosts_all }}'

That example from the docs shows the two options combined for a task that needs to touch every host's data but only execute once — run_once: true stops it from repeating per host, and the loop lets that single execution still iterate over all the hosts' data if needed. For a simpler case — one Slack message, no loop — you'd just write:

- name: Notify Slack that the deploy finished
  community.general.slack:
    token: "{{ slack_token }}"
    msg: "Deploy finished on {{ ansible_play_hosts_all | length }} hosts"
  run_once: true

Don't mix these two up: delegate_to changes where a task runs (which host executes it) — it still runs once per host in the play unless you also add run_once. run_once changes how many times a task runs (once for the whole play instead of once per host) — it still runs on a host from the play's group unless you also add delegate_to. They solve different problems and combine cleanly when you need both — like sending exactly one Slack message from the control node, not from whichever web server happened to be first.

Try it — before looking below

Q1. A play targets hosts: webservers (3 hosts). One task has no delegate_to and no run_once. How many times does it run, and where?

Three times — once on each of the three web servers. That's the default behavior every task has had in every earlier lesson: one execution per host in the target group. Delegation and run_once are both opt-in changes to that default, not the default itself.

Q2. Same play, 3 hosts. A task has delegate_to: localhost but no run_once. How many times does it run, and where?

Three times — but every one of those three executions happens on the control node (localhost), not on the web servers. delegate_to only changes where the task runs, it doesn't reduce how many times it runs. If you wanted it to happen just once on the control node, you'd need run_once: true as well.

Now write your own

Reuse the inventory from earlier lessons with a group of hosts (or a group containing a couple of localhost-style entries if you don't have real remote hosts handy — the point is a group with more than one host, so run_once has something to prove). Create delegation.yml:

- name: Delegation practice
  hosts: webservers
  tasks:
    - name: Log that this play ran, from the control node
      ansible.builtin.lineinfile:
        path: /tmp/delegation-log.txt
        line: "Play ran for {{ inventory_hostname }} at {{ ansible_date_time.iso8601 }}"
        create: true
      delegate_to: localhost

    - name: Print one message for the whole play
      ansible.builtin.debug:
        msg: "This runs exactly once, no matter how many hosts are in the group"
      run_once: true

Then:

  • run ansible-playbook -i inventory delegation.yml
  • find TASK [Log that this play ran, from the control node] — notice it still shows one line per host in the recap-style output (it ran once per host, just on the control node each time)
  • check /tmp/delegation-log.txt on your control node (not on the remote hosts) — confirm it has one line per host in the group
  • find TASK [Print one message for the whole play] — confirm the message printed only once, even though the group has multiple hosts

Try it yourself before checking the reference command below.

Reveal the reference command

ansible-playbook -i inventory delegation.yml
cat /tmp/delegation-log.txt
# confirm one line per host in the "webservers" group, and the debug message printed exactly once

Recap
  • delegate_to: <host> runs one task on a different host than the rest of the play, while {{ inventory_hostname }} still refers to the host the play is currently working through — the load-balancer take-out/add-back pattern is the classic case.
  • delegate_to: localhost is the everyday version: run one task on the control node itself (a local log write, a local notification) while the rest of the play targets remote hosts.
  • run_once: true runs a task exactly once for the whole play, on the first host, instead of once per host — the fix for "send one Slack message," not "send N."
  • The two are independent: delegate_to changes where a task runs, run_once changes how many times it runs. Combine them when you need both, like one Slack message sent from the control node.
