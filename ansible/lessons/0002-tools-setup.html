Tools setup: install Ansible, practice hosts

Two things before any playbook: Ansible itself installed on your own machine, and something for it to manage. Ansible has no agent to install on the machines it manages — it connects over plain SSH and runs Python there temporarily. That means setup is short: one install on your side, and a target to point at.

Simple example: Ansible is a command-line program, ansible (plus friends like ansible-playbook). You run it from your own machine — called the control node — and it reaches out over SSH to managed nodes to do work. No software needs to be pre-installed on the managed node beyond Python and SSH access. That agentless design is one of Ansible's defining traits — keep it in mind, it explains a lot of what's coming later in this course.

1. Install Ansible on your control node

Ansible's own docs are explicit: the officially supported way to install the Python packages is with pip (or pipx if your OS restricts installing packages into the system Python). This works the same way on macOS, Linux, and Windows-via-WSL, since the control node just needs "nearly any UNIX-like machine with Python installed."

Ansible's docs don't publish a Homebrew method for macOS — the officially documented cross-platform path is pip or pipx, so that's what this course uses on macOS. If you already have a package-manager install working (e.g. an unofficial brew formula), it's fine to keep using it — just confirm the version with the check below.

2. Confirm the install

Open a terminal and run:

ansible --version

You should see a line like ansible [core 2.x.x] along with the Python interpreter path it's using. The exact version will be whatever is current — that's fine. If the command isn't found, the install went into a location that isn't on your PATH — close and reopen the terminal, or re-check the install step above.

3. Your practice environment: control node + managed node

Ansible's whole job is to manage other machines over SSH. So strictly, you need two things: the control node (your own machine, where you just installed Ansible) and at least one managed node to point it at. For the first stretch of this course, we'll use the simplest zero-cost option: your own machine acting as both.

Ansible supports this officially through a special connection setting, ansible_connection=local, which tells it to run tasks directly on the control node instead of going out over SSH. In an inventory file it looks like this — this is Ansible's own documented example:

[targets]

localhost              ansible_connection=local
other1.example.com     ansible_connection=ssh        ansible_user=myuser
other2.example.com     ansible_connection=ssh        ansible_user=myotheruser

Notice localhost sits in the same inventory as real SSH-managed hosts — ansible_connection=local is just a per-host setting, not a different mode of Ansible. That's exactly why it's a good teaching tool: everything you learn against localhost now uses the same commands and files you'll later point at real servers.

A note on where this stops working: localhost with ansible_connection=local is enough for playbooks, variables, facts, conditionals, loops, and handlers — most of this course. It is not enough once we reach inventory-at-scale and delegation lessons, which are specifically about coordinating multiple real hosts. At that point you'll need a genuine second machine — a free-tier cloud VM (e.g. AWS/GCP/Azure free tier), a local VM via Vagrant + VirtualBox, or a Docker container with an SSH server running inside it. This course will tell you exactly when that becomes necessary — you don't need to set it up today.

4. First connectivity check

Create a small inventory file to hold your practice target. In your working folder, make a file named inventory.ini:

[local]
localhost ansible_connection=local

Then run an ad-hoc command — a one-off Ansible action with no playbook file, using the ping module (which just confirms Ansible can reach the host and run Python there, no network ping involved):

ansible local -m ping -i inventory.ini

A working setup replies with something like:

localhost | SUCCESS => {
    "ansible_facts": {
        "discovered_interpreter_python": "/usr/bin/python3"
    },
    "changed": false,
    "ping": "pong"
}

"pong" is the whole point of this check — Ansible found the host, connected to it (locally, in this case), found a Python interpreter, and ran a module successfully. Every later lesson builds on this exact command shape: ansible <pattern> -m <module> -i <inventory>.

Try it — before looking below

Q1. Why does ansible local -m ping -i inventory.ini work with no real second machine, and where will that stop being enough?

The inventory sets ansible_connection=local on the localhost entry, so Ansible runs tasks directly on your own machine instead of over SSH — no second machine needed. It stops being enough once a lesson is specifically about managing multiple real hosts (inventory at scale, delegation) — those need a genuine second host such as a free-tier cloud VM, a Vagrant/VirtualBox VM, or a Docker container running SSH.

Now do it yourself

Checklist — do these in order, don't skip ahead:

  • [ ] Install Ansible with pip/pipx (or your OS package manager)
  • [ ] Run ansible --version and confirm you see a version number printed
  • [ ] Create inventory.ini with the [local] group and localhost ansible_connection=local line
  • [ ] Run ansible local -m ping -i inventory.ini and confirm you get "ping": "pong"

Recap
  • Ansible is agentless — install it once on your control node with pip/pipx (or apt/dnf on Linux); managed nodes just need Python and SSH.
  • ansible --version confirms the install worked.
  • For most of this course, localhost with ansible_connection=local in your inventory is your zero-cost practice target — same commands you'll later run against real hosts.
  • A real second host (cloud free-tier VM, Vagrant/VirtualBox VM, or Docker+SSH container) becomes necessary later, for inventory-at-scale and delegation lessons.
  • ansible local -m ping -i inventory.ini replying "pong" is your proof the whole chain — install, inventory, connection, Python — works end to end.
