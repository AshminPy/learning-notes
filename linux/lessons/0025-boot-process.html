Boot Process & Troubleshooting

A machine that won't boot, or boots into the wrong state, is one of the few incidents where SSH itself isn't available yet — you need to understand the boot sequence to know which stage failed and what console access you actually need.

Simple example: A typo in /etc/fstab that references a filesystem that no longer exists can drop a server into an emergency/rescue shell on boot — it never gets far enough to start SSH, so the fix requires console access, not a remote login.

The boot sequence, high level

StageWhat happens
Firmware (BIOS/UEFI)Hardware self-test, then hands off to the bootloader
Bootloader (GRUB, typically)Loads the selected kernel and initial RAM disk into memory
Kernel initKernel initializes hardware drivers, mounts the root filesystem
systemd (PID 1)Starts every service in dependency order, per Lesson 7 — reaches a "target" (runlevel equivalent) like multi-user.target

A failure early (firmware, bootloader) usually means no console output reaches you over SSH at all — you need physical or virtual console access (cloud provider's "serial console" feature, for a VM). A failure late (a specific systemd service failing) usually still lets you SSH in, since core networking already started.

Diagnosing after a failed boot

systemctl --failed              # every service that failed to start this boot
journalctl -b                   # full log of the current boot
journalctl -b -1                # full log of the PREVIOUS boot (if it crashed)
systemd-analyze blame           # which services took the longest to start

If a system won't boot because of a bad /etc/fstab entry, adding nofail to that mount's options prevents it from blocking the entire boot in the future — a single bad mount shouldn't be able to take down an otherwise-healthy system.

Try it — before looking below

Q1. A server rebooted after a config change and now SSH doesn't respond at all — not even a connection refused, just a timeout. Is this more likely an early-stage or late-stage boot failure?

Early-stage — if SSH doesn't even refuse the connection, networking likely never came up, meaning the failure happened before or during early systemd startup. You'd need console access, not another SSH attempt, to see what's actually happening.

Now try it yourself

systemctl --failed              # any services that failed on this boot
systemd-analyze                 # total boot time breakdown
systemd-analyze blame | head    # slowest-starting services

Source

systemd bootup(7) man page — the official reference for the systemd boot sequence.

Recap
  • Boot order: firmware → bootloader (GRUB) → kernel init → systemd starts services to reach a target.
  • An early-stage failure usually means no SSH at all — you need console access; a late-stage (single service) failure usually still allows SSH in.
  • systemctl --failed and journalctl -b are the first two commands after any boot problem.
A cloud provider's "serial console" or "out-of-band console" feature is the equivalent of physical console access for a VM — know how to reach it before you need it during an actual outage.
