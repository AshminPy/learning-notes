Security Fundamentals

Two layers of Linux security work independently of the permissions from Lesson 3: mandatory access control (a stricter rule system that even root can't casually override) and the firewall (which controls what network traffic is allowed in and out at all).

Simple example: A misconfigured web server directory can have perfect Unix permissions and still fail to serve files — because SELinux (RHEL family) or AppArmor (Debian/Ubuntu family) enforces its own separate policy on top of standard permissions, and that policy is what's actually blocking access.

Mandatory access control

SystemDistro familyCheck status
SELinuxRHEL/Fedora/Rocky/Almagetenforce (Enforcing / Permissive / Disabled)
AppArmorDebian/Ubuntuaa-status

The mental model is the same for both: standard Unix permissions (Lesson 3) say who can read/write/execute a file. Mandatory access control adds a second, independent layer of rules — even the file's owner and root are bound by it. This is exactly why "permissions look fine but access still fails" is one of the most common confusing symptoms in production.

Never permanently disable SELinux/AppArmor to "fix" an access problem — that removes the second security layer entirely instead of finding the actual policy rule that's blocking you. setenforce 0 (temporary, SELinux) or checking the relevant policy/audit log is the correct first step to confirm SELinux is the cause before deciding what to actually change.

firewalld and ufw are friendlier front-ends most people use day to day; nftables (successor to the older iptables) is the actual kernel packet-filtering framework underneath both.

Try it — before looking below

Q1. A process has correct Unix file permissions (rwx for its user) but still gets "permission denied." What's the second layer to check before assuming the permissions are wrong?

Mandatory access control — SELinux (getenforce, check with ausearch/audit log) or AppArmor (aa-status). It enforces a separate policy on top of standard permissions and is a very common cause of this exact symptom.

Now try it yourself

# On a RHEL-family system:
getenforce
firewall-cmd --list-all

# On a Debian/Ubuntu system:
aa-status
ufw status

Recap
  • SELinux (RHEL family) and AppArmor (Debian family) enforce a second, independent access-control layer on top of standard Unix permissions.
  • "Permissions look correct but access still fails" is the classic symptom of a mandatory-access-control block, not a permissions bug.
  • firewalld/ufw are friendly front-ends; nftables is the modern underlying kernel packet-filtering framework on most current distros.
Never leave SELinux/AppArmor permanently disabled as a "fix" — find the specific policy denial in the audit log and address that instead.
