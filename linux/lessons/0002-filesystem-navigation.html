Filesystem Hierarchy & Navigation

Learning objectives

  • Explain the Filesystem Hierarchy Standard (FHS) and what lives where, and why
  • Navigate confidently with absolute and relative paths
  • Use find and basic globbing to locate files without guessing
  • Understand hard links vs symbolic links and when each is appropriate
  • Diagnose "no space left on device" even when df shows free space

Mental model

Everything is a file, and there is exactly one filesystem tree, rooted at /. Unlike Windows' separate drive letters (C:\, D:\), Linux mounts every disk, partition, and even some non-disk things (like /proc, which represents running processes) as a directory somewhere under one single tree starting at /. "Everything is a file" means devices, sockets, and process info are all accessed through the same filesystem interface as a text document.

Beginner-friendly explanation

When you plug in a second disk on Windows, it becomes D:\ — a separate tree. On Linux, that disk gets mounted onto an existing directory (say, /mnt/data), and from then on, everything under /mnt/data lives on that separate disk, but it looks and behaves like any other directory in the one unified tree. You (usually) can't tell just by looking at a path whether it's on the root disk or a separate mounted one — you have to ask (Lesson 9 covers mount/df in depth).

Real-world analogy

Think of the filesystem like a company's single org chart, not separate org charts per office location. A new office (a new disk) doesn't get its own separate chart — it gets grafted onto the existing one at a specific reporting line (a mount point). Someone reading the chart sees one continuous structure, even though "IT support" and "the new office" might physically be in different buildings (different physical disks).

The Filesystem Hierarchy Standard (FHS)

flowchart TD
    ROOT["/"]
    ROOT --> BIN["/bin, /usr/bin — executables"]
    ROOT --> ETC["/etc — system-wide config"]
    ROOT --> HOME["/home/<user> — personal files"]
    ROOT --> VAR["/var — logs, variable data"]
    ROOT --> TMP["/tmp — temporary files, cleared on reboot"]

PathWhat lives hereWhy it matters operationally
/etcSystem-wide configuration filesFirst place to look when a service misbehaves — its config is almost always under /etc/<service>
/var/logLog filesFirst place to look when debugging any failure — see Lesson 19
/tmpTemporary filesOften cleared on reboot or by a scheduled job — never store anything you need to keep here
/home/<user>Personal files for each userOn shared servers, quota/disk-full issues often trace back here
/procA virtual filesystem — not real files on disk, a live window into kernel/process stateReal-time process/kernel inspection without a special tool — e.g. /proc/<pid>/status
/optThird-party/optional software not managed by the distro's package managerCommon install location for vendor-supplied production software

/proc being a live view — not stored data — means reading it never goes stale, but it also means some files there can leak sensitive process info (command-line arguments, environment variables) to any user who can read them. Production hardening often restricts /proc visibility between users (hidepid mount option).

Absolute vs relative paths

An absolute path starts with / and is unambiguous from anywhere: /etc/nginx/nginx.conf always means the same file, no matter your current directory. A relative path is interpreted from wherever you currently are (pwd): ../config/app.conf means "go up one directory, then into config."

Scripts using relative paths without first confirming the working directory are a classic source of "works on my machine, fails in cron/CI" bugs — a cron job or CI runner often starts in a different working directory than your interactive shell. Always use absolute paths (or explicitly cd first) in anything automated.

Hands-on lab — navigate and locate

Try it

pwd                          # print current directory (absolute path)
cd /var/log                  # absolute path — works from anywhere
ls -la                       # list all, including hidden (dot) files, long format
cd -                         # jump back to your previous directory
cd ~                         # go to your home directory
cd ..                        # go up one level (relative)

Now practice finding things without guessing:

find /etc -name "*.conf" -type f 2>/dev/null | head -5
find / -maxdepth 3 -type d -name "log*" 2>/dev/null

find searches recursively by real criteria (name, type, size, modified time) — much more reliable than trying to remember exactly where something lives.

In production, symlinks are everywhere for versioned releases: /opt/app/current symlinked to /opt/app/releases/v2.3.1, atomically re-pointed to the new version on deploy, and instantly rolled back by re-pointing to the old target.

Troubleshooting walkthrough — "No space left on device" but df shows free space

StepDetail
SymptomsA process fails to write a file with ENOSPC ("No space left on device"), but df -h shows plenty of free space on the relevant filesystem.
InvestigationRun df -i instead of df -h — this shows inode usage, not byte usage. A filesystem has a fixed number of inodes (metadata slots, one per file/directory) set at creation time, independent of disk space.
Root causeA huge number of tiny files (a classic case: an application writing millions of small cache/session files) exhausted the inode table even though plenty of disk bytes remained free.
ResolutionDelete or archive the excess small files to free inodes. There is no "add more inodes" fix without reformatting the filesystem with different parameters — this must be prevented, not just fixed after the fact.
PreventionMonitor df -i alongside df -h in production dashboards; design apps that generate many small files to clean them up or use a proper database/object store instead of the filesystem for high-volume ephemeral data.

Common mistakes

Deleting a symlink with rm -rf linkname/ (trailing slash) when you meant to remove only the link — depending on the shell and exact command, a trailing slash can cause tools to follow the link and act on its target instead of the link itself. When in doubt, use rm linkname (no trailing slash) to remove just the link.

Best practices

Never hardcode paths like /home/ashmin/app in scripts meant to run elsewhere — use environment variables, config files, or at minimum $HOME. Keep application data out of /tmp if it must survive a reboot. Follow FHS conventions when deploying your own software (config in /etc, logs in /var/log, binaries in /opt or /usr/local/bin) so the next engineer can find things using the same instincts this lesson teaches.

Performance considerations

find / without narrowing scope (no -maxdepth, searching from the true root) walks the entire filesystem tree, including large mounted network filesystems if any are attached — this can be slow and I/O-heavy on a large or busy system. Scope your searches (-maxdepth, a more specific starting path) whenever you know roughly where to look.

Production checklist

  • Scripts use absolute paths or explicitly cd first — never assume a working directory
  • Monitoring covers both df -h (space) and df -i (inodes)
  • New services follow FHS conventions (config in /etc, logs in /var/log)
  • Deploy tooling uses an atomically-repointed symlink for instant rollback capability

Interview questions

Q. What's the difference between a hard link and a symbolic link?

A hard link is a second name pointing to the exact same data (inode) on the same filesystem — the data survives as long as any hard link to it exists. A symbolic link is a separate small file storing a path to another file; it can cross filesystems and point to directories, but breaks (dangles) if the target is removed.

Q. A server reports "no space left on device" but df -h shows 40% free. What do you check next, and why?

df -i — inode exhaustion. A filesystem can run out of inodes (metadata slots, one per file) from having too many small files, entirely independent of how many actual bytes are used.

Recap
  • One unified filesystem tree rooted at / — separate disks are mounted onto directories in that same tree, not given separate drive letters.
  • FHS gives every major directory a purpose: /etc config, /var/log logs, /tmp ephemeral, /proc live kernel/process state.
  • Absolute paths are unambiguous everywhere; relative paths depend on your current directory — use absolute paths in scripts/automation.
  • Hard links share the same underlying data; symlinks are separate pointer files that can dangle.
  • "No space" isn't always about bytes — check df -i for inode exhaustion too.

Practical challenge

On a real Linux system, create a directory with 50,000 tiny empty files (for i in $(seq 1 50000); do touch /tmp/test/file$i; done in a dedicated throwaway directory — clean it up after). Run df -i before and after to watch inode usage climb, even though df -h barely moves. Then create both a hard link and a symlink to one real file, delete the original, and observe which link survives and which dangles.

FHS conventions feel like arbitrary trivia until you're debugging a production incident at 2am and instinctively know to check /var/log first — that instinct is exactly what this lesson is building.
