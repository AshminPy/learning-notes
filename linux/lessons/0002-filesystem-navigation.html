The Disk That Isn't Full

Learning objectives

  • Diagnose "no space left on device" when the obvious check says there's plenty of space
  • Navigate the filesystem with absolute and relative paths, and know why the difference matters in automation
  • Explain what lives where under the Filesystem Hierarchy Standard, and use that to find a problem fast
  • Explain hard links vs symbolic links well enough to predict what happens when you delete one

The scenario

A deploy pipeline fails at 11 AM on a Tuesday — nothing dramatic, just a build step writing its output artifact: write failed: No space left on device. You check the obvious thing first:

$ df -h /
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        50G   30G   18G  64% /

64% used, 18GB free. The disk is not full. The error message says it is. Where do you begin?

Stop and think

Q. The error and the evidence directly contradict each other. What's your first move?

Question whether df -h is actually measuring the thing that's exhausted. It measures free bytes. "No space left" doesn't have to mean bytes — a filesystem can run out of something else entirely while bytes remain plentiful.

Q. What's a dangerous assumption here?

Assuming the error message is simply wrong or stale, and just retrying the build. If the real resource is exhausted, retrying wastes time and the next run fails identically — or somewhere else entirely.

Build the mental model

A filesystem tracks two separate, independently-exhaustible resources: data blocks (the actual bytes of file content — what df -h shows) and inodes (fixed-size metadata slots, one consumed per file or directory, allocated when the filesystem was created — what df -i shows). You can run out of either one completely independently of the other. A million 0-byte files can exhaust every inode on a disk that's otherwise almost empty.

Generate hypotheses

HypothesisPlausible?
Bytes are actually exhausted somewhere df -h / doesn't show (a different mount)Worth ruling out — the pipeline might write somewhere other than /.
Inode exhaustion — plenty of bytes free, no metadata slots leftFits the contradiction exactly.
A permissions problem masquerading as a space errorLess likely — Linux's real permission-denied errors read differently, but worth a fast check since it's cheap.

Investigate

Try it

Check every mounted filesystem for bytes, not just /:

df -h
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        50G   30G   18G  64% /
/dev/sdb1        20G  1.2G   17G   7% /var/app-data

Bytes are fine everywhere. Now test the inode hypothesis directly — same flag family, different letter:

df -i
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/sda1      3276800 3276800     0  100%  /
/dev/sdb1      1310720   50221 1260499    4%  /var/app-data

Gather evidence

/ is at 100% inode usage — zero free — while sitting at only 64% byte usage. That's your contradiction, fully explained by evidence, not a guess. Now find what's actually consuming the inodes:

Try it

# Count files per top-level directory to find the culprit fast
for d in /var /tmp /home /opt; do
  echo "$d: $(find "$d" -xdev | wc -l)"
done
/var: 2984112
/tmp: 812
/home: 4021
/opt: 340

/var is wildly out of proportion. One more level in:

find /var -maxdepth 3 -type d | xargs -I{} sh -c 'echo "$(find "{}" -maxdepth 1 | wc -l) {}"' | sort -rn | head -3
2981004 /var/app-data/sessions
 812 /tmp
 340 /opt

Eliminate wrong assumptions

Notice /var/app-data/sessions is under /var — but it wasn't originally on a separate mount, meaning someone (correctly, per FHS conventions covered below) intended session data to live under /var's variable-data purpose, but never mounted it separately. If you'd assumed "the app writes to /var/app-data, and /var/app-data is a separate healthy mount at 7%" without checking, you'd have missed the real problem entirely — that path only became a real separate mount recently, and the OLD session files from before that change are still sitting on the root filesystem, silently eating every inode.

Root cause

An application writing one tiny file per user session, never cleaning old ones up, accumulated millions of near-empty files over months — entirely on the root filesystem, before a separate data mount was added and only new sessions started landing there. Root's fixed inode count (set when the filesystem was formatted) was exhausted, even though almost no actual disk space was used.

Fix

Try it

# Confirm before deleting anything at this scale
find /var/app-data/sessions -type f | wc -l

# Delete in batches — 3 million unlinks at once can itself cause problems
find /var/app-data/sessions -type f -mtime +30 -delete

# Re-check
df -i /

Explain WHY the fix worked

Deleting a file releases its inode back to the free pool — that's the actual resource that was exhausted, so that's the actual fix. Freeing bytes wouldn't have helped at all; the disk was never short on bytes.

Prevent recurrence

Monitor df -i in every dashboard alongside df -h — most default monitoring only watches bytes. Fix the application to clean up its own session files, or move high-churn small-file data onto its own dedicated, properly-monitored mount from day one rather than discovering the gap during an incident.

  • Monitoring covers df -i, not just df -h, on every filesystem
  • High-churn small-file workloads get their own mount, sized and monitored deliberately
  • Cleanup/retention jobs exist for anything that writes files per-request/per-session

Widen the lens

Why does the Filesystem Hierarchy Standard (FHS) matter here? It exists precisely so an engineer can predict where variable, high-churn data lives (/var) versus stable installed software (/opt, /usr) versus truly temporary data cleared on reboot (/tmp) — without that convention, "where did 3 million session files end up" would have no faster answer than searching the entire disk blind.

flowchart TD
    ROOT["/"]
    ROOT --> ETC["/etc — config"]
    ROOT --> VARD["/var — variable data (this incident)"]
    ROOT --> TMP["/tmp — cleared on reboot, never for data you need to keep"]
    ROOT --> OPT["/opt — installed software"]

Absolute vs relative paths — why it mattered in every command above: every investigation command used an absolute path (/var/app-data/sessions), unambiguous regardless of where your shell session happened to start. A relative path in the cleanup command above, run from the wrong working directory, could have deleted the wrong thing entirely — a classic cause of "it worked when I tested it, then deleted production data when cron ran it from a different directory."

Hard links vs symbolic links — the trap this incident could have hidden: if any of those session files had been hard-linked elsewhere (a second name for the same inode), deleting the original wouldn't free that inode at all — the data, and the inode, survive until the last hard link is removed. A symbolic link, by contrast, is its own separate file with its own separate inode, pointing at a path; deleting the target leaves it dangling but doesn't block reclaiming the target's inode. Always check with ls -la (link count in the second column) before assuming a delete actually reclaimed anything.

ScaleDoes inode planning matter more or less?
A personal dev VMRarely matters — default inode counts are generous relative to typical usage.
A production fleet handling millions of small per-request writesMatters enormously — this exact incident, at scale, is one of the most common "impossible" disk-full reports SREs see.

Interview questions

Q. A server reports "no space left on device" but df -h shows 40% free. Walk through your investigation.

Check df -i for inode exhaustion — a filesystem can run out of inodes (metadata slots) independent of byte usage, typically from too many small files. Locate the offending directory with a targeted find/count sweep, confirm before deleting, then fix the root cause (retention/cleanup), not just the symptom.

Q. You delete a large file but df -h shows no space freed. What's a likely explanation?

Either a process still has the file open (Linux won't reclaim space until the last file handle closes — even after the directory entry is removed), or the file has other hard links still pointing at the same inode, so the underlying data isn't actually released yet.

Recap
  • "No space" isn't always about bytes — inodes are a separate, independently-exhaustible resource; check df -i alongside df -h.
  • FHS conventions (/var for variable data, /tmp for ephemeral, /opt for installed software) exist so you can predict where a problem lives instead of searching blind.
  • Absolute paths are unambiguous everywhere; relative paths depend on the working directory — a real risk in automation.
  • Hard links share the same inode/data; deleting one doesn't free anything until the last link is gone. Symlinks are separate files that can dangle.

Progressive challenge

  1. Level 1 — Fix: On a real or container Linux system, create 100,000 tiny files in a throwaway directory, confirm inode usage climbing via df -i, then clean them up and confirm it drops back down.
  2. Level 2 — Diagnose: You're told "disk full" on a box with df -h showing 55% free. Reproduce this lesson's investigation from scratch, unaided, and produce a one-paragraph incident summary.
  3. Level 3 — Design: Design a monitoring + alerting setup that would have caught this incident hours before the deploy pipeline failed, not after.
  4. Level 4 — Explain: Explain to a teammate why "df -h shows free space" does not mean "this filesystem has room for more files" — using this incident as the example, no notes.
  5. Level 5 — Optimize: The team wants to keep per-session files (product requirement, not up for debate) but never repeat this incident, while keeping infrastructure cost low. Propose a design — what changes, what does it cost, what does it trade off?
"No space left on device" feeling solvable by pure logic instead of a memorized fix — that instinct is the actual goal of this lesson, more than the specific inode command.
