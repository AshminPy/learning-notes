Containers at the Linux Level

A container isn't a lightweight VM — there's no separate kernel, no hypervisor. It's a set of normal Linux processes made to look isolated using two kernel features: namespaces (what a process can see) and cgroups (what resources a process can use). Docker and Kubernetes are built on top of these, not instead of them.

Simple example: Run a container and then run ps aux on the host machine — the container's processes show up as ordinary processes in the host's normal process list. They're not running in a separate kernel; they're regular processes with a restricted view.

Namespaces — what a process can see

NamespaceIsolates
PIDProcess IDs — a container's "PID 1" isn't the host's PID 1
NetworkIts own network interfaces, IP address, routing table
MountIts own view of the filesystem tree
UTSIts own hostname
UserIts own user/group ID mapping — "root" inside can map to an unprivileged user outside

Each namespace type gives a process a private view of one specific kind of system resource, while the underlying kernel resource is still shared and managed by one single kernel.

cgroups — what a process can use

Control groups limit and account for resource usage — CPU, memory, disk I/O — per group of processes. This is what stops one container from starving every other container on the same host of memory or CPU, and it's the exact mechanism Kubernetes resource limits (requests/limits) configure under the hood.

Seeing it directly

lsns                          # list namespaces currently active on this system
cat /proc/self/cgroup         # which cgroups the current shell process belongs to
docker inspect <container> --format '{{.State.Pid}}'   # find a container's real host PID

Try it — before looking below

Q1. Inside a container, ps aux shows your application as PID 1. On the host, what does that same process actually look like?

A completely ordinary process with a normal, much higher host PID — the "PID 1" inside the container is just what the PID namespace shows that process from the inside. It's the same kernel, the same process, viewed through two different lenses.

Now try it yourself

lsns | head            # see the namespace types active right now
cat /proc/self/cgroup   # see the cgroups your current shell belongs to

Source

namespaces(7) man page — the official kernel reference for namespace isolation.

Recap
  • A container is ordinary Linux processes with restricted visibility (namespaces) and bounded resources (cgroups) — no separate kernel.
  • Namespaces control what a process can see; cgroups control what it can use.
  • Kubernetes resource requests/limits are a friendlier interface over the same cgroups mechanism.
When a container "sees" a resource limit that seems wrong, checking cat /sys/fs/cgroup/... for that container's actual cgroup values is the ground truth — above any dashboard reporting on it.
