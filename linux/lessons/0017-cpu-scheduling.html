CPU & Scheduling

With more processes than CPU cores — which is always — the kernel's scheduler decides which process runs on which core at any given instant, switching between them many times per second. Load average is the standard number for seeing whether that scheduler is keeping up or falling behind.

Simple example: uptime shows load average as three numbers: 1, 5, and 15-minute averages. On a 4-core machine, a load average of 4.0 means the CPUs are fully busy with no queue; 8.0 means processes are waiting roughly as long as they're running.

Reading load average correctly

uptime
 14:32:01 up 3 days,  2:14,  1 user,  load average: 2.15, 1.98, 1.75

Load average means nothing on its own — it must be read against core count. A load of 4.0 is fine on 8 cores and a real problem on 2. Always check nproc first before judging a load number.

nproc     # how many cores this machine actually has

top / htop — live per-process view

Where load average gives you the whole-system trend, top (or the friendlier htop) shows which specific process is consuming CPU right now — sorted by %CPU by default, which is usually the first column worth checking during a spike.

Nice values — CPU priority

Every process has a "nice" value from -20 (highest priority) to 19 (lowest) that hints the scheduler how much CPU time to favor it with. A higher nice value means the process is being "nicer" to everyone else, yielding CPU time when there's contention.

nice -n 10 ./backup-job.sh    # start a job at lower priority
renice -n 5 -p 1234            # change priority of an already-running process

Background batch jobs — backups, log rotation, big data crunching — are good candidates for a higher (lower-priority) nice value, so they don't compete with user-facing services for CPU time during a busy moment.

Try it — before looking below

Q1. A server reports a load average of 6.0. Is that a problem?

It depends entirely on core count — run nproc first. 6.0 on a 16-core box is comfortably idle; 6.0 on a 4-core box means processes are queuing and waiting for CPU time.

Now try it yourself

nproc              # how many cores you have
uptime              # current load average, all three windows
top -o %CPU         # live view sorted by CPU usage — press q to quit

Source

uptime(1) man page — the official reference for load average reporting.

Recap
  • Load average only means something relative to core count — always check nproc first.
  • top/htop show which process is actually driving a CPU spike, load average only shows the trend.
  • Nice values (-20 to 19) let you deprioritize background batch work so it doesn't compete with user-facing services.
A rising load average with a healthy per-core CPU% in top often points to processes waiting on I/O, not CPU — Lesson 18 covers reading that distinction properly.
