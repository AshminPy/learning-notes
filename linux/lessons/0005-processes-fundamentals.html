Processes Fundamentals

Every running program is a process, identified by a process ID (PID). Processes have a lifecycle (running, sleeping, stopped, zombie) and the kernel talks to them using signals — small messages like "please stop" or "die right now."

Simple example: kill -15 1234 sends SIGTERM to PID 1234 — a polite "please shut down," which the process can catch and clean up after. kill -9 1234 sends SIGKILL — the kernel kills it immediately, no cleanup, no chance to object.

Inspecting and signaling processes

CommandWhat it does
ps auxList every process, with user, CPU%, memory%, and command
top / htopLive, continuously updating process view
kill -15 <pid>SIGTERM — ask the process to stop gracefully
kill -9 <pid>SIGKILL — force-kill, cannot be caught or ignored
pkill <name>Kill by process name instead of PID

Always try SIGTERM (kill -15, or plain kill, which defaults to SIGTERM) before SIGKILL. A process that catches SIGTERM can flush data, close connections, and exit cleanly — SIGKILL gives it zero chance to do any of that.

Try it — before looking below

Q1. Why would you reach for SIGKILL instead of SIGTERM?

When SIGTERM was already sent and the process didn't respond (it's genuinely stuck or ignoring the signal) — SIGKILL is the last resort, not the default first move, because it skips all cleanup.

Now try it yourself

sleep 300 &                # start a background process
ps aux | grep sleep        # find its PID
kill -15 %1                # or: kill -15 <pid>, ask it to stop
jobs                       # confirm it's gone

Source

signal(7) man page — the official reference for every Linux signal.

Recap
  • Every running program is a process with a PID; the kernel manages its lifecycle.
  • Signals are how you communicate with a process — SIGTERM (15) asks nicely, SIGKILL (9) doesn't ask.
  • Always try SIGTERM first — it gives the process a chance to clean up before exiting.
A process that ignores SIGTERM entirely and only dies to SIGKILL is worth investigating later, not just killing and forgetting — Lesson 23 covers that debugging.
