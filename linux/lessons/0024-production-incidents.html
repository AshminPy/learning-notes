Common Production Incidents

This lesson doesn't introduce new tools — it connects Lessons 1-23 into the handful of incidents that repeat across almost every Linux server in production. Recognizing the pattern fast is what separates a two-minute fix from a two-hour one.

Simple example: "Disk full" and "no space left on device" almost always mean one specific filesystem is full, found with df -h from Lesson 9 — not that the whole physical disk is out of capacity.

Five patterns, and which lesson's tools solve them

SymptomLikely causeTools (lesson)
"No space left on device"One filesystem full — often /var/log from unrotated logs, or a runaway process writing datadf -h, du -sh /var/log/* (Lesson 9)

A repeatable investigation order

Across nearly all of these, the same sequence gets to a root cause fastest: check the service's own status and logs first (cheapest, most specific), then check system-wide resource state (disk/memory/CPU), then check security layers (SELinux/firewall) only once the first two are ruled out — they're less common causes and more time-consuming to verify.

Restarting the service before checking why it failed destroys the evidence you need to find the real cause — journalctl -u <service> -n 100 before any restart, every time.

Try it — before looking below

Q1. A web server suddenly returns connection refused, but was working an hour ago. What are the first two things to check, in order?

First: systemctl status <service> and journalctl -u <service> -n 50 — is it even running, and what does it say happened. Second, if it's running: ss -tulnp to confirm it's actually listening on the expected port.

Now try it yourself

df -h                          # check for any filesystem near capacity
free -h                        # check memory pressure
journalctl -p err --since "1 hour ago"   # any recent errors, system-wide

Recap
  • Most production incidents repeat across five patterns: disk full, service crash-looping, OOM/swap, permission-vs-policy confusion, and network/firewall blocks.
  • Investigate cheapest and most specific first: service status/logs, then system resources, then security layers.
  • Never restart a failed service before capturing its logs — that's the evidence you need.
If a symptom doesn't match any of these five patterns, that's exactly when strace/lsof/tcpdump from Lesson 23 earn their keep — go one level deeper.
