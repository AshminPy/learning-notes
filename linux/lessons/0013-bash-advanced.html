Bash Scripting Advanced

The gap between a script that works on your laptop and one that's safe to run in production is a handful of specific habits: fail fast instead of limping on with bad state, quote your variables, and organize repeated logic into functions.

Simple example: set -euo pipefail at the top of a script makes it exit immediately on any error (-e), on any use of an unset variable (-u), and treats a failure anywhere in a piped command as a failure of the whole pipeline (-o pipefail) — three silent-failure traps closed in one line.

The safety line every real script should have

#!/bin/bash
set -euo pipefail

echo "This stops immediately if any command below fails."
FlagWithout it
-eA failed command is silently ignored, script keeps going with bad state
-uA typo'd variable name silently expands to an empty string instead of erroring
-o pipefailIn cmd1 | cmd2, only cmd2's exit code counts — cmd1 can fail invisibly

Functions

check_disk_space() {
    local threshold=$1
    local usage
    usage=$(df / | awk 'NR==2 {print $5}' | tr -d '%')
    if [ "$usage" -gt "$threshold" ]; then
        echo "WARNING: disk usage is ${usage}%"
        return 1
    fi
    return 0
}

check_disk_space 80

local keeps a variable scoped to the function — without it, every variable in bash is global by default, and a name collision between a function and the main script becomes a real bug.

Arrays

HOSTS=("web1" "web2" "web3")
for h in "${HOSTS[@]}"; do
    echo "Checking $h"
done
echo "Total hosts: ${#HOSTS[@]}"

Quoting — the habit that prevents the most bugs

Always quote variable expansions: "$var", not $var. Without quotes, a variable containing a space or a filename with special characters gets split into multiple words or glob-expanded — a script that works in every test and then breaks on one real file with a space in its name is almost always a missing-quotes bug.

Try it — before looking below

Q1. Your script references $FILENAME but you actually named the variable $FILE_NAME earlier. With plain bash, what happens? With set -u?

Plain bash: $FILENAME silently expands to an empty string — the typo goes unnoticed and the script runs with wrong (empty) data. With set -u: bash immediately errors "unbound variable" and stops, catching the typo right away.

Now try it yourself

echo '#!/bin/bash
set -euo pipefail
greet() {
    local name=$1
    echo "Hello, $name"
}
greet "World"' > safe.sh
chmod +x safe.sh
./safe.sh

Recap
  • set -euo pipefail is close to a default requirement for any script that isn't purely disposable.
  • Use local inside functions — otherwise every variable is global and name collisions become real bugs.
  • Quote every variable expansion ("$var") — the single most common source of "works on my machine" script bugs.
A script that behaves differently on one specific file or hostname almost always traces back to a missing quote — check that first before anything more exotic.
