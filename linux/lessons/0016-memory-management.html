Memory Management

The single most misread piece of Linux output is free -h — specifically the "used" column. Linux deliberately uses spare RAM to cache disk data, because free memory that isn't caching anything is memory being wasted, not memory being saved.

Simple example: A fresh server shows 200MB free. After running for a week, it might show 20MB free and gigabytes in the "cache" column — that's not a memory leak, it's the kernel using otherwise-idle RAM to cache files it expects to read again, and it releases that cache instantly if an application actually needs the RAM.

Reading free -h correctly

free -h
              total        used        free      shared  buff/cache   available
Mem:           15Gi       2.1Gi       1.2Gi       200Mi        12Gi        13Gi
ColumnWhat it really means
usedActually held by running programs — the number that matters for "am I about to run out"
buff/cacheDisk cache — reclaimable instantly if something else needs it, not a problem
availableWhat could actually be given to a new process right now, cache included — the real number to watch

Don't judge memory pressure from the "free" column alone — a small "free" number with a large "buff/cache" number is completely normal and healthy. Watch "available" instead; that's the number that accounts for reclaimable cache.

Swap — the overflow valve

Swap is disk space used as overflow when RAM is genuinely exhausted. Some swap use is normal; heavy, sustained swap use is a real problem, because disk is orders of magnitude slower than RAM — a system that's swapping heavily will feel sluggish across everything, not just the process using the memory.

swapon --show      # what swap is configured and how much is in use
vmstat 1 5         # 5 samples, 1 second apart — watch the si/so (swap in/out) columns

The OOM killer

When the system genuinely runs out of both RAM and swap, the kernel's Out-Of-Memory killer picks a process and kills it to free memory rather than let the whole system lock up. dmesg | grep -i "out of memory" or journalctl -k after an unexplained process death is the first place to look for OOM kill evidence.

Try it — before looking below

Q1. free -h shows almost no "free" memory and a huge "buff/cache" number. Is this server in trouble?

No — that's expected and healthy. The "available" column, not "free," is what tells you real memory pressure, because it accounts for cache the kernel can instantly reclaim.

Now try it yourself

free -h              # look at available, not free
swapon --show        # check swap configuration and usage
dmesg | grep -i "out of memory" || echo "no recent OOM kills found"

Source

kernel.org — proc.txt (meminfo documentation) — the official reference for how the kernel reports memory.

Recap
  • A low "free" number is normal — Linux uses spare RAM as disk cache; watch "available," not "free."
  • Some swap use is normal; sustained heavy swapping means genuine memory pressure and will slow the whole system down.
  • The OOM killer kills a process rather than letting the system lock up when RAM and swap both run out — check dmesg/journalctl -k after an unexplained process death.
A process that "randomly" dies with no application-level error in its own logs is worth an OOM check before anything else — the kernel doesn't ask the application's permission.
