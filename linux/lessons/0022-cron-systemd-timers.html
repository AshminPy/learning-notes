Automation with Cron & systemd Timers

Two ways exist to run something on a schedule: the classic cron, and the newer systemd timers. Both are still widely used — cron for its simplicity and near-universal familiarity, systemd timers for tighter integration with the logging and service management you already learned in Lessons 7 and 19.

Simple example: 0 3 * * * /opt/scripts/backup.sh in a crontab runs that script at 3:00 AM every day. Read left to right: minute, hour, day-of-month, month, day-of-week.

Cron

crontab -e          # edit your own user's crontab
crontab -l          # list your current cron jobs
FieldRange
Minute0-59
Hour0-23
Day of month1-31
Month1-12
Day of week0-6 (0 = Sunday)

* means "every value." */15 * * * * means every 15 minutes. 0 9 * * 1-5 means 9:00 AM on weekdays only.

Cron jobs run with a minimal environment — no $PATH from your interactive shell, none of your shell aliases or profile. A script that runs fine when you test it manually can fail silently under cron because it can't find a command that's normally on your $PATH. Always use full paths to commands inside cron scripts.

systemd timers

A systemd timer pairs with a systemd service unit: the service defines what to run, the timer defines when. The advantage over cron: the job's output goes straight into journalctl (Lesson 19), and you get the same systemctl status visibility as any other service.

systemctl list-timers                # see every active timer and its next run
systemctl status backup.timer        # is this specific timer active
journalctl -u backup.service         # see the actual job's output/logs

Try it — before looking below

Q1. A script works perfectly when you run it by hand, but fails when cron runs it. What's the most common reason?

Cron runs with a minimal environment — the script's $PATH doesn't include everything your interactive shell has, so a command the script calls by name (instead of full path) can't be found.

Now try it yourself

crontab -l                      # see your own scheduled jobs, if any
systemctl list-timers            # see every systemd timer on this system

Source

crontab(5) man page — the official reference for cron syntax.

Recap
  • Cron: five time fields (minute, hour, day-of-month, month, day-of-week), simple and universal.
  • Cron scripts should use full paths — the cron environment doesn't have your normal $PATH.
  • systemd timers pair with a service unit and integrate directly with journalctl and systemctl status.
A cron job that "just stopped running" with no error anywhere is almost always a $PATH or permissions issue in the cron environment, not a bug in the script itself.
