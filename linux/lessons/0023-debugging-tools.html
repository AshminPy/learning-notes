Debugging Tools

When a process behaves strangely and its own logs don't explain why, four tools let you observe what it's actually doing at the system call, file, and network level — without needing to modify or restart it.

Simple example: A process is failing to read a config file it should have access to. strace -e trace=open,openat -p <pid> shows every file-open attempt that process makes in real time — including the exact path and the exact error it got back.

The four essential tools

ToolShows
straceEvery system call a process makes — file opens, reads, network calls, everything it asks the kernel to do
lsofEvery file (including sockets and pipes) a process currently has open
tcpdumpRaw network packets — what's actually being sent and received on the wire
dmesgKernel ring buffer — hardware errors, OOM kills, driver messages (also viewable via journalctl -k, Lesson 19)

strace — what is this process actually doing

strace -p 1234                          # attach to a running process, watch its syscalls live
strace -e trace=network -p 1234         # narrow to just network-related syscalls
strace -c ./myprogram                   # run a program, get a summary count of syscalls used

lsof — what files does this process have open

lsof -p 1234              # every file this specific process has open
lsof -i :8080              # which process is using port 8080
lsof /var/log/app.log      # which process(es) have this specific file open

lsof -i :<port> is the fastest way to answer "what's already using this port" before starting a service that fails with "address already in use."

tcpdump — what's actually on the wire

tcpdump -i eth0 port 443 -c 20     # capture 20 packets on port 443
tcpdump -i eth0 host 10.0.0.5      # capture traffic to/from one specific host

Try it — before looking below

Q1. A service fails to start with "address already in use." Which single command tells you exactly which process is holding that port?

lsof -i :<port> — it lists exactly which process (and PID) currently has that port open.

Now try it yourself

lsof -i :22                 # see what's using the SSH port
strace -c ls / 2>&1 | tail   # run a harmless command, see a syscall summary
dmesg | tail -20             # recent kernel messages

Source

strace(1) man page — the official reference.

Recap
  • strace shows what system calls a process makes; lsof shows what files/sockets it has open — both without touching application logs.
  • tcpdump shows the actual network traffic, not what an application claims it sent.
  • lsof -i :<port> is the fast answer to "what's already using this port."
When application logs are silent about a failure, these four tools observe the process from the outside — often the fastest way to find a cause the application itself never reported.
