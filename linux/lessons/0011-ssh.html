SSH

SSH (Secure Shell) is how you get an encrypted remote terminal on another machine. In production, key-based authentication is the standard — not because passwords are inconvenient, but because they're the weakest, most guessable credential a server can expose to the internet.

Simple example: ssh-keygen -t ed25519 creates a key pair: a private key that never leaves your machine, and a public key you copy to any server you want to access. The server checks a signature made with the private key against the public key it already trusts — no password ever crosses the network.

Key-based auth, step by step

StepCommand
1. Generate a key pair (once, on your own machine)ssh-keygen -t ed25519
2. Copy the public key to a serverssh-copy-id user@server
3. Connect — no password neededssh user@server

The public key ends up in ~/.ssh/authorized_keys on the server. Anyone whose private key matches an entry in that file can log in — which is why the private key file itself must stay readable only by its owner (chmod 600) and never be copied or emailed anywhere.

~/.ssh/config — stop retyping connection details

Host prod-web
    HostName 203.0.113.10
    User deploy
    IdentityFile ~/.ssh/id_ed25519_prod
    Port 2222

With this saved, ssh prod-web connects with the right user, key, and port automatically — no need to remember or retype any of it.

Hardening basics

Two settings in /etc/ssh/sshd_config matter most for a server exposed to the internet: PasswordAuthentication no (forces key-only login, eliminating password brute-force) and PermitRootLogin no (forces attackers — and admins — to log in as a normal user and use sudo, never root directly). Change either one, then systemctl restart sshd to apply it.

Try it — before looking below

Q1. You generate a new SSH key pair. Which file do you copy to the remote server?

The public key (the .pub file). The private key never leaves your own machine — that's the entire security model.

Now try it yourself

ls -la ~/.ssh/                  # see your existing keys, if any
cat ~/.ssh/config 2>/dev/null   # see any saved host shortcuts
ssh -v user@host                # -v shows exactly which key/method was tried

Source

sshd_config(5) man page — the official OpenSSH server configuration reference.

Recap
  • SSH key auth: private key stays on your machine, public key goes on the server's authorized_keys.
  • ~/.ssh/config saves per-host connection details so you don't retype them.
  • Production hardening: disable password auth and disable direct root login in sshd_config.
ssh -v (or -vvv for more detail) is the fastest way to see exactly why a connection is being rejected — which key was offered, and why the server refused it.
