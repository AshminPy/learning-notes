Managing dev/stage/prod environments

Lesson 21 gave you workspaces as a tool for running the same config against multiple states. This lesson is the judgment call that sits on top of that tool: given a real team with a dev, staging, and production environment, which pattern do you actually reach for? There are three patterns you'll meet in real Terraform codebases, and they trade off isolation against duplication in different ways. This lesson closes out the Environments phase of the course — no new syntax, just the design thinking that decides how your whole repo is laid out.

Why this decision matters more than it looks

Get this wrong and the failure mode isn't a syntax error — it's a terraform apply against the wrong workspace at 2am touching production instead of dev, or a staging change that silently drifts from prod because nobody remembered to port it across a branch. The three patterns below all "work" in the sense that Terraform will run. What separates them is how hard they make it to accidentally hurt production, and how much duplicated code you carry to get that safety.

Pattern 1 — Terraform workspaces

You already know this one from Lesson 21: one directory, one set of .tf files, multiple named workspaces (terraform workspace new staging), each with its own state file but sharing the same backend and the same configuration. Environment differences get expressed through terraform.workspace conditionals or workspace-keyed .tfvars.

It's the simplest pattern to set up — no duplicated files, one config to maintain. But the official CLI workspaces documentation is explicit about its limits: "CLI workspaces within a working directory use the same backend, so they are not a suitable isolation mechanism" for scenarios that need separate credentials and access controls between environments. Same backend also means the same state storage, the same IAM permissions on that storage, and — if you're not careful with your prompt or CI step — a single typo'd workspace name away from running a prod-shaped plan against the wrong state.

Pattern 2 — separate directories per environment

Instead of one directory with multiple workspaces, each environment gets its own directory, its own backend configuration, and its own .tfvars file — all of them calling shared modules for the actual resources:

environments/
  dev/
    main.tf        # module "app" { source = "../../modules/app" ... }
    backend.tf      # backend "s3" { key = "dev/app.tfstate" ... }
    dev.tfvars
  staging/
    main.tf
    backend.tf
    staging.tfvars
  prod/
    main.tf
    backend.tf
    prod.tfvars
modules/
  app/
    main.tf
    variables.tf
    outputs.tf

This is more explicit and more isolated: each environment can point at a completely different backend (different S3 bucket, different IAM role, different account even), and a plan run from environments/dev physically cannot touch prod's state — there's no shared workspace name to mistype. It costs you some duplication (each directory repeats the module-calling boilerplate), but the actual resource logic still lives once, in the shared module.

This is the pattern the official docs point you toward when workspaces aren't enough. The same "When NOT to Use Workspaces" guidance recommends: "Instead of creating CLI workspaces, you can use one or more re-usable modules to represent the common elements and then represent each instance as a separate configuration that instantiates those common elements in the context of a different backend." That's exactly this pattern — shared modules, separate configurations, separate backends.

Pattern 3 — separate git branches per environment

The third pattern you'll encounter in the wild: one directory, one config, but a long-lived branch per environment (dev, staging, main/prod), where promoting a change means merging one branch into the next. It feels natural if your team already thinks in GitFlow-style branching for application code.

It's generally discouraged for Terraform specifically, and HashiCorp's own recommended-practices guide says so directly. Discussing how to structure environments, it states plainly: "we believe a model of one canonical branch works best" — meaning one branch, with environments differentiated by variables (which is pattern 1 or 2's job), not by which branch you're on. Branch-per-environment is mentioned only as a fallback for teams whose existing code isn't yet structured to support the single-branch model — a migration stepping stone, not the target design.

The reason it's discouraged is specific to infrastructure, not code style: state doesn't merge the way code does. If staging and prod branches drift apart — someone hotfixes prod directly, or a module version gets bumped on one branch but not merged to the other — git merge can't reconcile "which infrastructure state is correct" the way it reconciles text. You end up finding out about the drift during a stressful production apply, not during a code review.

Best practice: whichever pattern you pick, production should never share a workspace or a state file with dev — full stop. Blast-radius isolation matters more than staying perfectly DRY. A typo in a workspace name or a stale branch shouldn't be the only thing standing between a routine dev change and a production outage. If keeping dev and prod maximally similar (pattern 1) starts to conflict with keeping prod maximally safe, safety wins — that's exactly why HashiCorp's own guidance steers meaningfully-different environments toward separate directories and separate backends instead.

Try it — before looking below

Q1. Your dev and prod environments use Terraform workspaces sharing one backend. A teammate on the ops team says "prod state should be encrypted with a different KMS key and only our senior engineers should have write access to it." Can you achieve that with workspaces alone? Why or why not?

No, not with workspaces alone. Workspaces within one directory share a single backend, which means they share the same storage location, the same encryption configuration, and the same IAM permissions on that storage — you can't give one workspace a different KMS key or a stricter access policy than another. To get per-environment backend configuration (different key, different access controls), you need separate directories with separate backend blocks — pattern 2.

Q2. A teammate proposes a dev branch and a prod branch, promoting changes by merging dev into prod after testing. What does HashiCorp's own guidance say about this pattern, and what's the specific reason it causes problems for infrastructure (as opposed to application code)?

HashiCorp's recommended-practices guide states "we believe a model of one canonical branch works best," treating branch-per-environment as a fallback for teams migrating off it, not the target design. The specific problem for infrastructure: state doesn't merge the way source code does. If the two branches' real infrastructure drifts apart — a manual prod hotfix, a module bump applied to one branch but not the other — git merge can resolve the text conflict but can't tell you which actual infrastructure state is correct. That mismatch surfaces later, often during a prod apply, instead of during code review where it'd be cheap to catch.

Hands-on: pick the pattern for a real scenario

Scenario: your team runs a web app in dev and prod. Dev runs on a single small instance with permissive security group rules so engineers can debug freely. Prod needs to run on larger, autoscaled instances, with tightly locked-down security groups, and only two senior engineers should be able to apply changes to prod state at all — nobody on the wider team should even have read access to prod's backend.

  • Write down which of the three patterns fits this scenario, and which pattern(s) you're ruling out.
  • For the pattern you picked, sketch (in words, no code needed) what would differ between the dev and prod setups: what lives in a shared module, and what's specific to each environment's own configuration.
  • Name the one thing pattern 1 (workspaces) cannot give you here, that's a hard requirement in this scenario.

Reveal one reasonable answer (the point is the reasoning, not memorizing this exact answer)

Pattern chosen: separate directories per environment (pattern 2). Ruled out workspaces, because the access-control requirement — only two senior engineers can touch prod state, nobody else even gets read access — needs a genuinely separate backend with its own IAM policy, and workspaces share one backend by design. Ruled out branches too: the requirement here is about isolation of state and access, not about code promotion timing, so branches don't solve the actual problem and add drift risk on top.

What's shared vs specific: a shared module (e.g. modules/webapp) owns the actual resources — instance definition, security group shape, autoscaling group — parameterized by inputs like instance size and allowed CIDR ranges. environments/dev calls that module with a small instance size and open CIDR ranges, pointed at a backend anyone on the team can read. environments/prod calls the same module with a larger, autoscaled instance size and locked-down CIDR ranges, pointed at a separate backend whose IAM policy only grants the two senior engineers write access.

What workspaces can't give you: per-environment backend access control. Workspaces sharing one backend means whoever can apply to the dev workspace has the same underlying storage access as whoever applies to the prod workspace — there's no way to lock prod's state behind a stricter IAM policy while dev stays open, because it's all the same backend.

Recap
  • Three real-world patterns for managing dev/stage/prod: Terraform workspaces (Lesson 21), separate directories per environment with their own backend and .tfvars, and separate git branches per environment.
  • Workspaces are simplest but weakest on isolation — same backend, same credentials, same access controls for every environment, per HashiCorp's own docs.
  • Separate directories, each with its own backend calling shared modules, is HashiCorp's recommended alternative once environments need meaningfully different config or access controls.
  • Separate branches per environment are generally discouraged — HashiCorp's guidance favors "one canonical branch," because infrastructure state doesn't merge the way code does, and long-lived branches drift.
  • Best practice regardless of pattern: production should never share a workspace or state file with dev. Blast-radius isolation beats staying perfectly DRY.
