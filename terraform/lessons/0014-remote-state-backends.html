Remote state & backends

Lesson 13 showed you what state is and why Terraform needs it. By default, that state lives in one file — terraform.tfstate — sitting on whatever laptop happened to run terraform apply. That's fine for a solo learning folder. It breaks the moment a second person, or a second machine, gets involved.

Why local state doesn't survive contact with a team

Picture two engineers, Priya and Marcus, both working on the same infrastructure folder.

  • The file lives on one laptop. Priya runs terraform apply from her machine. The only copy of the state — the only record Terraform has of what it created and how it maps to your config — now lives in Priya's terraform.tfstate. If her laptop dies, or she just forgets to push the file somewhere, Marcus has no way to run Terraform against that infrastructure safely. He'd either have to reconstruct state by hand or risk Terraform creating duplicate resources because it doesn't know they already exist.
  • Two people apply at the same time. Even if they share the file — say, by committing it to Git — nothing stops Marcus from running terraform apply at the exact moment Priya is mid-apply. Two Terraform processes now read the same "before" state, compute two different plans, and both start making real API calls to change real infrastructure. Whoever writes their state file last silently overwrites the other's changes in the state — even though both sets of infrastructure changes actually happened. The state file no longer matches reality, and nobody gets an error telling them so.

Mental model: local state has exactly the two problems any shared mutable file has when multiple people touch it — no single source of truth (whose copy is current?), and no protection against simultaneous writes. Committing terraform.tfstate to Git does not fix either problem: Git can merge text, but it has no idea how to merge "two different sets of real cloud resources," and it does nothing to stop two applies from racing each other. This is also why state files should never go into Git at all — beyond the race condition, they routinely contain sensitive values (database passwords, private keys) in plain text.

What a backend actually is

A backend is Terraform's answer to "where does the state file live, and how does Terraform read/write it?" Every Terraform configuration has a backend — if you never configure one, you're using the default: local, which just reads and writes a file on the disk you're standing on. A remote backend moves that file to shared storage that every team member and every CI pipeline can reach, over the network, using the same credentials-based access control you already use for that storage.

Moving state off your laptop solves the "single source of truth" half of the team problem directly: everyone who runs Terraform reads and writes the same state, from the same place, through the same access controls. It does not, by itself, solve simultaneous applies — that's a separate capability called state locking, which not every backend supports the same way. Lesson 15 covers locking in depth; for now, just note that remote storage and locking are two different problems that happen to often be solved by the same backend.

The backend block

You configure a backend inside the terraform block, as a nested backend "<type>" block. The syntax is the same shape regardless of which backend you pick — a type name in quotes, then key/value arguments specific to that backend:

terraform {
  backend "<backend_type>" {
    # arguments specific to this backend type
  }
}

Whenever you add, remove, or change a backend block, you must run terraform init again — Terraform needs to reconfigure itself to talk to the new location, and it will prompt you about what to do with any existing state (migrate it to the new backend, or start fresh).

Common remote backends, conceptually

You won't set any of these up hands-on in this lesson — each one needs a real cloud account and a pre-existing storage bucket/container, which is beyond a local learning folder. The goal here is to recognize the shape of each, so the config makes sense the day you do have a cloud account wired up.

AWS — s3

Stores state as an object in an S3 bucket. State locking on this backend is handled natively by S3 itself via the use_lockfile argument (Terraform writes a lock object alongside the state file) — older guides pair the S3 backend with a separate DynamoDB table for locking, but HashiCorp's current documentation marks DynamoDB-based locking as deprecated in favor of this native approach.

terraform {
  backend "s3" {
    bucket       = "mybucket"
    key          = "path/to/my/key"
    region       = "us-east-1"
    use_lockfile = true
  }
}

Azure — azurerm

Stores state as a blob in an Azure Storage Account container.

terraform {
  backend "azurerm" {
    resource_group_name  = "StorageAccount-ResourceGroup"
    storage_account_name = "abcd1234"
    container_name       = "tfstate"
    key                  = "prod.terraform.tfstate"
  }
}

Google Cloud — gcs

Stores state as an object in a Google Cloud Storage bucket.

terraform {
  backend "gcs" {
    bucket = "tf-state-prod"
    prefix = "terraform/state"
  }
}

HCP Terraform — cloud block, not backend

HashiCorp's own managed offering (HCP Terraform, formerly Terraform Cloud) stores and locks state for you automatically as part of a "workspace." It's configured differently from the others — with a cloud block instead of a backend block, and HashiCorp's documentation is explicit that a configuration cannot have both at once:

terraform {
  cloud {
    organization = "example_corp"

    workspaces {
      name = "my-app-prod"
    }
  }
}

Everything else you've learned about remote backends still applies conceptually — state lives off your laptop, in one shared place — HCP Terraform just also runs the plan/apply itself and manages locking for you, rather than you pointing Terraform at storage you manage.

Best practice — always remote in production: production Terraform should always use a remote backend. Never local state. The failure modes above (one laptop is the only copy, two people apply at once) aren't hypothetical edge cases — they are the default behavior the moment more than one person or one CI job touches the same infrastructure. Set the backend up before the first real apply, not after the first incident.

Try it — before looking below

Q1. Your team moves from local state to an S3 backend. Does this, by itself, stop two people from running apply at the same time?

Not automatically. Moving to a remote backend gives you one shared, authoritative copy of the state — it solves the "whose copy is current" problem. Preventing two simultaneous applies is a separate capability, state locking, which depends on the backend supporting it and being configured for it (e.g. S3's use_lockfile). This is exactly what Lesson 15 covers.

Q2. What problem does remote state solve on its own, without locking?

Team collaboration and a single source of truth — everyone (and every CI pipeline) reads and writes the same state file, from shared storage, instead of state being scattered across individual laptops where no one else can find or trust it.

Q3. True or false: you can configure both a backend block and a cloud block in the same terraform block to get extra redundancy.

False. HCP Terraform's cloud block replaces a backend block entirely — a configuration cannot have both. HCP Terraform manages state storage and locking itself once you use cloud.

Recap
  • Local state fails a team in two ways: it lives on one laptop (no shared source of truth), and nothing stops two people from applying at the same time (races that silently overwrite each other's state).
  • A backend is where Terraform stores state and how it accesses it. Remote backends (s3, azurerm, gcs, and others) move state to shared storage everyone can reach; HCP Terraform uses a cloud block instead and manages storage/locking for you.
  • Remote state alone solves collaboration and single-source-of-truth. It does not automatically solve simultaneous applies — that's state locking, covered in Lesson 15.
  • Best practice: production Terraform should always use a remote backend, never local state.
