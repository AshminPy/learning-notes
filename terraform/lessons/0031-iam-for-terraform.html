Least-privilege IAM for Terraform itself

This lesson opens the Production Patterns phase of the course, and it starts with a question most teams never ask out loud: what permissions does Terraform itself have? Not the resources it creates — the identity Terraform runs as. Lesson 29 built a CI/CD pipeline that runs plan and apply automatically. Lesson 30 added policy-as-code to check the plan's output. Neither of those protects you if the credential Terraform authenticates with is over-permissioned. This lesson is about scoping that credential down.

The mistake almost everyone makes early

Here's how it usually happens. Someone sets up a Terraform CI pipeline. The first apply fails with an access-denied error — the pipeline's cloud credential is missing some permission. Rather than add the specific permission, under time pressure, someone attaches the broadest policy available: AdministratorAccess on AWS, Owner or Editor on GCP, Contributor on Azure. The errors stop. Nobody revisits it.

This "fixes" the symptom and creates a much bigger problem: the CI pipeline's credential can now create, modify, or delete anything in the account — not just the handful of resource types the actual Terraform configs manage. That credential typically lives as a secret in the CI platform (Lesson 29). If that CI system is ever compromised — a leaked secret, a malicious pull request that runs in CI, a supply-chain attack on a GitHub Action — the blast radius is the entire cloud account, not just "whatever this Terraform config touches."

Mental model: the permissions attached to Terraform's credential are not a convenience setting, they're the blast radius of every CI compromise, every leaked secret, and every mistake in a .tf file, all at once. Terraform will apply whatever a config tells it to, as far as its credential allows. Scoping that credential down is the only backstop between "a bug in a pull request" and "a bug in a pull request that can delete production."

What least privilege means for Terraform's own credentials

Least privilege for Terraform isn't abstract — it means the credential Terraform authenticates with should only be allowed to act on the specific resource types and actions the specific config it runs actually manages. A Terraform config that manages an S3 bucket and a DynamoDB table doesn't need a credential that can also touch IAM, EC2, RDS, or billing.

Compare the two AWS policies below for a config that only manages an S3 bucket:

  • What people reach for under pressure: the AWS managed policy AdministratorAccess — full access to every service, every action, every resource.
  • What least privilege actually looks like — a customer-managed policy scoped to exactly the actions that config needs, on exactly the resources it manages:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:CreateBucket",
        "s3:DeleteBucket",
        "s3:PutBucketPolicy",
        "s3:PutBucketVersioning",
        "s3:GetBucketPolicy",
        "s3:GetBucketVersioning",
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::my-app-*"
    }
  ]
}

Notice the second policy is also scoped by resource ARN, not just action — it can only touch buckets matching my-app-*, not every bucket in the account. This is more setup work than attaching AdministratorAccess, and the AWS IAM docs are honest that teams often start broad and narrow over time: "you might start with broad permissions while you explore the permissions that are required for your workload or use case," then work toward least privilege as the use case matures. The point isn't that you must hand-write a perfect policy before your first apply — it's that "broad while exploring" has to actually get narrowed down afterward, not become the permanent state of a production CI pipeline.

Prefer short-lived, federated credentials over static keys

Scoping what the credential can do is half the problem. The other half is what kind of credential it is. A long-lived static access key — the kind you generate once and paste into a CI secrets store — is a standing liability: if it leaks, it's valid until someone notices and manually revokes it, which could be days or months.

Lesson 29 already introduced the fix: OIDC. Instead of storing a static access key in CI at all, the CI job authenticates to the cloud provider using its own OIDC identity token, and the provider hands back a short-lived, automatically-expiring credential scoped to an assumed role. AWS's own IAM best practices guide states this directly for automation: "require workloads to use temporary credentials with IAM roles to access AWS," and specifically calls out that CI/CD platforms running outside the cloud can get these temporary credentials by calling the AWS STS AssumeRoleWithWebIdentity API using a JSON web token from an identity provider — which is exactly what GitHub Actions' or GitLab's OIDC token is. No static key sitting in a secrets store, nothing to rotate, and a leaked token from one job run is worthless once that run ends.

Every major provider Terraform targets supports some form of this now — AWS via AssumeRoleWithWebIdentity, GCP via Workload Identity Federation, Azure via workload identity federation for service principals. Static long-lived keys should be the exception you can justify, not the default you reach for.

Separate credentials per environment

Lesson 22 covered separating dev, staging, and prod — different workspaces, directories, or branches, each with its own state. That separation is pointless from a security standpoint if all three environments share one Terraform credential. If dev, staging, and prod all authenticate as the same role, a compromised dev credential — the environment where people experiment, run untrusted code, and are least careful — can touch prod directly.

Give each environment its own scoped credential (its own IAM role on AWS, its own service account on GCP, its own service principal on Azure), matched to what that specific environment's config manages. A dev credential that can only touch dev-tagged or dev-namespaced resources cannot become a path into production, no matter what goes wrong in the dev pipeline.

Where policy-as-code fits: Lesson 30 covered Sentinel and OPA checking a Terraform plan's output before apply — did this plan try to open a security group to the world, did it try to create an unencrypted bucket. The same policy-as-code layer can enforce IAM discipline organizationally: a Sentinel or OPA policy can reject any pull request that attaches AdministratorAccess (or an equivalent broad managed policy) to a Terraform-related role, or flag any new static access key being created for CI use. Least privilege for Terraform's credentials isn't just something one careful engineer remembers to do — policy-as-code is how an organization makes it a rule that gets enforced automatically, on every PR, regardless of who wrote it.

Try it — before looking below

Q1. A teammate says "I just gave the CI pipeline's credential AdministratorAccess so I'd never have to debug a permissions error again." What's wrong with that reasoning, in terms of blast radius?

It trades a short-term annoyance (fixing permission errors as they come up) for a permanent, much larger risk: if that CI system, its secrets store, or a malicious PR ever gets compromised, the attacker inherits full account access — not just the ability to touch the handful of resource types the actual Terraform configs manage. The credential's permissions define the blast radius of every future compromise, not just today's convenience.

Q2. Your CI pipeline's AWS credentials have full AdministratorAccess so Terraform "just works" for any config anyone writes. What's the risk, and what should change?

The risk: any compromise of the CI pipeline or its stored credential — a leaked secret, a malicious pull request, a compromised GitHub Action — gives an attacker full control of the AWS account, including services and resources no Terraform config in that pipeline even touches. What should change: replace the broad managed policy with a customer-managed policy scoped to only the resource types and actions the actual configs manage; move from a static long-lived access key to short-lived, OIDC-federated credentials (AssumeRoleWithWebIdentity) so there's no standing key to leak; and give each environment (dev/staging/prod) its own separately-scoped credential so a compromise in one can't reach the others.

Hands-on: scope a policy instead of reaching for admin

No cloud account needed for this one — it's a design exercise, and it's the exercise that matters most in real teams.

  • picture a Terraform config that manages exactly two things: an AWS DynamoDB table and the IAM role that lets a Lambda function read from it
  • on paper (or in a text file), list only the actions that config's apply and destroy would actually need to call — think about create, read, update, delete for each resource, plus whatever's needed to look up existing state during plan
  • now compare your list against what AdministratorAccess would grant. Count roughly how many AWS services your list touches versus how many AdministratorAccess covers
  • that gap — the difference between "everything" and "the six or eight actions this config actually calls" — is exactly the blast radius you'd be removing by scoping the CI credential's policy down to match

Reveal a reasonable scoped-actions list for that DynamoDB + IAM role example

Roughly: dynamodb:CreateTable, dynamodb:DeleteTable, dynamodb:DescribeTable, dynamodb:UpdateTable, dynamodb:TagResource for the table; and iam:CreateRole, iam:DeleteRole, iam:GetRole, iam:PutRolePolicy, iam:DeleteRolePolicy, iam:PassRole for the role — scoped by resource ARN to the specific table and role name pattern this config owns, not every table or role in the account. Two services, a dozen or so actions, versus every action on every service AdministratorAccess would grant.

Recap
  • Granting Terraform's CI credential admin/root access "to avoid permission errors" trades a minor annoyance for a massive blast radius if CI or its secrets are ever compromised.
  • Scope Terraform's credential to only the resource types and actions the specific config actually manages — not every service in the account.
  • Prefer short-lived, OIDC-federated credentials (Lesson 29) over static long-lived access keys wherever the provider supports it — nothing to leak, nothing to rotate.
  • Give each environment (Lesson 22) its own scoped credential, so a compromised dev credential can't reach staging or prod.
  • Policy-as-code (Lesson 30) can enforce this organizationally — rejecting overly broad IAM policies or new static keys automatically, on every PR.
