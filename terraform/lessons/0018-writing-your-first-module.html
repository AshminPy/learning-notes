Writing your first module

Lesson 17 made the case for modules — reuse, organization, a clean interface between "what a thing does" and "how many of it you want." This lesson is where you actually build one. And here's the reassurance up front: a module's own files use resource, variable, and output blocks — the exact same syntax you've been writing since Lesson 5. Nothing new to learn there. The only genuinely new thing is the module block you use to call it, plus a folder to put it in.

Mental model: a module is a function. variables.tf is its parameter list, main.tf is its body, outputs.tf is its return statement. You already wrote all three concepts in your root config — you were just writing them inline instead of packaging them into something callable more than once.

What you're building

A tiny reusable module called named-file: give it a name_prefix, and it generates a random pet name (random_pet, from Lesson 5) and writes that name into a text file (local_file, from Lessons 7–10) whose filename starts with your prefix. Both providers are free and need no cloud account, so you can run every command in this lesson without spending a cent. Then you'll call that one module twice from a root config — once for "dev," once for "prod" — proving the whole point of a module: write the logic once, reuse it with different inputs.

Step 1 — the module's folder

Inside your working directory, create a subfolder for the module. The standard convention (confirmed by HashiCorp's own module-development docs) is a modules/ directory at the root, with one subfolder per module:

your-project/
├── main.tf              # root config — calls the module
├── modules/
│   └── named-file/
│       ├── main.tf      # the module's own resources
│       ├── variables.tf # the module's inputs
│       └── outputs.tf   # the module's outputs

Make the folders now:

mkdir -p modules/named-file

Step 2 — the module's input: modules/named-file/variables.tf

Same variable block syntax from Lesson 6 — nothing module-specific about it:

variable "name_prefix" {
  description = "Prefix used in the generated file's name (e.g. \"dev\", \"prod\")"
  type        = string
}

Step 3 — the module's resources: modules/named-file/main.tf

Same resource block syntax from Lessons 5, 7, and 8. The only thing to notice is that local_file's filename now uses var.name_prefix instead of a hardcoded string — that's what makes this module reusable with different inputs:

resource "random_pet" "name" {}

resource "local_file" "pet_file" {
  filename = "${path.module}/${var.name_prefix}-pet.txt"
  content  = random_pet.name.id
}

path.module (not path.root) resolves to this module's own folder — so the file lands next to the module's .tf files, not wherever the root config happens to live. That matters once a module gets called from a different directory than where it's defined.

Step 4 — the module's output: modules/named-file/outputs.tf

Same output block syntax from Lesson 7. This is the module's public interface — the only thing the calling config gets to see:

output "file_path" {
  description = "Path to the generated pet-name file"
  value       = local_file.pet_file.filename
}

Why this matters: random_pet.name and local_file.pet_file exist only inside the module — the root config can never reference them directly, even by their full local names. The only thing that crosses the boundary is what the module explicitly outputs. This is the same "outputs are the only sanctioned way to hand something back" idea from Lesson 7, just applied at the module level instead of the resource level.

Step 5 — call the module twice from the root: main.tf

Back in your project root (not inside modules/), delete or comment out any leftover random_pet/local_file resource blocks from earlier lessons — the module owns those now. Your root main.tf needs the provider block (same as always, Lesson 4) plus two module blocks:

terraform {
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

module "dev_pet" {
  source      = "./modules/named-file"
  name_prefix = "dev"
}

module "prod_pet" {
  source      = "./modules/named-file"
  name_prefix = "prod"
}

output "dev_file_path" {
  description = "Path to the dev environment's generated file"
  value       = module.dev_pet.file_path
}

output "prod_file_path" {
  description = "Path to the prod environment's generated file"
  value       = module.prod_pet.file_path
}

Two new pieces of syntax here, both small:

  • module "dev_pet" { ... } — the label (dev_pet) is a local name you choose, exactly like a resource's local name. source is required and points at the module's folder — a relative path starting with ./ or ../ tells Terraform "this is a local module, not a registry one" (registry sources are Lesson 19's topic).
  • module.dev_pet.file_path — how you read a module's output from outside it. Same dotted syntax as reading a resource attribute (random_pet.example.id), just with module.<local name>.<output name> instead of <type>.<local name>.<attribute>.

Every argument you set inside a module block (here, just name_prefix) must match a variable the module actually declares — Terraform validates this at plan time, the same way it validates arguments against a resource's schema.

Try it — before looking below

Q1. Inside modules/named-file/main.tf, could you write output "pet_id" { value = random_pet.name.id } directly in that file and expect the root config to read it as random_pet.name.id?

You could add that output block, but the root config would never read it as random_pet.name.id — that resource is private to the module. The root config can only reach it through the module's declared output, as module.dev_pet.pet_id (or whatever you name the output). The resource's local name inside the module is invisible outside it.

Q2. You call the same module twice, as dev_pet and prod_pet. Do they share one random_pet resource, or does each call get its own?

Each call gets its own, completely separate copy of every resource inside the module. module.dev_pet and module.prod_pet are two independent instances — two separate random_pet resources, two separate local_file resources, two separate state entries. That's the entire point of calling a module more than once: it's not shared state, it's the same logic stamped out twice with different inputs.

Hands-on: build it, call it twice, inspect the plan

Build the exact structure above in a fresh (or existing) project folder:

  • create modules/named-file/variables.tf, main.tf, and outputs.tf with the content from Steps 2–4
  • create the root main.tf from Step 5, calling the module twice as dev_pet and prod_pet
  • run terraform init — Terraform needs to discover the local module as well as the two providers; watch the output mention Initializing modules... before Initializing provider plugins...
  • run terraform plan and read the resource addresses carefully. You should see four resources to add, addressed as:
    • module.dev_pet.random_pet.name
    • module.dev_pet.local_file.pet_file
    • module.prod_pet.random_pet.name
    • module.prod_pet.local_file.pet_file
  • notice the pattern: module.<call name>.<resource type>.<resource local name> — the module call name becomes a prefix on every resource address inside it. That prefix is exactly what keeps dev_pet's resources and prod_pet's resources from colliding, even though both instances declare a resource literally named random_pet.name inside the module
  • run terraform apply, type yes
  • run terraform output — you should see both dev_file_path and prod_file_path, each pointing at a different generated file (e.g. ./modules/named-file/dev-pet.txt and ./modules/named-file/prod-pet.txt)
  • open both files and confirm each contains its own independently generated pet name
  • run terraform destroy, type yes, to clean up

# modules/named-file/variables.tf
variable "name_prefix" {
  description = "Prefix used in the generated file's name (e.g. \"dev\", \"prod\")"
  type        = string

output "file_path" {
  description = "Path to the generated pet-name file"
  value       = local_file.pet_file.filename
}

# main.tf (root)
terraform {
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

module "dev_pet" {
  source      = "./modules/named-file"
  name_prefix = "dev"
}

module "prod_pet" {
  source      = "./modules/named-file"
  name_prefix = "prod"
}

output "dev_file_path" {
  value = module.dev_pet.file_path
}

output "prod_file_path" {
  value = module.prod_pet.file_path

Recap
  • A module's own files (main.tf, variables.tf, outputs.tf) use the exact same resource/variable/output syntax you already know — modules are an organizational feature, not a new language.
  • The standard layout is a modules/<name>/ subfolder with those three files; the root config calls it with a module block whose source points at that folder.
  • A module's internal resources are private — the calling config can only reach values the module explicitly exposes via output, read as module.<call name>.<output name>.
  • Calling the same module more than once creates fully independent resource instances, addressed as module.<call name>.<resource type>.<resource name> — that's how dev_pet and prod_pet coexist without colliding.
