HCP Terraform workspaces & remote execution

Lesson 14 mentioned HCP Terraform in passing — the cloud block that replaces a backend block, storing and locking state for you. This lesson opens the CI/CD & Collaboration phase of the course by going much deeper: what HCP Terraform actually is as a platform, what a "workspace" means there, and why that word colliding with Lesson 21's terraform workspace command trips up almost every beginner. It's also worth knowing this isn't a side topic — HCP Terraform is its own scored domain on the Terraform Associate exam, so the concepts here show up directly on the test, not just in real-world team setups.

What HCP Terraform is

HCP Terraform (formerly called Terraform Cloud — you'll still see both names in the wild, including in older docs and blog posts) is HashiCorp's own managed application for running Terraform. Instead of Terraform living only as a CLI binary on your laptop, HCP Terraform is a hosted service: you point your configuration at it, and it takes over storing state, running plan/apply, managing variables and credentials, and keeping a full history of every run — all through a web UI and API, not just your terminal.

Everything you learned in Lessons 13–15 about state still applies conceptually. HCP Terraform is, among other things, a remote backend — it solves the same "one shared source of truth, with locking" problem. What it adds on top is the subject of this lesson: a place to run Terraform, not just store its state.

The workspace name collision — the single most important thing in this lesson

Here's the trap. You already know the word "workspace" from Lesson 21: terraform workspace new staging creates a second, isolated state file for the same local configuration, still run entirely from your own laptop with your own credentials. HCP Terraform uses the exact same word, workspace, for something much bigger — and the two are genuinely different concepts that happen to share a name, not two views of the same thing.

Mental model — pin this down before anything else in the lesson: a CLI workspace (Lesson 21) is a state-file partition inside one working directory on your machine — same config, same backend, same credentials, just a different .tfstate. An HCP Terraform workspace is a full managed environment on HashiCorp's platform: its own VCS connection, its own variables and credentials, its own state, its own run history, its own access controls — roughly the equivalent of "one deployable unit," closer in spirit to what an entire remote-backend-plus-CI-pipeline setup looks like for one piece of infrastructure. HashiCorp's own workspaces documentation calls out this exact confusion directly, describing CLI workspaces as "a legacy feature" that are "very different from HCP Terraform workspaces," and warns that "the use of the same term for two different concepts is an unfortunate naming clash." That's not a beginner's assumption — that's HashiCorp's own docs telling you it's a real, acknowledged source of confusion.

A practical way to keep them apart: a CLI workspace changes almost nothing except which state file gets read — same folder, same person running it, same access. An HCP Terraform workspace is closer to "a whole project's home" — it holds configuration, variables (including secrets), state, and a full run history, and it's the unit that role-based access control and governance policies attach to. If you're not sure which one a sentence means, ask: "does this exist only on my laptop, or does it live on HashiCorp's platform with its own login and access controls?" CLI workspace → laptop. HCP Terraform workspace → platform.

Projects — grouping workspaces

Once you have more than a handful of HCP Terraform workspaces — one per microservice, one per environment, one per region — you need a way to organize them. That's what a project is: a grouping layer that sits above workspaces, letting you organize related workspaces together and apply scoped access control at the project level rather than managing permissions workspace-by-workspace one at a time. Think of it the way you'd think of a folder of related repos in GitHub — the project doesn't run anything itself, it's an organizational and permissions boundary around a set of workspaces that belong together.

Remote execution — plan/apply run on HCP Terraform, not your laptop

This is the other half of what makes HCP Terraform more than "just" a remote backend. When a workspace is configured for remote execution, running a plan or apply doesn't execute on your machine at all — it runs on HCP Terraform's own infrastructure (disposable virtual machines it provisions per run), using the workspace's stored configuration, variables, and credentials.

Why that matters in practice:

  • No "works on my machine." Every run — whether triggered by you, a teammate, or a pull request — executes with the exact same Terraform version, the exact same provider plugins, and the exact same environment. You stop debugging "it worked when I ran it locally but failed in CI" because there's no longer a separate "locally" — the run environment is always the same one.
  • Credentials stay off laptops. Cloud provider credentials live as variables inside the workspace on HCP Terraform, not in a shell environment variable or a config file on someone's machine. Nobody needs their own copy of the production AWS keys just to run terraform plan.
  • Every run is recorded. HCP Terraform keeps a full history — who triggered each run, what the plan showed, whether it was approved, what actually applied. That audit trail doesn't exist by default when applies happen from scattered local terminals.

VCS-driven workflow

The other major piece: a workspace can connect directly to a version control repository (GitHub, GitLab, and others). Once connected, HCP Terraform automatically triggers a plan run whenever a pull request touches that workspace's configuration — you get a plan output showing exactly what would change, attached right to the PR, before anyone reviews or merges. Push to the branch that workspace tracks (commonly after merge), and HCP Terraform can automatically kick off the corresponding apply, subject to whatever approval settings the workspace requires.

Why this matters for CI/CD: this is the mechanical foundation the rest of this phase of the course builds on. "Plan on PR, apply on merge, always the same machine, full history of who approved what" is the core loop a real Terraform CI/CD pipeline needs — Lesson 29 builds a complete pipeline, and having HCP Terraform's VCS-driven workflow as a mental model makes that pipeline much easier to follow, whether you build it with HCP Terraform itself or with a general-purpose CI tool doing the equivalent job.

Cost — is this something you can actually try?

Yes. HCP Terraform has a genuine free tier suitable for learning and small teams — HashiCorp's own documentation states that "many of its features are free for small teams, including remote state storage, remote runs, and VCS connections," with the constraint that "free organizations are limited to 500 managed resources." For a learning account, or a small real team, 500 managed resources is a lot of room — you won't hit that ceiling working through this course. Paid tiers (Essentials, Standard, Premium) exist for larger organizations that need things like Sentinel/OPA policy enforcement at scale, SSO, or higher resource ceilings, but none of that is required to follow along here.

Try it — before looking below

Q1. Priya says "I ran terraform workspace new staging on my laptop, so now I have an HCP Terraform workspace called staging." Is she right?

No. terraform workspace new staging is the CLI workspace command from Lesson 21 — it creates a second local state file for the same config, still run from her laptop with her own credentials. It has nothing to do with HCP Terraform's platform. An HCP Terraform workspace is created on HashiCorp's platform (via the UI, API, or `cloud` block config) and comes with its own VCS connection, variables, and run history — a completely different, unrelated concept that happens to share the word "workspace."

Q2. What specifically does "remote execution" mean in HCP Terraform, and name one concrete problem it solves that plain remote state storage (Lesson 14) does not.

Remote execution means the `plan`/`apply` commands themselves run on HCP Terraform's own infrastructure (disposable VMs), not on whoever's laptop triggered them. Plain remote state storage (an S3/GCS/azurerm backend) only moves *where the state file lives* — the actual Terraform process, and whatever Terraform version, plugins, and credentials happen to be on that person's machine, still runs locally. Remote execution removes that variability entirely: every run uses the same environment and the workspace's own stored credentials, which is what kills "works on my machine" and keeps cloud credentials off individual laptops.

Q3. What does a "project" group together in HCP Terraform, and why would a team want that?

A project groups related workspaces together — for example, all the workspaces for one application's dev/staging/prod environments. It exists so a team can apply access control and organization at the project level (who can see or touch this whole group of workspaces) instead of configuring permissions one workspace at a time.

Hands-on: read a real HCP Terraform workspace, no cloud account required

This lesson doesn't require signing up for anything to get the core mental model straight, but HCP Terraform does have a genuine free tier if you want to go further later. For now:

  • reread the cloud block from Lesson 14: 
    terraform {
  cloud {
    organization = "example_corp"

    workspaces {
      name = "my-app-prod"
    }
  }
}
  • point at the name = "my-app-prod" line and say out loud: "this is an HCP Terraform workspace — a managed environment on HashiCorp's platform, not a local state partition." Compare it to terraform workspace new prod from Lesson 21 and name, out loud, at least two things the HCP Terraform workspace has that the CLI one doesn't (its own VCS connection, its own stored variables/credentials, its own run history, project-level access control).
  • if you do want to look at the real thing: HCP Terraform's free signup lets you create an organization, a project, and a workspace without a credit card — connect it to a throwaway GitHub repo with a single main.tf (even just the random_pet example from earlier lessons) and open a pull request that touches it. Watch the plan appear automatically on the PR — that's the VCS-driven workflow from this lesson, happening for real.
