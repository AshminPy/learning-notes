Meta-arguments: count, for_each, depends_on

Every resource block you've written so far creates exactly one thing, in an order Terraform figures out on its own. Real infrastructure isn't that tidy — you often want five identical subnets, or one IAM policy per team, or a resource that must wait for something Terraform can't see through a reference. This lesson covers the three meta-arguments that handle those cases: count, for_each, and depends_on. "Meta-argument" just means it's not specific to any provider — you can add it to almost any resource or module block, and Terraform itself interprets it.

count — create N copies, indexed 0..N-1

count takes a whole number and creates that many instances of the resource. Inside the block, count.index gives you the current instance's position, starting at 0:

resource "aws_instance" "server" {
  count = 4
  # count.index is 0, 1, 2, 3 across the four instances
}

Each instance gets addressed with bracket notation — aws_instance.server[0], aws_instance.server[1], and so on. You'll see this same numbered pattern in terraform plan output.

Mental model: count turns one resource block into an array. count.index is the array position — nothing more. Terraform doesn't know or care what instance 2 "means"; it only knows there are 4 slots, numbered 0 to 3.

The pitfall — removing from the middle shifts everything after it

Because count.index is just a position, Terraform's state ties each instance's identity to its index, not to anything about what that instance actually is. Say you have three servers built from a list:

variable "server_names" {
  default = ["alpha", "beta", "gamma"]
}

resource "aws_instance" "server" {
  count = length(var.server_names)
  tags  = { Name = var.server_names[count.index] }
}

This creates server[0] = alpha, server[1] = beta, server[2] = gamma. Now delete "beta" from the middle of the list. The list is now ["alpha", "gamma"], so server[1] is now gamma instead of beta. Terraform doesn't see "beta was deleted" — it sees "the thing at index 1 changed from beta to gamma," and plans to destroy and recreate server[1] (and everything after it, if the list were longer). You wanted to delete one server. Terraform's plan touches every server after it in the list.

Best practice — avoid count over lists you expect to change. This isn't a bug, it's the direct consequence of indexing by position. It's fine for genuinely interchangeable copies (four identical worker nodes, where losing any one and getting a new one back is a non-event). It's a trap for named, distinct things — servers, users, buckets — where each item has an identity you care about keeping stable.

for_each — one resource per item, keyed by a stable key

for_each solves exactly this problem. It takes a map or a set of strings, and creates one instance per entry — keyed by the map's key (or the string itself, for a set) instead of a numeric position:

resource "aws_iam_user" "example" {
  for_each = toset(["Todd", "James", "Alice"])
  name     = each.key
}

Or with a map, when you need a value alongside the key:

resource "azurerm_resource_group" "rg" {
  for_each = tomap({
    a_group       = "eastus"
    another_group = "westus2"
  })
  name     = each.key
  location = each.value
}

Inside the block: each.key is the map key (or the set member itself), each.value is the map's value (for a set, it's identical to each.key). Instances are addressed by their key, not a number — aws_iam_user.example["Todd"], azurerm_resource_group.rg["a_group"].

Now replay the earlier problem with for_each instead of count: remove "beta" from a set of server names, and Terraform destroys exactly server["beta"]. Nothing else moves, because server["alpha"] and server["gamma"] were never identified by position in the first place — their keys didn't change.

Best practice, per HashiCorp's own guidance: "Use the count argument when you want to create nearly identical instances. Use for_each when some instance arguments must have distinct values that can't be directly derived from an integer index." In practice, that steers most real-world "one resource per named thing" cases toward for_each — the key-based identity is what avoids the reshuffling pitfall above. Note one restriction: the keys of a map, or every value in a set of strings, must be values Terraform can know before apply — you can't for_each over something only known after a resource is created.

Try it — before looking below

Q1. You have count = 3 building three S3 buckets from var.bucket_names[count.index], where the list is ["logs", "backups", "archive"]. You remove "backups" from the list, leaving ["logs", "archive"]. What does terraform plan propose, and why?

It proposes destroying and recreating bucket[1] (previously "backups", now "archive") — and destroying bucket[2] entirely, since the list is now shorter. Terraform tracks instances by index, not by name, so shifting positions looks like a change to the resource at that index, not a clean removal of one item.

Q2. Same scenario, but built with for_each = toset(var.bucket_names) instead of count. What happens when you remove "backups"?

Only bucket["backups"] is destroyed. bucket["logs"] and bucket["archive"] are untouched, because their keys never changed — for_each identifies instances by key, not position.

Implicit dependencies, recapped

Lesson 8 covered this without naming the contrast yet: when one resource's argument references another resource's attribute (random_pet.example.id, for instance), Terraform automatically works out the create order from that reference. No ordering keyword needed — this is an implicit dependency, and it's how Terraform builds its dependency graph the vast majority of the time.

depends_on — for the order Terraform can't see

Occasionally a resource depends on another resource's behavior, not its data — nothing you can reference in an argument. The classic example: an IAM policy that must finish propagating before an application tries to use the role it's attached to. Terraform has no attribute reference to infer that ordering from, so you state it explicitly:

resource "aws_instance" "example" {
  # ... configuration ...
  depends_on = [
    aws_iam_role_policy.example
  ]
}

depends_on takes a list of resource (or module) references. Terraform completes all actions on everything listed before it touches this resource — same ordering effect as an implicit dependency, just declared instead of inferred.

Best practice — last resort, not a habit. HashiCorp's own guidance is direct: "You should only use depends_on as a last resort because it can cause Terraform to create more conservative plans that replace more resources than necessary." Reach for it only when you've confirmed there's genuinely no attribute you can reference to create the dependency implicitly. If you find yourself adding depends_on out of habit "just to be safe," that's usually a sign the config is missing a real reference — go find it first.

Q3. You add content = "Pet: ${random_pet.example.id}" to a local_file resource. Do you also need depends_on = [random_pet.example] on that resource?

No. Referencing random_pet.example.id already creates an implicit dependency — Terraform will create random_pet.example first automatically. Adding depends_on on top would be redundant, and redundant depends_on is exactly the habit the "last resort" guidance warns against.

Hands-on: one random_pet per environment, with for_each

Same folder as previous lessons, random provider already in your required_providers block from Lesson 8. Replace your single random_pet resource with this:

resource "random_pet" "env_pet" {
  for_each = toset(["dev", "staging", "prod"])
  length   = 2
}

Add an output so you can see all three at once:

output "pet_names" {
  value = { for env, pet in random_pet.env_pet : env => pet.id }
}

Walk through it:

  • run terraform plan and read the resource addresses in the output — you should see random_pet.env_pet["dev"], random_pet.env_pet["staging"], random_pet.env_pet["prod"], each planned separately
  • run terraform apply, type yes
  • check the pet_names output — three key/value pairs, one generated pet name per environment
  • edit the for_each set to remove "staging", run terraform plan again, and confirm only random_pet.env_pet["staging"] is planned for destruction — dev and prod don't move
  • run terraform destroy, type yes, to clean up

Recap
  • count = N creates N instances, indexed 0..N-1 via count.index — good for identical, interchangeable copies, risky for named lists that change, because removing a middle item shifts every index after it and Terraform recreates those instances.
  • for_each creates one instance per entry in a map or set, keyed by each.key/each.value instead of a position — generally preferred over count whenever instances have distinct identities, since removing one item only touches that one key.
  • Implicit dependencies (referencing another resource's attribute) are how Terraform orders things almost all the time — no keyword needed.
  • depends_on declares an ordering Terraform can't infer from any reference. Use it only as a last resort — it's official HashiCorp guidance, not just a style preference — since it can make plans more conservative than necessary.
