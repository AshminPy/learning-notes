Lesson 35 walked the exam's 8 official domains one at a time. This lesson does something different on purpose: it mixes them up. The real exam (004, Lesson 1) doesn't group questions by domain and tell you which one you're being tested on — a question about a forced replacement can sit right next to one about module versioning, with no label telling you which phase of this course it came from. That's the actual skill worth practicing: recognizing which concept a scenario is testing before you can pick the right answer.

How to use this lesson: every scenario below is multiple choice, matching the real exam's format. Every correct answer is something already taught earlier in this course — nothing new appears here. Read the scenario, commit to an answer before revealing, then check the one-line "why" and follow the link back if it doesn't click immediately. Getting one wrong is the whole point of practicing — it tells you exactly which lesson to reread before Lesson 37's final review.

Scenario 1 — meta-arguments

Your config builds three S3 buckets with count = length(var.bucket_names), naming each one from var.bucket_names[count.index], where the list is ["logs", "backups", "archive"]. You need to delete the "backups" bucket without touching logs or archive at all. What should you have used instead of count to make that possible?

  1. depends_on, so Terraform tracks deletion order explicitly
  2. for_each over a set of the bucket names, so each instance is keyed by name instead of position
  3. lifecycle { prevent_destroy = true } on the resource block
  4. A separate resource block for each bucket, written out by hand
Correct: B. count ties each instance's identity to its numeric position, so removing an item from the middle of the list shifts every index after it — Terraform sees that as a change, not a clean removal, and plans to destroy/recreate the shifted instances too. for_each keys each instance by name, so deleting "backups" only touches bucket["backups"]. See Lesson 11 — Meta-arguments.

Scenario 2 — lifecycle rules

An aws_instance sits behind a load balancer, serving live traffic. You need to change an argument that forces a replace. Left at Terraform's default behavior, what happens during that replace — and which lifecycle setting fixes it?

  1. Terraform updates the instance in place; no fix needed
  2. Terraform destroys the old instance, then creates the new one — a gap with nothing serving traffic. Add lifecycle { create_before_destroy = true } to flip the order
  3. Terraform refuses to plan the change at all unless ignore_changes is set
  4. Terraform creates the new instance and leaves the old one running forever unless you manually destroy it
Correct: B. The default replace order is destroy-then-create (-/+ in plan output) — there's a real moment where the resource doesn't exist. create_before_destroy = true flips it to create-then-destroy (+/-), so the new instance exists before the old one is torn down — the exact reason this setting is a named exam objective. See Lesson 12 — Lifecycle rules & custom conditions.

Scenario 3 — state surgery

During a refactor you rename a resource in your config — aws_instance.worker becomes aws_instance.app_server — with no change to the real infrastructure. You want the next terraform plan to show no destroy and no create, just the address updated in state, and you want that intent committed to git and reviewed in your pull request like any other config change. What do you add?

  1. Run terraform state mv aws_instance.worker aws_instance.app_server from your terminal only
  2. A moved block in your .tf config: moved { from = aws_instance.worker to = aws_instance.app_server }
  3. lifecycle { ignore_changes = [all] } on the renamed resource
  4. Nothing — Terraform detects renames automatically by comparing attribute values
Correct: B. Without either fix, Terraform's three-way comparison sees a new address with no state entry (create) and an old address no longer in config (destroy) — a real destroy-and-recreate for what was just a rename. terraform state mv (option A) fixes it too, but only from one person's terminal, invisible to teammates until someone tells them. A moved block lives in version control, shows up in the PR diff, and gets reviewed — the safer default for refactors that go through normal review. See Lesson 16 — State surgery.

Scenario 4 — environments

Ops tells you: prod's state must sit behind a different encryption key and a stricter IAM policy than dev's — only two senior engineers should even have read access to prod's backend. Dev and prod currently share one directory of .tf files, switched between with terraform workspace select. Does that setup satisfy the requirement, and if not, what pattern does?

  1. Yes — just create a prod workspace with terraform workspace new prod and the access control follows automatically
  2. No — workspaces in one directory share a single backend, so they share the same storage, encryption, and IAM permissions. Use separate directories per environment, each with its own backend block, calling shared modules
  3. No — switch to a separate git branch per environment instead; branches give each environment its own backend automatically
  4. Yes, as long as prevent_destroy = true is set on prod's resources
Correct: B. Workspaces sharing one directory share one backend by design — same storage location, same encryption config, same IAM permissions for every workspace. There's no way to give one workspace a stricter policy than another. HashiCorp's own guidance for this exact case is separate directories, each with its own backend, calling shared modules for the actual resource logic — pattern 2. Branches (option C) don't solve access control either, and they carry their own drift risk since infrastructure state doesn't merge like code. See Lesson 21 — Workspaces and Lesson 22 — Managing dev/stage/prod environments.

Scenario 5 — reading a plan

You bump random_pet.sidecar's length from 2 to 3, expecting a small in-place tweak. terraform plan instead shows:

  # random_pet.sidecar must be replaced
-/+ resource "random_pet" "sidecar" {
      ~ length = 2 -> 3 # forces replacement
    }

What does this actually mean is about to happen, and how could you have known which argument caused it before reading the detail line?

  1. Nothing unusual — -/+ means the same thing as ~, an in-place update
  2. The resource will be destroyed, then a new one created — not updated in place. The # forces replacement comment next to length is Terraform telling you exactly which argument triggered it
  3. Terraform made a mistake; length should never force a replacement
  4. You can only know this by checking the summary line at the bottom of the plan
Correct: B. -/+ means destroy-then-create, not an in-place update — some arguments (like length on random_pet) can't be changed on the live object, so Terraform has no choice but to replace it. The # forces replacement comment appears right next to the specific argument responsible. The bottom summary line (option D) only gives you counts — "1 to change" vs "1 to destroy" — never which resource or which argument, which is exactly why skimming it is the costliest beginner habit in plan review. See Lesson 12 and Lesson 26 — Plan review discipline.

Scenario 6 — sensitive data

A teammate marks a database password variable sensitive = true and says "great, now it's encrypted and safe." terraform plan does show (sensitive value) instead of the real string. Is your teammate right that the value is now protected?

  1. Yes — sensitive = true encrypts the value everywhere it's stored
  2. No — sensitive only hides the value from CLI output (plan, apply, output). It's still written into terraform.tfstate in plaintext, and terraform output -raw prints it directly
  3. No — sensitive does nothing at all; it's purely cosmetic and has no effect on any command's output
  4. Yes, but only if the backend is remote (Lesson 14)
Correct: B. sensitive = true is a CLI display filter, not encryption — HashiCorp's own docs are explicit that Terraform "still stores the values of sensitive variables in your state." The real protection is never committing state (Lesson 13) plus an encrypted remote backend (Lesson 14); sensitive only stops the value from flashing across a terminal or CI log by accident. See Lesson 24 — Handling sensitive data.

Scenario 7 — module versioning

Your root config calls a registry module: source = "terraform-aws-modules/vpc/aws", with no version argument at all. Six months later, a teammate's fresh terraform init pulls a newer major version than the one you originally tested, and part of your config breaks. What single change would have prevented this, while still allowing safe patch/minor updates through automatically?

  1. Add version = "~> 6.0" — a pessimistic constraint that allows patch/minor bumps but blocks a jump to 7.0.0
  2. Add lifecycle { ignore_changes = [all] } to the module block
  3. Switch the module source to a local path instead of the registry
  4. Nothing — registry modules always resolve to the version you first applied
Correct: A. An unpinned registry module source resolves to "whatever's latest right now" at every fresh init — the same failure mode as an unpinned provider version. A pessimistic constraint like ~> 6.0 lets 6.1, 6.10, and so on in automatically, but blocks 7.0.0, forcing a deliberate, reviewed bump instead of a silent one. See Lesson 19 — Module sources & versioning.

Scenario 8 — CI/CD plan review

Your team's pipeline runs terraform plan, posts it as a pull-request comment for a human to review, then — after approval — runs a bare terraform apply (no saved plan file) in a separate pipeline step. What's the risk in that setup, and how do you close it?

  1. There's no risk — apply always re-executes exactly the plan a human already approved
  2. Between the reviewed plan and the later apply, state could change (a teammate's apply, drift). A bare apply silently recomputes a fresh plan against current state, which may differ from what was reviewed — close the gap with terraform plan -out=tfplan in the plan step and terraform apply tfplan in the apply step
  3. Add prevent_destroy = true to every resource so nothing can change unexpectedly
  4. Skip the human review step entirely and trust terraform plan's summary count
Correct: B. Per HashiCorp's own docs, running apply without a saved plan file "automatically generates a new plan and prompts for you to approve it" — meaning what actually executes was never guaranteed to be the exact thing a human reviewed. Saving the plan with -out and applying that same file makes the executed plan byte-for-byte identical to the reviewed one, which is exactly how real Terraform CI/CD pipelines are built. See Lesson 26 — Plan review discipline.
