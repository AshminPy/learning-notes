Why modules? DRY infrastructure

In Lesson 16 you did surgery on state — moving and importing resources without touching real infrastructure. That was a "fix the map when it stops matching the territory" skill. This lesson is different: it's about not having to redraw the same map three times in the first place. You already know resources, variables, and outputs (Lessons 6–8). Modules don't introduce a new concept — they're about organizing the blocks you already know so you can reuse them instead of copy-pasting.

What a module actually is

A module is a reusable, self-contained group of .tf files — resources, variables, outputs — bundled together so you can call the whole group as a single unit. Here's the twist that trips people up at first: every Terraform configuration you've written so far has already been a module. The official HashiCorp docs call it the root module — the collection of .tf files in the directory where you run terraform apply. Every other module you write or download is a child module, called from the root (or from another module).

Mental model: think of a module like a function in a programming language. A function takes inputs (parameters), does some work internally, and returns outputs (a return value) — and you can call it as many times as you want without rewriting its body. A Terraform module takes inputs (variables), creates resources internally, and exposes outputs — and you can call it from as many places as you want without rewriting the resource blocks inside it.

Why modules matter — DRY infrastructure

Imagine your "standard web server setup" is five resource blocks: a security group, an EC2 instance, an EBS volume, an Elastic IP, and a DNS record. Without modules, if you need that same setup for dev, staging, and prod, you'd copy-paste those five blocks into three separate configs, changing a few variable values each time (instance size, environment tag, subnet).

That's a maintenance trap. Find a bug in the security group rule, or need to add a new tag everyone requires? Now you're hunting down and fixing the same change in three (or ten, or fifty) places, and it's only a matter of time before one copy drifts out of sync with the others. This is the same "Don't Repeat Yourself" (DRY) principle you'd apply in any programming language — write the logic once, reuse it everywhere, fix it in exactly one place when it needs fixing.

A module fixes this: write the five-resource "standard web server setup" once, as a module. Then call it three times — once per environment — passing in only what differs (instance size, environment name, subnet ID). The resource logic lives in exactly one place.

The anatomy of a typical module folder

There's no required file layout enforced by Terraform — a module is just "a directory containing .tf files." But the community convention, and the one you should default to, mirrors exactly what you already learned in Lessons 6–8:

  • main.tf — the resource blocks, the actual infrastructure logic
  • variables.tf — the module's input variables, i.e. what the caller is allowed to configure
  • outputs.tf — the module's output values, i.e. what the caller can read back out

Notice: this is not new syntax. It's the same resource, variable, and output blocks you've been writing all along, just grouped into their own folder so they can be called as a unit instead of pasted inline.

Calling a module from your root config

To use a module, you write a module block in your root configuration (or in another module). Per the official Terraform docs, the basic shape is:

module "<LABEL>" {
  source = "<location-of-module-files>"
}

"<LABEL>" is a local name you choose for this call to the module — it's how you'll refer to it elsewhere in your config. source tells Terraform where to find the module's files: a local path like "./modules/web-server", a Git repo, or the public Terraform Registry.

You pass values into the module the same way you'd set variables anywhere else — as extra arguments inside the block, one per input variable the module declares:

module "web_dev" {
  source        = "./modules/web-server"
  environment   = "dev"
  instance_size = "t3.micro"
}

module "web_prod" {
  source        = "./modules/web-server"
  environment   = "prod"
  instance_size = "t3.large"
}

Same module, called twice, only the inputs differ — exactly the copy-paste problem solved. To read a value back out of a module (something it exposed via its outputs.tf), you use module.<LABEL>.<output name>:

output "prod_server_ip" {
  value = module.web_prod.public_ip
}

Best practice — don't over-modularize: a module only pays for itself when you actually reuse it, or when it meaningfully hides complexity behind a clean interface. Wrapping a single resource block in a module you call exactly once, "just in case," usually adds a layer of indirection with no real benefit — now anyone reading your config has to jump into another folder to see what a single aws_instance actually does. Lesson 20 covers this in more depth ("when NOT to modularize") — for now, just keep the instinct: reach for a module when you're about to repeat yourself, not by default for every resource.

Try it — before looking below

Q1. You have the exact same 3 resource blocks in your dev, staging, and prod configs — only the variable values differ between them (instance size, environment name, and so on). What should you do?

Pull those 3 resources out into a module (e.g. main.tf + variables.tf + outputs.tf in their own folder). Then call that module three times — once per environment — with a module block for each, passing in only the values that differ (environment, instance size, subnet, etc.) as inputs. The resource logic lives in one place instead of being copy-pasted three times, so a fix or an added tag only needs to happen once.

Q2. True or false: your root configuration — the .tf files where you normally run terraform apply — is technically already a module.

True. HashiCorp calls it the "root module." Every configuration you've written since Lesson 1 has been a module — you just weren't calling any child modules from inside it yet.

Hands-on: spot the duplication

You don't need to write a module yet (that's Lesson 18) — this exercise is just about recognizing the smell.

  • open any config folder from earlier lessons that has more than one resource block
  • ask yourself: if I needed this exact same group of resources again, in a different environment, would I copy-paste these blocks into a new folder and hand-edit a few values?
  • if yes — that's the exact situation a module is built for. Note which values would need to change between copies (those become your module's input variables) and which values you'd want to read back out (those become your module's outputs)
  • keep that list — you'll turn it into a real module folder in Lesson 18

Recap
  • A module is a reusable, self-contained group of Terraform resources — your root config (where you run apply) is technically already a module, called the "root module."
  • Modules exist to keep infrastructure DRY: write a setup once, reuse it across environments instead of copy-pasting resource blocks.
  • A typical module folder is just main.tf, variables.tf, outputs.tf — the same building blocks from Lessons 6–8, organized as a reusable unit.
  • You call a module with module "name" { source = "./path" ... }, pass values in as arguments, and read values out with module.name.output.
  • Don't over-modularize — a module used only once with no reuse benefit usually just adds indirection (more on this in Lesson 20).
