Module sources & versioning

In Lesson 18 every module you called used source = "./path" — a folder sitting right next to your root config. That's the simplest case, but it's only one of several source types Terraform understands. This lesson covers the other two you'll use constantly in real work: the Terraform Registry and git repositories — plus the versioning discipline that keeps either of them from quietly breaking your infrastructure.

Local paths — a quick recap

A local path source always starts with ./ or ../. Terraform treats it as a folder on disk, copies nothing, and just reads the .tf files there directly.

module "servers" {
  source = "./modules/app-cluster"
}

Local paths are great for organizing your own repo into reusable pieces. They're not great for sharing a module across teams or projects — there's no versioning, no registry listing, nothing but a relative path that only makes sense inside this one repo.

The Terraform Registry

registry.terraform.io is the same registry you met in Lesson 4 for providers — it hosts modules too. Anyone can publish a module there; some are maintained by HashiCorp partners and verified, most are community-published. A registry module's source is written as a three-part address: namespace/name/provider.

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "6.0.1"
}

terraform-aws-modules is the namespace (the publisher), vpc is the module name, and aws is the target provider it's written for. No https://, no .git — the registry resolves that short address to the actual source behind the scenes. This is the same mental shift as Lesson 4's provider source = "hashicorp/aws": a short address that a registry resolves for you, instead of a raw URL you have to know.

Git repositories

Not every module lives on the public registry — private company modules, or modules that just haven't been published, are commonly pulled straight from a git repo. The source string is prefixed with git:: followed by the repo URL:

module "vpc" {
  source = "git::https://example.com/vpc.git?ref=v1.2.0"
}

The ?ref= query parameter is how you pin which commit gets pulled. Per the official docs, ref accepts "any value supported by the git checkout command" — a tag, a branch name, or a full commit SHA:

module "storage" {
  source = "git::https://example.com/storage.git?ref=51d462976d84fdea54b47d80dcabbf680badcdb8"
}

A tag like v1.2.0 is the most common choice — readable, and it assumes the repo owner doesn't move tags around. A commit SHA is the strongest possible pin: that exact content, guaranteed, forever. A branch name (?ref=main) is the weakest — the branch tip moves every time someone pushes, so you're back to "whatever is there right now."

Why version pinning matters for modules — same problem as Lesson 4, one level up

Lesson 4 covered this for providers: an unpinned version in required_providers lets Terraform silently install whatever is newest at init time, and that can change on a teammate's machine or in CI with no warning. Modules have the exact same failure mode, and it's arguably worse, because a module isn't one plugin — it's a whole bundle of resources, variables, and defaults that someone else controls.

Mental model: a module source without a version pin is a promise that can be broken without telling you. The registry address terraform-aws-modules/vpc/aws with no version argument doesn't point at fixed code — it points at "whatever the latest published version is right now." The module's maintainer can publish a new major version tomorrow that renames a variable, changes a default, or removes a resource. Your config didn't change. Your terraform init output did.

The version argument and constraint operators

version is only valid for registry modules (git and local sources use ref and the path itself instead). It accepts the same constraint operators you already learned for providers in Lesson 4:

OperatorExampleMeaning
= (or nothing)version = "6.0.1"Exactly this version — cannot combine with other conditions
!=!= 6.0.0Excludes a specific version
>= / <=>= 6.0.0This version or newer / older, no other bound
> / << 7.0.0Strictly newer / older than this version
~>~> 6.0.1Pessimistic constraint — only the rightmost segment can increment: allows 6.0.5, blocks 6.1.0
~>~> 6.0Allows 6.1, 6.10, blocks 7.0

Same recommendation as Lesson 4: reach for ~> by default. It lets patch or minor fixes in without a manual bump, but blocks the kind of major-version jump that's likely to break your config outright.

Best practice — vet third-party registry modules before you use them: anyone can publish to the Terraform Registry, "verified" or not. Before pulling a community module into production, check: maintenance activity (when was the last release — is this abandoned?), open issues (are there long-standing unresolved bugs, especially security ones?), and download counts / adoption (a module with a few dozen downloads and no other signal is a bigger unknown than one used by thousands of configs). Read the source before you trust it with real infrastructure — a module can create IAM policies, security groups, or storage buckets just as easily as your own code can, and you're the one who ends up owning whatever it deploys.

Try it — before looking below

Q1. Your root config calls a registry module with no version constraint. Six months later, terraform init pulls a different version than what you tested. What went wrong, and how do you prevent it?

With no version argument, the source address doesn't point at fixed code — it resolves to whatever the latest published version is at the moment init runs. In six months the maintainer may have published new minor or major releases, so a fresh init (a new machine, a CI run, a teammate's laptop) can silently pull a newer version than the one you originally tested against, potentially with breaking changes. Prevent it the same way you pin providers (Lesson 4): add a version constraint, ideally a pessimistic one like ~> 6.0, so you get patch/minor fixes automatically but a major bump requires you to deliberately raise the constraint.

Q2. You need a private, unpublished module from your company's git server, pinned to an exact, unchangeable point in history. Which source syntax and which query parameter do you use, and what value gives you the strongest possible guarantee?

source = "git::https://your-server/repo.git?ref=<value>". The ref parameter accepts anything git checkout accepts — branch, tag, or commit SHA. A branch name is the weakest guarantee (it moves on every push); a tag is stronger but can technically be moved by the repo owner; a full commit SHA is the strongest — that exact content, permanently, since a commit hash can't be reassigned to different content.

Hands-on: point your Lesson 18 module at a version-pinned source

Reuse the root config from Lesson 18 (the one that called your local ./modules/app-cluster module). Add a second module block that pulls a small, real, free registry module — no cloud account needed to just read its inputs:

module "example_vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.0"

  name = "learning-vpc"
  cidr = "10.0.0.0/16"
}
  • run terraform init and read the output — Terraform reports the exact version it resolved and downloaded into .terraform/modules/
  • open .terraform.lock.hcl if present, and separately check .terraform/modules/modules.json — this is where Terraform records precisely which version of each module it pulled, the module equivalent of the provider lock file from Lesson 4
  • now delete the version line entirely and run terraform init -upgrade — notice Terraform is free to jump to whatever the newest published version is, with no constraint stopping it
  • put the version = "~> 6.0" line back before doing anything else with this config

You don't need to apply this — the point is watching init resolve a version, and seeing exactly where that decision gets recorded.

Recap
  • Module sources beyond local paths: the Terraform Registry (namespace/name/provider, with a version argument) and git repos (source = "git::https://..." with ?ref= for a tag/branch/commit).
  • An unpinned module source resolves to "whatever's latest right now" — it can change under you exactly like an unpinned provider (Lesson 4).
  • Use version constraint operators (=, !=, >=, <=, ~>) on registry modules; use ref (ideally a commit SHA) on git modules.
  • Before trusting a third-party registry module, check maintenance activity, open issues, and download counts — don't blindly deploy someone else's IAM policies and resources.
