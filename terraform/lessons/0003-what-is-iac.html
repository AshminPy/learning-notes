What is Infrastructure as Code?

Before you write a single line of Terraform, you need the mental model underneath it. This lesson has no hands-on labs — it's the concept that every later lesson assumes you already understand. Get this right and the rest of the course clicks into place. Get it wrong and Terraform will keep feeling confusing no matter how many commands you memorize.

Infrastructure as Code, defined

Infrastructure as Code (IaC) means you manage your servers, networks, databases, and other infrastructure by writing and versioning configuration files — not by clicking buttons in a cloud console, and not by running one-off scripts by hand.

HashiCorp describes Terraform itself as "an infrastructure as code tool that lets you build, change, and version cloud and on-prem resources safely and efficiently," using "human-readable configuration files that you can version, reuse, and share."

Simple example: instead of logging into the AWS console and clicking "Launch Instance" five times, you write one file that says "I want 5 servers of this type," save that file in Git, and run a tool that creates them. Need a 6th next month? Change one number in the file, run the tool again.

The single most important mental model: declarative vs imperative

This is the idea the whole course is built on, so slow down here.

  • Imperative — you write the exact steps to take, in order. A shell script is imperative: "create a server, then attach a disk, then open port 443, then install nginx." You are telling the computer how to get there, step by step. If a step is already done, you have to write logic to check for that yourself.
  • Declarative — you describe the end state you want, and the tool figures out the steps to get there. Terraform is declarative. HashiCorp's own docs put it plainly: "Terraform configuration files are declarative, meaning that they describe the end state of your infrastructure." You write "I want 5 servers, this disk, this open port" — and Terraform compares that to what currently exists, then works out what to create, change, or destroy to match.

Mental model: imperative is a recipe ("do this, then this, then this"). Declarative is an order form ("this is what I want the finished kitchen to look like"). The recipe breaks if you run it twice or start from a different kitchen. The order form doesn't care where you're starting from — it just compares "what exists" to "what's on the form" and closes the gap.

Why this matters in practice: with an imperative script, re-running it can create duplicates or error out on a step that already ran. With Terraform, re-running it is safe — if the real infrastructure already matches your config, Terraform sees no gap and does nothing. This property is called idempotency, and it's only possible because Terraform is declarative.

Why teams adopt IaC

BenefitWhat it means
RepeatabilityRun the same config twice, get the same result — no "it worked when I clicked it last time" drift.
Code review for infraInfrastructure changes go through a pull request like application code — someone else reviews before it's applied.
Disaster recoveryIf a whole environment is deleted or corrupted, you rebuild it from the config files instead of remembering every manual click that set it up originally.
CollaborationThe config file is the shared source of truth for what infrastructure should exist — not tribal knowledge in one engineer's head.

Where Terraform fits among other tools

vs. configuration management tools (Ansible, Chef, Puppet): these solve a different problem — configuring software on a machine that already exists (installing packages, editing config files, starting services). HashiCorp's own comparison is direct: "Configuration management tools install and manage software on a machine that already exists. Terraform is not a configuration management tool." Terraform's job is provisioning — creating the server, network, and disk in the first place. In short: Terraform builds the kitchen, Ansible stocks the fridge. The two are commonly used together, not as competitors. (This site has a separate Ansible course if you want to go deep on that side.)

vs. cloud-native tools (AWS CloudFormation, Azure ARM templates): these are declarative too, but each is locked to one cloud provider. Terraform's comparison page notes it "can be used to orchestrate an AWS and OpenStack cluster simultaneously, while enabling 3rd-party providers like Cloudflare and DNSimple," and that it is "both cloud-agnostic and enabling multiple providers and services to be combined and composed" — giving you "a single unified syntax, instead of requiring operators to use independent and non-interoperable tools for each platform and service." If your infrastructure spans AWS, GCP, Cloudflare DNS, and a SaaS API, Terraform can describe all of it in one place; CloudFormation can only describe the AWS part.

Try it — before looking below

Q1. You write a bash script: "SSH into the server, run apt install nginx, then edit /etc/nginx/nginx.conf line by line." Is this declarative or imperative?

Imperative — it's a list of exact steps in order. Nothing describes the end state; it just says what to do.

Q2. You write a Terraform file that says instance_count = 5. Terraform checks what exists, sees only 3 servers, and creates 2 more to match. Declarative or imperative?

Declarative — you stated the end state (5 servers) and Terraform figured out the steps needed to get there from whatever the current state was.

Q3. A script that logs into an already-running server and installs a security patch — is this a job for Terraform or a configuration management tool like Ansible?

Configuration management (Ansible) — the server already exists; this is about changing software on it, not provisioning new infrastructure.

Q4. A task that creates a new VPC, a subnet, and a load balancer in AWS — Terraform or a configuration management tool?

Terraform — this is provisioning brand-new infrastructure resources, which is exactly what Terraform is built for.

Recap
  • Infrastructure as Code means managing infrastructure through versioned config files, not manual clicks or one-off scripts.
  • Declarative (describe the end state, Terraform figures out how) vs imperative (a script of exact steps) — this is the core mental model for the whole course.
  • Being declarative is why Terraform runs are idempotent: re-running against a matching state does nothing.
  • IaC benefits: repeatability, code review for infra, disaster recovery, collaboration.
  • Terraform provisions infrastructure; tools like Ansible configure what's already running. Terraform is provider-agnostic; CloudFormation/ARM are locked to one cloud.
If declarative vs imperative still feels fuzzy, that's normal — it clicks once you write your first config in Lesson 4 and watch Terraform figure out the steps on its own. Come back and reread this lesson after that if you need to.
