Providers & the terraform block

Terraform's core engine knows nothing about AWS, Azure, GCP, or anything else. It only knows how to read HCL, build a dependency graph, and talk to plugins. Those plugins are called providers — this lesson is about what they are, and the two blocks you write to bring one into your config.

What a provider actually is

Simple example: think of Terraform core as a translator that only speaks one language — HCL. A provider is a dictionary for one specific system. The aws provider translates your HCL into AWS API calls. The random provider translates HCL into "generate a random value locally." Without a provider, Terraform has nothing to talk to.

Each provider is a separate downloadable plugin, published to the Terraform Registry by HashiCorp, a cloud vendor, or the community. Common ones: hashicorp/aws, hashicorp/azurerm, hashicorp/google. There are also small, credential-free providers like hashicorp/random and hashicorp/local — useful for learning Terraform's mechanics without needing a cloud account or spending any money. That's what you'll use in this lesson.

The terraform block

Every root module should start with a terraform block. It configures Terraform itself — not your infrastructure. Two settings you'll use constantly: required_version (which Terraform CLI versions are allowed to run this config) and required_providers (which provider plugins this config needs, and which versions).

terraform {
  required_version = ">= 1.5.0"

  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.0"
    }
  }
}

Inside required_providers, each entry has a local name (here, random — the name you'll use elsewhere in your config), a source (the provider's global address, usually namespace/type, e.g. hashicorp/aws), and a version constraint.

The provider block

The terraform block only declares that you need a provider. The provider block configures how to use it — region, credentials, project ID, whatever that specific system needs.

provider "aws" {
  region = "us-east-1"
}

You don't need an AWS account to understand this — just the shape. Every cloud provider block typically needs a region or endpoint, and credentials (usually picked up from environment variables or a config file, not hardcoded in the block — never put a secret key directly in HCL). The random provider needs neither, which is why it's the perfect first example:

provider "random" {}

An empty provider block is valid. It just means "use this provider with no extra configuration."

Version constraint operators

Version constraints stop Terraform from silently grabbing a provider update that changes behavior underneath you. Here are the operators you'll see:

OperatorExampleMeaning
== 3.6.0Exactly this version (rarely used — too rigid)
>=>= 3.0This version or newer, no upper bound
<=<= 3.9.0This version or older
~>~> 3.5Allow the rightmost segment to increase — here, 3.5.x but not 3.6
~>~> 3.5.0Allow patch updates only — 3.5.x, same as above but explicit

Best-practice tip: always pin a version constraint in required_providers. If you leave it out, Terraform installs whatever the latest version is at the time — and that can silently change on a teammate's machine or in CI, upgrading a provider and breaking your config with no warning. ~> ("pessimistic constraint") is the common default: it lets you get bug fixes but blocks breaking major/minor changes.

Try it — before looking below

Q1. What's the difference between the terraform block and a provider block?

The terraform block declares which providers you need and what versions are acceptable. The provider block configures how to use one of them (region, credentials, etc.).

Q2. You write version = "~> 2.1" for a provider. The registry has versions 2.1.4, 2.2.0, and 3.0.0 available. Which one does Terraform install?

2.2.0. ~> 2.1 allows the last segment to increase, so any 2.x ≥ 2.1 is fine, but 3.0.0 is a major-version bump and is blocked.

Now write your own

Create a new folder for this lesson, e.g. lesson-04/, and inside it a file called main.tf containing:

  • a terraform block requiring the hashicorp/random provider, version ~> 3.0
  • an empty provider "random" {} block

Then open a terminal in that folder and run:

terraform init

Watch the output. Terraform will report that it's finding and installing the hashicorp/random provider, then confirm it initialized successfully. It downloads the plugin binary into a hidden .terraform folder and writes a .terraform.lock.hcl file that records the exact version it picked — that lock file is what keeps everyone on your team using the same provider version, not just "something matching ~> 3.0."

Recap
  • A provider is a plugin that lets Terraform talk to one specific system (AWS, Azure, GCP, random, local, ...).
  • The terraform block's required_providers declares which providers and versions you need — the provider block configures how to use one.
  • Always pin versions (e.g. ~> 3.0). Unpinned providers can silently upgrade and break your config.
  • terraform init downloads the providers you declared and locks the exact version in .terraform.lock.hcl.
