Data sources

Every block you've written since Lesson 5 has been a resource — something Terraform creates, tracks in state, and will change or destroy on your behalf. But real infrastructure is rarely one clean config that owns everything. A networking team already created the VPC. A security team already created the AMI. Another Terraform config, run by someone else entirely, already created the S3 bucket you need to read from. You need to use that infrastructure without pretending you own it. That's what a data source is for.

Mental model: resource = Terraform owns this — it will create it, and it will change or destroy it if your config changes. data = Terraform only reads this — it looks the value up fresh on every plan, and will never create, change, or destroy the real thing behind it, no matter what you do to the data block. Deleting a data block from your config never deletes anything in the real world; deleting a resource block schedules the real thing for destruction. That single distinction is the entire lesson.

The data block

Same shape as a resource block, one keyword different:

data "<TYPE>" "<LOCAL_NAME>" {
  # arguments that identify *which* existing thing to read
}

Side by side, so the difference is visible:

# resource — Terraform will CREATE this
resource "aws_instance" "web" {
  ami           = "ami-123456"
  instance_type = "t3.micro"
}

# data — Terraform only READS this, an AMI that already exists
data "aws_ami" "web" {
  most_recent = true
  owners      = ["099720109477"]
}

To use a value from a data source elsewhere in your config, reference it as data.<TYPE>.<LOCAL_NAME>.<ATTRIBUTE> — note the extra data. prefix that resource references don't have (you've been writing random_pet.example.id, not resource.random_pet.example.id, since Lesson 7).

A runnable example — data "local_file"

To keep this course at zero cost and no cloud account, we'll read a file that lives on your own disk using the hashicorp/local provider's local_file data source. It needs no credentials and touches nothing outside your project folder.

First, create a plain text file next to your main.tf — something that already exists, the way a data source expects:

$ echo "hello from outside terraform" > notes.txt

Add the local provider to your required_providers block from Lesson 4, alongside random:

terraform {
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

Then add the data block and an output to prove Terraform actually read the file:

data "local_file" "notes" {
  filename = "${path.module}/notes.txt"
}

output "notes_content" {
  description = "Contents of notes.txt, read by Terraform, not written by it"
  value       = data.local_file.notes.content
}

filename is the one required argument. path.module is a built-in reference to the folder holding the current .tf file — you'll meet the full family of path.* references properly in a later lesson; for now read it as "this folder." The data source exposes several read-only attributes: content (the file's text), content_base64, and several checksum attributes (content_md5, content_sha1, content_sha256, and their base64 forms) — useful for detecting if a file changed.

Step through it

Run the same workflow you already know from Lesson 5, with one addition — because you added a new provider, init is required again:

$ terraform init

Initializing provider plugins...
- Finding hashicorp/local versions matching "~> 2.5"...
- Installing hashicorp/local v2.5.3...
- Installed hashicorp/local v2.5.3 (signed by HashiCorp)

Terraform has been successfully initialized!

$ terraform plan

Terraform will perform the following actions:

  # random_pet.example: (no changes)

Changes to Outputs:
  + notes_content = "hello from outside terraform\n"

Plan: 0 to add, 0 to change, 0 to destroy.

Read that plan carefully — this is the payoff of the whole lesson. There is no + create, no ~ change, no - destroy line for data.local_file.notes anywhere in the output. Terraform doesn't touch notes.txt at all; it just read it and used the value inside the new output. Compare that to every random_pet plan you've seen since Lesson 5, which always shows an explicit create/change/destroy action — because random_pet is a resource Terraform owns.

Run terraform apply and type yes, and you'll see notes_content printed at the bottom, exactly like any other output from Lesson 7 — data source values flow through the rest of your config exactly like resource attributes do, once read.

Best practice — data sources are re-read on every plan, they are not cached. Edit notes.txt outside Terraform and run terraform plan again: you'll see notes_content listed as an output that will change, even though you never touched your .tf files. This is normal and expected — a data source's whole job is to reflect current outside reality back into your config every time you plan. It's the opposite of a resource, where Terraform's state file is the source of truth between runs.

The cloud-scale case — data "aws_ami" (conceptual)

The most common real-world use of data sources is looking up a cloud object your team doesn't manage in this config, then feeding its ID into a resource you are creating. The canonical example, straight from HashiCorp's own AWS tutorials, is looking up the latest AMI to boot a new EC2 instance from:

data "aws_ami" "ubuntu" {
  most_recent = true

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }

  owners = ["099720109477"] # Canonical's official AWS account ID
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
}

This example is illustrative, not something to run in this course — it needs a real AWS account and credentials, which this zero-cost course deliberately avoids until the AWS-specific lessons later on. But read the shape of it: data "aws_ami" "ubuntu" never creates an AMI — Canonical (Ubuntu's publisher) already built and published it. The data block just finds the right one by filtering on name and owner, and most_recent = true picks the newest match if several fit the filter. The resource "aws_instance" block underneath is the part Terraform actually creates, and it borrows data.aws_ami.ubuntu.id instead of a hardcoded AMI ID that would go stale the next time Canonical ships an update.

One timing subtlety worth knowing

Terraform normally reads a data source's real value during plan — that's why you saw the actual file content, not (known after apply), in the plan output above. But if a data source's arguments depend on a value that won't exist until something else is created or changed first, Terraform can't read it yet — it defers the read until apply, and the plan shows (known after apply) for that data source instead, same as you saw for a brand-new resource's id in Lesson 5. You don't need to do anything differently — Terraform figures this out from your config's dependency graph on its own.

Try it — before looking below

Q1. "This block reads an existing VPC that the networking team already created." Resource or data?

data — Terraform is only looking the VPC up, not creating or managing it.

Q2. "This block creates a brand-new VPC for this project." Resource or data?

resource — Terraform will create it, and will change or destroy it if the config changes.

Q3. You delete a data "aws_ami" "ubuntu" {} block from your config and run apply. What happens to the actual AMI in AWS?

Nothing. The AMI was never Terraform's to destroy — deleting a data block only stops Terraform from reading it. Compare this to deleting a resource block, which schedules the real thing for destruction.

Q4. "This looks up the latest Ubuntu AMI ID, then uses it to launch a new EC2 instance." Is this one block or two, and what type(s)?

Two blocks: a data "aws_ami" block to read the existing AMI (data), whose id attribute feeds into a resource "aws_instance" block that Terraform creates and owns (resource). This combination — data feeding a resource — is the most common real-world pattern.

Now write your own

In the same folder you've been building since Lesson 4:

  • create notes.txt with any one line of text
  • add the local provider to required_providers
  • add the data "local_file" "notes" block and the notes_content output
  • run terraform init (new provider, so this is required)
  • run terraform plan — confirm there is no create/change/destroy line for the data source itself, only a new output
  • run terraform apply, type yes, and confirm notes_content prints the file's text
  • edit notes.txt outside Terraform, then run terraform plan again — confirm it now shows the output changing, with no edits to any .tf file

Recap
  • Mental model: resource = Terraform owns it and will create/change/destroy it. data = Terraform only reads it, and never touches the real thing no matter what the config does.
  • Syntax: data "<TYPE>" "<LOCAL_NAME>" { ... }, referenced elsewhere as data.<TYPE>.<LOCAL_NAME>.<ATTRIBUTE> — note the extra data. prefix resources don't need.
  • Data sources are re-read on every plan, not cached — if the real thing changes outside Terraform, your next plan reflects it immediately.
  • The most common real pattern: a data block looks up something that already exists, and its attribute feeds into a resource block that Terraform actually creates.
