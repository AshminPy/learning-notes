State locking & drift detection

Lesson 14 moved your state file to a remote backend so a team can share it. But sharing a single file raises a new question immediately: what stops two people from running apply at the same time and corrupting it? And separately — what happens when the real infrastructure changes but nobody tells Terraform? Both problems are about the same thing: keeping state trustworthy once more than one actor (a person, a pipeline, a console click) can touch the real world. This lesson covers both: locking (protects against concurrent writes) and drift (protects your understanding of what's actually true).

What state locking actually does

When Terraform runs an operation that could write to state — most importantly apply — it first acquires a lock on that state. HashiCorp's own docs put the reason plainly: locking "prevents others from acquiring the lock and potentially corrupting your state." While the lock is held, a second apply targeting the same state doesn't get to barge in and write at the same time — it either waits or errors out, depending on how it's invoked.

Mental model: a state lock is a "do not disturb" sign on a hotel room door, not a deadbolt permanently welded shut. It goes up automatically the moment Terraform starts an operation that writes state, and it comes down automatically the moment that operation finishes — success or failure. Nobody has to remember to lock or unlock anything by hand in the normal case. It exists only to stop two people from redecorating the same room at the same second, not to keep the room locked forever.

Not every backend supports locking

Locking is a backend feature, not a Terraform-core guarantee that applies everywhere — the docs are explicit that "not all backends support locking," and each backend that does support it implements the mechanism differently. Two you already know from this course:

  • Local backend (your terraform.tfstate on disk, Lessons 5–13) — supports locking too. The docs describe it as locking "that state using system APIs," i.e. your operating system's own file-locking calls. It's why even solo, single-laptop Terraform occasionally shows a lock error if you accidentally run two commands against the same folder at once.
  • S3 backend (Lesson 14) — locking is optional and configured explicitly. The current recommended method is a native S3 lockfile, enabled with use_lockfile = true in the backend block. The older method — a separate DynamoDB table holding a lock row — still works but HashiCorp's docs now mark it deprecated and slated for removal in a future minor version. If you're following an older tutorial that shows dynamodb_table, know that it still works today but isn't the current recommendation.

Other backends (Terraform Cloud/HCP Terraform, Google Cloud Storage, Azure Storage, Postgres, and others) each implement locking their own way. The rule to carry forward: before you trust a shared backend to protect you from concurrent applies, check that specific backend's docs — don't assume locking is on just because the backend is remote.

Stuck locks and force-unlock

Because the lock is tied to a running operation, anything that kills that operation abnormally — a crashed laptop, a killed CI job, a network drop mid-apply — can leave the lock standing with nobody actually working. The next person to run apply gets blocked by a lock that no longer corresponds to real, in-progress work.

Terraform's answer is terraform force-unlock <LOCK_ID>. It requires the specific lock ID (Terraform prints this in the error message of whoever got blocked), which acts as a confirmation that you're releasing the lock you think you're releasing, not a different one. The official guidance is a genuine warning, worth quoting exactly:

From HashiCorp's docs: "Be very careful with this command. If you unlock the state when someone else is holding the lock it could cause multiple writers." Force-unlock is meant to clear your own stuck lock after automatic unlocking failed — never to override a lock someone else is actively holding. Before running it, confirm with your team that no apply is genuinely in flight.

Drift — when reality stops matching state

State locking protects against Terraform corrupting itself. It does nothing about a completely different problem: someone opens the AWS console and resizes an instance by hand. Someone runs a one-off kubectl or CLI command that touches a resource Terraform manages. An auto-scaler, a security tool, or another automation changes something outside Terraform entirely. In every case, the real infrastructure now disagrees with what's recorded in state (and by extension, with your config). This gap is called drift.

Mental model: state is Terraform's memory of what it last saw. Drift is what happens when the world moves on without updating that memory — like a to-do list that says "in progress" for a task someone else already finished, or already threw out, without telling you.

How terraform plan catches it — refresh, then compare

You don't run a separate "check for drift" command. terraform plan already does it as its first step, before it ever compares anything to your config: it refreshes state, meaning it queries each real resource's provider API and pulls back the actual current values, updating its in-memory picture of what really exists right now. Only after that refresh does it diff the refreshed reality against your .tf config to produce the plan you read.

This is why a resource can show up as needing changes in plan even though you haven't touched a single .tf file since the last apply — the config didn't change, but reality did, and the refresh step is what surfaces that gap. (You can skip the refresh with terraform plan -refresh=false if you specifically want to compare against last-known state instead of live reality, but that's the exception, not the default.)

Fixing drift — two directions, one real tradeoff

Once plan shows drift, you have exactly two honest ways to resolve it, and picking between them is a judgment call, not a technical one:

Re-apply (reality → config)Update config (config → reality)
What happensterraform apply pushes your config's values back onto the real resource, overwriting the manual changeYou edit your .tf files to match what the resource now actually looks like, so plan shows no diff
Use whenthe manual change was accidental, unauthorized, or simply wrong — config is the source of truth and should winthe manual change was legitimate and should be kept — reality is right, and your config was the thing out of date
Riskyou silently undo someone's real, possibly urgent, fix (e.g. a manual scale-up during an incident)you have to correctly translate whatever was clicked in a console back into accurate HCL — easy to get subtly wrong

Best practice: treat recurring drift as a process signal, not just a technical one. If the same resource keeps drifting, something outside Terraform keeps touching infrastructure it shouldn't — restrict console/API access for Terraform-managed resources, or bring that change into the config properly instead of leaving it as a manual habit.

Try it — before looking below

Q1. A teammate manually deletes a resource in the cloud console — a resource your Terraform config still declares and your state still tracks. What does terraform plan show, and why?

Terraform refreshes state first and finds the resource genuinely gone from the real infrastructure. Since your config still declares it, plan shows it needs to be created again (not "no changes") — from Terraform's refreshed view, a resource it's supposed to own simply doesn't exist anymore.

Q2. What are the two ways to resolve that situation, and what does each one actually decide?

(1) Run terraform apply — this recreates the resource, pushing your config back onto reality, appropriate if the deletion was a mistake. (2) Remove the resource's block from your config (and use terraform state rm so Terraform stops tracking it without trying to destroy something that's already gone) — appropriate if the deletion was intentional and the resource should no longer exist. Which one is correct depends entirely on whether the manual deletion was wanted — Terraform can't tell you that, only a human can.

Q3. Your teammate's apply got killed mid-run when their laptop lost power. Your own apply now fails with a lock error. Is it safe to immediately run terraform force-unlock?

Only after confirming nobody's apply is genuinely still running. The lock outlived the crashed process, so it's now stale — but force-unlock can't tell the difference between "stale lock from a crash" and "someone's apply is legitimately mid-write." Unlocking a lock someone else actually holds risks two writers touching state at once, the exact corruption locking exists to prevent.

Hands-on: watch plan catch drift, for free

Reproducing a stuck lock needs a real crash mid-write, which isn't practical to force in a lesson. Drift detection, though, you can see with the same local, zero-cost setup from Lessons 8–9 — no cloud account required, because the local backend and the local_file resource are enough to prove the mechanism.

In the same project folder, make sure you have this (from earlier lessons):

resource "local_file" "pet_note" {
  filename = "${path.module}/pet.txt"
  content  = "hello from terraform"
}

Walk through it:

  • run terraform apply, type yes — this creates pet.txt and records it in state
  • run terraform plan once more first, and confirm it reports no changes — state and reality agree
  • now simulate someone changing infrastructure outside Terraform: delete the file directly, not through Terraform — rm pet.txt
  • run terraform plan again — you'll see it plan to create local_file.pet_note again, even though you didn't touch a single .tf file. That's the refresh step finding the file gone and comparing against your still-unchanged config.
  • you now have the same choice as the quiz above: run terraform apply to recreate pet.txt (reality loses), or remove the resource block and run terraform state rm local_file.pet_note if you'd decided you didn't want the file anymore (config catches up to reality)
  • if you re-applied, run terraform destroy, type yes, to clean up before moving on

Note on locking hands-on: you won't reliably see a lock error running solo against the local backend — apply against a couple of local resources finishes in well under a second, too fast for two terminals to genuinely collide. On a shared remote backend with a team actually running applies concurrently, this is a routine, expected error message, not a bug — it's the lock doing its job.

Recap
  • State locking is a "do not disturb" sign, not a permanent lock — Terraform acquires it automatically for operations that write state (like apply) and releases it automatically when the operation ends.
  • Not every backend supports locking, and mechanisms differ — the local backend uses system file-locking APIs; the S3 backend supports an optional native lockfile (use_lockfile), with the older DynamoDB-table method now deprecated. Always check your specific backend's docs.
  • A crashed process can leave a lock stuck. terraform force-unlock <LOCK_ID> clears it, but only after confirming no one else is actually holding it — unlocking an active lock risks the exact corruption locking prevents.
  • Drift is when real infrastructure changes outside Terraform, so it no longer matches state/config. terraform plan catches it automatically by refreshing state against real infrastructure before diffing against config.
  • Two fixes for drift: re-apply to force reality back to match config (config wins), or update your config to match reality (reality wins) — the right choice depends on whether the manual change should be kept, which only a human can decide.
