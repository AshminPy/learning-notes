Cost awareness

Everything so far has been about correctness and safety — state (Lesson 13), plan review (Lesson 26), policy as code (Lesson 30), IAM (Lesson 31). This lesson is about a different kind of risk: money. A perfectly correct, perfectly secure Terraform config can still bankrupt a budget in seconds, and it happens in a very specific, IaC-shaped way that clicking around a cloud console doesn't.

Why IaC makes cost surprises worse, not just possible

Think about how you'd accidentally overspend in the AWS or GCP console by hand. You click "create instance," pick a size, click again. Cost creeps up one click at a time — you'd have to click "create" dozens of times in a row to spin up dozens of expensive resources, and somewhere around click five or six, most people notice what they're doing.

Terraform removes that friction entirely, which is exactly its selling point from Lesson 3 — and exactly why it's a cost risk. A single terraform apply can create one resource or two hundred, and from where you're sitting, typing yes, both look almost identical: one confirmation prompt, one keystroke. You saw this mechanism directly in Lesson 11 — a for_each or count block that looks like a few lines of HCL can expand into dozens of real, billable resources the moment you approve the plan. There's no "click five more times and maybe reconsider" pause built in. The friction that naturally slows down console-driven overspending doesn't exist in Terraform — the plan output is the only place that friction can live.

Mental model: the console makes cost visible through repetition — you feel the cost adding up because you're the one clicking each time. Terraform makes cost invisible through automation — the same "create N things" power that makes Terraform valuable also means cost can scale instantly, with a single approval, unless you deliberately go looking for it in the plan.

Reading the plan's resource count as a cost-risk signal

You already know from Lesson 5 to read the plan summary line before typing yes — Plan: 1 to add, 0 to change, 0 to destroy. That habit was taught as a correctness check: does the resource count match what you expected? It's also, with zero extra effort, a rough cost-risk signal.

Plan: 1 to add deserves a glance. Plan: 40 to add deserves real scrutiny — not because more resources are automatically wrong, but because the blast radius for both mistakes and spend is proportional to that number. Before approving a plan with a large add count, it's worth asking:

  • Does this number match what I intended? (A stray for_each over the wrong set, or a count pointed at the wrong variable, can silently multiply resources — Lesson 11's exact pitfall, just pointed at your wallet instead of your state.)
  • What resource types are being added? Forty aws_s3_bucket objects and forty aws_instance objects with a large instance type are not remotely the same cost event, even though both show up as "40 to add."
  • Is this a one-time cost (created once, billed once or not at all) or an ongoing cost (billed every hour/month it exists)? The plan's resource count doesn't tell you this — you have to know your resource types.

Important limit: the resource count is a rough triage signal, not a cost estimate. "40 to add" could be forty free resources or forty expensive ones — the number alone can't tell the difference. Treat a high count as "look closer," not as a verdict either way. The tools later in this lesson exist precisely because resource count isn't precise enough on its own.

Tagging for cost allocation

Lesson 30 introduced policy as code with an example rule: "every resource must carry a cost-center tag so finance can attribute cloud spend." That wasn't just an example of what a policy engine can check — it's the actual mechanism cost allocation runs on. Cloud billing tools (AWS Cost Explorer, GCP's billing reports, and equivalents) can break down spend by tag, but only if the tag is actually present on the resource. No tag, no attribution — that spend just shows up as unexplained cost sitting in a shared bucket nobody can trace back to a team or project.

This is a case where a correctness lesson and a cost lesson are the same lesson wearing two hats. A hard-mandatory Sentinel or OPA policy requiring a cost-center (or team, or project) tag on every resource isn't just tidy governance — it's what makes "how much is team X actually spending" an answerable question instead of a guess. Untagged infrastructure is cost you can see the total for, but never explain.

Third-party cost estimation: Infracost

Reading resource counts and enforcing tags both help, but neither one tells you an actual dollar figure before you apply. That's the gap third-party cost-estimation tools fill. Infracost is the best-known example — a tool built specifically to sit alongside Terraform and estimate the cost impact of a plan before it's applied.

Conceptually, the workflow mirrors the policy-as-code workflow from Lesson 30: Infracost reads Terraform's plan output (it works from the same terraform show -json plan JSON that OPA consumes) and matches the resources in it against cloud provider pricing data, producing a cost estimate and — critically — a cost diff for changes, so you can see "this PR adds $340/month" as a number attached to the pull request, not something you discover on next month's bill. Its own documentation describes this as a "shift-left" approach: surfacing cost during code review, in the same pull request where Lesson 26's plan review and Lesson 30's policy checks already happen, rather than after the infrastructure is live and already being billed.

This lesson isn't teaching you to install or configure Infracost — that's implementation detail for a later, hands-on moment if you ever need it. What matters here is the mental model: a plan is structured data (Lesson 30 already established this for policy checks), and cost estimation is just another automated reader of that same data, slotting into the same place in your pipeline — after the plan, before the apply.

Basic cost hygiene: always destroy throwaway resources

None of the above matters if learning resources are just left running. Lesson 5 taught terraform destroy as the fourth command in the core workflow, and every hands-on section in this course since has ended with a reminder to run it. That reminder isn't filler — it's the single cheapest cost-control habit that exists. A random_pet resource costs nothing left running, because it isn't real infrastructure. A forgotten aws_instance or a database from a course exercise absolutely does cost something, for every hour it keeps existing, whether or not anyone is using it or even remembers it's there.

Best practice: if you provisioned it to learn, and you're done learning from it, run terraform destroy before you close the terminal. Don't rely on remembering later — "I'll clean it up tomorrow" is exactly how idle cloud spend accumulates. State (Lesson 13) makes this trivial: Terraform already knows everything it created, so destroy is always a complete, accurate teardown, not a manual hunt through a console.

Try it — before looking below

Q1. You run terraform plan and see Plan: 25 to add, 0 to change, 0 to destroy, mostly instances of one resource type created through a for_each or count block (Lesson 11). What should you check before typing yes?

First, confirm 25 is actually what you intended — check the collection driving the for_each/count (a variable, a data source result, a list) to rule out the Lesson 11 pitfall of it silently containing more entries than you expected. Second, look at what resource type is being multiplied and whether it's a one-time or ongoing (billed-per-hour) cost — 25 free/cheap resources and 25 large, always-on instances are both "25 to add," but very different cost events. Third, if this is going to real cloud spend and not a throwaway exercise, consider running it through a cost-estimation tool (like Infracost) or checking it against a tagging/cost policy (Lesson 30) before approving, so the cost is visible and attributable, not just multiplied.

Q2. Your org has an OPA policy requiring every resource to carry a cost-center tag. Why does enforcing that tag matter for cost specifically, beyond just being tidy governance?

Cloud billing tools can only attribute spend to a team or project if the resource is tagged with that information. Without the tag, the resource still costs money and still shows up on the bill — it's just unexplained spend nobody can trace back to who owns it or why it exists. The policy isn't decoration; it's the actual mechanism that makes "what is team X spending" an answerable question instead of a guess.

Hands-on: read a plan for cost risk, not just correctness

No new resources to create for this one — reuse the for_each example from Lesson 11 (three random_pet resources keyed by environment name) if you still have it, or rebuild it quickly:

resource "random_pet" "env_pet" {
  for_each = toset(["dev", "staging", "prod"])
  length   = 2
}
  • run terraform plan and find the summary line — note the "to add" count
  • before you'd normally jump to apply, pause and ask the three questions from this lesson: does the count match intent, what resource type is this, is it one-time or ongoing cost
  • random_pet is free and stateless-to-the-cloud, so the honest answer here is "zero cost, low risk" — the point of the exercise is practicing the pause, not finding a real bill
  • now imagine the same for_each set had ten entries instead of three, and the resource were aws_instance with a large instance type instead of random_pet — walk through out loud what you'd check differently before approving that plan
  • run terraform destroy, type yes, to clean up if you built the resources

This is a habit exercise, not a syntax exercise — the goal is making "check the count, check the type, check one-time vs. ongoing" as automatic as reading the plan at all.

Recap
  • Terraform can create dozens of billable resources from one apply approval — unlike the console, where cost creeps up visibly one click at a time, Terraform has no built-in pause proportional to blast radius.
  • Treat the plan's "to add" count as a rough cost-risk signal, not a verdict: a high count means look closer at intent, resource type, and one-time vs. ongoing cost — it doesn't by itself mean something is wrong.
  • Tagging resources (Lesson 30's cost-center tag example) is what makes spend attributable to a team or project — untagged resources still cost money, they just can't be traced.
  • Infracost is a real third-party tool that reads Terraform plan JSON and estimates cost impact before apply, commonly surfaced as a cost diff on pull requests, alongside Lesson 26's plan review and Lesson 30's policy checks.
  • Always run terraform destroy on throwaway/learning resources (Lesson 5) — it's the cheapest, most reliable cost-control habit in the entire course.
