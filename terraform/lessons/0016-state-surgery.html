State surgery: import, mv, rm, moved blocks

Lessons 13–15 taught you what state is and how it stays safe under a team. This lesson teaches you how to operate on it directly — on purpose. Real infrastructure work is messy: someone clicks "create" in the console before Terraform exists for that project, you rename a resource while refactoring, or a resource genuinely needs to leave Terraform's management without being destroyed. Terraform has a specific toolset for exactly this, and it's called "state surgery" for a reason — done carefully, these commands are precise and safe; done carelessly, they can make Terraform's next plan propose something you really don't want.

First: look, don't touch

Before changing anything, you need to see what's actually in state. Two read-only commands cover this, and you should reach for them constantly — they cannot modify anything, so there's no risk in running them.

terraform state list prints every resource address currently tracked in state:

$ terraform state list
aws_instance.foo
aws_instance.bar[0]
aws_instance.bar[1]
module.elb.aws_elb.main

You can filter it to a specific resource or module by passing an address: terraform state list aws_instance.bar, or terraform state list module.elb to include everything nested inside that module.

terraform state show <ADDRESS> prints every attribute Terraform has recorded for one specific resource — the same detail you'd otherwise have to go dig out of the raw JSON file by hand (Lesson 13):

$ terraform state show 'aws_instance.foo'
# aws_instance.foo:
resource "aws_instance" "foo" {
    ami           = "ami-0c55b159cbfafe1f0"
    id            = "i-0abc123"
    instance_type = "t2.micro"
    ...
}

Neither command writes to state or touches real infrastructure. Get comfortable with both before you go anywhere near the commands below — state list plus state show is how you confirm, before and after any surgery, exactly what Terraform believes exists.

terraform import — bring existing infrastructure under management

Real-world scenario: someone created an S3 bucket by hand in the AWS console, months before your team started using Terraform. That bucket is real, it's in use, and you don't want to destroy and recreate it just to get it under Terraform's control — that would mean data loss and downtime for no reason. terraform import exists for exactly this: it tells Terraform "this real object, at this address, is now yours to track," without touching the real resource at all.

Syntax:

terraform import [options] ADDRESS ID

where ADDRESS is the resource address in your config (it must already exist as an empty-ish resource block — more on that below), and ID is whatever identifier the provider uses for that resource type — an EC2 instance ID like i-abcd1234, an S3 bucket name, a Route53 zone ID. The exact ID format is documented on each resource's page in the Terraform Registry, because every provider and resource type defines its own.

$ terraform import aws_instance.foo i-abcd1234

The step people miss: terraform import only writes to state. It does not generate the matching resource block in your .tf files — HashiCorp's docs are explicit that "importing via the CLI does not generate configuration." You have to write the resource "aws_instance" "foo" {} block yourself first (even a mostly-empty one is enough to give the import a target address), run the import, then run terraform plan and fill in your config's arguments until the plan shows no changes. If your config doesn't match what got imported, Terraform will plan to "fix" the real resource to match your incomplete config — which can mean unwanted changes on the very next apply.

terraform state mv — rename or relocate a resource in state

Different scenario: no real infrastructure changed, but you renamed a resource in your config — maybe aws_instance.worker became aws_instance.app_server during a refactor, or you moved a resource into a module. As far as Terraform's default comparison logic is concerned (Lesson 13), a resource with a new address that isn't in state looks like a brand-new resource to create, and the old address that's no longer in config looks like something to destroy. Left alone, that's a real destroy-and-recreate — exactly what you don't want for a rename.

terraform state mv fixes the state file directly, telling Terraform "the object at this old address is the same object now living at this new address":

terraform state mv [options] SOURCE DESTINATION
$ terraform state mv aws_instance.worker aws_instance.app_server

It also handles moving something into a module (terraform state mv aws_instance.worker module.compute.aws_instance.worker), and addresses with count or for_each indices (terraform state mv 'aws_instance.worker[0]' 'aws_instance.helper[0]').

The official docs flag a real collaboration risk here: because state mv is an imperative command you run once, from your own terminal, it isn't something your teammates automatically see. HashiCorp's guidance: "if you are using Terraform in a collaborative environment, you must ensure that... you communicate carefully with your coworkers to ensure that nobody makes any other changes between your configuration change and your terraform state mv command." That gap — a manual command outside version control — is exactly what moved blocks (below) were built to close.

terraform state rm — stop managing a resource, without destroying it

This is the command most likely to be confused with terraform destroy, so be precise about the difference:

  • terraform destroy — deletes the real infrastructure, then removes it from state.
  • terraform state rm — removes the entry from state only. The real infrastructure is untouched and keeps running exactly as it was — Terraform simply stops knowing about it, forgets it, and stops managing it.
terraform state rm [options] ADDRESS...
$ terraform state rm 'aws_instance.legacy'

The docs describe it as removing "the binding to an existing remote object without first destroying it. The remote object continues to exist but is no longer managed by Terraform." You'd reach for this when a resource is being handed off to a different team's Terraform config, being migrated to manual/ClickOps management on purpose, or being adopted by a completely different tool.

Watch this consequence: after you run state rm, the resource is still sitting in your .tf config (unless you also delete that block). So the very next terraform plan sees "config wants this, state doesn't have it" — the same logic as Lesson 13's three-way comparison — and will propose creating a brand-new copy of that resource. If you meant to stop managing it, delete the config block too, or you'll get a surprise duplicate on the next apply.

moved blocks — the modern, declarative alternative

Since Terraform 1.1, there's a second way to handle renames and relocations: instead of running state mv from your terminal, you write the intent directly into your configuration as a moved block, and Terraform applies it automatically during the next plan/apply.

moved {
  from = aws_instance.a
  to   = aws_instance.b
}

HashiCorp's docs describe the mechanism plainly: "by default, Terraform interprets a change as an instruction to destroy the existing resource and create a new resource at the new address. You can use a moved block to update a resource address without destroying it." When you run plan, Terraform checks state for an object at the from address and, if found, treats it as the same object now at the to address — no destroy, no recreate.

Why prefer this over state mv where you can: a moved block lives in a .tf file, which means it's committed to git, shows up in your pull request diff, and gets reviewed by a teammate exactly like any other config change. state mv is a one-off command that runs against one person's local (or remote) state right now, invisible to anyone not in that terminal at that moment — which is precisely the coordination risk the official docs warn about above. For refactors that ship through normal version control and code review, moved blocks are the safer default; reach for the imperative state mv command mainly for one-off, ad-hoc fixes outside your normal config workflow.

Safety callout — this is the whole point of the lesson: terraform state rm and terraform state mv change what Terraform believes exists, not what actually exists. Get one wrong, and the next plan/apply can try to recreate a resource that's still running (duplicate real infrastructure) or lose track of a resource Terraform should still be managing (orphaned drift). HashiCorp's own tooling treats this risk as serious enough that "backups for state modification can not be disabled" — every state-modifying command writes an automatic local backup file before it touches anything. Even so, before doing state surgery on anything real: confirm your backend has versioning enabled (Lesson 14), or manually copy terraform.tfstate somewhere safe first, and run terraform state list before and after so you can see exactly what changed.

Try it — before looking below

Q1. You rename a resource's local name in your config — aws_instance.worker becomes aws_instance.app_server — and change nothing else. What happens on the next terraform plan if you do nothing further, versus if you add a moved block?

If you do nothing: Terraform's three-way comparison sees aws_instance.app_server in config with no matching state entry (looks new → plan to create) and aws_instance.worker in state with no matching config (looks removed → plan to destroy). You get a destroy-and-recreate of a resource that didn't actually need to change — real downtime/data loss risk for what was just a rename. If you add a moved { from = aws_instance.worker to = aws_instance.app_server } block: Terraform finds the object at the old address in state and renames it in place to the new address, with no destroy and no create. The plan shows no changes (or only genuine attribute changes, if any), because Terraform now understands it's the same object.

Q2. What is the actual difference between terraform destroy on a resource and terraform state rm on that same resource?

terraform destroy deletes the real infrastructure and then removes it from state. terraform state rm only removes the state entry — the real infrastructure keeps running untouched, Terraform just stops tracking and managing it. If you then leave the resource block in your config, the next plan will propose creating a new one, since config now says "should exist" and state says "doesn't exist."

Hands-on: inspect state safely, then simulate a rename

Use the random_pet example from earlier lessons (same folder as Lesson 13's exercise).

  • run terraform apply if you don't already have a live pet
  • run terraform state list — confirm you see random_pet.example
  • run terraform state show random_pet.example — confirm you see its attributes, including the generated id
  • in main.tf, rename the resource: change resource "random_pet" "example" to resource "random_pet" "buddy"
  • run terraform plan — without a moved block, watch it propose destroying random_pet.example and creating random_pet.buddy
  • now add this to main.tf: 
    moved {
  from = random_pet.example
  to   = random_pet.buddy
}
  • run terraform plan again — this time it should show no destroy/create, just the rename applied in state
  • run terraform apply to confirm, then terraform destroy to clean up when done

This is the whole lesson in miniature: the resource never changed, only its address did — and the tool you choose (do nothing, state mv, or moved) determines whether Terraform treats that as "same thing, new name" or "destroy this, build a new one."

Recap
  • terraform state list and terraform state show <address> are read-only — always inspect before you operate.
  • terraform import ADDRESS ID brings an existing real resource under Terraform's management without recreating it — but it only touches state, you must still write the matching config block yourself.
  • terraform state mv SOURCE DESTINATION renames/relocates a resource in state without destroy/recreate — coordinate with your team, since it's an imperative command outside version control.
  • terraform state rm ADDRESS stops Terraform managing a resource without destroying it — very different from terraform destroy. Remove the config block too, or the next plan will propose creating a duplicate.
  • moved blocks are the modern, declarative alternative to state mv — written in config, committed to git, reviewable in a PR. Prefer them for refactors that go through your normal workflow.
  • State surgery changes what Terraform believes, not what's real — back up state (or confirm backend versioning) before running state rm/mv on anything that matters.
