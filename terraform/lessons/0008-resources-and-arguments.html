Resources & arguments

You've already written a resource block twice — random_pet in Lesson 5, more resources in Lesson 6. This lesson slows down and takes that block apart piece by piece, because everything else in Terraform is built on top of it. Once the anatomy is solid, the rest of the language is just variations on this one shape.

The anatomy of a resource block

resource "TYPE" "LOCAL_NAME" {
  argument_one = "value"
  argument_two = "value"
}

Four parts, every time:

  • resource — the keyword. It tells Terraform "this block describes a piece of infrastructure to manage," as opposed to variable, output, provider, etc.
  • "TYPE" — which kind of thing, defined by a provider. random_pet, local_file, aws_instance, google_compute_instance. The prefix before the underscore (random, local, aws, google) tells you which provider owns it — that's how Terraform knows which plugin handles this resource.
  • "LOCAL_NAME" — a name you choose, covered in detail below.
  • { arguments } — the settings for this specific instance of that type.

Mental model: TYPE is the noun ("a filing cabinet"), LOCAL_NAME is the sticky label you put on it so you can talk about it ("cabinet-A"), and the arguments are what's inside it ("three drawers, painted grey"). Two different resource blocks can use the same TYPE — same kind of filing cabinet — but each needs its own unique sticky label within that type.

The local name is not real

This is the part beginners trip over: LOCAL_NAME (the second quoted string) exists only inside your Terraform configuration and state. It is never sent to AWS, GCP, or any provider's API. The cloud has no idea your resource is called "example" or "web_server" — as far as the real infrastructure is concerned, that name doesn't exist.

What the local name actually does:

  • lets you refer to this resource elsewhere in your config (random_pet.example.id)
  • is how Terraform tracks this exact resource in its state file (Lesson 5 mentioned terraform.tfstate — this is the key it's stored under)
  • is how terraform plan output addresses it, e.g. random_pet.example will be created

If you rename a resource's local name and re-run plan, Terraform doesn't see "the same resource, renamed" — it sees the old name disappear and a brand new one appear, and will plan to destroy the old one and create a new one. (There's a way to avoid that, moved blocks, which is a later lesson. For now: pick a good name up front and don't change it lightly.)

Arguments vs. attributes — the distinction that matters most

These two words look similar and get confused constantly. Keep them separate:

ArgumentAttribute
What it isA value you set, inside the { } blockA value the provider gives back after Terraform talks to the real infrastructure
When it's knownBefore apply — you wrote itUsually only after apply — it's generated by the provider
Examplelength = 2 on random_petid on random_pet (the generated name itself)

You saw this exact split in Lesson 5's plan output without naming it yet:

+ resource "random_pet" "example" {
    + id        = (known after apply)
    + length    = 2
    + separator = "-"
  }

length and separator are arguments — you could have set them, or let them default. id is an attribute — you cannot set it, it's (known after apply) because only the provider generates it, at create time. Every resource type has its own mix: some values can only be arguments, some can only be attributes, and some (like an AWS instance's instance_type) are arguments you set that the provider also echoes back.

Referencing another resource's attribute

Once a resource has attributes, other resources can read them, using this address:

TYPE.LOCAL_NAME.ATTRIBUTE

For example, random_pet.example.id reaches into the random_pet resource named example and pulls out its id attribute — the generated pet name. You can drop that expression into any other resource's argument, and Terraform will fill in the real value at apply time.

Implicit dependencies

Here's the part that makes this genuinely powerful, not just convenient. When one resource's argument references another resource's attribute, Terraform automatically figures out it must create (or update) the first resource before the second one — you never write "do A then B" anywhere. This is called an implicit dependency, and it's the main way Terraform builds its execution order.

Mental model: think of it like a spreadsheet formula. If cell B1 contains =A1+1, you never tell the spreadsheet "calculate A1 first" — it sees the reference and works out the order itself. Terraform's dependency graph works the same way: reference an attribute, and the ordering is free.

Multiple resources of the same type

Nothing stops you from writing several blocks with the same TYPE, as long as each has a distinct LOCAL_NAME within that type:

resource "random_pet" "frontend" {}
resource "random_pet" "backend" {}

resource "local_file" "frontend_note" {
  filename = "${path.module}/frontend.txt"
  content  = "Frontend pet: ${random_pet.frontend.id}"
}

random_pet.frontend and random_pet.backend are two completely independent resources of the same type — separate entries in state, separate lifecycle, no relationship to each other unless you create one by referencing one from the other.

Best practice — name local names clearly and consistently: example is fine for a one-off lesson, but in a real config, name each resource after what it does, not its type again. Prefer frontend over random_pet_1, prefer app_server over server2. A good local name reads clearly in plan output and in every reference to it — aws_instance.app_server tells you something; aws_instance.this or aws_instance.instance doesn't. Pick a convention (this course uses short, purpose-based names) and use it everywhere, especially once a config has more than a handful of resources.

Try it — before looking below

Q1. You write resource "aws_instance" "web" { instance_type = "t3.micro" }. After apply, AWS assigns this instance an ID like i-0abc123. Is instance_type an argument or an attribute? Is the assigned i-0abc123 an argument or an attribute?

instance_type is an argument — you set it yourself, before apply. The assigned ID is an attribute — AWS generates it, Terraform only learns it after the instance is actually created.

Q2. If local_file.note has content = "Pet: ${random_pet.example.id}", which resource does Terraform create first, and why?

random_pet.example first. local_file.note references its id attribute, which doesn't exist until random_pet.example has been created — Terraform sees that reference and builds an implicit dependency, no explicit ordering needed.

Hands-on: two resources, one implicit dependency

Same folder as previous lessons. Add both the local and random providers to your terraform block if you haven't already (Lesson 4 covered adding a provider):

terraform {
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

Then add these two resources to main.tf:

resource "random_pet" "example" {}

resource "local_file" "pet_note" {
  filename = "${path.module}/pet.txt"
  content  = "The pet's name is ${random_pet.example.id}"
}

Walk through it:

  • run terraform init (new provider — local — so this is required even if you ran it before)
  • run terraform plan and check the order resources are listed in — random_pet.example before local_file.pet_note
  • notice content in the plan shows something like (known after apply) — Terraform can't compute the string until it knows the pet's name
  • run terraform apply, type yes
  • open the new pet.txt file in this folder and confirm it contains the actual generated pet name
  • run terraform destroy, type yes, to clean up

Recap
  • A resource block is resource "TYPE" "LOCAL_NAME" { arguments } — the local name is only for your config and state, never sent to the real infrastructure.
  • Arguments are values you set; attributes are values the provider gives back, often only known after apply.
  • Referencing TYPE.LOCAL_NAME.ATTRIBUTE from another resource creates an implicit dependency — Terraform figures out the create order for you.
  • You can have many resources of the same type; give each a distinct, purpose-based local name.
