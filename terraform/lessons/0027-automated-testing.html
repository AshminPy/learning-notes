Automated testing (terraform test)

Lesson 25 gave you fmt, validate, and lint — all of them check that your code is well-formed. None of them check that your code does what you meant it to do. terraform validate will happily pass on a module whose logic is completely wrong, as long as the syntax is legal HCL. This lesson closes that gap with Terraform's native terraform test framework: real assertions, run against real (or planned) infrastructure, that fail loudly when a module's behavior breaks.

Why test Terraform at all

Think back to the modules you built in Lessons 17–20: named-file, and whatever else you composed on top of it. The whole point of a module is that other people — or other-future-you — call it without reading its internals. That's convenient right up until you change something inside the module and don't notice it broke a case you weren't thinking about. The person who finds out is whoever runs terraform apply next, possibly against production, possibly weeks later, possibly not you.

That's the problem automated tests solve: catch the broken module before someone else's apply does. A test suite you run in CI, on every change to a module, tells you in seconds whether your edit still produces the outputs and resources the module promises — instead of that answer arriving as a production incident.

Mental model: terraform validate checks grammar — is this valid HCL, do argument types match. terraform test checks behavior — given these inputs, does this module actually produce the outputs and resources it's supposed to. Validate answers "is this well-formed?" Test answers "is this correct?" You need both, and they catch completely different classes of bugs.

The native framework: .tftest.hcl files

Since Terraform 1.6, testing is a built-in feature — no extra tooling, no extra language, just more HCL. Test files live in a tests/ directory by default (next to your module or root config) and end in .tftest.hcl. You run them with terraform test.

A test file is built from a small set of blocks:

  • run blocks — the core unit of a test. Each one executes either a plan or an apply against your configuration (or a specific module), then checks assertions against the result. A test file needs at least one.
  • assert blocks — nested inside a run block. Each one has a condition (an expression that must evaluate to true) and an error_message (shown when it doesn't).
  • variables blocks — supply input variable values, either for the whole file or scoped to one run block.
  • module blocks — optional, nested inside a run block, used when you want that run to test a specific module (via source) rather than the root configuration.
  • provider blocks — optional, same syntax as your normal provider configuration, for when a test needs specific provider settings.

Here's the shape, straight from HashiCorp's own docs:

variables {
  bucket_prefix = "test"
}

run "valid_string_concat" {
  command = plan

  assert {
    condition     = aws_s3_bucket.bucket.bucket == "test-bucket"
    error_message = "S3 bucket name did not match expected"
  }
}

Assertions can also reference outputs — output.some_name for the current run, or run.earlier_run_name.some_output to chain off a previous run block's result. That chaining is what lets you build multi-step tests: run one creates a dependency, run two tests against it.

command = plan vs command = apply

This is the one distinction to really internalize, because it changes what a test can and can't catch.

  • command = plan — Terraform builds a plan and checks your assertions against the planned values. No real resource is created. Fast, cheap, safe to run constantly. But: any value that only becomes known once a resource is actually created (a cloud provider's generated ID, a randomly generated name) is still unknown at plan time — and per HashiCorp's docs, "there are instances when Terraform does not execute a custom condition during the planning stage, because that condition is relying on computed attributes that are only available after Terraform creates the referenced resource." A plan-only assertion on that kind of value simply doesn't run.
  • command = apply (the default if you omit command) — Terraform actually applies the configuration, creating real infrastructure, then checks assertions against the real, fully-known result. Slower, and it genuinely creates and destroys resources — but it's the only way to test the things plan-only can't see. HashiCorp describes this as "analogous to integration testing," because you're validating what Terraform actually built, not just what it intended to build.

At the end of a test file, Terraform "attempts to destroy every resource it created during the execution of that test file" — in reverse run block order. So an apply-based test cleans up after itself. It's still real infrastructure for the duration of the test, though.

Cost and safety callout: apply-based tests create real infrastructure — the HashiCorp docs are direct that this can incur real cost, and they recommend a dedicated testing account/subscription you can purge routinely, in case a run gets interrupted before cleanup finishes. For the free local providers you've used throughout this course (random, local), there's nothing to worry about. Once you're testing modules that create real cloud resources, treat an apply-based test suite with the same caution as any other apply.

A pointer, not a deep dive: Terratest

You'll see Terratest mentioned constantly once you start reading about Terraform testing in the wild. It's a third-party, Go-based testing library — you write real Go test functions that run terraform apply, make live assertions against the resulting infrastructure (HTTP calls, SDK calls, whatever you need), then tear it down. It's more powerful than terraform test in the sense that you get a full general-purpose programming language to write assertions in, not just HCL expressions. The trade-off is a real learning curve: you need to know Go, and you're maintaining a separate test codebase alongside your Terraform. For most teams, native terraform test covers module-level correctness just fine, and Terratest earns its complexity only once you need assertions that go beyond what plan/apply output can express — for now, just know it exists.

Try it — before looking below

Q1. Why does testing matter more for the reusable modules from Lessons 17–20 than for a one-off root config you'll only ever apply yourself?

A module is meant to be called by other configs, other environments, maybe other people — the whole point is reuse without reading the internals every time. If you change the module's logic and it breaks a case you weren't thinking about, the person who discovers that is whoever calls the module next, potentially against production, potentially long after you've forgotten the change. A one-off root config only ever hurts the person who wrote it, and they find out immediately at apply time. A broken module can hurt someone else, later, silently — that's exactly the failure mode automated tests are built to catch early.

Q2. You write an assert block checking that a resource's provider-generated ID is a non-empty string. You put it in a run block with command = plan. What happens, and why?

A provider-generated ID doesn't exist until the resource is actually created — at plan time it's still an unknown value, not a real string. Per the docs, Terraform doesn't execute a custom condition during the planning stage when that condition depends on a computed attribute only available after creation. So the assertion effectively can't run as intended against a plan-only run block. To actually check that value, the run block needs command = apply, so the resource is genuinely created first and the ID is a real, known string by the time the assertion runs.

Hands-on: test the module from Lesson 18

Go back to the project folder from Lesson 18 — the one with root main.tf calling module "dev_pet" and module "prod_pet", both pointing at ./modules/named-file.

  • from that project root, create the default test directory: mkdir -p tests
  • create tests/named_file.tftest.hcl with a run block that tests the module directly, applies it, and asserts its file_path output is not empty
  • run terraform test and read the output — it should report the run block as a pass, and confirm resources were created then destroyed
  • then add a second run block using command = plan with an identical assertion, and notice it also passes — because file_path here is built only from path.module and the name_prefix input variable, both fully known before anything is created. Not every output needs an apply to verify.

Write the file yourself first — the module block syntax, the assert block, the two commands — then check the reference below.

Reveal the full test file

# tests/named_file.tftest.hcl

run "plan_only_check" {
  command = plan

  module {
    source = "./modules/named-file"
  }

  variables {
    name_prefix = "planonly"
  }

  assert {
    condition     = output.file_path != ""
    error_message = "file_path should be a known, non-empty value even at plan time"
  }
}

run "apply_and_check" {
  command = apply

  module {
    source = "./modules/named-file"
  }

  variables {
    name_prefix = "test"
  }

  assert {
    condition     = output.file_path != ""
    error_message = "file_path output was empty after apply"
  }
}

# then, from the project root:
terraform test
# expect both run blocks to report success;
# apply_and_check will create a real random_pet + local_file, then destroy them

Stretch goal, optional: add output "pet_id" { value = random_pet.name.id } to modules/named-file/outputs.tf, then write a third run block asserting output.pet_id != "". Try it first with command = apply — it passes, because the pet name is a real generated value by then. Then switch that same run block to command = plan and re-run terraform test. random_pet.name.id is unknown until the resource is actually created, so this is the concrete case from Q2 above, happening in your own terminal instead of in the abstract.

Recap
  • terraform test checks behavior, not just syntax — it catches broken modules before someone else's apply does, which matters most for the reusable modules built in Lessons 17–20.
  • Test files (.tftest.hcl, in a tests/ directory by default) are built from run blocks containing assert blocks, each with a condition and an error_message.
  • command = plan is fast and creates nothing real, but can't verify values that stay unknown until a resource is actually created. command = apply (the default) creates real infrastructure, checks against real results, and Terraform destroys it afterward.
  • Terratest exists as a more powerful, Go-based third-party alternative — know it exists, reach for it only once native terraform test genuinely isn't enough.
