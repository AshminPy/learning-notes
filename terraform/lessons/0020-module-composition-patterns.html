Module composition patterns

You now know how to write a module, how to call one, and how to source and version one. What this lesson adds is judgment: given a real infrastructure need, how do you decide what becomes a module, how many modules, and how they talk to each other? There's no new syntax here. This is the lesson that closes out the Modules phase of the course — everything from here on assumes you can look at a pile of resources and design a sensible module boundary around them.

One giant module vs several focused modules

Picture a typical small platform: a VPC with subnets and route tables, a couple of EC2 instances or an ECS service behind a load balancer, and an RDS database. A beginner instinct is often "let's put this all in one module" — one main.tf with every resource, one set of variables, one set of outputs. It works, technically. But it doesn't scale as judgment.

The alternative — and the pattern almost every real Terraform codebase converges on — is several small, focused modules, each responsible for one part of the system: a networking module that owns the VPC, subnets, and route tables; a database module that owns the RDS instance and its subnet group; a compute module that owns the app servers or ECS service. The root module then calls all three and wires them together.

This isn't just taste. HashiCorp's own module design guidance says a module should "raise the level of abstraction by describing a new concept in your architecture" — their example is a whole "Consul cluster running in AWS" being one module, rather than exposing individual aws_instance and aws_elb resources one by one. A networking module is a new concept in your architecture. A single security group is usually not.

Data flow between modules: outputs feeding inputs

Focused modules only work together if they can pass data between each other, and the mechanism is one you already know: outputs and variables. A networking module outputs its VPC ID and subnet IDs. The root module takes those outputs and passes them as input variables into the compute and database modules.

module "networking" {
  source = "./modules/networking"
  cidr_block = "10.0.0.0/16"
}

module "database" {
  source    = "./modules/database"
  vpc_id    = module.networking.vpc_id
  subnet_ids = module.networking.private_subnet_ids
}

module "compute" {
  source    = "./modules/compute"
  vpc_id    = module.networking.vpc_id
  subnet_ids = module.networking.public_subnet_ids
  db_endpoint = module.database.endpoint
}

Notice the wiring happens entirely in the root module, using module.<name>.<output> references — the same expression syntax you'd use to reference one resource's attribute from another. None of the child modules know about each other directly; they only know about their own inputs and outputs. The root module is the only place that understands how the pieces fit together.

Mental model: this is HashiCorp's own recommended pattern, sometimes called dependency inversion for modules — a module shouldn't create its own prerequisites internally if another module could supply them instead. Passing dependencies in as variables (rather than a module reaching out and creating what it needs) is what keeps modules swappable and testable in isolation. It's the same reason you inject a database connection into a function instead of having the function open its own connection.

When NOT to modularize

This is the part beginners get wrong most often, usually in the direction of overdoing it. Not every resource block deserves to become a module. If you have exactly one security group, used in exactly one place, wrapping it in a module buys you nothing — you've added a file, an indirection, a set of variables and outputs that just pass values straight through, and a debugging step (now you have to go look inside the module to see what it actually does) for zero reuse benefit.

HashiCorp says this directly: "We do not recommend writing modules that are just thin wrappers around single other resource types." Their practical test — if you can't come up with a module name that's different from the name of the primary resource type inside it, you probably don't need a module. A module called security_group that contains one aws_security_group resource is a wrapper, not an abstraction.

The broader principle from the same page: "Over-using modules can make your overall Terraform configuration harder to understand and maintain, so we recommend moderation." Indirection has a real cost — every module boundary is a place a reader has to jump to another file to understand what's happening. Reserve modules for things that are genuinely reused, or that represent a real concept in your architecture (a whole subsystem), not for every individual resource.

Modules you write vs modules you consume

By now you've done both. Lesson 19 covered pulling a module from the public Terraform Registry (a source pointing at terraform-aws-modules/vpc/aws or similar) — that's a module you consume. This lesson has been about modules you write yourself, usually with a local source = "./modules/..." path, tailored to your own environment.

Real root modules mix both freely, and that's normal, not a compromise. A common pattern: use a well-maintained registry module for something generic and widely solved (VPC networking, an EKS cluster) where reinventing it buys you nothing, and write your own local modules for anything specific to your organization (your naming conventions, your particular compute + database pairing, your internal service pattern). The registry module handles the commodity part; your own modules handle the part that's actually yours.

Keep each module focused on one responsibility

Best practice: a networking module should create networking resources — VPCs, subnets, route tables, maybe a NAT gateway. It should not also create IAM roles, or an S3 bucket, or a database, just because those happened to be needed on the same project. Mixing unrelated responsibilities into one module makes it harder to reuse (you can't take the networking half without dragging in IAM you don't want elsewhere) and harder to reason about (a person reading modules/networking shouldn't need to also understand your IAM strategy to know what it does). One module, one clear responsibility — the same single-responsibility instinct you'd apply to a function or a class in any other codebase.

Try it — before looking below

Q1. You have a networking module and a database module. The database needs to be created inside the VPC's private subnets. How does the database module find out which subnet IDs to use, given it doesn't create the VPC itself?

The networking module outputs its private subnet IDs. The root module reads that output with an expression like module.networking.private_subnet_ids and passes it in as an input variable to the database module. The database module never talks to the networking module directly — the root module wires them together.

Q2. You have one aws_s3_bucket resource, used in exactly one place, with no plans to reuse it anywhere. A teammate suggests wrapping it in a module called s3_bucket "for consistency." Is this a good idea? Use HashiCorp's own guidance to justify your answer.

No. HashiCorp explicitly advises against modules that are "just thin wrappers around single other resource types" — and their own naming test applies here: the module's name (s3_bucket) is the same as the resource type inside it (aws_s3_bucket), which is a strong sign it's not adding abstraction. With no reuse benefit, the module only adds an indirection layer someone has to open and read to understand what a single resource block would have told them directly. Just write the resource in the root module.

Hands-on: sketch the module boundaries

Scenario: you need to provision a VPC, a database, and three near-identical microservices (same container image family, same scaling pattern, different names and a couple of config values each). No code to write for this exercise — do it on paper or in a text file.

  • Decide: does the VPC become its own module? Justify it — is it a distinct concept, reused, or complex enough to warrant its own boundary?
  • Decide: does the database become its own module, or a resource block living in the root module? Consider whether you'll ever need a second database in another project.
  • Decide: do the three microservices share one module, called three times with different variables, or do you write three separate copies of the same resources? Think about what happens when you need to add a fourth microservice, or change the scaling policy for all three at once.
  • For every module you decided to create, write down its one responsibility in a single sentence. If you can't, that's a sign the boundary is wrong.
  • Sketch (in words) how outputs flow: what does the VPC module output that the database and microservice modules need as inputs?

Reveal one reasonable design (not the only correct answer — the point is defensible reasoning, not memorizing this one)

VPC → its own module. Networking is a distinct concept, has real internal complexity (subnets, route tables, gateways), and is the kind of thing you'll likely reuse across other projects.

Database → a resource block in the root module (or a small module only if you expect a second database elsewhere). A single RDS instance with no reuse case is close to the "thin wrapper" HashiCorp warns against — unless your org provisions databases this same way repeatedly across projects, in which case a shared module earns its keep.

Three microservices → one module, called three times. This is the textbook reuse case: near-identical resources with only a few varying inputs (name, image tag, maybe replica count) is exactly what modules are for. Three copy-pasted resource blocks would mean fixing the same bug three times later; a fourth microservice becomes one more module block instead of a fresh copy-paste.

Data flow: the VPC module outputs vpc_id and subnet IDs. The root module passes those into both the database module and each of the three microservice module calls, so every piece lands in the right network without any module reaching out to find its own dependencies.

Recap
  • Prefer several small, focused modules (e.g. networking, database, compute) over one giant module — each should represent a real concept in your architecture, not just group unrelated resources.
  • Modules pass data to each other through outputs feeding into other modules' input variables, wired together in the root module — child modules don't talk to each other directly.
  • Don't modularize a single-use resource with no reuse benefit — HashiCorp explicitly warns against "thin wrappers around single other resource types"; indirection has a real readability and debugging cost.
  • Real projects mix modules you write (local, tailored) with modules you consume (registry, generic and well-maintained) — that's normal, not a compromise.
  • Keep each module to one clear responsibility — a networking module shouldn't also create IAM roles — for the same reason a function or class should do one thing.
