Your first resource: init, plan, apply, destroy

Lesson 4 gave you a terraform block and a provider block — the paperwork. This lesson you finally write a resource, the thing Terraform actually manages, and run it through the full lifecycle every Terraform config goes through, from an empty folder to real infrastructure and back to nothing.

Four commands, always in this order, for the rest of your Terraform career:

CommandWhat it doesChanges anything?
terraform initDownloads providers, sets up the working directoryNo
terraform planShows what would changeNo
terraform applyExecutes the plan, after you confirmYes
terraform destroyTears down everything Terraform manages, after you confirmYes

Mental model: think of plan as a building inspector walking through with a clipboard, writing down every change they'd make — nothing gets touched. apply is the crew showing up and actually doing the work on that clipboard. Terraform never lets the crew in without showing you the clipboard first.

The resource we'll use: random_pet

We need something to provision that costs nothing and needs no cloud account, so you can run this lesson right now. The random provider's random_pet resource generates a random pet name like climbing-mudfish — it exists only inside Terraform's state, never touches any real infrastructure, and is genuinely used in real configs (commonly to give a unique, human-readable suffix to a resource name).

Every argument on random_pet is optional, so the smallest valid block is just this. In your main.tf from Lesson 4 (which already has the terraform and provider "random" blocks), add:

resource "random_pet" "example" {}

random_pet's optional arguments, confirmed against the provider's docs: length (words in the name, default 2), separator (default "-"), prefix, and keepers (a map that forces a new name when it changes). Leaving the block empty just takes the defaults. It exposes one read-only attribute, id — the generated name itself.

Step 1 — terraform init

Run this once per config, in the folder that holds your .tf files. It reads your required_providers block from Lesson 4, downloads the random provider plugin, and writes a lock file pinning the exact version it downloaded.

$ terraform init

Initializing the backend...
Initializing provider plugins...
- Finding hashicorp/random versions matching "~> 3.6"...
- Installing hashicorp/random v3.9.0...
- Installed hashicorp/random v3.9.0 (signed by HashiCorp)

Terraform has created a lock file .terraform.lock.hcl to record the provider
selections it made above. Include this file in your version control
repository so that Terraform can guarantee to make the same selections by
default when you run "terraform init" in the future.

Terraform has been successfully initialized!

You may now begin working with Terraform. Try running "terraform plan" to see
any changes that are required for your infrastructure. All Terraform commands
should now work.

You'll see a new .terraform folder (the downloaded plugin) and a .terraform.lock.hcl file (the version pin — commit this one to git, ignore the folder). You only need to run init again if you add a new provider or module to the config, or if someone else's version of the lock file changes.

Step 2 — terraform plan

plan compares your .tf files against what Terraform currently knows exists (its state — more on this in a later lesson), and prints exactly what it would do to make reality match your config. It changes nothing on disk or in the cloud — it's a dry run.

$ terraform plan

Terraform used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
  + create

Terraform will perform the following actions:

  # random_pet.example will be created
  + resource "random_pet" "example" {
      + id        = (known after apply)
      + length    = 2
      + separator = "-"
    }

Plan: 1 to add, 0 to change, 0 to destroy.

Read this output line by line, it's a skill you'll use every single day:

  • + create — the symbol legend. + means add, ~ means change in place, - means destroy.
  • # random_pet.example will be created — which resource, addressed as <type>.<name>, matching your block.
  • id = (known after apply) — Terraform can't know the generated name until the resource actually exists; it fills this in during apply.
  • length = 2, separator = "-" — the defaults you didn't set explicitly, shown so you can see exactly what will be created.
  • Plan: 1 to add, 0 to change, 0 to destroy. — the summary line. Always check this number matches what you expected before you go any further.

Best practice — read the plan before you type yes: this is the single most important safety habit in all of Terraform. Every production incident caused by Terraform traces back to someone approving a plan they didn't actually read. A plan that says 1 to add when you expected a small tweak, or 1 to destroy when you didn't touch that resource, is Terraform warning you before the damage happens — but only if you read it. In Lesson 26 you'll build on this exact habit for reviewing plans in a team pull-request workflow, so treat it as non-negotiable from day one, not an optional extra.

Step 3 — terraform apply

apply generates the same plan again, shows it to you, and then — only after you type yes — actually executes it.

$ terraform apply

Terraform used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
  + create

Terraform will perform the following actions:

  # random_pet.example will be created
  + resource "random_pet" "example" {
      + id        = (known after apply)
      + length    = 2
      + separator = "-"
    }

Plan: 1 to add, 0 to change, 0 to destroy.

Do you want to perform these actions?
  Terraform will perform the actions described above.
  Only 'yes' will be accepted to approve.

  Enter a value: yes

random_pet.example: Creating...
random_pet.example: Creation complete after 0s [id=climbing-mudfish]

Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

Your pet name will be different — it's randomly generated at apply time, that's the whole point of the resource. Notice the prompt only accepts the literal word yes; anything else, including Enter, cancels. Terraform also just wrote a terraform.tfstate file to this folder — that's how it remembers "I created a random_pet named climbing-mudfish" for next time you run plan.

Step 4 — terraform destroy

Run this to tear down everything Terraform is tracking in this config. For this course's free practice resources it's completely safe and expected — you'll run it constantly. In a real production environment it is one of the most dangerous commands that exists: it deletes real infrastructure, with real data, for real users. Never run it against a production working directory without a second person's eyes on the plan first.

$ terraform destroy

Terraform used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
  - destroy

Terraform will perform the following actions:

  # random_pet.example will be destroyed
  - resource "random_pet" "example" {
      - id        = "climbing-mudfish" -> null
      - length    = 2 -> null
      - separator = "-" -> null
    }

Plan: 0 to add, 0 to change, 1 to destroy.

Do you really want to destroy all resources?
  Terraform will destroy all your managed infrastructure, as shown above.
  There is no undo. Only 'yes' will be accepted to confirm.

  Enter a value: yes

random_pet.example: Destroying... [id=climbing-mudfish]
random_pet.example: Destruction complete after 0s

Destroy complete! Resources: 1 destroyed.

Notice the wording is deliberately scarier than apply's prompt — "Do you really want to destroy" and "There is no undo" — because HashiCorp wants this specific command to make you stop and think. After this runs, check your folder: the .tf file is untouched (destroy never deletes your code, only the infrastructure it describes), but terraform.tfstate now shows zero resources.

Try it — before looking below

Q1. Which of the four commands is the only one that is guaranteed to never change anything?

terraform plan (and init, in the sense that it only sets up tooling — but plan is the one whose entire job is to preview changes to infrastructure without making them).

Q2. You run terraform plan and the summary line reads Plan: 0 to add, 0 to change, 3 to destroy — but you only meant to add one new resource. What should you do?

Stop and do not type yes. Read the full plan output to find out why 3 resources are marked for destruction — this is exactly the scenario the plan-reading habit exists to catch, before real infrastructure is deleted.

Now write your own

In the same folder you set up in Lesson 4:

  • add the resource "random_pet" "example" {} block to your main.tf
  • run terraform init (skip this if you already ran it in Lesson 4 and haven't changed providers)
  • run terraform plan and read every line of the output before moving on
  • run terraform apply, type yes, and note the generated pet name
  • run terraform plan again — confirm it now says No changes, because reality matches your config
  • run terraform destroy, type yes, and confirm the resource is gone

Recap
  • The core workflow, always in order: init (once, downloads providers) → plan (preview, changes nothing) → apply (executes, asks for confirmation) → destroy (tears down, asks for confirmation).
  • Only apply and destroy touch real infrastructure — and both refuse to act until you type the literal word yes.
  • Reading the plan output before approving it is the single most important safety habit in Terraform — check the resource names and the summary line against what you actually intended.
