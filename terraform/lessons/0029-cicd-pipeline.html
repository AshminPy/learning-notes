A real CI/CD pipeline (plan on PR, apply on merge)

Every lesson so far has been building toward this one. You know state (Lesson 13), remote backends and locking (Lessons 14–15), modules (Lessons 17–20), workspaces and environments (Lessons 21–22), how to keep secrets out of state and logs (Lesson 24), and how fmt/validate catch mistakes before they cost you anything (Lesson 25). This lesson wires all of that into the pattern almost every real Terraform team runs in production: plan on pull request, apply on merge. No more typing terraform apply from your laptop and hoping.

The shape of the pipeline

Strip away the YAML and the pattern is two rules:

  • Open a pull request that changes .tf files → a CI job runs terraform fmt -check, terraform validate, and terraform plan, then posts the plan output as a comment on the PR. Nothing gets applied. This is Lesson 26's plan-review discipline, automated — every reviewer sees the exact diff of real-world changes before they approve.
  • That pull request gets merged to main → a separate CI job checks out the now-merged code and runs terraform apply, automatically, no human typing yes.

Mental model: a pull request becomes the approval gate for infrastructure changes, the same way it's already the approval gate for application code. The plan comment is the diff. A human reviewing and approving the PR is the "yes" that used to happen at your terminal — it just happens once, in one place, with a permanent record of who approved what and why. apply only ever runs on code that already passed review on main.

Why review the plan on the PR — not trust the pipeline blindly

It's tempting to think "the pipeline ran validate, it's automated, it must be safe." It isn't. validate only checks syntax and internal consistency — it has no idea that your plan is about to destroy and recreate a production database, or that a variable default changed and will now resize every instance in the account. Only plan shows that, and only a human reading that plan output catches it before it happens. That's exactly why this pipeline posts the plan as a comment instead of silently applying it — it forces a person to read "1 to add, 0 to change, 1 to destroy" before clicking merge, not after.

Automation is there to make the review easier and more consistent — same commands, same output format, every single time — not to replace the review. The apply step running unattended after merge is safe specifically because a human already looked at the plan for that exact code before it reached main.

Credentials in CI — never in the workflow file

Your pipeline needs cloud credentials to run plan and apply. The one rule that matters more than any other: never hardcode an access key, secret, or token in the workflow YAML. That file lives in git, git history is forever, and a credential committed once is compromised forever — the same discipline Lesson 24 covers for sensitive = true variables and state applies here too, just one layer up the stack.

Two acceptable ways to hand credentials to CI:

  • The CI platform's secrets store — GitHub Actions has repository/environment secrets (Settings → Secrets and variables → Actions). Reference them in the workflow as ${{ secrets.AWS_ACCESS_KEY_ID }}; the value is encrypted at rest, masked in logs, and never appears in the YAML itself.
  • OIDC / short-lived credentials — the stronger option. Instead of storing a long-lived cloud access key at all, the CI job requests a short-lived token directly from the cloud provider at run time, using GitHub's own OIDC identity token as proof of who's asking. No secret to leak, no key to rotate, and the token expires automatically once the job finishes. The exact setup step differs per cloud (AWS, GCP, Azure each publish their own official GitHub Action for it) — check that provider's current docs when you wire it up, but the workflow always needs permissions: id-token: write to allow the OIDC token request in the first place.

Either way, the workflow file itself never contains a credential — only a reference to where one lives or how to fetch one.

Try it — before looking below

Q1. Your plan-on-PR job runs terraform validate and it passes with no errors. Does that mean it's safe to merge without reading the plan output? Why or why not?

No. validate only checks that your configuration is syntactically correct and internally consistent — it has no knowledge of what real infrastructure exists or what the change would actually do. A config can validate perfectly and still plan to destroy a production resource. Only reading the actual plan output (the add/change/destroy summary) tells you what will really happen — that's why the plan gets posted as a PR comment for a human to read, not just run silently.

Q2. Why is terraform apply allowed to run unattended (no human typing "yes") after merge to main, when Lesson 5 taught you to always read the interactive apply prompt?

Because the review already happened — on the pull request, before merge. A human read the exact plan output for that exact code and approved it. The unattended apply after merge runs against code that's already been through that human checkpoint, so skipping the interactive prompt isn't skipping review, it's just moving the review to happen once, earlier, in a place everyone can see — instead of alone, at apply time, on someone's laptop.

Hands-on: a full plan-on-PR / apply-on-merge workflow

This uses the official hashicorp/setup-terraform GitHub Action to install the Terraform CLI on the runner. Save this as .github/workflows/terraform.yml in a repo whose Terraform code lives in a terraform/ folder, and adjust the working directory to match your own layout.

name: Terraform

on:
  pull_request:
    branches: [main]
    paths: ["terraform/**"]
  push:
    branches: [main]
    paths: ["terraform/**"]

permissions:
  contents: read
  pull-requests: write
  id-token: write   # needed only if you switch to OIDC cloud auth

env:
  working_dir: terraform

jobs:
  plan:
    name: Plan (on pull request)
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ${{ env.working_dir }}
    env:
      AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
      AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
    steps:
      - uses: actions/checkout@v4

      - uses: hashicorp/setup-terraform@v4
        with:
          terraform_version: "1.9.0"

      - name: Terraform fmt
        id: fmt
        run: terraform fmt -check
        continue-on-error: true

      - name: Terraform Init
        id: init
        run: terraform init -input=false

      - name: Terraform Validate
        id: validate
        run: terraform validate -no-color

      - name: Terraform Plan
        id: plan
        run: terraform plan -no-color -input=false
        continue-on-error: true

      - name: Comment plan on PR
        uses: actions/github-script@v7
        env:
          PLAN: "terraform\n${{ steps.plan.outputs.stdout }}"
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          script: |
            const output = `#### Terraform Format \`${{ steps.fmt.outcome }}\`
            #### Terraform Validate \`${{ steps.validate.outcome }}\`
            #### Terraform Plan \`${{ steps.plan.outcome }}\`

            <details><summary>Show plan</summary>

            \`\`\`
            ${process.env.PLAN}
            \`\`\`

            </details>

            *Pusher: @${{ github.actor }}, Action: \`${{ github.event_name }}\`*`;

            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: output
            })

      - name: Fail job if plan errored
        if: steps.plan.outcome == 'failure'
        run: exit 1

  apply:
    name: Apply (on merge to main)
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ${{ env.working_dir }}
    env:
      AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
      AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
    steps:
      - uses: actions/checkout@v4

      - uses: hashicorp/setup-terraform@v4
        with:
          terraform_version: "1.9.0"

      - name: Terraform Init
        run: terraform init -input=false

      - name: Terraform Apply
        run: terraform apply -auto-approve -input=false

Read the shape of it, not just the syntax: two jobs, gated by two different if: conditions on the same trigger file. plan only runs on pull_request events and never touches real infrastructure — every step that could change something (plan itself) uses continue-on-error: true purely so the PR comment step still runs and shows you the failure, then a final step explicitly fails the job if the plan errored. apply only runs on a push to main, which in a protected-branch setup only happens via a merged, reviewed pull request. Credentials in both jobs come from secrets.* — nothing sensitive is written in this file, matching Lesson 24's rule.

Source

github.com/hashicorp/setup-terraform (confirms the action is invoked as hashicorp/setup-terraform@v4, its inputs including terraform_version and terraform_wrapper, and the official example workflow pattern of fmt -check → init → validate → plan → posting the plan via actions/github-script@v7 as a PR comment gated on github.event_name == 'pull_request' with permissions: pull-requests: write) — verified 2026-07-30.

Recap
  • Production CI/CD pattern: terraform fmt -check + validate + plan run on every pull request, with the plan posted as a PR comment for review — nothing is applied yet.
  • terraform apply runs automatically only after merge to main, triggered by the push event on that branch.
  • The PR review is the safety gate. Automation makes the plan easy to see; a human reading it before merge is what makes the unattended apply afterward safe.
  • Never hardcode cloud credentials in the workflow file — use the CI platform's secrets store, or better, OIDC/short-lived credentials with permissions: id-token: write.
