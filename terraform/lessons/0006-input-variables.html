Input variables

In Lesson 5 you wrote resource "random_pet" "example" {} — every value baked straight into the file. That's fine for a one-off experiment, but real configs get reused: the same main.tf deployed for dev and prod, or shared with a teammate who needs slightly different settings without editing your code. Input variables are how you pull those settings out of the resource block and let the caller supply them.

Mental model: a variable block is a function parameter. The rest of your config is the function body — it uses var.something the same way a function uses an argument name, without caring where the value came from. Terraform figures out the actual value from several possible sources before it ever evaluates your resources.

Declaring a variable

Variables are declared with a variable block, named in the label. A full declaration has three common arguments — all optional, but you should get in the habit of setting at least type and description:

variable "pet_length" {
  type        = number
  description = "Number of words in the generated pet name"
  default     = 2
}
  • type — a type constraint. Terraform checks any value it receives against this and errors out if it doesn't match, before plan even runs. Confirmed against HashiCorp's docs.
  • description — a one-line explanation shown in terraform plan prompts and generated docs. Cheap to add, always worth it.
  • default — the value used if nothing else supplies one. A variable with no default is required — Terraform will stop and prompt you for it interactively if you don't provide it another way.

Using a variable: var.<name>

Anywhere inside your config, reference the value with var. followed by the variable's name — no quotes needed even though the value itself might be a string, because this is an expression, not a literal:

resource "random_pet" "example" {
  length = var.pet_length
}

Three ways to set a value

Terraform will look in several places for a variable's value. You've already met the first — the default in the block itself. Here are the two you'll use constantly on top of that:

MethodExampleBest used for
Default in the blockdefault = 2A safe fallback that works for most cases — the config still runs with zero extra input.
-var on the CLIterraform apply -var="pet_length=3"One-off overrides and CI/CD pipelines, where the value is generated or injected at run time rather than stored in a file.
A .tfvars fileterraform apply -var-file="prod.tfvars", or a file literally named terraform.tfvars which Terraform loads automaticallyEnvironment-specific values you want checked into version control (or kept alongside it) — one file per environment, e.g. dev.tfvars, prod.tfvars.

A terraform.tfvars file just holds plain assignments, no variable keyword:

# terraform.tfvars
pet_length = 3

Terraform loads terraform.tfvars and any *.auto.tfvars file automatically, with no flag needed — any other .tfvars file needs an explicit -var-file flag. If a value shows up in more than one place, the CLI -var/-var-file flags win, then *.auto.tfvars files, then terraform.tfvars, then environment variables (TF_VAR_pet_length), and the block's own default loses to all of them. You rarely need to memorize that full order — just avoid setting the same variable in two places at once, and it never comes up.

Best practice: keep default for values that are genuinely safe to leave alone, use a .tfvars file per environment for anything that should differ between dev/staging/prod, and reach for -var only for a quick manual override or when a CI pipeline needs to inject a value it just computed (like a build number). Don't use -var for anything you'd want to reuse tomorrow — it's not saved anywhere.

Type constraints, briefly

Confirmed against HashiCorp's type-constraints docs. The three primitive types:

  • string — text, like "prod"
  • number — whole or fractional, like 2 or 6.28
  • bool — true or false

And the complex ones you'll meet soon, at an introductory level for now:

  • list(string) — an ordered sequence, e.g. ["a", "b", "c"]
  • map(string) — key/value pairs, e.g. { dev = "t2.micro", prod = "t2.large" }
  • object({ name = string, age = number }) — a fixed set of named attributes, each with its own type — useful when one variable needs to bundle several related values together

The validation block

A type constraint only checks the shape of a value. A validation block checks the content — custom rules with a message when they fail. Confirmed against HashiCorp's docs, exact syntax:

variable "pet_length" {
  type        = number
  description = "Number of words in the generated pet name"
  default     = 2

  validation {
    condition     = var.pet_length > 0 && var.pet_length <= 5
    error_message = "pet_length must be between 1 and 5."
  }
}

condition is any expression that evaluates to true or false; error_message is what Terraform prints when it's false. This runs during plan, before anything is created — catching a bad value here is far cheaper than catching it after apply.

Try it — before looking below

Q1. You declare variable "region" { type = string } with no default, and run terraform plan without passing a value any other way. What happens?

Terraform stops and interactively prompts you to type a value for region, because a variable with no default is required — it has no fallback to fall back on.

Q2. You have default = 2 in the block, pet_length = 3 in terraform.tfvars, and you also run terraform apply -var="pet_length=5". What value does random_pet.example actually get?

5. Command-line -var beats a .tfvars file, which beats the block's own default.

Recap
  • A variable block declares an input; var.<name> reads it anywhere in the config — think function parameter, not hardcoded value.
  • Set values with a default (safe fallback), a .tfvars file (per-environment values), or -var on the CLI (one-off overrides, CI) — CLI beats .tfvars beats default.
  • type constrains the shape of a value (string, number, bool, list, map, object...); a validation block constrains its content, and both are checked before anything is created.
