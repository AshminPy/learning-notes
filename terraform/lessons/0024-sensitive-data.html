Handling sensitive data

Back in Lesson 13 you opened terraform.tfstate and saw, in plain readable JSON, every attribute a provider handed back — including things like generated passwords. Last lesson (23) you met ephemeral values, which solve that by never letting a value touch state at all. This lesson covers the older, far more common tool for sensitive data: the sensitive argument. It's on variables and outputs everywhere in real Terraform code, so you need to know exactly what it protects — and, just as important, exactly what it doesn't.

What sensitive = true actually does

You can mark either a variable or an output as sensitive:

variable "api_key" {
  type      = string
  sensitive = true
}

output "api_key_out" {
  value     = var.api_key
  sensitive = true
}

With that in place, Terraform redacts the value everywhere it would normally show up in the CLI: terraform plan and terraform apply print (sensitive value) instead of the real string, and a plain terraform output prints <sensitive>. HashiCorp's own docs describe it plainly: the argument exists "to prevent Terraform from displaying the value in CLI output."

Sensitivity also propagates. If var.api_key is sensitive, any expression that uses it becomes sensitive too — which is why the output block above also needs sensitive = true. If you try to output a sensitive value without marking the output sensitive, Terraform refuses and errors out, forcing you to confirm you meant to expose it.

The limitation you must not forget

Critical: sensitive = true is a CLI display filter. It is not encryption, and it does not remove the value from state. The official docs are explicit about this: "Terraform still stores the values of sensitive variables in your state," and the same is true for sensitive outputs. Open terraform.tfstate in a text editor and the real value is sitting there in plaintext, exactly as if sensitive had never been set. The redaction is also easy to bypass on purpose: running terraform output -json or terraform output -raw <name> prints the plaintext value, by design — those flags exist so scripts can consume the real value.

This is exactly why Lesson 13 told you to never commit terraform.tfstate to git, and why a remote backend with encryption at rest (Lesson 14) matters — encryption of the state file itself is the only thing in this picture that actually protects the value once it's stored. sensitive = true only stops it from flashing across your terminal or CI logs by accident.

Contrast this with Lesson 23's ephemeral values: an ephemeral variable is never written to state or plan files at all, which is a stronger guarantee — but it also means the value can't persist for later reference the way a normal resource attribute can. sensitive and ephemeral solve different problems: one hides output, the other avoids persistence. Neither one encrypts anything.

Never hardcode real secrets

None of this matters if the secret is sitting in plaintext in a file you're about to git add. Two habits to build now, before you have real credentials in play:

  • Never write a real API key, password, or token directly into a .tf file. Even with sensitive = true on the variable, the literal default value would still be readable by anyone who opens the file — sensitive only affects CLI output, not source-code readability.
  • Never commit a .tfvars file that contains real secret values. A terraform.tfvars full of passwords committed to git is exactly as bad as committing state — it's a plaintext secrets file in your repo history forever, even if you delete it later.

Instead, feed secret values in from outside your config at apply time:

  • Environment variables — Terraform reads any TF_VAR_<name> environment variable as the value for a matching variable "<name>" block. export TF_VAR_api_key="..." in your shell (or as a CI secret) never puts the value in a file at all.
  • A dedicated secrets manager — for real production use, tools like AWS Secrets Manager, HashiCorp Vault, or Azure Key Vault store the secret centrally, with access control and audit logging, and a Terraform data source fetches it at apply time. The secret still ends up in state (same limitation as above), but it's never typed into a .tf or .tfvars file, and rotating it doesn't mean editing code.

A .gitignore every Terraform project needs

Before your first commit in any Terraform project, add these lines:

terraform.tfstate*
*.tfvars
.terraform/
  • terraform.tfstate* — covers terraform.tfstate and its automatic terraform.tfstate.backup. Both can hold plaintext secrets, per Lesson 13.
  • *.tfvars — blocks any .tfvars file by default, since that's the most common place real secret values end up. If you have a .tfvars file that's genuinely safe to share (no secrets in it), you can add a narrower exception for it — but the safe default is to block the pattern and opt specific files back in, not the other way around.
  • .terraform/ — the local working directory Terraform creates (provider binaries, module cache). Not sensitive by itself, but it's large, machine-specific, and never belongs in git.

Q1. You mark a variable sensitive = true and run terraform apply. The plan output shows (sensitive value) instead of the real string — great, it's hidden. Is the value actually gone from your project once apply finishes? Where would you go to check?

No — it's only hidden from CLI output. The real value is still written into terraform.tfstate in plaintext, same as any other resource attribute. Open the state file directly in a text editor to see it. sensitive never encrypts or removes anything from state.

Q2. A teammate says "we don't need a secrets manager, we just mark every password variable sensitive = true and we're good." What's wrong with that reasoning?

sensitive only stops the value from printing in the terminal or logs — it does nothing to protect the value in state, and does nothing to stop someone hardcoding the secret into a .tf or .tfvars file and committing it. Real protection needs encrypted state (remote backend, Lesson 14), secrets never typed into source files, and ideally a dedicated secrets manager for rotation and access control.

Hands-on: watch it get redacted — then find it anyway

Make a new folder for this exercise, with a main.tf:

variable "api_key" {
  type      = string
  sensitive = true
  default   = "totally-real-secret-abc123"
}

output "api_key_out" {
  value     = var.api_key
  sensitive = true
}
  • run terraform init, then terraform apply. In the plan, notice the output line reads api_key_out = (sensitive value) instead of the real string
  • type yes to apply
  • run terraform output — api_key_out shows as <sensitive>
  • now run terraform output -raw api_key_out — the real value prints in plaintext. This is the documented bypass, not a bug
  • finally, open terraform.tfstate in a text editor (no terraform command, just read the file) and find the outputs section — the real value totally-real-secret-abc123 is sitting there in plaintext, exactly like every other value you saw in Lesson 13
  • run terraform destroy and type yes to clean up

That's the whole lesson in one exercise: the CLI hid it, and the state file never did.

Recap
  • sensitive = true on a variable or output hides the value from plan/apply/output CLI display — it prints (sensitive value) or <sensitive> instead.
  • It does not encrypt or remove the value from state — the real value is still in terraform.tfstate in plaintext, and terraform output -json/-raw bypasses the redaction on purpose.
  • Real protection comes from never committing state (Lesson 13) and using an encrypted remote backend (Lesson 14) — sensitive is a display filter, not a security boundary.
  • Never hardcode real secrets in .tf files or commit .tfvars containing them. Use environment variables (TF_VAR_*) or a secrets manager (AWS Secrets Manager, Vault, Azure Key Vault) instead.
  • Every Terraform project's .gitignore should include terraform.tfstate*, *.tfvars, and .terraform/.
