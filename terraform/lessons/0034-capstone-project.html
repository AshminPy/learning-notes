Terraform / Zero to Expert — Lesson 34 of 37 — CAPSTONE

Capstone project: end-to-end stack

This is the capstone — the longest lesson in the course, on purpose. It doesn't teach anything new. It combines everything from Lessons 1–33 into one working project: providers and resources (Lessons 4–8), for_each (Lesson 11), lifecycle preconditions (Lesson 12), state and backends (Lessons 13–14), modules (Lessons 17–20), and automated testing (Lesson 27). Like every hands-on example in this course, it uses only the free, zero-cost random and local providers — no cloud account, no billing, runnable on any machine with Terraform installed. Budget real time for this one. Rushing it costs you more later than slowing down now.

What you're building

A small "stack" module, called once per environment from a variable-driven list, wired together the way a real team's root config is structured — just pointed at free local providers instead of a cloud account:

  • a root config that calls a child module using for_each over var.environments, so adding or removing an environment name is the only thing you ever touch (Lessons 11, 17–20)
  • a local backend, structured so that switching to a real remote backend later is a small, contained change — not a rewrite (Lesson 14)
  • an output that surfaces every generated name across every environment, in one place (Lesson 7)
  • a lifecycle block with a precondition that refuses to proceed if var.environments is empty — there's nothing to build a stack from (Lesson 12)
  • a minimal .tftest.hcl test file asserting the stack produces exactly one generated name per environment, plus a second test proving the precondition actually fires (Lesson 27)

By the end you'll have a small, real, working Terraform project — plus a README write-up and GitHub commit, so it becomes an actual portfolio piece, not just a folder on your laptop.

Step 1 — the child module: modules/env-stack/

Same three-file module shape from Lesson 18 — variables.tf, main.tf, outputs.tf. This module knows nothing about "environments" as a list — it just knows how to build one named thing, given one environment name. That's the whole point of a module: the list-handling logic lives outside it, in the root.

# modules/env-stack/variables.tf
variable "environment" {
  description = "Name of the environment this module instance represents"
  type        = string
}
# modules/env-stack/main.tf
resource "random_pet" "name" {
  length = 2
}

resource "local_file" "record" {
  filename = "${path.module}/${var.environment}-stack.txt"
  content  = "environment=${var.environment}\nname=${random_pet.name.id}\n"
}
# modules/env-stack/outputs.tf
output "generated_name" {
  description = "The generated pet name for this environment"
  value       = random_pet.name.id
}

Nothing here is new syntax — path.module and the ${var.environment}-stack.txt filename pattern are exactly Lesson 18's named-file module, just with environment instead of name_prefix as the input name.

Step 2 — root providers and backend: main.tf

Same required_providers block you've used since Lesson 18, plus an explicit backend "local" block (Lesson 14). Local state is the right choice for a solo learning project — but the config is written so that swapping to a team backend later touches only this one block:

# main.tf
terraform {
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }

  backend "local" {
    path = "terraform.tfstate"
  }

  # Production version of this same project, one variable-of-a-different-
  # kind away (Lesson 14): swap the block above for something like this.
  # Note this is NOT a variable substitution — Lesson 14 established that a
  # backend block can't reference var.* at all. Instead, leave the
  # environment-specific values (bucket, key, region) out of the block
  # entirely and supply them at `terraform init` time with
  # `-backend-config=prod.backend.hcl`, so the .tf files never change
  # between environments — only which config file you pass in does:
  #
  # backend "s3" {
  #   bucket       = ""
  #   key          = ""
  #   region       = ""
  #   use_lockfile = true
  # }
}

Why not just a variable? It's tempting to think "make the backend type a variable." Lesson 14 already covered why that doesn't work: a backend block can't refer to input variables, locals, or data sources — it has to be resolvable before Terraform has even loaded the rest of your config. The realistic version of "one change away" is exactly what HashiCorp calls partial configuration: leave the backend's arguments blank (or omit them) in code, and supply the real values via a separate -backend-config file or flags at terraform init — so the same .tf files work unchanged across dev, staging, and a real remote backend.

Step 3 — var.environments and the module call: variables.tf

One list variable drives the whole stack. The module block calls the child module once per entry, using for_each instead of count (Lesson 11) — so renaming or removing one environment never reshuffles the others:

# variables.tf
variable "environments" {
  description = "Names of the environments to build a stack for"
  type        = list(string)
  default     = ["dev", "staging", "prod"]
}
# main.tf, continued — the module call
module "env_stack" {
  source   = "./modules/env-stack"
  for_each = toset(var.environments)

  environment = each.key
}

for_each on a module block works exactly like for_each on a resource block from Lesson 11 — HashiCorp's own docs confirm the meta-argument applies to module blocks the same way, keyed by each.key/each.value, addressed from outside as module.env_stack["dev"]. Each entry in var.environments gets its own fully independent copy of everything inside modules/env-stack — its own random_pet, its own local_file, its own state entry — exactly like dev_pet and prod_pet in Lesson 18, just driven by a list instead of two hand-written module blocks.

Step 4 — the output surfacing every name: outputs.tf

One output, built the same way you built pet_names back in Lesson 11's hands-on — a for expression over the module's instances, turned into a map:

# outputs.tf
output "generated_names" {
  description = "Generated name for every environment in var.environments"
  value       = { for env, mod in module.env_stack : env => mod.generated_name }
}

After apply, this one output shows you every environment's generated name at a glance — { dev = "...", staging = "...", prod = "..." } — without digging through terraform show or the state file.

Step 5 — the lifecycle precondition: back in main.tf

Lesson 12 covered precondition nested inside a resource's lifecycle block — an assumption that must hold before Terraform proceeds. Here, the thing worth asserting is simple: there's no point building a stack for zero environments. Attach the precondition to a small root-level resource that references the whole list — a manifest file summarizing every generated name:

# main.tf, continued — the manifest + its precondition
resource "local_file" "manifest" {
  filename = "${path.module}/generated/manifest.txt"
  content  = join("\n", [for env, mod in module.env_stack : "${env} = ${mod.generated_name}"])

  lifecycle {
    precondition {
      condition     = length(var.environments) > 0
      error_message = "var.environments must contain at least one environment name — nothing to build a stack from."
    }
  }
}

This is the exact same shape as Lesson 12's AMI-architecture example — condition, error_message, nested in lifecycle on a resource block. Because length(var.environments) is known before anything is created, this precondition runs and can fail during terraform plan — you don't need to wait for apply to find out your environments list was accidentally emptied.

Note on directories: generated/ doesn't need to exist beforehand — the local provider's own docs confirm local_file creates any missing parent directories in its filename path automatically.

Step 6 — the test file: tests/stack.tftest.hcl

Lesson 27's native terraform test framework, testing the root config directly (no module block override needed here — omitting it just tests the current configuration, same as running terraform apply in this folder). Two run blocks: one proving the happy path produces the right count of outputs, one proving the precondition actually fires:

# tests/stack.tftest.hcl
run "one_generated_name_per_environment" {
  command = apply

  variables {
    environments = ["dev", "staging"]
  }

  assert {
    condition     = length(output.generated_names) == length(var.environments)
    error_message = "Expected exactly one generated name per environment in var.environments."
  }
}

run "rejects_empty_environment_list" {
  command = plan

  variables {
    environments = []
  }

  expect_failures = [
    local_file.manifest,
  ]
}

The first run applies real (free, local) resources and checks the count matches — a genuine integration test, per Lesson 27. The second uses expect_failures, which HashiCorp's docs describe as a list of "checkable objects... that should fail their custom conditions" — here, local_file.manifest, whose precondition you just wrote in Step 5. This run block passes precisely because the precondition fails as designed — proving the guardrail from Step 5 actually works, not just that it compiles.

Try it — before looking below

Q1. The module call uses for_each = toset(var.environments) instead of count = length(var.environments). If someone removes "staging" from the middle of the list, what's the practical difference between the two approaches, and which lesson covered why?

Lesson 11. With for_each, only module.env_stack["staging"] is destroyed — dev and prod are untouched, because they're keyed by name, not position. With count, removing the middle entry would shift every index after it, and Terraform would plan to destroy and recreate everything past that point in the list, even though only one environment was actually meant to go away.

Q2. Why can't you write backend "s3" { bucket = var.bucket_name } to make the backend "swap in" automatically based on an environment variable — and what's the real mechanism from Lesson 14 that gets you close to that?

A backend block can't reference input variables, locals, or data sources at all — it has to be resolvable before the rest of the configuration is even loaded, so var.bucket_name simply isn't available there. The real mechanism is partial configuration: leave the backend's arguments blank or omitted in the .tf file, and supply the actual values with -backend-config=<file> (or repeated -backend-config="key=value" flags) at terraform init time — so the code stays identical across environments, only the init-time input changes.

Step 7 — run it end to end

From the capstone-stack/ folder:

terraform init
# watch it discover the local module (Initializing modules...)
# and download the random + local provider plugins

terraform plan
# read the resource addresses: module.env_stack["dev"].random_pet.name,
# module.env_stack["staging"]..., module.env_stack["prod"]...
# plus local_file.manifest, and its precondition passing silently

terraform apply
# type: yes

terraform output generated_names
# { dev = "...", staging = "...", prod = "..." }

cat generated/manifest.txt
# dev = ...
# staging = ...
# prod = ...

terraform test
# expect both run blocks in tests/stack.tftest.hcl to report success —
# one_generated_name_per_environment applies real resources then checks
# the count; rejects_empty_environment_list expects (and gets) a failure

terraform destroy
# type: yes

Then try breaking it on purpose: temporarily set default = [] on var.environments in variables.tf and run terraform plan again. You should see the precondition's error_message stop the plan cold — the exact same mechanism tests/stack.tftest.hcl already proved automatically. Set the default back to your real list afterward.

What to put in your project README

Same discipline as every project in a real portfolio: code alone doesn't explain itself. Use this structure, filled in with what your run actually produced:

## Capstone: End-to-End Terraform Stack

**Problem statement**
Provision a small, named "stack" of resources per environment
(dev/staging/prod), from a single variable-driven list, in a way
that's structured to scale to a real team workflow later.

**Approach**
- Root config calls a reusable child module (modules/env-stack)
  once per entry in var.environments, via for_each — not count,
  so removing one environment never touches the others.
- Local backend, structured for a partial-configuration swap to a
  real remote backend (S3/GCS/Azure) with no change to the .tf files.
- A precondition on local_file.manifest refuses to plan against an
  empty environments list.
- tests/stack.tftest.hcl asserts the right output count on apply,
  and proves the precondition actually fires on an empty list.

**What each part demonstrates**
- for_each over a variable-driven list (Lesson 11)
- lifecycle precondition as a guardrail, not just a rule (Lesson 12)
- state + backend structured for a future remote swap (Lessons 13-14)
- a reusable child module, called for_each instead of by hand (17-20)
- terraform test with both an apply-based and a plan-based run,
  including expect_failures (Lesson 27)

**What I'd change for real production**
- Swap random_pet/local_file for real provider resources (aws,
  google, azurerm) inside modules/env-stack — the calling pattern
  (for_each, outputs, precondition) doesn't need to change.
- Swap the local backend for a real remote one (S3 + use_lockfile,
  or GCS/azurerm) using -backend-config per environment, per Lesson 14.
- Add sensitive-data handling (Lesson 24) for anything the real
  provider resources generate that shouldn't sit in state in plain
  text, and wire terraform test into CI (Lesson 29).

**Results**
- terraform apply: [paste your actual generated_names output]
- terraform test: [paste your actual pass/fail summary]

Recap
  • The capstone combines Lessons 1–33 into one working project: a root config calling a reusable child module for_each over a variable-driven environment list, a local backend structured for a future remote swap, an aggregated output, a lifecycle precondition guardrail, and a .tftest.hcl test suite — all on the free random/local providers.
  • for_each on a module block behaves exactly like for_each on a resource — keyed by name, not position, so removing one environment never touches the others.
  • A backend block can never reference var.* — the real mechanism for environment-specific backend config is partial configuration via -backend-config at terraform init, not a variable.
  • A lifecycle precondition (Lesson 12) can guard an entire stack, not just one resource's own inputs — and expect_failures in a test file (Lesson 27) is how you prove that guardrail actually fires, not just that it compiles.
  • A capstone belongs in a real GitHub repo with a README written the same way as every other project in this course: problem, approach, what it demonstrates, what you'd change for production, and your own actual results.
