Policy as code (Sentinel/OPA)

You now have two real safety nets. Lesson 26 taught you to actually read a terraform plan before approving it — a human check. Lesson 29 wired that into a CI/CD pipeline, so nothing gets applied without passing through review and automation. Both are genuinely good. Both also share the same weak point: they depend on a person, or a pipeline someone configured, to remember to check for a specific thing. This lesson is about closing that gap — teaching your organization's rules to a machine so they get enforced every single time, automatically, with nobody needing to remember anything.

The gap plan review and CI don't close

Think about what Lesson 26's plan review actually catches: whatever the reviewer happens to notice. A careful engineer reading a plan will probably catch "wait, this destroys a database" or "this security group looks too open." But plan review doesn't scale to rules like:

  • "No S3 bucket (or GCS bucket, or Azure Storage account) may ever be created with public read access, anywhere, by anyone, in any workspace."
  • "Every resource must carry a cost-center tag so finance can attribute cloud spend."
  • "No production workspace may run terraform apply outside business hours."

A human reviewer can miss these — they're tired, the plan is 400 lines long, the violating resource is buried on line 217, or the reviewer simply doesn't know that rule exists. Lesson 29's CI pipeline runs the same lint and validate steps on every PR, but "does this bucket have public access" isn't something terraform validate checks — validate only confirms your HCL is syntactically and internally consistent, not that it complies with your organization's rules.

Mental model: plan review is a human reading comprehension exercise, applied inconsistently. Policy as code is a rule written once, in a language a machine executes, applied to every plan, every time, with zero chance of "I didn't notice." It doesn't replace review — it catches the class of mistakes review is bad at catching.

Sentinel — HashiCorp's own policy-as-code framework

Sentinel is HashiCorp's policy-as-code framework, built into HCP Terraform (and Terraform Enterprise) as one of the ways to enforce policy on runs. You write policies in Sentinel's own language, using imports like tfplan, tfconfig, and tfrun to inspect the plan, the configuration, and run metadata, then write rules that pass or fail based on what they find — for example, checking every resource in the plan for a required tag, or scanning for any S3 bucket resource with a public-access argument set to true.

Sentinel policies in HCP Terraform run at one of three enforcement levels, and this is the part worth remembering precisely, because it changes what happens on failure:

  • Advisory — a failed policy shows a warning, but the run continues regardless. Good for rolling out a new rule without breaking anyone yet.
  • Soft-mandatory — a failed policy blocks the run, but a user with override permissions can approve it anyway. HCP Terraform logs every override, so there's an audit trail.
  • Hard-mandatory — a failed policy blocks the run, full stop. No override exists. The apply cannot happen until the plan complies.

OPA — a general, cloud-native policy engine

Open Policy Agent (OPA) is a different kind of tool: a general-purpose policy engine, not built by HashiCorp and not specific to Terraform at all. The same OPA engine is used to enforce policy on Kubernetes admission control, API authorization, CI/CD gates — anywhere you need "evaluate this JSON input against a rule, get pass or fail." Policies are written in OPA's query language, Rego.

To use OPA with Terraform, the workflow is: run terraform plan, convert that plan to JSON with terraform show -json, then hand that JSON to OPA (directly via opa eval/opa exec, or through a Terraform-focused wrapper tool like conftest, which is built specifically to run OPA/Rego policies against structured config files including Terraform plan JSON). Your Rego policy queries that JSON — commonly a rule like data.terraform.deny that collects violations into a list. An empty list means the policy passed; anything in the list is a violation, and the calling tool fails the pipeline step.

HCP Terraform actually supports OPA natively as a second policy framework alongside Sentinel — you're not limited to Sentinel just because you're on HashiCorp's platform. Outside HCP Terraform (plain open-source Terraform plus your own CI), OPA/conftest is usually the more common choice precisely because it isn't tied to a HashiCorp product — the same policy engine and the same skillset carry over to Kubernetes and other parts of your stack.

Where policy checks run in the pipeline

Go back to the pipeline you built in Lesson 29: commit, PR, CI runs fmt/validate/plan, a human reviews the plan, then apply. A policy check slots in after the plan is generated but before the apply is allowed to proceed — it needs the plan as input (it's checking what's about to happen, not the raw HCL), and it needs to run early enough to block a bad apply before it touches real infrastructure. In HCP Terraform, this happens automatically as part of the run workflow: HCP Terraform checks the plan against your policy set for every run in a workspace with policies attached. In a self-hosted CI pipeline, you'd add an explicit step — generate the plan, convert to JSON, run conftest test (or your Sentinel/OPA equivalent) against it — positioned between the plan step and the apply step, with the apply step configured to only run if that policy step exits successfully.

Try it — before looking below

Q1. Your org has a rule: "every resource must be tagged with an owner." In the Lesson 29 pipeline (commit → PR → CI: fmt/validate/plan → human review → apply), where exactly would a policy check for this rule run, and why there and not somewhere else?

It runs right after the plan is generated and before apply is allowed — typically as its own CI step (or, in HCP Terraform, automatically as part of the run) sitting between the plan step and the apply step. It has to come after the plan because the check needs the plan's JSON output to see every resource that would actually be created, including their tags — checking raw .tf files wouldn't reliably catch tags set via variables, defaults, or modules. It has to come before apply because the entire point is to stop a non-compliant resource from ever being created, not to notice after the fact.

Q2. A plan violates that owner-tag rule. What should happen next, and what's the difference between how a hard-mandatory Sentinel policy and a soft-mandatory one would each handle it?

The pipeline should block the apply — the policy step should fail (non-zero exit / a non-empty "deny" result), which stops CI from ever reaching the apply job. Under hard-mandatory enforcement, that's final: the run cannot proceed until the offending resource gets an owner tag and a new plan passes. Under soft-mandatory, the run is still blocked by default, but someone with override permission could explicitly approve it anyway — and that override gets logged, so there's a record of who let an untagged resource through and why. Advisory would just warn and let the apply happen regardless, which is why you wouldn't use advisory for a rule you actually want enforced.

Recap
  • Plan review (Lesson 26) and CI (Lesson 29) catch mistakes a person happens to notice — they don't automatically enforce organization-wide rules like "no public buckets" or "every resource needs a cost-center tag."
  • Sentinel is HashiCorp's own policy-as-code framework, built into HCP Terraform, with three enforcement levels: advisory (warn only), soft-mandatory (block, but overridable and logged), hard-mandatory (block, no override).
  • OPA is a general-purpose, vendor-neutral policy engine using the Rego language — usable with Terraform via terraform show -json plus OPA/conftest, and also supported natively inside HCP Terraform.
  • Policy checks run between plan and apply: they need the plan as structured input, and they must be able to block the apply before real infrastructure changes.
