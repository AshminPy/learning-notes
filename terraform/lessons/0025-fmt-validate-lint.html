fmt, validate & linting

Up to Lesson 24 you've focused on writing configuration — resources, variables, modules, sensitive data. Starting here, the course shifts into a new phase: Testing & Validation. Before you ever run plan against real infrastructure, there's a cheap, fast, local checkpoint you should run every single time. This lesson covers the first three tools in that checkpoint: terraform fmt, terraform validate, and the open-source linter tflint.

terraform fmt — canonical style, automatically

HCL, like any language, can be written in inconsistent styles — different indentation, ragged alignment, spacing that varies from person to person. terraform fmt removes that problem entirely. Per the official docs, it "formats Terraform configuration file contents so that it matches the canonical format and style." It rewrites formatting only — indentation, spacing, alignment — never your logic. It cannot break your configuration, because it doesn't touch what the configuration does, only how it looks.

Run it with no arguments in a directory and it scans your .tf files and overwrites them in place with the formatted version, listing which files it changed. Useful flags:

  • -recursive — also format subdirectories, not just the current one
  • -diff — show you the formatting diff instead of (or alongside) applying it
  • -write=false — check without overwriting files
  • -check — the CI-friendly one: don't write anything, just report whether files are already formatted. Exits 0 if everything's clean, non-zero if anything needs formatting

Mental model: fmt is a style referee, not a proofreader. It guarantees every .tf file in a codebase — no matter who wrote it — reads the same way. That matters more than it sounds like: in a team repo, inconsistent formatting creates noisy diffs (a PR that changes one line but "changes" indentation on fifty others) and makes code review harder. Run terraform fmt before every commit as a habit — and wire terraform fmt -check -recursive into CI so nobody can merge unformatted HCL by accident.

terraform validate — catch mistakes before you even plan

Where fmt checks style, validate checks substance — but only the substance Terraform can verify without leaving your laptop. The official docs describe it as running "checks that verify whether a configuration is syntactically valid and internally consistent," including "correctness of attribute names and value types."

The critical line, worth memorizing: validate explicitly "does not validate remote services, such as remote state or provider APIs." It never contacts AWS, GCP, Azure, or any backend. It's a purely local, offline check — it reads your .tf files and asks "is this internally coherent HCL?", not "will this actually work against the real cloud?" That's exactly why it's fast, and exactly why it's the second checkpoint, before the (slower, provider-talking) plan step.

Two things worth knowing before you run it:

  • it needs an initialized directory (terraform init first) — though you can init without a real backend using terraform init -backend=false if you only want to validate
  • it's explicitly safe to run constantly — the docs say it's fine as "a post-save check in a text editor or as a test step for a reusable module in a CI system"

What validate catches: a typo'd argument name, a string passed where a number is expected, a reference to something that doesn't exist, mismatched types between a variable and how it's used. What it can't catch: whether an AWS instance type actually exists, whether your credentials have permission to create the resource, whether a name is already taken in the real account. Those only surface later, at plan or apply, because they require talking to the provider.

tflint — the linter that looks further than validate

tflint is a separate, open-source project (terraform-linters/tflint on GitHub) — it is not built into Terraform and not maintained by HashiCorp. It's a "pluggable Terraform linter," built as a framework where "each feature is provided by plugins," and it's actively maintained (thousands of stars, thousands of commits).

The reason it exists alongside validate: validate only checks that your HCL is internally coherent. It has no opinion on whether you're using deprecated syntax, whether you picked an invalid AWS instance type, or whether you declared a variable and never used it — because none of that breaks internal consistency. tflint fills that gap. It catches:

  • deprecated syntax and outdated language features
  • provider-specific mistakes — e.g. an instance type or region that doesn't actually exist for AWS/Azure/GCP
  • unused declarations — variables or locals declared but never referenced
  • naming-convention and best-practice violations, enforceable via its plugin/ruleset system

Mental model: think of the three tools as concentric circles, each one catching problems the last one can't. fmt checks how it looks. validate checks whether the HCL is internally coherent — offline, no provider contact. tflint checks whether it follows sensible, provider-aware practice — still offline, no real changes, but it knows more about AWS/Azure/GCP specifics than core Terraform does. None of the three ever touch real infrastructure. That's exactly why they belong before plan, not after.

The pre-commit habit

Put these three in a fixed order, every time, before you run plan against anything real:

  1. terraform fmt — fix style
  2. terraform validate — catch syntax/type errors, offline
  3. tflint — catch deprecated syntax and provider-specific mistakes, still offline

Only after all three pass should you run terraform plan — the point where Terraform finally talks to the provider and refresh/state get involved (Lesson 13). Catching a typo at step 2 costs you a second. Catching the same typo at plan costs you a slower round trip; catching it at apply against real infrastructure can cost you a lot more.

Try it — before looking below

Q1. You run terraform validate and it passes with no errors. Does that mean terraform apply will definitely succeed? Why or why not?

No. validate only checks that your configuration is syntactically valid and internally consistent — it explicitly does not contact remote services like provider APIs or remote state. Your HCL could be perfectly valid and still fail at apply time for reasons validate can't see: bad credentials, a resource name already taken, an instance type that doesn't exist in that region, insufficient permissions, and so on.

Q2. Why would a team run tflint at all if terraform validate already passes? What does it catch that validate doesn't?

validate only checks internal consistency of the HCL — it has no opinion on style/practice questions. tflint is a separate, provider-aware linter that catches things that are syntactically valid but still wrong or risky: deprecated syntax, provider-specific mistakes (like an AWS instance type that doesn't actually exist), unused variable declarations, and naming/best-practice violations — none of which break "internal consistency," so validate lets them through.

Hands-on: write it broken, fix it in three steps

Create a fresh scratch folder and a file called main.tf with this deliberately messy, deliberately wrong snippet — bad indentation and a type error (a string passed where count needs a number):

resource "random_pet" "example" {
    length = "3"
        separator="-"
count = "two"
}
  • Run terraform init (or terraform init -backend=false if you just want validate to work without a real backend).
  • Run terraform fmt -diff. Watch it show you the indentation/spacing it wants to fix — the ragged length/separator lines, the missing spaces around =. Run terraform fmt (no flags) to actually apply the fix, then open the file — it's now cleanly aligned.
  • Notice fmt did not touch count = "two" — that's a logic problem, not a style problem, and fixing logic isn't fmt's job.
  • Run terraform validate. It should now report an error on the count argument — a string ("two") where a number is required. This is exactly the kind of error validate is built to catch, fast, without ever touching a provider.
  • Fix it: change count = "two" to count = 2. Run terraform validate again — it should now pass clean.
  • If you have tflint installed, run it too, and compare: on this tiny snippet it likely won't find anything extra, which is expected — its value shows up on real provider-specific resources (like aws_instance with a bad instance type), not on a generic random_pet example.

This is the muscle memory the lesson is really teaching: format, then validate, before you ever let plan near real infrastructure.

Recap
  • terraform fmt rewrites HCL to canonical style only — never logic. Use -check in CI to enforce it without auto-writing.
  • terraform validate checks syntax and internal consistency locally — it never contacts a provider or remote state, so a clean validate does not guarantee a clean apply.
  • tflint is a separate, open-source, provider-aware linter that catches deprecated syntax and provider-specific mistakes that validate can't see.
  • Habit: fmt, then validate, then tflint — every time, before you ever run plan against real infrastructure.
