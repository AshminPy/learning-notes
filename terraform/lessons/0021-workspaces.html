Terraform workspaces

So far, every folder of .tf files you've run has had exactly one state file, tracking exactly one set of real infrastructure. What if you want the same config to manage more than one instance of that infrastructure — say, a throwaway copy for testing a change, sitting alongside the real one? Terraform has a built-in feature for exactly that: workspaces. This lesson covers what they are, the CLI commands, and — just as important — where HashiCorp itself says not to reach for them. That last part sets up Lesson 22, where we compare workspaces against the alternative for managing dev/stage/prod.

What a workspace actually is

Recall from Lesson 13: state is just a JSON file that maps your config's resource blocks to real-world infrastructure. A workspace is nothing more exotic than a separate state file for the same configuration. Every Terraform working directory starts with one workspace already, called default. When you create a new workspace, Terraform doesn't touch your .tf files at all — it just creates a fresh, empty state file and starts tracking a second, independent set of infrastructure under the same code.

Locally, you can see this happen on disk. Terraform stores non-default workspace states in a directory called terraform.tfstate.d, one subfolder per workspace. The docs are explicit that this directory should be treated the same way as a local terraform.tfstate file — same sensitivity, same "never commit it" rule from Lesson 13. With a remote backend (Lesson 14), the workspace name gets folded into the state path on the backend instead, but the principle is identical: one workspace, one isolated state.

Mental model: your .tf files are the recipe. State is the specific cake you baked from it. A workspace lets you bake a second cake from the exact same recipe, without the two cakes getting mixed up — plan and apply in workspace A never look at workspace B's state.

The CLI commands

All workspace operations live under terraform workspace:

  • terraform workspace list — show every workspace that exists for this config, with a * marking the one you're currently in
  • terraform workspace new <name> — create a new workspace and switch to it immediately (e.g. terraform workspace new staging)
  • terraform workspace select <name> — switch to an existing workspace
  • terraform workspace show — print the name of the workspace you're currently in
  • terraform workspace delete <name> — remove a workspace (Terraform won't let you delete one that still has resources tracked in its state)

Whichever workspace is currently selected is the one every subsequent plan, apply, and destroy in that directory operates on. There's no flag to bolt onto apply to target a different workspace — you select first, then run your command.

Varying behavior with terraform.workspace

Having a separate state per workspace is only half the story — most of the time you also want your config to behave slightly differently depending on which workspace is active. Terraform exposes the current workspace name as an expression: terraform.workspace. You can use it anywhere an interpolation is allowed, the same as any other expression you've used since Lesson 3.

Two patterns straight from HashiCorp's own docs:

count = terraform.workspace == "default" ? 5 : 1

— run 5 instances in default, but only 1 in any other workspace (handy for a cheap, single-instance test copy).

tags = {
  Name = "web - ${terraform.workspace}"
}

— bake the workspace name straight into a resource's tag, so web - staging and web - default are visibly distinguishable even though they came from the same resource block.

Where workspaces are a poor fit — read this before Lesson 22

It's tempting, the first time you see this feature, to think "great — I'll make a dev workspace, a staging workspace, and a prod workspace, and I'm done with environments." HashiCorp's own documentation pushes back on that directly. Quoting the official guidance: "Workspaces alone are not a suitable tool for system decomposition," and they're explicitly called out as unsuitable for situations needing "strong separation between multiple deployments...serving different development stages or different internal teams," especially because "the backend for each deployment often has different credentials and access controls." The state-workspaces reference page adds a second, related warning: workspaces "are not appropriate for system decomposition or deployments requiring separate credentials and access controls."

Think about why, using the mental model above: a workspace changes which state file Terraform reads, but it's still the exact same .tf config, the exact same backend, the exact same provider credentials. That's perfect when your "different instances" really are near-identical and low-risk — a temporary feature-branch test environment, a handful of interchangeable regional copies. It falls apart the moment prod needs something meaningfully different from dev: bigger instance sizes, extra modules, a locked-down backend only a subset of engineers can write to, stricter access controls. terraform.workspace == "prod" ? big : small conditionals scattered through your config get unreadable fast, and — more seriously — a typo that selects the wrong workspace means someone's laptop just ran apply against prod using the same credentials as dev, because workspaces don't separate credentials at all.

Rule of thumb going into Lesson 22: workspaces are for many similar, low-risk copies of one config. When environments need genuinely different configuration, sizing, modules, or access control — which prod almost always does — HashiCorp's own recommendation is separate configurations with distinct backends, built from reusable modules (the module patterns from Lesson 20). That's exactly the comparison Lesson 22 walks through in full.

Try it — before looking below

Q1. You run terraform workspace new staging then terraform apply. What happens to your existing default workspace's infrastructure and state?

Nothing happens to it. Creating and switching to staging gives you a brand-new, empty state file for that workspace — default's state and the real infrastructure it tracks are completely untouched. The apply you just ran only creates resources tracked in staging's state, using the same .tf config.

Q2. Why does HashiCorp specifically warn against using workspaces to separate dev, staging, and prod, even though it seems like the obvious use case?

Because a workspace only swaps which state file is active — the config, backend, and provider credentials stay identical across every workspace. Real environments usually need more than that: different resource sizes, different modules, and different access controls (prod often needs a locked-down backend only some people can write to). Workspaces give you none of that separation, so a mistake (e.g. selecting the wrong workspace) can apply prod-shaped changes using dev's exact same credentials.

Hands-on: create a staging workspace and compare state

Use the same random_pet example from earlier lessons (resource "random_pet" "example" {} in main.tf).

  • run terraform workspace list — you should see just * default
  • run terraform workspace new staging — Terraform creates the workspace and switches you into it automatically
  • run terraform apply, type yes — this creates a pet inside the staging workspace's own state
  • run terraform workspace show — confirms you're in staging
  • run terraform workspace select default, then terraform apply, type yes — this creates a separate pet, tracked in default's state
  • run terraform workspace list again — you'll see both workspaces, with * marking whichever one you last selected
  • look inside the terraform.tfstate.d folder that appeared next to your .tf files — you'll find a staging subfolder with its own terraform.tfstate, completely separate from the default one in your working directory
  • clean up both: terraform destroy while in default, then terraform workspace select staging and terraform destroy again

Two pet names, from one config, tracked in two independent state files you can see side by side on disk — that's the entire mechanism.

Recap
  • A workspace is a separate state file for the same config — default exists from the start; terraform workspace new <name> adds more, stored locally under terraform.tfstate.d.
  • Manage workspaces with terraform workspace list / new / select / show / delete. Whichever is selected is what plan/apply/destroy act on.
  • The terraform.workspace expression lets a single config behave differently per workspace (e.g. count, tags).
  • HashiCorp's own guidance: workspaces suit many near-identical, low-risk copies of one config — not environments needing different sizing, modules, or access controls (like real prod vs dev). That's the setup for Lesson 22.
