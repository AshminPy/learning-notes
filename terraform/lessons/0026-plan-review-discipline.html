Plan review discipline

Back in Lesson 5 you got a callout: "read the plan before you type yes — this is the single most important safety habit in all of Terraform," with a promise that Lesson 26 would build on it. This is that lesson. Lesson 25 gave you the offline checkpoint — fmt, validate, tflint — that runs before a plan even talks to a provider. This lesson is about the step right after: once terraform plan does talk to the provider and hands you real output, how do you actually read it so it catches mistakes instead of rubber-stamping them?

The symbol legend, properly this time

You've seen pieces of this already — + in Lesson 5, -/+ in Lesson 12. Here's the complete set, confirmed against HashiCorp's own plan output and tutorials:

SymbolMeaningWhat Terraform will do
+createA resource in config has no matching entry in state — build it new.
-destroyA resource in state has no matching block in config — tear it down.
~update in-placeThe resource stays; only some of its attributes change on the existing object.
-/+destroy and then create replacementThe default replace order: old object destroyed first, then a new one built. There's a gap where nothing exists.
+/-create replacement and then destroyReplace with create_before_destroy = true (Lesson 12): new object built first, old one destroyed only after it succeeds.

The two single-character symbols are the ones beginners read correctly. The two combined ones — -/+ and +/- — are where most plan-review mistakes actually happen, because at a glance they both just look like "some kind of change," and it's easy to skim past the fact that a destroy is one half of that symbol.

-/+ — the one that's most dangerous to miss

A "replace" happens whenever you change an argument that the provider can't update on the live object — the only way to apply that change is to destroy the existing resource and create a new one. Terraform calls this out explicitly in the plan, on the line right above the resource block:

# aws_instance.web must be replaced
-/+ resource "aws_instance" "web" {
      ~ ami           = "ami-0old11111" -> "ami-0new22222" # forces replacement
        id            = "i-0abc123" -> (known after apply)
        instance_type = "t3.micro"
    }

Plan: 1 to add, 0 to change, 1 to destroy.

Two things worth noticing in that output. First, the comment # forces replacement next to the changed argument — Terraform tells you exactly which attribute triggered the replace, so you don't have to guess. Second, the summary line: Plan: 1 to add, 0 to change, 1 to destroy, not "1 to change." A replace is not a change — it's a destroy and a create, counted as both, even though it reads to a skimming eye like a routine update to one resource.

Mental model, tying back to Lesson 12: by default, a replace is destroy-then-create — there's a moment where the resource doesn't exist at all. create_before_destroy = true flips the order and the symbol to +/-, so the new object exists before the old one is torn down. Seeing -/+ in a plan for anything users depend on — a running server, a database, a DNS record — is exactly the moment to stop and ask: "should this have create_before_destroy set, and does it?" If the resource doesn't have that lifecycle rule, -/+ means real downtime, not just a diff.

The costly mistake: skimming because "it'll probably be fine"

Here's the single most expensive habit beginners fall into with plan. The output can run long — twenty, fifty, a hundred lines for a config with several resources — and it's tempting to jump straight to the last line, see Plan: 3 to add, 1 to change, 1 to destroy, decide that roughly matches what you expected, and type yes. Most of the time nothing bad happens. That's exactly what makes the habit dangerous: it works often enough to feel safe, right up until the one time it doesn't — the day the 1 to destroy is your production database, not the throwaway test resource you assumed it was.

Best practice — read every resource line, not just the count: the summary line Plan: X to add, Y to change, Z to destroy tells you how many, never which. A plan reading 1 to add, 0 to change, 1 to destroy is completely consistent with two totally different realities: a harmless rename, or your production database about to be dropped and rebuilt empty. The count is the same either way. The only way to tell them apart is to actually read the # resource_type.name will be <action> line for every single resource listed above the summary — not just the resources you expected to see, but confirming nothing unexpected showed up too. Make this a fixed habit before every yes, not something you do only when the numbers look surprising — by the time you notice a number looks wrong, you're already trusting the numbers more than the detail.

terraform plan -out=tfplan + terraform apply tfplan — apply exactly what you reviewed

There's a gap in the plain terraform plan then terraform apply workflow you've used since Lesson 5: those are two separate commands, run at two separate moments. apply on its own does not remember the plan you just read — per HashiCorp's own docs, running apply without a saved plan file "automatically generates a new plan and prompts for you to approve it." If anything changed state in between — a teammate applied their own config, a resource drifted, an automated process ran — the plan apply actually executes can differ from the one you reviewed with your own eyes.

The fix is to save the plan to a file and apply that exact file:

$ terraform plan -out=tfplan
...
Saved the plan to: tfplan

To perform exactly these actions, run the following command to apply:
    terraform apply "tfplan"

$ terraform apply tfplan
...
Apply complete! Resources: 1 added, 0 changed, 1 destroyed.

-out=tfplan writes the generated plan to an opaque file. terraform apply tfplan then applies precisely that saved plan — no re-computation, no fresh round-trip to the provider to see if anything changed underneath you. What you reviewed is, byte for byte, what gets executed.

Best practice: in any workflow where a human reviews a plan before approving it — which, per Lesson 5's earlier promise, includes team pull-request workflows where a plan gets posted as a PR comment for a teammate to review — always review a saved plan file, and apply that same file. Reviewing one plan and then running a bare terraform apply (which silently recomputes a new one) means the thing that actually executes was never the thing anyone looked at. This is exactly how CI/CD pipelines for Terraform are built: a plan stage that saves -out, a human or automated approval gate, then an apply stage that applies that exact saved artifact.

Try it — before looking below

Q1. A plan shows -/+ resource "aws_db_instance" "prod" with the comment # forces replacement next to a storage_type argument you changed. What does this symbol actually mean is about to happen, and what Lesson 12 setting would change the order (and the symbol) if it were applied to this resource?

It means the database will be destroyed first, then a brand-new one created to replace it — not updated in place. Changing storage_type isn't something the provider can apply to the live object, so Terraform has no choice but to replace it. Adding lifecycle { create_before_destroy = true } (Lesson 12) would flip the order to create-then-destroy and change the symbol to +/- — though for a database, the real question to ask first is whether this attribute should be changing at all, since even create-before-destroy means a brand-new, empty database unless data migration is handled separately.

Q2. Why is Plan: 2 to add, 3 to change, 1 to destroy not enough information to safely type yes, even if those numbers match what you expected?

The summary line tells you counts, not identities. "1 to destroy" is consistent with a harmless resource you meant to remove, or with a critical resource you never intended to touch — the number alone can't distinguish them. You have to read the actual # resource_type.name will be <action> line for every resource in the plan to confirm the specific resources being destroyed, replaced, or changed are the ones you actually intended.

Q3. You run terraform plan -out=tfplan, review it carefully, then five minutes later a teammate applies an unrelated change to the same state. You then run terraform apply tfplan. Does your apply pick up your teammate's change, or apply exactly what you reviewed?

It applies exactly what you reviewed — the saved plan file is a frozen snapshot, not a live recomputation. This is precisely why -out plus applying that saved file is safer than a bare terraform apply: a bare apply would regenerate a fresh plan against the now-changed state, which could differ from what you approved. (In practice, if the underlying state changed enough to make the saved plan invalid, Terraform will refuse to apply it rather than silently apply something else — but the discipline is the same either way: what you reviewed is what should run.)

Hands-on: spot the hidden replace

Go back to the random_pet rename scenario from Lesson 16. Suppose your main.tf currently has two resources:

resource "random_pet" "example" {}

resource "random_pet" "sidecar" {
  length = 2
}

You do a small refactor: rename example to buddy for clarity, and bump sidecar's length from 2 to 3 because a teammate asked for slightly longer names. You forget the moved block from Lesson 16. Run terraform plan, and this is what you'd see:

$ terraform plan

Terraform used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
  -/+ destroy and then create replacement

Terraform will perform the following actions:

  # random_pet.buddy will be created
  + resource "random_pet" "buddy" {
      + id        = (known after apply)
      + length    = 2
      + separator = "-"
    }

  # random_pet.example will be destroyed
  - resource "random_pet" "example" {
      - id        = "climbing-mudfish" -> null
      - length    = 2 -> null
      - separator = "-" -> null
    }

  # random_pet.sidecar must be replaced
-/+ resource "random_pet" "sidecar" {
      ~ id        = "quick-marmot" -> (known after apply)
      ~ length    = 2 -> 3 # forces replacement
        separator = "-"
    }

Plan: 2 to add, 0 to change, 2 to destroy.

Look at the summary line by itself: 2 to add, 0 to change, 2 to destroy. If you only glanced at that and thought "yeah, two adds and two destroys sounds about right for a rename plus a tweak," you'd approve it — and you'd be wrong about what actually happens. The rename correctly needs a destroy-and-create (that's the whole point of the missing moved block). But sidecar was supposed to be a simple, harmless length change — a one-line tweak — and it's actually a full destroy-and-recreate too, because length forces replacement on random_pet. Read only the count, and both destroys look identical and equally expected. Read the individual resource lines, and sidecar's # random_pet.sidecar must be replaced plus the # forces replacement comment on length tells you this "small tweak" is not the in-place update you assumed.

Q4. In the plan above, which resource's action would most likely surprise someone who only skimmed the summary line, and why?

random_pet.sidecar. The rename of example to buddy is expected to show up as a destroy-plus-create, because no moved block was added. But sidecar was only supposed to be a length tweak — something that sounds like a routine in-place update — and it's actually a full replace, because length forces replacement. The summary line's "2 to destroy" hides this: it makes the intentional rename-destroy and the surprise replace-destroy look identical. Only reading the # random_pet.sidecar must be replaced line and its # forces replacement comment reveals it.

Fix it two ways, matching Lesson 16: add a moved block for the rename (random_pet.example → random_pet.buddy), which removes that pair from the plan entirely. The sidecar replace, though, isn't a mistake to "fix" — length genuinely can't be changed in place on a random_pet, so a replace is the correct plan. The discipline this hands-on teaches isn't "make every plan show zero destroys" — it's "know, resource by resource, exactly what's about to happen, and confirm each one is a replace you actually intended before you type yes."

Recap
  • Five symbols: + create, - destroy, ~ update in-place, -/+ destroy-then-create (default replace), +/- create-then-destroy (replace with create_before_destroy, Lesson 12).
  • -/+ is the one most dangerous to miss — it reads like "some kind of change" but means the resource is destroyed and rebuilt, often triggered by an argument that forces replacement (look for the # forces replacement comment).
  • The costliest beginner habit: trusting the Plan: X to add, Y to change, Z to destroy summary line alone. It tells you counts, never identities — always read every individual resource line before approving.
  • terraform plan -out=tfplan then terraform apply tfplan applies exactly the plan you reviewed, instead of letting a bare apply silently recompute a fresh one against whatever state looks like by the time you run it.
