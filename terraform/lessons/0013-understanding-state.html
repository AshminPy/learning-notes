Understanding Terraform state

You've typed terraform.tfstate in passing since Lesson 5, and even referenced it when talking about local names in Lesson 8. It's time to stop treating it as background noise and actually open it up. This lesson is conceptual — no new resource types, no new syntax — but it's one of the most important lessons in the whole course. Almost every confusing Terraform error, and almost every team workflow decision (Lesson 14 onward), comes back to how state works.

What state actually is

The moment you run terraform apply for the first time in a folder, Terraform creates a file called terraform.tfstate right next to your .tf files. Strip away the mystery: it's a JSON text file. Nothing more exotic than that — you could open it in any text editor and read it, the same way you'd read a .json config file for any other tool.

What's inside that JSON is a mapping: for every resource block in your config, an entry recording which real-world object it corresponds to. random_pet.example in your .tf file maps to an entry in state that says "this one's actual generated value is climbing-mudfish." aws_instance.web would map to an entry recording the real AWS instance ID, something like i-0abc123.

Why Terraform needs this at all

Here's the problem state solves. When you run terraform plan, Terraform has to answer: "what needs to change?" To answer that, it needs to know which real, already-existing infrastructure corresponds to which resource block in your config. But there's no reliable way to ask a cloud provider's API "which of your resources belong to this Terraform config?" — providers don't know Terraform exists. Tags could theoretically identify ownership, but not every resource type or every provider supports tags, so it's not a general solution.

So Terraform keeps that mapping itself, in state. The official docs put it plainly: Terraform uses this mapping to know that a resource block "represents a real world object with the instance ID i-abcd1234." Without state, Terraform would have no memory between runs — every plan would be starting from zero, unable to tell "already created" apart from "needs creating."

Mental model: state is Terraform's memory. Your .tf files describe what you want — they're stateless, they don't remember anything about previous runs. State is the only place Terraform records what it has actually done. Delete your config and Terraform forgets nothing about the past; delete your state and Terraform forgets everything it ever built, even though the real infrastructure is still sitting there in the cloud.

The three-way comparison

This is the mental model that makes plan and apply click. Every time you run terraform plan, Terraform is comparing three things, not two:

  1. Your configuration — the .tf files, what you want to exist
  2. The state file — what Terraform last recorded as existing
  3. Real infrastructure — what's actually out there right now (Terraform checks this by querying the provider, a step called "refresh")

Out of that three-way comparison, Terraform works out a plan: anything in config but not in state gets created; anything in state but not in config gets destroyed; anything where config and real infrastructure disagree gets updated to match config. If real infrastructure has drifted from state (someone changed something by hand in the console), that shows up too — Terraform will plan to bring it back in line with config.

State also carries dependency metadata — which resource depends on which. You saw in Lesson 8 that Terraform infers creation order from references in your config (implicit dependencies). But when you delete a resource block entirely, that reference is gone — the order can no longer be read from the config, because the config no longer mentions it. State is what remembers "this one used to depend on that one," so terraform destroy can still tear things down in a safe order.

What's actually stored inside

Each resource's entry in state typically holds:

  • the resource's real-world identity (its provider-assigned ID)
  • every attribute value the provider returned — not just the ID, but things like IP addresses, ARNs, generated passwords, connection strings
  • dependency metadata, so Terraform knows relationships even after config changes
  • a small amount of internal bookkeeping Terraform uses to detect drift and plan changes efficiently

Critical security callout: because state stores every attribute a provider returns, it can contain genuinely sensitive values — initial database passwords, API tokens, TLS private keys, anything a resource generates or receives as an argument. The official HashiCorp docs are direct about this: state and plan files "contain detailed information about your infrastructure, including resource attributes and metadata that can contain sensitive values, such as initial database passwords or API tokens," and locally, "Terraform stores your state in a plaintext file, which includes any secret values you defined in your configuration." Never commit terraform.tfstate to git, and never share it carelessly — treat it exactly like you'd treat a file full of passwords, because in practice, it often is one. Lesson 14 covers remote backends, which is the real fix for this (encryption at rest, access control, no plaintext file sitting in your repo).

Try it — before looking below

Q1. Terraform can't just ask AWS or GCP "which resources belong to my config" — why not, and what does Terraform use instead to know the answer?

Cloud provider APIs have no concept of Terraform or its configs — they just manage resources, with no reliable universal way (like tags) to mark "this belongs to config X" across every resource type and provider. Instead, Terraform keeps its own record: the state file, which maps each resource block to the real-world object it created.

Q2. You delete a resource block from your .tf file entirely, then run terraform apply. The real infrastructure still exists in the cloud. What does Terraform do, and how does it know to do it, given the block is no longer in your config?

Terraform plans to destroy that real resource. It knows to, because state still has an entry for it — config says "this shouldn't exist," state says "this exists," and Terraform reconciles the two by proposing a delete. Without state remembering that entry, Terraform would have no way to know that resource was ever under its management.

Hands-on: open the state file yourself

Go back to the random_pet example from earlier lessons (same folder, same main.tf with resource "random_pet" "example" {}).

  • run terraform apply, type yes, if you don't already have a live pet from a previous lesson
  • now — do not use any terraform command. Open terraform.tfstate directly in a plain text editor (VS Code, nano, whatever you have)
  • read the raw JSON. Find the resources array, find the entry for random_pet.example, and look inside its instances — you'll see an attributes object with an id field holding your actual pet name, e.g. "id": "climbing-mudfish"
  • notice there's no magic here — it's a plain, readable, mildly verbose JSON file, same as any config file you've opened for any other tool
  • run terraform destroy, type yes, to clean up when you're done looking

This is the whole point of the exercise: seeing "this is just a file" with your own eyes removes the mystery. State isn't a black box Terraform hides from you — it's a JSON file sitting right there in your folder, and now you know exactly what's in it and why it matters enough to never commit to git.

Recap
  • State (terraform.tfstate) is a plain JSON file, created after your first apply, that maps your config's resources to real-world infrastructure IDs.
  • Terraform needs it because cloud provider APIs can't tell you which resources belong to which config — Terraform has to track that mapping itself.
  • plan/apply work by a three-way comparison: your configuration, the state file, and real infrastructure.
  • State can contain sensitive values (passwords, tokens, keys) in plaintext — never commit it to git or share it carelessly.
