Lifecycle rules & custom conditions

By default, Terraform decides how to change a resource for you: update in place if it can, destroy-and-recreate if it can't. Most of the time that's fine. This lesson covers the escape hatch — the lifecycle block, nested inside a resource block — for the cases where you need to override that default behavior: change the order of a replace, block a destroy outright, tell Terraform to stop caring about a specific attribute, or assert your own rules about what a good plan or a good result looks like.

Where lifecycle sits

resource "TYPE" "LOCAL_NAME" {
  argument = "value"

  lifecycle {
    # rules go here
  }
}

lifecycle is not an argument on the resource — it's a nested block with its own fixed set of settings. It doesn't configure the infrastructure itself; it configures how Terraform is allowed to change that infrastructure.

create_before_destroy — build the replacement first

Some changes can't be done in place — Terraform has to destroy the old resource and create a new one (a "replace"). By default, that happens in the order the words suggest: destroy old, then create new. For anything users depend on — a server, a load balancer target, a DNS record — that ordering means a gap where nothing exists at all.

resource "aws_instance" "web" {
  ami           = "ami-0abcd1234"
  instance_type = "t3.micro"

  lifecycle {
    create_before_destroy = true
  }
}

Set create_before_destroy = true and Terraform flips the order: create the new resource first, wait for it to succeed, then destroy the old one. There's a moment where both exist side by side, but never a moment where neither does. This is a named objective on the Terraform Associate exam, so remember the plain-English reason, not just the setting name: it exists to avoid downtime during a replace.

Mental model: default replace is "move out, then move in" — there's a night with no roof. create_before_destroy is "move into the new place, then give up the old lease" — never homeless, briefly paying for two.

Two consequences worth knowing before you flip this on:

  • Anything that must be unique (a name, an IP, a port) will briefly need two valid values — the old resource and the new one existing at once. If your config hard-codes a name that can't be duplicated, the create step fails before the old one is ever destroyed.
  • Terraform automatically carries this ordering into resources that depend on the one you set it on, so a replace doesn't tear down something a still-live dependency needs.

prevent_destroy — a safety guardrail

resource "aws_db_instance" "prod" {
  # ...

  lifecycle {
    prevent_destroy = true
  }
}

With prevent_destroy = true, any plan that would destroy this resource — a manual terraform destroy, or an ordinary change that Terraform can only achieve by replacing it — is rejected with an error instead of proceeding. It's a deliberate speed bump against the single most expensive kind of mistake: deleting a production database or its data by accident.

Best practice: put prevent_destroy = true on anything where an accidental delete would be a genuinely bad day — production databases, stateful storage, anything holding data you can't regenerate. It costs nothing day to day and only ever gets in the way on the one occasion you'd actually want the pause.

It's a guardrail, not a lock: it only stops Terraform from planning the destroy while the resource block still exists in your config. If someone removes the resource block entirely, that removal is itself the change, and prevent_destroy won't stop it. Treat it as "make destroying this resource require a deliberate, reviewable code change," not "this can never be destroyed."

ignore_changes — stop caring about drift on specific attributes

Sometimes something outside Terraform legitimately changes an attribute after creation — a teammate adds a tag in the AWS console, an autoscaler changes an instance count, a CI pipeline stamps a build tag on. Left alone, Terraform sees that as drift and wants to "fix" it back on every plan. ignore_changes tells Terraform: for these specific attributes, don't try to correct drift.

resource "aws_instance" "web" {
  ami           = "ami-0abcd1234"
  instance_type = "t3.micro"
  tags = {
    Name = "web"
  }

  lifecycle {
    ignore_changes = [tags]
  }
}

Take a list of attribute names — or the special value all to ignore every attribute on the resource after creation. Listed attributes are still used normally when the resource is first created; after that, Terraform stops comparing them against your config, so changes made outside Terraform survive future plans without being reverted.

Best practice: reach for all rarely and deliberately — it silences drift detection for the whole resource, which can hide real problems, not just the one field you meant to ignore. Prefer naming the exact attribute (tags, or a specific key like tags["LastDeployedBy"]) over ignoring everything.

Custom conditions — precondition and postcondition

The three settings above change how Terraform applies a change. precondition and postcondition are different: they let you assert something must be true, and fail the run with your own message if it isn't. Both are blocks nested inside lifecycle, on a resource or data block:

precondition {
  condition     = <boolean expression>
  error_message = "<string shown when condition is false>"
}

postcondition {
  condition     = <boolean expression>
  error_message = "<string shown when condition is false>"
}

condition must evaluate to a boolean, and error_message is required on both — it's what shows up in the failed plan or apply. The difference between the two is timing:

preconditionpostcondition
When it runsAfter the plan is generated, before the resource is created or changedAfter the resource has been created or changed
What it checksSomething must be true before Terraform proceeds — an assumption about inputsSomething must be true after Terraform acts — a promise about the result
Can reference selfNoYes — the resource/data source's own resulting attributes

A precondition catches a bad input before Terraform wastes an apply on it — for example, refusing to use an AMI that isn't the right CPU architecture:

resource "aws_instance" "example" {
  instance_type = "t3.micro"
  ami           = data.aws_ami.example.id

  lifecycle {
    precondition {
      condition     = data.aws_ami.example.architecture == "x86_64"
      error_message = "The selected AMI must be for the x86_64 architecture."
    }
  }
}

A postcondition checks the actual result, and can use self to read the resulting attributes of the very resource or data source it's attached to — something a precondition can't do, since those attributes don't exist yet at precondition time:

data "aws_ami" "example" {
  most_recent = true
  owners      = ["self"]
  filter {
    name   = "name"
    values = ["myami-*"]
  }

  lifecycle {
    postcondition {
      condition     = self.tags["Component"] == "nomad-server"
      error_message = "tags[\"Component\"] must be \"nomad-server\"."
    }
  }
}

Mental model: a precondition is a bouncer at the door — checks you before you're let in. A postcondition is a receipt check on the way out — confirms what you actually got matches what was promised. Both stop the run and show your error_message if the check fails; neither one changes what Terraform does, they only decide whether Terraform is allowed to consider the result acceptable.

Try it — before looking below

Q1. You add prevent_destroy = true to a resource. A teammate later deletes that resource's entire block from the .tf file and runs terraform apply. Does prevent_destroy stop this?

No. prevent_destroy only blocks a plan that would destroy the resource while its resource block (and the lifecycle setting on it) still exists in config. Once the block itself is removed, there's no lifecycle rule left to enforce anything — the removal goes through.

Q2. What's the real difference between ignore_changes and prevent_destroy — aren't they both just "protect this resource"?

Different jobs. ignore_changes stops Terraform from reverting drift on specific attributes — the resource can still be destroyed or replaced, Terraform just stops "fixing" those fields back to match config. prevent_destroy stops the whole resource from being destroyed at all. You can use either alone, or both together on the same resource.

Q3. Why can a postcondition reference self.tags["Component"] but a precondition can't reference self at all?

A precondition runs before the resource is created or changed — its own resulting attributes don't exist yet, so there's nothing for self to point to. A postcondition runs after the action, once the resource actually has real attribute values, so self can read them.

Hands-on: watch create_before_destroy change the apply order

Same folder as previous lessons. Start with a plain resource that forces a replace when changed — random_pet's length triggers a replace, same as you saw in Lesson 10:

resource "random_pet" "example" {
  length = 2
}

Walk through the default behavior first:

  • run terraform apply, type yes — note the pet name it generates
  • change length = 2 to length = 3
  • run terraform plan and read the plan output carefully — it shows -/+ resource "random_pet" "example", meaning destroy, then create, in that order (Terraform prints -/+ for exactly this reason)

Now add the lifecycle block:

resource "random_pet" "example" {
  length = 3

  lifecycle {
    create_before_destroy = true
  }
}
  • run terraform plan again — the symbol changes to +/-, meaning create, then destroy — the order is now flipped
  • run terraform apply, type yes
  • run terraform destroy, type yes, to clean up

What actually changed, step by step:

  1. Default (no lifecycle block): Terraform destroys random_pet.example first, freeing its state slot, then creates a brand new one with length = 3. Between those two steps, as far as your config is concerned, the resource doesn't exist.
  2. With create_before_destroy = true: Terraform creates the new random_pet.example (new name, new id) first. Only once that succeeds does it destroy the old one. For one brief moment, Terraform's plan is tracking two instances of what will become the same resource address before the old one drops out.
  3. For a throwaway resource like random_pet this doesn't matter much — but picture the same flip on aws_instance.web behind a load balancer: default order means the server briefly doesn't exist at all; create_before_destroy means the new server is up and could be serving traffic before the old one goes away.

Recap
  • lifecycle is a block nested inside resource (and, for conditions, data) that changes how Terraform is allowed to apply changes — it doesn't configure the infrastructure itself.
  • create_before_destroy = true flips a replace from destroy-then-create to create-then-destroy, avoiding a gap with nothing live — a named exam objective, and the right default instinct for anything users depend on.
  • prevent_destroy = true rejects any plan that would destroy the resource while its config still exists — a strong best practice for production databases and anything irreplaceable. It doesn't stop destruction caused by removing the resource block itself.
  • ignore_changes = [attr, ...] (or all) tells Terraform to stop reverting drift on specific attributes — for values legitimately changed outside Terraform. Prefer naming exact attributes over all.
  • precondition checks an assumption before Terraform acts; postcondition checks a promise after it acts and can reference self. Both require condition and error_message.
