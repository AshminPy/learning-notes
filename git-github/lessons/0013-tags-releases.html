Git Tags & Releases

A branch name (Lesson 4) moves — it always points at the latest commit made on it. Sometimes you need the opposite: a permanent, unmoving pointer at exactly one commit, marking "this is what v1.0 actually was," forever. That's a tag.

Mental model: a branch is a sticky note that moves to whatever page you're currently on. A tag is a bookmark glued to one specific page — it never moves, even after you keep reading (committing) past it. That predicts something branches can't offer: come back in two years, and v1.0 still points at exactly the commit it did the day you tagged it, no matter how much history has been added since.

Where this fits

main:  A---B---C---D---E   (branch pointer: moves to E, the latest commit)
           │
          v1.0              (tag: stays glued to B, forever)

Lightweight vs. annotated tags

git tag v1.0-lite                          # lightweight — just a name, no metadata
git tag -a v1.0 -m "First stable release"  # annotated — name + message + author + date

Why it's built this way: a lightweight tag is barely more than a branch name that doesn't move — cheap, but no record of who tagged it or why. An annotated tag is a real Git object with its own message, tagger identity, and date, which is what makes it show up properly in git describe and GitHub Releases. Use annotated for anything meant to mark an actual release; lightweight is fine for a quick personal bookmark.

git tag                          # list all tags
git push origin v1.0             # tags don't push automatically — explicit, on purpose
git push origin --tags           # push every local tag at once

Try it

Q1. You commit five more times after tagging v1.0. Does v1.0 move to include those commits?

No. A tag is a fixed pointer to the exact commit it was created on — unlike a branch, it never moves as you keep committing.

Now try it yourself: make a commit, tag it as an annotated release, then confirm the tag stays put after a second commit. Try before revealing.

Reveal the sequence

echo release > f.txt && git add f.txt && git commit -m "release commit"
git tag -a v1.0 -m "First release"
echo more >> f.txt && git commit -am "post-release work"
git log --oneline v1.0        # shows only up through "release commit"
git log --oneline main        # shows the newer "post-release work" too

Common mistake: assuming git push also pushes your tags — it doesn't, by design, since a tag is often created after review/CI passes, separately from the push that triggered it. You need git push origin <tag> or --tags explicitly.

A controlled failure

git tag v1.0
echo change > f.txt && git add f.txt && git commit -m "another commit"
git tag v1.0

Predict first: does the second git tag v1.0 move the tag to the new commit? Observe: Git refuses — fatal: tag 'v1.0' already exists. Tags are deliberately immutable once created; moving one requires an explicit, unambiguous -f:

git tag -f v1.0
git push origin v1.0 --force   # remote tags need the same explicit force, for the same reason

Production best practices

Production note: never force-move a tag that's already been pulled by others or referenced in a deployed artifact — same divergence risk as force-pushing a branch (Lesson 9's reset-vs-revert logic applies here too). Once v1.0 has shipped, treat it as permanently immutable; cut v1.0.1 instead of moving v1.0.

Interview notes

Interview Q: "Why does Git require an explicit --tags or tag name to push tags, instead of pushing them along with commits automatically?" A: Tags often mark a deliberate milestone (a release) created after review, separately from routine commit pushes — making tag pushes explicit prevents an unfinished or accidental tag from shipping just because a normal git push happened.

Recap
  • A tag is a fixed pointer to one commit — unlike a branch, it never moves as you keep committing.
  • Annotated tags (-a -m) carry a real message/author/date; lightweight tags are just a name.
  • Tags don't push automatically — git push origin <tag> or --tags is required, on purpose.
  • Moving an existing tag requires explicit -f — treat a shipped tag as immutable in practice.
