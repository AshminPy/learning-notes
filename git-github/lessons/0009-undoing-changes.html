Undoing Changes

Git has four different "undo" commands, and picking the wrong one is a common source of real trouble — they operate on different areas from Lesson 1's three-stage model, and only one of them is safe to use on already-shared history.

Simple example: git restore file.txt discards uncommitted changes to a file — gone, back to the last commit's version. git revert <commit> instead creates a brand-new commit that undoes an old one, leaving the original commit fully intact in history — the safe choice once something's already shared.

The four undo commands, by what they touch

CommandUndoesRewrites history?
git restore <file>Uncommitted changes in the working directory, back to the last commitNo — nothing was committed yet
git restore --staged <file>Unstages a file (moves it from staged back to just-modified) without discarding the edit itselfNo
git reset <commit>Moves the current branch pointer to an earlier commitYes — later commits become unreachable from this branch
git revert <commit>Creates a new commit that undoes a specific past commit's changesNo — adds history, doesn't remove it

reset vs. revert — the choice that matters most

git reset rewrites your branch to point somewhere earlier — exactly like a rebase (Lesson 5), it creates a divergence for anyone who already has the commits you're resetting past. git revert never removes a commit; it adds a new one that cancels a previous one out, which is why it's the only safe option for undoing something on a branch others have already pulled.

Running git reset --hard discards uncommitted working directory changes permanently, with no confirmation prompt and no easy undo — it's one of the few Git commands that can genuinely destroy real, uncommitted work in one step. Double-check git status and consider stashing (Lesson 10) before ever running it.

Try it — before looking below

Q1. A bad commit was pushed to a shared branch two days ago, and three teammates have already pulled it. Should you git reset past it, or git revert it?

git revert — the commit is already shared, so rewriting history with reset would create the same divergence problem as rebasing shared work (Lesson 5). revert adds a new commit undoing the bad one, which is safe for everyone who already has the original.

Now try it yourself

echo "oops" >> file.txt
git restore file.txt              # discard the uncommitted change safely

echo "real change" >> file.txt && git commit -am "a change"
git revert HEAD --no-edit          # undo it with a new commit, history stays intact
git log --oneline                  # see both the original and the revert commit

Source

Pro Git — Reset Demystified — the official Git documentation, git-scm.com.

Recap
  • restore discards uncommitted changes; reset moves the branch pointer (rewrites history); revert adds a new commit that undoes an old one (safe, preserves history).
  • Use revert, not reset, for anything already shared — the same rule as merge vs. rebase from Lesson 5.
  • git reset --hard can permanently discard uncommitted work with no confirmation — treat it with real caution.
When unsure which undo command applies, ask first "has anyone else already seen this?" — that single question decides between the rewrite-history and add-history options.
