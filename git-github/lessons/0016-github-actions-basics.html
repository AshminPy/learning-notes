GitHub Actions Basics

Lesson 15's PRs get reviewed by humans, but humans shouldn't have to manually run tests on every push to check them. GitHub Actions runs automation — tests, builds, deploys — triggered directly by the same events you already produce: a push, a PR being opened, a tag created (Lesson 13).

Mental model: a workflow file is a standing instruction taped to the repo's door: "whenever X happens, do Y, automatically, on a fresh machine." That predicts something important: each run starts from a completely clean environment — nothing persists between runs unless you explicitly save it, which is exactly why a workflow has to check out the repo itself as its first real step.

Anatomy of a workflow

# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "run your tests here"
  • on — which events trigger this workflow (push, pull_request, a schedule, manual dispatch)
  • jobs.<id>.runs-on — what kind of machine runs it
  • steps — run in order; uses runs someone else's packaged action, run runs a raw shell command

Why actions/checkout@v4 comes first, always: the runner starts with an empty filesystem — no repo, no history, nothing. actions/checkout is what actually clones your repository onto the runner; skip it and every later step that expects your files to exist fails immediately.

Try it

Q1. A workflow's second step tries to read a file from your repo and fails with "file not found." What's the most likely missing first step?

actions/checkout@v4 — without it, the runner never clones the repository, so no file from it exists on the runner's filesystem at all.

Now write your own, by hand: a workflow that runs on every push to main, checks out the repo, and prints "hello from CI." Try before revealing.

Reveal the reference answer

name: Hello CI
on:
  push:
    branches: [main]
jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "hello from CI"

Common mistake: hardcoding a secret value directly in the workflow YAML — it's committed history the moment you push, permanently, even if you delete it in a later commit. Use ${{ secrets.MY_SECRET }}, configured in the repo's Settings, never a literal value in the file.

A controlled failure

# .github/workflows/broken.yml — missing checkout on purpose
name: Broken
on: push
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: cat README.md

Predict first: does this workflow fail, and with what kind of error? Observe (reason through it, or push this to a scratch repo): cat: README.md: No such file or directory — the runner's filesystem is genuinely empty at that point; this isn't a permissions or syntax error, the file simply was never placed there because checkout was skipped.

Production best practices

Production note: pin action versions to a specific major version (@v4) rather than @main/@latest — an upstream action can change behavior under you otherwise, the exact same "don't pull latest unpinned" lesson as Lesson 17's Helm chart-version advice, applied to CI.

Interview notes

Interview Q: "A CI workflow works on your branch but fails on the exact same code after merging to main. What's a likely GitHub-Actions-specific cause?" A: Different trigger conditions or secrets availability — some secrets/environments are restricted to specific branches, and a workflow can be defined differently (or missing) on main versus the feature branch until the PR that adds it is itself merged.

Recap
  • A workflow file declares events (on) and steps to run automatically when they happen.
  • Every run starts on a fresh, empty runner — actions/checkout is what actually puts your repo there.
  • Secrets go through ${{ secrets.NAME }}, configured in repo settings — never a literal value in the YAML.
