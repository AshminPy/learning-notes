GitHub Pull Requests

Everything so far (Lessons 1-14) is Git — it works with no network, no GitHub. A pull request (PR) is GitHub's layer on top: a proposal to merge one branch into another, with a place for discussion, review, and automated checks before it happens. This is where a local habit becomes a team process.

Mental model: a PR is a diff with a conversation attached, not a copy of your branch. Push commits to the same branch after opening a PR, and the PR updates live — it's always showing the real, current difference between two branches, not a snapshot taken when you opened it. That predicts something worth knowing: closing a PR doesn't touch the branch or its commits at all, they're independent of the PR object.

Where this fits

Local branch (Lesson 4) + commits (Lesson 3)
   │  git push origin feature-branch
   ▼
Remote branch on GitHub
   │  open a PR: feature-branch → main
   ▼
Pull Request  ← you are here (review, checks, discussion)
   │  merge
   ▼
main gets feature-branch's commits, one of three ways (below)

Opening one

git checkout -b add-login
# make commits
git push -u origin add-login

Then open a PR on GitHub comparing add-login against main — GitHub shows every commit and the full diff between the two branches, computed live, not a fixed snapshot.

The three merge strategies

StrategyResult on main
Merge commitAll original commits kept, plus one new merge commit joining them — full history preserved (Lesson 5's merge)
Squash and mergeEvery commit on the branch becomes one new commit on main — clean history, original commits' individual hashes gone from main
Rebase and mergeEach commit replayed individually onto main, no merge commit — linear history (Lesson 11's rebase, done by GitHub)

Why it's built this way: these map directly to Lessons 5 and 11's Git operations — GitHub isn't inventing new merge semantics, it's running the same three approaches you already know, triggered by a button instead of a local command.

Try it

Q1. You push a new commit to a branch that already has an open PR. Does the PR need to be recreated?

No — a PR tracks a branch comparison live. New commits pushed to the branch show up in the same PR automatically.

Now, before revealing: your team wants a clean, linear main history with no merge commits and no individual "wip" commits from feature branches. Which merge strategy fits, and why not the others?

Reveal the answer

Squash and merge — one clean commit per PR, no merge commit, and messy intermediate commits never reach main. Merge commit keeps a non-linear graph; rebase and merge keeps every intermediate commit individually.

Common mistake: assuming closing a PR without merging deletes the branch or its commits — it doesn't. The commits still exist on the branch until someone explicitly deletes it.

A controlled failure

git checkout -b test-pr
echo change > f.txt && git add f.txt && git commit -m "test change"
git checkout main
echo other > f.txt && git commit -am "conflicting main change"
git push origin main test-pr

Predict first: if you open a PR from test-pr into main now, can it merge automatically? Observe: GitHub reports the PR as not mergeable — the same conflict Lesson 6 taught, just surfaced in the PR UI instead of your terminal. The fix is identical: merge main into your branch locally, resolve the conflict markers, push, and the PR updates to reflect the resolution.

Production best practices

Production note: require at least one review approval before merge is allowed (Lesson 17 covers the setting) — but review quality matters more than the rule existing: a rubber-stamp approval provides no real safety net, the discussion and actual reading of the diff is what catches problems.

Interview notes

Interview Q: "Squash-merge vs. a regular merge commit — what's the real trade-off?" A: Squash gives a clean, one-commit-per-feature main history but loses the granular intermediate commits (useful for git bisect (Lesson 14) if a feature's internal history mattered). A merge commit preserves everything but makes main's history non-linear. Most teams pick squash for feature branches and reserve merge commits for release branches.

Recap
  • A PR is a live comparison between two branches, not a snapshot — new pushes update it automatically.
  • Three merge strategies map to Git operations you already know: merge commit (Lesson 5), squash, rebase and merge (Lesson 11).
  • A PR conflict is the same conflict as Lesson 6 — resolve locally, push, the PR reflects it.
  • Closing a PR doesn't touch its branch or commits — they're independent objects.
