Resolving Merge Conflicts

A conflict happens when Git can't automatically decide how to combine two changes to the same lines — it needs a human to pick. This isn't a failure or an error state; it's Git correctly recognizing that it doesn't have enough information to guess safely, and asking you instead of guessing wrong.

Simple example: Two branches both changed line 5 of the same file, differently. Git can't know which change is "correct" — it stops the merge, marks the file as conflicted, and inserts special markers showing both versions so you can decide.

Reading the conflict markers

<<<<<<< HEAD
your current branch's version
=======
the other branch's version
>>>>>>> feature-branch

Everything between <<<<<<< HEAD and ======= is your current branch's version. Everything between ======= and >>>>>>> is the incoming branch's version. Resolving means editing the file to what it should actually say — keeping one side, the other, a combination, or something new entirely — then removing all three marker lines completely.

The resolution workflow

StepCommand
1. See which files conflictgit status
2. Edit each conflicted fileResolve manually, remove all marker lines
3. Mark it resolvedgit add <file>
4. Complete the mergegit commit (message is often pre-filled)

Committing a file with the conflict markers still left in it — because they were missed in the resolution — is a surprisingly common mistake, and it silently breaks the file (invalid syntax in code, garbled content elsewhere). Always re-read the resolved section fully before staging it, not just skim for the marker symbols.

Aborting if it's going wrong

If a merge conflict resolution is getting confusing or you realize you need more context first, git merge --abort cleanly cancels the whole merge and returns you to exactly where you were before it started — no harm done, no partial state left behind. This is a genuinely safe escape hatch, worth using rather than pushing through a resolution you're not confident about.

Try it — before looking below

Q1. Halfway through resolving a conflicted file, you realize you don't actually understand what the other branch's change was trying to do. What's the safe move?

git merge --abort — it cleanly cancels the merge and restores your branch to its exact pre-merge state, giving you time to investigate (read the other branch's commit, ask a teammate) before trying again with real understanding.

Now try it yourself

git switch -c branch-a
echo "version A" > shared.txt && git commit -am "A's version"
git switch main
echo "version B" > shared.txt && git commit -am "B's version"
git merge branch-a          # this will conflict — practice resolving it
cat shared.txt               # see the actual conflict markers
# Edit shared.txt to resolve, then:
git add shared.txt
git commit

Recap
  • A conflict means Git needs a human decision, not that anything went wrong — it's correctly avoiding a guess it can't make safely.
  • Resolve by editing to the correct final content and removing all three marker lines, then git add and git commit.
  • git merge --abort is a safe, complete escape hatch if a resolution gets confusing mid-way.
Always re-read a resolved file fully, not just for marker symbols — a left-over marker line is invisible at a glance but breaks the file completely.
