What Git Actually Is: The Mental Model

The single most common wrong mental model of Git is "it stores a list of diffs between versions." That's actually how some older version control systems worked — Git does something different: every commit is a full snapshot of your entire project at that moment. Almost every confusing Git behavior makes sense once this clicks.

Simple example: If you change one line in one file and commit, Git doesn't store "line 5 changed from X to Y." It stores a complete snapshot of the whole project as it exists right now — but efficiently, by reusing the unchanged files from the previous snapshot rather than copying everything.

The three areas every file moves through

AreaWhat it holds
Working directoryThe actual files on disk, as you're editing them right now
Staging area (the "index")Changes you've marked as ready to include in the next commit
Repository (commit history)Permanent, saved snapshots — each one a complete point-in-time record

A change moves through these areas in order: you edit a file (working directory), git add it (staging area), then git commit it (repository, permanently recorded). This three-stage model is why git add exists at all — it lets you build up exactly the set of changes you want in the next commit, rather than being forced to commit every edit you've made.

Why "snapshots, not diffs" actually matters

Because each commit is a complete snapshot, checking out any past commit gives you the entire project exactly as it was — instantly, without replaying a chain of diffs to reconstruct it. This is also why branches are so cheap in Git: a branch is just a lightweight pointer to a specific commit, not a full copy of the project.

A common confusion: assuming git add means "save this change." It doesn't — it means "include this change in the next commit." The change isn't actually recorded in history until git commit runs. Losing uncommitted staged changes (e.g., from an accidental git checkout on the file) is a real, frequent early mistake.

Try it — before looking below

Q1. You edit a file and run git add, but haven't committed yet. Is that change permanently recorded in Git's history?

No — it's staged (marked ready for the next commit) but not yet committed. It only becomes a permanent part of history once git commit actually runs.

Now try it yourself

mkdir git-lesson-1 && cd git-lesson-1
git init
echo "hello" > file.txt
git status                # working directory: file.txt is untracked
git add file.txt
git status                # staging area: file.txt is staged, ready to commit
git commit -m "first commit"
git status                # repository: clean, the snapshot is saved

Recap
  • Git stores complete snapshots at each commit, not a chain of diffs — this is the core mental model everything else builds on.
  • Every change moves through three areas in order: working directory → staging area (git add) → repository (git commit).
  • A staged change isn't permanent history yet — only a committed one is.
If a later lesson's behavior ever feels surprising, come back to "it's a snapshot, not a diff" first — it explains more Git behavior than any other single fact.
