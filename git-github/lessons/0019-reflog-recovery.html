Recovering from Mistakes: Reflog & Lost Commits

Lesson 9's git reset --hard, Lesson 11's interactive rebase, Lesson 12's cherry-pick — every history-rewriting operation in this course can make a commit look gone. It almost never actually is. The reflog is Git's private log of everywhere your branches and HEAD have pointed, and it's the safety net under nearly every "I think I just lost work" panic.

Mental model: the reflog is a security camera pointed at your own HEAD, not the commit history itself. It doesn't record what changed in each commit — it records every place HEAD and your branches have pointed, second by second, including addresses you've since moved away from. That predicts its real limit: it only sees your local repository's movements. A commit that existed only on someone else's machine, never checked out or fetched locally, was never in this camera's view to begin with.

Where this fits

git reset --hard HEAD~3    (Lesson 9)  → branch pointer moves, 3 commits look "gone"
git rebase -i HEAD~5       (Lesson 11) → new commits replace old ones, old hashes look "gone"
        │
        ▼
git reflog   ← you are here — every one of those old positions is still logged, locally

Reading the reflog

git reflog
a1b2c3d HEAD@{0}: reset: moving to HEAD~3
d4e5f6g HEAD@{1}: commit: add feature
e5f6g7h HEAD@{2}: commit: fix bug

Each line is a snapshot of where HEAD pointed, most recent first. HEAD@{1} in the example above is the commit that existed right before the reset moved things — genuinely still in your repository's object database, just no longer reachable from any branch, which is the actual definition of "looks gone."

Recovering a lost commit

git checkout d4e5f6g              # look at it directly, detached HEAD
git branch recovered-work d4e5f6g  # or: give it a permanent name
# or, to move your current branch back to it entirely:
git reset --hard d4e5f6g

Why it's built this way: Git almost never deletes commit objects immediately — a "lost" commit becomes genuinely unreachable garbage only after it drops out of the reflog (default ~90 days) and a garbage collection run happens. That two-stage delay is deliberate breathing room, specifically so a reset/rebase mistake has a real recovery window instead of being instantly, permanently destructive.

Try it

Q1. You run git reset --hard HEAD~2 by mistake. Are the two commits you just "lost" actually deleted?

No — they still exist as objects, just unreachable from any branch. git reflog shows the commit hash your branch pointed to right before the reset; git reset --hard <that-hash> restores it.

Now try it yourself: make two commits, hard-reset past both, then use the reflog to get them back. Try before revealing.

Reveal the sequence

echo a > f.txt && git add f.txt && git commit -m "commit one"
echo b >> f.txt && git commit -am "commit two"
git reset --hard HEAD~2       # both commits now unreachable from this branch
git reflog                     # find the hash labeled "commit two" (right before the reset)
git reset --hard <that-hash>   # both commits are back

Common mistake: assuming the reflog protects commits that were only ever on a teammate's machine or an unpushed remote branch that got deleted — it only logs your own local repository's ref movements. If you never fetched or checked out those commits locally, your reflog never saw them, and this recovery path doesn't apply.

A controlled failure

echo a > f.txt && git add f.txt && git commit -m "important work"
git reflog | head -1

Predict first: if you now run git gc --prune=now immediately (forcing garbage collection), does the commit disappear? Observe: no — it's still referenced by the current branch and by the reflog entry itself; gc only removes objects that are both unreachable from any ref and aged out of the reflog. This is why the two-stage delay in "Why it's built this way" above matters in practice, not just in theory.

Production best practices

Production note: the reflog is local-only — it doesn't survive a fresh clone, isn't backed up with your remote, and isn't a substitute for pushing important work. Push to a remote (even a personal scratch branch) as soon as work matters enough to lose sleep over; the reflog is a short-term local safety net, not durable storage.

Interview notes

Interview Q: "A teammate ran git rebase -i and accidentally dropped a commit they needed. Is it recoverable?" A: Almost certainly yes, on their own machine — git reflog will show the pre-rebase position, and git cherry-pick or git reset --hard against that hash restores it. It's only unrecoverable if their reflog has already aged out and garbage collection has run, which takes real time by default.

Recap
  • The reflog logs every position your local HEAD/branches have pointed to — a "lost" commit almost always still exists as an object.
  • Commits become truly unreachable only after aging out of the reflog (~90 days default) and a garbage-collection run — a deliberate recovery window.
  • The reflog is strictly local — it can't recover a commit that never existed in your own repository.
