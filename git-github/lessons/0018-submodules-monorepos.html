Submodules & Monorepos

When one project depends on another repository's code — a shared library, a design-system repo — there are two opposite ways to structure that: keep them as separate repos linked together (a submodule), or put everything in one repo (a monorepo). Neither is universally right; they trade different problems for different ones.

Mental model: a submodule is a shipping label pointing at one exact box in another warehouse — not a copy of the box's contents, just its precise address (a commit hash) at the time you pointed at it. That predicts the single most common submodule confusion: updating the other warehouse's box doesn't move your label. Your submodule stays pinned to the old commit until you deliberately update the pointer.

Where this fits

Your repo
  └ .gitmodules            (records: path, url, for each submodule)
  └ path/to/submodule/  →  pinned to ONE exact commit (not a branch) in another repo

vs.

Monorepo: everything in one repo, one history, one set of commits (Lesson 3)

Submodules

git submodule add https://github.com/org/shared-lib.git libs/shared-lib
git commit -am "add shared-lib submodule"

This records the exact commit in .gitmodules and as a special entry in your repo — not the submodule's files themselves. Anyone cloning your repo needs an extra step to actually get its contents:

git clone --recurse-submodules <your-repo>
# or, after a plain clone:
git submodule update --init --recursive

Why it's built this way: pinning to an exact commit (not a branch) means your repo's build is fully reproducible — the submodule can't silently change under you just because someone pushed to the other repo. Updating is a deliberate, separate action:

cd libs/shared-lib
git pull origin main        # move the submodule's own checkout forward
cd ../..
git commit -am "bump shared-lib submodule"   # record the new pinned commit

Monorepos — the alternative

A monorepo puts everything in one repository instead — one git log, one PR can touch both the library and its consumer atomically, no separate pinning step. The trade-off: `git clone` gets slower and larger as the repo grows, and CI (Lesson 16) often needs path-based filtering to avoid rebuilding everything on every change.

Try it

Q1. You update code in a submodule's own repository and push it. Does your parent repo's checkout of that submodule change automatically?

No — the submodule is pinned to a specific commit, recorded in the parent repo. It stays exactly there until someone deliberately updates the submodule's checkout and commits the new pointer.

Now, before revealing: a teammate clones your repo with a plain git clone (no --recurse-submodules) and reports the submodule directory is empty. What happened, and what's the fix?

Reveal the answer

A plain clone only creates the empty directory and records where it should point — it doesn't fetch the submodule's actual contents. Fix: git submodule update --init --recursive.

Common mistake: assuming a submodule tracks a branch, so it'll "just update" — it tracks one exact commit. Nothing changes it except an explicit update-and-commit cycle, even if the submodule's own branch has moved far ahead.

A controlled failure

git submodule add https://github.com/octocat/Hello-World.git demo-sub
git commit -am "add demo submodule"
cd demo-sub && git log -1 --oneline && cd ..
# simulate someone else forgetting --recurse-submodules:
git clone . /tmp/fresh-clone-test
cd /tmp/fresh-clone-test && ls demo-sub

Predict first: is demo-sub populated in the fresh clone? Observe: the directory exists but is empty — exactly the symptom from the quiz above, reproduced directly, confirming a plain clone never fetches submodule contents automatically.

cd /tmp/fresh-clone-test && git submodule update --init --recursive
ls demo-sub   # now populated

Production best practices

Production note: document the --recurse-submodules requirement prominently (README, CI setup) if you use submodules — the "empty directory" confusion is common enough that it costs real onboarding time otherwise, and CI pipelines need the same explicit flag or they'll build against an empty submodule silently.

Interview notes

Interview Q: "When would you choose submodules over a monorepo for sharing code between projects?" A: When the shared code has genuinely independent versioning/release cycles and different ownership/access needs — a submodule lets consumers pin to a specific tested version deliberately. A monorepo fits better when the projects are tightly coupled and should always move together.

Recap
  • A submodule pins your repo to one exact commit in another repository — not a branch, not automatically updating.
  • A plain clone leaves submodule directories empty — --recurse-submodules or a follow-up submodule update --init --recursive is required.
  • Monorepos trade submodule pinning/update overhead for one unified history and atomic cross-project changes, at the cost of repo size and CI complexity.
