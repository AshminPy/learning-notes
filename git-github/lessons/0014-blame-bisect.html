Git Blame & Bisect

Two different questions, both answered by history you already have: "who last touched this line, and why?" (blame), and "which of these 200 commits actually broke this?" (bisect). Neither requires guessing — both search history that's already sitting in your repository.

Mental model: blame is a magnifying glass on one line; bisect is a metal detector sweeping a whole field. blame answers "who, when, why" for a line you've already found. bisect finds the line/commit you haven't found yet, by narrowing a range in half repeatedly instead of reading every commit in order. That predicts the speed difference: checking 200 commits one at a time is 200 steps; bisecting the same range is about 8 (log2 of 200).

Where this fits

git log        → the full linear history (Lesson 3)
   │
   ├─→ git blame <file>    → per-line: which commit, who, when
   └─→ git bisect            → binary search across commits for the one that broke something

git blame — per-line history

git blame f.txt
a1b2c3d4 (Alice  2026-07-01 10:00:00) line one
b2c3d4e5 (Bob    2026-07-15 14:30:00) line two

Every line shows its last-modifying commit, author, and date. git log -L 10,20:f.txt goes further — full history for just that line range, across every change, not only the most recent one.

git bisect — binary search for a regression

git bisect start
git bisect bad                # current commit is broken
git bisect good v1.0           # this old tag/commit was known-working

Git checks out a commit roughly halfway between good and bad. Test it, then tell Git the result:

git bisect good     # or: git bisect bad

Why it's built this way: each answer halves the remaining search space — the same divide-and-conquer idea behind binary search in any sorted list, applied to commit history instead of an array. Repeat until Git reports the exact first-bad commit, then stop:

git bisect reset    # return to the branch/commit you started from

Try it

Q1. History has 100 commits between the last known-good and known-bad state. Roughly how many test steps will bisect take to find the exact breaking commit?

About 7 (log2 of 100 ≈ 6.6, rounded up) — each test halves the remaining range, regardless of how the 100 commits are ordered.

Now try it yourself: use git blame on a real file in one of your repos to find who last touched a specific line, and why (read that commit's message). Try before revealing what you'd expect.

Reveal what to expect

A commit hash, author, and date per line. git show <that-hash> gives the full commit message and diff — often the real "why," which the blame output alone doesn't show.

Common mistake: reading blame output as "who wrote this code" — it only shows who last touched the line. A one-character formatting fix by someone unrelated to the original logic shows up as the blamed author, which can misdirect who you ask about the actual reasoning.

A controlled failure

git bisect start
git bisect bad HEAD
git bisect good HEAD~10

Predict first: what happens if, mid-bisect, you accidentally run a normal git checkout main instead of testing? Observe: bisect's internal state doesn't reset — it's still mid-search, tracking its own detached-HEAD position separately from your branches. Running git bisect good/bad again continues correctly from where it left off; only git bisect reset actually ends the session.

git bisect reset

Production best practices

Production note: git bisect run <script> automates the whole loop — point it at a test script that exit-codes 0 for good, non-zero for bad, and bisect drives the entire search unattended, checking out and testing each candidate commit itself. Worth setting up for any regression with a reliable automated test, instead of manually testing each step.

Interview notes

Interview Q: "A regression was introduced somewhere in the last 150 commits, but you don't know which one. What's your approach?" A: git bisect — mark the current commit bad and the last known-good one good, then let Git's binary search narrow it down in roughly log2(150) ≈ 8 steps, automating the test with bisect run if a reliable test exists.

Recap
  • git blame shows the last commit/author/date per line — a magnifying glass on a line you've already found.
  • git bisect binary-searches commit history for a regression — roughly log2(N) steps instead of checking N commits one by one.
  • bisect run <script> automates the whole search against a reliable test.
