Merging vs. Rebasing

Both merge and rebase bring changes from one branch into another — the difference is what they do to history. A merge preserves exactly what happened, including a new "merge commit" tying the two histories together. A rebase rewrites history, replaying your branch's commits on top of the other branch as if they'd been made there from the start.

Simple example: git merge feature from main creates a new commit with two parents — the tip of main and the tip of feature — and both branches' full history remains visible exactly as it happened. git rebase main from feature instead moves your feature commits to start from the current tip of main, producing a straight, linear history with no merge commit.

The one rule that matters most

Never rebase a branch that others have already pulled and are working from. Rebase creates brand-new commits (same content, different hashes) — anyone who already has the old commits now has a history that's diverged from yours in a way that's genuinely painful to reconcile. The safe default: rebase your own local, not-yet-pushed (or not-yet-shared) work; merge for anything already shared.

Why teams still choose rebase for feature branches

A clean, linear history (via rebase, or its GitHub equivalent "squash and merge") is easier to read later — git log tells a straight story instead of a tangle of merge commits from every small update. This is a real trade-off, not a strict rule: merge preserves more truth about what actually happened; rebase produces a more readable result. Different teams land differently here, and both are legitimate — know which your team uses.

Try it — before looking below

Q1. You've pushed your feature branch, and a teammate has already pulled it and started their own commits on top. Is it safe to rebase your branch now?

No — your teammate's local history now depends on the commits you'd be rewriting. Rebasing at this point creates a divergence between your rewritten history and their existing history, causing real conflicts when they try to sync. Merge instead, once a branch has been shared and built upon.

Now try it yourself

git switch -c feature-a
echo "a" >> file.txt && git commit -am "add a"
git switch main
echo "b" >> other.txt && git commit -am "add b"
git switch feature-a
git rebase main                 # feature-a's commit now replays on top of main's latest
git log --oneline --all --graph  # compare this to what merge would have looked like

Recap
  • Merge preserves history exactly as it happened, adding a merge commit; rebase rewrites your commits to replay linearly on top of another branch.
  • Rebase creates new commit hashes — never rebase a branch others have already pulled and built on.
  • Both are legitimate choices with a real trade-off (truthful history vs. readable history) — know which your team uses.
When in doubt about whether a branch has been shared, treat it as shared and merge — the cost of an unnecessary merge commit is far lower than the cost of rewriting someone else's history.
