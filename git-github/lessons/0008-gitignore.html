.gitignore & What Not to Track

Not everything in a project directory belongs in version control — build output, dependency folders, local environment files, and secrets should never be committed. A .gitignore file tells Git which paths to leave alone, so they never show up as "untracked" clutter in git status and can't be accidentally staged with a broad git add ..

Simple example: A .gitignore containing node_modules/ and .env means git status never lists them, and git add . silently skips them — even though they're sitting right there in your project folder.

Common patterns

PatternMatches
*.logAny file ending in .log, anywhere in the repo
node_modules/That directory and everything inside it
.envThat exact file at the repo root
build/A build output directory
!important.logAn exception — un-ignore one specific file that a broader pattern would otherwise match

.gitignore only works before a file is tracked

Adding a pattern to .gitignore has no effect on a file that's already been committed — it only prevents Git from noticing new untracked files matching that pattern. A file already in history needs to be explicitly removed with git rm --cached <file> (which untracks it going forward while leaving it on disk) before .gitignore can take over.

A secret (API key, password, credential file) committed to Git history is not safely removed just by deleting it in a later commit — the old commit still contains it, in full, in the repository's history forever, unless you deliberately rewrite history to remove it (a real, disruptive operation, not covered in this lesson) or rotate the leaked credential entirely. Treat any committed secret as compromised and rotate it — don't rely on a follow-up commit to "fix" it.

Try it — before looking below

Q1. You add .env to .gitignore, but it was already committed three commits ago. Does git status stop showing it as changed?

No — .gitignore only affects files Git doesn't already know about. Since .env is already tracked, it needs git rm --cached .env to actually stop tracking it; only then does the .gitignore entry take effect going forward.

Now try it yourself

echo "*.log" > .gitignore
echo "test log entry" > debug.log
git status                    # debug.log doesn't appear — .gitignore is working
git add .gitignore
git commit -m "add gitignore"

Recap
  • .gitignore patterns keep build artifacts, dependencies, and local files out of git status and broad add commands.
  • It only affects untracked files — an already-committed file needs git rm --cached first.
  • A committed secret lives in history permanently until deliberately rewritten — rotate the credential, don't just delete it in a later commit.
Set up .gitignore before your first commit on a new project, not after — it's far easier to prevent tracking a file than to remove one already committed.
