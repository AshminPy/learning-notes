Remote Repositories: Push, Pull, Fetch

Everything in Lessons 1-6 happens entirely on your own machine — a remote is simply another copy of the repository, usually hosted on GitHub, that you sync with explicitly. Git never syncs automatically; every exchange with a remote is a command you run on purpose.

Simple example: git clone <url> downloads a full copy of a repository, including its entire history, and automatically sets up a remote called origin pointing back to where it came from. From then on, git push origin main sends your local commits there; git pull origin main brings their commits to you.

The core remote commands

CommandWhat it does
git clone <url>Download a full copy of a remote repository
git remote -vList configured remotes and their URLs
git fetchDownload remote changes, but don't merge them into your branch yet
git pullFetch, then immediately merge (or rebase, if configured) into your current branch
git pushUpload your local commits to the remote

Fetch vs. pull — a distinction worth keeping straight

git fetch is the safer of the two: it updates your knowledge of what's on the remote (visible as origin/main) without touching your own working branch at all. git pull is fetch immediately followed by a merge — convenient, but it means your branch changes right away, potentially creating a merge commit or a conflict you weren't expecting. When you want to look before you act, fetch then decide is the more deliberate choice.

git push failing with a message about the remote having work you don't have locally is Git protecting you — it refuses to silently overwrite commits someone else pushed. The fix is git pull first (to bring in and reconcile those commits), then push again — never force-push past this without first understanding what you'd be discarding.

Tracking branches

A local branch can be "tracking" a remote branch — once set up (automatically on clone, or via git push -u origin branch-name the first time), plain git push and git pull know which remote branch to sync with, without needing to specify it every time.

Try it — before looking below

Q1. You want to see what changed on the remote before deciding whether to bring it into your branch. Should you run git fetch or git pull?

git fetch — it updates your local knowledge of the remote (origin/main) without touching your current branch, letting you inspect what changed (git log main..origin/main) before deciding to merge it in.

Now try it yourself

git remote -v                        # see configured remotes, if any
git fetch origin                     # download remote state without merging
git log main..origin/main --oneline  # see what's on the remote that you don't have yet

Source

Pro Git — Working with Remotes — the official Git documentation, git-scm.com.

Recap
  • Remotes are separate copies of the repository, usually on GitHub — Git only syncs with them when you explicitly run a command.
  • fetch downloads and updates your knowledge of the remote without touching your branch; pull is fetch plus an immediate merge.
  • A rejected push means the remote has commits you don't — pull and reconcile first, don't force past it without understanding why.
When unsure what a pull will actually do to your branch, fetch first and look — it costs nothing and removes the guesswork.
