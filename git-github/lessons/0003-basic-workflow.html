The Basic Workflow

Four commands cover the everyday loop of working with Git: status to see where things stand, add to stage changes, commit to save a snapshot, and log to see the history you've built. Everything else in this course adds capability on top of this loop — it never replaces it.

Simple example: Edit a file, run git status to confirm what changed, git add . to stage everything, git commit -m "add login form" to save it, then git log --oneline to see it listed as the newest entry in history.

The four commands

CommandWhat it does
git statusShows what's changed, staged, or untracked right now
git add <file> / git add .Stages one file, or everything changed, for the next commit
git commit -m "message"Saves a permanent snapshot of everything currently staged
git log / git log --onelineShows the commit history, full detail or one line per commit

Writing a commit message that's actually useful later

A commit message should explain why a change was made, not just restate what the diff already shows. "Fix bug" tells a future reader (often you, months later) nothing; "fix race condition in session cleanup on concurrent logout" tells them exactly what to expect and why it mattered. git log is only as useful as the messages that built it.

Running git commit -m "wip" repeatedly and never going back to write a real message is a common habit that makes git log useless for anyone (including future you) trying to understand what actually happened and why. Lesson 11 covers cleaning this up after the fact with interactive rebase — but writing it right the first time is cheaper.

git diff — seeing exactly what changed

git diff              # unstaged changes — what you've edited but not yet added
git diff --staged      # staged changes — exactly what the next commit will contain

Checking git diff --staged right before committing is a simple habit that catches accidental inclusions (a debug print left in, a file you didn't mean to stage) before they become a permanent part of history.

Try it — before looking below

Q1. You ran git add . and are about to commit. What's the fastest way to double-check exactly what will be included, before you commit it?

git diff --staged — it shows exactly what's staged and will go into the next commit, distinct from git diff alone, which shows unstaged changes instead.

Now try it yourself

echo "line one" > notes.txt
git add notes.txt
git diff --staged             # see exactly what's about to be committed
git commit -m "add initial notes file"
git log --oneline              # see it in history

Recap
  • status, add, commit, log — the four-command loop underlying everything else in Git.
  • A good commit message explains why a change was made, not just what changed — git log is only as useful as the messages behind it.
  • git diff --staged right before committing catches accidental inclusions before they're permanent.
This four-command loop is what you'll run dozens of times a day for the rest of your career — the rest of this course is about handling everything that doesn't fit this simple case.
