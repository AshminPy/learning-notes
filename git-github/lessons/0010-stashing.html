Stashing Work in Progress

You're mid-change — some edits staged, some not — and you need a clean working directory right now: switch branches to pull an urgent fix, or check out someone else's PR. Committing half-finished work just to switch away is worse than the interruption itself. git stash shelves everything uncommitted, restorable exactly as it was.

Mental model: a stash is a coat-check counter, not a trash can. It holds your uncommitted changes off to the side with a claim ticket (a stash reference), giving you a clean desk to do something else, then hands back exactly what you handed over. That predicts something real: stashes are addressable, not just a single "undo" slot — check three coats in, and you can reclaim the second one specifically, not just whichever's on top.

Where this fits

Working directory  →  Staging area  →  Repository (commits)   (Lesson 1's three areas)
        │                    │
        └──────────┬─────────┘
                    ▼
                 STASH   ← you are here (both areas, bundled, set aside)
git stash
  Working directory: cleared back to last commit
  Staging area:       cleared
  Repository:          untouched
  stash@{0}:           everything that was cleared, safely stored

The basic cycle

git stash              # shelve tracked changes (staged + unstaged)
git stash list          # stash@{0}: WIP on main: a1b2c3 last commit message
git stash pop            # reapply the most recent stash, and remove it from the list

Why it's built this way: pop defaults to the most recent stash (LIFO — last in, first out) because that matches the common case: you interrupted one thing, you want it back. But every stash keeps its own address (stash@{1}, stash@{2}...), so a second or third interruption doesn't overwrite or hide the first — git stash apply stash@{1} reaches any of them directly, and unlike pop, apply leaves the stash in the list afterward.

Try it

Q1. git stash pop vs. git stash apply — which one removes the stash from the list afterward?

pop — it applies and removes in one step. apply only applies, leaving the stash available to apply again elsewhere.

Now try it yourself: edit a tracked file, stash it, confirm the working directory is clean (git status), then bring it back. Try before revealing.

Reveal the sequence

echo "wip change" >> file.txt
git status                # shows file.txt modified
git stash
git status                # clean
git stash pop
git status                # file.txt modified again, exactly as before

Common mistake: assuming git stash shelves everything — untracked and ignored files are skipped by default. Use git stash -u to include untracked files too, or a genuinely new file silently stays in your working directory through the whole cycle.

A controlled failure

echo "line one" > conflict.txt && git add conflict.txt && git commit -m "base"
echo "stash version" >> conflict.txt
git stash
echo "new commit version" >> conflict.txt && git commit -am "conflicting commit"
git stash pop

Predict first: does the pop apply cleanly? Observe: a merge conflict, same markers as Lesson 6 — the stash and the new commit both touched the same line. git status shows the conflicted file, and the stash is deliberately not dropped from the list until you resolve it and run git stash drop yourself — losing a stash on a failed pop would be worse than the conflict.

# resolve the conflict marker in conflict.txt, then:
git stash drop

Production best practices

Production note: don't treat a stash as durable storage — it's local to your machine, invisible to teammates, and easy to lose track of after a few days of accumulating entries. For anything that genuinely needs to survive (a machine switch, a longer interruption), commit to a throwaway WIP branch instead — git stash list gets forgotten; a named branch doesn't.

Interview notes

Interview Q: "You need to pull an urgent hotfix but have uncommitted, unrelated changes. What's the fastest safe move?" A: git stash, pull/checkout the fix, then git stash pop once you're back — safer and faster than a throwaway commit-then-reset cycle, and it never touches the repository's actual history.

Recap
  • A stash bundles working-directory and staged changes together, clears both, leaves commits untouched.
  • Stashes are addressable (stash@{0}, stash@{1}...) — pop takes the most recent and removes it; apply reapplies without removing.
  • Untracked files are skipped by default — -u includes them.
  • A conflicting pop keeps the stash in the list until you resolve and explicitly drop it — nothing is silently lost.
