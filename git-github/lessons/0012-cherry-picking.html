Cherry-Picking Commits

Sometimes you need exactly one commit from another branch — a critical bug fix on main that also needs to land on a release-1.2 branch — without merging or rebasing the whole branch. git cherry-pick takes one specific commit and replays just its changes onto your current branch.

Mental model: cherry-picking is photocopying one page from another book into yours, not lending the whole book. The original commit stays exactly where it was, untouched — what lands on your branch is a brand-new commit with the same changes and message, but its own hash and its own place in your branch's history. That predicts something Lesson 11 already showed for rebase: cherry-picked commits are new objects, not the original moved.

Where this fits

main:     A---B---C---D  (D = the fix you need)
                     \
release:  A---B---E       (missing D)
                     │
                     ▼  git cherry-pick D  (while on release)
release:  A---B---E---D'  (D' = new commit, same changes, new hash)

The basic command

git checkout release-1.2
git cherry-pick a1b2c3d

Why it's built this way: unlike merge (Lesson 5), cherry-pick doesn't care about the two branches' shared history at all — it just takes one commit's diff and applies it fresh. That's exactly what makes it the right tool for "just this one fix," and the wrong tool for bringing over a whole feature (that's what merge/rebase are for).

git cherry-pick a1b2c3d b2c3d4e   # multiple commits, applied in the order given
git cherry-pick -n a1b2c3d         # apply changes, but don't auto-commit — stage only

Try it

Q1. After cherry-picking a commit, does the original commit on the source branch change or disappear?

No — it's untouched. Cherry-pick creates a brand-new commit with a new hash on your current branch; the original stays exactly where it was.

Now try it yourself: make a commit on main, branch off before it, then cherry-pick it onto the new branch. Try before revealing.

Reveal the sequence

git checkout main
echo fix >> f.txt && git commit -am "critical fix"
FIX_HASH=$(git rev-parse HEAD)
git checkout -b hotfix-branch HEAD~1
git cherry-pick $FIX_HASH
git log --oneline -2      # a new commit, different hash than $FIX_HASH

Common mistake: cherry-picking a whole sequence of commits one-by-one to bring over a feature — that's what merge or rebase are actually for. Reach for cherry-pick when you need one or two specific commits, not as a substitute for combining branches.

A controlled failure

echo a > conflict.txt && git add conflict.txt && git commit -m "base"
git checkout -b feature-x
echo b >> conflict.txt && git commit -am "feature change"
git checkout main
echo c >> conflict.txt && git commit -am "main change, same line"
git cherry-pick feature-x

Predict first: does this apply cleanly? Observe: a merge conflict, same markers as Lesson 6 — cherry-pick replays a diff, and a diff can conflict with unrelated changes exactly like a merge or rebase can. Resolve it the same way:

# fix the conflict markers in conflict.txt, then:
git add conflict.txt
git cherry-pick --continue

Production best practices

Production note: cherry-picked commits keep an (cherry picked from commit ...) line in their message (add -x to make this automatic) — worth doing on any release-branch backport, so anyone reading history later can trace exactly which original commit a fix came from.

Interview notes

Interview Q: "You need a single hotfix from main on an older release branch, without pulling in every other change since the branches diverged. What do you use?" A: git cherry-pick <commit> — it applies just that one commit's diff, unlike merge or rebase which bring the full history between the branches.

Recap
  • Cherry-pick applies one commit's changes as a brand-new commit on your current branch — the original is untouched.
  • It ignores shared history between branches entirely, unlike merge/rebase — the right tool for "just this one fix."
  • A cherry-pick can conflict exactly like a merge — resolve, git add, then git cherry-pick --continue.
