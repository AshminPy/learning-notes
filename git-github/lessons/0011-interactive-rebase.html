Interactive Rebase

Lesson 5 used rebase to replay one branch's commits onto another. Interactive rebase replays your own recent commits back onto themselves — letting you clean up messy history (squash a "fix typo" commit into the one it fixes, reorder, reword a bad message) before anyone else sees it.

Mental model: interactive rebase hands you your last N commits as an editable to-do list, one line per commit, and lets you rewrite the list before Git replays it. That predicts the actual mechanic: nothing happens by editing the list itself — Git only acts once you save and close it, replaying each commit in the order and mode you specified, top to bottom.

Where this fits

git log --oneline -3
   c3d4e5  fix typo
   b2c3d4  add feature
   a1b2c3  base commit
        │
        ▼  git rebase -i HEAD~2
[editable to-do list, in reverse-chronological-becomes-top order]
   pick b2c3d4 add feature
   pick c3d4e5 fix typo
        │  (edit the list, save)
        ▼
Git replays each line, producing new commits with new hashes

The to-do list commands

git rebase -i HEAD~3
CommandEffect
pickKeep the commit as-is (default for every line)
rewordKeep the changes, edit the commit message
squashCombine into the commit above it, keep both messages (edit prompt shown)
fixupSame as squash, but discard this commit's message entirely
dropRemove the commit entirely
editPause here so you can amend the commit's content before continuing

Why it's built this way: like Lesson 5's rebase, every replayed commit gets a new hash — this is history rewriting, same rule applies: safe on commits only you have, unsafe (same divergence problem from Lesson 9) on anything already pushed and pulled by someone else.

Try it

Q1. You want to combine a commit into the one above it, but don't care about its message at all. squash or fixup?

fixup — combines silently, discarding the fixed-up commit's message. squash combines but stops to let you edit a merged message from both.

Now try it yourself: make three small commits on a scratch branch, then squash the last two into one with a clean message. Try before revealing.

Reveal the sequence

echo a > f.txt && git add f.txt && git commit -m "add f"
echo b >> f.txt && git commit -am "wip"
echo c >> f.txt && git commit -am "fix wip"
git rebase -i HEAD~2
# in the editor, change the second "pick" to "squash" (or "s"), save
# Git then prompts for a combined commit message — edit and save that too
git log --oneline

Common mistake: running interactive rebase on commits already pushed to a shared branch — every replayed commit gets a new hash, creating the exact divergence Lesson 9 warned about for plain reset. If it's shared, use git rebase --abort the moment you realize, before saving the to-do list.

A controlled failure

echo a > conflict.txt && git add conflict.txt && git commit -m "base"
echo b >> conflict.txt && git commit -am "first change"
echo c >> conflict.txt && git commit -am "second change"
git rebase -i HEAD~2
# mark the second commit "edit", save — rebase pauses there

Predict first: does edit apply the commit and stop, or stop before applying it? Observe: it applies that commit, then pauses with it as the current HEAD — you can now amend it (git commit --amend) before running git rebase --continue to resume replaying the rest.

git rebase --continue

Production best practices

Production note: squash noisy WIP commits into logical, reviewable units before opening a pull request (Lesson 15) — a reviewer reading 8 "wip" commits gets no value from that history; 2-3 clean, well-described commits do.

Interview notes

Interview Q: "What's the difference between squash and fixup in an interactive rebase, and when would you use each?" A: Both combine a commit into the one above it; squash keeps both messages for you to merge, fixup silently discards the absorbed commit's message. Use fixup for pure "oops, forgot a line" commits with no message worth keeping; squash when both messages add real information.

Recap
  • Interactive rebase presents your last N commits as an editable to-do list — nothing happens until you save it.
  • pick/reword/squash/fixup/drop/edit — each line's command decides that commit's fate.
  • Every replayed commit gets a new hash — safe only on commits nobody else has pulled, same rule as Lesson 9's reset vs. revert.
