Branch Protection & Code Review Workflows

Lesson 15's review-before-merge and Lesson 16's CI checks are both optional habits unless something enforces them. Branch protection rules are what turn "we're supposed to review before merging" into "GitHub literally won't let you merge without it."

Mental model: a branch protection rule is a bouncer at the merge button, not a suggestion posted on the wall. It checks a list of requirements — approvals, passing checks, up-to-date branch — and physically disables the merge button until every one is satisfied. That predicts something people miss: an admin can usually still bypass it (a documented, logged exception), but the button itself is genuinely locked for everyone else, not just discouraged.

Where this fits

PR opened (Lesson 15) → CI runs (Lesson 16) → review requested
   │
   ▼
Branch protection rule on `main`   ← you are here (gate, not a habit)
   requires: N approvals, passing checks, up-to-date branch
   │
   ▼
Merge button enabled only once every requirement is met

What a rule can require

  • Require pull request reviews before merging — set a minimum approval count; the button stays disabled below it.
  • Require status checks to pass — name specific CI jobs (Lesson 16) that must succeed; a red or pending check blocks merge.
  • Require branches to be up to date before merging — the PR branch must include main's latest commits first, so what merges is tested against current main, not a stale copy.
  • Restrict who can push directly — forces even trusted contributors through a PR, no direct commits to the protected branch.

Why it's built this way: each requirement targets a specific failure mode: reviews catch what CI can't (design, intent), status checks catch what a human reviewer might miss (a failing test), "up to date" catches integration problems that only show up once two branches' changes combine — three different safety nets, not redundant copies of the same one.

Try it

Q1. A PR has 2 approvals and passing CI, but the branch is 10 commits behind main. Does a rule requiring "up to date before merge" allow merging?

No — the branch must first be updated (merge or rebase main into it) even with approvals and green CI, specifically to test the merge result against current main, not a stale snapshot.

Now, before revealing: your team wants direct commits to main completely disabled, even for admins, no exceptions. What setting achieves that, and what's the real trade-off?

Reveal the answer

"Do not allow bypassing the above settings" (applies the rule to admins too). Trade-off: a genuine emergency fix now has zero fast path — even a critical hotfix must go through the full PR/review/CI cycle, which is sometimes the wrong call for a true outage.

Common mistake: requiring status checks by name, then renaming the CI job (Lesson 16) — the rule keeps looking for the old name, which never reports again, so the branch is permanently unmergeable until the rule is updated to match.

Predict first: can you approve and merge your own PR? Observe: the merge button stays disabled — GitHub doesn't count the PR author's own approval toward most protection rules by default, specifically to prevent a single person from satisfying their own review requirement.

Production best practices

Production note: require status checks by their exact job name from the workflow YAML (Lesson 16), and revisit the required-checks list whenever CI job names change — a rule pointing at a renamed or deleted job silently blocks every future PR with no obvious error explaining why.

Interview notes

Interview Q: "Your team enabled branch protection, but a critical hotfix needs to bypass review during an active outage. What's the safe way to handle that?" A: A designated admin uses the documented, logged bypass (if enabled) rather than disabling the protection rule entirely — disabling the rule removes protection for every other PR in flight too, not just the emergency one.

Recap
  • A branch protection rule disables the merge button until its requirements are met — enforcement, not a posted convention.
  • Reviews, status checks, and "up to date" each catch a different failure mode — not redundant with each other.
  • Renaming a required CI job without updating the rule silently blocks every future merge.

Confidence check — answer without looking back:

  • Why does "up to date before merge" catch problems that reviews and CI alone can't?
  • When would allowing admin bypass be the right call despite weakening the protection?
  • What happens to a required status check after its underlying CI job is renamed?
  • How would you verify a branch protection rule is actually blocking what you think it is?
