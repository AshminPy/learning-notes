GCP PCA — Session 4 of 10 (Day 1)

Networking: VPC design, hybrid connectivity, and load balancing

This session covers exam Section 1.3 (cloud-native networking — VPC, peering, firewalls, load balancers, routing, Shared VPC, Private Service Connect) and Section 2.1 (configuring network topologies — hybrid, multicloud, security, VPC design). Together these are a big slice of the 25% Design & Plan section. You already run Shared VPC and Gateway API daily — skip the "what is a VPC" part, go straight to the GCP-specific naming and the trap zones: VPN vs Interconnect, LB tiers, and network service tiers.

1. VPC & Shared VPC — foundation you already run

VPC

What: global resource, subnets are regional (span all zones in the region) — not zonal like AWS. AWS analogue: VPC, but AWS subnets are zonal, GCP subnets are regional.

Use when: always — it's the base network object. Not when: n/a, every project needs one (default or custom-mode).

Exam trap: because GCP subnets are regional, "add a subnet in a new zone" is a trick distractor — you don't add subnets per zone, you add subnets per region, and instances in any zone of that region draw from the same subnet's IP range.

Shared VPC

What: one host project owns the VPC; service projects attach and their resources use the host's subnets with internal IPs, while IAM/billing stay separate per service project. AWS analogue: no exact match — closest is AWS RAM VPC subnet sharing, but Shared VPC's host/service-project model is more deeply tied into GCP's org/folder resource hierarchy.

Use when: centralized network/security team, multiple app teams needing isolated IAM/billing but shared connectivity (this is your daily Autopilot-cluster pattern). Not when: a single team owns both network and workload — plain VPC Peering or one project is simpler.

Exam trap: attaching a service project requires a Shared VPC Admin holding compute.xpnAdmin and resourcemanager.projectIamAdmin — a scenario granting only one of these and expecting attachment to work is the distractor (verified: Shared VPC docs).

2. Name resolution, NAT, and the routing control plane

Cloud DNS

What: managed authoritative DNS with public and private zones; private zones are visible only to the VPCs you authorize. AWS analogue: Route 53 (public + private hosted zones).

Use when: internal service discovery across a Shared VPC (create the zone in the host project, authorize the shared network), or hybrid resolution via DNS forwarding. Not when: you need a third-party registrar's advanced features Cloud DNS doesn't cover — domain registration itself is a separate product (Cloud Domains).

Exam trap: DNS forwarding (on-prem ↔ GCP over VPN/Interconnect) and DNS peering (GCP network ↔ GCP network) are different mechanisms — a scenario about resolving on-prem records from GCP needs forwarding, not peering, and vice versa (verified: Cloud DNS overview).

Cloud Router

What: BGP control plane only — it exchanges routes, it does not carry data-plane traffic itself. Backs Cloud VPN (HA VPN requires it), Cloud Interconnect, and Router Appliances (Network Connectivity Center). AWS analogue: no single product — closest is the BGP session config on a Direct Connect Gateway or Virtual Private Gateway.

Use when: any dynamic routing scenario — HA VPN, Interconnect, or Cloud NAT (NAT needs a Cloud Router even with no BGP configured). Not when: Classic VPN with static routes only — Cloud Router isn't required there.

Exam trap: Cloud NAT requires a Cloud Router purely as the config holder, even though no BGP peering happens for NAT-only use — candidates forget this dependency and think NAT is Router-free (verified: Cloud NAT overview).

Cloud NAT

What: managed, distributed outbound NAT — no proxy VMs, no bottleneck instance. AWS analogue: NAT Gateway.

Use when: private instances (no external IP) need outbound internet access, e.g. pulling OS patches. Not when: you need inbound connections — Cloud NAT explicitly does not allow unsolicited inbound traffic; use a load balancer for that.

Exam trap: "Cloud NAT lets external clients reach my private VM" is always false — it only translates outbound-initiated flows and their return traffic, never new inbound connections (verified: Cloud NAT overview).

3. Hybrid connectivity: Cloud VPN vs Cloud Interconnect

Cloud VPN

What: encrypted tunnel over the public internet. HA VPN uses dynamic BGP routing via Cloud Router and gets up to 99.99% SLA for most topologies; Classic VPN is static-route only at 99.9% SLA. Each tunnel handles up to 250,000 pps (roughly 1–3 Gbps depending on packet size). AWS analogue: Site-to-Site VPN.

Use when: fast to provision, moderate/variable bandwidth, encryption over the public internet is acceptable. Not when: you need guaranteed low, consistent latency or sustained throughput above a few Gbps per tunnel — Interconnect wins there.

Exam trap: "Cloud VPN" isn't one option — a scenario demanding 99.99% availability needs HA VPN specifically (dynamic BGP, redundant interfaces); picking generic "VPN" or Classic VPN under an HA requirement is the wrong answer (verified: Cloud VPN overview).

Cloud Interconnect

What: private physical connection to Google's network, bypassing the public internet. Dedicated Interconnect is a direct circuit (10 Gbps links, up to 8×10 Gbps; 100 Gbps links, up to 8×100 Gbps; 400 Gbps also available) requiring your own presence in a Google colocation facility. Partner Interconnect goes through a service provider, offering 50 Mbps–50 Gbps VLAN attachments, no colocation presence required. Both support 99.9% or 99.99% SLA depending on topology. AWS analogue: Direct Connect (Dedicated ≈ Direct Connect dedicated connection, Partner ≈ Direct Connect through an APN partner).

Use when: sustained high throughput, predictable low latency, or compliance requiring traffic to avoid the public internet. Not when: you need something live in days, or have no colocation presence and no reason to pay for guaranteed bandwidth — VPN is faster to stand up.

Exam trap: Dedicated Interconnect requires your own equipment inside a Google colocation facility. A scenario stating "no data center presence near a Google PoP" is explicitly ruling out Dedicated — the answer is Partner Interconnect, not "add more Dedicated circuits" (verified: Dedicated Interconnect overview, Partner Interconnect overview).

4. Load balancing: internal vs external

Internal Load Balancer

What: private frontend IP, backends never exposed externally. Regional internal Application LB (HTTP/HTTPS) and cross-region internal ALB (multi-region) for L7; internal passthrough Network LB (TCP/UDP/ICMP/SCTP/ESP/AH/GRE) for L4, regional only. AWS analogue: internal ALB / internal NLB.

Use when: service-to-service traffic inside the VPC/Shared VPC, e.g. microservices behind a Gateway API internal listener. Not when: you need public internet-facing entry — that's External LB.

Exam trap: Cloud Armor does not attach to every internal LB type — it covers the regional internal Application LB but not the internal passthrough Network LB. A scenario asking to WAF-protect an internal TCP passthrough LB is a trick; that protection has to happen elsewhere (verified: Cloud Armor overview).

External Load Balancer

What: internet-facing. Global external Application LB (HTTP/HTTPS, single anycast IP, multi-region backends) and regional external ALB for L7; global/regional external proxy Network LB (TCP with optional SSL offload) and external passthrough Network LB (TCP/UDP/ESP/GRE/ICMP, regional) for L4. AWS analogue: internet-facing ALB/NLB — but note AWS is inherently regional; GCP's global anycast single-IP model needs Global Accelerator in AWS to approximate.

Use when: public-facing app needing a single global IP with backends in multiple regions for latency/failover. Not when: Standard network tier is in play — global external LB requires Premium Tier.

Exam trap: "Global load balancer on Standard Tier" cannot exist — global external IPs and global LBs are Premium Tier only. If a scenario demands lowest cost and explicitly picks Standard Tier, a global LB answer is automatically wrong (verified: Network Service Tiers overview).

5. Edge: Cloud CDN and Cloud Armor

Cloud CDN

What: caches content at Google's edge network, fronted only by the global external Application LB (or classic ALB). Backends: Compute Engine, Cloud Storage buckets, GKE Ingress/Gateway, serverless (Cloud Run/Functions/App Engine), and external backends via internet NEGs. AWS analogue: CloudFront.

Use when: public static/cacheable content needs global low-latency delivery. Not when: the app sits behind an internal LB or a regional external ALB — CDN needs the global external (or classic) Application LB specifically.

Exam trap: a scenario asking to "add Cloud CDN in front of an internal-only service" is unanswerable as stated — CDN requires a global external Application LB, so the real fix is re-architecting the entry point, not just flipping a CDN toggle (verified: Cloud CDN overview).

Cloud Armor

What: WAF + DDoS protection at the edge. Always-on Layer 3/4 volumetric and protocol DDoS mitigation requires no configuration; Layer 7 protection (preconfigured WAF rules based on OWASP CRS, custom rules, rate limiting, bot management, Adaptive Protection for L7 DDoS) requires you to attach a security policy. Attaches to external Application LBs (incl. classic), regional internal Application LB, and proxy Network LBs (global/classic). AWS analogue: AWS WAF + Shield combined.

Use when: internet-facing app needs WAF rules, rate limiting, or geo-blocking. Not when: you assume L7 protection is automatic — it isn't, you must attach a policy.

Exam trap: "Cloud Armor is enabled, so the app is protected from HTTP floods" is false if no security policy with WAF/rate-limiting rules is attached — only L3/4 volumetric DDoS defense is automatic; L7 needs explicit configuration (verified: Cloud Armor overview).

Try it — before reading the answer

Scenario: a company runs prod, staging, and shared-services in 3 separate GCP projects and wants centralized network/firewall administration with per-project IAM boundaries preserved. They also need a new on-prem link: average 200 Mbps, spikes to 800 Mbps twice daily, no rack space in any Google colocation facility, and it must be live in 2 weeks. What network topology and what hybrid connectivity option fit, and why?

Topology: Shared VPC, with shared-services (or a dedicated network project) as the host and prod/staging attached as service projects — centralizes firewall/subnet administration while each team keeps its own project-level IAM and billing. Connectivity: Partner Interconnect — it handles the 800 Mbps spikes comfortably within its 50 Mbps–50 Gbps VLAN attachment range, needs no colocation presence (ruling out Dedicated), and turns up faster than building a Dedicated circuit. HA VPN is the fallback if the 2-week deadline can't be met by any provider, but it caps around 1–3 Gbps per tunnel and rides the public internet — Partner Interconnect is the better fit given the stated constraints.

Quiz — Session 4

Q1. A company needs sub-3ms latency, sustained 40 Gbps throughput to on-prem, and already has rack space in a Google colocation facility. Which option fits?

A. Dedicated Interconnect is built exactly for this: colo presence already exists, and 10/100 Gbps circuits comfortably cover 40 Gbps with the lowest, most predictable latency. B (Partner) is for when there's no colo presence — unnecessary here and often costlier at this scale. C (HA VPN) tops out around 1–3 Gbps per tunnel, far short of 40 Gbps. D (Classic VPN) is even more limited — static routing only, lower SLA, same bandwidth ceiling as HA VPN.

Q2. A company has no presence in any Google colocation facility but needs 10 Gbps guaranteed capacity within a month, provisioned by their existing telecom provider. Best option?

B. Partner Interconnect needs no colocation presence, supports 50 Mbps–50 Gbps VLAN attachments through a service provider, and provisions faster since there's no physical circuit to build. A (Dedicated) is ruled out — no colo presence. C (HA VPN) doesn't guarantee 10 Gbps — a single tunnel caps around 1–3 Gbps. D (Classic VPN) is strictly worse than HA VPN for this need.

Q3. Per the official Shared VPC docs, a Shared VPC Admin needs resourcemanager.projectIamAdmin plus which other IAM role to attach service projects to a host project?

A. Google's docs specifically name compute.xpnAdmin alongside resourcemanager.projectIamAdmin as the pair needed to enable a host project and attach service projects. B (networkAdmin) manages network resources but doesn't grant Shared VPC attachment rights. C (securityAdmin) is IAM/firewall-policy focused, unrelated. D (instanceAdmin) manages VM instances, not project attachment.

Q4. Which load balancer type is required for a single global anycast IP serving HTTP(S) backends across multiple regions?

B. Only the global external Application LB gives one anycast IP with multi-region backend routing for public HTTP(S) traffic. A (regional external) is scoped to one region, no single global IP. C (regional internal) isn't internet-facing at all. D (cross-region internal) is multi-region but private, not internet-facing.

Q5. Which statement about Cloud NAT and Cloud Router is correct?

B. Per Google's docs, "you configure a NAT gateway on a Cloud Router" — it's the control-plane holder for NAT config, even without BGP peering. A is directly contradicted by that requirement. C misunderstands the relationship — NAT doesn't replace Router, it depends on it. D confuses Cloud NAT (address translation) with Classic VPN's static-routing limitation — unrelated services.

Q6. What must be true for Cloud CDN to cache content served through a load balancer?

A. Cloud CDN works exclusively with the global external (or classic) Application LB. B is internal — never internet-facing, can't front public cacheable content. C is both internal and Layer 4 — no HTTP caching semantics. D is Layer 4 passthrough — no HTTP layer for CDN to cache against.

Q7. Which Cloud Armor protection layer is "always-on" and needs no security policy configured first?

B. Google's docs state L3/L4 volumetric and protocol DDoS mitigation is "always-on," automatic, with no policy required. A and C (Layer 7, including HTTP floods and bot traffic) explicitly require a configured security policy with WAF/Adaptive Protection rules. D (Layer 4 port scanning) isn't the always-on guarantee Google documents — L3/4 volumetric DDoS is.

Q8. Under which network service tier can you provision a global external HTTP(S) load balancer with a single anycast IP?

A. Global external IPs and global load balancers are documented as Premium Tier only, routed over Google's private backbone. B is backwards — Standard Tier is regional-only for LBs. C is false — the tiers differ materially in routing path, SLA (99.99% vs 99.9%), and cost. D is false — global LB does exist, just gated to Premium Tier.

Recap
  • Shared VPC = host/service projects, needs compute.xpnAdmin + resourcemanager.projectIamAdmin — no exact AWS equivalent
  • VPN vs Interconnect: bandwidth/latency/SLA needs point to Interconnect; no colo presence or fast turnup points to VPN or Partner Interconnect
  • Dedicated needs your own colo presence; Partner doesn't — this is the #1 connectivity trap
  • Global LB, Cloud CDN, and global external IPs are Premium Tier only — Standard Tier is regional-only
  • Cloud Armor's L3/4 DDoS defense is automatic; L7 WAF/rate-limiting needs an explicit security policy
