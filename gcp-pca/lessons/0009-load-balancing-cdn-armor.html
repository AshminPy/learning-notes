Load balancing, CDN, and Cloud Armor

A load balancer spreads traffic across backends. Some load balancers face the public internet, some stay private inside your network. CDN and Cloud Armor both sit in front of the public-facing kind.

Simple example: think of a reception desk. An external load balancer is the front desk anyone off the street can walk up to. An internal load balancer is a desk only staff (other services in your network) can reach — the public never sees it.

Internal vs external load balancer

Internal load balancer: private IP only. Used for service-to-service traffic inside your network — one app calling another app.

External load balancer: public IP. Used for traffic coming in from the internet — users hitting your website or API.

Cloud CDN

Cloud CDN caches your content at Google's edge locations, closer to users, so pages load faster and your backend does less work. It only works in front of the external (internet-facing) load balancer — never the internal one.

Cloud Armor

Cloud Armor is a firewall for web traffic (a WAF) plus DDoS protection. It blocks bad requests — attacks, bots, unwanted countries — before they reach your app.

  • Basic flood/DDoS defense is on automatically.
  • Custom rules (block an IP, block a country, rate limits) need you to attach a security policy — they are not automatic.
Exam trap: "Cloud Armor is enabled, so we're protected from attacks" is a trap answer. Basic DDoS defense is automatic, but blocking specific attacks (like a flood of bad HTTP requests) needs a security policy you configure yourself. Enabled alone is not the same as configured.

Try it — before looking below

Q1. A team wants to cache their public website's images at the edge for faster loading worldwide. Which service?

B. Cloud CDN caches content at Google's edge, closest to users — exactly what "faster loading worldwide" needs.

Q2. Two microservices inside the same network need to talk to each other. Which load balancer type fits?

B. Internal load balancers handle private, service-to-service traffic — no public exposure needed.

Q3. A team turns on Cloud Armor but adds no custom rules. Are they protected from a flood of malicious HTTP requests?

B. Basic volumetric DDoS defense is on by default. Blocking specific attack patterns at the HTTP layer needs a security policy attached — that step isn't automatic.

Source

cloud.google.com/load-balancing/docs/load-balancing-overview and cloud.google.com/armor/docs/cloud-armor-overview

Recap
  • Internal load balancer = private, service-to-service. External load balancer = public, internet-facing.
  • Cloud CDN only works with the external load balancer.
  • Cloud Armor's basic DDoS defense is automatic; custom rules need a security policy you configure.
