GCP PCA — Session 6 of 10 (Day 2)

Reliability & operations: Cloud Observability suite + release/reliability practices

This covers exam Section 6 — Ensuring solution and operations excellence (12.5%). This is your daily job in different clothes, so this should be one of your fastest sessions: no SRE theory, just GCP's naming, defaults, and the traps Google likes to bait with — especially the audit log retention split, which catches people who assume "audit logs = always kept forever."

1. Cloud Monitoring

What it is: metrics, dashboards, uptime checks, alerting policies. AWS analogue: CloudWatch Metrics + Alarms + Dashboards. When to reach for it: "is the system healthy right now / over time" — latency, error rate, saturation, custom app metrics.

Exam trap: Cloud Monitoring can alert on log-based metrics too — a counter or distribution metric derived from Cloud Logging entries (e.g. count of a specific error string). If a scenario needs an alert on something that only shows up in log text (no native metric exists), the answer is "create a log-based metric in Cloud Logging, then alert on it in Cloud Monitoring" — not "write a custom exporter."

2. Cloud Logging

What it is: centralized log storage, search, log-based metrics, log routing/sinks (to BigQuery, Cloud Storage, Pub/Sub, another project). AWS analogue: CloudWatch Logs (+ some Kinesis Firehose-style routing built in). When to reach for it: "what happened / why" — the audit trail and free-text search side of ops.

Exam trap: the _Default log bucket retains entries for only 30 days; the _Required bucket retains for 400 days and is not configurable (Logging quotas — retention periods). A scenario that needs logs kept 1+ year for compliance is NOT satisfied by default settings — you need a sink to BigQuery/Cloud Storage or a custom retention bucket. Don't pick "Cloud Logging handles this out of the box" as the answer when the constraint says "long-term retention" or "compliance archive."

Exam trap (stack this one — it's the highest-yield fact in this session): "audit logs" is not one bucket with one retention. Admin Activity + System Event live in _Required (400 days, always on). Data Access is the only type off by default and the only one needing the special privateLogViewer role — a scenario about "who accessed this customer's data" requires you to have explicitly turned Data Access logging on beforehand. If the scenario implies it was never enabled, the answer is "that data isn't available," not "check the audit logs." Source: Cloud Audit Logs overview and Logging access control.

4. Error Reporting

What it is: automatically aggregates and groups stack traces/crashes surfaced through Cloud Logging into a dashboard, with notifications on new/regressed errors. AWS analogue: no direct 1:1 — closest is X-Ray's error grouping, but Error Reporting is purely log-driven, not trace-driven. When to reach for it: "what's breaking in prod right now, grouped by root exception" instead of grepping raw logs.

Exam trap: Error Reporting has no separate ingestion pipeline — it scans Cloud Logging entries for properly-formatted stack traces (or errors sent via its API) and groups them (Error Reporting docs). If a scenario says errors aren't showing up in Error Reporting, the fix is almost always "fix the log format / write to stderr correctly," not "enable a new API" — most languages/platforms need zero extra setup beyond correct log formatting.

5. Cloud Trace

What it is: distributed request latency tracing across services. AWS analogue: X-Ray. When to reach for it: "which hop in this request chain is slow," not "is the system up" (that's Monitoring) or "why did it error" (that's Logging/Error Reporting).

Exam trap: Trace does not capture every request by default — it samples. On Cloud Run, the documented default is 0.1 requests per second per instance (one request roughly every 10 seconds), and each Google Cloud service makes its own sampling decision (Cloud Run distributed tracing). If a scenario needs guaranteed capture of a specific rare/critical request, the answer is "force-trace that request via the API," not "Trace already logs everything."

7. Deployment & release management (6.3)

Not a single product — this is CI/CD practice tested at the "which strategy fits this constraint" level, same as you already run with Flux/Argo. Know the names and map them to your existing mental model:

  • Rolling update — default GKE deployment behavior; gradual replacement, brief mixed-version window.
  • Blue/green — full parallel environment, instant cutover, easy instant rollback, costs double during transition.
  • Canary — small % of traffic to new version first; best when you need real production signal before full rollout (pairs naturally with Cloud Monitoring alerts as the go/no-go gate).

Exam framing: when a scenario says "minimize blast radius" or "need instant rollback," that's canary or blue/green. When it says "minimize cost/complexity, standard risk tolerance," that's rolling update — same elimination logic as Session 1.

Try it — before reading the answer

Scenario: a compliance team asks "show me every time someone read customer PII from BigQuery in the last 90 days." You check Cloud Logging and find nothing for most of that window, then entries start appearing 20 days ago. What's the most likely explanation, and what should have been done differently?

Data Access audit logs were not enabled until ~20 days ago (they're off by default for most services), so nothing was captured before that. The fix isn't a Logging bug — it's that Data Access logging must be explicitly turned on ahead of time for the resource/service in question. Also note: even after enabling it, the _Default bucket only keeps 30 days by default, so "last 90 days" would need a sink to longer-term storage (BigQuery/Cloud Storage) regardless.

Quiz — Session 6

Q1. Which audit log type is disabled by default for most services?

A. Data Access logs are off by default (BigQuery is the documented exception) because of their potential volume. B and C are always written and can't be disabled. D is on by default and also can't be disabled.

Q2. What is the default retention period for the _Required log bucket?

A. 400 days, per the Logging quotas page, and it isn't configurable. B is the _Default bucket's retention (where Data Access and Policy Denied logs land). C and D are not real defaults for either bucket.

Q3. Which IAM role is required to view Data Access audit logs?

A. The standard Logs Viewer role (roles/logging.viewer) explicitly excludes Data Access logs; you need the Private Logs Viewer role. C and D are broader than necessary and not the documented minimum-privilege answer, which matters on a "least privilege" exam.

Q4. A team needs to alert when a specific error string appears in application logs, but there's no native metric for it. What should they do?

A. Log-based metrics turn log text into a metric Cloud Monitoring can alert on — the standard, no-extra-infrastructure answer. B adds unnecessary custom infrastructure. C is the wrong tool (Trace is latency, not error text). D is unrelated to this problem.

Q5. On Cloud Run, what is the documented default trace sampling behavior?

A. 0.1 requests/sec/instance — roughly one request every 10 seconds — per the Cloud Run tracing docs. B is the common wrong assumption this trap targets. C understates the rate. D isn't a real relationship — Monitoring and Trace sample independently.

Q6. Errors aren't appearing in Error Reporting even though the app is crashing. What's the most likely first thing to check?

A. Error Reporting scans Cloud Logging for properly-formatted stack traces — no separate ingestion pipeline. B, C, D are unrelated services/layers to this specific symptom.

Q7. A scenario needs instant rollback and full parallel-environment validation before cutover, cost is not the primary constraint. Which release strategy fits best?

A. Blue/green gives a full parallel environment and instant cutover/rollback — matches "instant rollback" and "cost not primary constraint" exactly. B is cheaper but slower to fully roll back. C is for gradual real-traffic validation, not instant full cutover. D introduces downtime the scenario didn't ask for.

Q8. Does Google Cloud require you to request permission before penetration testing your own project's resources?

A. Per Google's published policy: "If you plan to evaluate the security of your Cloud Platform infrastructure with penetration testing, you are not required to contact us" — as long as you stay within your own resources and the Acceptable Use Policy. B/C/D all invent an approval requirement that doesn't exist.

Recap
  • Monitoring = is it healthy (metrics/alerts), Logging = what happened (events/audit), Trace = where's the latency (sampled, not exhaustive)
  • 4 audit log types: Admin Activity + System Event always on, _Required bucket, 400 days. Data Access (off by default) + Policy Denied, _Default bucket, 30 days
  • Data Access logs need roles/logging.privateLogViewer — standard Logs Viewer role can't see them
  • Error Reporting has no separate pipeline — it reads Cloud Logging
  • Cloud Trace samples (e.g. 0.1/s/instance default on Cloud Run) — it does not capture every request
  • No Google approval needed to penetration-test your own GCP resources
