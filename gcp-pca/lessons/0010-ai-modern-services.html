AI platform & modern services: Vertex AI, Agent Builder, and the event-driven glue

This is the last content session. It covers exam section 1.3 (AI/ML solutions bullet), 2.4 (Gemini Enterprise Agent Platform for ML workflows), and 2.5 (prebuilt solutions/APIs) — plus the async-messaging services (Pub/Sub, Eventarc, Cloud Scheduler) that show up across every section as "how do these services talk to each other." Flag up front: Google renamed Vertex AI to the Gemini Enterprise Agent Platform in April 2026 — very recent. Third-party prep material, blog posts, and even some cached docs you find while googling will still say "Vertex AI" everywhere. Don't let that confuse you: same platform, new name, some sub-products renamed too. The current official exam guide already uses the new name in section 2.4's title, so know both.

1. Vertex AI → Gemini Enterprise Agent Platform (naming)

Verified against cloud.google.com/products/gemini-enterprise-agent-platform and docs.cloud.google.com/gemini-enterprise-agent-platform/overview: this is a rename/evolution, not a new separate product. Same underlying ML platform (train, deploy, serve custom + foundation models) — now branded to emphasize agent building on top of it. Google's own docs subtitle it "(formerly Vertex AI)."

What it is (unchanged)What to call it now

Catalog of foundation models (Gemini, Claude, Gemma, Llama, 200+ models)Model Garden
Toolkit to build agents: code-first SDK, low-code canvas, templates, model catalogAgent Builder (bundles Agent Development Kit, Agent Studio, Agent Garden, Model Garden)

AWS/GKE analogue: think of it like SageMaker (train/deploy) merged with Bedrock (foundation models + agents) under one brand — except Google just relabeled the whole thing mid-2026, so the exam guide itself is chasing its own rename.

Exam trap: if a question stem says "Vertex AI," don't assume it's testing outdated material — the exam guide and question bank may use either name during this transition. Answer based on what the service does (train/deploy/predict, or build agents), not which brand name is used in the stem. Don't waste time trying to decide if "Vertex AI" vs "Gemini Enterprise Agent Platform" is itself the trick — it almost never is.

2. Agent Builder & Model Garden — decision level, not implementation level

Per exam guide section 1.3 and 2.5, you need to know when to reach for these, not how to code an agent.

ComponentWhen to use it
Model GardenScenario needs a foundation model (Gemini, or a third-party/open model like Claude/Gemma/Llama) without training from scratch. "Pick a pretrained model and start calling it" scenarios.
Agent BuilderScenario needs an autonomous or semi-autonomous agent — something that reasons, calls tools, and orchestrates multi-step tasks (not just a single prompt/response). Includes a low-code option (Agent Studio) for teams without ML engineers, and a code-first SDK (Agent Development Kit) for custom control.
Custom training on the platformScenario needs a model trained on the org's own proprietary data that no foundation model covers well (rare on this exam — mentioned as out-of-scope depth in the MISSION).
Exam trap: "we need a chatbot that answers from our internal documents" sounds like it needs custom model training — it usually doesn't. That's Agent Builder + RAG (retrieval-augmented generation) over your existing docs, or Vertex AI Search, not a custom-trained model. Custom training is the expensive, slow, wrong answer when a foundation model + retrieval solves it.

3. AI Hypercomputer — infrastructure layer, not a service you "pick" per app

Verified via docs.cloud.google.com/ai-hypercomputer/docs/overview: AI Hypercomputer is the underlying supercomputing system — performance-optimized hardware (TPUs/GPUs), networking, storage, and open ML frameworks (TensorFlow, PyTorch, JAX) — that large-scale training and serving runs on. Named explicitly in exam guide sections 1.3 and 2.4.

Exam-level takeaway: if a scenario says "large-scale model training" or "choosing between GPUs and TPUs, optimizing for cost across different consumption models" — that's AI Hypercomputer territory. It's the "what runs underneath" answer, not something you provision directly the way you'd provision a VM.

4. Google AI APIs & Gemini Enterprise features (section 2.5)

The exam guide (2.5) explicitly separates two things: (a) prebuilt Google AI APIs, and (b) Gemini Enterprise features. Know the distinction — one is "call an API for a specific task," the other is "use a Google-built enterprise product."

CategoryExamplesWhen to use
Google AI APIs (prebuilt, task-specific)Vision, Video, Image, Audio, Search, Conversation APIsScenario needs one narrow capability (OCR, image labeling, speech-to-text) without building or hosting a model at all.
Gemini Enterprise featuresAI Agents, NotebookLMScenario needs a ready-made enterprise product experience (research/synthesis assistant, agent workspace) rather than an API you integrate into your own app.
Exam trap: a scenario asking to "extract text from scanned invoices" is the Vision API (prebuilt, task-specific) — not Agent Builder and not custom training. Reaching for the biggest/newest AI tool when a narrow prebuilt API solves it is a classic overkill wrong-answer pattern (same Operational Excellence logic from Session 1).

5. Cloud Run — brief, event-driven compute target

Deep dive was Session 2 (compute selection). Here it matters only as the thing events land on: Cloud Run runs stateless containers, scales to zero, and is a common destination for Eventarc triggers and Pub/Sub push subscriptions — "something happened, now run this container."

6. Pub/Sub — async messaging (you already know this from SNS/SQS)

Verified via docs.cloud.google.com/pubsub/docs/pubsub-basics: many-to-many async messaging. Publishers send to a topic; subscribers pull or get pushed messages via a subscription. At-least-once delivery, no ordering guarantee by default (ordering keys available if you need them).

AWS analogue: Pub/Sub topic ≈ SNS topic (fan-out) merged with SQS (durable queue) in one service — a Pub/Sub subscription already gives you the durable-queue behavior SQS provides separately in AWS. You don't chain an SNS topic into separate SQS queues; one Pub/Sub topic + multiple subscriptions does both jobs.

Exam trap: "decouple two services with guaranteed delivery and independent consumer scaling" is almost always Pub/Sub. Don't pick Cloud Tasks (that's for app-scheduled work queues you control the rate of) or Eventarc (that's for reacting to platform events, and often uses Pub/Sub as its transport anyway — see below).

7. Eventarc — event routing across GCP services

Verified via docs.cloud.google.com/eventarc/docs/overview and Google's Pub/Sub-trigger docs: Eventarc routes events from Google Cloud sources (audit logs, direct events like Storage object-finalize) and third-party providers to destinations like Cloud Run, Cloud Run functions, GKE, and Workflows — handling delivery, security, and retries for you. Confirmed detail: when you create an Eventarc trigger on a Pub/Sub topic, Eventarc uses a Pub/Sub topic as the transport mechanism under the hood — Eventarc is a routing/management layer on top of event sources, not a replacement for Pub/Sub.

Decision rule: Pub/Sub = you design the message and both ends yourself. Eventarc = you want to react to something a GCP service already did (a file landed in a bucket, a Cloud Build finished) without writing the plumbing.

Exam trap: "trigger a Cloud Run function whenever a file is uploaded to Cloud Storage" — this is Eventarc (it standardizes the Storage event and manages delivery/retries), not "write custom code to poll the bucket" and not raw Pub/Sub you wire up manually, even though Pub/Sub is running underneath.

8. Cloud Scheduler — cron-as-a-service

Verified via docs.cloud.google.com/scheduler/docs/overview: fully managed cron. Unix cron syntax, at-least-once delivery, fault-tolerant retries, no infrastructure to manage. Targets: HTTP endpoints, Pub/Sub topics, App Engine.

Exam trap: "run a batch job every night at 2am" is Cloud Scheduler, full stop — don't overthink it into a Cloud Composer/Workflows answer unless the scenario also needs multi-step orchestration logic, not just a time trigger.

9. Comparison table — trigger type is the fast filter

ServiceTrigger typeTypical use caseWhat triggers what
Pub/SubMessage (app-published)Decouple services; fan-out one event to many independent consumersA publisher app sends a message → any number of subscribers pull/receive it
EventarcEvent (GCP service or third-party event)React to platform state changes (file uploaded, resource created) without custom pollingA GCP service emits an event (often via audit log or direct event) → Eventarc routes it to Cloud Run/Functions/GKE/Workflows
Cloud SchedulerTime (cron schedule)Recurring batch jobs, nightly reports, periodic cleanupA clock fires on schedule → calls an HTTP endpoint or publishes to a Pub/Sub topic

So what: if the scenario names a specific moment in time → Scheduler. If it names something happening to a GCP resource → Eventarc. If it's your own app publishing arbitrary data for other services to consume → Pub/Sub. Scheduler and Eventarc both frequently use Pub/Sub as their delivery mechanism — that doesn't make them the same answer.

Try it — before reading the answer

Scenario: "Every time a new CSV file lands in a Cloud Storage bucket, run a Cloud Run function to validate and load it into BigQuery. This must happen automatically with no custom polling code." Which service is the primary trigger mechanism — Pub/Sub, Eventarc, or Cloud Scheduler — and why do the other two not fit?

Eventarc. The trigger is a GCP resource state change (object finalized in Cloud Storage), which is exactly Eventarc's job — it standardizes the Storage event and routes it to the Cloud Run function, managing retries/security for you. Cloud Scheduler is wrong because there's no fixed time interval, this is event-driven. Raw Pub/Sub is wrong as the primary answer because you'd have to build the Storage-to-topic plumbing yourself — Eventarc already does that (and uses Pub/Sub as transport underneath, but you don't manage that part).

Quiz — Session 10

Q1. What happened to the name "Vertex AI" as of the current exam guide period?

A. Verified against cloud.google.com/products/gemini-enterprise-agent-platform, subtitled "(formerly Vertex AI)" — same platform, evolved branding, announced April 2026. B/C/D are fabricated distractors; the platform didn't disappear or merge into BigQuery ML.

Q2. A scenario needs a pretrained foundation model with no custom training. Which component fits best?

A. Model Garden is the catalog of 200+ foundation models (Gemini, Claude, Gemma, Llama) ready to call without training. B/C/D are unrelated services with no model-selection role.

Q3. A scenario needs a multi-step agent that calls tools and reasons over documents. Best fit?

A. Agent Builder bundles the Agent Development Kit, Agent Studio, and Agent Garden specifically for building tool-using, multi-step agents. B/C/D solve completely different problems (scheduling, storage, network security).

Q4. A scenario needs OCR text extraction from scanned invoices, nothing more. Best fit?

A. The Vision API is a prebuilt, task-specific API — exactly matching a narrow, single-purpose need. B/C/D are all overkill: custom training, full agent orchestration, or self-managed infrastructure for a problem a single API call solves.

Q5. Which service is the underlying supercomputing layer for large-scale AI training across GPUs and TPUs?

A. AI Hypercomputer is the performance-optimized hardware/networking/framework layer named explicitly in exam guide sections 1.3 and 2.4. B/C/D handle scheduling, event routing, and CI builds — none provide accelerator infrastructure.

Q6. A scenario needs to decouple two services, letting many independent consumers each receive every published message. Best fit?

A. Pub/Sub is many-to-many async messaging — a topic fans out to multiple independent subscriptions, matching AWS SNS+SQS combined. B/C/D are unrelated to message fan-out.

Q7. A scenario says "run a nightly batch job at a fixed time, no event trigger involved." Best fit?

A. A fixed-time trigger with no dependency on a resource event is textbook Cloud Scheduler — managed cron. B/C/D are all event- or agent-driven, not time-driven.

Q8. A file lands in Cloud Storage and must trigger a Cloud Run function automatically, with no custom polling code written. Best fit?

A. Eventarc standardizes the Storage object-finalize event and routes it to Cloud Run, managing delivery/retries for you — even though Pub/Sub runs underneath as transport, you don't build that plumbing yourself. B doesn't fit (no fixed time). C/D both require you to hand-build what Eventarc already manages.

Recap
  • Vertex AI was renamed to Gemini Enterprise Agent Platform (April 2026) — same platform, expect both names on the exam; answer by function, not by brand name
  • Model Garden = pick a foundation model. Agent Builder = build a multi-step tool-using agent. Prebuilt Google AI APIs = one narrow task, no model management at all
  • AI Hypercomputer = the hardware/framework layer underneath large-scale training, not something you provision per-app
  • Pub/Sub = your own async messaging (AWS SNS+SQS combined). Eventarc = reacting to GCP service events, often using Pub/Sub as transport underneath. Cloud Scheduler = managed cron, pure time trigger
  • Fast filter: message → Pub/Sub, resource event → Eventarc, fixed time → Scheduler
