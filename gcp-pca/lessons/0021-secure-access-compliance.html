GCP PCA — Lesson 21 of 24

Secure remote access & compliance

Lessons 10-11 covered IAM and the core security tools. This lesson closes the rest of Section 3: how people and workloads connect in without a VPN, how AI-specific risk gets handled, and what "compliant" actually means as a design constraint, not a checkbox.

Simple example: a VPN is a key to the whole building. IAP is a bouncer at each door who checks your ID and the day's guest list every single time — no standing access, no lingering "I'm already inside" trust.

Secure remote access — no VPN required

  • Identity-Aware Proxy (IAP) — puts identity- and context-aware access control in front of an app or VM. Every request is checked against IAM, not just "is this IP on the VPN." This is Google's zero-trust (BeyondCorp) model: trust the request, not the network it came from.
  • Workload Identity Federation (WIF) — lets a workload running outside GCP (another cloud, on-prem, a CI/CD pipeline) authenticate using its own external identity, exchanged for short-lived GCP credentials. No downloaded service account key sitting in a repo or a CI secret store waiting to leak.
  • Chrome Enterprise Premium — browser-level security controls (data-loss prevention, malware protection) as another zero-trust layer, independent of network location.
Exam trap: if a scenario's problem is "we have long-lived service account keys checked into a CI pipeline," the answer is Workload Identity Federation — eliminating the key entirely — not "rotate the keys more often." Rotation manages the risk; WIF removes it.

Software supply chain security

Binary Authorization enforces that only signed, trusted container images can deploy to GKE or Cloud Run — a build that wasn't produced and attested by your pipeline is rejected before it ever runs. Combine with Artifact Registry's vulnerability scanning to catch known CVEs before deploy, not after.

Securing AI

  • Model Armor — screens prompts and model responses for AI applications (prompt injection, unsafe content) — a security layer specific to AI workloads, not general app security.
  • Sensitive Data Protection (the current name for what was Cloud DLP) — discovers and redacts sensitive data (PII, secrets) in text, structured data, or AI inputs/outputs.

Designing for compliance

Compliance isn't a separate architecture — it's a constraint on the one you're already designing.

  • Legislation/regulation — health data (HIPAA-equivalent handling), children's privacy, data sovereignty (data must stay in a specific region/country).
  • Commercial — PII and payment data (PCI-DSS-style handling) need explicit protection, not just "IAM is configured."
  • Industry certifications — SOC 2 attests to security/availability/confidentiality controls. Google Cloud's infrastructure is independently certified; what you build on top still needs its own controls to inherit that compliance — certification isn't automatic just because it runs on GCP.
  • Audits — Cloud Audit Logs (Admin Activity, Data Access, System Event, Policy Denied) are the evidence trail auditors actually ask for. See Lesson 12 for the logging mechanics.
Exam trap: "GCP is SOC 2 certified" does not mean your application is automatically compliant. Compliance is a shared responsibility — the platform's certification covers the platform, not your IAM policy, your data handling, or your app code.

Try it — before looking below

Q1. A CI/CD pipeline outside GCP currently authenticates using a downloaded service account key stored as a repo secret. What's the fix, and why is it better than key rotation?

Workload Identity Federation — the pipeline authenticates with its own native identity and gets short-lived GCP credentials, with no long-lived key to leak in the first place. Rotation reduces the exposure window; WIF removes the exposed key entirely.

Quiz — Lesson 21

Q1. What does Binary Authorization actually enforce?

A. It's a deploy-time gate on image provenance, not a network/traffic control.

Q2. True or false: running on GCP, which is SOC 2 certified, makes your application automatically SOC 2 compliant.

A. The platform being certified is necessary, not sufficient — your own IAM, data handling, and application controls still need to meet the standard.

Recap
  • IAP checks identity+context per request, replacing "on the VPN = trusted."
  • Workload Identity Federation removes long-lived service account keys for external workloads, it doesn't just rotate them.
  • Binary Authorization gates deploys on image provenance; Artifact Registry scanning catches known CVEs.
  • Platform certification (SOC 2) ≠ your application's compliance — it's shared responsibility.
