GCP PCA — Session 5 of 10 (Day 1)

IAM, resource hierarchy, and security & compliance

This is exam Section 3, "Designing for security and compliance" — 17.5%, tied for second-highest weight with Provisioning. You run IAM, Workload Identity Federation (WIF), and ESO/Vault daily on GKE in production — none of this is new to you conceptually. The gap is GCP-specific naming and the exam-trap distinctions Google loves to test: org policy vs IAM, Secret Manager vs KMS, VPC-SC vs IAM. That's where the depth goes.

1. IAM — roles, bindings, policy (fast recap, you know this)

Same model as AWS IAM: a policy binds principals (users, groups, service accounts) to roles (bundles of permissions) on a resource. Three role types (source):

TypeWhat it isExam signal
Basic (Owner/Editor/Viewer)Broad, legacy, project-wide"do not grant basic roles unless there is no alternative" — official guidance. Never the "BEST" answer.
PredefinedGoogle-created, service-scoped, granularDefault correct answer for "least privilege, low maintenance"
CustomYou assemble specific permissionsOnly when predefined roles are too broad AND you accept the maintenance cost (below)
Exam trap: custom roles are not maintained by Google. "Custom roles are static — they don't auto-update when Google adds new permissions to a service" (source). If a scenario says "minimize ongoing maintenance" AND "least privilege" both — predefined roles usually win over custom, because custom roles silently drift out of date and someone has to own that upkeep. Only pick custom when the scenario explicitly needs a permission set no predefined role offers.

2. Resource hierarchy & policy inheritance

AWS analogue: AWS Organizations + OUs + accounts, but GCP's hierarchy is a strict tree used for both IAM and org policy: Organization → Folder → Project → Resource.

IAM policy inheritance rule, verified: "The effective allow policy for a resource is the union of the allow policy set at that resource and the allow policy inherited from its parent" (source). Grant Editor at the org, and it applies to every folder/project/resource below — a child resource's IAM policy can only add access, never revoke what a parent granted. Example from the docs: grant Compute Admin at the project, and "the user can administer any Compute Engine VM in that project, regardless of the allow policy you set on each VM."

Exam trap: you cannot use IAM alone to "wall off" a sensitive project from an org-wide grant — IAM only ever unions permissions downward. If a scenario needs a hard exception ("nobody outside this project's team, even org admins with broad grants, should touch it"), the answer involves deny policies (an explicit block that overrides allow policies) or restructuring the hierarchy — not "just don't grant IAM roles there."

3. Organization Policy vs IAM — the classic trap

This is the single most-tested distinction in this session. They solve different problems:

IAMOrganization Policy
Question it answersWHO can act on a resourceWHAT configurations are allowed, regardless of who
Verified definition"IAM focuses on who... Organization Policy focuses on what, and lets the administrator set restrictions on specific resources to determine how they can be configured." (source)
Applies even to org admins?No — an Owner can do anything IAM allowsYes — a constraint blocks the action even for a project Owner
Example constraintsroles/editor, roles/storage.adminiam.disableServiceAccountKeyCreation, iam.allowedPolicyMemberDomains (domain-restricted sharing), gcp.resourceLocations (data residency) (source)
InheritanceUnion — child adds to parentAlso inherits down the hierarchy by default, can be overridden per node (source)
Exam trap: "prevent anyone from creating service account keys" is an org policy question (iam.disableServiceAccountKeyCreation), not an IAM question — no IAM role removal stops a permitted user from minting a key. Conversely, "prevent this specific engineer from deleting buckets" is IAM, not org policy — org policy has no concept of individual principals. If the scenario names a person/group/role, think IAM; if it names a resource property (region, external sharing, key creation, VM shielded settings), think Organization Policy.

4. Service Accounts & Workload Identity Federation (go deep — you use this daily)

AWS analogue: a service account ≈ an IAM role assumed by a workload; WIF ≈ AWS IAM Roles Anywhere / EKS IRSA (which you already run). Same mental model, different plumbing.

The core problem WIF solves: "service account keys are a security risk if not managed correctly... Workload Identity Federation eliminates the maintenance and security burden associated with service account keys" (source). Supported external IdPs: AWS, Azure, GitHub, GitLab, Kubernetes (GKE/on-prem), Okta, AD FS, Terraform — anything OIDC or SAML 2.0.

Three components, verified (source):

ComponentRole
Workload Identity PoolContainer for external identities — Google recommends one pool per non-GCP environment (dev/staging/prod), not one shared pool
Pool ProviderThe trust relationship with your specific IdP (AWS account, OIDC issuer, etc.)
Attribute MappingCEL expressions translating IdP token claims into GCP-usable attributes for IAM conditions

Flow: external credential → Google's Security Token Service exchanges it (OAuth 2.0 token exchange) → federated token → either used directly or to impersonate a service account for short-lived GCP credentials.

Service account impersonation: "an authenticated principal... authenticates as a service account to gain the service account's permissions" using short-lived tokens (hours or less, not auto-refreshed) instead of long-lived keys (source). WIF + impersonation is the pattern you already run: no downloaded key ever exists.

Exam trap: a scenario describing a CI/CD pipeline (e.g. GitHub Actions) that needs to deploy to GCP, where the "correct-looking but wrong" answer is "create a service account, download a JSON key, store it as a CI secret." That answer works but violates the security pillar — it's a long-lived credential outside Google's control. The exam-correct answer is WIF: no key ever leaves Google, and the trust is scoped to the specific repo/branch via attribute conditions.

5. Secret Manager vs Cloud KMS — the second classic trap

Secret ManagerCloud KMS
What it storesThe actual sensitive value — "API keys, usernames, passwords, certificates, and more" (source)Cryptographic keys, not secrets themselves
Can a caller read the raw value?Yes, if authorized — you fetch the plaintext secretNo — "users can't view, extract, or export the actual cryptographic secrets" (source); keys only encrypt/decrypt on request
VersioningYes — rollback to a previous known-good secret version, full audit of who changed what and whenYes — key versions, rotation schedules
AWS analogueSecrets ManagerKMS
When you need BOTHStore the secret's value in Secret Manager, encrypt Secret Manager's storage (or your app's other data at rest) with a customer-managed key (CMEK) in Cloud KMS. They compose — Secret Manager can be backed by a CMEK from KMS for the storage layer itself.
Exam trap: a question about rotating a database password should point you to Secret Manager (it stores and versions the value app code reads). A question about encrypting a BigQuery dataset or Cloud Storage bucket with a customer-controlled key you can revoke/rotate independently of Google's default encryption should point you to Cloud KMS + CMEK — not Secret Manager, which was never designed to hold bulk data encryption keys for a storage service.

6. VPC Service Controls vs IAM — perimeter vs identity

AWS has no exact equivalent — closest is a mix of VPC endpoint policies + SCPs, but VPC-SC is its own primitive. "A service perimeter creates a security boundary around Google Cloud resources... blocks communication to Google Cloud services across the perimeter" by default (source).

IAMVPC Service Controls
ControlsWho can call an API, granular per-identityWhether data can cross a perimeter boundary at all, regardless of identity's IAM grants
Verified relationship"VPC Service Controls provides an extra layer of security defense... that is independent of IAM. While IAM enables granular identity-based access control, VPC Service Controls enables broader context-based perimeter security" (source)
Threat it stops that IAM alone can'tA correctly-authorized (valid IAM) but compromised or malicious insider copying data OUT of Cloud Storage/BigQuery to a personal project. IAM says "yes you may read this bucket" — VPC-SC says "but you may not move that data across this boundary." Explicitly: "Data cannot be copied to unauthorized resources outside the perimeter using service operations such as gcloud storage cp or bq mk" (source)
Exam trap: "prevent data exfiltration even by an authorized insider with valid credentials, including via a misconfigured IAM policy" is the exact phrase that means VPC-SC, not IAM and not firewall rules. Firewall rules control network-layer packet flow (L3/L4); VPC-SC controls API-layer access to managed services (Cloud Storage, BigQuery, etc.) regardless of network path. If the scenario is about a managed service's data leaving a boundary, not about network packets, VPC-SC is the answer even when IAM already looks "correctly" configured.

7. Identity-Aware Proxy (IAP) — brief

AWS analogue: replaces a bastion host / VPN for admin access. "IAP lets you establish a central authorization layer for applications accessed by HTTPS, so you can use an application-level access control model instead of relying on network-level firewalls" — access is granted "without requiring a VPN" (source). Works in front of App Engine, Cloud Run, Compute Engine, GKE.

Use when: you need SSH/RDP or app access for humans without standing up a VPN or bastion. Not for: service-to-service auth (that's WIF/service account impersonation) or workload-to-workload traffic inside a VPC (that's firewall + IAM).

8. Securing the software supply chain — brief

AWS analogue: think CodeArtifact + a signing/attestation layer, though GCP's story is more built-out here. Two pieces, verified (source):

  • Artifact Registry — "universal package manager for all your build artifacts and dependencies" — the trusted, scanned source of images/packages.
  • Binary Authorization — "collects attestations, which are digital documents that certify images," and enforces that only images meeting policy (e.g. built by your CI, scanned, signed) can deploy to GKE/Cloud Run/Distributed Cloud.

Cloud Build natively supports SLSA Level 3 builds (isolated, ephemeral build environments + non-falsifiable build provenance) — if a scenario mentions "verifiable build provenance" or "only deploy signed/attested images," think Binary Authorization + Artifact Registry + Cloud Build provenance together.

9. Compliance (Section 3.2) — brief

Exam guide bullets: legislation (health record privacy, children's privacy, data privacy, data sovereignty), commercial (PII, credit card data), industry certs (e.g. SOC 2), audits (including logs). Mental model: this section is less "which service" and more "which control satisfies which requirement" — data sovereignty/residency → Organization Policy gcp.resourceLocations (Section 3 above); audit trail → Cloud Audit Logs (Admin Activity logs are always on and cannot be disabled); PII/credit card → Sensitive Data Protection (formerly DLP) for discovery/classification, paired with the encryption controls above.

Try it — before reading the answer: A scenario says: "A contractor from a partner company needs read-only access to run BigQuery queries against one dataset in your project. They must never be able to export or copy query results outside your organization's boundary, even though they'll be granted the BigQuery Data Viewer role." What two controls does this scenario need, and why is IAM alone insufficient?
IAM (BigQuery Data Viewer, scoped to that one dataset — least privilege) grants the read access. But IAM alone cannot stop an authorized principal from exporting/copying data out once they can read it — that's exactly the exfiltration gap VPC Service Controls closes. The answer is IAM for least-privilege read access + a VPC-SC perimeter around the project/dataset so query results and exports can't leave the boundary, even though the contractor's IAM grant is valid. This is the "authorized but should still be contained" pattern the exam tests repeatedly.

Quiz — Session 5

Q1. A scenario requires blocking creation of service account keys org-wide, even for project Owners. What's the correct control?

A. constraints/iam.disableServiceAccountKeyCreation is an org policy constraint — it blocks the action regardless of who holds it, including Owners. B and D are IAM changes, which only control who has a role, not whether the action itself is blocked. C (VPC-SC) governs data movement across a perimeter, not key creation.

Q2. Which statement correctly distinguishes IAM from Organization Policy?

A. Verified from the docs: IAM focuses on who, Organization Policy focuses on what/how resources can be configured. B reverses the definitions. C and D are false — they're complementary, not identical or substitutable.

Q3. A CI/CD pipeline in GitHub Actions needs to deploy to GCP. What is the exam-correct approach?

A. WIF eliminates the need for any long-lived key to leave Google's systems — the pipeline authenticates as its GitHub OIDC identity and impersonates a scoped service account for short-lived credentials. B is the classic "works but violates security pillar" distractor. C and D are outright anti-patterns.

Q4. Which service lets an authorized user retrieve the actual plaintext value it stores?

A. Secret Manager returns the plaintext secret to an authorized caller. Cloud KMS never exposes the key material — it only performs encrypt/decrypt operations on your behalf. This is the core distinction the exam tests: "store a value" vs "manage a key."

Q5. An authorized contractor has valid BigQuery Data Viewer access but must never export data outside the org boundary. What closes this gap?

A. IAM already authorizes the read (B/D just adjust IAM, which can't prevent exfiltration by a validly authorized principal). Firewall rules (C) operate at the network packet layer, not the BigQuery/Cloud Storage API layer. VPC-SC is purpose-built to block data leaving the perimeter regardless of valid IAM grants.

Q6. Why are custom IAM roles a maintenance risk compared to predefined roles?

A. Predefined roles are created and maintained by Google — new permissions get added automatically as services evolve. Custom roles are static; you must manually add new permissions or they silently drift behind service capabilities. B/C/D are false claims about custom roles.

Q7. A scenario requires all Cloud Storage buckets to be created only in EU regions, enforced even against project Owners. What's correct?

A. constraints/gcp.resourceLocations rejects resource creation outside approved regions at the API layer, before the resource exists — enforced regardless of the caller's IAM role. B only restricts what Owner can do with IAM actions, not where resources land. C and D don't govern resource location.

Q8. A scenario needs "only deploy container images that were built by our CI pipeline and passed a vulnerability scan" onto GKE. What enforces this?

A. Binary Authorization enforces deploy-time policy based on attestations (digital proof of who built/scanned an image); Artifact Registry is the trusted source those images come from. B is a network control unrelated to image provenance. C protects data at rest, not build provenance. D governs sharing outside allowed domains, unrelated to deployments.

Recap
  • IAM = who; Organization Policy = what/how, regardless of who — the #1 tested distinction this session
  • Predefined roles auto-update from Google; custom roles are static and need manual upkeep — pick custom only when you accept that cost
  • IAM policy inheritance is a strict union down the hierarchy; deny policies are the one mechanism that can override an inherited allow
  • WIF + service account impersonation eliminates downloaded keys — the exam-correct answer whenever a workload (CI/CD, another cloud) needs GCP access
  • Secret Manager stores retrievable values; Cloud KMS manages keys you can never extract — they compose, they don't substitute
  • VPC-SC blocks data movement across a perimeter independent of IAM — the answer whenever a scenario worries about exfiltration by an already-authorized identity
  • IAP replaces VPN/bastion for human access; Binary Authorization + Artifact Registry secure what gets deployed

If you can't cleanly separate them, that's the gap this session was for.
