Storage lifecycle & data protection

Lesson 5 covered choosing a storage type. This lesson is what happens to data after it's written — most storage cost in a mature system comes from data nobody configured a lifecycle for, sitting in the most expensive class forever.

Simple example: a lifecycle rule is a standing instruction to your storage: "if this file turns 90 days old, move it to the cheap shelf. If it turns a year old, throw it out." You write the rule once; it runs forever without you.

Object Lifecycle Management

Rules on a Cloud Storage bucket, evaluated automatically, that can transition an object to a cheaper storage class or delete it, based on conditions like age, storage class, or number of newer versions.

{
  "rule": [{
    "action": {"type": "SetStorageClass", "storageClass": "COLDLINE"},
    "condition": {"age": 90}
  }]
}
ClassTypical use
StandardAccessed frequently
NearlineAccessed roughly monthly
ColdlineAccessed roughly quarterly
ArchiveAccessed roughly yearly or less

All four classes have the same millisecond access latency — the difference is storage price vs. retrieval price and minimum storage duration, not speed.

Retention — the opposite control

A bucket retention policy stops objects from being deleted or overwritten before a set period — the opposite direction from a lifecycle rule. Bucket Lock makes that retention policy permanent and unremovable, satisfying regulatory requirements that data can't be tampered with or deleted early (WORM: write once, read many). This is what "compliance" from Lesson 22 actually looks like configured, not just discussed.

Exam trap: a lifecycle rule and a retention policy can conflict — a lifecycle "delete after 30 days" rule cannot delete an object a retention policy still protects. Retention always wins; that's the point of it.

Data protection & growth planning

  • Object versioning — keeps prior versions when an object is overwritten, protecting against accidental overwrite (not the same as backup — still one bucket, one failure domain).
  • Backup and DR service — GCP's centralized backup for Compute Engine, Cloud SQL, and GKE workloads, separate from storage-class lifecycle management.
  • Growth planning — forecasting storage growth against class choice and lifecycle rules up front avoids a painful, disruptive re-tiering project later. This is a design-time decision, not something to bolt on after the bucket is already full.

Try it — before looking below

Q1. Compliance requires that uploaded audit logs cannot be deleted for 7 years, even by an admin. Lifecycle rule, or something else?

Bucket Lock with a 7-year retention policy — a lifecycle rule only automates transitions/deletions, it doesn't prevent them. Retention + Bucket Lock is the control that makes deletion impossible, even for an admin, until the period expires.

Quiz — Lesson 22

Q1. What's the actual difference between Standard and Archive storage classes?

A. All classes are millisecond-latency — the tradeoff is entirely storage cost vs. retrieval cost vs. minimum duration, never speed.

Q2. A lifecycle rule says "delete after 30 days," but a retention policy protects the same object for 1 year. What happens at day 30?

A. Retention policies always override lifecycle deletion — that's their entire purpose.

Recap
  • Lifecycle rules automate class transitions/deletion by age or version count.
  • Retention + Bucket Lock does the opposite — prevents deletion, even by an admin, until the period expires.
  • All storage classes have the same access latency — the tradeoff is cost and minimum duration, not speed.
  • Versioning protects against accidental overwrite; it is not a substitute for backup.
