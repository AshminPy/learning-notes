Migration strategies, Migration Center, and the programmatic-tooling facts (Section 5.2)

This session covers exam Section 1.4, "Creating a migration plan" (part of the 25%-weighted Design & plan section), plus a compact pass through Section 5.2, "Interacting with Google Cloud programmatically" (12.5% weight). 5.2 has no dedicated session in the original 10-topic plan — migration tooling is the closest conceptual fit, so it's folded in here rather than skipped. Keep the two halves mentally separate: migration strategy is scenario-judgment, 5.2 is pure fact-recall.

1. Migration strategies — the exam's core three, plus a fourth

You already know AWS's "6 Rs" (Rehost, Replatform, Repurchase, Refactor, Retire, Retain). Google's own framework is close cousin: rehost, replatform, refactor, re-architect, rebuild, repurchase (verified at Migrate to Google Cloud: Get started). The PCA exam mostly tests you on three tiers, and a fourth strategy that isn't a tier at all:

  • Lift and Shift / Rehost — move the workload "with minor or no modifications." Fastest, uses skills your team already has, but the workload isn't optimized for cloud once it lands.
  • Replatform (Lift and Optimize) — lift it, then optimize for the cloud environment — e.g. swap a self-managed DB for Cloud SQL, containerize without a full rewrite. Google's framing: "take advantage of all the core competencies of the cloud, including elastic computing, redundancy, improved performance, and security."
  • Refactor (Rearchitect) — modify the workload to genuinely take advantage of cloud capabilities: "improve each workload for performance, features, cost, and user experience."
  • Hybrid/multicloud coexistence — not a migration phase, a deliberate long-term architecture. Google defines hybrid as public cloud + at least one private environment (on-prem/colo), and multicloud as 2+ public CSPs together (Hybrid and multicloud architecture patterns). Drivers the exam cares about: data sovereignty/regulatory residency, business continuity/DR across providers, and avoiding vendor lock-in — not "we haven't finished migrating yet."

All four bullets can be true in the same scenario: "different application layers might use different strategies — a database might get replatformed while the application layer gets rehosted" (same source). Don't assume one scenario has one answer.

Exam trap — the "obviously better" answer is often the wrong one. If a scenario states a hard deadline ("data center lease ends in 6 weeks," "must exit by end of quarter") with no long-term cost goal mentioned, the exam wants Rehost — even when Refactor is technically the architecturally superior long-term choice. This is the same elimination algorithm from Session 1: the constraint keyword ("hard deadline") points at the pillar being tested (time-to-migrate, not cost optimization). Picking Refactor here is a classic distractor — it's a real Google best practice, just for a different scenario (no deadline pressure, team has engineering capacity, long-term TCO stated as the goal).

2. Google Cloud Migration Center — the assessment tool

Migration Center is the named tool the exam expects you to recognize for Section 1.4's "assessing and migrating systems... e.g., Google Cloud Migration Center." Verified capabilities (Migration Center overview):

  • Discovery — inventories servers, VMs, and MySQL/PostgreSQL/SQL Server databases via automatic scanning or manual import, using a discovery client.
  • Cost estimation — rapid and detailed cost estimates, plus formal TCO (total cost of ownership) reports for building a migration business case.
  • Assessment — technical-fit recommendations for which Google Cloud product to target, application/network dependency mapping, and migration risk assessment run in parallel with discovery.
  • Planning — organizes work into migration waves (apps sharing characteristics/interdependencies) and move groups, sequenced across environments (R&D → pre-production → production) (migration planning overview). Migration Center's own strategy list is the six-way one: rehost, replatform, refactor, re-architect, replace, retire.

Exam framing: Migration Center does discovery/assessment/planning without making changes to your applications or workloads — it's an assessment tool, not a migration-execution tool. If an option describes Migration Center actually moving data, that's wrong.

3. Migration methodology basics

Google's 4-phase framework is Assess → Plan → Deploy → Optimize (source). Inside "Assess/Plan," four things the exam names explicitly:

  • Workload testing — validate the migrated workload behaves correctly before cutover; part of the Deploy phase's iterative approach.
  • Network and dependency planning — Migration Center's dependency mapping exists precisely because you can't safely rehost App A if you haven't mapped that it talks to Database B over a path that won't exist post-migration.
  • License implications (BYOL) — per-core/per-processor licenses (classic case: Windows Server, SQL Server) with dedicated-hardware requirements need sole-tenant nodes on Compute Engine. Not all licensing needs this — Linux BYOS (RHEL/SLES) and most Microsoft application licensing don't require sole tenancy, but Windows Server BYOL does (Bringing your own licenses).
  • Financial impact (TCO) — Migration Center's TCO reports are the named mechanism for this; it's assessed early (Assess phase) and tracked into the business case, not bolted on after the fact.

5. Section 5.2 — programmatic interaction tooling (folded in here, exam-fact recall only)

Why it's here: Section 5.2 (12.5% of the exam) has no dedicated session in the original plan. It's grouped with migration because "data and system migration and management tooling" sits in the same exam area (Section 5.1). Ashmin uses Terraform daily — this section is deliberately brief, it's testing recall of tool names and purposes, not teaching Terraform.

  • Cloud Shell Terminal — free browser-based shell, pre-authenticated with your identity, gcloud/gsutil/bq pre-installed.
  • Cloud Shell Editor — the built-in code editor inside Cloud Shell, based on Theia; browse/edit files while keeping terminal access (editor overview).
  • Cloud Code — IDE extension (built into Cloud Shell Editor, also available for VS Code/IntelliJ) giving IDE support for the full GKE/Cloud Run dev cycle without leaving the editor (Cloud Code overview).
  • gcloud CLI — the primary CLI for Google Cloud administrative tasks (Cloud SDK overview).
  • gsutil — the legacy Cloud Storage CLI. Current official guidance: use `gcloud storage` instead — gsutil doesn't support newer features like soft delete and managed folders (gsutil tool docs). If a question asks for the current recommended CLI for Cloud Storage, gsutil is the trap answer, not the right one.
  • bq — the BigQuery command-line tool.
  • Emulators — Bigtable, Spanner, Pub/Sub, and Firestore all ship local emulators so client code can be developed/tested without touching production billing or quota.
  • IaC / Terraform — Google's own docs call Terraform "the most commonly used tool to provision and automate Google Cloud infrastructure," with two providers: `google` (GA APIs) and `google-beta` (beta APIs) (Terraform on Google Cloud overview).
  • API client libraries — Cloud Client Libraries in Python, Java, Node.js, Go, Ruby, C++, PHP, .NET for idiomatic programmatic access, alongside documented API best practices.
  • Gemini Cloud Assist (Section 5.1) — AI assistant across design/deploy/troubleshoot/optimize, currently in preview and free (Gemini Cloud Assist overview).

Try it — before reading the answer

Scenario: A retailer runs 200 VMs on VMware for a monolithic Java app. The on-prem data center contract ends in 8 weeks — hard deadline, no extension possible. Leadership separately wants to eventually break the monolith into microservices, but that's an unfunded "phase 2" with no timeline. Which migration strategy do you pick for phase 1, and why doesn't "refactor is architecturally better" win here?

Rehost (lift and shift). The constraint keyword is "8 weeks, hard deadline" — that's a time-to-exit pillar, not a cost-optimization or architecture pillar. Refactor is real, valid, and probably true long-term, but it doesn't fit the stated constraint, and the exam always prioritizes the constraint actually given over a generically "better" answer. Phase 2 (refactor to microservices) can happen later, once the workload is safely off VMware and the deadline pressure is gone — that's literally why Google's own guidance says different layers/phases can use different strategies over time.

Quiz — Session 9

Q1. Google's official migration framework names three core strategies most tested on the exam. Which set matches Google's own terms?

A. Rehost, replatform, refactor are the three tiers the exam drills, drawn directly from Google's "Migrate to Google Cloud" framework. B is invented (not Google's naming). C is a data-pipeline concept (ETL), unrelated to migration strategy. D describes backup/DR operations, not a migration path.

Q2. What is Google Cloud Migration Center primarily used for?

A. Confirmed from the official overview: Migration Center does asset discovery, technical-fit assessment, dependency mapping, and cost/TCO estimation — without touching your actual workloads. B describes GKE, not Migration Center. C describes Cloud Monitoring/Ops. D describes Cloud Billing, a separate product.

Q3. Which statement best describes a Rehost (lift and shift) migration?

A. Google's own wording: rehost moves workloads "with minor or no modifications." B describes Rebuild/Refactor. C describes Repurchase (moving to a SaaS equivalent). D describes Replatform or Refactor, both of which intentionally adopt cloud-native capabilities — rehost explicitly does not.

Q4. A scenario states a hard 6-week deadline to exit a data center lease, with no mention of long-term cost goals. Which strategy does the exam want?

A. The constraint keyword is the hard deadline, which points at speed, not cost or architecture. B and C are real strategies but solve a different stated problem (long-term cost/architecture) that this scenario never mentions — classic distractor pattern. D assumes a SaaS equivalent exists, which isn't stated and isn't a safe assumption.

Q5. Which Compute Engine feature supports per-core BYOL licenses that require dedicated hardware?

A. Per official docs, per-core/per-processor licenses with dedicated-hardware requirements (e.g. Windows Server BYOL) need sole-tenant nodes. B and C are cost-optimization mechanisms, unrelated to licensing compliance. D lets you size a VM's vCPU/memory, not a licensing feature.

Q6. A regulated bank must keep certain data on-premises permanently while running new analytics workloads in Google Cloud. Which strategy fits best?

A. "Permanently on-prem for some data" plus "new workloads in cloud" is the textbook hybrid driver: data sovereignty/regulatory residency. B contradicts the stated constraint (some data must stay on-prem forever). C doesn't fit a regulated bank with data-residency needs. D is about cost leverage, not the compliance constraint actually stated.

Q7. Which Google Cloud emulators let you test client code locally without connecting to production?

A. Bigtable, Spanner, Pub/Sub, and Firestore all ship official local emulators for exactly this. B, C, and D name real services, but none of them ship a local emulator in the way these data/messaging services do.

Q8. Which official Google guidance applies to gsutil today?

A. Official Cloud Storage docs now recommend `gcloud storage` over gsutil — it's faster and supports newer features (soft delete, managed folders) that gsutil doesn't. B is the outdated recommendation. C is wrong tool (bq is for BigQuery). D is an IDE extension for GKE/Cloud Run, unrelated to object storage.

Recap
  • Three core strategies: Rehost (fast, unoptimized) → Replatform (optimize without rewrite) → Refactor (full cloud-native redesign) — plus hybrid/multicloud as a deliberate 4th strategy, not a leftover migration phase
  • Migration Center = discovery + assessment + cost/TCO + dependency mapping, all before touching workloads — it plans, it doesn't migrate
  • Exam trap: a hard deadline overrides "architecturally better" every time — match the strategy to the stated constraint, not to best practice in the abstract
  • BYOL with dedicated-hardware requirements (e.g. Windows Server) → sole-tenant nodes; not all BYOL needs this
  • Section 5.2 tooling (folded in here): Cloud Shell/Cloud Code, gcloud (not gsutil), bq, emulators, Terraform (`google`/`google-beta` providers), client libraries, Gemini Cloud Assist — recall the names, not the syntax

Try solo: pick one system you actually run today (even something at your day job) and decide, out loud, which of Rehost/Replatform/Refactor you'd choose if GCP gave you a 4-week deadline vs. a 12-month runway. Notice how the answer flips purely on the timeline, not on which is "objectively best."
