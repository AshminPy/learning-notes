GCP PCA — Lesson 18 of 24

Interacting with GCP programmatically

Everything in this course so far has been "which service." This lesson is "how do you actually touch it" — the console is one option, and the exam expects you to know the others exist and when each fits.

Simple example: the Console is a showroom — good for browsing, bad for repeating the same order 500 times. The CLI, SDKs, and Terraform are the ordering system a real operation actually runs on.

Cloud Shell & Cloud Code

  • Cloud Shell — a free, browser-based terminal with gcloud, kubectl, and common tools preinstalled, plus 5GB of persistent home-directory storage. No local setup, but it's ephemeral compute — not for anything long-running.
  • Cloud Code — an IDE extension (VS Code, IntelliJ) for writing and deploying to GKE/Cloud Run without leaving the editor.

The three CLIs

ToolWhat it's for
gcloudEverything else — Compute, IAM, networking, most resources
gcloud storageCloud Storage (Google's current recommended path — replacing the older gsutil)
bqBigQuery specifically — queries, datasets, jobs
Exam trap: gsutil still exists and still works, but Google's own current guidance is gcloud storage for new scripts. If the exam asks "what's recommended now," don't default to the older name just because it's more familiar.

Cloud Emulators

Local, in-memory stand-ins for Bigtable, Spanner, Pub/Sub, and Firestore — so you can develop and test against them without touching real cloud resources or paying for them. Start one with gcloud emulators <service> start, point your app's client library at the emulator's local endpoint instead of the real API.

Infrastructure as Code — Terraform

The exam guide names Terraform specifically as the IaC example. Declarative: you describe the desired resources, Terraform diffs that against real state and applies only the difference — the same idea as a Kubernetes reconcile loop, applied to cloud infrastructure itself instead of one cluster's objects.

API client libraries

Language-specific SDKs (Python, Go, Java, Node...) generated from Google's API definitions — call GCP services as native functions instead of hand-building REST requests. Same underlying API either way; client libraries just save you the HTTP plumbing.

Try it — before looking below

Q1. A team wants to provision the same VPC + subnet layout identically across 5 projects, repeatably, with a reviewable diff before each change. Console, gcloud script, or Terraform?

Terraform. A one-off gcloud script can create resources but doesn't track state or show a diff before applying — Terraform's whole value is "here's exactly what will change, before it changes."

Quiz — Lesson 18

Q1. Which tool would you reach for to test Firestore-backed code locally without touching a real project?

A. Cloud Emulators exist exactly for this — local, free, no real-resource risk while developing.

Q2. What's Google's current recommended CLI path for Cloud Storage operations?

A. gsutil still works, but gcloud storage is the current recommended path — a classic "the old name is still valid, but isn't the best current answer" exam trap.

Recap
  • Cloud Shell/Cloud Code = no local setup, browser or IDE-based access.
  • gcloud for most things, gcloud storage (not gsutil) is current for Cloud Storage, bq for BigQuery.
  • Cloud Emulators let you develop against Bigtable/Spanner/Pub/Sub/Firestore locally, for free.
  • Terraform is the exam's named IaC tool — declarative, diffed, repeatable.
Stuck? Re-read the docs link above — that's the habit the real exam requires anyway.
