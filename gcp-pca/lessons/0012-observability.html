Observability: Monitoring, Logging, Trace

Three tools that answer three different questions about your system.

Simple example: think of a doctor checking a patient. Cloud Monitoring is the heart rate monitor — is the patient okay right now? Cloud Logging is the patient's diary — what happened, and when? Cloud Trace is an X-ray of one visit — which part of the body (or which service call) is slow.

Cloud Monitoring — "is it healthy?"

Metrics, dashboards, uptime checks, alerts. Use it for latency, error rate, and "is the system up right now."

Cloud Logging — "what happened?"

Stores and searches log entries — the audit trail. Use it to find out why something broke, or who did what.

Cloud Trace — "where's the slow part?"

Follows one request as it hops between services, timing each hop. Use it to find which service is slow in a chain of calls.

Exam trap: Cloud Trace does not capture every single request — it samples. On Cloud Run the default is about one request every 10 seconds. If a scenario needs a guaranteed trace of one specific critical request, the answer is "force-trace that request," not "Trace already logs everything."

Try it — before looking below

Q1. Your team wants to know if the app is up and check latency right now. Which tool?

A. "Is it healthy right now" is exactly what Monitoring's metrics, dashboards, and alerts are for.

Q2. A request is slow, and you need to find which one of five microservices is causing the delay. Which tool?

A. Trace times each hop across services, so it's the tool that finds the slow one.

Q3. A scenario needs a guaranteed trace of one specific rare, critical request. What's the catch with Cloud Trace's default behavior?

A. Trace samples by default (e.g. roughly one request per 10 seconds on Cloud Run) — you must force-trace the specific request to guarantee it's captured.

Recap
  • Monitoring = is it healthy. Logging = what happened. Trace = where's the delay.
  • Trace samples requests by default — it does not capture everything.
