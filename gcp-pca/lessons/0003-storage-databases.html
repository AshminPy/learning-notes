GCP PCA — Session 3 of 10 (Day 1)

Storage & databases: picking the right service under a constraint

This is the core of exam Section 1.3 (choosing storage/data-processing solutions) and Section 2.2 (configuring individual storage systems — capacity, security, latency, retention, growth, backup) — together a meaningful slice of that 25%-weighted Design & Plan section. You already run Postgres/MySQL on RDS, key-value on DynamoDB, and blobs on S3 in production. The gap is GCP's naming and — more importantly — three services with no clean AWS 1:1 (Spanner, Bigtable, BigQuery) that the exam loves to test against each other.

1. Object, block, and file storage

Cloud Storage — object storage

AWS analogue: S3. Purpose: durable, HTTP-addressable object storage in buckets. Best for static assets, backups, data lake landing zone, ML training data, anything read/written as a whole blob rather than mounted as a filesystem.

ScalabilityEffectively unlimited objects per bucket; hierarchical namespace buckets get up to 8x higher QPS for read/write
ConsistencyStrong global consistency for read-after-write, read-after-metadata-update, read-after-delete, and bucket/object listing — across all storage classes, including multi-region
Cost shapePer-GB by storage class (Standard/Nearline/Coldline/Archive) + per-operation + egress
Exam trap: older material (and outdated exam-prep sites) still say "GCS is eventually consistent, unlike S3." Both are now strongly consistent for object data (verified — Cloud Storage consistency). The part that's still eventually consistent is IAM/ACL permission grants and revokes — "it typically takes about a minute... in some cases, several minutes longer." A scenario testing "revoke access must take effect instantly" is a trap toward Cloud Storage ACLs.

Persistent Disk — block storage

AWS analogue: EBS. Purpose: network block storage attached to a Compute Engine VM (or GKE node). Best for VM boot disks and low-latency database storage that needs a real filesystem, not an object API.

ScalabilityUp to 64 TiB per disk, up to 257 TiB combined across up to 127 disks per VM
ConsistencyZonal (single zone, redundant across physical drives) vs Regional (synchronous replication across 2 zones in one region)
Cost shapePer-GB-month by type (Standard/Balanced/SSD/Extreme); regional disks cost roughly 2x zonal for the same type
Exam trap: Persistent Disk is zonal by default (verified — Persistent Disk docs). Unlike the assumption "cloud storage just survives failures," a zonal disk is gone if that zone has an outage — you must explicitly provision a Regional PD (or design around snapshots/backups) if the scenario says "must survive a zone failure."

Filestore — file storage

AWS analogue: EFS. Purpose: managed NFS, mountable by many clients at once. Best for GKE ReadWriteMany volumes, HPC/render farms, and lift-and-shift apps that need a real POSIX filesystem.

ScalabilityMultiple tiers (Basic legacy, Zonal, Regional, Enterprise multishare-for-GKE) spanning GB to 100+ TiB
ConsistencyRegional/Enterprise tiers use strict consistency — "acknowledging writes only after they are persisted"; Zonal/Basic tiers don't carry that zone-redundancy guarantee
Cost shapePer-GB-hour by tier; Enterprise is priced well above Zonal, which is above Basic
Exam trap: a "mission-critical, multi-zone GKE" scenario paired with the Basic/legacy tier is a mismatch — Basic has no cross-zone redundancy (verified — Filestore overview). If the scenario says "continuous availability," it's naming the Regional or Enterprise tier, not "any Filestore instance."

2. Relational databases

Cloud SQL

AWS analogue: RDS. Purpose: managed MySQL, PostgreSQL, or SQL Server. Best for single-region OLTP and lift-and-shift of existing relational apps where you don't need global scale.

ScalabilityVertical (bigger machine) + read replicas for read scaling; no built-in write sharding; storage up to 64 TB on dedicated-core instances
ConsistencyStrong, single-primary. HA ("regional instance") = synchronous replication to a standby across 2 zones within one region
Cost shapePer vCPU/RAM/storage-hour; enabling HA roughly doubles instance cost (you're paying for the standby)
Exam trap: Cloud SQL HA protects against a zone failure, not a region failure — the primary and standby both live in the same region (verified — Cloud SQL HA docs). A scenario needing multi-region durability or a global write path is signaling Spanner, not "just enable Cloud SQL HA."

Cloud Spanner

AWS analogue: none direct. Aurora Global Database and DynamoDB Global Tables both trade off either synchronous multi-region writes or strong consistency — Spanner is the one service that gives you both relational SQL and synchronous multi-region strong consistency, which is exactly why it's exam-famous. Purpose: horizontally scalable, globally distributed relational DB.

ScalabilityHorizontal — add nodes/processing units, scales to petabytes without resharding your schema
ConsistencyExternal consistency (stronger than plain "strong consistency") via TrueTime: "the system guarantees that clients can never see a state that includes the effect of the second transaction but not the first" (verified — TrueTime & external consistency)
Cost shapePer-node or per-processing-unit-hour + storage — priced for scale; expensive relative to Cloud SQL at small size
Exam trap: Spanner is often the "technically best" answer (global, strongly consistent, relational, ACID) — but if the scenario says single-region and cost-sensitive, that's the Well-Architected Cost Optimization pillar overriding "best" with "right-sized." Don't reflexively pick Spanner just because it can do everything; pick it when the scenario names global scale or global strong consistency as a hard requirement.

3. NoSQL databases

Firestore

AWS analogue: DynamoDB (plus real-time sync, closer to DynamoDB + AppSync combined). Purpose: serverless NoSQL document database. Best for mobile/web apps needing offline sync, real-time collaborative state, user profiles/session data.

ScalabilityAutomatic, but new collections should ramp gradually — Google's own "500/50/5" guidance: start at 500 ops/sec, increase 50% every 5 minutes
ConsistencyNative mode gives "strongly consistent queries across the entire database" (verified — Firestore modes)
Cost shapePer-operation (document read/write/delete) + storage
Exam trap: "automatic scaling" doesn't mean instant scaling. A sudden traffic spike against one new collection can hit a hotspot even though Firestore is serverless (verified — reads/writes at scale) — same class of trap as a DynamoDB hot partition. A scenario describing a traffic spike into a brand-new collection is testing whether you know the ramp-up rule, not whether Firestore "can scale."

Bigtable

AWS analogue: no direct equivalent — closest conceptually is a wide-column store like DynamoDB for key-value access, but Bigtable's linear-with-nodes throughput model and native HBase API have no single AWS match; call it out as GCP-unique on the exam. Purpose: massive-scale, low-latency wide-column NoSQL. Best for time-series, IoT, adtech clickstream, financial tick data, ML feature stores.

ScalabilityLinear with cluster nodes — SSD clusters: up to ~17,000 reads/sec and ~14,000 writes/sec per node (1 KB rows), scans up to 220 MBps/node (verified — Bigtable performance)
ConsistencyStrong on single-cluster instances; multi-cluster instances default to eventual consistency (configurable to read-your-writes or strong via app profile)
Cost shapePer-node-hour (cluster is provisioned, not serverless) + per-GB storage
Exam trap: multi-cluster Bigtable is eventually consistent by default — assuming "Google managed = always strongly consistent" is exactly the wrong instinct here. Also: Bigtable has no SQL, no joins, no multi-row ACID — a scenario needing complex queries over a small dataset is not a Bigtable scenario no matter how "high scale" the wording sounds.

4. Analytics warehouse

BigQuery

AWS analogue: Redshift + Athena combined — provisioned-warehouse SQL like Redshift, serverless pay-per-scan like Athena, but with storage and compute natively separated. Purpose: serverless OLAP data warehouse. Best for BI dashboards, ad-hoc SQL analytics, BigQuery ML, log/event analytics at petabyte scale.

ScalabilityServerless, auto-scaling compute; storage and compute scale independently; "query terabytes in seconds and petabytes in minutes"
ConsistencySupports ACID multi-statement transactions with snapshot isolation; automatic replication for availability
Cost shapeOn-demand = pay per TB scanned, OR flat-rate/Editions = provisioned slot capacity; storage billed separately, with long-term (90-day-unmodified) data discounted (verified — BigQuery pricing)
Exam trap: BigQuery is an OLAP engine — query latency is seconds, not milliseconds, and on-demand billing scans whole columns unless the table is partitioned/clustered. A scenario asking for low-latency point lookups, or "frequent small queries, cost-sensitive, unpartitioned," is a trap toward BigQuery: partitioning/clustering isn't optional at that shape, or the cost model blows up.

Try it — before reading the answer

Scenario: "A global ad-bidding platform needs a relational schema with joins, strict transactional consistency between a US region and an EU region, and write throughput beyond what a single primary can handle." Candidate answers: (A) Cloud SQL with cross-region read replicas, (B) Cloud Spanner in a multi-region configuration. Which do you pick, and specifically why does Cloud SQL fail here — not just "Spanner is more scalable"?

Pick B, Spanner. The precise reason Cloud SQL fails: its HA model is a synchronous standby within one region — cross-region read replicas are asynchronous, so they can't give you strict transactional consistency across US and EU, and Cloud SQL has no built-in multi-primary write path to scale writes horizontally. Spanner's external consistency (TrueTime-backed) is designed exactly for "relational + globally strong-consistent + horizontally scalable writes" — that three-way combination is the tell.

Quiz — Session 3

Q1. Which service fits "global, strongly-consistent, horizontally-scalable relational database"?

A. Spanner's multi-region configuration is the only option offering horizontal write scaling with external consistency across regions. B is single-region only. C is NoSQL document, not relational/global-write. D is wide-column NoSQL, and multi-cluster defaults to eventual consistency — the opposite of what's asked.

Q2. A mission-critical GKE workload across zones needs one shared POSIX filesystem, read-write, by many pods. Best fit?

A. Regional/Enterprise Filestore tiers give strict consistency and cross-zone redundancy for a shared POSIX filesystem. B (Basic) has no zone redundancy — wrong for "mission-critical." C is single-VM block storage, not shareable across pods. D is an object store bolted onto a POSIX-like interface — it isn't built for true low-latency multi-writer NFS semantics.

Q3. A time-series IoT pipeline needs sustained high write throughput, key-value access, low-latency reads at scale. Best fit?

A. Bigtable's node-linear throughput and wide-column key-value model is purpose-built for exactly this — time-series/IoT is a textbook Bigtable use case. B, C, D are all functionally capable but the wrong shape: Firestore is operational/document, BigQuery is analytical (seconds latency), Spanner is relational OLTP, not tuned for this throughput pattern at this cost.

Q4. Analytics team wants ad-hoc SQL over 50TB of logs, no ops burden, pay only for data scanned. Right service and model?

A. "Pay only for data scanned, no ops burden" is literally BigQuery's on-demand pricing description. B, C, D are all provisioned-capacity models — you pay for the cluster/instance size regardless of query volume, which is the wrong shape for ad-hoc, bursty analytics.

Q5. In Cloud Storage, which of these is NOT strongly consistent?

A. IAM/ACL grants and revokes are explicitly eventually consistent (~1 minute, sometimes longer) per the official consistency docs. B, C, and D — read-after-write, listing, and read-after-delete — are all explicitly called out as strongly consistent.

Q6. Cloud SQL HA (regional instance) protects against which failure — and doesn't protect against which?

A. The regional-instance HA design is a primary + standby synchronously replicated across two zones in one region — it survives a zone outage, not a full region outage. B, C, D all misstate this; C in particular is the trap for anyone who assumes "HA" automatically means region-level.

Q7. What are Bigtable's default consistency behaviors for single-cluster vs multi-cluster instances?

A. Single-cluster Bigtable instances are strongly consistent; multi-cluster instances default to eventual consistency (configurable to read-your-writes or strong via app profile settings). B reverses this. C and D ignore that the behavior is configuration-dependent, not universal.

Q8. A finance case study needs ad-hoc historical trend analysis over 5 years of transaction logs, hundreds of analysts, SQL. Best fit, and why not Bigtable?

A. "Ad-hoc historical SQL analysis, many analysts" is the exact BigQuery shape — serverless OLAP built for scan-heavy queries across large datasets. B (Bigtable) has no SQL/joins and is tuned for low-latency serving, not ad-hoc analytics. C is operational document storage. D (Spanner) supports SQL but is priced and optimized for OLTP, not scan-heavy historical analysis — the wrong cost shape for this job.

Recap
  • Object/block/file map cleanly to S3/EBS/EFS — the trap is GCS's IAM propagation delay and Persistent Disk's zonal-by-default design
  • Cloud SQL vs Spanner is a region-vs-global and vertical-vs-horizontal question, not a "which is better" question
  • Firestore and Bigtable are both NoSQL but split on consistency defaults and access pattern (document/point-read vs high-throughput wide-column)
  • BigQuery is OLAP, not OLTP — seconds-latency, pay-per-scan, and the wrong answer whenever the scenario wants low-latency point lookups
  • Bigtable has no direct AWS 1:1 — that's a GCP-unique exam signal by itself
