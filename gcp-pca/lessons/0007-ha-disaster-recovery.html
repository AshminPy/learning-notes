GCP PCA — Session 7 of 10 (Day 2)

High availability & disaster recovery

This session covers Section 1.2 ("high availability and fail-over design," "backup and recovery" — part of the 25%-weighted design section) and Section 4.1 ("Disaster recovery" is an explicit bullet in the 15%-weighted process-analysis section). You already know DR patterns from AWS — backup & restore, pilot light, warm standby, multi-site active-active, and what RPO/RTO mean. This session is the GCP-native mapping: which service implements each pattern, and the exact numbers the exam expects you to know.

1. HA design: multi-zone vs multi-region

HA (surviving a failure with near-zero interruption) and DR (recovering after a bigger failure, possibly with some data loss and downtime) are different design problems. Start with HA:

ScopeWhat it protects againstHow GCP does it
Multi-zone (single region)Zone failureRegional Persistent Disk (synchronous replication across 2 zones), Cloud SQL HA (synchronous replication to a standby zone, ~60s failover), regional Managed Instance Groups, GKE regional clusters
Multi-regionFull region failureSpanner multi-region instance configs (99.999% SLA vs 99.99% regional), Cloud Storage dual-region/multi-region buckets, GKE Multi-cluster Gateway across regional clusters, global external Load Balancing

Cloud SQL HA is the direct analogue of RDS Multi-AZ: synchronous replication to each zone's persistent disk — "all writes made to the primary instance are replicated to disks in both zones before a transaction is reported as committed", with failover taking about 60 seconds via a shared static IP (Cloud SQL HA docs). That's multi-zone HA, not DR — it doesn't help if the whole region goes down.

AWS naming note: Google's own DR docs don't use "pilot light / warm standby / multi-site active-active" — they use a cold / warm / hot spectrum instead (DR planning guide). The exam may phrase questions either way. Treat AWS backup & restore ≈ GCP cold, AWS pilot light ≈ low end of GCP warm, AWS warm standby ≈ GCP warm/hot boundary, AWS multi-site active-active ≈ GCP hot. The table below uses the AWS 4-pattern names since that's your existing mental model.

3. Worked examples

Example A: Internal nightly batch reporting job. RPO of 24 hours is acceptable, RTO of a few hours is acceptable, small ops team, cost is the primary constraint.

Backup & restore. Loose RPO/RTO + cost-sensitive + small team is the exact signature for the cheapest pattern. Enable Cloud SQL automated backups with PITR (covers the 24h RPO easily), store any file exports in Nearline/Coldline Cloud Storage, and accept a multi-hour restore-and-reprovision RTO. Anything fancier here fails the Cost Optimization pillar for no benefit — no scenario keyword demands better.

Example B: Global fintech trading platform. RPO near-zero (seconds), RTO near-zero (seconds), users across US/EU/APAC, cannot tolerate downtime during a full regional outage.

Multi-site active-active. Near-zero RPO/RTO plus a global user base rules out every cheaper pattern — only continuously-running infrastructure in multiple regions gets you there. Use a Spanner multi-region instance configuration (built-in cross-region synchronous quorum writes, 99.999% SLA), GKE clusters in multiple regions behind Multi-cluster Gateway, and a global external load balancer routing to the nearest healthy region. This is expensive — that expense is the trade-off the scenario is explicitly asking for.
Exam trap: a multi-region or dual-region Cloud Storage bucket is not a DR strategy by itself. It gives you durable, geo-replicated object storage — it says nothing about your Compute Engine VMs, GKE workloads, or Cloud SQL instances. A scenario that says "we use a multi-region bucket, are we DR-ready?" is testing whether you notice that compute and database tiers still need their own DR plan (snapshots, cross-region replicas, standby instances). Storage replication is one building block, not the whole plan.

5. RPO/RTO as the decision input, not the definition

You already know what RPO/RTO mean. On this exam they function as a lookup key: read the two numbers (or their proxies — "cannot lose more than a few minutes of data," "must be back within the hour") and the tightest one usually determines the pattern band from the table in Section 2. A loose RPO/RTO with a tight budget always points toward backup & restore; a near-zero RPO/RTO with a global/mission-critical scenario always points toward multi-site active-active. The two middle patterns (pilot light, warm standby) are where most exam ambiguity lives — that's where "small standby already running" language in the scenario is the tell.

Try it — before reading the answer: "A hospital's patient-scheduling system can tolerate losing at most 5 minutes of data and must be back online within 10 minutes after a regional outage. It's mission-critical but only operates in one country." Which pattern, and why not the cheaper or more expensive neighbor?

Warm standby. 5-minute RPO / 10-minute RTO is too tight for pilot light (which typically needs "tens of minutes" to scale up from idle) but doesn't require the cost of full multi-site active-active — the single-country scope means you don't need simultaneous multi-region active traffic. A running-but-scaled-down standby (Cloud SQL HA + cross-region replica ready to promote, or a Spanner warm standby instance at minimum nodes) hits both numbers without paying for full active-active capacity.

Quiz — Session 7

Q1. Which Cloud Storage replication behavior gives automatic zone failover with zero RTO during a zonal outage?

A. Regional buckets replicate synchronously across zones within one region, giving automatic zero-RTO zone failover. B is asynchronous and cross-region, not the zonal case. C (turbo replication) is a dual-region feature for cross-region RPO, not zonal failover. D is a deletion/overwrite protection mechanism, unrelated to zone availability.

Q2. A finance team needs a Cloud SQL Enterprise Plus database recoverable to any second within roughly the last month, after an accidental table drop. Which feature provides this?

A. Enterprise Plus PITR supports up to 35 days of transaction-log retention (default 14, configurable), which covers a roughly-month-long recoverability window to a specific second. B only gives you the replica's current state, not a point-in-time within the past. C and D are Cloud Storage and Compute Engine mechanisms — they don't apply to Cloud SQL transaction recovery.

Q3. Why does restoring a Cloud Spanner database from a managed backup have a lower RTO than restoring from an export/import?

A. Spanner backup restore directly mounts the backup without copying the underlying data, so it's fast regardless of database size. B is the opposite of what happens (that's closer to how export/import behaves). C is not how export/import works — it isn't a validation-skipping shortcut, it's a slower Dataflow-based copy. D describes Persistent Disk snapshots, not Spanner backups.

Q4. Per Google's own DR planning guide, which pattern best suits historical, compliance-only data with a large tolerable RTO?

A. The guide names cold as appropriate for historical/compliance-oriented data with a large RTO — no need to pay for readiness you won't use in time. B and C are for tighter RTOs than this scenario needs. D is the trap from this lesson: storage replication alone isn't a DR pattern for a whole system.

Q5. What's true about Persistent Disk snapshot storage behavior by default?

A. Snapshots are incremental by default — after the first full snapshot, later ones store only changed blocks, reducing cost and storage. B describes non-incremental behavior, which isn't the default. C overstates the replication guarantee — it's not framed as synchronous. D is false: a globally-scoped snapshot can create a new disk in any region, which is exactly what makes it useful for cross-region DR.

Q6. Which statement about Cloud Storage Object Versioning is accurate?

A. Object Versioning keeps noncurrent object versions on overwrite/delete but explicitly does not protect against bucket deletion — Google's docs recommend Soft Delete for that. B is backwards. C is wrong — Google recommends using both, not one instead of the other. D overclaims; it's an object-recovery feature, not a total-loss-prevention guarantee.

Q7. In a Cloud Spanner multi-region instance configuration, how are writes handled across regions?

A. One region is the designated leader that holds the database's leader replicas; writes form a quorum coordinated through that leader region (Spanner automatically relocates the leader if that region fails). B is false — this is not independent multi-write active-active. C and D are wrong in the other direction: reads can be served locally from any region without requiring leader involvement, which is one of the main benefits of the multi-region config.

Q8. RPO near-zero, RTO near-zero, users spread across multiple continents, business cannot tolerate any downtime during a full regional outage. Which pattern fits?

A. Near-zero RPO/RTO plus a global, zero-downtime requirement is the signature scenario for multi-site active-active — only continuously-running multi-region infrastructure gets you there. B and D describe patterns with hours-scale RPO/RTO, far too slow. C (pilot light) still needs time to scale from idle, which violates the near-zero RTO requirement.

Recap
  • HA (multi-zone/multi-region) and DR (documented recovery plan with RPO/RTO targets) are different problems — HA alone isn't a DR plan.
  • 4 DR patterns, increasing cost/decreasing RPO+RTO: backup & restore → pilot light → warm standby → multi-site active-active. GCP's own docs use cold/warm/hot instead of these 4 names — know both.
  • Cloud SQL PITR: 7 days default (Enterprise, max 7) vs 14 days default (Enterprise Plus, max 35). Spanner PITR: 7 days max, separate from backups (max 1 year retention, direct-mount restore).
  • Cloud Storage: regional = sync/zone-level, dual-region/multi-region = async/cross-region (dual-region can add turbo replication for a 15-minute RPO). Object Versioning ≠ bucket protection — that's Soft Delete's job.
  • Exam trap: a replicated storage bucket is not, by itself, a DR strategy for your compute or database tier.
