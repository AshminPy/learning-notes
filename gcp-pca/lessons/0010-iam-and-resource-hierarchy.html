GCP PCA — Lesson 10 of 28

IAM basics and resource hierarchy

IAM answers one question: who can do what to which resource. GCP organizes all resources into a tree, and permissions flow down that tree.

Simple example: think of a company org chart. The CEO's rules apply to everyone below. A department head's rules apply to their department only. GCP's resource tree works the same way — rules set higher up apply to everything underneath.

IAM: who can do what

An IAM policy binds a principal (a person, group, or service account) to a role (a bundle of permissions) on a resource. Three kinds of roles:

  • Basic roles — Owner, Editor, Viewer. Broad, old-style. Avoid unless nothing else fits.
  • Predefined roles — made by Google, scoped to one service. The usual right answer.
  • Custom roles — you pick the exact permissions. Only when predefined roles are too broad.

Resource hierarchy

GCP resources sit in a strict tree: Organization → Folder → Project → Resource. A permission granted at a higher level applies to everything below it. Grant a role at the Organization, and it reaches every folder, project, and resource underneath — automatically.

Exam trap: permissions only ever ADD as they flow down — a project can never take away a permission granted at the Organization above it. If a scenario needs to block one project from an org-wide grant, "just don't assign the role there" doesn't work — you need a deny policy, or a different hierarchy.

Try it — before looking below

Q1. A role is granted at the Organization level. Does it reach a project three levels down?

A. The hierarchy is Organization → Folder → Project → Resource, and grants flow down to everything underneath.

Q2. A scenario needs "least privilege, low ongoing maintenance." Which role type usually wins?

B. Predefined roles are scoped and maintained by Google. Basic roles are too broad; custom roles need someone to keep updating them by hand.

Q3. A project needs to block a permission that was granted at the Organization level above it. Can a project-level policy remove that permission?

B. IAM policy inheritance is a one-way union going down. A project can add permissions, never subtract ones granted higher up — a deny policy is the tool for that.

Source

cloud.google.com/iam/docs/roles-overview and cloud.google.com/iam/docs/resource-hierarchy-access-control

Recap
  • IAM = who (principal) gets what (role) on which resource.
  • Resource hierarchy: Organization → Folder → Project → Resource — permissions flow down.
  • Lower levels can only add permissions, never remove ones from above — use a deny policy to block.
