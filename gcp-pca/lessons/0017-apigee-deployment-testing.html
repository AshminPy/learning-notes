Apigee, deployment & testing tooling

Section 5, "Managing implementation," isn't about which service to pick (that's Section 1) — it's about advising the team actually shipping it: how APIs get exposed, tested, and deployed safely.

Simple example: a backend service and an API are not the same thing. The backend is the kitchen. Apigee is the front counter — it's what decides who gets served, how fast, and what they're charged, without the kitchen knowing any of that happened.

Apigee — API management, not API hosting

Apigee sits in front of backend APIs (Cloud Run, GKE, on-prem, anything) and adds what raw backends don't have: authentication, rate limiting/quotas, analytics, a developer portal, and monetization. It doesn't run your code — it manages access to it.

  • API proxy — the policy layer Apigee actually executes (auth checks, quota, transformation) in front of your real backend.
  • Quotas & rate limiting — protect the backend from being overwhelmed by one noisy consumer.
  • Developer portal — self-service API keys and docs for external/partner developers.
Exam trap: Apigee is not a load balancer and not a compute platform. If a scenario needs API monetization, quotas per partner, or a developer portal, that's Apigee. If it just needs to route traffic to healthy backends, that's Cloud Load Balancing (Lesson 9).

CI/CD: Cloud Build & Cloud Deploy

  • Cloud Build — runs your build/test steps (CI). Triggered by a commit, produces an artifact (container image, package).
  • Cloud Deploy — takes that artifact and progressively rolls it out (CD) to Cloud Run, GKE, or Anthos — supports canary and other progressive-delivery strategies, with an approval gate between stages.

Testing frameworks the exam expects you to recognize by category, not by product name: unit (one function, in isolation), integration (multiple components together), load (does it hold up under real traffic). Cloud Build runs all three as pipeline stages — it doesn't care which testing library you use.

Gemini Cloud Assist

An AI assistant built into the Cloud Console — suggests architecture improvements, helps troubleshoot, and can explain a resource's config in plain language. The exam guide names it under both design (1.2) and implementation advising (5.1) — treat it as a helper woven through the console, not a separate product you provision.

Try it — before looking below

Q1. A partner team needs their own API key, a request quota, and self-serve documentation to call your backend. Apigee, or Cloud Load Balancing?

Apigee. Quotas, developer self-service, and API keys are API-management concerns — Cloud Load Balancing only routes traffic to healthy backends, it has no concept of "who" is calling.

Quiz — Lesson 17

Q1. What's the difference between what Cloud Build and Cloud Deploy each do?

A. Cloud Build produces a tested artifact. Cloud Deploy takes that artifact and rolls it out progressively, with approval gates between stages.

Q2. A scenario says a service needs monetized, metered access for external developers. What's the tell that this is an Apigee question, not a networking question?

A. Not every API question is an Apigee question — plenty of API traffic just needs a load balancer. The tell is business-facing concerns: billing, quotas per consumer, developer onboarding.

Recap
  • Apigee manages access to APIs (auth, quota, monetization, portal) — it doesn't host the backend.
  • Cloud Build = CI. Cloud Deploy = CD, with progressive rollout and approval gates.
  • Exam trap: an API-shaped question isn't automatically an Apigee question — look for quota/monetization/developer-facing language.
