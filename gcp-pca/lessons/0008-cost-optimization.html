GCP PCA — Session 8 of 10 (Day 2)

Cost optimization: CUDs, SUDs, Spot VMs, lifecycle rules, and rightsizing

This is Section 4.2 (Analyzing and optimizing business processes, 15%) — the exam guide lists "cost optimization/resource optimization (CapEx/OpEx)" as an explicit bullet, and it also shows up under Section 1.1's business requirements. It's also the WAF Cost Optimization pillar from Session 1: maximize business value per dollar, not minimize the invoice. Every mechanism below is a lever you pick based on workload shape, not a universal "turn this on."

1. Committed Use Discounts (CUDs) — the RI/Savings Plan analogue

Same idea as AWS Reserved Instances / Savings Plans: commit, get a discount, lose flexibility. GCP splits this into two purchase models — verified against the official CUD overview:

  • Resource-based CUDs — like an AWS RI: you commit to specific vCPU/memory/GPU/Local SSD amounts in a specific region and machine family. Highest discount, least flexible. Up to 55% off (1yr/3yr blended) for standard machine families, up to 70% for memory-optimized on a 3-year term. Also covers sole-tenant nodes and OS licenses (SLES up to 79%, RHEL up to 20%).
  • Spend-based (Compute Flexible) CUDs — like an AWS Savings Plan: commit to a minimum $/hour spend, GCP applies it across Compute Engine, GKE, and Cloud Run automatically, no region/machine-family lock-in. Verified exact rates from the same doc: general-purpose/compute-optimized 28% (1yr) / 46% (3yr); memory-optimized (M1–M4) has no 1yr option, 63% (3yr); H3/H4D 17%/38%; C4N 28%/54%.

Both also apply to eligible non-Compute services (BigQuery, Spanner, Bigtable, Cloud SQL, AlloyDB, Dataflow, Firestore, Memorystore) with service-specific spend-based commitments — same spend-commit mechanic, different rate cards per service.

2. Sustained Use Discounts (SUDs) — verify before you assume

Do not assume this is gone. SUDs are still active for Compute Engine, per the official SUD docs — but the eligible machine families are narrower than they used to be, and this is exam-trap territory if you're working from stale material.

SUD applies automatically (no commitment, no CapEx decision) when a resource runs >25% of a billing month and isn't already receiving a CUD or other discount:

  • Up to 30% max: N1, M1/M2 memory-optimized, f1-micro/g1-small, and GPUs attached to N1 instances.
  • Up to 20% max: N2 and N2D general-purpose, C2 compute-optimized.
  • Excluded: App Engine, Dataflow, anything already covered by a CUD, and newer machine series not listed above.

Discount scales in steps as usage climbs past 25/50/75% of the month, and GCP auto-aggregates usage across instances of the same family/region to hit the threshold faster — you don't manage this, it's automatic OpEx savings on variable/always-on workloads that don't justify a CUD commitment.

3. Spot VMs — the cost lever with real interruption risk

AWS analogue: Spot Instances. GCP's current terms, verified from the official Spot VM docs:

  • Discount: up to 91% off on-demand (varies by machine type/region/real-time capacity — not fixed like a CUD).
  • Preemption notice: default is a short/no dedicated grace window; you can configure a longer notice window (up to 120s, a newer option) so your shutdown script has time to checkpoint.
  • No max runtime cap — this is the key difference from the legacy "preemptible VM" product, which was hard-capped at 24 hours. Spot VMs can run indefinitely until Google reclaims the capacity.
  • Best fit: stateless, fault-tolerant, checkpointable workloads — batch/ML training, CI/CD runners, GKE node pools for non-critical workloads, big-data/Spark. Not for anything needing continuous uptime (databases, stateful interactive services).

4. Autoscaling as a cost lever, not just a reliability lever

You already run this daily (GKE Autopilot, HPA). On the exam, remember to frame autoscaling as OpEx cost control: it converts a "provision for peak, pay 24/7" CapEx-shaped cost into "pay only for what's actually running." Scale-to-zero (Cloud Run, GKE Autopilot with zero-pod scaling) is the extreme version — no traffic, no compute spend at all. When a scenario says "spiky/unpredictable traffic + minimize cost," autoscaling + managed serverless usually beats any fixed-capacity CUD-backed fleet.

5. Cloud Storage lifecycle rules

Verified from the official lifecycle management docs. Storage classes, cheapest access pattern to most restrictive: Standard → Nearline (accessed < 1×/month) → Coldline (< 1×/quarter) → Archive (long-term, rare access). Lifecycle rules automate the downgrade based on object age or other conditions, using SetStorageClass, which changes the class without rewriting the object (no retrieval/egress fee triggered by the transition itself).

Minimum storage durations apply per class — delete or transition out early and you pay an early-deletion fee for the remaining minimum. Coldline's minimum is 90 days; check current per-class minimums on the pricing page before an exam-adjacent design decision, since these are exactly the kind of number a distractor answer gets wrong on purpose.

6. Rightsizing recommendations

Compute Engine's built-in recommender watches CPU and memory utilization (via Cloud Monitoring, more precise with the Ops Agent installed) over roughly the trailing 8 days, then suggests a smaller or larger machine type — or a custom shape — per instance. Recommendations appear within 24 hours of instance creation and refresh throughout the day; GCP suppresses ones below $10/month estimated savings. Source: official sizing recommendations doc. This is a zero-commitment, always-on OpEx optimization — pairs naturally with CUDs (rightsize first, then commit to the rightsized baseline).

Exam trap: the WAF Cost Optimization pillar is explicitly defined as "maximize the business value of your investment," not "spend the least money." A question that offers "cheapest option" as bait — e.g. an all-Spot-VM fleet for a workload that also has a reliability requirement stated in the scenario — is testing whether you'll pick cheapest over best-value. If the scenario states any uptime/SLA constraint alongside a cost constraint, the correct answer respects both; a pure-Spot or pure-preemptible design that ignores the SLA line is a trap answer even though it's the cheapest one on the page.

Try it — before reading the answer

Scenario: "A team runs a nightly batch ETL job (4 hours, can restart from checkpoint if interrupted) and a customer-facing API that must stay up 24/7 with predictable steady traffic. They want to minimize cost without risking the API's SLA." Which lever goes where, and why is putting Spot VMs under the API the wrong answer even though it's the cheapest option?

ETL job → Spot VMs: it's checkpointable and fault-tolerant, exactly the profile Spot is built for, and the interruption risk costs nothing but a retry. API → resource-based or spend-based CUD (plus SUD as a free bonus on top of any non-committed baseline capacity): steady predictable 24/7 traffic is the textbook CUD profile, and the SLA constraint rules out Spot entirely — an evicted API instance mid-request is a reliability failure, not just a retry. Putting Spot under the API optimizes for "cheapest" while violating the stated SLA constraint — exactly the WAF Cost-pillar trap above: cheapest is not automatically best value when reliability is an explicit requirement.

Quiz — Session 8

Q1. A workload runs 24/7 with steady, predictable resource needs for the next 3 years. Which lever gives the deepest discount?

A. A 3-year resource-based CUD reaches up to 55% (70% for memory-optimized families) — the deepest discount available for genuinely predictable, steady-state usage. B trades away reliability for a discount that isn't even guaranteed to beat a CUD. C caps out lower (20–30%) and doesn't stack as well once a CUD is present. D reduces spend but doesn't address discount rate at all.

Q2. True or false: sustained use discounts have been fully deprecated across all Compute Engine machine families.

A. Verified against current docs: SUDs are still active for N1, M1/M2, f1-micro/g1-small (up to 30%) and N2/N2D/C2 (up to 20%). B is wrong — the program continues. C is wrong — coverage is narrower than "every family," e.g. newer machine series aren't listed. D is wrong — Spot is a separate, unrelated program.

Q3. What is the maximum published discount range for Spot VMs versus on-demand pricing?

A. Official docs state up to 91% off, varying by machine type, region, and real-time capacity. B and D understate the range — those numbers describe SUD and rough legacy preemptible territory, not Spot. C is wrong because Spot pricing is dynamic, never a fixed rate.

Q4. Which best describes the key operational difference between Spot VMs and the legacy preemptible VM product?

A. Legacy preemptible VMs were hard-capped at 24 hours; Spot VMs have no max runtime and only end on reclaim. B is backwards — Spot is generally cheaper/more flexible pricing. C is backwards — stateless batch is Spot's ideal use case. D is false — Spot has zero commitment, it's pure on-demand pricing with a reclaim risk.

Q5. An object in Cloud Storage needs to move automatically from Standard to Coldline after 90 days without being re-uploaded or incurring a rewrite. Which mechanism does this?

A. Object Lifecycle Management with a SetStorageClass action transitions the object's class automatically based on age, without rewriting the object or triggering retrieval fees for the transition itself. B defeats the point of automation. C — CUDs don't apply to Cloud Storage classes this way. D changes redundancy, not storage class/cost tier.

Q6. A scenario states a workload has an explicit uptime SLA alongside a request to minimize cost. Which answer reflects the correct WAF Cost Optimization interpretation?

A. The pillar is defined as maximizing business value per dollar, not minimizing spend at any cost — an SLA is a hard constraint the "cheapest" answer must still satisfy. B is the classic trap answer. C and D both discard a stated requirement, which the exam never rewards.

Q7. Which committed use discount type lets spend automatically apply across Compute Engine, GKE, and Cloud Run without locking a specific machine family or region?

A. Spend-based (Compute Flexible) CUDs commit to a $/hour spend level and apply automatically across Compute Engine, GKE, and Cloud Run — no region or machine-family lock-in, unlike resource-based (B). C is wrong — SUD is Compute Engine-specific and automatic, not a purchased commitment. D isn't a real product name.

Q8. What signal does the Compute Engine rightsizing recommender primarily use to suggest a smaller or larger machine type?

A. The recommender watches CPU and memory utilization (roughly the trailing 8 days via Cloud Monitoring) and suggests resizing when usage is consistently low or high. B, C, and D aren't signals the recommender is documented to use.

Recap
  • CUD = commitment for discount (resource-based up to 55–70%, spend-based/flexible 17–63%) — the AWS RI/Savings Plan analogue
  • SUD is still active (verified, not deprecated) but narrower than it used to be: N1/M1/M2/f1-micro/g1-small up to 30%, N2/N2D/C2 up to 20%, automatic, no commitment
  • Spot VMs: up to 91% off, no max runtime (unlike old 24h-capped preemptible), real interruption risk — fault-tolerant/checkpointable workloads only
  • Autoscaling, lifecycle rules, and rightsizing are all zero/low-commitment OpEx levers — use them before reaching for a commitment
  • WAF Cost pillar = value per dollar, not "cheapest" — an SLA or compliance constraint in the scenario always overrides a cheaper-but-riskier option
