GCP PCA — Lesson 25 of 27

Business requirements, integration & workload disposition

Every lesson so far started from "here's the technical requirement, pick the service." This lesson is one step earlier — before you can pick anything, you have to translate a business conversation into requirements a design can actually satisfy.

Simple example: "make the app faster" is not a requirement — it's a feeling. "P95 latency under 200ms for the checkout API" is a requirement. Half of this lesson is that translation step.

Functional vs. non-functional requirements

  • Functional — what the system does. "Users can check out with a saved card." "Orders sync to the warehouse system within 5 minutes."
  • Non-functional — how well it does it. Performance, availability, security, scalability, cost — the "ilities." A design can be functionally perfect and still fail the exam's "best answer" test because it ignores a stated non-functional constraint (the WAF pillars from Lesson 2 are exactly this).
Exam trap: a scenario listing "must integrate with the existing CRM" is a functional requirement. A scenario listing "must survive a zone failure" is non-functional. Confusing the two means you eliminate the wrong answers in Lesson 2's elimination algorithm.

Integration patterns & moving data between systems

Once you know what the system must do, you need a pattern for how it talks to everything else:

  • Synchronous request/response — REST/gRPC APIs. Caller waits for an answer. Simple, but couples the two systems' uptime together.
  • Asynchronous messaging — Pub/Sub (Lesson 16). Caller fires and moves on; decouples uptime and load between systems.
  • Bulk/batch data movement — Storage Transfer Service (scheduled bulk copy into Cloud Storage from another cloud or on-prem), Datastream (change-data-capture replication from a live database), Dataflow (streaming/batch ETL pipelines).

The exam question is usually "sync or async," then "batch or streaming" — read the latency and coupling tolerance in the scenario before picking.

Workload disposition: build, buy, modify, or deprecate

Before Lesson 15's rehost/replatform/refactor decision (how to move something), there's an earlier decision: whether to move it at all.

  • Build — no adequate solution exists; build it cloud-native.
  • Buy — a SaaS/managed product already solves this; building your own is wasted effort (e.g., don't build a CRM).
  • Modify — the existing system is close, needs targeted change (this is where Lesson 15's replatform applies).
  • Deprecate — the workload no longer earns its keep; retire it instead of migrating it.
Exam trap: "migrate everything" is rarely the best answer when a scenario mentions a legacy system nobody uses anymore. Deprecating it is a valid, sometimes correct, disposition — migration isn't automatically the right move just because the case study mentions a system exists.

Try it — before looking below

Q1. A case study says "the internal timesheet tool has had no updates requested in 3 years and usage has dropped 90%." What disposition fits, and why isn't migrating it automatically correct?

Deprecate. Low, declining usage and no active development are signals the workload isn't earning its keep — migrating dead weight into the cloud just moves the cost, it doesn't fix the underlying problem. Not every existing system deserves a destination.

Quiz — Lesson 25

Q1. "The new service must integrate with the existing on-prem inventory database, with changes reflected in near-real time." Which integration pattern fits best?

A. "Near-real time" plus "changes reflected" is a change-data-capture signal — Datastream streams DB changes as they happen. Storage Transfer Service is for scheduled bulk moves, not continuous replication.

Q2. A requirement says "the checkout flow must remain available during a single-zone outage." Functional or non-functional?

A. Availability under failure is a quality attribute, not a feature — classic non-functional requirement.

Recap
  • Functional = what it does. Non-functional = how well it does it under load, failure, and constraint.
  • Integration choice is sync-vs-async first, then batch-vs-streaming — read latency/coupling tolerance in the scenario.
  • Workload disposition (build/buy/modify/deprecate) is a decision that comes before rehost/replatform/refactor, not the same decision.
  • A low-usage, unmaintained system is a deprecate signal, not an automatic migration candidate.
