GCP PCA — Session 2 of 10 (Day 1)

Core compute: Compute Engine, GKE, Cloud Run, App Engine, Cloud Run functions

This is Section 1.3 (mapping compute needs to platform products) and Section 2.3 (configuring compute systems) of the exam guide — together a slice of the 25%+17.5% that Design/Plan and Provisioning carry. You already run GKE Autopilot daily; the gap isn't "what is a container platform," it's which of five compute products the exam wants for a given constraint sentence, and the traps built to catch people who default to the platform they already know.

1. Compute Engine — IaaS VMs

AWS analogue: EC2 (on-demand/reserved), Spot VM ≈ Spot Instance.

  • Use when: you need OS/kernel-level control, licensed software with per-core licensing, sole-tenant/dedicated-hardware compliance, long-running stateful processes, or GPU/TPU attachment outside a managed platform.
  • Don't use when: the scenario is a stateless HTTP service with bursty traffic and a small ops team — self-managed patch/scale/HA is the Operational Excellence violation the exam is testing for.
  • Advantages: full control; custom machine types let you pick exact vCPU/memory outside predefined shapes (N and E series only, 5% premium over predefined on-demand/commitment pricing); live migration; sustained-use and committed-use discounts.
  • Limitations: you own OS patching, scaling logic (Managed Instance Groups), and HA design; no automatic scale-to-zero.
  • Cost shape: per-second billing on standard VMs; Spot VMs give up to 91% discount, no minimum or maximum runtime by default, and either 0-second (default) or 120-second (preview) preemption notice with a best-effort ~30s shutdown window. (Spot VM docs, custom machine types docs)
Exam trap: the reflex "always pick managed" is wrong when the scenario explicitly names a constraint only Compute Engine solves — custom kernel modules, per-core licensed software, or a compliance rule requiring dedicated/sole-tenant hardware. Don't over-apply the "less ops burden wins" default when the scenario states a hard technical requirement.

2. GKE — how the exam actually tests it

You know GKE operationally. What the exam tests is the decision, not the mechanics: when GKE is right, when Autopilot vs Standard is right, and — the trap most people miss — when GKE is the technically-valid but wrong answer.

  • GKE is the right answer when: the workload genuinely needs Kubernetes primitives — StatefulSets, DaemonSets, sidecars/service mesh, custom schedulers, CRDs/operators — or needs portability across clouds, or is a mixed batch+online multi-service platform.
  • GKE is the wrong answer when: the scenario says "small ops team," "simple stateless HTTP API," "event-driven," or "infrequent/bursty traffic" with no mention of K8s-specific requirements. Even Autopilot carries more conceptual and configuration surface than Cloud Run for a single stateless service — a classic "technically correct, wrong pillar" distractor.
  • Autopilot vs Standard: Autopilot — Google manages node lifecycle, security patching, and Pod bin-packing; you pay per Pod resource request. Standard — you provision and pay for nodes directly, whether or not Pods are using them. Exam default bias is Autopilot unless the scenario needs node-level control (DaemonSets needing host access, specific node OS/GPU driver requirements, or Autopilot's restricted configurations). (Autopilot overview)
  • Cost shape: a flat cluster management fee of $0.10/cluster/hour applies to every GKE cluster regardless of mode, size, or topology; the GKE free tier gives $74.40/month in credit, covering one zonal Standard or Autopilot cluster's management fee. On top of that: Autopilot bills per Pod resource request, Standard bills per provisioned node. (GKE pricing)
Exam trap: Autopilot is Google's recommended default and reads as "fully managed," which tempts you to pick it for everything. But if the scenario is a single stateless HTTP microservice with no K8s-specific requirement, Cloud Run is the correct answer — it has zero cluster concept at all, not just a managed one. The tell for "GKE is actually required": StatefulSet, DaemonSet, CRD, service mesh, or multi-cloud portability language in the scenario.

3. Cloud Run (service) — managed serverless containers

AWS analogue: App Runner / ECS Fargate.

  • Use when: stateless HTTP(S)/gRPC microservices, bursty/unpredictable traffic, want true scale-to-zero, want to bring any language or binary in a container (unlike Cloud Run functions).
  • Don't use when: the workload needs persistent local disk state, full K8s orchestration primitives, or processing longer than the request timeout ceiling — use Cloud Run Jobs or GKE instead.
  • Advantages: scale-to-zero by default; request timeout up to 60 minutes; concurrency configurable up to 1000 requests per instance (default is 80 for console deployments, or 80×vCPU for gcloud/Terraform deployments) — tuning concurrency directly trades instance count against cost. (concurrency docs)
  • Limitations: 60-minute hard timeout ceiling; stateless only; cold starts possible on scale-from-zero — Cloud Run queues pending requests up to 3.5× the average container startup time (or 10 seconds, whichever is greater), and can keep instances idle up to 15 minutes (10 for GPU) to reduce repeat cold starts. (autoscaling docs)
  • Cost shape: two billing models. Request-based (default): CPU/memory are only allocated while a request is being processed — cheapest for spiky traffic, but CPU throttles after the response is sent. Instance-based: CPU stays allocated for the instance's full lifecycle, enabling background/async work after the response returns, priced for steady traffic. (CPU allocation docs)
Exam trap: request-based billing (the default) silently throttles CPU the moment the HTTP response is sent. If a scenario needs background processing after the response — async logging, a monitoring agent, deferred work — the default setting quietly breaks it. The fix is explicitly switching to instance-based billing, not switching platforms.

4. App Engine — the original PaaS

AWS analogue: Elastic Beanstalk.

  • Standard environment: sandboxed runtime, cold start in seconds, true scale-to-zero, restricted set of supported language runtimes/versions.
  • Flexible environment: runs your Docker container on Compute Engine-backed VMs, cold start in minutes, no scale-to-zero — minimum 1 instance always running, supports custom runtimes/binaries. (App Engine environments docs)
  • Use when: a legacy monolithic app is already on App Engine, or you want PaaS-style deploy simplicity without touching containers or Kubernetes (Standard specifically, for scale-to-zero + low idle cost).
  • Don't use when: it's a greenfield project — Google's own current guidance steers new stateless HTTP workloads to Cloud Run first; or the scenario wants a containerized app that also needs to scale to zero (Flexible can't do both).
  • Advantages: fully managed, built-in versioning and traffic-splitting, minimal deploy config.
  • Limitations: Standard's sandbox restricts runtime versions and outbound behavior; Flexible loses scale-to-zero and has minutes-scale deploy/cold-start latency.
  • Cost shape: Standard can hit near-zero cost when idle (billed per instance-hour only while running); Flexible is billed continuously for at least one always-on VM-backed instance.
Exam trap: App Engine Flexible looks like the "managed, container-friendly" answer because it runs Docker — but it cannot scale to zero. If the scenario says "minimize cost for a rarely-used containerized app," Cloud Run is correct, not App Engine Flexible. This exact pairing is a common distractor.

5. Cloud Run functions (formerly Cloud Functions)

Naming, verified: Google renamed Cloud Functions to Cloud Run functions on August 21, 2024, unifying the underlying infrastructure with Cloud Run. Existing Cloud Functions 2nd gen deployments, APIs, gcloud commands, and Terraform continue working unchanged under the new name; 1st gen still exists as "Cloud Run functions (1st gen)." If you see "Cloud Functions" in an older question bank, it's the same product. (official rename announcement)

AWS analogue: Lambda.

  • Use when: single-purpose event-driven code triggered by Cloud Storage, Pub/Sub, Firestore, or any of 90+ Eventarc sources via Cloud Audit Logs; glue code; you want to deploy from source with no Dockerfile.
  • Don't use when: the workload is multi-step/stateful, needs custom system binaries (Cloud Run service allows any container; functions are source-code deploys with a more restricted execution environment), or an event-triggered run needs more than 9 minutes.
  • Advantages: no container build step; tightest event-trigger integration in the platform; up to 16 GiB RAM / 4 vCPU per instance; up to 1000 concurrent requests per instance.
  • Limitations: HTTP-triggered functions get up to 60-minute timeout, but event-triggered functions are capped at 9 minutes — a hard ceiling, not tunable away. (Cloud Run functions vs Cloud Run comparison)
  • Cost shape: same pay-per-use serverless pricing family as Cloud Run — billed per invocation plus compute time.
Exam trap: if a scenario needs more than 9 minutes of processing per event trigger, plain Cloud Run functions is the wrong answer — even though "it's event-driven, so use functions" sounds right. The correct fix is an HTTP-triggered function (60 min) or a full Cloud Run service/job, not tuning the function's timeout, because event-triggered timeout isn't configurable past 9 minutes.

Try it — before reading the answer

Scenario (EHR Healthcare-style): a small script runs whenever a new file lands in a Cloud Storage bucket, parses it, and finishes in under a minute. No other steps, no state kept between runs, small team. Which compute product needs the least setup, and which product from today's lesson would be over-engineering here?

Least setup: Cloud Run functions — it deploys straight from source, has a native Cloud Storage/Eventarc trigger, and a sub-minute run is nowhere near the 9-minute event-triggered ceiling. Over-engineering: GKE (even Autopilot) — there's no multi-service orchestration need, no StatefulSet/DaemonSet requirement, just single-event glue code. Cloud Run (service) would also work but adds a container-build step this scenario doesn't need.

Quiz — Session 2

Q1. How many concurrent requests can a single Cloud Run instance be configured to handle at maximum?

A. Cloud Run lets you configure concurrency up to 1000 requests per instance; the default is 80 (console) or 80×vCPU (gcloud/Terraform). B/C/D are plausible-sounding numbers but not the documented ceiling — don't guess on exact limits, they're memorizable facts, not judgment calls.

Q2. By default, what happens to a Cloud Run service that receives no traffic?

A. Scale-to-zero is Cloud Run's default behavior — it's the single biggest cost-shape difference from GKE Standard and App Engine Flexible, both of which keep something running even at zero traffic. B/C/D describe behaviors that don't match any documented default.

Q3. GKE Autopilot bills you primarily based on which unit of consumption?

A. Autopilot uses a Pod-based billing model — you pay for what your Pods actually request. Standard mode is B (you provision and pay for nodes directly, whether or not Pods use them) — this is the single fact that distinguishes the two modes' cost shape.

Q4. Which statement about the GKE cluster management fee is accurate?

A. The flat $0.10/cluster/hour management fee applies to every GKE cluster regardless of mode, size, or topology — a common trap is assuming Autopilot has a fee Standard doesn't, or vice versa. One free zonal Standard or Autopilot cluster/month is covered by the $74.40 monthly free-tier credit.

Q5. How does a Spot VM differ from the older preemptible VM regarding runtime?

A. Spot VMs have no minimum or maximum runtime unless you set one yourself — the older preemptible VM had a hard 24-hour cap. B/C/D describe the kind of fixed limit Spot VMs specifically removed; don't carry the old preemptible mental model forward.

Q6. What is the current official name for the former Cloud Functions product?

A. Google renamed Cloud Functions to Cloud Run functions on August 21, 2024, unifying the infra with Cloud Run. B/C/D are invented names — if the exam question bank hasn't been refreshed you may still see "Cloud Functions," but treat it as the same product.

Q7. Which App Engine environment supports scaling all the way down to zero instances?

A. Standard scales to zero; Flexible always keeps a minimum of 1 instance running because it's VM-backed. This is the exact distinction behind the "App Engine Flexible looks managed but can't scale to zero" trap earlier in this lesson.

Q8. Scenario: small team, stateless HTTP API, bursty traffic, must scale to zero to save cost, no Kubernetes-specific requirement stated. Which compute option best fits without extra justification?

A. No K8s-specific requirement (no StatefulSet/DaemonSet/service mesh/portability language) means GKE — even Autopilot — is more platform than the scenario needs; Cloud Run gives scale-to-zero with zero cluster concept. B and C fail the scale-to-zero requirement outright (Standard's nodes and Compute Engine VMs don't disappear at zero traffic without extra automation). D is the classic distractor: "managed" but still the wrong abstraction level for a single stateless service.

Recap
  • Compute Engine = full control, custom machine types, Spot VMs up to 91% off, no scale-to-zero — right answer only when a stated constraint needs VM-level control.
  • GKE = right when the scenario needs K8s primitives or portability; wrong (even Autopilot) when it's just "small team, stateless HTTP, minimal ops" — that's Cloud Run's job. Both modes pay the same $0.10/cluster/hr fee; Autopilot bills per Pod request, Standard bills per node.
  • Cloud Run = scale-to-zero by default, 60-min timeout, concurrency up to 1000/instance; default request-based billing throttles CPU after the response — switch to instance-based for background work.
  • App Engine Flexible cannot scale to zero (min 1 instance); only Standard can — don't confuse "container-friendly" with "scales to zero."
  • Cloud Functions is now officially Cloud Run functions (renamed Aug 2024); event-triggered functions cap at 9 min, HTTP-triggered at 60 min.
